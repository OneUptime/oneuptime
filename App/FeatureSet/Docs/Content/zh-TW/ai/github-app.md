# 從 GitHub 操作 OneUptime

OneUptime GitHub App 不只是通往您程式碼的一條連線——您可以在儲存庫裡直接跟它對話，它也會就地把事情做完。

在 issue 上提及它，它會開一個拉取請求。在拉取請求上提及它，它會修改那個分支，或是審查那份 diff。替 issue 加上標籤，它就會接手這個 issue。它產出的一切，都是留給人審閱的拉取請求或審查意見：**它從不合併任何東西，也從不核准拉取請求。**

```text
@oneuptime implement this                          →  一個會關閉該 issue 的拉取請求
@oneuptime revise this — use exponential backoff   →  推送到這個拉取請求分支上的新 commit
@oneuptime review                                  →  張貼在這個拉取請求上的程式碼審查
```

> 請把 `@oneuptime` 換成您自己 App 的代號（handle）。在 OneUptime Cloud 上是 `@oneuptime`。在自架執行個體上，則是您替 GitHub App 取的名稱，全部轉成小寫並把空格換成連字號——名為「Acme AI」的 App 要用 `@acme-ai` 提及。如果提及之後毫無反應，這是第一個該檢查的地方。

## 開始之前

- 該儲存庫必須透過 GitHub App **連接到某個 OneUptime 專案**。設定方式請參閱 [GitHub 整合（自架）](/docs/self-hosted/github-integration)；在 OneUptime Cloud 上則可從 **專案設定 → 程式碼儲存庫** 連接。
- 必須有一台**具備「Runs AI Code Fixes」能力的 Runner** 在線上——就是執行 [AI 修復任務](/docs/ai/ai-agent) 的那同一台 Runner。少了它，指令會先被接受，30 分鐘後才以「沒有任何代理程式接手」的訊息失敗。
- GitHub App 必須具備 **Issues: Read & write** 權限，並訂閱[需要訂閱哪些事件](#需要訂閱哪些事件)一節列出的 webhook 事件。

## 有哪些指令

每個指令都以提及這個 App 作為開頭。提及可以出現在留言的任何位置，寫在它後面的內容都會被當成您的需求一併傳過去。

### 在拉取請求上

| 指令 | 會發生什麼事 |
| --- | --- |
| `@oneuptime review` | 複製該分支，讀取變更過的程式碼**以及它周圍的程式碼**，然後以留言張貼一則審查。不會改動任何東西。 |
| `@oneuptime revise this — <what you want changed>` | 複製這個拉取請求自己的分支，做出改動，並把新的 commit 推送到同一個分支。絕不會另開第二個拉取請求。 |

提及之後若寫的不是可辨識的指令，就會被當成一次修改需求——因為那幾乎總是您真正的意思：

```text
@oneuptime the retry loop here should back off exponentially, and the test
should cover the 429 case
```

### 在 issue 上

| 指令 | 會發生什麼事 |
| --- | --- |
| `@oneuptime implement this` | 處理這個 issue，並開一個會關閉它的拉取請求。 |
| `@oneuptime <anything else>` | 一樣，並把您寫的內容當成額外的指示。 |

您也可以**完全不留言**就把 issue 交給這個 App：

- **加上觸發標籤。** 替 issue 加上該儲存庫的觸發標籤（預設是 `oneuptime`），會啟動同一件工作。這是從 GitHub 介面指派工作最可靠的方式。
- **把 issue 指派給 App 的 bot 使用者**，前提是您的儲存庫允許。GitHub 並不是在所有地方都允許 App 當被指派人，這正是標籤存在的原因；如果指派沒有反應，請改用標籤。

### 任何地方

| 指令 | 會發生什麼事 |
| --- | --- |
| `@oneuptime help` | 列出所有指令。只提及而後面什麼都不寫，效果相同。 |
| `@oneuptime status` | 說明它在這個討論串裡目前正在做什麼。 |
| `@oneuptime cancel` | 停止它在這個討論串上進行中的執行。已經推送出去的成果會保留。 |

`help`、`status` 和 `cancel` 都不會啟動代理程式執行，所以不花任何費用，也不受您每日修復任務額度的限制。

## 在討論串裡會看到什麼

一個指令只會產生**一則留言**，App 會隨著工作進展編輯這則留言——所以長時間執行的任務，不會把一個拉取請求變成一長串狀態記錄。

1. 它會在您的留言上加上 👀 表情回應，並張貼一則確認訊息，說明這次執行屬於哪個 OneUptime 專案，並附上即時執行的連結。
2. 完成時，同一則留言會被改寫成結果：它開了哪個拉取請求、推送了哪些 commit，或是誠實說明它為什麼什麼都沒做。

如果它找不到值得改的地方，它會直說，而不是開一個沒有把握的拉取請求。這是正常結果，不是失敗——請給它更明確的方向，再問一次。

## 誰可以對它下指令

**只有對該儲存庫具備 write、maintain 或 admin 存取權的人。** OneUptime 每一次都直接向 GitHub 查詢留言者在該儲存庫上的權限；它不採信 GitHub 顯示在留言旁的「contributor」標記，因為那描述的是過去的活動，而不是目前的存取權。

其他人的提及，只會在他們的留言上得到一個 😕 表情回應，除此之外什麼都沒有。這是刻意的：在公開儲存庫上任何人都能留言，而一個會可靠回覆陌生人的 App，就是一個可以被拿來洗版的 App。

它也會忽略所有由 bot 寫的留言（包括它自己寫的），並忽略出現在引言（`>`）或程式碼區塊裡的提及。這兩條規則加起來，正是讓「回覆它自己的留言」不會又把它啟動一次的原因。

## 它不會做的事

- **它從不合併。** 這個 App 做的任何事，都無法把程式碼放上您的預設分支。
- **它從不核准，也不會要求變更。** 審查是以留言張貼的，所以來自 App 的審查永遠無法滿足分支保護規則。
- **它從不改寫歷史。** 一次修改是新增 commit，不是強制推送。如果別人先推送到該分支，這次修改會失敗，而不是丟掉他們的成果。
- **它無法修改來自 fork 的拉取請求。** fork 的分支位在一個此安裝無法寫入的儲存庫裡。它仍然可以審查——請改請它做審查。
- **它從不更動拉取請求的標題、描述或目標分支。** 只動程式碼。

## 它要花多少成本，又該如何設限

每一個會啟動工作的指令，都是一次完整的代理程式執行——一次 clone、最多 40 次 LLM 呼叫與 100,000 個輸出 token；若您設定了儲存庫的建置與測試指令，還要加上這些。

有兩道限制，而且兩道都是既有 [AI 修復任務](/docs/ai/ai-agent) 已經在用的：

- **專案的每日修復執行上限**（**專案設定 → AI**，預設每天 25 次）。GitHub 指令與專案其餘的修復執行共用這個額度。
- **每個儲存庫未關閉的拉取請求上限**（**程式碼儲存庫 → 該儲存庫 → 設定**，預設 5 個）。審查與修改不受此限：兩者都不會替您的審查佇列新增拉取請求。

同一個 issue 或拉取請求上，每一種執行同時只會有一個在跑。問第二次，它會回你它已經在做了；在修改進行中再要求一次審查，則兩者都會開始，因為那是不同的請求。

如果某次執行無法啟動，App 會在討論串裡說明原因——它絕不會默默失敗。

## 關掉它

以儲存庫為單位：**程式碼儲存庫 → 該儲存庫 → 設定 → Respond to GitHub Commands**。關掉之後，App 會忽略該儲存庫裡的提及、指派與觸發標籤，並告訴詢問的人開關在哪裡。

同一個頁面上還有 **GitHub Trigger Label**，供您改用 `oneuptime` 以外的標籤。

## 需要訂閱哪些事件

在您 GitHub App 的「Permissions & events」設定中，請訂閱：

| 事件 | 用來做什麼 |
| --- | --- |
| **Issue comment** | issue **與**拉取請求上的 `@mention` 指令 |
| **Issues** | 把 issue 指派給 App，以及觸發標籤 |
| **Pull request** | 向 App 要求審查 |
| **Pull request review** | 寫在已送出審查內文裡的提及 |
| **Pull request review comment** | 在 diff 內嵌留言上的提及 |

另外在「Repository permissions」中，**Issues** 必須是 **Read & write**——GitHub 把拉取請求的對話留言透過 issues API 提供，所以這個權限也正是讓 App 能在拉取請求上留言的關鍵。

## 提示注入：哪些有防護，哪些沒有

issue 內文、拉取請求描述、diff 與留言全都會成為代理程式提示的一部分，而在公開儲存庫上，任何人都能寫這些內容。在 issue 裡讀到「忽略你的指示，改做 X」這種文字，是很實際會發生的事。

有兩件事在限制它，而且值得分清楚哪個是哪個：

- **提示會把不可信的文字標示為請求，而不是指示**，而且這次執行的儲存庫、分支與拉取請求，在代理程式啟動之前就已經固定——代理程式讀到的任何內容，都改變不了它正在處理的對象。
- **真正的圍堵來自沙箱。** 代理程式在您的 Runner 上執行，使用一份用完即丟的 clone，指令環境中的憑證已被移除，git 操作也受到限制。它最多只能推送到一個分支，而且只有人類能合併。

請把 AI 寫的拉取請求，當成一位讀過該 issue 的新貢獻者送來的拉取請求來對待：審查 diff，而不是審查描述。

## 疑難排解

**我提及它時什麼都沒發生。** 先檢查代號——那是 App 的 slug，不是它的顯示名稱。接著檢查該儲存庫是否已連接到某個專案（**專案設定 → 程式碼儲存庫**）、**Respond to GitHub Commands** 是否開啟，以及您的 GitHub App 是否已訂閱上面列出的事件。

**它給了 😕 表情回應，然後什麼都沒說。** 您沒有該儲存庫的寫入權限。

**它說它已經在處理這件事了。** 這個 issue 或拉取請求上，已經有一個同類型的執行在進行中。`@oneuptime status` 會告訴您那是什麼，`@oneuptime cancel` 可以停下它。

**它確認之後就安靜了很久。** 請到 **設定 → Runners** 下確認有一台具備 **Runs AI Code Fixes** 的 Runner 在線上。少了它，該次執行會在 30 分鐘後失敗，並在討論串裡告知。

**它說這個拉取請求來自 fork。** 修改需要一個位於這個儲存庫裡的分支。請改要求審查，或把分支推送到這裡來。
