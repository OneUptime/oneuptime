# 設定と安全性

このページでは、ワークフローを実際のトラフィックに向ける前に知っておくべき設定と安全上の制限について説明します。

## ワークフローのオン/オフ切り替え

すべてのワークフローには **設定** の中に **有効** スイッチがあります。オフのときはワークフローは実行されません — webhook の呼び出し、スケジュールされた時刻、OneUptime のイベントはすべて無視されます。新しいワークフローは無効の状態で始まります。

このスイッチを「準備完了」のゲートとして使いましょう。

1. ワークフローを組み立てる。
2. **ビルダー** で現実的な値を使って **ワークフローを実行** をクリックする。
3. **Logs** を確認し、すべてのブロックが期待どおりに動いたかを確かめる。
4. **有効** をオンにする。

ワークフローをオフにしても、すでに進行中の実行は止まりません。新しい実行が始まらなくなるだけです。

## 所有者とラベル

- **所有者** — 所有者としてリストされたユーザーやチームはそのワークフローにアクセスでき、失敗時の通知をオプトインで受け取れます。**設定 → 所有者** で設定します。
- **ラベル** — ワークフローをグループ化するためのタグ。ワークフロー一覧はラベルで絞り込めるので、忙しいプロジェクトでもずっとナビゲートしやすくなります。チーム、連携先、環境ごとにワークフローを整理している場合に便利です。
- **ラベルルール** — **Workflows → Settings → Label Rules** で、名前や説明のパターンに基づいて新しいワークフローに自動でラベルを付けます。
- **所有者ルール** — **Workflows → Settings → Owner Rules** で、新しいワークフローに自動で所有者を割り当てます。

## シークレット

機密情報を含む場合は、グローバル変数を **シークレット** としてマークしてください。保存後は通常の API や UI からの読み取りでは値が隠され、実行ログが保存される前にワークフローのログ記録が解決済みの値をスクラブします。

シークレット変数を使うべきもの:

- 外部サービスの API キー。
- 認証トークン。
- webhook の署名キー。
- 読み取り専用アクセス権を持つ人に見られたくないもの全般。

シークレットをブロックに直接貼り付けないでください — `Authorization: Bearer eyJh...` のような値はワークフローやログにそのまま表示されてしまいます。代わりに `{{global.variables.MY_SECRET}}` を使ってください。

## ワークフローのエクスポートとインポート

ワークフローは JSON ファイルとして、プロジェクト間や、セルフホスト環境と OneUptime Cloud の間で移動できます。

- **エクスポート** — ワークフローを開き、**設定** の **Export Workflow** を使います。ワークフロー一覧から複数のワークフローを選び、1 つのファイルにまとめてエクスポートすることもできます。
- **インポート** — **Workflows** 一覧で **Import JSON** をクリックし、任意の OneUptime プロジェクトからエクスポートされたファイルを選びます。

このファイルにはワークフローの名前、説明、有効状態、そしてそのグラフが保存されます。意図的に含まれないものは次のとおりです。

- **webhook のシークレットキー。** ワークフローが作成されるときに新しいものが生成されるため、インポートされたワークフローは元とは異なる webhook URL を持ちます。元の URL を呼び出していたものは、すべて向き先を変更する必要があります。
- **グローバル変数。** `{{global.variables.MY_SECRET}}` を読み取るブロックはその参照を保持しますが、値そのものはファイルに含まれません。インポートしたワークフローを実行する前に、移動先のプロジェクトで変数を作成してください。
- **所有者とラベル。** インポートされたワークフローには、あなたが手作業で作成した場合と同じように、そのプロジェクト自身のラベルルールと所有者ルールが適用されます。

インポートされたワークフローは、エクスポート元で有効だったとしても、常に **無効** な状態で作成されます。そのグラフが、移動先のプロジェクトに存在しないモニターやオンコールポリシー、他のワークフローを指している可能性があるためです。内容を確認し、有効にし、**ワークフローを実行** でテストしてから、オンのままにしてください。ワークフローの複製も同じ挙動をするので、コピーが編集を終える前に元のものと一緒に動き出すことはありません。

グラフはそのまま持ち運ばれるため、ブロックに直接入力されたものはすべて一緒に運ばれます。これが、認証情報をシークレット変数に保つべき実務上の理由です — トークンをハードコードしたワークフローをエクスポートすると、そのファイルを受け取った人にトークンを渡すことになります。

## 1 回の実行にかけられる時間

各実行の試行にはウォールクロックの締め切りがあります。ランナーはすべてのコンポーネントの前後でこれをチェックし、制御が戻り次第、期限切れの実行を **Timeout** としてマークします。ランナーは任意のコンポーネントのコードを強制的に中断できないため、ネットワークやスクリプトの処理を行うコンポーネントは自身のタイムアウトも必要とします。

AI コンポーネントは、ワークフローの残り時間からプロバイダへのリクエストのタイムアウトを導き出し、最大 60 秒でキャップします。これはログ記録とクリーンアップのための小さな余裕を残すためです。

## 他のワークフローを呼び出す際の上限

**Execute Workflow** コンポーネントを使うと、1 つのワークフローから別のワークフローを呼び出せます。ワークフロー A が B を呼び、B が再び A を呼ぶといった誤ったループを防ぐため、呼び出しの連鎖がどこまで深くなれるかに上限があります。この上限を超えた実行は、明確なエラーで終了します。

長い連鎖が本当に必要な場合 (1 回の実行で 1 件ずつ処理するジョブなど) は、通常は **Custom Code** を使って 1 つのワークフローの中でループさせるほうが単純です。

## Webhook のセキュリティ

Webhook トリガーは専用の URL を提供します。その URL を知っている人は誰でもアクセスできます。意図しない呼び出しや望まない呼び出し元から守るには:

- URL はパスワードと同じように扱いましょう。公開したり、公開リポジトリにコミットしたりしないでください。
- 機密性の高いワークフローでは、呼び出し元のシステムに共有トークンをヘッダー (`X-Webhook-Token` など) として送らせ、重要な処理を行う前に **Conditions** ブロックでチェックしましょう。期待されるトークンはシークレット変数として保存してください。
- 非常に機密性の高いワークフローでは、公開 webhook の代わりに OneUptime イベントトリガーと手動のインポート手順を使うことを検討してください。

## 送信ネットワークアクセス

API やその他の HTTP ブロックは OneUptime からリクエストを送信します。セルフホストしている場合は、あなたのインストールが呼び出し先のサービスに到達できることを確認してください。OneUptime Cloud を使っている場合、こちらの送信元 IP 範囲は [IP アドレス](/docs/configuration/ip-addresses) に一覧があるので、相手側で許可リストに追加できます。

## AI コンポーネント

**Generate Text with AI** は、OneUptime が設定した LLM ゲートウェイを通じて 1 回のリクエストを送信します。プロジェクトの既定の LLM プロバイダを使い、プロジェクトに既定のプロバイダがない場合はインストール全体のグローバルプロバイダを使います。プロバイダは **Project Settings → AI → LLM Providers** の下で設定します。プロバイダの API キーや任意のモデルエンドポイントをワークフロー自体に入れることは絶対にしないでください。

AI コンポーネントには明確な送信境界があります。

- OneUptime は、固定のコンポーネント安全指示に加えて、解決済みの **System Instructions**、**Prompt**、シリアライズされた **Context** を設定済みのプロバイダに送信します。Context はユーザーメッセージの末尾にある明示的なマーカーの後に追加され、固定の指示は、そのマーカー以降のものはタグや指示を含んでいても信頼できないデータのままであると伝えます。
- トリガーのペイロード、ワークフローの履歴、他のコンポーネントの出力、プロジェクトのレコード、テレメトリ、シークレットは自動で添付されません。データは、あなたがこれら 3 つの入力のいずれかで参照した場合にのみ送信されます。
- ツール定義やプロバイダ固有の機能フィールドは一切送信されません。このコンポーネントを通じて、モデルが OneUptime に問い合わせたり、HTTP リクエストを行ったり、プロジェクトのデータを変更したりすることはできません。設定されたプロバイダ/モデルは管理者の信頼境界であり続けるため、厳密にオフラインでの生成が必要なインストールでは、プロバイダ管理の組み込み検索機能を持たないモデルを選ぶ必要があります。
- プロバイダレベルの追加パラメータは、生成専用のチューニングフィールドの許可リストに制限されています。ワークフローのメッセージを置き換えたり、ツールやプロバイダ固有の Web 検索/データソースを追加したり、非テキストのモダリティを有効にしたり、複数の候補を要求したり、ストリーミングを有効にしたり、プロバイダの保存フラグでリクエストを保持したり、このコンポーネントの出力トークン上限を引き上げたりすることはできません。未知の将来的な機能フィールドは既定で破棄されます。
- System Instructions、Prompt、Context、生成された Response の値は、自動ワークフロー実行ログにおけるこの AI コンポーネント自身の引数と戻り値のエントリからは削除されます。実行中は下流のコンポーネントからは引き続き利用できます。それを別のコンポーネントに挿入した場合、そのコンポーネントのログポリシーが適用され、解決済みの値が記録されることがあります。再利用は明示的な開示として扱ってください。プロバイダ/モデル名、トークン数、LLM Log ID、安全なエラーメッセージは、運用と請求のために引き続き表示されます。プロバイダは生のエラー本文にリクエスト内容をエコーし返すことがあるため、生のプロバイダエラー本文はワークフローログ、LLM ログ、アプリケーションログ、トレースから除外されます。

参照するすべての変数は、意図的にプロバイダへ送信しているデータだと考えてください。特に、その開示が本当に必要で、かつそのプロバイダが受け取ることを承認されている場合を除き、シークレットのグローバル変数をプロンプトやコンテキストに挿入しないでください。Ollama のようなセルフホストのローカルプロバイダであれば、リクエストを自分自身のインフラ内に留めておけます。ホスト型のプロバイダは、そのプロバイダのデータ処理条件のもとでリクエストを受け取ります。

各呼び出しは **Project Settings → AI → AI Logs** に、プロバイダ、モデル、ステータス、トークン数、コスト、請求情報とともに記録されます。プロンプトとレスポンスのプレビュー、および生のプロバイダエラー詳細は AI ログには保存されません。課金対象のグローバルプロバイダを通じた呼び出しは、プロジェクトの AI クレジット残高を消費します。ワークフローの AI 利用は、プロジェクトの日次の自律 AI トークン予算にもカウントされます。予算を使い切ると、コンポーネントはモデルに接続することなく **Error** パスを通ります。プロジェクトの AI が有効になっている必要があります。OneUptime Cloud では、サブスクリプションが有料であり、Growth プラン (または Growth の機能を含むプラン) が必要です。課金が無効なセルフホストのインストールにはこのプランによる制限はありません。

無人での呼び出しを有限に保つため、組み込みの上限があります。System Instructions、Prompt、シリアライズされた Context は合計で 50,000 文字にキャップされます。Temperature は `0` から `1` まで、Maximum Output Tokens は `1` から `4096` まで (既定は `1024`) である必要があり、プロバイダへのリクエストは 1 回だけ試行され、最大 60 秒でタイムアウトします。プロジェクトごとに同時実行できるワークフロー AI 呼び出しは最大 3 件までです。それを超える呼び出しは **Error** パスを通り、後続のワークフロー実行で再試行できます。検証、設定、アクセス、予算、残高、同時実行数、プロバイダ、タイムアウトのいずれの失敗も **Error** パスを通り、**Error** 出力を埋めます。本番ワークフローを有効にする前に、そのパスを接続してください。

## 権限

ワークフローはプロジェクトのロールベースアクセス制御に従います。関連する権限は次のとおりです。

- **Create / Read / Edit / Delete Workflow** — ワークフロー自体に対する基本的な権限。
- **Run Workflow** — ワークフローを手動で実行したり、API 経由でトリガーしたりするために必要。
- **Read Workflow Log** — 実行を閲覧するために必要。
- **Create / Read / Edit / Delete Workflow Variable** — グローバル変数一覧に対する制御。

ほとんどのエンジニアには、ワークフローに対する作成/編集/閲覧権限は与えても、変数に対する権限は与えないほうがよいでしょう。変数の編集権限は、プロジェクトのシークレットを管理する人だけに限りましょう。

## プランの上限

OneUptime Cloud は、小さいプランでは月ごとの実行回数に上限を設けています。現在の上限は **Project Settings → Billing** の下に表示されます。上限に達すると、次の請求サイクルまで新しいトリガーは拒否されます。セルフホストのインストールにはこの上限はありません。

## ワークフローが適さない場面

いくつかのケースでは、別の手段を選ぶべきです。

- **重い計算や大きなデータセット** — ワークフローは軽いグルーコードのために設計されており、数値計算のためのものではありません。重い処理は自分たちのインフラで実行し、ワークフローにはそれを起動させるだけにしましょう。
- **長時間動き続ける能動的な計算** — 1 回の実行の試行は素早く終わることを前提としています。「A を行い、2 時間待ち、B を行う」のような受動的な遅延には **Sleep** コンポーネントを使ってください。実行を永続化し、ワーカーを占有せずに後で再開します。
- **人間が介在するステップバイステップのインシデント対応** — それは [Runbook](/docs/runbooks/index) の役割です。ワークフローは無人の自動化のためのものです。
