# 実行とログ

ワークフローが実行されるたびに、OneUptime は何が起きたか — いつ実行されたか、成功したかどうか、各ブロックが何をしたか — の記録を保存します。この記録を **run（実行）** と呼びます。実行は、ワークフローがうまく動いたことを確認し、動かなかったものをデバッグし、過去のアクティビティを振り返るための手段です。

## 見つける場所

| ページ                      | 表示内容                                                                                       |
| ---------------------------- | ---------------------------------------------------------------------------------------------- |
| **Workflows → Runs & Logs** | プロジェクト内のすべてのワークフローのすべての実行。ワークフロー名、ステータス、時間でフィルターできます。 |
| **Workflow → Runs & Logs**  | この 1 つのワークフローの実行のみ。ワークフロー用フィルターの代わりに **Run ID** フィルターがあります。 |
| **個々の実行**               | 実行行の **View Logs** ボタンから開きます — 実行行自体はクリックできません。                    |

## 実行ステータス

| ステータス                              | 意味                                                                                                                                                             |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Scheduled**                             | トリガーが発火し、実行がランナー待ちのキューに入りました。通常はほんの一瞬です。5 分経ってもまだ Scheduled のままの実行は失敗です — 誰も拾わなかったということです。 |
| **Running**                                | ワークフローが進行中です。長時間動作するブロックがあると、実行はこの状態のままになります。                                                                      |
| **Waiting**                                | 実行は **Sleep** ブロックで止まっており、自動的に再開します。待機中はワーカーを 1 つも占有しません。                                                            |
| **Executed**                               | 実行は失敗することなく最後まで到達しました（これが成功状態です — ピルには「Success」ではなく **Executed** と表示されます）。                                     |
| **Error**                                  | ブロックがエラーを発生させたために実行が停止しました。キューに入った実行が誰にも拾われなかったとき、Sleep 中の実行の再開が失われたとき、スケジュール式が解決できないとき、あるいは実行中にワークフローが無効化されたときにも使われます。 |
| **Timeout**                                | 許可された時間より長く実行が続きました。[Configuration & Safety](/docs/workflows/configuration) を参照してください。                                             |
| **Execution Exceeded Current Plan**        | プロジェクトが過去 30 日間のワークフロー実行数を使い切ったか、サブスクリプションが未払いです。実行は記録されますが実行はされません。OneUptime Cloud のみ。       |

**Error** の出力に処理を渡すブロック — たとえば 4xx を返した API ブロック — があっても、実行自体は失敗しません。エラー分岐が実行され、実行は引き続き **Executed** で終わります。ただし、そのステップ自体は見つけやすいように赤く描画されます。

## 実行を読む

実行の **View Logs** をクリックして開きます。**Workflow Run** ビューには 2 つのタブがあります。

**Steps** — 実行されたブロックごとに 1 行、実行順に並びます。各行にはブロックのタイトル、そのコンポーネント ID、所要時間、そして通った出力（`→ success`、`→ error`、`→ yes`）が表示されます。行を展開すると、詳細が 2 つのブロックに分かれて表示されます。

- **Received** — すべての変数が解決された後に、そのブロックに渡された設定。
- **Returned** — それが生成したもの。

失敗したステップは赤く表示され、最初から展開された状態になり、**Received** の上にエラーメッセージが表示されます。

**Full Log** — ランナーが出力した生のログを行単位で表示します。ブロック自身がログに出したものも含まれます。Steps ビューで失敗の原因が分からないときに使います。

知っておくと便利な点が 2 つあります。各ステップのタイトルの下に表示されるコンポーネント ID は、`{{local.components.<id>.returnValues.…}}` 参照にそのまま貼り付けられる文字列そのものなので、参照を正しく書く最も速い方法になります。また、実行が保持するステップは直近 100 件だけです — 長い実行や何度も再開された実行では、それより前のステップが省略された箇所にオレンジ色の注記が表示されます。

表示される値は、変数が埋め込まれた後にブロックが見た値です。ただし 2 つ例外があります。シークレットと、ブロックが機微情報としてマークしたフィールドは伏せ字になり、非常に長い値は「… (truncated)」と表示されて途中で切られます。

**Builder** から実行を開始すると、この同じビューがその実行を追いかけている状態で開くので、あとから探しに行くのではなく、実行されるところをその場で見ることができます。

## よくあるデバッグ

### 「ワークフローが実行されなかった」

1. ワークフローの **Overview** ページで **Enabled** になっていることを確認してください。新しいワークフローは無効な状態で始まり、無効なワークフローは手動実行を含むすべての実行を拒否します。
2. OneUptime のイベントトリガーの場合: そのイベントが実際に発生したかを確認してください。レコードを開いて履歴を確認します。
3. Webhook トリガーの場合: 相手のシステムが正しい URL に送信しているかを確認してください。多くのツールは Webhook を送信した記録を残しているので、そこを確認します。
4. スケジュールトリガーの場合: cron 式が想定している時刻と一致しているかを確認してください。

実行が **Execution Exceeded Current Plan** というステータスで *表示される* 場合、プロジェクトは過去 30 日間のワークフロー実行数を使い切ったか、サブスクリプションが未払いです。実行のログには件数とプランの上限が記載されます。これは OneUptime Cloud にのみ適用されます。

### 「後続のブロックが実行されなかった」

ブロックが実行されないのは、たいてい配線の問題です。**Builder** を開いて次を確認してください。

- 前のブロックの出力がこのブロックの入力に接続されているか？
- 前のブロックが想定と違う出力を取っていないか — **Success** ではなく **Error**、あるいは **Yes** ではなく **No** など？ どちらを通ったかは Steps タブで分かります。

### 「変数が空のまま渡ってきた」

実行を開き、失敗したステップの **Received** ブロックを確認します。

- リテラルの `{{local.components.…}}` というテキストが見えたら、その参照は解決されませんでした。多くの場合、コンポーネント ID か返り値 ID のタイプミスです — それはブロックに表示されている名前ではなく、ブロックの **Identifier** であることを忘れないでください。`local.components` というスペル自体も確認してください。`{{local.componets.api-get-1.returnValues.response-body}}` はそのままリテラルテキストとして送られ、実行は依然として **Executed** と報告されます。
- 空文字列が見えたら、前のブロックは実行されたものの、そのフィールドを生成しなかったということです。

**Full Log** タブには、解決されなかった参照名を示す警告行があり、それを見つける最も速い方法になっていることが多いです。

### 「手動で実行するとうまくいくのに、トリガーからだとうまくいかない」

**Builder** を開き、**Run Workflow** をクリックして、実トリガーが送ってきそうな値をトリガーのフィールドに入力します。そのうえで、この実行の **Received** の値を実際の実行のものと並べて比較します。違いはたいてい、1 つのフィールド名か型です。

## ワークフローを再実行する

「この実行を再試行する」ボタンはありません。Slack メッセージ、API 呼び出し、チケット作成といった副作用を繰り返しても安全とは限らないため、過去の実行を自動的に再実行することはありません。作業をやり直すには、ワークフローを修正して次の実トリガーに発火させるか、**Builder** を開いて同じ値で **Run Workflow** をクリックしてください。

## 実行はどれくらい保持される?

OneUptime Cloud では、実行は **30 日間** 保持されてから削除されます — どちらの実行一覧も「直近 30 日間」を対象としていると説明しているのはそのためです。セルフホスト環境では、削除するまで実行は保持され続けます。ワークフローが頻繁に実行されて履歴が乱雑になる場合は、そのワークフローを無効化または削除してノイズを増やさないようにしてください。

ステップのトレースが追加される前に記録された実行には **Steps** の内容がなく、**Full Log** のみが表示されます。
