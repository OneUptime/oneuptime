# コンポーネント

コンポーネントは、トリガーの後ろに足していく部品です。ひとつひとつが 1 つの仕事をし — メッセージを送る、API を呼ぶ、条件を確かめる — 次に来るものへつながります。

このページはそのカタログです。キャンバス上での足し方とつなぎ方は [ワークフローを作成する](/docs/workflows/authoring) を参照してください。

## API

任意の URL に HTTP リクエストを送ります。

**設定**:

- **Method** — `GET`、`POST`、`PUT`、`PATCH`、`DELETE` のいずれか。
- **URL** — 呼び出す先のアドレス。
- **Headers** — 送るヘッダー。
- **Body** — `POST` / `PUT` / `PATCH` のときのリクエストボディ。

**出力**:

- **成功** — 呼び出しがうまくいった（2xx の応答）ときに発火します。ステータス、ヘッダー、ボディを次に渡します。
- **エラー** — ネットワークの失敗か、2xx 以外の応答のときに発火します。エラーメッセージを次に渡します。

向いている場面: 外部の API 全般、自前の管理用エンドポイント、専用のコンポーネントがない連携。

## AI

### Generate Text with AI

プロンプトと、任意の JSON のコンテキストから、テキストの応答を 1 つ生成します。このコンポーネントは、プロジェクトに設定された既定の LLM プロバイダーを使い、それがなければ、インストール全体のプロバイダーが用意されていればそちらにフォールバックします。プロバイダーの資格情報とエンドポイントは中央で設定するもので、ワークフローの引数ではありません。

**設定**:

- **System Instructions** — 任意。モデルの役割、口調、制約についての指示です。
- **Prompt** — 必須。やってほしいことです。ワークフローの変数や、前のコンポーネントの出力を含められます。
- **Context** — 任意。リクエストに意図して同梱する JSON です。メッセージの終わりを示す信頼のマーカーの後ろに追加され、そこから先は信頼できないデータとして扱われます。
- **Temperature** — `0` から `1` までのばらつき。自動化では結果が読めるほうがよいので、既定は `0.2` です。
- **Maximum Output Tokens** — `1` から `4096` まで。既定は `1024` です。

System Instructions、Prompt、直列化された Context を合わせた長さの上限は 50,000 文字です。プロバイダーへのリクエストは最長 60 秒で、試行は 1 回だけです。ワークフローの AI リクエストは、プロジェクトごとに同時 3 件までしか動きません。

**出力**:

- **Response** — 生成されたテキスト。
- **プロバイダー** と **Model** — この呼び出しに使われた設定。
- **Total Tokens** と **Completion Tokens** — プロバイダーが報告した使用量。
- **LLM Log ID** — この呼び出しについて計測された AI ログのエントリー。
- **エラー** — 検証、アクセス、プロバイダー、予算、請求、タイムアウトのいずれかのエラー（あれば）。

応答を使うコンポーネントには **成功** をつなぎます。**エラー** は、はっきり決めたフォールバック、通知、ログの経路につないでください。このコンポーネントは、ツール定義もプロバイダー固有の機能フィールドも付けずに、モデルへ 1 回リクエストするだけです。自分で OneUptime に問い合わせることも、API を呼ぶことも、プロジェクトのデータを変えることもできません。OneUptime が固定で付けるコンポーネントの安全指示を除けば、プロバイダーに送られるのは、あなたが設定した System Instructions、Prompt、Context だけで、それらの中のワークフロー変数が解決されたあとに送られます。設定したプロバイダーとモデルは信頼境界であり続けます — モデル自身が、プロバイダー側で管理された機能を備えていることがあるからです。

モデルの出力は、信頼できないテキストです。顧客に届く連絡に使う前には目を通してください。また、自由記述の AI テキストだけを根拠に、破壊的なワークフロー操作を許可しないでください。プロバイダー、外向きの通信、ログ、コストの詳細は [ワークフロー 設定と安全性](/docs/workflows/configuration) を参照してください。

## Webhook（送信）

「投げっぱなし」でよい場面のための、API コンポーネントの簡易版です。JSON のボディを URL に POST します。

応答を読む必要があるなら **API** を、通知を送ってそのまま先へ進みたいだけなら **Webhook** を使ってください。

## Slack

Slack のチャンネルにメッセージを投稿します。

**設定**:

- **チャンネル** — チャンネル名。ボットがあらかじめそのチャンネルに入っている必要があります。
- **メッセージ** — 送る本文。Slack の書式に対応しています。

まず **プロジェクト設定 → ワークスペース → Slack** で、プロジェクトを Slack につないでください。[Slack ワークスペース接続](/docs/workspace-connections/slack) を参照してください。

## Microsoft Teams

Microsoft Teams のチャンネルにメッセージを投稿します。

**設定**:

- **チームとチャンネル** — どこに投稿するか。
- **メッセージ** — 送る本文。

設定の手順は [Microsoft Teams ワークスペース接続](/docs/workspace-connections/microsoft-teams) を参照してください。

## Discord

受信 Webhook の URL を通して、Discord のチャンネルにメッセージを投稿します。

## Telegram

ボットのトークンとチャット ID を使って、Telegram のチャットにメッセージを送ります。

## メール

OneUptime からメールを送ります。

**設定**:

- **宛先** — 受信者のメールアドレス。
- **件名** — 件名の行。
- **Body** — Markdown か HTML で書いた本文。

メールは、プロジェクトに設定された送信元から出ます — [SMTP](/docs/emails/smtp) を参照してください。

## Custom Code

他のブロックではできないことが必要なときに、小さな JavaScript を実行します。

**設定**:

- **コード** — あなたの JavaScript。最後の値（または async 関数から返した値）が、このブロックの出力になります。
- **Arguments** — 渡せる、名前の付いた値。

**出力**: 成功（あなたの戻り値）とエラー（送出された例外）。

向いている場面: 2 つのシステムのあいだでデータの形を整える、ちょっとした計算をする、専用のブロックを立てるほどでもない処理。もっと本格的なスクリプトを書きたいなら、代わりに [Runbook](/docs/runbooks/index) を使ってください。

## JSON

テキストと JSON を相互に変換します。

- **JSON → Text** — JSON オブジェクトを文字列にします。次のブロックがテキストを期待しているときに便利です。
- **Text → JSON** — 文字列を JSON オブジェクトにパースします。何かがテキストとして届いて、その中の項目を読みたいときに便利です。

## 条件

比較の結果で分岐します。**コンポーネントを追加** のパネルでは、このブロックは Conditions カテゴリの下に **If / Else** という名前で並んでいます。

**設定**:

- **Left value** — たいていは、前のブロックから来た値。
- **Operator** — `==`、`!=`、`>`、`>=`、`<`、`<=`、`contains`、`starts with`、`ends with`。
- **Right value** — 比較する相手。

**出力**: **はい** と **いいえ**。次のブロックは、使いたいほうの分岐につないでください。

## Delay

先へ進む前に、決めた時間だけワークフローを止めます。別のシステムが追いつくのを、少し待ちたいときに便利です。

## ログ

実行ログに 1 行書きます。外部への影響はなく、あなたが読むためにワークフローのログへ出るだけです。デバッグに重宝します。

## Execute Workflow

このワークフローから、別のワークフローを呼びます。呼ばれたワークフローは独立して動き、こちらのワークフローは、その完了を待たずに先へ進みます。

共通の処理を使い回すのに使ってください。「インシデントのチャンネルに投稿する」ワークフローを一度作っておけば、そのチャンネルに知らせたい他のどのワークフローからでも呼べます。

ワークフローどうしが延々と呼び合わないよう、安全のための上限があります。[ワークフロー 設定と安全性](/docs/workflows/configuration) を参照してください。

## OneUptime のデータコンポーネント

OneUptime にあるレコードの種類ごとに（モニター、インシデント、アラート、ステータスページ、オンコールポリシー、その他たくさん）、**コンポーネントを追加** のパネルには次のコンポーネントが並びます — その種類の名前で検索してください。タイトルはレコードの種類から自動で作られるので、モニターの一式はこうなります。

- **Find One Monitor** — クエリに一致するレコードを 1 件読みます。
- **Find Many Monitors** — クエリに一致するレコードの一覧を読みます。
- **Create One Monitor** — JSON オブジェクトからレコードを 1 件追加します。
- **Create Many Monitors** — JSON 配列から複数のレコードを追加します。
- **Update One Monitor** — 書き込みのペイロードを、一致するレコード 1 件に適用します。
- **Update Many Monitors** — 書き込みのペイロードを、一致するレコードに Limit の件数まで適用します。
- **Delete One Monitor** — 一致するレコードを 1 件削除します。
- **Delete Many Monitors** — 一致するレコードを、Limit の件数まで削除します。

同じ一式から、トリガーも 3 つ使えます — **On Create Monitor**、**On Update Monitor**、**On Delete Monitor** です。[ワークフロー トリガー](/docs/workflows/triggers) を参照してください。

どの種類も、そのモデルが許すコンポーネントしか出しません。読み取り専用の種類なら、Find が 2 つあるだけです。ですからパネルで **Delete One Monitor** が見つからないなら、その種類では削除が許されていない、ということです。

ワークフローが OneUptime のデータを読み書きするのは、この仕組みを通してです。たとえば、CI ツールからの Webhook が **Create One Incident** を使って、失敗の詳細を載せたインシデントを立てられます。

## レコードを扱う

データコンポーネントのどの項目も、レコード自身の **カラム** 名を鍵にします — ダッシュボードのフォームに出ているラベルではなく、API が使うのと同じ名前です。ID のカラムは `_id` です。カラム名を書けるところでは `id` という綴りも別名として受け付けますが、レコードが返してくるのは `_id` なので、読み取り側で使うのはこちらです。

```json
{ "_id": "00000000-0000-0000-0000-000000000000" }
```

**Query** が、そのコンポーネントの対象になるレコードを決めます。キーはカラム、値は一致させたいものです。

```json
{ "monitorType": "Website", "isEnabled": true }
```

クエリの範囲は、常にそのワークフローが動いているプロジェクトの中です。他のプロジェクトのレコードには手が届きませんし、プロジェクトを自分でクエリに書き足す必要もありません。

書き込む項目を運ぶのは、Create One では **JSON Object**、Create Many では **JSON Array**、Update 系では **Data (JSON Object)** です。キーの付け方は同じです。

```json
{ "name": "Checkout API", "monitorType": "Website" }
```

カラムでないキーは、拒否されるのではなく無視されます — 捨てられたキーの名前は実行ログに出るので、項目が反映されないときはそこを見てください。Find コンポーネントとトリガーにある **Select Fields** も、同じカラム名をキーにして値を `true` にします: `{"_id": true, "name": true}`。

**スキップ** と **Limit** は、Find Many、Update Many、Delete Many にある 2 つの数値の項目です — `Skip: 0` と `Limit: 100` なら、一致したうち先頭の 100 件が対象になります。Limit の既定は `10` で、Update Many と Delete Many では、返ってくる件数ではなく、実際に書き換わる件数の上限になります。ですから `Items Deleted: 10` は 10 件が削除されたという意味であって、10 件が一致したという意味ではありません。10 件より多く変えるつもりなら、Limit を上げてください。

**成功** と **エラー** が示すのは、クエリが走ったかどうかであって、何が見つかったかではありません。何にも一致しないクエリは `0` を返し、それでも成功の側から抜けます — これは失敗ではありません。何か一致したかどうかで分岐したいなら、**If / Else** ブロックで、返ってきた件数を読んでください。

## どのコンポーネントを使うべきか

目安をいくつか。

- やりたいことに専用のブロックがあるなら（Slack、メール、OneUptime のレコード）、それを使ってください — エラーの扱いが行き届き、ログも読みやすくなります。
- それ以外の外部 API には **API** を使います。
- 明示的に選んだワークフローのデータをもとに、要約したり、分類したり、文章の下書きをしたりするなら **Generate Text with AI** を使います。
- ブロックのあいだでデータの形を整えるなら **Custom Code** か **JSON** を使います。
- 値によって違う動きをさせたいなら **条件** を使います。
