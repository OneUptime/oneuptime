# インシデントの宣言

インシデントを宣言することは、OneUptime が記録を取り始める瞬間です。レコードが作成され、番号が刻まれ、オンコールポリシーが発動し、そして特に指定しない限り、ステータスページの購読者にも伝わります。インシデントのライフサイクルにあるそれ以外のすべては、この最初の書き込みにぶら下がっています。

インシデントが OneUptime に入る経路は 4 つあり、どれも行き着く先は同じです — `Incident` テーブルの 1 行で、重大度、現在の状態、影響を受けるリソースの一覧を持ちます。違うのはフィールドを埋めるのが誰かだけです — 深夜 3 時のあなた、保存済みのテンプレート、モニターの条件、あるいはあなた自身のコードによる API 呼び出しです。

このページでは、この 4 つの経路をフィールド単位で順に見ていき、続いてサーバーが代わりに埋める内容と、インシデントが存在した瞬間に発火するものを扱います。

## インシデントが宣言される 4 つの方法

| やりたいこと…                                                 | 選ぶもの                                                                     |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| すべてを手作業で入力してインシデントを開く                     | **インシデントを宣言** ウィザード                                            |
| フィールドが事前入力された、繰り返し発生する種類のインシデントを開く | **テンプレートから作成**                                                     |
| モニターのチェックが失敗したときに自動で開く                   | **When filters match, declare an incident.** を有効にしたモニター条件フィルター |
| 自分のコード、スクリプト、または別のツールから開く              | `POST /api/incident`                                                        |

この 4 つはすべて同じモデルに書き込むため、プローブが開いたインシデントは、対応者が手作業で開いたものと見た目上まったく同じです — サーバーが自動作成されたものにだけ設定する、いくつかの記録用カラムを除いては。

## 手作業で宣言する

**インシデント → すべてのインシデント** を開き、**インシデント** 一覧の右上にある **インシデントを宣言** をクリックします。すると **新しいインシデントを宣言** というタイトルのカードに移動し、フォームは 5 つのステップに分かれています — **インシデントの詳細**、**影響を受けるリソース**、**インシデントの役割**、**オンコール**、**もっと**。最後の送信ボタンも **インシデントを宣言** と表示されます。

必須フィールドがあるのは最初のステップだけです。急いでいる場合は **インシデントの詳細** を入力して送信すれば十分です — リソースの紐付け、役割の割り当て、オンコールポリシーの追加は、あとからインシデント自身のページで行えます。

### ステップ 1 — インシデントの詳細

- **タイトル** — 必須。一覧、Slack、そして（インシデントが表示される場合は）ステータスページで全員が目にする一行の要約です。プレースホルダー: `Incident Title`。
- **説明** — 任意、Markdown で記述します。このフィールドはステータスページに表示されるので、チーム向けではなく顧客向けに書いてください。あとからインシデントのサイドメニューの **説明** で編集できます。
- **宣言日時** — フォーム上は必須で、既定値は現在時刻です。インシデントのすべての経過時間はこのタイムスタンプを起点に計測されるので、以前に始まった出来事を記録する場合は日時をさかのぼって設定してください。
- **インシデントの重大度** — 必須。プロジェクトに設定されている重大度のいずれかです。新規プロジェクトには **Critical Incident**、**Major Incident**、**Minor Incident** がシードされます。
- **インシデントの状態** — 任意。そのままにしておくと、インシデントは `isCreatedState` フラグを持つ状態に入ります。これは新規プロジェクトでは **Identified** としてシードされています。すでにその段階を過ぎたインシデントを記録する場合にのみ設定してください。

**状態のドロップダウンでうまくいかない場合。** プロジェクトに `isCreatedState` フラグを持つ状態が 1 つもない場合、作成呼び出しは失敗し、設定から作成状態を追加するよう案内が表示されます。これは通常、状態が大きく編集されたプロジェクトでのみ発生します — 詳しくは [インシデントの状態と重大度](/docs/incidents/states-and-severities) を参照してください。

### ステップ 2 — 影響を受けるリソース

- **影響を受けるリソース** — モニター、ホスト、Kubernetes クラスター、Docker ホスト、Podman ホスト、サービスを紐付ける単一の検索ボックスです。内部的にはこれらはインシデント上の別々のリレーション（`monitors`、`hosts`、`kubernetesClusters`、`dockerHosts`、`podmanHosts`、`services` など）ですが、フォームは 1 つのピッカーにまとめています。
- **Change Monitor Status to** — 任意。このインシデントに紐付いたすべてのモニターに適用するモニターステータスを選びます。これにより、インシデントを宣言することとモニターを degraded とマークすることが、2 つの操作ではなく 1 つの操作になります。

**冗長に感じてもモニターを紐付けてください。** インシデントとステータスページのつながりは、インシデントのモニターを通じて成立します — ステータスページは、自身のリソースのいずれかがインシデントのモニターの 1 つであるときに、そのインシデントを表示します。インシデントにモニターが 1 つも紐付いていない場合、状態変更通知は購読者に対して完全にスキップされます。詳しくは [ステータスページのリソースとグループ](/docs/status-pages/resources-and-groups) を参照してください。

### ステップ 3 — インシデントの役割

- **Assign Incident Roles** — プロジェクトが定義する役割にチームメンバーを割り当てます。複数のユーザーを受け付ける役割もあります。

役割自体は **インシデント → 設定 → インシデントの役割** で設定します。ここで、対応中に割り当て可能な役割 — Incident Commander、Responder、その他プロセスに必要なもの — を定義します。このステップを飛ばした場合、まだ誰もその役割を持っていなければ、最初の状態変更時に Incident Commander が自動で割り当てられます。

### ステップ 4 — オンコール

- **オンコールポリシー** — このインシデントが作成されたときに実行するオンコール当番ポリシーの複数選択です。これはインシデントの `onCallDutyPolicies` に対応します。

オンコールポリシーがインシデントに直接紐付けられるのはここだけです。重大度はオンコールポリシーを持ちません — 重大度はラベルであり、オンコールルール内の *一致条件* としてのみページングに影響します。**インシデント → ルール → オンコールルール** で設定されたルールは、ここで選んだものに加えて自身のポリシーを追加します。最終的に実行されるのは、両方を重複排除した和集合です。

### ステップ 5 — もっと

- **ラベル** — 任意で、高度な機能です。これらのラベルへのアクセス権を持つチームメンバーだけが、そのインシデントにアクセスできます。
- **ステータスページの購読者に通知** — チェックボックス、既定でオン。インシデントが作成されたことを購読者にメールで知らせるかどうかを制御します（`shouldStatusPageSubscribersBeNotifiedOnIncidentCreated`）。記録はしたいが社内向けのノイズにしたい場合はオフにしてください。
- **プライベートインシデント** — チェックボックス、既定でオフ（`isPrivate`）。プライベートインシデントは、所有者ユーザー、所有者チームのメンバー、プロジェクト管理者、プロジェクトオーナーにのみ表示され、他の設定にかかわらずすべてのステータスページから隠されます。インシデント一覧では赤い **Private** ピルでマークされます。

**Should be visible on status page?** フラグ（`isVisibleOnStatusPage`）はウィザードにはなく、既定で true です。あとからインシデントのサイドメニューの **設定** で変更でき、そこでは **ステータスページに表示** というラベルになっています。

## テンプレートから宣言する

同じ形のインシデント — 同じタイトルのパターン、同じ重大度、同じオンコールポリシー — を何度も宣言するなら、一度テンプレートとして保存しておきましょう。

**テンプレートから作成**（**インシデントを宣言** の隣にあるアウトラインボタン）をクリックすると、**Create Incident from Template** モーダルが開き、**インシデントテンプレートを選択** ドロップダウンが表示されます。テンプレートを選ぶと作成フォームが事前入力された状態で開きます。送信前であればどこでも変更できます。プロジェクトにまだテンプレートがない場合は、代わりに **No Incident Templates** モーダルが表示され、**Create Template** ボタンから **インシデント → 設定 → インシデントテンプレート** に移動できます。

テンプレートは独自の 6 ステップのウィザードで作成されます — **Template Info**、**インシデントの詳細**、**影響を受けるリソース**、**オンコール**、**Owners**、**ラベル** — 次のフィールドがあります。

| フィールド                    | 用途                                                     |
| ------------------------------ | ---------------------------------------------------------- |
| **テンプレート名**            | ピッカーの中でテンプレートを識別する方法。                 |
| **テンプレートの説明**        | いつこのテンプレートを使うべきかを未来の自分に伝えるメモ。 |
| **タイトル**                  | インシデントに事前入力されるタイトル。                     |
| **説明**                      | インシデントに事前入力される Markdown の説明。             |
| **インシデントの重大度**      | インシデントに事前入力される重大度。                       |
| **Initial Incident State**    | このテンプレートから作られるインシデントが開始する状態。   |
| **影響を受けるリソース**      | 紐付けるモニター、ホスト、クラスター、サービス。            |
| **Change Monitor Status to**  | 紐付けたモニターに適用するモニターステータス。              |
| **オンコールポリシー**        | インシデント作成時に実行するポリシー。                      |
| **Owner - Teams**             | このテンプレートから作成されたインシデントを所有するチーム。 |
| **Owner - Users**              | このテンプレートから作成されたインシデントを所有するユーザー。 |
| **ラベル**                    | インシデントに適用されるラベル。                            |

いくつか簡単なルールがあります。

- テンプレートはテンプレート一覧からは編集できません — 作成してから、それを開いて変更します。
- テンプレートが埋めるのは、あなたが空欄のままにしたフィールドだけです。作成ページでは、テンプレートは上書き可能な事前入力として適用されます。API では、リクエストでそのフィールドが `undefined` のままだった場合にのみ、サーバーがテンプレートからフィールドを埋めます。呼び出し側が指定した値は常に優先されます。

## モニターの条件から自動で宣言する

ほとんどのインシデントは、人が手で入力する必要がないはずです。モニターの条件エディターで **When filters match, declare an incident.** トグルをオンにすると、**Create Incident** セクションが表示され、**Add Incident** ボタンが現れます — 1 つの条件フィルターから複数のインシデントを宣言できます。

各エントリには次があります。

- **Incident Title** — テンプレート化に対応しています。プレースホルダーは `{{monitorName}} is down` のようなものを示唆します。
- **Severity** — 必須。
- **Incident Description** — こちらもテンプレート化されています。
- **On-Call → On-Call Policies** — このインシデントが作成されたときに実行するポリシー。
- **インシデントの役割** — チームメンバーを役割に事前割り当てします。
- **Ownership & Labels → Owner Teams**、**Owner Users**、**ラベル**。
- **Advanced Options → Auto Resolve Incident**（条件が一致しなくなったときにインシデントを自動的に解決する）、**Show Incident on Status Page**、**プライベートインシデント**、**Remediation Notes**。

タイトル、説明、修復ノートで使える `{{variable}}` プレースホルダーの完全なリストは、[インシデント & アラート テンプレート](/docs/monitor/incident-alert-templating) を参照してください。

この方法で作成されたインシデントには、サーバーによってタグが付けられます — `isCreatedAutomatically` が設定され、`createdCriteriaId` にはどの条件フィルターが発火したかが記録され、`createdByProbe` にはどのプローブが検知したかが記録されます。それ以外の挙動は、手作業で宣言したインシデントとまったく同じです。

## API 経由で宣言する

インシデントモデルは標準の CRUD エンドポイントを公開しているので、`POST /api/incident` で 1 件作成できます。**Project Settings → API Keys** で生成した API キーで認証し、`apikey` ヘッダーで送信します — キーがプロジェクトを識別するので、プロジェクト ID を別途渡す必要はありません。

```bash
curl -X POST https://oneuptime.com/api/incident \
  -H "apikey: $ONEUPTIME_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "data": {
      "title": "Checkout latency above SLO",
      "description": "Investigating elevated p99 latency on the checkout service.",
      "incidentSeverityId": "<incident-severity-id>"
    }
  }'
```

リクエストボディで使える主なフィールド。

- `title` — 実質的に必ず指定する必要がある唯一のフィールド。
- `declaredAt` — フォームでは必須ですが、こちらでは任意です。省略するとサーバーが現在時刻を使います。
- `incidentSeverityId` と `currentIncidentStateId` — サーバーは、この両方が API キーと同じプロジェクトに属しているかを確認し、そうでなければリクエストを拒否します。**Change Monitor Status to** の背後にあるモニターステータスにも同じチェックが適用されます。
- `createdIncidentTemplateId` — 保存済みのテンプレートを適用します。省略したフィールドはテンプレートから埋められます。送信したフィールドはそのまま保持されます。

関連するエンドポイントは `/api/incident-state`、`/api/incident-severity`、`/api/incident-state-timeline` です。生成された [API リファレンス](/reference) には、それぞれの正確なリクエストとレスポンスの形（モニターなどのリレーションフィールドの表現方法を含む）が載っています。

## インシデント番号とプレフィックス

すべてのインシデントには、作成時にサーバーが割り当てる、プロジェクトごとのカウンターによる連番が付きます。この値は 2 つのカラムに保持されます — `incidentNumber`（生の整数）と `incidentNumberWithPrefix`（実際に目にするもの）です。プレフィックスが設定されていない場合、表示値は `#42` です。

これを変更するには、**インシデント → 設定 → その他の設定** に移動します。**番号プレフィックス** カードには **インシデント番号のプレフィックス** フィールド（最大 20 文字、プレースホルダー `INC-`）があります — これを設定すると、同じインシデントが `INC-42` として表示されます。空のままにすると既定の `#` が使われます。このカードには、エピソード番号付け用の **インシデントエピソード番号のプレフィックス** もあります。

番号はインシデント一覧の最初の列として表示され、インシデントへのリンクになっており、インシデントの **概要** では **インシデント番号** として表示されます。

## インシデントが宣言された瞬間に起きること

作成呼び出しは、単に行を書き込むだけではありません。順番に次が起こります。

1. **サーバーが空欄を埋めます。** `declaredAt` は既定で現在時刻になり、現在の状態は既定でプロジェクトの `isCreatedState` 状態になり、インシデント番号とプレフィックス付き番号がプロジェクトのカウンターから割り当てられます。
2. **テンプレートが適用されます**（`createdIncidentTemplateId` が指定されていた場合） — 呼び出し側が未定義のままにしたフィールドだけを埋めます。
3. **プライバシールールが実行され**、一致するルールがあればインシデントをプライベートとマークします。これは最初に実行されるルールエンジンなので、それ以降のすべての処理は正しいプライバシー設定を見ることになります。
4. **所有者ルールが実行され**、一致するルールが指定する所有者ユーザーとチームが追加されます。
5. **ラベルルールが実行され**、インシデントに一致するラベルが追加されます。
6. **オンコールルールが実行されます。** **インシデント → ルール → オンコールルール** にある、条件が一致する有効なルールすべてが、自身のポリシーをインシデントに追加します。優先順位はなく、ショートサーキットもありません — 一致したすべてのルールが発火し、ポリシーは重複排除されます。
7. **Runbook ルールが実行され**、一致した Runbook が紐付けられ開始されます。詳しくは [Runbook 概要](/docs/runbooks/index) を参照してください。
8. **オンコールポリシーが実行されます。** インシデントに紐付いたすべてのポリシー — ウィザードで選んだもの、テンプレートから継承したもの、ルールで追加されたもの — が、イベントタイプ `IncidentCreated` で並列に実行されます。あるポリシーが失敗しても、他のポリシーは止まりません。
9. **購読者がキューに入れられます**（**ステータスページの購読者に通知** がオンのままで、インシデントがステータスページに表示される設定になっている場合）。配信はバックグラウンドジョブが処理し、リクエストと同期しては行われません。
10. **ワークフローが発火します。** **On Create Incident** トリガーが、それを基に構築されたワークフローを起動します。詳しくは [ワークフロー 概要](/docs/workflows/index) を参照してください。

ここからインシデントは稼働状態になります — インシデントのサイドメニューにある **アクティブなインシデント** バッジにカウントされ（`isResolvedState` フラグが付いていないすべての状態がアクティブとしてカウントされます）、自身のモニターのいずれかを持つステータスページに表示され、**状態タイムライン** の記録が始まります。
