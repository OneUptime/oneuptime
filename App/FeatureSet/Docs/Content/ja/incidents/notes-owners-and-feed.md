# インシデントのメモ、オーナー、フィード

インシデントは対応している間に、書かれた記録を積み重ねていきます。その一部は顧客向けです — 02:14 にステータスページへ出す、悪いデプロイを見つけたという更新です。残りはチーム向けです — 誰かが貼り付けたスタックトレース、ようやく意味が通ったグラフ、フェイルオーバーの決断です。

OneUptime はこの 2 つの読み手を分けて扱います。**Public Notes** はステータスページに公開され、購読者に通知できます。**Private Notes**(`IncidentInternalNote` モデル)はダッシュボードの内側にとどまります。両方の下には、インシデントに起きたすべてを記録する追記専用のタイムラインである **Incident Feed** と、誰に知らせるかを決める **Owners** リストがあります。

これらはすべてインシデントの左サイドメニューにぶら下がっています — **Notes → Public Notes**、**Notes → Private Notes**、**Team → Owners**。フィードはインシデントの **Overview** ページにあります。

## パブリックノートとプライベートノート

この 2 つのノートタイプはダッシュボード上では似て見えますが、動作はまったく異なります。

- **パブリックノート** — `IncidentPublicNote` モデルで、インシデントタイムラインの一部としてステータスページに配信されます。自分で設定できる **Posted At** の日時と、**Notify Status Page Subscribers** チェックボックスを持ちます。
- **プライベートノート** — `IncidentInternalNote` モデルです。ステータスページアプリはこれを一切読み込みません。posted-at フィールドは持たず(一覧は `createdAt` でスタンプされ並び替えられます)、購読者関連のフィールドもまったくないため、プライベートノートが購読者通知を発生させることは絶対にありません。

**「プライベート」が実際に意味すること。** それは「ステータスページに公開されない」という意味であり、「より小さな人数のグループに限定される」という意味ではありません。両方のノートタイプは同じ読み取り権限を共有しているため、インシデントを読める人なら誰でもそのプライベートノートを読めます。インシデント自体を見られる人を制限したい場合は、インシデント自体の **Private Incident** フラグ(`isPrivate`)を使ってください。これはすべてのステータスページからインシデントを隠し、インシデントの所有者ユーザー、所有者チームのメンバー、そしてプロジェクトの管理者とオーナーだけに限定します。

**Owners は両方を見ます。** 所有者通知ジョブはパブリックノートとプライベートノートを一緒に問い合わせます。プライベートノートは購読者から見て非公開であって、対応する人たちから見て非公開なのではありません。

| やりたいこと…                                             | 選ぶもの         |
| ---------------------------------------------------------- | ---------------- |
| 顧客に、今わかっていることといつわかりそうかを伝える       | **Public Note**  |
| 別の場所で既に送った更新をさかのぼって記録する             | **Public Note**  |
| 仮説、実行したコマンド、行き詰まった経緯を記録する         | **Private Note** |
| ヒープダンプや内部ダッシュボードのスクリーンショットを添付する | **Private Note** |

## パブリックノートを投稿する

インシデントのサイドメニューで **Notes → Public Notes** を開き、ノートを作成します。このカードには、ここに書いた内容がステータスページに表示されると説明があり、空の状態ではこのインシデントについてまだパブリックノートが作成されていないと表示されます。

| フィールド                          | 目的                                                                                                                  |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| **Public Incident Note**             | Markdown で書く本文。必須です。このノートはステータスページに表示されることをフォームが念押しし、チートシートへのリンクもあります。 |
| **Attachments**                      | ステータスページで購読者と共有されるファイル。任意です。                                                              |
| **Notify Status Page Subscribers**   | チェックボックス。既定でオンです。静かに公開したい場合はオフにします。                                                |
| **Posted At**                        | 必須の日時。既定は現在時刻で、あなたの現在のタイムゾーンで表示されます。                                              |

**Posted At はノートの実際のタイムスタンプです。** ステータスページはパブリックノートを、入力した時刻ではなく `postedAt` で並び替えて表示します。したがって、40 分前に送った更新をステータスページに追いつかせているのであれば、**Posted At** を実際に起きた時刻に設定してください。API 経由でこの値を指定せずにノートが届いた場合、OneUptime は現在時刻をスタンプします。

一覧には、各ノートを書いた人、その **Posted At**、添付ファイル付きでレンダリングされた Markdown、そして **Subscriber Notification Status** 列が表示されます。**Created By**、**Note**、**Created At** で絞り込めます。

## プライベートノートを投稿する

**Notes → Private Notes** は意図的にシンプルです。フィールドは 2 つだけです。

- **Private Incident Note** — Markdown 本文、必須です。これがチーム内限定でステータスページには表示されないことが、フォーム上ではっきりと説明されます。
- **Attachments** — インシデント対応チーム向けのファイル。

**Posted At** はなく、購読者チェックボックスもありません — ノートは作成された時点でスタンプされます。

## ノートへの添付ファイル

両方のノートタイプは **Attachments** フィールドを通じてファイル添付を受け付け、どちらもノート本文の下に、ファイルごとの **Download attachment** リンク付きの添付ファイル一覧を表示します。

異なるのは、誰がそのファイルを取得できるかです。

- **パブリックノートの添付ファイル** は、ステータスページのルートを通じてノート本体とともに、ステータスページの訪問者がダウンロードできます。
- **プライベートノートの添付ファイル** は、認証されたダッシュボード API を通じてのみアクセスできます。ステータスページ側にそのためのルートはありません。

これはノート本文と同じ、パブリックかプライベートかの判断がそのまま添付ファイルにも及ぶということです。顧客向けのタイムライン画像はパブリックノートに、設定ファイルのダンプはプライベートノートに置きます。

## AI でノートを生成する

どちらのノートページにも **Generate with AI** ボタンがあります。これはインシデントをプロジェクトの AI プロバイダーに送信し、生成された Markdown をノートエディターに投入します。保存前に編集できる状態であり、自動的に公開されるものは何もありません。

- **Generate Public Note with AI** — インシデントデータを分析して顧客向けのノートを作成すると説明されています。テンプレートには **Status Update** と **Resolution Notice** があります。
- **Generate Private Note with AI** — 代わりに社内向けの技術的なノートを作成します。テンプレートには **Investigation Update** と **Technical Analysis** があります。

ボタンの裏側では、ダッシュボードが選択したテンプレートと `public` または `internal` のノートタイプを添えて `/incident/generate-note-from-ai/{incidentId}` に POST します。

## ノートテンプレート

チームが毎回の障害で同じ 3 種類の更新を書いているなら、一度保存してしまいましょう。どちらのノートページにも **Create from Template** ボタンがあり、**Select Note Template** ドロップダウンを持つ **Create Note from Template** ピッカーが開きます。

テンプレートはパブリックノートとプライベートノートで共有されます — 単一のテンプレート一覧が両方に使われ、同じテンプレートをどちらのノートにも挿入できます。

管理は **Incidents → Settings → Note Templates** で行います — カードのタイトルは **Public or Private Note Templates for Incidents** で、フォームには本体の **Template Info** ステップ(**Template Name** と **Template Description**、どちらも必須)と **Note Details** ステップがあります。テンプレートを作成する前に **Create from Template** をクリックすると、OneUptime はまだ存在しないと伝えます。なお、そのメッセージは Project Settings を指していますが、実際のページは **Incidents → Settings → Note Templates** の下にあります。

## Slack や Microsoft Teams からノートを投稿する

ワークスペースを接続していれば、対応者はチャンネルを離れる必要がありません。Slack と Microsoft Teams はどちらもノート追加アクションを提供しており、これを開くと **Public Note** か **Private Note** を選ぶドロップダウンとテキストボックスを持つモーダルが表示され、その結果がそのままインシデントに書き込まれます。

知っておくべき点が 2 つあります。

- **重複防止** — 各ノートは元になった Slack メッセージ(`postedFromSlackMessageId`、`channel_id:message_ts` の形式)を記録するため、複数人が同じメッセージにリアクションしても、ノートは 1 件だけ生成され 5 件にはなりません。
- **ノートがチャンネルに反映される** — どちらの種類のノートを投稿しても、接続されたインシデントチャンネルにメッセージが送られます。これはノートのフィードアイテムがワークスペース通知を有効にした状態で作成されるためです。

## パブリックノートが実際に購読者に届くとき

**Notify Status Page Subscribers** をオンにしてパブリックノートを作成しただけでは、メールが送られることは保証されません。ノートは一連のチェックをクリアする必要があり、失敗するたびにエラーではなく具体的な理由が記録されます。

1. **Notify Status Page Subscribers** がオンでなければなりません。オフの場合、ノートは作成された瞬間にスキップ済みとしてスタンプされます。
2. ノートは、まだ存在しているインシデントに属していなければなりません。
3. インシデントには少なくとも 1 つのモニターが紐付いていなければなりません — モニターがなければ、ノートを送り届けるステータスページ側のリソースが存在しません。
4. インシデントの **Visible on Status Page** フラグ(`isVisibleOnStatusPage`)が true でなければなりません。
5. インシデントが表示される各ステータスページで **Show Incidents**(`showIncidentsOnStatusPage`)がオンになっていなければなりません。
6. 各購読者は自分自身の設定をクリアしていなければなりません — 購読解除しておらず、このリソースと、ページが選択を許している場合は `Incident` イベントタイプの両方を購読している必要があります。

**通知は即時ではありません。** 通知を送るジョブは 1 分ごとに実行されるため、ノートを保存してからメールが送られるまで最大で約 1 分程度かかると見込んでください。それが **Sending Soon** ラベルの意味です。

**Subscriber Notification Status** 列は、その一連の流れ全体を追跡します。

| ステータス                    | 意味                                                    |
| ----------------------------- | ------------------------------------------------------- |
| **Notifications skipped.**    | 上記のゲートのいずれかで止まりました。理由が記録されます。 |
| **Sending Soon**              | キューに入っており、送信ジョブの次の実行を待っています。 |
| **Notifications Being Sent**  | ジョブが購読者リストを順に処理しています。               |
| **Notifications Sent**        | すべての購読者通知が送信されました。                     |
| **Failed**                    | ジョブがエラーになりました。エラーはノートとともに保存されます。 |

ステータス上の **more details** をクリックすると **Notification Status Details** が開きます。再送信が意味を持つ場合、そのモーダルのボタンは **Retry** で、これはノートを保留状態に戻し、次回の実行で再度拾われるようにします。

購読者が実際に受け取るメッセージは、ステータスページごと、チャンネルごとにテンプレート化されています — メール、SMS、Slack、Microsoft Teams はそれぞれ **Subscriber Incident Note Created** イベント用の独自テンプレートを持ち、ステータスページ名と URL、詳細リンク、影響を受けるリソース、インシデントの重大度とタイトル、ノート本文、購読者ごとの購読解除リンクといった変数を使えます。これらのテンプレートとチャンネルの設定方法については [購読者とお知らせ](/docs/status-pages/subscribers) を参照してください。

## インシデントフィード

**Incident Feed** カードは、インシデントの **Overview** ページの左カラム下部にあります。これはインシデントの出来事を時系列で語るものです — 各項目は、アイコン、原因となった人物のアバターと名前、ホバーすると正確なローカル時刻が表示される相対タイムスタンプ、そして Markdown 本文から成ります。項目は古い順に並びます。

一部の項目は追加の詳細を持ちます — たとえば所有者通知の項目は、メールが送られた全員を一覧表示します。そうした項目には **More Information** ボタンがあり、**More Information** パネルが開きます。

カードのヘッダーには **Actions** メニューもあり、タイムラインを離れずに操作できます。

- **Execute Runbook** — このインシデントに対して [Runbook](/docs/runbooks/index) を開始します。
- **Execute On-Call Policy** — オンデマンドでポリシーをページします。
- **Add Public Note** — Public Notes ページと同じ 4 つのフィールドが、モーダルで開きます。
- **Add Private Note** — ノート本文と添付ファイルだけです。

その隣にある **Refresh** はフィードを再取得します。

**フィードは追記専用であり、監査ログではありません。** API はフィード項目の作成と読み取りは許可しますが、更新や削除は許可しないため、誰もインシデントの履歴を静かに書き換えることはできません。永続的でもありません — 課金対象のインストールでは、3 年より古いフィードの行は削除されます。誰が何を変更したかの永続的な記録が必要な場合は、インシデントのサイドメニューの **Audit → Audit Logs** を使ってください。

## フィードが記録するもの

フィード項目は、インシデントサービス自身、両方のノートサービス、状態タイムライン、所有者とメンバーの変更、ルールエンジン、オンコール実行、AI 調査とポストモーテムのランナー、そして通知の cron ジョブによって書き込まれます。イベントタイプは次をカバーします。

- **インシデント自体** — `IncidentCreated`、`IncidentUpdated`、`IncidentStateChanged`。
- **ノートと書き起こし** — `PublicNote`、`PrivateNote`、`RootCause`、`RemediationNotes`、`PostmortemNote`。
- **人** — `OwnerUserAdded`、`OwnerTeamAdded`、`OwnerUserRemoved`、`OwnerTeamRemoved`、`IncidentMemberAdded`、`IncidentMemberRemoved`。
- **通知** — `OwnerNotificationSent`、`SubscriberNotificationSent`、`OnCallPolicy`、`OnCallNotification`。
- **自動化** — `LabelRuleExecuted`、`OwnerRuleExecuted`、`PrivacyRuleExecuted`、`OnCallRuleExecuted`、`AutoRemediation`。

各タイプにはそれぞれ専用のアイコンがあるため、長いフィードでも状態変化と雑多な項目を見分けながらざっと確認できます。AI が生成した根本原因分析は明確に区別され、制限付きの Markdown モードでレンダリングされます。

フィードはインシデントのプライバシー設定を尊重します — プライベートインシデントでは、フィードの読み取りもインシデント自体と同じように絞り込まれます。

## Owners

Owners は、インシデントに責任を持つ人とチームです。インシデントに起きるすべてのことの通知先であり、誰かが対応していると全員が思い込んで、インシデントが見過ごされずに済む理由でもあります。

インシデントのサイドメニューで **Team → Owners** を開きます。**Owners** カードには件数バッジがあり、Owners はこのインシデントに責任を持ち変更を通知される人とチームであると説明され、「2 人 · 1 チーム」のような件数が表示されます。Owners は重なり合ったアバターとして表示され、いずれかにホバーすると、その人のメールアドレスが表示されるか、その項目が **Team** であることが示されます。

- **Add owner** をクリックすると、人またはチームを検索できる検索ボックス付きのピッカーが開きます。
- アバターの削除コントロールをクリックすると **Remove owner** 確認が開き、続けて **Remove** します。
- Owners がまだいない場合、カードはその旨を伝え、変更を通知できるようチームメイトかチームを追加するよう促します。

所有者ユーザーと所有者チームは別々のレコードです — チームを追加すると、通知の目的においてはそのチームの全メンバーが個別に列挙されることなく所有者になります。

## Owners への追加のされ方

Owners リストに載る経路は 4 つあります。

- **インシデントテンプレートから** — テンプレートは **Owner - Teams** と **Owner - Users** フィールドを持ち、作成時または更新時に通知される、インシデントを所有するチームとユーザーとして説明されています。テンプレートからインシデントを作成すると、これらが事前入力されます。[インシデントの宣言](/docs/incidents/declaring-incidents) を参照してください。
- **Incident Owner Rules から** — 一致するルールが作成時に自動で所有者を追加します。
- **API 経由の作成時に** — 作成呼び出しとともに渡された所有者ユーザーとチームは即座に追加され、「追加されました」というメールを送るかどうかを制御するフラグも付きます。
- **手作業で** — インシデントの最中いつでも、**Owners** ページの **Add owner** コントロールを使います。

同じ人を 2 回追加しても安全です。すでに割り当てられている所有者は重複しません。

## インシデント所有者ルール

**Incident Owner Rules** は、一致するインシデントが作成されたときに所有者ユーザーとチームを自動で割り当てます — データベースのインシデントが、誰も意識しなくてもデータベースチームにたどり着く、その経路づけの層です。他のインシデント自動化とあわせて [インシデントの設定と自動化](/docs/incidents/settings) にまとめてあります。

ルールフォームには 3 つのステップ — **Basic Info**、**Match Criteria**、**Owners** — があり、Owners ステップには 2 つのセクションがあります。

- **Owners to Assign** — **Owner Teams** と **Owner Users** を選びます。ルールが一致すると、選択されたすべてのユーザーとチームが所有者として追加され、すでに割り当てられている所有者は重複しません。
- **Inherit Owners** — 名前を指定する代わりに、関連するエンティティから所有者を割り当てます。**Inherit Owners From Monitors** はインシデントのモニターの所有者全員をインシデントの所有者にし、**Inherit Owners From Hosts**、**… From Kubernetes Clusters**、**… From Docker Hosts**、**… From Podman Hosts**、**… From Services** も、それぞれのリソースについて同じことを行います。

**Notify Owners** トグルは、人々に知らせるかどうかを制御します。実際にルーティングとして使うならオンのままにしておき、静かに所有者を追加したいだけなら — ルールが単なる帳簿づけの便宜であり、ページングではない場合に有用です — オフにします。

すべてのルール実行はインシデントフィードに書き込まれるため、ある人がルールによって追加されたのか人間によって追加されたのかを常に判別できます。

## Owners が通知される内容

5 つのジョブが、それぞれ 1 分ごとに実行されて所有者に通知します。

- **インシデントが作成された** — 件名 `[New Incident {number}] - {title}`。
- **ノートが投稿された** — パブリックノートとプライベートノートの両方が対象で、件名 `[Update Incident {number}] - {title}`。
- **インシデントの状態が変化した** — [インシデントの状態と重大度](/docs/incidents/states-and-severities) を参照してください。
- **あなたが所有者として追加された** — 件名 `You have been added as the owner of Incident {number} - {title}`。
- **まだ未解決** — インシデントの次回リマインダー時刻に基づくリマインダーで、件名 `[Reminder] Incident {number} is still {state} - {title}`。

各通知はメール、SMS、音声通話、プッシュ、WhatsApp 向けに組み立てられ、実際に何を送るかを決めるユーザーの通知設定に渡されます。すべての受信者は、これらの各項目を個別にオフにできます — ユーザーごとの設定は、インシデント作成、ノート投稿、状態変更、所有者追加、メンバー割り当て、未解決リマインダーの各通知を送信するかどうかという言葉で表現されています。状態変化のときだけ電話がほしい人は、ちょうどそれだけを受け取ることもできます。

**所有者がいないインシデントも、通知が止まるわけではありません。** インシデントにまったく所有者がいない場合、通知ジョブはプロジェクトの所有者にフォールバックするため、何も見落とされずに済みます。通知されたすべての人は、対応するフィード項目にも追記されるため、後から誰にどのアドレスで伝わったかを正確に確認できます。
