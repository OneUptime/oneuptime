# インシデントの状態と重大度

すべてのインシデントは 2 つの分類を持ちます — 対応のどこにいるかを示す **状態**、そしてどれだけ深刻かを示す **重大度** です。ダッシュボードでは似たように見えます — どちらもインシデント一覧では色付きのピルとして表示され、どちらも名前と色を変更できるプロジェクトスコープのリストです。しかし、それぞれが担う役割はまったく異なります。

状態は挙動を左右します。状態の行にある 3 つの真偽値フラグが、どのインシデントがアクティブとしてカウントされるか、インシデントヘッダーにどのボタンが表示されるか、SLA の時計がいつ止まるか、そしてインシデントがいつステータスページから外れるかを決めます。重大度はそれ自体では何も動かしません — 影響の度合いを表すラベルであり、他のルールが一致条件として参照できるものです。

どちらのリストもプロジェクト作成時にシードされ、どちらも **インシデント → 設定** の下で編集します。インシデントのサイドメニューのこのセクションは既定で折りたたまれているので、探す前に **設定** を展開してください。

## 状態は挙動を運び、重大度は意味を運ぶ

`IncidentState` モデルは `name`、`description`、`color`、`order` に加えて、3 つの真偽値 `isCreatedState`、`isAcknowledgedState`、`isResolvedState` を持ちます。状態に関して製品が行うことはすべて、これらの真偽値と `order` を起点にしており — 状態の名前を起点にすることは決してありません。だからこそ **解決済み** を「Closed」に改名しても何も壊れないのです — フラグはその行に付いて回ります。

`IncidentSeverity` モデルは `name`、`description`、`color`、`order` を持ち、それ以外は何もありません。フラグはありません。OneUptime のどこにも、**Critical Incident** を **Minor Incident** と単独で区別して扱うコードはありません。重大度が意味を持つのは、あなたが何かをそれに向けて紐付けたとき、たとえばオンコールルールの **Incident Severities** 一致条件の中だけです。

いくつか簡単なルールがあります。

- **影響を伝えるために重大度を選びます** — インシデント一覧、インシデントの **概要** に表示され、インシデントを宣言する際の必須フィールドです。
- **プロセスをモデル化するために状態を選びます** — 実際にたどる対応のステップを、実際にたどる順序で並べます。
- **状態に緊急度をエンコードしないでください** — 「Critical」という名前の状態を作っても、誰かを呼び出すわけではありません。それを行うのは重大度とオンコールルールの組み合わせです。

## シードされる状態

プロジェクトの作成と同時に、次の順序で 3 つの状態が作成されます。シードは冪等です — 同じ名前の状態がすでに存在する場合は追加されません。

| 状態             | `order` | フラグ                 | 色        | 意味                                             |
| ---------------- | ------- | ---------------------- | --------- | ------------------------------------------------ |
| **Identified**   | `1`     | `isCreatedState`       | `#fd625e` | 新規インシデントが入る状態。                      |
| **承認済み**     | `2`     | `isAcknowledgedState`  | `#ffbf53` | 誰かがインシデントを引き受けた状態。              |
| **解決済み**     | `3`     | `isResolvedState`      | `#2ab57d` | インシデントが終了し、アクティブとしてカウントされなくなる状態。 |

名前に注目してください。最初の状態は **Identified** ですが、製品内のいくつかの説明では今も「created」状態と呼ばれています。ドキュメントやツールチップが「created state」と言うとき、それは `isCreatedState` フラグを持つ状態のことを指します — 新規プロジェクトでは、それは **Identified** です。

## 各状態フラグが実際に行うこと

| フラグ                 | 用途                                                                                                                                        |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `isCreatedState`       | 誰も状態を選ばなかったときにインシデントが持つ状態。プロジェクト内のどの状態もこのフラグを持たない場合、インシデントの作成は失敗し、設定から作成状態を追加するよう伝えるエラーが表示されます。 |
| `isAcknowledgedState`  | **Acknowledge** ボタンと、インシデントの **概要** にある「<状態名> in」統計タイルを動かします。この状態への状態変更が発生すると、インシデントの SLA は応答済みとマークされます。 |
| `isResolvedState`      | **解決** ボタンと解決済み統計タイルを動かし、**アクティブなインシデント** リストを定義し、インシデントをステータスページのアクティブセクションから除外するものです。SLA を解決済みとマークします。 |

各フラグを持つ状態はプロジェクトごとに 1 つだけであることが想定されています — 検索は単一行を取得します。フラグを持つ 3 つの状態は名前の変更、色の変更、並べ替えが可能ですが、設定ページはそれらの削除を拒否し、作成状態、承認状態、解決状態を名指ししたエラーを表示します。

UI は状態名を動的に読み取るため、状態名を変更するとあらゆる場所での見え方が変わります — 統計タイル、確認モーダルのタイトル、インシデント一覧のピルはすべて、その行に付けた名前に従います。

## 独自の状態を追加する

**インシデント → 設定 → インシデントの状態** に移動します。このページは `order` の昇順でソートされた順序付きリストで、新しい状態は末尾に追加されます。行をドラッグすると位置を変更できます。

**状態のフィールド:**

- **Name** — 必須、2 文字以上。プレースホルダーは「Investigating」のようなものを示唆します。
- **Description** — 任意の自由記述で、インシデントがこの状態にあるのはどういうときかを説明します。
- **Color** — 必須。カラーピッカーから選び、`#fd625e` のような 16 進値として保存されます。

このフォームから 3 つのフラグを設定することはできません — それらはシードされた行に属します。したがって、あなたが追加する状態はフラグなしの状態であり、これには計画しておくべき 2 つの結果があります。

- **アクティブとしてカウントされます。** **アクティブなインシデント** は「現在の状態が解決状態ではない」と定義されているため、解決状態以外に追加したものは何であれ、インシデントをアクティブなリストとサイドバーの件数に留めます。
- **遷移ボタンが汎用のものになります。** **Acknowledge** や **解決** の代わりに、確認モーダルのタイトルは **Mark Incident as `<状態名>`** となり、送信ボタンは **Mark as `<状態名>`** になります。

よくある形は、承認済み状態と解決済み状態の間にトリアージや軽減のステップを挿入することです — たとえば、新しい「Mitigated」状態をドラッグして **承認済み** の後、**解決済み** の前に配置します。

## 順序は表示上の好みではなく、実質的な制約です

`order` カラムは、リストが描画されるときだけでなく、状態変更が書き込まれるときにも強制されます。

- **後戻りする遷移は拒否されます。** インシデントを、現在の状態より順序が前にある状態に移動しようとすると、両方の状態名を挙げたエラーで失敗します。
- **現在と同じ状態を再選択することは拒否されます。** インシデントをすでにその状態に設定しようとすると、「Incident state cannot be same as previous state.」で失敗します。
- **さかのぼって追加した行は、隣接する行と重複できません。** 直後に続く行と同じ状態を持つタイムライン行の挿入も拒否されます。
- **ヘッダーのボタンは、順序の中でのフラグ付き状態の位置に従います。** **Acknowledge** と **解決** は、現在の状態が順序でソートされたリストのどこにあるかに基づいて提供されます。解決状態の *あとに* 配置されたカスタム状態は、決して **解決** ボタンを表示しません。なぜなら、そこから先へ進める先が何もないからです。

したがって、状態を追加するときは、インシデントが実際にそこを通過する位置に配置してください。順序を間違えると、単に見た目が変になるだけでなく、遷移そのものが不可能になります。

## シードされる重大度

プロジェクトの作成と同時に、次の順序で 3 つの重大度が作成されます。

- **Critical Incident**（`order` 1、`#b70400`） — 顧客に対する影響が非常に大きく、即時対応が必要な問題。完全な障害やデータ漏洩など。
- **Major Incident**（`order` 2、`#fd625e`） — 影響が大きく、通常は即時対応が必要で、被害を抑える回避策がある場合もあります。重要なサブシステムの障害など。
- **Minor Incident**（`order` 3、`#ffbf53`） — 影響が小さく、通常は業務時間内に対応でき、ほとんどの顧客は気づかない可能性が高いもの。アプリケーションの性能がわずかに低下した場合など。

重大度はインシデントを宣言する際に必須であり、モニターの条件にある各インシデント仕様でも必須です。そのため、手動であれ自動であれ、すべてのインシデントは重大度を伴って届きます。宣言のフローについては [インシデントの宣言](/docs/incidents/declaring-incidents) を、モニター駆動の経路については [Incident and Alert Templating](/docs/monitor/incident-alert-templating) を参照してください。

## 重大度を編集する

**インシデント → 設定 → インシデントの重大度** に移動します。状態のページと同じ形です — `order` でソートされた順序付きリストで、ドラッグして並べ替え、新しい重大度は末尾に追加され、フォームには **Name**、**Description**、**Color** があります。

状態との違いは 2 つです。

- **削除のガードがありません。** シードされた 3 つを含め、どの重大度も削除できます。
- **継承すべきフラグがありません。** 新しい重大度は、シードされたものとまったく同じように振る舞います — 色と位置を持つラベルです。

**プレースホルダーについての注記。** 重大度のフォームは、状態フォームの例のテキストをそのまま流用しているため、ヒントは重大度ではなく状態について語っています。無視して、独自の重大度名と説明を書いてください。

重大度がラベル以上の働きをする場所 — **インシデント → ルール → オンコールルール** では、ルールの **Incident Severities** フィールドが一致条件になります。そこに **Critical Incident** を挙げることが、「Critical なものはすべてデータベースチームを呼び出す」を表現する方法です — オンコールポリシーはルールに属し、重大度には属しません。

## インシデントを状態間で動かす

インシデントの状態が変わる経路は 4 つあります。

- **ヘッダーのボタン。** インシデントを開きます。現在の状態が承認状態より前であれば **Acknowledge** と **解決** が、両者の間であれば **解決** が表示されます。それぞれをクリックすると確認モーダル — **Acknowledge Incident** または **Resolve Incident** — が開き、**Select Note Template**、**Public Note**、**ステータスページの購読者に通知** も併せて提供されます。
- **状態タイムライン。** インシデントの **状態タイムライン** ページから、**Incident Status**、**Starts At**、**ステータスページの購読者に通知** を使って手作業で行を追加します。
- **一括変更。** インシデント一覧には、複数のインシデントを一度に動かすための **状態を変更** 一括アクションがあります。
- **自動的に。** **Auto Resolve Incident** を有効にしたモニター条件は、条件が満たされなくなるとそのインシデントを解決し、API も `/api/incident-state-timeline` を通じて状態を更新できます。

これらはいずれもタイムライン行を書き込みます。状態変更は、あなたが明示的に求めなくてもいくつかのことを行います — インシデントフィードにエントリを投稿し、まだ誰も持っていなければ Incident Commander を割り当て、SLA の時計を更新します。解決済みのインシデントを再オープンすると、再オープン時点から新しい SLA の記録が始まります。

## 状態タイムライン

インシデントのサイドメニューにある **状態タイムライン** ページは、インシデントがこれまでにあったすべての状態の監査証跡です。そのページのカードは **Status Timeline** というタイトルで、新しい順にソートされています。

**列:**

- **Incident Status** — 状態の名前と色を持つ、色付きのピル。
- **Starts At** — インシデントがこの状態に入った日時。
- **Ends At** — 抜けた日時。現在の状態は `Currently Active` と表示されます。
- **Duration** — その状態に費やした時間。現在の状態については現在時刻までがカウントされます。
- **Subscriber Notification Status** — この変更に対するステータスページ通知が送信済みか、スキップされたか、まだ保留中かを示し、**more details** リンクがあり、送信に失敗した場合は **Retry** アクションがあります。

**行のアクション:**

- **View Cause** — その状態変更とともに記録された Markdown をレンダリングする **Root Cause** モーダルを開きます。
- **View Logs** — ステータスが変更された理由を説明するモーダルを開き、**Incident State Log** ビューアーを表示します。

タイムラインの行は作成と削除ができますが、編集はできません。誤った行を削除するとインシデントの履歴が書き換わるので、日常的な整理の習慣としてではなく、訂正の手段として扱ってください。

## アクティブなインシデントのリスト

**インシデント → アクティブなインシデント** は、シフト中に見張るリストです。その定義はただ 1 つの条件です — インシデントの現在の状態が、`isResolvedState` が false である状態であること。それ以外は一切考慮されません — 重大度でも、経過時間でも、誰かが承認したかどうかでもありません。

サイドメニューの項目には同じクエリを使った赤い件数バッジが付いており、バッジとリストは常に一致します。何も見るものがないときは、ページがそう表示します。

実務上の帰結として、追加したカスタム状態はどれも、インシデントをこのリストに留め続けます。それは通常あなたが望むことです — 「Mitigated」は「完了」ではありません — ただし、バッジが実際にクリアされるのは、インシデントが本当に解決状態に到達したときだけです。

## ステータスページ購読者に状態変更を伝える

状態変更はステータスページの購読者にメールを送ることができますが、その前にいくつかのゲートを通過します。これらを理解しておくと、「なぜ誰も通知を受けなかったのか」というデバッグの手間が大きく省けます。

通知は、状態変更モーダルおよび手動タイムラインフォームのチェックボックスである **ステータスページの購読者に通知**（`shouldStatusPageSubscribersBeNotified`）によって、タイムライン行ごとにリクエストされます。オフのとき、その行はスキップ済みステータスと理由付きで保存されます。オンのとき、その行はキューに入れられ、バックグラウンドジョブがそれを拾います — このジョブは毎分実行されるため、配信は速いものの即時ではありません。

**キューに入れられた行は、次のいずれかに該当する場合スキップされます。**

- **新しい状態が作成状態である場合。** 購読者にはインシデントが宣言された時点ですでに知らされているため、最初のタイムライン行は意図的に 2 通目のメッセージを送りません。
- **インシデントにモニターが紐付いていない場合。** リソースがなければ、インシデントを対応付けるステータスページがありません。
- **インシデントがステータスページに表示されない設定になっている場合**（`isVisibleOnStatusPage` がオフ）。
- **ステータスページでインシデントの表示がオフになっている場合**（`showIncidentsOnStatusPage` がオフ）。これはステータスページごとの設定です — 同じモニターを表示している他のページには、通知が届きます。

**結果を変えるもう一つの要素。** 状態変更モーダルに **Public Note** を入力すると、そのタイムライン行はキューに入れられる代わりに、すでに通知済みとしてマークされます。購読者に届くのはそのノート自体であり、2 通ではなく 1 通のメッセージになります。単純な状態変更メッセージの背後にあるイベントタイプは `Subscriber Incident State Changed` です。

これらの通知が誰に届くか、テンプレートがどう選ばれるかについては、[購読者とお知らせ](/docs/status-pages/subscribers) を参照してください。

## インシデントをステータスページに出さないようにする

インシデントが公開ページに表示されるかどうかは、次の 3 つの独立した要素で決まり、3 つとも true でなければなりません。

- ステータスページ自体の **Show Incidents**（`showIncidentsOnStatusPage`）。
- インシデントの **ステータスページに表示**（`isVisibleOnStatusPage`） — インシデントの **設定** ページにあるトグルです。既定で true であり、宣言ウィザードにはありません。モニター条件は **Show Incident on Status Page** でこれを設定できます。
- **現在の状態が解決状態ではないこと。** これが、インシデントをアクティブセクションから外すものです — ステータスページのクエリは、現在の状態が未解決状態であるインシデントを取得します。何かをアーカイブしたりクローズしたりするわけではなく、解決するだけで履歴に移動します。

**プライベートインシデントは決して表示されません。** **プライベートインシデント** をオンにすると、上記のトグルにかかわらず、そのインシデントはすべてのステータスページから隠され、所有者とプロジェクト管理者・オーナーだけに制限されます。

ページがどれだけの解決済み履歴を保持するかは、インシデントではなくステータスページの設定です。ページ上のモニターがそもそもどのインシデントを表示対象とするかについては、[ステータスページのリソースとグループ](/docs/status-pages/resources-and-groups) を参照してください。
