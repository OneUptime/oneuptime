# インシデント 概要

OneUptime のインシデントは、何かが壊れたときにチームが結集するための記録です。番号、タイトル、重大度、現在の状態、影響を受けるリソース、そして対応中にチームが書き留めたすべて — ノート、根本原因、修復手順、そして誰が何をしたかを記録する追記専用のフィード — を保持します。

インシデントは、モニターが赤くなった状態を協調的な対応へと変えるものです。インシデントを宣言すると、適切なオンコールローテーションが呼び出され、あらゆる変更について通知を受ける所有者が追加され、Runbook が開始されます。さらに希望すれば、障害を公開ステータスページに掲載できるので、「もう把握していますか?」と顧客がチケットを開くのを防げます。

インシデントは深夜 3 時に手作業で宣言することも、条件が一致した瞬間にモニターに宣言させることもできます。どちらの経路でも同じオブジェクトであり、同じライフサイクルを持ち、最後に同じ記録が残ります。

## ひと目で

- **トップレベル機能** — ダッシュボードの左ナビゲーションにある **インシデント**。パスは `/dashboard/{projectId}/incidents` です。
- **3 つのシードされた状態** — **Identified**、**承認済み**、**解決済み** が新しいプロジェクトごとに作成されます。独自の状態を追加できます。シードされた 3 つは名前と色を変更できますが、削除はできません。
- **3 つのシードされた重大度** — **Critical Incident**、**Major Incident**、**Minor Incident**。重大度は色と順序を持つラベルであり、それ自体は何の動作も伴いません。
- **4 つの入口** — **インシデントを宣言** ウィザード、**テンプレートから作成**、モニターの条件ルール、または `POST /api/incident`。
- **プロジェクトごとの採番** — すべてのインシデントにインシデント番号が付き、既定では `#42` として、独自のプレフィックスを設定すれば `INC-42` のように表示されます。
- **2 種類のノート** — チーム向けのプライベートノート (内部ノート) と、ステータスページ購読者向けのパブリックノート。
- **設定はプロジェクト設定ではなくインシデントの下にあります** — 状態、重大度、テンプレート、カスタムフィールド、ルールエンジンはすべて **インシデント → 設定** と **インシデント → ルール** にあります。

## キー用語

このセクションのほかのページに何度も登場する言葉がいくつかあります。まずここを揃えておきましょう。

| 用語                     | 意味                                                                                                                                             |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **インシデント**         | 記録そのもの — タイトル、説明、重大度、現在の状態、影響を受けるリソース、そして対応中に書き込まれたすべて。                                      |
| **インシデントの状態**   | インシデントがライフサイクルのどこにいるか。名前、色、`order` を持つプロジェクトスコープの行で、意味を与えるフラグも併せ持ちます。               |
| **インシデントの重大度** | どれくらい深刻か。名前、色、`order` を持つプロジェクトスコープの行です。純粋な分類であり、製品内で特定の重大度が特別扱いされることはありません。 |
| **インシデント番号**     | プロジェクトごとのカウンターで、`#42`、または設定したプレフィックスを付けて `INC-42` と表示されます。                                            |
| **影響を受けるリソース** | インシデントに紐付けるモニター、ホスト、Kubernetes クラスター、Docker ホスト、サービスなどのインフラ。                                           |
| **パブリックノート**     | ステータスページの読者と購読者に向けて書く更新。ステータスページのタイムラインに表示されます。                                                  |
| **プライベートノート**   | 対応チーム向けの内部ノート (`IncidentInternalNote` モデル)。ステータスページに届くことはありません。                                             |
| **所有者**               | インシデントに責任を持つユーザーまたはチーム。作成時、ノート投稿時、状態変更時に通知されます。                                                  |
| **インシデント フィード** | インシデントの **概要** にある追記専用のアクティビティタイムライン。状態変更、ノート、所有者の変更、ルールの実行、通知を記録します。             |
| **状態タイムライン**     | インシデントがいつ、どの状態に、どれくらいの時間いたかの記録 — 各遷移の購読者通知ステータスも含みます。                                          |

## OneUptime がすべてのプロジェクトにシードする 3 つの状態

プロジェクトを作成すると、OneUptime はちょうど 3 つのインシデント状態をこの順序でシードします。

| 状態             | 順序  | 色                 | 意味                                                                     |
| ---------------- | ----- | ------------------ | ------------------------------------------------------------------------ |
| **Identified**   | 1     | 赤 (`#fd625e`)     | 新しく作られたインシデントが入る状態です。これが作成状態です。           |
| **承認済み**     | 2     | 黄 (`#ffbf53`)     | 誰かがインシデントを引き受け、対応中です。                               |
| **解決済み**     | 3     | 緑 (`#2ab57d`)     | インシデントが終了しました。解決するとステータスページから外れます。     |

名前は単なるラベルであり、実際に動作を左右するのは状態の行にある 3 つの真偽値、`isCreatedState`、`isAcknowledgedState`、`isResolvedState` です。プロジェクトごとに、各フラグを持つ状態は 1 つだけであることが前提です。

この区別は聞こえ以上に重要です。

- `isCreatedState` は新しいインシデントがどこから始まるかを決めます。作成時に状態が明示的に選択されていない場合、OneUptime はプロジェクトの作成状態を探してそれを使います。
- `isAcknowledgedState` と `isResolvedState` は、インシデントヘッダーの **Acknowledge** ボタンと **解決** ボタン、インシデントの **概要** にある 2 つの統計タイル、そしてサイドメニューの **アクティブなインシデント** 件数バッジを動かします。
- **アクティブなインシデント** は「現在の状態が解決状態ではない」ことだけで定義されます。したがって、追加した独自の状態は解決状態でない限りすべてアクティブとして扱われます。

**名前に注意してください。** 最初にシードされる状態の名前は **Identified** ですが、製品内のいくつかの説明では今も作成状態と呼ばれています。プロジェクトの状態一覧で「Created」を探しているなら、それは **Identified** という名前の行です。

独自の状態は **インシデント → 設定 → インシデントの状態** で追加できます。新しい状態は順序付きリストの末尾に追加され、ドラッグして並べ替えられます。フラグを持つ 3 つの状態は削除できません — OneUptime がブロックします — が、名前と色は変更できます。UI が状態名を動的に読み取っているのはそのためです。

順序は見た目だけのものではなく強制されます。インシデントは、現在の状態より順序が前にある状態へは移動できません。

詳細は [インシデントの状態と重大度](/docs/incidents/states-and-severities) にあります。

## OneUptime がすべてのプロジェクトにシードする 3 つの重大度

新しいプロジェクトには 3 つの重大度も作成されます。

| 重大度                | 順序  | 色                   | 意味                                                     |
| --------------------- | ----- | -------------------- | -------------------------------------------------------- |
| **Critical Incident** | 1     | マルーン (`#b70400`) | 顧客への影響が非常に大きく、即時対応が必要。             |
| **Major Incident**    | 2     | 赤 (`#fd625e`)       | 影響が大きく、通常は即時対応が必要。                     |
| **Minor Incident**    | 3     | 黄 (`#ffbf53`)       | 影響は小さく、通常は業務時間内に対応。                   |

シードされる説明の全文は [インシデントの状態と重大度](/docs/incidents/states-and-severities) にあります。

重大度が持つのは `name`、`description`、`color`、`order` だけです。フラグはなく、「Critical Incident」を他の行と違う扱いにするコードパスもありません。重大度は人間がトリアージするための手段であり、オンコールルールを書くときの一致条件として利用できますが、重大度を選ぶこと自体が誰かを呼び出すわけではありません。

重大度の編集と追加は **インシデント → 設定 → インシデントの重大度** で行います。

## インシデントの一生

### 1. 宣言される

4 つの経路が同じオブジェクトにたどり着きます。

- **手作業で** — インシデント一覧から **インシデントを宣言** をクリックします。**新しいインシデントを宣言** ウィザードが開き、**インシデントの詳細**、**影響を受けるリソース**、**インシデントの役割**、**オンコール**、**もっと** の 5 ステップで構成されています。
- **テンプレートから** — **テンプレートから作成** をクリックし、保存済みの **インシデントテンプレート** を選びます。テンプレートはタイトル、説明、重大度、初期状態、リソース、オンコールポリシー、所有者、ラベルを事前入力します。
- **モニターから** — 「インシデントを宣言する」トグルを有効にしたモニターの条件ルールが、フィルターに一致した瞬間にインシデントを自動作成します。そこではタイトルと説明で `{{variable}}` テンプレートが使えます。
- **API 経由で** — API キーを使った `POST /api/incident`。サーバーが `declaredAt`、作成状態、インシデント番号を代わりに埋めます。

フィールドごとの詳しい手順は [インシデントの宣言](/docs/incidents/declaring-incidents) を参照してください。

### 2. 適切な人に伝わる

作成時に OneUptime は設定済みの自動化を実行します。ラベルルール、オンコールルール、所有者ルール、Runbook ルールです。インシデントに紐付いたオンコール当番ポリシー — 手動、テンプレート、または一致したオンコールルールによってマージされたもの — は並列で実行されます。

所有者にはメール、SMS、電話、プッシュ、WhatsApp で通知されます。ただし各ユーザー自身の通知設定に従います。インシデントに所有者がまったくいない場合、通知は破棄されるのではなくプロジェクトの所有者にフォールバックします。

インシデントがステータスページに表示され、購読者通知が有効になっていれば、購読者にも伝わります。通知は cron で駆動され毎分実行されるため、即時送信ではなく最大 1 分程度の遅れを見込んでください。

### 3. チームが対応する

対応者はインシデントを承認し、影響を受けるリソースを紐付け、Runbook を実行し、インシデントの役割を割り当て、分かったことを書き留めます — チーム向けにはプライベートノート、顧客向けにはパブリックノート、さらに状況がはっきりしてきたら **根本原因** と **修復** のページも使います。行った操作はすべて **概要** ページの **インシデント フィード** に記録されます。

### 4. 解決される

**解決** をクリックすると、インシデントは解決状態に移り、状態タイムラインに記録され、経過時間の計測が止まり、表示されていたステータスページのアクティブ欄からインシデントが消えます。そのために他に変更する必要はありません — ステータスページのクエリが見ているのは解決状態のフラグだけです。

その後、ポストモーテムを書き、任意でステータスページに公開できます。

## ダッシュボード内でインシデントがある場所

左ナビゲーションの **インシデント** を開きます。サイドメニューは次のセクションに分かれています。

| セクション         | そこで行うこと                                                                                                                                                       |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **概要**           | **すべてのインシデント** と **アクティブなインシデント** — 後者には解決状態にないインシデントの件数を示す赤いバッジが付きます。                                       |
| **エピソード**     | インシデント エピソード。独自のページを持つ別のグルーピング機能です。                                                                                                |
| **AI**             | **調査** と **修復** — 自動調査と自動修復の設定です。                                                                                                                |
| **ワークスペース** | インシデント向けの **Slack** と **Microsoft Teams** の接続。                                                                                                          |
| **ルール**         | ルールエンジン: **グループ化ルール**、**オンコールルール**、**所有者ルール**、**Runbook ルール**、**プライバシールール**、**ラベルルール**、**SLA ルール**、**Reminder Rules**。 |
| **設定**           | **インシデントの状態**、**インシデントの重大度**、**インシデントテンプレート**、**ノートテンプレート**、**ポストモーテムテンプレート**、**カスタムフィールド**、**インシデントの役割**、**その他の設定**。 |

**ルール** と **設定** は既定で折りたたまれています。以降のドキュメントが参照するページを見つけるには展開してください。インシデントの設定はプロジェクト設定の下にはなく、すべてここにあります。

インシデント一覧そのものには **インシデント番号**、**タイトル**、**状態**、**重大度**、**影響を受けるリソース**、**宣言済み**、**期間**、**ラベル**、**所有者** が表示され、複数をまとめて閉じるための **状態を変更** 一括アクションがあります。

## インシデントの各ページに表示される内容

インシデントを開くと、次のようにグループ分けされた左サイドメニューが現れます。

- **概要** — **インシデントの詳細** カード (タイトル、重大度、ラベル、インシデント番号、宣言日時、宣言者、オンコールポリシー)、**影響を受けるリソース** カード、そして **インシデント フィード**。その上には承認までの時間、解決までの時間、合計 **期間** の統計タイルがあります。
- **状態タイムライン** — インシデントが経てきたすべての状態と、**開始**、**終了**、**期間**、各遷移の購読者通知ステータス。**原因を表示** と **ログを表示** で各変更が起きた理由が分かります。
- **SLA** — このインシデントの SLA 追跡。
- **説明**、**根本原因**、**修復** — 3 つの Markdown ページ。ステータスページに表示されるのは説明です。
- **Runbook** — このインシデントに紐付いた Runbook の実行。
- **ポストモーテム** — 事後の書き起こし。任意でステータスページに公開できます。
- **役割**、**オンコール実行**、**所有者** — 誰が対応しているか、どのポリシーが発火したか、誰に通知されるか。
- **通知ログ**、**AI ログ**、**監査ログ** — 何が送信され、何が変更されたか。
- **プライベートノート** と **公開ノート** — サイドメニューの **ノート** セクションの下にあります。
- **カスタムフィールド**、**設定**、**インシデントを削除** — **詳細** の下にあります。**設定** ページには **ステータスページに表示**、**プライベートインシデント**、**Reminders** カードがあります。

[インシデントのメモ、オーナー、フィード](/docs/incidents/notes-owners-and-feed) では、共同作業に関するページを詳しく扱います。

## インシデントと OneUptime のほかの機能との関係

- **モニターが問題を見つけ、インシデントがそれを記録します。** モニターの条件ルールはインシデントを自動で宣言し、タイトル、重大度、オンコールポリシー、所有者、ラベル、修復ノートを事前入力できます。そこで使える変数については [インシデント & アラート テンプレート](/docs/monitor/incident-alert-templating) を参照してください。
- **呼び出しを行うのはオンコールポリシーです。** 宣言ウィザードの **オンコール** ステップ、テンプレート、または **インシデント → ルール → オンコールルール** でポリシーを紐付けます。一致したルールはすべて発火し、実行されるのは一致したすべてのルールと直接紐付けたものの和集合を重複排除したものです。
- **Runbook が何をすべきかを人に伝えます。** Runbook ルールは一致したインシデントの作成時に手順を自動で紐付け、対応者はインシデントから手動で開始することもできます。[Runbook 概要](/docs/runbooks/index) を参照してください。
- **ステータスページが顧客に伝えます。** ページでインシデントが有効になっており、インシデントがステータスページに表示する設定になっており、現在の状態が解決状態でない場合に、インシデントはステータスページのアクティブ一覧に表示されます。プライベートインシデントは常にすべてのステータスページから隠されます。[ステータス ページ 概要](/docs/status-pages/index) を参照してください。
- **ワークフローが周辺を自動化します。** **On Create Incident**、**On Update Incident**、**On Delete Incident** の各トリガーを使えば、インシデントのライフサイクルの上にノーコードの自動化を組み立てられます。[ワークフロー 概要](/docs/workflows/index) を参照してください。
