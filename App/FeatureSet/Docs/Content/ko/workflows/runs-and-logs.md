# 실행 및 로그

워크플로가 실행될 때마다 OneUptime은 무슨 일이 일어났는지에 대한 기록을 저장합니다 — 언제 실행되었는지, 성공했는지, 각 블록이 무엇을 했는지. 이 기록을 **run**이라고 부릅니다. run을 통해 워크플로가 제대로 동작했는지 확인하고, 실패한 워크플로를 디버깅하고, 지난 활동을 되돌아볼 수 있습니다.

## 어디에서 찾나요

| 페이지                       | 보이는 내용                                                                                    |
| ----------------------------- | ---------------------------------------------------------------------------------------------- |
| **Workflows → Runs & Logs**   | 프로젝트의 모든 워크플로에서 발생한 모든 run. 워크플로 이름, 상태, 시간으로 필터링할 수 있습니다. |
| **Workflow → Runs & Logs**    | 이 워크플로 하나의 run만 보여줍니다. 워크플로 필터 대신 **Run ID** 필터가 있습니다.              |
| **단일 run**                  | run 행의 **View Logs** 버튼으로 엽니다 — run 행 자체는 클릭할 수 없습니다.                       |

## run 상태

| 상태                                | 의미                                                                                                                                                                             |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Scheduled**                        | 트리거가 발생했고 run이 러너에 배정되기를 대기 중입니다. 보통 1초도 걸리지 않습니다. 5분이 지나도 여전히 Scheduled 상태라면 아무도 가져가지 않은 것이므로 실패로 간주합니다.        |
| **Running**                          | 워크플로가 진행 중입니다. 오래 실행되는 블록은 run을 이 상태로 유지합니다.                                                                                                       |
| **Waiting**                          | run이 **Sleep** 블록에서 멈춰 있으며 스스로 재개됩니다. 대기하는 동안에는 워커를 점유하지 않습니다.                                                                              |
| **Executed**                         | run이 실패 없이 끝까지 도달했습니다. (이것이 성공 상태입니다 — 표시되는 값은 "Success"가 아니라 **Executed**입니다.)                                                              |
| **Error**                            | 블록이 오류를 일으켜 run이 중단되었습니다. 대기 중이던 run을 아무도 가져가지 않은 경우, 잠들어 있던 run의 재개 정보가 유실된 경우, 스케줄 표현식을 해석할 수 없는 경우, run 도중 워크플로가 비활성화된 경우에도 이 상태가 사용됩니다. |
| **Timeout**                          | run이 허용된 시간보다 오래 실행되었습니다. [워크플로우 설정 및 보안](/docs/workflows/configuration)을 참고하세요.                                                                 |
| **Execution Exceeded Current Plan**  | 프로젝트가 지난 30일 동안의 워크플로 실행 횟수를 모두 소진했거나 구독료가 미납 상태입니다. run은 기록되지만 실행되지는 않습니다. OneUptime Cloud에서만 해당됩니다.               |

**Error** 출력으로 처리를 넘기는 블록 — 예를 들어 4xx를 받은 API 블록 — 은 run을 실패시키지 않습니다. error 분기가 실행되고 run은 그대로 **Executed**로 끝납니다. 다만 해당 단계 자체는 찾기 쉽도록 빨간색으로 표시됩니다.

## run 읽기

run 행에서 **View Logs**를 클릭하면 열립니다. **Workflow Run** 화면에는 두 개의 탭이 있습니다.

**Steps** — 실행된 블록마다 한 행씩, 순서대로 표시됩니다. 각 행에는 블록의 제목, component id, 소요 시간, 결과로 나간 출력(`→ success`, `→ error`, `→ yes`)이 표시됩니다. 행을 펼치면 두 가지 세부 정보 블록이 나타납니다.

- **Received** — 모든 변수가 해석된 후 블록에 전달된 설정 값.
- **Returned** — 블록이 생성한 결과.

실패한 단계는 빨간색이며 처음부터 펼쳐진 상태로 표시되고, **Received** 위에 오류 메시지가 인쇄됩니다.

**Full Log** — 러너가 출력한 원본 로그를 한 줄씩 그대로 보여주며, 블록 자체가 남긴 로그도 포함됩니다. Steps 탭으로 실패 원인을 알 수 없을 때 사용하세요.

알아두면 좋은 두 가지가 있습니다. 각 단계 제목 아래 표시되는 component id는 `{{local.components.<id>.returnValues.…}}` 참조에 그대로 붙여넣을 수 있는 정확한 문자열이므로, 참조를 정확하게 작성하는 가장 빠른 방법입니다. 그리고 run은 마지막 100개의 단계만 보관하며, 길거나 여러 번 재개된 run은 앞부분이 삭제되었다는 노란색 안내가 표시됩니다.

표시되는 값은 변수가 채워진 후 블록이 실제로 본 값이며, 두 가지 예외가 있습니다. 시크릿과 블록이 민감 정보로 표시한 필드는 마스킹되고, 매우 긴 값은 "… (truncated)"로 잘려서 표시됩니다.

**Builder**에서 run을 시작하면 같은 화면이 곧바로 해당 run을 따라가며 열리므로, 나중에 찾아다닐 필요 없이 실시간으로 지켜볼 수 있습니다.

## 일반적인 디버깅

### "워크플로가 실행되지 않았어요."

1. **Overview** 페이지에서 워크플로가 **Enabled** 상태인지 확인하세요. 새 워크플로는 비활성화 상태로 시작하며, 비활성화된 워크플로는 수동 실행을 포함한 모든 run을 거부합니다.
2. OneUptime 이벤트 트리거의 경우 해당 이벤트가 실제로 발생했는지 확인합니다. 레코드를 열고 이력을 확인하세요.
3. webhook 트리거의 경우 다른 시스템이 올바른 URL로 보내고 있는지 확인합니다. 대부분의 도구는 webhook을 보낼 때 기록을 남기므로 거기서 확인하세요.
4. schedule 트리거의 경우 cron 표현식이 예상한 시간과 일치하는지 확인합니다.

run이 나타나긴 하지만 상태가 **Execution Exceeded Current Plan**이라면, 프로젝트가 지난 30일 동안의 워크플로 실행 횟수를 모두 소진했거나 구독료가 미납 상태인 것입니다. run의 로그에 사용 횟수와 플랜 한도가 명시되어 있습니다. OneUptime Cloud에서만 해당됩니다.

### "이후 블록이 실행되지 않았어요."

블록이 실행되지 않는 것은 대개 연결 문제입니다. **Builder**를 열고 다음을 확인하세요.

- 이전 블록의 출력이 이 블록의 입력에 연결되어 있나요?
- 이전 블록이 예상과 다른 출력을 사용했나요 — **Success** 대신 **Error**, 또는 **Yes** 대신 **No**? Steps 탭에서 어느 쪽으로 갔는지 확인할 수 있습니다.

### "변수가 비어 있게 들어왔어요."

run을 열고 실패한 단계의 **Received** 블록을 확인하세요.

- `{{local.components.…}}` 라는 텍스트가 그대로 보인다면 참조가 해석되지 않은 것입니다. 보통 component id나 return-value id의 오타가 원인이며, 화면에 표시되는 이름이 아니라 블록의 **Identifier**를 사용해야 한다는 점을 기억하세요. `local.components` 자체의 철자도 확인하세요 — `{{local.componets.api-get-1.returnValues.response-body}}`는 그대로 문자로 전송되며 run은 여전히 **Executed**로 표시됩니다.
- 빈 문자열이 보인다면 이전 블록은 실행되었지만 해당 필드를 생성하지 않은 것입니다.

**Full Log** 탭에는 해석되지 않은 참조를 알려주는 경고 줄이 있으며, 이를 확인하는 것이 대개 가장 빠른 방법입니다.

### "수동으로 실행하면 동작하는데, 트리거에서는 안 돼요."

**Builder**를 열고 **Run Workflow**를 클릭한 다음, 실제 트리거가 보낼 법한 값으로 트리거 필드를 채웁니다. 그런 다음 이 run의 **Received** 값을 실제 run의 값과 나란히 비교합니다. 차이는 대개 필드 이름 하나 또는 타입 하나입니다.

## 워크플로 다시 실행하기

"이 run 다시 시도" 버튼은 없습니다. Slack 메시지, API 호출, 티켓 등 부작용을 반복하는 것이 안전하지 않을 수 있기 때문에 과거 실행을 자동으로 다시 실행하지 않습니다. 작업을 다시 수행하려면 워크플로를 수정하고 다음 실제 트리거가 발생하도록 하거나, **Builder**를 열고 같은 값으로 **Run Workflow**를 클릭하세요.

## run은 얼마나 오래 보관되나요?

OneUptime Cloud에서는 run이 **30일** 동안 보관된 후 삭제됩니다 — 두 run 목록 모두 스스로를 "지난 30일"의 기록이라고 설명하는 이유가 이것입니다. 셀프 호스팅 설치에서는 삭제하기 전까지 run이 계속 보관되므로, 워크플로가 매우 자주 실행되어 이력을 어지럽힌다면 비활성화하거나 삭제하여 노이즈를 줄이세요.

step 추적 기능이 추가되기 전에 기록된 run에는 **Steps** 내용이 없으며 **Full Log**만 표시됩니다.
