# 실행 및 로그

워크플로가 실행될 때마다 OneUptime은 무슨 일이 있었는지 기록해 둡니다 — 언제 실행됐는지, 잘 동작했는지, 각 블록이 무엇을 했는지. 이 기록을 **실행**이라고 부릅니다. 워크플로가 제대로 동작했는지 확인하고, 실패한 워크플로를 디버깅하고, 지난 활동을 되짚어 볼 때 모두 실행 기록을 봅니다.

## 실행 기록을 찾는 곳

| 페이지                        | 볼 수 있는 것                                                                                       |
| --------------------------- | ---------------------------------------------------------------------------------------------------- |
| **워크플로 → 실행 및 로그** | 프로젝트의 모든 워크플로에서 발생한 모든 실행. 워크플로 이름, 상태, 시간으로 필터링할 수 있습니다.           |
| **개별 워크플로 → 실행 및 로그**  | 이 워크플로 하나의 실행만. 여기에는 워크플로 필터 대신 **실행 ID** 필터가 있습니다.  |
| **실행 하나**            | 실행 행의 **로그 보기** 버튼으로 엽니다 — 행 자체는 클릭되지 않습니다.           |

## 실행 상태

| 상태                             | 의미                                                                                                                                             |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **예정됨**                      | 트리거가 발생했고 실행이 러너를 기다리는 중입니다. 보통 1초도 걸리지 않습니다. 5분이 지나도 여전히 예정 상태인 실행은 실패로 처리됩니다 — 아무도 가져가지 않은 것입니다. |
| **실행 중**                        | 워크플로가 진행 중입니다. 오래 걸리는 블록이 있으면 실행이 이 상태에 머무릅니다.                                                                                |
| **대기 중**                        | 실행이 **Sleep** 블록에서 멈춰 있으며 스스로 다시 이어집니다. 기다리는 동안 워커를 점유하지 않습니다.                                                      |
| **Executed**                       | 실행이 실패 없이 끝까지 도달했습니다. (이것이 성공 상태입니다 — 알약 표시에는 "Success"가 아니라 **Executed**라고 나옵니다.)                                        |
| **오류**                          | 블록이 오류를 일으켜 실행이 멈췄습니다. 대기 중이던 실행을 아무도 가져가지 않았을 때, 잠자던 실행의 재개 신호를 잃었을 때, 일정 표현식을 해석할 수 없을 때, 실행 도중 워크플로가 비활성화됐을 때도 이 상태가 됩니다. |
| **Timeout**                        | 실행이 허용된 시간보다 오래 걸렸습니다. [워크플로우 설정 및 보안](/docs/workflows/configuration)을 참고하세요.                                                              |
| **Execution Exceeded Current Plan** | 프로젝트가 최근 30일간의 워크플로 실행 횟수를 모두 사용했거나 구독이 미결제 상태입니다. 실행은 기록되지만 수행되지는 않습니다. OneUptime Cloud에만 해당합니다. |

블록이 **Error** 출력으로 빠진다고 해서 — 이를테면 API 블록이 4xx를 받은 경우 — 실행 전체가 실패하지는 않습니다. 오류 분기가 실행되고, 실행은 그대로 **Executed**로 끝납니다. 다만 해당 단계는 찾기 쉽도록 여전히 빨간색으로 표시됩니다.

## 실행 기록 읽기

실행의 **로그 보기**를 클릭하면 열립니다. **Workflow Run** 화면에는 탭이 두 개 있습니다.

**단계** — 실행된 블록마다 한 줄씩, 순서대로 보여 줍니다. 각 줄에는 블록의 제목, 구성 요소 id, 걸린 시간, 그리고 어느 출력으로 빠져나갔는지(`→ success`, `→ error`, `→ yes`)가 나옵니다. 줄을 펼치면 두 가지 상세 내용이 나옵니다.

- **Received** — 모든 변수가 해석된 뒤 블록에 전달된 설정.
- **Returned** — 블록이 만들어 낸 결과.

실패한 단계는 빨간색이고 처음부터 펼쳐진 상태이며, **Received** 위에 오류 메시지가 표시됩니다.

**Full Log** — 러너가 출력한 한 줄 한 줄의 원본 로그로, 블록이 스스로 기록한 내용까지 담겨 있습니다. 단계 화면만으로 실패 원인이 설명되지 않을 때 사용하세요.

알아 두면 좋은 두 가지가 있습니다. 각 단계 제목 아래에 찍히는 구성 요소 id는 `{{local.components.<id>.returnValues.…}}` 참조에 그대로 붙여 넣으면 되는 문자열이라, 참조를 정확히 만드는 가장 빠른 방법입니다. 그리고 실행 기록은 마지막 100단계만 보관하므로, 길거나 여러 번 재개된 실행에서는 앞부분이 잘려 나간 자리에 주황색 안내가 나타납니다.

표시되는 값은 변수가 채워진 뒤 블록이 실제로 본 값이며, 예외는 두 가지입니다. 시크릿과 블록이 민감하다고 표시한 필드는 가려지고, 아주 긴 값은 "… (truncated)"로 잘립니다.

**빌더**에서 실행을 시작하면 바로 이 화면이 실행을 따라가는 상태로 열리므로, 나중에 찾아 나설 필요 없이 진행 과정을 지켜볼 수 있습니다.

## 자주 겪는 문제

### "워크플로가 실행되지 않았어요."

1. 워크플로의 **개요** 페이지에서 **활성화됨**인지 확인하세요. 새 워크플로는 비활성화 상태로 시작하고, 비활성화된 워크플로는 수동 실행을 포함해 모든 실행을 거부합니다.
2. OneUptime 이벤트 트리거라면 그 이벤트가 정말 일어났는지 확인하세요. 해당 레코드를 열어 이력을 살펴보면 됩니다.
3. 웹훅 트리거라면 상대 시스템이 올바른 URL로 보내고 있는지 확인하세요. 대부분의 도구는 웹훅을 보낼 때 기록을 남기니 거기서 확인하면 됩니다.
4. 일정 트리거라면 cron 표현식이 기대한 시각과 맞는지 확인하세요.

실행 기록이 **Execution Exceeded Current Plan** 상태로 나타난다면, 프로젝트가 최근 30일간의 워크플로 실행 횟수를 모두 사용했거나 구독이 미결제 상태입니다. 실행 로그에 사용량과 플랜 한도가 함께 적혀 있습니다. 이는 OneUptime Cloud에만 해당합니다.

### "뒤쪽 블록이 실행되지 않았어요."

블록이 실행되지 않는 것은 대개 연결 문제입니다. **빌더**를 열고 확인하세요.

- 앞선 블록의 출력이 이 블록의 입력에 연결되어 있나요?
- 앞선 블록이 예상과 다른 출력으로 빠지지는 않았나요 — **Success** 대신 **Error**, **예** 대신 **아니오** 같은 경우 말입니다. 단계 탭을 보면 어느 쪽으로 갔는지 알 수 있습니다.

### "변수가 비어서 넘어왔어요."

실행 기록을 열어 실패한 단계의 **Received** 항목을 살펴보세요.

- `{{local.components.…}}` 문구가 그대로 보인다면 참조가 해석되지 않은 것입니다. 대개 구성 요소 id나 반환값 id의 오타입니다 — 블록에 표시된 이름이 아니라 블록의 **Identifier**라는 점을 기억하세요. `local.components` 자체의 철자도 확인해 보세요. `{{local.componets.api-get-1.returnValues.response-body}}`는 문자 그대로 전송되고, 실행은 여전히 **Executed**로 보고됩니다.
- 빈 문자열이 보인다면 앞선 블록은 실행됐지만 그 필드를 만들어 내지 않은 것입니다.

**Full Log** 탭에는 해석되지 않은 참조를 이름과 함께 알려 주는 경고 줄이 남으며, 보통 이것이 원인을 찾는 가장 빠른 길입니다.

### "손으로 실행하면 되는데 트리거로는 안 돼요."

**빌더**를 열고 **워크플로 실행**을 클릭한 다음, 실제 트리거가 보내는 것과 비슷한 값으로 트리거의 필드를 채우세요. 그런 뒤 그 실행의 **Received** 값과 실제 실행의 값을 나란히 비교해 보세요. 차이는 대개 필드 이름 하나 또는 타입 하나입니다.

## 워크플로 다시 실행하기

"이 실행 다시 시도" 버튼은 없습니다. Slack 메시지, API 호출, 티켓처럼 부수 효과를 다시 일으켜도 안전하다는 보장이 없기 때문에, 지난 실행을 자동으로 되돌려 실행하지 않습니다. 같은 작업을 다시 하려면 워크플로를 고친 뒤 다음 실제 트리거가 발생하기를 기다리거나, **빌더**를 열고 같은 값으로 **워크플로 실행**을 클릭하세요.

## 실행 기록은 얼마나 보관되나요?

OneUptime Cloud에서는 실행 기록을 **30일** 동안 보관한 뒤 삭제합니다 — 두 실행 목록이 모두 최근 30일을 다룬다고 안내하는 이유입니다. 자체 호스팅 설치본은 여러분이 지울 때까지 보관합니다. 아주 자주 실행되는 워크플로 때문에 이력이 지저분해진다면, 해당 워크플로를 비활성화하거나 삭제해 더 이상 쌓이지 않게 하세요.

단계 추적 기능이 추가되기 전에 기록된 실행에는 **단계** 내용이 없고 **Full Log**만 표시됩니다.
