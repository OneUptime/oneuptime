# 설정 및 보안

이 페이지는 워크플로를 실제 트래픽에 연결하기 전에 알아 두면 좋은 설정과 안전 한도를 다룹니다.

## 워크플로 켜고 끄기

모든 워크플로에는 **설정**에 **활성화됨** 스위치가 있습니다. 꺼져 있으면 워크플로는 실행되지 않습니다 — 웹훅 호출도, 예약된 시각도, OneUptime 이벤트도 모두 무시됩니다. 새 워크플로는 비활성화 상태로 시작합니다.

이 스위치를 "준비 완료" 관문으로 사용하세요.

1. 워크플로를 만듭니다.
2. **빌더**에서 현실적인 값으로 **워크플로 실행**을 클릭합니다.
3. **로그**를 확인합니다 — 모든 블록이 예상한 대로 흘러갔는지 살펴보세요.
4. **활성화됨**을 켭니다.

워크플로를 꺼도 이미 진행 중인 실행이 멈추지는 않습니다. 새로운 실행이 시작되지 않을 뿐입니다.

## 소유자와 레이블

- **소유자** — 소유자로 등록된 사용자와 팀은 워크플로에 접근할 수 있고, 실패했을 때 알림을 받도록 선택할 수 있습니다. **설정 → 소유자**에서 지정하세요.
- **레이블** — 워크플로를 묶는 태그입니다. 워크플로 목록에서 레이블로 필터링할 수 있어 바쁜 프로젝트를 훨씬 수월하게 다룰 수 있습니다. 팀별, 통합별, 환경별로 워크플로를 정리할 때 유용합니다.
- **레이블 규칙** — **워크플로 → 설정 → 레이블 규칙**에서 이름이나 설명 패턴에 따라 새 워크플로에 레이블을 자동으로 적용합니다.
- **소유자 규칙** — **워크플로 → 설정 → 소유자 규칙**에서 새 워크플로에 소유자를 자동으로 지정합니다.

## 시크릿

민감한 값이 들어 있는 전역 변수는 **시크릿**으로 표시하세요. 저장한 뒤에는 일반적인 API와 UI 조회에서 값이 감춰지고, 워크플로 로깅은 실행 로그를 저장하기 전에 해석된 값을 지웁니다.

시크릿 변수는 이런 경우에 사용하세요.

- 외부 서비스의 API 키.
- 인증 토큰.
- 웹훅 서명 키.
- 읽기 전용 권한을 가진 사람에게도 보이면 안 되는 모든 것.

시크릿을 블록에 직접 붙여 넣지 마세요 — `Authorization: Bearer eyJh...` 같은 값은 워크플로와 로그에 그대로 드러납니다. 대신 `{{global.variables.MY_SECRET}}`을 사용하세요.

## 워크플로 내보내기와 가져오기

워크플로를 JSON 파일로 만들어 프로젝트 사이에서, 또는 자체 호스팅 설치본과 OneUptime Cloud 사이에서 옮길 수 있습니다.

- **내보내기** — 워크플로를 열고 **설정** 아래의 **Export Workflow**를 사용합니다. 워크플로 목록에서 여러 개를 선택해 파일 하나로 함께 내보낼 수도 있습니다.
- **가져오기** — **워크플로** 목록에서 **Import JSON**을 클릭하고 어느 OneUptime 프로젝트에서든 내보낸 파일을 고릅니다.

파일에는 워크플로의 이름, 설명, 활성화 상태, 그리고 그래프가 담깁니다. 다음은 의도적으로 담기지 않습니다.

- **웹훅 시크릿 키.** 워크플로가 생성될 때 새로 만들어지므로, 가져온 워크플로는 웹훅 URL이 달라집니다. 원래 URL을 호출하던 것들은 새 주소로 바꿔 주어야 합니다.
- **전역 변수.** `{{global.variables.MY_SECRET}}`을 읽는 블록은 그 참조를 그대로 유지하지만, 값 자체는 파일에 없습니다. 가져온 워크플로를 실행하기 전에 대상 프로젝트에서 변수를 만들어 두세요.
- **소유자와 레이블.** 손으로 직접 만들었을 때와 똑같이, 프로젝트의 레이블 규칙과 소유자 규칙이 가져온 워크플로에 적용됩니다.

가져온 워크플로는 내보낸 곳에서 활성화되어 있었더라도 언제나 **비활성화** 상태로 만들어집니다 — 그래프가 대상 프로젝트에 없는 모니터, 온콜 정책, 다른 워크플로를 가리킬 수 있기 때문입니다. 내용을 검토하고, 활성화하고, **워크플로 실행**으로 테스트한 다음에 켠 채로 두세요. 워크플로 복제도 똑같이 동작하므로, 복사본이 편집을 마치기도 전에 원본과 나란히 실행되기 시작하는 일은 없습니다.

그래프는 있는 그대로 옮겨지므로, 블록에 직접 입력한 것도 함께 따라갑니다. 자격 증명을 시크릿 변수에 보관해야 하는 현실적인 이유가 바로 이것입니다. 토큰을 하드코딩한 워크플로를 내보내면 그 파일을 받는 사람에게 토큰까지 넘겨주는 셈입니다.

## 실행이 걸릴 수 있는 최대 시간

각 실행 시도에는 실제 시간 기준의 마감 시각이 있습니다. 러너는 구성 요소마다 실행 전후로 이를 확인하고, 제어권이 돌아오는 즉시 마감을 넘긴 실행을 **Timeout**으로 표시합니다. 네트워크 작업이나 스크립트 작업을 하는 구성 요소는 자체 타임아웃도 두어야 합니다. 러너가 임의의 구성 요소 코드를 강제로 중단시킬 수는 없기 때문입니다.

AI 구성 요소는 남은 워크플로 시간에서 제공자 요청 타임아웃을 계산하고 최대 60초로 제한하며, 로깅과 정리를 위한 여유를 조금 남겨 둡니다.

## 다른 워크플로 호출 제한

**Execute Workflow** 구성 요소를 쓰면 한 워크플로가 다른 워크플로를 호출할 수 있습니다. 워크플로 A가 B를 부르고 B가 다시 A를 부르는 실수를 막기 위해 호출 깊이에 상한이 있습니다. 이 한도를 넘어간 실행은 명확한 오류와 함께 종료됩니다.

정말로 긴 호출 사슬이 필요하다면(실행 한 번에 항목 하나를 처리하는 작업처럼), 보통은 **Custom Code**로 워크플로 하나 안에서 반복하는 편이 더 간단합니다.

## 웹훅 보안

웹훅 트리거는 고유 URL을 제공합니다. 그 URL을 아는 사람은 누구나 호출할 수 있습니다. 실수로 또는 원치 않게 호출되는 것을 막으려면 이렇게 하세요.

- URL을 비밀번호처럼 다루세요. 공개적으로 공유하거나 공개 저장소에 커밋하지 마세요.
- 민감한 워크플로라면 호출하는 시스템이 공유 토큰을 헤더로 보내도록 하고(`X-Webhook-Token` 같은), 중요한 작업을 하기 전에 **Conditions** 블록으로 확인하세요. 기대하는 토큰 값은 시크릿 변수로 저장해 두세요.
- 매우 민감한 워크플로라면 공개 웹훅 대신 OneUptime 이벤트 트리거와 수동 가져오기 단계를 사용하는 편이 낫습니다.

## 아웃바운드 네트워크 접근

API를 비롯한 HTTP 블록은 OneUptime에서 요청을 보냅니다. 자체 호스팅이라면 설치본이 호출하려는 서비스에 닿을 수 있는지 확인하세요. OneUptime Cloud를 사용한다면 아웃바운드 IP 대역이 [IP 주소](/docs/configuration/ip-addresses)에 나와 있으니, 상대편에서 허용 목록에 넣으면 됩니다.

## AI 구성 요소

**Generate Text with AI**는 OneUptime에 설정된 LLM 게이트웨이를 통해 요청 하나를 보냅니다. 프로젝트의 기본 LLM 제공자를 사용하며, 프로젝트에 설정된 것이 없으면 설치본의 전역 제공자를 사용합니다. 제공자는 **프로젝트 설정 → AI → LLM 공급자**에서 설정하고, 제공자 API 키나 임의의 모델 엔드포인트는 절대 워크플로 자체에 넣지 마세요.

AI 구성 요소에는 명시적인 데이터 유출 경계가 있습니다.

- OneUptime은 고정된 구성 요소 안전 지침과 함께 해석된 **System Instructions**, **Prompt**, 직렬화된 **Context**를 설정된 제공자에게 보냅니다. Context는 사용자 메시지 끝의 명시적인 표시 뒤에 덧붙여지며, 고정 지침은 그 표시 뒤의 모든 것이 태그나 지시문을 포함하고 있더라도 신뢰할 수 없는 데이터로 남는다고 명시합니다.
- 트리거 페이로드, 워크플로 이력, 다른 구성 요소의 출력, 프로젝트 레코드, 텔레메트리, 시크릿은 자동으로 첨부되지 않습니다. 데이터는 이 세 입력 중 하나에서 직접 참조했을 때만 밖으로 나갑니다.
- 도구 정의나 제공자 고유의 기능 필드는 전송되지 않습니다. 모델은 이 구성 요소를 통해 OneUptime에 질의하거나, HTTP 요청을 보내거나, 프로젝트 데이터를 변경할 수 없습니다. 설정된 제공자와 모델은 여전히 관리자가 관리하는 신뢰 경계이므로, 엄격하게 오프라인 생성이 필요한 설치본은 제공자가 관리하는 내장 검색 기능이 없는 모델을 선택해야 합니다.
- 제공자 수준의 추가 매개변수는 생성 관련 튜닝 필드만 담은 허용 목록으로 제한됩니다. 워크플로 메시지를 대체하거나, 도구나 제공자 고유의 웹 검색·데이터 소스를 추가하거나, 텍스트가 아닌 형식을 켜거나, 여러 개의 선택지를 요청하거나, 스트리밍을 켜거나, 제공자 저장 플래그로 요청을 보관하거나, 이 구성 요소의 출력 토큰 상한을 올릴 수는 없습니다. 앞으로 등장할 알 수 없는 기능 필드는 기본적으로 무시됩니다.
- System Instructions, Prompt, Context, 그리고 생성된 Response 값은 자동 워크플로 실행 로그에서 이 AI 구성 요소 자신의 인자 및 반환값 항목에서 가려집니다. 실행이 진행되는 동안에는 이후 구성 요소에서 계속 사용할 수 있습니다. 이 값을 다른 구성 요소에 넣으면 그 구성 요소의 로깅 정책이 적용되어 해석된 값이 기록될 수 있으므로, 재사용은 명시적인 정보 공개로 여기세요. 제공자와 모델 이름, 토큰 수, LLM 로그 ID, 안전한 오류 메시지는 운영과 과금을 위해 그대로 보입니다. 제공자가 요청 내용을 그대로 되돌려 줄 수 있으므로, 가공되지 않은 제공자 오류 본문은 워크플로 로그, LLM 로그, 애플리케이션 로그, 트레이스에서 제외됩니다.

참조하는 모든 변수는 여러분이 의도적으로 제공자에게 보내는 데이터라고 생각하세요. 특히 그 정보 공개가 꼭 필요하고 제공자가 이를 받아도 되도록 승인된 경우가 아니라면, 시크릿 전역 변수를 프롬프트나 컨텍스트에 넣지 마세요. Ollama처럼 자체 호스팅하는 로컬 제공자를 쓰면 요청을 자체 인프라 안에 둘 수 있고, 호스팅 제공자를 쓰면 그 제공자의 데이터 처리 약관에 따라 요청이 처리됩니다.

호출 하나하나는 **프로젝트 설정 → AI → AI 로그**에 제공자, 모델, 상태, 토큰, 비용, 과금 정보와 함께 기록됩니다. 프롬프트와 응답 미리보기, 가공되지 않은 제공자 오류 상세 내용은 AI 로그에 저장되지 않습니다. 비용이 발생하는 전역 제공자를 통한 호출은 프로젝트의 AI 크레딧 잔액을 소모합니다. 워크플로 AI는 프로젝트의 일일 자율 AI 토큰 예산에도 포함되며, 예산이 소진되면 구성 요소는 모델과 통신하지 않고 **Error** 경로를 탑니다. 프로젝트 AI가 활성화되어 있어야 합니다. OneUptime Cloud에서는 구독이 결제되어 있어야 하고 Growth 플랜(또는 Growth 기능을 포함하는 플랜)이 필요하며, 결제가 비활성화된 자체 호스팅 설치본에는 이러한 플랜 제한이 없습니다.

내장된 한도가 무인 호출을 유한하게 유지합니다. System Instructions, Prompt, 직렬화된 Context는 합쳐서 50,000자로 제한되고, Temperature는 `0`에서 `1` 사이여야 하며, Maximum Output Tokens는 `1`에서 `4096` 사이(기본값 `1024`)여야 하고, 제공자 요청은 한 번만 시도되며 최대 60초 후 타임아웃됩니다. 프로젝트당 워크플로 AI 호출은 동시에 세 개까지만 실행되며, 그 이상은 **Error** 경로를 타므로 이후 워크플로 실행에서 다시 시도할 수 있습니다. 검증, 설정, 접근, 예산, 잔액, 동시성, 제공자, 타임아웃 실패는 모두 **Error** 경로를 타고 **Error** 출력을 채웁니다. 프로덕션 워크플로를 활성화하기 전에 이 경로를 반드시 연결해 두세요.

## 권한

워크플로는 프로젝트의 역할 기반 접근 제어를 따릅니다. 관련 권한은 다음과 같습니다.

- **Create / Read / Edit / Delete Workflow** — 워크플로 자체에 대한 기본 권한입니다.
- **Run Workflow** — 워크플로를 손으로 실행하거나 API로 트리거하는 데 필요합니다.
- **Read Workflow Log** — 실행 내역을 보는 데 필요합니다.
- **Read / Create / Edit / Delete Workflow Variable** — 전역 변수 목록에 대한 제어 권한입니다.

대부분의 엔지니어에게는 워크플로에 대한 생성·편집·읽기 권한을 주되 변수 권한은 주지 않는 편이 좋습니다. 변수 편집 권한은 프로젝트의 시크릿을 관리하는 사람들에게만 남겨 두세요.

## 플랜 한도

OneUptime Cloud는 하위 플랜에서 월간 실행 횟수를 제한합니다. 현재 한도는 **프로젝트 설정 → 결제**에서 확인할 수 있습니다. 한도에 도달하면 다음 결제 주기가 시작될 때까지 새 트리거가 거부됩니다. 자체 호스팅 설치본에는 이 한도가 없습니다.

## 워크플로가 적합하지 않은 경우

다른 도구를 찾는 편이 나은 몇 가지 경우입니다.

- **무거운 연산이나 대용량 데이터셋** — 워크플로는 숫자를 갈아 넣는 작업이 아니라 가벼운 접착제 역할을 하도록 설계되었습니다. 무거운 작업은 자체 인프라에서 돌리고, 워크플로는 그것을 시작시키는 역할만 맡기세요.
- **오래 이어지는 능동적인 연산** — 한 번의 실행 시도는 빠르게 끝나도록 만들어졌습니다. "A를 하고, 두 시간 기다리고, B를 한다"처럼 수동적으로 기다려야 한다면 **Sleep** 구성 요소를 쓰세요. 워커를 붙잡아 두지 않고 실행 상태를 저장했다가 나중에 재개합니다.
- **사람이 개입하는 단계별 인시던트 대응** — 그것은 [Runbook](/docs/runbooks/index)이 하는 일입니다. 워크플로는 무인 자동화를 위한 것입니다.
