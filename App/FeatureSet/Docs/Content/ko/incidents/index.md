# 인시던트 개요

OneUptime의 인시던트는 무언가 고장났을 때 팀이 중심으로 모여드는 기록입니다. 번호, 제목, 심각도, 현재 상태, 영향을 받는 리소스, 그리고 대응하는 동안 팀이 적어 두는 모든 것 — 메모, 근본 원인, 해결 조치, 그리고 누가 무엇을 했는지 기록하는 추가 전용 피드 — 을 담고 있습니다.

인시던트는 모니터에 빨간불이 켜지는 순간을 체계적인 대응으로 바꿔 주는 장치입니다. 인시던트를 선언하면 적절한 온콜 로테이션이 호출되고, 모든 변경 사항을 통보받는 소유자가 추가되며, runbook이 시작되고, 원한다면 공개 상태 페이지에 장애가 게시되어 "혹시 알고 계신가요?"라고 묻는 고객 티켓이 줄어듭니다.

새벽 3시에 직접 인시던트를 선언할 수도 있고, 모니터의 조건이 일치하는 순간 모니터가 대신 선언하도록 맡길 수도 있습니다. 어느 쪽이든 인시던트는 같은 객체이며, 같은 라이프사이클을 거치고 마지막에 같은 기록을 남깁니다.

## 한눈에 보기

- **최상위 기능** — 대시보드 왼쪽 내비게이션의 **인시던트**이며, 경로는 `/dashboard/{projectId}/incidents`입니다.
- **기본 제공되는 세 가지 상태** — 모든 신규 프로젝트에 **Identified**, **인지됨**, **해결됨**이 생성됩니다. 직접 상태를 추가할 수 있으며, 기본 제공되는 세 가지는 이름과 색상을 바꿀 수는 있지만 삭제할 수는 없습니다.
- **기본 제공되는 세 가지 심각도** — **Critical Incident**, **Major Incident**, **Minor Incident**입니다. 심각도는 색상과 순서를 가진 레이블일 뿐, 그 자체로는 아무런 동작도 하지 않습니다.
- **네 가지 진입 경로** — **인시던트 선언** 마법사, **템플릿에서 생성**, 모니터 조건 규칙, 또는 `POST /api/incident`입니다.
- **프로젝트별 번호 부여** — 모든 인시던트에는 인시던트 번호가 부여되며, 기본적으로 `#42`로 표시되거나 직접 지정한 접두사를 붙여 `INC-42`처럼 표시됩니다.
- **두 종류의 메모** — 팀을 위한 비공개 메모(내부 메모)와 상태 페이지 구독자를 위한 공개 메모가 있습니다.
- **설정은 프로젝트 설정이 아니라 인시던트 아래에 있습니다** — 상태, 심각도, 템플릿, 사용자 정의 필드, 규칙 엔진은 모두 **인시던트 → 설정**과 **인시던트 → 규칙**에 있습니다.

## 핵심 용어

이 섹션의 다른 페이지마다 반복해서 등장하는 몇 가지 단어가 있습니다. 이것부터 정리해 두세요.

| 용어                   | 의미                                                                                                                                                |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **인시던트**           | 기록 그 자체 — 제목, 설명, 심각도, 현재 상태, 영향받는 리소스, 그리고 대응 중에 인시던트에 기록된 모든 내용입니다.                                  |
| **인시던트 상태**      | 인시던트가 라이프사이클의 어디쯤에 있는지를 나타냅니다. 이름, 색상, `order`와 의미를 부여하는 플래그를 가진 프로젝트 범위의 행입니다.               |
| **인시던트 심각도**    | 얼마나 심각한지를 나타냅니다. 이름, 색상, `order`를 가진 프로젝트 범위의 행입니다. 순수한 분류일 뿐이며, 제품 어디에서도 특정 심각도를 특별 취급하지 않습니다. |
| **인시던트 번호**      | 프로젝트별 카운터로, `#42`처럼 표시되거나 설정한 접두사를 붙여 `INC-42`처럼 표시됩니다.                                                             |
| **영향받는 리소스**    | 인시던트에 연결하는 모니터, 호스트, Kubernetes 클러스터, Docker 호스트, 서비스 및 기타 인프라입니다.                                                |
| **공개 메모**          | 상태 페이지 독자와 구독자를 위해 작성하는 업데이트입니다. 상태 페이지 타임라인에 표시됩니다.                                                        |
| **비공개 메모**        | 대응 팀을 위한 내부 메모(`IncidentInternalNote` 모델)입니다. 상태 페이지에는 절대 노출되지 않습니다.                                                |
| **소유자**             | 인시던트를 책임지는 사용자 또는 팀입니다. 소유자는 인시던트가 생성될 때, 메모가 게시될 때, 상태가 바뀔 때 알림을 받습니다.                          |
| **인시던트 피드**      | 인시던트 **개요**에 있는 추가 전용 활동 타임라인으로, 상태 변경, 메모, 소유자 변경, 규칙 실행, 알림을 기록합니다.                                   |
| **상태 타임라인**      | 인시던트가 언제 어떤 상태에 얼마나 오래 있었는지에 대한 기록이며, 각 전환에 대한 구독자 알림 상태가 함께 표시됩니다.                                |

## OneUptime이 모든 프로젝트에 기본 생성하는 세 가지 상태

프로젝트가 생성되면 OneUptime은 정확히 세 개의 인시던트 상태를 다음 순서로 생성합니다.

| 상태             | 순서  | 색상               | 의미                                                                      |
| ---------------- | ----- | ------------------ | ------------------------------------------------------------------------- |
| **Identified**   | 1     | 빨강 (`#fd625e`)   | 새로 만들어진 인시던트가 도달하는 상태입니다. 생성 상태에 해당합니다.     |
| **인지됨**       | 2     | 노랑 (`#ffbf53`)   | 누군가 인시던트를 맡아 처리하고 있습니다.                                 |
| **해결됨**       | 3     | 초록 (`#2ab57d`)   | 인시던트가 끝났습니다. 해결해야 상태 페이지에서 내려갑니다.               |

이름은 어디까지나 레이블일 뿐이며, 실제 동작을 좌우하는 것은 상태 행에 있는 세 개의 불리언 값 `isCreatedState`, `isAcknowledgedState`, `isResolvedState`입니다. 각 플래그는 프로젝트당 하나의 상태만 가지는 것이 전제입니다.

이 구분은 생각보다 훨씬 중요합니다.

- `isCreatedState`는 새 인시던트가 어디에서 시작할지 결정합니다. 생성 시 상태를 명시적으로 선택하지 않으면 OneUptime은 프로젝트의 생성 상태를 찾아 사용합니다.
- `isAcknowledgedState`와 `isResolvedState`는 인시던트 헤더의 **Acknowledge** 및 **해결** 버튼, 인시던트 **개요**의 두 통계 타일, 사이드 메뉴의 **활성 인시던트** 개수 배지를 좌우합니다.
- **활성 인시던트**는 오로지 "현재 상태가 해결 상태가 아님"으로만 정의됩니다. 따라서 직접 추가한 사용자 지정 상태는 해결 상태가 아닌 한 모두 활성으로 간주됩니다.

**이름에 주의하세요.** 첫 번째 기본 상태의 이름은 **Identified**이지만, 제품 내부의 여러 설명은 여전히 이를 생성 상태라고 부릅니다. 프로젝트의 상태 목록에서 "Created"를 찾고 있다면, 그것은 **Identified**라는 이름의 행입니다.

**인시던트 → 설정 → 인시던트 상태**에서 직접 상태를 추가할 수 있습니다. 새 상태는 정렬된 목록의 맨 뒤에 추가되며, 끌어서 순서를 바꿀 수 있습니다. 플래그가 붙은 세 상태는 삭제할 수 없고 OneUptime이 이를 막지만, 이름과 색상은 변경할 수 있습니다. UI가 상태 이름을 동적으로 읽는 이유가 바로 이것입니다.

순서는 장식이 아니라 강제되는 제약입니다. 인시던트는 현재 상태보다 순서상 앞에 있는 상태로 이동할 수 없습니다.

자세한 내용은 [인시던트 상태 및 심각도](/docs/incidents/states-and-severities)에 있습니다.

## OneUptime이 모든 프로젝트에 기본 생성하는 세 가지 심각도

모든 신규 프로젝트에는 세 가지 심각도도 함께 생성됩니다.

| 심각도                | 순서  | 색상               | 의미                                                        |
| --------------------- | ----- | ------------------ | ----------------------------------------------------------- |
| **Critical Incident** | 1     | 적갈색 (`#b70400`) | 고객 영향이 매우 크며 즉각적인 대응이 필요합니다.           |
| **Major Incident**    | 2     | 빨강 (`#fd625e`)   | 영향이 상당하며 대개 즉각적인 대응이 필요합니다.            |
| **Minor Incident**    | 3     | 노랑 (`#ffbf53`)   | 영향이 작으며 대개 업무 시간 내에 처리합니다.               |

기본 제공되는 전체 설명은 [인시던트 상태 및 심각도](/docs/incidents/states-and-severities)에 있습니다.

심각도는 `name`, `description`, `color`, `order`만 가지며 그 외에는 아무것도 없습니다. 플래그도 없고, "Critical Incident"를 다른 행과 다르게 취급하는 코드 경로도 없습니다. 심각도는 사람이 분류하는 수단이며, 온콜 규칙을 작성할 때 일치 기준으로 사용할 수 있습니다. 하지만 심각도를 선택하는 것만으로는 누구도 호출되지 않습니다.

심각도는 **인시던트 → 설정 → 인시던트 심각도**에서 편집하거나 추가합니다.

## 인시던트의 일생

### 1. 선언됩니다

네 가지 경로가 모두 같은 객체로 이어집니다.

- **직접 선언** — 인시던트 목록에서 **인시던트 선언**을 클릭합니다. 그러면 **새 인시던트 선언** 마법사가 열리며, **인시던트 세부 정보**, **영향받는 리소스**, **인시던트 역할**, **온콜**, **더보기**의 다섯 단계로 구성됩니다.
- **템플릿에서 선언** — **템플릿에서 생성**을 클릭하고 저장해 둔 **인시던트 템플릿**을 선택합니다. 템플릿은 제목, 설명, 심각도, 초기 상태, 리소스, 온콜 정책, 소유자, 레이블을 미리 채웁니다.
- **모니터에서 선언** — "인시던트 선언" 토글이 켜진 모니터 조건 규칙은 필터가 일치하는 순간 자동으로 인시던트를 생성합니다. 여기에서 제목과 설명은 `{{variable}}` 템플릿을 지원합니다.
- **API로 선언** — API 키를 사용해 `POST /api/incident`를 호출합니다. 서버가 `declaredAt`, 생성 상태, 인시던트 번호를 대신 채워 줍니다.

필드별 안내는 [인시던트 선언](/docs/incidents/declaring-incidents)을 참고하세요.

### 2. 적절한 사람들이 알게 됩니다

생성 시 OneUptime은 구성해 둔 자동화를 실행합니다. 레이블 규칙, 온콜 규칙, 소유자 규칙, runbook 규칙이 그것입니다. 수동으로든, 템플릿에서든, 일치하는 온콜 규칙에 의해 병합되었든 인시던트에 연결된 온콜 듀티 정책은 모두 병렬로 실행됩니다.

소유자는 각 사용자의 알림 환경설정에 따라 이메일, SMS, 전화, 푸시, WhatsApp으로 알림을 받습니다. 인시던트에 소유자가 전혀 없으면 알림이 버려지는 대신 프로젝트 소유자에게 전달됩니다.

인시던트가 상태 페이지에 표시되고 구독자 알림이 켜져 있다면 구독자도 알림을 받습니다. 알림은 cron 기반으로 매분 실행되므로, 즉시 발송이 아니라 최대 1분 정도의 지연을 예상하세요.

### 3. 팀이 대응합니다

대응자는 인시던트를 확인 처리하고, 영향받는 리소스를 연결하고, runbook을 실행하고, 인시던트 역할을 배정하며, 알게 된 내용을 기록합니다. 팀을 위한 비공개 메모, 고객을 위한 공개 메모, 그리고 상황이 명확해지면 **근본 원인**과 **해결** 페이지도 작성합니다. 이들이 하는 모든 일은 **개요** 페이지의 **인시던트 피드**에 남습니다.

### 4. 해결됩니다

**해결**을 클릭하면 인시던트가 해결 상태로 이동하고, 상태 타임라인에 기록되며, 지속 시간 시계가 멈추고, 표시 중이던 모든 상태 페이지의 활성 섹션에서 인시던트가 사라집니다. 이를 위해 다른 것을 바꿀 필요는 없습니다. 상태 페이지 쿼리가 보는 것은 해결 상태 플래그이기 때문입니다.

그 후에는 사후 분석을 작성하고, 원한다면 상태 페이지에 게시할 수 있습니다.

## 대시보드에서 인시던트가 있는 위치

왼쪽 내비게이션에서 **인시던트**를 엽니다. 사이드 메뉴는 다음 섹션으로 구성되어 있습니다.

| 섹션          | 하는 일                                                                                                                                                                    |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **개요**      | **모든 인시던트**와 **활성 인시던트** — 후자에는 해결 상태가 아닌 인시던트 개수를 나타내는 빨간 배지가 붙습니다.                                                           |
| **에피소드**  | 인시던트 에피소드로, 자체 페이지를 가진 별도의 그룹화 기능입니다.                                                                                                          |
| **AI**        | **조사**와 **해결** — 자동 조사 및 자동 해결 설정입니다.                                                                                                                   |
| **워크스페이스** | 인시던트용 **Slack** 및 **Microsoft Teams** 연결입니다.                                                                                                                 |
| **규칙**      | 규칙 엔진입니다. **그룹화 규칙**, **온콜 규칙**, **소유자 규칙**, **Runbook 규칙**, **개인정보 보호 규칙**, **레이블 규칙**, **SLA 규칙**, **Reminder Rules**.              |
| **설정**      | **인시던트 상태**, **인시던트 심각도**, **인시던트 템플릿**, **노트 템플릿**, **포스트모템 템플릿**, **사용자 정의 필드**, **인시던트 역할**, **기타 설정**.                |

**규칙**과 **설정**은 기본적으로 접혀 있습니다. 이 문서의 나머지 부분에서 언급하는 페이지를 찾으려면 펼치세요. 인시던트 구성은 프로젝트 설정 아래에 있지 않고 모두 여기에 있습니다.

인시던트 목록 자체에는 **인시던트 번호**, **제목**, **상태**, **심각도**, **영향받는 리소스**, **선언됨**, **기간**, **레이블**, **소유자**가 표시되며, 여러 건을 한 번에 닫을 수 있는 **상태 변경** 일괄 작업이 제공됩니다.

## 인시던트의 각 페이지가 보여 주는 것

인시던트를 열면 다음과 같이 묶인 왼쪽 사이드 메뉴가 나타납니다.

- **개요** — **인시던트 세부 정보** 카드(제목, 심각도, 레이블, 인시던트 번호, 선언 시각, 선언자, 온콜 정책), **영향받는 리소스** 카드, 그리고 **인시던트 피드**입니다. 그 위에는 확인까지 걸린 시간, 해결까지 걸린 시간, 전체 **기간** 통계 타일이 있습니다.
- **상태 타임라인** — 인시던트가 거쳐 온 모든 상태를 **시작**, **종료**, **기간**, 그리고 각 전환의 구독자 알림 상태와 함께 보여 줍니다. **원인 보기**와 **로그 보기**는 각 변경이 왜 일어났는지 설명합니다.
- **SLA** — 이 인시던트의 SLA 추적입니다.
- **설명**, **근본 원인**, **해결** — 세 개의 마크다운 페이지입니다. 상태 페이지에 표시되는 것은 설명입니다.
- **런북** — 이 인시던트에 연결된 runbook 실행입니다.
- **포스트모템** — 사후 정리 문서이며, 원한다면 상태 페이지에 게시할 수 있습니다.
- **역할**, **온콜 실행**, **소유자** — 누가 대응 중인지, 어떤 정책이 실행되었는지, 누가 알림을 받는지 보여 줍니다.
- **알림 로그**, **AI 로그**, **감사 로그** — 무엇이 발송되었고 무엇이 바뀌었는지 보여 줍니다.
- **비공개 노트**와 **공개 노트** — 사이드 메뉴의 **노트** 섹션 아래에 있습니다.
- **사용자 정의 필드**, **설정**, **인시던트 삭제** — **고급** 아래에 있습니다. **설정** 페이지에는 **상태 페이지에 표시**, **비공개 인시던트**, **Reminders** 카드가 있습니다.

[인시던트 메모, 소유자 및 피드](/docs/incidents/notes-owners-and-feed)에서 협업 페이지를 자세히 다룹니다.

## 인시던트가 OneUptime의 나머지 기능과 맞물리는 방식

- **모니터는 문제를 발견하고, 인시던트는 그것을 기록합니다.** 모니터 조건 규칙은 제목, 심각도, 온콜 정책, 소유자, 레이블, 해결 노트를 미리 채운 채 인시던트를 자동으로 선언할 수 있습니다. 여기에서 사용할 수 있는 변수는 [인시던트 및 알림 템플릿](/docs/monitor/incident-alert-templating)을 참고하세요.
- **호출은 온콜 정책이 담당합니다.** 선언 마법사의 **온콜** 단계, 템플릿, 또는 **인시던트 → 규칙 → 온콜 규칙**에서 정책을 연결합니다. 일치하는 규칙은 모두 실행되며, 실행되는 집합은 모든 일치 항목과 직접 연결한 항목의 합집합에서 중복을 제거한 것입니다.
- **Runbook은 사람들에게 무엇을 해야 할지 알려 줍니다.** Runbook 규칙은 일치하는 인시던트가 생성될 때 절차를 자동으로 연결하며, 대응자는 인시던트에서 직접 실행할 수도 있습니다. [Runbook 개요](/docs/runbooks/index)를 참고하세요.
- **상태 페이지는 고객에게 알립니다.** 인시던트는 페이지에서 인시던트 표시가 켜져 있고, 인시던트가 상태 페이지에 표시되도록 설정되어 있으며, 현재 상태가 해결 상태가 아닐 때 상태 페이지의 활성 목록에 나타납니다. 비공개 인시던트는 언제나 모든 상태 페이지에서 숨겨집니다. [상태 페이지 개요](/docs/status-pages/index)를 참고하세요.
- **워크플로우는 그 주변을 자동화합니다.** **On Create Incident**, **On Update Incident**, **On Delete Incident** 트리거를 사용하면 인시던트 라이프사이클 위에 노코드 자동화를 구축할 수 있습니다. [워크플로우 개요](/docs/workflows/index)를 참고하세요.
