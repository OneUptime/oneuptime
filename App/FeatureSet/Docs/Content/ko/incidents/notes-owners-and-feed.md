# 인시던트 메모, 소유자 및 피드

모든 인시던트는 대응하는 동안 기록을 쌓아 갑니다. 그 기록 중 일부는 고객을 위한 것입니다 — 새벽 2시 14분에 상태 페이지에 올라가는, 문제가 된 배포를 찾았다는 업데이트 같은 것입니다. 나머지는 팀을 위한 것입니다 — 누군가 붙여넣은 스택 트레이스, 마침내 실마리가 보인 그래프, 페일오버를 결정한 순간 같은 것입니다.

OneUptime은 이 두 대상을 서로 분리해 둡니다. **공개 노트**는 상태 페이지에 게시되며 구독자에게 알릴 수 있습니다. **비공개 노트**(`IncidentInternalNote` 모델)는 대시보드 안에만 머무릅니다. 이 둘 아래에는 인시던트에 일어난 모든 일을 기록하는 추가 전용 타임라인인 **인시던트 피드**와, 누구에게 알릴지 결정하는 **소유자** 목록이 있습니다.

이 모든 것은 인시던트의 왼쪽 사이드 메뉴에 걸려 있습니다. **Notes → Public Notes**, **Notes → Private Notes**, **Team → Owners**입니다. 피드는 인시던트 **개요** 페이지에 있습니다.

## 공개 노트와 비공개 노트

두 노트 유형은 대시보드에서 비슷해 보이지만 동작 방식은 매우 다릅니다.

- **공개 노트** — `IncidentPublicNote` 모델로, 인시던트 타임라인의 일부로 상태 페이지에 제공됩니다. 직접 설정할 수 있는 **Posted At** 날짜와 **Notify Status Page Subscribers** 체크박스를 가집니다.
- **비공개 노트** — `IncidentInternalNote` 모델입니다. 상태 페이지 앱은 이를 전혀 읽지 않습니다. 게시 시각 필드가 없어서(목록은 `createdAt` 기준으로 시각이 찍히고 정렬됩니다) 구독자 관련 필드도 전혀 없으므로, 비공개 노트는 절대 구독자 알림을 촉발할 수 없습니다.

**"비공개"가 실제로 의미하는 것.** 이는 "더 작은 그룹의 사람들에게만 제한된다"가 아니라 "상태 페이지에 게시되지 않는다"는 뜻입니다. 두 노트 유형은 같은 읽기 권한을 공유하므로, 인시던트를 읽을 수 있는 사람이라면 누구나 그 비공개 노트도 읽을 수 있습니다. 인시던트 자체를 볼 수 있는 사람을 제한해야 한다면, 인시던트 자체의 **Private Incident** 플래그(`isPrivate`)를 사용하세요. 이는 모든 상태 페이지에서 인시던트를 숨기고 인시던트의 소유자 사용자, 소유자 팀의 구성원, 프로젝트 관리자와 소유자로만 접근을 제한합니다.

**소유자는 둘 다 봅니다.** 소유자 알림 작업은 공개 노트와 비공개 노트를 함께 조회합니다. 비공개 노트는 구독자로부터 비공개인 것이지, 대응하는 사람들로부터 비공개인 것이 아닙니다.

| 이렇게 하고 싶다면…                                        | 선택하세요            |
| ----------------------------------------------------------- | ---------------------- |
| 고객에게 아는 것과 언제 더 알게 될지 알리고 싶다            | **공개 노트**          |
| 이미 다른 곳에 보낸 업데이트를 소급해서 기록하고 싶다        | **공개 노트**          |
| 가설, 실행한 명령, 막다른 길을 기록하고 싶다                | **비공개 노트**        |
| 힙 덤프나 내부 대시보드 스크린샷을 첨부하고 싶다             | **비공개 노트**        |

## 공개 노트 게시하기

인시던트 사이드 메뉴에서 **Notes → Public Notes**를 열고 노트를 만듭니다. 카드에는 여기에 작성한 내용이 상태 페이지에 나타난다는 설명이 있으며, 빈 상태에는 이 인시던트에 대해 아직 생성된 공개 노트가 없다는 안내가 표시됩니다.

| 필드                                | 용도                                                                                                     |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| **Public Incident Note**            | 마크다운 본문입니다. 필수입니다. 양식은 이 노트가 상태 페이지에서 보인다는 점을 알리며 치트시트를 링크합니다. |
| **Attachments**                     | 상태 페이지에서 구독자와 공유되는 파일입니다. 선택 사항입니다.                                            |
| **Notify Status Page Subscribers**  | 체크박스이며 기본적으로 켜져 있습니다. 조용히 게시하려면 꺼 두세요.                                        |
| **Posted At**                       | 필수 날짜와 시각이며 기본값은 현재 시각이고, 현재 타임존으로 표시됩니다.                                    |

**Posted At은 노트의 실제 타임스탬프입니다.** 상태 페이지는 공개 노트를 작성한 시각이 아니라 `postedAt` 기준으로 정렬하고 표시합니다 — 그러므로 40분 전에 이미 보낸 업데이트를 상태 페이지에도 반영하는 것이라면, **Posted At**을 실제로 그 일이 일어난 시각으로 설정하세요. API를 통해 값 없이 노트가 도착하면 OneUptime은 현재 시각을 찍습니다.

목록은 각 노트를 작성한 사람, **Posted At**, 첨부 파일이 포함된 렌더링된 마크다운, 그리고 **Subscriber Notification Status** 열을 보여줍니다. **Created By**, **Note**, **Created At**으로 필터링할 수 있습니다.

## 비공개 노트 게시하기

**Notes → Private Notes**는 의도적으로 더 단순합니다. 필드는 단 두 개뿐입니다.

- **Private Incident Note** — 마크다운 본문이며 필수입니다. 양식은 이것이 팀에게만 비공개이며 상태 페이지에는 보이지 않는다고 명확히 밝힙니다.
- **Attachments** — 인시던트 대응 팀을 위한 파일입니다.

**Posted At**도 없고 구독자 체크박스도 없습니다 — 노트는 생성될 때 시각이 찍힙니다.

## 노트의 첨부 파일

두 노트 유형 모두 **Attachments** 필드를 통해 파일 첨부를 받을 수 있으며, 둘 다 노트 본문 아래에 파일별 **Download attachment** 링크가 있는 첨부 파일 목록을 렌더링합니다.

다른 점은 누가 그 파일을 가져올 수 있느냐입니다.

- **공개 노트 첨부 파일**은 상태 페이지 경로를 통해 상태 페이지 방문자가 노트 자체와 함께 다운로드할 수 있습니다.
- **비공개 노트 첨부 파일**은 인증된 대시보드 API를 통해서만 접근할 수 있습니다. 상태 페이지 경로는 존재하지 않습니다.

이는 첨부 파일에도 노트 본문과 동일한 공개/비공개 결정이 적용된다는 뜻입니다. 고객에게 보여줄 타임라인 이미지는 공개 노트에, 설정 덤프는 비공개 노트에 넣으세요.

## AI로 노트 생성하기

두 노트 페이지 모두 **Generate with AI** 버튼을 제공합니다. 이 버튼은 인시던트를 프로젝트의 AI 제공업체로 보내고 생성된 마크다운을 노트 편집기에 넣어 주며, 저장하기 전에 직접 수정할 수 있습니다 — 자동으로 게시되는 것은 아무것도 없습니다.

- **Generate Public Note with AI** — 인시던트 데이터를 분석해 고객 대상 노트를 만든다고 설명되어 있습니다. 템플릿에는 **Status Update**와 **Resolution Notice**가 있습니다.
- **Generate Private Note with AI** — 대신 내부 기술 노트를 생성합니다. 템플릿에는 **Investigation Update**와 **Technical Analysis**가 있습니다.

버튼 뒤에서 대시보드는 선택한 템플릿과 `public` 또는 `internal`의 노트 유형을 담아 `/incident/generate-note-from-ai/{incidentId}`로 요청을 보냅니다.

## 노트 템플릿

팀이 매 장애마다 같은 세 가지 업데이트를 작성한다면 한 번만 저장해 두세요. 두 노트 페이지 모두 **Create from Template** 버튼을 가지며, 이를 누르면 **Select Note Template** 드롭다운이 있는 **Create Note from Template** 선택기가 열립니다.

템플릿은 공개 노트와 비공개 노트 사이에 공유됩니다. 하나의 템플릿 목록이 둘 다에 쓰이며, 같은 템플릿을 어느 쪽 노트에든 삽입할 수 있습니다.

관리는 **Incidents → Settings → Note Templates**에서 합니다 — 카드 제목은 **Public or Private Note Templates for Incidents**이며, 양식에는 **Template Info** 단계(**Template Name**과 **Template Description**, 둘 다 필수)와 본문을 위한 **Note Details** 단계가 있습니다. 아직 하나도 만들지 않은 상태에서 **Create from Template**을 클릭하면 OneUptime은 아직 없다고 알려 줍니다. 이 메시지는 프로젝트 설정을 가리키지만, 실제 페이지는 **Incidents → Settings → Note Templates** 아래에 있다는 점에 유의하세요.

## Slack 또는 Microsoft Teams에서 노트 게시하기

워크스페이스를 연결해 두었다면, 대응자는 채널을 벗어날 필요가 없습니다. Slack과 Microsoft Teams 모두 노트 추가 작업을 제공하며, 이를 열면 **Public Note** 또는 **Private Note**를 고르는 드롭다운과 텍스트 상자가 있는 모달이 나타나고, 결과는 인시던트에 바로 기록됩니다.

알아 둘 만한 두 가지가 있습니다.

- **중복 방지** — 각 노트는 그것이 유래한 Slack 메시지(`postedFromSlackMessageId`, `channel_id:message_ts` 형식)를 기록하므로, 같은 메시지에 여러 사람이 반응해도 노트가 하나만 생성되고 다섯 개가 생기지 않습니다.
- **노트가 다시 되돌아옵니다** — 어느 쪽 노트를 게시하든 연결된 인시던트 채널에도 메시지가 밀려 들어갑니다. 노트의 피드 항목이 워크스페이스 알림이 켜진 상태로 생성되기 때문입니다.

## 공개 노트가 실제로 구독자에게 도달하는 시점

**Notify Status Page Subscribers**를 켠 상태로 공개 노트를 만든다고 해서 그 자체로 이메일이 나간다는 보장은 없습니다. 노트는 일련의 검사를 통과해야 하며, 실패할 때마다 오류를 내는 대신 구체적인 이유가 기록됩니다.

1. **Notify Status Page Subscribers**가 켜져 있어야 합니다. 꺼져 있다면 노트는 생성되는 순간 건너뛴 것으로 표시됩니다.
2. 노트는 여전히 존재하는 인시던트에 속해 있어야 합니다.
3. 인시던트에는 최소 한 개의 모니터가 연결되어 있어야 합니다 — 모니터가 없으면 노트를 보낼 상태 페이지 리소스가 없습니다.
4. 인시던트의 **Visible on Status Page** 플래그(`isVisibleOnStatusPage`)가 true여야 합니다.
5. 인시던트가 도달하는 각 상태 페이지에 **Show Incidents**(`showIncidentsOnStatusPage`)가 켜져 있어야 합니다.
6. 각 구독자는 자신의 환경설정을 통과해야 합니다 — 구독 취소 상태가 아니고, 이 리소스와, 페이지가 구독자에게 선택을 허용하는 경우 `Incident` 이벤트 유형을 구독하고 있어야 합니다.

**알림은 즉시 전송되지 않습니다.** 발송을 담당하는 작업은 1분마다 실행되므로, 노트를 저장한 시점부터 메일이 발송되기까지 최대 약 1분이 걸릴 수 있습니다. 이것이 **Sending Soon** 레이블이 의미하는 바입니다.

**Subscriber Notification Status** 열은 전체 과정을 추적합니다.

| 상태                           | 의미                                                    |
| ------------------------------ | -------------------------------------------------------- |
| **Notifications skipped.**     | 위의 관문 중 하나가 막혔습니다. 이유가 기록됩니다.       |
| **Sending Soon**               | 대기열에 들어갔으며 다음 발송 작업 실행을 기다립니다.    |
| **Notifications Being Sent**   | 작업이 구독자 목록을 처리하는 중입니다.                  |
| **Notifications Sent**         | 모든 구독자 알림이 발송되었습니다.                       |
| **Failed**                     | 작업이 오류를 냈습니다. 오류는 노트와 함께 저장됩니다.   |

상태에서 **more details**를 클릭하면 **Notification Status Details**가 열립니다. 재발송이 필요한 경우 그 모달의 버튼은 **Retry**이며, 이를 누르면 노트가 다시 대기 상태로 돌아가 다음 실행에서 처리됩니다.

구독자가 실제로 받는 메시지는 상태 페이지별, 채널별로 템플릿화되어 있습니다 — 이메일, SMS, Slack, Microsoft Teams는 각각 **Subscriber Incident Note Created** 이벤트를 위한 자체 템플릿을 가지며, 상태 페이지 이름과 URL, 세부 정보 링크, 영향받는 리소스, 인시던트 심각도와 제목, 노트 본문, 구독자별 구독 취소 링크를 변수로 사용합니다. 이러한 템플릿과 채널이 어떻게 구성되는지는 [구독자 및 공지](/docs/status-pages/subscribers)를 참고하세요.

## 인시던트 피드

**Incident Feed** 카드는 인시던트 **개요** 페이지 왼쪽 열 맨 아래에 있습니다. 인시던트의 이야기를 순서대로 보여 줍니다. 각 항목은 아이콘, 원인이 된 사람의 아바타와 이름, 마우스를 올리면 정확한 현지 시각이 보이는 상대적 타임스탬프, 그리고 마크다운 본문으로 구성됩니다. 항목은 오래된 순으로 정렬됩니다.

일부 항목은 추가 세부 정보를 담고 있습니다 — 예를 들어 소유자 알림은 메일을 받은 모든 사람을 나열합니다. 이런 항목에는 **More Information** 버튼이 있어 누르면 **More Information** 패널이 열립니다.

카드 헤더에는 **Actions** 메뉴도 있어 타임라인을 벗어나지 않고도 작업할 수 있습니다.

- **Execute Runbook** — 이 인시던트에 대해 [runbook](/docs/runbooks/index)을 시작합니다.
- **Execute On-Call Policy** — 필요할 때 정책을 호출합니다.
- **Add Public Note** — Public Notes 페이지와 같은 네 개의 필드를 모달로 제공합니다.
- **Add Private Note** — 노트 본문과 첨부 파일만 있습니다.

그 옆의 **Refresh**는 피드를 다시 불러옵니다.

**피드는 추가 전용이며 감사 로그가 아닙니다.** API는 피드 항목을 생성하고 읽는 것만 허용하며 수정이나 삭제는 허용하지 않으므로, 누구도 인시던트의 이력을 조용히 다시 쓸 수 없습니다. 영구 보관되는 것도 아닙니다. 유료 설치본에서는 3년보다 오래된 피드 행이 제거됩니다. 누가 무엇을 바꿨는지에 대한 지속적인 기록이 필요하다면 인시던트 사이드 메뉴의 **Audit → Audit Logs**를 사용하세요.

## 피드가 기록하는 것

피드 항목은 인시던트 서비스 자체, 두 노트 서비스, 상태 타임라인, 소유자 및 구성원 변경, 규칙 엔진, 온콜 실행, AI 조사 및 포스트모템 실행기, 그리고 알림 크론 작업에 의해 작성됩니다. 이벤트 유형은 다음을 포괄합니다.

- **인시던트 자체** — `IncidentCreated`, `IncidentUpdated`, `IncidentStateChanged`.
- **노트와 기록** — `PublicNote`, `PrivateNote`, `RootCause`, `RemediationNotes`, `PostmortemNote`.
- **사람** — `OwnerUserAdded`, `OwnerTeamAdded`, `OwnerUserRemoved`, `OwnerTeamRemoved`, `IncidentMemberAdded`, `IncidentMemberRemoved`.
- **알림** — `OwnerNotificationSent`, `SubscriberNotificationSent`, `OnCallPolicy`, `OnCallNotification`.
- **자동화** — `LabelRuleExecuted`, `OwnerRuleExecuted`, `PrivacyRuleExecuted`, `OnCallRuleExecuted`, `AutoRemediation`.

각 유형은 자체 아이콘을 가지므로, 길게 이어진 피드를 훑으면서 잡담 속에서 상태 변경을 골라낼 수 있습니다. AI가 생성한 근본 원인 분석은 구분되게 표시되며 제한된 마크다운 모드로 렌더링됩니다.

피드는 인시던트 개인정보 보호를 존중합니다. 비공개 인시던트의 경우 피드 읽기도 인시던트와 동일한 방식으로 필터링됩니다.

## 소유자

소유자는 인시던트를 책임지는 사람과 팀입니다. 이들은 인시던트에 일어나는 모든 일의 알림 대상이며 — 모두가 다른 누군가가 처리하고 있으리라 여기는 동안 인시던트가 아무도 모르게 방치되지 않도록 하는 이유입니다.

인시던트 사이드 메뉴에서 **Team → Owners**를 엽니다. **Owners** 카드는 개수 배지를 보여 주며, "2 people · 1 team"처럼 진행 중인 카운트와 함께 소유자를 이 인시던트를 책임지고 변경 사항을 알림받는 사람과 팀으로 설명합니다. 소유자는 겹쳐진 아바타로 표시됩니다. 하나에 마우스를 올리면 그 사람의 이메일이 보이거나 해당 항목이 **Team**으로 표시됩니다.

- **Add owner**를 클릭하면 사람이나 팀을 검색할 수 있는 선택기가 열립니다.
- 아바타의 제거 컨트롤을 클릭하면 **Remove owner** 확인 창이 열리고, 이어서 **Remove**를 누릅니다.
- 아직 소유자가 없다면 카드가 그렇게 알리며, 변경 사항을 알림받을 수 있도록 팀원이나 팀을 추가하라고 안내합니다.

소유자 사용자와 소유자 팀은 별개의 레코드입니다. 팀을 추가하면 알림 목적으로 그 팀의 모든 구성원이 소유자가 되며, 개별적으로 나열할 필요는 없습니다.

## 소유자가 배정되는 방법

소유자 목록에 오르는 경로는 네 가지입니다.

- **인시던트 템플릿에서** — 템플릿은 **Owner - Teams**와 **Owner - Users** 필드를 가지며, 인시던트를 소유하고 생성 또는 업데이트될 때 알림을 받을 팀과 사용자로 설명됩니다. 템플릿에서 인시던트를 만들면 이 값이 미리 채워집니다. [인시던트 선언](/docs/incidents/declaring-incidents)을 참고하세요.
- **Incident Owner Rules에서** — 일치하는 규칙은 생성 시점에 소유자를 자동으로 추가합니다.
- **API를 통한 생성 시점에** — 생성 호출과 함께 전달된 소유자 사용자와 팀은 즉시 추가되며, "당신이 추가되었습니다" 이메일을 받을지 여부를 제어하는 플래그가 있습니다.
- **수동으로** — 인시던트 진행 중 언제든 **Owners** 페이지의 **Add owner** 컨트롤을 통해서입니다.

같은 사람을 두 번 추가해도 안전합니다. 이미 배정된 소유자는 중복 추가되지 않습니다.

## 인시던트 소유자 규칙

**Incident Owner Rules**는 일치하는 인시던트가 생성될 때 소유자 사용자와 팀을 자동으로 배정합니다 — 아무도 신경 쓰지 않아도 데이터베이스 인시던트가 데이터베이스 팀에 도달하게 하는 라우팅 계층입니다. 나머지 인시던트 자동화와 함께 [인시던트 설정 및 자동화](/docs/incidents/settings)에서 다룹니다.

규칙 양식은 **Basic Info**, **Match Criteria**, **Owners**의 세 단계로 구성되며, 소유자 단계는 두 개의 섹션을 가집니다.

- **Owners to Assign** — **Owner Teams**와 **Owner Users**를 고릅니다. 규칙이 일치하면 선택된 모든 사용자와 팀이 소유자로 추가되며, 이미 배정된 소유자는 중복 추가되지 않습니다.
- **Inherit Owners** — 소유자를 직접 지정하는 대신 관련 엔티티로부터 상속받습니다. **Inherit Owners From Monitors**는 인시던트 모니터의 모든 소유자를 인시던트의 소유자로 만들며, **Inherit Owners From Hosts**, **… From Kubernetes Clusters**, **… From Docker Hosts**, **… From Podman Hosts**, **… From Services**도 해당 리소스에 대해 같은 일을 합니다.

**Notify Owners** 토글은 사람들에게 알릴지 여부를 제어합니다. 실제 라우팅을 위해서는 켜 두고, 소유자를 조용히 추가하려면 끄세요 — 규칙이 호출이 아니라 장부 정리용 편의 기능일 때 유용합니다.

모든 규칙 실행은 인시던트 피드에 기록되므로, 어떤 사람이 규칙에 의해 추가되었는지 사람에 의해 추가되었는지 항상 확인할 수 있습니다.

## 소유자가 알림받는 내용

다섯 개의 작업이 소유자에게 알리며, 각각 1분마다 실행됩니다.

- **인시던트 생성** — 제목 `[New Incident {number}] - {title}`.
- **노트 게시됨** — 공개 노트와 비공개 노트 모두에 대해, 제목 `[Update Incident {number}] - {title}`.
- **인시던트 상태 변경** — [인시던트 상태 및 심각도](/docs/incidents/states-and-severities)를 참고하세요.
- **소유자로 추가됨** — 제목 `You have been added as the owner of Incident {number} - {title}`.
- **여전히 미해결** — 인시던트의 다음 리마인더 시각에 따른 알림이며, 제목 `[Reminder] Incident {number} is still {state} - {title}`.

각 알림은 이메일, SMS, 음성 통화, 푸시, WhatsApp용으로 만들어져 사용자의 알림 설정에 전달되며, 실제로 무엇이 발송될지는 그 설정이 결정합니다. 모든 수신자는 이 각각을 개별적으로 끌 수 있습니다 — 사용자별 설정은 인시던트 생성, 노트 게시, 상태 변경, 소유자 추가, 구성원 배정, 미해결 리마인더 알림을 보낸다는 문구로 표현됩니다. 상태 변경에 대해서만 전화를 받고 싶은 사람은 정확히 그렇게 설정할 수 있습니다.

**소유자가 없는 인시던트도 조용히 지나가지 않습니다.** 인시던트에 소유자가 전혀 없으면 알림 작업은 프로젝트의 소유자에게 대신 알리므로, 아무것도 빠뜨려지지 않습니다. 알림을 받은 모든 사람은 해당 피드 항목에도 추가되므로, 나중에 정확히 누가 어떤 주소로 알림을 받았는지 확인할 수 있습니다.
