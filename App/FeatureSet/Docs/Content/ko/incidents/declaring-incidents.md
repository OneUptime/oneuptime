# 인시던트 선언

인시던트를 선언하는 순간부터 OneUptime이 기록을 시작합니다. 레코드가 만들어지고, 번호가 찍히고, 온콜 정책이 실행되고 — 그러지 말라고 하지 않는 한 — 상태 페이지 구독자에게 소식이 나갑니다. 인시던트 수명 주기의 나머지는 모두 그 첫 번째 쓰기 위에 얹힙니다.

인시던트가 OneUptime에 들어오는 길은 네 가지이고, 모두 같은 곳에 도착합니다. 심각도와 현재 상태, 영향받는 리소스 목록을 가진 `Incident` 테이블의 한 행입니다. 차이는 누가 필드를 채우느냐뿐입니다 — 새벽 3시의 당신, 저장해 둔 템플릿, 모니터의 기준, 아니면 API를 호출하는 여러분의 코드.

이 페이지는 그 네 가지를 필드 단위로 훑고, 이어서 서버가 대신 채워 주는 것과 인시던트가 존재하게 되는 순간 실행되는 것을 다룹니다.

## 인시던트가 선언되는 네 가지 방법

| 이렇게 하고 싶다면…                                     | 이것을 고르세요                                                             |
| ------------------------------------------------------------ | --------------------------------------------------------------------------- |
| 모든 항목을 직접 채워 인시던트를 연다                       | **인시던트 선언** 마법사                                                    |
| 반복되는 유형의 인시던트를 미리 채워진 상태로 연다          | **템플릿에서 생성**                                                         |
| 모니터 검사가 실패할 때 자동으로 연다                       | **When filters match, declare an incident.** 를 켠 모니터 기준 필터         |
| 여러분의 코드, 스크립트, 다른 도구에서 연다                 | `POST /api/incident`                                                        |

네 가지 모두 같은 모델에 기록하므로, 프로브가 연 인시던트는 대응자가 직접 연 인시던트와 똑같이 생겼습니다 — 자동 생성 건에 서버가 붙이는 몇 개의 관리용 컬럼만 다릅니다.

## 직접 선언하기

**인시던트 → 모든 인시던트**를 열고 **인시던트** 목록 오른쪽 위의 **인시던트 선언**을 클릭합니다. **새 인시던트 선언**이라는 제목의 카드로 이동하며, 양식은 **인시던트 세부 정보**, **영향받는 리소스**, **인시던트 역할**, **온콜**, **더보기** 다섯 단계에 걸쳐 펼쳐집니다. 마지막 제출 버튼도 **인시던트 선언**입니다.

필수 항목이 있는 단계는 첫 번째뿐입니다. 급하다면 **인시던트 세부 정보**만 채우고 제출하세요 — 리소스 연결, 역할 배정, 온콜 정책 추가는 나중에 인시던트 자체 페이지에서 할 수 있습니다.

### 1단계 — 인시던트 세부 정보

- **제목** — 필수입니다. 목록에서, Slack에서, 그리고 (인시던트가 공개되어 있다면) 상태 페이지에서 모두가 보게 될 한 줄 요약입니다. 자리 표시자는 `Incident Title`입니다.
- **설명** — 선택 사항이며 마크다운으로 작성합니다. 상태 페이지에 렌더링되는 필드이므로 팀이 아니라 고객을 위해 쓰세요. 나중에 인시던트 사이드 메뉴의 **설명**에서 수정할 수 있습니다.
- **선언 시각** — 양식에서는 필수이고 기본값은 현재 시각입니다. 인시던트의 모든 지속 시간이 이 시각을 기준으로 측정되므로, 더 일찍 시작된 일을 기록하는 중이라면 과거 시각으로 조정하세요.
- **인시던트 심각도** — 필수입니다. 프로젝트에 설정된 심각도 중 하나이며, 새 프로젝트에는 **심각한 인시던트**, **주요 인시던트**, **경미한 인시던트**가 기본으로 들어 있습니다.
- **인시던트 상태** — 선택 사항입니다. 그대로 두면 인시던트는 `isCreatedState` 플래그가 달린 상태로 들어가고, 새 프로젝트에서는 그것이 **확인됨**입니다. 이미 그 단계를 지난 인시던트를 기록하는 경우에만 직접 지정하세요.

**상태 드롭다운이 말썽이라면.** 프로젝트에 `isCreatedState` 플래그를 가진 상태가 하나도 없으면 생성 호출이 실패하면서 설정에서 생성 인시던트 상태를 추가하라고 안내합니다. 이는 보통 상태를 많이 손댄 프로젝트에서만 벌어집니다 — [인시던트 상태 및 심각도](/docs/incidents/states-and-severities)를 보세요.

### 2단계 — 영향받는 리소스

- **영향받는 리소스** — 모니터, 호스트, Kubernetes 클러스터, Docker 호스트, Podman 호스트, 서비스를 붙이는 하나의 검색 상자입니다. 내부적으로는 인시던트의 별개 관계(`monitors`, `hosts`, `kubernetesClusters`, `dockerHosts`, `podmanHosts`, `services` 등)이지만, 양식은 이를 하나의 선택기로 합쳐 보여 줍니다.
- **Change Monitor Status to** — 선택 사항입니다. 이 인시던트에 붙은 모든 모니터에 적용할 모니터 상태를 고릅니다. 인시던트 선언과 모니터 저하 표시를 두 번이 아니라 한 번에 끝낼 수 있습니다.

**군더더기처럼 느껴져도 모니터는 꼭 붙이세요.** 인시던트와 상태 페이지를 잇는 고리는 인시던트의 모니터를 통과합니다. 상태 페이지의 리소스 중 하나가 인시던트의 모니터일 때 그 인시던트가 페이지에 나타납니다. 인시던트에 붙은 모니터가 없으면 구독자에게 가는 상태 변경 알림은 아예 건너뜁니다. [상태 페이지 리소스 및 그룹](/docs/status-pages/resources-and-groups)을 보세요.

### 3단계 — 인시던트 역할

- **인시던트 역할 할당** — 프로젝트가 정의한 역할에 팀원을 배정합니다. 일부 역할은 여러 사용자를 받습니다.

역할 자체는 **인시던트 → 설정 → 인시던트 역할**에서 구성하며, 대응 중에 배정할 수 있는 역할 — 인시던트 책임자, 대응자, 그 밖에 여러분의 프로세스에 필요한 무엇이든 — 을 정의합니다. 이 단계를 건너뛰면 아직 역할을 맡은 사람이 없을 경우 첫 상태 변경 때 인시던트 책임자가 자동으로 배정됩니다.

### 4단계 — 온콜

- **온콜 정책** — 이 인시던트가 생성될 때 실행할 온콜 근무 정책을 여러 개 고르는 항목입니다. 인시던트의 `onCallDutyPolicies`에 대응됩니다.

온콜 정책을 인시던트에 직접 붙이는 곳은 여기가 유일합니다. 심각도는 온콜 정책을 갖지 않습니다 — 심각도는 이름표이고, 호출에 영향을 주는 것은 온콜 규칙 안의 *일치 조건*으로 쓰일 때뿐입니다. **인시던트 → 규칙 → 온콜 규칙**에 설정한 규칙은 여기서 고른 것 위에 자기 정책을 더하며, 최종적으로 실행되는 집합은 둘을 합쳐 중복을 제거한 결과입니다.

### 5단계 — 더보기

- **레이블** — 선택 사항이자 고급 기능입니다. 이 레이블에 접근 권한이 있는 팀원만 해당 인시던트에 접근할 수 있습니다.
- **상태 페이지 구독자에게 알림** — 체크박스이며 기본적으로 켜져 있습니다. 인시던트 생성 사실을 구독자에게 이메일로 알릴지 결정합니다(`shouldStatusPageSubscribersBeNotifiedOnIncidentCreated`). 기록은 남기되 밖으로 알리고 싶지 않은 내부 소음이라면 끄세요.
- **비공개 인시던트** — 체크박스이며 기본적으로 꺼져 있습니다(`isPrivate`). 비공개 인시던트는 소유자 사용자, 소유자 팀의 구성원, 프로젝트 관리자, 프로젝트 소유자에게만 보이며 — 다른 어떤 설정과도 무관하게 모든 상태 페이지에서 숨겨집니다. 인시던트 목록에서는 빨간 **Private** 알약으로 표시됩니다.

**Should be visible on status page?** 플래그(`isVisibleOnStatusPage`)는 마법사에 없고 기본값은 참입니다. 나중에 인시던트 사이드 메뉴의 **설정**에서 바꿀 수 있으며, 그곳에서는 **상태 페이지에 표시**라고 되어 있습니다.

## 템플릿에서 선언하기

같은 모양의 인시던트를 계속 선언하고 있다면 — 같은 제목 패턴, 같은 심각도, 같은 온콜 정책 — 한 번 템플릿으로 저장해 두세요.

**템플릿에서 생성**(**인시던트 선언** 옆의 외곽선 버튼)을 클릭하면 **인시던트 템플릿 선택** 드롭다운이 있는 **템플릿에서 인시던트 만들기** 모달이 열립니다. 템플릿을 고르면 생성 양식이 미리 채워진 채 열리고, 제출 전에 무엇이든 바꿀 수 있습니다. 프로젝트에 아직 템플릿이 없다면 대신 **No Incident Templates** 모달이 뜨고, 거기 있는 **Create Template** 버튼이 **인시던트 → 설정 → 인시던트 템플릿**으로 데려다줍니다.

템플릿은 자체 6단계 마법사 — **템플릿 정보**, **인시던트 세부 정보**, **영향받는 리소스**, **온콜**, **소유자**, **레이블** — 로 만들며 다음 필드를 갖습니다.

| 필드                         | 용도                                                   |
| ---------------------------- | ------------------------------------------------------ |
| **템플릿 이름**              | 선택기에서 템플릿을 알아보는 이름입니다.               |
| **템플릿 설명**              | 언제 이걸 꺼내 쓸지 미래의 자신에게 남기는 메모입니다. |
| **제목**                     | 인시던트에 미리 채워질 제목입니다.                     |
| **설명**                     | 인시던트에 미리 채워질 마크다운 설명입니다.            |
| **인시던트 심각도**          | 인시던트에 미리 채워질 심각도입니다.                   |
| **초기 인시던트 상태**       | 이 템플릿에서 만든 인시던트가 시작할 상태입니다.       |
| **영향받는 리소스**          | 연결할 모니터, 호스트, 클러스터, 서비스입니다.         |
| **Change Monitor Status to** | 연결된 모니터에 적용할 모니터 상태입니다.              |
| **온콜 정책**                | 인시던트 생성 시 실행할 정책입니다.                    |
| **소유자 - 팀**              | 이 템플릿으로 만든 인시던트를 소유할 팀입니다.         |
| **소유자 - 사용자**          | 이 템플릿으로 만든 인시던트를 소유할 사용자입니다.     |
| **레이블**                   | 인시던트에 적용할 레이블입니다.                        |

간단한 규칙 몇 가지가 있습니다.

- 템플릿은 템플릿 목록에서 편집할 수 없습니다 — 하나를 만든 다음, 열어서 바꾸세요.
- 템플릿은 여러분이 비워 둔 필드만 채웁니다. 생성 페이지에서는 덮어쓸 수 있는 미리 채우기로 적용되고, API에서는 요청이 해당 필드를 `undefined`로 남겨 둔 경우에만 서버가 템플릿에서 채웁니다. 호출자가 보낸 값이 언제나 이깁니다.

## 모니터 기준으로 자동 선언하기

대부분의 인시던트는 사람이 직접 입력할 필요가 없어야 합니다. 모니터의 기준 편집기에서 **When filters match, declare an incident.** 토글을 켜면 **Add Incident** 버튼이 있는 **인시던트 생성** 섹션이 나타납니다 — 하나의 기준 필터가 인시던트를 여러 개 선언할 수도 있습니다.

각 항목에는 다음이 있습니다.

- **인시던트 제목** — 템플릿 표현식을 지원하며, 자리 표시자는 `{{monitorName}} is down` 같은 형태를 제안합니다.
- **심각도** — 필수입니다.
- **인시던트 설명** — 역시 템플릿 표현식을 씁니다.
- **온콜 → 온콜 정책** — 이 인시던트가 생성될 때 실행할 정책입니다.
- **인시던트 역할** — 팀원을 역할에 미리 배정합니다.
- **소유권 및 레이블 → 소유자 팀**, **소유자 사용자**, **레이블**.
- **고급 옵션 → 인시던트 자동 해결**(기준이 더 이상 일치하지 않으면 인시던트를 자동으로 해결), **상태 페이지에 인시던트 표시**, **비공개 인시던트**, **해결 노트**.

제목, 설명, 해결 노트에 쓸 수 있는 `{{variable}}` 자리 표시자 전체 목록은 [인시던트 및 알림 템플릿](/docs/monitor/incident-alert-templating)을 보세요.

이렇게 만들어진 인시던트에는 서버가 표식을 붙입니다. `isCreatedAutomatically`가 설정되고, `createdCriteriaId`에 어떤 기준 필터가 실행됐는지, `createdByProbe`에 어떤 프로브가 발견했는지가 기록됩니다. 그 밖의 모든 동작은 직접 선언한 인시던트와 완전히 같습니다.

## API로 선언하기

인시던트 모델은 표준 CRUD 엔드포인트를 제공하므로 `POST /api/incident`로 하나를 만들 수 있습니다. 인증은 **프로젝트 설정 → API 키**에서 발급한 API 키를 `apikey` 헤더에 실어 보내면 됩니다 — 키가 프로젝트를 식별하므로 프로젝트 id를 따로 넘길 필요가 없습니다.

```bash
curl -X POST https://oneuptime.com/api/incident \
  -H "apikey: $ONEUPTIME_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "data": {
      "title": "Checkout latency above SLO",
      "description": "Investigating elevated p99 latency on the checkout service.",
      "incidentSeverityId": "<incident-severity-id>"
    }
  }'
```

요청 본문에서 유용한 필드는 다음과 같습니다.

- `title` — 반드시 넣어야 하는 유일한 필드입니다.
- `declaredAt` — 양식에서는 필수지만 여기서는 선택입니다. 생략하면 서버가 현재 시각을 씁니다.
- `incidentSeverityId`와 `currentIncidentStateId` — 서버는 둘 다 API 키와 같은 프로젝트에 속하는지 확인하고, 아니면 요청을 거부합니다. **Change Monitor Status to** 뒤에 있는 모니터 상태에도 같은 검사가 적용됩니다.
- `createdIncidentTemplateId` — 저장해 둔 템플릿을 적용합니다. 빠뜨린 필드는 템플릿에서 채워지고, 보낸 필드는 그대로 유지됩니다.

관련 엔드포인트로는 `/api/incident-state`, `/api/incident-severity`, `/api/incident-state-timeline`이 있습니다. 자동 생성된 [API 참조](/reference)에 각각의 정확한 요청과 응답 형태가 있으며, 모니터 같은 관계 필드를 어떻게 표현하는지도 나와 있습니다.

## 인시던트 번호와 접두사

모든 인시던트는 프로젝트별 카운터에서 순차 번호를 받으며, 생성 시점에 서버가 할당합니다. 이를 담는 컬럼은 둘입니다. `incidentNumber`(원시 정수)와 `incidentNumberWithPrefix`(실제로 보이는 값)입니다. 접두사를 설정하지 않으면 표시 값은 `#42`입니다.

이를 바꾸려면 **인시던트 → 설정 → 기타 설정**으로 가세요. **숫자 접두사** 카드에 **인시던트 번호 접두사** 필드(최대 20자, 자리 표시자 `INC-`)가 있고, 값을 넣으면 같은 인시던트가 `INC-42`로 표시됩니다. 비워 두면 기본값 `#`가 유지됩니다. 이 카드에는 에피소드 번호를 위한 **인시던트 에피소드 번호 접두사**도 함께 있습니다.

번호는 인시던트 목록의 첫 번째 열에 나타나 인시던트로 연결되며, 인시던트 **개요**에서는 **인시던트 번호**로 표시됩니다.

## 인시던트가 선언되는 순간 벌어지는 일

생성 호출은 행 하나를 쓰는 것 이상을 합니다. 순서대로 보면 이렇습니다.

1. **서버가 빈 곳을 채웁니다.** `declaredAt`은 현재 시각으로, 현재 상태는 프로젝트의 `isCreatedState` 상태로 기본 설정되고, 인시던트 번호와 접두사가 붙은 번호가 프로젝트 카운터에서 할당됩니다.
2. **템플릿이 적용됩니다.** `createdIncidentTemplateId`가 넘어온 경우이며, 호출자가 정의하지 않은 채 남긴 필드만 채웁니다.
3. **개인정보 보호 규칙이 실행되어**, 일치하는 규칙이 그렇게 말하면 인시던트를 비공개로 표시합니다. 가장 먼저 실행되는 규칙 엔진이라 이후의 모든 단계가 올바른 공개 설정을 보게 됩니다.
4. **소유자 규칙이 실행되어**, 일치하는 규칙이 지목한 소유자 사용자와 팀을 추가합니다.
5. **레이블 규칙이 실행되어**, 인시던트에 맞는 레이블을 붙입니다.
6. **온콜 규칙이 실행됩니다.** **인시던트 → 규칙 → 온콜 규칙**에 있는 활성 규칙 중 기준이 일치하는 것은 모두 자기 정책을 인시던트에 더합니다. 우선순위도 없고 도중에 멈추지도 않습니다 — 일치하는 규칙이 전부 실행되고 정책은 중복 제거됩니다.
7. **런북 규칙이 실행되어**, 일치하는 런북을 연결하고 시작합니다. [Runbook](/docs/runbooks/index)을 보세요.
8. **온콜 정책이 실행됩니다.** 마법사에서 고른 것, 템플릿에서 물려받은 것, 규칙이 더한 것 등 인시던트에 붙은 모든 정책이 `IncidentCreated` 이벤트 유형으로 병렬 실행됩니다. 한 정책이 실패해도 나머지는 멈추지 않습니다.
9. **구독자가 대기열에 올라갑니다.** **상태 페이지 구독자에게 알림**을 켜 두었고 인시던트가 상태 페이지에 보이는 경우입니다. 발송은 요청과 함께 처리되지 않고 백그라운드 작업이 담당합니다.
10. **워크플로우가 실행됩니다.** **On Create Incident** 트리거가 그 위에 만들어진 워크플로우를 시작합니다. [워크플로우 개요](/docs/workflows/index)를 보세요.

여기서부터 인시던트는 살아 있습니다. 인시던트 사이드 메뉴의 **활성 인시던트** 배지에 잡히고(`isResolvedState` 플래그가 없는 모든 상태는 활성으로 셉니다), 자기 모니터를 담고 있는 상태 페이지에 나타나며, **상태 타임라인**이 기록을 시작합니다.
