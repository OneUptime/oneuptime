# 인시던트 선언

인시던트 선언은 OneUptime이 기록을 시작하는 순간입니다. 기록이 생성되고, 번호가 부여되며, 온콜 정책이 실행되고, 따로 지정하지 않는 한 상태 페이지 구독자에게도 소식이 전해집니다. 인시던트 라이프사이클의 나머지는 모두 이 첫 번째 쓰기에 달려 있습니다.

인시던트가 OneUptime에 들어오는 경로는 네 가지이며, 모두 같은 곳으로 이어집니다. 바로 심각도, 현재 상태, 영향받는 리소스 목록을 가진 `Incident` 테이블의 한 행입니다. 차이는 누가 필드를 채우느냐뿐입니다. 새벽 3시의 여러분, 저장해 둔 템플릿, 모니터의 조건, 또는 API를 호출하는 여러분의 코드일 수 있습니다.

이 페이지에서는 네 가지 경로를 필드 단위로 살펴본 다음, 서버가 대신 채워 주는 값과 인시던트가 생성되는 순간 실행되는 것들을 다룹니다.

## 인시던트가 선언되는 네 가지 방법

| 이렇게 하고 싶다면…                                          | 선택하세요                                                                  |
| ------------------------------------------------------------ | --------------------------------------------------------------------------- |
| 모든 항목을 직접 입력해 수동으로 인시던트를 열고 싶다        | **인시던트 선언** 마법사                                                    |
| 반복되는 유형의 인시던트를 미리 채워진 필드로 열고 싶다      | **템플릿에서 생성**                                                         |
| 모니터 점검이 실패하면 자동으로 열리게 하고 싶다             | **필터가 일치하면 인시던트를 선언합니다.**가 켜진 모니터 조건 필터           |
| 직접 작성한 코드, 스크립트, 다른 도구에서 열고 싶다          | `POST /api/incident`                                                        |

네 가지 모두 같은 모델에 기록되므로, 프로브가 연 인시던트는 대응자가 직접 연 인시던트와 완전히 똑같아 보입니다. 자동 생성된 인시던트에 서버가 설정하는 몇 개의 관리용 컬럼만 다를 뿐입니다.

## 직접 선언하기

**인시던트 → 모든 인시던트**를 열고 **인시던트** 목록 오른쪽 위의 **인시던트 선언**을 클릭합니다. 그러면 **새 인시던트 선언**이라는 제목의 카드로 이동하며, 양식이 **인시던트 세부 정보**, **영향받는 리소스**, **인시던트 역할**, **온콜**, **더보기**의 다섯 단계로 나뉘어 있습니다. 마지막의 제출 버튼도 **인시던트 선언**이라고 표시됩니다.

필수 필드가 있는 단계는 첫 번째 단계뿐입니다. 급하다면 **인시던트 세부 정보**만 채우고 제출하세요. 리소스 연결, 역할 배정, 온콜 정책 추가는 나중에 인시던트 자체 페이지에서 할 수 있습니다.

### 1단계 — 인시던트 세부 정보

- **제목** — 필수입니다. 목록에서, Slack에서, 그리고 (인시던트가 표시된다면) 상태 페이지에서 모두가 보게 될 한 줄 요약입니다. 플레이스홀더는 `Incident Title`입니다.
- **설명** — 선택 사항이며 마크다운으로 작성합니다. 상태 페이지에 렌더링되는 필드이므로 팀이 아니라 고객을 위해 쓰세요. 나중에 인시던트 사이드 메뉴의 **설명**에서 편집할 수 있습니다.
- **선언 시각** — 양식에서는 필수이며 기본값은 현재 시각입니다. 인시던트의 모든 지속 시간이 이 타임스탬프를 기준으로 측정되므로, 더 이전에 시작된 일을 기록하는 중이라면 시각을 앞당겨 지정하세요.
- **인시던트 심각도** — 필수입니다. 프로젝트에 구성된 심각도 중 하나이며, 신규 프로젝트에는 **Critical Incident**, **Major Incident**, **Minor Incident**가 기본 생성됩니다.
- **인시던트 상태** — 선택 사항입니다. 그대로 두면 인시던트는 `isCreatedState` 플래그가 붙은 상태로 들어가며, 신규 프로젝트에서는 **Identified**가 그것입니다. 이미 그 지점을 지난 인시던트를 기록할 때만 지정하세요.

**상태 드롭다운이 말썽이라면.** 프로젝트에 `isCreatedState` 플래그를 가진 상태가 없으면 생성 호출이 실패하고, 설정에서 생성 인시던트 상태를 추가하라는 안내가 표시됩니다. 이는 보통 상태를 크게 손댄 프로젝트에서만 발생합니다. [인시던트 상태 및 심각도](/docs/incidents/states-and-severities)를 참고하세요.

### 2단계 — 영향받는 리소스

- **영향받는 리소스** — 모니터, 호스트, Kubernetes 클러스터, Docker 호스트, Podman 호스트, 서비스를 연결하는 단일 검색 상자입니다. 내부적으로는 인시던트의 별도 관계(`monitors`, `hosts`, `kubernetesClusters`, `dockerHosts`, `podmanHosts`, `services` 등)이지만, 양식에서는 하나의 선택기로 합쳐져 있습니다.
- **Change Monitor Status to** — 선택 사항입니다. 이 인시던트에 연결된 모든 모니터에 적용할 모니터 상태를 고릅니다. 덕분에 인시던트를 선언하고 모니터를 저하 상태로 표시하는 일을 두 번이 아니라 한 번에 처리할 수 있습니다.

**불필요해 보여도 모니터를 연결하세요.** 인시던트와 상태 페이지 사이의 연결은 인시던트의 모니터를 통해 이루어집니다. 상태 페이지는 자신의 리소스 중 하나가 인시던트의 모니터일 때 그 인시던트를 표시합니다. 인시던트에 연결된 모니터가 없으면 구독자에게 보내는 상태 변경 알림은 아예 건너뜁니다. [상태 페이지 리소스 및 그룹](/docs/status-pages/resources-and-groups)을 참고하세요.

### 3단계 — 인시던트 역할

- **인시던트 역할 할당** — 프로젝트가 정의한 역할에 팀 구성원을 배정합니다. 일부 역할은 여러 사용자를 받을 수 있습니다.

역할 자체는 **인시던트 → 설정 → 인시던트 역할**에서 구성하며, 대응 중에 배정할 수 있는 역할(Incident Commander, Responder, 그 밖에 프로세스에 필요한 역할)을 정의합니다. 이 단계를 건너뛰면 아직 역할을 가진 사람이 없을 때 첫 상태 변경 시 Incident Commander가 자동으로 배정됩니다.

### 4단계 — 온콜

- **온콜 정책** — 이 인시던트가 생성될 때 실행할 온콜 듀티 정책의 다중 선택입니다. 인시던트의 `onCallDutyPolicies`에 대응됩니다.

온콜 정책을 인시던트에 직접 연결하는 곳은 여기뿐입니다. 심각도는 온콜 정책을 가지지 않습니다. 심각도는 레이블이며, 온콜 규칙 안의 *일치 기준*으로서만 호출에 영향을 줍니다. **인시던트 → 규칙 → 온콜 규칙**에서 구성한 규칙은 여기에서 고른 정책 위에 자신의 정책을 더하며, 최종적으로 실행되는 집합은 둘의 합집합에서 중복을 제거한 것입니다.

### 5단계 — 더보기

- **레이블** — 선택 사항이자 고급 기능입니다. 이 레이블에 접근 권한이 있는 팀 구성원만 인시던트에 접근할 수 있습니다.
- **상태 페이지 구독자에게 알림** — 체크박스이며 기본적으로 켜져 있습니다. 인시던트 생성에 대해 구독자에게 이메일을 보낼지 여부를 제어합니다(`shouldStatusPageSubscribersBeNotifiedOnIncidentCreated`). 기록은 남기되 외부에는 알리고 싶지 않은 내부 잡음이라면 끄세요.
- **비공개 인시던트** — 체크박스이며 기본적으로 꺼져 있습니다(`isPrivate`). 비공개 인시던트는 소유자 사용자, 소유자 팀의 구성원, 프로젝트 관리자, 프로젝트 소유자에게만 보이며, 다른 설정과 무관하게 모든 상태 페이지에서 숨겨집니다. 인시던트 목록에서는 빨간 **Private** 알약 표시로 구분됩니다.

**상태 페이지에 표시되어야 하나요?** 플래그(`isVisibleOnStatusPage`)는 마법사에 없으며 기본값은 true입니다. 나중에 인시던트 사이드 메뉴의 **설정**에서 바꿀 수 있으며, 그곳에서는 **상태 페이지에 표시**로 표기됩니다.

## 템플릿에서 선언하기

같은 형태의 인시던트를 계속 선언하고 있다면 — 같은 제목 패턴, 같은 심각도, 같은 온콜 정책 — 한 번 템플릿으로 저장해 두세요.

**템플릿에서 생성**(**인시던트 선언** 옆의 외곽선 버튼)을 클릭하면 **템플릿에서 인시던트 만들기** 모달이 열리고 **인시던트 템플릿 선택** 드롭다운이 나타납니다. 템플릿을 고르면 생성 양식이 미리 채워진 상태로 열리며, 제출 전에 무엇이든 바꿀 수 있습니다. 프로젝트에 템플릿이 아직 없다면 대신 **No Incident Templates** 모달이 나타나고, **Create Template** 버튼이 **인시던트 → 설정 → 인시던트 템플릿**으로 안내합니다.

템플릿은 자체적인 6단계 마법사 — **템플릿 정보**, **인시던트 세부 정보**, **영향받는 리소스**, **온콜**, **소유자**, **레이블** — 로 만들며, 다음 필드를 가집니다.

| 필드                             | 용도                                                   |
| -------------------------------- | ------------------------------------------------------ |
| **템플릿 이름**                  | 선택기에서 템플릿을 식별하는 방식입니다.               |
| **템플릿 설명**                  | 언제 이 템플릿을 쓸지 미래의 자신에게 남기는 메모입니다. |
| **제목**                         | 인시던트에 미리 채워지는 제목입니다.                   |
| **설명**                         | 인시던트에 미리 채워지는 마크다운 설명입니다.          |
| **인시던트 심각도**              | 인시던트에 미리 채워지는 심각도입니다.                 |
| **초기 인시던트 상태**           | 이 템플릿으로 만든 인시던트가 시작하는 상태입니다.     |
| **영향받는 리소스**              | 연결할 모니터, 호스트, 클러스터, 서비스입니다.         |
| **Change Monitor Status to**     | 연결된 모니터에 적용할 모니터 상태입니다.              |
| **온콜 정책**                    | 인시던트가 생성될 때 실행할 정책입니다.                |
| **소유자 - 팀**                  | 이 템플릿으로 만든 인시던트를 소유하는 팀입니다.       |
| **소유자 - 사용자**              | 이 템플릿으로 만든 인시던트를 소유하는 사용자입니다.   |
| **레이블**                       | 인시던트에 적용되는 레이블입니다.                      |

몇 가지 간단한 규칙이 있습니다.

- 템플릿은 템플릿 목록에서 편집할 수 없습니다. 먼저 만든 다음, 열어서 변경합니다.
- 템플릿은 비워 둔 필드만 채웁니다. 생성 페이지에서 템플릿은 덮어쓸 수 있는 사전 입력값으로 적용되며, API에서는 요청이 해당 필드를 `undefined`로 남긴 경우에만 서버가 템플릿에서 채웁니다. 호출자가 제공한 값이 언제나 우선합니다.

## 모니터 조건에서 자동으로 선언하기

대부분의 인시던트는 사람이 직접 입력할 필요가 없어야 합니다. 모니터의 조건 편집기에서 **필터가 일치하면 인시던트를 선언합니다.** 토글을 켜면 **인시던트 추가** 버튼이 있는 **인시던트 생성** 섹션이 나타납니다. 하나의 조건 필터가 둘 이상의 인시던트를 선언할 수 있습니다.

각 항목에는 다음이 있습니다.

- **인시던트 제목** — 템플릿을 지원합니다. 플레이스홀더는 `{{monitorName}} is down` 같은 형태를 제안합니다.
- **심각도** — 필수입니다.
- **인시던트 설명** — 역시 템플릿을 지원합니다.
- **온콜 → 온콜 정책** — 이 인시던트가 생성될 때 실행되는 정책입니다.
- **인시던트 역할** — 팀 구성원을 역할에 미리 배정합니다.
- **소유권 및 레이블 → 소유자 팀**, **소유자 사용자**, **레이블**.
- **고급 옵션 → 인시던트 자동 해결**(조건이 더 이상 일치하지 않으면 인시던트를 자동으로 해결), **상태 페이지에 인시던트 표시**, **비공개 인시던트**, **해결 노트**.

제목, 설명, 해결 노트에 사용할 수 있는 `{{variable}}` 플레이스홀더의 전체 목록은 [인시던트 및 알림 템플릿](/docs/monitor/incident-alert-templating)을 참고하세요.

이렇게 생성된 인시던트에는 서버가 표시를 남깁니다. `isCreatedAutomatically`가 설정되고, `createdCriteriaId`에 어떤 조건 필터가 실행되었는지, `createdByProbe`에 어떤 프로브가 감지했는지 기록됩니다. 그 외의 모든 동작은 직접 선언한 인시던트와 완전히 동일합니다.

## API로 선언하기

인시던트 모델은 표준 CRUD 엔드포인트를 제공하므로 `POST /api/incident`로 하나를 생성할 수 있습니다. **프로젝트 설정 → API 키**에서 생성한 API 키로 인증하며, `apikey` 헤더에 담아 보냅니다. 키가 프로젝트를 식별하므로 프로젝트 ID를 따로 전달할 필요는 없습니다.

```bash
curl -X POST https://oneuptime.com/api/incident \
  -H "apikey: $ONEUPTIME_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "data": {
      "title": "Checkout latency above SLO",
      "description": "Investigating elevated p99 latency on the checkout service.",
      "incidentSeverityId": "<incident-severity-id>"
    }
  }'
```

요청 본문에서 유용한 필드는 다음과 같습니다.

- `title` — 반드시 제공해야 하는 유일한 필드입니다.
- `declaredAt` — 양식에서는 필수이지만 여기에서는 선택 사항입니다. 생략하면 서버가 현재 시각을 사용합니다.
- `incidentSeverityId`와 `currentIncidentStateId` — 서버는 둘 다 API 키와 같은 프로젝트에 속하는지 확인하고, 그렇지 않으면 요청을 거부합니다. **Change Monitor Status to** 뒤에 있는 모니터 상태에도 같은 검사가 적용됩니다.
- `createdIncidentTemplateId` — 저장된 템플릿을 적용합니다. 생략한 필드는 템플릿에서 채워지고, 보낸 필드는 그대로 유지됩니다.

관련 엔드포인트로는 `/api/incident-state`, `/api/incident-severity`, `/api/incident-state-timeline`이 있습니다. 자동 생성된 [API 참조](/reference)에는 각 엔드포인트의 정확한 요청 및 응답 형태가 있으며, 모니터 같은 관계 필드를 어떻게 표현하는지도 나와 있습니다.

## 인시던트 번호와 접두사

모든 인시던트는 프로젝트별 카운터에서 순차 번호를 받으며, 생성 시점에 서버가 부여합니다. 두 개의 컬럼이 이를 담습니다. `incidentNumber`(원시 정수)와 `incidentNumberWithPrefix`(실제로 보이는 값)입니다. 접두사를 설정하지 않으면 표시 값은 `#42`입니다.

이를 바꾸려면 **인시던트 → 설정 → 기타 설정**으로 이동하세요. **숫자 접두사** 카드에 **인시던트 번호 접두사** 필드(최대 20자, 플레이스홀더 `INC-`)가 있으며, 이를 설정하면 같은 인시던트가 `INC-42`로 표시됩니다. 비워 두면 기본값 `#`가 유지됩니다. 이 카드에는 에피소드 번호 부여를 위한 **인시던트 에피소드 번호 접두사**도 있습니다.

번호는 인시던트 목록의 첫 번째 열에 나타나 인시던트로 연결되며, 인시던트 **개요**에는 **인시던트 번호**로 표시됩니다.

## 인시던트가 선언되는 순간 일어나는 일

생성 호출은 단순히 한 행을 쓰는 것 이상을 합니다. 순서대로 보면 다음과 같습니다.

1. **서버가 빈 곳을 채웁니다.** `declaredAt`은 현재 시각으로, 현재 상태는 프로젝트의 `isCreatedState` 상태로 기본 설정되며, 인시던트 번호와 접두사가 붙은 번호가 프로젝트 카운터에서 부여됩니다.
2. **템플릿이 적용됩니다.** `createdIncidentTemplateId`가 제공된 경우이며, 호출자가 정의하지 않은 필드만 채웁니다.
3. **개인정보 보호 규칙이 실행되어**, 일치하는 규칙이 그렇게 지시하면 인시던트를 비공개로 표시합니다. 가장 먼저 실행되는 규칙 엔진이므로 이후의 모든 단계는 올바른 비공개 설정을 보게 됩니다.
4. **소유자 규칙이 실행되어**, 일치하는 규칙이 지정한 소유자 사용자와 팀을 추가합니다.
5. **레이블 규칙이 실행되어**, 인시던트에 맞는 레이블을 추가합니다.
6. **온콜 규칙이 실행됩니다.** **인시던트 → 규칙 → 온콜 규칙**에 있는 활성화된 규칙 중 조건이 일치하는 모든 규칙이 자신의 정책을 인시던트에 추가합니다. 우선순위도 없고 단축 평가도 없습니다. 일치하는 모든 규칙이 실행되며 정책은 중복 제거됩니다.
7. **Runbook 규칙이 실행되어**, 일치하는 runbook을 연결하고 시작합니다. [Runbook](/docs/runbooks/index)을 참고하세요.
8. **온콜 정책이 실행됩니다.** 마법사에서 고른 것이든, 템플릿에서 상속된 것이든, 규칙이 추가한 것이든 인시던트의 모든 정책이 `IncidentCreated` 이벤트 유형으로 병렬 실행됩니다. 하나의 정책이 실패해도 나머지는 멈추지 않습니다.
9. **구독자 발송이 대기열에 들어갑니다.** **상태 페이지 구독자에게 알림**이 켜져 있고 인시던트가 상태 페이지에 표시되는 경우입니다. 전달은 요청과 동시에 처리되지 않고 백그라운드 작업이 담당합니다.
10. **워크플로우가 실행됩니다.** **On Create Incident** 트리거가 그 위에 만들어진 워크플로우를 시작합니다. [워크플로우 개요](/docs/workflows/index)를 참고하세요.

이제 인시던트가 살아 움직입니다. 인시던트 사이드 메뉴의 **활성 인시던트** 배지에 집계되고(`isResolvedState` 플래그가 없는 모든 상태가 활성으로 계산됩니다), 인시던트의 모니터 중 하나를 담고 있는 상태 페이지에 나타나며, **상태 타임라인**이 기록을 시작합니다.
