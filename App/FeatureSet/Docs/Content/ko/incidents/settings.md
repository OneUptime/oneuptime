# 설정 및 자동화

인시던트 설정은 프로젝트 설정에 있지 않습니다. Incidents 제품 영역 안에, **인시던트 → 설정**과 **인시던트 → 규칙** 아래에 있고, 경로는 `/dashboard/{projectId}/incidents/settings/`로 시작합니다. 인시던트 템플릿이나 사용자 정의 필드를 찾겠다고 **프로젝트 설정**을 뒤지고 계셨다면, 못 찾은 이유가 바로 이것입니다.

인시던트 사이드 메뉴의 **규칙** 섹션과 **설정** 섹션은 둘 다 기본적으로 접혀 있어서, 아래 항목들을 보려면 먼저 펼쳐야 합니다. 여기 있는 모든 것은 프로젝트 범위입니다 — 템플릿, 역할, 사용자 정의 필드, 규칙은 하나의 프로젝트에 속하고 그 프로젝트에서 선언되는 모든 인시던트에 적용됩니다.

이 페이지는 그 설정에 대한 레퍼런스입니다 — 각 페이지가 무엇을 담고 있는지, 그리고 그중 어떤 것이 인시던트가 생성되는 순간 자동으로 실행되는지를 다룹니다.

## 인시던트 설정이 있는 곳

왼쪽 내비게이션에서 **인시던트**를 연 다음, 사이드 메뉴 맨 아래의 **설정**을 펼치세요.

| 페이지                     | 거기서 하는 일                                                                                    |
| ------------------------ | -------------------------------------------------------------------------------------------- |
| **인시던트 상태**       | 인시던트가 거쳐 가는 상태를 추가하고, 이름과 색상을 바꾸고, 순서를 정합니다.                       |
| **인시던트 심각도**    | 심각도 수준을 추가하고, 이름과 색상을 바꾸고, 순서를 정합니다.                                            |
| **인시던트 템플릿**   | 인시던트 전체를 미리 채웁니다 — 제목, 설명, 리소스, 온콜 정책, 소유자, 레이블까지. |
| **노트 템플릿**       | 공개 노트와 비공개 노트에 재사용할 텍스트입니다.                                                                  |
| **포스트모템 템플릿** | 재사용 가능한 포스트모템 구조입니다.                                                                         |
| **사용자 정의 필드**        | 모든 인시던트에 나타나는 추가 필드를 정의합니다.                                                           |
| **인시던트 역할**       | Incident Commander처럼 대응자에게 배정할 역할을 정의합니다.                       |
| **기타 설정**        | 인시던트 번호와 인시던트 에피소드 번호의 접두사입니다.                                           |

**인시던트 상태**와 **인시던트 심각도**는 [인시던트 상태 및 심각도](/docs/incidents/states-and-severities)에서 깊이 다룹니다 — 이 페이지의 나머지는 **인시던트 템플릿**부터 이어집니다.

**규칙**을 펼치면 여덟 개의 페이지가 더 나옵니다. **그룹화 규칙**, **온콜 규칙**, **소유자 규칙**, **Runbook 규칙**, **개인정보 보호 규칙**, **레이블 규칙**, **SLA 규칙**, **Reminder Rules**입니다. 이들은 아래에서 다룹니다.

## 인시던트 템플릿

인시던트 템플릿은 저장해 둔 인시던트의 뼈대입니다. 결제 클러스터가 흔들릴 때마다 같은 제목, 같은 모니터 목록, 같은 온콜 정책을 다시 입력하는 대신, 한 번 저장해 두고 거기서부터 선언하면 됩니다.

**인시던트 → 설정 → 인시던트 템플릿**(`/dashboard/{projectId}/incidents/settings/templates`)으로 이동하세요. 카드 제목은 **인시던트 템플릿**입니다. 하나를 만들면 여섯 단계 마법사를 거치게 됩니다.

- **템플릿 정보** — **템플릿 이름**과 **템플릿 설명**. 이것은 템플릿 자체의 이름이며, 인시던트에는 절대 나타나지 않습니다.
- **인시던트 세부 정보** — **제목**, **설명**(마크다운), **인시던트 심각도**, **초기 인시던트 상태**. **초기 인시던트 상태**는 선택 항목이고 비어 있는 상태로 시작하며, 선택지는 상태 순서대로 나열됩니다. 비워 두면 이 템플릿으로 만든 인시던트는 프로젝트의 생성 상태로 들어갑니다.
- **영향받는 리소스** — 인시던트에 연결할 모니터, 호스트, 클러스터, 서비스, 그리고 **Change Monitor Status to**.
- **온콜** — **온콜 정책**, 즉 이 템플릿으로 만든 인시던트가 선언될 때 실행할 정책입니다.
- **소유자** — **소유자 - 팀**과 **소유자 - 사용자**.
- **레이블** — **레이블**.

간단한 규칙 몇 가지가 있습니다.

- 템플릿 목록에는 **이름**과 **설명**만 표시됩니다. 목록에서 행을 편집하거나 삭제할 수는 없습니다 — 템플릿을 열어서(`/dashboard/{projectId}/incidents/settings/templates/{modelId}`) 변경하세요.
- 템플릿은 JSON 가져오기와 내보내기를 지원하므로 프로젝트 사이로 옮길 수 있습니다.
- 비어 있을 때는 "No incident templates found."라고 표시됩니다.

### 템플릿이 적용되는 방식

경로는 두 가지이고, 동작 방식은 같습니다.

- **대시보드에서** — 인시던트 목록의 **템플릿에서 생성** 버튼이 **인시던트 템플릿 선택** 선택창을 열고, 선언 페이지는 `incidentTemplateId` 쿼리 문자열 매개변수에서 템플릿을 읽어 템플릿과 그 소유자 팀·소유자 사용자로 양식을 미리 채웁니다.
- **API에서** — `POST /api/incident`에 `createdIncidentTemplateId`를 전달하면 서버가 템플릿으로 인시던트를 채웁니다.

중요한 것은 병합 규칙입니다. **템플릿은 여러분이 정의하지 않은 필드만 채웁니다.** 제목, 설명, 인시던트 심각도, 초기 인시던트 상태, **Change Monitor Status to** 뒤의 모니터 상태, 모니터, 호스트, Kubernetes 클러스터, Docker 호스트, Podman 호스트, 서비스, 온콜 정책, 레이블은 호출자나 양식이 아무것도 제공하지 않았을 때만 템플릿에서 복사됩니다. 명시적으로 지정한 값은 언제나 우선합니다.

**빈 상태 대화상자는 엉뚱한 곳을 가리킵니다.** 아직 템플릿이 하나도 없으면 **템플릿에서 생성** 버튼은 **No Incident Templates** 대화상자를 보여 줍니다. 그 안내문은 프로젝트 설정을 가리키지만, 버튼은 **인시던트 → 설정 → 인시던트 템플릿**으로 이동합니다 — 그쪽이 진짜 위치입니다.

## 노트 템플릿

노트 템플릿은 대응자에게 인시던트 업데이트용 상용구 텍스트를 제공합니다. 새벽 3시에 반쯤 잠든 사람이 상태 페이지 업데이트를 맨손으로 쓰지 않아도 되도록 말이죠.

**인시던트 → 설정 → 노트 템플릿**(`/dashboard/{projectId}/incidents/settings/note-templates`)으로 이동하세요. 카드 제목은 **인시던트용 공개 또는 비공개 메모 템플릿**입니다 — 하나의 라이브러리가 두 노트 유형을 모두 담당합니다. 생성 양식은 두 단계입니다.

- **템플릿 정보** — **템플릿 이름**과 **템플릿 설명**, 둘 다 필수입니다.
- **메모 세부정보** — 노트 본문 자체로, 마크다운이며 필수입니다.

인시던트 템플릿과 마찬가지로 행은 인라인 편집이 아니라 생성하고 열어 보는 방식입니다. 변경하려면 템플릿을 여세요.

노트 템플릿은 실제로 필요한 자리에서 나타납니다. **Acknowledge Incident**와 **Resolve Incident** 확인 대화상자 모두 **공개 메모** 필드 옆에 **메모 템플릿 선택**을 제공합니다. 공개 노트와 비공개 노트의 차이는 [인시던트 메모, 소유자 및 피드](/docs/incidents/notes-owners-and-feed)를 보세요.

## 포스트모템 템플릿

포스트모템 템플릿은 인시던트가 끝난 뒤 작성하는 기록물의 뼈대입니다 — 여러분의 제목 구성, 여러분의 질문 항목, 늘 묻는 것들 말이죠. 덕분에 프로젝트의 모든 리뷰가 같은 형태를 따르게 됩니다.

**인시던트 → 설정 → 포스트모템 템플릿**(`/dashboard/{projectId}/incidents/settings/postmortem-templates`)으로 이동하세요. 카드 제목은 **포스트모템 템플릿**입니다. 생성 양식은 두 단계입니다.

- **템플릿 정보** — **템플릿 이름**과 **템플릿 설명**, 둘 다 필수입니다.
- **사후 분석 세부 정보** — **사후 분석 템플릿**, 즉 본문 자체이며 마크다운이고 필수입니다.

적용은 설정이 아니라 인시던트에서 합니다. 인시던트를 열고 사이드 메뉴에서 **포스트모템**(`/dashboard/{projectId}/incidents/{incidentId}/postmortem`)을 고른 다음 **템플릿 적용**을 사용하세요. 그러면 **사후 분석 템플릿 적용** 대화상자가 열리고 **템플릿 선택** 드롭다운이 나옵니다. 하나를 고르면 템플릿 본문이 **사후 분석 메모** 편집기에 불러와지고, 저장하기 전에 여기서 손보면 됩니다. 인시던트 에피소드에도 같은 **포스트모템** 페이지가 있고 같은 템플릿 라이브러리를 씁니다.

## 사용자 정의 필드

사용자 정의 필드를 쓰면 모든 인시던트에 여러분만의 메타데이터를 실을 수 있습니다 — 내부 서비스 이름, 변경 티켓 번호, 고객 등급 같은 것들이죠.

**인시던트 → 설정 → 사용자 정의 필드**(`/dashboard/{projectId}/incidents/settings/custom-fields`)로 이동하세요. 페이지 제목은 **인시던트 사용자 정의 필드**입니다. 각 정의는 다음을 갖습니다.

- **필드 이름** — 필수이며 최소 두 글자입니다. 플레이스홀더는 `internal-service` 같은 슬러그 형태의 이름을 제안합니다.
- **필드 설명** — 선택 항목입니다.
- **필드 유형** — 필수입니다. 데이터를 어떻게 입력할지 결정합니다. 드롭다운 유형은 선택지 목록도 함께 필요합니다.
- **드롭다운 옵션** — 드롭다운에 나타나는 값들이며, 각각 선택적으로 색상을 지정할 수 있습니다.

정의는 자체 모델에 저장되고, 값은 인시던트 자체의 `customFields` 열에 저장됩니다. 개별 인시던트에서는 인시던트 사이드 메뉴의 **사용자 정의 필드**(`/dashboard/{projectId}/incidents/{incidentId}/custom-fields`)에서 값을 채웁니다.

**알아 둘 만한 빈틈이 하나 있습니다.** 인시던트 사용자 정의 필드 정의는 인시던트 계열에서 유일하게 워크플로우 트리거가 없는 부분입니다 — 아래 워크플로우 섹션을 보세요.

## 인시던트 역할

인시던트 역할은 대응 중에 사람에게 배정하는 이름 붙은 직무입니다. **인시던트 → 설정 → 인시던트 역할**(`/dashboard/{projectId}/incidents/settings/roles`)에서 정의하세요. 카드 설명은 Incident Commander와 Responder를 예로 듭니다.

역할은 정의일 뿐입니다. 사람 배정은 인시던트마다 합니다 — 선언 마법사에 **인시던트 역할** 단계와 **인시던트 역할 할당** 필드가 있고, 각 인시던트의 사이드 메뉴에는 **역할** 페이지가 있습니다.

## 번호 접두사

모든 인시던트에는 번호가 붙습니다. 기본적으로 `#42`처럼 표시됩니다. 팀에서 입으로 "INC-42"라고 부른다면, 제품도 그렇게 말하게 만드세요.

**인시던트 → 설정 → 기타 설정**(`/dashboard/{projectId}/incidents/settings/more`)으로 이동하세요. 카드는 **숫자 접두사**이고 프로젝트에 저장되는 필드 두 개를 담고 있습니다.

- **인시던트 번호 접두사** — 최대 20자, 플레이스홀더 `INC-`. 설정하면 인시던트 `#42`가 `INC-42`로 표시됩니다.
- **인시던트 에피소드 번호 접두사** — 인시던트 에피소드 번호에 대한 같은 개념이며, 플레이스홀더는 `IE-`입니다.

둘 중 하나를 비워 두면 기본 `#` 접두사가 유지되고, 설정하지 않은 필드는 `# (default)`로 표시됩니다. **업데이트**로 저장하세요. 접두사가 붙은 값은 인시던트에 `incidentNumberWithPrefix`로 저장되며, 인시던트 목록과 인시던트 헤더가 렌더링하는 것이 바로 이 값입니다.

## 인시던트가 생성될 때 실행되는 규칙

**인시던트 → 규칙**에는 여덟 개의 규칙 엔진이 있습니다. 하는 일은 모두 같습니다 — 인시던트가 생성되는 순간 그것을 살펴보고, 조건에 맞으면 동작합니다 — 하지만 무엇을 하는지, 그리고 여러 규칙이 동시에 일치할 때 어떻게 정리되는지는 서로 다릅니다.

- **그룹화 규칙** — 관련된 인시던트를 에피소드로 묶습니다. 규칙은 우선순위 순으로 평가되며, 우선순위 숫자가 작은 쪽이 먼저입니다.
- **온콜 규칙** — 일치하는 인시던트에 대해 온콜 당직 정책을 실행합니다. 아래에서 자세히 다룹니다.
- **소유자 규칙** — 소유자를 자동으로 배정합니다.
- **Runbook 규칙** — 인시던트가 일치하면 [runbook](/docs/runbooks/index)을 시작합니다.
- **개인정보 보호 규칙** — 일치하는 인시던트를 비공개로 할지 결정합니다.
- **레이블 규칙** — 레이블을 자동으로 붙입니다.
- **SLA 규칙** — 응답 시간과 해결 시간을 추적합니다. 규칙은 순서대로 평가되며, 순서 숫자가 작은 쪽이 먼저입니다.
- **Reminder Rules** — 인시던트가 아직 열려 있는 동안 인시던트 소유자에게 주기적으로 알립니다. 규칙은 순서대로 평가되고 처음 일치하는 규칙이 이깁니다.

**순서 의미가 전부 같지는 않습니다.** 그룹화 규칙, SLA 규칙, Reminder Rules는 순서대로 평가됩니다. 온콜 규칙은 그렇지 않습니다 — 일치하는 모든 규칙이 실행됩니다. 하나의 모델이 여덟 개 전부에 적용된다고 가정하지 마세요.

**온콜 규칙**, **소유자 규칙**, **레이블 규칙**, **개인정보 보호 규칙** 페이지에는 탭이 있습니다 — **Incident Rules** 탭과 **Episode Rules** 탭이며 각각 자체 테이블을 갖습니다. 특별히 에피소드를 뜻하는 경우가 아니라면 **Incident Rules** 탭을 설정하세요. **그룹화 규칙**, **Runbook 규칙**, **SLA 규칙**, **Reminder Rules**는 단일 테이블입니다.

## 인시던트 온콜 규칙

**인시던트 → 규칙 → 온콜 규칙**(`/dashboard/{projectId}/incidents/settings/on-call-rules`)은 호출을 자동화하는 곳입니다. **인시던트 온콜 규칙** 카드는 일치하는 인시던트가 생성될 때 온콜 당직 정책을 자동으로 실행하는 규칙을 설명합니다. 이 페이지에는 **Incident Rules**와 **Episode Rules** 두 개의 탭이 있습니다.

생성 양식은 세 단계입니다.

- **기본 정보** — **이름**(플레이스홀더는 모든 DB 인시던트에 대해 데이터베이스 팀을 호출하는 것 같은 예를 제안합니다), **설명**, 그리고 **활성화됨** 토글. 목록은 규칙마다 초록색 **활성화됨** 또는 빨간색 **비활성화** 알약을 렌더링합니다.
- **일치 기준** — **모니터**, **인시던트 심각도**, **인시던트 레이블**, **모니터 레이블**, 그리고 인시던트 제목, 인시던트 설명, 모니터 이름, 모니터 설명에 대한 대소문자 구분 없는 정규 표현식 필드들.
- **온콜 정책** — 이 규칙이 실행할 정책들.

### 일치가 판정되는 방식

이 페이지에 함께 실려 있는 규칙 자체를 머리에 넣어 두면 좋습니다.

- 규칙은 여러분이 채운 기준이 **전부** 통과할 때만 일치합니다. 비워 둔 기준은 실패가 아니라 건너뜁니다.
- 하나의 목록형 기준 안에서는 — **모니터**, **인시던트 심각도**, **인시던트 레이블**, **모니터 레이블** — 하나라도 맞으면 일치입니다.
- 패턴 필드는 대소문자를 구분하지 않는 정규 표현식입니다.
- **일치하는 모든 규칙이 실행됩니다.** 우선순위도 없고 조기 종료도 없습니다.
- 실제로 실행되는 정책 집합은 일치한 모든 규칙의 정책에 수동으로 또는 템플릿으로 인시던트에 붙은 정책을 더한 합집합이며, 중복이 제거되어 각 정책은 최대 한 번만 실행됩니다.

심각도가 일치 기준이 되는 곳은 여기뿐입니다. 인시던트 심각도에는 온콜 필드가 없습니다 — "심각한 인시던트"를 고른다고 해서 그 자체로 누군가가 호출되지는 않습니다. 심각도로 호출을 몰고 가고 싶다면, 심각도를 기준으로 일치하는 온콜 규칙을 작성하세요.

## 온콜 정책을 직접 붙이기

규칙만이 유일한 경로는 아닙니다. 모든 인시던트는 자체 온콜 정책 목록을 갖고 있고, 이는 선언 마법사의 **온콜** 단계와 인시던트 템플릿의 **온콜** 단계에 있는 **온콜 정책** 필드로 드러납니다. 필드 설명이 그대로 말해 줍니다. 이 인시던트가 생성될 때 실행할 온콜 당직 정책이라고요.

인시던트가 생성되면 OneUptime은 레이블 규칙을 실행하고, 그다음 온콜 규칙을 실행하며(일치한 정책을 인시던트 목록에 병합합니다), 그다음 Runbook 규칙을 실행합니다 — 그리고 그렇게 만들어진 목록이 비어 있지 않으면 그 안의 모든 정책이 실행됩니다. 실행은 병렬로 이루어지고 각각 독립적으로 정리되므로, 정책 하나가 실패해도 나머지가 멈추지 않습니다. 각 실행에는 이를 촉발한 인시던트와 인시던트 생성 알림 이벤트 유형이 태그로 붙습니다.

무슨 일이 일어났는지 보려면 인시던트를 열고 사이드 메뉴에서 **온콜 실행**(`/dashboard/{projectId}/incidents/{incidentId}/on-call-policy-execution-logs`)을 고르세요.

## 워크플로우로 인시던트 다루기

인시던트용 워크플로우 트리거는 손으로 작성한 것이 아닙니다 — OneUptime이 데이터 모델에서 생성하기 때문에, 인시던트 계열의 모든 모델은 모델의 단수 이름을 따서 지은 **On Create X**, **On Update X**, **On Delete X** 구성 요소를 갖습니다. 대표적인 셋은 **On Create Incident**, **On Update Incident**, **On Delete Incident**이며, `/dashboard/{projectId}/workflows`의 **구성 요소 추가** 패널에서 **인시던트** 범주 아래에 있습니다.

같은 생성 방식 덕분에 설정 자체에 대한 트리거도 생깁니다. **On Create Incident State**, **On Update Incident Severity**, **On Create Incident Template**, **On Create Incident Note Template**, **On Create Incident State Timeline**, **On Create Incident Public Note**, **On Create Incident Internal Note**, **On Create Incident On-Call Rule**, **On Create Incident Role**, **On Create Incident Member** 등이 있습니다. 각 모델은 짝이 되는 액션 구성 요소도 갖습니다 — **Find One Incident**, **Create One Incident**, **Update One Incident**, **Delete One Incident**과 여러 행을 다루는 그 대응물들 — 그래서 이름이 비슷한 트리거와 액션이 같은 범주 안에 나란히 놓입니다. **On Create Incident**는 워크플로우를 시작하고, **Create One Incident**는 인시던트를 만듭니다.

이것들을 연결할 때 중요한 세부 사항 몇 가지가 있습니다.

- **On Update X**는 선택적인 **Listen on** 인수를 받아, 특정 필드를 건드리는 업데이트로만 트리거를 좁힙니다. 비워 두면 어떤 변경에도 실행됩니다. 어떤 필드가 바뀌었는지에 대한 기록 없이 업데이트가 도착하면 필터는 건너뛰고 워크플로우는 그대로 실행됩니다.
- **On Create X**와 **On Update X**는 둘 다 필수 인수인 **Select Fields**를 받고, **On Delete X**는 인수를 받지 않습니다.
- 세 가지 모두 **성공** 아웃포트 하나를 노출하며, 각각 ID 인수를 받으므로 특정 레코드에 대해 워크플로우를 수동으로 실행할 수 있습니다.
- 이름은 테이블 이름이 아니라 모델의 단수 이름에서 옵니다 — 그래서 테이블 형태의 이름 대신 **On Create Incident Team Owner**와 **On Create Incident User Owner**가 보이는 것입니다.
- 인시던트 사용자 정의 필드 정의에는 트리거가 없습니다. 그 모델은 인시던트 계열에서 워크플로우가 비활성화된 유일한 구성원입니다.

워크플로우의 나머지를 만드는 방법은 [워크플로우 작성](/docs/workflows/authoring)과 [워크플로우 변수](/docs/workflows/variables)를 보세요.
