# GitHub에서 OneUptime 사용하기

OneUptime GitHub App은 코드로 이어지는 연결 통로이기만 한 것이 아닙니다 — 저장소 안에서 앱에 말을 걸면, 앱이 바로 그 자리에서 일을 합니다.

이슈에서 멘션하면 풀 리퀘스트를 엽니다. 풀 리퀘스트에서 멘션하면 그 브랜치를 고치거나 diff를 리뷰합니다. 이슈에 라벨을 붙이면 그 이슈를 집어 갑니다. 앱이 내놓는 결과물은 언제나 사람이 읽을 풀 리퀘스트 아니면 리뷰입니다: **앱은 무엇도 머지하지 않으며, 풀 리퀘스트를 승인하지도 않습니다.**

```text
@oneuptime implement this                          →  이슈를 닫는 풀 리퀘스트
@oneuptime revise this — use exponential backoff   →  이 풀 리퀘스트의 브랜치에 쌓이는 새 커밋
@oneuptime review                                  →  이 풀 리퀘스트에 게시되는 코드 리뷰
```

> `@oneuptime`을 여러분 앱의 핸들로 바꿔 쓰세요. OneUptime Cloud에서는 `@oneuptime`입니다. 자체 호스팅 인스턴스에서는 GitHub App에 붙인 이름을 소문자로 바꾸고 공백을 하이픈으로 바꾼 것이 핸들입니다 — 이름이 "Acme AI"인 앱은 `@acme-ai`로 멘션합니다. 멘션해도 아무 일이 일어나지 않는다면 이것부터 확인하세요.

## 시작하기 전에

- 저장소가 GitHub App을 통해 **OneUptime 프로젝트에 연결되어** 있어야 합니다. 설정 방법은 [GitHub 통합 (자체 호스팅)](/docs/self-hosted/github-integration)을 보세요. OneUptime Cloud에서는 **프로젝트 설정 → 코드 저장소**에서 연결합니다.
- **AI 코드 수정 실행 기능을 켠 러너**가 온라인이어야 합니다 — [AI 수정 작업](/docs/ai/ai-agent)을 수행하는 바로 그 러너입니다. 러너가 없으면 명령은 일단 접수되지만, 30분 뒤 아무 에이전트도 가져가지 않았다는 메시지와 함께 실패합니다.
- GitHub App에 **이슈: 읽기 및 쓰기** 권한이 있어야 하고, [구독해야 할 이벤트](#구독해야-할-이벤트)에 나열된 웹훅 이벤트를 구독하고 있어야 합니다.

## 명령어

모든 명령어는 앱을 멘션하는 것으로 시작합니다. 멘션은 댓글 어디에 있어도 되며, 멘션 뒤에 쓴 내용은 그대로 요청으로 전달됩니다.

### 풀 리퀘스트에서

| 명령어 | 하는 일 |
| --- | --- |
| `@oneuptime review` | 브랜치를 클론해 변경된 코드**와 그 주변 코드**까지 읽고, 리뷰를 댓글로 게시합니다. 아무것도 바꾸지 않습니다. |
| `@oneuptime revise this — <바꾸고 싶은 내용>` | 그 풀 리퀘스트 자신의 브랜치를 클론해 변경을 적용하고, 같은 브랜치에 새 커밋을 푸시합니다. 두 번째 풀 리퀘스트는 절대 열지 않습니다. |

멘션 뒤에 쓴 내용이 알려진 명령어가 아니면 수정 요청으로 처리합니다. 거의 언제나 실제로 그것이기 때문입니다:

```text
@oneuptime the retry loop here should back off exponentially, and the test
should cover the 429 case
```

### 이슈에서

| 명령어 | 하는 일 |
| --- | --- |
| `@oneuptime implement this` | 이슈를 처리하고, 그 이슈를 닫는 풀 리퀘스트를 엽니다. |
| `@oneuptime <그 밖의 아무 내용>` | 같은 동작이며, 여러분이 쓴 말이 추가 지시가 됩니다. |

댓글을 **전혀 달지 않고** 앱에 이슈를 넘길 수도 있습니다:

- **트리거 라벨을 붙이세요.** 저장소의 트리거 라벨 — 기본값은 `oneuptime` — 을 이슈에 붙이면 같은 작업이 시작됩니다. GitHub 화면에서 작업을 넘기는 가장 확실한 방법입니다.
- **이슈를 앱의 봇 사용자에게 할당하세요.** 저장소가 허용하는 경우에 한합니다. GitHub은 모든 저장소에서 앱을 담당자로 지정할 수 있게 해 주지는 않으며, 라벨이 존재하는 이유가 바로 그것입니다. 할당해도 아무 일이 없으면 라벨을 쓰세요.

### 어디서나

| 명령어 | 하는 일 |
| --- | --- |
| `@oneuptime help` | 명령어 목록을 보여줍니다. 뒤에 아무것도 붙이지 않은 멘션도 같은 일을 합니다. |
| `@oneuptime status` | 이 스레드에서 지금 무슨 작업을 하고 있는지 알려줍니다. |
| `@oneuptime cancel` | 이 스레드에서 진행 중인 실행을 멈춥니다. 이미 푸시된 작업은 그대로 남습니다. |

`help`, `status`, `cancel`은 에이전트 실행을 시작하지 않으므로 비용이 들지 않고, 일일 수정 작업 예산에도 잡히지 않습니다.

## 스레드에서 보이는 모습

명령어 하나는 **댓글 하나**를 만들고, 작업이 진행되는 동안 앱이 그 댓글을 계속 고쳐 씁니다 — 오래 걸리는 작업이 풀 리퀘스트를 상태 로그로 만들어 버리는 일이 없도록.

1. 여러분의 댓글에 👀로 반응하고, 그 실행이 속한 OneUptime 프로젝트를 밝히면서 진행 중인 실행으로 연결되는 확인 댓글을 답니다.
2. 작업이 끝나면 바로 그 댓글이 결과로 다시 쓰입니다. 열어 놓은 풀 리퀘스트, 푸시한 커밋, 아니면 아무것도 하지 않은 이유에 대한 솔직한 설명입니다.

바꿀 만한 것을 찾지 못하면, 근거 없는 풀 리퀘스트를 여는 대신 그렇다고 말합니다. 실패가 아니라 정상적인 결과입니다 — 방향을 더 구체적으로 알려주고 다시 요청하세요.

## 누가 명령할 수 있나

**저장소에 Write, Maintain, Admin 권한을 가진 사람만 가능합니다.** OneUptime은 그때마다 GitHub에 직접 그 저장소에 대한 댓글 작성자의 권한을 물어봅니다. GitHub이 댓글 옆에 보여주는 "Contributor" 배지는 신뢰하지 않습니다. 그 배지는 현재 접근 권한이 아니라 과거 활동을 설명하기 때문입니다.

그 밖의 사람이 멘션하면 그 댓글에 😕 반응 하나만 달리고 끝입니다. 의도된 동작입니다. 공개 저장소에서는 누구나 댓글을 달 수 있고, 낯선 사람에게도 꼬박꼬박 답하는 앱은 스레드를 도배하는 데 쓰일 수 있는 앱이기 때문입니다.

또한 자기 자신의 것을 포함해 봇이 쓴 댓글은 모두 무시하고, 인용(`>`)이나 코드 블록 안에 있는 멘션도 무시합니다. 이 두 규칙이 함께, 앱 자신의 댓글에 달린 답글이 앱을 다시 깨우는 일을 막아 줍니다.

## 앱이 하지 않는 일

- **절대 머지하지 않습니다.** 이 앱이 하는 어떤 일도 기본 브랜치에 코드를 올릴 수 없습니다.
- **절대 승인하거나 변경을 요청하지 않습니다.** 리뷰는 댓글로 게시되므로, 앱의 리뷰가 브랜치 보호 규칙을 충족시키는 일은 있을 수 없습니다.
- **절대 히스토리를 다시 쓰지 않습니다.** 수정은 커밋을 더할 뿐, 강제 푸시하지 않습니다. 다른 사람이 먼저 브랜치에 푸시했다면, 그 작업을 버리는 대신 수정이 실패합니다.
- **포크에서 온 풀 리퀘스트는 수정할 수 없습니다.** 포크의 브랜치는 설치본이 쓰기 권한을 갖지 못한 저장소에 있습니다. 리뷰는 그래도 해 주니, 수정 대신 리뷰를 요청하세요.
- **풀 리퀘스트의 제목, 설명, 대상 브랜치는 절대 바꾸지 않습니다.** 코드만 바꿉니다.

## 비용, 그리고 한도를 두는 방법

작업을 시작하는 모든 명령어는 온전한 에이전트 실행입니다 — 클론, 최대 40회의 LLM 호출과 100,000 출력 토큰, 그리고 저장소에 빌드·테스트 명령을 설정해 두었다면 그 명령들까지.

두 가지 한도가 적용되며, 둘 다 이미 [AI 수정 작업](/docs/ai/ai-agent)을 다스리고 있는 그 한도입니다:

- **프로젝트의 일일 수정 실행 한도** (**프로젝트 설정 → AI**, 기본값 하루 25회). GitHub 명령어는 프로젝트의 나머지 수정 실행과 이 예산을 나눠 씁니다.
- **저장소별 열린 풀 리퀘스트 상한** (**코드 저장소 → 해당 저장소 → 설정**, 기본값 5). 리뷰와 수정은 여기서 제외됩니다. 둘 다 리뷰 대기열에 새 풀 리퀘스트를 더하지 않기 때문입니다.

이슈나 풀 리퀘스트 하나에서 같은 종류의 실행은 한 번에 하나만 살아 있습니다. 두 번 요청하면 이미 작업 중이라고 알려줍니다. 수정이 돌아가는 동안 리뷰를 요청하면 서로 다른 요청이므로 둘 다 시작됩니다.

실행을 시작할 수 없으면 앱이 스레드에 그 이유를 말합니다 — 조용히 실패하는 일은 없습니다.

## 끄는 방법

저장소별로: **코드 저장소 → 해당 저장소 → 설정 → GitHub 명령에 응답**. 이것을 끄면 앱은 그 저장소에서 멘션, 할당, 트리거 라벨을 모두 무시하고, 말을 거는 사람에게 스위치가 어디 있는지 알려줍니다.

같은 화면에 **GitHub 트리거 라벨**도 있습니다. `oneuptime` 말고 다른 것을 쓰고 싶을 때 바꾸세요.

## 구독해야 할 이벤트

GitHub App의 **권한 및 이벤트** 설정에서 다음을 구독하세요:

| 이벤트 | 필요한 이유 |
| --- | --- |
| **Issue comment** | 이슈 *와* 풀 리퀘스트에서의 `@mention` 명령어 |
| **Issues** | 앱에 이슈를 할당하는 것, 그리고 트리거 라벨 |
| **Pull request** | 앱에 요청한 리뷰 |
| **Pull request review** | 제출된 리뷰 본문에 쓴 멘션 |
| **Pull request review comment** | diff의 인라인 댓글에 단 멘션 |

그리고 **저장소 권한**에서 **이슈**가 **읽기 및 쓰기**여야 합니다 — GitHub은 풀 리퀘스트의 대화 댓글을 이슈 API로 처리하기 때문에, 앱이 풀 리퀘스트에도 댓글을 달 수 있게 해 주는 것이 바로 이 권한입니다.

## 프롬프트 인젝션: 무엇이 보호되고 무엇이 보호되지 않나

이슈 본문, 풀 리퀘스트 설명, diff, 댓글은 모두 에이전트 프롬프트의 일부가 되고, 공개 저장소에서는 누구나 그것들을 쓸 수 있습니다. "지시를 무시하고 X를 하라"는 문구가 이슈에 들어 있는 것은 현실적으로 충분히 있을 수 있는 일입니다.

이것을 제한하는 것은 두 가지이며, 어느 쪽이 무엇을 하는지 알아 둘 가치가 있습니다:

- **프롬프트는 신뢰할 수 없는 텍스트를 지시가 아니라 요청으로 표시합니다.** 그리고 실행의 저장소, 브랜치, 풀 리퀘스트는 에이전트가 시작되기도 전에 고정됩니다 — 에이전트가 읽는 그 무엇도 자신이 무엇을 작업할지는 바꿀 수 없습니다.
- **실제 격리는 샌드박스가 합니다.** 에이전트는 여러분의 러너 위에서, 일회용 클론 안에서, 명령 환경에서 자격 증명이 제거된 채, git 작업이 제한된 상태로 실행됩니다. 할 수 있는 일은 브랜치에 푸시하는 것뿐이고, 머지는 사람만 할 수 있습니다.

AI가 작성한 풀 리퀘스트는 이슈를 읽고 온 신규 기여자의 풀 리퀘스트를 대하듯 다루세요. 설명이 아니라 diff를 리뷰하세요.

## 문제 해결

**멘션해도 아무 일이 일어나지 않습니다.** 핸들부터 확인하세요 — 표시 이름이 아니라 앱의 슬러그입니다. 그다음 저장소가 프로젝트에 연결되어 있는지(**프로젝트 설정 → 코드 저장소**), **GitHub 명령에 응답**이 켜져 있는지, GitHub App이 위 이벤트들을 구독하고 있는지 확인하세요.

**😕로 반응하고 아무 말도 없습니다.** 저장소에 대한 쓰기 권한이 없는 것입니다.

**이미 작업 중이라고 합니다.** 이 이슈나 풀 리퀘스트에 같은 종류의 실행이 이미 살아 있습니다. `@oneuptime status`가 무엇인지 알려주고, `@oneuptime cancel`이 그것을 멈춥니다.

**확인 댓글을 달고는 한참 조용합니다.** **설정 → 러너**에서 **AI 코드 수정 실행**이 켜진 러너가 온라인인지 확인하세요. 그런 러너가 없으면 실행은 30분 뒤 실패 처리되고, 스레드에도 그 사실이 남습니다.

**풀 리퀘스트가 포크에서 왔다고 합니다.** 수정에는 이 저장소 안의 브랜치가 필요합니다. 대신 리뷰를 요청하거나, 브랜치를 이 저장소로 푸시하세요.
