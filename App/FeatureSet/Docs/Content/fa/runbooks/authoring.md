# نوشتن یک رانبوک

یک رانبوک را زیر **Runbooks → Create Runbook** بسازید، سپس بازش کنید و به زبانه **Steps** بروید.

## کالبدشکافی یک گام

هر گام این‌ها را دارد:

| فیلد | کاربرد |
| ------------------------ | ------------------------------------------------------------------------------------------------------- |
| **Title** | برچسب کوتاهی که در رابط کاربری چک‌لیست نمایش داده می‌شود. الزامی است. |
| **Description** | زمینه اختیاری برای پاسخ‌دهنده. متن سازگار با Markdown. |
| **Continue on failure** | اگر روشن باشد، شکست یک گام اجرا را متوقف نمی‌کند — گام بعدی همچنان اجرا می‌شود. |
| **Require approval** | اگر روشن باشد، رانبوک پس از این گام مکث می‌کند و منتظر می‌ماند تا کاربری پیش از اجرای گام بعدی تأیید کند. |
| **Type-specific config** | اسکریپت، نشانی، عامل و غیره — پایین‌تر را ببینید. |

گام‌ها **به‌ترتیب** اجرا می‌شوند. با پیکان‌های بالا/پایین در ویرایشگر Steps ترتیبشان را تغییر دهید.

## نوع‌های گام

### دستی

جعبه‌ای که پاسخ‌دهنده تیک می‌زند. اجرای رانبوک وقتی به یک گام Manual می‌رسد مکث می‌کند و در وضعیت `WaitingForManualStep` می‌ماند تا کسی آن را کامل (یا رد) کند.

از این برای چیزهایی استفاده کنید که فقط یک انسان می‌تواند تأییدشان کند: «تأیید شد که ترافیک در داشبورد متعادل‌کننده بار به ناحیه ثانویه منتقل شده است.»

### JavaScript

قطعه‌ای JavaScript که در یک `isolated-vm` ایزوله اجرا می‌شود. این محیط ایزوله روی یک [عامل رانبوک](/docs/runbooks/agents) در زیرساخت خودتان قرار دارد — نه روی Worker OneUptime.

این‌ها را روی یک گام JavaScript پیکربندی کنید:

- **Runbook Agent** — از فهرست کشویی، عاملی را که باید این گام را اجرا کند انتخاب کنید. فقط عامل انتخاب‌شده می‌تواند کار را بردارد.
- **Script** — JavaScriptای که اجرا می‌شود.
- **Execution timeout** — عامل چقدر اجازه می‌دهد قطعه اجرا شود پیش از آنکه ایزوله را برچیند. پیش‌فرض ۳۰ ثانیه.
- **Claim timeout** — Worker چقدر منتظر می‌ماند تا عامل کار را بردارد. پیش‌فرض ۲ دقیقه.

```js
const start = Date.now();
// ... your logic ...
return { durationMs: Date.now() - start };
```

مقدار بازگشتی روی اجرای گام ثبت می‌شود. خروجی `console.log` به‌عنوان خطوط گزارش ضبط می‌شود. مهلت اجرای پیش‌فرض: ۳۰ ثانیه. مهلت برداشت پیش‌فرض (اینکه Worker چقدر منتظر می‌ماند تا عامل کار را بردارد): ۲ دقیقه. هر دو روی گام قابل ویرایش‌اند — **Execution timeout** و **Claim timeout** زیر اسکریپت را ببینید.

### درخواست HTTP

یک فراخوان HTTP خروجی انجام دهید. متد (GET/POST/PUT/PATCH/DELETE/HEAD)، نشانی، هدرهای JSON اختیاری، بدنه اختیاری و یک **Request timeout** (پیش‌فرض ۳۰ ثانیه) را پیکربندی کنید. وضعیت، هدرها و بدنه پاسخ ضبط می‌شوند (سقف مجموع ۵۰ کیلوبایت).

مفید برای: راه‌اندازی یک حادثه PagerDuty، ارسال به Slack، فراخوانی API مدیریتی خودتان و غیره. گام‌های HTTP مستقیماً روی Worker OneUptime اجرا می‌شوند؛ به عامل نیازی نیست.

### Bash

اسکریپتی bash (`bash -c <script>`) که روی یک [عامل رانبوک](/docs/runbooks/agents) در زیرساخت خودتان اجرا می‌شود. Bash هرگز روی Worker OneUptime اجرا نمی‌شود.

این‌ها را روی یک گام Bash پیکربندی کنید:

- **Runbook Agent** — از فهرست کشویی، عاملی را که باید این گام را اجرا کند انتخاب کنید. فقط عامل انتخاب‌شده می‌تواند کار را بردارد.
- **Script** — bashای که اجرا می‌شود. خروجی (stdout + stderr) تا ۵۰ کیلوبایت ضبط می‌شود؛ فرایند در زمان اتمام مهلت کشته می‌شود.
- **Execution timeout** — عامل چقدر اجازه می‌دهد اسکریپت اجرا شود پیش از آنکه با `SIGKILL` بکشدش. پیش‌فرض ۳۰ ثانیه؛ برای گام‌هایی که به‌درستی دقیقه‌ها طول می‌کشند بالاترش ببرید.
- **Claim timeout** — Worker چقدر منتظر می‌ماند تا عامل کار را بردارد. پیش‌فرض ۲ دقیقه.

اگر عامل انتخاب‌شده هنگام رسیدن رانبوک به این گام آفلاین باشد، گام تا سقف **claim timeout** (پیش‌فرض ۲ دقیقه) منتظر می‌ماند و سپس با `TimedOut` شکست می‌خورد. پیش از تکیه بر یک گام Bash، زیر **Settings → Runners** عاملی اضافه کنید.

### SSH

فرمانی را روی میزبانی اجرا کنید که Runner می‌تواند از راه SSH به آن برسد. برخلاف نوشتن `ssh host cmd` درون یک گام Bash، دسترسی یک [اعتبارنامه](/docs/runbooks/credentials) مدیریت‌شده است نه کلیدی خصوصی روی دیسک Runner — رمزگذاری‌شده در حالت سکون، تخصیص‌یافته به Runnerهای مشخص، و هرگز از طریق API قابل بازخوانی نیست.

روی یک گام SSH پیکربندی کنید:

- **Runner** — Runnerای که اتصال را باز می‌کند. باید بتواند از نظر شبکه به میزبان برسد.
- **Credential** — اعتبارنامه‌ای SSH که میزبان، درگاه، کاربر و کلید را نگه می‌دارد. باید به Runnerای که انتخاب کرده‌اید تخصیص یافته باشد، وگرنه گام به‌جای اجرا با دسترسی اشتباه شکست می‌خورد.
- **Command** — روی میزبان راه دور با کاربر اعتبارنامه اجرا می‌شود. خروجی تا ۵۰ کیلوبایت ضبط می‌شود و کد خروج غیرصفر گام را شکست‌خورده می‌کند.
- **Execution timeout** — اتصال، احراز هویت و اجرای فرمان را با هم پوشش می‌دهد، پس فرمانی که معلق بماند نمی‌تواند گام را بی‌پایان باز نگه دارد.

### Kubernetes

بار کاری‌ای را در یک خوشه بازراه‌اندازی یا مقیاس‌بندی کنید. عمداً مجموعه فعل‌ها بسته است: گامی که بتواند اشیای دلخواه را PATCH کند یک پوسته cluster-admin می‌شد، و هدف این نوع گام آن است که اصلاحات رایج را آن‌قدر امن کند که بتوان به اصلاح خودکار سپردشان.

روی یک گام Kubernetes پیکربندی کنید:

- **Runner** — Runnerای که کارساز API را فرا می‌خواند.
- **Credential** — اعتبارنامه‌ای Kubernetes که نشانی کارساز API، توکن یک حساب سرویس و CA خوشه را نگه می‌دارد. آن حساب سرویس را به نقشی مقید کنید که فقط چیزی را مجاز کند که رانبوک‌هایتان لازم دارند.
- **Action** — **Restart workload** الگوی پاد را مهر می‌زند تا کنترلر پادها را بازبسازد (همان کاری که `kubectl rollout restart` می‌کند)، یا **Scale workload** تعداد نسخه‌ها را تنظیم می‌کند.
- **Workload kind** — Deployment، StatefulSet یا DaemonSet.
- **Namespace** و **Workload name**.
- **Replicas** — فقط برای Scale. صفر مجاز است؛ تخلیه یک بار کاری اصلاحی مشروع است. DaemonSetها مقیاس‌پذیر نیستند — به ازای هر گره یک پاد اجرا می‌کنند — پس به‌جایش بازراه‌اندازیشان کنید.

اگر کارساز API تغییر را رد کند، پیام خودش روی گام نمایان می‌شود، پس یک شکست دسترسی به شما می‌گوید کدام role binding را باید گشاد کنید.

### AI

از هوش مصنوعی بخواهید در میانه اجرا چیزی را تحلیل، خلاصه یا درباره‌اش تصمیم‌گیری کند. اعلان به ارائه‌دهنده LLM پروژه شما (**Settings → AI → LLM Providers**) فرستاده می‌شود و پاسخ مدل به خروجی گام روی خط زمانی اجرا تبدیل می‌شود. گام‌های AI روی Worker OneUptime اجرا می‌شوند؛ به عاملی نیاز نیست.

روی یک گام AI پیکربندی کنید:

- **Prompt** — هوش مصنوعی چه کاری باید بکند. برای نمونه: «خروجی گام‌های قبلی را بررسی کن و بگو آیا ادامه دادن با اصلاح امن است یا نه.»
- **Include previous step context** — اگر روشن باشد، هوش مصنوعی همه‌چیز درباره گام‌هایی را که پیش از این اجرا شده‌اند می‌بیند: عنوان، نوع، وضعیت، خروجی و پیام‌های خطا.
- **Include trigger context** — اگر روشن باشد، هوش مصنوعی می‌بیند چه چیزی اجرا را شروع کرده است: حادثه، هشدار یا رویداد نگهداری زمان‌بندی‌شده پیوندخورده (توضیحاتش، شدت، وضعیت جاری، مانیتورهای متأثر، ریشه علت، خط زمانی وضعیت و یادداشت‌های عمومی)، یا اینکه چه کسی رانبوک را دستی اجرا کرده است.

یک گام AI را با **Require approval** جفت کنید تا انسانی در حلقه باشد: هوش مصنوعی تحلیل می‌کند، پاسخ‌دهنده جوابش را می‌خواند و تأیید می‌کند، و تنها آنگاه گام بعدی (اصلاح) اجرا می‌شود.

**آنچه هوش مصنوعی هرگز نمی‌بیند.** پاسخ یک گام AI به‌عنوان خروجی گام روی اجرا ذخیره می‌شود، و اجراها برای هر کسی با دسترسی خواندن رانبوک قابل خواندن‌اند — مخاطبی گسترده‌تر از ACL حادثه. پس زمینه تریگر عمداً **یادداشت‌های داخلی خصوصی** و **پیام‌های کانال Slack/Teams** را کنار می‌گذارد: آن‌ها درون حادثه می‌مانند، جایی که تولیدکننده‌های موجود پس‌مرگ و یادداشت، متن مشتق‌شده‌شان را نگه می‌دارند. خروجی گام‌های پیشین پیش از فرستاده شدن به مدل، از نظر اسرار (توکن‌ها، کلیدها، اعتبارنامه‌ها) پویش و پاک‌سازی می‌شود.

گام‌های AI مانند هر قابلیت هوش مصنوعی دیگری اندازه‌گیری و صورت‌حساب می‌شوند. اگر برای پروژه هیچ ارائه‌دهنده LLMای پیکربندی نشده باشد، گام با خطایی روشن شکست می‌خورد (اگر باقی رانبوک باید همچنان اجرا شود، **Continue on failure** را تنظیم کنید).

## ذخیره و ویرایش

برای ماندگار کردن، **Save Steps** را بزنید. اجراهای در جریانِ نسخه‌های قدیمی‌تر رانبوک متأثر نمی‌شوند — آن‌ها به استفاده از عکس فوری خودشان ادامه می‌دهند.

## چند گام و مدیریت شکست

به‌طور پیش‌فرض، شکست یک گام اجرا را متوقف می‌کند و اجرا را `Failed` علامت می‌زند. اگر روی گامی **Continue on failure** را تنظیم کنید، شکست ثبت می‌شود اما گام بعدی اجرا می‌شود. این برای الگوهای «این سه کار را امتحان کن، بعد خبر بده» مفید است.

## یک نمونه عملی

رانبوکی ساده برای «دسترسی‌ناپذیری پایگاه داده اصلی»:

1. **JavaScript** — میزبان اصلی جاری را از سرویس پیکربندی خود بگیرید و گزارش کنید.
2. **Manual** — «تأیید کنید تأخیر همانندسازی در ثانویه زیر ۵ ثانیه است.»
3. **HTTP request** — به API هماهنگ‌کننده failover خود POST کنید.
4. **Manual** — «تأیید کنید نوشتن‌ها اکنون به اصلی جدید می‌روند.»
5. **HTTP request** — پیام «همه‌چیز مرتب است» را به Slack POST کنید.

پاسخ‌دهنده اجرای یک گام خودکار را تماشا می‌کند، یکی دستی را تیک می‌زند، اجرای گام خودکار بعدی را تماشا می‌کند و همین‌طور ادامه می‌دهد. خروجی هر گام برای پس‌مرگ ضبط می‌شود.
