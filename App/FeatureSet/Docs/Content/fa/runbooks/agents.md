# عامل‌های رانبوک

**عامل رانبوک** فرایندی کوچک و خودمیزبان است که گام‌های Bash _و_ JavaScript رانبوک‌های شما را **درون زیرساخت خودتان** اجرا می‌کند. Worker در OneUptime هرگز اسکریپت‌های شما را اجرا نمی‌کند — آن‌ها را در صف می‌گذارد، و عامل رانبوکی که نویسنده گام برگزیده برشان می‌دارد، اجرایشان می‌کند و نتیجه را پس می‌فرستد.

‏JavaScript همچنان در محیط ایزوله `isolated-vm` اجرا می‌شود؛ تفاوت این است که محیط ایزوله به‌جای میزبان ما روی میزبان عامل شما زندگی می‌کند.

این صفحه توضیح می‌دهد چگونه عاملی نصب کنید، گام‌های Bash و JavaScript را به آن نشانه بگیرید، و روزبه‌روز اداره‌اش کنید.

## چرا عامل‌ها وجود دارند

نسخه‌های پیشین OneUptime گام‌های Bash و JavaScript را روی Worker اجرا می‌کردند. JavaScript ایزوله بود (از راه `isolated-vm`)، Bash نبود. هر دو برای هر چیزی فراتر از راه‌اندازی خودمیزبان تک‌مستأجری مشکل داشتند:

- **مرز اعتماد.** هر کسی که می‌توانست رانبوکی بنویسد می‌توانست کدی روی Worker اجرا کند، با دسترسی به هر متغیر محیطی و سامانه فایلی که Worker داشت. محیط ایزوله JavaScript چیزهای آشکار را مسدود می‌کرد اما نمی‌توانست جلوی کاربری مصمم را از کاویدن آنچه از شبکه ما دست‌یافتنی بود بگیرد.
- **دسترس.** بیشتر گام‌های مفید می‌خواهند روی زیرساخت _مشتری_ عمل کنند («این سرویس را بازراه‌اندازی کن»، «kubectl روی خوشه ما»، «رکوردی در پایگاه داده داخلی ما جستجو کن») — نه روی زیرساخت OneUptime.

عامل‌های رانبوک این را وارونه می‌کنند. گام‌های Bash و JavaScript روی ما اجرا نمی‌شوند. روی میزبانی اجرا می‌شوند که شما کنترلش می‌کنید، و شما تصمیم می‌گیرید آن میزبان چه بتواند بکند.

## چگونه کار می‌کند

1. در OneUptime عامل رانبوکی می‌سازید. OneUptime شناسه و کلیدی محرمانه تولید می‌کند.
2. کانتینر عامل را با آن شناسه/کلید به‌علاوه نشانی OneUptime خود روی میزبانی درون زیرساختتان اجرا می‌کنید.
3. عامل هر چند ثانیه از OneUptime می‌پرسد «کاری برای من هست؟»
4. وقتی گام Bash یا JavaScript می‌نویسید، عامل را از فهرست کشویی برمی‌گزینید — گام به همان عامل مشخص مقید می‌شود.
5. وقتی گام اجرا می‌شود، Worker سطر کاری با `targetAgentId` تنظیم‌شده روی آن عامل درج می‌کند. فقط همان عامل می‌تواند برش دارد.
6. عامل اسکریپت را محلی اجرا می‌کند — `bash -c <script>` برای Bash، محیط ایزوله `isolated-vm` برای JavaScript — نتیجه را ثبت می‌کند و پس می‌فرستد. Worker رانبوک را با آن نتیجه از سر می‌گیرد.

عامل فقط به **HTTPS خروجی** به نمونه OneUptime شما نیاز دارد. هیچ اتصال ورودی‌ای نمی‌پذیرد.

## نصب یک عامل

### ۱. ساخت رکورد عامل

به **Settings → Runners** بروید و عاملی تازه بسازید. پر کنید:

| فیلد | یادداشت‌ها |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Name** | نامی دوستانه — معمولاً `جایی-که-اجرا-می‌شود-و-چه-می‌تواند-بکند`، برای نمونه `prod-eu-west-1`. همین چیزی است که هنگام نوشتن گام در فهرست کشویی پدیدار می‌شود. |
| **Description** | اختیاری. جمله‌ای درباره اینکه این میزبان به چه چیزی می‌رسد. خودِ آینده‌تان سپاسگزار خواهد بود. |

### ۲. کپی کردن فرمان نصب

پس از ساختن عامل، در سطرش روی **Show setup instructions** کلیک کنید. فرمان `docker run` از پیش پرشده با شناسه و کلید این عامل را می‌بینید. **کلید را همین حالا ذخیره کنید** — می‌توانید بعداً بازنشانی‌اش کنید، اما پس از بستن پنجره نمی‌توانید دوباره همان مقدار کلید را ببینید.

### ۳. اجرایش روی میزبانی درون زیرساختتان

فرمان Docker را روی هر میزبانی در محیطتان اجرا کنید که بتواند:

- روی HTTPS به نمونه OneUptime شما برسد، و
- کارهایی را بکند که می‌خواهید گام‌های Bash/JavaScript شما بکنند (برای نمونه SSH به میزبان‌های دیگر، `kubectl`، حرف زدن با پایگاه داده).

```bash
docker run --name oneuptime-runner --restart unless-stopped \
  -e ONEUPTIME_RUNNER_ID=<agent-id> \
  -e ONEUPTIME_RUNNER_KEY=<agent-key> \
  -e ONEUPTIME_URL=https://oneuptime.yourdomain.com \
  -d oneuptime/runner:release
```

### ۴. تأیید اتصال عامل

به **Settings → Runners** برگردید. ظرف حدود ۶۰ ثانیه سطر عامل باید با مهر زمانی تازه **Last seen** به `Connected` تغییر کند. اگر `Disconnected` ماند:

- گزارش‌های کانتینر (`docker logs oneuptime-runner`) را برای خطاهای احراز هویت یا شکست شبکه بررسی کنید.
- تأیید کنید میزبان با `curl` می‌تواند به نشانی OneUptime شما برسد.
- تأیید کنید شناسه و کلید بدون فاصله سفید کپی شده‌اند.

## نشانه گرفتن یک گام به یک عامل

در رانبوک خود، گام Bash یا JavaScript بیفزایید. فرم فهرست کشویی **Runbook Agent** دارد که هر عاملی در پروژه جاری را فهرست می‌کند (با نشانگر متصل/قطع):

- عاملی را که باید این گام را اجرا کند برگزینید.
- اسکریپتتان را در ویرایشگر پایین بنویسید.

وقتی رانبوک اجرا شود و به گام برسد، Worker کاری نشانه‌گرفته به شناسه آن عامل در صف می‌گذارد. فقط همان عامل می‌تواند برش دارد. Bash از راه `bash -c` اجرا می‌شود؛ JavaScript درون محیط ایزوله `isolated-vm` روی عامل اجرا می‌شود (بدون سامانه فایل، بدون شبکه، بدون `Function`/`eval`).

بیش از یک عامل لازم دارید؟ بسازیدشان، سپس هر گام را به هرکدام که جا می‌افتد نشانه بگیرید. اگر افزونگی می‌خواهید، می‌توانید دو رانبوک بنویسید (به ازای هر عامل یکی) یا گام‌ها را میان عامل‌ها تقسیم کنید.

## یادداشت‌های عملیاتی

### مهلت‌ها

دو مهلت روی هر گام Bash یا JavaScript اعمال می‌شوند:

| مهلت | پیش‌فرض | چه چیزی را کنترل می‌کند |
| --------------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Claim timeout** | ۲ دقیقه | Worker چقدر منتظر می‌ماند تا عامل برگزیده کار را بردارد. اگر عامل به‌موقع برش ندارد، گام با `TimedOut` شکست می‌خورد و رانبوک ادامه می‌دهد (یا می‌ایستد، بسته به **Continue on failure**). |
| **Execution timeout** | ۳۰ ثانیه | عامل چقدر اجازه می‌دهد اسکریپت اجرا شود پیش از خاتمه دادنش. (Bash ‏`SIGKILL` می‌گیرد؛ ایزوله JavaScript برچیده می‌شود.) |

هر دو به ازای هر گام قابل پیکربندی‌اند. **Runbooks &rsaquo; رانبوک شما &rsaquo; Steps** را باز کنید، گام Bash یا JavaScript را بگسترانید، و **Execution timeout** و **Claim timeout** (بر حسب ثانیه) را زیر اسکریپت تنظیم کنید. برای استفاده از پیش‌فرض، فیلد را خالی بگذارید. هرکدام از ۱ ثانیه تا ۱ ساعت می‌پذیرند؛ مقادیر بیرون آن بازه هنگام اجرای گام محدود می‌شوند.

پنجره انتظار کلی Worker برابر است با `مهلت برداشت + مهلت اجرا + چند ثانیه`. اعدادی برگزینید که با گام بخوانند.

هنگام پایین آوردن مهلت برداشت دو چیز را به یاد داشته باشید:

- عامل روی چرخه‌ای نظرسنجی (`ONEUPTIME_RUNNER_POLL_INTERVAL_MS`، به‌طور پیش‌فرض ۵ ثانیه) درخواست کار می‌کند. مهلت برداشتی کوتاه‌تر از یک چرخه نظرسنجی می‌تواند پیش از آنکه عاملی کاملاً سالم حتی کار را ببیند منقضی شود، و آنگاه گام با همان پیام «هیچ عاملی کار را برنداشت» شکست می‌خورد که از عاملی آفلاین می‌گرفتید.
- عامل به‌طور پیش‌فرض یک کار در هر زمان اجرا می‌کند (`ONEUPTIME_RUNNER_CONCURRENCY`). تا وقتی گامی طولانی اشغالش کرده، گام‌های دیگری که به همان عامل نشانه گرفته‌اند مهلت برداشت خودشان را می‌سوزانند. اگر مهلت اجرایی را به دقیقه‌ها بالا می‌برید، مهلت برداشت گام‌هایی را که آن عامل را به اشتراک می‌گذارند متناسب بالا ببرید — یا عاملی دیگر به آن‌ها بدهید.

### اجاره و ضربان قلب

وقتی عاملی کاری را برمی‌دارد، اجاره کوتاهی می‌گیرد (به‌طور پیش‌فرض ۳۰ ثانیه). تا وقتی اسکریپت اجرا می‌شود، عامل هر ۱۰ ثانیه اجاره را تمدید می‌کند. اگر عامل بمیرد یا در میانه اسکریپت شبکه‌اش را از دست بدهد، اجاره منقضی می‌شود و Worker به‌جای انتظار بی‌پایان، کار را `TimedOut` علامت می‌زند.

فرایندهای فرزند Bash هنگام انقضای اجاره خودکار لغو **نمی‌شوند** (ایزوله JavaScript هم رها می‌شود تا اگر روزی تمام شد تمام شود) — اما Worker دیگر منتظرشان نمی‌ماند، و عامل پس از آنکه برداشتی دیگر جایش را گرفت نمی‌تواند نتیجه‌ای ثبت کند. اگر «دقیقاً یک بار» برایتان مهم است، اسکریپت‌ها را طوری طراحی کنید که اجرای دوباره‌شان امن باشد.

### اگر Worker در OneUptime در میانه گام بازراه‌اندازی شود

اجرای رانبوک از آغاز تا پایان روی یک Worker اجرا می‌شود، پس استقرار یا فروریزی می‌تواند در حین اجرای گامی قطعش کند. آنچه در ادامه رخ می‌دهد به این بستگی دارد که اجرا دوباره برداشته می‌شود یا نه:

- **از سر گرفته می‌شود.** Workerای که برش می‌دارد سطر کاری‌ای را که گام شما از پیش ساخته می‌یابد و **دوباره به آن می‌چسبد** — به‌جای فرستادن نسخه دومی از اسکریپت به عاملتان، منتظر همان کار می‌ماند. اگر عامل از پیش تمام کرده باشد، نتیجه ثبت‌شده همان‌طور که هست به کار می‌رود. هر گام در هر اجرا حداکثر یک بار به عاملی فرستاده می‌شود.
- **از سر گرفته نمی‌شود.** اگر اجرا هرگز دوباره برداشته نشود، جارویی آن را پس از گذشتن از پنجره برداشت + اجرایی که گام جاری‌اش برایش پیکربندی شده بود `Failed` علامت می‌زند، با پیامی که نام آن گام را می‌برد. اجرا هرگز در `Running` معلق نمی‌ماند.

تنها چیزی که این نمی‌تواند به شما بگوید این است که اسکریپت پیش از ناپدید شدن Worker تا کجا رفته بود. گامی که در میانه اجرا بوده شکست‌خورده گزارش می‌شود با یادداشتی که ممکن است نیمه‌کاره اجرا شده باشد — پیش از اجرای دوباره رانبوک، سامانه هدف را بررسی کنید.

### هیچ عاملی آنلاین نیست

اگر عامل برگزیده در لحظه اجرای گام آفلاین باشد، کار تا سپری شدن مهلت برداشت `Pending` می‌نشیند، سپس با پیام روشن «هیچ عاملی کار را برنداشت» شکست می‌خورد. صفحه عامل‌ها جایی است که پیش از اجرای جدی رانبوک، پوشش را تأیید می‌کنید.

### سقف خروجی

مجموع stdout + stderr به ازای هر گام به **۵۰ کیلوبایت** سقف می‌خورد. خروجی بزرگ‌تر با نشانگری کوتاه می‌شود. اگر گزارش کامل لازم دارید، درون اسکریپت آن را روی S3 یا انباره گزارشتان بنویسید و نشانی‌اش را `echo` کنید.

### لغو

لغو اجرای رانبوک (از نمای اجرا یا از API) بی‌درنگ همه کارهای `Pending`/`Claimed`/`Running` بش و JavaScript آن را `Cancelled` علامت می‌زند. عاملی که از پیش در میانه اسکریپت است کارش را تمام می‌کند، اما نتیجه‌اش را کارساز نمی‌پذیرد، و هیچ گام بعدی‌ای در رانبوک فرستاده نمی‌شود.

### هم‌زمانی

هر عامل به‌طور پیش‌فرض یک کار در هر زمان اجرا می‌کند. برای اجازه دادن به بیشتر، `ONEUPTIME_RUNNER_CONCURRENCY` را روی کانتینر عامل تنظیم کنید — اما به یاد داشته باشید عامل میزبان را با هر چیز دیگری که آنجا زندگی می‌کند به اشتراک می‌گذارد.

## متغیرهای محیطی

عامل هنگام راه‌اندازی این‌ها را می‌خواند:

| متغیر | الزامی | پیش‌فرض | یادداشت‌ها |
| ----------------------------------------- | -------- | ------- | ----------------------------------------------------------------------------- |
| `ONEUPTIME_URL` | بله | — | نشانی پایه نمونه OneUptime شما، برای نمونه `https://oneuptime.yourdomain.com`. |
| `ONEUPTIME_RUNNER_ID` | بله | — | ‏UUIDای که در پنجره راه‌اندازی عامل نشان داده شد. |
| `ONEUPTIME_RUNNER_KEY` | بله | — | رازی که در پنجره راه‌اندازی عامل نشان داده شد. |
| `ONEUPTIME_RUNNER_POLL_INTERVAL_MS` | خیر | `5000` | هر چند وقت عامل دنبال کار تازه می‌گردد. |
| `ONEUPTIME_RUNNER_HEARTBEAT_INTERVAL_MS` | خیر | `60000` | هر چند وقت عامل زنده بودنش را گزارش می‌دهد. |
| `ONEUPTIME_RUNNER_JOB_HEARTBEAT_INTERVAL_MS` | خیر | `10000` | هر چند وقت عامل اجاره کاری در حال اجرا را تمدید می‌کند. |
| `ONEUPTIME_RUNNER_CONCURRENCY` | خیر | `1` | بیشینه کارهای هم‌زمان روی این عامل. |

## چرخاندن کلید یک عامل

اگر کلیدی درز کند، عامل را در OneUptime باز کنید و کلیدش را بازنشانی کنید. کلید قدیمی بی‌درنگ از کار می‌افتد. کانتینر عامل را با کلید تازه به‌روزرسانی و بازراه‌اندازی کنید.

## دسترسی‌ها

مدیریت عامل‌ها زیر گروه دسترسی موجود رانبوک‌ها زندگی می‌کند:

- `CreateRunner`، `EditRunner`، `DeleteRunner`، `ReadRunner` — مدیریت رکوردهای عامل.
- `RunbookAdmin`، `RunbookMember`، `RunbookViewer` (نقش‌ها) — به تیمی تخصیص دهید تا به‌ترتیب کنترل کامل، استفاده روزمره یا دسترسی فقط‌خواندنی بگیرد. `RunbookAdmin` همه دسترسی‌های ریزدانه بالا را بسته‌بندی می‌کند.

دسترسی برای _راه انداختن_ یک رانبوک (و در نتیجه فرستادن گام‌های Bash و JavaScript) همچنان `CreateRunbookExecution` / `EditRunbookExecution` است.

## API رو به عامل

برای کنجکاوان — عامل این نقطه‌های پایانی را که زیر `/runner-ingest` سوار شده‌اند به کار می‌برد. مسیر پیش از ادغام `/runbook-agent-ingest` همچنان برای عامل‌هایی که هنوز دوباره مستقر نشده‌اند سرو می‌شود، پس ارتقای کارساز نمی‌شکندشان. احراز هویتشان با شناسه + کلید عامل در بدنه JSON (یا هدرهای `x-agent-id` / `x-agent-key`) است.

| نقطه پایانی | هدف |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `POST /heartbeat` | زنده بودن؛ `lastAlive`، `connectionStatus`، `hostInfo`، `agentVersion` را به‌روزرسانی می‌کند. |
| `POST /claim-next-job` | قدیمی‌ترین کار `Pending` نشانه‌گرفته به شناسه این عامل را اتمی برمی‌دارد. وقتی کاری نباشد `{ job: null }` برمی‌گرداند. |
| `POST /job/:jobId/heartbeat` | اجاره کار را تازه می‌کند. پس از سپری شدن اجاره یا پایانی شدن کار، ۴۰۴ برمی‌گرداند. |
| `POST /job/:jobId/result` | نتیجه نهایی را ثبت می‌کند. اگر اجاره از پیش جابه‌جا شده باشد نادیده گرفته می‌شود. |

نباید لازم باشد این‌ها را دستی فرا بخوانید — عامل همراه این کار را می‌کند. اینجا مستند شده‌اند تا اگر محدودیتی دارید که عامل ما با آن جور نیست، بتوانید عامل خودتان را بسازید.
