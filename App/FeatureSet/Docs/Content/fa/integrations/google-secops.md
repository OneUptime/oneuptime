# یکپارچه‌سازی Google SecOps

سیگنال‌های SIEM از [Google SecOps](https://cloud.google.com/security/products/security-operations) (پیش‌تر Chronicle) را به OneUptime بیاورید، تا تشخیص‌های امنیتی در همان دریاچه داده ClickHouse گزارش‌ها، ردیابی‌ها و سنجه‌هایتان زندگی کنند — قابل جستجو، هم‌بسته با داده رصدپذیری، قابل هشدار، و مسیردهی‌شده به کشیک.

سه راه برای وصل شدن هست، از بدون‌کد تا همگام‌سازی کامل رویداد:

```text
1. SOAR playbook webhook   ──►  Security Events ingest  ──►  Events + Detection Rules + Alerts
2. Managed connector       ──►  polls detection alerts  ──►  Detection Finding events
3. UDM event forwarding    ──►  Security Events ingest  ──►  full event search + correlation
```

هر مسیری رویدادها را به [OCSF](https://schema.ocsf.io/) نرمال می‌کند (چارچوب باز طرحواره امنیت سایبری)، که شکل متعارف رویداد امنیتی در OneUptime است، پس قواعد و داشبوردها هر گویش منبعی که باشد یکسان کار می‌کنند.

## پیش‌نیازها

- پروژه‌ای در OneUptime با **کلید دریافت تله‌متری** (**Settings → Telemetry Ingestion Keys**).
- مستأجری در Google SecOps. برای رابط مدیریت‌شده: دسترسی ساخت حساب سرویس Google Cloud با دسترسی خواندن API ‏Chronicle.

## گزینه ۱ — وب‌هوک پلی‌بوک SOAR (ظرف چند دقیقه کار می‌کند)

پلی‌بوک‌های SOAR در Google SecOps می‌توانند هشدارها را به هر نقطه پایانی HTTPای POST کنند. یکی را به دریافت رویدادهای امنیتی OneUptime نشانه بگیرید:

1. در پلی‌بوک SecOps SOAR خود، کنشی از نوع **HTTP request** بیفزایید که روی هشدارهای تازه شلیک کند.
2. پیکربندی‌اش کنید:

   - **Method**: `POST`
   - **URL**: `https://oneuptime.com/security-events/v1/ingest` (یا `https://<your-host>/security-events/v1/ingest` برای خودمیزبان)
   - **Headers**:

     ```text
     Content-Type: application/json
     x-oneuptime-token: <your telemetry ingestion key>
     ```

   - **Body**: JSON هشدار. محموله‌های تشخیص (فراداده قاعده به‌علاوه رویدادهای UDM تطبیق‌یافته زیر `collectionElements`) خودکار شناخته و به‌عنوان رویدادهای **Detection Finding** ذخیره می‌شوند، با مشاهده‌پذیرها (کاربران، میزبان‌ها، IPها) که از رویدادهای تطبیق‌یافته استخراج می‌شوند.

3. هشدارها ظرف چند ثانیه زیر **Security Events** در داشبورد پدیدار می‌شوند.

## گزینه ۲ — رابط مدیریت‌شده (تشخیص‌های پیمایشی)

‏OneUptime هشدارهای تشخیص مستأجر شما را روی فاصله‌ای پیمایش می‌کند — به پیکربندی SOAR نیازی نیست.

1. در Google Cloud، **حساب سرویسی** با نقش **Chronicle API Viewer** روی پروژه‌ای که نمونه SecOps شما به آن مقید است بسازید، و **کلید JSON** آن را دانلود کنید.
2. در OneUptime، **Security Events → Connections** را (`/dashboard/{projectId}/security-events/connections`) باز کنید و روی کارت **Google SecOps Connections** اتصالی بسازید:

   - **Region**: پیشوند ناحیه‌ای مستأجر شما، با حروف کوچک — `us`، `europe` و مانند آن. برای ساخت نشانی پایه API به کار می‌رود.
   - **Instance resource name**: `projects/{project}/locations/{location}/instances/{instance}` — از **SIEM Settings → Profile** در SecOps شما.
   - **Service account JSON**: کلید را بچسبانید. فقط‌نوشتنی است — در حالت سکون رمزگذاری می‌شود، هرگز توسط API برنمی‌گردد، و هرگز در صفحه به شما بازنشان داده نمی‌شود. برای چرخاندن بعدی‌اش، از کنش **Update Service Account JSON** اتصال استفاده کنید.
   - **Poll interval (minutes)**: عددی کامل از `1` تا `1440`، پیش‌فرض `5`. هر چیزی بیرون آن بازه هنگام ذخیره رد می‌شود.

3. تشخیص‌های تازه به‌عنوان رویدادهای **Detection Finding** منتسب به سرویس تله‌متری `Google SecOps` دریافت می‌شوند.

رابط هر دقیقه یک بار تیک می‌زند و هر اتصال فعالی را که بر پایه فاصله خودش سررسیده پیمایش می‌کند. نخستین پیمایش **۱۵ دقیقه** به عقب نگاه می‌کند؛ هر پیمایش پس از آن از مکان‌نمای ذخیره‌شده اتصال با **۱ دقیقه** هم‌پوشانی از سر می‌گیرد، پس هشدارهایی که روی مرز پنجره می‌نشینند هرگز از دست نمی‌روند. هیچ پیمایش تنهایی بیش از **۲۴ ساعت** را بازپخش نمی‌کند — اتصالی که یک هفته غیرفعال نشسته یک روز به عقب از سر می‌گیرد، نه یک هفته.

فهرست اتصال‌ها همان گزارش سلامت پیمایش است: **Name**، **Status** (فعال/غیرفعال)، **Region**، **Interval (Minutes)**، **Last Polled** و **Last Error**.

> رابط از API هشدارهای `v1alpha` در Chronicle استفاده می‌کند، که گوگل آن را پیش از GA عرضه می‌کند. اگر شکل API مستأجر شما فرق کند، فیلد **Last Error** اتصال آغاز آنچه را API برگردانده حمل می‌کند، پشت پیشوندی که درخواست شکست‌خورده را نام می‌برد — از جمله حالتی که Chronicle پاسخ `200` می‌دهد و رد را درون بدنه می‌گذارد.

### رفع اشکال

- **وضعیت `Disabled` است** — اتصال‌های غیرفعال کلاً رد می‌شوند. پیمایشگر فقط فعال‌ها را برمی‌دارد.
- **‏Last Polled برابر `Never` است و Last Error خالی است** — کارگر پس‌زمینه اصلاً کار پیمایش را اجرا نکرده، پس هیچ‌چیز هرگز به Chronicle نرسیده است. در استقرارهای خودمیزبان علت معمول `DISABLE_QUEUE_WORKERS=true` روی کانتینر برنامه بدون استقرار کارگر جداگانه‌ای است که صف‌ها را تخلیه کند. یا `DISABLE_QUEUE_WORKERS=false` بگذارید (پیش‌فرض `config.example.env` که Docker Compose با آن می‌آید)، یا استقرار کارگر اختصاصی را اجرا کنید (Helm: ‏`worker.enabled: true`، که به‌طور پیش‌فرض `false` است).
- **‏Last Error پر است** — پیمایشی تلاش شده و چیزی در آن شکست خورده است. فیلد آن شکست را همان‌گونه که OneUptime ثبتش کرده نگه می‌دارد: پیشوندی که گام را نام می‌برد، سپس حداکثر ۵۰۰ نویسه نخست بدنه پاسخ، که کلاً محدود می‌شود و اگر باز هم بلند باشد `... (truncated)` علامت می‌خورد. نخست پیشوند را بخوانید. فقط دو پیشوند وضعیت HTTP حمل می‌کنند، پس پیامی بدون آن شاهد ایرادی در سمت OneUptime نیست:
  - `Google token exchange failed (HTTP ...)` — اعتبارنامه حساب سرویس در نقطه پایانی OAuth گوگل رد شده، پیش از آنکه اصلاً با Chronicle تماس گرفته شود. معمولاً کلیدی بدشکل، باطل‌شده یا از پروژه‌ای اشتباه.
  - `Google token exchange returned ...` — همان نقطه پایانی OAuth پاسخ داده، اما با چیزی غیرقابل استفاده: بدون `access_token`، یا بدنه‌ای که JSON نیست. باز هم پیش از Chronicle، و معمولاً پراکسی یا دروازه‌ای در میانه نه خودِ کلید.
  - `Google SecOps alerts fetch failed (HTTP ...)` — خودِ Chronicle درخواست را رد کرده است. `403` معمولاً یعنی حساب سرویس نقش **Chronicle API Viewer** را روی پروژه‌ای که نمونه به آن مقید است ندارد؛ `404` معمولاً یعنی نام منبع نمونه به نمونه‌ای دیگر اشاره می‌کند، یا پیشوند ناحیه از آن‌هایی نیست که Chronicle سرو می‌کند.
  - `Google SecOps alerts fetch returned ...` — ‏Chronicle پاسخ `200` داده، اما بدنه جریان خواندنی هشدارهای تشخیص نبوده: خالی، غیر JSON، یا شکلی که تفکیک‌کننده نمی‌شناسد. عمداً به‌جای شمرده شدن به‌عنوان پنجره‌ای خالی گزارش می‌شود — رفتار با بدنه‌ای که نتوانسته بخواند به‌عنوان «بدون هشدار» مکان‌نما را از آنچه از دست رفته جلو می‌برد.
  - `Google SecOps alerts query was rejected by Chronicle on an HTTP 200` — ‏Chronicle درخواست را پذیرفته، اجرایش کرده، و پرس‌وجو را درون بدنه‌ای که برگردانده رد کرده است (`validSnapshotQuery` یا `validBaselineQuery` نادرست، یا `queryValidationErrors`). این رد گوگل است، و هیچ وضعیت HTTPای در آن نیست.
  - `timed out after 60 seconds with no response` — نه نقطه پایانی OAuth گوگل و نه Chronicle پیش از تسلیم کلاینت پاسخ داده‌اند. چیزی برنگشته، پس پیام هیچ سویی را متهم نمی‌کند؛ خروج ترافیک از کارگر OneUptime و نیز مستأجر را بررسی کنید.
  - پیامی که با هیچ‌کدام از بالا نمی‌خواند — شکست در سمت OneUptime بوده است. پیام `Google SecOps connection is missing id, projectId, region, instance, or credentials` یعنی این سطر اتصال با وجود `Google` جلویش ناقص است؛ وگرنه هشدارها رسیده‌اند و نوشتنشان در انباره تله‌متری شکست خورده است.
- **‏Last Error می‌گوید `Google SecOps alerts fetch failed (HTTP 400)` و `Unknown name "pageSize": Cannot bind query parameter` را نقل می‌کند** — این اشکالی در OneUptime در شکل درخواست بود که در همین انتشار رفع شد. ارتقا دهید و پیمایش بدون هیچ تغییری از سمت شما موفق می‌شود. به‌خاطرش کلید حساب سرویس را دوباره تولید **نکنید**: گوگل درخواستی را پیش از ترجمه رشته پرس‌وجو احراز هویت می‌کند، پس رسیدن به مرحله مقید کردن پارامتر خودش اثباتی است که کلید پذیرفته شده. همان درخواست دقیق بدون اعتبارنامه با `401` برمی‌گردد و هرگز به اندازه‌ای پیش نمی‌رود که این `400` را تولید کند.

## گزینه ۳ — فوروارد کردن رویدادهای UDM

برای جستجو و هم‌بستگی با وفاداری کامل، خودِ رویدادهای UDM را فوروارد کنید (برای نمونه از خط لوله صادرات BigQuery، یک Cloud Function، یا هر فورواردری که از پیش اجرا می‌کنید):

```bash
curl -X POST "https://oneuptime.com/security-events/v1/ingest?format=udm" \
  -H "Content-Type: application/json" \
  -H "x-oneuptime-token: <your telemetry ingestion key>" \
  -d '{
    "events": [
      {
        "metadata": {
          "event_type": "USER_LOGIN",
          "event_timestamp": "2026-08-21T10:00:00Z",
          "vendor_name": "Google",
          "product_name": "Google SecOps"
        },
        "principal": { "user": { "userid": "alice" }, "ip": ["203.0.113.7"] },
        "target": { "hostname": "vpn-gw-01" },
        "security_result": [{ "severity": "HIGH", "action": ["BLOCK"] }]
      }
    ]
  }'
```

- مقدار `format` می‌تواند `udm`، `ocsf`، `google-secops-alert` یا `generic` باشد؛ نگذاریدش و گویش به ازای هر رویداد تشخیص داده می‌شود.
- بدنه شیئی تنها، آرایه‌ای خالی، یا `{ "events": [...] }` می‌پذیرد.
- هدر `x-oneuptime-service-name` را بگذارید تا کنترل کنید رویدادها به کدام سرویس تله‌متری منتسب شوند (پیش‌فرض نام محصول در محموله است).

## چه می‌گیرید

- **کاوشگر رویدادهای امنیتی** — جستجو و پالایش رویدادها بر پایه شدت، کلاس OCSF، بازیگر، هدف، یا هر مشاهده‌پذیری.
- **هم‌بستگی** — مشاهده‌پذیرهای هر رویداد (کاربران، میزبان‌ها، IPها، دامنه‌ها) نمایه می‌شوند، پس «هر چیزی که این میزبان را می‌آورد» یک پرس‌وجوست، کنار گزارش‌ها و سنجه‌های همان میزبان.
- **قواعد تشخیص** — تشخیص‌های [Sigma](https://sigmahq.io/) به‌صورت کد که هر دقیقه بر رویدادهای شما سنجیده می‌شوند؛ تطبیق‌ها هشدارهای بدون تکرار (با مسیردهی کشیک) باز می‌کنند و رویدادهای Detection Finding می‌نویسند.
- **مانیتورهای رویداد امنیتی** — وقتی شمار رویدادهای مطابق از آستانه‌ای بگذرد هشدار بده، با همان معیارها، حادثه و ماشین‌آلات کشیکی که هر مانیتور دیگری دارد.
- **داشبوردها و هوش مصنوعی** — ابزارک‌های رویداد امنیتی (از جمله نمای جریان Sankey) روی داشبوردهای سفارشی، و ابزارهای دستیار هوش مصنوعی (`search_security_events`، `security_event_summary`) برای بررسی به زبان طبیعی.

## صورت‌حساب

رویدادهای امنیتی مانند دیگر تله‌متری‌ها، به ازای هر گیگابایت دریافتی اندازه‌گیری می‌شوند. [قیمت‌گذاری](https://oneuptime.com/pricing) را ببینید.
