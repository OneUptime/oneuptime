# مانیتور Docker

مانیتورینگ Docker به شما امکان می‌دهد سلامت و کارایی میزبان‌های Docker و کانتینرهای در حال اجرا رویشان را زیر نظر بگیرید. OneUptime سنجه‌ها و گزارش‌های کانتینر را از راه جمع‌کننده‌ای از پیش پیکربندی‌شده از OpenTelemetry (**عامل Docker در OneUptime**) جمع می‌کند و بر پایه معیارهای پیکربندی‌شده شما می‌سنجدشان.

## نمای کلی

مانیتورهای Docker از سنجه‌ها و گزارش‌های میزبان‌هایتان برای دید به بارهای کاری کانتینری استفاده می‌کنند. این به شما امکان می‌دهد:

- سلامت میزبان Docker و هر کانتینر را زیر نظر بگیرید
- ‏CPU، حافظه، شبکه، ورودی/خروجی بلوکی و شمار فرایندها را در سراسر کانتینرها ردیابی کنید
- بازراه‌اندازی، فروریزی و خفگی CPU کانتینرها را تشخیص دهید
- گزارش‌های ساخت‌یافته کانتینر را در قالب بومی OpenTelemetry جریان دهید
- بر CPU بالا، حافظه بالا، حلقه بازراه‌اندازی و بیشتر هشدار بدهید

## ساختن یک مانیتور Docker

1. در داشبورد OneUptime به **Monitors** بروید
2. روی **Create Monitor** کلیک کنید
3. نوع مانیتور را **Docker** برگزینید
4. میزبان Docker و دامنه منبعی را که باید زیر نظر گرفته شود برگزینید
5. پرس‌وجوهای سنجه و تجمیع را پیکربندی کنید
6. معیارهای مانیتورینگ را به‌فراخور پیکربندی کنید

## گزینه‌های پیکربندی

### میزبان Docker

میزبان Dockerای را که باید زیر نظر گرفته شود برگزینید. میزبان‌ها نخستین بار که عامل Docker در OneUptime از آن‌ها تله‌متری می‌فرستد خودکار ثبت می‌شوند — لازم نیست دستی بسازیدشان.

### دامنه منبع

سطحی را که در آن منابع زیر نظر گرفته می‌شوند برگزینید:

| دامنه | توضیح |
| --------- | ---------------------------------------------------------------- |
| Host | زیر نظر گرفتن کل میزبان Docker، تجمیع‌شده در سراسر همه کانتینرها |
| Container | زیر نظر گرفتن کانتینری مشخص بر پایه نام یا ایمیج |

### پرس‌وجوهای سنجه

یک یا چند پرس‌وجوی سنجه برای سنجش پیکربندی کنید. هر پرس‌وجو این‌ها را مشخص می‌کند:

- **نام سنجه** — سنجه کانتینری که پرس‌وجو می‌شود
- **تجمیع** — اینکه مقادیر سنجه چگونه تجمیع شوند (میانگین، مجموع، بیشینه، کمینه)
- **پالایه‌ها** — پالایش بیشتر بر پایه ویژگی (برای نمونه بر پایه نام کانتینر، ایمیج یا میزبان)
- **Group By** — اختیاراً بر پایه `resource.container.name` گروه‌بندی کنید تا هر کانتینری مستقل سنجیده شود

می‌توانید **فرمول‌هایی** هم بسازید که چند پرس‌وجوی سنجه را با عبارت‌های ریاضی ترکیب می‌کنند.

### پنجره زمانی غلتان

پنجره زمانی ارزیابی سنجه را برگزینید:

- ۱ دقیقه گذشته
- ۵ دقیقه گذشته
- ۱۰ دقیقه گذشته
- ۱۵ دقیقه گذشته
- ۳۰ دقیقه گذشته
- ۶۰ دقیقه گذشته

## سنجه‌های جمع‌آوری‌شده

عامل Docker از گیرنده `docker_stats` در OpenTelemetry استفاده می‌کند، که API موتور Docker را روی فاصله‌ای قابل پیکربندی (پیش‌فرض هر ۳۰ ثانیه) برداشت می‌کند.

### CPU

| سنجه | توضیح |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `container.cpu.utilization` | بهره‌برداری CPU، که ۱۰۰٪ یک هسته کامل CPU است (ستون CPU% در `docker stats`) |
| `container.cpu.usage.total` | زمان تجمعی CPU مصرف‌شده توسط کانتینر از آغازش (شمارنده عمر) |
| `container.cpu.throttling_data.throttled_time` | کل نانوثانیه‌هایی که کانتینر از آغازش توسط cgroups خفه شده است (شمارنده عمر) |
| `container.cpu.throttling_data.throttled_periods` | شمار دوره‌های خفگی از آغاز کانتینر (شمارنده عمر) |

### حافظه

| سنجه | توضیح |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `container.memory.usage.total` | مصرف جاری حافظه بر حسب بایت |
| `container.memory.usage.limit` | محدودیت حافظه بر حسب بایت |
| `container.memory.percent` | مصرف حافظه به‌صورت درصدی از محدودیت حافظه کانتینر، یا از کل حافظه میزبان وقتی کانتینر محدودیتی ندارد |

### شبکه

| سنجه | توضیح |
| ------------------------------------- | ----------------------- |
| `container.network.io.usage.rx_bytes` | کل بایت‌های دریافتی |
| `container.network.io.usage.tx_bytes` | کل بایت‌های فرستاده‌شده |

### ورودی/خروجی بلوکی

| سنجه | توضیح |
| ---------------------------------------------------- | ------------------------------ |
| `container.blockio.io_service_bytes_recursive.read` | بایت‌های خوانده‌شده از دستگاه‌های بلوکی |
| `container.blockio.io_service_bytes_recursive.write` | بایت‌های نوشته‌شده روی دستگاه‌های بلوکی |

### اطلاعات کانتینر

| سنجه | توضیح |
| ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| `container.uptime` | آپ‌تایم کانتینر بر حسب ثانیه |
| `container.restarts` | شمار دفعاتی که کانتینر از ساخته شدنش بازراه‌اندازی شده است (شمارنده عمر) |
| `container.pids.count` | شمار وظیفه‌های درون کانتینر — کنترلر pids در cgroup علاوه بر فرایندها، رشته‌های هسته را هم می‌شمارد |

## معیارهای مانیتورینگ

### چه چیزی سنجیده می‌شود

این مانیتورها همیشه **Metric Value** را می‌سنجند — مقدار پرس‌وجوی سنجه یا فرمول پیکربندی‌شده. فرم معیارها انتخابگر Filter Type ندارد؛ **Metric**، **Aggregation**، **Condition** و **Threshold** را نشان می‌دهد.

### نوع‌های تجمیع

| تجمیع | توضیح |
| ------------- | ---------------------------------- |
| Average | مقدار میانگین در پنجره زمانی |
| Sum | مجموع همه مقادیر |
| Maximum Value | بالاترین مقدار در پنجره زمانی |
| Minimum Value | پایین‌ترین مقدار در پنجره زمانی |
| All Values | همه مقادیر باید با معیار بخوانند |
| Any Value | دست‌کم یک مقدار باید بخواند |

### شرط‌ها

آستانه‌های ایستا — با **Threshold**ای که وارد می‌کنید مقایسه می‌شوند:

- **Greater Than**، **Less Than**، **Greater Than or Equal To**، **Less Than or Equal To**، **Equal To**

تشخیص ناهنجاری خط پایه — بدون آستانه؛ به‌جایش فرم **Sensitivity** و **Baseline Window** را نشان می‌دهد و هر نمونه را با خط پایه همان ساعت از هفته که از آن پنجره ساخته شده مقایسه می‌کند:

- **Anomalously High** — مقدار بالای محدوده مورد انتظار می‌رود
- **Anomalously Low** — مقدار زیر محدوده مورد انتظار می‌افتد
- **Anomalous** — مقدار در هر جهتی از محدوده مورد انتظار بیرون می‌رود

شرط‌های ناهنجاری در وضعیت «Learning» می‌مانند و تا وقتی دست‌کم به اندازه Baseline Window برگزیده تاریخچه سنجه وجود نداشته باشد هیچ هشداری تولید نمی‌کنند.

## قالب‌های آماده هشدار

‏OneUptime برای سناریوهای رایج مانیتورینگ Docker قالب‌هایی ارائه می‌دهد:

| قالب | توضیح | آستانه | تجمیع |
| ---------------------------- | ---------------------------------------------- | ----------------- | -------------------------------------------- |
| High Container CPU | بهره‌برداری CPU به ازای هر کانتینر | > ۸۰٪ یک هسته | بیشینه (به ازای هر کانتینر) |
| High Container Memory | مصرف حافظه به‌صورت درصدی از محدودیت (یا RAM میزبان) | > ۸۵٪ | بیشینه (به ازای هر کانتینر) |
| High CPU Throttling | رشد زمان خفگی CPU | > ۱۰۰۰ میلی‌ثانیه در ۵ دقیقه | بیشینه − کمینه در هر دقیقه، جمع‌شده (به ازای هر کانتینر) |
| Container Restart Loop | رشد شمار بازراه‌اندازی کانتینر | > ۳ در ۱۵ دقیقه | بیشینه − کمینه در هر دقیقه، جمع‌شده (به ازای هر کانتینر) |
| High Container Process Count | شمار وظیفه (فرایندها به‌علاوه رشته‌ها) | > ۲۰۰۰ | بیشینه (به ازای هر کانتینر) |
| Container Down | بازنشانی آپ‌تایم کانتینر به ۰ | = ۰ | کمینه |

> توجه: قالب‌های CPU، حافظه و شمار فرایند از تجمیع **بیشینه** با گروه‌بندی بر پایه `resource.container.name` استفاده می‌کنند. این جلوی رقیق شدن سیگنال یک کانتینر داغ با کانتینرهای بیکار فراوان روی همان میزبان را می‌گیرد.

> توجه: **High Container CPU** روی `container.cpu.utilization` آستانه می‌گذارد، که همان عددی است که `docker stats` چاپ می‌کند — ۱۰۰٪ یک هسته کامل CPU است، نه ۱۰۰٪ میزبان، پس کانتینری که روی دو هسته پخش شده ۲۰۰ می‌خواند. روی میزبانی چندهسته‌ای آستانه بودجه‌ای مطلق از CPU است نه سهمی از ماشین.

> توجه: مقادیر `container.restarts` و `container.cpu.throttling_data.throttled_time` **شمارنده‌های عمر** هستند، پس آن دو قالب به‌جای مقدار، بر میزان رشد شمارنده در پنجره هشدار می‌دهند. مقایسه مقدار برای هر کانتینری که هرگز بازراه‌اندازی شده یا خفه شده تا ابد شلیک می‌کرد و هرگز نمی‌توانست بازیابی شود، چون شمارنده‌ای یکنوا نمی‌تواند پایین بیاید. رشد میان برداشت‌ها درون هر سطل یک‌دقیقه‌ای سنجیده می‌شود، پس با `collection_interval` سی‌ثانیه‌ای عامل تقریباً نیمی از فعالیت واقعی پنجره را می‌گیرد — آستانه‌های بالا از پیش برای همان تنظیم شده‌اند. بالا بردن `collection_interval` به ۶۰ ثانیه یا بیشتر به ازای هر سطل یک نمونه می‌گذارد، تفاوت را یکسان صفر می‌کند، و هر دو قالب را خاموش غیرفعال می‌کند.

> توجه: **High Container Memory** مقدار `container.memory.percent` را می‌خواند، که وقتی محدودیتی گذاشته شده باشد بر محدودیت حافظه کانتینر تقسیم می‌کند و وقتی نه، بر کل حافظه **میزبان**. پیش از آنکه شکستن آستانه را کشتن قریب‌الوقوع OOM بدانید، بررسی کنید کانتینر با `--memory` آغاز شده باشد.

## گزارش‌های جمع‌آوری‌شده

افزون بر سنجه‌ها، عامل Docker فایل `*-json.log` هر کانتینری را با گیرنده filelog در OpenTelemetry دنبال می‌کند و رکوردهای گزارش را در قالب بومی گزارش OTLP می‌فرستد. هر رکورد گزارش با این‌ها غنی می‌شود:

- `resource.host.name` — شناسه میزبان Docker
- `resource.container.id` — شناسه کامل کانتینر
- `resource.container.runtime` — همیشه `docker`
- `attributes["log.iostream"]` — `stdout` یا `stderr`
- `severityText` / `severityNumber` — از کلیدواژه سطحی در خط خوانده می‌شود (`app.INFO:`، `{"level":"warn"}`، `[ERROR]`)؛ خط‌هایی که سطح قابل تشخیصی ندارند به جریان بازمی‌گردند: `stderr` → `ERROR`، `stdout` → `INFO`
- `body` — خط خام گزارشی که فرایند کانتینر منتشر کرده
- `time` — مهر زمانی دیمن Docker برای آن خط

گزارش‌ها در زبانه **Logs** میزبان Docker و در صفحه جزئیات هر کانتینری پدیدار می‌شوند.

### نیازمندی راه‌انداز گزارش

**عامل Docker فقط گزارش‌های کانتینرهایی را دریافت می‌کند که راه‌انداز گزارش `json-file` در Docker را به کار می‌برند.** این پیش‌فرض Docker است، اما می‌توان به ازای هر کانتینر یا سراسری بازنویسی‌اش کرد:

- راه‌انداز **`local`** — تکه‌های دودویی protobuf را در `/var/lib/docker/containers/<id>/local-logs/container.log` می‌نویسد. گیرنده filelog نمی‌تواند این قالب را تفکیک کند.
- **`journald`**، **`syslog`**، **`fluentd`**، **`gelf`**، **`awslogs`**، **`splunk`** و غیره — گزارش‌ها را به مقصدی راه دور می‌فرستند؛ فایلی برای دنبال کردن نیست.
- **`none`** — گزارش‌ها را کلاً دور می‌ریزد.

اگر هرکدام از بالا به کار رفته باشند، سنجه‌ها را در صفحه میزبان Docker می‌بینید اما زبانه **Logs** خالی خواهد بود (یا فقط گزارش‌های خود عامل Docker را دربر دارد).

**بررسی راه‌انداز گزارش کانتینری مشخص:**

```bash
docker inspect <container> --format '{{.HostConfig.LogConfig.Type}}'
```

**بررسی پیش‌فرض دیمن:**

```bash
docker info --format '{{.LoggingDriver}}'
```

**سوییچ کردن سرویسی در Docker Compose به `json-file` با چرخش معقول:**

```yaml
services:
  my-app:
    image: my-app:latest
    logging:
      driver: "json-file"
      options:
        max-size: "100m"
        max-file: "5"
```

**تغییر پیش‌فرض دیمن** (روی هر کانتینری که پس از آن ساخته شود اعمال می‌شود) با ویرایش `/etc/docker/daemon.json`:

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "100m",
    "max-file": "5"
  }
}
```

سپس دیمن Docker را بازراه‌اندازی کنید و کانتینرهای متأثر را **بازبسازید**. Docker راه‌انداز گزارش را هنگام ساخت کانتینر مقید می‌کند، پس کانتینر موجود تا وقتی برداشته و بازساخته نشود راه‌انداز قدیمی‌اش را نگه می‌دارد:

```bash
# Docker Compose
docker compose up -d --force-recreate <service>

# Plain docker
docker rm -f <container>
docker run ... <image>
```

## نیازمندی‌های راه‌اندازی

برای استفاده از مانیتورینگ Docker، باید:

1. عامل Docker در OneUptime را روی هر میزبان Dockerای که می‌خواهید زیر نظر بگیرید نصب کنید
2. مقادیر `ONEUPTIME_URL`، `ONEUPTIME_SERVICE_TOKEN` و `DOCKER_HOST_NAME` را به‌عنوان متغیر محیطی بدهید
3. مطمئن شوید کانتینرهایی که می‌خواهید مشاهده کنید راه‌انداز گزارش `json-file` را به کار می‌برند (بالا را ببینید)

عامل روی Docker Hub با نام `oneuptime/docker-agent:release` منتشر می‌شود. برای نمونه‌های کامل `docker run` و `docker compose`، [راهنمای نصب عامل Docker](https://github.com/OneUptime/oneuptime/tree/master/DockerAgent) را ببینید.

## رفع اشکال

### سنجه‌ها پدیدار می‌شوند اما زبانه Logs خالی است

کانتینرهای شما تقریباً بی‌تردید راه‌انداز گزارش `json-file` را به کار نمی‌برند. فرمان‌های تشخیصی بخش [نیازمندی راه‌انداز گزارش](#نیازمندی-راهانداز-گزارش) بالا را اجرا کنید و هر کانتینری را که گزارش‌هایش باید فرستاده شوند سوییچ کنید.

### گیرنده filelog گزارش می‌دهد `no files match the configured criteria`

این یعنی الگوی include یعنی `/var/lib/docker/containers/*/*-json.log` هنگام آغاز عامل با هیچ فایلی نخوانده است. یا:

1. هیچ کانتینری روی این میزبان `json-file` را به کار نمی‌برد، یا
2. سوارسازی پیوندی `-v /var/lib/docker/containers:/var/lib/docker/containers:ro` نیست یا به پوشه‌ای خالی اشاره می‌کند، یا
3. عامل روی Docker Desktop برای macOS اجرا می‌شود بدون آنکه پوشه کانتینر ماشین مجازی لینوکسی در معرض باشد.

### گزارش‌ها می‌رسند اما زیر نام میزبان اشتباه گروه می‌شوند

‏OneUptime میزبان‌های Docker را بر پایه `resource.host.name` خودکار ثبت می‌کند، که از متغیر محیطی `DOCKER_HOST_NAME` گرفته می‌شود. تغییر `DOCKER_HOST_NAME` پس از نخستین دسته تله‌متری، به‌جای تغییر نام میزبان موجود، سطر میزبان دومی می‌سازد.

### حادثه‌ها برای «CPU بالا» شلیک نمی‌شوند

مطمئن شوید تجمیع پرس‌وجوی سنجه **بیشینه** باشد (نه میانگین) و بر پایه `resource.container.name` گروه‌بندی کند. میانگینی در سراسر همه کانتینرهای میزبانی شلوغ با کانتینرهای بیکار رقیق می‌شود و به‌ندرت از آستانه می‌گذرد.
