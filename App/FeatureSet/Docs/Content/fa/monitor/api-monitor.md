# مانیتور API

پایش API به شما امکان می‌دهد در دسترس بودن، کارایی و درستی APIهای HTTP/REST خود را پایش کنید. OneUptime به‌صورت دوره‌ای درخواست HTTP به نقاط پایانی API شما می‌فرستد و پاسخ‌ها را بر اساس معیارهای پیکربندی‌شده ارزیابی می‌کند.

## نمای کلی

مانیتورهای API به نقاط پایانی شما درخواست HTTP می‌زنند و پاسخ‌ها را بررسی می‌کنند. این کار به شما امکان می‌دهد:

- زمان کارکرد و در دسترس بودن API را پایش کنید
- زمان پاسخ و کارایی را دنبال کنید
- کدهای وضعیت HTTP و بدنه پاسخ را راستی‌آزمایی کنید
- هدرهای پاسخ را اعتبارسنجی کنید
- روش‌های مختلف HTTP را آزمایش کنید (GET، POST، PUT، DELETE و مانند آن)
- هدرها و بدنه‌های سفارشی درخواست بفرستید

## ساخت یک مانیتور API

1. در داشبورد OneUptime به **Monitors** بروید
2. روی **Create Monitor** کلیک کنید
3. نوع مانیتور را **API** انتخاب کنید
4. نشانی API را وارد کنید و تنظیمات درخواست را پیکربندی کنید
5. معیارهای پایش را در صورت نیاز پیکربندی کنید

## گزینه‌های پیکربندی

### نشانی API

نشانی کامل نقطه پایانی APIای را که می‌خواهید پایش کنید وارد کنید (برای نمونه `https://api.example.com/v1/health`).

### جانگهدارهای پویا در نشانی

هنگام پایش APIهایی که پشت CDN یا پراکسی کش قرار دارند، ممکن است مانیتور به‌جای رسیدن به سرور مبدأ، پاسخی کش‌شده بگیرد. برای شکستن کش در هر بررسی، می‌توانید از جانگهدارهای پویای نشانی استفاده کنید که در هر درخواست پایش با مقداری یکتا جایگزین می‌شوند.

#### جانگهدارهای پشتیبانی‌شده

| جانگهدار        | توضیحات                                              | نمونه مقدار                        |
| --------------- | ---------------------------------------------------- | ---------------------------------- |
| `{{timestamp}}` | با مهر زمانی یونیکس فعلی (به ثانیه) جایگزین می‌شود   | `1719500000`                       |
| `{{random}}`    | با یک رشته یکتای تصادفی جایگزین می‌شود               | `a3f8b2c1d4e5f6a7b8c9d0e1f2a3b4c5` |

#### نمونه

نشانی مانیتور خود را با یک جانگهدار پیکربندی کنید:

```
https://api.example.com/health?cb={{timestamp}}
```

در هر بررسی پایش، نشانی به این شکل درمی‌آید:

```
https://api.example.com/health?cb=1719500000
https://api.example.com/health?cb=1719500005
...
```

برای رشته‌ای یکتا در هر درخواست هم می‌توانید از `{{random}}` استفاده کنید:

```
https://api.example.com/health?nocache={{random}}
```

### نوع درخواست API

روش HTTP درخواست را انتخاب کنید:

- **GET** (پیش‌فرض)
- **POST**
- **PUT**
- **DELETE**
- **PATCH**
- **HEAD**

### گزینه‌های پیشرفته

#### هدرهای درخواست

هدرهای سفارشی HTTP را به درخواست اضافه کنید. برای توکن‌های احراز هویت، تعیین نوع محتوا و سایر هدرهای مخصوص API مفید است.

می‌توانید در مقادیر هدر از [اسرار مانیتور](/docs/monitor/monitor-secrets) استفاده کنید تا داده‌های حساس مانند کلیدهای API را امن نگه دارید.

#### بدنه درخواست (JSON)

برای درخواست‌های POST، PUT و PATCH می‌توانید یک بدنه درخواست JSON مشخص کنید. در بدنه درخواست هم می‌توانید از [اسرار مانیتور](/docs/monitor/monitor-secrets) استفاده کنید.

#### تغییر مسیرها را دنبال نکن

به‌صورت پیش‌فرض OneUptime تغییر مسیرهای HTTP (۳۰۱، ۳۰۲ و مانند آن) را دنبال می‌کند. اگر می‌خواهید به‌جای مقصد نهایی، خودِ پاسخ تغییر مسیر را پایش کنید این گزینه را فعال کنید.

#### اجازه گواهی‌های خودامضا

این گزینه را فعال کنید تا اعتبارسنجی گواهی TLS انجام نشود. وقتی سرور هدف از گواهی TLS خودامضا یا نامعتبر استفاده می‌کند مفید است (برای نمونه یک محیط آزمایشی داخلی).

#### گواهی کلاینت (mTLS)

اگر نقطه پایانی شما به احراز هویت TLS دوطرفه نیاز دارد، **استفاده از گواهی کلاینت (mTLS)** را فعال کنید و این‌ها را وارد کنید:

- **گواهی کلاینت (PEM)** — گواهی کلاینت با رمزگذاری PEM که باید ارائه شود.
- **کلید خصوصی کلاینت (PEM)** — کلید خصوصی متناظر با رمزگذاری PEM.
- **عبارت عبور کلید خصوصی کلاینت** _(اختیاری)_ — فقط اگر کلید خصوصی رمزگذاری شده باشد لازم است.

این معادل پرچم‌های `--cert` و `--key` در curl است:

```bash
curl --cert client.crt --key client.key https://api.example.com/health
```

برای مقادیر حساس، گواهی و کلید را به‌عنوان [اسرار مانیتور](/docs/monitor/monitor-secrets) ذخیره کنید و با `{{monitorSecrets.name}}` به آن‌ها ارجاع دهید. اسرار مانیتور سمت سرور تبدیل می‌شوند و مقادیر رندرشده هرگز در داشبورد ظاهر نمی‌شوند.

## معیارهای پایش

می‌توانید معیارهایی پیکربندی کنید که تعیین کنند API شما بر چه پایه‌ای آنلاین، تضعیف‌شده یا آفلاین در نظر گرفته شود:

- **کد وضعیت پاسخ** — بررسی اینکه کد وضعیت HTTP با مقادیر موردانتظار مطابقت دارد (برای نمونه ۲۰۰، ۲۰۱)
- **زمان پاسخ** — پایش اینکه زمان پاسخ از یک آستانه فراتر می‌رود یا نه
- **بدنه پاسخ** — بررسی اینکه بدنه پاسخ محتوای مشخصی را دارد یا با آن مطابقت می‌کند
- **هدرهای پاسخ** — راستی‌آزمایی اینکه هدرهای مشخصی وجود دارند یا با مقادیر موردانتظار مطابقت دارند
- **عبارت JavaScript** — عبارت‌های سفارشی برای ارزیابی پاسخ بنویسید. برای جزئیات [عبارت‌های JavaScript](/docs/monitor/javascript-expression) را ببینید.

### ارزیابی در یک بازه زمانی

**این معیار را در یک بازه زمانی ارزیابی کن** یک چک‌باکس جداگانه در فرم معیار است، نه یک شرط فیلتر. آن را روشن کنید تا به‌جای مقدار آخرین بررسی، پنجره‌ای از بررسی‌های گذشته مقایسه شود — با مقدار تجمیعی‌ای که زیر **ارزیابی** انتخاب می‌شود (میانگین، جمع، بیشینه، کمینه، همه مقادیر، هر مقدار) در پنجره‌ای که با **در (دقیقه) گذشته** تعیین می‌کنید.

**همه مقادیر** فقط وقتی مطابقت پیدا می‌کند که پنجره واقعاً با داده پوشیده شده باشد. مانیتوری که تازه ساخته شده، یا مانیتوری که ثبت بررسی‌هایش متوقف شده، تاریخچه کافی برای اظهارنظر درباره N دقیقه گذشته ندارد، بنابراین معیار به‌جای مطابقت با تنها داده موجود، منتظر می‌ماند. **هر مقدار** تنظیم مناسب برای «همان لحظه که یک بررسی از حد گذشت به من بگو» است و همچنان بی‌درنگ فعال می‌شود.

**اگر داده‌ای نبود** تعیین می‌کند تا وقتی پنجره نمی‌تواند پشتیبان معیار باشد چه اتفاقی بیفتد:

- **نادیده بگیر** (پیش‌فرض) — معیار مطابقت پیدا نمی‌کند. برای هشداردهی معمولی روی آستانه از این استفاده کنید.
- **فعال کن** — نبود داده را خودِ مشکل در نظر بگیر. برای بررسی‌های ضربان‌گونه که سکوت خودش شکست است از این استفاده کنید.
- **صفر در نظر بگیر** — پنجره را به‌عنوان یک صفر مقایسه کن. برای شمارنده‌هایی که «هیچ رویدادی» واقعاً یعنی صفر از این استفاده کنید.
