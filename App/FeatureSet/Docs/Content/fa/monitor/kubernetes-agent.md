# نصب عامل Kubernetes

عامل Kubernetes در OneUptime سنجه‌های خوشه، رویدادها، گزارش‌های پاد، **ردیابی‌های برنامه (‏HTTP/gRPC از راه eBPF)** و **سنجه‌های سطح سیستم‌عامل گره** را از خوشه Kubernetes شما جمع می‌کند و به OneUptime می‌فرستد. به‌صورت نمودار Helm توزیع می‌شود و با یک فرمان نصب می‌شود — ابزارگذاری خودکار eBPF به‌طور پیش‌فرض روشن است، پس بدون هیچ تغییری در کد، ردیابی‌های سطح سرویس و سنجه‌های RED می‌بینید. **نمودارهای شعله CPU پیوسته (پروفایلر eBPF)** هم در دسترس‌اند — هر وقت تله‌متری بیشتری خواستید با `--set profiling.enabled=true` واردشان شوید.

## شروع سریع

```bash
helm repo add oneuptime https://helm-chart.oneuptime.com
helm repo update

helm install oneuptime-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-kubernetes-agent \
  --create-namespace \
  --set oneuptime.url=https://oneuptime.com \
  --set oneuptime.apiKey=<YOUR_API_KEY> \
  --set clusterName=<A_UNIQUE_NAME_FOR_THIS_CLUSTER>
```

خوشه شما ظرف چند دقیقه در OneUptime پدیدار می‌شود.

## اختیاری — برچسب‌گذاری خودکار این خوشه با برچسب‌های پروژه

هر صفت منبعی که پیشوند `oneuptime.label.` بگیرد به یک Label پروژه ارتقا می‌یابد و به خوشه، سرویس‌ها و میزبان‌هایی که از این عامل منتشر می‌شوند می‌چسبد. الگو: `oneuptime.label.<dimension>=<value>` به برچسبی به نام `<dimension>:<value>` بدل می‌شود.

برچسب‌ها را هنگام نصب با `--set oneuptime.labels.<key>=<value>` بدهید:

```bash
helm install oneuptime-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-kubernetes-agent \
  --create-namespace \
  --set oneuptime.url=https://oneuptime.com \
  --set oneuptime.apiKey=<YOUR_API_KEY> \
  --set clusterName=prod \
  --set oneuptime.labels.team=payments \
  --set oneuptime.labels.env=production \
  --set oneuptime.labels.region=us-east-1
```

یا آن‌ها را در پرونده‌ای از مقادیر نگه دارید:

```yaml
# values.yaml
oneuptime:
  url: https://oneuptime.com
  apiKey: <YOUR_API_KEY>
  labels:
    team: payments
    env: production
    region: us-east-1
clusterName: prod
```

```bash
helm install oneuptime-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-kubernetes-agent --create-namespace \
  -f values.yaml
```

هر رکوردی که این عامل می‌فرستد — گزارش‌ها، سنجه‌ها، ردیابی‌ها، اسپن‌های خودکارابزارگذاری‌شده eBPF و پروفایل‌های CPU — در رابط کاربری OneUptime با برچسب‌های `team:payments`، `env:production` و `region:us-east-1` پدیدار می‌شود. برچسب‌ها بدون حساسیت به بزرگی و کوچکی حروف تطبیق داده می‌شوند، پس برچسب `Production`ای که پیش‌تر دستی ساخته شده به‌جای دوباره‌کاری از نو به کار می‌رود. برچسب‌هایی که دستی در رابط کاربری OneUptime افزوده شده‌اند هرگز به‌دست عامل برداشته نمی‌شوند.

## پیش‌تنظیم درست را برای خوشه‌تان برگزینید

توزیع‌های گوناگون Kubernetes محدودیت‌های گوناگونی دارند — به‌ویژه اینکه آیا بارهای کاری می‌توانند حجم‌های `hostPath` را سوار کنند یا نه. نمودار به‌جای اینکه شما را به خواندن مستندات امنیتی وا دارد، یک گزینه سطح‌بالا در معرض می‌گذارد: `preset`.

| پیش‌تنظیم             | برای                                                                          | جمع‌آوری گزارش                                  | یادداشت                                                                                                             |
| -------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `standard` (پیش‌فرض) | خودمدیریت، **EKS on EC2**، **GKE Standard**، **AKS**، minikube، kind، k3s | ‏DaemonSetای که `/var/log/pods` را از راه hostPath می‌خواند | کمترین سربار. hostPath روی این سکوها در دسترس است. |
| `gke-autopilot`      | **GKE Autopilot**                                                            | دنبال‌کننده API‏ Kubernetes (‏Deployment)             | ‏hostPath روی Autopilot مسدود است. زمینه امنیتی سخت‌شده‌ای تنظیم می‌کند که از استانداردهای امنیت پاد Autopilot می‌گذرد. |
| `eks-fargate`        | **EKS Fargate**                                                              | دنبال‌کننده API‏ Kubernetes (‏Deployment)             | همانند `gke-autopilot`. Fargate هم hostPath و هم DaemonSet را مسدود می‌کند.                                                   |

اگر مطمئن نیستید، `preset` را تنظیم‌نشده بگذارید — پیش‌فرض‌های `standard` را می‌گیرید. اگر خوشه‌تان نصب را با خطای سیاست امنیت پاد که به `hostPath` اشاره می‌کند رد کرد، به `gke-autopilot` (یا روی EKS Fargate به `eks-fargate`) جابه‌جا شوید و دوباره نصب کنید.

### نمونه‌ها

**‏GKE Standard، EKS on EC2، خودمدیریت یا AKS:**

```bash
helm install oneuptime-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-kubernetes-agent --create-namespace \
  --set oneuptime.url=https://oneuptime.com \
  --set oneuptime.apiKey=<YOUR_API_KEY> \
  --set clusterName=prod
```

**‏GKE Autopilot:**

```bash
helm install oneuptime-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-kubernetes-agent --create-namespace \
  --set oneuptime.url=https://oneuptime.com \
  --set oneuptime.apiKey=<YOUR_API_KEY> \
  --set clusterName=prod-gke-autopilot \
  --set preset=gke-autopilot
```

**‏EKS Fargate:**

```bash
helm install oneuptime-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-kubernetes-agent --create-namespace \
  --set oneuptime.url=https://oneuptime.com \
  --set oneuptime.apiKey=<YOUR_API_KEY> \
  --set clusterName=prod-eks-fargate \
  --set preset=eks-fargate
```

## دو حالت جمع‌آوری گزارش چه فرقی دارند

زیر پوسته، `preset` مقدار `logs.mode` را تنظیم می‌کند — و اگر بخواهید پیش‌فرض پیش‌تنظیم را بازنویسی کنید می‌توانید همان را مستقیم هم تنظیم کنید.

### حالت DaemonSet (`logs.mode: daemonset`)

یک DaemonSet به ازای هر گره یک پاد OpenTelemetry Collector اجرا می‌کند. پرونده‌های گزارش زیر `/var/log/pods/` را از راه حجمی hostPath دنبال می‌کند و از راه OTLP به جلو می‌فرستد.

- **مزیت‌ها:** کمترین سربار، مقیاس‌گیری خطی با گره‌ها، بی‌باری روی کارساز API‏ Kubernetes، رسیدگی به چرخش گزارش.
- **کاستی‌ها:** به hostPath نیاز دارد، به توانایی زمان‌بندی DaemonSet نیاز دارد — هر دو روی GKE Autopilot و EKS Fargate در دسترس نیستند.

### حالت API (`logs.mode: api`)

یک Deployment تک‌نسخه‌ای (تصویر `oneuptime/kubernetes-log-tailer`) از API‏ Kubernetes برای جاری کردن گزارش‌های کانتینر استفاده می‌کند — همان نقطه پایانی‌ای که `kubectl logs -f` به کار می‌برد. نه hostPath، نه دسترسی به میزبان، نه DaemonSet.

- **مزیت‌ها:** روی GKE Autopilot، EKS Fargate و هر خوشه‌ای که hostPath را مسدود می‌کند یا استاندارد امنیت پاد `restricted` را اعمال می‌کند کار می‌کند.
- **کاستی‌ها:** هر جریان کانتینری یک اتصال دیرزی به `kube-apiserver` است. در عمل یک نسخه به‌راحتی از پس چند هزار کانتینر برمی‌آید. برای خوشه‌های خیلی بزرگ، انتشارهای جداگانه را با قاعده‌های include دامنه‌دارشده به `podLogs` در `namespaceFilters.rules` تکه‌تکه کنید.

### کدام را باید به کار ببرید؟

اگر hostPath کار می‌کند، DaemonSet را به کار ببرید. هر جای دیگری، حالت API را. تنظیم `preset` درستش را برایتان برمی‌گزیند.

می‌توانید جمع‌آوری گزارش را به‌کل هم با `--set logs.enabled=false` از کار بیندازید و به‌جایش گزارش‌های برنامه را از راه SDKهای OpenTelemetry بفرستید. مستندات [OpenTelemetry](/docs/telemetry/open-telemetry) را ببینید.

### خوشه‌های چندسیستم‌عامله (استخرهای گره Windows)

هر تصویر عامل فقط Linux است، پس همه بارهای کاری عامل خودشان را به گره‌های Linux سنجاق می‌کنند (`kubernetes.io/os: linux`) — گره‌های Windows هرگز پاد عاملی اجرا نمی‌کنند. تله‌متری سطح خوشه درباره گره‌های Windows و پادهایشان (شرایط گره، فازهای پاد، رویدادهای Kubernetes، kube-state-metrics) همچنان جاری است، چون از API‏ Kubernetes می‌آید. آنچه گره‌های Windows ندارند جمع‌آوری محلیِ گره است: سنجه‌های میزبان، برداشت‌های kubelet/cAdvisor، ردیابی‌های eBPF، پروفایل‌گیری — و در حالت گزارش `daemonset`، گزارش‌های پاد.

برای جمع‌آوری گزارش از پادهای روی گره‌های Windows هم، حالت ترکیبی را فعال کنید:

```bash
helm upgrade oneuptime-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent --reuse-values \
  --set logs.windowsPods.enabled=true
```

این کار دنبال‌کننده گزارش API را در کنار DaemonSet اجرا می‌کند، محدود به پادهای روی گره‌های Windows. پادهای Linux همان دنبال کردن ارزان‌ترِ پرونده به‌صورت محلیِ گره را نگه می‌دارند، و دو جمع‌کننده پادها را بر پایه سیستم‌عامل گره افراز می‌کنند تا هیچ خط گزارشی دو بار فرستاده نشود. دو نکته:

- **نسخه تصویر دنبال‌کننده.** محدودیت «فقط Windows» در تصویر `kubernetes-log-tailer` جا دارد؛ تصویری قدیمی‌تر نادیده‌اش می‌گیرد و *هر* پادی را دنبال می‌کند و بی‌صدا گزارش هر پاد Linux را دو بار می‌فرستد. مقدار `logs.api.image.tag` را قدیمی‌تر از انتشار نمودار سنجاق نکنید، و اگر ممکن است گره‌ای تصویر `release` کهنه‌ای را انباشته باشد، برای ارتقا `--set logs.api.image.pullPolicy=Always` را بیفزایید.
- **پالایش شدت.** با تنظیم‌شدن `filters.logs.minSeverity`، خط‌هایی که شدت قابل‌تشخیصی ندارند در مسیر DaemonSet انداخته می‌شوند اما در مسیر API نگه داشته می‌شوند — [پالایش بر پایه شدت گزارش](/docs/telemetry/kubernetes-agent#filtering-by-log-severity) را ببینید. بنابراین پادهای Windows می‌توانند خط‌های بی‌کلیدواژه بیشتری از پادهای Linux بفرستند.

## ردیابی‌های برنامه و درخواست‌های HTTP از راه eBPF (به‌طور پیش‌فرض روشن)

نمودار DaemonSetای عرضه می‌کند که [ابزارگذاری eBPF در OpenTelemetry‏ (OBI)](https://opentelemetry.io/docs/zero-code/obi/) را روی هر گره اجرا می‌کند. OBI برنامه‌های eBPF را در هسته Linux بار می‌کند و ترافیک سطح سوکت را می‌پاید تا فراخوانی‌های HTTP/HTTPS، gRPC و SQL/Redis هر پادی روی آن گره را بازسازی کند — بی هیچ تغییری در کد، بی SDK، بی کانتینر جانبی. ترافیک گرفته‌شده به‌صورت ردیابی‌های OTLP و سنجه‌های درخواست/تأخیر مستقیم به OneUptime صادر می‌شود.

پس از نصب، سرویس‌هایتان ظرف یکی دو دقیقه زیر **Products → Traces** و در نقشه سرویس پدیدار می‌شوند، با `k8s.cluster.name`ای که روی `clusterName` شما تنظیم شده تا بتوانید بر پایه خوشه پالایه بگذارید.

### چه وقت خاموشش کنید

‏eBPF **به‌طور پیش‌فرض فعال** است. در این حالت‌ها باید از کارش بیندازید (`--set ebpf.enabled=false`):

- روی **GKE Autopilot** یا **EKS Fargate** نصب می‌کنید. آن سکوها پادهای ممتاز را مسدود می‌کنند، و OBI برای بار کردن برنامه‌های eBPF به حالت ممتاز نیاز دارد.
- گره‌هایتان هسته‌ای قدیمی‌تر از **Linux 5.8** بدون بازپورت‌های BTF اجرا می‌کنند. (توزیع‌های امروزی — Debian 11+، Ubuntu 20.10+، Fedora 34+، RHEL/Stream 9+ — مشکلی ندارند.)
- از پیش ردیابی‌ها را از راه SDK‏ OpenTelemetry از برنامه‌هایتان می‌فرستید و نسخه تکراری نمی‌خواهید.

### چه چیزی منتشر می‌شود

‏OBI چند خانواده سیگنال را از ترافیک گرفته‌شده استخراج می‌کند. همه به‌طور پیش‌فرض روشن‌اند؛ هر کدام را می‌توان جداگانه با `--set ebpf.features.<key>=false` از کار انداخت:

| سیگنال                                   | پیش‌فرض | چه می‌افزاید                                                                                                                                                  |
| --------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ebpf.features.httpMetrics`             | روشن      | سنجه‌های RED برای HTTP/gRPC — نرخ درخواست، بافت‌نگار تأخیر، شمار خطاها — به ازای هر سرویس.                                                                        |
| `ebpf.features.spanMetrics`             | روشن      | سنجه‌های کلیدخورده به صفت اسپن: اندازه درخواست، اندازه پاسخ، مدت‌زمان به تفکیک مسیر/عملیات.                                                         |
| `ebpf.features.serviceGraph`            | روشن      | سنجه‌های یال سرویس به سرویس (نرخ درخواست و تأخیر فراخوان → فراخوانده). به نقشه سرویس نیرو می‌دهد.                                                                            |
| `ebpf.features.hostMetrics`             | روشن      | ‏CPU و حافظه به ازای هر فرایند ابزارگذاری‌شده — شما را از اجرای پروفایلری جداگانه برای پرسش‌های پایه‌ای ظرفیت بی‌نیاز می‌کند.                                                                    |
| `ebpf.features.networkMetrics`          | روشن      | شمارنده‌های بایت و بسته جریان TCP/UDP بین پادها همراه فراداده k8s. هر جفت پادی را که با هم حرف می‌زنند آشکار می‌کند، از جمله آن‌هایی که پروتکل‌هایی اجرا می‌کنند که OBI نمی‌تواند تجزیه‌شان کند. |
| `ebpf.features.networkInterZoneMetrics` | خاموش     | گونه بین‌ناحیه‌ای سنجه‌های شبکه. کاردینالیتی را دو برابر می‌کند؛ فقط اگر واقعاً از زمان‌بندی ناحیه‌محور استفاده می‌کنید فعال کردنش می‌ارزد.                                   |
| `ebpf.features.tcpStats`                | روشن      | آمار TCP در سطح گره: بافت‌نگارهای RTT، شمار اتصال‌های ناموفق، بازارسال‌ها.                                                                            |

‏OBI می‌تواند زمینه ردیابی را از مرزهای سرویس هم بگذراند، تا وقتی پاد A درخواستی HTTP/gRPC به پاد B می‌فرستد، اسپن سمت پاد B به همان ردیابی فراخوان خروجی پاد A پیوند بخورد — بی هیچ تغییری در SDK هیچ‌کدام از دو برنامه. **این به‌طور پیش‌فرض خاموش است؛ با `--set ebpf.contextPropagation=true` واردش شوید.**

| گزینه                        | پیش‌فرض | توضیح                                                                                                                                                                                                       |
| ---------------------------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ebpf.contextPropagation`    | خاموش     | یک `traceparent`‏ W3C را در ترافیک خروجی تزریق می‌کند تا اسپن‌ها در سراسر سرویس‌ها پیوند بخورند. به‌طور پیش‌فرض خاموش — نخست هشدار پایین را بخوانید. نیاز هسته‌ای اضافه‌ای ندارد؛ هیچ نسخه هسته‌ای بی‌اثرش نمی‌کند.                       |
| `ebpf.contextPropagationMode`| headers | اینکه `traceparent` چگونه تزریق شود: `headers` (سرآیندهای درخواست HTTP/1.1، تنگ‌ترین)، `tcp` (گزینه TCP از راه Traffic Control در Linux) یا `all` (هر دو). فقط وقتی `contextPropagation` درست باشد خوانده می‌شود.                     |
| `ebpf.trackRequestHeaders`   | روشن      | ردیابی سرآیند درخواست در سمت هسته تا انتشار روی کارسازهای HTTP ساده (غیر Go، غیر TLS) هم کار کند. فقط وقتی `contextPropagation` درست باشد اثر می‌کند.                                                        |

> **⚠️ چرا این به‌طور پیش‌فرض خاموش است.** هر حالت انتشاری ترافیکی را که همین حالا در پرواز است دستکاری می‌کند. برای HTTP متن‌ساده، OBI بافر درخواست خروجی را در هسته گشاد می‌کند تا سرآیند اضافی جا شود؛ برای TLS و TCP خام، گزینه‌ای TCP را از قلابی در Traffic Control می‌افزاید و بسته و جمع کنترلی‌اش را بازنویسی می‌کند. آنگاه حسابداری بایت اتصال باید تصحیح شود، و وقتی آن تصحیح اشتباه باشد جریان به‌جای اینکه صرفاً اسپنی را از دست بدهد **از همگامی می‌افتد**. نشانه گزارش‌شده این است که انتقال‌ها از راه پراکسی L7ای مانند nginx، همین‌که پاسخ از نقطه‌ای بگذرد که بازنویسی روی چند قطعه پخش می‌شود (‏~۶۴ کیلوبایت)، وسط بدنه معلق می‌مانند و اتصال تا مهلت‌زدگی باز می‌ماند. درخواست‌های کوچک همچنان کار می‌کنند، پس بیشتر شبیه اشکالی در برنامه یا پراکسی به نظر می‌رسد تا اشکالی در عامل. **برای رد کردن این از سن هسته استفاده نکنید:** زیر هسته 5.17، ‏OBI به گونه‌های برنامه با پویش کران‌دار عقب می‌نشیند و ترافیک را دقیقاً به همان شکل بازنویسی می‌کند. اگر انتشار فعال باشد، فرض بگیرید ترافیک روی هر گره بازنویسی می‌شود.
>
> ردیابی‌ها، سنجه‌های RED و نقشه سرویس همه بدون آن کار می‌کنند — آنچه از دست می‌دهید فقط دوختن خودکار اسپن‌ها در مرز سرویس‌هاست، آن هم برای برنامه‌هایی که خودشان `traceparent` نمی‌فرستند. اگر آن پیوند را می‌خواهید، ابزارگذاری سرویس‌هایتان با SDK‏ OpenTelemetry سرآیند را در فضای کاربر منتشر می‌کند بی آنکه هسته چیزی بازنویسی کند، و راه امن‌تری است. اگر این را فعال می‌کنید، روی خوشه‌ای غیرتولیدی امتحانش کنید و پیش از گستراندن بیشترش، انتقال‌های بزرگ از راه پراکسی‌تان را تأیید کنید.

### همبستگی گزارش ↔ ردیابی (اختیاری)

**به‌طور پیش‌فرض خاموش.** وقتی فعال باشد، غنی‌ساز گزارش OBI یک uprobe به فراخوان سیستمی `write()` در هر فرایند ابزارگذاری‌شده می‌چسباند و:

- برای **گزارش‌های قالب JSON**: فیلدهای `trace_id` و `span_id` را در خط تزریق می‌کند (هر مقداری که از پیش در گزارش هست نگه داشته می‌شود). آنگاه DaemonSet‏ filelog آن فیلدها را به شکاف‌های بومی trace_id/span_id در LogRecord بلند می‌کند، پس کلیک روی اسپنی در نمای ردیابی شما را در OneUptime به گزارش‌هایش می‌برد — و کلیک روی خط گزارشی به ردیابی والدش.
- برای **گزارش‌های غیر JSON**: خط دست‌نخورده نگه داشته می‌شود — همچنان جمع می‌شود، فقط خودکار پیوند نمی‌خورد.

با این فعالش کنید:

```bash
helm upgrade oneuptime-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-kubernetes-agent --reset-then-reuse-values \
  --set ebpf.logToTraceCorrelation=true
```

| گزینه                        | پیش‌فرض                           | توضیح                                                                                                                                                                                                                                                                                                                                             |
| ---------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ebpf.logToTraceCorrelation` | `false`                          | غنی‌ساز گزارش OBI و بلند کردن trace_id در خط لوله filelog را فعال می‌کند. به‌طور پیش‌فرض خاموش — هشدار سازگاری پایین را ببینید.                                                                                                                                                                                                                            |
| `ebpf.logEnricher.services`  | `[{service: [{exe_path: "*"}]}]` | گزینشگر فرایند برای غنی‌ساز گزارش. هر مدخل یک گزینشگر [GlobAttributes](https://opentelemetry.io/docs/zero-code/obi/configure/options/#service-discovery) از OBI است — فیلدها شامل `exe_path`، `languages`، `k8s_pod_labels`، `k8s_pod_annotations`، `open_ports`، `cmd_args` هستند. وقتی می‌خواهید غنی‌سازی گزارش را به زیرمجموعه‌ای از بارهای کاری محدود کنید این را تنگ کنید. |

#### چرا به‌طور پیش‌فرض خاموش است — سازگاری با عامل APM

غنی‌ساز گزارش بافر stdout برنامه را **درون-فرایندی** بازنویسی می‌کند: وقتی فرایندی تطبیق‌یافته `write()` را فرا می‌خواند، پویشگر eBPF در OBI بایت‌های بافر اصلی را صفر می‌کند (پایین‌دست پالوده می‌شوند) و رونوشتی غنی‌شده را از راهی جداگانه دوباره منتشر می‌کند. آن بازنویسی درون-فرایندی بافر با عامل‌های APMای ناسازگار است که خودشان را از راه `LD_PRELOAD` تزریق می‌کنند و `write()` در libc را می‌پیچند:

| عامل APM           | کتابخانه              | اثر وقتی هر دو حاضر باشند                                                                                                                                                      |
| ------------------ | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Dynatrace OneAgent | `liboneagentproc.so` | ‏SIGSEGV برنامه (‏exit 139). پویشگر زنده‌بودنِ دیده‌بان Dynatrace شکست می‌خورد (‏`write()` خودش به پرونده PID از آستانه ۱۰ ثانیه می‌گذرد و می‌ایستد) و OneAgent وارد چرخه بازراه‌اندازی می‌شود. |
| New Relic          | `libnewrelic*.so`    | همان رده فروریزی.                                                                                                                                                              |
| AppDynamics        | `libappdynamics*.so` | همان رده فروریزی.                                                                                                                                                              |
| Datadog            | `libdd*.so`          | همان رده فروریزی.                                                                                                                                                              |
| Instana            | `libinstana*.so`     | همان رده فروریزی.                                                                                                                                                              |

**بارهای کاری ‎.NET بیش از همه در معرض‌اند** — عامل ‎.NET در Dynatrace همیشه از راه `LD_PRELOAD` تزریق می‌شود، و مقصد کنسول Microsoft.Extensions.Logging بی‌بافر است، پس هر خط گزارشی از مسیر مسابقه‌ایِ `write()` می‌گذرد. بارهای کاری Python و Go معمولاً بی‌اثر می‌مانند چون مدل‌های ورودی/خروجی‌شان روی همان مسیر کد نمی‌نشینند.

**اگر همبستگی گزارش↔ردیابی را در کنار یکی از این عامل‌های APM لازم دارید**، دامنه `logEnricher.services` را چنان تنگ کنید که غنی‌ساز از پادهایی که APM را اجرا می‌کنند بگذرد. گزینشگر log_enricher در OBI فیلد `exclude_services` ندارد (فقط گزینشگرهای مثبت)، پس باید بارهای کاری‌ای را که *می‌خواهید* غنی شوند فهرست کنید:

```yaml
ebpf:
  logToTraceCorrelation: true
  logEnricher:
    services:
      # Enrich only pods with the apm-agent=none label
      - service:
          - k8s_pod_labels:
              apm-agent: "none"
```

یا بر پایه زمان اجرا دامنه بگذارید — تزریق `LD_PRELOAD` در Dynatrace ‎.NET را نشانه گرفته، پس غنی کردن فقط Python/Go از این ناسازگاری می‌گریزد:

```yaml
ebpf:
  logToTraceCorrelation: true
  logEnricher:
    services:
      - service:
          - languages: "python,go,ruby,nodejs"
```

#### نکته‌های دیگر

- **گزارش‌ها باید JSON باشند تا `trace_id` پدیدار شود.** گزارشگرتان را به قالب‌بند JSON جابه‌جا کنید — `structlog`، `pino`، `winston`، `serilog`، `logback-json`، ‏klog با `--logging-format=json` و مانند این‌ها.
- **‏stdout بافرشده همبستگی را می‌شکند** چون فراخوان سیستمی `write()` روی نخی جز نخی که درخواست را رسیدگی کرده شلیک می‌شود. رفع‌های رایج:
  - **‏Python**: مقدار `PYTHONUNBUFFERED=1` را تنظیم کنید (زمان اجرا وقتی stdout یک TTY نباشد آن را بلوکی بافر می‌کند).
  - **‎.NET**: هنگام راه‌اندازی، `Console.SetOut(new StreamWriter(Console.OpenStandardOutput()) { AutoFlush = true })`. متد `AddConsole()` در Microsoft.Extensions.Logging و مقصدهای ناهمگام Serilog هم کار نمی‌کنند — به نویسنده کنسولی همگام جابه‌جا شوید (‏`WriteTo.Console()` پیش‌فرض Serilog خوب است).
- ‏Greenlet / gevent، ‏Tornado و دیگر زمان‌های اجرای ناهمگام سفارشی پوشش داده نمی‌شوند.

| گزینه                  | پیش‌فرض                                                   | توضیح                                                                                                               |
| ---------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `ebpf.enabled`         | `true`                                                   | کلید اصلی. برای گذشتن به‌کل از DaemonSet‏ eBPF روی `false` بگذارید.                                                 |

| `ebpf.excludeExePaths` | (پوسته‌ها، kubelet، runc، containerd، otelcol، خود OBI) | گلاب‌های کاماجدا که از آن‌ها گذشته شود.                                                                                            |

| `ebpf.printTraces`     | `false`                                                  | افزون بر صدور OTLP، اسپن‌ها را در stdout خود OBI چاپ می‌کند — برای وارسی گرفتن ترافیک هنگام نصب مفید است.              |
| `ebpf.resources.*`     | درخواست‌های `100m / 256Mi`، محدودیت‌های `1000m / 1Gi`            | برای خوشه‌های پرترافیک بالاترش ببرید.                                                                                                   |

برای بررسی اینکه OBI اجرا می‌شود و ترافیک می‌بیند:

```bash
kubectl get pods -n oneuptime-kubernetes-agent -l component=ebpf-instrument
kubectl logs -n oneuptime-kubernetes-agent -l component=ebpf-instrument --tail=200
```

## پروفایل‌گیری پیوسته CPU (به‌طور پیش‌فرض خاموش)

یک DaemonSet جداگانه [پروفایلر eBPF در OpenTelemetry](https://github.com/open-telemetry/opentelemetry-ebpf-profiler) را اجرا می‌کند — که به‌صورت تصویر `otel/opentelemetry-collector-ebpf-profiler` بسته‌بندی شده. این پروفایلر پشته‌های روی-CPU را با فراوانی ۱۹ هرتز در سراسر هر زمان اجرای پشتیبانی‌شده (‏Go، Java، ‎.NET، Python، Ruby، Node.js، PHP، Perl، C/C++، Rust) نمونه‌برداری می‌کند و پروفایل‌های OTLP را به OneUptime می‌فرستد، جایی که زیر **Products → Performance Profiles** و به‌صورت نمودارهای شعله پیوندخورده از تک‌تک اسپن‌های ردیابی پدیدار می‌شوند.

پروفایل‌گیری **به‌طور پیش‌فرض خاموش** است — از ابزارگذاری خودکار OBI سنگین‌تر است (‏CPU بیشتر به ازای هر گره، ردپای حافظه بزرگ‌تر) و هر خوشه‌ای نمودار شعله همیشه‌روشن نمی‌خواهد. وقتی تله‌متری غنی‌تری می‌خواهید فعالش کنید: `--set profiling.enabled=true`.

وقتی ابزارگذاری خودکار eBPF هم روشن باشد (‏`ebpf.enabled: true`، که پیش‌فرض است)، هر نمونه CPU از راه نگاشتی مشترک در bpffs با زمینه ردیابی OBI همبسته می‌شود — پس نمودارهای شعله trace_id/span_id را حمل می‌کنند و رابط کاربری OneUptime می‌تواند نمودار شعله‌ای به ازای هر اسپن نشانتان دهد.

نیازمندی‌ها:

- **هسته Linux 5.10 یا بالاتر** (کمی تازه‌تر از 5.8ای که OBI لازم دارد).
- پاد ممتاز با hostPID — همان محدودیت‌های DaemonSet ابزارگذاری خودکار eBPF. روی GKE Autopilot، ‏EKS Fargate یا دیگر محیط‌های قفل‌شده نمی‌تواند اجرا شود.

تنظیم دقیق:

| گزینه                         | پیش‌فرض                | توضیح                                                                                                                              |
| ----------------------------- | --------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `profiling.enabled`           | `false`               | کلید اصلی. به‌طور پیش‌فرض خاموش؛ برای نمودارهای شعله CPU پیوسته واردش شوید.                                                            |
| `profiling.image.tag`         | `0.152.0`             | برچسب تصویر `otel/opentelemetry-collector-ebpf-profiler`. پروفایلر پیش از 1.0 است؛ به نسخه‌ای شناخته‌شده و سالم سنجاق کنید.                     |
| `profiling.samplesPerSecond`  | `19`                  | فراوانی نمونه‌برداری بر حسب هرتز. پیش‌فرض بالادست؛ از هم‌نامیِ تصادفی با فراوانی‌های رایج زمان‌سنج می‌گریزد.                           |
| `profiling.offCpuThreshold`   | `0`                   | بازه (۰ تا ۱] پروفایل‌گیری خارج-از-CPU را فعال می‌کند — کشمکش قفل و ورودی/خروجی مسدودکننده را تشخیص می‌دهد. به‌طور پیش‌فرض خاموش چون سربار نقطه‌ردیابی می‌افزاید. |
| `profiling.tracers`           | `""` _(همه زمان‌های اجرا)_ | فهرست کاماجدای ردیاب‌های زبانی که بار شوند.                                                                                 |
| `profiling.obiProcessContext` | `true`                | نمونه‌ها را با زمینه ردیابی OBI همبسته می‌کند تا ردیابی ↔ پروفایل به هم پیوند بخورند.                                                          |

## جمع‌آوری داده‌های دیگر (سنجه‌های میزبان، اشباع، cAdvisor، KSM، گزارش‌های ممیزی، CSI، CoreDNS)

نمودار می‌تواند این‌ها را هم جمع کند:

| `<key>.enabled`                   | پیش‌فرض | چه می‌افزاید                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| --------------------------------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `hostMetrics`                     | روشن      | سنجه‌های سیستم‌عامل به ازای هر گره از `/proc` و `/sys` — ژرفای صف ورودی/خروجی دیسک، مصرف آی‌نود سامانه‌پرونده، شمارنده‌های خطای NIC، آمار صفحه‌بندی، بار میانگین. درون DaemonSet جمع‌کننده گزارش جا دارد (بی پاد اضافه).                                                                                                                                                                                                                 |
| `kubeletstats.utilizationMetrics` | روشن      | سنجه‌های اشباع — CPU/حافظه کانتینر و پاد بیان‌شده به‌صورت درصدی از درخواست و محدودیت. هشت خانواده سنجه مشتق‌شده که به مانیتورهای «CPU/Memory vs Request» و «CPU/Memory vs Limit» نیرو می‌دهند. همان برداشت گیرنده `kubeletstats` موجود، بی پاد اضافه. وقتی پادی درخواست/محدودیتی تنظیم نکرده باشد همیشه ۰ است.                                                                                                                                                            |

| `cadvisor`                        | روشن      | نقطه پایانی `/metrics/cadvisor` در kubelet را از پاد DaemonSet هر گره برداشت می‌کند، برای آن سنجه‌های کانتینری که `kubeletstats` ترجمه‌شان نمی‌کند: خفگی CFS (`container_cpu_cfs_throttled_seconds_total`، `container_cpu_cfs_periods_total`) و رویدادهای کشتن OOM (`container_oom_events_total`). فهرست مجاز بازبرچسب‌گذاری هر چیز دیگری را در گیرنده می‌اندازد تا کاردینالیتی کران‌دار بماند.                                                        |
| `kubeStateMetrics`                | خاموش     | سنجه‌های وضعیت خوشه را از kube-state-metrics می‌کشد: فازهای پاد (‏Pending / Terminating)، وضعیت زمان‌بندی پاد (پادهایی که زمان‌بندی نمی‌شوند)، دلیل‌های انتظار کانتینر (‏CrashLoopBackOff، ImagePullBackOff) و مصرف سهمیه منابع. حالت `mode: bundled` (پیش‌فرض) یک Deployment کوچک KSM برایتان مستقر می‌کند؛ `mode: external` یک KSM موجود را از راه `endpoint` برداشت می‌کند. به‌طور پیش‌فرض خاموش است چون حالت همراه یک Deployment به ردپای نمودار می‌افزاید. |
| `auditLogs`                       | خاموش     | ‏`/var/log/kubernetes/audit.log` را از میزبان دنبال می‌کند. هر درخواست API‏ Kubernetes را می‌گیرد — چه کسی با کدام منبع چه کرد. فقط خوشه‌های خودمدیریت — K8s مدیریت‌شده (‏EKS، GKE، AKS، DOKS) گزارش‌های ممیزی را به مقصد ارائه‌دهنده ابری می‌برد.                                                                                                                                                                                                                             |

| `coreDns`                         | خاموش     | سرویس CoreDNS خوشه را روی `:9153/metrics` برداشت می‌کند. نرخ پرس‌وجو، تأخیر، نرخ اصابت انباره و شمار خطاها را آشکار می‌کند — مقصران رایج تأخیر P99.                                                                                                                                                                                                                                                                                                     |

## ارتقا

```bash
helm repo update
helm upgrade oneuptime-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-kubernetes-agent \
  --reuse-values
```

پرچم `--reuse-values` پیکربندی موجودتان را نگه می‌دارد؛ هر بازنویسی تازه‌ای با `--set` را روی آن بدهید.

> **حواستان باشد: `--reuse-values` پیش‌فرض‌های تازه نمودار را ادغام نمی‌کند.** ‏Helm مقادیری را که پیش‌تر رندر کرده‌اید عیناً دوباره به کار می‌برد — پس هر فیلد سطح‌بالای تازه‌ای که در نسخه تازه‌تری از نمودار افزوده شده (مثلاً `profiling.*`، `ebpf.features.*`) روی انتشار موجود شما تنظیم‌نشده می‌ماند و قالب چنان رندر می‌شود که انگار از کارش انداخته‌اید.
>
> **‏Helm 3.14 و بالاتر** — به `--reset-then-reuse-values` جابه‌جا شوید. این پرچم پیش‌فرض‌های نمودار را برای کلیدهایی که بازنویسی نکرده‌اید دوباره می‌خواند:
>
> ```bash
> helm upgrade oneuptime-agent oneuptime/kubernetes-agent \
>   --namespace oneuptime-kubernetes-agent \
>   --reset-then-reuse-values
> ```
>
> **‏Helm 3.13 و پایین‌تر** — `--reuse-values` را بیندازید و پرچم‌های اصلی `--set` خود (یا `-f values.yaml`) را صریح بدهید. پیش‌فرض‌های تازه نمودار برای هر چیزی که بازنویسی نکنید اعمال می‌شوند.
>
> اگر پادهای قابلیتی تازه (مثلاً `kubernetes-agent-profiling-*`) پس از ارتقا پدیدار نشدند، تقریباً همیشه دلیلش همین است. فرمان `helm get values <release>` نشان می‌دهد Helm واقعاً چه چیزی در دست دارد — فیلدهایی که در خروجی نیستند یعنی پیش‌فرض‌ها برایشان ادغام نشده است.

## حذف نصب

```bash
helm uninstall oneuptime-agent --namespace oneuptime-kubernetes-agent
kubectl delete namespace oneuptime-kubernetes-agent
```

## رفع اشکال

### نصب با «hostPath volumes are not allowed» شکست می‌خورد

خوشه شما hostPath را مسدود می‌کند. به پیش‌تنظیمی با حالت API جابه‌جا شوید:

```bash
helm upgrade oneuptime-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-kubernetes-agent \
  --reuse-values \
  --set preset=gke-autopilot   # or eks-fargate
```

### پادهای عامل روی گره‌های Windows در `ImagePullBackOff` گیر کرده‌اند

نسخه‌های قدیمی‌تر نمودار DaemonSetهای عامل را روی گره‌های Windows زمان‌بندی می‌کردند، جایی که تصویرهای فقط-Linux هرگز کشیده نمی‌شوند. نمودارهای کنونی هر بار کاری را به گره‌های Linux سنجاق می‌کنند — `helm upgrade` را اجرا کنید و پادهای گیرکرده خودکار برداشته می‌شوند. از گره‌های Windows عمداً گذشته می‌شود؛ برای جمع‌آوری گزارش از پادهایی که روی آن‌ها اجرا می‌شوند، [خوشه‌های چندسیستم‌عامله](#خوشههای-چندسیستمعامله-استخرهای-گره-windows) را ببینید.

### هیچ گزارشی در OneUptime پدیدار نمی‌شود

پادهای عامل را بررسی کنید:

```bash
kubectl get pods -n oneuptime-kubernetes-agent
kubectl logs -n oneuptime-kubernetes-agent -l app.kubernetes.io/part-of=oneuptime --tail=200
```

در حالت API، پاد دنبال‌کننده گزارش `/healthz` را روی درگاه ۱۳۱۳۳ در معرض می‌گذارد — برای گرفتن عکسی لحظه‌ای از وضعیت صدور، از راه `kubectl port-forward` به آن بزنید.

### پاد DaemonSet‏ eBPF در `CrashLoopBackOff` است یا راه نمی‌افتد

گزارش‌های پاد OBI را بررسی کنید:

```bash
kubectl logs -n oneuptime-kubernetes-agent -l component=ebpf-instrument --tail=200
```

دلیل‌های رایج:

- **هسته خیلی قدیمی است یا BTF ندارد.** ‏OBI به Linux 5.8 یا بالاتر همراه BTF نیاز دارد. روی گره‌ای با `uname -r` بررسی کنید. اگر نمی‌توانید ارتقا دهید، eBPF را از کار بیندازید: `--set ebpf.enabled=false`.
- **پادهای ممتاز مسدودند.** برخی خوشه‌ها حتی بیرون از Autopilot/Fargate هم پادهای ممتاز را رد می‌کنند. eBPF را از کار بیندازید.
- **هیچ ردیابی‌ای در داشبورد نیست ولی OBI اجرا می‌شود.** مقدار `--set ebpf.printTraces=true` را بگذارید و stdout ‏OBI را بررسی کنید — اگر آنجا اسپن می‌بینید، مشکل تحویل OTLP است (‏`OTEL_EXPORTER_OTLP_ENDPOINT` و نشانی/کلید API‏ OneUptime خود را بررسی کنید). اگر اسپنی نمی‌بینید، شاید تمام ترافیکی که OBI می‌پاید با کتابخانه TLSای رمزگذاری شده که OBI نمی‌تواند رهگیری‌اش کند (مثلاً پیاده‌سازی TLSای که ایستا پیوند خورده و OBI نمی‌شناسدش).

### خوشه‌ام پادهای بیش از اندازه‌ای برای یک نسخه دنبال‌کننده گزارش دارد (فقط حالت API)

با تکه‌تکه کردن فضاهای نام افقی مقیاس بگیرید. به ازای هر گروه فضای‌نام یک بار مستقر کنید:

```bash
helm install oneuptime-agent-ns-a oneuptime/kubernetes-agent \
  --set preset=gke-autopilot \
  --set-json 'namespaceFilters.rules=[{"action":"include","namespaces":["app-a","app-b"],"scopes":["podLogs"]}]' \
  ...
```

در غیر این صورت `logs.api.replicas` را بالا ببرید — اما توجه کنید که هر نسخه همه فضاهای نام مجاز را پردازش می‌کند، پس برای زدودن تکرار همچنان به تکه‌تکه کردن فضای‌نام نیاز دارید.
