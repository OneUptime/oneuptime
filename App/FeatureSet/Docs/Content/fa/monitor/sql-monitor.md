# مانیتور پرس‌وجوی SQL

مانیتور پرس‌وجوی SQL روی یک زمان‌بندی از یک پروب، پرس‌وجویی فقط‌خواندنی SQL اجرا می‌کند و بر نتیجه هشدار می‌دهد — شمار سطرهای بازگشتی، مقداری اسکالر، اینکه پرس‌وجو چقدر طول کشید، یا خطای پرس‌وجو. برای مورد کاربرد «پرس‌وجویی اجرا کن و حادثه‌ای باز کن» ساخته شده است، برای نمونه هشدار وقتی شمار سفارش‌های لغوشده در پنج دقیقه گذشته جهش می‌کند، وقتی جدول صفی خیلی بزرگ می‌شود، یا وقتی سطری حیاتی ناپدید می‌شود.

چون پرس‌وجو از پروبی درون شبکه شما اجرا می‌شود، OneUptime هرگز به اتصال مستقیم به پایگاه داده شما نیاز ندارد، و مجموعه نتیجه کامل هرگز از پروب بیرون نمی‌رود — فقط فرافکنی کوچک و کران‌دار از نتیجه گزارش می‌شود.

## پایگاه‌های داده پشتیبانی‌شده

مانیتور پرس‌وجوی SQL از موتورهای پایگاه داده زیر پشتیبانی می‌کند:

- **PostgreSQL** (درگاه پیش‌فرض `5432`)
- **MySQL** (درگاه پیش‌فرض `3306`)
- **Microsoft SQL Server** (درگاه پیش‌فرض `1433`)

موتورهای سازگار با MySQL و سازگار با PostgreSQL که همان پروتکل سیم و گویش SQL را حرف می‌زنند معمولاً هم کار می‌کنند، اما فقط سه موتور بالا رسماً آزموده شده‌اند.

## چگونه کار می‌کند

در هر بررسی، پروب به پایگاه داده شما وصل می‌شود، پرس‌وجویتان را در بافتاری فقط‌خواندنی اجرا می‌کند، حداکثر شمار کران‌داری از سطرها را بازمی‌خواند و فرافکنی فشرده‌ای به OneUptime گزارش می‌دهد. سپس معیارهای مانیتور شما بر پایه آن فرافکنی سنجیده می‌شوند.

پروب فقط این‌ها را گزارش می‌دهد:

- **Row Count** — شمار سطرهایی که پرس‌وجو برگرداند (کران‌دار به محدودیت Max Rows).
- **Scalar Value** — نخستین ستون نخستین سطر. این مقدار طبیعی برای پرس‌وجویی به سبک `SELECT COUNT(*)` است.
- **First Row** — نخستین سطر به‌صورت مجموعه‌ای از جفت‌های ستون/مقدار، که برای زمینه در خلاصه بررسی نشان داده می‌شود.
- **Execution Time** — اینکه پرس‌وجو چقدر طول کشید، بر حسب میلی‌ثانیه.
- **Query Error** — پیام خطای پاک‌سازی‌شده در صورت شکست پرس‌وجو.

مجموعه نتیجه کامل هرگز به OneUptime فرستاده نمی‌شود، پس داده مشتری در انباره OneUptime تکثیر نمی‌شود.

## مدل امنیتی

اجرای پرس‌وجویی که مشتری فراهم کرده روی پایگاه داده‌ای تولیدی حساس است، پس مانیتور پرس‌وجوی SQL از پایه فقط‌خواندنی است و چند کنترل را لایه‌بندی می‌کند:

- **کاربر پایگاه داده با کمترین امتیاز (کنترل اصلی).** همیشه باید با کاربر پایگاه داده اختصاصی و فقط‌خواندنی وصل شوید که فقط به جدول‌هایی که پرس‌وجو لازم دارد دسترسی دارد. این مهم‌ترین کنترل است — [ساخت کاربر فقط‌خواندنی](#create-a-read-only-user) در پایین را ببینید.
- **اجرای فقط‌خواندنی.** روی PostgreSQL و MySQL پروب تراکنشی `READ ONLY` باز می‌کند، که هر نوشتنی را (از جمله CTEهای نوشتنی) صرف‌نظر از متن پرس‌وجو رد می‌کند. روی Microsoft SQL Server، که تراکنش فقط‌خواندنی ندارد، پروب درون تراکنشی اجرا می‌کند که همیشه برگردانده می‌شود.
- **پرس‌وجوهای تک‌دستوری و در فهرست مجاز.** پرس‌وجو باید یک دستور تنها باشد که با `SELECT`، `WITH`، `VALUES` یا `TABLE` آغاز شود. دستورهای روی هم انباشته (`SELECT 1; DROP TABLE …`) و نوشتن/DDL پیش از وصل شدن پروب رد می‌شوند. بررسی از توضیح‌ها و ثابت‌های رشته‌ای آگاه است، پس کلیدواژه‌ای پنهان در توضیح یا رشته از آن نمی‌گریزد.
- **مهلت دستور.** هر پرس‌وجو محدودیت زمانی سختی دارد. پرس‌وجویی که خیلی طول بکشد لغو می‌شود.
- **سطرهای کران‌دار.** فقط تا Max Rows (به‌علاوه یکی، برای تشخیص کوتاه شدن) سطر بازخوانده می‌شود، که حافظه پروب و اندازه محموله را سقف می‌گذارد.
- **پاک‌سازی اعتبارنامه.** خطاهای پایگاه داده پیش از ذخیره پاک‌سازی می‌شوند — گذرواژه و هر رشته اتصالی پاک می‌شوند، پس اعتبارنامه‌ها هرگز به پیام‌های خطا درز نمی‌کنند.

## پیش‌نیازها

- یک **پروب** با دسترسی شبکه به میزبان و درگاه پایگاه داده شما. این می‌تواند پروبی میزبانی‌شده توسط OneUptime باشد (اگر پایگاه داده شما از اینترنت دست‌یافتنی است) یا پروبی خودمیزبان که درون شبکه شما اجرا می‌شود. برای نحوه نصب پروب سفارشی، مستندات پروب را ببینید.
- یک **کاربر فقط‌خواندنی پایگاه داده** و جزئیات اتصال (میزبان، درگاه، نام پایگاه داده، نام کاربری، گذرواژه)، یا هویتی فقط‌خواندنی از ویندوز/دامنه هنگام استفاده از احراز هویت یکپارچه SQL Server.

## پیکربندی

مانیتور تازه‌ای بسازید و نوع مانیتور را **SQL Query** برگزینید، سپس جزئیات اتصال را پر کنید:

- **Database Type** — ‏PostgreSQL، ‏MySQL یا Microsoft SQL Server. برگزیدن نوع، درگاه پیش‌فرض را تنظیم می‌کند.
- **Host** — میزبان پایگاه داده که از پروب دست‌یافتنی است (برای نمونه `db.internal`).
- **Port** — درگاه پایگاه داده.
- **Database Name** — پایگاه داده‌ای که پرس‌وجو روی آن اجرا می‌شود.
- **Use Windows Integrated Authentication** — فقط Microsoft SQL Server. به‌جای نام کاربری و گذرواژه SQL، با حسابی که پروب را اجرا می‌کند احراز هویت کنید. [احراز هویت یکپارچه ویندوز](#windows-integrated-authentication) را ببینید.
- **Username** — کاربر فقط‌خواندنی پایگاه داده با کمترین امتیاز.
- **Password** — گذرواژه پایگاه داده. اکیداً توصیه می‌کنیم به‌جای تایپ گذرواژه به‌صورت متن ساده، با `{{monitorSecrets.name}}` به یک [راز مانیتور](/docs/monitor/monitor-secrets) ارجاع دهید (پایین‌تر را ببینید).
- **SQL Query** — پرس‌وجوی فقط‌خواندنی‌ای که اجرا می‌شود ([نوشتن پرس‌وجو](#writing-the-query) را ببینید).
- **Use SSL/TLS** — برای اتصال روی TLS فعالش کنید. وقتی فعال باشد، اگر پایگاه داده گواهی خودامضا به کار می‌برد می‌توانید **Verify server certificate** را خاموش کنید.

### احراز هویت یکپارچه ویندوز

برای Microsoft SQL Server، گزینه **Use Windows Integrated Authentication** را فعال کنید تا اتصالی مورد اعتماد با هویت فرایند پروب باز شود. فیلدهای Username و Password در این حالت نادیده گرفته می‌شوند و به راه‌انداز داده نمی‌شوند. چون پروب به هویتی نیاز دارد که دامنه شما به آن اعتماد دارد، برای این حالت احراز هویت از پروبی خودمیزبان استفاده کنید.

- **پروب‌های ویندوزی:** سرویس پروب را با حساب دامنه‌ای اجرا کنید که ورودی فقط‌خواندنی به SQL Server دارد.
- **پروب‌های Linux یا macOS:** Kerberos را برای دامنه SQL Server پیکربندی کنید و به فرایند پروب بلیتی معتبر بدهید (برای نمونه از راه یک keytab). ایمیج رسمی پروب Linux شامل Microsoft ODBC Driver 18، ‏unixODBC و کلاینت Kerberos است. پیکربندی Kerberos و حافظه نهان بلیت را درون کانتینر سوار کنید، برای فرایند پروب خواندنی‌شان کنید، و اگر جایشان غیرپیش‌فرض است `KRB5_CONFIG` یا `KRB5CCNAME` را تنظیم کنید.

پروب به Microsoft ODBC Driver برای SQL Server نصب‌شده روی میزبانی که اجرایش می‌کند نیاز دارد. ایمیج رسمی پروب **ODBC Driver 18** را همراه دارد. وقتی پروبی خودمیزبان یا سفارشی اجرا می‌کنید، پروب به‌طور خودکار تازه‌ترین `ODBC Driver N for SQL Server` ثبت‌شده روی میزبان را تشخیص می‌دهد و به کار می‌برد (برای نمونه Driver 17 اگر همان نصب است) — لازم نیست دقیقاً Driver 18 داشته باشید. برای سنجاق کردن راه‌اندازی مشخص، متغیر محیطی `SQL_SERVER_ODBC_DRIVER` را روی پروب به نام دقیق راه‌انداز تنظیم کنید (برای نمونه `ODBC Driver 17 for SQL Server`).

‏SQL Server باید نام اصلی سرویس `MSSQLSvc` مناسبی داشته باشد، ساعت پروب و کنترلر دامنه باید همگام باشند، و پروب باید SQL Server را با نام میزبانی که آن نام اصلی سرویس پوشش می‌دهد تفکیک و به آن دسترسی پیدا کند. فقط دسترسی‌های پایگاه داده‌ای را که پرس‌وجوی مانیتورینگ لازم دارد به هویت مورد اعتماد اعطا کنید.

### گزینه‌های پیشرفته

- **Connection Timeout (ms)** — چقدر برای برقراری اتصال منتظر بماند. پیش‌فرض `10000`، بیشینه `30000`.
- **Statement Timeout (ms)** — سقف سخت اینکه پرس‌وجو چقدر می‌تواند اجرا شود. پیش‌فرض `15000`، بیشینه `60000`.
- **Max Rows** — کران بالای سطرهایی که از پایگاه داده بازخوانده می‌شوند. پیش‌فرض `100`، بیشینه `1000`.

## نوشتن پرس‌وجو

پرس‌وجو باید **یک دستور فقط‌خواندنی تنها** باشد. باید با یکی از `SELECT`، `WITH`، `VALUES` یا `TABLE` آغاز شود. یک نقطه‌ویرگول پایانی مجاز است؛ چند دستور نه.

پرس‌وجوها را ارزان و خوش‌دامنه نگه دارید — در هر بررسی اجرا می‌شوند، پس ستون‌های نمایه‌دار و پنجره‌های زمانی تنگ را ترجیح دهید.

```sql
-- Count recent cancellations (PostgreSQL)
SELECT COUNT(*) AS cancelled
FROM orders
WHERE status = 'CANCELLED'
  AND created_at > NOW() - INTERVAL '5 minutes';
```

```sql
-- The same idea on MySQL
SELECT COUNT(*) AS cancelled
FROM orders
WHERE status = 'CANCELLED'
  AND created_at > NOW() - INTERVAL 5 MINUTE;
```

```sql
-- The same idea on Microsoft SQL Server
SELECT COUNT(*) AS cancelled
FROM orders
WHERE status = 'CANCELLED'
  AND created_at > DATEADD(minute, -5, GETDATE());
```

برای پرس‌وجویی به سبک `COUNT(*)`، شمار هم به‌عنوان **Row Count** در دسترس است (که `1` است، چون یک سطر برمی‌گردد) و هم به‌عنوان **Scalar Value** (خودِ شمار، از نخستین ستون). برای هشدار بر «چند تا»، با **Scalar Value** مقایسه کنید.

## استفاده از یک راز مانیتور برای گذرواژه

تا گذرواژه پایگاه داده هرگز به‌صورت متن ساده روی مانیتور ذخیره نشود، یک [راز مانیتور](/docs/monitor/monitor-secrets) بسازید و از فیلد Password به آن ارجاع دهید:

1. به داشبورد OneUptime → Monitors → Settings → Secrets → Create Monitor Secret بروید.
2. رازی بسازید (برای نمونه `dbPassword`) و به این مانیتور دسترسی به آن بدهید.
3. در فیلد Password مانیتور، `{{monitorSecrets.dbPassword}}` را وارد کنید.

‏OneUptime پیش از سپردن پیکربندی به پروب، راز را سمت کارساز تفکیک می‌کند. OneUptime هرگز این اسرار را برایتان نمی‌سازد — ارجاع دادن به یکی انتخاب شماست.

## برپا کردن معیارها

معیارهایی بیفزایید تا تصمیم بگیرد مانیتور کی آنلاین، تنزل‌یافته یا آفلاین در نظر گرفته شود. بررسی‌های زیر برای مانیتور پرس‌وجوی SQL در دسترس‌اند:

- **SQL Is Online** — اینکه آیا پایگاه داده دست‌یافتنی بود و پرس‌وجو موفق شد.
- **SQL Query Row Count** — شمار سطرهای بازگشتی. با عملگرهایی مانند بزرگ‌تر از، کوچک‌تر از یا برابر با مقایسه کنید.
- **SQL Query Scalar Value** — نخستین ستون نخستین سطر. وقتی هر دو سو عددی به نظر برسند عددی مقایسه می‌شود، وگرنه به‌صورت رشته. این بررسی‌ای است که برای پرس‌وجوهای به سبک `COUNT(*)` به کار می‌برید.
- **SQL Query Execution Time (in ms)** — اینکه پرس‌وجو چقدر طول کشید. برای گرفتن پایگاه داده‌ای کند مفید است.
- **SQL Query Error** — پیام خطای پرس‌وجو. وقتی خالی است (یا نیست)، یا با رشته‌ای مشخص می‌خواند هشدار بدهید.
- **JavaScript Expression** — برای کنترل کامل، عبارتی سفارشی از JavaScript را ارزیابی کنید. [عبارت‌های JavaScript](/docs/monitor/javascript-expression) را ببینید.

### نمونه: هشدار وقتی لغوها جهش می‌کنند

با استفاده از پرس‌وجوی بالا:

- **معیار: تنزل‌یافته** — `SQL Query Scalar Value` بزرگ‌تر از `10` است.
- **معیار: آفلاین** — `SQL Query Scalar Value` بزرگ‌تر از `50` است، یا `SQL Is Online` برابر `false` است.

سیاست کشیکی را به معیارها پیوست کنید تا آدم‌های درست فراخوانده شوند.

## ساخت یک کاربر فقط‌خواندنی

همیشه با کاربری فقط‌خواندنی و اختصاصی وصل شوید. نمونه‌ها:

```sql
-- PostgreSQL
CREATE USER oneuptime_ro WITH PASSWORD 'a-strong-password';
GRANT CONNECT ON DATABASE orders TO oneuptime_ro;
GRANT USAGE ON SCHEMA public TO oneuptime_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO oneuptime_ro;
-- Include tables created in the future:
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO oneuptime_ro;
```

```sql
-- MySQL
CREATE USER 'oneuptime_ro'@'%' IDENTIFIED BY 'a-strong-password';
GRANT SELECT ON orders.* TO 'oneuptime_ro'@'%';
FLUSH PRIVILEGES;
```

```sql
-- Microsoft SQL Server
CREATE LOGIN oneuptime_ro WITH PASSWORD = 'a-strong-password';
USE orders;
CREATE USER oneuptime_ro FOR LOGIN oneuptime_ro;
ALTER ROLE db_datareader ADD MEMBER oneuptime_ro;
```

## چیزهایی که باید در نظر بگیرید

- پرس‌وجو در هر بررسی اجرا می‌شود، پس ارزان نگهش دارید. از نمایه‌ها و پنجره‌های زمانی تنگ استفاده کنید و به Statement Timeout به‌عنوان پشتوانه تکیه کنید.
- فقط شمار سطر، نخستین خانه (اسکالر) و نخستین سطر گزارش می‌شوند — پرس‌وجویتان را طوری طراحی کنید که مقداری که می‌خواهید بر آن هشدار بدهید نخستین ستون باشد.
- اگر نتیجه به دلیل گذشتن از Max Rows کوتاه شود، خلاصه بررسی آن را سقف‌خورده نشانه‌گذاری می‌کند. فقط اگر لازم دارید Max Rows را بالا ببرید؛ مجموعه‌های نتیجه بزرگ‌تر روی پروب حافظه بیشتری هزینه دارند.
- نوشتن و DDL همیشه رد می‌شوند. اگر لازم دارید مسیر نوشتنی را بیازمایید، این مانیتور برای آن نیست.
- به‌جای گذرواژه متن ساده، راز مانیتور را ترجیح دهید تا اعتبارنامه در حالت سکون رمزگذاری‌شده بماند.
