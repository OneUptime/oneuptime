# مانیتور صفحه وضعیت بیرونی

مانیتورینگ صفحه وضعیت بیرونی به شما امکان می‌دهد صفحه‌های وضعیت شخص ثالث را زیر نظر بگیرید و وقتی سرویس‌هایی که به آن‌ها وابسته‌اید دچار قطعی یا کارایی تنزل‌یافته می‌شوند هشدار بگیرید. OneUptime دوره‌ای صفحه‌های وضعیت بیرونی (مانند AWS، GCP، Azure، GitHub، OpenAI، Anthropic و بیشتر) را بررسی می‌کند و وضعیتشان را می‌سنجد.

## نمای کلی

مانیتورهای صفحه وضعیت بیرونی سلامت سرویس‌هایی را که به آن‌ها تکیه می‌کنید با پرس‌وجو از صفحه‌های وضعیت عمومی‌شان بررسی می‌کنند. این به شما امکان می‌دهد:

- دسترس‌پذیری سرویس‌های شخص ثالثی را که برنامه‌تان به آن‌ها وابسته است زیر نظر بگیرید
- وقتی ارائه‌دهندگان بالادستی دچار قطعی می‌شوند هشدار بگیرید
- وضعیت مؤلفه‌های منفرد را ردیابی کنید (برای نمونه، «AWS EC2 us-east-1»)
- مانیتورینگ را به یک گروه مؤلفه محدود کنید (برای نمونه، فقط «APIs» در OpenAI)، تا حادثه‌های نامرتبط در جاهای دیگر صفحه مانیتور شما را نلغزانند
- کارایی تنزل‌یافته را پیش از اثرگذاری بر کاربرانتان تشخیص دهید
- حادثه‌های خودتان را با مشکل‌های ارائه‌دهنده بالادستی هم‌بسته کنید

## ارائه‌دهندگان پشتیبانی‌شده

‏OneUptime از مانیتورینگ صفحه‌های وضعیت از راه روش‌های زیر پشتیبانی می‌کند:

| نوع ارائه‌دهنده | توضیح |
| ------------------------ | ----------------------------------------------------------------- |
| **Auto** (پیش‌فرض) | قالب صفحه وضعیت را به‌طور خودکار تشخیص می‌دهد |
| **Atlassian Statuspage** | صفحه‌های وضعیتی که Atlassian Statuspage نیرو می‌دهدشان (‏API از نوع JSON) |
| **incident.io** | صفحه‌های وضعیتی که incident.io نیرو می‌دهدشان (برای نمونه `https://status.openai.com`) |
| **RSS** | صفحه‌های وضعیتی که خوراک RSS ارائه می‌دهند |
| **Atom** | صفحه‌های وضعیتی که خوراک Atom ارائه می‌دهند |

### تشخیص خودکار

وقتی روی **Auto** تنظیم شود، OneUptime می‌کوشد قالب صفحه وضعیت را به‌طور خودکار و به این ترتیب تشخیص دهد:

1. نخست، API صفحه وضعیت incident.io را می‌آزماید (`/proxy/<host>`)
2. سپس، API از نوع JSON در Atlassian Statuspage را می‌آزماید (`/api/v2/status.json`، `/api/v2/components.json` و `/api/v2/incidents/unresolved.json`)
3. اگر آن‌ها شکست خوردند، می‌کوشد صفحه را به‌عنوان خوراک RSS یا Atom تفکیک کند
4. به‌عنوان آخرین پناه، بررسی پایه‌ای دست‌یافتنی بودن HTTP انجام می‌دهد

> **توجه:** ابتدا incident.io بررسی می‌شود چون برخی صفحه‌های وضعیت incident.io (مانند `https://status.openai.com`) نقطه پایانی محدود سازگار با Atlassian را هم در معرض می‌گذارند که گروه‌های مؤلفه و حادثه‌های فعال را جا می‌اندازد. بررسی نخستِ incident.io تضمین می‌کند داده غنی‌تر و آگاه از گروه به کار برود.

## ساختن یک مانیتور صفحه وضعیت بیرونی

1. در داشبورد OneUptime به **Monitors** بروید
2. روی **Create Monitor** کلیک کنید
3. نوع مانیتور را **External Status Page** برگزینید
4. نشانی صفحه وضعیتی را که می‌خواهید زیر نظر بگیرید وارد کنید
5. اختیاراً نوع ارائه‌دهنده مشخصی برگزینید (یا روی **Auto** بگذارید)
6. اختیاراً یک **گروه مؤلفه** وارد کنید تا به گروهی مانند «APIs» محدود شود
7. اختیاراً یک **نام مؤلفه** وارد کنید تا به یک مؤلفه تنها پالوده شود (اگر گروهی تنظیم شده باشد، درون آن گروه)
8. معیارهای مانیتورینگ را به‌فراخور پیکربندی کنید

## گزینه‌های پیکربندی

### نشانی صفحه وضعیت

نشانی صفحه وضعیت بیرونی‌ای را که می‌خواهید زیر نظر بگیرید وارد کنید. برای سایت‌هایی که Atlassian Statuspage و incident.io نیرو می‌دهندشان، این معمولاً نشانی ریشه است (برای نمونه `https://status.example.com`). برای خوراک‌های RSS/Atom، مستقیم نشانی خوراک را وارد کنید.

### نوع ارائه‌دهنده

نوع ارائه‌دهنده صفحه وضعیت را برگزینید. از **Auto** (پیش‌فرض) استفاده کنید تا OneUptime قالب را به‌طور خودکار تشخیص دهد، یا اگر می‌دانید **Atlassian Statuspage**، **incident.io**، **RSS** یا **Atom** را مشخص کنید.

### پالایه گروه مؤلفه

اگر صفحه وضعیت مؤلفه‌هایش را در گروه‌ها سازمان می‌دهد، می‌توانید مانیتور را به یک گروه تنها محدود کنید. برای نمونه، در `https://status.openai.com`، وارد کردن `APIs` مانیتور را به سرویس‌های API در OpenAI محدود می‌کند.

وقتی گروه مؤلفه‌ای تنظیم شود، **شمار حادثه‌های فعال** و **وضعیت کلی** فقط با مؤلفه‌های آن گروه محاسبه می‌شوند — حادثه‌ای که گروهی نامرتبط (برای نمونه ChatGPT) را متأثر کند مانیتوری را که به گروه «APIs» محدود شده نمی‌لغزاند.

پالایش گروه مؤلفه برای ارائه‌دهندگان **Atlassian Statuspage** و **incident.io** پشتیبانی می‌شود. (خوراک‌های RSS/Atom گروه‌های مؤلفه را در معرض نمی‌گذارند.)

### پالایه نام مؤلفه

اگر صفحه وضعیت درباره چند مؤلفه گزارش می‌دهد، می‌توانید اختیاراً نام مؤلفه‌ای مشخص کنید تا فقط همان مؤلفه را زیر نظر بگیرید. برای نمونه، برای زیر نظر گرفتن فقط AWS EC2 در us-east-1، `EC2 us-east-1` را وارد می‌کنید (نام دقیق مؤلفه، همان‌طور که در صفحه وضعیت نشان داده شده است).

وقتی گروه مؤلفه‌ای هم تنظیم شده باشد، پالایه نام مؤلفه **درون** آن گروه اعمال می‌شود و به شما امکان می‌دهد یک مؤلفه تنها درون گروهی بزرگ‌تر را نشانه بگیرید. وقتی هیچ‌کدام از پالایه‌ها مشخص نشوند، همه مؤلفه‌های در دامنه زیر نظر گرفته می‌شوند.

### گزینه‌های پیشرفته

#### مهلت

بیشینه زمانی (بر حسب میلی‌ثانیه) که برای پاسخ از صفحه وضعیت منتظر می‌ماند. پیش‌فرض ۱۰۰۰۰ میلی‌ثانیه (۱۰ ثانیه) است.

#### تلاش دوباره

شمار دفعاتی که در صورت شکست، درخواست دوباره تلاش می‌شود. پیش‌فرض ۳ تلاش است.

## معیارهای مانیتورینگ

می‌توانید معیارهایی پیکربندی کنید تا مشخص شود سرویس بیرونی کی عملیاتی یا پایین در نظر گرفته می‌شود، بر پایه:

- **Is Online** — اینکه آیا صفحه وضعیت دست‌یافتنی است و داده وضعیت برمی‌گرداند یا نه
- **Overall Status** — نشانگر وضعیت کلی صفحه وضعیت (برای نمونه `operational`، `degraded_performance`، `partial_outage`، `major_outage`)
- **Component Status** — وضعیت مؤلفه‌های در دامنه (با احترام به پالایه‌های گروه مؤلفه / نام مؤلفه)
- **Active Incidents** — شمار حادثه‌های هم‌اکنون فعالی که در صفحه وضعیت گزارش شده‌اند (وقتی پالایه‌ای تنظیم شده باشد، محدود به گروه مؤلفه / مؤلفه)
- **Response Time** — گرفتن داده صفحه وضعیت چقدر طول می‌کشد

### معیارهای پیش‌فرض

به‌طور پیش‌فرض، OneUptime معیارها را بر پایه آنچه واقعاً برای یک صفحه وضعیت اهمیت دارد بذر می‌پاشد — حادثه‌های فعال و سلامت مؤلفه‌هایش، نه صرفاً دست‌یافتنی بودن:

- وقتی هیچ حادثه فعالی در دامنه نباشد، مانیتور **Operational** علامت می‌خورد.
- وقتی دست‌کم یک حادثه فعال در دامنه باشد، یا وقتی مؤلفه‌ای در دامنه `degraded_performance`، `partial_outage`، `major_outage` یا `full_outage` گزارش کند، مانیتور **Down** علامت می‌خورد (و حادثه‌ای ساخته می‌شود).

چون شمار حادثه‌های فعال و وضعیت مؤلفه‌ها به پالایه‌های گروه مؤلفه / نام مؤلفه احترام می‌گذارند، این معیارهای پیش‌فرض به‌طور خودکار فقط مؤلفه‌هایی را نشانه می‌گیرند که برایتان مهم‌اند.

## قالب‌بندی حادثه و هشدار

هنگام ساختن حادثه یا هشدار از مانیتورهای صفحه وضعیت بیرونی، می‌توانید متغیرهای قالب زیر را به کار ببرید:

| متغیر | توضیح |
| ------------------------- | ------------------------------------------------------------ |
| `{{isOnline}}` | اینکه صفحه وضعیت آنلاین است یا نه (true/false) |
| `{{responseTimeInMs}}` | زمان پاسخ بر حسب میلی‌ثانیه |
| `{{failureCause}}` | علت شکست، در صورت وجود |
| `{{overallStatus}}` | مقدار نشانگر وضعیت کلی |
| `{{activeIncidentCount}}` | شمار حادثه‌های فعال (در صورت وجود پالایه، محدود به آن) |
| `{{componentStatuses}}` | آرایه JSON از وضعیت مؤلفه‌ها (`name`، `status`، `description`، `groupName`) |
| `{{provider}}` | ارائه‌دهنده تشخیص‌داده‌شده (Atlassian Statuspage، incident.io، RSS، Atom) |
| `{{componentGroup}}` | گروه مؤلفه‌ای که مانیتور به آن محدود شده، در صورت وجود |
| `{{componentName}}` | مؤلفه‌ای که مانیتور به آن محدود شده، در صورت وجود |

## بهترین شیوه‌ها

- **از نوع ارائه‌دهنده Auto استفاده کنید** مگر آنکه قالب دقیق را بدانید — تشخیص خودکار برای بیشتر صفحه‌های وضعیت خوب کار می‌کند
- **به یک گروه مؤلفه محدود کنید** اگر فقط به بخشی از یک ارائه‌دهنده وابسته‌اید (برای نمونه فقط «APIs» در OpenAI)، تا حادثه‌های نامرتبط نویز نسازند
- **مؤلفه‌های مشخصی را زیر نظر بگیرید** اگر فقط به سرویس‌های خاصی وابسته‌اید (برای نمونه، یک ناحیه مشخص AWS)
- **هم‌بستگی حادثه برپا کنید** — وقتی مانیتورهایتان مشکلی تشخیص می‌دهند و صفحه وضعیت بالادستی هم مشکل نشان می‌دهد، شناسایی سریع‌تر ریشه علت را آسان می‌کند
- **با مانیتورهای دیگر ترکیب کنید** — مانیتورهای صفحه وضعیت بیرونی را با مانیتورهای API/وب‌سایت خودتان جفت کنید تا دید جامعی داشته باشید
