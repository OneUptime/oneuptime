# مانیتور Podman

مانیتورینگ Podman به شما امکان می‌دهد سلامت و کارایی میزبان‌های Podman و کانتینرهای در حال اجرا رویشان را زیر نظر بگیرید. OneUptime سنجه‌ها و گزارش‌های کانتینر را از راه جمع‌کننده‌ای از پیش پیکربندی‌شده از OpenTelemetry (**عامل Podman در OneUptime**) جمع می‌کند و بر پایه معیارهای پیکربندی‌شده شما می‌سنجدشان.

## نمای کلی

مانیتورهای Podman از سنجه‌ها و گزارش‌های میزبان‌هایتان برای دید به بارهای کاری کانتینری استفاده می‌کنند. این به شما امکان می‌دهد:

- سلامت میزبان Podman و هر کانتینر را زیر نظر بگیرید
- ‏CPU، حافظه، شبکه، ورودی/خروجی بلوکی و شمار فرایندها را در سراسر کانتینرها ردیابی کنید
- بازراه‌اندازی، فروریزی و خفگی CPU کانتینرها را تشخیص دهید
- گزارش‌های ساخت‌یافته کانتینر را در قالب بومی OpenTelemetry جریان دهید
- بر CPU بالا، حافظه بالا، حلقه بازراه‌اندازی و بیشتر هشدار بدهید

## ساختن یک مانیتور Podman

1. در داشبورد OneUptime به **Monitors** بروید
2. روی **Create Monitor** کلیک کنید
3. نوع مانیتور را **Podman** برگزینید
4. میزبان Podman و دامنه منبعی را که باید زیر نظر گرفته شود برگزینید
5. پرس‌وجوهای سنجه و تجمیع را پیکربندی کنید
6. معیارهای مانیتورینگ را به‌فراخور پیکربندی کنید

## گزینه‌های پیکربندی

### میزبان Podman

میزبان Podmanای را که باید زیر نظر گرفته شود برگزینید. میزبان‌ها نخستین بار که عامل Podman در OneUptime از آن‌ها تله‌متری می‌فرستد خودکار ثبت می‌شوند — لازم نیست دستی بسازیدشان.

### دامنه منبع

سطحی را که در آن منابع زیر نظر گرفته می‌شوند برگزینید:

| دامنه | توضیح |
| --------- | ---------------------------------------------------------------- |
| Host | زیر نظر گرفتن کل میزبان Podman، تجمیع‌شده در سراسر همه کانتینرها |
| Container | زیر نظر گرفتن کانتینری مشخص بر پایه نام یا ایمیج |

### پرس‌وجوهای سنجه

یک یا چند پرس‌وجوی سنجه برای سنجش پیکربندی کنید. هر پرس‌وجو این‌ها را مشخص می‌کند:

- **نام سنجه** — سنجه کانتینری که پرس‌وجو می‌شود
- **تجمیع** — اینکه مقادیر سنجه چگونه تجمیع شوند (میانگین، مجموع، بیشینه، کمینه)
- **پالایه‌ها** — پالایش بیشتر بر پایه ویژگی (برای نمونه بر پایه نام کانتینر، ایمیج یا میزبان)
- **Group By** — اختیاراً بر پایه `resource.container.name` گروه‌بندی کنید تا هر کانتینری مستقل سنجیده شود

می‌توانید **فرمول‌هایی** هم بسازید که چند پرس‌وجوی سنجه را با عبارت‌های ریاضی ترکیب می‌کنند.

### پنجره زمانی غلتان

پنجره زمانی ارزیابی سنجه را برگزینید:

- ۱ دقیقه گذشته
- ۵ دقیقه گذشته
- ۱۰ دقیقه گذشته
- ۱۵ دقیقه گذشته
- ۳۰ دقیقه گذشته
- ۶۰ دقیقه گذشته

## سنجه‌های جمع‌آوری‌شده

عامل Podman از گیرنده `docker_stats` در OpenTelemetry استفاده می‌کند که به سوکت سازگار با Docker در Podman ‏(`/run/podman/podman.sock`) نشانه گرفته شده و API ‏Podman را روی فاصله‌ای قابل پیکربندی (پیش‌فرض هر ۳۰ ثانیه) برداشت می‌کند.

### CPU

| سنجه | توضیح |
| ------------------------------------------------- | ----------------------------------------------------------------- |
| `container.cpu.utilization` | بهره‌برداری CPU کانتینر، که ۱۰۰٪ یک هسته کامل CPU است |
| `container.cpu.usage.total` | زمان تجمعی CPU مصرف‌شده توسط کانتینر |
| `container.cpu.throttling_data.throttled_time` | زمانی که کانتینر توسط cgroups خفه شده است |
| `container.cpu.throttling_data.throttled_periods` | شمار دوره‌های خفگی |

### حافظه

| سنجه | توضیح |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| `container.memory.usage.total` | مصرف جاری حافظه بر حسب بایت |
| `container.memory.usage.limit` | محدودیت حافظه بر حسب بایت |
| `container.memory.percent` | مصرف حافظه به‌صورت درصدی از محدودیت حافظه کانتینر، یا از حافظه میزبان وقتی کانتینر محدودیتی ندارد |

### شبکه

| سنجه | توضیح |
| ------------------------------------- | ----------------------- |
| `container.network.io.usage.rx_bytes` | کل بایت‌های دریافتی |
| `container.network.io.usage.tx_bytes` | کل بایت‌های فرستاده‌شده |

### ورودی/خروجی بلوکی

| سنجه | توضیح |
| ---------------------------------------------------- | ------------------------------ |
| `container.blockio.io_service_bytes_recursive.read` | بایت‌های خوانده‌شده از دستگاه‌های بلوکی |
| `container.blockio.io_service_bytes_recursive.write` | بایت‌های نوشته‌شده روی دستگاه‌های بلوکی |

### اطلاعات کانتینر

| سنجه | توضیح |
| ---------------------- | ------------------------------------------- |
| `container.uptime` | آپ‌تایم کانتینر بر حسب ثانیه |
| `container.restarts` | شمار دفعاتی که کانتینر بازراه‌اندازی شده است |
| `container.pids.count` | شمار فرایندهای درون کانتینر |

## معیارهای مانیتورینگ

### چه چیزی سنجیده می‌شود

این مانیتورها همیشه **Metric Value** را می‌سنجند — مقدار پرس‌وجوی سنجه یا فرمول پیکربندی‌شده. فرم معیارها انتخابگر Filter Type ندارد؛ **Metric**، **Aggregation**، **Condition** و **Threshold** را نشان می‌دهد.

### نوع‌های تجمیع

| تجمیع | توضیح |
| ------------- | ---------------------------------- |
| Average | مقدار میانگین در پنجره زمانی |
| Sum | مجموع همه مقادیر |
| Maximum Value | بالاترین مقدار در پنجره زمانی |
| Minimum Value | پایین‌ترین مقدار در پنجره زمانی |
| All Values | همه مقادیر باید با معیار بخوانند |
| Any Value | دست‌کم یک مقدار باید بخواند |

### شرط‌ها

آستانه‌های ایستا — با **Threshold**ای که وارد می‌کنید مقایسه می‌شوند:

- **Greater Than**، **Less Than**، **Greater Than or Equal To**، **Less Than or Equal To**، **Equal To**

تشخیص ناهنجاری خط پایه — بدون آستانه؛ به‌جایش فرم **Sensitivity** و **Baseline Window** را نشان می‌دهد و هر نمونه را با خط پایه همان ساعت از هفته که از آن پنجره ساخته شده مقایسه می‌کند:

- **Anomalously High** — مقدار بالای محدوده مورد انتظار می‌رود
- **Anomalously Low** — مقدار زیر محدوده مورد انتظار می‌افتد
- **Anomalous** — مقدار در هر جهتی از محدوده مورد انتظار بیرون می‌رود

شرط‌های ناهنجاری در وضعیت «Learning» می‌مانند و تا وقتی دست‌کم به اندازه Baseline Window برگزیده تاریخچه سنجه وجود نداشته باشد هیچ هشداری تولید نمی‌کنند.

## قالب‌های آماده هشدار

‏OneUptime برای سناریوهای رایج مانیتورینگ Podman قالب‌هایی ارائه می‌دهد:

| قالب | توضیح | آستانه | تجمیع |
| ---------------------------- | --------------------------------------------------------- | --------- | ------------------- |
| High Container CPU | بهره‌برداری CPU به ازای هر کانتینر (۱۰۰٪ = یک هسته) | > ۸۰ | میانگین (به ازای هر کانتینر) |
| High Container Memory | مصرف حافظه به‌صورت درصدی از محدودیت، یا از حافظه میزبان | > ۸۵٪ | میانگین (به ازای هر کانتینر) |
| High Container Restart Count | شمار بازراه‌اندازی کانتینر (جمع در حال اجرا، نه به ازای هر پنجره) | > ۵ | بیشینه (به ازای هر کانتینر) |
| High Process Count | شمار فرایند به ازای هر کانتینر | > ۵۰۰ | بیشینه (به ازای هر کانتینر) |
| Container Restarted | آپ‌تایم کانتینر پس از بازراه‌اندازی | < ۱۲۰ ثانیه | کمینه (به ازای هر کانتینر) |

> توجه: هر قالبی بر پایه `resource.container.name` گروه‌بندی می‌کند، پس هر کانتینری روی میزبان مستقل سنجیده می‌شود و هشدار خودش را می‌گیرد. دو گیج درصدی از **میانگین** استفاده می‌کنند — آن‌ها از پیش درصدهایی به ازای هر کانتینرند، پس میانگین در دقیقه همان خوانش پایدار است — در حالی که شمار بازراه‌اندازی و شمار فرایند از **بیشینه** استفاده می‌کنند، جایی که یک نمونه شکننده آستانه واقعاً خودِ سیگنال است.

> سنجه `container.cpu.utilization` همان رقمی است که `podman stats` چاپ می‌کند: ۱۰۰٪ یک هسته کامل CPU است، نه کل سهم CPU کانتینر. کانتینری که چند هسته گرفته باشد در حالی که کاملاً سالم است بسیار بالای ۱۰۰ می‌خواند، پس آستانه را روی آن‌ها بالا ببرید.

> سنجه `container.uptime` فقط برای کانتینرهای RUNNING وجود دارد — کانتینری که متوقف شود و متوقف بماند اصلاً نمونه‌ای منتشر نمی‌کند، پس قالب **Container Restarted** بازراه‌اندازی‌ها و استقرارهای دوباره را تشخیص می‌دهد، نه خاموشی دائمی را. کانتینری که طراحی شده کمتر از دو دقیقه اجرا شود کل عمرش در حالت هشدار می‌ماند.

> قالبی برای خفگی CPU وجود ندارد. سنجه‌های خفگی‌ای که عامل جمع می‌کند (`container.cpu.throttling_data.throttled_time` و `.throttled_periods`) شمارنده‌های تجمعی عمرند، و OneUptime هنوز شمارنده‌ای تجمعی را در مسیر هشداردهی به نرخ تبدیل نمی‌کند، پس هشدار «زمان خفگی > ۰» یک بار شلیک می‌کرد و هرگز پاک نمی‌شد. هر دو سنجه همچنان جمع می‌شوند و می‌توان روی داشبوردی ترسیمشان کرد.

## گزارش‌های جمع‌آوری‌شده

افزون بر سنجه‌ها، عامل Podman فایل گزارش هر کانتینری را با گیرنده filelog در OpenTelemetry دنبال می‌کند و رکوردهای گزارش را در قالب بومی گزارش OTLP می‌فرستد. هر رکورد گزارش با این‌ها غنی می‌شود:

- `resource.host.name` — شناسه میزبان Podman
- `resource.container.id` — شناسه کامل کانتینر
- `resource.container.runtime` — همیشه `podman`
- `attributes["log.iostream"]` — `stdout` یا `stderr`
- `severityText` / `severityNumber` — از کلیدواژه سطحی در خط خوانده می‌شود (`app.INFO:`، `{"level":"warn"}`، `[ERROR]`)؛ خط‌هایی که سطح قابل تشخیصی ندارند به جریان بازمی‌گردند: `stderr` → `ERROR`، `stdout` → `INFO`
- `body` — خط خام گزارشی که فرایند کانتینر منتشر کرده
- `time` — مهر زمانی موتور کانتینر برای آن خط

گزارش‌ها در زبانه **Logs** میزبان Podman و در صفحه جزئیات هر کانتینری پدیدار می‌شوند.

### نیازمندی راه‌انداز گزارش

**‏Podman به‌طور پیش‌فرض راه‌انداز گزارش `journald` را به کار می‌برد، که به‌جای فایلی که عامل بتواند دنبالش کند در journal سیستم‌دی می‌نویسد.** گیرنده filelog عامل Podman مسیر **`k8s-file`** یعنی `/var/lib/containers/storage/overlay-containers/*/userdata/ctr.log` را دنبال می‌کند. برای فرستادن گزارش‌های کانتینر به OneUptime، کانتینرهایتان را با راه‌انداز گزارش `k8s-file` (یا `json-file`) اجرا کنید:

- **`journald`** (پیش‌فرض Podman) — گزارش‌ها را به journal سیستم‌دی می‌فرستد؛ فایلی برای دنبال کردن نیست. زبانه **Logs** خالی خواهد بود.
- **`k8s-file`** — فایل `ctr.log`ای به ازای هر کانتینر می‌نویسد که گیرنده filelog می‌تواند تفکیکش کند. **توصیه‌شده.**
- **`none`** — گزارش‌ها را کلاً دور می‌ریزد.

**اجرای یک کانتینر تنها با راه‌انداز `k8s-file`:**

```bash
podman run --log-driver k8s-file ... <image>
```

**تغییر پیش‌فرض برای کانتینرهای تازه** با ویرایش `/etc/containers/containers.conf`:

```toml
[containers]
log_driver = "k8s-file"
```

سپس کانتینرهای متأثر را **بازبسازید**. Podman راه‌انداز گزارش را هنگام ساخت کانتینر مقید می‌کند، پس کانتینر موجود تا وقتی برداشته و بازساخته نشود راه‌انداز قدیمی‌اش را نگه می‌دارد.

## نیازمندی‌های راه‌اندازی

برای استفاده از مانیتورینگ Podman، باید:

1. عامل Podman در OneUptime را روی هر میزبان Podmanای که می‌خواهید زیر نظر بگیرید نصب کنید
2. مقادیر `ONEUPTIME_URL`، `ONEUPTIME_SERVICE_TOKEN` و `PODMAN_HOST_NAME` را به‌عنوان متغیر محیطی بدهید
3. مطمئن شوید کانتینرهایی که می‌خواهید مشاهده کنید راه‌انداز گزارش `k8s-file` را به کار می‌برند (بالا را ببینید)

عامل روی Docker Hub با نام `oneuptime/podman-agent:release` منتشر می‌شود. برای نمونه‌های کامل `podman run` و Compose، [راهنمای نصب میزبان Podman](https://github.com/OneUptime/oneuptime/tree/master/PodmanAgent) را ببینید.

## رفع اشکال

### سنجه‌ها پدیدار می‌شوند اما زبانه Logs خالی است

کانتینرهای شما تقریباً بی‌تردید راه‌انداز گزارش پیش‌فرض `journald` در Podman را به کار می‌برند. هر کانتینری را که گزارش‌هایش باید فرستاده شوند به راه‌انداز `k8s-file` سوییچ کنید (بخش [نیازمندی راه‌انداز گزارش](#نیازمندی-راهانداز-گزارش) بالا را ببینید) و بازبسازیدشان.

### گیرنده filelog گزارش می‌دهد `no files match the configured criteria`

این یعنی الگوی include یعنی `/var/lib/containers/storage/overlay-containers/*/userdata/ctr.log` هنگام آغاز عامل با هیچ فایلی نخوانده است. یا:

1. هیچ کانتینری روی این میزبان `k8s-file` را به کار نمی‌برد، یا
2. سوارسازی پیوندی که `/var/lib/containers/storage` را در معرض می‌گذارد نیست یا به پوشه‌ای خالی اشاره می‌کند، یا
3. عامل بدون ریشه اجرا می‌شود و نمی‌تواند مسیر انباره کانتینر ریشه‌دار را بخواند (یا برعکس).

### گزارش‌ها می‌رسند اما زیر نام میزبان اشتباه گروه می‌شوند

‏OneUptime میزبان‌های Podman را بر پایه `resource.host.name` خودکار ثبت می‌کند، که از متغیر محیطی `PODMAN_HOST_NAME` گرفته می‌شود. تغییر `PODMAN_HOST_NAME` پس از نخستین دسته تله‌متری، به‌جای تغییر نام میزبان موجود، سطر میزبان دومی می‌سازد.

### حادثه‌ها برای «CPU بالا» شلیک نمی‌شوند

مطمئن شوید تجمیع پرس‌وجوی سنجه **بیشینه** باشد (نه میانگین) و بر پایه `resource.container.name` گروه‌بندی کند. میانگینی در سراسر همه کانتینرهای میزبانی شلوغ با کانتینرهای بیکار رقیق می‌شود و به‌ندرت از آستانه می‌گذرد.
