# رصدپذیری هزینه Kubernetes

## نمای کلی

‏OneUptime می‌تواند به شما نشان دهد هر بار کاری Kubernetes واقعاً چقدر هزینه دارد — خرج به ازای هر فضای‌نام، هر کنترلر و هر پاد، همراه با ظرفیت بیکار و کارایی درخواست در برابر مصرف — درست کنار سنجه‌ها، گزارش‌ها و ردیابی‌هایی که از پیش با [عامل Kubernetes](/docs/telemetry/kubernetes-agent) جمع می‌کنید.

فعال کردنش یک فرمان است:

```bash
helm upgrade oneuptime-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent \
  --reuse-values \
  --set cost.enabled=true
```

این نصبی کامل است. نمودار موتور متن‌باز [OpenCost](https://opencost.io) را همراه دارد (‏Apache-2.0، ‏CNCF — همان [cost-model](https://github.com/kubecost/cost-model) که به Kubecost هم نیرو می‌دهد) به‌علاوه یک Prometheus کمینه و اختصاصی که برای تاریخچه مصرف لازم دارد — دو پاد کوچک از لوله‌کشی نامرئی. OpenCost گره‌ها، حجم‌ها و متعادل‌کننده‌های بار شما را از **قیمت‌های فهرست عمومی ارائه‌دهنده ابری‌تان به‌طور خودکار و بدون هیچ اعتبارنامه‌ای** قیمت‌گذاری می‌کند (AWS، GCP، Azure)؛ خوشه‌های درون‌سازمانی به‌جایش کارت نرخ تنظیم می‌کنند (پایین‌تر).

ظرف حدود یک ساعت (نخستین پنجره ساعتی بسته‌شده)، این‌ها را می‌گیرید:

- یک **صفحه Costs به ازای هر خوشه** (_Kubernetes → خوشه شما → Costs_): روند خرج، خرج به تفکیک فضای‌نام با تفکیک cpu/حافظه/ذخیره‌سازی، خرج به تفکیک بار کاری، خرج بیکار و کارایی.
- یک **صفحه Costs در سطح پروژه** (_Kubernetes → Costs_): خرج در سراسر همه خوشه‌های پروژه.
- یک **قالب داشبورد هزینه Kubernetes** (_Dashboards → Create → Kubernetes Cost Dashboard_): روند هزینه ساعتی گره، هزینه واحد CPU/RAM، خرج حجم ماندگار و متعادل‌کننده بار.
- سنجه‌های خام هزینه (`node_total_hourly_cost`، `pv_hourly_cost`، ...) در **Metric Explorer**، قابل استفاده در داشبوردهای سفارشی و هشدارهای سنجه.

## چگونه کار می‌کند

با `cost.enabled=true` نمودار چهار چیز اجرا می‌کند:

1. **OpenCost** (همراه) — خوشه را می‌پاید، قیمت‌های فهرست ابری را کشف می‌کند و تخصیص هزینه از پیش قیمت‌گذاری‌شده به ازای هر بار کاری محاسبه می‌کند.
2. **یک Prometheus کمینه** (همراه) — OpenCost برای تاریخچه مصرف/قیمت به نقطه پایانی PromQL نیاز دارد. این یکی صرفاً برای همان هست: تک‌نسخه، نگهداشت ۳ روزه و دقیقاً دو هدف برداشت (cAdvisor از راه پراکسی گره کارساز API، و خودِ OpenCost — که سنجه‌های درخواست منابع به سبک KSM را خودش منتشر می‌کند، پس kube-state-metrics در کار نیست). هرگز بیرون خوشه در معرض قرار نمی‌گیرد و داده‌اش هرگز از آن بیرون نمی‌رود.
3. **پیمایشگر تخصیص هزینه** (`cost.agent`) — یک بار در هر پنجره ساعتی بسته‌شده از API تخصیص OpenCost پرس‌وجو می‌کند و سطرهای هزینه به ازای هر بار کاری (cpu / ram / gpu / pv / شبکه / متعادل‌کننده بار / بیکار، به‌علاوه کارایی) را به OneUptime POST می‌کند. پنجره‌ها دقیقاً یک بار فرستاده می‌شوند — کارساز پنجره‌هایی را که پیش‌تر دریافت کرده رد می‌کند، پس بازراه‌اندازی‌ها نمی‌توانند خرج را دوباره بشمارند.
4. **برداشت سنجه‌های هزینه** (`cost.metrics`) — جمع‌کننده OpenTelemetry عامل، سنجه‌های Prometheus در OpenCost را (با فهرست مجاز محدود به سری‌های هزینه) از راه همان خط لوله OTLP باقی سنجه‌های خوشه‌تان برداشت می‌کند.

## از پیش Kubecost یا OpenCost اجرا می‌کنید؟

به‌جایش نمودار را به موتور موجودتان نشانه بگیرید — آنگاه هیچ‌چیزی همراه نمی‌شود:

```bash
helm upgrade oneuptime-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent \
  --reuse-values \
  --set cost.enabled=true \
  --set cost.engine.url=http://kubecost-cost-analyzer.kubecost.svc.cluster.local:9090
```

| موتور | نشانی معمول سرویس |
| -------- | ---------------------------------------------------------------- |
| OpenCost | `http://opencost.opencost.svc.cluster.local:9003` |
| Kubecost | `http://kubecost-cost-analyzer.kubecost.svc.cluster.local:9090` |

مسیر API تخصیص خودکار تشخیص داده می‌شود (`/model/allocation` برای Kubecost، ‏`/allocation/compute` یا `/allocation` برای OpenCost). مقدار `cost.engine.allocationPath` را فقط برای نصب‌های نامتعارف تنظیم کنید.

## قیمت‌گذاری درون‌سازمانی / سخت‌افزار خالص

خوشه‌هایی که گره‌هایشان قیمت فهرست ابری عمومی ندارند می‌توانند کارت نرخ تنظیم کنند — آنگاه OpenCost هر منبعی را از این ارقام قیمت‌گذاری می‌کند. همه مقادیر بر حسب **دلار آمریکا به ازای هر منبع-ساعت** هستند:

```yaml
cost:
  enabled: true
  opencost:
    customPricing:
      enabled: true
      cpuPerCoreHour: "0.031611"       # ~$23 per core-month
      ramPerGiBHour: "0.004237"        # ~$3 per GiB-month
      storagePerGBHour: "0.00005479452" # ~$0.04 per GB-month
      gpuPerHour: "0.95"
```

## کلیدهای مفید

همه اختیاری‌اند — برای فهرست کامل `values.yaml` نمودار را ببینید:

```yaml
cost:
  agent:
    windowSeconds: 3600   # allocation window length (hourly = native)
    includeIdle: true     # ship the engine's __idle__ allocation
    currency: USD         # currency code shown in the UI (informational)
  prometheus:
    retention: 7d         # bundled TSDB history; right-sizing reads peaks back over days
    persistence:
      enabled: false      # set true for a small PVC; emptyDir otherwise
  metrics:
    enabled: true         # cost metrics for dashboards / Metric Explorer
    scrapeInterval: 60s
```

## اندازه‌گذاری درست

کارت **Right-Sizing** روی صفحه Costs یک خوشه، برای هر کانتینری که تاریخچه کافی دارد یک درخواست CPU و حافظه توصیه می‌کند، رتبه‌بندی‌شده بر پایه اینکه هر تغییر ماهانه چقدر صرفه‌جویی می‌کند.

توصیه، تقاضای مشاهده‌شده به‌علاوه ۲۵٪ فضای مانور است، گرد شده به مقداری که بتوانید در یک مانیفست بچسبانید (10m برای CPU، 16Mi برای حافظه):

- **CPU** از **صدک ۹۵** میانگین مصرف ساعتی اندازه‌گذاری می‌شود. آن‌قدر بالا که بار واقعی را بپوشاند، آن‌قدر پایین که یک جهش تنها درخواست را برای یک ماه دوباره باد نکند.
- **حافظه** از **اوج** مجموعه کاری اندازه‌گذاری می‌شود — هرگز از میانگین. پایین‌تر را ببینید.

درخواست‌ها توصیه می‌شوند؛ محدودیت‌ها نه. درخواست همان چیزی است که زمان‌بند رزرو می‌کند و صورت‌حساب از آن محاسبه می‌شود، پس همان عددی است که هزینه را جابه‌جا می‌کند. محدودیت‌ها تصمیمی درباره شعاع انفجارند که به این بستگی دارد که ترجیح می‌دهید کانتینر بدرفتار خفه شود یا کشته، و این تصمیمی نیست که داده مصرف بتواند برایتان بگیرد.

هر کانتینر در برابر درخواست جاری‌اش امتیاز می‌گیرد:

- **بیش‌تأمین‌شده** — به‌طور معنادار بیش از آنچه مصرف می‌کند رزرو می‌کند. برآورد صرفه‌جویی از همین‌جا می‌آید.
- **کم‌تأمین‌شده** — کمتر از آنچه مصرف می‌کند رزرو می‌کند، پس خفه می‌شود یا در معرض OOMKill است. درست کردن این *هزینه* دارد، و کارت آن را به‌جای پنهان کردن، به‌عنوان افزایش نشان می‌دهد.
- **بدون درخواست** — چیزی برای کوچک کردن نیست، اما زمان‌بند نمی‌تواند کانتینر را امن جای دهد و زیر فشار نخستین چیزی است که بیرون انداخته می‌شود.
- هر چیزی که در ۱۵٪ توصیه‌اش باشد از پیش درست‌اندازه در نظر گرفته می‌شود و کنار گذاشته می‌شود. هیچ‌کس نباید برای تراشیدن ۳٪ از یک درخواست، مانیفستی را ویرایش کند.

دو نگهبان توصیه را صادق نگه می‌دارند. یک بار کاری پیش از هر اندازه‌گذاری‌ای به دست‌کم **۲۴ ساعت** پنجره هزینه نیاز دارد — پنجره‌ای چهارساعته کار دسته‌ای شبانه را در حالت استراحت می‌گیرد و با خوشحالی توصیه می‌کند به هیچ کوچکش کنید. و صرفه‌جویی‌ها از طول پنجره‌ای که می‌بینید فرافکنی می‌شوند، نه از شمار سطرها، پس صرفه‌جویی یک Deployment در شمار نسخه‌هایش ضرب نمی‌شود.

برآورد فرض می‌گیرد خرج با آنچه موتور تخصیص داده مقیاس می‌گیرد، که `max(request, usage)` است. در حالت بیش‌تأمین‌شده این به خودِ درخواست فرو می‌کاهد، پس رقم صرفه‌جویی به‌جای تقریبی، دقیق است.

### داده پشت آن

در کنار خرج، پیمایشگر آنچه را توصیه اندازه‌گذاری درست لازم دارد جمع می‌کند: **درخواست‌ها**، **محدودیت‌ها** و **مصرف** CPU و حافظه به ازای هر کانتینر.

حافظه به منبع اضافه‌ای نیاز دارد. API تخصیص فقط میانگینی روی هر پنجره گزارش می‌دهد، و میانگین ساعتی همان جهشی را پنهان می‌کند که کانتینر را OOMKill می‌کند — پس اندازه‌گذاری درخواست حافظه از آن فعالانه خطرناک است. بنابراین عامل **اوج** حافظه به ازای هر کانتینر را از Prometheus می‌خواند و روی `(namespace, pod, container)` پیوند می‌زند.

این اختیاری است و تمیز تنزل می‌کند:

- **موتور همراه (پیش‌فرض):** Prometheus خود نمودار به‌طور خودکار به کار می‌رود. چیزی برای پیکربندی نیست.
- **موتور بیرونی (`cost.engine.url` تنظیم‌شده):** هیچ Prometheus همراهی نیست، پس `cost.engine.prometheusUrl` را به یکی نشانه بگیرید که cAdvisor را برداشت می‌کند. اگر نام کار برداشت آن `kubernetes-nodes-cadvisor` نیست، `cost.engine.prometheusCadvisorJob` را هم تنظیم کنید.
- **اصلاً بدون Prometheus:** توصیه‌های CPU همچنان کار می‌کنند — از میانگین‌های ساعتی ذخیره‌شده مشتق می‌شوند — و توصیه‌های حافظه به‌جای اشتباه بودن، در دسترس نیستند.

قطعی Prometheus هرگز جمع‌آوری خرج را نمی‌بندد: اوج‌ها غنی‌سازی‌اند و پنجره بدون آن‌ها فرستاده می‌شود.

‏CPU عمداً از Prometheus استفاده نمی‌کند. زیاده‌روی در درخواست CPU کانتینر را خفه می‌کند در حالی که زیاده‌روی در حافظه می‌کشدش، پس CPU با خیال راحت از میانگین‌های ساعتی که از پیش در ClickHouse هستند اندازه‌گذاری می‌شود — و پرس‌وجوی نرخ CPU به ازای هر کانتینر در سراسر یک خوشه آن‌قدر گران است که Prometheus کوچکی را بی‌ثبات کند.

## هشدار بر هزینه

سنجه‌های هزینه برداشت‌شده سنجه‌های معمولی OneUptime هستند، پس می‌توانید مانند هر چیز دیگری روی آن‌ها هشدار سنجه بگذارید — برای نمونه، وقتی میانگین `node_total_hourly_cost` از آستانه بودجه بالاتر می‌رود، یا وقتی `pv_hourly_cost` برای رده حجمی پدیدار می‌شود که نباید در خوشه وجود داشته باشد.

## مدل داده و نگهداشت

سطرهای تخصیص در ClickHouse ذخیره می‌شوند (یک سطر به ازای هر خوشه، پنجره، فضای‌نام، کنترلر، پاد و کانتینر) و از نگهداشت تله‌متری خوشه پیروی می‌کنند: تنظیم `retainTelemetryDataForDays` روی منبع خوشه Kubernetes، با بازگشت به نگهداشت داده پروژه. ظرفیت بیکار و تخصیص‌نیافته به‌عنوان سطرهای عادی زیر فضای‌نام‌های `__idle__` / `__unallocated__` ذخیره می‌شوند تا با همان گروه‌بندی‌های خرج بار کاری قابل پرس‌وجو باشند.

## رفع اشکال

- **صفحه‌های Costs خالی‌اند** — گزارش‌های عامل هزینه را بررسی کنید: `kubectl logs -n <agent namespace> deploy/<release>-kubernetes-agent-cost`. خطای `401` یعنی کلید دریافت نامعتبر است؛ پیام `cost engine did not answer any known allocation path` یعنی موتور هنوز بالا نیامده (OpenCost همراه پس از نصب چند دقیقه زمان می‌خواهد تا نخستین پنجره‌هایش را قیمت‌گذاری کند) یا `cost.engine.url` اشتباه است.
- **‏OpenCost همراه آماده نیست** — `kubectl logs -n <agent namespace> deploy/<release>-kubernetes-agent-opencost`. گزارش می‌دهد چه ارائه‌دهنده ابری‌ای تشخیص داده و آیا داده قیمت‌گذاری بارگذاری شده است.
- **‏`mkdir /var/configs: permission denied` در گزارش OpenCost** — اشکالی در نمودار که در نمودار ۰٫۶٫۱ رفع شد. OpenCost به‌عنوان غیر ریشه و بدون پوشه پیکربندی قابل نوشتن اجرا می‌شد، پس `Error downloading default pricing data` باعث می‌شد API تخصیصش نتواند پاسخ دهد و پیمایشگر بایستد — در حالی که پاد `Running` می‌ماند، `/healthz` سبز می‌ماند و سنجه‌های هزینه گره همچنان منتشر می‌شدند. نمودار را ارتقا دهید (`helm repo update && helm upgrade ... --reuse-values`)؛ سطرهای هزینه در پیمایش بعدی پدیدار می‌شوند.
- **قالب داشبورد داده‌ای نشان نمی‌دهد** — قالب سنجه‌های هزینه برداشت‌شده را می‌خواند؛ تأیید کنید `cost.metrics.enabled` برابر `true` باشد.
- **کارت Right-Sizing خالی است** — یا پنجره کوتاه‌تر از ۲۴ ساعتی است که یک توصیه لازم دارد (بازه زمانی را گشاد کنید)، یا هر کانتینری از پیش در ۱۵٪ درخواست توصیه‌شده‌اش است، که کارت صریح می‌گویدش.
- **توصیه‌های حافظه `-` نشان می‌دهند اما CPU کار می‌کند** — هیچ اوج حافظه‌ای به کارساز نرسیده، پس حافظه به‌جای حدس زدن از میانگین، عمداً بدون اندازه‌گذاری رها شده است. روی نصبی با موتور بیرونی، `cost.engine.prometheusUrl` را تنظیم کنید. کارت گزارش می‌دهد این چند کانتینر را متأثر می‌کند.
- **اعداد با رابط کاربری خود موتور فرق دارند** — OneUptime تعدیل‌های تطبیقی موتور را در هر مؤلفه هزینه می‌گنجاند و پنجره‌های بسته‌شده کامل را می‌فرستد؛ خرج جزئی ساعت جاری پس از بسته شدن پنجره پدیدار می‌شود.
- **پاد Prometheus بازراه‌اندازی شد** — با ذخیره‌سازی پیش‌فرض `emptyDir`، بازراه‌اندازی چند ساعت تاریخچه مصرف را از دست می‌دهد، پس تخصیص آن پنجره‌ها ممکن است کوچک‌تر باشد. اگر برایتان مهم است `cost.prometheus.persistence.enabled=true` را تنظیم کنید.
