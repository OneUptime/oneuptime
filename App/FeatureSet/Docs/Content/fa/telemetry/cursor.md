# پاییدن Cursor با OneUptime

صادرات OpenTelemetry در Cursor **سمت کارساز** است. روی ماشین‌های توسعه‌دهنده چیزی نصب نمی‌کنید، متغیرهای محیطی `CURSOR_*` یا `OTEL_EXPORTER_OTLP_*` را تنظیم نمی‌کنید، و توسعه‌دهندگان جداگانه در آن شرکت نمی‌کنند. مدیری OneUptime را در داشبورد وب Cursor به‌عنوان مقصد ثبت می‌کند، و کارسازهای Cursor تله‌متری را برای کل تیم به نقطه پایانی OTLP شما هل می‌دهند.

دو پیش‌نیاز پیش از آنکه جلوتر بخوانید:

- **فقط طرح Cursor Enterprise.** صفحه OpenTelemetry Export روی طرح‌های دیگر وجود ندارد.
- **نقطه پایانی OTLP شما در OneUptime باید از اینترنت عمومی دست‌یافتنی باشد.** Cursor به‌صورت ورودی به شما وصل می‌شود. اگر پشت دیوار آتش خودمیزبانی می‌کنید، [اجازه دادن به IPهای خروجی Cursor](#step-3-allow-cursors-egress-ips-self-hosted-only) را ببینید.

## چه چیزی می‌گیرید و چه چیزی نمی‌گیرید

پیش از آنکه دنبال آبشار ردیابی بگردید این را بخوانید. صادرات Cursor **فقط سنجه‌ها و گزارش‌ها** را می‌فرستد. مستندات خود Cursor آشکارا می‌گویدش: نه محتوای اعلان، نه ردیابی، و نه پرکردن تاریخچه گذشته.

| سیگنال                                                                     | وضعیت                                               |
| ------------------------------------------------------------------------- | --------------------------------------------------- |
| سنجه‌ها (توکن، هزینه، فراخوان ابزار)                                       | بله — مجموع‌های دلتا                                |
| رویدادهای گزارش (مصرف به ازای هر درخواست، خطاها، مهارت‌ها، قلاب‌ها، عامل‌های ابری) | بله                                                 |
| ردیابی‌ها / اسپن‌ها                                                        | **نه** — Cursor هیچ‌کدام را صادر نمی‌کند            |
| محتوای اعلان و تکمیل                                                       | **نه** — از این خط لوله هرگز Cursor را ترک نمی‌کند  |
| پرکردن تاریخچه پیش از فعال کردن مقصد                                       | **نه** — داده از لحظه فعال‌سازی به بعد جاری می‌شود  |

پیامدهای عملی در OneUptime:

- مصرف Cursor در فهرست اسپن‌محور **LLM Calls** پدیدار **نمی‌شود**، و ردیابی‌ای به ازای هر فراخوان برای باز کردن وجود ندارد. آن فهرست از اسپن‌های `gen_ai.*` ساخته می‌شود؛ Cursor هیچ‌کدام را منتشر نمی‌کند.
- ‏Cursor در زبانه **Usage** از بخش **AI / LLM** پدیدار **می‌شود**، چون OneUptime ‏`cursor.token.usage` و `cursor.cost.usage` را می‌شناسد. از آنجا که Cursor منبعی فقط-سنجه است، دو محدودیت صدق می‌کند — پیش از آنکه گزارش بازپرداخت هزینه‌ای رویش بسازید [جایی که Cursor در زبانه Usage پدیدار می‌شود](#where-cursor-shows-up-in-the-usage-tab) را بخوانید.
- دانه‌بندی به ازای هر درخواست در کاوشگر **Logs** زندگی می‌کند، روی رویداد گزارش `cursor.api.request` — این تنها جایی است که مجموع توکن به ازای هر درخواست وجود دارد.

اگر به ردیابی در سطح اعلان از Cursor نیاز دارید، این خط لوله نمی‌تواند آن را به شما بدهد. نزدیک‌ترین چیزی که Cursor عرضه می‌کند [قلاب‌های](https://cursor.com/docs/hooks) سمت کارخواه است — فرایندهایی زاده‌شده که روی stdio ارتباط می‌گیرند و می‌توانند تله‌متری ساخت‌یافته را هرجا که بخواهید پیش بفرستند. صفحه‌های OpenTelemetry در Cursor قلاب‌ها را به‌عنوان جایگزین معرفی نمی‌کنند؛ صرفاً سازوکاری است که وجود دارد، و راهی است که باید خودتان بسازید و اینجا پوشش داده نمی‌شود.

## گام ۱ — ساختن کلید دریافت OneUptime

در OneUptime، ‏**Project Settings → Telemetry & APM → Ingestion Keys** را باز کنید و روی **Create Ingestion Key** بزنید. کلید را رونوشت کنید.

نشانی پایه OTLP شما `https://oneuptime.com/otlp` است، یا `https://YOUR-ONEUPTIME-HOST/otlp` اگر خودمیزبان هستید.

## گام ۲ — ساختن مقصد در Cursor

در داشبورد وب Cursor، به‌عنوان مدیر تیم **Team Settings → OpenTelemetry Export** را باز کنید، سپس:

1. **Create destination.** نشانی HTTPS پایه و هدر احراز هویت را وارد کنید.

   | فیلد                | مقدار                        |
   | ------------------- | ---------------------------- |
   | Endpoint (base URL) | `https://oneuptime.com/otlp` |
   | Header name         | `x-oneuptime-token`          |
   | Header value        | `YOUR_INGESTION_TOKEN`       |

   **نشانی پایه را بدون پسوند `/v1` وارد کنید.** خود Cursor ‏`/v1/metrics` و `/v1/logs` را به آن می‌افزاید. وارد کردن `https://oneuptime.com/otlp/v1` به `.../otlp/v1/v1/metrics` می‌انجامد و هیچ‌چیزی نمی‌رسد.

2. **Test connection.** Cursor این را به‌عنوان بررسی نشانی و احراز هویت مستند می‌کند؛ اینکه خود این بررسی چه چیزی گزارش می‌دهد مشخص نشده است.

3. **Enable.** صادرات ظرف حدود یک دقیقه آغاز می‌شود. ویرایش‌های بعدی هدرها یا اعتبارنامه‌ها ظرف حدود ۳۰ ثانیه اثر می‌کنند.

هدرها را Cursor رمزگذاری‌شده ذخیره می‌کند. فقط **یک** مقصد مدیریت‌شده تیمی پشتیبانی می‌شود — نمی‌توانید از خودِ Cursor هم‌زمان به OneUptime و پسانه‌ای دیگر پخش کنید. اگر به آن نیاز دارید، جمع‌کننده‌ای جلویش بگذارید.

### محدودیت پروتکل

‏Cursor **فقط OTLP/HTTP با protobuf دودویی** حرف می‌زند (`Content-Type: application/x-protobuf`، ‏HTTP POST). **‏gRPC پشتیبانی نمی‌شود. OTLP/JSON پشتیبانی نمی‌شود.** نقطه پایانی OTLP در OneUptime ‏protobuf دودویی روی HTTP را می‌پذیرد، پس جمع‌کننده‌ای در میانه لازم نیست — اما اگر نقشه داشتید Cursor را به دریافتی gRPC از آنِ خودتان نشانه بگیرید، وصل نخواهد شد.

دامنه ابزارگذاری روی هر چیزی که Cursor می‌فرستد `cursor.telemetry` نسخه `0.1.0` است.

### کلیدهای سیگنال و خانواده

‏Cursor می‌گذارد به ازای هر سیگنال و هر **خانواده** کلید بزنید. هر چهار خانواده پیش‌فرض روشن‌اند:

| خانواده                | پوشش می‌دهد                                                                                                                       |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `model_usage`          | `cursor.token.usage`، `cursor.cost.usage`، و رویدادهای گزارش `cursor.api.request` / `cursor.api.error` / `cursor.api.correction` |
| `tool_calls`           | `cursor.tool.calls`                                                                                                               |
| `skills_hooks_plugins` | `cursor.skill.activated`، `cursor.hook.execution_complete`، `cursor.plugin.installed`                                             |
| `cloud_agents`         | رویدادهای گزارش `cursor.cloud_agent.*`                                                                                            |

کلید مدیریتی‌ای هم هست، `auto_enable_new_families`، که تعیین می‌کند خانواده‌های تله‌متری‌ای که Cursor بعدها می‌افزاید خودکار روشن شوند یا نه. اگر داده تازه را بدون سر زدن دوباره به این صفحه می‌خواهید روشن نگهش دارید؛ اگر می‌خواهید هر افزوده را نخست بازبینی کنید خاموشش کنید.

## گام ۳ — اجازه دادن به IPهای خروجی Cursor (فقط خودمیزبان)

‏Cursor از مجموعه‌ای ثابت از نشانی‌های مبدأ صادر می‌کند. اگر دریافت خودمیزبان OneUptime شما پشت دیوار آتش یا WAF نشسته است، این شش نشانی `/32` را به‌صورت ورودی مجاز کنید:

```text
3.218.161.44
3.231.18.206
35.174.159.35
184.73.225.134
3.209.66.12
52.44.113.131
```

روی OneUptime Cloud (`https://oneuptime.com/otlp`) اینجا کاری برای انجام دادن نیست.

## سنجه‌هایی که Cursor می‌فرستد

هر سه، مجموع‌های **دلتای** یکنواخت‌اند. نقطه‌داده‌های سنجه **هیچ** شناسه گفتگو، درخواست یا رویداد مصرف را حمل نمی‌کنند — Cursor برای مهار کاردینالیتی حذفشان می‌کند — پس انتساب ابزار به ازای هر نشست و هزینه به ازای هر نشست از سنجه‌ها در دسترس نیست.

| سنجه                 | واحد                                        | ویژگی‌ها                                                                                                                                                                                                                                              |
| -------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `cursor.token.usage` | `{token}`                                   | `cursor.token.type` (همیشه؛ `input`، `output`، `cache_read`، `cache_creation`)، `cursor.model.name` (اختیاری)، `cursor.api.status` (اختیاری؛ `success`، `errored`، `aborted`)، `cursor.api.billable` (بولی اختیاری)                                  |
| `cursor.cost.usage`  | `USD` (عدد اعشاری)                          | `cursor.model.name` (اختیاری)                                                                                                                                                                                                                          |
| `cursor.tool.calls`  | `{call}` — مقدار ۱ به ازای هر فراخوان ابزار کامل‌شده | `cursor.tool.kind` (`builtin`، `mcp`)، `cursor.tool.name` (شناسه توکار مانند `read` یا `shell`، یا نام ابزار MCP شما)، `cursor.tool.status` (`success`، `failure`، `aborted`؛ فراخوان‌های MCP هرگز `aborted` گزارش نمی‌دهند)، `cursor.mcp.server.name` (فقط MCP) |

‏`cursor.model.name` همان مدل **عمومی** درخواست‌شده پس از فروکاست نیت مسیریابی‌شده است: Cursor ‏`auto:` را به `Auto`، `thinking:` را به `Thinking`، `pro:` را به `Pro` و `premium:` را به `Premium` بازنویسی می‌کند و هر چیز دیگری را عیناً عبور می‌دهد. روی Bugbot و هر جا که منبع مدلی نداشته باشد غایب است. پس تفکیک مدل سطلی خواهد داشت که عیناً `Auto` نام دارد و نمی‌توان آن را به مدل‌های زیرینی که Cursor به آن‌ها مسیریابی کرده تجزیه کرد — همان دلیلی که تفکیک Provider در دسترس نیست.

‏`cursor.tool.calls` و `cursor.cost.usage` فقط-سنجه‌اند — رویداد گزارشی که همان داده را حمل کند وجود ندارد.

چون این‌ها سنجه‌های معمولی OpenTelemetry هستند، می‌توانید روی **Dashboards** نمودارشان کنید و با [مانیتور سنجه‌ها](/docs/monitor/metrics-monitor) رویشان هشدار بگذارید — برای نمونه، نرخ شکست ابزار گروه‌شده بر `cursor.tool.name`، یا سوخت روزانه توکن گروه‌شده بر `cursor.model.name`.

### کلیدهای پیوند روی رکوردهای گزارش

| کلید                     | معنا                                                                                                                                                                 |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cursor.event.id`        | همیشه حاضر. **فقط کلید حذف تکراری** — مبهم و قطعی در سراسر تلاش‌های دوباره و بازپخش (با پیشوند `customer-telemetry:v1:`). کلید پیوند میان‌رویدادی نیست                |
| `cursor.source_event.id` | همیشه حاضر. هویت منبع درونی و مبهم؛ چند سیگنال ممکن است یک مقدار را مشترک داشته باشند                                                                                 |
| `cursor.conversation.id` | اختیاری. کلید پیوند نشست — در IDE و CLI یک UUID گفتگوی composer، و برای عامل‌های ابری شناسه‌ای `bc-...` که برای مشتری دیدنی است                                       |
| `cursor.usage_event.id`  | اختیاری؛ فقط روی `cursor.api.request`، `cursor.api.error` و `cursor.api.correction`. کلید دانه‌بندی درخواست که با صادرات مصرف و صورت‌حساب Cursor تطبیق می‌خورد        |
| `cursor.request.id`      | اختیاری. هرگز روی `cursor.api.correction` یا هیچ رویداد `cursor.cloud_agent.*` حاضر نیست                                                                              |

زیرعامل‌ها `cursor.conversation.id` مخصوص خودشان را می‌گیرند بی‌آنکه جمع‌بندی‌ای زیر والد باشد، پس فعالیت یک زیرعامل زیر نشستی که زاده‌اش کرده گروه نمی‌شود.

## انتساب کارمند

درباره محدودیت اینجا واقع‌بین باشید. **تنها هویتی که روی سیم OpenTelemetry در Cursor هست `cursor.user.id` است — عددی صحیح، مبهم و محدود به تیم که Cursor آن را اختیاری مستند می‌کند.** نه ایمیلی هست، نه نامی، و نه شناسه‌ای از SSO. راهنمایی خود Cursor این است که این شناسه روی عامل‌های ابری اغلب غایب است و نباید حضورش را الزامی بگیرید.

‏OneUptime با آنچه می‌گیرد چه می‌کند:

- ‏`cursor.user.id` کلید هویت **کارمند** شناخته‌شده‌ای است، پس جمع‌بندی خرج به ازای هر کاربر در زبانه **Usage** کار می‌کند — اما افراد را به‌صورت عدد صحیح شناسایی می‌کند.
- ‏`cursor.team.id` کلید **تیم** شناخته‌شده‌ای است، پس جمع‌بندی تیم و مرکز هزینه بدون هیچ پیکربندی اضافه‌ای کار می‌کند.
- هر دو به‌عنوان ویژگی منبع می‌آیند، که به OneUptime به‌صورت `resource.cursor.user.id` و `resource.cursor.team.id` می‌رسند. هر دو املا شناخته می‌شوند، و همین است که اصلاً این کار را ممکن می‌کند — تطبیقی که فقط کلید برهنه را ببیند هرگز حتی یک سطر Cursor را نمی‌دید.
- ستون **ایمیل کارمند** برای داده Cursor خالی می‌ماند. OneUptime آن را از `user.email` و معادل‌هایش می‌خواند، و Cursor هیچ‌کدام را نمی‌فرستد.

‏OneUptime عمداً `gen_ai.user`، `llm.user` یا شناسه‌های کاربر نهایی LiteLLM (`litellm.metadata.user_api_key_end_user_id`، `metadata.user_api_key_end_user_id`، `litellm.end_user.id`) را کارمند در نظر **نمی‌گیرد**. آن‌ها _مشتری_ پایین‌دستی خودِ فراخوان‌کننده را حمل می‌کنند، و نگاشتشان به کارمند بازپرداخت هزینه درونی نادرستی می‌سازد. این قاعده‌ای عمومی در سراسر [رصدپذیری هوش مصنوعی/LLM](/docs/telemetry/ai-llm-observability) است، نه ویژه Cursor.

### جایی که Cursor در زبانه Usage پدیدار می‌شود

‏Cursor سنجه منتشر می‌کند و اسپنی نه، و همین دقیقاً تعیین می‌کند زبانه Usage چه چیزی می‌تواند برایش نشان دهد.

**اسپن‌های GenAI مرجع‌اند؛ جریان سنجه بازگشتی است، هرگز افزوده‌ای نیست.** OneUptime فقط برای رقمی که جریان اسپن چیزی درباره‌اش گزارش نکرده به سنجه‌ها رجوع می‌کند، و هرگز آن دو را با هم جمع نمی‌زند — وگرنه منتشرکننده‌ای که هر دو سیگنال را تولید می‌کند دو بار شمرده می‌شد. پیامدش برای پروژه‌ای آمیخته صریح است: **اگر همان پروژه OneUptime از پیش اسپن‌های GenAI حامل هزینه داشته باشد، خرج Cursor پدیدار نمی‌شود.** اگر می‌خواهید اعدادش مستقل بایستند، مقصد Cursor را به پروژه‌ای از آنِ خودش (با کلید دریافت خودش) نشانه بگیرید.

وقتی این بازگشت واقعاً درگیر می‌شود:

| تفکیک                 | Cursor                                                                                           |
| --------------------- | ------------------------------------------------------------------------------------------------ |
| Employee              | **بله** — گروه‌شده بر `cursor.user.id` (در املای پیشونددارِ `resource.`)، به‌صورت عدد صحیح       |
| Team / cost centre    | **بله** — گروه‌شده بر `cursor.team.id`                                                           |
| Model                 | **بله** — `cursor.cost.usage` ویژگی `cursor.model.name` را حمل می‌کند                            |
| Provider              | **نه.** Cursor پشت یک اشتراک به چند ارائه‌دهنده مدل مسیریابی می‌کند و هرگز گزارش نمی‌دهد به کدام |
| Application / Service | **نه.** شمارنده هزینه Cursor به سرویس تله‌متری OneUptime وصل نیست                                |

و یک محدودیت که مردم را غافلگیر می‌کند: **سطری که منبعش سنجه است فقط هزینه حمل می‌کند.** خانه‌های Calls، Input tokens، Output tokens و Total tokens برای سطرهای Cursor به‌صورت `—` نمایش داده می‌شوند، چون `cursor.cost.usage` جزئیاتی به ازای هر فراخوان ندارد و `0` آنجا چنین خوانده می‌شد که «این توسعه‌دهنده هیچ فراخوانی نکرده است». مقدار `cursor.token.usage` هنوز کاشی‌های توکن ورودی/خروجی صفحه Overview را تغذیه می‌کند، و هنوز روی داشبورد و گروه‌شده بر `cursor.token.type` نمودارپذیر است — آنچه در دسترس نیست _ستون_ توکن به ازای هر کارمند در جدول Usage است. توجه کنید که در آن مجموع‌ها فقط گونه‌های توکن `input` و `output` شمرده می‌شوند؛ `cache_read` و `cache_creation` توکن‌های واقعی‌اند اما هیچ‌کدام از آن دو نیستند، پس به‌جای آنکه در آن‌ها ادغام شوند، کنار گذاشته می‌شوند.

### تبدیل شناسه کاربر به یک فرد

تبدیل `cursor.user.id` به یک نام — و گرفتن خرج به ازای هر کاربر در تراز صورت‌حساب به‌جای برآورد — به **Admin API** در Cursor نیاز دارد. **OneUptime امروز آن را پیمایش نمی‌کند**، پس اگر لازمش دارید این کاری است که خودتان اجرایش می‌کنید.

این API در `https://api.cursor.com` زندگی می‌کند، فقط Enterprise است، و با HTTP Basic احراز هویت می‌کند؛ کلید API شما همان _نام کاربری_ است و گذرواژه خالی:

```bash
curl -u YOUR_API_KEY: https://api.cursor.com/teams/members
```

کلید را در **cursor.com/dashboard → API Keys → New API Key** بسازید؛ یک بار نشان داده می‌شود، شکلش مانند `crsr_...` است، و به دامنه `admin:*` نیاز دارد.

دو نقطه پایانی مهم‌اند:

- **`GET /teams/members`** — فهرست اعضا. هر عضوی `id`، `email`، `name`، `role` (‏Cursor مقادیر `member` و `owner` را به‌عنوان نمونه مستند می‌کند، نه به‌عنوان مجموعه‌ای بسته — مقادیر دیگر را تاب بیاورید) و `isRemoved` دارد. توجه کنید که `id` اینجا **رشته‌ای رمزگذاری‌شده** مانند `user_PDSPmvukpYgZEDXsoNirw3CFhy` است، نه عدد صحیح. محدودیت نرخ ۲۰ درخواست در دقیقه به ازای هر تیم — پیش‌فرض Admin API برای بیشتر نقطه‌های پایانی؛ ۶۰ در دقیقه‌ای که پایین‌تر می‌آید ویژه `/teams/filtered-usage-events` است.
- **`POST /teams/filtered-usage-events`** — نمای پول. هر رویدادی `userEmail`، `model`، `kind`، `chargedCents`، `requestsCosts`، `isTokenBasedCall`، `isChargeable`، `isHeadless` و یک `timestamp` بر حسب میلی‌ثانیه از مبدأ زمان یونیکس را حمل می‌کند — که به‌صورت **رشته** JSON فرستاده می‌شود، پس پیش از حساب‌وکتاب تجزیه‌اش کنید. دو فیلد مشروط‌اند: `tokenUsage` (`inputTokens`، `outputTokens`، `cacheWriteTokens`، `cacheReadTokens`، `totalCents`، و `discountPercentOff` اختیاری) فقط وقتی حاضر است که `isTokenBasedCall` برابر `true` باشد، و `conversationId` برای رویدادهایی که گفتگوی مرتبطی ندارند حذف می‌شود. برای خرج، `chargedCents` را جمع بزنید — Cursor آن را به‌عنوان فیلدی مستند می‌کند که هزینه‌های سطح رویداد را با مجموع‌های `/teams/spend` و مجموع‌های داشبورد تطبیق می‌دهد، هم شامل هزینه مدل و هم Cursor Token Rate آنجا که آن نرخ صدق می‌کند. بدنه، `startDate` و `endDate` را بر حسب میلی‌ثانیه از مبدأ زمان یونیکس می‌گیرد (هر دو کران شامل‌اند)، به‌علاوه `userId` اختیاری (عدد)، `email`، `page` و `pageSize` (پیش‌فرض ۱۰۰، بیشینه ۱۰۰۰). محدودیت نرخ ۶۰ درخواست در دقیقه؛ داده ساعتی تجمیع می‌شود، پس دست‌بالا ساعتی یک بار پیمایش کنید.

پیوند بازگشتی به داده OneUptime شما **`conversationId`** است: Cursor آن را به‌عنوان کلید پیوند با منابع دیگری که شناسه گفتگو را نمایان می‌کنند مستند می‌کند، و همان فضای شناسه‌ای است که `cursor.conversation.id` روی سیم OTel دارد، و همین می‌گذارد ایمیل و رقمی دلاری و واقعی را به نشستی بچسبانید که از پیش برایش رویداد گزارش دارید. این **در هر دو سو اختیاری** است — Admin API آن را برای رویدادهای بدون گفتگوی مرتبط حذف می‌کند، و `cursor.conversation.id` ویژگی گزارشی اختیاری است. انتظار ته‌مانده‌ای از رویدادهای مصرف و رکوردهای گزارش را داشته باشید که نمی‌توان پیوندشان زد، و به‌جای فرض پوشش کامل، در سطل «انتساب‌نیافته» بگذاریدشان.

> **تأییدنشده:** Cursor مستند نمی‌کند که آیا عدد صحیح `cursor.user.id` روی سیم OTel همان فضای‌نام پالایه عددی `userId` در `/teams/filtered-usage-events` است یا نه. محتمل است، و Cursor دست‌کم سه فضای‌نام متمایز برای شناسه کاربر به کار می‌برد (رشته‌های رمزگذاری‌شده `user_...`، شناسه‌های عددی، و عدد صحیح OTel). بازپرداخت هزینه را بر آن فرض نسازید مگر آنکه در برابر مستأجر خودتان تأییدش کنید، و به‌جای صورت‌حساب بستن به نام فرد نادرست، نرم به سطل «انتساب‌نیافته» شکست بخورید.

## معناشناسی تحویل

این‌ها پانوشت نیستند — آنچه در نمودارها می‌بینید را عوض می‌کنند، پس پیش از آنکه اشکالی علیه OneUptime ثبت کنید بدانیدشان.

- **سنجه‌ها حداکثر یک بار تحویل می‌شوند.** صادرات سنجه‌ای که شکست بخورد هرگز دوباره تلاش یا بازپخش نمی‌شود. پس از شکست، شکاف‌های کوتاه در مجموع‌های دلتا انتظار می‌رود. **برای داده Cursor روی شکاف‌های سنجه هشدارهای حادثه‌ساز نسازید.**
- **گزارش‌ها دست‌کم یک بار تحویل می‌شوند**، با حذف تکراری بر `cursor.event.id`. شکست‌های گذرا حدود ۷ روز خودکار بازیابی می‌شوند. ردهای پایانی (‏4xx پایدار، بارهای بدریخت) بازپخش نمی‌شوند.
- **همه سنجه‌ها زمانمندی دلتا دارند.** آن‌ها را به‌عنوان مجموع دلتاها مصرف کنید. پردازنده‌ای که سخت‌گیرانه دلتا را به تجمعی تبدیل کند ممکن است نقطه‌هایی با زمان پایان وارونه را بیندازد، و پنجره‌های تخلیه برای همان سری می‌توانند هم‌پوشانی کنند.
- **هیچ تضمین ترتیبی نیست.** رویداد `cursor.api.correction` ‏_پس از_ درخواستی می‌رسد که اصلاحش می‌کند. بر مُهر زمانی رکورد مرتب کنید، هرگز بر زمان رسیدن.
- **موفقیت جزئی OTLP رعایت می‌شود.** اقلام ردشده درون دسته‌ای پذیرفته‌شده دوباره فرستاده نمی‌شوند.
- **بدون پرکردن گذشته.** هیچ‌چیزی از پیش از فعال کردن مقصد هرگز نخواهد رسید، و نگهداشت منبع بالادستی Cursor حدود ۷ روز است — پس مقصدی که یک هفته خراب رها شود آن هفته را برای همیشه از دست می‌دهد.
- **غیرفعال کردن یا حذف یک مقصد، داده در حال پرواز را می‌اندازد.** برای چرخاندن کلید دریافت OneUptime، به‌جای حذف و افزودن دوباره، هدر مقصد موجود را **ویرایش** کنید. ویرایش ظرف حدود ۳۰ ثانیه اثر می‌کند.

### خواندن اصلاح‌ها

رویداد گزارش `cursor.api.correction` نهایی‌سازی صورت‌حساب است: یعنی رویداد مصرفی عطف به ماسبق صورت‌حساب **نشده** است. آن را بر `cursor.usage_event.id` به `cursor.api.request` یا `cursor.api.error` متناظرش پیوند بزنید و کل گروه را صورت‌حساب‌نشده در نظر بگیرید. چون اصلاح‌ها دیر و بی‌ترتیب می‌رسند، هر رقم خرجی که از داده تازه Cursor محاسبه می‌کنید تا وقتی پنجره اصلاحش نگذشته موقتی است.

## هزینه برآورد است، نه صورت‌حساب

مقدار `cursor.cost.usage` را Cursor صریحاً **برآوردی در حد توان** مستند می‌کند. آن را خط روند بگیرید، نه صورت‌حساب:

- یک سری هم برداشت از سهمیه گنجانده‌شده و هم مصرف درخواستی را پوشش می‌دهد — آن‌ها را از هم جدا نمی‌کند.
- برای راه‌اندازی‌های BYOK فقط Cursor Token Rate را بازتاب می‌دهد، نه آنچه ارائه‌دهنده مدلتان واقعاً از شما می‌گیرد.
- اصلاح‌ها (بالا) می‌توانند مصرفی را که سنجه پیش‌تر شمرده، عطف به ماسبق از صورت‌حساب بردارند.

برای رقمی که بتوانید با صورت‌حساب تطبیقش دهید، `chargedCents` را از `POST /teams/filtered-usage-events` روی Admin API جمع بزنید. هر چیزی که OneUptime برای خرج Cursor نشان می‌دهد از `cursor.cost.usage` می‌آید و همان ملاحظات را هم به ارث می‌برد.

## تأیید اینکه رسیده است

پس از فعال کردن مقصد، یکی دو دقیقه از Cursor استفاده کنید، سپس در OneUptime:

1. **Logs** را باز کنید و روی نام سرویس `cursor` پالایه بزنید. باید رکوردهای `cursor.api.request` را با شمار توکن‌ها ببینید. این سریع‌ترین تأیید این است که هم احراز هویت و هم نقطه پایانی درست‌اند.
2. **Metrics** را روی `cursor.token.usage` باز کنید (یا نموداری به داشبورد بیفزایید)، گروه‌شده بر `cursor.token.type`. یادتان باشد که مجموعی دلتاست.
3. **AI / LLM → Usage** را باز کنید. هزینه برآوردی Cursor باید در تفکیک‌های Employee، Team و Model پدیدار شود، منتسب بر `cursor.user.id`، `cursor.team.id` و `cursor.model.name`، با جدولی که برچسب **from GenAI metrics** خورده است. اگر خالی است، بررسی کنید که آیا این پروژه اسپن‌های GenAI هم دریافت می‌کند — [جایی که Cursor در زبانه Usage پدیدار می‌شود](#where-cursor-shows-up-in-the-usage-tab) را ببینید.

هیچ‌چیزی نمی‌رسد؟

- در Cursor دوباره **Test connection** را اجرا کنید — Cursor آن را به‌عنوان بررسی نشانی و احراز هویت مستند می‌کند.
- نشانی را از نظر بخش مسیر دوتاشده بررسی کنید — نشانی پایه نباید به `/v1` ختم شود.
- هدر را دوباره بررسی کنید: نام `x-oneuptime-token`، و مقدار دقیقاً همان کلید دریافت. توکن نادرست هنگام دریافت رد می‌شود.
- اگر خودمیزبان هستید، تأیید کنید که آن شش [IP خروجی](#step-3-allow-cursors-egress-ips-self-hosted-only) به دریافت شما می‌رسند و نقطه پایانی به‌طور عمومی در DNS قابل تفکیک است.
- تأیید کنید کلید خانواده مربوطه روشن است — `model_usage` برای توکن و هزینه، `tool_calls` برای سنجه‌های ابزار.
- یک دقیقه فرصت بدهید. صادرات حدود یک دقیقه پس از فعال‌سازی آغاز می‌شود، و ویرایش اعتبارنامه‌ها حدود ۳۰ ثانیه می‌برد.
