# عامل Kubernetes در OneUptime (‏Helm)

## نمای کلی

عامل Kubernetes در OneUptime نمودار Helmی از پیش بسته‌بندی‌شده است که خط لوله جمع‌کننده‌ای بر پایه OpenTelemetry را روی خوشه شما نصب می‌کند. سنجه‌های گره، پاد، کانتینر و خوشه؛ رویدادهای Kubernetes؛ گزارش‌های پاد؛ و — با eBPFای که به‌طور پیش‌فرض روشن است — ردیابی‌های برنامه، سنجه‌های RED مربوط به HTTP، داده نمودار سرویس و سنجه‌های جریان شبکه پاد به پاد را می‌فرستد. با `cost.enabled=true` علاوه بر این‌ها **تخصیص‌های هزینه** به ازای هر بار کاری را هم می‌فرستد (خرج به تفکیک فضای‌نام/بار کاری/پاد، ظرفیت بیکار، کارایی). نه تغییری در کد، نه SDKای، فقط یک `helm install`.

این صفحه **راهنمای نصب** است. برای پیکربندی مانیتورها و هشدارهای Kubernetes روی داده‌ای که عامل جمع می‌کند، [عامل Kubernetes (مانیتورها)](/docs/monitor/kubernetes-agent) را ببینید. برای رصدپذیری هزینه، [رصدپذیری هزینه Kubernetes](/docs/telemetry/kubernetes-cost) را ببینید.

## پیش‌نیازها

- خوشه‌ای Kubernetes که در حال اجراست (‏v1.23 یا بالاتر)
- ‏`kubectl` پیکربندی‌شده برای دسترسی به خوشه‌تان
- ‏`helm` نسخه ۳ نصب‌شده
- یک **کلید API در OneUptime** — یکی را از _Project Settings → API Keys_ بسازید

## گام ۱ — افزودن مخزن Helm در OneUptime

```bash
helm repo add oneuptime https://helm-chart.oneuptime.com
helm repo update
```

## گام ۲ — برگزیدن پیش‌تنظیمی برای خوشه‌تان

نمودار یک گزینه سطح‌بالای یگانه در معرض می‌گذارد — `preset` — که پیش‌فرض‌های سازگار با توزیع Kubernetes شما را برمی‌گزیند. چیزهایی را کنترل می‌کند که وگرنه باید دستی تنظیمشان می‌کردید: اینکه گزارش‌ها از راه DaemonSetای با hostPath فرستاده شوند یا از راه API‏ Kubernetes، و اینکه چه زمینه امنیتی‌ای اعمال شود.

| `preset`               | برای                                                                               | جمع‌آوری گزارش                                                     |
| ---------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `standard` _(پیش‌فرض)_ | خوشه‌های خودمدیریت، **EKS on EC2**، **GKE Standard**، **AKS**، minikube، kind، k3s | ‏DaemonSetای که `/var/log/pods` را از راه hostPath می‌خواند (کمترین سربار)   |
| `gke-autopilot`        | **GKE Autopilot**                                                                     | ‏Deployment دنبال‌کننده گزارش از API‏ Kubernetes (نه hostPath، نه دسترسی به میزبان) |
| `eks-fargate`          | **EKS Fargate**                                                                       | ‏Deployment دنبال‌کننده گزارش از API‏ Kubernetes (نه hostPath، نه دسترسی به میزبان) |

اگر مطمئن نیستید، با `standard` شروع کنید. اگر نصب با خطای Pod Security که به `hostPath` اشاره می‌کند شکست خورد، با `preset=gke-autopilot` (یا روی Fargate با `eks-fargate`) دوباره اجرایش کنید و کار می‌کند.

## گام ۳ — نصب عامل Kubernetes

مقادیر `YOUR_ONEUPTIME_URL`، `YOUR_ONEUPTIME_API_KEY` و نام خوشه را با مقادیر محیط خودتان جایگزین کنید. نام خوشه همان چیزی است که خوشه با آن در OneUptime پدیدار می‌شود — چیزی پایدار مانند `prod-us-east-1` برگزینید.

### خوشه‌های استاندارد (خودمدیریت، EKS on EC2، GKE Standard، AKS)

```bash
helm install kubernetes-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent \
  --create-namespace \
  --set oneuptime.url="YOUR_ONEUPTIME_URL" \
  --set oneuptime.apiKey="YOUR_ONEUPTIME_API_KEY" \
  --set clusterName="my-cluster"
```

### GKE Autopilot

```bash
helm install kubernetes-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent \
  --create-namespace \
  --set oneuptime.url="YOUR_ONEUPTIME_URL" \
  --set oneuptime.apiKey="YOUR_ONEUPTIME_API_KEY" \
  --set clusterName="my-cluster" \
  --set preset=gke-autopilot
```

### EKS Fargate

```bash
helm install kubernetes-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent \
  --create-namespace \
  --set oneuptime.url="YOUR_ONEUPTIME_URL" \
  --set oneuptime.apiKey="YOUR_ONEUPTIME_API_KEY" \
  --set clusterName="my-cluster" \
  --set preset=eks-fargate
```

## گام ۴ — وارسی نصب

بررسی کنید پادهای عامل در حال اجرا باشند:

```bash
kubectl get pods -n oneuptime-agent
```

روی خوشه‌ای **استاندارد** یک Deployment جمع‌کننده خوشه به‌علاوه یک پاد DaemonSet جمع‌کننده گره به ازای هر گره می‌بینید:

```
NAME                                          READY   STATUS    RESTARTS   AGE
kubernetes-agent-xxxxxxxxxx-xxxxx             1/1     Running   0          1m
kubernetes-agent-logs-xxxxx                   1/1     Running   0          1m
kubernetes-agent-logs-yyyyy                   1/1     Running   0          1m
```

روی **GKE Autopilot** جمع‌کننده گره همچنان اجرا می‌شود — سنجه‌های kubelet و cAdvisor را بدون نیاز به hostPath جمع می‌کند — و Deployment دیگری گزارش‌های پاد را از راه API‏ Kubernetes دنبال می‌کند:

```
NAME                                          READY   STATUS    RESTARTS   AGE
kubernetes-agent-xxxxxxxxxx-xxxxx             1/1     Running   0          1m
kubernetes-agent-logs-yyyyyyyyyy-yyyyy        1/1     Running   0          1m
kubernetes-agent-logs-xxxxx                   1/1     Running   0          1m
```

روی **EKS Fargate** دو Deployment و هیچ DaemonSetی نمی‌بینید — Fargate به هر پاد ماشین مجازی خُرد خودش را می‌دهد و هرگز DaemonSet زمان‌بندی نمی‌کند، پس سنجه‌های سطح گره آنجا در دسترس نیستند:

```
NAME                                          READY   STATUS    RESTARTS   AGE
kubernetes-agent-xxxxxxxxxx-xxxxx             1/1     Running   0          1m
kubernetes-agent-logs-yyyyyyyyyy-yyyyy        1/1     Running   0          1m
```

به‌محض اینکه عامل وصل شود، خوشه‌تان خودکار در بخش **Kubernetes** داشبورد OneUptime پدیدار می‌شود.

## گزینه‌های پیکربندی

### پالایش فضای‌نام

مقدار `namespaceFilters.rules` الگوهای فضای‌نام را مستقل بر چهار دامنه اعمال می‌کند:

| دامنه | کجا پالایش می‌کند | بر چه چیزی اثر می‌گذارد |
| ----- | ---------------- | --------------- |
| `podLogs` | در گیرنده filelog روی hostPath یا در دنبال‌کننده گزارش API | فقط stdout/stderr پاد؛ رویدادهای Kubernetes و گزارش‌های ممیزی دست‌نخورده می‌مانند |
| `ebpfDiscovery` | در کشف فرایند OBI | هم ردیابی‌های eBPF و هم سنجه‌های eBPF از بارهای کاری منطبق |
| `metrics` | در جمع‌کننده، پس از غنی‌سازی با فراداده Kubernetes | سری‌های سنجه فضای‌نام‌دار؛ سری‌های گره/خوشه که فضای‌نامی ندارند نگه داشته می‌شوند |
| `traces` | در جمع‌کننده، پس از غنی‌سازی با فراداده Kubernetes | هم اسپن‌های eBPF و هم اسپن‌های OTLPای که خود برنامه می‌فرستد |

الگوهای فضای‌نام با نام کامل تطبیق می‌یابند و از `*` پشتیبانی می‌کنند (`team-*`). اگر دامنه‌ای هر قاعده `include`ای داشته باشد، برای آن دامنه فقط فضای‌نام‌های منطبق نگه داشته می‌شوند. قاعده‌های `exclude` همیشه برنده‌اند. قاعده پیش‌فرض `kube-system` را فقط از `podLogs` و `ebpfDiscovery` بیرون می‌گذارد.

برای محدود کردن گزارش‌های پاد و کشف eBPF به فضای‌نام‌هایی مشخص:

```bash
helm install kubernetes-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent \
  --create-namespace \
  --set oneuptime.url="YOUR_ONEUPTIME_URL" \
  --set oneuptime.apiKey="YOUR_ONEUPTIME_API_KEY" \
  --set clusterName="my-cluster" \
  --set-json 'namespaceFilters.rules=[{"action":"include","namespaces":["default","production","staging"],"scopes":["podLogs","ebpfDiscovery"]}]'
```

برای اینکه گزارش‌های فضای‌نامی پرسروصدا را بازدارید اما ردیابی‌های eBPF، نقشه سرویس و سنجه‌هایش را نگه دارید، حذف را به `podLogs` دامنه بدهید:

```bash
  --set-json 'namespaceFilters.rules=[{"action":"exclude","namespaces":["kube-system"],"scopes":["podLogs","ebpfDiscovery"]},{"action":"exclude","namespaces":["noisy-*"],"scopes":["podLogs"]}]'
```

قاعده‌های `podLogs` و `ebpfDiscovery` در سرچشمه پالایش می‌کنند: پرونده‌های گزارش حذف‌شده هرگز باز نمی‌شوند و بارهای کاری حذف‌شده هرگز ابزارگذاری نمی‌شوند. قاعده‌های `metrics` و `traces` دیرتر در جمع‌کننده عمل می‌کنند، پس از اینکه فضای‌نام به‌عنوان فراداده منبع چسبانده شد.

#### پالایش سنجه‌ها و ردیابی‌ها بر پایه فضای‌نام

وقتی می‌خواهید سنجه‌ها یا اسپن‌های فضای‌نام‌دار را هم بپالایید، همان دامنه‌ها را مستقیم به قاعده بیفزایید:

```bash
  --set-json 'namespaceFilters.rules=[{"action":"exclude","namespaces":["kube-system","noisy-*"],"scopes":["podLogs","ebpfDiscovery","metrics","traces"]}]'
```

> **سنجه‌های سطح گره و سطح خوشه همیشه نگه داشته می‌شوند.** فضای‌نام ویژگی پاد است، نه گره، پس سری‌هایی مانند CPU گره، حافظه گره و مصرف سامانه پرونده چیزی برای تطبیق ندارند و هرگز انداخته نمی‌شوند. قاعده فضای‌نامی با دامنه `metrics` کاردینالیتی هر پاد را می‌تراشد بی‌آنکه شما را نسبت به خراب شدن گره‌ای کور کند.

**رویدادهای** Kubernetes در عامل بر پایه فضای‌نام پالایش‌پذیر نیستند. از گیرنده `k8sobjects` بدون ویژگی `k8s.namespace.name` می‌رسند — فضای‌نام درون بدنه رویداد است — پس چیزی نیست که پالایه‌ای با آن تطبیق دهد. به‌جایش آن‌ها را سمت کارساز بیندازید (پایین‌تر را ببینید).

### پالایش بر پایه شدت گزارش

مقدار `filters.logs.minSeverity` رکوردهای **گزارش پاد** را که زیر شدتی باشند، در خود عامل و پیش از فرستادن هر چیزی می‌اندازد:

```bash
  --set filters.logs.minSeverity=WARN
```

مقادیر `TRACE`، `DEBUG`، `INFO`، `WARN`، `ERROR` و `FATAL` را می‌پذیرد. مقدار `WARN` سطوح WARN، ERROR و FATAL را نگه می‌دارد و INFO، DEBUG و TRACE را می‌اندازد. پیش‌فرض (`""`) همه‌چیز را نگه می‌دارد. در **هر دو** حالت گزارش اعمال می‌شود — در حالت `daemonset` از راه جمع‌کننده، و در حالت `api` درون خود دنبال‌کننده گزارش — پس پیش‌تنظیم‌ها نمی‌توانند بی‌خبر از شما خاموشش کنند.

زمان‌های اجرای کانتینر شدتی روی خط گزارش ثبت نمی‌کنند، پس عامل خودش شدت را از متن گزارش بیرون می‌کشد (`[ERROR]`، `WARN:`، `"level":"info"`، …).

> **رویدادهای Kubernetes و مشخصات منابع هرگز با این پالایش نمی‌شوند.** این‌ها از API‏ Kubernetes می‌رسند و شدتی از خود ندارند، پس آستانه‌ای به‌جای نازک کردن، کل خوراک را پاک می‌کرد — از جمله همان اخطارهای `FailedScheduling`، `BackOff` و `OOMKilling` که بیش از همه می‌خواهیدشان. کم‌حجم و پرارزش‌اند، پس عامل همیشه می‌فرستدشان. برای نازک کردنشان به‌جای این، از **Logs → Settings → Drop Filters** سمت کارساز در داشبورد استفاده کنید.

**اینکه بر سر خطی بدون سطح قابل‌تشخیص چه می‌آید به حالت گزارش بستگی دارد**، چون این دو حالت اطلاعات متفاوتی در دست دارند:

| حالت | خط بی‌برچسب | چرا |
| ---- | --------------- | --- |
| `daemonset` | `stderr` → به‌عنوان ERROR گرفته می‌شود (نگه داشته می‌شود)، `stdout` → به‌عنوان INFO گرفته می‌شود (با آستانه WARN انداخته می‌شود) | زمان اجرای کانتینر ثبت می‌کند هر خط از کدام جریان آمده است. |
| `api` | همیشه **نگه داشته می‌شود** | ‏API‏ `pods/log` در Kubernetes، ‏stdout و stderr را در یک جریان یگانه و بدون نشانگر هر خط ادغام می‌کند. عامل به‌جای حدس زدن، خط را نگه می‌دارد. |

> پس حالت `api` اکیداً کمتر از حالت `daemonset` می‌اندازد. این عمدی است: ردگیری پشته Python یا `npm ERR!` هیچ کلیدواژه شدتی حمل نمی‌کند، و خاموشانه پاک کردنش دقیقاً همان شکستی است که قرار بوده آستانه شدت از آن محافظتتان کند.
>
> در حالت دورگه (`logs.windowsPods.enabled`) هر دو سطر هم‌زمان صدق می‌کنند، شکافته بر پایه سیستم‌عامل گره: پادهای Linux از سطر `daemonset` پیروی می‌کنند و پادهای Windows از سطر `api` — پس زیر آستانه شدت، پادهای Windows می‌توانند خط‌های بی‌کلیدواژه بیشتری از پادهای Linux بفرستند.

رویدادهای چندخطی در هر دو حالت **پیش از** پالایش دوباره به هم چسبانده می‌شوند، پس ردگیری پشته Java بر پایه نخستین خطش داوری می‌شود و یکپارچه نگه داشته یا انداخته می‌شود — هرگز خط `ERROR` برهنه‌ای با قاب‌های کنده‌شده نمی‌گیرید.

### گنجاندن یا حذف سنجه‌ها بر پایه نام

مقدار `filters.metrics` تعیین می‌کند چه سنجه‌هایی خوشه را ترک کنند، در سراسر هر گیرنده‌ای در خط لوله.

**انداختن چند سنجه پرسروصدا** (فهرست ممنوع — معمولاً همان چیزی که می‌خواهید):

```bash
  --set-json 'filters.metrics.exclude=["k8s.volume.available","k8s.volume.capacity"]'
```

**فرستادن فقط مجموعه‌ای ثابت** (فهرست مجاز — هر چیز دیگری انداخته می‌شود):

```bash
  --set-json 'filters.metrics.include=["k8s.pod.cpu.utilization","k8s.pod.memory.usage"]'
```

**تطبیق بر پایه الگو** به‌جای نام دقیق:

```bash
  --set filters.metrics.matchType=regexp \
  --set-json 'filters.metrics.exclude=["^container_network_"]'
```

| کلید | معنا |
| --- | ------- |
| `filters.metrics.exclude` | نام سنجه‌هایی که انداخته شوند. روی `include` اعمال می‌شود، پس حذف همیشه برنده است. |
| `filters.metrics.include` | وقتی ناتهی باشد، **فقط** این‌ها فرستاده می‌شوند. |
| `filters.metrics.matchType` | `strict` (نام دقیق، پیش‌فرض) یا `regexp` (‏RE2، **بدون لنگر**). |

یادداشت‌هایی که یک حادثه برایتان صرفه‌جویی می‌کنند:

- ‏`regexp` **بدون لنگر** است — `system.cpu` با `system.cpu.time` هم می‌خواند. وقتی دقیقاً یک سنجه را در نظر دارید لنگرش بیندازید (`^system\.cpu$`).
- ‏RE2 **پیش‌نگری ندارد**، پس `^(?!container_)` کامپایل نمی‌شود. «هر چیزی جز» را با `include` بیان کنید، نه با عبارت باقاعده منفی.
- ‏`include` هم‌زمان همه گیرنده‌ها را در بر می‌گیرد. فهرست مجازی که سنجه‌ای را از قلم بیندازد، خاموشانه مانیتورهای ساخته‌شده بر آن را برمی‌دارد. مگر واقعاً مجموعه‌ای بسته بخواهید، `exclude` را ترجیح دهید.
- برای فهرست‌ها از `--set-json` (یا پرونده‌ای از مقادیر) استفاده کنید. `--set` ساده فهرست را به‌جای ادغام، جایگزین می‌کند.

> **پیش از گستراندن عبارت باقاعده، آزمایشش کنید.** الگوها هنگام راه‌اندازی به‌دست جمع‌کننده کامپایل می‌شوند، نه به ازای هر رکورد، پس الگوی نامعتبر خاموشانه بدرفتاری نمی‌کند — جمع‌کننده از راه‌اندازی سر باز می‌زند و به CrashLoopBackOff می‌رود و **گزارش‌های** آن جمع‌کننده را هم همراه سنجه‌هایش پایین می‌کشد. Helm نمی‌تواند RE2 را کامپایل کند، پس `helm upgrade` الگوی بد را بی‌هیچ گلایه‌ای می‌پذیرد.

### نمونه‌برداری از ردیابی

پالایه‌های بالا یک **رده** از تله‌متری را برمی‌دارند — یک فضای‌نام، یک شدت، یک نام سنجه. نمونه‌برداری فرق دارد: هر رده را نگه می‌دارد و به‌جایش جمعیت را نازک می‌کند. مقدار `sampling.traces.percentage` را روی سهمی از ردیابی‌ها که می‌خواهید نگه دارید بگذارید:

```bash
helm upgrade kubernetes-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent --reuse-values \
  --set sampling.traces.percentage=10
```

این یک ردیابی از هر ده تا را نگه می‌دارد و نُه تای دیگر را در خود عامل، پیش از ترک خوشه‌تان، می‌اندازد.

**ردیابی‌های کامل می‌گیرید، نه تکه‌پاره.** تصمیم درهم‌سازی شناسه ردیابی است، نه شیر یا خط به ازای هر اسپن، پس هر اسپن یک ردیابی با هم نگه داشته یا انداخته می‌شود — ردیابی‌هایی که جان به در می‌برند از سر تا ته کامل و خواندنی‌اند. همین ویژگی است که روشن کردن نمونه‌برداری را امن می‌کند.

**مانیتورهای سنجه‌محورتان تکان نمی‌خورند.** سنجه‌های RED مربوط به eBPF — نرخ درخواست، نرخ خطا، طول مدت — خانواده‌ای *سنجه‌ای* هستند. OBI آن‌ها را از هر درخواستی محاسبه می‌کند و از خط لوله سنجه‌ها می‌گذرند، که نمونه‌بردار در آن نیست. با `percentage: 10` یک‌دهم ردیابی‌ها را می‌گیرید و نرخ/خطا/تأخیر ۱۰۰٪ دقیق. داشبوردها و مانیتورهای ساخته‌شده بر آن سنجه‌ها دست‌نخورده می‌مانند.

**اما مانیتورهای اسپن‌محورتان تکان می‌خورند.** هر چیزی که OneUptime از خود اسپن‌ها مشتق می‌کند با همان نرخ کوچک می‌شود — پیش از روشن کردن این، اخطار پایین‌تر را ببینید.

| کلید | معنا |
| --- | ------- |
| `sampling.traces.percentage` | درصد ردیابی‌هایی که **نگه داشته** شوند، ۰ تا ۱۰۰. پیش‌فرض `100` (نگه داشتن همه‌چیز). |
| `sampling.traces.hashSeed` | بذر درهم‌سازی شناسه ردیابی. پیش‌فرض `22`. |

یادداشت‌هایی که یک حادثه برایتان صرفه‌جویی می‌کنند:

- **‏`0` هیچ ردیابی‌ای نگه نمی‌دارد.** این یک نرخ است، نه کلید خاموشی — هر ردیابی را پاک می‌کند در حالی که DaemonSet‏ eBPF همچنان اجرا می‌شود و برایتان هزینه دارد. اگر ردیابی نمی‌خواهید، از `ebpf.enabled=false` استفاده کنید. اگر ردیابی نمی‌خواهید اما سنجه‌های RED و نقشه سرویس را *می‌خواهید*، eBPF را روشن نگه دارید و این را عمداً روی `0` بگذارید.
- **فقط وقتی `ebpf.enabled` باشد اعمال می‌شود.** وگرنه خط لوله ردیابی‌ها اصلاً وجود ندارد، پس با `ebpf.enabled=false` این مقدار کاری نمی‌کند.
- **فقط ردیابی‌ها.** نه `sampling.logs`ای هست و نه `sampling.metrics`ای، و این عمدی است — یادداشت پایین‌تر را ببینید.
- **کسرها به `--set-json` نیاز دارند، و کفی دارند.** ‏`--set sampling.traces.percentage=0.5` شکست می‌خورد، چون Helm‏ `0.5` را رشته می‌خواند — از `--set-json 'sampling.traces.percentage=0.5'` یا پرونده‌ای از مقادیر استفاده کنید. عددهای درست با `--set` بی‌دردسر کار می‌کنند. زیر حدود `0.0061` نرخ به صفر کوانتیده می‌شود و دقیقاً مانند `0` رفتار می‌کند — هر ردیابی انداخته می‌شود، بی‌هیچ خطایی. مقدار `0.01` (یک در ده هزار) کوچک‌ترین مقداری است که همان کاری را می‌کند که می‌گوید.
- **حالت چندخوشه‌ای به‌طور پیش‌فرض کار می‌کند.** دو عامل تنها وقتی همان ردیابی را نگه می‌دارند که بر سر هر دوی `hashSeed` و `percentage` هم‌داستان باشند. هر دو همه‌جا پیش‌فرض یکسانی دارند، پس ردیابی‌ای که از دو خوشه می‌گذرد بی‌هیچ پیکربندی اضافه‌ای یکپارچه جان به در می‌برد. `hashSeed` را فقط برای *ناهمبسته کردن* عمدی دو لایه نمونه‌برداری تغییر دهید — چون تصمیم آستانه‌ای روی همان درهم‌سازی است، همان بذر با نرخ‌های متفاوت تودرتو می‌شود، پس لایه دوم به‌جای قرعه مستقل، همان ردیابی‌هایی را که لایه اول از پیش نگه داشته دوباره برمی‌گزیند.
- **از گزارش‌های پاد هرگز نمونه‌برداری نمی‌شود**، پس با `ebpf.logToTraceCorrelation: true` هر رکورد گزارش همچنان شناسه ردیابی حمل می‌کند در حالی که فقط `percentage`٪ آن ردیابی‌ها نگه داشته می‌شوند. تقریباً (‏۱۰۰ − `percentage`)٪ رکوردهای گزارش پیوند ردیابی‌ای نشان می‌دهند که به بن‌بست می‌خورد. پیمایش ردیابی → گزارش‌ها دست‌نخورده است؛ فقط گزارش‌ها → ردیابی می‌تواند خطا بخورد.

> **وقتی این را تنظیم می‌کنید، مانیتورهای اسپن‌محورتان را دوباره کوک کنید.** نمونه‌برداری از اسپن‌هایی که به OneUptime می‌رسند می‌کاهد، پس هر چیزی که آن‌ها را می‌شمارد کمتر می‌شمارد: مانیتور **Traces** روی `Span Count` و مانیتور **Exceptions** روی `Exception Count` تقریباً `percentage`٪ حجم دیروز را می‌بینند. آستانه‌ای که روی ترافیک نمونه‌برداری‌نشده کوک شده خاموشانه دیگر رد نمی‌شود — مانیتور خطا نمی‌دهد، فقط ساکت می‌شود. هنگام تنظیم نرخ، آن آستانه‌ها را بر همان ضریب تقسیم کنید؛ نرخ در سطح کل خوشه است، پس راهی برای معاف کردن سرویسی منفرد از آن نیست. **گروه‌بندی** خطاها بدتر از خطی تنزل می‌کند: استثنایی رایج هنوز رو می‌آید، اما استثنایی نادر و یک‌باره بیشتر احتمال دارد به‌کل ناپدید شود تا اینکه یک‌دهمِ دفعات پدیدار شود.

> **چرا اینجا نمونه‌برداری از گزارش یا سنجه نیست.** نمونه‌بردار جمع‌کننده اصلاً نمی‌تواند از سنجه‌ها نمونه بردارد. می‌تواند از گزارش‌ها نمونه بردارد، اما تصادفی بودنش را از شناسه ردیابی می‌گیرد — و گزارش‌های پاد چنین چیزی ندارند. آنگاه هر رکورد بی‌شناسه‌ردیابی به همان سطل درهم می‌رود، پس نرخی برای گزارش خوراک را نازک نمی‌کرد: بسته به بذر یا همه‌اش را نگه می‌داشت یا همه‌اش را پاک می‌کرد. نمودار به‌جای عرضه کردن پیچی که خاموشانه گزارش‌هایتان را پاک می‌کند، اصلاً چنین چیزی پیشنهاد نمی‌دهد. گزارش‌ها را با [پالایش بر پایه شدت گزارش](#filtering-by-log-severity) و [پالایش فضای‌نام](#namespace-filtering) نازک کنید، که درباره آنچه برمی‌دارند دقیق‌اند.

### از کار انداختن جمع‌آوری گزارش

اگر به گزارش‌های پاد نیاز ندارید:

```bash
helm install kubernetes-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent \
  --create-namespace \
  --set oneuptime.url="YOUR_ONEUPTIME_URL" \
  --set oneuptime.apiKey="YOUR_ONEUPTIME_API_KEY" \
  --set clusterName="my-cluster" \
  --set logs.enabled=false
```

سنجه‌هایتان دست‌نخورده می‌مانند: جمع‌کننده گره برای kubelet، cAdvisor و سنجه‌های میزبان به کارش ادامه می‌دهد و فقط خواندن گزارش‌های پاد را وامی‌نهد. هشدارهای گزارش‌محور می‌ایستند و چیز دیگری نمی‌ایستد.

### وادار کردن به حالت جمع‌آوری گزارش مشخص

کاربران پیشرفته می‌توانند انتخاب پیش‌تنظیم را با `logs.mode` بازنویسی کنند:

- `logs.mode=daemonset` — ‏DaemonSet با hostPath (کمترین سربار، به hostPath نیاز دارد)
- `logs.mode=api` — ‏Deployment دنبال‌کننده گزارش از API‏ Kubernetes (روی هر خوشه‌ای کار می‌کند)
- `logs.mode=disabled` — بدون جمع‌آوری گزارش

> حالت گزارش تنها تصمیم می‌گیرد **گزارش‌های پاد** از کجا بیایند. سنجه‌های گره مستقل از آن جمع می‌شوند، پس `api` و `disabled` سنجه‌های kubelet، cAdvisor و میزبانتان را نگه می‌دارند.
>
> تنها استثنا سکو است، نه حالت: **EKS Fargate اصلاً نمی‌تواند DaemonSet زمان‌بندی کند**، پس آنجا جمع‌کننده گره‌ای وجود ندارد و سنجه‌های گره/پاد/کانتینر در دسترس نیستند. GKE Autopilot جمع‌کننده گره را بی‌دردسر اجرا می‌کند، اما `hostPath` را مسدود می‌کند، پس سنجه‌های kubelet و cAdvisor را بدون آن سنجه‌های `hostmetrics` (ورودی/خروجی دیسک، آی‌نودها، خطاهای کارت شبکه) جمع می‌کند که برای خواندن `/proc` و `/sys` میزبان لازم‌اند.

مقدار صریح `logs.mode` همیشه بر پیش‌فرض پیش‌تنظیم برنده است. اگر خوشه‌تان را بهتر از پیش‌تنظیم می‌شناسید از این استفاده کنید.

روی خوشه‌هایی با استخرهای گره Windows، حالت `daemonset` فقط گره‌های Linux را پوشش می‌دهد — هر تصویر عامل فقط Linux است، پس DaemonSet به آن‌ها سنجاق می‌شود. با `--set logs.windowsPods.enabled=true` دنبال‌کننده گزارش API را در کنارش اجرا کنید، محدود به پادهای روی گره‌های Windows: پادهای Linux دنبال کردن محلیِ پرونده روی گره را نگه می‌دارند و آن دو جمع‌کننده هرگز همان خط را دو بار نمی‌فرستند. این کار به تصویر `kubernetes-log-tailer`ای دست‌کم به‌تازگیِ خودِ نمودار نیاز دارد — تصویری قدیمی‌تر این محدودیت را نادیده می‌گیرد و گزارش‌های Linux را دوباره‌کاری می‌کند.

### فعال کردن پایش صفحه کنترل

برای خوشه‌های خودمدیریت (نه EKS / GKE / AKS) می‌توانید سنجه‌های صفحه کنترل را فعال کنید:

```bash
helm install kubernetes-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent \
  --create-namespace \
  --set oneuptime.url="YOUR_ONEUPTIME_URL" \
  --set oneuptime.apiKey="YOUR_ONEUPTIME_API_KEY" \
  --set clusterName="my-cluster" \
  --set controlPlane.enabled=true
```

> سرویس‌های مدیریت‌شده Kubernetes (‏EKS، GKE، AKS) معمولاً سنجه‌های صفحه کنترل را در معرض نمی‌گذارند. این را فقط برای خوشه‌های خودمدیریت فعال کنید.

### فعال کردن رصدپذیری هزینه

ببینید هر فضای‌نام، بار کاری و پاد واقعاً چقدر هزینه دارد — از جمله ظرفیت بیکار و کارایی درخواست در برابر مصرف — روی صفحه **Costs** خوشه:

```bash
helm upgrade kubernetes-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent \
  --reuse-values \
  --set cost.enabled=true
```

همین به‌تنهایی نصبی کامل است: نمودار موتور متن‌باز [OpenCost](https://opencost.io) را همراه دارد (به‌علاوه یک Prometheus کمینه و اختصاصی که لازم دارد) و گره‌ها و حجم‌هایتان را از قیمت‌های فهرست عمومی ارائه‌دهنده ابری‌تان قیمت‌گذاری می‌کند — بدون هیچ اعتبارنامه‌ای. دو پاد کوچک اضافی؛ نخستین داده پس از نخستین پنجره ساعتی بسته‌شده پدیدار می‌شود. از پیش Kubecost یا OpenCost اجرا می‌کنید؟ به‌جایش `--set cost.engine.url=<its service URL>` را بیفزایید و آنگاه هیچ‌چیزی همراه نمی‌شود. خوشه‌های درون‌سازمانی می‌توانند از راه `cost.opencost.customPricing` کارت نرخ تنظیم کنند.

راهنمای کامل، از جمله قیمت‌گذاری درون‌سازمانی و رفع اشکال: [رصدپذیری هزینه Kubernetes](/docs/telemetry/kubernetes-cost).

### برچسب‌گذاری خودکار با برچسب‌های پروژه

هر صفت منبعی که پیشوند `oneuptime.label.` بگیرد به یک Label پروژه ارتقا می‌یابد و به خوشه، سرویس‌ها و میزبان‌هایی که از این عامل منتشر می‌شوند می‌چسبد. الگو: `oneuptime.label.<dimension>=<value>` به برچسبی به نام `<dimension>:<value>` بدل می‌شود.

برچسب‌ها را هنگام نصب با `--set oneuptime.labels.<key>=<value>` بدهید:

```bash
helm install kubernetes-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent \
  --create-namespace \
  --set oneuptime.url="YOUR_ONEUPTIME_URL" \
  --set oneuptime.apiKey="YOUR_ONEUPTIME_API_KEY" \
  --set clusterName="prod" \
  --set oneuptime.labels.team=payments \
  --set oneuptime.labels.env=production \
  --set oneuptime.labels.region=us-east-1
```

یا آن‌ها را در پرونده‌ای از مقادیر نگه دارید:

```yaml
# values.yaml
oneuptime:
  url: YOUR_ONEUPTIME_URL
  apiKey: YOUR_ONEUPTIME_API_KEY
  labels:
    team: payments
    env: production
    region: us-east-1
clusterName: prod
```

برچسب‌ها بدون حساسیت به بزرگی و کوچکی حروف تطبیق داده می‌شوند، پس برچسب `Production`ای که پیش‌تر دستی ساخته شده به‌جای دوباره‌کاری از نو به کار می‌رود. برچسب‌هایی که دستی در رابط کاربری OneUptime افزوده شده‌اند هرگز به‌دست عامل برداشته نمی‌شوند.

## ارتقای عامل

```bash
helm repo update
helm upgrade kubernetes-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent \
  --reuse-values
```

مقدار `--reuse-values` پیکربندی موجودتان را نگه می‌دارد (پیش‌تنظیم، نام خوشه، پالایه‌ها)؛ هر بازنویسی تازه‌ای را با `--set` روی آن بدهید.

## حذف نصب عامل

```bash
helm uninstall kubernetes-agent --namespace oneuptime-agent
kubectl delete namespace oneuptime-agent
```

## ردیابی‌های برنامه و سنجه‌های HTTP از راه eBPF (به‌طور پیش‌فرض روشن)

نمودار روی هر گره DaemonSetی با [ابزارگذاری eBPF در OpenTelemetry‏ (OBI)](https://opentelemetry.io/docs/zero-code/obi/) اجرا می‌کند. برنامه‌های eBPF را در هسته بار می‌کند و ترافیک HTTP/HTTPS، gRPC و SQL/Redis را از هر زمان اجرای پشتیبانی‌شده (‏Go، ‎.NET، Java، Node.js، Python، Ruby، Rust) خودکار می‌گیرد — بی هیچ SDK و بی هیچ کانتینر جانبی. ردیابی‌ها و سنجه‌های درخواست سپس از راه جمع‌کننده درون خوشه به OneUptime جاری می‌شوند.

**نیازمندی‌ها:** هسته Linux نسخه **5.8 یا بالاتر** همراه BTF (پیش‌فرض روی Debian 11+، Ubuntu 20.10+، Fedora 34+، RHEL/Stream 9+). DaemonSet‏ eBPF در **حالت ممتاز** اجرا می‌شود، چون برای بار کردن برنامه‌های eBPF ناچار است.

### از کار انداختن ابزارگذاری خودکار eBPF

در این حالت‌ها باید از کارش بیندازید:

- نصب روی **GKE Autopilot** یا **EKS Fargate** — آن سکوها پادهای ممتاز را مسدود می‌کنند (‏`preset=gke-autopilot` / `preset=eks-fargate` را به کار ببرید و با `ebpf.enabled=false` جفتش کنید).
- گره‌ها هسته‌ای قدیمی‌تر از 5.8 بدون پس‌انتقال BTF اجرا می‌کنند.
- از پیش ردیابی‌ها را با SDKهای OpenTelemetry از برنامه‌هایتان می‌فرستید و رونوشت تکراری نمی‌خواهید.

```bash
helm install kubernetes-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent \
  --create-namespace \
  --set oneuptime.url="YOUR_ONEUPTIME_URL" \
  --set oneuptime.apiKey="YOUR_ONEUPTIME_API_KEY" \
  --set clusterName="my-cluster" \
  --set ebpf.enabled=false
```

### روشن و خاموش کردن تک‌تک خانواده‌های سیگنال

همه به‌طور پیش‌فرض روشن‌اند. هر کدام را با `--set ebpf.features.<name>=false` خاموش کنید:

| `ebpf.features.*`         | پیش‌فرض | چه چیزی می‌افزاید                                                      |
| ------------------------- | ------- | ----------------------------------------------------------------- |
| `httpMetrics`             | روشن      | سنجه‌های RED مربوط به HTTP/gRPC (نرخ درخواست، تأخیر، خطا) به ازای هر سرویس |
| `spanMetrics`             | روشن      | اندازه درخواست/پاسخ و طول مدت به ازای هر اسپن                       |
| `serviceGraph`            | روشن      | سنجه‌های یال فراخوان → فراخوانده؛ به نقشه سرویس نیرو می‌دهد              |
| `hostMetrics`             | روشن      | ‏CPU و حافظه به ازای هر فرایند ابزارگذاری‌شده                                   |
| `networkMetrics`          | روشن      | شمارنده‌های جریان TCP/UDP پاد به پاد                                  |
| `networkInterZoneMetrics` | خاموش     | گونه بین‌ناحیه‌ای سنجه‌های شبکه (کاردینالیتی را دو برابر می‌کند)       |
| `tcpStats`                | روشن      | شمارنده‌های RTT مربوط به TCP، اتصال ناموفق و بازارسال در سطح گره        |

انتشار زمینه ردیابی میان سرویس‌ها — جایی که OBI یک `traceparent` استاندارد W3C تزریق می‌کند تا درخواستی که از پاد A به پاد B می‌گذرد بدون هیچ تغییری در SDK به‌صورت یک ردیابی یگانه دیده شود — **به‌طور پیش‌فرض خاموش** است. با `--set ebpf.contextPropagation=true` واردش شوید. به هسته‌ای فراتر از آنچه باقی عامل نیاز دارد محتاج نیست — و هیچ نسخه‌ای از هسته بی‌اثرش نمی‌کند.

خاموش است چون تزریق آن سرآیند یعنی بازنویسی ترافیکی که از پیش در پرواز است: درخواست‌های HTTP متن‌ساده در جای خود در هسته گشاد می‌شوند، در حالی که TLS و TCP خام از قلاب Traffic Control گزینه‌ای TCP به دمشان می‌چسبد. اگر حسابداری بایت‌های اتصال دقیقاً درست تصحیح نشود جریان ناهمگام می‌شود — نشانه‌ای که گزارش شده این است که انتقال‌ها از راه پراکسی لایه ۷ مانند nginx وقتی پاسخ از حدود ۶۴ کیلوبایت می‌گذرد وسط بدنه معلق می‌مانند، در حالی که درخواست‌های کوچک به کار کردن ادامه می‌دهند. برای رد کردن این احتمال به سن هسته تکیه نکنید — زیر هسته 5.17، ‏OBI به گونه‌های برنامه با پویش کران‌دار پس‌نشینی می‌کند و ترافیک را به همان شیوه بازنویسی می‌کند. ردیابی‌ها، سنجه‌های RED و نقشه سرویس به آن وابسته نیستند؛ برای پیوند میان سرویس‌ها، SDK‏ OpenTelemetry، ‏`traceparent` را در فضای کاربر منتشر می‌کند بی‌آنکه هسته چیزی بازنویسی کند و گزینه امن‌تری است.

## کاستن از حجم داده جمع‌آوری‌شده

عامل بیرون از جعبه برای **پوشش** کوک شده — سنجه‌ها، گزارش‌های پاد و ردیابی‌های eBPF را از سراسر خوشه می‌فرستد تا هر داشبورد و مانیتوری از روز اول کار کند. روی خوشه‌های بزرگ یا پرمشغله این می‌تواند بیش از تله‌متری موردنیازتان باشد، که خودش را در حجم دریافتی بالاتر (و روی OneUptime Cloud، هزینه بالاتر) نشان می‌دهد. هیچ‌چیز اینجا الزامی نیست، اما اگر خوشه‌ای بیش از آنچه می‌خواهید می‌فرستد، این‌ها پیچ‌هایی هستند که باید بچرخانید — تقریباً به ترتیب اثرگذاری.

ترفند این است که **جمع کردن آنچه را نگاه نخواهید کرد وابگذارید**، نه اینکه همه‌چیز را جمع کنید و برای انبار کردنش پول بدهید. هر اهرمی که پایین می‌آید یک مقدار Helm است، پس می‌توانید با `--set` روی `helm upgrade --reuse-values` اعمالش کنید و به همان شیوه پسش بگیرید.

### حجم از کجا می‌آید

| سیگنال                         | بزرگ‌ترین محرک                                           | با چه چیزی پایینش بیاورید                                                                            |
| ------------------------------ | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| **گزارش‌های پاد**                   | هر خط از هر کانتینری، در سراسر خوشه            | `namespaceFilters`، `filters.logs.minSeverity`، `logs.enabled`، `logs.mode`                  |
| **ردیابی‌ها و سنجه‌های اسپن eBPF** | یک ردیابی به ازای هر درخواست از هر فرایند ابزارگذاری‌شده    | `sampling.traces.percentage`، `ebpf.enabled`، `ebpf.features.*`، `ebpf.autoTargetExe`، `ebpf.excludeExePaths` |
| **نقاط داده سنجه**         | فراوانی برداشت × شمار پادها/کانتینرها             | `collectionInterval`، `hostMetrics.collectionInterval`، `cadvisor.scrapeInterval`            |
| **کاردینالیتی سنجه**         | شمار سری‌های متمایز (به ازای هر کانتینر، هر PVC، …)    | `filters.metrics.exclude`، `namespaceFilters.rules` با دامنه `metrics`، `cadvisor.metricsAllowlist`، `kubeletstats.volumeMetrics` |
| **افزوده‌های اختیاری**              | پروفایل‌گیری، گزارش‌های ممیزی، صفحه کنترل، سنجه‌های بین‌ناحیه‌ای | خاموش بگذاریدشان (از پیش هم خاموش‌اند)                                                 |

سه راه برای کاستن حجم هست، و ارزش دارد بدانید کدام را به کار می‌برید:

- **در گیرنده** — داده اصلاً جمع نمی‌شود. `namespaceFilters` روی گزارش‌های پاد، `cadvisor.metricsAllowlist`، `collectionInterval` بلندتر. اجرایش چیزی هزینه ندارد و هم‌زمان CPU، خروجی و دریافت را صرفه‌جویی می‌کند. هر جا مورد شما را پوشش می‌دهند همیشه این‌ها را ترجیح دهید.
- **در پردازنده پالایه** — داده جمع می‌شود، سپس پیش از صدور انداخته می‌شود. `filters.logs.minSeverity`، `filters.metrics.*` و `namespaceFilters.rules` با دامنه `metrics` یا `traces`. کمی CPU بیشتر برای جمع‌کننده، اما در سراسر گیرنده‌ها کار می‌کند و می‌تواند چیزهایی را بیان کند که گیرنده نمی‌تواند.
- **در نمونه‌بردار** — داده جمع می‌شود، سپس کسری نماینده از آن نگه داشته می‌شود. `sampling.traces.percentage`. این یکی متفاوت است: آن دوی بالا یک *رده* کامل از تله‌متری را برمی‌دارند، پس هر چه بیندازند از هر ردیابی‌ای رفته است. نمونه‌برداری هر رده را نگه می‌دارد و جمعیت را نازک می‌کند، پس آنچه جان به در می‌برد هنوز کامل و نماینده است.

هر سه **برگشت‌ناپذیرند**: آنچه اینجا می‌اندازید هرگز به OneUptime نمی‌رسد، و هر سه می‌توانند مانیتوری را ساکت کنند. دو تای اول با برداشتن سیگنالی که مانیتور می‌پاید ساکتش می‌کنند. نمونه‌برداری باریک‌تر است: سنجه‌های RED مربوط به eBPF پیش از اجرای نمونه‌بردار محاسبه می‌شوند، پس مانیتورهای سنجه‌محور دقیق می‌مانند — اما مانیتورهایی که *اسپن* می‌شمارند (‏Traces روی `Span Count`، Exceptions روی `Exception Count`) به‌تناسب کمتر می‌بینند و آستانه‌هایشان باید با همان ضریب دوباره کوک شود. اگر ترجیح می‌دهید بعداً تصمیم بگیرید، OneUptime می‌تواند به‌جایش داده را سمت کارساز بیندازد (**Logs → Settings → Drop Filters**، **Metrics → Settings → Pipeline Rules**) — این هنوز خروجی هزینه دارد، اما تنظیمی است که بی‌نیاز از استقرار دوباره می‌توانید تغییرش دهید.

### اهرم ۱ — گزارش‌های پاد معمولاً بزرگ‌ترین منبع یگانه‌اند

گزارش‌های کانتینر تقریباً همیشه بزرگ‌ترین برش دریافت‌اند، چون به ازای هر خط گزارش از هر کانتینری در خوشه یک رکورد است.

- **فقط گزارش فضای‌نام‌هایی خاص را می‌خواهید؟** از قاعده `include` با دامنه `podLogs` استفاده کنید. تطبیق در سرچشمه گزارش پاد رخ می‌دهد، پس فضای‌نام‌های پالایش‌شده هرگز خوانده نمی‌شوند — و تله‌متری eBPF مستقل می‌ماند:

  ```bash
  helm upgrade kubernetes-agent oneuptime/kubernetes-agent \
    --namespace oneuptime-agent --reuse-values \
    --set-json 'namespaceFilters.rules=[{"action":"include","namespaces":["default","production"],"scopes":["podLogs"]}]'
  ```

  برای نگه داشتن هر فضای‌نامی جز خانواده‌ای پرسروصدا، از قاعده حذف با `"namespaces":["noisy-*"]` و `"scopes":["podLogs"]` استفاده کنید.

- **فقط به اخطارها و خطاها اهمیت می‌دهید؟** مقدار `filters.logs.minSeverity` باقی را در خود عامل می‌اندازد. روی خوشه‌ای پرگو این اغلب بزرگ‌ترین کاهش یگانه در دسترس است، چون INFO و DEBUG بخش عمده خروجی بیشتر برنامه‌ها هستند:

  ```bash
  helm upgrade kubernetes-agent oneuptime/kubernetes-agent \
    --namespace oneuptime-agent --reuse-values \
    --set filters.logs.minSeverity=WARN
  ```

  برای اینکه شدت چگونه تعیین می‌شود و بر سر گزارش‌هایی که نمی‌تواند رده‌بندی کند چه می‌آید، [پالایش بر پایه شدت گزارش](#filtering-by-log-severity) را ببینید.

- **اصلاً به گزارش‌های پاد در OneUptime نیاز ندارید؟** خاموششان کنید:

  ```bash
  helm upgrade kubernetes-agent oneuptime/kubernetes-agent \
    --namespace oneuptime-agent --reuse-values \
    --set logs.enabled=false
  ```

  > این فقط گزارش‌های پاد را می‌ایستاند. سنجه‌های گره، پاد و کانتینر همچنان جاری‌اند، و مانیتورهای ساخته‌شده بر آن‌ها (کشتن OOM، خفگی CPU، کمبود دیسک PVC) به کار ادامه می‌دهند — جمع‌کننده گره می‌ماند و فقط خواندن `/var/log/pods` را وامی‌نهد. همین درباره `logs.mode: api` و `logs.mode: disabled` هم صادق است.

### اهرم ۲ — تراشیدن ابزارگذاری خودکار eBPF

‏eBPF بدون هیچ تغییری در کد ردیابی‌ها، سنجه‌های RED، نقشه سرویس و سنجه‌های جریان شبکه را به شما می‌دهد — اما دومین منبع بزرگ داده هم هست، چون به ازای هر درخواست یک اسپن و به ازای هر سرویس چند خانواده سنجه منتشر می‌کند. سه سطح کنترل دارید:

- **از پیش ردیابی‌ها را از SDKهای OTel می‌فرستید، یا ردیابی خودکار نمی‌خواهید؟** ‏eBPF را به‌کل خاموش کنید:

  ```bash
  helm upgrade kubernetes-agent oneuptime/kubernetes-agent \
    --namespace oneuptime-agent --reuse-values \
    --set ebpf.enabled=false
  ```

- **ردیابی‌ها را نگه دارید، خانواده‌های سنجه سنگین را بیندازید.** [جدول خانواده‌های سیگنال بالا](#toggle-individual-signal-families) هر پرچم `ebpf.features.*` را فهرست می‌کند. پرحجم‌ترین خانواده‌ها سنجه‌های شبکه و سنجه‌های اسپن‌اند — خاموش کردنشان ردیابی‌ها، سنجه‌های RED مربوط به HTTP و نقشه سرویس را دست‌نخورده می‌گذارد:

  ```bash
  helm upgrade kubernetes-agent oneuptime/kubernetes-agent \
    --namespace oneuptime-agent --reuse-values \
    --set ebpf.features.networkMetrics=false \
    --set ebpf.features.tcpStats=false \
    --set ebpf.features.spanMetrics=false
  ```

  مقدار `ebpf.features.networkInterZoneMetrics` را خاموش بگذارید (پیش‌فرضش) — کاردینالیتی جریان شبکه را دو برابر می‌کند.

- **فقط زمان‌های اجرایی را ابزارگذاری کنید که برایتان مهم‌اند.** به‌طور پیش‌فرض OBI به هر فرایندی که بشناسد می‌چسبد (`ebpf.autoTargetExe: "*"`). برای کاستن از شمار «سرویس»ها و ردیابی‌هایی که عامل تولید می‌کند، آن را به زمان‌های اجرای مشخصی باریک کنید، یا دودویی‌هایی را به فهرست گذشتن بیفزایید:

  ```bash
  helm upgrade kubernetes-agent oneuptime/kubernetes-agent \
    --namespace oneuptime-agent --reuse-values \
    --set ebpf.autoTargetExe='*/python,*/java'
  ```

  برای پیش‌فرض‌های کامل، [روشن و خاموش کردن تک‌تک خانواده‌های سیگنال](#toggle-individual-signal-families) و یادداشت `excludeExePaths` در مقادیر نمودار را ببینید.

### اهرم ۳ — کند کردن بازه‌های برداشت

حجم سنجه مستقیماً با فراوانی برداشت عامل نسبت دارد. دو برابر کردن بازه‌ای تقریباً شمار نقاط داده آن سنجه را نصف می‌کند، بی‌هیچ از دست دادن پوششی — فقط تفکیک‌پذیری درشت‌تر. اگر به ریزدانگی ۳۰ ثانیه‌ای نیاز ندارید، ۶۰ یا ۱۲۰ ثانیه کاهشی بزرگ و امن است:

```bash
helm upgrade kubernetes-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent --reuse-values \
  --set collectionInterval=60s \
  --set hostMetrics.collectionInterval=60s \
  --set cadvisor.scrapeInterval=60s
```

- ‏`collectionInterval` (پیش‌فرض `30s`) سنجه‌های گره / پاد / کانتینر (`kubeletstats`) و سنجه‌های وضعیت خوشه (`k8s_cluster`) را می‌راند — بخش عمده حجم سنجه.
- ‏`hostMetrics.collectionInterval` و `cadvisor.scrapeInterval` سنجه‌های سیستم‌عامل هر گره و شمارنده‌های خفگی / OOM را پوشش می‌دهند.
- ‏`resourceSpecs.interval` (پیش‌فرض `300s`) تعیین می‌کند چند وقت یک بار مشخصات کامل منابع (برچسب‌ها، حاشیه‌نویسی‌ها، وضعیت) کشیده شوند — اگر لازم ندارید تغییرهای مشخصات زود بازتاب یابند بالاترش ببرید.
- اگر هر یک از برداشت‌کننده‌های اختیاری را فعال کرده‌اید، آن‌ها هم پیچ‌های خودشان را دارند: `kubeStateMetrics.scrapeInterval`، `serviceMesh.*.scrapeInterval`، `coreDns.scrapeInterval`، `csi.scrapeInterval`.

### اهرم ۴ — کران‌دار نگه داشتن کاردینالیتی سنجه

کاردینالیتی (شمار سری‌های زمانی متمایز) به اندازه فراوانی مهم است، چون هر سری جداگانه ذخیره و صورت‌حساب می‌شود.

- **‏cAdvisor عمداً فهرست مجاز دارد.** گیرنده cAdvisor (به‌طور پیش‌فرض روشن) می‌تواند صدها سنجه منتشر کند؛ نمودار فقط همان چند تایی را جلو می‌فرستد که به مانیتورها نیرو می‌دهند (`cadvisor.metricsAllowlist`). فهرست را تنگ نگه دارید — **هر مدخل به ازای هر کانتینر نگه داشته می‌شود، پس یک سنجه اضافه در شمار کانتینرهای خوشه ضرب می‌شود.** ‏kube-state-metrics به‌طور پیش‌فرض خاموش است، اما اگر فعالش کنید (`kubeStateMetrics.enabled=true`) مقدار `kubeStateMetrics.metricsAllowlist` آن به همان شیوه کاردینالیتی را مهار می‌کند.
- **سنجه‌های حجم به ازای هر PVC** (`kubeletstats.volumeMetrics.enabled`، به‌طور پیش‌فرض روشن) به ازای هر PVC در هر پاد یک سری منتشر می‌کنند. برای بیشتر خوشه‌ها مشکلی نیست اما روی بارهای کاری حالت‌دار (‏Kafka، پایگاه‌های داده) با هزاران PVC می‌تواند چشمگیر باشد — اگر فضای دیسک PVC را نمی‌پایید آنجا خاموشش کنید:

  ```bash
  --set kubeletstats.volumeMetrics.enabled=false
  ```

- **سنجه‌های اشباع** (`kubeletstats.utilizationMetrics.enabled`، به‌طور پیش‌فرض روشن) ۸ خانواده مشتق «درصد درخواست/محدودیت» می‌افزایند. ارزان‌اند (برداشت اضافه‌ای ندارند) اما اگر مانیتورهای CPU/حافظه در برابر محدودیت را به کار نمی‌برید می‌توانید با `--set kubeletstats.utilizationMetrics.enabled=false` بیندازیدشان.

- **انداختن سنجه‌هایی مشخص بر پایه نام.** فهرست‌های مجاز بالا به ازای هر گیرنده‌اند؛ `filters.metrics.exclude` همه‌شان را در بر می‌گیرد، پس برای هر چیزی که پیچ‌های سطح گیرنده نمی‌توانند بیانش کنند از آن استفاده کنید:

  ```bash
  helm upgrade kubernetes-agent oneuptime/kubernetes-agent \
    --namespace oneuptime-agent --reuse-values \
    --set filters.metrics.matchType=regexp \
    --set-json 'filters.metrics.exclude=["^container_network_"]'
  ```

  برای تطبیق دقیق در برابر عبارت باقاعده و شکل فهرست مجاز، [گنجاندن یا حذف سنجه‌ها بر پایه نام](#including-or-excluding-metrics-by-name) را ببینید.

- **انداختن سنجه‌های یک فضای‌نام کامل.** قاعده حذفی با دامنه `metrics` بیفزایید. سری‌های هر پاد و هر کانتینر پالایش می‌شوند، در حالی که سری‌های سطح گره و سطح خوشه که فضای‌نامی ندارند همیشه نگه داشته می‌شوند:

  ```bash
  helm upgrade kubernetes-agent oneuptime/kubernetes-agent \
    --namespace oneuptime-agent --reuse-values \
    --set-json 'namespaceFilters.rules=[{"action":"exclude","namespaces":["noisy-*"],"scopes":["metrics"]}]'
  ```

### اهرم ۵ — ویژگی‌های سنگین اختیاری را خاموش بگذارید

این‌ها دقیقاً از آن رو **به‌طور پیش‌فرض خاموش‌اند** که بار می‌افزایند — یکی را فقط وقتی فعال کنید که فعالانه از آنچه به آن نیرو می‌دهد استفاده می‌کنید، و اگر صرفاً امتحانش می‌کردید دوباره خاموشش کنید:

| مقدار                                                     | چه می‌افزاید                                                                               |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `profiling.enabled`                                       | ‏DaemonSet پروفایل‌گیری پیوسته CPU — سنگین‌تر از ردیابی‌های eBPF                      |
| `auditLogs.enabled`                                       | هر درخواست API‏ Kubernetes به‌صورت یک رکورد گزارش (پرحجم)                         |
| `controlPlane.enabled`                                    | سنجه‌های etcd / کارساز API / زمان‌بند / مدیر کنترلر                         |
| `kubeStateMetrics.enabled`                                | سنجه‌های CrashLoop / ImagePull / دلیل زمان‌بندی (یک Deployment‏ KSM و برداشتی می‌افزاید) |
| `ebpf.features.networkInterZoneMetrics`                   | کاردینالیتی سنجه جریان شبکه را دو برابر می‌کند                                            |
| `serviceMesh.enabled` / `csi.enabled` / `coreDns.enabled` | کارهای برداشت Prometheus اضافه                                                       |
| `cost.enabled`                                            | رصدپذیری هزینه بار کاری (‏OpenCost و یک Prometheus کوچک را همراه می‌کند؛ سطرهای هزینه ساعتی به‌علاوه برداشت سنجه با فهرست مجاز تنگ — دریافت متعارف، دو پاد اضافی) |

### اهرم ۶ — به‌جای انداختن ردیابی‌ها از آن‌ها نمونه بردارید

هر اهرم بالاتر حجم را با از دست دادن چیزی می‌خرد: فضای‌نامی که دیگر نمی‌پایید، شدتی که دیگر نگه نمی‌دارید، خانواده سنجه‌ای که دیگر جمع نمی‌کنید. نمونه‌برداری استثناست، و روی خوشه‌ای پرمشغله اغلب بزرگ‌ترین کاهش در دسترس در برابر کمترین از دست دادن است:

```bash
helm upgrade kubernetes-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent --reuse-values \
  --set sampling.traces.percentage=10
```

این کاهشی ۹۰٪ در حجم ردیابی است در برابر از دست دادنی باریک‌تر از هر اهرم دیگری اینجا:

- ردیابی‌هایی که نگه می‌دارید **کامل‌اند** — تصمیم شناسه ردیابی را درهم می‌سازد، پس همه اسپن‌های یک ردیابی در آن شریک‌اند. ردیابی کمتر می‌گیرید، نه ردیابی شکسته.
- **سنجه‌های RED شما دقیق می‌مانند.** نرخ درخواست، نرخ خطا و طول مدت را OBI از هر درخواستی محاسبه می‌کند و از خط لوله سنجه‌ها می‌گذرند، که نمونه‌بردار در آن نیست. هر داشبورد و مانیتوری که بر آن‌ها ساخته شده همان چیز پیشین را می‌خواند.

آنچه از دست می‌دهید بیشتر ردیابی‌های نمونه است: وقتی مانیتوری شلیک می‌کند، یک‌دهم ردیابی‌های پیشین را برای باز کردن دارید. روی خوشه‌ای که ثانیه‌ای هزاران درخواست یکسان انجام می‌دهد این معمولاً معامله خوبی است — صدمین اسپن یکسان `/healthz` چیزی به شما نمی‌آموزد که اولی نیاموخته باشد. روی خوشه‌ای آرام معامله بدی است، چون ممکن است هیچ نمونه‌ای از آن درخواست نادری که خراب شد نداشته باشید.

استثنا، و تنها چیزی که پیش از گستراندنش باید بررسی کنید: مانیتورهایی که به‌جای سنجه **اسپن می‌شمارند** — ‏Traces روی `Span Count`، Exceptions روی `Exception Count` — به‌تناسب کمتر می‌بینند، پس آستانه‌هایشان باید با همان ضریب دوباره کوک شود. [نمونه‌برداری از ردیابی](#trace-sampling) را ببینید.

وقتی ردیابی‌های eBPF سهم بزرگی از دریافت شما هستند اما هنوز نقشه سرویس و سنجه‌های RED را دست‌نخورده می‌خواهید، سراغ این بیایید. وقتی می‌خواهید ابزارگذاری چیزی را به‌کل بایستانید، اهرم ۲ را ترجیح دهید.

برای رفتار کامل، از جمله اینکه چرا `0` نرخ است نه کلید خاموشی و چرا معادلی برای گزارش یا سنجه ندارد، [نمونه‌برداری از ردیابی](#trace-sampling) را ببینید.

### نقطه شروعی لاغر

اگر ردپای کوچک‌تری می‌خواهید اما همچنان می‌خواهید مانیتورها کار کنند، این نمایه **پوشش کامل سنجه** را نگه می‌دارد و آن دو چیزی را که واقعاً حجم را می‌رانند می‌برد — خط‌های گزارش و اسپن‌های eBPF:

```yaml
# lean-values.yaml
oneuptime:
  url: YOUR_ONEUPTIME_URL
  apiKey: YOUR_ONEUPTIME_API_KEY
clusterName: my-cluster

# Halve the metric data points. Coarser resolution, same coverage.
collectionInterval: 60s
hostMetrics:
  collectionInterval: 60s
cadvisor:
  scrapeInterval: 60s

# Keep pod logs, but only ship the ones worth alerting on. (Metrics do
# not depend on this — the node collector runs either way.)
logs:
  enabled: true
  mode: daemonset

filters:
  logs:
    minSeverity: WARN # drop INFO / DEBUG / TRACE at the agent

namespaceFilters:
  rules:
    - action: exclude
      namespaces: [kube-system]
      scopes: [podLogs, ebpfDiscovery]
    - action: exclude
      namespaces: [noisy-*]
      scopes: [podLogs]

ebpf:
  enabled: true
  features:
    networkMetrics: false # the heaviest eBPF families
    tcpStats: false
    spanMetrics: false
```

```bash
helm upgrade --install kubernetes-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent --create-namespace \
  -f lean-values.yaml
```

هر جا لازم شد بیشتر تنگش کنید: `minSeverity` را به `ERROR` ببرید، `metrics` را به دامنه‌های قاعده‌ای فضای‌نامی بیفزایید، یا اگر از پیش ردیابی‌ها را از SDKهای OTel می‌فرستید `ebpf.enabled=false` بگذارید.

> **مواظب باشید چه می‌برید.** برخی مانیتورها به سیگنال‌هایی مشخص وابسته‌اند: از کار انداختن `cadvisor` مانیتورهای کشتن OOM و خفگی CPU را برمی‌دارد؛ از کار انداختن `kubeletstats.volumeMetrics` مانیتور کمبود دیسک PVC را برمی‌دارد؛ از کار انداختن گزارش‌ها هشدارهای گزارش‌محور را برمی‌دارد؛ و `sampling.traces.percentage` مانیتوری را برنمی‌دارد اما مانیتورهای اسپن‌محور (‏Traces روی `Span Count`، Exceptions روی `Exception Count`) را کوچک می‌کند، پس آستانه‌هایشان را متناسب دوباره کوک کنید. سیگنال‌هایی را بتراشید که بر پایه‌شان کاری نمی‌کنید، نه آن‌هایی را که مانیتوری می‌پایدشان.

### اثر را اندازه بگیرید

مصرف تله‌متری روزانه تجمیع می‌شود، پس برای تأیید افت، روند یکی دو روز را زیر **Project Settings → Usage History** بررسی کنید — به‌محض اعمال تغییر تکان نمی‌خورد. هر بار یک اهرم را تغییر دهید تا بتوانید تفاوت را به آن نسبت دهید — اول گزارش‌ها خاموش، بعد بازه بالاتر، بعد eBPF تراشیده — به‌جای اینکه یک‌جا همه‌چیز را پایین بیاورید و مانیتوری را که واقعاً به آن تکیه داشتید از دست بدهید.

## رفع اشکال

> **سریع‌ترین راه — اسکریپت تشخیصی را اجرا کنید.** سلامت پادها را بازرسی می‌کند، کلید دریافت را رمزگشایی و اعتبارسنجی می‌کند، بررسی می‌کند خوشه‌تان به OneUptime می‌رسد یا نه، و از OneUptime می‌پرسد که آیا نشانه‌تان واقعاً پذیرفته می‌شود — سپس یک حکم یگانه درباره ریشه مشکل چاپ می‌کند:
>
> ```bash
> curl -fsSL https://raw.githubusercontent.com/OneUptime/oneuptime/master/HelmChart/Public/kubernetes-agent/troubleshoot.sh \
>   | bash -s -- -n oneuptime-agent
> ```
>
> فقط وضعیت خوشه را می‌خواند و یکی دو پروب اجرا می‌کند؛ هیچ‌چیز را تغییر نمی‌دهد. برای دقیق‌ترین آزمون خروجی، نخست با `--set debug.enabled=true` نصب کنید (این کانتینر جانبی کوچکی از ابزارهای شبکه به پادهای عامل می‌افزاید تا اسکریپت دقیقاً همان مسیر خروجی جمع‌کننده را بیازماید) و سپس دوباره اجرایش کنید.

### نصب با «hostPath volumes are not allowed» یا خطای پذیرش Pod Security شکست می‌خورد

خوشه‌تان `hostPath` را مسدود می‌کند — روی **GKE Autopilot** و **EKS Fargate** رایج است. به پیش‌تنظیم حالت API جابه‌جا شوید:

```bash
helm upgrade kubernetes-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent \
  --reuse-values \
  --set preset=gke-autopilot   # or eks-fargate
```

### عامل «Disconnected» نشان می‌دهد

وضعیت وصل بودن خوشه صرفاً از رسیدن تله‌متری رانده می‌شود — اگر داده‌ای فرود نیاید، خوشه پس از حدود ۱۵ دقیقه قطع‌شده نشانه می‌خورد. پس «قطع‌شده» و «بدون سنجه» تقریباً همیشه **همان** علت را دارند: تله‌متری عامل پذیرفته نمی‌شود.

رایج‌ترین دلیل — به‌ویژه پس از نصب دوباره — **کلید دریافت اشتباه یا باطل‌شده** است. این را آسان از دست می‌دهید چون نقاط پایانی دریافت OTLP عمداً حتی برای نشانه بد هم HTTP‏ `200` برمی‌گردانند (تا جمع‌کننده‌ای بدپیکربندی نتواند کارساز را با توفان تلاش دوباره بکوبد). نتیجه: جمع‌کننده موفقیت گزارش می‌دهد، گزارش‌هایش هیچ خطایی نشان نمی‌دهند، و داده خاموشانه انداخته می‌شود.

1. بررسی کنید پادهای عامل در حال اجرا باشند: `kubectl get pods -n oneuptime-agent`
2. گزارش‌های جمع‌کننده سنجه را بررسی کنید: `kubectl logs -n oneuptime-agent -l component=metrics-collector -c otel-collector` (نبودن خطا اینجا **به این معنا نیست** که داده فرود می‌آید — بالا را ببینید)
3. **کلید دریافت را اعتبارسنجی کنید.** مستقیم از OneUptime بپرسید که آیا نشانه‌تان پذیرفته می‌شود (`200` = معتبر، `401` = ناشناخته/باطل‌شده):

   ```bash
   curl -i -H "x-oneuptime-token: <YOUR_API_KEY>" https://oneuptime.com/otlp/v1/validate
   ```

   اگر `401` برگرداند، کلید موجود در انتشار شما اشتباه است یا باطل شده. کلیدی زنده را از _Project Settings → Telemetry & APM → Ingestion Keys_ رونوشت بگیرید و دوباره مستقر کنید:

   ```bash
   helm upgrade kubernetes-agent oneuptime/kubernetes-agent \
     --namespace oneuptime-agent --reuse-values \
     --set oneuptime.apiKey=<LIVE_KEY>
   ```

4. وارسی کنید نشانی OneUptime شما درست باشد و خوشه‌تان بتواند از راه شبکه به آن برسد.
5. اگر هنگام نصب دوباره `clusterName` را تغییر داده‌اید، عامل به‌صورت خوشه‌ای **تازه** پدیدار می‌شود — مدخل قدیمی «Disconnected» می‌ماند (این انتظار می‌رود؛ کهنه است).

### هیچ گزارشی پدیدار نمی‌شود (فقط حالت API)

1. تأیید کنید پاد دنبال‌کننده گزارش Ready باشد: `kubectl get pods -n oneuptime-agent -l component=log-collector`
2. مسیر `/healthz` آن را بررسی کنید — شمار جریان‌های فعال و آخرین خطای صدور را گزارش می‌دهد
3. گزارش‌ها را بررسی کنید: `kubectl logs -n oneuptime-agent deployment/kubernetes-agent-logs`
4. برای خوشه‌های خیلی بزرگ، یک نسخه تنها ممکن است گلوگاه باشد — با قاعده‌های `include` دامنه‌دار به `podLogs` در `namespaceFilters.rules` انتشارهای جداگانه را خرد کنید

### هیچ سنجه‌ای پدیدار نمی‌شود

1. نخست کلید دریافت ردشده را کنار بگذارید — رایج‌ترین علت است و از سمت عامل نامرئی. بخش [عامل «Disconnected» نشان می‌دهد](#agent-shows-disconnected) بالا را ببینید (یا صرفاً اسکریپت تشخیصی را اجرا کنید).
2. بررسی کنید شناسه خوشه با مقداری که به‌عنوان `clusterName` داده‌اید بخواند
3. مجوزهای RBAC را وارسی کنید: `kubectl get clusterrolebinding | grep kubernetes-agent`
4. گزارش‌های جمع‌کننده OTel را برای خطاهای صدور بررسی کنید

### پادهای eBPF در CrashLoopBackOff‌اند یا راه نمی‌افتند

```bash
kubectl logs -n oneuptime-agent -l component=ebpf-instrument --tail=200
```

علت‌های رایج:

- **هسته خیلی قدیمی است یا BTF ندارد.** ‏OBI به Linux 5.8 یا بالاتر همراه BTF نیاز دارد. روی گره‌ای `uname -r` را اجرا کنید. اگر نمی‌توانید ارتقا دهید، eBPF را از کار بیندازید: `--set ebpf.enabled=false`.
- **پادهای ممتاز مسدودند.** برخی خوشه‌ها پادهای ممتاز را رد می‌کنند (‏GKE Autopilot، EKS Fargate و محیط‌های قفل‌شده). eBPF را از کار بیندازید.
- **‏`debugfs` / `tracefs` روی میزبان سوار نیستند.** ویژگی `tcpStats` به نقاط ردگیری هسته می‌چسبد که به آن‌ها نیاز دارند. نمودار هر دو را از راه `hostPath` سوار می‌کند — اما اگر میزبان شما در معرضشان نمی‌گذارد، فقط همان خانواده را از کار بیندازید: `--set ebpf.features.tcpStats=false`.

### هیچ ردیابی برنامه‌ای پدیدار نمی‌شود

1. تأیید کنید DaemonSet‏ eBPF سالم باشد: `kubectl get pods -n oneuptime-agent -l component=ebpf-instrument`
2. چاپگر ردیابی اشکال‌زدایی را روشن کنید تا تأیید شود OBI ترافیک را می‌گیرد: `--set ebpf.printTraces=true --set ebpf.logLevel=debug`، سپس `kubectl logs -n oneuptime-agent -l component=ebpf-instrument --tail=200` را بررسی کنید
3. اگر اسپن‌ها را در stdout مربوط به OBI می‌بینید اما در داشبورد نه، مشکل صدور جمع‌کننده → OneUptime است — گزارش‌های پاد جمع‌کننده سنجه را بررسی کنید.

## گام‌های بعدی

- روی سنجه‌هایی که این عامل جمع می‌کند **مانیتورهای Kubernetes** را پیکربندی کنید — [عامل Kubernetes (مانیتورها)](/docs/monitor/kubernetes-agent) را ببینید.
- **مانیتورهای Logs** را بیفزایید تا روی الگوهای گزارش مشخصی هشدار دهند (برای نمونه شمار خطاهای بالاتر از آستانه‌ای به ازای هر پاد یا هر فضای‌نام).
- برای میزبان‌های غیر Kubernetes (ماشین‌های مجازی Linux / macOS / Windows و سخت‌افزار خالص)، از صفحه [جمع‌کننده OpenTelemetry میزبان](/docs/telemetry/host-otel-collector) استفاده کنید.
