# پاییدن Claude Code با OneUptime

‏Claude Code یک کارخواه OTLP درجه‌یک است. با `http/protobuf`، `http/json` و `grpc` حرف می‌زند، از نقطه پایانی جداگانه به ازای هر سیگنال پشتیبانی می‌کند و هدرهای دلخواه می‌فرستد — پس بدون هیچ جمع‌کننده، دروازه یا رابطی در میانه، مستقیم به OneUptime صادر می‌کند. برپاسازی یک بلوک متغیر محیطی است.

## آنچه می‌گیرید

به‌محض روشن شدن صادرات، مصرف Claude Code هر توسعه‌دهنده‌ای به‌صورت سنجه‌ها و گزارش‌های معمولی OpenTelemetry در OneUptime می‌نشیند:

- **هزینه و توکن به ازای هر توسعه‌دهنده** — `claude_code.cost.usage` (دلار) و `claude_code.token.usage` (توکن)، تفکیک‌شده بر پایه مدل، بر پایه `query_source` (عامل اصلی در برابر زیرعامل) و بر پایه عامل/مهارت/افزونه/کارساز MCPای که فراخوان را اجرا کرده است.
- **نشست‌ها** — `claude_code.session.count`، تفکیک‌شده بر پایه اینکه نشست چگونه آغاز شده است.
- **خروجی** — `claude_code.commit.count`، `claude_code.pull_request.count` و `claude_code.lines_of_code.count` که به `added` / `removed` تفکیک می‌شود.
- **نرخ پذیرش ابزار** — `claude_code.code_edit_tool.decision` مقدار `decision=accept|reject` را حمل می‌کند، پس نرخ پذیرش برابر `accept / (accept + reject)` است و بر پایه زبان و ابزاری که به کار رفته برش‌پذیر است.
- **زمان فعال** — `claude_code.active_time.total`، تفکیک‌شده به `user` (تعامل با صفحه‌کلید) و `cli` (اجرای ابزار و پاسخ‌های مدل).
- **رویدادها** — اعلان‌ها، نتیجه‌های ابزار، درخواست‌های API، خطاهای API، تغییرهای حالت اجازه و اتصال‌های کارساز MCP، به‌صورت رکوردهای گزارش OTLP.

‏Claude Code مقدار `user.email` را روی هر نقطه داده سنجه و هر رکورد رویداد می‌گذارد، و OneUptime آن را روی نقطه داده‌های سنجه به‌عنوان کارمند می‌خواند — همان‌جا که ارقام هزینه و توکن زندگی می‌کنند. (هویت روی رکوردهای گزارش امروز برای انتساب خوانده نمی‌شود، پس جریان رویداد جستجوپذیر است اما هنوز به خرج پیوند نخورده.) برای ملاحظه‌ها [انتساب مصرف به کارمندان و تیم‌ها](#attributing-usage-to-employees-and-teams) را ببینید.

## پیش از آغاز

1. در OneUptime توکن دریافت تله‌متری بسازید: **Project Settings → Telemetry & APM → Ingestion Keys → Create Ingestion Key**.
2. نقطه پایانی OTLP خود را یادداشت کنید: `https://oneuptime.com/otlp`، یا اگر خودمیزبان هستید `https://YOUR-ONEUPTIME-HOST/otlp`.
3. توکن روی هر صادراتی به‌صورت هدر `x-oneuptime-token` سفر می‌کند.

برای کل ناوگان Claude Code یک کلید دریافت به کار ببرید. سر از هر ماشین توسعه‌دهنده‌ای درمی‌آورد، پس با آن مانند اعتبارنامه‌ای مشترک و فقط‌نوشتنی رفتار کنید و همان‌گونه که هر اعتبارنامه دیگری را می‌چرخانید، بچرخانیدش.

## آغاز سریع برای یک توسعه‌دهنده

این‌ها را در پوسته خود (یا در `.zshrc` / `.bashrc`) صادر کنید و Claude Code را دوباره راه‌اندازی کنید:

```bash
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export OTEL_METRICS_EXPORTER=otlp
export OTEL_LOGS_EXPORTER=otlp
export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
export OTEL_EXPORTER_OTLP_ENDPOINT="https://oneuptime.com/otlp"
export OTEL_EXPORTER_OTLP_HEADERS="x-oneuptime-token=YOUR_INGESTION_TOKEN"
```

هرکدام چه می‌کند:

- `CLAUDE_CODE_ENABLE_TELEMETRY=1` کلید اصلی است. بدون آن هیچ‌چیز صادر نمی‌شود.
- `OTEL_METRICS_EXPORTER` و `OTEL_LOGS_EXPORTER` مقادیر `console`، `otlp` و `none` را می‌پذیرند (سنجه‌ها `prometheus` را هم می‌پذیرند) و فهرستی جداشده با ویرگول می‌گیرند — `otlp,console` هم‌زمان صادر و چاپ می‌کند، که هنگام برپاسازی به کار می‌آید.
- `OTEL_EXPORTER_OTLP_ENDPOINT` نشانی **پایه** است — نمونه‌های Anthropic اینجا مبدأی برهنه به کار می‌برند و مسیرهای کامل هر سیگنال را روی متغیرهای همان سیگنال می‌گذارند، مطابق مشخصات صادرکننده OpenTelemetry که در آن `/v1/metrics` و `/v1/logs` به نشانی پایه افزوده می‌شوند. تنها اگر لازم دارید سیگنال‌ها را جدا کنید از `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` / `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` استفاده کنید، و به آن‌ها مسیر کامل بدهید (`https://oneuptime.com/otlp/v1/metrics`، `.../v1/logs`).
- `OTEL_EXPORTER_OTLP_HEADERS` جفت‌های `key=value` جداشده با ویرگول می‌گیرد، پس هدرهای اضافی می‌شوند `key1=val1,key2=val2`.

سنجه‌ها به‌طور پیش‌فرض هر ۶۰ ثانیه و گزارش‌ها هر ۵ ثانیه تخلیه می‌شوند، پس پیش از آنکه بروید دنبالشان بگردید یک دقیقه فرصت بدهید.

## عرضه ناوگانی با تنظیمات مدیریت‌شده

برای یک سازمان، همان متغیرها را به‌صورت فایل تنظیمات مدیریت‌شده عرضه کنید. تنظیمات مدیریت‌شده همان شکل JSON فایل `settings.json` را دارند، با متغیرها زیر یک بلوک `env`:

```json
{
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "OTEL_METRICS_EXPORTER": "otlp",
    "OTEL_LOGS_EXPORTER": "otlp",
    "OTEL_EXPORTER_OTLP_PROTOCOL": "http/protobuf",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "https://oneuptime.com/otlp",
    "OTEL_EXPORTER_OTLP_HEADERS": "x-oneuptime-token=YOUR_INGESTION_TOKEN",
    "OTEL_RESOURCE_ATTRIBUTES": "team.id=platform,cost_center=eng-123,department=engineering"
  }
}
```

آن را در مسیر تنظیمات مدیریت‌شده مربوط به آن بستر بگذارید:

| بستر          | مسیر                                                            |
| ------------- | --------------------------------------------------------------- |
| macOS         | `/Library/Application Support/ClaudeCode/managed-settings.json` |
| Linux و WSL   | `/etc/claude-code/managed-settings.json`                        |
| Windows       | `C:\Program Files\ClaudeCode\managed-settings.json`             |

روی Windows، مسیر قدیمی `C:\ProgramData\ClaudeCode\managed-settings.json` دیگر خوانده **نمی‌شود**. فایل را آنجا نگذارید.

**اگر از پیش سیاستی دارید، به‌جای فایل اصلی از فایل افزودنی استفاده کنید.** پوشه‌ای به نام `managed-settings.d/` کنار فایل اصلی، فایل‌های `*.json` را به ترتیب الفبایی ادغام می‌کند، پس یک `10-telemetry.json` که فقط تله‌متری دارد، بدون دست زدن به فایل سیاست امنیتی موجود، تمیز عرضه می‌شود. از نسخه v2.1.223 بلوک `env` **به ازای هر متغیر** در سراسر منبع‌های مدیریتی ادغام می‌شود — اما متغیرهای تله‌متری همان استثنایی‌اند که باید برایش برنامه بریزید. کلیدهای صادرکننده `OTEL_EXPORTER_OTLP_*`، کلیدهای روشن/خاموش ثبت محتوا یعنی `OTEL_LOG_*`، متغیر `OTEL_LOGS_EXPORTER` و متغیرهای بتای ردیابی همگی به‌صورت **یک واحد یکپارچه** جابه‌جا می‌شوند: همه‌شان از بالارتبه‌ترین منبع مدیریتی می‌آیند که هر یک از آن‌ها را تنظیم کرده باشد، پس نقطه پایانی صادرکننده از یک منبع هرگز نمی‌تواند با اعتبارنامه‌های منبعی دیگر جفت شود. بنابراین یک فایل افزودنی تله‌متری در `managed-settings.d/` اگر منبعی بالارتبه‌تر (تنظیمات مدیریت‌شده کارساز، یا سیاست MDM/رجیستری) از پیش هر متغیر `OTEL_EXPORTER_OTLP_*`، `OTEL_LOG_*` یا `OTEL_LOGS_EXPORTER` را تنظیم کرده باشد — یا `otelHeadersHelper` را برساند — اصلاً هیچ سهمی نمی‌گذارد. متغیرهای `OTEL_METRICS_EXPORTER` و `OTEL_TRACES_EXPORTER` واقعاً کلید به کلید ادغام می‌شوند. فایل‌های افزودنی درون منبع فایلی هنوز کلید به کلید با یکدیگر ادغام می‌شوند.

سازوکارهای دیگر تحویل همان JSON، اگر ناوگان شما این‌گونه مدیریت می‌شود:

- تنظیمات مدیریت‌شده کارساز از کنسول مدیریت claude.ai — هنگام راه‌اندازی دریافت و ساعتی یک بار پیمایش می‌شود.
- یک نمایه پیکربندی macOS در دامنه ترجیحات مدیریت‌شده `com.anthropic.claudecode`.
- رجیستری Windows: مقداری به نام `Settings` از نوع `REG_SZ` زیر `HKLM\SOFTWARE\Policies\ClaudeCode`، با بازگشت به `HKCU`.

تقدم، از بالاترین: مدیریت‌شده کارساز → سیاست MDM/سیستم‌عامل → فایل‌های تنظیمات مدیریت‌شده (`managed-settings.json` به‌علاوه `managed-settings.d/*.json`) → `HKCU`. این منبع‌ها با یکدیگر ادغام **نمی‌شوند**: Claude Code نخستین منبعی را که دست‌کم یک کلید سیاست برساند به کار می‌برد و باقی را به‌کل و بی‌هیچ هشداری نادیده می‌گیرد. کلید `env` یکی از معدود کلیدهایی است که در سراسر منبع‌ها خوانده می‌شود — مشروط به همان ملاحظه واحد یکپارچه تله‌متری در بالا.

یک دام که ارزش دارد برایش برنامه بریزید: وقتی تغییری از تنظیمات **مدیریت‌شده کارساز** برخی متغیرهای `env` را لمس کند، توسعه‌دهنده باید پیش از اثرگذاری آن، در نشستی تعاملی یک گفتگوی تأیید امنیتی را بپذیرد. هر متغیری این را برنمی‌انگیزد — Anthropic کلیدهای ویژگی، تنظیمات مدل، گزینه‌های رابط کاربری و کران‌های عددی را بی‌هیچ پرسشی اعمال می‌کند — اما `OTEL_EXPORTER_OTLP_ENDPOINT` ناتهی همیشه برمی‌انگیزدش، پس عرضه تله‌متری از راه مدیریت‌شده کارساز همیشه به آن گفتگو نیاز دارد. تنظیمات مدیریت‌شده فایل‌محور و سیاست‌های MDM این گام را ندارند.

**روی ماشین یک توسعه‌دهنده راستی‌آزمایی کنید.** در Claude Code فرمان `/status` را اجرا کنید و به خط `Setting sources` نگاه کنید — باید `Enterprise managed settings` را نشان دهد و پس از آن منبع را در پرانتز: ‏`(file)` برای `managed-settings.json`، ‏`(drop-ins)` یا `(file + drop-ins)` اگر `managed-settings.d/` را به کار برده‌اید، `(remote)` برای مدیریت‌شده کارساز، `(plist)` / `(HKLM)` برای سیاست MDM یا سیستم‌عامل، و `(HKCU)` برای بازگشت به رجیستری. این تأیید می‌کند که فایل پیدا و تجزیه شده است، پیش از آنکه در OneUptime دنبال داده گمشده بگردید. اگر آن خط منبعی جز آنچه مستقر کرده‌اید را نام ببرد، منبعی با تقدم بالاتر برنده شده و منبع شما نادیده گرفته شده است.

**چرخاندن اعتبارنامه‌ها.** اگر نمی‌توانید توکنی درازعمر را در فایل بپزید، در `.claude/settings.json` مقدار `"otelHeadersHelper": "/path/to/generate-otel-headers.sh"` را بگذارید. اسکریپت باید یک شیء JSON تخت از جفت‌های کلید/مقدار رشته‌ای چاپ کند، برای نمونه `{"x-oneuptime-token":"..."}`. هنگام راه‌اندازی اجرا می‌شود و سپس هر `CLAUDE_CODE_OTEL_HEADERS_HELPER_DEBOUNCE_MS` میلی‌ثانیه (پیش‌فرض `1740000`، یعنی ۲۹ دقیقه). شکست‌ها در `/status`، در گزارش `--debug` و روی stderr زیر `-p` پدیدار می‌شوند.

## انتساب مصرف به کارمندان و تیم‌ها

‏OneUptime کنشگر انسانی را از تله‌متری بیرون می‌کشد و به ستون‌های پرس‌وجوپذیر غیرعادی‌سازی می‌کند، پس می‌توانید افراد و تیم‌ها را بر پایه خرج رتبه‌بندی کنید بی‌آنکه پالایه ویژگی را دستی بنویسید.

**کلید کارمند `user.email` است.** ‏Claude Code آن را «نشانی ایمیل کاربر (وقتی از راه OAuth احراز هویت شده باشد)» و «همیشه گنجانده‌شده وقتی در دسترس باشد» مستند می‌کند، و برخلاف `session.id`، `app.version`، `app.entrypoint` و شناسه‌های حساب — که همه کلید روشن/خاموش دارند — هیچ متغیر محیطی‌ای برای سرکوبش نیست. پس زیر ورود claude.ai / Console SSO به‌طور پیش‌فرض هم روی نقطه داده‌های سنجه و هم روی رکوردهای رویداد می‌رسد، و OneUptime بی‌هیچ پیکربندی‌ای برش می‌دارد.

**حواستان به ملاحظه احراز هویت باشد.** عبارت «وقتی از راه OAuth احراز هویت شده باشد» می‌رساند که وقتی CLI با `ANTHROPIC_API_KEY` خام، یا از راه Amazon Bedrock یا Google Vertex احراز هویت کند، `user.email` **غایب** است. مستندات Anthropic این را صریح نمی‌گوید، پس به‌جای فرض کردن، آن را در برابر ناوگان خودتان راستی‌آزمایی کنید. اگر توسعه‌دهندگانتان از احراز هویت کلید API، Bedrock یا Vertex استفاده می‌کنند و ایمیل نیست، گزینه‌هایتان این‌هاست:

- به `user.account_uuid` (و `user.account_id`) بازگردید، که با `OTEL_METRICS_INCLUDE_ACCOUNT_UUID` دروازه‌بانی می‌شوند — پیش‌فرض `true`. این‌ها به ازای هر حساب پایدارند اما UUIDهایی مبهم‌اند، پس به نگاشت خودتان از UUID به شخص نیاز خواهید داشت.
- اگر تدارک‌دهی شما از پیش می‌داند چه کسی پشت صفحه‌کلید است، هویت را خودتان روی هر ماشین در `OTEL_RESOURCE_ATTRIBUTES` بگذارید.

**روی نصبی معمولی `user.id` را به‌عنوان کلید کارمند به کار نبرید.** به‌طور پیش‌فرض شناسه‌ای ناشناس و تصادفی است که در `~/.claude.json` ماندگار می‌شود: به ازای هر نصب، نه به ازای هر شخص، و اگر آن فایل پاک شود بازنشانی می‌شود. (‏OneUptime برای ترافیک عمومی GenAI در OpenTelemetry مقدار `user.id` را به‌عنوان شناسه کارمند می‌خواند، جایی که ویژگی متعارف کنشگر است — Claude Code استثناست، و به همین دلیل `user.email` تقدم دارد.)

**یک استثنا هست: دروازه اپ‌های Claude.** وقتی Claude Code به دروازه خودمیزبان اپ‌های Claude وارد شده باشد، CLI صادرات‌ها را با هویت احراز هویت‌شده از نشست دروازه مهر می‌زند — `user.id` به‌جای شناسه‌ای ناشناس برای نصب، همان سوژه IdP است، `user.email` ایمیل واردشده است، `user.groups` عضویت گروهی IdP را به‌صورت رشته‌ای جداشده با ویرگول حمل می‌کند، و هر صادراتی `identity.source=gateway-oidc` را هم حمل می‌کند. همین دروازه را به راه پشتیبانی‌شده برای رساندن `user.email` واقعی به ناوگانی روی Bedrock، Vertex یا کلید API تبدیل می‌کند. توجه کنید که در نشست‌های دروازه، هویت دروازه آخر از همه اعمال می‌شود، پس کلیدهای `user.*` و `identity.*` که از راه `OTEL_RESOURCE_ATTRIBUTES` تنظیم کرده باشید نادیده گرفته می‌شوند.

**تیم‌ها و مراکز هزینه** از ویژگی‌های منبع می‌آیند. آن‌ها را به ازای هر ماشین، هر تیم، یا هر نمایه تنظیمات مدیریت‌شده بگذارید:

```bash
export OTEL_RESOURCE_ATTRIBUTES="team.id=platform,team=Platform_Engineering,cost_center=eng-123,department=engineering"
```

**مقادیر `OTEL_RESOURCE_ATTRIBUTES` نمی‌توانند فاصله داشته باشند.** ‏Anthropic این را قاعده‌ای سخت‌گیرانه در قالب‌بندی مستند می‌کند: `team=Platform Engineering` نامعتبر است. به‌جایش از زیرخط، camelCase یا رمزگذاری درصدی (`team=John%27s%20Team`) استفاده کنید. گیومه گذاشتن فاصله را نمی‌گریزاند — ‏`org.name="My Company"` مقدار تحت‌اللفظی `"My Company"` را با خود گیومه‌ها تولید می‌کند.

‏OneUptime روی `team.id`، `team`، `cost_center` و `department` تجمیع می‌کند، و هرکدام را در هر دو املا می‌شناسد — کلید برهنه، و کلید پیشونددار `resource.` که دریافت OTLP برای یک ویژگی منبع تولید می‌کند. این اینجا اهمیت دارد، چون Claude Code هر دو را به شما می‌دهد: به‌طور پیش‌فرض هر کلید `OTEL_RESOURCE_ATTRIBUTES` را روی هر نقطه داده سنجه و هر رکورد رویداد رونوشت می‌کند (`OTEL_METRICS_INCLUDE_RESOURCE_ATTRIBUTES`، پیش‌فرض `true`)، و کلیدها صرف‌نظر از آن در بلوک منبع OTLP هستند. گذاشتن این کلید روی `false` باز هم تجمیع تیمی را کارآمد نگه می‌دارد، از راه املای بلوک منبع. کلیدهای سفارشی هرگز نمی‌توانند بر توکارها بچربند — در برخورد، مقدار توکار برنده است.

مقدار `organization.id` وقتی در دسترس باشد گنجانده می‌شود و اگر بیش از یک سازمان Anthropic را به همان پروژه دریافت می‌کنید، کلید مستأجر مفیدی است.

## مرجع سنجه‌ها

هر سنجه‌ای یک شمارنده است. همه‌شان **افزون بر** ویژگی‌های ویژه هر سنجه، ویژگی‌های استاندارد زیر را هم حمل می‌کنند.

| سنجه                                  | یکا    | ویژگی‌های کلیدی                                                                                                                                                                                                                                                                                |
| ------------------------------------- | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `claude_code.session.count`           | ندارد  | `start_type` = `fresh` \| `resume` \| `continue` \| `agents_view`                                                                                                                                                                                                                              |
| `claude_code.lines_of_code.count`     | ندارد  | `type` = `added` \| `removed`؛ `model`                                                                                                                                                                                                                                                         |
| `claude_code.commit.count`            | ندارد  | فقط ویژگی‌های استاندارد                                                                                                                                                                                                                                                                        |
| `claude_code.pull_request.count`      | ندارد  | فقط ویژگی‌های استاندارد                                                                                                                                                                                                                                                                        |
| `claude_code.cost.usage`              | USD    | `model`؛ `query_source` = `main` \| `subagent` \| `auxiliary`؛ `speed` = `fast` (در غیر این صورت غایب)؛ `effort` = `low` \| `medium` \| `high` \| `xhigh` \| `max`؛ `agent.name`، `skill.name`، `plugin.name`، `marketplace.name`، `mcp_server.name`، `mcp_tool.name` (وقتی مصداق ندارد غایب) |
| `claude_code.token.usage`             | tokens | `type` = `input` \| `output` \| `cacheRead` \| `cacheCreation`؛ به‌علاوه `model`، `query_source`، `speed`، `effort` و همان کلیدهای انتساب عامل/مهارت/افزونه/MCP                                                                                                                               |
| `claude_code.code_edit_tool.decision` | ندارد  | `tool_name` = `Edit` \| `Write` \| `NotebookEdit`؛ `decision` = `accept` \| `reject`؛ `source` = `config` \| `hook` \| `user_permanent` \| `user_temporary` \| `user_abort` \| `user_reject`؛ `language` (برای نمونه `TypeScript`، `Python`، `Markdown`، `unknown`)                           |
| `claude_code.active_time.total`       | s      | `type` = `user` (تعامل با صفحه‌کلید) \| `cli` (اجرای ابزار و پاسخ‌های مدل)                                                                                                                                                                                                                     |

دو نکته که غافلگیرتان می‌کنند:

- نوع‌های توکن کش **camelCase** هستند: رشته‌های تحت‌اللفظی `cacheRead` و `cacheCreation` هستند، نه `cache_read` / `cache_creation`. آن‌ها را در پالایه داشبورد به snake_case عادی‌سازی نکنید، و فرض نکنید با واژگانی که Anthropic در Admin API خود به کار می‌برد یکی‌اند.
- سنجه `claude_code.active_time.total` با یکای `s` مستند شده است. اینکه مقدارش ثانیه کسری است یا نه مستند نشده — پیش از آنکه آن را رقمی دقیق گزارش کنید، نمونه‌ای از داده خودتان را بررسی کنید.
- تنها سه سنجه اصلاً رشته یکای OpenTelemetry حمل می‌کنند: `claude_code.cost.usage` (`USD`)، `claude_code.token.usage` (`tokens`) و `claude_code.active_time.total` (`s`). آن پنج سنجه شمارشی هیچ‌کدام را حمل نمی‌کنند. و وقتی `prometheus` تنها صادرکننده فهرست‌شده در `OTEL_METRICS_EXPORTER` باشد، Claude Code حتی همان سه یکا را هم حذف می‌کند.

**ویژگی‌های استاندارد روی هر سنجه و هر رویداد:** `session.id`، `app.version`، `app.entrypoint`، `organization.id`، `user.account_uuid`، `user.account_id`، `user.id`، `user.email`، `terminal.type`، به‌علاوه کلیدهای `OTEL_RESOURCE_ATTRIBUTES` شما. چند تا از این‌ها دروازه‌بانی می‌شوند — [کاردینالیتی و مهار هزینه](#cardinality-and-cost-control) را ببینید.

روی `claude_code.cost.usage` و `claude_code.token.usage`، نام‌های عامل، مهارت، افزونه، کارساز MCP و ابزار MCP که شخص ثالث یا کاربر تعریفشان کرده باشد، به مقادیر عمومی مانند `custom` / `third-party` **پوشانده** می‌شوند — بی‌قید و شرط. متغیر `OTEL_LOG_TOOL_DETAILS` به‌عنوان چیزی مستند شده که بر رویدادهای ابزار، نام فرمان‌های `user_prompt` و ویژگی‌های اسپن ردیابی اثر می‌گذارد، نه بر این ویژگی‌های انتساب سنجه‌ای، پس روشن کردنش تفکیک هزینه را از پوشش درنمی‌آورد. نام‌های توکار، همراه‌شده، تعریف‌شده کاربر (برای مهارت‌ها) و بازارچه رسمی عیناً پدیدار می‌شوند؛ `marketplace.name` اصلاً فقط برای افزونه‌های بازارچه رسمی منتشر می‌شود.

## مرجع رویدادها (گزارش‌های OTLP)

رویدادها به‌صورت رکوردهای گزارش OTLP می‌رسند. هر رکوردی `event.name` (نام برهنه بدون پیشوند `claude_code.`)، `event.timestamp` (‏ISO 8601) و `event.sequence` (شمارنده‌ای یکنوا) را هم حمل می‌کند. رکوردها افزون بر آن، برای همبستگی `prompt.id`، `message.uuid`، `workspace.host_paths`، `workflow.run_id`، `workflow.name` و `client_request_id` را حمل می‌کنند، و — **تنها در Agent SDK و نشست‌های غیرتعاملی `-p`** — مقادیر `trace_id` / `span_id` را از `TRACEPARENT` ورودی برمی‌دارند، حتی وقتی هیچ صادرکننده ردیابی‌ای پیکربندی نشده باشد. نشست‌های تعاملی عمداً `TRACEPARENT` ورودی را نادیده می‌گیرند تا مقادیر محیطی CI یا کانتینر را به ارث نبرند، پس رکوردهای نشست پایانه یک توسعه‌دهنده هیچ بافتار ردیابی ارثی حمل نمی‌کنند.

| `claude_code.assistant_response`      | `response_length`، `model`، `request_id`، `query_source`؛ متن `response` مگر اینکه صراحتاً انتخابش کنید پوشانده می‌شود                                                                                         |
| `claude_code.tool_result`             | `tool_name`، `tool_use_id`، `success`، `duration_ms`، `error_type`، `decision_type`، `decision_source`، اندازه‌های ورودی/نتیجه                                                                                 |

## کاردینالیتی و مهار هزینه

‏Claude Code به‌طور پیش‌فرض `session.id` را روی هر نقطه داده سنجه می‌گذارد، و شناسه‌های نشست بی‌کران‌اند. روی ناوگانی با هر اندازه‌ای، همین یک ویژگی بزرگ‌ترین محرک هزینه ذخیره‌سازی سنجه است — صد توسعه‌دهنده که روزی ده نشست اجرا می‌کنند یعنی روزی هزار سری تازه، به ازای هر سنجه، تا ابد.

**برای عرضه‌های ناوگان‌گستر خاموشش کنید.** برای گزارش‌دهی هزینه و مصرف چیزی از دست نمی‌دهید. این متغیر به‌عنوان مهار کاردینالیتیِ _سنجه‌ها_ نام‌گذاری و مستند شده است، اما جدول ویژگی‌های Anthropic سنجه‌ها و رویدادها را با هم پوشش می‌دهد و صریح نمی‌گوید که وقتی خاموش باشد رکوردهای رویداد `session.id` را نگه می‌دارند یا نه — پیش از آنکه در جریان رویداد به همبستگی به ازای هر نشست تکیه کنید، نمونه‌ای از رویدادهای خودتان را بررسی کنید.

```bash
export OTEL_METRICS_INCLUDE_SESSION_ID=false
```

مجموعه کامل کلیدهای روشن/خاموش هویت، با پیش‌فرض‌هایشان:

| متغیر                                      | پیش‌فرض | اثر                                                                           |
| ------------------------------------------ | ------- | ----------------------------------------------------------------------------- |
| `OTEL_METRICS_INCLUDE_SESSION_ID`          | `true`  | مقدار `session.id` را می‌افزاید — کاردینالیتی بی‌کران                         |
| `OTEL_METRICS_INCLUDE_VERSION`             | `false` | مقدار `app.version` را می‌افزاید                                              |
| `OTEL_METRICS_INCLUDE_ACCOUNT_UUID`        | `true`  | هم `user.account_uuid` و هم `user.account_id` را می‌افزاید                    |
| `OTEL_METRICS_INCLUDE_ENTRYPOINT`          | `false` | مقدار `app.entrypoint` را می‌افزاید (`cli`، `sdk-cli`، `sdk-ts`، `sdk-py`، `claude-vscode`) |
| `OTEL_METRICS_INCLUDE_RESOURCE_ATTRIBUTES` | `true`  | کلیدهای `OTEL_RESOURCE_ATTRIBUTES` را روی هر نقطه داده رونوشت می‌کند          |

برای `user.email`، `user.id`، `organization.id` یا `terminal.type` هیچ کلید روشن/خاموشی نیست — وقتی در دسترس باشند همیشه گنجانده می‌شوند.

**بازه‌های صادرات** به‌طور پیش‌فرض برای سنجه‌ها ۶۰۰۰۰ میلی‌ثانیه (`OTEL_METRIC_EXPORT_INTERVAL`)، برای گزارش‌ها ۵۰۰۰ میلی‌ثانیه (`OTEL_LOGS_EXPORT_INTERVAL`) و برای ردیابی‌ها ۵۰۰۰ میلی‌ثانیه (`OTEL_TRACES_EXPORT_INTERVAL`) هستند. گزارش‌ها سیگنال پرسروصدا هستند: تخلیه‌ای ۵ ثانیه‌ای به ازای هر صندلی فعال توسعه‌دهنده همان چیزی است که باید دریافت را برایش اندازه‌گذاری کنید. بالا بردن `OTEL_LOGS_EXPORT_INTERVAL` به ازای هر درخواست دسته بزرگ‌تری می‌فرستد و حجم درخواست را کم می‌کند، به بهای تأخیری بلندتر تا پدیدار شدن رویدادها.

اگر فقط گزارش‌دهی هزینه و مصرف می‌خواهید و نه جریان رویداد، `OTEL_LOGS_EXPORTER=none` را بگذارید و سنجه‌ها را روشن نگه دارید. هزینه، توکن، نشست، کامیت، PR، خط کد، تصمیم ابزار و زمان فعال، همه در سنجه‌ها زندگی می‌کنند.

## حریم خصوصی: محتوای اعلان و ابزار به‌طور پیش‌فرض خاموش است

‏Claude Code متن اعلان، پاسخ‌های دستیار، آرگومان‌های ابزار یا خروجی ابزار را صادر **نمی‌کند** مگر اینکه هرکدام را صریحاً روشن کنید. هر چیزی در این جدول به‌طور پیش‌فرض خاموش است:

| متغیر                          | پیش‌فرض | مقدار `1` چه چیزی را روشن می‌کند                                                                                             |
| ------------------------------ | ------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `OTEL_LOG_USER_PROMPTS`        | خاموش   | متن خام اعلان روی `claude_code.user_prompt`                                                                                  |
| `OTEL_LOG_ASSISTANT_RESPONSES` | خاموش   | متن خام پاسخ؛ وقتی تنظیم نشده باشد به `OTEL_LOG_USER_PROMPTS` بازمی‌گردد، و `0` پوشیده نگهش می‌دارد                          |
| `OTEL_LOG_TOOL_DETAILS`        | خاموش   | پارامترها و آرگومان‌های ابزار، و نام‌های افزونه/مهارت/MCP شخص ثالث را از پوشش درمی‌آورد                                      |
| `OTEL_LOG_TOOL_CONTENT`        | خاموش   | محتوای ورودی و خروجی ابزار در رویدادهای اسپن — به بتای ردیابی‌ها نیاز دارد، پس روی راه‌اندازی فقط‌سنجه‌وگزارش کاری نمی‌کند |
| `OTEL_LOG_RAW_API_BODIES`      | خاموش   | بدنه‌های کامل درخواست/پاسخ به‌صورت درون‌خطی، یا `file:<dir>` برای نوشتنشان روی دیسک                                          |

**‏OneUptime روشن کردن این‌ها را توصیه نمی‌کند.** سنجه‌ها و رویدادهای پوشیده از پیش به پرسش‌هایی که این صفحه درباره‌شان است پاسخ می‌دهند — چه کسی چه خرجی کرد، روی کدام مدل، با چه نرخ پذیرشی. روشن کردن ثبت محتوا، اعلان‌های توسعه‌دهندگانتان، کد منبعتان و خروجی ابزارتان را به انباره‌ای تله‌متری می‌برد، جایی که مشمول مجموعه‌ای متفاوت از کنترل‌های دسترسی نسبت به مخزن شماست. متغیر `CLAUDE_CODE_OTEL_CONTENT_MAX_LENGTH` (پیش‌فرض `61440`، یعنی ۶۰ کیلوبایت بر حسب یکاهای کد UTF-16) سقف می‌گذارد که چه مقدار از آن به ازای هر رکورد سفر کند، که حجم را محدود می‌کند اما حساسیت را نه.

اگر برای بررسی مشخصی ثبت محتوا را فعال می‌کنید، **قاعده‌های پاک‌سازی** و **پالایه‌های انداختن** تله‌متری OneUptime را زیر **Traces → Settings** اعمال کنید تا ویژگی‌ها پیش از ذخیره شدن پوشانده یا انداخته شوند، و وقتی بررسی تمام شد دوباره خاموشش کنید.

## سنجه‌ها به‌صورت جمع‌های دلتا می‌رسند

‏Claude Code مقدار `OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE` را به‌طور پیش‌فرض روی `delta` می‌گذارد، نه `cumulative`. هر نقطه داده افزایش از صادرات پیشین است، نه جمعی دونده.

این وقتی نمودار و مانیتور می‌سازید اهمیت دارد: **نقطه داده‌ها را روی پنجره جمع بزنید**. آن‌گونه که با شمارنده‌ای یکنوا و تجمعی رفتار می‌کنید، تابع نرخ تغییر یا بازنشانی شمارنده را اعمال نکنید — عددها به‌جای اینکه آشکارا خراب باشند، غلط درمی‌آیند، که بدترین نوع غلط است.

اگر سازمان شما روی زمان‌مندی تجمعی در سراسر هر صادرکننده‌ای استاندارد شده است، می‌توانید سنجاقش کنید:

```bash
export OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE=cumulative
```

دلتا پیش‌فرض است و بیشتر ناوگان‌ها باید به حال خودش بگذارندش. فقط سازگار باشید — دو حالت را در سراسر همان ناوگان قاطی نکنید، وگرنه تجمیع‌هایتان دوبار می‌شمارند.

## ‏OneUptime چه چیزی نشانتان می‌دهد

در نوار ناوبری (زیر Observability) بخش **AI / LLM** را باز کنید. زبانه **Usage** کارمندان، تیم‌ها، مدل‌ها، ارائه‌دهندگان و سرویس‌ها را بر پایه خرج رتبه‌بندی می‌کند، و سنجه `claude_code.cost.usage` از Claude Code مستقیم تفکیک‌های کارمند، تیم و مدل را تغذیه می‌کند — بدون گام نگاشت، بدون بخش جداگانه‌ای برای عامل کدنویس. مقدار `claude_code.token.usage` هم به همین شکل کاشی‌های توکن صفحه Overview را تغذیه می‌کند.

پیش از آنکه گزارشی بر این بنا کنید، دو بند بعدی را بخوانید، چون هر دو باربرند.

**سنجه‌ها بازگشتی برای اسپن‌ها هستند، نه هرگز افزوده‌ای بر آن‌ها.** اسپن‌های GenAI مرجع‌اند، و به جریان سنجه تنها وقتی رجوع می‌شود که جریان اسپن چیزی گزارش نکرده باشد — این دو هرگز با هم جمع نمی‌شوند، چون وگرنه منتشرکننده‌ای که هر دو سیگنال را تولید کند هر دلاری را دوبار می‌شمرد. پس در پروژه‌ای که برنامه‌های ابزارگذاری‌شده خودتان از پیش اسپن‌های GenAI با هزینه روی آن‌ها تولید می‌کنند، **خرج سنجه‌منشأ Claude Code پدیدار نمی‌شود**. اگر می‌خواهید خرج ناوگان به‌تنهایی دیده شود، آن را به پروژه OneUptime خودش با کلید دریافت خودش صادر کنید، تا جریان اسپن آنجا تهی باشد و بازگشت درگیر شود. (روشن کردن [بتای ردیابی‌ها](#optional-traces-beta) هم تصویر را عوض می‌کند: آن اسپن‌ها اسپن‌های واقعی GenAI هستند، و به‌محض وجودشان همان‌هایند که صفحه می‌خواند.)

**سطری که منشأ سنجه‌ای دارد فقط هزینه حمل می‌کند.** در جدول Usage، ستون‌های Calls و توکن برای سطرهای سنجه‌منشأ به‌صورت `—` رندر می‌شوند — شمارنده خرج هیچ جزئیاتی به ازای هر فراخوان ندارد، و خط تیره صادق است جایی که `0` ادعا می‌کرد توسعه‌دهنده هیچ فراخوانی نکرده است. ارقامی که منشأشان سنجه است روی صفحه با برچسب **from GenAI metrics** نشانه‌گذاری می‌شوند. تفکیک‌های Provider و Application / Service اصلاً بازگشت سنجه‌ای ندارند: شمارنده‌های `claude_code.*` هیچ `gen_ai.system` حمل نمی‌کنند و به سرویس تله‌متری OneUptime بسته نیستند.

از آنجا:

- برای دیدن خرج به ازای هر توسعه‌دهنده بر کارمند مرتب کنید، و برای بازپرداخت هزینه بر تیم یا مرکز هزینه، با به‌کارگیری ویژگی‌های منبع `team.id` / `cost_center` که هنگام عرضه گذاشته‌اید. هر دو تفکیک از سنجه‌ها کار می‌کنند؛ گروه‌بندی کارمند نخست با `user.email` تطبیق می‌کند و از راه `user.account_uuid` / `user.account_id` عقب می‌نشیند، پس ناوگانی با احراز هویت کلید API و بدون ایمیل هم به‌جای فرو ریختن در یک سطل Unattributed واحد، روی سطرهای خودش می‌نشیند.
- خرج را بر پایه مدل تفکیک کنید — ویژگی `model` روی `claude_code.cost.usage` برای تفکیک Model خوانده می‌شود. مقدار `query_source` (عامل اصلی در برابر زیرعامل‌ها) یکی از بُعدهای زبانه Usage نیست؛ به‌جایش روی داشبوردی نمودارش کنید.
- روی هر یک از آن هشت سنجه **داشبورد** بسازید — نرخ پذیرش، خط کد، کامیت و PR به ازای هر توسعه‌دهنده، زمان فعال.
- **مانیتور سنجه** بسازید تا روی آستانه‌ای از خرج یا توکن هشدار دهد. [مانیتور سنجه‌ها](/docs/monitor/metrics-monitor) را ببینید.

برای تصویر گسترده‌تر — فراخوان‌های LLM از برنامه‌های خودتان، اعلان‌ها و تکمیل‌ها، بودجه‌های روزانه هزینه — [رصدپذیری هوش مصنوعی/LLM](/docs/telemetry/ai-llm-observability) را ببینید.

## اختیاری: بتای ردیابی‌ها

هر چیزی در بالا سنجه و گزارش است، که راه پشتیبانی‌شده و همانی است که باید عرضه کنید. Claude Code یک صادرکننده ردیابی **بتا** هم دارد که برای اجرای یک عامل آبشارهای واقعی تولید می‌کند. اختیاری است، Anthropic آن را بتا نشانه‌گذاری کرده، و می‌تواند تغییر کند.

```bash
export CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1
export OTEL_TRACES_EXPORTER=otlp
```

(مقدار `ENABLE_ENHANCED_TELEMETRY_BETA` نام مستعار پذیرفته‌شده متغیر نخست است.)

نام اسپن‌ها در بالا `claude_code.interaction` است، با `claude_code.llm_request` و `claude_code.tool` زیرش، و `claude_code.tool.blocked_on_user` / `claude_code.tool.execution` زیر اسپن ابزار. اسپن `claude_code.hook` با آن دو متغیر بالا منتشر **نمی‌شود**: به ردیابی بتای _تفصیلی_ نیاز دارد (`ENABLE_BETA_TRACING_DETAILED=1` به‌علاوه `BETA_TRACING_ENDPOINT`)، و در نشست‌های تعاملی CLI سازمان شما باید برایش در فهرست مجاز باشد — نشست‌های Agent SDK و غیرتعاملی `-p` دروازه‌بانی نمی‌شوند. اسپن‌های LLM کلیدهای قرارداد معنایی GenAI را حمل می‌کنند — `gen_ai.system` (همیشه `anthropic`)، `gen_ai.request.model`، `gen_ai.response.id`، `gen_ai.response.finish_reasons` — در کنار `input_tokens`، `output_tokens`، `cache_read_tokens`، `cache_creation_tokens`، `ttft_ms`، `duration_ms`، `stop_reason` و `llm_request.context`. (کلید `gen_ai.tool.call.id` روی اسپن‌های `claude_code.tool` و `claude_code.tool.execution` می‌نشیند و آینه `tool_use_id` است — نه روی اسپن LLM.) چون کلیدهای استاندارد GenAI را به کار می‌برند، OneUptime آن‌ها را همان‌گونه فراخوان LLM رده‌بندی می‌کند که اسپن‌های هر [ابزارگذاری GenAI](/docs/telemetry/ai-llm-observability) دیگری را.

به‌طور پیش‌فرض هدر `traceparent` استاندارد W3C روی درخواست‌های مدل و درخواست‌های MCP روی HTTP تنها وقتی فرستاده می‌شود که `ANTHROPIC_BASE_URL` تنظیم نشده باشد یا به API خود Anthropic اشاره کند، چون برخی پراکسی‌ها هدرهای ناشناخته را رد می‌کنند. مقدار `CLAUDE_CODE_PROPAGATE_TRACEPARENT=1` آن را از میان پراکسی `ANTHROPIC_BASE_URL` سفارشی هم پیش می‌برد. زیرفرایندهای Bash و PowerShell مقدار `TRACEPARENT` را خودکار به ارث می‌برند، پس اسکریپت ساختی که خودش ابزارگذاری شده به همان ردیابی می‌پیوندد — اما آن وراثت را همان کلید اداره می‌کند، پس پشت پراکسی سفارشی، زیرفرایندها تنها وقتی `TRACEPARENT` می‌گیرند که `CLAUDE_CODE_PROPAGATE_TRACEPARENT=1` را هم بگذارید.

## رفع اشکال

**اصلاً چیزی نمی‌رسد.** کلید اصلی را تأیید کنید: `CLAUDE_CODE_ENABLE_TELEMETRY=1`. بدون آن هیچ‌یک از متغیرهای دیگر کاری نمی‌کنند.

**پیش از آنکه شبکه را مقصر بدانید، تأیید کنید Claude Code دارد داده تولید می‌کند.** مقدار `console` را به فهرست صادرکننده‌ها بیفزایید و stdout را تماشا کنید:

```bash
export OTEL_METRICS_EXPORTER=otlp,console
export OTEL_LOGS_EXPORTER=otlp,console
```

اگر نقطه داده‌ها چاپ شدند، ابزارگذاری سالم است و مشکل از نقطه پایانی، توکن، یا چیزی میان شما و OneUptime است.

**بررسی کنید Claude Code واقعاً چه تنظیماتی را بارگذاری کرده است.** فرمان `/status` را اجرا کنید. خط `Setting sources` به شما می‌گوید کدام منبع مدیریت‌شده برداشته شده است — `Enterprise managed settings (file)`، `(drop-ins)`، `(file + drop-ins)`، `(remote)`، `(plist)`، `(HKLM)` یا `(HKCU)`. اگر چیزی فهرست نشده، فایل در مسیر اشتباه است، JSON معتبری نیست، یا حساب کاربری توسعه‌دهنده نمی‌تواند بخواندش. اگر منبع دیگری نام برده شده، آن منبع یکسره برنده شده و منبع شما نادیده گرفته شده است.

**تنظیمات مدیریت‌شده درست به نظر می‌رسند اما بلوک env نادیده گرفته می‌شود.** اگر تغییر به‌جای فایل از تنظیمات **مدیریت‌شده کارساز** آمده باشد، توسعه‌دهنده باید نخست در نشستی تعاملی گفتگوی تأیید امنیتی را بپذیرد — `OTEL_EXPORTER_OTLP_ENDPOINT` ناتهی همیشه برمی‌انگیزدش. از او بخواهید یک بار Claude Code را تعاملی باز کند. اگر تنظیمات از فایل آمده، بررسی کنید هیچ منبع مدیریت‌شده با تقدم بالاتری (مدیریت‌شده کارساز، سیاست MDM/سیستم‌عامل) یکسره برنده نشده باشد — [عرضه ناوگانی با تنظیمات مدیریت‌شده](#fleet-rollout-with-managed-settings) را ببینید.

**داده هست اما بدون انتساب نشان داده می‌شود.** مقدار `user.email` تنها زیر احراز هویت OAuth به‌عنوان حاضر مستند شده است. بررسی کنید آن توسعه‌دهندگان با `ANTHROPIC_API_KEY`، Bedrock یا Vertex احراز هویت می‌کنند یا نه — [انتساب مصرف به کارمندان و تیم‌ها](#attributing-usage-to-employees-and-teams) را ببینید.

**تیم یا مرکز هزینه نیست.** تأیید کنید `OTEL_RESOURCE_ATTRIBUTES` روی ماشین تنظیم شده باشد، و `OTEL_METRICS_INCLUDE_RESOURCE_ATTRIBUTES` روی `false` گذاشته نشده باشد — روی `false`، کلیدهای شما در بلوک منبع OTLP می‌مانند و روی نقطه داده‌ها رونوشت نمی‌شوند. برخورد با کلیدی توکار را هم بررسی کنید: توکارها همیشه برنده‌اند.

**سنجه‌ها می‌نشینند اما عددها خیلی کوچک یا خیلی بزرگ به نظر می‌رسند.** بررسی کنید نمودارتان به‌جای رفتار کردن با نقطه داده‌ها مانند شمارنده‌ای تجمعی، جمعشان می‌زند — [سنجه‌ها به‌صورت جمع‌های دلتا می‌رسند](#metrics-arrive-as-delta-sums) را ببینید.

**پیش از هر نتیجه‌گیری یک بازه کامل صبر کنید.** سنجه‌ها به‌طور پیش‌فرض هر ۶۰ ثانیه تخلیه می‌شوند. آزمونی که ۱۰ ثانیه اجرا شود و بعد OneUptime را بررسی کند چیزی نخواهد یافت.

**املای نقطه پایانی.** مقدار `OTEL_EXPORTER_OTLP_ENDPOINT` نشانی پایه (`https://oneuptime.com/otlp`) را می‌گیرد و Claude Code خودش `/v1/metrics` و `/v1/logs` را به آن می‌افزاید. متغیرهای هر سیگنال (`OTEL_EXPORTER_OTLP_METRICS_ENDPOINT`، `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT`) به‌جایش مسیر کامل می‌خواهند، و بر متغیر عمومی می‌چربند.

**توکن رد شد.** مقدار نادرست `x-oneuptime-token` هنگام دریافت رد می‌شود. آن را دوباره از **Project Settings → Telemetry & APM → Ingestion Keys** رونوشت کنید، و بررسی کنید رشته هدر `x-oneuptime-token=YOUR_INGESTION_TOKEN` باشد، بدون فاصله در دو سوی `=`.
