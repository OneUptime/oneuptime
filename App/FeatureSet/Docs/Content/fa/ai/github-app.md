# کار با OneUptime از درون GitHub

GitHub App مربوط به OneUptime فقط اتصالی به کد شما نیست — می‌توانید در خودِ مخزنتان با آن حرف بزنید و کار را همان‌جا انجام می‌دهد.

روی یک issue نامش را ببرید، درخواست ادغامی باز می‌کند. روی یک درخواست ادغام نامش را ببرید، شاخه را بازنگری می‌کند یا diff را بازبینی. به issueای برچسب بزنید، آن issue را برمی‌دارد. هرچه تولید می‌کند یک درخواست ادغام یا یک بازبینی است که انسانی بخواندش: **هرگز چیزی را ادغام نمی‌کند و هرگز درخواست ادغامی را تأیید نمی‌کند.**

```text
@oneuptime implement this                          →  درخواست ادغامی که issue را می‌بندد
@oneuptime revise this — use exponential backoff   →  کامیت‌های تازه روی شاخه همین درخواست ادغام
@oneuptime review                                  →  بازبینی کدی که روی این درخواست ادغام منتشر می‌شود
```

> به‌جای `@oneuptime` شناسه برنامه خودتان را بگذارید. روی OneUptime Cloud همان `@oneuptime` است. روی نمونه خودمیزبان، هر نامی است که به GitHub App خود داده‌اید، با حروف کوچک و فاصله‌ها تبدیل‌شده به خط تیره — از برنامه‌ای به نام «Acme AI» با `@acme-ai` نام برده می‌شود. اگر نام بردن هیچ اثری ندارد، نخستین چیزی که باید بررسی کنید همین است.

## پیش از شروع

- مخزن باید از راه GitHub App **به یک پروژه OneUptime وصل** باشد. برای راه‌اندازی [یکپارچه‌سازی GitHub (خودمیزبان)](/docs/self-hosted/github-integration) را ببینید، یا روی OneUptime Cloud از **Project Settings → Code Repositories** وصلش کنید.
- یک **Runner با قابلیت «Runs AI Code Fixes»** باید آنلاین باشد — همان Runnerای که [وظیفه‌های رفع با هوش مصنوعی](/docs/ai/ai-agent) را انجام می‌دهد. بدون آن، فرمان‌ها پذیرفته می‌شوند و سپس پس از ۳۰ دقیقه با پیامی شکست می‌خورند که می‌گوید هیچ عاملی برشان نداشته است.
- GitHub App باید دسترسی **Issues: Read & write** را داشته باشد و در رویدادهای وب‌هوکِ فهرست‌شده در [در چه رویدادهایی مشترک شوید](#در-چه-رویدادهایی-مشترک-شوید) مشترک باشد.

## فرمان‌ها

هر فرمان با نام بردن از برنامه شروع می‌شود. نام بردن می‌تواند هرجای نظر باشد، و هرچه پس از آن بنویسید به‌عنوان درخواست شما فرستاده می‌شود.

### روی یک درخواست ادغام

| فرمان | چه اتفاقی می‌افتد |
| --- | --- |
| `@oneuptime review` | شاخه را کلون می‌کند، کد تغییریافته **و کد پیرامونش** را می‌خواند و بازبینی‌ای به‌صورت نظر منتشر می‌کند. چیزی را تغییر نمی‌دهد. |
| `@oneuptime revise this — <what you want changed>` | شاخه خودِ درخواست ادغام را کلون می‌کند، تغییر را انجام می‌دهد و کامیت‌های تازه را روی همان شاخه می‌فرستد. هرگز درخواست ادغام دومی باز نمی‌کند. |

هرچه پس از نام بردن بنویسید و فرمان شناخته‌شده‌ای نباشد، درخواست بازنگری شمرده می‌شود، چون تقریباً همیشه همان است:

```text
@oneuptime the retry loop here should back off exponentially, and the test
should cover the 429 case
```

### روی یک issue

| فرمان | چه اتفاقی می‌افتد |
| --- | --- |
| `@oneuptime implement this` | روی issue کار می‌کند و درخواست ادغامی باز می‌کند که آن را می‌بندد. |
| `@oneuptime <anything else>` | همان، با کلمات شما به‌عنوان راهنمایی بیشتر. |

می‌توانید issueای را **بدون هیچ نظری** هم به برنامه بسپارید:

- **برچسب تریگر را بزنید.** زدن برچسب تریگر مخزن — به‌طور پیش‌فرض `oneuptime` — به یک issue همان کار را شروع می‌کند. این مطمئن‌ترین راه واگذاری کار از رابط GitHub است.
- **issue را به کاربر بات برنامه واگذار کنید**، جایی که مخزنتان اجازه‌اش را می‌دهد. GitHub همه‌جا نمی‌گذارد یک برنامه مسئول کار باشد، و برچسب دقیقاً برای همین هست؛ اگر واگذاری کاری نکرد، از برچسب استفاده کنید.

### هرجا

| فرمان | چه اتفاقی می‌افتد |
| --- | --- |
| `@oneuptime help` | فرمان‌ها را فهرست می‌کند. نام بردن خالی، بدون هیچ چیز پس از آن، همین کار را می‌کند. |
| `@oneuptime status` | می‌گوید هم‌اکنون در این گفت‌وگو روی چه کار می‌کند. |
| `@oneuptime cancel` | اجراهایی را که در این گفت‌وگو در جریان دارد متوقف می‌کند. کاری که از پیش فرستاده شده، فرستاده می‌ماند. |

`help`، `status` و `cancel` هرگز اجرای عاملی را شروع نمی‌کنند، پس هزینه‌ای ندارند و مشمول بودجه روزانه وظیفه‌های رفع شما نیستند.

## در گفت‌وگو چه شکلی است

هر فرمان **یک نظر** تولید می‌کند که برنامه همراه پیش رفتن کار ویرایشش می‌کند — پس وظیفه‌ای طولانی هرگز درخواست ادغام را به گزارش وضعیت بدل نمی‌کند.

1. روی نظر شما واکنش 👀 می‌گذارد و تأییدیه‌ای منتشر می‌کند که نام پروژه OneUptimeای را که اجرا به آن تعلق دارد می‌برد و به اجرای زنده پیوند می‌دهد.
2. وقتی تمام می‌شود، همان نظر با نتیجه بازنویسی می‌شود: درخواست ادغامی که باز کرده، کامیت‌هایی که فرستاده، یا توضیحی صادقانه از اینکه چرا کاری نکرده است.

اگر چیزی که ارزش تغییر داشته باشد نیابد، به‌جای باز کردن درخواست ادغامی حدسی، همین را می‌گوید. این نتیجه‌ای عادی است، نه شکست — راهنمایی بیشتری بدهید و دوباره بخواهید.

## چه کسی اجازه فرمان دادن دارد

**فقط کسانی که دسترسی write، maintain یا admin به مخزن دارند.** OneUptime هر بار مستقیم از GitHub دسترسی نویسنده نظر را روی آن مخزن می‌پرسد؛ به نشان «contributor» که GitHub کنار نظر نشان می‌دهد اعتماد نمی‌کند، چون آن نشان فعالیت گذشته را توصیف می‌کند نه دسترسی کنونی.

نام بردن از سوی هر کس دیگری فقط یک واکنش 😕 روی نظرش می‌گیرد و هیچ چیز دیگر. این عمدی است: روی مخزنی عمومی هرکسی می‌تواند نظر بدهد، و برنامه‌ای که با اطمینان به غریبه‌ها پاسخ می‌دهد، برنامه‌ای است که می‌شود با آن یک گفت‌وگو را اسپم کرد.

همچنین هر نظری را که باتی نوشته باشد، از جمله نظرهای خودش، نادیده می‌گیرد، و نام‌بردن‌هایی را که درون نقل‌قول (`>`) یا بلوک کد بیایند نادیده می‌گیرد. این دو قاعده با هم همان چیزی‌اند که نمی‌گذارند پاسخ به یکی از نظرهای خودش دوباره راهش بیندازد.

## کارهایی که نمی‌کند

- **هرگز ادغام نمی‌کند.** هیچ کاری که این برنامه می‌کند نمی‌تواند کدی را روی شاخه پیش‌فرض شما بنشاند.
- **هرگز تأیید نمی‌کند و درخواست تغییر نمی‌دهد.** بازبینی‌ها به‌صورت نظر منتشر می‌شوند، پس بازبینی یک برنامه هرگز نمی‌تواند قاعده حفاظت شاخه را برآورده کند.
- **هرگز تاریخچه را بازنویسی نمی‌کند.** بازنگری کامیت می‌افزاید؛ force-push نمی‌کند. اگر کس دیگری زودتر روی شاخه فرستاده باشد، بازنگری به‌جای دور انداختن کار او شکست می‌خورد.
- **نمی‌تواند درخواست ادغامی را که از یک fork می‌آید بازنگری کند.** شاخه یک fork در مخزنی است که نصب نمی‌تواند در آن بنویسد. بازبینی‌اش را همچنان انجام می‌دهد — به‌جایش بازبینی بخواهید.
- **هرگز عنوان، توضیح یا شاخه مقصد درخواست ادغام را تغییر نمی‌دهد.** فقط کد.

## چه هزینه‌ای دارد و چگونه محدودش کنید

هر فرمانی که کاری را شروع می‌کند یک اجرای کامل عامل است — یک کلون، تا ۴۰ فراخوان LLM و ۱۰۰٬۰۰۰ توکن خروجی، به‌علاوه فرمان‌های ساخت و آزمون مخزنتان اگر پیکربندی‌شان کرده باشید.

دو محدودیت اعمال می‌شوند، و هر دو همان‌هایی‌اند که از پیش بر [وظیفه‌های رفع با هوش مصنوعی](/docs/ai/ai-agent) حاکم‌اند:

- **محدودیت روزانه اجرای رفع پروژه** (**Project Settings → AI**، به‌طور پیش‌فرض ۲۵ در روز). فرمان‌های GitHub این بودجه را با باقی اجراهای رفع پروژه شما شریک‌اند.
- **سقف درخواست‌های ادغام باز هر مخزن** (**Code Repositories → مخزن موردنظر → Settings**، به‌طور پیش‌فرض ۵). بازبینی‌ها و بازنگری‌ها معاف‌اند: هیچ‌کدام درخواست ادغام تازه‌ای به صف بازبینی شما نمی‌افزایند.

روی هر issue یا درخواست ادغام، در هر لحظه فقط یک اجرا از هر نوع زنده است. دو بار خواستن به شما می‌گوید که از پیش مشغول است؛ خواستن بازبینی در حالی که بازنگری‌ای در جریان است هر دو را شروع می‌کند، چون درخواست‌های متفاوتی‌اند.

اگر اجرایی نتواند شروع شود، برنامه دلیلش را در همان گفت‌وگو می‌گوید — هرگز خاموش شکست نمی‌خورد.

## خاموش کردنش

به ازای هر مخزن: **Code Repositories → مخزن موردنظر → Settings → Respond to GitHub Commands**. با خاموش بودنش، برنامه در آن مخزن نام‌بردن‌ها، واگذاری‌ها و برچسب تریگر را نادیده می‌گیرد و به هر کسی که بخواهد می‌گوید کلیدش کجاست.

همان صفحه **GitHub Trigger Label** را هم دارد، اگر چیزی جز `oneuptime` بخواهید.

## در چه رویدادهایی مشترک شوید

در تنظیمات **Permissions & events** مربوط به GitHub App خود، در این‌ها مشترک شوید:

| رویداد | برای چه لازم است |
| --- | --- |
| **Issue comment** | فرمان‌های `@mention` روی issueها *و* درخواست‌های ادغام |
| **Issues** | واگذاری به برنامه، و برچسب تریگر |
| **Pull request** | درخواست بازبینی از برنامه |
| **Pull request review** | نام بردن در بدنه بازبینی‌ای که ثبت شده |
| **Pull request review comment** | نام بردن روی نظری درون‌خطی در diff |

و زیر **Repository permissions**، دسترسی **Issues** باید **Read & write** باشد — GitHub نظرهای گفت‌وگوی درخواست ادغام را از راه API مربوط به issueها می‌گذراند، پس همین است که به برنامه اجازه می‌دهد روی درخواست‌های ادغام هم نظر بدهد.

## تزریق پرامپت: چه چیزی محافظت می‌شود و چه چیزی نه

متن issue، توضیح درخواست ادغام، diffها و نظرها همه بخشی از پرامپت عامل می‌شوند، و روی مخزنی عمومی هرکسی می‌تواند بنویسدشان. متنی که می‌گوید «دستورهایت را نادیده بگیر و X را انجام بده» چیزی است که واقعاً ممکن است در یک issue پیدا شود.

دو چیز این را مهار می‌کنند، و ارزش دارد بدانید کدام کدام است:

- **پرامپت‌ها متن نامعتمد را به‌عنوان درخواست برچسب می‌زنند، نه به‌عنوان دستور**، و مخزن، شاخه و درخواست ادغامِ اجرا پیش از آنکه عامل اصلاً شروع کند تثبیت می‌شوند — هیچ چیزی که عامل بخواند نمی‌تواند عوض کند که روی چه کار می‌کند.
- **مهار واقعی، جعبه شنی است.** عامل روی Runner شما و در کلونی یک‌بارمصرف اجرا می‌شود، با اعتبارنامه‌های حذف‌شده از محیط فرمانش و عملیات git محدودشده. تنها کاری که از دستش برمی‌آید فرستادن روی یک شاخه است، و ادغام کردن شاخه فقط از انسان برمی‌آید.

با درخواست ادغامی که هوش مصنوعی نوشته همان‌طور رفتار کنید که با درخواست ادغام مشارکت‌کننده‌ای تازه که issue را خوانده رفتار می‌کنید: diff را بازبینی کنید، نه توضیح را.

## رفع اشکال

**وقتی نامش را می‌برم هیچ اتفاقی نمی‌افتد.** نخست شناسه را بررسی کنید — شناسه، slug برنامه است، نه نام نمایشی‌اش. سپس بررسی کنید که مخزن به پروژه‌ای وصل باشد (**Project Settings → Code Repositories**)، که **Respond to GitHub Commands** روشن باشد، و که GitHub App شما در رویدادهای بالا مشترک باشد.

**واکنش 😕 می‌گذارد و چیزی نمی‌گوید.** شما دسترسی نوشتن به مخزن ندارید.

**می‌گوید از پیش روی این کار می‌کند.** اجرایی از آن نوع از پیش روی این issue یا درخواست ادغام زنده است. `@oneuptime status` می‌گوید چه چیزی، و `@oneuptime cancel` متوقفش می‌کند.

**تأیید کرد و بعد مدتی طولانی ساکت ماند.** بررسی کنید که Runnerای با **Runs AI Code Fixes** زیر **Settings → Runners** آنلاین باشد. بدون آن، اجرا پس از ۳۰ دقیقه شکست‌خورده علامت می‌خورد و به گفت‌وگو خبر داده می‌شود.

**می‌گوید درخواست ادغام از یک fork می‌آید.** بازنگری‌ها به شاخه‌ای در همین مخزن نیاز دارند. به‌جایش بازبینی بخواهید، یا شاخه را همین‌جا بفرستید.
