# وظیفه‌های رفع با هوش مصنوعی — رفع استثناها با یک درخواست ادغام

هوش مصنوعی OneUptime استثنایی برطرف‌نشده را به درخواست ادغامی قابل بازبینی تبدیل می‌کند. روی هر استثنای برطرف‌نشده، **Fix with AI** را بزنید: یک [Runner](/docs/runbooks/agents) وظیفه را برمی‌دارد، استثنا را می‌خواند (نوع، پیام خطا و ردیابی پشته)، مخزن GitHub پیوندخورده به سرویسی را که آن را پرتاب کرده کلون می‌کند، روی شاخه‌ای تازه رفعی می‌نویسد و درخواست ادغامی باز می‌کند.

هر درخواست ادغام را انسانی بازبینی و ادغام می‌کند. Runner هرگز تغییرات خودش را ادغام نمی‌کند — می‌تواند شاخه بفرستد و PR باز کند، نه بیشتر.

> **این را از خودِ GitHub هم می‌توانید شروع کنید.** روی یک issue یا درخواست ادغام از GitHub App مربوط به OneUptime نام ببرید و همان‌جا پیاده‌سازی، بازنگری یا بازبینی می‌کند — [کار با OneUptime از درون GitHub](/docs/ai/github-app) را ببینید. همان عامل، همان Runner و همان بودجه‌هاست؛ فقط تریگر فرق می‌کند.

## یک اجرای رفع چگونه کار می‌کند

1. روی استثنایی برطرف‌نشده **Fix with AI** را می‌زنید.
2. وظیفه‌ای رفع ساخته می‌شود و Runner در دسترسی با قابلیت **Runs AI Code Fixes** برش می‌دارد.
3. ‏Runner جزئیات استثنا را می‌گیرد — نوع استثنا، پیام خطا و ردیابی پشته.
4. مخزن پیوندخورده را در فضای کاری زودگذری کلون می‌کند و شاخه‌ای می‌سازد (به نام `oneuptime-fix-exception-` که پس از آن نویسه‌های نخست شناسه اجرا می‌آید).
5. عاملی کدنویس، که ارائه‌دهنده LLM پروژه شما نیرویش می‌دهد، پایگاه کد را تحلیل می‌کند و رفع را می‌نویسد. فراخوان‌های LLM را کارساز OneUptime اجرا می‌کند — کانتینر Runner هرگز کلید API ارائه‌دهنده شما را نگه نمی‌دارد — و هر فراخوان اندازه‌گیری و در گزارش‌های هوش مصنوعی ثبت می‌شود.
6. اگر مخزن فرمان‌های تأیید پیکربندی‌شده داشته باشد، Runner پیش از کامیت شدن هر چیزی رفع را می‌سازد و می‌آزماید (بخش **تأیید پیش از درخواست ادغام** در پایین را ببینید).
7. ‏Runner کامیت می‌کند، شاخه را می‌فرستد، درخواست ادغامی باز می‌کند و فضای کاری را حذف می‌کند.

صفحه استثنا وضعیت زنده وظیفه را نشان می‌دهد. صفحه جزئیات وظیفه (زیر **AI** > **Tasks**) گزارش کامل اجرا را نگه می‌دارد — از جمله خطی برای هر فایلی که Runner خوانده یا نوشته و هر فرمانی که اجرا کرده — و به هر درخواست ادغامی که وظیفه باز کرده پیوند می‌دهد.

هر اجرای رفع با بودجه‌های حلقه‌ای که کارساز اعمال می‌کند سقف می‌خورد: حداکثر **۴۰ فراخوان LLM** و **۱۰۰٬۰۰۰ توکن خروجی** در هر اجرا. اجرایی که به بودجه‌اش بخورد به‌جای حلقه زدن بی‌پایان، با خلاصه‌ای از کار انجام‌شده تا آنجا تمام می‌شود. اجراهای رفع، اگر بودجه روزانه توکن هوش مصنوعی خودگردان پروژه تنظیم شده باشد، به آن هم می‌شمارند.

## تأیید پیش از درخواست ادغام

یک مخزن کد می‌تواند تا سه فرمان تأیید حمل کند — **Setup Command**، **Build Command** و **Test Command** (برای نمونه `npm ci`، `npm run build`، `npm test`) — در صفحه **Settings** آن زیر **Code Repositories**. وقتی هرکدام پیکربندی شده باشند، هر اجرای رفع پیش از باز شدن درخواست ادغام تغییراتش را تأیید می‌کند:

1. پس از پایان کار عامل کدنویس، فرمان‌های پیکربندی‌شده به ترتیب (setup → build → test) در ریشه مخزن، روی Runner و درون فضای کاری کلون‌شده اجرا می‌شوند. هر فرمان تا ۱۵ دقیقه زمان می‌گیرد و با `CI=true` اجرا می‌شود تا چیزی منتظر اعلانی تعاملی نماند؛ نخستین شکست، گذر را متوقف می‌کند.
2. هنگام شکست، دنباله خروجی فرمان شکست‌خورده به‌عنوان وظیفه‌ای ترمیمی به همان عامل کدنویس بازداده می‌شود — با دستور رفع تغییرات خودش، نه سست کردن یا رد کردن آزمون‌ها — و فرمان‌ها دوباره اجرا می‌شوند. حداکثر **۲** تلاش ترمیم انجام می‌شود؛ گذرهای ترمیم بودجه LLM اجرا را به اشتراک می‌گذارند و ویرایش‌هایشان در همان کامیت رفع می‌نشیند.
3. نتیجه — **Passed**، **Failed** یا **Skipped** (بدون فرمان پیکربندی‌شده) — در بخش **Verification** بدنه درخواست ادغام بیان می‌شود و روی رکورد درخواست ادغام وظیفه ثبت می‌شود.

رفعی که همچنان تأیید نشود دور انداخته نمی‌شود: درخواست ادغام به‌هرحال باز می‌شود، با بخشی به‌روشنی علامت‌خورده به نام **Verification failed** در بدنه‌اش که فرمان شکست‌خورده و دنباله خروجی‌اش را حمل می‌کند — کار حفظ می‌شود و بازبین انسانی تصمیم می‌گیرد. مخزنی بدون فرمان پیکربندی‌شده صادقانه **Skipped** گزارش می‌شود، نه اینکه ساختی سبز را القا کند.

فرمان‌ها پیکربندی مخزنی نوشته اپراتورند که روی Runner خودتان اجرا می‌شوند — همان مدل اعتمادی که گام‌های Bash در رانبوک دارند. هوش مصنوعی هرگز آن‌ها را نمی‌نویسد یا تغییر نمی‌دهد.

## پیش‌نیازها

پیش از اجرای وظیفه رفع، سه چیز باید سر جایشان باشند. صفحه استثنا هر سه را از پیش بررسی می‌کند و چک‌لیست آمادگی نشان می‌دهد، تا پیش از ساخته شدن وظیفه دقیقاً ببینید چه چیزی کم است.

### ۱. یک ارائه‌دهنده LLM

- **‏OneUptime Cloud**: بدون پیکربندی — اگر پروژه شما ارائه‌دهنده LLM خودش را نداشته باشد، وظیفه‌های عامل از ارائه‌دهنده سراسری مشترک استفاده می‌کنند و مصرف مانند هر قابلیت هوش مصنوعی دیگری به‌صورت توکن اندازه‌گیری‌شده صورت‌حساب می‌شود. برای استفاده از کلیدهای خودتان، ارائه‌دهنده‌ای زیر **Project Settings** > **AI** > **LLM Providers** پیکربندی کنید — ارائه‌دهنده متعلق به پروژه همیشه اولویت دارد.
- **خودمیزبان**: ارائه‌دهنده متعلق به پروژه به همین شکل کار می‌کند، اما مسیر بدون پیکربندی این است که متغیرهای محیطی `GLOBAL_LLM_PROVIDER_*` را یک بار روی کارساز OneUptime خود تنظیم کنید (در `config.env` برای Docker Compose، یا از راه مقادیر Helm) — ارائه‌دهنده‌ای سراسری هنگام راه‌اندازی خودکار ثبت می‌شود و قابلیت‌های هوش مصنوعی هر پروژه، از جمله وظیفه‌های عامل، از آن استفاده می‌کنند. برای Ollama محلی:

```bash
GLOBAL_LLM_PROVIDER_TYPE=Ollama
GLOBAL_LLM_PROVIDER_BASE_URL=http://your-ollama-host:11434
GLOBAL_LLM_PROVIDER_MODEL_NAME=llama3
# No GLOBAL_LLM_PROVIDER_API_KEY needed — Ollama is keyless.
```

هر ارائه‌دهنده پشتیبانی‌شده‌ای کار می‌کند — برای همه ارائه‌دهنده‌ها و فهرست کامل متغیرهای محیطی [ارائه‌دهندگان LLM](/docs/ai/llm-provider) را ببینید.

### ۲. اتصال GitHub از راه GitHub App

‏GitHub را زیر **Code Repositories** با **Connect with GitHub App** وصل کنید — نصب برنامه همه مخزن‌هایش را خودکار وارد می‌کند و همگام نگهشان می‌دارد. GitHub App تنها اتصالی است که Runner می‌تواند از راهش بفرستد (GitLab در نقشه راه است).

لازم **نیست** مخزن‌ها را به سرویس‌ها نگاشت کنید: OneUptime هنگام رفع، مخزن درست را با تطبیق مسیرهای فایل در ردیابی پشته استثنا با مخزن‌های وصل‌شده شما تفکیک می‌کند (با بازگشت به تطبیق نام مخزن و، وقتی پروژه دقیقاً یک مخزن دارد، به همان مخزن). چک‌لیست آمادگی روی صفحه استثنا نشان می‌دهد کدام مخزن تفکیک شده است.

### ۳. یک Runner با رفع کد هوش مصنوعی فعال

- **‏OneUptime Cloud**: ناوگان مشترک Runner خودکار در دسترس است — چیزی برای اجرا نیست.
- **خودمیزبان**: کانتینر Runner به‌طور پیش‌فرض اجرا می‌شود — نصب Docker Compose سرویس `runner` را دربر دارد و نمودار Helm مستقرش می‌کند (`runner.enabled`، پیش‌فرض `true`). خودش را به‌طور خودکار نزد نمونه شما ثبت می‌کند (بدون اعتبارنامه‌ای برای کپی) و از همان ابتدا روی رفع کد هوش مصنوعی کار می‌کند. وقتی هیچ ارائه‌دهنده LLMای پیکربندی نشده باشد Runner ارزان بیکار می‌ماند؛ وظیفه‌ها تا وقتی یکی برپا نشود زود و با راهنمایی شکست می‌خورند.

برای اجرای Runner اضافه‌ای جای دیگر (برای نمونه روی ماشینی نزدیک‌تر به مخزن‌هایتان):

1. زیر **Settings** > **Runners** یک Runner بسازید و در سطرش از **Show setup instructions** برای فرمان نصب از پیش پرشده استفاده کنید. کلید یک بار نشان داده می‌شود — امن ذخیره‌اش کنید. فرمان چنین است:

```bash
docker run --name oneuptime-runner --restart unless-stopped \
  -e ONEUPTIME_RUNNER_ID=<runner-id> \
  -e ONEUPTIME_RUNNER_KEY=<runner-key> \
  -e ONEUPTIME_URL=<your-oneuptime-url> \
  -d oneuptime/runner:release
```

2. گزینه **Runs AI Code Fixes** را روی Runner فعال کنید — این قابلیت به‌طور پیش‌فرض خاموش است و Runner در ضربان قلب بعدی‌اش (حدود یک دقیقه) تغییر را می‌پذیرد؛ به بازراه‌اندازی نیازی نیست.

هر راهی برای اجرای کانتینر کار می‌کند (Docker Compose، ‏Kubernetes و مانند آن) تا وقتی این متغیرهای محیطی تنظیم شده باشند و کانتینر بتواند روی HTTPS به نمونه OneUptime شما برسد:

| متغیر | توضیح |
| ---------------------- | -------------------------------------------------------------- |
| `ONEUPTIME_RUNNER_ID` | شناسه Runner از داشبورد |
| `ONEUPTIME_RUNNER_KEY` | کلید Runner که هنگام ساختش نشان داده شد |
| `ONEUPTIME_URL` | نشانی نمونه OneUptime شما (`https://oneuptime.com` روی Cloud) |

‏Runner ظرف یکی دو دقیقه در صفحه **Settings** > **Runners** به‌صورت متصل نشان داده می‌شود. اگر چنین نشد، گزارش‌های کانتینر (`docker logs oneuptime-runner`) را برای خطاهای اعتبارنامه یا شبکه بررسی کنید.

> پیش از OneUptime 12، رفع‌های کد هوش مصنوعی روی مؤلفه‌ای جدا به نام **AI Agent** اجرا می‌شدند (ایمیج `oneuptime/ai-agent` با متغیرهای `AI_AGENT_*`). آن مؤلفه در Runner ادغام شد — اگر هنوز یکی اجرا می‌کنید، برای نحوه جایگزینی‌اش [راهنمای ارتقای v11 → v12](/docs/installation/upgrading) را ببینید.

## وقتی رفعی شکست می‌خورد

- **اجرا خطا می‌دهد** (رفع اعمال نشد، مخزن دست‌یافتنی نبود، فراخوان LLM شکست خورد): خطای وظیفه با دلیلش روی صفحه استثنا نشان داده می‌شود و می‌توانید از همان‌جا دوباره تلاش کنید. گزارش کامل اجرا در صفحه جزئیات وظیفه است.
- **‏Runner در میانه اجرا فرو می‌ریزد**: اجرایی که ضربان قلبش بیش از حدود ده دقیقه کهنه شود با خطا شکست‌خورده علامت می‌خورد. هرگز خودکار دوباره در صف نمی‌رود — Runner ممکن است از پیش شاخه‌ای رفع ناقص فرستاده باشد — اما می‌توانید از صفحه استثنا دوباره تلاش کنید.
- **هیچ Runnerای آنلاین نیست**: وظیفه‌ای در صف که بیش از ۳۰ دقیقه منتظر بماند در حالی که هیچ Runnerای با قابلیت **Runs AI Code Fixes** متصل نیست، به‌طور خودکار با راهنمایی بررسی Runner شکست‌خورده علامت می‌خورد — برای همیشه «در جریان» نشان داده نمی‌شود. (اگر Runnerای آنلاین اما مشغول باشد، وظیفه‌های در صف صرفاً نوبتشان را منتظر می‌مانند.)

## رفع خودکار کد از دل بررسی‌ها

وقتی یک [بررسی هوش مصنوعی](/docs/ai/ai-sre) تحلیل ریشه علتی روی حادثه یا هشداری منتشر می‌کند و دسته‌بندی محافظه‌کارانه‌اش تغییری در کد مخزن را توصیه می‌کند، پنل بررسی گزینه **Open Fix PR from this analysis** را ارائه می‌دهد — وظیفه رفعی که تمام زمینه‌اش تحلیل منتشرشده است. وقتی راه‌حل عملیاتی، صرفاً زیرساختی، بیرونی، ردی مورد انتظار، خطای کاربر یا بی‌نتیجه باشد، این کنش پنهان می‌شود. پروژه‌هایی که می‌خواهند رفع‌های واجد شرایط بدون کلیک انجام شوند می‌توانند با **Enable Automatic Code Fixes** ثبت‌نام کنند، که **به‌طور پیش‌فرض خاموش و مستقل پیکربندی می‌شود**، زیر **Incidents > AI > Investigation** یا **Alerts > AI > Investigation**.

وقتی فعال باشد، بررسی‌ای که با تحلیل ریشه علتی **مطمئن، مستند و قابل رفع در کد** پایان می‌یابد به‌طور خودکار همان وظیفه رفعی را در صف می‌گذارد که دکمه می‌سازد. دروازه، دسته‌بندی‌ای محدود و تأییدشده توسط کارساز است، نه عبارتی باقاعده روی نثر تحلیل: فقط رأی مثبت رفع کد درخواست ادغام باز می‌کند. نبود شواهد، راه‌حل‌های غیرکدی و دسته‌بندی‌های شکست‌خورده همه به سمت هیچ‌کاری‌نکردن شکست می‌خورند.

باقی همه‌چیز با دکمه دستی یکی است: درخواست ادغام آماده بازبینی باز می‌شود، از تحلیل منتشرشده تولید می‌شود، به مخزنی وصل‌شده با GitHub App و Runnerای با **Runs AI Code Fixes** فعال نیاز دارد، به **Daily AI Fix Task Limit** آن نوع سیگنال (پیش‌فرض ۲۵ در هر روز UTC) و سقف PRهای باز هر مخزن می‌شمارد، و هر تریگر نخست بررسی می‌کند آیا برای همان حادثه یا هشدار وظیفه رفعی از پیش در صف یا در حال اجرا هست — پس تریگری خودکار و کلیکی انسانی معمولاً به‌جای دو درخواست ادغام در یک وظیفه فرو می‌ریزند. (بررسی خواندنی پیش از نوشتن است، نه قفل، پس دو تریگری که دقیقاً در یک لحظه شلیک کنند هنوز می‌توانند هر دو رد شوند.) اجرا نوشته سامانه است (بدون انتساب به کاربر)، و هیچ‌چیز خودکار ادغام نمی‌شود.

## حریم خصوصی

کلون مخزن در فضای کاری زودگذری درون کانتینر Runner زندگی می‌کند و هنگام پایان اجرا، چه موفق و چه شکست‌خورده، حذف می‌شود. کانتینر Runner هرگز کلید API ارائه‌دهنده LLM شما را نگه نمی‌دارد — فراخوان‌های LLM را کارساز OneUptime به نمایندگی از Runner اجرا می‌کند. OneUptime مخزن شما را نگه نمی‌دارد و روی کدتان آموزش نمی‌بیند؛ گزارش اجرای وظیفه پیش‌نمایش کوتاهی از خروجی هر گام (چند صد نویسه) نگه می‌دارد تا بتوانید کار Runner را حسابرسی کنید، و آن پیش‌نمایش‌ها می‌توانند قطعه‌های کد را دربر بگیرند. Runnerای خودمیزبان با ارائه‌دهنده LLM خودتان (از جمله Ollama محلی) اجرا کنید و کدتان هرگز زیرساختتان را ترک نمی‌کند.

## در نقشه راه

برنامه‌ریزی‌شده، اما **امروز در دسترس نیست**:

- **پشتیبانی از GitLab** — اتصال‌های مخزن در حال حاضر فقط GitHub App هستند.
- **زمینه غنی‌تر تله‌متری** — تغذیه ردیابی‌ها، گزارش‌ها و سنجه‌های مرتبط پیرامون استثنا به رفع، فراتر از ردیابی پشته.
