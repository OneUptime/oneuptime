# 声明事件

声明一个事件，就是 OneUptime 开始记分的那一刻。一条记录被创建，一个编号被打在上面，值班策略被触发——而且，除非你另有设置，你的状态页订阅者也会听到这个消息。事件生命周期里的其他一切，都挂在这第一次写入之上。

有四种方式可以让一个事件进入 OneUptime，它们最终都落在同一个地方：`Incident` 表里的一行，带有一个严重性、一个当前状态和一份受影响资源的列表。区别只在于是谁填的这些字段——是你在凌晨三点，是一个已保存的模板，是一个监视器的条件，还是你自己的代码在调用 API。

本页会逐个字段走完这四种方式，然后介绍服务器会替你填上什么、以及事件一旦存在会触发什么。

## 事件被声明的四种方式

| 如果你想要……                                       | 选择                                                                         |
| ---------------------------------------------------- | ----------------------------------------------------------------------------- |
| 手动打开一个事件，填写所有内容                       | **声明事件** 向导                                                             |
| 打开一种会反复出现的事件类型，字段已预先填好         | **从模板创建**                                                               |
| 在监视器检查失败时自动打开一个                       | 一条监视器条件过滤规则，启用 **When filters match, declare an incident.**    |
| 从你自己的代码、脚本或其他工具打开一个               | `POST /api/incident`                                                          |

这四种方式写入的是同一个模型，所以由探测器打开的事件，看起来和响应人员手动打开的事件一模一样——除了服务器在自动创建的事件上设置的几个记账用字段之外。

## 手动声明一个事件

打开 **事件 → 所有事件**，点击 **事件** 列表右上角的 **声明事件**。这会带你进入一张名为 **声明新事件** 的卡片，表单分成五个步骤：**事件详情**、**受影响的资源**、**事件角色**、**值班** 和 **更多**。末尾的提交按钮同样写着 **声明事件**。

只有第一步含有必填字段。如果你赶时间，填完 **事件详情** 就提交——之后你可以从事件自己的页面附加资源、分配角色、添加值班策略。

### 第一步——事件详情

- **标题**——必填。这是每个人都会在列表、Slack 以及（如果事件可见）你的状态页上看到的一行摘要。占位符：`Incident Title`。
- **描述**——可选，用 Markdown 编写。这是渲染在状态页上的字段，所以要写给客户看，而不是写给团队看。之后你可以从事件侧边菜单中的 **描述** 编辑它。
- **声明时间**——表单中必填，默认是现在。事件上的每一段时长都是从这个时间戳开始计算的，所以如果你记录的是一个更早开始的事情，就把它往前调。
- **事件严重性**——必填。为你的项目配置的严重性之一；新项目会预置 **Critical Incident**、**Major Incident** 和 **Minor Incident**。
- **事件状态**——可选。不管它，事件就会落入标记为 `isCreatedState` 的那个状态，新项目里预置的是 **Identified**。只有在你记录一个已经过了这个阶段的事件时，才需要设置它。

**如果状态下拉框给你添麻烦。** 如果你的项目里没有任何状态带有 `isCreatedState` 标志，创建调用就会失败，并提示你去设置里添加一个创建状态。这通常只会发生在状态被大幅修改过的项目上——见 [事件状态与严重级别](/docs/incidents/states-and-severities)。

### 第二步——受影响的资源

- **受影响的资源**——一个单一的搜索框，可以附加监视器、主机、Kubernetes 集群、Docker 主机、Podman 主机和服务。在底层，这些是事件上各自独立的关联关系（`monitors`、`hosts`、`kubernetesClusters`、`dockerHosts`、`podmanHosts`、`services` 等），但表单把它们合并成了一个选择器。
- **将监视器状态更改为**——可选。选择一个监视器状态，应用到附加到这个事件上的每一个监视器，这样声明事件和把监视器标记为降级就变成了一个动作，而不是两个。

**即使感觉多余，也要附加监视器。** 事件和状态页之间的关联，走的是事件的监视器：当事件的某个资源同时是状态页的资源之一时，状态页才会显示这个事件。如果事件没有附加任何监视器，给订阅者的状态变更通知会被直接跳过。见 [状态页资源与分组](/docs/status-pages/resources-and-groups)。

### 第三步——事件角色

- **分配事件角色**——把团队成员分配到你项目定义的角色上。有些角色可以接受多个用户。

角色本身是在 **事件 → 设置 → 事件角色** 中配置的，你在那里定义响应过程中可以分配的角色——Incident Commander、Responder，以及你的流程需要的其他任何角色。如果你跳过这一步，在第一次状态变更时，只要还没人担任 Incident Commander，系统就会自动分配一个。

### 第四步——值班

- **值班策略**——一个多选框，选择这个事件创建时要执行的值班策略。它对应事件上的 `onCallDutyPolicies`。

这是唯一一个可以把值班策略直接附加到事件上的地方。严重性本身不携带值班策略——严重性是一个标签，它只在值班规则内部作为一个 *匹配条件* 来影响呼叫。在 **事件 → 规则 → 值班规则** 配置的规则，会在你这里选的基础上叠加它们自己的策略；最终运行的集合是两者去重后的并集。

### 第五步——更多

- **标签**——可选，属于高级功能：只有拥有这些标签访问权限的团队成员才能访问该事件。
- **通知状态页订阅者**——复选框，默认开启。控制是否通过邮件通知订阅者该事件已创建（`shouldStatusPageSubscribersBeNotifiedOnIncidentCreated`）。如果是你仍想记录但不想让外部知道的内部噪音，就把它关掉。
- **私密事件**——复选框，默认关闭（`isPrivate`）。私密事件只对其所有者用户、所有者团队的成员、项目管理员和项目所有者可见——并且无论其他设置如何，它都会对所有状态页隐藏。事件列表会用红色的 **Private** 徽标标出这些事件。

**Should be visible on status page?** 标志（`isVisibleOnStatusPage`）不在向导里；它默认是开启的。之后可以从事件侧边菜单的 **设置** 中修改，那里它被标记为 **在状态页面上可见**。

## 从模板声明

如果你一直在声明形状相同的事件——同样的标题模式、同样的严重性、同样的值班策略——那就把它保存成一个模板，一次就好。

点击 **从模板创建**（在 **声明事件** 旁边的描边按钮），会打开一个 **从模板创建事件** 弹窗，里面有一个 **选择事件模板** 下拉框。选一个模板，创建表单就会带着预填内容打开；提交之前你仍然可以修改任何内容。如果你的项目还没有模板，你会看到一个 **No Incident Templates** 弹窗，里面有一个 **Create Template** 按钮，会带你去 **事件 → 设置 → 事件模板**。

模板是用它们自己的六步向导构建的——**Template Info**、**事件详情**、**受影响的资源**、**值班**、**Owners**、**标签**——包含以下字段：

| 字段                          | 用途                                                     |
| ----------------------------- | -------------------------------------------------------- |
| **Template Name**             | 模板在选择器里的识别方式。                                |
| **Template Description**     | 给未来的自己留个提醒：什么时候该用这个模板。               |
| **标题**                      | 预填到事件上的标题。                                       |
| **描述**                      | 预填到事件上的 Markdown 描述。                             |
| **事件严重性**                | 预填到事件上的严重性。                                     |
| **初始事件状态**              | 从这个模板创建的事件所处的初始状态。                        |
| **受影响的资源**              | 要附加的监视器、主机、集群和服务。                          |
| **将监视器状态更改为**        | 应用到所附加监视器上的监视器状态。                          |
| **值班策略**                  | 事件创建时要执行的策略。                                    |
| **所有者 - 团队**             | 拥有由这个模板创建的事件的团队。                             |
| **所有者 - 用户**             | 拥有由这个模板创建的事件的用户。                             |
| **标签**                      | 应用到事件上的标签。                                        |

几条速记规则：

- 模板不能在模板列表里直接编辑——你先创建一个，然后打开它去修改。
- 模板只会填充你留空的字段。在创建页面上，模板是作为预填内容应用的，你可以覆盖它；在 API 上，服务器只会在请求把某个字段留为 `undefined` 时，才用模板去填充它。调用方提供的内容永远优先。

## 从监视器条件自动声明

大多数事件应该不需要人手动打字来创建。在监视器的条件编辑器里，打开 **When filters match, declare an incident.** 开关，就会出现一个 **Create Incident** 区块，带有一个 **Add Incident** 按钮——一条条件过滤规则可以声明不止一个事件。

每一条包含：

- **事件标题**——支持模板变量；占位符建议类似 `{{monitorName}} is down` 这样的写法。
- **严重程度**——必填。
- **事件描述**——同样支持模板变量。
- **值班 → 值班策略**——这个事件创建时要执行的策略。
- **事件角色**——预先把团队成员分配到角色。
- **所有权和标签 → 所有者团队**、**所有者用户**、**标签**。
- **高级选项 → 自动解决事件**（当条件不再匹配时自动解决事件）、**在状态页上显示事件**、**私密事件** 和 **补救备注**。

标题、描述和补救备注中可以使用的完整 `{{variable}}` 占位符列表，见 [事件与告警模板](/docs/monitor/incident-alert-templating)。

用这种方式创建的事件会被服务器打上标记：`isCreatedAutomatically` 会被设置，`createdCriteriaId` 记录是哪条条件过滤规则触发的，`createdByProbe` 记录是哪个探测器发现的。除此之外，它们的行为和手动声明的事件完全一样。

## 通过 API 声明

事件模型暴露了一个标准的 CRUD 端点，所以 `POST /api/incident` 就能创建一个。用在 **项目设置 → API 密钥** 生成的 API 密钥进行认证，放在 `apikey` 请求头里——这个密钥本身就能识别项目，所以你不需要另外传项目 ID。

```bash
curl -X POST https://oneuptime.com/api/incident \
  -H "apikey: $ONEUPTIME_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "data": {
      "title": "Checkout latency above SLO",
      "description": "Investigating elevated p99 latency on the checkout service.",
      "incidentSeverityId": "<incident-severity-id>"
    }
  }'
```

请求体上一些有用的字段：

- `title`——唯一一个你真正必须提供的字段。
- `declaredAt`——这里是可选的，即使表单要求必填。省略它，服务器就会用当前时间。
- `incidentSeverityId` 和 `currentIncidentStateId`——服务器会检查两者是否都属于和 API 密钥相同的项目，不属于就拒绝请求。**将监视器状态更改为** 背后的监视器状态也遵循同样的检查。
- `createdIncidentTemplateId`——应用一个已保存的模板。你没有提供的字段会由模板填充；你发送的字段则原样保留。

相关端点还有 `/api/incident-state`、`/api/incident-severity` 和 `/api/incident-state-timeline`。自动生成的 [API 参考](/reference) 里有每一个端点确切的请求和响应结构，包括像监视器这样的关联字段是如何表示的。

## 事件编号与前缀

每个事件都会从一个按项目计数的计数器那里拿到一个顺序编号，由服务器在创建时分配。有两列保存它：`incidentNumber`（原始整数）和 `incidentNumberWithPrefix`（你实际看到的那个）。没有配置前缀时，显示值是 `#42`。

要修改这一点，去 **事件 → 设置 → 更多设置**。**号码前缀** 卡片上有一个 **事件编号前缀** 字段（最多 20 个字符，占位符 `INC-`）——设置它，同一个事件就会渲染成 `INC-42`。留空则保持默认的 `#`。这张卡片上还有 **事件片段编号前缀**，用于片段编号。

编号会出现在事件列表的第一列，链接到该事件，并在事件的 **概览** 上显示为 **事件编号**。

## 一个事件被声明的那一刻发生了什么

创建调用做的不只是写一行记录。按顺序：

1. **服务器把空白填上。** `declaredAt` 默认为当前时间，当前状态默认为项目的 `isCreatedState` 状态，事件编号和带前缀的编号从项目计数器分配。
2. **应用模板**，如果提供了 `createdIncidentTemplateId`——只填充调用方留空的字段。
3. **隐私规则运行**，在有规则匹配时把事件标记为私密。这是第一个运行的规则引擎，所以之后的一切都能看到正确的隐私设置。
4. **所有者规则运行**，添加匹配规则指定的所有者用户和团队。
5. **标签规则运行**，添加匹配该事件的标签。
6. **值班规则运行。** **事件 → 规则 → 值班规则** 里每一条条件匹配的已启用规则，都会把自己的策略加到事件上。没有优先级顺序，也不会短路——所有匹配的规则都会触发，策略会去重。
7. **Runbook 规则运行**，附加并启动匹配的 Runbook。见 [Runbook 概览](/docs/runbooks/index)。
8. **值班策略执行。** 事件上的每一条策略——在向导里选的、从模板继承的，或由规则添加的——都会以事件类型 `IncidentCreated` 并行执行。一条策略失败不会阻止其他策略。
9. **订阅者被排队通知**，如果 **通知状态页订阅者** 是开启的，并且事件在状态页上可见。投递由后台任务处理，不会和你的请求同步完成。
10. **工作流触发。** **On Create Incident** 触发器会启动基于它构建的任何工作流。见 [工作流概览](/docs/workflows/index)。

从这一刻起，事件就是活动的：它会计入事件侧边菜单里的 **活动事件** 徽章（任何未标记 `isResolvedState` 的状态都算活动的），它会出现在带有它某个监视器的状态页上，它的 **状态时间线** 也会开始记录。
