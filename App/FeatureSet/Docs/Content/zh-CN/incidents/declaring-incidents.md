# 声明事件

声明事件，是 OneUptime 开始计时记账的那一刻。一条记录被创建、一个编号被打上、值班策略被触发，并且——除非你另有指示——你的状态页订阅者会收到消息。事件生命周期里的其他一切，都挂在这第一次写入之上。

事件进入 OneUptime 有四条途径，而它们最终都殊途同归：`Incident` 表里的一行，带着严重性、当前状态和一份受影响资源清单。区别只在于由谁来填这些字段——凌晨三点的你、一个已保存的模板、某个监视器的条件，或者你自己调用 API 的代码。

本页会逐字段走完这四条途径，然后讲清楚服务器替你填了什么，以及事件一旦存在会触发什么。

## 声明事件的四种方式

| 如果你想……                                     | 就选                                                                |
| ------------------------------------------------------------ | --------------------------------------------------------------------------- |
| 手动开一个事件，自己填完所有内容                | **声明事件** 向导                                                    |
| 开一类反复出现的事件，字段已经预填好             | **从模板创建**                                                       |
| 监视器检查失败时自动开一个                       | 带 **当过滤器匹配时，声明事件。** 的监视器条件过滤器                   |
| 从你自己的代码、脚本或其他工具开一个              | `POST /api/incident`                                                        |

这四条途径写入的是同一个模型，所以探针开出的事件和响应者手动开出的事件长得一模一样——只有几个记账用的列，服务器会在自动创建的事件上额外标记。

## 手动声明

打开 **事件 → 所有事件**，点击 **事件** 列表右上角的 **声明事件**。这会带你进入一张标题为 **声明新事件** 的卡片，表单被拆成五个步骤：**事件详情**、**受影响的资源**、**事件角色**、**值班** 和 **更多**。最后的提交按钮同样写着 **声明事件**。

只有第一步有必填字段。如果你很赶时间，填完 **事件详情** 直接提交——资源、角色和值班策略稍后都可以从事件自己的页面上补。

### 第 1 步 —— 事件详情

- **标题** —— 必填。所有人在列表里、在 Slack 里，以及（如果事件可见）在状态页上看到的那一行摘要。占位提示：`Incident Title`。
- **描述** —— 可选，用 Markdown 编写。这个字段会呈现在状态页上，所以请为客户而不是为团队来写。之后可以从事件侧边菜单中的 **描述** 修改它。
- **声明时间** —— 表单中必填，默认为当前时间。事件上所有的时长都以这个时间戳为起点，因此如果你在补记一件更早开始的事，请把它往前调。
- **事件严重性** —— 必填。取自项目已配置的严重性；新项目预置了 **Critical Incident**、**Major Incident** 和 **Minor Incident**。
- **事件状态** —— 可选。不动它，事件就会落入带 `isCreatedState` 标志的状态，新项目把它预置为 **Identified**。只有当你在补记一个早已越过该阶段的事件时，才需要设置它。

**如果状态下拉框让你犯难。** 如果你的项目里没有任何状态带 `isCreatedState` 标志，创建调用会失败，并提示你去设置里添加一个创建事件状态。这通常只发生在状态被大幅改动过的项目上——参见 [事件状态与严重级别](/docs/incidents/states-and-severities)。

### 第 2 步 —— 受影响的资源

- **受影响的资源** —— 一个搜索框，用来附加监视器、主机、Kubernetes 集群、Docker 主机、Podman 主机和服务。在底层，这些是事件上各自独立的关联（`monitors`、`hosts`、`kubernetesClusters`、`dockerHosts`、`podmanHosts`、`services` 等），但表单把它们合并成了一个选择器。
- **将监视器状态更改为** —— 可选。选择一个监视器状态，它会被应用到附加在本事件上的每一个监视器，这样"声明事件"和"把监视器标记为降级"就是一步而不是两步。

**即使觉得多余，也要附加监视器。** 事件与状态页之间的联系是通过事件的监视器建立的：当状态页的某个资源正是事件的监视器之一时，该状态页才会显示这个事件。如果事件没有附加任何监视器，发给订阅者的状态变更通知会被直接跳过。参见 [状态页资源与分组](/docs/status-pages/resources-and-groups)。

### 第 3 步 —— 事件角色

- **分配事件角色** —— 把团队成员分配到你项目定义的各个角色上。有些角色可以容纳多个用户。

角色本身在 **事件 → 设置 → 事件角色** 配置，你在那里定义响应期间可以分配的角色——事件指挥官、响应者，以及你的流程需要的任何其他角色。如果你跳过这一步，且当时还没有人担任事件指挥官，系统会在第一次状态变更时自动指派一位。

### 第 4 步 —— 值班

- **值班策略** —— 一个多选框，选择本事件创建时要执行的值班策略。它对应事件上的 `onCallDutyPolicies`。

这是唯一一处把值班策略直接附加到事件上的地方。严重性并不携带值班策略——严重性只是一个标签，它只有作为值班规则里的*匹配条件*时才会影响呼叫。在 **事件 → 规则 → 值班规则** 配置的规则会在你这里选的策略之上追加它们自己的策略；最终运行的是两者去重后的并集。

### 第 5 步 —— 更多

- **标签** —— 可选，属于高级功能：能访问这些标签的团队成员，才是能访问该事件的人。
- **通知状态页订阅者** —— 复选框，默认开启。控制订阅者是否会收到事件创建的邮件（`shouldStatusPageSubscribersBeNotifiedOnIncidentCreated`）。对于你想记录但不想惊动外界的噪音，把它关掉。
- **私密事件** —— 复选框，默认关闭（`isPrivate`）。私密事件只对它的所有者用户、所有者团队的成员、项目管理员和项目所有者可见——并且无论其他设置如何，它对所有状态页都是隐藏的。事件列表会给这类事件打上一个红色的 **Private** 标记。

**Should be visible on status page?** 标志（`isVisibleOnStatusPage`）不在向导里；它默认为 true。之后可以从事件侧边菜单的 **设置** 中修改，那里它的标签是 **在状态页面上可见**。

## 从模板声明

如果你总在声明同一类事件——同样的标题格式、同样的严重性、同样的值班策略——那就把它保存成模板，一次搞定。

点击 **从模板创建**（**声明事件** 旁边那个描边按钮），会打开一个 **从模板创建事件** 对话框，里面有一个 **选择事件模板** 下拉框。选中一个模板，创建表单就会带着预填内容打开；提交前你仍然可以改任何东西。如果项目里还没有模板，你看到的会是 **No Incident Templates** 对话框，其中的 **Create Template** 按钮会把你带到 **事件 → 设置 → 事件模板**。

模板通过自己的六步向导创建——**模板信息**、**事件详情**、**受影响的资源**、**值班**、**Owners**、**标签**——包含这些字段：

| 字段                          | 用途                                              |
| ---------------------------- | ------------------------------------------------------ |
| **模板名称**                  | 模板在选择器中的标识。                                 |
| **模板描述**                  | 给未来的自己留一句话：什么时候该用它。                  |
| **标题**                     | 预填到事件上的标题。                                    |
| **描述**                     | 预填到事件上的 Markdown 描述。                          |
| **事件严重性**                | 预填到事件上的严重性。                                  |
| **初始事件状态**              | 由该模板创建的事件从哪个状态开始。                       |
| **受影响的资源**              | 要附加的监视器、主机、集群和服务。                       |
| **将监视器状态更改为**         | 要应用到已附加监视器的监视器状态。                       |
| **值班策略**                  | 事件创建时要执行的策略。                                |
| **所有者 - 团队**             | 拥有由该模板创建的事件的团队。                           |
| **所有者 - 用户**             | 拥有由该模板创建的事件的用户。                           |
| **标签**                     | 应用到事件上的标签。                                    |

几条简单规则：

- 模板不能在模板列表里直接编辑——先创建，再打开它来修改。
- 模板只会填充你留空的字段。在创建页面上，模板是以可覆盖的预填形式应用的；在 API 上，只有当请求把某个字段留为 `undefined` 时，服务器才会用模板填它。调用方提供的内容永远优先。

## 通过监视器条件自动声明

大多数事件都不该需要人来手动录入。在监视器的条件编辑器里打开 **当过滤器匹配时，声明事件。** 开关，就会出现一个 **创建事件** 区块，带一个 **添加事件** 按钮——一个条件过滤器可以声明不止一个事件。

每一项包含：

- **事件标题** —— 支持模板语法；占位提示会建议类似 `{{monitorName}} is down` 的写法。
- **严重程度** —— 必填。
- **事件描述** —— 同样支持模板语法。
- **值班 → 值班策略** —— 该事件创建时要执行的策略。
- **事件角色** —— 预先把团队成员分配到各角色。
- **所有权和标签 → 所有者团队**、**所有者用户**、**标签**。
- **高级选项 → 自动解决事件**（条件不再匹配时自动解决该事件）、**在状态页上显示事件**、**私密事件** 和 **补救备注**。

标题、描述和补救备注中可用的 `{{variable}}` 占位符完整清单，见 [事件与告警模板](/docs/monitor/incident-alert-templating)。

以这种方式创建的事件会被服务器打上标记：设置 `isCreatedAutomatically`，用 `createdCriteriaId` 记录是哪个条件过滤器触发的，用 `createdByProbe` 记录是哪个探针发现的。除此之外，它们的表现与手动声明的事件完全一致。

## 通过 API 声明

事件模型暴露了标准的 CRUD 端点，所以 `POST /api/incident` 就能创建一个事件。用在 **项目设置 → API 密钥** 生成的 API 密钥进行认证，通过 `apikey` 请求头发送——密钥本身标识了项目，因此你不需要另外传项目 id。

```bash
curl -X POST https://oneuptime.com/api/incident \
  -H "apikey: $ONEUPTIME_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "data": {
      "title": "Checkout latency above SLO",
      "description": "Investigating elevated p99 latency on the checkout service.",
      "incidentSeverityId": "<incident-severity-id>"
    }
  }'
```

请求体上有用的字段：

- `title` —— 唯一一个你真正必须提供的字段。
- `declaredAt` —— 这里是可选的，尽管表单要求填写。省略它，服务器会使用当前时间。
- `incidentSeverityId` 和 `currentIncidentStateId` —— 服务器会检查两者是否与 API 密钥属于同一个项目，不属于就拒绝请求。**将监视器状态更改为** 背后的监视器状态也适用同样的检查。
- `createdIncidentTemplateId` —— 应用一个已保存的模板。你省略的字段会从模板填充；你传了的字段会原样保留。

相关端点还有 `/api/incident-state`、`/api/incident-severity` 和 `/api/incident-state-timeline`。自动生成的 [API 参考](/reference) 给出了每个端点确切的请求和响应结构，包括监视器这类关联字段是如何表达的。

## 事件编号与前缀

每个事件都会从项目级计数器获得一个递增编号，由服务器在创建时分配。两个列保存它：`incidentNumber`（原始整数）和 `incidentNumberWithPrefix`（你实际看到的值）。没有配置前缀时，显示值是 `#42`。

要改这一点，去 **事件 → 设置 → 更多设置**。**号码前缀** 卡片有一个 **事件编号前缀** 字段（最多 20 个字符，占位提示 `INC-`）——设置它，同一个事件就会显示成 `INC-42`。留空则保持默认的 `#`。这张卡片还带有用于片段编号的 **事件片段编号前缀**。

编号会出现在事件列表的第一列，可点击跳转到该事件，并在事件的 **概览** 上以 **事件编号** 的形式出现。

## 事件被声明的那一刻会发生什么

创建调用做的不只是写一行数据。按顺序：

1. **服务器补齐空缺。** `declaredAt` 默认为当前时间，当前状态默认为项目里带 `isCreatedState` 的状态，事件编号和带前缀的编号从项目计数器分配。
2. **应用模板**（如果传了 `createdIncidentTemplateId`）—— 只填充调用方留为 undefined 的字段。
3. **隐私规则运行**，当有规则匹配时把事件标记为私密。这是第一个运行的规则引擎，因此之后的一切看到的都是正确的隐私设置。
4. **所有者规则运行**，添加匹配规则所指定的所有者用户和团队。
5. **标签规则运行**，为事件添加匹配的标签。
6. **值班规则运行。** **事件 → 规则 → 值班规则** 下每一条启用且条件匹配的规则，都会把自己的策略加到事件上。这里没有优先级顺序，也不会短路——所有匹配的规则都会触发，策略随后去重。
7. **Runbook 规则运行**，附加并启动匹配的 runbook。参见 [Runbook 概览](/docs/runbooks/index)。
8. **值班策略执行。** 事件上的每一个策略——向导里选的、从模板继承的，或由规则添加的——都会以事件类型 `IncidentCreated` 并行执行。某个策略失败不会影响其他策略。
9. **订阅者进入队列**，前提是 **通知状态页订阅者** 保持开启且事件在状态页上可见。投递由后台任务处理，不会在你的请求中同步完成。
10. **工作流触发。** **On Create Incident** 触发器会启动构建在它之上的所有工作流。参见 [工作流概览](/docs/workflows/index)。

从这一刻起事件就"活"了：它会计入事件侧边菜单里的 **活动事件** 徽章（任何未带 `isResolvedState` 标志的状态都算活动），它会出现在包含其某个监视器的状态页上，它的 **状态时间线** 也开始记录。
