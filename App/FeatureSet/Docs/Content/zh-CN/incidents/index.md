# 事件概览

OneUptime 中的事件，就是出问题时团队围绕它开展工作的那条记录。它带有一个编号、一个标题、一个严重性、一个当前状态、它所影响的资源，以及团队在响应过程中写下的一切——备注、根本原因、补救步骤，还有一条只增不改的信息流，记录谁做了什么。

事件是把"监视器变红"变成协同响应的东西。声明一个事件会呼叫对应的值班轮值、添加会收到每一次变更通知的所有者、启动 Runbook，并且——如果你希望的话——把这次故障发布到公开状态页，让客户不必再开工单来问你是否已经知情。

你可以在凌晨三点手动声明一个事件，也可以让监视器在条件匹配的那一刻替你声明。无论哪种方式，事件都是同一个对象，具有同样的生命周期，最后留下同样的记录轨迹。

## 一览

- **顶层功能**——仪表板左侧导航中的 **事件**，位于 `/dashboard/{projectId}/incidents`。
- **三个预置状态**——每个新项目都会创建 **Identified**、**已确认** 和 **已解决**。你可以添加自己的状态；这三个预置状态可以改名和改颜色，但永远无法删除。
- **三个预置严重性**——**Critical Incident**、**Major Incident** 和 **Minor Incident**。严重性只是一个带颜色和顺序的标签——它自身不带任何行为。
- **四种创建方式**——**声明事件** 向导、**从模板创建**、监视器条件规则，或者 `POST /api/incident`。
- **按项目编号**——每个事件都会得到一个事件编号，默认渲染为 `#42`，也可以带上你自己的前缀，比如 `INC-42`。
- **两类备注**——给团队看的私密备注（内部备注），以及给状态页订阅者看的公开备注。
- **设置在"事件"下，而不在项目设置里**——状态、严重性、模板、自定义字段和规则引擎全都在 **事件 → 设置** 和 **事件 → 规则** 下。

## 关键术语

有一小撮词会出现在本章的每一页上。先把它们理顺。

| 术语               | 含义                                                                                                 |
| ------------------ | ---------------------------------------------------------------------------------------------------- |
| **事件**           | 记录本身——标题、描述、严重性、当前状态、受影响的资源，以及响应期间写在上面的一切。                    |
| **事件状态**       | 事件处在生命周期的哪个位置。一条项目范围内的记录，带有名称、颜色和 `order`，外加赋予它含义的那些标志。 |
| **事件严重性**     | 有多严重。一条项目范围内的记录，带有名称、颜色和 `order`。纯粹是一种分类——产品中没有任何地方会特殊对待某个严重性。 |
| **事件编号**       | 一个按项目递增的计数器，显示为 `#42`，或者带上你配置的前缀，显示为 `INC-42`。                         |
| **受影响的资源**   | 你附加到事件上的监视器、主机、Kubernetes 集群、Docker 主机、服务以及其他基础设施。                    |
| **公开备注**       | 写给状态页读者和订阅者的更新。它会渲染在状态页的时间线上。                                            |
| **私密备注**       | 给响应团队看的内部备注（`IncidentInternalNote` 模型）。它永远不会到达状态页。                         |
| **所有者**         | 对事件负责的用户或团队。事件创建、备注发布和状态变更时，所有者都会收到通知。                          |
| **事件信息流**     | 事件 **概览** 上只增不改的活动时间线，记录状态变更、备注、所有者变更、规则执行和通知。                |
| **状态时间线**     | 事件曾处于哪个状态、何时进入、持续多久的记录——并附带每次转换的订阅者通知状态。                        |

## OneUptime 为每个项目预置的三个状态

创建项目时，OneUptime 会按这个顺序恰好预置三个事件状态：

| 状态             | 顺序  | 颜色               | 含义                                                     |
| ---------------- | ----- | ------------------ | -------------------------------------------------------- |
| **Identified**   | 1     | 红色（`#fd625e`）  | 全新事件落入的状态。这就是创建状态。                     |
| **已确认**       | 2     | 黄色（`#ffbf53`）  | 已经有人接手这个事件并在处理。                           |
| **已解决**       | 3     | 绿色（`#2ab57d`）  | 事件结束了。把它解决掉，才会让它从你的状态页上消失。     |

名称只是标签——真正驱动行为的是状态记录上的三个布尔值：`isCreatedState`、`isAcknowledgedState` 和 `isResolvedState`。每个项目中，预期每个标志只由一个状态持有。

这个区别比听上去更重要：

- `isCreatedState` 决定新事件从哪里开始。如果创建时没有显式选择状态，OneUptime 会去找项目的创建状态并使用它。
- `isAcknowledgedState` 和 `isResolvedState` 驱动事件头部的 **Acknowledge** 和 **解决** 按钮、事件 **概览** 上的两块统计卡片，以及侧边菜单里的 **活动事件** 计数徽章。
- **活动事件** 的定义纯粹就是"当前状态不是已解决状态"。因此你添加的任何自定义状态都算活动的，除非它就是那个已解决状态。

**注意命名。** 第一个预置状态叫 **Identified**，尽管产品内部有些描述仍然把它称作创建状态。如果你在项目的状态列表里找 "Created"，那就是名为 **Identified** 的那一行。

你可以在 **事件 → 设置 → 事件状态** 添加自己的状态。新状态会追加到有序列表的末尾，你可以拖动来重新排序。那三个带标志的状态无法删除——OneUptime 会阻止——但你可以给它们改名和改颜色，这也是界面动态读取状态名称的原因。

顺序是被强制执行的，不只是装饰：事件无法移动到顺序上早于当前状态的状态。

完整细节见 [事件状态与严重级别](/docs/incidents/states-and-severities)。

## OneUptime 为每个项目预置的三个严重性

每个新项目还会得到三个严重性：

| 严重性                | 顺序  | 颜色               | 含义                                       |
| --------------------- | ----- | ------------------ | ------------------------------------------ |
| **Critical Incident** | 1     | 栗色（`#b70400`）  | 对客户影响极大，需要立即响应。             |
| **Major Incident**    | 2     | 红色（`#fd625e`）  | 影响显著，通常需要立即响应。               |
| **Minor Incident**    | 3     | 黄色（`#ffbf53`）  | 影响较小，通常在工作时间内处理。           |

预置的完整描述见 [事件状态与严重级别](/docs/incidents/states-and-severities)。

严重性只有 `name`、`description`、`color` 和 `order`，别无其他。没有标志，也没有任何代码路径会把 "Critical Incident" 与其他记录区别对待。严重性是人类做分诊的方式，并且在你编写值班规则时可以作为匹配条件——但选择一个严重性本身并不会呼叫任何人。

在 **事件 → 设置 → 事件严重性** 编辑或添加严重性。

## 一个事件的一生

### 1. 它被声明

四条路线通向同一个对象：

- **手动**——在事件列表中点击 **声明事件**。这会打开 **声明新事件** 向导，共五步：**事件详情**、**受影响的资源**、**事件角色**、**值班**、**更多**。
- **从模板**——点击 **从模板创建** 并选择一个保存好的 **事件模板**。模板会预填标题、描述、严重性、初始状态、资源、值班策略、所有者和标签。
- **从监视器**——启用了"声明事件"开关的监视器条件规则，会在其过滤器匹配的那一刻自动创建事件。那里的标题和描述支持 `{{variable}}` 模板。
- **通过 API**——用 API 密钥调用 `POST /api/incident`。服务器会替你填好 `declaredAt`、创建状态和事件编号。

逐字段的详细讲解见 [声明事件](/docs/incidents/declaring-incidents)。

### 2. 该知道的人知道了

创建时 OneUptime 会运行你配置的自动化：标签规则、值班规则、所有者规则和 Runbook 规则。附加到事件上的所有值班策略——手动附加的、来自模板的，或由匹配的值班规则合并进来的——会并行执行。

所有者会通过电子邮件、短信、电话、推送和 WhatsApp 收到通知，具体取决于每个用户自己的通知偏好。如果一个事件完全没有所有者，通知会回退到项目所有者，而不是被丢弃。

如果事件在某个状态页上可见并且启用了订阅者通知，订阅者也会被告知。通知由定时任务驱动，每分钟运行一次，所以要预期最多约一分钟的延迟，而不是即时发送。

### 3. 团队开始处理

响应者确认事件、附加受影响的资源、运行 Runbook、分配事件角色，并把了解到的信息写下来——给团队的私密备注、给客户的公开备注，以及在情况逐渐清晰时填写的 **根本原因** 和 **补救** 页面。他们做的每一件事都会落到 **概览** 页的 **事件信息流** 上。

### 4. 它被解决

点击 **解决** 会把事件移到已解决状态、在状态时间线上打戳、停止持续时间计时，并把事件从它所显示的任何状态页的活动区域中移除。要做到这些，不需要改动别的任何东西——状态页查询看的就是那个已解决状态标志。

之后你可以写事后分析，并可选择把它发布到状态页。

## 事件在仪表板中的位置

在左侧导航中打开 **事件**。它的侧边菜单分成几个区块：

| 区块           | 你在那里做什么                                                                                                                    |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **概览**       | **所有事件** 和 **活动事件**——后者带有一个红色徽章，显示不处于已解决状态的事件数量。                                               |
| **片段**       | 事件片段，一个有自己页面的独立分组功能。                                                                                           |
| **人工智能**   | **调查** 和 **补救**——自动调查与自动补救设置。                                                                                    |
| **工作区**     | 事件的 **Slack** 和 **Microsoft Teams** 连接。                                                                                    |
| **规则**       | 规则引擎：**分组规则**、**值班规则**、**所有者规则**、**Runbook 规则**、**隐私规则**、**标签规则**、**SLA 规则**、**Reminder Rules**。 |
| **设置**       | **事件状态**、**事件严重性**、**事件模板**、**备注模板**、**事后分析模板**、**自定义字段**、**事件角色**、**更多设置**。            |

**规则** 和 **设置** 默认是折叠的——展开它们才能找到这些文档后面提到的页面。事件配置不在项目设置里；它全都在这儿。

事件列表本身显示 **事件编号**、**标题**、**状态**、**严重程度**、**受影响的资源**、**已声明**、**持续时间**、**标签** 和 **所有者**，并带有一个 **更改状态** 批量操作，可以一次关掉好几个。

## 事件的每个页面显示什么

打开一个事件，你会得到一个左侧菜单，分组如下：

- **概览**——**事件详情** 卡片（标题、严重性、标签、事件编号、声明时间、声明人、值班策略）、一张 **受影响的资源** 卡片，以及 **事件信息流**。它们上方是确认耗时、解决耗时和总 **持续时间** 的统计卡片。
- **状态时间线**——事件经历过的每一个状态，带有 **开始**、**结束**、**持续时间** 以及每次转换的订阅者通知状态。**查看原因** 和 **查看日志** 解释每次变更为何发生。
- **SLA**——本事件的 SLA 跟踪。
- **描述**、**根本原因**、**补救**——三个 Markdown 页面。描述就是显示在你状态页上的那一个。
- **运行手册**——附加到本事件的 Runbook 执行。
- **事后分析**——事后总结，你可以选择把它发布到状态页。
- **角色**、**值班执行**、**所有者**——谁在处理、哪些策略被触发、谁会收到通知。
- **通知日志**、**AI 日志**、**审计日志**——发送了什么、变更了什么。
- **私人备注** 和 **公开备注**——在侧边菜单的 **备注** 区块下。
- **自定义字段**、**设置**、**删除事件**——在 **高级** 下。**设置** 页面包含 **在状态页面上可见**、**私密事件** 和 **Reminders** 卡片。

[事件备注、负责人与动态](/docs/incidents/notes-owners-and-feed) 深入讲解这些协作页面。

## 事件如何与 OneUptime 的其他部分配合

- **监视器发现问题；事件记录问题。** 监视器条件规则可以自动声明事件，并预填标题、严重性、值班策略、所有者、标签和补救备注。那里可用的变量见 [事件与告警模板](/docs/monitor/incident-alert-templating)。
- **值班策略负责呼叫。** 在声明向导的 **值班** 步骤、在模板上，或通过 **事件 → 规则 → 值班规则** 附加策略。每一条匹配的规则都会触发——最终执行的集合是所有匹配项加上直接附加内容的并集，并去重。
- **Runbook 告诉大家该做什么。** Runbook 规则会在匹配的事件创建时自动附加一份流程，响应者也可以从事件手动启动一份。见 [Runbook 概览](/docs/runbooks/index)。
- **状态页告诉客户。** 当状态页启用了事件、该事件被标记为在状态页上可见，且其当前状态不是已解决状态时，事件会出现在状态页的活动列表中。私密事件始终对所有状态页隐藏。见 [状态页概览](/docs/status-pages/index)。
- **工作流围绕它做自动化。** **On Create Incident**、**On Update Incident** 和 **On Delete Incident** 触发器让你在事件生命周期之上构建无代码自动化。见 [工作流概览](/docs/workflows/index)。
