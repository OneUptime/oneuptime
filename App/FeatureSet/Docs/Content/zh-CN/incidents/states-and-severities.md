# 事件状态与严重级别

每个事件都带有两种分类：一个 **状态**，说明它在你的响应过程中处于哪个位置；一个 **严重性**，说明它有多痛。在仪表板里它们看起来很像——都渲染成事件列表上的彩色徽标，都是可以重命名和重新配色的项目范围列表。但它们做的事情非常不同。

状态驱动行为。状态记录上的三个布尔标志，决定了哪些事件算作活动的、事件头部会出现哪些按钮、SLA 计时何时停止，以及事件何时从你的状态页上消失。严重性本身不驱动任何东西——它们是描述影响的标签，供其他规则去匹配。

两份列表都会在项目创建时预置，也都在 **事件 → 设置** 下编辑。事件侧边菜单里的这个区块默认是折叠的，所以要先展开 **设置**，才能找到它。

## 状态承载行为，严重性承载含义

`IncidentState` 模型有 `name`、`description`、`color` 和 `order`，外加三个布尔值：`isCreatedState`、`isAcknowledgedState` 和 `isResolvedState`。产品对状态所做的一切都取决于这些布尔值和 `order`——从来不取决于状态的名称。这就是为什么你可以把 **已解决** 改名为 "Closed" 而不会出问题：标志跟着这一行记录走。

`IncidentSeverity` 模型有 `name`、`description`、`color` 和 `order`，别无其他。没有标志。OneUptime 里没有任何地方会自行把 **Critical Incident** 和 **Minor Incident** 区别对待——严重性只在你把某个东西指向它的地方才有意义，比如值班规则上的 **Incident Severities** 匹配条件。

几条速记规则：

- **用严重性来传达影响**——它显示在事件列表上、事件的 **概览** 上，并且是声明事件时的必填字段。
- **用状态来建模你的流程**——你实际会走过的响应步骤，按你实际走过的顺序。
- **不要用状态编码紧急程度**——一个叫 "Critical" 的状态并不会呼叫任何人。严重性加上一条值班规则才能做到这一点。

## 预置的状态

项目创建时会按这个顺序创建三个状态。预置过程是幂等的——只有当同名状态还不存在时，才会添加它。

| 状态             | `order` | 标志                   | 颜色      | 含义                                       |
| ---------------- | ------- | ---------------------- | --------- | ------------------------------------------ |
| **Identified**   | `1`     | `isCreatedState`       | `#fd625e` | 新事件落入的状态。                          |
| **已确认**       | `2`     | `isAcknowledgedState`  | `#ffbf53` | 已经有人接手了这个事件。                    |
| **已解决**       | `3`     | `isResolvedState`      | `#2ab57d` | 事件结束了，不再计入活动状态。              |

注意这个名字：第一个状态是 **Identified**，尽管产品内部有几处描述仍然把它称作 "created" 状态。当文档或提示里说 "created state" 时，它指的是持有 `isCreatedState` 的那个状态——在一个全新的项目里，就是 **Identified**。

## 每个状态标志实际做什么

| 标志                   | 作用                                                                                                                       |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `isCreatedState`       | 没有人指定状态时，事件会拿到的那个状态。如果项目里没有任何状态带有这个标志，创建事件会失败，并提示你去设置里添加一个创建状态。 |
| `isAcknowledgedState`  | 驱动 **Acknowledge** 按钮和事件 **概览** 上的 "<state name> in" 统计卡片。当状态变更进入这个状态时，事件的 SLA 会被标记为已响应。 |
| `isResolvedState`      | 驱动 **解决** 按钮和已解决统计卡片，定义了 **活动事件** 列表，也是把事件从状态页活动区域移除的原因。把 SLA 标记为已解决。     |

每个项目里，预期每个标志只由一个状态持有——查询取的是单独一行。这三个带标志的状态可以重命名、重新配色和重新排序，但设置页面拒绝删除它们，并会显示一个指名创建状态、已确认状态和已解决状态的错误。

由于界面是动态读取状态名称的，重命名一个状态会改变你在各处看到的内容——统计卡片、确认弹窗标题，以及事件列表上的徽标，都会跟着你给这一行起的名字走。

## 添加你自己的状态

前往 **事件 → 设置 → 事件状态**。这个页面是一个按 `order` 升序排列的有序列表，新状态会追加到末尾。拖动一行可以改变它的位置。

**状态上的字段：**

- **名称**——必填，至少两个字符。占位符建议类似 "Investigating" 这样的写法。
- **描述**——可选的自由文本，说明什么情况下事件会处于这个状态。
- **颜色**——必填。从颜色选择器里挑选；存储为像 `#fd625e` 这样的十六进制值。

你不能从这个表单设置那三个标志——它们属于预置的那几行。因此你添加的状态是一个不带标志的状态，这带来两个值得提前规划的后果：

- **它算作活动的。** **活动事件** 的定义是"当前状态不是已解决状态"，所以除了已解决状态以外，你添加的任何状态都会让事件留在活动列表和侧边栏计数里。
- **它的转换按钮是通用的。** 不是 **Acknowledge** 或 **解决**，确认弹窗的标题会是 **Mark Incident as `<state name>`**，提交按钮是 **Mark as `<state name>`**。

一种常见的用法是在已确认和已解决状态之间插入一个分诊或缓解步骤——比如拖一个新的 "Mitigated" 状态，让它排在 **已确认** 之后、**已解决** 之前。

## 顺序是一个真实的约束，不只是显示偏好

`order` 这一列是在写入状态变更时强制执行的，不只是在渲染列表时：

- **向后的转换会被拒绝。** 把事件移动到一个在顺序上早于其当前状态的状态会失败，错误会指名这两个状态。
- **重新选择当前状态会被拒绝。** 把事件设置为它已经处于的那个状态会失败，提示 "Incident state cannot be same as previous state."
- **回填的行不能和相邻行重复。** 插入一条时间线行，如果它的状态和紧随其后的那一行相同，同样会被拒绝。
- **头部按钮跟随带标志状态在顺序中的位置。** **Acknowledge** 和 **解决** 是否出现，取决于当前状态在按顺序排列的列表中所处的位置。一个排在已解决状态 *之后* 的自定义状态永远不会显示 **解决** 按钮，因为已经没有可以继续前进的地方了。

所以，当你添加一个状态时，要把它放在事件真正会经过它的位置上。顺序放错了不只是看起来奇怪——它会让转换根本无法进行。

## 预置的严重性

项目创建时会按这个顺序创建三个严重性：

- **Critical Incident**（`order` 1，`#b70400`）——对客户造成极大影响的问题，需要立即响应。比如一次完全的服务中断或一次数据泄露。
- **Major Incident**（`order` 2，`#fd625e`）——影响显著，通常需要立即响应，有时可以用一个限制损害的临时方案顶一下。比如一个重要子系统出了故障。
- **Minor Incident**（`order` 3，`#ffbf53`）——影响较小，通常可以在工作时间内处理，大多数客户都不太可能注意到。比如应用性能有轻微下降。

声明事件时严重性是必填的，监视器条件里的每一条事件规格也都要求填写严重性，所以每一个事件——不管是手动的还是自动的——都会带着一个严重性到来。声明流程见 [声明事件](/docs/incidents/declaring-incidents)，监视器驱动的路径见 [事件与告警模板](/docs/monitor/incident-alert-templating)。

## 编辑严重性

前往 **事件 → 设置 → 事件严重性**。和状态页面形状相同——一个按 `order` 排序的有序列表，拖动来重新排序，新的严重性追加到末尾，表单上有 **名称**、**描述** 和 **颜色**。

和状态相比有两点不同：

- **没有删除保护。** 任何严重性都可以删除，包括那三个预置的。
- **没有可继承的标志。** 一个新的严重性和预置的那些行为完全一样——它就是一个带颜色和位置的标签。

**关于占位符的一个说明。** 严重性表单一字不差地复用了状态表单的示例文本，所以提示里说的是事件状态而不是严重性。忽略它们，写你自己的严重性名称和描述就好。

严重性发挥更大作用的地方：在 **事件 → 规则 → 值班规则** 上，一条规则的 **Incident Severities** 字段是一个匹配条件。在那里列出 **Critical Incident**，就是"任何严重的问题都呼叫数据库团队"这句话的具体表达方式——值班策略挂在规则上，而不是挂在严重性上。

## 让一个事件在各个状态之间流转

一个事件改变状态有四种方式：

- **头部按钮。** 打开一个事件。如果它的当前状态在已确认状态之前，你会看到 **Acknowledge** 和 **解决**；如果它介于两者之间，你会看到 **解决**。每一个都会打开一个确认弹窗——**Acknowledge Incident** 或 **Resolve Incident**——里面还提供 **Select Note Template**、**Public Note** 和 **通知状态页订阅者**。
- **状态时间线。** 从事件的 **状态时间线** 页面手动添加一行，填写 **Incident Status**、**开始** 和 **通知状态页订阅者**。
- **批量修改。** 事件列表有一个 **更改状态** 批量操作，可以一次移动好几个事件。
- **自动。** 一条启用了 **Auto Resolve Incident** 的监视器条件，会在条件不再满足时解决对应的事件，API 也可以通过 `/api/incident-state-timeline` 更新状态。

以上每一种方式都会写入一行时间线记录。状态变更还会做几件你不需要额外要求的事：它会在事件信息流上发一条记录，如果事件还没有 Incident Commander 就会指派一个，并更新 SLA 计时。重新打开一个已解决的事件，会从重新打开的那一刻开始一条全新的 SLA 记录。

## 状态时间线

事件侧边菜单里的 **状态时间线** 页面，是这个事件曾经处于过的每一个状态的审计轨迹。这个页面上的卡片标题是 **Status Timeline**，按最新优先排序。

**列：**

- **Incident Status**——一个带颜色的徽标，显示状态的名称和颜色。
- **开始**——事件进入这个状态的时间。
- **结束**——它离开的时间。当前状态显示为 `Currently Active`。
- **持续时间**——在这个状态里花费的时间，对于当前状态会计算到现在为止。
- **订阅者通知状态**——这次变更的状态页通知是已发送、已跳过还是仍在等待中，带有一个 **more details** 链接，以及——当发送失败时——一个 **Retry** 操作。

**行内操作：**

- **查看原因**——打开一个 **根本原因** 弹窗，渲染随这次状态变更记录的 markdown 内容。
- **查看日志**——打开一个弹窗，解释状态为什么变化，带有一个 **Incident State Log** 查看器。

时间线行可以创建和删除，但不能编辑。删掉错误的一行会重写事件的历史，所以要把它当作一种纠错手段，而不是日常清理习惯。

## 活动事件列表

**事件 → 活动事件** 是你在值班期间盯着的那份列表。它的定义恰好只有一个条件：事件的当前状态是 `isResolvedState` 为 false 的状态。别的都不考虑——不看严重性，不看时长，也不看有没有人确认过。

侧边栏的这一项用同一个查询来算一个红色计数徽标，所以徽标和列表永远一致。没有内容时，页面会明确说明。

实际的后果是：你添加的任何自定义状态都会让事件留在这份列表里。这通常正是你想要的——"Mitigated" 不等于"完成了"——但这也意味着，只有当事件真正到达已解决状态时，徽标才会清零。

## 把状态变更告诉状态页订阅者

状态变更可以给你的状态页订阅者发邮件，但要经过好几道关卡。理解它们能省下大量"为什么没人收到通知"的排查时间。

通知是按每一行时间线记录来请求的，由 **通知状态页订阅者**（`shouldStatusPageSubscribersBeNotified`）决定——这是状态变更弹窗和手动时间线表单上的复选框。关闭时，这一行会以已跳过状态存储，并附带原因说明。打开时，这一行会被排队，由一个后台任务接手处理——这个任务每分钟运行一次，所以投递很快，但不是即时的。

**已排队的行在以下任何一种情况下都会被跳过：**

- **新状态是创建状态。** 事件声明时订阅者已经被告知过了，所以第一行时间线记录刻意不再发第二条消息。
- **事件没有附加任何监视器。** 没有资源，就没有可以把事件映射上去的状态页。
- **事件在状态页上不可见**（`isVisibleOnStatusPage` 关闭）。
- **状态页把事件展示关掉了**（`showIncidentsOnStatusPage` 关闭）。这一项是按每个状态页单独判断的——展示同一个监视器的其他状态页仍然会收到通知。

**还有一件事会改变结果。** 如果你在状态变更弹窗里填写了一条 **Public Note**，这一行时间线记录会被标记为已经通知过，而不是排队等待。备注本身就是发给订阅者的内容，所以他们只会收到一条消息，而不是两条。普通状态变更消息背后的事件类型是 `Subscriber Incident State Changed`。

关于谁会收到这些通知、模板是如何选择的，见 [订阅者与公告](/docs/status-pages/subscribers)。

## 让一个事件不出现在状态页上

有三件互相独立的事情决定一个事件是否会出现在公开页面上，而且三者都必须成立：

- 状态页本身的 **显示事件**（`showIncidentsOnStatusPage`）。
- 事件上的 **在状态页面上可见**（`isVisibleOnStatusPage`）——事件 **设置** 页面上的一个开关。它默认为开启，且不在声明向导里；一条监视器条件可以用 **Show Incident on Status Page** 来设置它。
- **当前状态不是已解决状态。** 这就是把一个事件从活动区域移除的原因：状态页查询取的是当前状态为任意未解决状态的事件。你不需要归档或关闭任何东西——你只需要解决它，它就会移入历史记录。

**私密事件永远不会出现。** 打开 **私密事件** 会让这个事件对所有状态页隐藏，无论上面那些开关如何设置，并且把它限制为只有它的所有者，加上项目管理员和所有者才能看到。

页面保留多少已解决的历史记录，是状态页的设置，而不是事件的设置。页面上的监视器如何决定哪些事件会出现，见 [状态页资源与分组](/docs/status-pages/resources-and-groups)。
