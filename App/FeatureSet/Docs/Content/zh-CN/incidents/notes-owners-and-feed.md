# 事件备注、负责人与动态

在处理事件的过程中，每个事件都会积累一份书面记录。其中一部分是给客户看的——比如凌晨 02:14 发布到状态页、说明你已经找到问题部署的那条更新。另一部分是给团队看的——有人贴出的堆栈跟踪、终于讲得通的那张图表、故障切换的决定。

OneUptime 把这两类受众区分开来。**公开备注** 会发布到你的状态页并可以通知订阅者。**私密备注**（`IncidentInternalNote` 模型）只留在仪表板内部。这两者之下是 **事件信息流**，一条只增不改的时间线，记录了事件发生的一切；还有 **所有者** 列表，决定谁会被告知。

这一切都挂在事件的左侧菜单下：**备注 → 公开备注**、**备注 → 私密备注**，以及 **团队 → 所有者**。信息流则位于事件的 **概览** 页面上。

## 公开备注与私密备注

这两种备注类型在仪表板中看起来相似，但行为差异很大。

- **公开备注** —— `IncidentPublicNote` 模型，作为事件时间线的一部分提供给状态页。它们带有一个可以自行设置的 **发布于** 日期，以及一个 **通知状态页订阅者** 复选框。
- **私密备注** —— `IncidentInternalNote` 模型。状态页应用中没有任何地方会读取它们。它们没有发布时间字段（列表按 `createdAt` 打上时间戳并排序），也完全没有订阅者相关字段，因此私密备注永远不会触发订阅者通知。

**"私密"的真正含义。** 它的意思是"不发布到状态页"——而不是"仅限一小部分人查看"。两种备注类型共享相同的读取权限，因此任何能读取该事件的人都能读取它的私密备注。如果你需要限制谁能看到某个事件本身，请使用事件上的 **Private Incident** 标志（`isPrivate`），它会让该事件对所有状态页都不可见，并把可见范围限制在该事件的所有者用户、其所有者团队的成员，以及项目管理员和所有者。

**所有者两者都能看到。** 所有者通知任务会同时查询公开备注和私密备注。私密备注是对你的订阅者保密，而不是对响应者保密。

| 如果你想要……                             | 选择         |
| ------------------------------------------ | ------------ |
| 告诉客户你目前所知道的，以及何时会有更多信息 | **公开备注** |
| 补录一条你已经在别处发送过的更新           | **公开备注** |
| 记录一个假设、你运行过的一条命令、或一条死胡同 | **私密备注** |
| 附上堆内存转储或内部仪表板截图             | **私密备注** |

## 发布一条公开备注

在事件侧边菜单中打开 **备注 → 公开备注** 并创建一条备注。卡片说明这里写的内容会出现在状态页上；空状态提示到目前为止该事件尚未创建任何公开备注。

| 字段                          | 用途                                                                             |
| ----------------------------- | -------------------------------------------------------------------------------- |
| **Public Incident Note**      | 正文，使用 Markdown。必填。表单会提醒你该备注在状态页上可见，并附有速查表链接。   |
| **Attachments**               | 与订阅者在状态页上共享的文件。可选。                                              |
| **通知状态页订阅者**          | 复选框，默认开启。关闭它可以悄悄发布。                                            |
| **发布于**                    | 必填的日期和时间，默认为当前时间，以你当前时区显示。                              |

**"发布于"是备注的真实时间戳。** 状态页按 `postedAt` 而非你输入的时间对公开备注进行排序和展示——所以如果你要把 40 分钟前发送过的更新补录到状态页上，请把 **发布于** 设置为它实际发生的时间。如果一条备注通过 API 到达却没有携带该字段，OneUptime 会打上当前时间的戳。

列表会显示每条备注的撰写者、其 **发布于** 时间、渲染后的 Markdown 及其附件，以及一列 **订阅者通知状态**。你可以按 **创建者**、**备注** 和 **创建于** 进行筛选。

## 发布一条私密备注

**备注 → 私密备注** 特意做得更简单。只有两个字段：

- **Private Incident Note** —— Markdown 正文，必填。表单直接说明这是团队内部私密内容，不会在状态页上显示。
- **Attachments** —— 供事件响应团队使用的文件。

没有 **发布于**，没有订阅者复选框——备注在创建时就会被打上时间戳。

## 备注上的附件

两种备注类型都通过 **Attachments** 字段接受文件附件，并且都会在备注正文下方渲染一个附件列表，每个文件都带有一个 **Download attachment** 链接。

它们的区别在于谁能获取该文件：

- **公开备注附件** 可由状态页访客通过状态页路由与备注本身一起下载。
- **私密备注附件** 只能通过经过身份验证的仪表板 API 获取。状态页没有对应的路由。

这使得附件面临与备注正文相同的公开/私密决策。面向客户的时间线图片放在公开备注上；配置转储放在私密备注上。

## 使用 AI 生成备注

两个备注页面都带有一个 **Generate with AI** 按钮。它会把事件发送给你项目的 AI 提供方，并把生成的 Markdown 放入备注编辑器中，你可以在保存前对其进行编辑——不会自动发布任何内容。

- **Generate Public Note with AI** —— 描述为分析事件数据以生成面向客户的备注。模板包括 **Status Update** 和 **Resolution Notice**。
- **Generate Private Note with AI** —— 生成的是内部技术备注。模板包括 **Investigation Update** 和 **Technical Analysis**。

在按钮背后，仪表板会向 `/incident/generate-note-from-ai/{incidentId}` 发出请求，携带所选模板以及 `public` 或 `internal` 的备注类型。

## 备注模板

如果你的团队在每次故障中都写着同样的三条更新，那就把它们保存一次。两个备注页面都有一个 **从模板创建** 按钮，会打开一个 **Create Note from Template** 选择器，里面有一个 **选择备注模板** 下拉框。

模板在公开备注和私密备注之间共享：同一个模板列表同时服务两者，同一个模板可以插入到任意一种备注中。

你可以在 **事件 → 设置 → 备注模板** 中管理它们——该卡片标题为 **Public or Private Note Templates for Incidents**，其表单包含一个 **模板信息** 步骤（**模板名称** 和 **模板描述**，均为必填）以及一个用于正文的 **备注详情** 步骤。如果你在还没有创建任何模板时点击 **从模板创建**，OneUptime 会告诉你目前还没有模板；请注意该提示信息指向 Project Settings，但该页面实际位于 **事件 → 设置 → 备注模板** 下。

## 从 Slack 或 Microsoft Teams 发布备注

如果你已经连接了一个工作区，响应者根本不需要离开频道。Slack 和 Microsoft Teams 都提供一个添加备注的操作，会打开一个模态框，里面有一个下拉框可选择 **Public Note** 或 **Private Note**，外加一个文本框，并会把结果直接写入事件中。

有两个值得了解的细节：

- **重复保护** —— 每条备注都会记录它来源的 Slack 消息（`postedFromSlackMessageId`，格式为 `channel_id:message_ts`），因此多人对同一条消息作出反应只会产生一条备注，而不是五条。
- **备注会回显** —— 发布任意一种备注也会向已连接的事件频道推送一条消息，因为该备注的信息流条目在创建时启用了工作区通知。

## 一条公开备注何时真正送达订阅者

创建一条开启了 **通知状态页订阅者** 的公开备注，本身并不能保证一定会发出邮件。该备注必须通过一连串检查，每次失败都会记录一个具体原因，而不是报错：

1. **通知状态页订阅者** 必须开启。如果没有开启，该备注在创建的那一刻就会被标记为跳过。
2. 该备注必须属于一个仍然存在的事件。
3. 该事件必须至少附加了一个监视器——没有监视器就没有状态页资源可以将备注路由过去。
4. 该事件的 **Visible on Status Page** 标志（`isVisibleOnStatusPage`）必须为真。
5. 该事件所触达的每个状态页都必须开启 **Show Incidents**（`showIncidentsOnStatusPage`）。
6. 每位订阅者都必须通过他们自己的偏好设置——未取消订阅，并且已订阅该资源以及页面允许订阅者选择的 `Incident` 事件类型。

**通知不是即时的。** 发送通知的任务每分钟运行一次，因此从保存备注到邮件发出之间预计会有最多约一分钟的间隔。这正是 **Sending Soon** 标签的含义。

**订阅者通知状态** 列跟踪整个过程：

| 状态                          | 含义                                       |
| ----------------------------- | ------------------------------------------ |
| **Notifications skipped.**    | 上述某道关卡被关闭了。原因会被记录下来。   |
| **Sending Soon**              | 已排队，等待发送任务的下一次运行。         |
| **Notifications Being Sent**  | 任务正在处理订阅者列表。                   |
| **已发送的通知**              | 所有订阅者通知都已发出。                   |
| **失败**                      | 该任务抛出了异常；错误信息与备注一同存储。 |

点击状态旁的 **更多详情** 会打开 **通知状态详情**。在适合重发的情况下，该模态框中的按钮是 **Retry**，它会把备注重新置于待处理状态，以便下一次运行再次处理它。

订阅者实际收到的消息是按状态页和渠道分别模板化的——邮件、短信、Slack 和 Microsoft Teams 各自都有自己的 **Subscriber Incident Note Created** 事件模板，其中包含状态页名称与 URL、详情链接、受影响资源、事件严重性与标题、备注正文，以及每位订阅者专属的取消订阅链接等变量。这些模板和渠道的配置方式请参见 [订阅者与公告](/docs/status-pages/subscribers)。

## 事件信息流

**Incident Feed** 卡片位于事件 **概览** 页面左栏的底部。它按顺序讲述了这个事件的故事：每一项都包含一个图标、触发者的头像与姓名、一个悬停可查看确切本地时间的相对时间戳，以及一段 Markdown 正文。条目按最早在前排序。

有些条目带有额外细节——例如一次所有者通知会列出所有收到邮件的人。这些条目会显示一个 **More Information** 按钮，点击后会打开一个 **More Information** 面板。

卡片头部还有一个 **操作** 菜单，让你无需离开时间线即可执行操作：

- **Execute Runbook** —— 针对该事件启动一个 [runbook](/docs/runbooks/index)。
- **执行值班策略** —— 按需触发一个策略。
- **Add Public Note** —— 与公开备注页面相同的四个字段，以模态框形式呈现。
- **添加私密注释** —— 仅有备注正文和附件。

旁边的 **刷新** 会重新获取信息流。

**信息流是只增不改的，它不是你的审计日志。** API 允许创建和读取信息流条目，但不允许更新或删除，因此没有人能够悄悄改写一个事件的历史。它也不是永久的：在计费安装中，超过三年的信息流行会被删除。若需要一份关于谁改动了什么的持久记录，请使用事件侧边菜单中的 **Audit → 审计日志**。

## 信息流记录的内容

信息流条目由事件服务本身、两种备注服务、状态时间线、所有者与成员变更、规则引擎、值班执行、AI 调查与事后分析运行器，以及通知的定时任务写入。事件类型包括：

- **事件本身** —— `IncidentCreated`、`IncidentUpdated`、`IncidentStateChanged`。
- **备注与文档** —— `PublicNote`、`PrivateNote`、`RootCause`、`RemediationNotes`、`PostmortemNote`。
- **人员** —— `OwnerUserAdded`、`OwnerTeamAdded`、`OwnerUserRemoved`、`OwnerTeamRemoved`、`IncidentMemberAdded`、`IncidentMemberRemoved`。
- **通知** —— `OwnerNotificationSent`、`SubscriberNotificationSent`、`OnCallPolicy`、`OnCallNotification`。
- **自动化** —— `LabelRuleExecuted`、`OwnerRuleExecuted`、`PrivacyRuleExecuted`、`OnCallRuleExecuted`、`AutoRemediation`。

每种类型都有自己的图标，因此你可以扫视一条很长的信息流，从闲聊中挑出状态变更。AI 生成的根本原因分析会被明显标记，并以受限的 Markdown 模式渲染。

信息流遵循事件的隐私设置：对于私密事件，信息流的读取会按与事件本身相同的方式被过滤。

## 所有者

所有者是对某个事件负责的人和团队。他们是该事件发生的一切事情的通知对象——也是让事件不会在人人都以为别人在处理时被忽视的原因。

在事件侧边菜单中打开 **团队 → 所有者**。**Owners** 卡片会显示一个计数徽章，并将所有者描述为对该事件负责、会收到变更通知的人和团队，附带一个实时计数，比如 "2 people · 1 team"。所有者以重叠头像的形式呈现；悬停某一个会显示该人的邮箱，或将该条目标记为 **Team**。

- 点击 **添加所有者** 打开一个带搜索框的选择器，用于查找人员或团队。
- 点击头像上的移除控件，打开 **Remove owner** 确认框，然后点击 **移除**。
- 在还没有任何所有者时，卡片会说明这一点，并邀请你添加一名队友或一个团队，以便他们能收到变更通知。

所有者用户和所有者团队是各自独立的记录——添加一个团队会让该团队的每个成员都成为该事件的所有者（就通知而言），而无需逐一列出他们。

## 所有者是如何被指定的

有四条途径可以进入所有者列表：

- **来自事件模板** —— 模板带有 **Owner - Teams** 和 **Owner - Users** 字段，被描述为拥有该事件、并会在其创建或更新时收到通知的团队和用户。从模板创建事件会预先填入它们。参见 [声明事件](/docs/incidents/declaring-incidents)。
- **来自 Incident Owner Rules** —— 匹配的规则会在创建时自动添加所有者。
- **在通过 API 创建时** —— 随创建请求一起传入的所有者用户和团队会立即被添加，并带有一个标志用于控制他们是否收到"你已被添加"的邮件。
- **手动添加** —— 在事件的任何阶段，使用 **所有者** 页面上的 **添加所有者** 控件。

重复添加同一个人是安全的；已经被指定的所有者不会被重复添加。

## 事件所有者规则

**Incident Owner Rules** 会在匹配的事件被创建时自动指定所有者用户和团队——正是这层路由，让一个数据库事件在没有任何人思考的情况下就落到数据库团队身上。你可以在 [事件设置与自动化](/docs/incidents/settings) 中与其余事件自动化功能一起找到它们。

规则表单有三个步骤——**基本信息**、**匹配条件** 和 **Owners**——所有者步骤包含两个部分：

- **Owners to Assign** —— 选择 **Owner Teams** 和 **Owner Users**。当规则匹配时，每个被选中的用户和团队都会被添加为所有者，已经被指定的所有者不会被重复添加。
- **Inherit Owners** —— 从相关实体分配所有者，而不是直接指名。**Inherit Owners From Monitors** 会让该事件所有监视器的每个所有者都成为该事件的所有者，**Inherit Owners From Hosts**、**… From Kubernetes Clusters**、**… From Docker Hosts**、**… From Podman Hosts** 和 **… From Services** 对相应资源做同样的事。

一个 **通知所有者** 开关控制人们是否会得到通知。若是真正的路由，请保持开启；若某条规则只是记账便利而非真的要寻呼谁，可以关闭它以静默添加所有者。

每一次规则执行都会写入事件信息流，因此你总能分辨出某个人是被规则添加的，还是被人手动添加的。

## 所有者会收到哪些通知

有五个任务会通知所有者，各自每分钟运行一次：

- **事件已创建** —— 主题为 `[New Incident {number}] - {title}`。
- **发布了一条备注** —— 公开备注 *和* 私密备注都适用，主题为 `[Update Incident {number}] - {title}`。
- **事件状态发生了变化** —— 参见 [事件状态与严重级别](/docs/incidents/states-and-severities)。
- **你被添加为所有者** —— 主题为 `You have been added as the owner of Incident {number} - {title}`。
- **仍未解决** —— 由事件的下一次提醒时间驱动的提醒，主题为 `[Reminder] Incident {number} is still {state} - {title}`。

每条通知都会为邮件、短信、语音电话、推送和 WhatsApp 分别构建，并交给用户的通知设置来决定实际发送什么。每位接收者都可以单独关闭这些通知中的任意一项——每用户设置的措辞是发送给你事件已创建、备注已发布、状态已变化、所有者已添加、成员已指定，以及仍未关闭提醒等通知。只想在状态变化时收到电话的人，可以精确地只保留这一项。

**没有所有者的事件不会被静默处理。** 如果一个事件完全没有所有者，通知任务会回退到项目的所有者，因此不会有任何遗漏。每个被通知的人也会被追加到对应的信息流条目中，因此你事后可以准确看到谁在什么时候通过什么地址被告知。
