# 配置与安全

在你把工作流对接到真实流量之前，这一页介绍了值得了解的设置和安全限制。

## 打开或关闭一个工作流

每个工作流在 **设置** 里都有一个 **已启用** 开关。关闭时，工作流不会运行——webhook 调用、计划时间点和 OneUptime 事件全都会被忽略。新建的工作流默认是禁用的。

把这个开关当作你的"准备就绪"闸门来用：

1. 搭建工作流。
2. 在 **生成器** 上用真实的值点击 **运行工作流**。
3. 查看 **日志**——确认每个方块都按你预期的方式走了。
4. 打开 **已启用**。

关闭一个工作流不会停止已经在进行中的运行；它只是阻止新的运行开始。

## 所有者和标签

- **所有者**——被列为所有者的用户和团队会获得该工作流的访问权限，并可以选择在它失败时接收通知。在 **设置 → 所有者** 下设置。
- **标签**——用于给工作流分组的标记。工作流列表允许按标签筛选，这让繁忙的项目更容易导航。当你按团队、集成或环境组织工作流时很有用。
- **标签规则**——在 **工作流 → 设置 → 标签规则** 下，根据名称或描述的模式自动给新工作流打上标签。
- **所有者规则**——在 **工作流 → 设置 → 所有者规则** 下，自动给新工作流分配所有者。

## 密钥

如果一个全局变量包含敏感内容，把它标记为 **secret**。保存之后，这个值在普通的 API 和 UI 读取中会被隐藏，并且工作流日志会在运行日志被持久化之前清除解析出的值。

在以下场景使用密钥变量：

- 外部服务的 API 密钥。
- 身份验证令牌。
- Webhook 签名密钥。
- 任何你不希望只有只读权限的人也能看到的东西。

不要把密钥直接粘贴进方块——像 `Authorization: Bearer eyJh...` 这样的值最终会在工作流和日志里暴露出来。请改用 `{{global.variables.MY_SECRET}}`。

## 导出和导入工作流

你可以把一个工作流以 JSON 文件的形式在项目之间迁移，或者在自托管安装与 OneUptime Cloud 之间迁移。

- **导出**——打开工作流，在 **设置** 下使用 **Export Workflow**。在工作流列表中，你也可以选择多个工作流，把它们导出到同一个文件里。
- **导入**——在 **工作流** 列表上，点击 **Import JSON**，选择一个从任意 OneUptime 项目导出的文件。

这个文件保存了工作流的名称、描述、启用状态和它的图。它刻意不保存：

- **Webhook 密钥。** 工作流被创建时会生成一个全新的密钥，所以导入的工作流会有一个不同的 webhook URL。任何调用原来那个 URL 的东西都需要重新指向新地址。
- **全局变量。** 一个读取 `{{global.variables.MY_SECRET}}` 的方块会保留这个引用，但这个值不在文件里。在运行导入的工作流之前，先在目标项目中创建好这些变量。
- **所有者和标签。** 你项目自己的标签规则和所有者规则会对导入的工作流生效，就像它是你手动创建的一样。

一个导入的工作流总是以 **禁用** 状态被创建，哪怕它在导出的那个项目里是启用的——因为它的图可能指向目标项目中并不存在的监视器、值班策略或其他工作流。先检查它、启用它、用 **运行工作流** 测试它，然后再让它保持打开。复制一个工作流的行为也是一样的，所以在你编辑之前，副本永远不会跟原件一起触发。

因为图是原样传输的，直接输入到方块里的任何东西也会一起传输过去。这就是为什么要把凭据放进密钥变量的实际原因：导出一个硬编码了令牌的工作流，会把这个令牌交给收到这个文件的任何人。

## 一次运行能持续多久

每一次执行尝试都有一个墙钟截止时间。运行器会在每个组件执行前后检查它，一旦控制权返回，就会立即把超时的运行标记为 **Timeout**。执行网络或脚本工作的组件也需要自己的超时，因为运行器无法强制中断任意组件代码。

AI 组件会根据工作流剩余的时间来推算它对提供方请求的超时时间，并把上限设为 60 秒，为日志记录和清理留出一点余量。

## 调用其他工作流的限制

**Execute Workflow** 组件让一个工作流可以调用另一个。为了防止工作流 A 调用 B、B 又调用 A 这样的意外循环，调用链能走多深有一个上限。超过这个限制的运行会以一个明确的错误结束。

如果你确实需要一条很长的调用链（比如一个每次运行处理一个项目的任务），通常用 **Custom Code** 在单个工作流内部循环会更简单。

## Webhook 安全

Webhook 触发器会给你一个专属 URL。任何知道这个 URL 的人都能命中它。为了防范意外或不想要的调用方：

- 把这个 URL 当作密码来对待。不要公开分享它，也不要把它提交到公开仓库里。
- 对于敏感的工作流，要求调用方系统在请求头中发送一个共享令牌（比如 `X-Webhook-Token`），并在做任何重要操作之前用一个 **Conditions** 方块检查它。把预期的令牌保存为一个密钥变量。
- 对于非常敏感的工作流，优先选择 OneUptime 事件触发器和手动导入步骤，而不是公开的 webhook。

## 出站网络访问

API 和其他 HTTP 方块从 OneUptime 发起请求。如果你是自托管，请确保你的安装能够访问你要调用的那些服务。如果你使用 OneUptime Cloud，我们的出站 IP 范围列在 [IP 地址](/docs/configuration/ip-addresses) 中，你可以在对方那边把它们放行。

## AI 组件

**Generate Text with AI** 会通过 OneUptime 配置好的 LLM 网关发送一次请求。它使用项目的默认 LLM 提供商，如果项目没有配置，则使用安装级别的全局提供商。在 **Project Settings → AI → LLM Providers** 下配置提供商；绝不要把提供商的 API 密钥或任意的模型端点直接放进工作流本身。

AI 组件有一个明确的出站边界：

- OneUptime 会向配置好的提供商发送一条固定的组件安全说明，加上解析后的 **System Instructions**、**Prompt** 和序列化后的 **Context**。Context 会附加在用户消息末尾一个明确的标记之后；那条固定说明会声明该标记之后的一切内容都是不可信数据，即便它包含标签或指令也是如此。
- 它不会自动附带触发器载荷、工作流历史、其他组件的输出、项目记录、遥测数据或密钥。只有当你在这三项输入中引用了数据时，数据才会离开。
- 它不会发送任何工具定义或提供方原生的能力字段。模型无法通过这个组件查询 OneUptime、发起 HTTP 请求或修改项目数据。配置好的提供方/模型仍然是一个管理员级别的信任边界，因此要求严格离线生成的安装应当选择一个没有内在提供方托管检索能力的模型。
- 提供方级别的附加参数被限制在一个仅用于生成调优的字段白名单内。它们不能替换工作流消息，不能添加工具或提供方原生的网页搜索/数据源，不能启用非文本模态，不能请求多个候选结果，不能启用流式传输，不能通过提供方存储标志保留请求，也不能提高这个组件的输出令牌上限。未知的未来能力字段会被默认丢弃。
- System Instructions、Prompt、Context 和生成的 Response 值，会在自动工作流执行日志中从这个 AI 组件自身的参数和返回值条目里被打上遮蔽。在运行执行期间，它们对下游组件仍然可用。如果你把其中一个值插入到另一个组件里，那个组件自己的日志策略就会适用，并且可能会记录解析出的值——请把这种复用当作一次明确的披露来对待。提供方/模型名称、令牌计数、LLM Log ID 和安全的错误信息在运维和计费场景下仍然可见。原始的提供方错误正文不会出现在工作流日志、LLM 日志、应用日志和追踪中，因为提供方可能会在其中回显请求内容。

把每一个被引用的变量都当作你有意发送给提供方的数据。尤其是，除非这种披露是必须的且该提供方被批准接收它，否则不要把一个密钥类的全局变量插入到提示词或上下文中。像 Ollama 这样的自托管本地提供方可以把请求留在你自己的基础设施内；一个托管型提供方会按照该提供方自己的数据处理条款来接收这个请求。

每次调用都会记录在 **Project Settings → AI → AI Logs** 中，包括提供方、模型、状态、令牌数、成本和计费信息。提示词和响应的预览以及原始的提供方错误详情不会被存储在 AI 日志里。通过一个计费型全局提供方发起的调用，会消耗项目的 AI 额度余额。工作流 AI 也会计入项目的每日自主 AI 令牌预算；当预算耗尽时，该组件会直接走 **Error** 路径，而不会联系模型。项目 AI 必须已启用。在 OneUptime Cloud 上，订阅必须是付费的，并且需要 Growth 套餐（或包含 Growth 功能的套餐）；关闭了计费的自托管安装没有这个套餐限制。

内置的边界让无人值守的调用保持有限：System Instructions、Prompt 和序列化后的 Context 合计上限为 50,000 个字符；Temperature 必须在 `0` 到 `1` 之间；Maximum Output Tokens 必须在 `1` 到 `4096` 之间（默认 `1024`）；提供方请求只会尝试一次，最多 60 秒后超时。每个项目最多同时运行三个工作流 AI 调用；额外的调用会走 **Error** 路径，可以在之后的工作流运行中重试。校验、配置、访问、预算、余额、并发、提供方和超时方面的失败都会走 **Error** 路径并填充 **Error** 输出。在启用一个生产环境的工作流之前，请先把这条路径连接好。

## 权限

工作流遵循你项目的基于角色的访问控制。相关权限有：

- **Create / Read / Edit / Delete Workflow**——针对工作流本身的基本权限。
- **Run Workflow**——手动运行一个工作流或通过 API 触发一个工作流所需要的权限。
- **Read Workflow Log**——查看运行记录所需要的权限。
- **Read / Create / Edit / Delete Workflow Variable**——对全局变量列表的控制权限。

大多数工程师应该拥有工作流上的创建/编辑/读取权限，但不应该拥有变量上的权限。把变量编辑权限留给管理项目密钥的人。

## 套餐限制

OneUptime Cloud 会在较小的套餐上限制每月的运行次数。你当前的限额显示在 **Project Settings → Billing** 下。达到限额后，新的触发都会被拒绝，直到下一个计费周期。自托管安装没有这个限制。

## 什么时候工作流不是合适的工具

有几种情况你应该改用别的东西：

- **繁重的计算或大规模数据集**——工作流是为轻量级的胶水工作设计的，不是为了数字运算。把繁重的工作放到你自己的基础设施中运行，让工作流去触发它。
- **长时间运行的主动计算**——一次执行尝试应该很快完成。对于像"做 A，等两小时，再做 B"这样被动的延迟，用 **Sleep** 组件；它会把这次运行持久化下来，之后再恢复它，而不会一直占用一个工作进程。
- **有人参与的分步事件响应**——这正是 [Runbook](/docs/runbooks/index) 的用途。工作流是为无人值守的自动化服务的。
