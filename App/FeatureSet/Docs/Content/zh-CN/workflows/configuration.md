# 配置与安全

在把工作流对准真实流量之前，这一页讲的是那些值得先弄清楚的设置和安全限制。

## 打开或关闭一个工作流

每个工作流在 **设置** 里都有一个 **已启用** 开关。关掉它，工作流就不会运行——Webhook 调用、计划的时间点、OneUptime 事件全都会被忽略。新建的工作流一开始是关着的。

把这个开关当成你的"可以上了"闸门：

1. 把工作流搭出来。
2. 用贴近真实的值，在 **生成器** 上点 **运行工作流**。
3. 看 **日志**——确认每个方块都走到了你预期的地方。
4. 把 **已启用** 打开。

关掉一个工作流不会中止已经在跑的运行，它只是不让新的运行再开始。

## 所有者与标签

- **所有者**——列为所有者的用户和团队可以访问这个工作流，并且可以选择在它失败时接收通知。在 **设置 → 所有者** 下设置。
- **标签**——用来给工作流分组的标记。工作流列表可以按标签筛选，项目一忙起来，这会让导航轻松很多。当你按团队、按集成或按环境来组织工作流时特别有用。
- **标签规则**——在 **工作流 → 设置 → 标签规则** 下，根据名称或描述的匹配模式，自动给新工作流打上标签。
- **所有者规则**——在 **工作流 → 设置 → 所有者规则** 下，自动给新工作流指派所有者。

## 密钥

如果一个全局变量里装的是敏感内容，就把它标记为 **密钥**。保存之后，这个值在正常的 API 和界面读取中都会被隐藏，工作流日志也会在运行日志落盘之前把解析出来的值抹掉。

以下这些用密钥变量：

- 外部服务的 API key。
- 认证令牌。
- Webhook 签名密钥。
- 任何你不希望被只读权限的人看到的东西。

不要把密钥直接粘进方块里——像 `Authorization: Bearer eyJh...` 这样的值会明晃晃地留在工作流和日志里。改用 `{{global.variables.MY_SECRET}}`。

## 导出与导入工作流

你可以把一个工作流以 JSON 文件的形式，在项目之间、或者在自托管安装与 OneUptime Cloud 之间搬来搬去。

- **导出**——打开工作流，用 **设置** 下的 **Export Workflow**。在工作流列表里，你也可以勾选多个工作流，一次性导出到同一个文件。
- **导入**——在 **工作流** 列表上点 **Import JSON**，选一个从任意 OneUptime 项目导出的文件。

这个文件里装着工作流的名称、描述、启用状态和它的图。它有意不包含：

- **Webhook 密钥。** 工作流被创建时会重新生成一个，所以导入后的工作流有一个不同的 Webhook URL。原来调用它的东西都得重新指向新地址。
- **全局变量。** 一个引用了 `{{global.variables.MY_SECRET}}` 的方块会保留这个引用，但值并不在文件里。在跑导入的工作流之前，先在目标项目里把这些变量建好。
- **所有者和标签。** 你项目自己的标签规则和所有者规则会对导入的工作流生效，就跟你亲手创建它时一样。

导入的工作流永远是以 **禁用** 状态创建的，哪怕它在导出的地方是开着的——它的图里可能指向了目标项目中并不存在的监视器、值班策略或其他工作流。先审一遍，再启用，用 **运行工作流** 测一测，然后才让它一直开着。复制工作流也是同样的行为，所以在你改完之前，副本绝不会跟着原件一起触发。

因为图是原样搬过去的，任何直接敲进方块里的东西也会跟着走。这就是把凭据放进密钥变量的现实理由：导出一个硬编码了令牌的工作流，等于把那个令牌交给了拿到文件的人。

## 一次运行能跑多久

每一次执行尝试都有一个墙钟时间的截止点。运行器在每个组件之前和之后都会检查它，一旦控制权回到手上，就把超时的运行标记为 **Timeout**。做网络或脚本工作的组件还需要自己的超时设置，因为运行器无法强行打断任意组件的代码。

AI 组件的提供方请求超时是从工作流剩余时间推算出来的，并且封顶在 60 秒，给日志和清理留一点余量。

## 调用其他工作流的限制

**Execute Workflow** 组件让一个工作流可以调用另一个。为了防止工作流 A 调用 B、B 又回头调用 A 这样的意外循环，调用链能走多深是有上限的。超出限制的运行会以一条明确的错误结束。

如果你确实需要很长的调用链（比如一个每次运行处理一项的任务），通常在单个工作流内部用 **Custom Code** 循环会更省事。

## Webhook 安全

Webhook 触发器会给你一个专属 URL。任何知道这个 URL 的人都能访问它。要防住误闯和不想要的调用方：

- 把这个 URL 当密码看待。不要公开分享，也不要提交到公开仓库里。
- 对敏感的工作流，让调用方把一个共享令牌放在请求头里（比如 `X-Webhook-Token`），并在做任何重要的事之前用一个 **Conditions** 方块检查它。把预期的令牌存成密钥变量。
- 对非常敏感的工作流，优先用 OneUptime 事件触发器加一个手动导入步骤，而不是一个公开的 Webhook。

## 出站网络访问

API 和其他 HTTP 方块是从 OneUptime 发出请求的。如果你是自托管，要确保你的安装能访问到你调用的那些服务。如果你用的是 OneUptime Cloud，我们的出站 IP 段列在 [IP 地址](/docs/configuration/ip-addresses) 里，你可以在对端把它们放行。

## AI 组件

**Generate Text with AI** 会通过 OneUptime 配置好的 LLM 网关发出一次请求。它使用项目的默认 LLM 提供方；项目没有默认提供方时，则使用整个安装的全局提供方。提供方在 **项目设置 → AI → LLM 提供商** 下配置；千万不要把提供方的 API key 或者任意模型端点写进工作流本身。

AI 组件有一条明确的出口边界：

- OneUptime 会把一段固定的组件安全指令，连同解析后的 **System Instructions**、**Prompt** 和序列化后的 **Context** 一起发给配置好的提供方。Context 会被追加在用户消息末尾一个明确的标记之后；那段固定指令声明：标记之后的一切都是不可信数据，哪怕其中含有标签或指令也一样。
- 它不会自动附带触发器载荷、工作流历史、其他组件的输出、项目记录、遥测数据或密钥。只有你在上面这三个输入里引用了的数据才会离开。
- 它不发送任何工具定义或提供方原生的能力字段。模型没法通过这个组件查询 OneUptime、发起 HTTP 请求或改动项目数据。配置的提供方/模型仍然属于管理员的信任边界，所以要求生成过程严格离线的安装，应当选择一个不带提供方托管检索能力的模型。
- 提供方层面的附加参数被限制在一份只涉及生成调优的白名单里。它们不能替换工作流消息、不能添加工具或提供方原生的网页搜索/数据源、不能启用非文本模态、不能请求多个候选、不能开启流式、不能通过提供方的存储标志留存请求，也不能抬高这个组件的输出令牌上限。未知的未来能力字段默认会被丢弃。
- System Instructions、Prompt、Context 以及生成的 Response 值，在这个 AI 组件自己在自动工作流执行日志中的参数和返回值条目里都会被脱敏。运行期间它们对下游组件依然可用。如果你把其中之一插进了另一个组件，那就适用那个组件的日志策略，它可能会记录下解析后的值；把这种复用当作一次明确的信息披露来对待。提供方/模型名称、令牌数、LLM Log ID 以及安全的错误消息仍然可见，供运维和计费使用。提供方返回的原始错误正文不会进入工作流日志、LLM 日志、应用日志和链路追踪，因为提供方有可能把请求内容原样回显出来。

把每一个被引用的变量都当成你有意发给提供方的数据。特别是，除非这次披露确有必要且该提供方获准接收，否则不要把密钥类的全局变量插进提示词或上下文里。像 Ollama 这样自托管的本地提供方可以让请求留在你自己的基础设施内；托管的提供方则会按该提供方的数据处理条款接收这个请求。

每次调用都会记录在 **项目设置 → AI → AI 日志** 里，包括提供方、模型、状态、令牌数、成本和计费信息。提示词与响应的预览、以及提供方原始错误详情都不会存进 AI 日志。走计费型全局提供方的调用会消耗项目的 AI 额度余额。工作流 AI 同样计入项目每日的自主 AI 令牌预算；预算耗尽时，组件会直接走 **Error** 路径，不再联系模型。项目 AI 必须处于启用状态。在 OneUptime Cloud 上，订阅必须是付费的，并且需要 Growth 套餐（或包含 Growth 功能的套餐）；关闭了计费的自托管安装没有这道套餐门槛。

内置的边界让无人值守的调用不至于失控：System Instructions、Prompt 和序列化后的 Context 合计上限 50,000 个字符；Temperature 必须在 `0` 到 `1` 之间；Maximum Output Tokens 必须在 `1` 到 `4096` 之间（默认 `1024`）；提供方请求只尝试一次，最长 60 秒后超时。每个项目最多同时跑三个工作流 AI 调用，多出来的调用会走 **Error** 路径，可以由之后的某次工作流运行重试。校验、配置、访问、预算、余额、并发、提供方和超时这些失败，全都会走 **Error** 路径并填充 **Error** 输出。在启用生产工作流之前，先把这条路径接好。

## 权限

工作流遵循你项目的基于角色的访问控制。相关的权限有：

- **创建 / 读取 / 编辑 / 删除工作流**——工作流本身最基本的那几个权限。
- **运行工作流**——手动运行工作流或通过 API 触发工作流所需要的权限。
- **Read Workflow Log**——查看运行记录所需要的权限。
- **读取 / 创建 / 编辑 / 删除工作流变量**——对全局变量列表的控制权。

大多数工程师应该拥有工作流的创建/编辑/读取权限，但不该有变量的权限。把变量的编辑权留给管你项目密钥的那些人。

## 套餐限制

OneUptime Cloud 在较小的套餐上会限制每月的运行次数。你当前的限额显示在 **项目设置 → 账单** 下。用满之后，新的触发会被拒绝，直到下一个计费周期。自托管安装没有这个限制。

## 什么时候工作流不是合适的工具

有几种情况，你该换个别的东西：

- **繁重的计算或大规模数据集**——工作流是为轻量的胶水活儿设计的，不是用来算数的。把重活放在你自己的基础设施里跑，让工作流去把它踢起来。
- **长时间运行的主动计算**——一次执行尝试的设计目标是很快结束。对于"做 A，等两小时，再做 B"这种被动等待，用 **Sleep** 组件；它会把这次运行持久化下来、之后再恢复，而不会一直占着一个工作进程。
- **有人参与的分步事件响应**——这正是 [Runbook](/docs/runbooks/index) 的用武之地。工作流是为无人值守的自动化服务的。
