# 运行与日志

每次工作流运行,OneUptime 都会保存一条记录——什么时候运行的、是否成功,以及每个模块做了什么。这条记录就叫一次 **run**。运行记录是你确认工作流是否正常工作、排查失败原因,以及回看过往活动的依据。

## 在哪里查看

| 页面                        | 你会看到什么                                                                       |
| --------------------------- | ---------------------------------------------------------------------------------- |
| **Workflows → Runs & Logs** | 项目中所有工作流的每一次运行。可以按工作流名称、状态和时间筛选。                    |
| **Workflow → Runs & Logs**  | 仅此一个工作流的运行记录。这里用的是 **Run ID** 筛选器,而不是工作流筛选器。         |
| **单次运行**                | 通过运行行上的 **View Logs** 按钮打开——运行行本身不可点击。                        |

## 运行状态

| 状态                                 | 含义                                                                                                                                             |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Scheduled**                        | 触发器已触发,运行正在排队等待执行器。通常只需要不到一秒。如果排队 5 分钟后仍是这个状态,那就算失败了——没有任何执行器接手它。                        |
| **Running**                          | 工作流正在进行。长时间运行的模块会让运行保持在这个状态。                                                                                            |
| **Waiting**                          | 运行停在一个 **Sleep** 模块上,会自行恢复。等待期间它不占用任何执行器。                                                                              |
| **Executed**                         | 运行顺利跑到了结尾,没有失败。(这是成功状态——状态标签写的是 **Executed**,而不是"Success"。)                                                        |
| **Error**                            | 运行因为某个模块抛出错误而停止。排队后一直没人接手、休眠中的运行丢失了恢复信号、无法解析调度表达式,或者工作流在运行途中被停用,也都会走到这个状态。 |
| **Timeout**                          | 运行时间超过了允许的上限。见 [Configuration & Safety](/docs/workflows/configuration)。                                                              |
| **Execution Exceeded Current Plan**  | 项目在过去 30 天内已用完工作流运行额度,或者订阅未付款。运行会被记录下来,但不会被执行。仅限 OneUptime Cloud。                                        |

一个把控制权交给 **Error** 输出的模块——比如返回 4xx 的 API 模块——并不会让运行失败。错误分支会继续执行,运行最终仍以 **Executed** 结束。不过那一步在图上仍会被标红,方便你找到它。

## 阅读一次运行

点击某次运行上的 **View Logs** 打开它。**Workflow Run** 视图有两个标签页。

**Steps**——每运行过一个模块就有一行,按顺序排列。每一行显示模块的标题、它的 component id、耗时,以及它走出的输出(`→ success`、`→ error`、`→ yes`)。展开一行可以看到两块详情:

- **Received**——模块拿到的设置,已经过所有变量解析。
- **Returned**——它产生的结果。

失败的步骤会标红并默认展开,错误信息打印在 **Received** 上方。

**Full Log**——执行器打印的原始逐行日志,包括模块自己记录的任何内容。当 Steps 视图无法解释失败原因时使用它。

有两个细节值得了解。每个步骤标题下打印的 component id,正是可以直接粘贴进 `{{local.components.<id>.returnValues.…}}` 引用里的那个字符串,这是确认引用写对了最快的方法。另外,一次运行只保留最近 100 步——运行时间很长或反复恢复的运行,会在早期步骤被丢弃的地方显示一条琥珀色提示。

展示出来的值就是模块在变量填充之后看到的值,只有两个例外:密钥以及模块标记为敏感的字段会被隐去,过长的值会被截断并标注"… (truncated)"。

从 **Builder** 启动一次运行,会直接打开这个视图并跟随该运行,这样你可以实时看着它发生,而不用事后再去找它。

## 常见排查

### "我的工作流没运行。"

1. 确认工作流在其 **Overview** 页面上是 **Enabled** 的。新建的工作流默认是停用的,停用的工作流会拒绝所有运行——包括手动触发的。
2. 对于 OneUptime 事件触发器:确认事件确实发生了。打开该记录,查看它的历史。
3. 对于 webhook 触发器:确认对方系统正在向正确的 URL 发送请求。大多数工具会记录它们发出 webhook 的情况——去那里检查。
4. 对于定时触发器:确认 cron 表达式与你预期的时间相符。

如果运行确实出现了,但状态是 **Execution Exceeded Current Plan**,说明项目在过去 30 天内已用完工作流运行额度,或者订阅未付款。运行的日志会写明具体次数和你套餐的上限。这仅适用于 OneUptime Cloud。

### "后面的某个模块没有运行。"

模块没有运行,通常是连线问题。打开 **Builder** 并检查:

- 前一个模块的输出是否连接到了这个模块的输入?
- 前一个模块走的输出是否和你预期的不一样——是 **Error** 而不是 **Success**,或者是 **No** 而不是 **Yes**?Steps 标签页会显示它实际走的是哪一个。

### "某个变量传过来是空的。"

打开该运行,查看失败步骤的 **Received** 区块。

- 如果你看到字面文本 `{{local.components.…}}`,说明引用没有解析。通常是 component id 或返回值 id 拼错了——记住那是模块的 **Identifier**,不是它显示出来的名称。也检查一下 `local.components` 本身的拼写:`{{local.componets.api-get-1.returnValues.response-body}}` 会被原样当作文本发送出去,而运行仍然报告 **Executed**。
- 如果你看到的是空字符串,说明前一个模块运行了,只是没有产生那个字段。

**Full Log** 标签页会有一行警告,点出没能解析的引用,通常是找到它最快的办法。

### "手动运行没问题,但由触发器触发时却不行。"

打开 **Builder**,点击 **Run Workflow**,给触发器的字段填上和真实触发器发送的内容相似的值。然后把这次运行的 **Received** 值和真实运行的值并排比较。差异通常只是一个字段名或类型不同。

## 重新运行一个工作流

没有"重试这次运行"这样的按钮。我们不会自动重跑过去的执行,因为它带来的副作用——Slack 消息、API 调用、工单——重复执行未必安全。要重做这些工作,修复工作流,让下一次真实的触发器触发它;或者打开 **Builder**,用相同的值点击 **Run Workflow**。

## 运行记录会保留多久?

在 OneUptime Cloud 上,运行记录会保留 **30 天** 然后被删除——这就是为什么两个运行列表都说自己覆盖的是最近 30 天。自托管安装会一直保留运行记录,直到你删除它们;如果某个工作流运行非常频繁,把历史记录搞乱了,停用或删除它以停止增加噪音。

在步骤追踪功能上线之前记录的运行没有 **Steps** 内容,只会显示它们的 **Full Log**。
