# Интеграция с Jira

Открывайте задачу в [Jira](https://www.atlassian.com/software/jira) при каждом объявлении инцидента OneUptime, держите её в согласии с ходом инцидента и позвольте Jira возвращать изменения статуса обратно в OneUptime — и всё это одним [рабочим процессом](/docs/workflows/index). Никакого специального блока для Jira ставить не нужно: OneUptime обращается к REST API Jira через [компонент API](/docs/workflows/components#api), а Jira вызывает [триггер Webhook](/docs/workflows/triggers#webhook).

```text
OneUptime Incident → On Create  ──►  API Post (POST /rest/api/3/issue)  ──►  Jira issue

Jira issue transitioned  ──►  Automation rule (Send web request)  ──►  OneUptime Webhook trigger  ──►  Update One Incident
```

Эта страница собирает оба направления. Всё до раздела о входящем направлении написано для **Jira Cloud**; раздел ближе к концу перечисляет, что меняется в **Jira Data Center**.

> Atlassian переименовывает сущности в Jira Cloud: **project** в большей части интерфейса стал **space**, а **issue** — **work item**. Тенанты живут на обоих словарях, поэтому там, где формулировка важна, ниже приведены оба варианта.

## Предварительные требования

- Сайт Jira Cloud (`https://your-domain.atlassian.net`) и проект, в котором будут заводиться задачи. Запомните его **ключ проекта** — это `OPS` в `OPS-1234`.
- Учётная запись Jira, которая может создавать задачи в этом проекте, и **API-токен** для неё со страницы [id.atlassian.com/manage-profile/security/api-tokens](https://id.atlassian.com/manage-profile/security/api-tokens). Заведите служебную учётную запись, а не личную: созданные так задачи приписываются владельцу токена.
- Право создавать правила автоматизации в этом проекте — для входящей половины.
- Проект OneUptime, в котором вы можете создавать рабочие процессы и глобальные переменные.

## Шаг 1 — Сохраните учётные данные Jira как секрет

REST API Jira Cloud принимает **Basic auth**, собранный из адреса электронной почты вашей учётной записи Atlassian и API-токена, закодированных вместе в base64.

1. Закодируйте `email:api_token` один раз:

   ```bash
   printf '%s' 'you@example.com:your_api_token' | base64
   ```

   Используйте `printf`, а не `echo`. `echo` дописывает символ новой строки, он кодируется вместе со всем остальным, и Jira отвечает `401` по причинам, которых не видно во вставленной строке.

2. В OneUptime перейдите в **Рабочие процессы → Глобальные переменные → Создать**. Назовите переменную `JIRA_AUTH`, вставьте строку base64 в поле **Содержимое** и включите **Секрет**.
3. Добавьте вторую, несекретную переменную `JIRA_URL` со значением `https://your-domain.atlassian.net` без завершающей косой черты.

Теперь любой блок может использовать `Basic {{global.variables.JIRA_AUTH}}` в качестве заголовка `Authorization`, а токен никогда не появится ни в рабочем процессе, ни в журналах его запусков. См. [Переменные](/docs/workflows/variables).

Два свойства API-токенов Atlassian, которые рано или поздно подведут интеграцию, за которой никто не следит:

- **У них есть срок жизни.** Токены создаются со сроком от одного дня до одного года, по умолчанию — на год, и обновления не предусмотрено: просроченный токен приходится вручную заменить на той же странице и заново закодировать в `JIRA_AUTH`. Поставьте дату истечения в календарь. Если рабочий процесс, месяцами работавший исправно, вдруг начал отвечать `401`, причина именно в этом.
- **Токену с областями действия нужен другой базовый URL.** На странице токенов есть не только классическая кнопка **Create API token**, но и **Create API token with scopes**. Токены с областями действия безопаснее, но они адресованы не вашему сайту: они идут на `https://api.atlassian.com/ex/jira/<cloudId>`, поэтому `JIRA_URL` становится этим адресом, а все пути ниже подставляются к нему без изменений. Ваш `cloudId` лежит в JSON по адресу `https://your-domain.atlassian.net/_edge/tenant_info`. Токен с областями действия, отправленный на `your-domain.atlassian.net`, просто не сработает.

Если ваша организация использует централизованное управление пользователями Atlassian, есть третий вариант, обходящий проблему истечения срока: [учётные данные OAuth 2.0 для служебной учётной записи](https://support.atlassian.com/user-management/docs/create-oauth-2-0-credential-for-service-accounts/). Он даёт идентификатор клиента и секрет вместо токена, а рабочий процесс обменивает их на короткоживущий токен доступа в начале каждого запуска — та же схема из двух блоков, что и на странице [Microsoft Dynamics 365](/docs/integrations/microsoft-dynamics-365): блок **API Post (JSON)** получает токен, а всё, что идёт после него, отправляет `Bearer <token>`. Ничего не придётся менять вручную год спустя. Точный вид запроса токена есть на странице Atlassian; базовый URL API — `https://api.atlassian.com`.

## Шаг 2 — Открывайте задачу Jira для каждого инцидента

1. Откройте **Рабочие процессы → Создать рабочий процесс**, назовите его `Incidents → Jira` и откройте **Конструктор**.
2. Нажмите на пунктирный блок-заглушку и добавьте триггер **On Create Incident**. В его поле **Select Fields** запросите колонки, которые хотите отправлять:

   ```json
   {
     "_id": true,
     "title": true,
     "description": true,
     "incidentNumber": true,
     "incidentSeverity": { "name": true }
   }
   ```

   Оставьте его **Identifier** равным `incident-on-create-1` — именно по этому имени на него будут ссылаться последующие блоки.

3. Нажмите **Добавить компонент**, добавьте блок **API Post (JSON)** и протяните линию от точки **Success** триггера к точке входа нового блока. Откройте его, задайте **Identifier** значение `create-issue` и заполните:

   - **URL**: `{{global.variables.JIRA_URL}}/rest/api/3/issue`
   - **Request Headers**:

     ```json
     {
       "Authorization": "Basic {{global.variables.JIRA_AUTH}}",
       "Accept": "application/json"
     }
     ```

   - **Request Body**:

     ```json
     {
       "fields": {
         "project": { "key": "OPS" },
         "issuetype": { "name": "Bug" },
         "summary": "OneUptime #{{local.components.incident-on-create-1.returnValues.model.incidentNumber}}: {{local.components.incident-on-create-1.returnValues.model.title}}",
         "labels": ["oneuptime"],
         "description": {
           "type": "doc",
           "version": 1,
           "content": [
             {
               "type": "paragraph",
               "content": [
                 {
                   "type": "text",
                   "text": "{{local.components.incident-on-create-1.returnValues.model.description}}"
                 }
               ]
             }
           ]
         }
       }
     }
     ```

   Замените `OPS` на ключ вашего проекта, а `Bug` — на тип задачи, существующий в этом проекте. И то и другое можно задать по идентификатору — `{"id": "10000"}`, — именно так сделано в примерах самой Atlassian, и именно так стоит поступать, если два типа задач на вашем сайте называются одинаково. Вызовы `createmeta` ниже выдадут вам эти идентификаторы.

Описание выглядит тяжеловесно, потому что API v3 в Jira Cloud принимает форматированный текст в виде **Atlassian Document Format** — дерева документа, а не строки. Показанная выше структура — минимальный корректный документ: один абзац с одним текстовым узлом. То же относится к `environment` и к любому многострочному текстовому пользовательскому полю; однострочные текстовые пользовательские поля по-прежнему принимают обычную строку.

Теперь включите рабочий процесс через **Обзор → Редактировать рабочий процесс → Включено**, объявите тестовый инцидент и откройте **Запуски и журналы**. Блок `create-issue` должен показать `201` и тело с `id`, `key` и `self` новой задачи. Изменения на холсте сохраняются сами — кнопки сохранения нет, а отключённый рабочий процесс не запустится вообще, даже вручную.

Ключ новой задачи доступен любому блоку после этого:

```text
{{local.components.create-issue.returnValues.response-body.key}}
```

### Заполнение дополнительных полей

Несколько типичных добавлений внутрь `fields`:

- **Приоритет** — `"priority": { "id": "20000" }` с идентификатором приоритета из вашего сайта. Чтобы сопоставить уровни серьёзности OneUptime с приоритетами Jira, поставьте между триггером и блоком API блок **If / Else** и ветвитесь по `{{local.components.incident-on-create-1.returnValues.model.incidentSeverity.name}}`.
- **Исполнитель** — `"assignee": { "id": "<accountId>" }`. Jira Cloud опознаёт людей по идентификатору учётной записи Atlassian; `username` и `userKey` убрали из Cloud API много лет назад.
- **Метки** — `"labels": ["oneuptime", "sev1"]`, плоский массив строк. Метки не могут содержать пробелов.
- **Компоненты** — `"components": [{ "id": "10000" }]`.
- **Пользовательские поля** — `"customfield_10034": "..."` с собственным идентификатором поля. Форма значения зависит от типа поля: одиночный выбор принимает `{"value": "red"}`, множественный — массив идентификаторов, многострочное текстовое поле — документ в Atlassian Document Format.

Чтобы узнать, что на самом деле требует проект, спросите об этом Jira, а не гадайте. Получите список типов задач в проекте, а затем поля одного из них:

```bash
curl -u 'you@example.com:your_api_token' \
  'https://your-domain.atlassian.net/rest/api/3/issue/createmeta/OPS/issuetypes'

curl -u 'you@example.com:your_api_token' \
  'https://your-domain.atlassian.net/rest/api/3/issue/createmeta/OPS/issuetypes/10001'
```

Второй вызов перечислит все поля, которые принимает этот тип задачи, укажет, какие из них обязательны, и выдаст точные идентификаторы `customfield_NNNNN`. Чтобы прочитать идентификаторы с уже существующей задачи, запросите её с `?expand=names`.

## Шаг 3 — Перенесите идентификатор инцидента в Jira

Обеим половинам двусторонней синхронизации нужно, чтобы одна система хранила идентификатор другой, и Jira для этого подходит лучше: колонка `customFields` в OneUptime — единый JSON-объект, поэтому запись одного значения из рабочего процесса заменяет все пользовательские поля этого инцидента.

**Если есть администратор Jira.** Добавьте короткое текстовое пользовательское поле — назовите его *OneUptime Incident ID* — на экран создания задачи в проекте, узнайте его идентификатор через `createmeta` и задавайте его вместе со всем остальным:

```json
"customfield_10050": "{{local.components.incident-on-create-1.returnValues.model._id}}"
```

**Если администратора нет.** Положите идентификатор в метку. Метки не допускают пробелов, а идентификатор OneUptime — обычный UUID, поэтому `oneuptime-<id>` является корректной меткой:

```json
"labels": ["oneuptime", "oneuptime-{{local.components.incident-on-create-1.returnValues.model._id}}"]
```

Тогда входящему рабочему процессу придётся выбирать эту метку из списка — это пара строк в блоке **Run Custom JavaScript**. Пользовательское поле аккуратнее, если вы можете его завести.

Раз уж вы здесь, стоит добавить на задачу Jira ссылку обратно на инцидент. Блок **API Post (JSON)** после `create-issue`, направленный на `{{global.variables.JIRA_URL}}/rest/api/3/issue/{{local.components.create-issue.returnValues.response-body.key}}/remotelink`, с телом:

```json
{
  "globalId": "system=https://oneuptime.com&id={{local.components.incident-on-create-1.returnValues.model._id}}",
  "object": {
    "url": "https://oneuptime.com/dashboard/{{local.components.incident-on-create-1.returnValues.model.projectId}}/incidents/{{local.components.incident-on-create-1.returnValues.model._id}}",
    "title": "OneUptime incident #{{local.components.incident-on-create-1.returnValues.model.incidentNumber}}"
  }
}
```

даёт всем в Jira путь обратно в один клик. Для этого добавьте `projectId` в **Select Fields** триггера. Именно `globalId` делает вызов безопасным для повторения: Jira обновляет уже существующую ссылку с этим идентификатором, а не добавляет вторую. И поскольку обновление обнуляет всё, что вы не передали, всегда отправляйте `object` целиком, а не его часть.

## Шаг 4 — Комментируйте и переводите задачу по ходу инцидента

Соберите это **вторым** рабочим процессом, чтобы сбой здесь никогда не помешал открытию задач.

1. **Создать рабочий процесс**, назовите его `Incident updates → Jira` и добавьте триггер **On Update Incident**.
2. В **Listen on** укажите `{"currentIncidentStateId": true}`. Тогда триггер будет срабатывать только на смену состояния, а не на каждое изменение. В **Select Fields** запросите `{"_id": true, "currentIncidentState": {"name": true}}`.
3. Добавьте блок **If / Else**: **Input 1** — `{{local.components.incident-on-update-1.returnValues.model.currentIncidentState.name}}`, **Operator** — `==`, **Input 2** — `Resolved` или то, как называется состояние «разрешён» в вашем проекте. См. [Состояния и уровни серьёзности инцидентов](/docs/incidents/states-and-severities).

Из ветки **Yes** сначала нужно найти задачу, открытую на Шаге 2. Запросите её у Jira по идентификатору, сохранённому на Шаге 3, блоком **API Post (JSON)** с **Identifier** `find-issue`:

- **URL**: `{{global.variables.JIRA_URL}}/rest/api/3/search/jql`
- **Request Body**:

  ```json
  {
    "jql": "project = OPS AND labels = \"oneuptime-{{local.components.incident-on-update-1.returnValues.model._id}}\"",
    "maxResults": 1
  }
  ```

  Если вместо метки вы использовали пользовательское поле, условие превращается в `cf[10050] ~ \"...\"` с идентификатором вашего поля.

Идентификатор задачи после этого — `{{local.components.find-issue.returnValues.response-body.issues[0].id}}`, и все конечные точки ниже принимают идентификатор так же охотно, как и ключ.

Об этой конечной точке стоит знать три вещи. **Отправляйте JQL в теле, а не в URL**: строка запроса, содержащая `=` внутри значения, обрезается по дороге из рабочего процесса, а JQL — это сплошные знаки `=`. **Запрос должен быть ограничен**: голое `order by key desc` отклоняется с `400`, ради этого там и стоит условие `project =`. И `/rest/api/3/search/jql` — актуальная конечная точка: более старая `/rest/api/3/search` объявлена устаревшей и скоро исчезнет, так что за неё браться не надо.

**Комментарий** оставляется одним блоком **API Post (JSON)** на `{{global.variables.JIRA_URL}}/rest/api/3/issue/<id>/comment` с телом в Atlassian Document Format — так же, как описание:

```json
{
  "body": {
    "type": "doc",
    "version": 1,
    "content": [
      {
        "type": "paragraph",
        "content": [{ "type": "text", "text": "Resolved in OneUptime." }]
      }
    ]
  }
}
```

**Перевод задачи** требует двух вызовов, потому что переход опознаётся по идентификатору, который отличается от процесса к процессу, а на некоторых досках — и от задачи к задаче.

1. Блок **API Get (JSON)** на `{{global.variables.JIRA_URL}}/rest/api/3/issue/<id>/transitions` возвращает переходы, доступные *из текущего статуса задачи*, каждый с `id` и `name`, а также с объектом `to`, называющим статус, куда он ведёт.
2. Блок **API Post (JSON)** на тот же URL выполняет один из них:

   ```json
   { "transition": { "id": "31" } }
   ```

Успешный переход отвечает `204` без тела. Если читать список во время выполнения не хочется, вызовите его один раз вручную для задачи в нужном статусе и зашейте идентификатор — только помните, что он привязан к тому процессу, а значит, администратор, редактирующий процесс Jira, может незаметно всё сломать.

## Входящее направление — из Jira в OneUptime

Теперь в обратную сторону: кто-то переводит задачу в Done, и инцидент OneUptime должен последовать за ней.

### Сначала соберите принимающий рабочий процесс

1. **Создать рабочий процесс**, назовите его `Jira → OneUptime` и добавьте триггер **Webhook**.
2. Откройте **Настройки** этого рабочего процесса и скопируйте **секретный ключ вебхука**. Ваш URL:

   ```text
   https://oneuptime.com/workflow/trigger/<webhook secret key>
   ```

   Self-hosted-установки используют собственный хост. Относитесь к этому URL как к паролю — кто им владеет, тот может запустить рабочий процесс, — и сбросьте ключ на той же странице, если он утёк.

3. Добавьте блок **If / Else**, который проверяет общий секрет прежде, чем выполнится что-либо ещё. **Input 1** — `{{local.components.webhook-1.returnValues.request-headers.x-oneuptime-secret}}`, **Operator** — `==`, **Input 2** — `{{global.variables.JIRA_WEBHOOK_SECRET}}`, значение, которое вы придумываете сами и сохраняете как секретную глобальную переменную.
4. Из ветки **Yes** добавьте блок **Update One Incident**:

   - **Query**: `{"_id": "{{local.components.webhook-1.returnValues.request-body.oneuptimeIncidentId}}"}`
   - **Data (JSON Object)**: то, что изменение в Jira должно означать здесь, — обычно смена состояния.

   Для перевода инцидента нужен идентификатор целевого состояния, который выдаст блок **Find One Incident State** с запросом `{"name": "Resolved"}` как `{{local.components.incident-state-find-one-1.returnValues.model._id}}`. Запишите его в `currentIncidentStateId`.

Оставьте рабочий процесс включённым. Теперь дайте Jira, куда обращаться.

### Отправьте событие правилом автоматизации Jira

1. В Jira откройте правила автоматизации проекта: **Space settings → Automation** на более новых тенантах, **Project settings → Automation** на старых. Для правила, охватывающего несколько проектов, используйте **Settings → System → Global automation** — для него нужно глобальное право *Administer Jira*.
2. **Create rule**, выберите триггер **Work item transitioned** — **Issue transitioned** на старых тенантах. Настройте его на срабатывание, когда статус переходит *в* **Done**.

   Используйте именно этот триггер, а не *Work item updated*: триггер обновления намеренно исключает смену статуса.

3. Добавьте действие **Send web request** и настройте его:

   - **Web request URL**: URL вебхука OneUptime из предыдущего раздела.
   - **HTTP method**: `POST`
   - **Headers**: `Content-Type` / `application/json`, а также `X-OneUptime-Secret` / ваш общий секрет. Примените к значению секрета опцию **Hide**, чтобы другие редакторы правил не могли его прочитать, — учтите, что скрытие для этого значения необратимо, а скрытые значения теряются при экспорте или дублировании правила.
   - **Web request body**: **Custom format**, чтобы структура была под вашим контролем:

     ```json
     {
       "oneuptimeIncidentId": "{{issue.customfield_10050}}",
       "issueKey": "{{issue.key}}",
       "summary": "{{issue.summary}}",
       "status": "{{issue.status.name}}"
     }
     ```

     Если на Шаге 3 вы использовали метку вместо пользовательского поля, отправляйте `"labels": "{{issue.labels}}"` и вытаскивайте идентификатор блоком **Run Custom JavaScript** на стороне OneUptime.

4. Включите правило, переведите тестовую задачу в Done и проверьте обе стороны: журнал аудита самого правила в Jira и **Запуски и журналы** в OneUptime.

Что стоит знать, прежде чем на это полагаться:

- **Порт назначения ограничен.** Send web request достигает только портов 80, 8080, 443, 6017, 8443, 8444, 7990, 8090, 8085, 8060, 8900 и 9900. OneUptime Cloud работает на 443; до self-hosted-установки на нестандартном порту таким способом не достучаться.
- **Подписи запроса нет.** У действия нет опции HMAC, поэтому общий секрет в заголовке поверх HTTPS — тот механизм, который документирует Atlassian. Проверка блоком **If / Else** на шаге 3 принимающего рабочего процесса как раз и делает его небесполезным.
- **Запуски правил тарифицируются.** Jira Cloud учитывает успешные выполнения правил в месячной квоте, зависящей от вашего плана: 100 на Free, 1 700 на Standard, 1 000 × число пользователей на Premium, без ограничений на Enterprise. Правило, срабатывающее на каждом переходе в загруженном проекте, набирает быстро.
- **Значения не кодируются для URL** за вас. Это важно, только если вы отправляете тело в формате form-encoded; с JSON выше всё в порядке.
- **Atlassian публикует диапазоны своих исходящих адресов** на [ip-ranges.atlassian.com](https://ip-ranges.atlassian.com) — на случай, если ваша установка OneUptime стоит за списком разрешённых адресов. Диапазоны меняются, поэтому опрашивайте ленту, а не закрепляйте адреса.

### Или используйте вебхук Jira

Администратор Jira может зарегистрировать вебхук напрямую в **Settings → System → Advanced → WebHooks**, выбрав события для отправки и, при желании, запрос JQL, сужающий круг задач, которые его вызывают. По сравнению с правилом автоматизации:

- Полезная нагрузка своя, не ваша: `webhookEvent`, `issue_event_type_name`, полный `issue` и `changelog`, в массиве `items` которого лежат значения «до» и «после» для каждого изменённого поля. Для смены статуса вам нужна запись, где `field` равно `status`. Прочитать это внутри рабочего процесса обычно означает добавить блок **Run Custom JavaScript**.
- Вебхуки **можно** подписывать — задайте вебхуку секрет, и Jira отправит заголовок `X-Hub-Signature` с HMAC тела запроса, — но рабочий процесс не может её проверить. Подпись покрывает ровно те байты, которые отправила Jira, а триггер Webhook отдаёт рабочему процессу тело, уже разобранное в JSON, так что хешировать больше нечего. Если запрос нужно аутентифицировать, используйте правило автоматизации с заголовком, содержащим общий секрет.
- URL должен быть HTTPS на порту из собственного списка Jira, и это *не* тот же список, что у действия автоматизации: порт 80 здесь не допускается.
- Доставка повторяется до пяти раз с задержкой от пяти до пятнадцати минут, поэтому ваш рабочий процесс должен переносить повторное поступление одного и того же события.

Вебхуки, зарегистрированные приложением через `/rest/api/3/webhook`, — совсем другая история: они истекают через 30 дней после регистрации, если их не обновить. Зарегистрированные администратором вебхуки выше не истекают.

## Jira Data Center

Самостоятельно управляемая Jira работает так же с горсткой замен. **Jira Server** перестала поддерживаться в феврале 2024 года и не получает исправлений, поэтому в качестве самостоятельно управляемой цели рассматривайте Data Center.

| Cloud                                             | Data Center                                                                  |
| ------------------------------------------------- | ---------------------------------------------------------------------------- |
| `/rest/api/3/...`                                 | `/rest/api/2/...` — версии v3 в Data Center нет                              |
| `description` как документ Atlassian Document Format | `description` как обычная строка в wiki-разметке                          |
| `Authorization: Basic base64(email:api_token)`    | `Authorization: Bearer <personal access token>`                              |
| API-токен с id.atlassian.com                      | **Profile → Personal access tokens → Create token** в вашей учётной записи Jira |
| Действие автоматизации **Send web request**       | Действие автоматизации **Send outgoing web request**                         |

Итак, блок создания задачи превращается в `POST` на `/rest/api/2/issue` с телом:

```json
{
  "fields": {
    "project": { "key": "OPS" },
    "issuetype": { "name": "Bug" },
    "summary": "OneUptime #123: Checkout is down",
    "description": "Plain text goes straight in here."
  }
}
```

которое проще шаблонизировать — никакого дерева документа.

Другие отличия, которые стоит учесть:

- **Personal access tokens** существуют начиная с Jira Core и Jira Software 8.14 и Jira Service Management 4.15. Они истекают — по умолчанию через 365 дней, — и интерфейс помечает токен как *Expires soon* за пять дней. Basic auth с именем пользователя и паролем в Data Center по-прежнему работает, но несколько неудачных входов включают CAPTCHA, которая полностью закрывает учётной записи доступ к REST API, пока человек не пройдёт её в браузере, — не лучший способ узнать об опечатке. Предпочитайте токен.
- **Автоматизация входит в поставку** начиная с Jira Data Center 10.0. До этого она ставилась отдельным приложением Automation for Jira. У её исходящего запроса таймаут по умолчанию 3000 мс, настраиваемый свойством `outgoing.webhook.timeout.ms`.
- **Вебхуки** регистрируются в **Administration → System → Advanced → WebHooks**, и сужение через JQL поддерживается. Держите эти фильтры узкими: Jira вычисляет JQL каждого зарегистрированного вебхука в том же потоке, который поднял событие, поэтому десяток широких фильтров замедляет само действие пользователя, их вызвавшее.
- **Начиная с Data Center 10.0 доставка вебхуков асинхронная**, синхронного варианта нет, поэтому события могут приходить не по порядку. Сделайте принимающий рабочий процесс идемпотентным.
- **Jira 10 убрала `$` из переменных в URL вебхуков** — `${issue.id}` стало `{issue.id}` — и перенесла REST-ресурс вебхуков с `/rest/webhooks/1.0/webhook` на `/rest/jira-webhook/1.0/webhooks`.

## То же самое для оповещений

Всё написанное выше построено вокруг инцидентов, потому что это самый частый случай, но с оповещениями всё работает точно так же — замените тип записи, и больше ничего не изменится:

| Инцидент                                 | Оповещение                                  |
| ---------------------------------------- | ------------------------------------------- |
| **On Create Incident** (`incident-on-create-1`) | **On Create Alert** (`alert-on-create-1`)   |
| **On Update Incident** (`incident-on-update-1`) | **On Update Alert** (`alert-on-update-1`)   |
| `incidentNumber`, `currentIncidentState`, `incidentSeverity` | `alertNumber`, `currentAlertState`, `alertSeverity` |
| **Find One Incident State**              | **Find One Alert State**                    |
| **Update One Incident**                  | **Update One Alert**                        |

У рабочего процесса ровно один триггер, поэтому под инциденты и оповещения нужно по отдельному рабочему процессу. Если оба делают одно и то же, соберите половину для Jira один раз и вызывайте её из обоих компонентом **Execute Workflow**.

## Устранение неполадок

Сначала откройте отказавший блок в разделе **Запуски и журналы**. Jira возвращает JSON-тело, называющее ровно то, что она отвергла, а компонент API сохраняет его в `response-body`.

**`401 Unauthorized`.** Заново закодируйте `email:api_token` через `printf` и обновите `JIRA_AUTH`; обычная причина — замыкающий символ новой строки от `echo`. Затем убедитесь, что учётная запись — владелец токена может создавать задачи в этом проекте. В Data Center проверьте, что вы отправляете `Bearer`, а не `Basic`.

**`400 Bad Request` с указанием поля.** Такого типа задачи в проекте нет либо в проекте есть обязательное поле, которое вы не отправляете. Выполните приведённые выше вызовы `createmeta` для этого проекта и типа задачи и сравните.

**`400` с жалобой на `description`.** В Cloud v3 описание должно быть документом Atlassian Document Format, а не строкой. Либо отправляйте показанный выше документ, либо переключите этот блок на `/rest/api/2/issue` и отправляйте простой текст.

**`404 Not Found`.** Проверьте базовый URL и версию API: `/rest/api/3/...` в Cloud, `/rest/api/2/...` в Data Center.

**`429 Too Many Requests`.** Jira ограничивает частоту запросов. В ответе приходит `Retry-After` в секундах и `RateLimit-Reason`, называющий, в какой лимит вы упёрлись. Запись в одну задачу ограничена жёстко — порядка двадцати операций за две секунды, — так что рабочий процесс, который быстро подряд комментирует и переводит задачу, может упереться в лимит на одной-единственной задаче. Поставьте между вызовами блок **Delay** или перенесите объёмную работу в рабочий процесс по расписанию.

**Вызов перехода возвращает `400`.** Идентификатор перехода недопустим из *текущего* статуса задачи. Запросите `/transitions` для этой задачи и используйте идентификатор из ответа.

**Правило автоматизации отчитывается об успехе, но в OneUptime ничего не приходит.** Сначала проверьте порт — см. список ограничений выше. Затем отправьте запрос на URL вебхука сами через `curl` и посмотрите, появится ли он в **Запусках и журналах**; если ваш доходит, а запрос Jira — нет, проблема на стороне Jira.

**Рабочий процесс запускается, но инцидент не меняется.** Блок **Update One Incident** сообщает `Items Updated: 0`, когда его запрос ничего не нашёл, и это считается успехом, а не ошибкой. Проверьте, что идентификатор в полезной нагрузке действительно является идентификатором инцидента OneUptime и что вы запрашиваете по `_id`.

**Ссылка вида `{{...}}` появляется в задаче Jira буквально.** Неразрешённая ссылка передаётся дальше как текст, а не обнуляется. Журнал запуска называет каждую ссылку, которая не разрешилась, — обычно это опечатка в идентификаторе блока или переименованная переменная.
