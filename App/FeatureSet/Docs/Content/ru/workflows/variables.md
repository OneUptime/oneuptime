# Переменные

Рабочие процессы — это про движение данных: от триггера в первый блок, от одного блока к следующему и от общих значений — в любое место, где они нужны. Переменные — это то, как данные движутся.

Есть две области видимости переменных, плюс выводы компонентов, создаваемые во время запуска.

## Глобальные переменные

Значения уровня проекта, которые вы сохраняете один раз и переиспользуете где угодно. API-ключи, URL, имена каналов — всё, что не хочется копировать в десяток разных рабочих процессов.

Найдите их в разделе **Workflows → Global Variables**. У каждой есть:

- **Name** — то, как вы будете на неё ссылаться. Минимум два символа, без пробелов, только буквы, цифры, дефисы и подчёркивания. `UPPER_SNAKE_CASE` — хорошая привычка, потому что так переменная выделяется в ваших блоках.
- **Description** — необязательно, произвольный текст, чтобы напомнить себе, для чего она нужна.
- **Secret** — когда включено, значение вычищается из журналов запусков и трассировки шагов.
- **Content** — само значение. Это длинное текстовое поле, так что многострочные значения тоже работают.

Используйте глобальную переменную в любом рабочем процессе так:

```
{{global.variables.NAME}}
```

Например, если вы сохранили ключ PagerDuty как `PAGERDUTY_KEY`, любой блок может использовать его как `{{global.variables.PAGERDUTY_KEY}}` — редактор хранит саму ссылку, а логирование рабочего процесса вычищает разрешённое секретное значение.

Переменные создаются и удаляются, а не редактируются. В таблице нет кнопки редактирования, поэтому чтобы изменить значение в интерфейсе, нужно удалить переменную и создать заново — либо обновить её через API, что описано в конце этой страницы. Глобальные переменные и переменные рабочего процесса — функция плана Growth.

## Локальные переменные рабочего процесса

Переменные в области видимости одного рабочего процесса, управляются в разделе **Workflow Variables** в левом меню этого рабочего процесса. Ссылайтесь на них так:

```
{{local.variables.NAME}}
```

## Выводы компонентов (данные из предыдущих блоков)

Каждый триггер и каждый компонент может производить вывод во время выполнения. Используйте выбор значения компонента (component-value picker) в редакторе, чтобы создать ссылку, а не вводить её вручную — он вставляет точные id, которые ожидает исполнитель.

Сослаться на вывод предыдущего блока можно так:

```
{{local.components.COMPONENT_ID.returnValues.FIELD_ID}}
```

`COMPONENT_ID` — это **Identifier** блока, короткий id, показанный на блоке, а не имя, отображаемое на нём. Новые блоки получают id вроде `api-get-1`, и вы можете переименовать его в разделе **ID** блока. Переименование ломает каждую ссылку, уже указывающую на него, — так же, как и переименование переменной. `FIELD_ID` — это выбранный id возвращаемого значения.

Примеры:

- После того как компонент **API** с ID `lookup-user` отработает, его код статуса — `{{local.components.lookup-user.returnValues.response-status}}`, а тело — `{{local.components.lookup-user.returnValues.response-body}}`.
- После компонента **Run Custom JavaScript** с ID `transform` его возвращённое значение — `{{local.components.transform.returnValues.returnValue}}`.
- Триггеры для типа записи — **On Create Incident** и подобные — возвращают ровно одно значение, `model`, и вы уточняете нужное поле внутри него. Для триггера с ID `incident-on-create-1` заголовок инцидента — `{{local.components.incident-on-create-1.returnValues.model.title}}`.

Локальные переменные существуют только в течение текущего запуска. Каждый новый запуск начинается с чистого листа.

## Где работают переменные

Почти любое текстовое поле принимает переменные:

- URL в блоке API.
- Текст сообщения в Slack, Teams, Discord, Telegram, Email.
- Тема и тело письма.
- Поля заголовков и тела (внутри строковых значений).
- Обе стороны блока **If / Else** (указан в категории Conditions).

В полях JSON переменную можно использовать внутри строкового значения, но не в качестве ключа. Ссылка, которая занимает всё значение целиком, подставляется как есть, так что таким способом можно вставить в поле JSON целый объект. Если нужно собрать структуру динамически, используйте блок **Run Custom JavaScript**, чтобы построить её, а затем передайте его вывод в следующий блок.

Блок **Run Custom JavaScript** не получает переменные автоматически — в песочницу ничего не внедряется. Поместите `{{global.variables.NAME}}` (или любую ссылку на компонент) в поле JSON **Arguments** блока; эти значения подставляются перед выполнением скрипта и приходят как `args`.

## Циклы по массивам

Внутри текстового поля можно перебрать массив с помощью `{{#each path}}…{{/each}}`. Внутри блока `{{property}}` читает поле текущего элемента, `{{@index}}` — это позиция с отсчётом от 0, а `{{this}}` — сам элемент, для массивов простых значений. Имена внутри блока `{{#each}}` обрезаются от пробелов, так что случайные пробелы там безобидны — в отличие от всех остальных случаев.

## Примеры

### Сборка нагрузки из webhook-а

Webhook приходит с телом вида `{ "service": "checkout", "status": "failed" }`. Чтобы превратить это в инцидент OneUptime:

1. Триггер **Webhook** с id `ci-webhook`.
2. Блок **If / Else**: выберите вывод Request Body у webhook-а и используйте его свойство `status`, оператор `==`, справа `failed`.
3. Из ветви **Yes** — блок **Create One Incident** с настройками:
   - Title: `CI build failed: {{local.components.ci-webhook.returnValues.request-body.service}}`
   - Description: `See {{local.components.ci-webhook.returnValues.request-body.url}} for the logs.`

### Использование секрета в API-вызове

Рабочий процесс, который вызывает PagerDuty:

1. Сохраните `PAGERDUTY_KEY` как секретную глобальную переменную.
2. В блоке **API** установите заголовок `Authorization` в `Token token={{global.variables.PAGERDUTY_KEY}}`.

Ключ не попадает ни в рабочий процесс, ни в журналы.

### Цепочка из двух API-вызовов

Первый вызов даёт вам ID, который нужен второму:

1. Компонент **API** `lookup-order`: с помощью пикера вставьте поле JSON email ручного триггера в `GET /orders?email=...`.
2. Компонент **API** `cancel-order`: `POST /orders/{{local.components.lookup-order.returnValues.response-body.id}}/cancel`.

Если `lookup-order` завершится с ошибкой, срабатывает его выход **Error** вместо **Success**. Соедините его с блоком Email или Slack, чтобы ошибки не оставались незамеченными.

## Обновление переменной из рабочего процесса

Частый паттерн — ротация учётных данных по расписанию: получить свежий токен у стороннего сервиса, а затем сохранить его обратно в переменную, чтобы следующий запуск его подхватил. Сделайте это блоком **API**, вызывающим API OneUptime.

`PUT /api/workflow-variable/<variable-id>` с заголовком `ApiKey`, и — вот момент, на котором обычно спотыкаются — поля, которые вы хотите изменить, **обёрнуты в объект `data`**:

```json
{
  "data": {
    "content": "{{local.components.get-token.returnValues.response-body.access_token}}"
  }
}
```

Плоское тело без обёртки `data` отклоняется с ошибкой 400. Отправляйте только те поля, которые действительно хотите изменить; `name` и `description` можно не включать в payload.

API-ключу нужно право **Edit Workflow Variables**. Право на чтение не требуется — обновление не читает строку обратно.

Две вещи, за которыми стоит следить:

- **Не переименовывайте переменную, на которую ссылаетесь.** `name` — часть `{{local.variables.NAME}}`. Изменение имени оставляет каждую существующую ссылку неразрешённой, а неразрешённая ссылка передаётся как буквальный текст — см. подводный камень ниже.
- **Переменную можно записать таким способом, но никогда нельзя прочитать обратно.** `content` доступен только на запись через API для любой переменной, секретной или нет. Именно это делает переменную безопасным местом для хранения ротируемого токена. Пометка «Secret» дополнительно скрывает значение из журналов запусков и трассировки шагов.

## Подводные камни

- **Используйте пикеры.** Они вставляют точные id компонента, возвращаемого значения и переменной, которые ожидает исполнитель, и делают ссылки независимыми от отображаемых меток.
- **Имена переменных чувствительны к регистру.** `{{global.variables.MyKey}}` и `{{global.variables.mykey}}` — это разные переменные.
- **Ссылка, которая не разрешилась, оставляется как есть, а не заменяется пустотой.** Ссылка на то, чего не существует, — это не ошибка, и она не даёт пустую строку: фигурные скобки передаются как есть, поэтому `{{local.components.api-get-1.returnValues.body}}` с опечаткой в id шага в итоге оказывается в вашем сообщении Slack, URL или теле запроса дословно, и запуск всё равно отчитается как **Executed**. В журнале запуска есть предупреждающая строка с именем любой ссылки, которая проскользнула таким образом.
- **Конструктор не может проверить имена переменных.** Он отмечает ссылки на компоненты, которые не может сопоставить, — неизвестный id шага, неизвестное возвращаемое значение, некорректный корень — ещё до сохранения. Но он не может определить, существует ли переменная, поэтому переименованную переменную можно поймать только по журналу запуска.
- **Пробелы внутри фигурных скобок не обрезаются.** `{{ local.variables.NAME }}` — это другой поиск, отличный от `{{local.variables.NAME}}`, и он никогда не разрешается. Единственное исключение — внутри блока `{{#each}}`, где имена обрезаются от пробелов.
