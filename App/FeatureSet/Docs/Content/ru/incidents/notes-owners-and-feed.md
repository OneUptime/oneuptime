# Заметки, владельцы и лента

Пока вы работаете над инцидентом, накапливается письменный след. Часть этого следа — для ваших клиентов: обновление, которое в 02:14 уходит на страницу статуса и сообщает, что вы нашли неудачный деплой. Остальное — для вашей команды: стек-трейс, который кто-то вставил, график, который наконец сложился в картину, решение о переключении на резерв.

OneUptime разделяет эти две аудитории. **Публичные заметки** публикуются на странице статуса и могут уведомлять подписчиков. **Приватные заметки** (модель `IncidentInternalNote`) остаются внутри панели управления. Под ними обеими лежит **лента инцидента** — хронология только для добавления, которая фиксирует всё, что произошло с инцидентом, — и список **владельцев**, который решает, кому сообщать.

Всё это находится в левом боковом меню инцидента: **Заметки → Публичные заметки**, **Заметки → Приватные заметки** и **Команда → Владельцы**. Лента находится на странице **Обзор** инцидента.

## Публичные заметки против приватных

Оба типа заметок выглядят похоже в панели управления, но ведут себя очень по-разному.

- **Публичные заметки** — модель `IncidentPublicNote`, отдаётся на страницы статуса как часть хронологии инцидента. У них есть дата **Опубликовано в**, которую можно задать самостоятельно, и флажок **Уведомить подписчиков страницы статуса**.
- **Приватные заметки** — модель `IncidentInternalNote`. Приложение страницы статуса их вообще не читает. У них нет поля даты публикации (список проставляется и сортируется по `createdAt`) и нет вообще никаких полей для подписчиков, поэтому приватная заметка никогда не может вызвать уведомление подписчика.

**Что на самом деле означает «приватная».** Это означает «не опубликовано на странице статуса», а не «доступно ограниченному кругу людей». Оба типа заметок используют одни и те же права на чтение, поэтому любой, кто может читать инцидент, может читать и его приватные заметки. Если вам нужно ограничить, кто вообще видит инцидент, используйте флаг **Приватный инцидент** (`isPrivate`) на самом инциденте — он скрывает инцидент со всех страниц статуса и ограничивает доступ пользователями-владельцами, участниками команд-владельцев, а также администраторами и владельцами проекта.

**Владельцы видят и то, и другое.** Задача уведомления владельцев запрашивает публичные и приватные заметки вместе. Приватная заметка приватна от ваших подписчиков, но не от тех, кто реагирует на инцидент.

| Если вы хотите…                                                  | Выберите          |
| ------------------------------------------------------------------ | ---------------- |
| Сообщить клиентам, что вам известно и когда появятся подробности   | **Публичная заметка**  |
| Задним числом зафиксировать обновление, уже отправленное где-то ещё | **Публичная заметка**  |
| Записать гипотезу, выполненную команду или тупиковую версию         | **Приватная заметка** |
| Приложить дамп памяти или скриншот внутренней панели                | **Приватная заметка** |

## Публикация публичной заметки

Откройте **Заметки → Публичные заметки** в боковом меню инцидента и создайте заметку. Карточка объясняет, что написанное здесь появится на странице статуса; пустое состояние сообщает, что для этого инцидента пока не создано ни одной публичной заметки.

| Поле                                | Назначение                                                                                                             |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| **Public Incident Note**             | Текст в Markdown. Обязательно. Форма напоминает, что заметка видна на странице статуса, и даёт ссылку на шпаргалку.  |
| **Attachments**                      | Файлы, доступные подписчикам на странице статуса. Необязательно.                                                     |
| **Notify Status Page Subscribers**   | Флажок, по умолчанию включён. Отключите его, чтобы опубликовать заметку тихо.                                        |
| **Posted At**                        | Обязательные дата и время, по умолчанию текущий момент, показываются в вашем текущем часовом поясе.                  |

**Posted At — это настоящая временная метка заметки.** Страницы статуса сортируют и показывают публичные заметки по `postedAt`, а не по времени набора текста — поэтому, если вы догоняете страницу статуса обновлением, отправленным 40 минут назад, установите **Posted At** на момент, когда это действительно произошло. Если заметка приходит через API без этого поля, OneUptime проставляет текущее время.

Список показывает, кто написал каждую заметку, её **Posted At**, отрисованный Markdown с вложениями и столбец **Subscriber Notification Status**. Можно фильтровать по **Created By**, **Note** и **Created At**.

## Публикация приватной заметки

**Заметки → Приватные заметки** намеренно проще. Здесь только два поля:

- **Private Incident Note** — текст в Markdown, обязательно. Форма прямо говорит, что это приватно для вашей команды и не видно на странице статуса.
- **Attachments** — файлы для команды реагирования на инцидент.

Нет ни **Posted At**, ни флажка подписчиков — заметка проставляется временем в момент создания.

## Вложения в заметках

Оба типа заметок принимают файловые вложения через поле **Attachments**, и оба отрисовывают список вложений под текстом заметки со ссылкой **Download attachment** для каждого файла.

Различие в том, кто может скачать файл:

- **Вложения публичных заметок** доступны для скачивания посетителям страницы статуса через маршрут страницы статуса, вместе с самой заметкой.
- **Вложения приватных заметок** доступны только через API панели управления с аутентификацией. Маршрута для них на странице статуса нет.

Это делает вложения тем же решением «публично/приватно», что и текст заметки. Изображение хронологии для клиентов идёт в публичную заметку; дамп конфигурации — в приватную.

## Генерация заметки с помощью ИИ

На обеих страницах заметок есть кнопка **Generate with AI**. Она отправляет инцидент вашему ИИ-провайдеру проекта и вставляет сгенерированный Markdown в редактор заметки, где вы можете отредактировать его перед сохранением — ничего не публикуется автоматически.

- **Generate Public Note with AI** — описывается как анализ данных инцидента для создания заметки, ориентированной на клиента. Шаблоны включают **Status Update** и **Resolution Notice**.
- **Generate Private Note with AI** — вместо этого создаёт внутреннюю техническую заметку. Шаблоны включают **Investigation Update** и **Technical Analysis**.

За кнопкой стоит запрос панели управления к `/incident/generate-note-from-ai/{incidentId}` с выбранным шаблоном и типом заметки `public` или `internal`.

## Шаблоны заметок

Если ваша команда пишет одни и те же три обновления при каждом сбое, сохраните их один раз. На обеих страницах заметок есть кнопка **Create from Template**, открывающая выбор **Create Note from Template** с выпадающим списком **Select Note Template**.

Шаблоны общие для публичных и приватных заметок: один список шаблонов обслуживает оба типа, и один и тот же шаблон можно вставить в заметку любого вида.

Управлять ими можно в **Инциденты → Настройки → Шаблоны заметок** — карточка называется **Public or Private Note Templates for Incidents**, а её форма имеет шаг **Template Info** (**Template Name** и **Template Description**, оба обязательны) и шаг **Note Details** для текста. Если нажать **Create from Template** до того, как создан хотя бы один шаблон, OneUptime сообщит, что их пока нет; учтите, что сообщение указывает на Project Settings, но страница на самом деле находится в **Инциденты → Настройки → Шаблоны заметок**.

## Публикация заметок из Slack или Microsoft Teams

Если вы подключили рабочее пространство, реагирующим не нужно покидать канал. И Slack, и Microsoft Teams предоставляют действие добавления заметки, которое открывает модальное окно с выпадающим списком **Public Note** или **Private Note** и текстовым полем, и записывает результат прямо в инцидент.

Стоит знать две детали:

- **Защита от дублирования** — каждая заметка сохраняет сообщение Slack, из которого она возникла (`postedFromSlackMessageId`, в формате `channel_id:message_ts`), поэтому несколько человек, отреагировавших на одно и то же сообщение, создают одну заметку, а не пять.
- **Заметки отражаются обратно** — публикация заметки любого типа также отправляет сообщение в подключённый канал инцидента, потому что элемент ленты для заметки создаётся с включёнными уведомлениями рабочего пространства.

## Когда публичная заметка действительно доходит до подписчиков

Создание публичной заметки с включённым **Notify Status Page Subscribers** само по себе не гарантирует, что письмо уйдёт. Заметка должна пройти цепочку проверок, и каждый отказ фиксируется с конкретной причиной, а не выдаёт ошибку:

1. **Notify Status Page Subscribers** должен быть включён. Если нет, заметка помечается как пропущенная в момент создания.
2. Заметка должна принадлежать инциденту, который всё ещё существует.
3. К инциденту должен быть прикреплён хотя бы один монитор — без мониторов нет ресурса страницы статуса, на который можно направить заметку.
4. Флаг **Visible on Status Page** (`isVisibleOnStatusPage`) инцидента должен быть истинным.
5. На каждой странице статуса, до которой доходит инцидент, должен быть включён **Show Incidents** (`showIncidentsOnStatusPage`).
6. Каждый подписчик должен пройти собственные настройки — не быть отписанным и быть подписанным на этот ресурс и на тип события `Incident`, если страница позволяет подписчикам выбирать.

**Уведомления приходят не мгновенно.** Задача, которая их отправляет, запускается раз в минуту, поэтому между сохранением заметки и уходом письма может пройти до минуты. Именно это означает метка **Sending Soon**.

Столбец **Subscriber Notification Status** отслеживает весь путь:

| Статус                        | Что это означает                                          |
| ------------------------------ | ------------------------------------------------------ |
| **Notifications skipped.**     | Один из шлюзов выше закрылся. Причина зафиксирована.    |
| **Sending Soon**               | В очереди, ожидает следующего запуска задачи отправки.  |
| **Notifications Being Sent**   | Задача проходит по списку подписчиков.                  |
| **Notifications Sent**         | Все уведомления подписчикам отправлены.                 |
| **Failed**                     | Задача завершилась с ошибкой; ошибка сохранена вместе с заметкой. |

Нажмите **more details** у статуса, чтобы открыть **Notification Status Details**. Там, где повторная отправка имеет смысл, в этом модальном окне есть кнопка **Retry**, которая возвращает заметку в состояние ожидания, чтобы её подхватил следующий запуск.

Само сообщение, которое получают подписчики, шаблонизировано отдельно для каждой страницы статуса и канала — у email, SMS, Slack и Microsoft Teams есть собственный шаблон для события **Subscriber Incident Note Created**, с переменными для названия и URL страницы статуса, ссылки на подробности, затронутых ресурсов, серьёзности и заголовка инцидента, текста заметки и персональной ссылки для отписки. О том, как настраиваются эти шаблоны и каналы, — в [Подписчики и объявления](/docs/status-pages/subscribers).

## Лента инцидента

Карточка **Incident Feed** находится внизу левой колонки на странице **Обзор** инцидента. Это история инцидента по порядку: каждый элемент — это иконка, аватар и имя того, кто его вызвал, относительная временная метка с точным местным временем при наведении, и текст в Markdown. Элементы отсортированы от самых старых.

Некоторые элементы содержат дополнительные детали — например, уведомление владельцев перечисляет всех, кому было отправлено письмо. У таких элементов есть кнопка **More Information**, открывающая панель **More Information**.

В шапке карточки также есть меню **Actions**, позволяющее действовать, не покидая хронологию:

- **Execute Runbook** — запустить [runbook](/docs/runbooks/index) для этого инцидента.
- **Execute On-Call Policy** — вызвать дежурного по требованию.
- **Add Public Note** — те же четыре поля, что и на странице публичных заметок, в модальном окне.
- **Add Private Note** — только текст заметки и вложения.

Рядом — **Refresh**, повторно загружающая ленту.

**Лента доступна только для добавления и не является журналом аудита.** API позволяет создавать и читать элементы ленты, но не обновлять и не удалять их, поэтому никто не может незаметно переписать историю инцидента. Она также не бессрочна: на платных инсталляциях строки ленты старше трёх лет удаляются. Для устойчивой записи о том, кто что изменил, используйте **Audit → Audit Logs** в боковом меню инцидента.

## Что фиксирует лента

Элементы ленты записываются самим сервисом инцидентов, обоими сервисами заметок, хронологией состояний, изменениями владельцев и участников, движками правил, выполнением дежурств, исполнителями ИИ-расследования и постмортема, а также cron-задачами уведомлений. Типы событий охватывают:

- **Сам инцидент** — `IncidentCreated`, `IncidentUpdated`, `IncidentStateChanged`.
- **Заметки и записи** — `PublicNote`, `PrivateNote`, `RootCause`, `RemediationNotes`, `PostmortemNote`.
- **Люди** — `OwnerUserAdded`, `OwnerTeamAdded`, `OwnerUserRemoved`, `OwnerTeamRemoved`, `IncidentMemberAdded`, `IncidentMemberRemoved`.
- **Уведомления** — `OwnerNotificationSent`, `SubscriberNotificationSent`, `OnCallPolicy`, `OnCallNotification`.
- **Автоматизация** — `LabelRuleExecuted`, `OwnerRuleExecuted`, `PrivacyRuleExecuted`, `OnCallRuleExecuted`, `AutoRemediation`.

У каждого типа своя иконка, поэтому в длинной ленте легко выделить смены состояния среди прочего шума. ИИ-анализ первопричины отмечается особо и отрисовывается в ограниченном режиме Markdown.

Лента учитывает приватность инцидента: для приватных инцидентов чтение ленты фильтруется так же, как и сам инцидент.

## Владельцы

Владельцы — это люди и команды, ответственные за инцидент. Они являются целью уведомлений обо всём, что с ним происходит, — и именно поэтому инцидент не остаётся незамеченным, пока все думают, что им занимается кто-то другой.

Откройте **Команда → Владельцы** в боковом меню инцидента. Карточка **Владельцы** показывает счётчик и описывает владельцев как людей и команды, ответственных за этот инцидент, которые уведомляются об изменениях, с текущим счётчиком вида «2 people · 1 team». Владельцы отображаются в виде накладывающихся аватаров; при наведении на аватар показывается email человека или отметка **Команда**.

- Нажмите **Добавить владельца**, чтобы открыть выбор с полем поиска для людей или команд.
- Нажмите на элемент удаления на аватаре, чтобы открыть подтверждение **Удалить владельца**, затем **Удалить**.
- Если владельцев ещё нет, карточка сообщает об этом и предлагает добавить коллегу или команду, чтобы они получали уведомления об изменениях.

Пользователи-владельцы и команды-владельцы — отдельные записи: добавление команды делает каждого её участника владельцем для целей уведомления, не перечисляя их по отдельности.

## Как владельцы назначаются

Есть четыре пути попадания в список владельцев:

- **Из шаблона инцидента** — шаблоны содержат поля **Owner - Teams** и **Owner - Users**, описанные как команды и пользователи, владеющие инцидентом и получающие уведомления при его создании или обновлении. Создание инцидента из шаблона предзаполняет их. См. [Объявление инцидента](/docs/incidents/declaring-incidents).
- **Из правил владельцев инцидента** — совпавшие правила автоматически добавляют владельцев в момент создания.
- **При создании через API** — пользователи-владельцы и команды-владельцы, переданные при вызове создания, добавляются немедленно, с флагом, управляющим тем, получат ли они письмо «вас добавили».
- **Вручную** — элемент управления **Добавить владельца** на странице **Владельцы**, в любой момент существования инцидента.

Добавить одного и того же человека дважды безопасно; уже назначенные владельцы не дублируются.

## Правила владельцев инцидента

**Incident Owner Rules** автоматически назначают пользователей-владельцев и команды-владельцы при создании подходящих инцидентов — это слой маршрутизации, из-за которого инцидент базы данных попадает к команде баз данных без чьего-либо участия. Вы найдёте их вместе с остальной автоматизацией инцидентов в [Настройках и автоматизации инцидентов](/docs/incidents/settings).

Форма правила состоит из трёх шагов — **Basic Info**, **Match Criteria** и **Владельцы** — и шаг владельцев содержит два раздела:

- **Owners to Assign** — выберите **Owner Teams** и **Owner Users**. Когда правило срабатывает, каждый выбранный пользователь и команда добавляются как владельцы, а уже назначенные владельцы не дублируются.
- **Inherit Owners** — назначает владельцев от связанных сущностей вместо явного указания. **Inherit Owners From Monitors** делает каждого владельца мониторов инцидента владельцем самого инцидента, а **Inherit Owners From Hosts**, **… From Kubernetes Clusters**, **… From Docker Hosts**, **… From Podman Hosts** и **… From Services** делают то же самое для соответствующих ресурсов.

Переключатель **Notify Owners** определяет, узнают ли люди об этом. Оставьте его включённым для реальной маршрутизации; выключите, чтобы добавлять владельцев тихо — это полезно, когда правило служит скорее учётным целям, чем оповещению.

Каждое срабатывание правила записывается в ленту инцидента, поэтому всегда можно понять, был ли человек добавлен правилом или вручную.

## О чём уведомляются владельцы

Пять задач уведомляют владельцев, каждая запускается раз в минуту:

- **Инцидент создан** — тема письма `[New Incident {number}] - {title}`.
- **Опубликована заметка** — как для публичных, *так и* для приватных заметок, тема `[Update Incident {number}] - {title}`.
- **Изменилось состояние инцидента** — см. [Состояния и уровни серьёзности инцидентов](/docs/incidents/states-and-severities).
- **Вас добавили как владельца** — тема `You have been added as the owner of Incident {number} - {title}`.
- **Всё ещё не устранён** — напоминание, управляемое временем следующего напоминания инцидента, тема `[Reminder] Incident {number} is still {state} - {title}`.

Каждое уведомление формируется для email, SMS, голосового звонка, push и WhatsApp и передаётся настройкам уведомлений пользователя, которые решают, что реально будет отправлено. Каждый получатель может отключить любое из этих уведомлений по отдельности — персональные настройки описаны как отправка уведомлений о создании инцидента, публикации заметки, смене состояния, добавлении владельца, назначении участника и напоминании об открытом инциденте. Тот, кто хочет получать только звонок при смене состояния, может настроить именно это.

**Инциденты без владельцев не остаются без внимания.** Если у инцидента вообще нет владельцев, задачи уведомления обращаются к владельцам проекта, поэтому ничего не теряется. Каждый уведомлённый человек также добавляется в соответствующий элемент ленты, поэтому позже можно точно увидеть, кому и на какой адрес сообщили.
