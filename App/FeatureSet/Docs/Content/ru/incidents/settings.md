# Настройки и автоматизация

Настройка инцидентов находится не в Project Settings. Она находится внутри самой продуктовой области Инцидентов, в разделах **Инциденты → Настройки** и **Инциденты → Правила**, по маршрутам, начинающимся с `/dashboard/{projectId}/incidents/settings/`. Если вы искали шаблоны инцидентов или пользовательские поля в **Project Settings**, вот почему вы их не нашли.

Разделы **Rules** и **Settings** бокового меню Инцидентов по умолчанию свёрнуты, поэтому их нужно развернуть, прежде чем появятся перечисленные ниже пункты. Всё здесь привязано к проекту: шаблоны, роли, пользовательские поля и правила принадлежат одному проекту и применяются к каждому инциденту, объявленному в нём.

Эта страница — справочник по такой настройке: что содержит каждая страница и что из этого срабатывает автоматически в момент создания инцидента.

## Где находятся настройки инцидентов

Откройте **Инциденты** в левой навигации, затем разверните **Settings** внизу бокового меню.

| Страница                 | Что вы там делаете                                                                             |
| ------------------------ | ---------------------------------------------------------------------------------------------- |
| **Incident State**       | Добавление, переименование, изменение цвета и порядка состояний, через которые проходит инцидент. |
| **Incident Severity**    | Добавление, переименование, изменение цвета и порядка уровней серьёзности.                     |
| **Incident Templates**   | Предзаполнение целого инцидента — заголовок, описание, ресурсы, политики дежурства, владельцы, метки. |
| **Note Templates**       | Многоразовый текст для публичных и приватных заметок.                                          |
| **Postmortem Templates** | Многоразовые структуры постмортема.                                                            |
| **Custom Fields**        | Определение дополнительных полей, которые появляются на каждом инциденте.                      |
| **Incident Roles**       | Определение ролей, на которые вы назначаете реагирующих, например Incident Commander.          |
| **More Settings**        | Префиксы номера инцидента и номера эпизода инцидента.                                          |

**Incident State** и **Incident Severity** подробно разобраны в [Состояниях и уровнях серьёзности инцидентов](/docs/incidents/states-and-severities) — остальная часть этой страницы продолжает с **Incident Templates**.

Разверните **Rules**, и вы получите ещё восемь страниц: **Grouping Rules**, **On-Call Rules**, **Owner Rules**, **Runbook Rules**, **Privacy Rules**, **Label Rules**, **SLA Rules** и **Reminder Rules**. Они разобраны дальше.

## Шаблоны инцидентов

Шаблон инцидента — это сохранённый скелет инцидента. Вместо того чтобы каждый раз заново набирать один и тот же заголовок, один и тот же список мониторов и одну и ту же политику дежурства, когда кластер платежей начинает шататься, вы сохраняете это один раз и объявляете инциденты из шаблона.

Перейдите в **Инциденты → Настройки → Шаблоны инцидентов** (`/dashboard/{projectId}/incidents/settings/templates`). Карточка называется **Incident Templates**. Создание проводит вас через мастер из шести шагов:

- **Template Info** — **Template Name** и **Template Description**. Они называют сам шаблон и никогда не появляются на инциденте.
- **Incident Details** — **Title**, **Description** (Markdown), **Incident Severity** и **Initial Incident State**. **Initial Incident State** необязателен и по умолчанию пуст; его варианты перечислены в порядке состояний. Оставьте пустым, и инциденты из этого шаблона попадут в состояние создания проекта.
- **Resources Affected** — мониторы, хосты, кластеры и сервисы, к которым должен быть привязан инцидент, а также **Change Monitor Status to**.
- **On-Call** — **On-Call Policy**, политики, которые выполняются при объявлении инцидента, созданного из этого шаблона.
- **Owners** — **Owner - Teams** и **Owner - Users**.
- **Labels** — **Labels**.

Несколько быстрых правил:

- Список шаблонов показывает только **Name** и **Description**. Строки нельзя редактировать или удалять прямо из списка — откройте шаблон (`/dashboard/{projectId}/incidents/settings/templates/{modelId}`), чтобы изменить его.
- Шаблоны поддерживают импорт и экспорт JSON, поэтому можно переносить их между проектами.
- Пустое состояние гласит: «No incident templates found.».

### Как применяется шаблон

Есть два пути, и оба ведут себя одинаково.

- **Из панели управления** — кнопка **Create from Template** в списке инцидентов открывает выбор **Select Incident Template**, а страница объявления считывает шаблон из параметра строки запроса `incidentTemplateId`, после чего предзаполняет форму шаблоном вместе с его командами-владельцами и пользователями-владельцами.
- **Из API** — передайте `createdIncidentTemplateId` в `POST /api/incident`, и сервер заполнит инцидент из шаблона.

Важная часть — правило слияния: **шаблон заполняет только то поле, которое вы оставили неопределённым**. Заголовок, описание, серьёзность инцидента, начальное состояние инцидента, статус монитора за **Change Monitor Status to**, мониторы, хосты, кластеры Kubernetes, хосты Docker, хосты Podman, сервисы, политики дежурства и метки копируются из шаблона только тогда, когда вызывающий код или форма ничего не передали. Всё, что вы задали явно, всегда побеждает.

**Диалог пустого состояния указывает не туда.** Если у вас ещё нет шаблонов, кнопка **Create from Template** показывает диалог **No Incident Templates**. Его текст указывает на Project Settings, но сама кнопка ведёт в **Инциденты → Настройки → Шаблоны инцидентов** — это и есть настоящее расположение.

## Шаблоны заметок

Шаблоны заметок дают реагирующим готовый текст для обновлений по инциденту, поэтому обновление на странице статуса в 3 часа ночи не пишется с нуля кем-то полусонным.

Перейдите в **Инциденты → Настройки → Шаблоны заметок** (`/dashboard/{projectId}/incidents/settings/note-templates`). Карточка называется **Public or Private Note Templates for Incidents** — одна библиотека обслуживает оба типа заметок. Форма создания состоит из двух шагов:

- **Template Info** — **Template Name** и **Template Description**, оба обязательны.
- **Note Details** — сам текст заметки, в Markdown, обязательно.

Как и шаблоны инцидентов, строки создаются и просматриваются, а не редактируются прямо в списке; откройте шаблон, чтобы изменить его.

Шаблоны заметок всплывают именно там, где они нужны: диалоги подтверждения **Acknowledge Incident** и **Resolve Incident** оба предлагают **Select Note Template** рядом с полем **Public Note**. О том, чем отличаются публичные и приватные заметки, — в [Заметки, владельцы и лента инцидента](/docs/incidents/notes-owners-and-feed).

## Шаблоны постмортема

Шаблон постмортема — это скелет разбора, который вы готовите после инцидента: ваши заголовки, ваши подсказки, ваши постоянные вопросы, — поэтому каждый разбор в проекте следует одной и той же форме.

Перейдите в **Инциденты → Настройки → Шаблоны постмортема** (`/dashboard/{projectId}/incidents/settings/postmortem-templates`). Карточка называется **Postmortem Templates**. Форма создания состоит из двух шагов:

- **Template Info** — **Template Name** и **Template Description**, оба обязательны.
- **Postmortem Details** — **Postmortem Template**, сам текст, в Markdown, обязательно.

Применяете вы шаблон из инцидента, а не из настроек. Откройте инцидент, выберите **Postmortem** в его боковом меню (`/dashboard/{projectId}/incidents/{incidentId}/postmortem`) и используйте **Apply Template**. Откроется диалог **Apply Postmortem Template** с выпадающим списком **Select Template**; выбор шаблона загружает его текст в редактор **Postmortem Note**, где вы редактируете его перед сохранением. У эпизодов инцидентов есть та же страница **Postmortem**, и они опираются на ту же библиотеку шаблонов.

## Пользовательские поля

Пользовательские поля позволяют нести собственные метаданные на каждом инциденте — внутреннее название сервиса, ссылку на заявку на изменение, уровень клиента.

Перейдите в **Инциденты → Настройки → Пользовательские поля** (`/dashboard/{projectId}/incidents/settings/custom-fields`). Страница называется **Incident Custom Fields**. У каждого определения есть:

- **Field Name** — обязательно, минимум два символа. Подсказка предлагает имя в стиле слага, например `internal-service`.
- **Field Description** — необязательно.
- **Field Type** — обязательно. Определяет, как вводятся данные. Типы с выпадающим списком также требуют перечисления вариантов.
- **Dropdown Options** — значения, которые появляются в выпадающем списке, каждое с необязательным цветом.

Определения живут в собственной модели; значения хранятся на самом инциденте, в столбце `customFields`. На отдельном инциденте вы заполняете их в разделе **Custom Fields** бокового меню инцидента (`/dashboard/{projectId}/incidents/{incidentId}/custom-fields`).

**Один нюанс, о котором стоит знать.** Определения пользовательских полей инцидента — единственная часть семейства инцидентов без триггеров рабочих процессов — см. раздел о рабочих процессах ниже.

## Роли инцидента

Роли инцидента — это именованные обязанности, на которые вы назначаете людей во время реагирования. Определите их в **Инциденты → Настройки → Роли инцидента** (`/dashboard/{projectId}/incidents/settings/roles`); описание карточки приводит в пример Incident Commander и Responder.

Роли — это только определения. Людей на них вы назначаете по каждому инциденту отдельно — мастер объявления имеет шаг **Incident Roles** с полем **Assign Incident Roles**, и у каждого инцидента есть страница **Roles** в боковом меню.

## Префиксы номеров

Каждый инцидент получает номер. По умолчанию он отображается как `#42`. Если ваша команда произносит вслух «INC-42», пусть продукт тоже так говорит.

Перейдите в **Инциденты → Настройки → More Settings** (`/dashboard/{projectId}/incidents/settings/more`). Карточка называется **Number Prefix** и содержит два поля на уровне проекта:

- **Incident Number Prefix** — до 20 символов, подсказка `INC-`. Задайте его, и инцидент `#42` будет отображаться как `INC-42`.
- **Incident Episode Number Prefix** — та же идея для номеров эпизодов инцидентов, подсказка `IE-`.

Оставьте любое поле пустым, чтобы сохранить префикс по умолчанию `#`; незаполненное поле показывает `# (default)`. Сохраните кнопкой **Update**. Значение с префиксом хранится на инциденте как `incidentNumberWithPrefix` — именно его отображают список инцидентов и заголовок инцидента.

## Правила, которые срабатывают при создании инцидента

**Инциденты → Rules** содержит восемь движков правил. Все они делают одно и то же — смотрят на инцидент в момент создания и действуют, если он совпадает, — но различаются тем, что именно делают и как разрешают конфликт нескольких совпавших правил.

- **Grouping Rules** — группируют связанные инциденты в эпизоды. Правила оцениваются в порядке приоритета; меньшие номера приоритета идут первыми.
- **On-Call Rules** — выполняют политики дежурства для подходящих инцидентов. Подробно разобраны ниже.
- **Owner Rules** — автоматически назначают владельцев.
- **Runbook Rules** — запускают [runbook](/docs/runbooks/index), когда инцидент совпадает.
- **Privacy Rules** — решают, будет ли подходящий инцидент приватным.
- **Label Rules** — автоматически применяют метки.
- **SLA Rules** — отслеживают время реакции и устранения. Правила оцениваются по порядку; меньшие номера порядка идут первыми.
- **Reminder Rules** — периодически напоминают владельцам инцидента, пока он остаётся открытым. Правила оцениваются по порядку, и побеждает первое совпавшее.

**Семантика порядка не одинакова для всех.** Grouping Rules, SLA Rules и Reminder Rules оцениваются по порядку. On-Call Rules — нет: срабатывает каждое подходящее правило. Не считайте, что одна модель применима ко всем восьми.

Страницы **On-Call Rules**, **Owner Rules**, **Label Rules** и **Privacy Rules** оформлены вкладками — вкладка **Incident Rules** и вкладка **Episode Rules**, каждая со своей таблицей. Настраивайте вкладку **Incident Rules**, если только вы не имеете в виду именно эпизоды. **Grouping Rules**, **Runbook Rules**, **SLA Rules** и **Reminder Rules** — это единые таблицы.

## Правила дежурства инцидента

**Инциденты → Rules → On-Call Rules** (`/dashboard/{projectId}/incidents/settings/on-call-rules`) — это место, где вы делаете вызов дежурного автоматическим. Карточка **Incident On-Call Rules** описывает правила, которые автоматически выполняют политики дежурства при создании подходящих инцидентов. У страницы две вкладки: **Incident Rules** и **Episode Rules**.

Форма создания состоит из трёх шагов:

- **Basic Info** — **Name** (подсказка предлагает что-то вроде вызова команды баз данных при любом инциденте БД), **Description** и переключатель **Enabled**. В списке для каждого правила отображается зелёная плашка **Enabled** или красная **Disabled**.
- **Match Criteria** — **Monitors**, **Incident Severities**, **Incident Labels**, **Monitor Labels**, а также поля регулярных выражений без учёта регистра для заголовка инцидента, описания инцидента, имени монитора и описания монитора.
- **On-Call Policies** — политики, которые выполняет это правило.

### Как разрешается совпадение

Правила, заложенные в саму страницу, стоит усвоить:

- Правило совпадает, только когда проходят **все** заполненные вами критерии. Критерии, оставленные пустыми, пропускаются, а не считаются несовпавшими.
- Внутри одного критерия-списка — **Monitors**, **Incident Severities**, **Incident Labels**, **Monitor Labels** — совпадение работает по принципу «любое из».
- Поля с шаблонами — это регулярные выражения без учёта регистра.
- **Срабатывают все совпавшие правила.** Приоритета и остановки на первом совпадении нет.
- Набор политик, которые в итоге выполняются, — это объединение политик всех совпавших правил плюс политик, прикреплённых к инциденту вручную или через шаблон, с исключением дублей, чтобы каждая политика выполнялась не более одного раза.

Серьёзность здесь — критерий совпадения, и больше нигде. У уровня серьёзности инцидента нет собственного поля дежурства — выбор «Critical Incident» сам по себе никого не вызывает. Если вы хотите, чтобы серьёзность влияла на вызов, напишите правило дежурства, которое сопоставляется по ней.

## Прямое прикрепление политик дежурства

Правила — не единственный путь. У каждого инцидента есть собственный список политик дежурства, представленный полем **On-Call Policy** на шаге **On-Call** мастера объявления и на шаге **On-Call** шаблона инцидента. Описание поля говорит прямо: это политики дежурства, которые выполняются при создании этого инцидента.

При создании инцидента OneUptime выполняет правила меток, затем правила дежурства (которые объединяют свои подходящие политики со списком инцидента), затем правила runbook-ов — и если получившийся список не пуст, выполняется каждая политика в нём. Выполнения идут параллельно и завершаются независимо, поэтому сбой одной политики не останавливает остальные. Каждое выполнение помечено инцидентом, который его вызвал, и типом события уведомления о создании инцидента.

Чтобы увидеть, что произошло, откройте инцидент и выберите **On-Call Executions** в его боковом меню (`/dashboard/{projectId}/incidents/{incidentId}/on-call-policy-execution-logs`).

## Управление инцидентами из рабочих процессов

Триггеры рабочих процессов для инцидентов не написаны вручную — OneUptime генерирует их из моделей данных, поэтому каждая модель семейства инцидентов получает компоненты **On Create X**, **On Update X** и **On Delete X**, названные по единственному числу модели. Главная тройка — это **On Create Incident**, **On Update Incident** и **On Delete Incident**, и они находятся в категории **Incident** палитры компонентов рабочих процессов по адресу `/dashboard/{projectId}/workflows`.

Та же генерация даёт триггеры и для самой конфигурации: **On Create Incident State**, **On Update Incident Severity**, **On Create Incident Template**, **On Create Incident Note Template**, **On Create Incident State Timeline**, **On Create Incident Public Note**, **On Create Incident Internal Note**, **On Create Incident On-Call Rule**, **On Create Incident Role**, **On Create Incident Member** и другие. Каждая модель также получает соответствующие компоненты действий — **Find One Incident**, **Create One Incident**, **Update One Incident**, **Delete One Incident** и их многострочные аналоги, — так что триггер и действие с похожими именами оказываются рядом в одной категории. **On Create Incident** запускает рабочий процесс; **Create One Incident** открывает инцидент.

Несколько деталей, важных при настройке:

- **On Update X** принимает необязательный аргумент **Listen on**, сужающий триггер до обновлений, затрагивающих определённые поля. Оставьте его пустым, чтобы срабатывать на любое изменение. Если обновление приходит без записи о том, какие поля изменились, фильтр пропускается и рабочий процесс всё равно запускается.
- **On Create X** и **On Update X** оба принимают обязательный аргумент **Select Fields**; **On Delete X** не принимает аргументов.
- Все три предоставляют единственный выходной порт **Success**, и каждый принимает аргумент ID, чтобы можно было запустить рабочий процесс вручную для одной записи.
- Имена берутся из единственного числа модели, а не из имени таблицы, поэтому вы видите **On Create Incident Team Owner** и **On Create Incident User Owner**, а не имена в стиле таблиц.
- Для определений пользовательских полей инцидента триггеров нет. Эта модель — единственный член семейства инцидентов с отключёнными рабочими процессами.

Об остальной части создания рабочего процесса — в [Создании рабочего процесса](/docs/workflows/authoring) и [Переменных](/docs/workflows/variables).
