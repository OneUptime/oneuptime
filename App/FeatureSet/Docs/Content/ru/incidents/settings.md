# Настройки и автоматизация

Конфигурация инцидентов живёт не в настройках проекта. Она находится внутри самой продуктовой области «Инциденты» — в **Инциденты → Настройки** и **Инциденты → Правила**, по маршрутам, начинающимся с `/dashboard/{projectId}/incidents/settings/`. Если вы перерыли **Настройки проекта** в поисках шаблонов инцидентов или пользовательских полей — вот почему вы их там не нашли.

Разделы **Правила** и **Настройки** в боковом меню Инцидентов по умолчанию свёрнуты, так что сначала разверните их — иначе перечисленных ниже пунктов вы не увидите. Всё здесь принадлежит проекту: шаблоны, роли, пользовательские поля и правила живут в одном проекте и применяются к каждому объявленному в нём инциденту.

Эта страница — справочник по такой конфигурации: что лежит на каждом экране и что из этого срабатывает само в момент создания инцидента.

## Где живут настройки инцидентов

Откройте **Инциденты** в левой навигации, затем разверните **Настройки** внизу бокового меню.

| Страница                          | Что вы там делаете                                                                                              |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **Состояние инцидента**           | Добавляйте, переименовывайте, перекрашивайте и переупорядочивайте состояния, через которые проходит инцидент.    |
| **Серьёзность инцидента**         | Добавляйте, переименовывайте, перекрашивайте и переупорядочивайте уровни серьёзности.                            |
| **Шаблоны инцидентов**            | Заполняйте инцидент целиком заранее — заголовок, описание, ресурсы, политики дежурства, владельцев, метки.       |
| **Шаблоны заметок**               | Многоразовый текст для публичных и приватных заметок.                                                            |
| **Шаблоны постмортема**           | Многоразовые структуры постмортемов.                                                                             |
| **Пользовательские поля**         | Определяйте дополнительные поля, которые появляются в каждом инциденте.                                          |
| **Роли инцидента**                | Определяйте роли, на которые вы назначаете участников реагирования, — например, Incident Commander.              |
| **Дополнительные настройки**      | Префиксы номеров инцидента и эпизода инцидента.                                                                  |

**Состояние инцидента** и **Серьёзность инцидента** подробно разобраны в [Состояниях и уровнях серьёзности инцидентов](/docs/incidents/states-and-severities) — остальная часть этой страницы продолжает с **Шаблонов инцидентов**.

Разверните **Правила**, и вы получите ещё восемь страниц: **Правила группировки**, **Правила дежурства**, **Правила владельца**, **Правила runbook-ов**, **Правила конфиденциальности**, **Правила меток**, **Правила SLA** и **Reminder Rules**. О них — ниже.

## Шаблоны инцидентов

Шаблон инцидента — это сохранённый каркас инцидента. Вместо того чтобы каждый раз, когда шатается платёжный кластер, заново набирать тот же заголовок, тот же список мониторов и ту же политику дежурства, вы сохраняете всё это один раз и объявляете инцидент из шаблона.

Перейдите в **Инциденты → Настройки → Шаблоны инцидентов** (`/dashboard/{projectId}/incidents/settings/templates`). Карточка называется **Шаблоны инцидентов**. Создание шаблона проводит вас через мастер из шести шагов:

- **Информация о шаблоне** — **Название шаблона** и **Описание шаблона**. Они именуют сам шаблон и никогда не попадают в инцидент.
- **Сведения об инциденте** — **Заголовок**, **Описание** (Markdown), **Серьёзность инцидента** и **Начальное состояние инцидента**. **Начальное состояние инцидента** необязательно и изначально пусто; варианты перечислены в порядке состояний. Оставьте его пустым — и инциденты из этого шаблона попадут в состояние создания, заданное в проекте.
- **Затронутые ресурсы** — мониторы, хосты, кластеры и сервисы, к которым нужно привязать инцидент, плюс **Change Monitor Status to**.
- **Дежурство** — **Политика дежурства**: политики, которые выполняются, когда объявлен инцидент, созданный из этого шаблона.
- **Владельцы** — **Владелец — Команды** и **Владелец — Пользователи**.
- **Метки** — **Метки**.

Несколько коротких правил:

- В списке шаблонов видны только **Имя** и **Описание**. Строки нельзя ни редактировать, ни удалять прямо из списка — чтобы что-то изменить, откройте шаблон (`/dashboard/{projectId}/incidents/settings/templates/{modelId}`).
- Шаблоны поддерживают импорт и экспорт JSON, так что шаблон можно перенести между проектами.
- Пустой список сообщает «No incident templates found.»

### Как применяется шаблон

Путей два, и ведут они себя одинаково.

- **Из дашборда** — кнопка **Создать из шаблона** в списке инцидентов открывает выбор **Выберите шаблон инцидента**, страница объявления читает шаблон из параметра строки запроса `incidentTemplateId` и заранее заполняет форму данными шаблона вместе с его командами-владельцами и пользователями-владельцами.
- **Через API** — передайте `createdIncidentTemplateId` в `POST /api/incident`, и сервер заполнит инцидент из шаблона.

Главное здесь — правило слияния: **шаблон заполняет только то поле, которое вы оставили неопределённым**. Заголовок, описание, серьёзность инцидента, начальное состояние инцидента, статус монитора за полем **Change Monitor Status to**, мониторы, хосты, кластеры Kubernetes, хосты Docker, хосты Podman, сервисы, политики дежурства и метки копируются из шаблона, только если вызывающая сторона или форма ничего не передали. Всё, что вы задали явно, всегда побеждает.

**Диалог пустого состояния указывает не туда.** Если шаблонов ещё нет, кнопка **Создать из шаблона** показывает диалог **No Incident Templates**. Его текст отправляет вас в настройки проекта, но сама кнопка ведёт в **Инциденты → Настройки → Шаблоны инцидентов** — вот где всё на самом деле.

## Шаблоны заметок

Шаблоны заметок дают участникам реагирования готовый текст для обновлений по инциденту, чтобы обновление страницы статуса в три часа ночи не приходилось писать с нуля человеку, который еле держит глаза открытыми.

Перейдите в **Инциденты → Настройки → Шаблоны заметок** (`/dashboard/{projectId}/incidents/settings/note-templates`). Карточка называется **Шаблоны публичных или приватных заметок для инцидентов** — одна библиотека обслуживает оба типа заметок. В форме создания два шага:

- **Информация о шаблоне** — **Название шаблона** и **Описание шаблона**, оба обязательны.
- **Сведения о заметке** — сам текст заметки, в Markdown, обязателен.

Как и шаблоны инцидентов, строки создаются и просматриваются, а не правятся прямо в списке; чтобы что-то изменить, откройте шаблон.

Шаблоны заметок появляются там, где они действительно нужны: диалоги подтверждения **Acknowledge Incident** и **Resolve Incident** оба предлагают **Выберите шаблон заметки** рядом с полем **Публичная заметка**. Чем публичные заметки отличаются от приватных, читайте в [Заметках, владельцах и ленте инцидента](/docs/incidents/notes-owners-and-feed).

## Шаблоны постмортема

Шаблон постмортема — каркас разбора, который вы пишете после инцидента: ваши заголовки, ваши подсказки, ваши постоянные вопросы. С ним каждый разбор в проекте имеет одну и ту же форму.

Перейдите в **Инциденты → Настройки → Шаблоны постмортема** (`/dashboard/{projectId}/incidents/settings/postmortem-templates`). Карточка называется **Шаблоны постмортема**. В форме создания два шага:

- **Информация о шаблоне** — **Название шаблона** и **Описание шаблона**, оба обязательны.
- **Детали разбора инцидента** — **Шаблон разбора инцидента**, то есть сам текст, в Markdown, обязателен.

Применяют шаблон из инцидента, а не из настроек. Откройте инцидент, выберите **Постмортем** в его боковом меню (`/dashboard/{projectId}/incidents/{incidentId}/postmortem`) и нажмите **Применить шаблон**. Откроется диалог **Применить шаблон ретроспективы** с раскрывающимся списком **Выберите шаблон**; выбор шаблона загружает его текст в редактор **Заметка разбора инцидента**, где вы правите его перед сохранением. У эпизодов инцидента есть такая же страница **Постмортем**, и опирается она на ту же библиотеку шаблонов.

## Пользовательские поля

Пользовательские поля позволяют носить в каждом инциденте свои метаданные — внутреннее имя сервиса, ссылку на тикет изменения, уровень клиента.

Перейдите в **Инциденты → Настройки → Пользовательские поля** (`/dashboard/{projectId}/incidents/settings/custom-fields`). Страница называется **Пользовательские поля инцидента**. У каждого определения есть:

- **Имя поля** — обязательно, минимум два символа. Плейсхолдер подсказывает имя в виде слага, например `internal-service`.
- **Описание поля** — необязательно.
- **Тип поля** — обязательно. Он определяет, как вводятся данные. Для типов с раскрывающимся списком нужно ещё перечислить варианты.
- **Параметры раскрывающегося списка** — значения, которые появятся в списке, у каждого — необязательный цвет.

Определения живут в собственной модели, а значения — в самом инциденте, в столбце `customFields`. В отдельном инциденте вы заполняете их через **Пользовательские поля** в боковом меню инцидента (`/dashboard/{projectId}/incidents/{incidentId}/custom-fields`).

**Один пробел, о котором стоит знать.** Определения пользовательских полей инцидента — единственная часть семейства инцидентов без триггеров рабочих процессов, см. раздел о рабочих процессах ниже.

## Роли инцидента

Роли инцидента — это именованные работы, на которые вы назначаете людей во время реагирования. Определите их в **Инциденты → Настройки → Роли инцидента** (`/dashboard/{projectId}/incidents/settings/roles`); в описании карточки как примеры приводятся Incident Commander и Responder.

Роли — это только определения. Людей вы назначаете на них в каждом инциденте: в мастере объявления есть шаг **Роли инцидента** с полем **Назначить роли инцидента**, а у каждого инцидента есть страница **Роли** в боковом меню.

## Префиксы номеров

У каждого инцидента есть номер. По умолчанию он выглядит как `#42`. Если вслух ваша команда говорит «INC-42», пусть и продукт говорит так же.

Перейдите в **Инциденты → Настройки → Дополнительные настройки** (`/dashboard/{projectId}/incidents/settings/more`). Карточка называется **Префикс номера** и содержит два поля проекта:

- **Префикс номера инцидента** — до 20 символов, плейсхолдер `INC-`. Задайте его — и инцидент `#42` отобразится как `INC-42`.
- **Префикс номера эпизода инцидента** — то же самое для номеров эпизодов инцидента, плейсхолдер `IE-`.

Оставьте любое из полей пустым, чтобы сохранить префикс `#` по умолчанию; незаданное поле показывает `# (default)`. Сохраните кнопкой **Обновить**. Значение с префиксом хранится в инциденте как `incidentNumberWithPrefix` — именно его рисуют список инцидентов и шапка инцидента.

## Правила, которые срабатывают при создании инцидента

В **Инциденты → Правила** живут восемь движков правил. Работу они делают одну и ту же — смотрят на инцидент в момент его создания и действуют, если он подходит, — но различаются тем, что именно делают и как разрешается совпадение сразу нескольких правил.

- **Правила группировки** — объединяют связанные инциденты в эпизоды. Правила вычисляются в порядке приоритета; меньший номер приоритета идёт первым.
- **Правила дежурства** — выполняют политики дежурства для подходящих инцидентов. Подробно — ниже.
- **Правила владельца** — назначают владельцев автоматически.
- **Правила runbook-ов** — запускают [runbook](/docs/runbooks/index), когда инцидент подходит.
- **Правила конфиденциальности** — решают, будет ли подходящий инцидент приватным.
- **Правила меток** — проставляют метки автоматически.
- **Правила SLA** — отслеживают время реакции и время устранения. Правила вычисляются по порядку; меньший номер порядка идёт первым.
- **Reminder Rules** — периодически напоминают владельцам инцидента, пока инцидент открыт. Правила вычисляются по порядку, и побеждает первое подошедшее.

**Семантика порядка не одинакова.** Правила группировки, Правила SLA и Reminder Rules учитывают порядок. Правила дежурства — нет: срабатывает каждое подошедшее правило. Не думайте, что одна модель годится для всех восьми.

Страницы **Правила дежурства**, **Правила владельца**, **Правила меток** и **Правила конфиденциальности** разбиты на вкладки — **Incident Rules** и **Episode Rules**, у каждой своя таблица. Настраивайте вкладку **Incident Rules**, если только вы не имеете в виду именно эпизоды. **Правила группировки**, **Правила runbook-ов**, **Правила SLA** и **Reminder Rules** — это одиночные таблицы.

## Правила дежурства по инцидентам

**Инциденты → Правила → Правила дежурства** (`/dashboard/{projectId}/incidents/settings/on-call-rules`) — место, где вызов дежурных становится автоматическим. Карточка **Правила дежурства по инцидентам** описывает правила, которые автоматически выполняют политики дежурства при создании подходящих инцидентов. На странице две вкладки: **Incident Rules** и **Episode Rules**.

В форме создания три шага:

- **Основная информация** — **Имя** (плейсхолдер предлагает что-то вроде вызова команды баз данных на любой инцидент с БД), **Описание** и переключатель **Включено**. В списке у каждого правила рисуется зелёная плашка **Включено** или красная **Отключено**.
- **Критерии совпадения** — **Мониторы**, **Инцидент Серьёзности**, **Метки инцидента**, **Метки монитора**, а также поля регулярных выражений без учёта регистра для заголовка инцидента, описания инцидента, имени монитора и описания монитора.
- **Политики дежурств** — политики, которые выполняет это правило.

### Как разрешается совпадение

Правила, по которым работает сама эта страница, стоит запомнить:

- Правило подходит, только когда проходят **все** заполненные вами критерии. Оставленные пустыми критерии пропускаются, а не считаются проваленными.
- Внутри одного списочного критерия — **Мониторы**, **Инцидент Серьёзности**, **Метки инцидента**, **Метки монитора** — совпадение работает по принципу «любое из».
- Поля с шаблонами — это регулярные выражения без учёта регистра.
- **Срабатывают все подошедшие правила.** Ни приоритета, ни короткого замыкания здесь нет.
- Реально выполняется объединение политик из всех подошедших правил плюс любые политики, привязанные к инциденту вручную или шаблоном, — с удалением дубликатов, чтобы каждая политика отработала не больше одного раза.

Серьёзность выступает критерием совпадения здесь и больше нигде. У серьёзности инцидента нет поля дежурства — выбор «Critical Incident» сам по себе никого не вызовет. Хотите, чтобы серьёзность управляла вызовами, — напишите правило дежурства, которое на неё смотрит.

## Прямое подключение политик дежурства

Правила — не единственный путь. У каждого инцидента есть собственный список политик дежурства: он показан как поле **Политика дежурства** на шаге **Дежурство** мастера объявления и на шаге **Дежурство** шаблона инцидента. Описание поля говорит об этом прямо: это политики дежурства, которые выполняются при создании этого инцидента.

При создании инцидента OneUptime выполняет правила меток, затем правила дежурства (они подмешивают свои подошедшие политики в список инцидента), затем правила runbook-ов — и если получившийся список не пуст, выполняется каждая политика из него. Выполнения идут параллельно и завершаются независимо друг от друга, так что сбой одной политики не останавливает остальные. Каждое выполнение помечается инцидентом, который его запустил, и типом события уведомления «инцидент создан».

Чтобы посмотреть, что произошло, откройте инцидент и выберите **Выполнения дежурств** в его боковом меню (`/dashboard/{projectId}/incidents/{incidentId}/on-call-policy-execution-logs`).

## Управление инцидентами из рабочих процессов

Триггеры рабочих процессов для инцидентов не пишутся вручную — OneUptime порождает их из моделей данных, поэтому каждая модель семейства инцидентов получает компоненты **On Create X**, **On Update X** и **On Delete X**, названные по имени модели в единственном числе. Главные три — **On Create Incident**, **On Update Incident** и **On Delete Incident**, и найти их можно в категории **Инцидент** панели **Добавить компонент** по адресу `/dashboard/{projectId}/workflows`.

Та же генерация даёт вам триггеры и для самой конфигурации: **On Create Incident State**, **On Update Incident Severity**, **On Create Incident Template**, **On Create Incident Note Template**, **On Create Incident State Timeline**, **On Create Incident Public Note**, **On Create Incident Internal Note**, **On Create Incident On-Call Rule**, **On Create Incident Role**, **On Create Incident Member** и другие. Каждая модель получает и парные компоненты-действия — **Find One Incident**, **Create One Incident**, **Update One Incident**, **Delete One Incident** и их варианты для множества строк, — так что триггер и действие с похожими именами стоят рядом в одной категории. **On Create Incident** запускает рабочий процесс; **Create One Incident** заводит инцидент.

Несколько деталей, важных при сборке:

- **On Update X** принимает необязательный аргумент **Listen on**, который сужает триггер до обновлений, затрагивающих конкретные поля. Оставьте его пустым — и триггер сработает на любое изменение. Если обновление пришло без записи о том, какие поля изменились, фильтр пропускается и рабочий процесс всё равно выполняется.
- **On Create X** и **On Update X** оба принимают обязательный аргумент **Select Fields**; **On Delete X** аргументов не принимает.
- Все три выставляют единственный выходной порт **Успешно**, и каждый принимает аргумент с ID, чтобы вы могли вручную прогнать рабочий процесс по одной записи.
- Имена берутся из имени модели в единственном числе, а не из имени таблицы — поэтому вы видите **On Create Incident Team Owner** и **On Create Incident User Owner**, а не имена в форме таблиц.
- Триггеров для определений пользовательских полей инцидента нет. Эта модель — единственный участник семейства инцидентов с отключёнными рабочими процессами.

О том, как собрать остальную часть рабочего процесса, читайте в [Создании рабочего процесса](/docs/workflows/authoring) и [Переменных](/docs/workflows/variables).
