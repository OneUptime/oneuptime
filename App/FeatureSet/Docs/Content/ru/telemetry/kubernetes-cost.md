# Наблюдаемость затрат Kubernetes

## Обзор

OneUptime может показать, сколько на самом деле стоит каждая рабочая нагрузка Kubernetes — расходы по пространствам имён, контроллерам и подам, вместе с простаивающей ёмкостью и эффективностью «запрошено против использовано», — прямо рядом с метриками, логами и трассировками, которые вы уже собираете с помощью [агента Kubernetes](/docs/telemetry/kubernetes-agent).

Включается это одной командой:

```bash
helm upgrade oneuptime-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent \
  --reuse-values \
  --set cost.enabled=true
```

Это полноценная установка. Чарт включает в себя open-source-движок [OpenCost](https://opencost.io) (Apache-2.0, CNCF — тот самый [cost-model](https://github.com/kubecost/cost-model), на котором работает и Kubecost) плюс минимальный выделенный Prometheus, который нужен ему для истории использования, — два небольших пода невидимой «сантехники». OpenCost оценивает ваши узлы, тома и балансировщики нагрузки по **публичным прайс-листам вашего облачного провайдера автоматически, без каких-либо учётных данных** (AWS, GCP, Azure); кластеры on-prem вместо этого задают тарифную карту (см. ниже).

Примерно в течение часа (после первого закрытого часового окна) вы получаете:

- **Страницу Costs для каждого кластера** (_Kubernetes → ваш кластер → Costs_): тренд расходов, расходы по пространствам имён с разбивкой на cpu/память/хранилище, расходы по рабочим нагрузкам, расходы на простой и эффективность.
- **Страницу Costs на уровне проекта** (_Kubernetes → Costs_): расходы по всем кластерам проекта.
- **Шаблон дашборда Kubernetes Cost** (_Dashboards → Create → Kubernetes Cost Dashboard_): тренды почасовой стоимости узлов, удельные стоимости CPU/RAM, расходы на постоянные тома и балансировщики нагрузки.
- Сырые метрики затрат (`node_total_hourly_cost`, `pv_hourly_cost`, ...) в **Metric Explorer**, пригодные для пользовательских дашбордов и метрических оповещений.

## Как это работает

При `cost.enabled=true` чарт запускает четыре вещи:

1. **OpenCost** (в составе чарта) — наблюдает за кластером, обнаруживает облачные прайс-листы и вычисляет заранее оценённые распределения затрат по каждой рабочей нагрузке.
2. **Минимальный Prometheus** (в составе чарта) — OpenCost требует PromQL-эндпоинт для истории использования и цен. Этот существует исключительно для этого: одна реплика, хранение 3 дня и ровно две цели сбора (cAdvisor через node proxy API-сервера и сам OpenCost — OpenCost сам генерирует метрики запросов ресурсов в стиле KSM, поэтому kube-state-metrics не задействован). Он никогда не публикуется за пределы кластера, и его данные никогда кластер не покидают.
3. **Опрашиватель распределения затрат** (`cost.agent`) — опрашивает Allocation API OpenCost один раз на каждое закрытое часовое окно и отправляет POST-запросом строки затрат по каждой рабочей нагрузке (cpu / ram / gpu / pv / сеть / балансировщик нагрузки / простой, плюс эффективность) в OneUptime. Окна отправляются ровно один раз — сервер пропускает окна, которые уже принял, поэтому перезапуски не могут привести к двойному учёту расходов.
4. **Сбор метрик затрат** (`cost.metrics`) — OpenTelemetry-сборщик агента собирает Prometheus-метрики OpenCost (ограниченные списком разрешённых до рядов затрат) через тот же OTLP-конвейер, что и остальные метрики вашего кластера.

## Уже используете Kubecost или OpenCost?

Вместо этого укажите чарту ваш существующий движок — тогда ничего не устанавливается в комплекте:

```bash
helm upgrade oneuptime-agent oneuptime/kubernetes-agent \
  --namespace oneuptime-agent \
  --reuse-values \
  --set cost.enabled=true \
  --set cost.engine.url=http://kubecost-cost-analyzer.kubecost.svc.cluster.local:9090
```

| Движок   | Типичный URL сервиса                                             |
| -------- | ---------------------------------------------------------------- |
| OpenCost | `http://opencost.opencost.svc.cluster.local:9003`                |
| Kubecost | `http://kubecost-cost-analyzer.kubecost.svc.cluster.local:9090`  |

Путь Allocation API определяется автоматически (`/model/allocation` для Kubecost, `/allocation/compute` или `/allocation` для OpenCost). Задавайте `cost.engine.allocationPath` только для нестандартных установок.

## Ценообразование on-prem / bare-metal

Кластеры, узлы которых не имеют публичной облачной цены, могут задать тарифную карту — тогда OpenCost оценивает каждый ресурс по этим цифрам. Все значения указываются в **долларах США за ресурсо-час**:

```yaml
cost:
  enabled: true
  opencost:
    customPricing:
      enabled: true
      cpuPerCoreHour: "0.031611"       # ~$23 per core-month
      ramPerGiBHour: "0.004237"        # ~$3 per GiB-month
      storagePerGBHour: "0.00005479452" # ~$0.04 per GB-month
      gpuPerHour: "0.95"
```

## Полезные регуляторы

Все параметры опциональны — полный список см. в `values.yaml` чарта:

```yaml
cost:
  agent:
    windowSeconds: 3600   # allocation window length (hourly = native)
    includeIdle: true     # ship the engine's __idle__ allocation
    currency: USD         # currency code shown in the UI (informational)
  prometheus:
    retention: 7d         # bundled TSDB history; right-sizing reads peaks back over days
    persistence:
      enabled: false      # set true for a small PVC; emptyDir otherwise
  metrics:
    enabled: true         # cost metrics for dashboards / Metric Explorer
    scrapeInterval: 60s
```

## Оповещения по затратам

Собранные метрики затрат — это обычные метрики OneUptime, поэтому вы можете вешать на них метрические оповещения, как на любые другие — например, оповещать, когда средний `node_total_hourly_cost` поднимается выше бюджетного порога, или когда `pv_hourly_cost` появляется для класса томов, которого в кластере быть не должно.

## Модель данных и хранение

Строки распределения затрат хранятся в ClickHouse (одна строка на кластер, окно, пространство имён, контроллер, под и контейнер) и следуют сроку хранения телеметрии кластера: параметр `retainTelemetryDataForDays` ресурса кластера Kubernetes, с откатом на срок хранения данных проекта. Простаивающая и нераспределённая ёмкость хранятся как обычные строки под пространствами имён `__idle__` / `__unallocated__`, поэтому их можно запрашивать с теми же группировками, что и расходы рабочих нагрузок.

## Устранение неполадок

- **Страницы Costs пусты** — проверьте логи cost-агента: `kubectl logs -n <agent namespace> deploy/<release>-kubernetes-agent-cost`. `401` означает, что ключ приёма данных недействителен; `cost engine did not answer any known allocation path` означает, что движок ещё не поднялся (встроенному OpenCost после установки нужно несколько минут, чтобы оценить первые окна) или что `cost.engine.url` указан неверно.
- **Встроенный OpenCost не готов** — `kubectl logs -n <agent namespace> deploy/<release>-kubernetes-agent-opencost`. Он логирует, какого облачного провайдера он обнаружил и загрузились ли данные о ценах.
- **Шаблон дашборда не показывает данных** — шаблон читает собранные метрики затрат; убедитесь, что `cost.metrics.enabled` имеет значение `true`.
- **Числа отличаются от собственного интерфейса движка** — OneUptime включает корректировки согласования движка в каждый компонент затрат и отправляет только целиком закрытые окна; частичные расходы текущего часа появляются после закрытия окна.
- **Под Prometheus перезапустился** — при хранении по умолчанию в `emptyDir` перезапуск теряет несколько часов истории использования, поэтому распределения для этих окон могут оказаться меньше. Установите `cost.prometheus.persistence.enabled=true`, если это для вас важно.
