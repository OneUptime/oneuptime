OneUptime AI access registers itself with the same key — within a minute the
cluster's AI page (Kubernetes → <cluster> → AI) shows the Runner as Connected

{{- if $aiRemediation.enabled }}

What the Runner's write access amounts to: patch on workloads and pods (and
create on jobs) in a namespace is as good as running any image as any
ServiceAccount there and reading its Secrets. OneUptime's command policy
refuses changing which ServiceAccount, security settings, volumes, command or
Secret wiring a pod runs with (pod-template security patches, set
serviceaccount, create deployment/cronjob/job --image, patch bodies that are
not JSON, patches that replace the pod spec or a whole containers list,
expose --overrides).
It still allows changing an image (set image, or a patch of an
image field) as a riskier change: the new image runs as the workload's own
ServiceAccount, with its Secrets, and a human approves it unless the cluster
bypasses approvals or its allowlist names the command. RBAC only decides
where writes may land.
{{- if $aiWriteNamespaces }}
Write access is bound only in: {{ join ", " $aiWriteNamespaces }} (aiAccess.remediation.namespaces).
Each listed namespace must already exist: the chart creates a RoleBinding in
each and never creates a namespace, so a missing one fails every install or
upgrade with 'namespaces "<name>" not found'. Take a namespace off the list
before you delete it; --set-json 'aiAccess.remediation.namespaces=[]' goes
back to cluster-wide (--set aiAccess.remediation.namespaces=null does not
reset a stored list under --reuse-values). A fix outside these namespaces is
refused when it is proposed or approved, and the Runner refuses it again
before it runs kubectl.
{{- else }}
Write access is bound cluster-wide. RBAC cannot keep it out of kube-system,
kube-public, kube-node-lease or {{ .Release.Namespace }}: there OneUptime's policy (never
without a human in the three system namespaces) and the Runner (never its own
namespace) hold the line. To bind it only where AI may fix things, upgrade
with (every listed namespace must already exist):
  --set "aiAccess.remediation.namespaces={web,api}"
{{- end }}
{{- if $aiNodeOperations }}

a taint or a patch of a node always waits for a human, in every mode; turn

{{- else }}
Node operations (cordon, uncordon, taint, drain) are off: the chart grants no

If it stays "Disconnected" or no data shows up (most often a wrong/revoked
ingestion key: OneUptime refuses it with 401/422, and the collector only logs
"Exporting failed. Dropping data.", which is easy to miss), run the diagnostic
script for a one-shot root-cause verdict:
  curl -fsSL https://raw.githubusercontent.com/OneUptime/oneuptime/master/HelmChart/Public/kubernetes-agent/troubleshoot.sh | bash -s -- -n {{ .Release.Namespace }}

Or validate your ingestion key directly (200 = valid, 401 = unknown/revoked):
  curl -i -H "x-oneuptime-token: <YOUR_API_KEY>" {{ .Values.oneuptime.url }}/otlp/v1/validate
