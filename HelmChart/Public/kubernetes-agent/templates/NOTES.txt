Write access comes from aiAgent.remediation.enabled, which aiAgent.fixes

{{- end }}

What write access amounts to: patch on workloads and pods (and create on
jobs) in a namespace is as good as running any image as any ServiceAccount
there and reading its Secrets. OneUptime's command policy refuses changing
which ServiceAccount, security settings, volumes, command or Secret wiring a
pod runs with (patches that replace the pod spec or a whole containers list
included), and expose --overrides. It still allows changing an image (set
image) as a riskier change a human approves unless the cluster bypasses
approvals or its allowlist names the command. RBAC only decides where writes
may land.
{{- if $aiAgent.writeNamespaces }}
Write access is bound only in: {{ join ", " $aiAgent.writeNamespaces }} ({{ $aiAgent.namespacesKey }}).
Each listed namespace must already exist: the chart creates a RoleBinding in
each and never creates a namespace, so a missing one fails every install or
upgrade with 'namespaces "<name>" not found'. Take a namespace off the list
before you delete it; --set-json 'aiAgent.remediation.namespaces=[]' goes
back to cluster-wide. A fix outside these namespaces is refused when it is
proposed or approved, and the agent refuses it again before it runs kubectl.
{{- else }}
Write access is bound cluster-wide. RBAC cannot keep it out of kube-system,
kube-public, kube-node-lease or {{ .Release.Namespace }}: there OneUptime's policy (never
without a human in the three system namespaces) and the agent (never its own
namespace) hold the line. To bind it only where AI may fix things, upgrade
with (every listed namespace must already exist):
  --set "aiAgent.remediation.namespaces={web,api}"
{{- end }}
{{- if $aiAgent.allowNodeOperations }}
Node operations (cordon, uncordon, taint, drain) are on, cluster-wide. A drain
evicts pods in every namespace, kube-system and {{ .Release.Namespace }} included, so a drain,
a taint or a patch of a node always waits for a human, in every mode; turn
node operations off with --set aiAgent.remediation.nodeOperations=false.
{{- else }}
Node operations (cordon, uncordon, taint, drain) are off: the chart grants no
node RBAC, and the agent refuses them before it runs kubectl. OneUptime refuses
a node fix already when it is proposed or approved.
{{- end }}
{{- else }}

If it stays "Disconnected" or no data shows up (most often a wrong/revoked
ingestion key: OneUptime refuses it with 401/422, and the collector only logs
"Exporting failed. Dropping data.", which is easy to miss), run the diagnostic
script for a one-shot root-cause verdict:
  curl -fsSL https://raw.githubusercontent.com/OneUptime/oneuptime/master/HelmChart/Public/kubernetes-agent/troubleshoot.sh | bash -s -- -n {{ .Release.Namespace }}

Or validate your ingestion key directly (200 = valid, 401 = unknown/revoked):
  curl -i -H "x-oneuptime-token: <YOUR_API_KEY>" {{ .Values.oneuptime.url }}/otlp/v1/validate
