# AI SRE — autonomous investigation engine

Wake-on-signal AI SRE: when an incident or alert is created (and the project has opted in), AI runs a read-only, budgeted, citation-minting investigation over the project's own telemetry and posts a root-cause analysis to the subject's feed, with a glass-box `AIRun`/`AIRunEvent` trail behind a live dashboard panel.

- `AIInvestigationEngine.ts` — shared run lifecycle, budgets, persona, quiet-mode confidence gate
- `IncidentInvestigationRunner.ts` / `AlertInvestigationRunner.ts` — per-subject context assembly + result posting
- Who reads the report (#9576): everyone who may see the incident or alert, so the runners work out its readers first (`Server/Utils/ReadAudience/ReadAudienceReader.ts`) and every starting context, tool and follow-up check reads with them (`ReadAudience` on the run's props). The permission layer narrows each read (`Server/Types/Database/Permissions/ReadAudiencePermission.ts`): a kind no role reads only by owner or label is read whole; otherwise none an owner or a label sets apart, beside what the subject names itself; never a private incident or alert but the subject. `InvestigationAccessForAudience.ts` keeps the clusters and resources it reaches directly to the same readers. Every other run of the engine reads the same way (#9612): a fix (`Remediation/RemediationReadAudience.ts` names what it acts on - its cluster or resource, the Runners and runbooks its AI rule names - beside the subject's own), a security case's triage (subject: the case and the incident it declared) and an AI insight's triage (subject: the insight and its service). A security case's triage is posted on the case and its timeline alone, so it counts only the owner and label narrowing that reaches somebody who may read the case, its timeline or the audit log (`postsOnlyWhereTheSubjectIsRead`, #9632); every other run counts every row, since its writing reaches channels or other runs. `SubjectReadersOnlyGuard.test.ts` holds the triage to those places. `EngineRunsReadForTheirReaders.test.ts` fails when a runner hands the engine no readers.
- `IncidentPostmortemRunner.ts` — auto-draft postmortem when an incident resolves
- `AIMemory.ts` — recurrence context from past resolved incidents and alerts: those that share a monitor, service or label with the subject, or whose words say the same thing happened (recall by meaning, `Common/Utils/AI/MeaningMatch.ts`: SRE concepts and stemmed words, TF-IDF cosine, no vector store). Each case says what it shares with the subject; an analysis a person confirmed counts as a known cause
- `ServiceKnowledge.ts` — what OneUptime AI has learned about the services the subject is on: each service's recurring failures, grouped by meaning from its resolved incidents and alerts with a known cause, with the fixes that worked. Read from the records each time; nothing is stored
- `RemediationHandoff.ts` — the investigation → auto-remediation hand-off (RCA-first ordering). The incident/alert create hooks defer `AutoRemediationRuleEngineService` whenever an investigation was enqueued (the runners' `investigateNew*` return "enqueued"); this module releases the subject to the rule engine when that investigation **settles** — any terminal outcome. Settle-once discipline is inherited from the run-status CAS transitions (the same discipline that keeps `postAnalysis` single-shot): only the actor that WON a terminal transition calls the hand-off. The settle sites: Completed and finalized-Error via `InvestigationRequest.onSettled` / the runners' `failOrRequeue` outcome, queue-TTL expiry and terminal-stale via `InvestigationQueue`'s private hand-off. A failed investigation still hands off — remediation degrades to its pre-RCA behavior, never silently disappears; with no investigation enqueued, the create hook applies rules immediately and this module is never involved.
- `ConfidenceSignal.ts` — the structured, server-verified confidence signal (deterministic evidence floor + one constrained classification call), with per-consumer fail directions
- `FixFromIncidentTaskTrigger.ts` — the FixFromIncident recipe's two trigger forms: the human "Open Fix PR from this analysis" button (shown only when the investigation's structured classification recommends a repository code change), and the automatic form for projects opted in through the independent incident or alert automatic-code-fix setting (default false). Both use the same fail-closed code-fix recommendation: operational, infrastructure, external, user-error, inconclusive and failed classifications never offer or open a code-fix PR. The automatic form fires only after the exact posted analysis and its Recommended decision are durably stored; it never throws, pre-checks the subject lane's daily fix-run budget as a quiet skip, and shares the same repo + serialized per-subject dedupe gates as the button. The enqueued automatic run is system-authored (no userId).
