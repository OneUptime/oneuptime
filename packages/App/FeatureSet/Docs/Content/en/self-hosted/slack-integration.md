# Slack Integration

Connect your self-hosted OneUptime project to Slack to send notifications and use incident actions, commands, and message events.

## Setup

1. Set your OneUptime hostname and HTTPS configuration as described below. In your project's **Settings > Slack Integration**, copy the generated app manifest. It is also available at `https://your-oneuptime-domain.com/api/slack/app-manifest`.
2. [Create a Slack app](https://api.slack.com/apps) from that manifest in your workspace. Use the manifest generated by your own deployment so its URLs match your hostname.
3. Copy the **Client ID**, **Client Secret**, and **Signing Secret** from the app's **Basic Information** page into `config.env` for Docker Compose:

   ```dotenv
   SLACK_APP_CLIENT_ID=YOUR_SLACK_APP_CLIENT_ID
   SLACK_APP_CLIENT_SECRET=YOUR_SLACK_APP_CLIENT_SECRET
   SLACK_APP_SIGNING_SECRET=YOUR_SLACK_APP_SIGNING_SECRET
   ```

   For Helm, set these values:

   ```yaml
   slackApp:
     clientId: "YOUR_SLACK_APP_CLIENT_ID"
     clientSecret: "YOUR_SLACK_APP_CLIENT_SECRET"
     signingSecret: "YOUR_SLACK_APP_SIGNING_SECRET"
   ```

4. Apply the configuration and wait for OneUptime to restart. If Slack's Events URL verification failed before the signing secret was configured, retry it now.
5. Return to **Settings > Slack Integration**, select **Connect to Slack**, and authorize the app. Connect your personal Slack account in OneUptime when using actions that require a user identity.

## Network access for self-hosted deployments

### Traffic direction and endpoints

| Traffic | Required access |
| --- | --- |
| OneUptime to Slack | DNS and outbound HTTPS on TCP 443 to `slack.com` for Web API calls and OAuth token exchange; `hooks.slack.com` for command response URLs and incoming-webhook notifications when used |
| Slack to OneUptime | Public HTTPS on TCP 443 to the four POST routes below for the complete integration |
| User's browser to OneUptime | Dashboard access and OAuth redirects to `/api/slack/auth/:projectId/:userId` and `/api/slack/auth/:projectId/:userId/user`; these can remain accessible through the user's VPN |

The outbound domains describe OneUptime's Slack integration, not an exhaustive allowlist for Slack clients or every Slack feature. A Slack *incoming webhook* is hosted by Slack: OneUptime sends to it; it is not an inbound endpoint on your OneUptime server. See Slack's [incoming webhook guide](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks/).

Forward these provider callbacks to OneUptime's application through its ingress:

| Method and path | Purpose |
| --- | --- |
| `POST /api/slack/events` | Events API verification, reactions, mentions, and messages |
| `POST /api/slack/interactive` | Buttons, shortcuts, modal submissions, `/incident`, and `/maintenance` |
| `POST /api/slack/options-load` | Interactive menu option requests |
| `POST /api/slack/command` | `/oneuptime` command |

OAuth is a [browser redirect followed by a server-side token exchange](https://docs.slack.dev/authentication/installing-with-oauth/). The manifest registers `/api/slack/auth` as the redirect URL prefix; OneUptime supplies the project and user paths during authorization. Browser access alone does not let Slack deliver events or button actions.

### Private deployments and callback security

Use public DNS and a gateway with a publicly trusted HTTPS certificate, a complete certificate chain, and a private route to your OneUptime ingress. Allow inbound TCP 443 to the gateway and forward only the four callback routes above. A private `ClusterIP`, internal DNS name, or employee VPN connection alone is not reachable by Slack. Split DNS can keep the dashboard and OAuth routes private under the same hostname.

Set `HOST=oneuptime.example.com` and `HTTP_PROTOCOL=https` in `config.env`, or `host: oneuptime.example.com` and `httpProtocol: https` in Helm. Apply the configuration and wait for the restart. These values generate URLs; they do not provision DNS, TLS, or firewall rules. Regenerate and update the Slack manifest after a hostname change.

Preserve the method, path, query string, original body, `Content-Type`, `X-Slack-Signature`, and `X-Slack-Request-Timestamp`. Preserve the public host and HTTPS scheme through trusted proxy headers. Exempt callback routes from browser SSO, CAPTCHA, and proxy login pages while retaining OneUptime's signing-secret and timestamp checks. Keep the server clock synchronized. Slack documents [request signature verification](https://docs.slack.dev/authentication/verifying-requests-from-slack/); a source IP check does not replace it.

### Verify access and understand limitations

In Slack's **Event Subscriptions**, verify the Events Request URL; Slack sends a [POST challenge and checks TLS](https://docs.slack.dev/apis/events-api/using-http-request-urls/). Then send a test notification, run a slash command, press an incident button, and trigger a subscribed event. Check gateway and OneUptime logs for failed deliveries without logging secrets. Slack expects prompt acknowledgments, including [a response within three seconds for interactions](https://docs.slack.dev/interactivity/handling-user-interaction/). A browser GET or successful outbound message does not verify these POST callbacks.

If all inbound connectivity is prohibited, an already authorized app can still send messages with outbound HTTPS, but events, buttons, shortcuts, and commands cannot work. OneUptime's manifest uses HTTP callbacks and disables Socket Mode; turning on Slack Socket Mode is not a supported substitute for these routes. The [private network access setting](/docs/self-hosted/private-network-access) controls outbound requests to private destinations and does not expose callbacks to Slack.
