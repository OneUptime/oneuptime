# Runbook क्रेडेंशियल

क्रेडेंशियल वह तरीक़ा है जिससे कोई Runbook ऐसी चीज़ तक पहुँचता है जो Runner का अपना होस्ट **नहीं** है: SSH से कोई सर्वर, या कोई Kubernetes क्लस्टर। इसके बिना "सेवा रीस्टार्ट करो" का मतलब है एक शेल स्क्रिप्ट लिखना और Runner के होस्ट पर हाथ से एक की या kubeconfig रखना, जहाँ वह OneUptime के नियंत्रण से बाहर डिस्क पर पड़ी रहती है। क्रेडेंशियल वही एक्सेस एक प्रबंधित ऑब्जेक्ट के रूप में है: स्टोरेज में एन्क्रिप्टेड, ख़ास Runner को सौंपा हुआ, और किसी चरण से नाम से संदर्भित।

इन्हें **रनबुक → Runbook एजेंट → क्रेडेंशियल** में प्रबंधित करें।

:::cards
- [क्रेडेंशियल बनाएँ](#क्रेडेंशियल-बनाएँ): उसका एक्सेस और वे Runner जो उसे इस्तेमाल कर सकते हैं।
- [दूसरी तरफ़ न्यूनतम अधिकार](#दूसरी-तरफ़-न्यूनतम-अधिकार): सीमित करें कि की या टोकन क्या कर सकता है।
- [स्क्रिप्ट के लिए सीक्रेट](#स्क्रिप्ट-के-लिए-सीक्रेट): किसी Bash या JavaScript स्क्रिप्ट को पासवर्ड या टोकन दें।
:::

## क्रेडेंशियल का इस्तेमाल कैसे होता है

```mermaid title="क्रेडेंशियल उस सिस्टम तक कैसे पहुँचता है जिसे वह खोलता है"
flowchart TB
    step["SSH या Kubernetes चरण"] -->|"नाम लेता है"| cred["क्रेडेंशियल, OneUptime में एन्क्रिप्टेड"]
    step -->|"इशारा करता है"| runner["Runner"]
    cred -->|"सौंपा गया"| runner
    runner -->|"चरण क्लेम करता है और सीक्रेट पाता है"| target["SSH होस्ट या Kubernetes API सर्वर"]
```

एक SSH या Kubernetes चरण एक क्रेडेंशियल और एक Runner का नाम लेता है। जब वह Runner चरण क्लेम करता है, तो OneUptime जाँचता है कि क्रेडेंशियल उसे सौंपा गया है, सीक्रेट को डिक्रिप्ट करता है और उसे केवल उस क्लेम के जवाब में देता है। सीक्रेट कभी जॉब पर सहेजा नहीं जाता और कभी API से पढ़ा नहीं जा सकता।

## शुरू करने से पहले

- **क्रेडेंशियल प्रबंधित करने वाली भूमिका।** Project Owner और Project Admin, या **Create Runbook Credential** अनुमति वाला कोई भी व्यक्ति। Runbook Admin भूमिका में यह शामिल नहीं है। OneUptime AI की कमांड चलाने वाले Runner को SSH क्रेडेंशियल सौंपने के लिए **Read Runbook Credential** भी चाहिए; [OneUptime AI की कमांड चलाने वाले Runner](#oneuptime-ai-की-कमांड-चलाने-वाले-runner) देखें।
- **ऐसा प्लान जिसमें ये शामिल हों।** OneUptime Cloud पर Runbook क्रेडेंशियल के लिए **Growth** या उससे ऊँचा प्लान चाहिए।
- **एक [Runner](/docs/runbooks/agents)** जो नेटवर्क पर होस्ट या क्लस्टर के API सर्वर तक पहुँच सके।

## क्रेडेंशियल बनाएँ

:::steps
### क्रेडेंशियल खोलें

**रनबुक → Runbook एजेंट → क्रेडेंशियल** खोलें, और **Runbook Credential बनाएँ** पर क्लिक करें।

### इसे नाम दें और प्रकार चुनें

**Credential** चरण में एक **नाम** दर्ज करें, जैसे `prod-cluster`, एक वैकल्पिक **विवरण** और **प्रकार**: **SSH** या **Kubernetes**। प्रकार बाद में नहीं बदला जा सकता; इसकी जगह नया क्रेडेंशियल बनाएँ।

### एक्सेस दर्ज करें

:::tabs
@tab SSH
**SSH होस्ट** के नीचे **होस्टनाम**, **पोर्ट** (ख़ाली हो तो 22) और **उपयोगकर्ता नाम** दर्ज करें। **SSH प्रमाणीकरण** के नीचे एक **Private Key (PEM)** उसके **Private Key Passphrase** के साथ (अगर हो) चिपकाएँ, या बिना की एक्सेस वाले होस्ट के लिए **पासवर्ड** दर्ज करें। जब विकल्प हो, तो की सबसे अच्छा चुनाव है।
@tab Kubernetes
**Kubernetes** के नीचे **API Server URL**, जैसे `https://10.0.0.1:6443`, **Service Account Token** और **CA Certificate (PEM)** दर्ज करें, ताकि Runner API सर्वर की पुष्टि कर सके। CA को केवल तभी ख़ाली छोड़ें जब API सर्वर ऐसा प्रमाणपत्र दिखाता हो जिस पर Runner पहले से भरोसा करता है।
:::

### इसे Runner को सौंपें

**Runbook एजेंट** चरण में वे Runner चुनें जो इस क्रेडेंशियल को इस्तेमाल कर सकते हैं, फिर **Runbook Credential बनाएँ** पर क्लिक करें। जो क्रेडेंशियल किसी Runner को नहीं सौंपा गया, उसे कोई चरण इस्तेमाल नहीं कर सकता।

### इसे किसी चरण में इस्तेमाल करें

किसी [SSH या Kubernetes चरण](/docs/runbooks/authoring#चरण-के-प्रकार) में उन Runner में से एक चुनें, फिर **Credential** के नीचे क्रेडेंशियल चुनें। चरण केवल अपने ही प्रकार के क्रेडेंशियल दिखाता है, और क्रेडेंशियल का नाम लेने वाले चरण को सहेजने के लिए Runbook क्रेडेंशियल पढ़ने की अनुमति चाहिए।
:::

## क्या सहेजा जाता है

| प्रकार | फ़ील्ड |
| --- | --- |
| SSH | होस्टनाम, पोर्ट (डिफ़ॉल्ट 22), उपयोगकर्ता नाम, और या तो PEM प्राइवेट की (वैकल्पिक पासफ़्रेज़ के साथ) या पासवर्ड। |
| Kubernetes | API सर्वर URL, सर्विस अकाउंट टोकन और क्लस्टर का CA प्रमाणपत्र। |

## सीक्रेट मान केवल लिखे जा सकते हैं

प्राइवेट की, पासफ़्रेज़, पासवर्ड और सर्विस अकाउंट टोकन स्टोरेज में एन्क्रिप्टेड हैं, और API उन्हें **कभी नहीं लौटाता**: न डैशबोर्ड को, न किसी वर्कफ़्लो को, न किसी एक्सपोर्ट में। तालिका आपको दिखा सकती है कि क्रेडेंशियल *क्या है*, लेकिन कभी यह नहीं कि उसमें क्या है।

इसलिए सीक्रेट मान के लिए कोई "दिखाएँ" नहीं है, केवल "बदलें": मान दोबारा दर्ज करना ही उसे रोटेट करने का तरीक़ा है। अगर मूल मान खो गया है, तो लक्ष्य सिस्टम पर नई की जारी करें और क्रेडेंशियल अपडेट करें।

## क्रेडेंशियल को Runner को सौंपना

क्रेडेंशियल केवल वही Runner इस्तेमाल कर सकते हैं जिन्हें आप इसे सौंपते हैं, और चरण को उनमें से किसी एक की ओर इशारा करना चाहिए। अगर कोई चरण ऐसे क्रेडेंशियल का नाम लेता है जो उसके Runner को नहीं सौंपा गया, तो **चरण चलने के बजाय विफल होता है**: चुपचाप कुछ न करने वाला Runner बिल्कुल सफल Runner जैसा दिखता है।

सौंपना ही एक्सेस की सीमा है, इसलिए इसे संकरा रखें: जो Runner केवल एक क्लस्टर रीस्टार्ट करता है, उसे आपके डेटाबेस होस्ट की SSH की की ज़रूरत नहीं।

### OneUptime AI की कमांड चलाने वाले Runner

जिस Runner पर **AI उपचार कमांड चलाता है** चालू है, उस पर OneUptime AI वहाँ चलाई जाने वाली कमांड के लिए Runner को सौंपे गए SSH क्रेडेंशियल में से चुनता है। इसलिए SSH क्रेडेंशियल ऐसे Runner तक केवल उस व्यक्ति के ज़रिए पहुँचता है जो Runbook क्रेडेंशियल पढ़ सकता है (**Read Runbook Credential**, या Project Owner या Project Admin), चाहे पहले कुछ भी सहेजा जाए:

- **क्रेडेंशियल सौंपना।** ऐसे Runner के साथ SSH क्रेडेंशियल बनाने, या किसी क्रेडेंशियल में ऐसा Runner जोड़ने के लिए वह अनुमति चाहिए। उसके बिना सहेजना अस्वीकार हो जाता है और Runner का नाम बताया जाता है: क्रेडेंशियल ऐसे Runner को सौंपें जो AI उपचार कमांड नहीं चलाते, या अनुमति वाले किसी व्यक्ति से उसे सौंपने को कहें।
- **स्विच चालू करना।** SSH क्रेडेंशियल वाले Runner के लिए **AI उपचार कमांड चलाता है** चालू करने के लिए भी वही अनुमति चाहिए।

किसी क्रेडेंशियल से Runner हटाना, क्रेडेंशियल को उसके मौजूदा Runner के साथ ही सहेजना, और Kubernetes क्रेडेंशियल के लिए इससे ज़्यादा कुछ नहीं चाहिए: OneUptime AI की kubectl कमांड अपने क्लस्टर से बँधे क्रेडेंशियल के साथ चलती हैं। उस अनुमति के बिना किसी व्यक्ति द्वारा किए गए क्रेडेंशियल असाइनमेंट और स्विच चालू करना किसी प्रोजेक्ट में एक-एक करके सहेजे जाते हैं, ताकि दोनों एक साथ अपनी जाँच पास न कर सकें; किसी दूसरे के सहेजे जाते समय आने वाला सहेजना उसकी प्रतीक्षा करता है, और बहुत देर लगने पर *Try again in a moment* के साथ अस्वीकार हो जाता है। फिर से सहेजें।

किसी वर्कफ़्लो का चरण Project Admin की तरह काम करता है, लेकिन Project Admin का Runbook क्रेडेंशियल पढ़ने का अधिकार उधार नहीं लेता: चरण के पास यह तभी होता है जब वर्कफ़्लो के चरण आख़िरी बार सहेजने वाले व्यक्ति के पास हो। [वर्कफ़्लो के चरण क्या कर सकते हैं](/docs/workflows/configuration#वर्कफ़्लो-के-चरण-क्या-कर-सकते-हैं) देखें।

## दूसरी तरफ़ न्यूनतम अधिकार

OneUptime यह सीमित नहीं कर सकता कि आपका क्रेडेंशियल लक्ष्य सिस्टम पर क्या कर सकता है: यह लक्ष्य सिस्टम का काम है, और करने लायक है:

- **SSH** — पासवर्ड से ज़्यादा की को प्राथमिकता दें, उपयोगकर्ता को केवल उसकी ज़रूरत की कमांड दें (जहाँ व्यावहारिक हो, फ़ोर्स्ड कमांड या सीमित शेल), और किसी एडमिन की निजी की दोबारा इस्तेमाल न करें।
- **Kubernetes** — सर्विस अकाउंट को एक ऐसे Role से बाँधें जो ठीक उन्हीं वर्कलोड पर `patch` की अनुमति दे जिन्हें आपके Runbook छूते हैं, ठीक उन्हीं नेमस्पेस में जिनमें वे चलते हैं। **Restart workload** ख़ुद वर्कलोड को पैच करता है, और **Scale workload** उसके `scale` सबरिसोर्स को: इससे ज़्यादा कुछ नहीं चाहिए।

उदाहरण के लिए, एक सर्विस अकाउंट जो एक Deployment को रीस्टार्ट और स्केल कर सकता है, और कुछ नहीं:

```yaml title="oneuptime-runbooks-rbac.yaml"
apiVersion: v1
kind: ServiceAccount
metadata:
  name: oneuptime-runbooks
  namespace: checkout
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: oneuptime-runbooks
  namespace: checkout
rules:
  # Restart workload: patches the Deployment's pod template.
  - apiGroups: ["apps"]
    resources: ["deployments"]
    resourceNames: ["checkout-api"]
    verbs: ["patch"]
  # Scale workload: patches the Deployment's scale subresource.
  - apiGroups: ["apps"]
    resources: ["deployments/scale"]
    resourceNames: ["checkout-api"]
    verbs: ["patch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: oneuptime-runbooks
  namespace: checkout
subjects:
  - kind: ServiceAccount
    name: oneuptime-runbooks
    namespace: checkout
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: oneuptime-runbooks
```

StatefulSet या DaemonSet के लिए इसकी जगह `statefulsets` या `daemonsets` इस्तेमाल करें। DaemonSet को स्केल नहीं किया जा सकता, इसलिए उसे `scale` नियम की ज़रूरत नहीं।

## स्क्रिप्ट के लिए सीक्रेट

Bash और JavaScript चरणों में कोई **Credential** फ़ील्ड नहीं होता। किसी स्क्रिप्ट को Runbook में लिखे बिना पासवर्ड, टोकन या API की देने के लिए उसे **Runbook सीक्रेट** के रूप में सहेजें। सीक्रेट **रनबुक → सेटिंग्स → सीक्रेट** में Project Owner और Project Admin द्वारा, या **Create Runbook Secret** अनुमति के साथ प्रबंधित होते हैं।

:::steps
### सीक्रेट बनाएँ

**Runbook Secret बनाएँ** पर क्लिक करें। **रहस्य** चरण में एक **नाम** (अक्षर, अंक, हाइफ़न और अंडरस्कोर), एक वैकल्पिक **विवरण** और **सीक्रेट मान** दर्ज करें। **एक्सेस** चरण में **Runbook एजेंट जिनकी इस सीक्रेट तक पहुंच है** के नीचे Runner चुनें।

### इसे स्क्रिप्ट में इस्तेमाल करें

जहाँ मान आना चाहिए, वहाँ `{{runbookSecrets.NAME}}` लिखें:

```bash
curl -s -X POST \
  -H "Authorization: Bearer {{runbookSecrets.CDN_API_TOKEN}}" \
  "https://api.cdn.example.com/v1/purge"
```

जब कोई Runner, जिसे सीक्रेट सौंपा गया है, चरण क्लेम करता है, तो उसे स्क्रिप्ट मान भरकर मिलती है।
:::

क्रेडेंशियल के सीक्रेट फ़ील्ड की तरह, सीक्रेट का मान स्टोरेज में एन्क्रिप्टेड है और API उसे कभी नहीं लौटाता: **सीक्रेट मान अपडेट करें** उसे बदल देता है। OneUptime Cloud पर Runbook सीक्रेट के लिए भी **Growth** या उससे ऊँचा प्लान चाहिए।

| | क्रेडेंशियल | Runbook सीक्रेट |
| --- | --- | --- |
| कौन इस्तेमाल करता है | SSH और Kubernetes चरण | Bash और JavaScript स्क्रिप्ट |
| इसमें क्या होता है | एक होस्ट और उसकी की, या किसी क्लस्टर का URL और टोकन | कोई भी एक अकेला मान |
| कहाँ प्रबंधित होता है | **रनबुक → Runbook एजेंट → क्रेडेंशियल** | **रनबुक → सेटिंग्स → सीक्रेट** |
| Runner तक कैसे पहुँचता है | उसका नाम लेने वाले चरण के क्लेम के जवाब में | जिस चरण को वह क्लेम करता है उसकी स्क्रिप्ट में भरकर |
| क्या API से फिर पढ़ा जा सकता है | केवल उसके गैर-सीक्रेट फ़ील्ड | उसका मान कभी नहीं |

## इन्हें कौन देख सकता है

क्रेडेंशियल बनाने, संपादित करने और हटाने के लिए Runbook क्रेडेंशियल अनुमतियाँ (या Project Owner/Admin) चाहिए। क्रेडेंशियल पढ़ने पर केवल उसके गैर-सीक्रेट फ़ील्ड दिखते हैं।

ध्यान दें कि किसी Runner की **एजेंट कुंजी** उस Runner को सौंपे गए क्रेडेंशियल के बराबर है: जिसके पास भी कुंजी है, वह उस Runner के रूप में काम क्लेम कर सकता है और क्रेडेंशियल पा सकता है। इसीलिए एजेंट कुंजियाँ केवल Project Owner, Project Admin और Runbook Admin पढ़ सकते हैं: उन्हें ख़ुद क्रेडेंशियल की तरह ही संभालें।
