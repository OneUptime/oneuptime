# रन और लॉग

जब भी कोई वर्कफ़्लो चलता है, OneUptime इसका ब्यौरा सहेज लेता है — कब चला, बात बनी या नहीं, और हर block ने क्या किया। इसी ब्यौरे को **run** कहते हैं। Runs से ही आप पक्का करते हैं कि वर्कफ़्लो चला, बिगड़े हुए वर्कफ़्लो की जड़ तक पहुँचते हैं, और पुरानी गतिविधि पलटकर देखते हैं।

## ये कहाँ मिलते हैं

| पेज                          | आपको क्या दिखता है                                                                                  |
| --------------------------- | ---------------------------------------------------------------------------------------------------- |
| **वर्कफ़्लो → रन और लॉग**       | प्रोजेक्ट के हर वर्कफ़्लो का हर run। वर्कफ़्लो के नाम, स्थिति और समय से छान सकते हैं।                       |
| **वर्कफ़्लो → रन और लॉग**       | सिर्फ़ इसी एक वर्कफ़्लो के runs। यहाँ वर्कफ़्लो वाले फ़िल्टर की जगह **रन ID** का फ़िल्टर मिलता है।              |
| **कोई एक run**               | run की पंक्ति पर मौजूद **लॉग्स देखें** बटन से खुलता है — पंक्तियाँ खुद क्लिक करने लायक नहीं होतीं।         |

## Run की स्थितियाँ

| स्थिति                              | इसका मतलब                                                                                                                                                  |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **निर्धारित**                        | trigger चल चुका है और run किसी runner के लिए कतार में है। आम तौर पर सेकंड के किसी हिस्से भर का मामला। 5 मिनट बाद भी निर्धारित पड़ा run नाकाम मान लिया जाता है — उसे किसी ने उठाया ही नहीं। |
| **चल रहा है**                        | वर्कफ़्लो चल रहा है। देर तक चलने वाले blocks run को इसी हालत में रोके रखते हैं।                                                                                  |
| **प्रतीक्षारत**                       | run किसी **Sleep** block पर टिका है और अपने-आप आगे बढ़ जाएगा। इंतज़ार के दौरान यह कोई worker नहीं घेरता।                                                          |
| **Executed**                       | run बिना नाकाम हुए अंत तक पहुँच गया। (यही सफलता वाली हालत है — pill पर **Executed** लिखा आता है, "Success" नहीं।)                                              |
| **त्रुटि**                           | किसी block ने त्रुटि दी और run रुक गया। यही हालत तब भी दर्ज होती है जब कतार में पड़ा run कभी उठाया ही न जाए, सोए हुए run का जागना खो जाए, कोई schedule expression हल न हो पाए, या बीच run में वर्कफ़्लो बंद कर दिया जाए। |
| **Timeout**                        | run तय समय से ज़्यादा देर चला। देखिए [वर्कफ़्लो कॉन्फ़िगरेशन और सुरक्षा](/docs/workflows/configuration)।                                                            |
| **Execution Exceeded Current Plan** | प्रोजेक्ट पिछले 30 दिनों के अपने वर्कफ़्लो runs खर्च कर चुका है, या subscription का भुगतान बाकी है। run दर्ज तो होता है, पर चलता नहीं। सिर्फ़ OneUptime Cloud पर। |

जो block अपने **त्रुटि** output से आगे बढ़ता है — मान लीजिए 4xx पर कोई API block — वह run को नाकाम नहीं करता। त्रुटि वाली शाखा चलती है और run फिर भी **Executed** पर खत्म होता है। हाँ, वह चरण खुद लाल ही दिखता है ताकि आप उसे ढूँढ सकें।

## कोई run पढ़ना

किसी run पर **लॉग्स देखें** दबाकर उसे खोलिए। **Workflow Run** दृश्य में दो tab होते हैं।

**चरण** — जो-जो block चला, क्रम से उसकी एक पंक्ति। हर पंक्ति block का शीर्षक, उसका घटक id, उसमें लगा समय, और वह output दिखाती है जिससे वह निकला (`→ success`, `→ error`, `→ yes`)। पंक्ति खोलिए तो ब्यौरे के दो हिस्से मिलते हैं:

- **Received** — सारे variables हल हो जाने के बाद block को जो सेटिंग्स मिलीं।
- **Returned** — उसने क्या पैदा किया।

नाकाम चरण लाल होते हैं और पहले से खुले आते हैं, जिनमें त्रुटि का संदेश **Received** के ऊपर छपा रहता है।

**Full Log** — runner ने जो कच्चा, पंक्ति-दर-पंक्ति log छापा, उसमें blocks का अपना लिखा हुआ सब कुछ शामिल। जब चरण वाला दृश्य नाकामी की वजह न बता पाए, तब इसे देखिए।

दो बातें जान लेना काम आता है। हर चरण के शीर्षक के नीचे छपा घटक id ठीक वही string है जिसे `{{local.components.<id>.returnValues.…}}` reference में चिपकाना है — reference सही लिखने का इससे तेज़ रास्ता कोई नहीं। और हर run अपने आख़िरी 100 चरण ही रखता है — लंबे या बार-बार आगे बढ़ाए गए run में, जहाँ पुराने चरण छोड़ दिए गए, वहाँ अंबर रंग की एक टिप्पणी दिख जाती है।

जो मान दिखते हैं, वे वही हैं जो variables भरे जाने के बाद block ने देखे — दो अपवादों के साथ: रहस्य और वे फ़ील्ड जिन्हें block संवेदनशील बताता है, छिपा दिए जाते हैं, और बहुत लंबे मान "… (truncated)" कहकर काट दिए जाते हैं।

**बिल्डर** से run शुरू करने पर यही दृश्य पहले से run के पीछे-पीछे चलता हुआ खुल जाता है, इसलिए आप सब कुछ होते हुए देख सकते हैं — बाद में ढूँढने जाने की ज़रूरत नहीं।

## आम गड़बड़ियाँ सुलझाना

### "मेरा वर्कफ़्लो चला ही नहीं।"

1. पक्का कीजिए कि वर्कफ़्लो अपने **अवलोकन** पेज पर **सक्षम** है। नए वर्कफ़्लो बंद हालत में शुरू होते हैं, और बंद वर्कफ़्लो हर run लौटा देता है — हाथ से चलाए गए भी।
2. OneUptime ईवेंट trigger के लिए: पक्का कीजिए कि ईवेंट सचमुच हुआ था। रिकॉर्ड खोलकर उसका इतिहास देखिए।
3. वेबहुक trigger के लिए: पक्का कीजिए कि दूसरा सिस्टम सही URL पर भेज रहा है। ज़्यादातर tools वेबहुक भेजते समय उसका log रखते हैं — वहाँ देख लीजिए।
4. schedule trigger के लिए: पक्का कीजिए कि cron expression उसी समय से मेल खाता है जिसकी आप उम्मीद कर रहे हैं।

अगर run दिखता *तो* है, पर स्थिति **Execution Exceeded Current Plan** है, तो प्रोजेक्ट पिछले 30 दिनों के अपने सारे वर्कफ़्लो runs खर्च कर चुका है, या subscription का भुगतान बाकी है। run का log गिनती और आपकी योजना की सीमा, दोनों बता देता है। यह सिर्फ़ OneUptime Cloud पर लागू होता है।

### "बाद वाला कोई block कभी चला ही नहीं।"

जो block नहीं चलता, उसके पीछे आम तौर पर जोड़-तोड़ की ग़लती होती है। **बिल्डर** खोलिए और जाँचिए:

- क्या पिछले block का output इस block के input से जुड़ा है?
- क्या पिछला block आपकी सोच से अलग output से निकला — **सफलता** की जगह **त्रुटि**, या **हाँ** की जगह **नहीं**? **चरण** tab बता देता है कि वह किससे निकला।

### "कोई variable खाली आया।"

run खोलिए और नाकाम चरण का **Received** हिस्सा देखिए।

- अगर वहाँ अक्षरशः `{{local.components.…}}` लिखा दिखे, तो reference हल ही नहीं हुई। आम तौर पर घटक id या return-value id में कोई टाइपिंग की चूक होती है — याद रखिए, यह block का **Identifier** है, उस पर दिखने वाला नाम नहीं। `local.components` की अपनी वर्तनी भी जाँच लीजिए: `{{local.componets.api-get-1.returnValues.response-body}}` सादे text के रूप में भेज दिया जाता है और run फिर भी **Executed** बताता है।
- अगर खाली string दिखे, तो पिछला block चला तो था, पर उसने वह फ़ील्ड पैदा नहीं की।

**Full Log** tab में एक चेतावनी पंक्ति हर उस reference का नाम लेती है जो हल नहीं हुई — उसे ढूँढने का यही सबसे तेज़ तरीका है।

### "हाथ से चलाने पर काम करता है, trigger से नहीं।"

**बिल्डर** खोलिए, **वर्कफ़्लो चलाएं** दबाइए, और trigger के फ़ील्ड ऐसे मानों से भरिए जो असली trigger के भेजे मानों जैसे दिखें। फिर उस run के **Received** मानों को असली run के मानों के साथ आमने-सामने रखकर देखिए। फ़र्क़ आम तौर पर किसी एक फ़ील्ड के नाम या क़िस्म का निकलता है।

## वर्कफ़्लो दोबारा चलाना

"इस run को फिर चलाओ" जैसा कोई बटन नहीं है। हम पुराने executions अपने-आप दोबारा नहीं चलाते, क्योंकि उनके असर — Slack संदेश, API calls, टिकट — दोहराने लायक सुरक्षित हों, ज़रूरी नहीं। काम दोबारा कराना हो तो वर्कफ़्लो सुधारिए और अगले असली trigger को उसे चलाने दीजिए, या **बिल्डर** खोलकर उन्हीं मानों के साथ **वर्कफ़्लो चलाएं** दबाइए।

## Runs कब तक रखे जाते हैं?

OneUptime Cloud पर runs **30 दिन** रखे जाते हैं और फिर हटा दिए जाते हैं — इसीलिए दोनों run सूचियाँ खुद को पिछले 30 दिनों की सूची बताती हैं। स्व-होस्टेड installs runs तब तक रखते हैं जब तक आप उन्हें न हटाएँ; कोई वर्कफ़्लो बहुत बार चलकर आपका इतिहास भर रहा हो, तो शोर बढ़ना रोकने के लिए उसे बंद कर दीजिए या हटा दीजिए।

चरणों का हिसाब रखने की सुविधा जुड़ने से पहले दर्ज हुए runs में कोई **चरण** सामग्री नहीं होती, उनका सिर्फ़ **Full Log** दिखता है।
