# مانیتور Docker Swarm

مانیتورینگ Docker Swarm به شما امکان می‌دهد سلامت و کارایی خوشه‌های Docker Swarm خود را زیر نظر بگیرید — کانتینرهایی که پشت هر وظیفه سرویس در سراسر گره‌های خوشه‌اند. OneUptime سنجه‌ها را از راه جمع‌کننده‌ای از پیش پیکربندی‌شده از OpenTelemetry (**عامل Docker Swarm در OneUptime**) که روی گره مدیر اجرا می‌شود جمع می‌کند، و بر پایه معیارهای پیکربندی‌شده شما می‌سنجدشان.

## نمای کلی

مانیتورهای Docker Swarm از سنجه‌های کانتینر به ازای هر وظیفه در خوشه‌تان برای دید به بارهای کاری Swarm استفاده می‌کنند. این به شما امکان می‌دهد:

- فشار CPU و حافظه به ازای هر وظیفه را در هر سرویسی زیر نظر بگیرید
- وظیفه‌هایی را که فرو می‌ریزند، بازراه‌اندازی می‌شوند یا دوباره زمان‌بندی می‌شوند تشخیص دهید (وظیفه جایگزین آپ‌تایمی زیر ۶۰ ثانیه نشان می‌دهد)
- شمار فرایندهای وظیفه را برای بمب انشعاب یا نشت منابع بپایید
- هشدارها را به یک سرویس، گره یا کانتینر وظیفه محدود کنید

## ساختن یک مانیتور Docker Swarm

1. در داشبورد OneUptime به **Monitors** بروید
2. روی **Create Monitor** کلیک کنید
3. نوع مانیتور را **Docker Swarm** برگزینید
4. خوشه Docker Swarmای را که باید زیر نظر گرفته شود برگزینید
5. پرس‌وجوهای سنجه و تجمیع را پیکربندی کنید (یا قالبی برگزینید)
6. معیارهای مانیتورینگ را به‌فراخور پیکربندی کنید

## گزینه‌های پیکربندی

### خوشه Docker Swarm

خوشه Docker Swarmای را که باید زیر نظر گرفته شود برگزینید. خوشه‌ها نخستین بار که عامل Docker Swarm در OneUptime از آن‌ها تله‌متری می‌فرستد خودکار ثبت می‌شوند (کلیدخورده بر پایه ویژگی منبع `docker.swarm.cluster.name`) — لازم نیست دستی بسازیدشان.

### پرس‌وجوهای سنجه

یک یا چند پرس‌وجوی سنجه برای سنجش پیکربندی کنید. هر پرس‌وجو این‌ها را مشخص می‌کند:

- **نام سنجه** — سنجه کانتینری که پرس‌وجو می‌شود (سری‌های `container.*` که گیرنده docker_stats منتشر می‌کند)
- **تجمیع** — اینکه مقادیر سنجه چگونه تجمیع شوند (میانگین، مجموع، بیشینه، کمینه)
- **پالایه‌ها** — پالایش اختیاری بر پایه ویژگی روی هویت کانتینر (پایین‌تر را ببینید)
- **Group By** — اختیاراً بر پایه ویژگی `resource.container.name` گروه‌بندی کنید تا هر وظیفه Swarm مستقل سنجیده شود — یک حادثه به ازای هر وظیفه

می‌توانید **فرمول‌هایی** هم بسازید که چند پرس‌وجوی سنجه را با عبارت‌های ریاضی ترکیب می‌کنند.

### سنجه‌ها

عامل Docker Swarm در OneUptime گیرنده **docker_stats** از OpenTelemetry را روی کانتینرهای خوشه اجرا می‌کند، پس سری‌هایی که می‌رسند سنجه‌های استاندارد زمان اجرای کانتینرند:

| سنجه | توضیح |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `container.cpu.utilization` | بهره‌برداری CPU (٪) کانتینر یک وظیفه (۱۰۰٪ = یک هسته کامل) |
| `container.memory.usage.total` | کل حافظه مصرف‌شده توسط کانتینر یک وظیفه (بایت) |
| `container.memory.percent` | حافظه مصرف‌شده به‌صورت درصدی از محدودیت کانتینر، یا از کل حافظه گره وقتی سرویس محدودیتی نگذارد |
| `container.network.io.usage.rx_bytes` | بایت‌های دریافت‌شده روی شبکه |
| `container.network.io.usage.tx_bytes` | بایت‌های فرستاده‌شده روی شبکه |
| `container.pids.count` | شمار فرایندهای درون کانتینر |
| `container.uptime` | کانتینر وظیفه چقدر در حال اجرا بوده (ثانیه) |

سنجه‌های `docker_swarm_*` وجود **ندارند** — توپولوژی Swarm (گره‌ها، سرویس‌ها، وظیفه‌ها) جداگانه به‌عنوان موجودی جمع می‌شود، نه به‌عنوان سنجه. این سری‌های سنجه، کانتینرهایی را توصیف می‌کنند که پشت هر وظیفه سرویس‌اند.

### دامنه خوشه و هویت کانتینر

هر سنجه‌ای که عامل جمع می‌کند با **ویژگی منبع** `docker.swarm.cluster.name` محدود می‌شود که عامل روی کل دسته مهر می‌زند. مانیتور همیشه این دامنه را از خوشه‌ای که برگزیده‌اید اعمال می‌کند — دستی پیکربندی‌اش نمی‌کنید. عامل `container.runtime` یا `host.name` را مهر **نمی‌زند**، پس مانیتور هرگز روی آن‌ها نمی‌پالاید.

سنجه‌های هر کانتینر به‌عنوان **منبع** OTLP خودشان می‌رسند، پس هویت کانتینر با پیشوند `resource.` در ClickHouse ذخیره می‌شود:

| ویژگی | معنا | نمونه |
| ------------------------------- | ----------------------------------------------------------- | -------------- |
| `resource.container.name` | کانتینر یک وظیفه Swarm، با نام `<service>.<slot>.<taskid>` | `web.1.abc123` |
| `resource.container.image.name` | ایمیج کانتینر | `nginx:latest` |
| `docker.swarm.service.name` | سرویس Swarm مالک (وقتی مهر شود) | `web` |
| `docker.swarm.node.name` | گره Swarmای که وظیفه رویش اجرا می‌شود (وقتی مهر شود) | `swarm-node-1` |

برای محدود کردن پرس‌وجویی روی `resource.container.image.name`، `docker.swarm.service.name` یا `docker.swarm.node.name` بپالایید، برای محدود کردن به یک وظیفه روی `resource.container.name`، و برای ارزیابی مستقل هر وظیفه بر پایه `resource.container.name` گروه‌بندی کنید — یک حادثه به ازای هر وظیفه.

### پنجره زمانی غلتان

پنجره زمانی ارزیابی سنجه را برگزینید:

- ۱ دقیقه گذشته
- ۵ دقیقه گذشته
- ۱۰ دقیقه گذشته
- و پنجره‌های بلندتر

## قالب‌های هشدار

زبانه Quick Setup قالب‌های آماده‌ای ارائه می‌دهد که سنجه، تجمیع، گروه‌بندی، بازه زمانی و آستانه‌ها را خودکار پیکربندی می‌کنند:

| قالب | شدت | شلیک می‌کند وقتی |
| --------------------------- | -------- | -------------------------------------------------------------------------------------------------------------- |
| **Task Down (Low Uptime)** | بحرانی | `container.uptime` هر وظیفه‌ای زیر ۶۰ ثانیه باشد (دوباره زمان‌بندی، بازراه‌اندازی، یا فروریخته و جایگزین شده) |
| **High Task CPU Usage** | هشدار | `container.cpu.utilization` هر وظیفه‌ای از ۸۰٪ یک هسته CPU بگذرد (۱۰۰٪ = یک هسته کامل) |
| **High Task Memory Usage** | هشدار | `container.memory.percent` هر وظیفه‌ای از ۸۵٪ محدودیتش بگذرد (یا از حافظه گره، برای سرویس‌های بدون محدودیت) |
| **High Task Process Count** | هشدار | `container.pids.count` هر وظیفه‌ای از ۵۰۰ بگذرد |

هر قالبی بر پایه `resource.container.name` گروه‌بندی می‌کند، پس به ازای هر وظیفه متأثر یک حادثه شلیک می‌شود.

## موجودی

گره‌ها، سرویس‌ها و وظیفه‌های Swarm جدا از این سنجه‌ها به‌عنوان **موجودی** ردیابی می‌شوند (جدول `DockerSwarmResource`، در دسترس زیر صفحه‌های خوشه). از موجودی برای مرور توپولوژی خوشه استفاده کنید؛ از مانیتور برای هشدار بر سلامت هر وظیفه.

## معیارها و حادثه‌ها

مانیتورهای Docker Swarm بر پایه سری‌های سنجه به ازای هر وظیفه می‌سنجند. وقتی آستانه معیاری شکسته شود، OneUptime حادثه/هشداری با تفکیک ریشه علت می‌سازد که وظیفه‌های متأثر (نام کانتینر، سرویس، گره و مقدار سنجه) را فهرست می‌کند. حادثه‌ها و هشدارهایی که مانیتور Docker Swarm می‌سازد خودکار به خوشه پیوند می‌خورند، پس در صفحه‌های فعالیت خوشه پدیدار می‌شوند.
