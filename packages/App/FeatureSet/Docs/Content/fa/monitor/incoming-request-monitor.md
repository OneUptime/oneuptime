# مانیتور درخواست ورودی

مانیتور درخواست ورودی نشانی‌ای به شما می‌دهد که سامانه‌های دیگر درخواست‌های HTTP را به آن می‌فرستند. OneUptime هر درخواستی را بر پایه معیارهای شما می‌سنجد، و می‌تواند وضعیت مانیتور را تغییر دهد، حادثه اعلام کند، و چرخش کشیک شما را فرا بخواند.

دو کار متفاوت را پوشش می‌دهد:

- **مانیتورینگ ضربان قلب** — کاری زمان‌بندی‌شده، کارگری یا دستگاهی روی زمان‌بندی‌ای نشانی را پینگ می‌کند، و OneUptime وقتی پینگ‌ها بند بیایند حادثه‌ای برمی‌انگیزد.
- **دریافت هشدار از سامانه‌ای دیگر** — ‏Prometheus Alertmanager، ‏Grafana، یا هر چیز دیگری که بتواند JSON ‏POST کند هشدارها را به درون می‌فرستد، و OneUptime هرکدام را به حادثه‌ای با تشدید کشیک و برطرف شدن خودکار هنگام بهبود تبدیل می‌کند.

هر دو همان نوع مانیتور را به کار می‌برند. آنچه جداشان می‌کند معیارهایی است که پیکربندی می‌کنید.

## نمای کلی

مانیتورهای درخواست ورودی نشانی یکتایی فراهم می‌کنند که سرویس‌هایتان فرا می‌خوانند. این به شما امکان می‌دهد:

- کارهای زمان‌بندی‌شده و وظیفه‌های cron را زیر نظر بگیرید
- تأیید کنید کارگرهای پس‌زمینه در حال اجرایند
- سرویس‌های پشت دیوار آتش را که از بیرون دست‌یافتنی نیستند زیر نظر بگیرید
- از Prometheus Alertmanager، ‏Grafana و دیگر سامانه‌های هشداردهی هشدار بگیرید
- سیگنال‌های ضربان قلب هر سامانه‌ای با توان HTTP را ردیابی کنید

## ساختن یک مانیتور درخواست ورودی

1. در داشبورد OneUptime به **Monitors** بروید
2. روی **Create Monitor** کلیک کنید
3. نوع مانیتور را **Incoming Request** برگزینید
4. یک **Secret Key** و نشانی برای این مانیتور تولید می‌شود
5. مانیتور را باز کنید و در منوی چپ روی **Documentation** کلیک کنید تا نشانی را کپی کنید
6. سرویس خود را برای فرستادن درخواست به آن نشانی پیکربندی کنید
7. معیارهای مانیتورینگ را همان‌گونه که پایین‌تر توضیح داده شده پیکربندی کنید

## نشانی درخواست

مانیتور شما نشانی یکتایی در این قالب دارد:

```
https://oneuptime.com/heartbeat/YOUR_SECRET_KEY
```

اگر خودمیزبان هستید به‌جای `https://oneuptime.com` نشانی نمونه OneUptime خود را بگذارید.

درخواست‌های **GET** یا **POST** به این نشانی بفرستید. HEAD پذیرفته می‌شود و مانند GET رفتار می‌شود. متدهای دیگر ۴۰۴ برمی‌گردانند. کلید محرمانه در مسیر تنها اعتبارنامه است — هیچ هدر یا توکنی لازم نیست.

> **هشدار:** هر کسی که این نشانی را بداند می‌تواند مانیتور را سالم علامت بزند، پس رازش بدانید. هر هدری که می‌فرستید روی مانیتور ذخیره می‌شود و برای هر کسی که بتواند بخواندش دیده می‌شود — کلید API یا توکن را در هدرها به این نقطه پایانی نفرستید.

‏OneUptime بی‌درنگ با `200` خالی پاسخ می‌دهد و درخواست را در صف پردازش می‌کند. آن پاسخ پیش از هر اعتبارسنجی‌ای نوشته می‌شود، پس `200` تأیید **نیست** که درخواست پذیرفته شده — کلید محرمانه اشتباه، مانیتور حذف‌شده و مانیتور غیرفعال هم همه `200` برمی‌گردانند. برای تأیید رسیدن درخواست‌ها، خط زمانی خود مانیتور را بررسی کنید.

### فرستادن بدنه درخواست

اگر می‌خواهید فیلدهای درون بدنه را آدرس‌دهی کنید — `{{requestBody.status}}` در عنوان حادثه، مسیری JSON در گروه‌بندی حادثه، یا معیاری از نوع عبارت JavaScript — هدر `Content-Type: application/json` بفرستید — این قالبی است که این مستندات سرتاسر فرض می‌گیرند. بدنه `application/x-www-form-urlencoded` هم تفکیک می‌شود، اما فقط به فیلدهای تخت سطح بالا. هر نوع محتوای دیگری، یا اصلاً هیچ‌کدام، تفکیک نمی‌شود و هر ارجاع `requestBody` به هیچ تفکیک می‌شود.

بدنه تا ۵۰ مگابایت پذیرفته می‌شود. بدنه را با `Content-Encoding: gzip` فشرده نکنید؛ تفکیک‌نشده ذخیره می‌شود و مسیرهای درونش تفکیک نمی‌شوند.

### فرستادن ضربان قلب

#### با curl

```bash
# Simple GET request
curl https://oneuptime.com/heartbeat/YOUR_SECRET_KEY

# POST request with custom body
curl -X POST https://oneuptime.com/heartbeat/YOUR_SECRET_KEY \
  -H "Content-Type: application/json" \
  -d '{"status": "healthy", "version": "1.2.3"}'
```

#### از یک کار cron

```bash
# Add to crontab to send heartbeat every 5 minutes
*/5 * * * * curl -s https://oneuptime.com/heartbeat/YOUR_SECRET_KEY > /dev/null
```

#### از کد برنامه

```javascript
// Node.js example
const https = require("https");
https.get("https://oneuptime.com/heartbeat/YOUR_SECRET_KEY");
```

```python
# Python example
import requests
requests.get('https://oneuptime.com/heartbeat/YOUR_SECRET_KEY')
```

## معیارهای مانیتورینگ

می‌توانید معیارهایی پیکربندی کنید تا مشخص شود سرویس شما کی آنلاین، تنزل‌یافته یا آفلاین در نظر گرفته می‌شود. هر پالایه معیاری یک **Filter Type** (به چه نگاه شود)، یک **Filter Condition** (چگونه مقایسه شود) و یک **Value** دارد.

### چه چیزی از همان ابتدا می‌گیرید

مانیتور درخواست ورودی تازه با دو معیار ساخته می‌شود که بدنه درخواست را می‌خوانند:

| معیار | نوع پالایه | شرط پالایه | مقدار | اثر |
| -------- | ------------ | ---------------- | ------- | ------------------------------------------ |
| Offline | Request Body | Contains | `error` | مانیتور را آفلاین علامت می‌زند، حادثه‌ای باز می‌کند |
| Online | Request Body | Not Contains | `error` | مانیتور را آنلاین علامت می‌زند |

این حالت رایج را پوشش می‌دهد که فرستنده سلامت خودش را در محموله گزارش می‌کند: درخواستی که بدنه‌اش `error` را می‌آورد مانیتور را پایین می‌آورد، و درخواست بعدی بدون آن، مانیتور را برمی‌گرداند بالا. درخواستی که اصلاً بدنه ندارد «`error` را دربر ندارد» شمرده می‌شود، پس پینگ ساده ضربان قلب مانیتور را آنلاین نگه می‌دارد.

مقدار را به هر چیزی که فرستنده‌تان واقعاً منتشر می‌کند تغییر دهید (`"status":"firing"`، `FAILED` و مانند آن) — تطبیق، آزمونی زیررشته‌ای و حساس به بزرگی و کوچکی حروف است.

این پیش‌فرض‌ها یک کلید مرد مرده **نیستند**: وقتی درخواست‌ها بند بیایند هیچ‌چیز اینجا شلیک نمی‌کند. اگر می‌خواهید بر سکوت هشدار بگیرید، همان‌طور که پایین‌تر آمده معیاری از نوع **Incoming Request** / **Not Recieved In Minutes** بیفزایید.

### نوع‌های پالایه در دسترس

| نوع پالایه | چه چیزی را بررسی می‌کند | یادداشت‌ها |
| --------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| Incoming Request | اینکه درخواستی درون پنجره‌ای زمانی دریافت شده است یا نه | تنها بررسی‌ای که می‌تواند وقتی چیزی نمی‌رسد شلیک کند |
| Request Body | بدنه درخواست | تطبیق زیررشته‌ای. بدنه‌های شیئی به‌صورت JSON فشرده مقایسه می‌شوند |
| Request Header | نام هدرهای درخواست | تطبیق دقیق با نام هدر، با حروف کوچک |
| Request Header Value | مقدار هدرهای درخواست | تطبیق دقیق با مقدار هدر، با حروف کوچک |
| JavaScript Expression | هر عبارتی روی `requestBody` و `requestHeaders` | انعطاف‌پذیرترین گزینه — [عبارت‌های JavaScript](/docs/monitor/javascript-expression) را ببینید |

### شرط‌های پالایه

هر نوع پالایه‌ای مجموعه شرط‌های خودش را ارائه می‌دهد.

برای **Incoming Request** (اینجا با همان املای داشبورد آورده شده است):

- **Recieved In Minutes** — درخواستی درون شمار مشخصی از دقیقه‌ها دریافت شده است
- **Not Recieved In Minutes** — هیچ درخواستی درون شمار مشخصی از دقیقه‌ها دریافت نشده است

برای **Request Body**، **Request Header** و **Request Header Value**: ‏**Contains** و **Not Contains**.

برای **JavaScript Expression**: ‏**Evaluates To True**.

> **توجه:** نام و مقدار هدرها پیش از مقایسه به حروف کوچک تبدیل می‌شوند، و تطبیق با کل نام یا مقدار است نه زیررشته. بنویسید `content-type` نه `Content-Type`، و `application/json` نه `application/JSON`. فقط **Request Body** تطبیق زیررشته‌ای واقعی می‌کند.

بدنه‌های شیئی به‌صورت JSON فشرده و بدون فاصله مقایسه می‌شوند، پس پالایه **Request Body** / **Contains** باید `"status":"firing"` نوشته شود — کپی کردن `"status": "firing"` از محموله‌ای خوش‌چاپ هرگز نمی‌خواند.

### نمونه معیارها

#### اگر ۱۰ دقیقه ضربان قلبی نبود آفلاین علامت بزن (کلید مرد مرده)

- **Filter Type**: Incoming Request
- **Filter Condition**: Not Recieved In Minutes
- **Value**: 10

#### بر پایه محتوای بدنه درخواست تنزل‌یافته علامت بزن

- **Filter Type**: Request Body
- **Filter Condition**: Contains
- **Value**: `"status":"degraded"`

> **هشدار:** مانیتوری فقط وقتی در پس‌زمینه دوباره سنجیده می‌شود که دست‌کم یکی از معیارهایش روی **Incoming Request** بررسی کند. مانیتوری که معیارهایش فقط Request Body، ‏Request Header یا عبارت JavaScript را بررسی می‌کنند وقتی درخواستی می‌رسد سنجیده می‌شود و در هیچ زمان دیگری — پس هرگز خودش نمی‌تواند آفلاین شود. اگر زنگ ضربان‌قلب‌گمشده می‌خواهید، به معیاری از نوع **Incoming Request** نیاز دارید.

همچنین توجه کنید که با مانیتوری که هرگز درخواستی دریافت نکرده چنان رفتار می‌شود که انگار زمان ساختش آخرین درخواست بوده است. معیار «Not Recieved In Minutes: 10» روی مانیتوری نو، ۱۰ دقیقه پس از ساختنش شلیک می‌کند، حتی اگر فرستنده هرگز سیم‌کشی نشده باشد.

## دریافت هشدار از سامانه‌ای دیگر

‏Alertmanager، ‏Grafana و ابزارهای مشابه سندی JSON که یک یا چند هشدار را توصیف می‌کند POST می‌کنند. به‌طور پیش‌فرض معیاری **یک** حادثه باز می‌کند، پس محموله‌ای که پنج هشدار حمل کند حادثه‌ای تنها تولید می‌کرد. گروه‌بندی حادثه این را تغییر می‌دهد: مقداری را از محموله استخراج می‌کند و به ازای هر مقدار متمایز **حادثه‌ای جدا** باز می‌کند، که همه می‌توانند هم‌زمان باز باشند.

### روشن کردن گروه‌بندی حادثه

معیار را باز کنید، **Settings** را بگسترانید، و **Group incidents and alerts by a payload field** را روشن کنید. چهار فیلد پدیدار می‌شود:

| فیلد | نمونه | چه می‌کند |
| ---------------------------------- | ---------------------------------------- | ---------------------------------------------------------------------- |
| به ازای هر … حادثه‌ای جدا باز کن | `requestBody.alerts[*].labels.alertname` | مسیری که مقادیر متمایزش حادثه‌ها را از هم جدا می‌کند |
| فیلدی که بهبود را نشان می‌دهد | `requestBody.alerts[*].status` | مسیری که برای تصمیم درباره بهبود هشداری بررسی می‌شود |
| مقداری که یعنی بهبودیافته | `resolved` | مقدار دقیقی که بهبود را علامت می‌زند |
| بیشینه حادثه به ازای هر درخواست | `100` (پیش‌فرض) | سقف ایمنی تا فیلدی پرتنوع نتواند حادثه‌های بی‌کران باز کند |

### نحو مسیر

مسیرها باید با پیشوند تحت‌اللفظی `requestBody.` آغاز شوند. مسیری بدون آن — `alerts[*].labels.alertname` — خاموش با چیزی نمی‌خواند. پوشش `{{ }}` اختیاری است: `requestBody.status` و `{{requestBody.status}}` یکسان رفتار می‌کنند.

- نماد `[*]` روی آرایه‌ای پخش می‌شود — به ازای هر مقدار **متمایز** یک حادثه. دو عنصری که مقدار یکسانی بدهند در یک حادثه فرو می‌ریزند، و وضعیت شلیک/بهبود آن حادثه از **نخستین** عنصر مطابق گرفته می‌شود. **فقط نخستین `[*]` در مسیر جانشین است**؛ `requestBody.groups[*].alerts[*].name` با چیزی نمی‌خواند.
- نمادهای `[0]` و `[last]` عنصری تنها را برمی‌گزینند، و می‌توانند پس از یک `[*]` بیایند.
- مقادیر شیئی و آرایه‌ای، رشته‌های خالی و nullها رد می‌شوند. مقادیر `0` و `false` کلیدهای معتبرند.

### برطرف شدن رویدادمحور است

وب‌هوک فقط آنچه را در همان محموله است توصیف می‌کند، پس OneUptime هرگز حادثه‌ای را به این دلیل که کلیدش دیگر پدیدار نمی‌شود برطرف نمی‌کند. حادثه‌ای فقط وقتی برطرف می‌شود که محموله‌ای صریح بگوید آن کلید بهبود یافته است. دو چیز باید هر دو درست باشند:

1. مقادیر **فیلدی که بهبود را نشان می‌دهد** و **مقداری که یعنی بهبودیافته** تنظیم شده باشند و با محموله بخوانند. مقایسه دقیق و حساس به بزرگی و کوچکی حروف است — `Resolved` با `resolved` نمی‌خواند.
2. حادثه معیار گزینه **Auto Resolve Incident** را روشن داشته باشد، زیر **Advanced Options** در فرم حادثه. بدون آن، رویدادهای بهبود مطابق نادیده گرفته می‌شوند و حادثه‌ها باز می‌مانند. (همین درباره هشدارها و **Auto Resolve Alert** هم صدق می‌کند.)

مقدار **بیشینه حادثه به ازای هر درخواست** استخراج را سقف می‌گذارد، نه فقط ساخت را. کلیدهای پس از سقف برای بهبود هم نامرئی‌اند، پس در محموله‌ای که کلیدهای متمایز بیشتری از سقف حمل کند، هشداری که فراتر از آن `resolved` گزارش دهد حادثه‌اش را نمی‌بندد.

> **هشدار:** اگر **فیلدی که بهبود را نشان می‌دهد** حاوی `[*]` باشد اما **به ازای هر … حادثه‌ای جدا باز کن** نه، هرگز چیزی برطرف نمی‌شود. یا در هر دو `[*]` به کار ببرید، یا در هیچ‌کدام. مسیر بهبودی بدون `[*]` در برابر کل محموله سنجیده می‌شود، پس `status: resolved` در سطح محموله هر کلیدی در آن محموله را برطرف می‌کند — از جمله هشدارهایی که وضعیت خودشان هنوز شلیک است.

### نام‌گذاری حادثه‌ها

کلید گروه‌بندی به‌عنوان متغیری با نام **آخرین بخش مسیر** به قالب‌های حادثه و هشدار عرضه می‌شود:

| مسیر | متغیر |
| ---------------------------------------- | ----------------- |
| `requestBody.alerts[*].labels.alertname` | `{{alertname}}` |
| `requestBody.alerts[*].fingerprint` | `{{fingerprint}}` |
| `requestBody.commonLabels.severity` | `{{severity}}` |

محموله کامل هم در کنارش در دسترس است، پس عنوان حادثه‌ای برابر `{{alertname}}` و توضیحاتی که به `{{requestBody.commonAnnotations.summary}}` ارجاع می‌دهد هر دو کار می‌کنند. [قالب‌بندی پویای حادثه و هشدار](/docs/monitor/incident-alert-templating) را ببینید.

> **هشدار:** نام متغیر بخشی از هویتی است که OneUptime برای تطبیق رویداد بهبود با حادثه‌ای باز به کار می‌برد. تغییر مسیر گروه‌بندی به مسیری با بخش پایانی متفاوت، هر حادثه‌ای را که هم‌اکنون زیر مسیر قدیمی باز است یتیم می‌کند — دیگر نمی‌توان خودکار برطرفشان کرد و باید دستی بسته شوند.

توجه کنید که `[*]` **فقط** در آن دو فیلد مسیر گروه‌بندی کار می‌کند. جای دیگر تفکیک نمی‌شود، و جانگهدار تفکیک‌نشده به‌جای خالی شدن **عیناً** چاپ می‌شود — عنوانی برابر `{{requestBody.alerts[*].labels.alertname}}` با آکولادهایش ترسیم می‌شود. عنوانی برابر `{{requestBody.alerts[0].annotations.summary}}` تفکیک می‌شود، اما همیشه نخستین هشدار محموله را می‌خواند، نه هشداری که این حادثه برایش باز شده است. متغیر گروه‌بندی به‌علاوه فیلدهای مشترک `commonAnnotations` محموله را ترجیح دهید.

### نمونه عملی

برای پیکربندی کامل Alertmanager، [Prometheus Alertmanager](/docs/integrations/prometheus-alertmanager) را ببینید. برای Grafana، [Grafana](/docs/integrations/grafana) را ببینید.

## بهترین شیوه‌ها

1. **پنجره زمانی را مناسب بگذارید** — اگر کار cron شما هر ۵ دقیقه اجرا می‌شود، آستانه «Not Recieved In Minutes» را روی ۱۰ تا ۱۵ دقیقه بگذارید تا جای تأخیرهای گاه‌به‌گاه باشد
2. **داده معنادار بگنجانید** — اطلاعات وضعیت را در بدنه درخواست بفرستید تا بتوانید معیارهای ریزدانه برپا کنید
3. **از POST با `Content-Type: application/json` استفاده کنید** — هر چیزی که درون بدنه می‌خواند به آن وابسته است
4. **دو کار را روی یک مانیتور ترکیب نکنید** — مانیتوری که هشدارهای رویدادمحور می‌گیرد آهنگ منظمی ندارد، پس معیار «Not Recieved In Minutes» رویش می‌لرزد. برای کلید مرد مرده مانیتوری جدا به کار ببرید
5. **مانیتور را زیر نظر بگیرید** — مطمئن شوید سرویسی که درخواست‌ها را می‌فرستد مدیریت خطای درستی دارد تا درخواست‌های شکست‌خورده بی‌توجه نمانند
