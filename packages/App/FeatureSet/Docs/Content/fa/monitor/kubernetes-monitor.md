# مانیتور Kubernetes

مانیتورینگ Kubernetes به شما امکان می‌دهد سلامت و کارایی خوشه‌های Kubernetes خود را زیر نظر بگیرید، از جمله گره‌ها، پادها، بارهای کاری و مؤلفه‌های صفحه کنترل. OneUptime سنجه‌ها را از خوشه شما جمع می‌کند و بر پایه معیارهای پیکربندی‌شده‌تان می‌سنجدشان.

## نمای کلی

مانیتورهای Kubernetes از سنجه‌های خوشه شما برای ارائه دیدی عمیق به زیرساختتان استفاده می‌کنند. این به شما امکان می‌دهد:

- سلامت خوشه، فضای‌نام، بار کاری، گره و پاد را زیر نظر بگیرید
- مصرف CPU، حافظه، دیسک و شبکه را در سراسر منابع ردیابی کنید
- فروریزی، بازراه‌اندازی و شکست زمان‌بندی پادها را تشخیص دهید
- دسترس‌پذیری نسخه‌های استقرار را زیر نظر بگیرید
- بر مشکل‌های صفحه کنترل هشدار بدهید (etcd، کارساز API، زمان‌بند)
- درخواست‌ها و محدودیت‌های منابع را ردیابی کنید

## ساختن یک مانیتور Kubernetes

1. در داشبورد OneUptime به **Monitors** بروید
2. روی **Create Monitor** کلیک کنید
3. نوع مانیتور را **Kubernetes** برگزینید
4. خوشه و دامنه منبعی را که باید زیر نظر گرفته شود برگزینید
5. پالایه‌های منبع و پرس‌وجوهای سنجه را پیکربندی کنید
6. معیارهای مانیتورینگ را به‌فراخور پیکربندی کنید

## گزینه‌های پیکربندی

### خوشه

خوشه Kubernetesای را که باید زیر نظر گرفته شود برگزینید. خوشه‌ها باید از راه OpenTelemetry با OneUptime یکپارچه شده باشند.

### دامنه منبع

سطحی را که در آن منابع زیر نظر گرفته می‌شوند برگزینید:

| دامنه | توضیح |
| --------- | ---------------------------------------------------------------------- |
| Cluster | زیر نظر گرفتن کل خوشه |
| Namespace | زیر نظر گرفتن منابع درون فضای‌نامی مشخص |
| Workload | زیر نظر گرفتن deployment، statefulset، daemonset، job یا cronjob مشخص |
| Node | زیر نظر گرفتن گره مشخصی از خوشه |
| Pod | زیر نظر گرفتن پادی مشخص |

### پالایه‌های منبع

دامنه را با پالایه‌های اختیاری محدود کنید:

| پالایه | توضیح | دامنه‌های قابل اعمال |
| ------------- | ------------------------------------------------ | ------------------------ |
| Namespace | فضای‌نام Kubernetes | Namespace، Workload، Pod |
| Workload Type | deployment، statefulset، daemonset، job، cronjob | Workload |
| Workload Name | نام بار کاری | Workload |
| Node Name | نام گره | Node |
| Pod Name | نام پاد | Pod |

### پرس‌وجوهای سنجه

یک یا چند پرس‌وجوی سنجه برای سنجش پیکربندی کنید. هر پرس‌وجو این‌ها را مشخص می‌کند:

- **نام سنجه** — سنجه Kubernetesای که پرس‌وجو می‌شود
- **تجمیع** — اینکه مقادیر سنجه چگونه تجمیع شوند
- **پالایه‌ها** — پالایش بیشتر بر پایه ویژگی

می‌توانید **فرمول‌هایی** هم بسازید که چند پرس‌وجوی سنجه را با عبارت‌های ریاضی ترکیب می‌کنند.

### پنجره زمانی غلتان

پنجره زمانی ارزیابی سنجه را برگزینید:

- ۱۵ دقیقه گذشته

## معیارهای مانیتورینگ

### چه چیزی سنجیده می‌شود

این مانیتورها همیشه **Metric Value** را می‌سنجند — مقدار پرس‌وجوی سنجه یا فرمول پیکربندی‌شده. فرم معیارها انتخابگر Filter Type ندارد؛ **Metric**، **Aggregation**، **Condition** و **Threshold** را نشان می‌دهد.

### نوع‌های تجمیع

| تجمیع | توضیح |
| ------------- | ---------------------------------- |
| Average | مقدار میانگین در پنجره زمانی |
| Sum | مجموع همه مقادیر |
| Maximum Value | بالاترین مقدار در پنجره زمانی |
| Minimum Value | پایین‌ترین مقدار در پنجره زمانی |
| All Values | همه مقادیر باید با معیار بخوانند |
| Any Value | دست‌کم یک مقدار باید بخواند |

### شرط‌ها

آستانه‌های ایستا — با **Threshold**ای که وارد می‌کنید مقایسه می‌شوند:

- **Greater Than**، **Less Than**، **Greater Than or Equal To**، **Less Than or Equal To**، **Equal To**

تشخیص ناهنجاری خط پایه — بدون آستانه؛ به‌جایش فرم **Sensitivity** و **Baseline Window** را نشان می‌دهد و هر نمونه را با خط پایه همان ساعت از هفته که از آن پنجره ساخته شده مقایسه می‌کند:

- **Anomalously High** — مقدار بالای محدوده مورد انتظار می‌رود
- **Anomalously Low** — مقدار زیر محدوده مورد انتظار می‌افتد
- **Anomalous** — مقدار در هر جهتی از محدوده مورد انتظار بیرون می‌رود

شرط‌های ناهنجاری در وضعیت «Learning» می‌مانند و تا وقتی دست‌کم به اندازه Baseline Window برگزیده تاریخچه سنجه وجود نداشته باشد هیچ هشداری تولید نمی‌کنند.

## قالب‌های آماده هشدار

‏OneUptime برای سناریوهای رایج مانیتورینگ Kubernetes قالب‌هایی ارائه می‌دهد:

| قالب | توضیح | آستانه |
| ----------------------------------- | ------------------------------------------ | --------------- |
| CrashLoopBackOff Detection | شمار بازراه‌اندازی کانتینر | > ۵ بازراه‌اندازی |
| Pod Stuck in Pending | پادهای در فاز Pending | > ۰ پاد |
| Node Not Ready | شرط آمادگی گره | = ۰ (آماده نیست) |
| High Node CPU | بهره‌برداری از CPU گره | > ۹۰٪ |
| High Node Memory | بهره‌برداری از حافظه گره | > ۸۵٪ |
| Deployment Replica Mismatch | نسخه‌های در دسترس نبوده | > ۰ نسخه |
| Job Failures | پادهای شکست‌خورده در یک job | > ۰ شکست |
| etcd No Leader | نبود رهبر خوشه etcd | = ۰ (بدون رهبر) |
| API Server Throttling | درخواست‌های API افتاده | > ۰ درخواست |
| Scheduler Backlog | پادهای در انتظار در زمان‌بند | > ۰ پاد |
| High Node Disk Usage | مصرف سامانه فایل گره | > ۹۰٪ |
| DaemonSet Unavailable | گره‌های بدزمان‌بندی‌شده | > ۰ گره |
| High Node CPU Request Commitment | مجموع درخواست CPU پادها ÷ تخصیص‌پذیر گره | > ۹۰٪ |
| High Node Memory Request Commitment | مجموع درخواست حافظه پادها ÷ تخصیص‌پذیر | > ۹۰٪ |
| HPA Saturated at Max Replicas | جاری HPA ÷ بیشینه نسخه‌ها | >= ۹۰٪ |
| Pod Memory Saturating Limit | مصرف حافظه پاد ÷ محدودیت حافظه کانتینر | > ۹۰٪ |
| Pod CPU Saturating Limit | مصرف CPU پاد ÷ محدودیت CPU کانتینر | > ۹۰٪ |

### گرفتن علت‌ها، نه فقط نشانه‌ها

قالب‌های سطح گره (High Node CPU/Memory، Node Not Ready، Pod Stuck in Pending) در _انتهای_ زنجیره تحلیل منابع شلیک می‌کنند، وقتی خوشه از پیش تنزل یافته است. سه قالب آخر جدول در _آغاز_ آن شلیک می‌کنند، که معمولاً همان جایی است که راه‌حل هست:

- **Pod Memory / CPU Saturating Limit** بار کاری‌ای را می‌گیرند که به محدودیت‌های کانتینر خودش سنجاق شده است. گذشتن از محدودیت حافظه یعنی OOMKill بی‌درنگ؛ گذشتن از محدودیت CPU یعنی هسته پاد را خفه می‌کند، پس بدون هیچ خطایی کندتر می‌شود. هر دو علت معمول پشت CrashLoopBackOff و تأخیر توضیح‌ناپذیرند.
- **HPA Saturated at Max Replicas** خودمقیاس‌کننده‌ای را می‌گیرد که دیگر فضای مانوری ندارد. بار کاری‌ای که محدودیت‌های هر پادش خیلی پایین است خفه یا کشته می‌شود، که همان سنجه‌ای را که HPA بر پایه‌اش مقیاس می‌گیرد باد می‌کند — پس خودمقیاس‌کننده نسخه‌هایی می‌افزاید که هرکدام به یک اندازه گرسنه‌اند، تا به سقفش بخورد یا خوشه را پر کند. راه‌حل بالا بردن محدودیت‌هاست؛ بالا بردن `maxReplicas` بدترش می‌کند.

آن‌ها را با هم روی هر فضای‌نامی که بار کاری خودمقیاس اجرا می‌کند فعال کنید — ترکیبشان «واقعاً به ظرفیت بیشتری نیاز دارد» را از «به ازای هر پاد کم‌منبع است» تمیز می‌دهد.

> **توجه درباره پادهای چندکانتینری:** دو قالب محدودیت پاد، سنجه مصرف در سطح پاد را با سنجه محدودیت در سطح کانتینر مقایسه می‌کنند. برای پادهای تک‌کانتینری (حالت رایج) نسبت دقیق است. برای پادهای چندکانتینری، مخرج به‌جای مجموعشان میانگین محدودیت کانتینرهاست، پس نسبت بیش‌گزارش می‌دهد و هشدار زودتر شلیک می‌کند — که برای هشدار OOMKill جهت امنی است، اما پیش از پایین آوردن آستانه بد نیست بدانید.

## نیازمندی‌های راه‌اندازی

برای استفاده از مانیتورینگ Kubernetes، باید عامل Kubernetes در OneUptime را در خوشه‌تان نصب کنید. عامل سنجه‌های خوشه، رویدادها، گزارش‌های پاد و — به‌طور پیش‌فرض — **ردیابی‌های برنامه و سنجه‌های RED در HTTP که با eBPF ثبت شده‌اند** را روی OTLP به OneUptime می‌فرستد. برای دیدن ترافیک در سطح سرویس، به هیچ تغییر کد یا SDK به ازای هر برنامه‌ای نیاز نیست.

راهنمای [نصب عامل Kubernetes](/docs/monitor/kubernetes-agent) را ببینید — نصب تک‌فرمانی Helm، گزینه `preset` برای برگزیدن پیکربندی درست برای خوشه‌تان (standard، GKE Autopilot، EKS Fargate) و کلیدهای `ebpf.features.*` برای خانواده‌های سیگنال منفرد (سنجه‌های RED در HTTP، گراف سرویس، جریان‌های شبکه، آمار TCP) را پوشش می‌دهد.
