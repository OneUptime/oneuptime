# پیکربندی و ایمنی رانبوک

## Bash و JavaScript واقعاً کجا اجرا می‌شوند

گام‌های Bash و JavaScript **هرگز روی Worker مربوط به OneUptime اجرا نمی‌شوند**. آن‌ها به‌عنوان کار به یک [عامل رانبوک](/docs/runbooks/agents) مشخص فرستاده می‌شوند — فرایندی کوچک که روی میزبانی درون زیرساخت خودتان نصب می‌کنید.

مدل ارسال:

1. نویسنده گام رانبوک هنگام نوشتن گام، یک عامل رانبوک را از فهرست کشویی انتخاب می‌کند.
2. وقتی گام اجرا می‌شود، Worker سطری در `RunnerJob` درج می‌کند که `targetAgentId` آن روی شناسه همان عامل و وضعیتش روی `Pending` است.
3. همان عامل مشخص (و فقط همان) کار را به‌صورت اتمی برمی‌دارد، اسکریپت را به‌صورت محلی اجرا می‌کند — Bash با `bash -c <script>` و JavaScript درون یک محیط ایزوله `isolated-vm` — و نتیجه را برمی‌گرداند.
4. Worker با آن نتیجه رانبوک را ادامه می‌دهد.

دیگر متغیر محیطی `RUNBOOK_BASH_ENABLED` وجود ندارد. اینکه گام‌های Bash یا JavaScript در یک استقرار کار می‌کنند یا نه، کاملاً به این بستگی دارد که دست‌کم یک عامل رانبوک متصل در پروژه باشد.

## سقف خروجی و وقفه‌ها

- خروجی هر گام: **۵۰ کیلوبایت**. خروجی بزرگ‌تر با یک نشانگر کوتاه می‌شود.
- وقفه پیش‌فرض اجرای هر گام: **۳۰ ثانیه** برای JavaScript، Bash و HTTP. این را در صفحه **Steps** رانبوک برای هر گام تنظیم کنید — فیلد را خالی بگذارید تا پیش‌فرض بماند.
- **وقفه برداشتن کار** برای گام‌های Bash و JavaScript: **۲ دقیقه** — مدتی که Worker منتظر می‌ماند تا عامل انتخاب‌شده کار را بردارد و پس از آن آن را ناموفق اعلام می‌کند. این هم برای هر گام تنظیم می‌شود.
- هر دو وقفه مقادیر **۱ ثانیه تا ۱ ساعت** را می‌پذیرند. مقداری خارج از این بازه هنگام اجرای گام محدود می‌شود، بنابراین یک پیکربندی اشتباه نه می‌تواند وقفه را غیرفعال کند و نه می‌تواند یک اسلات Worker را برای همیشه اشغال نگه دارد.

## دسترسی‌ها

دسترسی‌های رانبوک در گروه دسترسی `Runbook` قرار دارند:

- `CreateRunbook`، `EditRunbook`، `DeleteRunbook`، `ReadRunbook` — مدیریت قالب‌های رانبوک.
- `CreateRunbookExecution`، `EditRunbookExecution`، `ReadRunbookExecution` — شروع، تیک زدن و خواندن اجراها.
- `CreateRunbookRule`، `EditRunbookRule`، `DeleteRunbookRule`، `ReadRunbookRule` — مدیریت قواعد فعال‌سازی خودکار.
- `CreateRunner`، `EditRunner`، `DeleteRunner`، `ReadRunner` — مدیریت Runnerهایی که گام‌ها را در زیرساخت خودتان اجرا می‌کنند. (این‌ها پیش از تغییر نام به Runner، `*RunbookAgent` نام داشتند؛ اعطاهای موجود مهاجرت داده شده‌اند، پس چیزی نیاز به تخصیص دوباره ندارد.)
- `RunbookAdmin`، `RunbookMember`، `RunbookViewer` (نقش‌ها) — به یک تیم تخصیص دهید تا به‌ترتیب کنترل کامل، استفاده روزمره یا دسترسی فقط‌خواندنی بگیرد. `RunbookAdmin` همه دسترسی‌های دقیق بالا را در خود دارد.

## صف و کارگر

اجراهای رانبوک روی صف BullMQ به نام `Runbook` اجرا می‌شوند. هم‌زمانی کارگر برابر ۲۵ است — اگر اجراهای هم‌زمان زیادی دارید در استقرار خود تنظیمش کنید.

وقتی یک گام دستی از طریق API تیک می‌خورد، اجرا دوباره در صف قرار می‌گیرد تا از گام بعدی ادامه یابد. این کار کارگر را برای بقیه رانبوک گرم نگه می‌دارد.

## نکته‌های سخت‌سازی

- **JavaScript و Bash** روی میزبان عامل رانبوکی اجرا می‌شوند که خودتان کنترلش می‌کنید، نه روی Worker مربوط به OneUptime. JavaScript در یک محیط ایزوله `isolated-vm` با پیش‌درآمد معمول پیچیده می‌شود (زنجیره‌های prototype را قطع می‌کند، `Function`/`eval` را حذف می‌کند و prototypeهای درونی را منجمد می‌کند). Bash با `bash -c` و با اعمال وقفه روی عامل اجرا می‌شود.
- **گام‌های HTTP** از یک اعتبارسنج وضعیت آسان‌گیر استفاده می‌کنند، بنابراین پاسخ 4xx یا 5xx به‌عنوان گام ناموفق ثبت می‌شود نه به‌عنوان خطای پرتاب‌شده. این باعث می‌شود خروجی ثبت‌شده همان چیزی باشد که سرویس بالادست واقعاً برگردانده است.
- **احراز هویت عامل** با شناسه و کلید محرمانه انجام می‌شود که به‌عنوان متغیر محیطی روی کانتینر عامل تنظیم می‌شوند. سمت سرور، هویت معتبر عامل از سطر پایگاه داده‌ای می‌آید که با شناسه/کلید ارائه‌شده کلیدگذاری شده است — کلاینت‌ها حتی با یک کلید لو رفته هم نمی‌توانند خود را جای عامل دیگری جا بزنند.

## جدول‌های پایگاه داده

- `Runbook` — قالب (نام، اسلاگ، توضیحات، isEnabled، گام‌ها به‌صورت JSON).
- `RunbookExecution` — یک سطر به ازای هر اجرا، با کلیدهای خارجی تهی‌پذیر `incidentId`، `alertId` و `scheduledMaintenanceId` و یک آرایه JSON به نام `stepExecutions` که گام‌ها و وضعیت هر گام را تصویربرداری می‌کند.
- `RunbookRule` — قواعد فعال‌سازی خودکار با یک متمایزکننده `triggerEntityType` (Incident، Alert، ScheduledMaintenance) و رابطه چندبه‌چند با رانبوک‌هایی که باید شروع شوند.
- `Runner` — یک سطر به ازای هر عامل نصب‌شده: نام، کلید محرمانه، `lastAlive`، `connectionStatus` و اطلاعات میزبان.
- `RunnerJob` — یک سطر به ازای هر گام Bash یا JavaScript فرستاده‌شده: `targetAgentId` (عاملی که نویسنده گام انتخاب کرده)، نوع گام، اسکریپت، وضعیت (`Pending` → `Claimed` → `Running` → `Succeeded`/`Failed`/`TimedOut`/`Cancelled`)، مهلت برداشتن، اجاره، خروجی و کد خروج.

## نکته‌های عملیاتی

- **مطمئن شوید عاملی که روی یک گام انتخاب می‌کنید سالم است.** اگر به افزونگی نیاز دارید، عامل دومی اجرا کنید و گام‌های خود را میان آن‌ها تقسیم کنید، یا یک رانبوک پشتیبان نگه دارید که عامل دیگر را هدف بگیرد.
- **نشانی ذخیره کنید، نه حجم داده.** اگر یک گام بیش از چند کیلوبایت خروجی تولید می‌کند، آن را در S3 یا پشته لاگ خود بنویسید و نشانی را برگردانید.
- **خودتوانی اهمیت دارد.** اگر کارگر در میانه یک گام راه‌اندازی مجدد شود یا اجاره یک عامل در حین اجرای اسکریپت منقضی شود، گام‌های خودکار (HTTP، JavaScript، Bash) ممکن است بیش از یک بار اجرا شوند؛ آن‌ها را طوری طراحی کنید که تکرارشان بی‌خطر باشد.
