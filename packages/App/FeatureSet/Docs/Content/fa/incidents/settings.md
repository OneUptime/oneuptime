# تنظیمات و خودکارسازی

پیکربندی حادثه در Project Settings زندگی نمی‌کند. درون خودِ حوزه محصول Incidents زندگی می‌کند، زیر **Incidents → Settings** و **Incidents → Rules**، در مسیرهایی که با `/dashboard/{projectId}/incidents/settings/` آغاز می‌شوند. اگر در **Project Settings** دنبال قالب‌های حادثه یا فیلدهای سفارشی گشته‌اید، دلیل نیافتنشان همین است.

هر دو بخش **Rules** و **Settings** در منوی کناری Incidents به‌طور پیش‌فرض جمع‌اند، پس پیش از پدیدار شدن آیتم‌های زیر باید بگسترانیدشان. هر چیزی اینجا محدود به پروژه است: قالب‌ها، فرم‌ها، نقش‌ها، فیلدهای سفارشی و قواعد به یک پروژه تعلق دارند و روی هر حادثه‌ای که در آن اعلام شود اعمال می‌شوند.

این صفحه مرجع آن پیکربندی است — هر صفحه چه نگه می‌دارد، و کدامشان همان لحظه که حادثه‌ای ساخته می‌شود خودکار اجرا می‌شوند.

## تنظیمات حادثه کجا زندگی می‌کنند

بخش **Incidents** را در پیمایش چپ باز کنید، سپس **Settings** را پایین منوی کناری بگسترانید.

| صفحه | آنجا چه می‌کنید |
| ------------------------ | -------------------------------------------------------------------------------------------- |
| **AI** | روشن یا خاموش کردن بررسی خودکار، رفع خودکار کد و پیش‌نویس پس‌مرگ، و تنظیم محدودیت‌های اختیاری‌ای که هوش مصنوعی زیرشان کار می‌کند — هیچ‌کدام تا وقتی تنظیمشان نکنید اعمال نمی‌شود. [بررسی‌های هوش مصنوعی](/docs/ai/ai-sre) را ببینید. |
| **Incident State** | افزودن، تغییر نام، تغییر رنگ و مرتب کردن وضعیت‌هایی که حادثه از میانشان می‌گذرد. |
| **Incident Severity** | افزودن، تغییر نام، تغییر رنگ و مرتب کردن سطوح شدت. |
| **Incident Templates** | از پیش پر کردن کل حادثه — عنوان، توضیحات، منابع، سیاست‌های کشیک، مالکان، برچسب‌ها. |
| **Forms** | اشتراک‌گذاری پیوندی که هر کسی می‌تواند با آن حادثه‌ای گزارش دهد، بدون حساب OneUptime. |
| **Note Templates** | متن قابل استفاده دوباره برای یادداشت‌های عمومی و خصوصی. |
| **Postmortem Templates** | ساختارهای قابل استفاده دوباره پس‌مرگ. |
| **Custom Fields** | تعریف فیلدهای اضافه‌ای که روی هر حادثه‌ای پدیدار می‌شوند. |
| **Measurements** | تعریف مدت‌های نام‌دار — زمان تا تشخیص، زمان تا کاهش اثر — که برای هر حادثه‌ای محاسبه می‌شوند. |
| **Incident Roles** | تعریف نقش‌هایی که پاسخ‌دهندگان را به آن‌ها تخصیص می‌دهید، مانند فرمانده حادثه. |
| **More Settings** | پیشوندهای شماره حادثه و اپیزود حادثه، و کلیدهای هشدارهای پیوندشده. |

بخش‌های **Incident State** و **Incident Severity** به‌طور عمیق در [وضعیت‌ها و شدت‌های حادثه](/docs/incidents/states-and-severities) پوشش داده شده‌اند — باقی این صفحه از **Incident Templates** ادامه می‌دهد. **Forms** صفحه‌ای از آن خودشان دارند: [فرم‌های حادثه](/docs/incidents/forms).

بخش **Rules** را بگسترانید و نه صفحه دیگر می‌گیرید: **Grouping Rules**، **On-Call Rules**، **Owner Rules**، **Runbook Rules**، **Auto Remediation Rules**، **Privacy Rules**، **Label Rules**، **SLA Rules** و **Reminder Rules**. آن‌ها پایین‌تر پوشش داده شده‌اند.

## قالب‌های حادثه

قالب حادثه اسکلتی ذخیره‌شده از حادثه است. به‌جای تایپ دوباره همان عنوان، همان فهرست مانیتور و همان سیاست کشیک هر بار که خوشه پرداخت می‌لرزد، یک بار ذخیره‌اش می‌کنید و از آن اعلام می‌کنید.

به **Incidents → Settings → Incident Templates** (`/dashboard/{projectId}/incidents/settings/templates`) بروید. کارت با عنوان **Incident Templates** است. ساختن یکی شما را از جادوگری شش‌گامی می‌گذراند، که وقتی پروژه شما فیلدهای سفارشی حادثه دارد دو گام بیشتر دارد:

- **Template Info** — **Template Name** و **Template Description**. این‌ها خود قالب را نام می‌برند؛ هرگز روی حادثه پدیدار نمی‌شوند.
- **Incident Details** — **Title**، **Description** (مارک‌داون)، **Incident Severity** و **Initial Incident State**. مقدار **Initial Incident State** اختیاری است و خالی آغاز می‌شود؛ گزینه‌هایش به ترتیب وضعیت فهرست می‌شوند. خالی بگذاریدش و حادثه‌های این قالب در وضعیت created پروژه می‌نشینند.
- **Resources Affected** — مانیتورها، میزبان‌ها، خوشه‌ها و سرویس‌هایی که حادثه باید به آن‌ها پیوست شود، به‌علاوه **Limit to these status pages** و **Change Monitor Status to**. **Limit to these status pages** حادثه‌هایی را که از روی قالب اعلام می‌شوند به برخی از صفحه‌های وضعیتی که مانیتورهایشان را فهرست کرده‌اند محدود می‌کند — قالب `Region East outage` می‌تواند صفحه‌های سایت‌های شرقی را با خود داشته باشد. قالبی که وجود دارد آن را روی کارت **Status Page Scope**، با **Edit Status Page Scope**، نشان می‌دهد. [یک صفحه وضعیت برای هر مخاطب](/docs/status-pages/one-status-page-per-audience) را ببینید.
- **Custom Fields** — فقط وقتی پروژه شما فیلدهای سفارشی حادثه دارد: مقادیری که حادثه‌های اعلام‌شده از این قالب با آن‌ها آغاز می‌شوند. همه فیلدها اینجا ارائه می‌شوند، نه فقط آن‌هایی که گام **Details** می‌پرسد، و هیچ‌کدام الزامی نیست. قالبی که وجود دارد کارت **Custom Fields** برای تغییر آن‌ها دارد.
- **Custom Fields on Create** — این هم فقط وقتی پروژه شما فیلدهای سفارشی حادثه دارد: گام **Details** هنگام اعلام حادثه‌ای از روی این قالب کدام‌یک از آن‌ها را بپرسد، و کدام باید پر شود. قالبی که وجود دارد کارت **Custom Fields on Create** برای تغییر آن‌ها دارد. [فیلدهای سفارشی هنگام ساخت](#فیلدهای-سفارشی-هنگام-ساخت) را ببینید.
- **On-Call** — **On-Call Policy**، سیاست‌هایی که هنگام اعلام حادثه‌ای ساخته‌شده از این قالب اجرا می‌شوند.
- **Owners** — **Owner - Teams** و **Owner - Users**.
- **Labels** — **Labels**.

چند قاعده سریع:

- فهرست قالب‌ها فقط **Name** و **Description** را نشان می‌دهد. سطرها از فهرست قابل ویرایش یا حذف نیستند — برای تغییرش قالبی را باز کنید (`/dashboard/{projectId}/incidents/settings/templates/{modelId}`).
- قالب‌ها از وارد و صادر کردن JSON پشتیبانی می‌کنند، پس می‌توانید یکی را میان پروژه‌ها جابه‌جا کنید.
- حالت خالی می‌گوید «No incident templates found.»

### قالب چگونه اعمال می‌شود

دو مسیر هست، و به یک شکل ادغام می‌کنند.

- **در داشبورد** — دکمه **Create from Template** در فهرست حادثه‌ها انتخابگر **Select Incident Template** را باز می‌کند، و صفحه اعلام قالب را از پارامتر رشته پرس‌وجوی `incidentTemplateId` می‌خواند، سپس فرم را با قالب به‌علاوه تیم‌ها و کاربران مالکش از پیش پر می‌کند. گام **Details** آن از [فیلدهای سفارشی هنگام ساخت](#فیلدهای-سفارشی-هنگام-ساخت) قالب پیروی می‌کند. این مالکان بی‌آنکه خبردار شوند مالکان حادثه می‌شوند، وقتی کانال‌های Slack و Microsoft Teams حادثه ساخته شده‌اند، پس قاعده اعلانی که مالکان حادثه را به کانال تازه دعوت می‌کند آن‌ها را هم دعوت می‌کند.
- **روی کارساز** — حادثه‌ای که با `createdIncidentTemplateId` برابر با شناسه یک قالب ساخته شود از روی آن قالب پر می‌شود. آن ستون را فقط خود OneUptime تنظیم می‌کند: گام **Create One Incident** یک گردش کار، و [فرم حادثه‌ای](/docs/incidents/forms) که **Incident Template** دارد. کلید API یا کاربر واردشده نمی‌تواند — درخواستی که `createdIncidentTemplateId` بفرستد رد می‌شود — پس برای اعلام از روی قالب از راه API، قالب را از `/api/incident-templates` بخوانید و مقادیرش را در درخواست بفرستید. کارساز قالب را فقط وقتی اعمال می‌کند که حادثه وضعیتی را نام نبرد: گردش کاری که از روی قالب اعلام می‌کند باید `currentIncidentStateId` را کنار بگذارد.

بخش مهم قاعده ادغام است: **قالب فقط فیلدی را پر می‌کند که تعریف‌نشده گذاشته‌اید**. عنوان، توضیحات، شدت حادثه، وضعیت اولیه حادثه، وضعیت مانیتوری پشت **Change Monitor Status to**، مانیتورها، میزبان‌ها، خوشه‌های Kubernetes، میزبان‌های Docker، میزبان‌های Podman، سرویس‌ها، سیاست‌های کشیک، برچسب‌ها و صفحه‌های وضعیت فقط وقتی از قالب کپی می‌شوند که فراخوان‌دهنده یا فرم چیزی نداده باشد. هر چیزی که صریح بگذارید همیشه برنده است. مقادیر فیلدهای سفارشی فیلد به فیلد ادغام می‌شوند: قالب فیلدهایی را پر می‌کند که حادثه بدون آن‌ها اعلام شده، و مقداری که شما بگذارید — `0`، `false` و `null` هم — بر مقدار قالب برنده است.

**پنجره حالت خالی به جای اشتباهی اشاره می‌کند.** اگر هنوز قالبی ندارید، دکمه **Create from Template** پنجره **No Incident Templates** را نشان می‌دهد. متنش به Project Settings اشاره می‌کند، اما دکمه به **Incidents → Settings → Incident Templates** مسیردهی می‌کند — آن مکان واقعی است.

### فیلدهای سفارشی هنگام ساخت

تنظیم‌های پروژه تعیین می‌کنند گام **Details** هنگام اعلام حادثه چه بپرسد: **Show on Create** فیلدی را می‌پرسد، و **Required on Create** آن را اجباری می‌کند. قالب می‌تواند هر دو را برای حادثه‌هایی که از رویش اعلام می‌شوند تغییر دهد. کارت **Custom Fields on Create** آن — و گام هم‌نام در جادوگر — هر فیلد سفارشی حادثه را به ترتیب **Order** آن فهرست می‌کند، با یک تنظیم برای هرکدام:

| تنظیم        | وقتی حادثه‌ای از روی این قالب اعلام می‌شود                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------------------ |
| **Default**  | فیلد از **Show on Create** و **Required on Create** خودش پیروی می‌کند. گزینه می‌گوید کدام، مانند **Default (Required)**. |
| **Required** | گام **Details** فیلد را می‌پرسد، و باید پر شود. فیلد بله/خیر باید روشن شود.                                         |
| **Optional** | گام فیلد را می‌پرسد، و می‌توان خالی‌اش گذاشت — حتی وقتی پروژه آن را الزامی کرده است.                                 |
| **Hidden**   | گام فیلد را نمی‌پرسد، حتی وقتی پروژه آن را نشان می‌دهد یا الزامی کرده است. مقدار خود قالب برای آن همچنان اعمال می‌شود. |

روی کارت، فیلدی که قالب آن را **Required**، **Optional** یا **Hidden** گذاشته، زیر نوعش نشان می‌دهد پروژه با آن چه می‌کند: **Project default: Required**، **Project default: Optional** یا **Project default: Not Shown**. هر کسی که بتواند قالب را ببیند این را می‌بیند.

وقتی از آن استفاده کنید که حادثه‌های یک قالب پاسخی لازم دارند که بقیه ندارند — برای نمونه رده مشتری روی قالب `Customer data exposure` — یا برای بیرون نگه داشتن پرسشی که پروژه همه‌جا می‌پرسد از قالبی که با آن جور نیست.

- **کلیدگذاری با Template Variable.** هر تنظیم زیر **Template Variable** فیلد ذخیره می‌شود، که هرگز تغییر نمی‌کند، پس تغییر نام فیلد تنظیمش را نگه می‌دارد. فیلدی که حذف و دوباره با همان نام ساخته شود تنظیمش را پس می‌گیرد — برخلاف پرسش‌های یک فرم حادثه، که فیلد حذف‌شده را فراموش می‌کنند.
- **Edit و Save آن‌ها را از نو می‌خوانند.** **Edit** در کارت فیلدها و تنظیم‌های قالب را دوباره می‌خواند، و در این میان پنجره نشانگر بارگذاری را نشان می‌دهد، و **Save** آن‌ها را یک بار دیگر می‌خواند و فقط فیلدهایی را می‌نویسد که در پنجره تغییر داده‌اید. پس تغییری که مدیر دیگری در این میان روی فیلدهای دیگر داده نگه داشته می‌شود — از جمله تنظیمی که به فیلدی داده که وقتی پنجره شما باز بود ساخته شده — و تغییری که به فیلدی داده‌اید که در این میان حذف شده نوشته نمی‌شود. سپس کارت فیلدها را همان‌طور که هستند فهرست می‌کند. اگر هنگام زدن **Edit** خواندنشان ممکن نباشد، پنجره دلیلش را می‌گوید و به‌جای **Save**، **Try again** را پیشنهاد می‌کند؛ اگر هنگام زدن **Save** ممکن نباشد، دلیلش را می‌گوید، چیزی ذخیره نمی‌کند و گزینه‌هایتان را نگه می‌دارد.
- **فقط داشبورد آن‌ها را اعمال می‌کند.** مانند **Required on Create**، این تنظیم‌ها فقط فرم **Declare Incident** را شکل می‌دهند و بس. حادثه‌هایی که از راه API، با گردش کار، مانیتور، Slack، Microsoft Teams یا هوش مصنوعی اعلام می‌شوند به آن‌ها پایبند نیستند، و [فرم‌های حادثه](/docs/incidents/forms) پرسش‌های خودشان را دارند. [Required on Create فقط در داشبورد بررسی می‌شود](#required-on-create-فقط-در-داشبورد-بررسی-میشود) را ببینید.
- **فیلدی که از فیلد سفارشی مانیتور کپی می‌شود** همچنان وقتی حادثه مانیتوری دارد پرسیده نمی‌شود، هر چه قالب بگوید.
- **هر کسی که بتواند قالب‌های حادثه را ویرایش کند می‌تواند آن‌ها را تغییر دهد** — از جمله Project Member و Incident Member — حتی برای فیلدی که یک Project Admin آن را برای کل پروژه **Required on Create** کرده است. خود تنظیم‌های سطح پروژه به Project Owner، Project Admin یا مجوز **Edit Incident Custom Field** نیاز دارند.
- **همراه قالب جابه‌جا می‌شوند.** خروجی JSON قالب آن‌ها را در بر دارد، و در پروژه‌ای که قالب را به آن وارد می‌کنید روی فیلدهایی اعمال می‌شوند که همان **Template Variable** را دارند.

از راه API، این‌ها `customFieldSettings` قالب‌اند: شیئی که کلیدهایش **Template Variable** هر فیلد است، با `Required`، `Optional`، `Hidden` یا `Default` برای هر فیلد.

```json
{
  "customFieldSettings": {
    "impact": "Required",
    "affected_location": "Optional",
    "additional_information": "Hidden"
  }
}
```

فیلدی که فهرست نشده از تنظیم‌های خودش پیروی می‌کند، مانند `Default`. درخواست با خطای `400` رد می‌شود وقتی کلیدی **Template Variable** معتبری نباشد — حروف کوچک لاتین، رقم‌ها و زیرخط — یا مقداری یکی از این چهار نباشد. کلیدی که با هیچ فیلدی نمی‌خواند نگه داشته و نادیده گرفته می‌شود.

## قالب‌های یادداشت

قالب‌های یادداشت به پاسخ‌دهندگان متنی از پیش آماده برای به‌روزرسانی حادثه می‌دهند، تا به‌روزرسانی صفحه وضعیت ساعت سه بامداد را کسی نیمه‌خواب از صفر ننویسد.

به **Incidents → Settings → Note Templates** (`/dashboard/{projectId}/incidents/settings/note-templates`) بروید. کارت با عنوان **Public or Private Note Templates for Incidents** است — یک کتابخانه به هر دو نوع یادداشت خدمت می‌کند. فرم ساخت دو گام دارد:

- **Template Info** — **Template Name** و **Template Description**، هر دو الزامی.
- **Note Details** — خودِ بدنه یادداشت، به مارک‌داون، الزامی.

مانند قالب‌های حادثه، سطرها به‌جای ویرایش درجا ساخته و دیده می‌شوند؛ برای تغییرش قالبی را باز کنید.

**جای‌نگهدارها.** قالب یادداشت می‌تواند جای‌نگهدارهایی داشته باشد که هنگام برگزیدن قالب با مقادیر حادثه پر می‌شوند، تا نویسنده متن نهایی را پیش از انتشار ببیند — و همچنان بتواند تغییرش دهد:

| جای‌نگهدار | با چه پر می‌شود |
| ---------------------------------- | ------------------------------------------------------------------ |
| `{{incident.title}}` | عنوان حادثه. |
| `{{incident.number}}` | شماره‌اش، مثلاً `INC-42` یا `#42`. |
| `{{incident.severity}}` | شدتش. |
| `{{incident.state}}` | وضعیت فعلی‌اش. |
| `{{incident.startedAt}}` | زمان اعلامش، در منطقه زمانی نویسنده، با نام منطقه. |
| `{{incident.labels}}` | برچسب‌هایش، جداشده با ویرگول. |
| `{{incident.affectedStatusPages}}` | صفحه‌های وضعیتی که حادثه روی آن‌ها نشان داده می‌شود و به آن‌ها خبر می‌دهد و نویسنده می‌تواند ببیند. |
| `{{customFields.<key>}}` | مقدار یک فیلد سفارشی، با **Template Variable** نشان‌داده‌شده در صفحه تنظیمات فیلدهای سفارشی. |

جای‌نگهداری که مقداری ندارد، یا در این فهرست نیست، دقیقاً همان‌طور که نوشته شده باقی می‌ماند تا نویسنده پرش کند. مقادیر به‌صورت متن گذاشته می‌شوند: عنوان حادثه نمی‌تواند در یادداشت منتشرشده به تصویر، HTML یا پیوندی تبدیل شود که متنش مقصدش را پنهان کند، هرچند نشانی‌ای درون آن همچنان به‌صورت پیوندی به همان نشانی نشان داده می‌شود. فیلد سفارشی **Rich text (Markdown)** همان Markdownی که هست گذاشته می‌شود. فرم نوشتن قالب یادداشت این جای‌نگهدارها را زیر یادداشت فهرست می‌کند، همراه با یک هشدار: جای‌نگهدارهای فیلد سفارشی، برچسب و صفحه وضعیت با سوابق خود تیم شما پر می‌شوند، هر فیلد سفارشی چه **Include in Subscriber Notifications** برایش روشن باشد چه نه، و همین کتابخانه یادداشت‌های عمومی را هم پر می‌کند که روی صفحه‌های وضعیت حادثه نشان داده و برای مشترکانشان ایمیل می‌شوند. پیش از ارسال یادداشت عمومی، متن پرشده را بخوانید.

قالب‌های یادداشت جایی نمایان می‌شوند که واقعاً لازمشان دارید: پنجره‌های تأیید **Acknowledge Incident** و **Resolve Incident** هر دو کنار فیلد **Public Note** گزینه **Select Note Template** را ارائه می‌دهند. برای تفاوت یادداشت‌های عمومی و خصوصی [یادداشت‌ها، مالکان و خوراک حادثه](/docs/incidents/notes-owners-and-feed) را ببینید.

## قالب‌های پس‌مرگ

قالب پس‌مرگ اسکلت نوشته‌ای است که پس از حادثه تولید می‌کنید — سرتیترهای شما، اعلان‌های شما، پرسش‌های همیشگی شما — تا هر بازبینی‌ای در پروژه از همان شکل پیروی کند.

به **Incidents → Settings → Postmortem Templates** (`/dashboard/{projectId}/incidents/settings/postmortem-templates`) بروید. کارت با عنوان **Postmortem Templates** است. فرم ساخت دو گام دارد:

- **Template Info** — **Template Name** و **Template Description**، هر دو الزامی.
- **Postmortem Details** — **Postmortem Template**، خودِ بدنه، به مارک‌داون، الزامی.

یکی را از حادثه اعمال می‌کنید، نه از تنظیمات. حادثه‌ای را باز کنید، **Postmortem** را در منوی کناری‌اش برگزینید (`/dashboard/{projectId}/incidents/{incidentId}/postmortem`)، و از **Apply Template** استفاده کنید. آن پنجره **Apply Postmortem Template** را با فهرست کشویی **Select Template** باز می‌کند؛ برگزیدن یکی بدنه قالب را در ویرایشگر **Postmortem Note** بارگذاری می‌کند، جایی که پیش از ذخیره ویرایشش می‌کنید. اپیزودهای حادثه همان صفحه **Postmortem** را دارند و از همان کتابخانه قالب می‌کشند.

## فیلدهای سفارشی

فیلدهای سفارشی به شما امکان می‌دهند فراداده خودتان را روی هر حادثه‌ای حمل کنید — نام سرویسی داخلی، ارجاعی به تیکت تغییر، رده مشتری — و هر بار که حادثه‌ای اعلام می‌شود همان پرسش‌ها را بپرسید، مانند میزان اثر آن و زمانی که انتظار می‌رود برطرف شود.

به **Incidents → Settings → Custom Fields** (`/dashboard/{projectId}/incidents/settings/custom-fields`) بروید. صفحه با عنوان **Incident Custom Fields** است و فیلدها را به ترتیب **Order** آن‌ها فهرست می‌کند. هر تعریفی این‌ها را دارد:

- **Field Name** — الزامی، دست‌کم دو نویسه. جانگهدار نامی اسلاگ‌مانند مانند `internal-service` پیشنهاد می‌دهد.
- **Field Description** — اختیاری.
- **Field Type** — الزامی. این برمی‌گزیند داده چگونه وارد شود؛ نوع‌ها در پایین فهرست شده‌اند. نوع‌های فهرست کشویی گزینه‌هایشان را هم لازم دارند.
- **Dropdown Options** — مقادیری که در فهرست کشویی پدیدار می‌شوند، هرکدام با رنگی اختیاری.
- **Order** — جای فیلد میان فیلدهای سفارشی حادثه، از کوچک‌ترین: در صفحه **Custom Fields** حادثه، در گام **Details** و در پیام‌های مشترکان. فیلدهای بی‌ترتیب پس از فیلدهایی می‌آیند که ترتیب دارند.
- **Show on Create** — هنگام اعلام حادثه از داشبورد، فیلد را در گام **Details** می‌پرسد ([اعلام حادثه‌ها](/docs/incidents/declaring-incidents) را ببینید). قالب حادثه می‌تواند به هر فیلدی مقدار آغازین بدهد، چه هنگام ایجاد نشان داده شود چه نه، و می‌تواند فیلدی را برای حادثه‌هایی که از رویش اعلام می‌شوند بپرسد یا کنار بگذارد — [فیلدهای سفارشی هنگام ساخت](#فیلدهای-سفارشی-هنگام-ساخت) را ببینید. [فرم‌های حادثه](/docs/incidents/forms) از آن پیروی نمی‌کنند: هر فرم فقط فیلدهایی را می‌پرسد که به آن افزوده شده‌اند.
- **Required on Create** — وقتی **Show on Create** روشن باشد پیشنهاد می‌شود. گام **Details** تا این فیلد پر نشود اجازه اعلام حادثه را نمی‌دهد، و فیلد **Boolean** باید روشن شود. تنها جایی که این بررسی می‌شود داشبورد است؛ [Required on Create فقط در داشبورد بررسی می‌شود](#required-on-create-فقط-در-داشبورد-بررسی-میشود) را ببینید.
- **Include in Subscriber Notifications** — فیلد و مقدارش را همراه پیام‌های حادثه برای مشترکان صفحه وضعیت می‌فرستد: پیام‌های پیش‌فرض ایمیل، Slack و Microsoft Teams و وب‌هوک‌ها، اما نه پیامک. مشترکان معمولاً بیرون از تیم شما هستند، پس آن را فقط برای فیلدهایی روشن کنید که اشتراک‌گذاری‌شان امن است. [فیلدهای سفارشی حادثه در اعلان‌ها](/docs/status-pages/subscribers#فیلدهای-سفارشی-حادثه-در-اعلانها) را ببینید.
- **Template Variable** — کلیدی که قالب با آن به فیلد می‌رسد، `{{customFields.<key>}}`، در قالب‌های یادداشت و قالب‌های سفارشی اعلان مشترکان. هنگام ساختن فیلد از نام آن ساخته می‌شود — حروف کوچک لاتین، رقم‌ها و زیرخط، پس `Expected Resolution` می‌شود `expected_resolution`، و اگر فیلد دیگری همین کلید را داشته باشد `_2`، `_3` و مانند آن افزوده می‌شود — و با تغییر نام فیلد عوض نمی‌شود. کسی آن را دستی تنظیم نمی‌کند: API مقداری را که برایش فرستاده شود نادیده می‌گیرد.

**Order**، **Show on Create**، **Required on Create**، **Include in Subscriber Notifications** و **Template Variable** فقط روی فیلدهای سفارشی حادثه وجود دارند. فیلدهای سفارشی مانیتورها، هشدارها، رویدادهای نگهداری زمان‌بندی‌شده و منابع دیگر آن‌ها را ندارند.

تعریف‌ها در مدل خودشان زندگی می‌کنند؛ مقادیر روی خودِ حادثه در ستون `customFields`. روی حادثه‌ای منفرد آن‌ها را از **Custom Fields** در منوی کناری حادثه پر می‌کنید (`/dashboard/{projectId}/incidents/{incidentId}/custom-fields`)، جایی که فیلدها به ترتیب **Order** فهرست شده‌اند. قالب‌های حادثه مقادیر همین فیلدها را در `customFields` خودشان نگه می‌دارند.

**یک شکاف که دانستنش می‌ارزد.** تعریف فیلدهای سفارشی حادثه تنها بخشی از خانواده حادثه است که تریگر گردش کاری ندارد — بخش گردش کاری پایین را ببینید.

### نوع‌های فیلد

| نوع فیلد                     | چگونه وارد می‌شود                                    | به کار می‌آید برای                                 |
| ---------------------------- | ---------------------------------------------------- | -------------------------------------------------- |
| **Text**                     | یک خط متن                                            | ارجاع به تیکت تغییر، نام سرویسی داخلی              |
| **Number**                   | یک عدد                                               | مدت تخمینی به دقیقه، شمار کاربران درگیر            |
| **Boolean**                  | کلید بله/خیر                                         | یک تأیید، «رو به مشتری»                            |
| **Dropdown (single select)** | یک گزینه از یک فهرست                                 | میزان اثر، منطقه                                   |
| **Dropdown (multi-select)**  | چند گزینه از یک فهرست                                | سامانه‌های درگیر                                   |
| **Date**                     | یک تاریخ                                             | تاریخ تمدید قرارداد                                |
| **Date and time**            | یک تاریخ و یک زمان از روز                            | زمان مورد انتظار برای رفع                          |
| **Long text**                | چند خط متن ساده                                      | کاربران یا سامانه‌های درگیر، اطلاعات بیشتر         |
| **Rich text (Markdown)**     | متن قالب‌بندی‌شده، در ویرایشگر مارک‌داون با حالت دیداری آن | راه‌حلی موقت با پیوند و فهرست                |

**Long text** و **Rich text (Markdown)** برای فیلدهای سفارشی همه منابع در دسترس‌اند، نه فقط حادثه‌ها. مقدار متن غنی به همان صورت مارک‌داونی که نوشته شده ذخیره می‌شود. نوعی برای دکمه‌های رادیویی یا گروه کادرهای انتخاب نیست: از **Dropdown (single select)**، **Dropdown (multi-select)** یا **Boolean** استفاده کنید.

### ‏Required on Create فقط در داشبورد بررسی می‌شود

**Required on Create** فقط فرم **Declare Incident** را نگه می‌دارد و بس. حادثه‌هایی که یک مانیتور، API، Slack، Microsoft Teams یا هوش مصنوعی باز می‌کند نمی‌توانند فرمی پر کنند، پس با فیلد خالی ساخته می‌شوند. وقتی حادثه‌ای ساخته شد، همه فیلدها در صفحه **Custom Fields** آن اختیاری می‌مانند، تا پاسخ‌دهنده‌ای که وسط قطعی یک مقدار را درست می‌کند هرگز برای همه مقادیر دیگر هم تحت فشار قرار نگیرد. آن را یادآوری برای کسانی که حادثه اعلام می‌کنند بدانید، نه تضمینی که هر حادثه مقداری دارد.

[فیلدهای سفارشی هنگام ساخت](#فیلدهای-سفارشی-هنگام-ساخت) یک قالب هم همین‌طورند: فقط فرم **Declare Incident** را شکل می‌دهند و بس. [فرم‌های حادثه](/docs/incidents/forms) استثنا هستند، چون کارساز پرسش‌های **Required** یک فرم را هنگام ارسال فرم بررسی می‌کند.

### مقادیر فیلدهای سفارشی از راه API

در `POST /api/incident` و در به‌روزرسانی‌های یک حادثه، `customFields` شیئی است که کلیدهایش **Field Name** هر فیلد است:

```json
{
  "customFields": {
    "Impact": "Major",
    "Estimated Duration": 90,
    "Acknowledgement": true,
    "Expected Resolution": "2026-10-01T14:30:00.000Z"
  }
}
```

وقتی کاربر یا کلید API حادثه‌ای را می‌سازد یا به‌روز می‌کند، هر مقداری که درخواست تنظیم یا عوض می‌کند باید با فیلدش جور باشد، وگرنه درخواست با خطای `400` رد می‌شود که فیلد و مقدار فرستاده‌شده را نام می‌برد:

| نوع فیلد                                             | می‌پذیرد                                                     |
| ---------------------------------------------------- | ------------------------------------------------------------ |
| **Text**، **Long text**، **Rich text (Markdown)**    | متن. عدد، `true` یا `false` همان‌طور که فرستاده شده ذخیره می‌شود. |
| **Number**                                           | یک عدد، یا متنی که عدد است، مانند `"42"`.                     |
| **Boolean**                                          | `true` یا `false`، یا متن `"true"` یا `"false"`.              |
| **Date**، **Date and time**                          | یک تاریخ، ترجیحاً به‌صورت متن ISO 8601.                       |
| **Dropdown (single select)**                         | یکی از گزینه‌هایش.                                            |
| **Dropdown (multi-select)**                          | فهرستی از گزینه‌هایش، یا تنها یک گزینه.                       |

برای **Dropdown (multi-select)**، پیام رد ۱۰ مدخل نخستی را که در میان گزینه‌هایش نیستند نام می‌برد، و سپس می‌گوید چند مدخل دیگر هم هست.

آنچه بررسی نمی‌شود، تا یکپارچه‌سازی‌های موجود کار کنند:

- **مقادیری که درخواست دست‌نخورده می‌گذارد.** کارت **Custom Fields** وقتی یکی از مقادیر را ذخیره می‌کنید همه مقادیر را پس می‌فرستد، پس مقداری که پیش از این بررسی‌ها ذخیره شده، یا گزینه‌ای از فهرست کشویی که از آن پس برداشته شده، هرگز مانع ذخیره بقیه نمی‌شود. فیلد چندانتخابی مدخل‌هایی را که داشت نگه می‌دارد.
- **کلیدهایی که نام هیچ فیلد سفارشی حادثه نیستند**، مانند `jiraIssueKey` که [یکپارچه‌سازی Jira](/docs/integrations/jira) می‌نویسد.
- **مقادیر خالی.** `null` یا رشته خالی فیلد را پاک می‌کند.
- **مقادیری که از فیلد سفارشی مانیتور کپی می‌شوند**، و نوشتن‌هایی که خود OneUptime انجام می‌دهد.
- **Required on Create.** API هرگز فیلدی را الزامی نمی‌خواهد.

حادثه‌ای که یک گردش کار یا یک فرم حادثه از روی قالبی اعلام می‌کند (`createdIncidentTemplateId`) با مقادیر فیلدهای سفارشی قالب آغاز می‌شود، که فیلد به فیلد زیر مقادیری که خودش می‌فرستد ادغام می‌شوند ([قالب چگونه اعمال می‌شود](#قالب-چگونه-اعمال-میشود) را ببینید). کلید API نمی‌تواند از روی قالب اعلام کند: درخواستی که `createdIncidentTemplateId` بفرستد رد می‌شود.

### تغییر نام فیلد

مقادیر زیر نام فیلد ذخیره می‌شوند، پس تغییر نام فیلد باید آن‌ها را جابه‌جا کند. وقتی **Field Name** تازه‌ای ذخیره می‌کنید، OneUptime مقدار فیلد را روی هر حادثه و هر قالب حادثه در پروژه به نام تازه منتقل می‌کند، و نماهای ذخیره‌شده فهرست حادثه‌ها را که فیلد را نشان می‌دهند یا با آن فیلتر می‌کنند به‌روز می‌کند. این انتقال هیچ گردش کار **On Update Incident** را آغاز نمی‌کند، و زمان آخرین به‌روزرسانی هیچ حادثه‌ای را عوض نمی‌کند. **Template Variable** فیلد همان‌طور که بود می‌ماند، پس قالب‌های یادداشت، قالب‌های سفارشی اعلان مشترکان و یکپارچه‌سازی‌های وب‌هوکی که از آن استفاده می‌کنند کار می‌کنند.

دو تغییر نام رد می‌شوند: تغییر به نامی که فیلد سفارشی حادثه دیگری از پیش دارد (بدون توجه به کوچکی و بزرگی حروف)، و درخواست API که چند فیلد را یک‌جا تغییر نام دهد. گردش‌های کاری و کلاینت‌های API که مقدار را با نام قدیمی فیلد می‌خوانند یا می‌نویسند باید به نام تازه تغییر داده شوند.

پس از تغییر نام، فیلد فقط مقادیر خودش را دارد. حذف یک فیلد مقادیرش را روی حادثه‌هایی که آن‌ها را داشتند باقی می‌گذارد، پس حادثه‌ها ممکن است هنوز زیر نام تازه مقادیری از فیلدی حذف‌شده داشته باشند؛ تغییر نام آن‌ها را پاک می‌کند، به جای آنکه آن‌ها را پاسخ‌های این فیلد نشان دهد یا برای مشترکان بفرستد. همه حادثه‌ها و قالب‌ها با هم منتقل می‌شوند: اگر انتقال شکست بخورد، هیچ‌کدام تغییر نمی‌کند، فیلد نام قدیمی‌اش را نگه می‌دارد و ذخیره خطا می‌دهد، پس می‌توانید به‌سادگی دوباره تلاش کنید. فیلدی که با نام یک فیلد حذف‌شده **ساخته** شود فرق دارد: مقادیری را که آن فیلد به جا گذاشته نشان می‌دهد، و وقتی **Include in Subscriber Notifications** روشن شود آن‌ها را برای مشترکان می‌فرستد.

حذف یک فیلد همچنین آن را از پرسش‌های همه [فرم‌های حادثه](/docs/incidents/forms) پروژه برمی‌دارد، بی‌آنکه گردش کار **On Update Incident Form** را آغاز کند یا زمان آخرین به‌روزرسانی فرم‌ها را تغییر دهد. فیلدی که دوباره با همان نام ساخته شود تا وقتی کسی آن را در کارت **Questions** همان فرم نیفزاید در فرم پرسیده نمی‌شود. قالب‌های حادثه تنظیم **Custom Fields on Create** خود را برای آن نگه می‌دارند.

### ‏Terraform

تنظیم‌ها روی منبع `oneuptime_incident_custom_field` با نام‌های `sort_order`، `show_on_create`، `is_required_on_create` و `include_in_subscriber_notifications` هستند. `variable_key` فقط‌خواندنی است: کلیدی که OneUptime هنگام ساختن فیلد ساخت.

## اندازه‌گیری‌ها

اندازه‌گیری مدتی نام‌دار میان دو نقطه از زندگی حادثه است، که برای هر حادثه‌ای خودکار محاسبه می‌شود. «Time to Detect»، «Time to Mitigate» و «Time to Resolve» اندازه‌گیری‌اند. تعریف‌هایی هستند که یک بار می‌نویسید، نه عددهایی که کسی از خط زمانی می‌خواند.

به **Incidents → Settings → Measurements** (`/dashboard/{projectId}/incidents/settings/measurements`) بروید. هر تعریفی **نام**، **کلیدی** دائمی، **نقطه آغاز** و **نقطه پایان** دارد.

هشدارها و رویدادهای نگهداری زمان‌بندی‌شده همان قابلیت را دارند، در **Alerts → Settings → Measurements** و **Scheduled Maintenance → Settings → Measurements**. هر چیزی پایین برای هر سه صدق می‌کند، با واژگان خود هر حوزه.

### برگزیدن دو سر

سر یا مهر زمانی‌ای روی حادثه است یا نقطه‌ای در خط زمانی وضعیتش.

| نقطه پایان | به چه تفکیک می‌شود |
| ----------------------- | ---------------------------------------------------------------------------------- |
| **Impact Started At** | وقتی اثر بر مشتری واقعاً آغاز شد. تا وقتی کسی ثبتش نکند خالی است. |
| **Declared At** | وقتی حادثه اعلام شد. پیش‌فرضش لحظه ساخته شدنش است. |
| **Created At** | زمان ساخت سطر. |
| **Timeline Start** | مبدأیی که سنجه‌های توکار حادثه به کار می‌برند. برای خواندن با آن اعداد این را برگزینید. |
| **State Entered** | لحظه ورود به وضعیتی مشخص. |
| **State Role Entered** | لحظه ورود به هر وضعیتی که نقش acknowledged (یا created یا resolved) را دارد. |
| **Postmortem Posted At**| وقتی پس‌مرگ منتشر شد. |

گزینه **State Entered** یک وضعیت را با شناسه سنجاق می‌کند. **State Role Entered** به‌جایش از نقش پیروی می‌کند، پس اگر بعداً وضعیتی را که آن نقش را بازی می‌کند تغییر نام یا جایگزین کنید کار کردن ادامه می‌دهد.

وقتی وضعیتی بیش از یک بار وارد شود — حادثه‌ای بازگشوده — **Occurrence** تصمیم می‌گیرد کدام ورود بشمارد. **First** با رفتار سنجه‌های توکار می‌خواند. **Last** بازگشایی را تا ورود نهایی دنبال می‌کند.

### اندازه‌گیری چه گزارش می‌دهد

| وضعیت | معنا |
| ------------------ | ----------------------------------------------------------------------------------------- |
| **Recorded** | هر دو سر تفکیک شدند. مدت روی حادثه است و ترسیم می‌شود. |
| **Pending** | سری هنوز رخ نداده، اما هنوز می‌تواند. |
| **Not Applicable** | سری هرگز نمی‌تواند تفکیک شود — وضعیت رد شد، یا مهر زمانی هرگز ثبت نشد. |
| **Invalid** | هر دو سر تفکیک شدند، اما پایان پیش از آغاز است. مهرهای زمانی ثبت‌شده شما با هم نمی‌خوانند. |

فقط مقادیر **Recorded** به نقطه سنجه تبدیل می‌شوند. نقطه‌عطفی که رد شود به‌جای صفری چیزی نمی‌نویسد، پس نمی‌تواند میانگینی را به سمت خودش بکشد.

وضعیت **Invalid** همان است که پاییدنش می‌ارزد. چیزی است که اندازه‌گیری وقتی می‌گوید که خط زمانی‌ای که از آن محاسبه شده اشتباه است — برای نمونه پایانی ۱۷ دقیقه پیش از آغازش. آن عمداً بلندتر از عددی موجه است که کسی زیر سؤالش نمی‌برد.

### ‏Impact Started At، و چرا خالی است

فیلد **Impact Started At** روی حادثه است، و از صفحه حادثه قابل ویرایش. به‌طور پیش‌فرض خالی است و OneUptime هرگز پرش نمی‌کند.

نکته همین است. مقدار `Declared At` ثبت می‌کند OneUptime کی فهمید، که برای حادثه‌ای که مانیتوری راهش انداخته زمان پردازش معیارهاست — نه زمان آغاز اثر. اگر «Time to Detect» آغازش را به همان مهر زمانی‌ای که پایانش به کار می‌برد پیش‌فرض می‌گرفت، هر حادثه‌ای صفر گزارش می‌کرد و نمودار می‌خواند «ما آنی تشخیص می‌دهیم». فیلدی خالی و اندازه‌گیری‌ای **Not Applicable** چیز درست را می‌گویند: کسی ثبت نکرده این کی آغاز شد.

### تصحیح مهر زمانی اشتباه

هر اندازه‌گیری‌ای هر وقت داده زیرینش تغییر کند از نو محاسبه می‌شود — مدخلی از خط زمانی وضعیت ساخته، ویرایش یا حذف شود، یا `Impact Started At`، `Declared At` یا `Postmortem Posted At` روی حادثه اصلاح شود. چیزی افزایشی وصله نمی‌شود، پس مقدار کهنه‌ای برای ترمیم نیست.

فیلد **Starts At** روی مدخل خط زمانی وضعیت قابل ویرایش است. اگر حادثه‌ای ساعت ۰۹:۱۲ تصدیق شده اما مدخل ۰۹:۲۹ می‌گوید، مدخل را اصلاح کنید و هر اندازه‌گیری مشتق‌شده از آن با آن جابه‌جا می‌شود.

### نمودارها، API و Terraform

هر اندازه‌گیری فعالی سنجه‌ای به نام `oneuptime.incident.measurement.<key>` می‌نویسد، که پس از نوشته شدن نخستین مقدارش در انتخابگر نمودار داشبورد پدیدار می‌شود. هشدارها `oneuptime.alert.measurement.<key>` و نگهداری زمان‌بندی‌شده `oneuptime.scheduled-maintenance.measurement.<key>` را به کار می‌برند.

تعریف‌ها منابع معمولی API هستند، پس ارائه‌دهنده Terraform آن‌ها را به‌عنوان `oneuptime_incident_measurement`، `oneuptime_alert_measurement` و `oneuptime_scheduled_maintenance_measurement` مدیریت می‌کند. مقادیر محاسبه‌شده فقط‌خواندنی‌اند و به‌عنوان منبع داده نمایان می‌شوند.

**کلید** دائمی است چون بخشی از نام سنجه است — تغییرش سری را یتیم می‌کرد. اندازه‌گیری را آزادانه تغییر نام دهید؛ کلید می‌ماند.

### مهاجرت از پلتفرم حادثه دیگری

اگر از ابزاری با تعریف‌های اعلانی اندازه‌گیری می‌آیید، این‌ها مستقیم نگاشت می‌شوند:

| اندازه‌گیری آن‌ها | اینجا چنین برپایش کنید |
| ----------------------- | ----------------------------------------------------------------------------------- |
| Time to Detect | Impact Started At → Declared At |
| Time to Acknowledge | Timeline Start → State Role Entered (acknowledged) |
| Time to Mitigate | Timeline Start → State Entered (وضعیت **Mitigated**ای که میان Acknowledged و Resolved می‌افزایید) |
| Time to Resolve | Timeline Start → State Role Entered (resolved) |

‏Time to Mitigate به وضعیتی نیاز دارد که به‌طور پیش‌فرض وجود ندارد. آن را در **Incidents → Settings → Incident State** بیفزایید — فهرست مرتب به شما امکان می‌دهد وضعیتی را میان دو وضعیت موجود درج کنید، و هر چیزی پس از آن پایین می‌رود.

**یک چیز درباره تاریخچه.** تعریفی که امروز می‌سازید در پس‌زمینه برای حادثه‌های گذشته پر می‌شود، و آن مقادیر ذخیره‌شده روی هر حادثه‌ای پدیدار می‌شوند. تاریخچه ترسیم‌شده از لحظه ساخت تعریف رو به جلو پر می‌شود؛ حادثه‌های گذشته منفرد هم در تغییر وضعیت بعدی‌شان تازه می‌شوند.

## نقش‌های حادثه

نقش‌های حادثه کارهای نام‌داری هستند که در حین پاسخ آدم‌ها را به آن‌ها تخصیص می‌دهید. آن‌ها را در **Incidents → Settings → Incident Roles** (`/dashboard/{projectId}/incidents/settings/roles`) تعریف کنید؛ توضیحات کارت فرمانده حادثه و پاسخ‌دهنده را به‌عنوان نمونه می‌آورد.

نقش‌ها فقط تعریف‌اند. آدم‌ها را به ازای هر حادثه به آن‌ها تخصیص می‌دهید — جادوگر اعلام گامی به نام **Incident Roles** با فیلد **Assign Incident Roles** دارد، و هر حادثه‌ای صفحه **Roles** در منوی کناری‌اش دارد.

## پیشوندهای شماره

هر حادثه‌ای شماره‌ای می‌گیرد. به‌طور پیش‌فرض به‌صورت `#42` ترسیم می‌شود. اگر تیم شما بلند می‌گوید «INC-42»، محصول را هم وادار کنید همان را بگوید.

به **Incidents → Settings → More Settings** (`/dashboard/{projectId}/incidents/settings/more`) بروید. کارت **Number Prefix** است و دو فیلد روی پروژه نگه می‌دارد:

- **Incident Number Prefix** — تا ۲۰ نویسه، جانگهدار `INC-`. تنظیمش کنید و حادثه `#42` به‌صورت `INC-42` نمایش داده می‌شود.
- **Incident Episode Number Prefix** — همان ایده برای شماره اپیزود حادثه، جانگهدار `IE-`.

برای نگه داشتن پیشوند پیش‌فرض `#` هرکدام را خالی بگذارید؛ فیلد تنظیم‌نشده `# (default)` نشان می‌دهد. با **Update** ذخیره کنید. مقدار پیشونددار روی حادثه به‌عنوان `incidentNumberWithPrefix` ذخیره می‌شود، که همان چیزی است که فهرست حادثه‌ها و سرصفحه حادثه ترسیم می‌کنند.

## کلیدهای هشدارهای پیوندشده

پیوند دادن هشدارها به یک حادثه به‌خودی‌خود هرگز وضعیتشان را تغییر نمی‌دهد. دو کلید پروژه، روی کارت **Linked Alerts** در **Incidents → Settings → More Settings**، به حادثه اجازه می‌دهند هشدارهای پیوندشده‌اش را همراه خودش جلو ببرد:

- **Acknowledge Linked Alerts When Incident Is Acknowledged** — تصدیق حادثه هر هشدار پیوندشده‌ای را که هنوز تصدیق نشده تصدیق می‌کند، که تشدید کشیک آن هشدارها را متوقف می‌کند.
- **Resolve Linked Alerts When Incident Is Resolved** — برطرف کردن حادثه هر هشدار پیوندشده‌ای را که هنوز برطرف نشده برطرف می‌کند، جز هشداری که هنوز به حادثه دیگری پیوند شده که برطرف نشده است.

هر دو به‌طور پیش‌فرض خاموش‌اند، و فقط Project Owner و Project Admin می‌توانند با دکمه **Update** کارت تغییرشان دهند. وضعیت‌ها با ترتیبشان مقایسه می‌شوند، پس وضعیت‌های سفارشی هم حساب می‌شوند؛ هشدارها هرگز به عقب نمی‌روند، بازگشایی حادثه هشدارهایش را بازنمی‌گشاید، و هشداری که به حادثه‌ای از پیش تصدیق‌شده یا برطرف‌شده پیوند می‌شود همان هنگام پیوند هم‌تراز می‌شود. روشن کردن یک کلید، وضعیت هشدارهای پیوندشده را به دست حادثه می‌سپارد: هر کس بتواند وضعیت حادثه‌ای را تغییر دهد، یا هشداری را به حادثه‌ای از پیش تصدیق‌شده یا برطرف‌شده پیوند دهد، هشدارها را هم جابه‌جا می‌کند، بی آنکه به اجازه ویرایش هشدارها نیاز داشته باشد. [هشدارهای پیوندشده](/docs/incidents/linked-alerts) قاعده‌های کامل را دارد، از جمله اینکه چرا برطرف کردن هشداری که مانیتورش هنوز ناموفق است باعث می‌شود مانیتور هشداری تازه بسازد.

## قواعدی که هنگام ساخت حادثه اجرا می‌شوند

بخش **Incidents → Rules** نه موتور قاعده نگه می‌دارد. همه همان کار را می‌کنند — همان لحظه که حادثه‌ای ساخته می‌شود نگاهش می‌کنند، و اگر بخواند عمل می‌کنند — اما در آنچه می‌کنند و در نحوه تفکیک چند قاعده مطابق فرق دارند.

- **Grouping Rules** — حادثه‌های مرتبط را در اپیزودها گروه می‌کنند. قواعد به ترتیب اولویت سنجیده می‌شوند؛ شماره‌های اولویت کوچک‌تر زودتر می‌روند.
- **On-Call Rules** — سیاست‌های کشیک را برای حادثه‌های مطابق اجرا می‌کنند. پایین‌تر با جزئیات پوشش داده شده است.
- **Owner Rules** — مالکان را خودکار تخصیص می‌دهند.
- **Runbook Rules** — وقتی حادثه‌ای مطابقت کند [رانبوکی](/docs/runbooks/index) را آغاز می‌کنند.
- **Auto Remediation Rules** — وقتی حادثه‌ای مطابقت کند رانبوک‌های اصلاح را پیشنهاد یا آغاز می‌کنند. اگر بررسی هوش مصنوعی‌ای برای حادثه در صف باشد، وقتی آن بررسی تمام شود، با تحلیلش در دست، اجرا می‌شوند. [بررسی‌های هوش مصنوعی](/docs/ai/ai-sre) را ببینید.
- **Privacy Rules** — تصمیم می‌گیرند حادثه مطابق خصوصی باشد یا نه.
- **Label Rules** — برچسب‌ها را خودکار اعمال می‌کنند.
- **SLA Rules** — زمان پاسخ و برطرف شدن را ردیابی می‌کنند. قواعد به ترتیب سنجیده می‌شوند؛ شماره‌های ترتیب کوچک‌تر زودتر می‌روند.
- **Reminder Rules** — تا وقتی حادثه‌ای باز است دوره‌ای به مالکان حادثه یادآوری می‌کنند. قواعد به ترتیب سنجیده می‌شوند و نخستین قاعده مطابق برنده است.

**معناشناسی ترتیب یکسان نیست.** Grouping Rules، ‏SLA Rules و Reminder Rules ترتیب‌محورند. On-Call Rules نیستند — هر قاعده مطابقی شلیک می‌کند. فرض نکنید یک مدل برای هر نه تا صدق می‌کند.

صفحه‌های **On-Call Rules**، **Owner Rules**، **Label Rules** و **Privacy Rules** زبانه‌دارند — زبانه‌ای **Incident Rules** و زبانه‌ای **Episode Rules**، هرکدام با جدول خودشان. مگر مشخصاً اپیزودها را در نظر داشته باشید، زبانه **Incident Rules** را پیکربندی کنید. **Grouping Rules**، **Runbook Rules**، **Auto Remediation Rules**، **SLA Rules** و **Reminder Rules** جدول‌هایی تنهایند.

## قواعد کشیک حادثه

بخش **Incidents → Rules → On-Call Rules** (`/dashboard/{projectId}/incidents/settings/on-call-rules`) جایی است که فراخوانی را خودکار می‌کنید. کارت، **Incident On-Call Rules**، قواعدی را توصیف می‌کند که وقتی حادثه‌های مطابق ساخته می‌شوند سیاست‌های کشیک را خودکار اجرا می‌کنند. صفحه دو زبانه دارد: **Incident Rules** و **Episode Rules**.

فرم ساخت سه گام دارد:

- **Basic Info** — **Name** (جانگهدار چیزی مانند فراخواندن تیم پایگاه داده برای هر حادثه پایگاه داده‌ای پیشنهاد می‌دهد)، **Description**، و کلید **Enabled**. فهرست به ازای هر قاعده نشان سبز **Enabled** یا قرمز **Disabled** ترسیم می‌کند.
- **Match Criteria** — **Monitors**، **Incident Severities**، **Incident Labels**، **Monitor Labels**، به‌علاوه فیلدهای عبارت باقاعده بدون حساسیت به حروف برای عنوان حادثه، توضیحات حادثه، نام مانیتور و توضیحات مانیتور.
- **On-Call Policies** — سیاست‌هایی که این قاعده اجرا می‌کند.

### تطبیق چگونه تفکیک می‌شود

قواعدی که خود صفحه با آن‌ها عرضه می‌شود ارزش درونی کردن دارند:

- قاعده‌ای فقط وقتی مطابقت می‌کند که **همه** معیارهایی که پر کرده‌اید بگذرند. معیارهایی که خالی گذاشته‌اید رد می‌شوند، نه شکست‌خورده.
- درون یک معیار فهرستی — **Monitors**، **Incident Severities**، **Incident Labels**، **Monitor Labels** — تطبیق «هرکدام از» است.
- فیلدهای الگو عبارت‌های باقاعده بدون حساسیت به بزرگی و کوچکی حروف‌اند.
- **همه قواعد مطابق شلیک می‌کنند.** اولویتی نیست و اتصال کوتاهی نیست.
- مجموعه سیاست‌هایی که واقعاً اجرا می‌شود اجتماع سیاست‌های هر قاعده مطابق به‌علاوه هر سیاستی است که دستی یا با قالبی به حادثه پیوست شده، بدون تکرار تا هر سیاستی حداکثر یک بار اجرا شود.

شدت اینجا معیار تطبیق است و جای دیگری نه. روی شدت حادثه فیلد کشیکی وجود ندارد — برگزیدن «Critical Incident» به‌خودی‌خود کسی را فرا نمی‌خواند. اگر می‌خواهید شدت فراخوانی را براند، قاعده کشیکی بنویسید که بر پایه‌اش تطبیق کند.

## پیوست کردن مستقیم سیاست‌های کشیک

قواعد تنها مسیر نیستند. هر حادثه‌ای فهرست سیاست کشیک خودش را حمل می‌کند، که به‌صورت فیلد **On-Call Policy** در گام **On-Call** جادوگر اعلام و در گام **On-Call** قالب حادثه نمایان می‌شود. توضیحات فیلد صریح می‌گوید: این‌ها سیاست‌های کشیکی هستند که هنگام ساخت این حادثه اجرا می‌شوند.

وقتی حادثه‌ای ساخته می‌شود، OneUptime قواعد برچسب، سپس قواعد کشیک (که سیاست‌های مطابقشان را در فهرست حادثه ادغام می‌کنند)، سپس قواعد رانبوک را اجرا می‌کند — و اگر فهرست حاصل خالی نباشد، هر سیاستی در آن اجرا می‌شود. اجراها موازی می‌روند و مستقل قطعی می‌شوند، پس شکست یک سیاست بقیه را متوقف نمی‌کند. هر اجرایی با حادثه‌ای که راهش انداخته و با نوع رویداد اعلان «حادثه ساخته شد» برچسب می‌خورد.

برای دیدن آنچه رخ داده، حادثه را باز کنید و **On-Call Executions** را در منوی کناری‌اش برگزینید (`/dashboard/{projectId}/incidents/{incidentId}/on-call-policy-execution-logs`).

## راندن حادثه‌ها از گردش‌های کاری

تریگرهای گردش کاری برای حادثه‌ها دست‌نویس نیستند — OneUptime آن‌ها را از مدل‌های داده تولید می‌کند، پس هر مدلی از خانواده حادثه مؤلفه‌های **On Create X**، **On Update X** و **On Delete X** می‌گیرد، که از نام مفرد مدل نام‌گذاری می‌شوند. سه‌تای سرخط **On Create Incident**، **On Update Incident** و **On Delete Incident** هستند. آن‌ها را در پنل **Add Trigger** در `/dashboard/{projectId}/workflows` زیر **OneUptime resources → Incident** می‌یابید؛ دوتای اول زیر **Popular** هم هستند.

همان تولید، تریگرهایی برای خود پیکربندی هم به شما می‌دهد: **On Create Incident State**، **On Update Incident Severity**، **On Create Incident Template**، **On Create Incident Note Template**، **On Create Incident State Timeline**، **On Create Incident Public Note**، **On Create Incident Internal Note**، **On Create Incident On-Call Rule**، **On Create Incident Role**، **On Create Incident Member** و بیشتر. هر مدلی مؤلفه‌های کنش متناظر هم می‌گیرد — **Find One Incident**، **Create One Incident**، **Update One Incident**، **Delete One Incident** و معادل‌های چندسطری‌شان — پس تریگری و کنشی با نام‌های مشابه کنار هم در همان دسته می‌نشینند. **On Create Incident** گردش کاری‌ای را آغاز می‌کند؛ **Create One Incident** حادثه‌ای باز می‌کند.

چند جزئیات که هنگام سیم‌کشی این‌ها مهم‌اند:

- مؤلفه **On Update X** آرگومان اختیاری **Listen on** می‌گیرد که تریگر را به به‌روزرسانی‌هایی که فیلدهای مشخصی را لمس می‌کنند تنگ می‌کند. برای شلیک روی هر تغییری خالی بگذاریدش. اگر به‌روزرسانی‌ای بدون رکوردی از اینکه کدام فیلدها جابه‌جا شده‌اند برسد، پالایه رد می‌شود و گردش کاری به‌هرحال اجرا می‌شود.
- مؤلفه‌های **On Create X** و **On Update X** هر دو آرگومان الزامی **Select Fields** می‌گیرند؛ **On Delete X** آرگومانی نمی‌گیرد.
- هر سه یک درگاه خروجی **Success** در معرض می‌گذارند، و هرکدام آرگومان شناسه‌ای می‌پذیرند تا بتوانید گردش کاری را دستی روی یک رکورد اجرا کنید.
- نام‌ها از نام مفرد مدل می‌آیند، نه نام جدولش — که دلیل این است که **On Create Incident Team Owner** و **On Create Incident User Owner** می‌بینید نه نام‌هایی به شکل جدول.
- برای تعریف فیلدهای سفارشی حادثه تریگری وجود ندارد. آن مدل تنها عضوی از خانواده حادثه است که گردش‌های کاری‌اش غیرفعال‌اند.

برای ساختن باقی گردش کاری، [نوشتن یک گردش کاری](/docs/workflows/authoring) و [متغیرها](/docs/workflows/variables) را ببینید.
