# OneUptime AI و API

OneUptime AI داده‌های شما را می‌شناسد: یک هشدار داده را از نویسندگان، اجراها و تبار جدول واکاوی می‌کند، هر جا که پرسیده شود پاسخ می‌دهد که آیا یک جدول تازه است و از چه ساخته می‌شود، و از قاعده‌ای که در یک جمله گفته شده یک بررسی می‌نویسد. هر آنچه مشاهده‌پذیری داده نشان می‌دهد، از راه نقاط پایانی، متریک‌ها و سرور MCP آن برای ابزارهای خودتان هم در دسترس است.

## OneUptime AI

- **واکاوی هشدارهای داده.** وقتی OneUptime AI هشداری را روی یک جدول، یک پایپ‌لاین یا یک پایگاه داده واکاوی می‌کند، از آنچه کنار آن است آغاز می‌کند: تازگی و هشدارهای باز جدول، هشداری که این هشدار پیامد آن است، اجراهای پایپ‌لاین‌هایی که از روز قبل در آن نوشته‌اند (یک اجرای ناموفق با خطایش، یا اجرایی که هرگز انجام نشد)، سرویس‌هایی که در آن می‌نویسند همراه با نوشتن‌های ناموفق، استقرارها و تغییرات دیگرشان، تبار جدول (جدول‌هایی که جدول از آن‌ها ساخته می‌شود و جدول‌هایی که از آن ساخته می‌شوند، آن‌هایی که مشکلی دارند نخست، جای هشداری که این هشدار پیامد آن است در این تبار، و این‌که هشدارهایی که این هشدار به بار آورده روی کدام جدول‌ها هستند)، و ستون‌هایی که تغییر کرده‌اند. برای هشداری که از یک بررسی روی یک ستون آمده است، آن ستون را هم در تبار دنبال می‌کند: ستون‌های بالادستی که از آن‌ها ساخته می‌شود و ستون‌های پایین‌دستی که از آن ساخته می‌شوند، جدول به جدول، همان‌طور که منبع‌های تبار نامشان را می‌برند. اجرا، استقرار یا جدول بالادستی را که پشت هشدار است نام می‌برد. [AI SRE](/docs/ai/ai-sre) را ببینید.
- **آیا این جدول تازه است؟** در [پرسش از هوش مصنوعی](/docs/ai/ask-ai)، Slack یا Microsoft Teams بپرسید: «آیا جدول orders تازه است؟». پاسخ، تازگی جدول بر اساس ریتم خودش، زمان آخرین تغییر، هشدارهای باز، آخرین اجراهای نویسندگانش و محصولات داده‌ای را که جدول جزئی از آن‌هاست می‌دهد. نامی که چند پایگاه داده در آن شریک‌اند، برای هر کدام جداگانه پاسخ داده می‌شود، تا به کسی گفته نشود که جدول اشتباهی تازه است.
- **این جدول از چه ساخته می‌شود؟** بپرسید: «چه چیزی جدول revenue را تغذیه می‌کند؟» یا «اگر بارگذاری raw.orders متوقف شود چه چیزی خراب می‌شود؟». پاسخ، تبار جدول را تا سه گام در هر سو، و اگر بخواهید تا پنج گام، دنبال می‌کند و آنچه را که درست نیست نخست می‌آورد: جدول‌های بالادست و پایین‌دستی که دیر شده‌اند، حذف شده‌اند، هشدار باز دارند یا پایپ‌لاینشان در آخرین اجرا ناموفق بوده است، نزدیک‌ترین‌ها نخست، هر کدام با این‌که چند گام فاصله دارد و جدول‌های میان راه. سپس بقیه می‌آیند، پایپ‌لاین‌هایی که منابع آن را از بیرونِ آنچه OneUptime پایش می‌کند بارگذاری می‌کنند، و داشبوردهای BI که بر پایهٔ آن ساخته شده‌اند. هشدارهای باز شمرده می‌شوند، هرگز نام برده نمی‌شوند، و فقط آن‌هایی که پرسنده اجازهٔ دیدنشان را دارد.
- **یک بررسی از روی یک جمله.** در زبانهٔ **بررسی‌ها** در صفحهٔ یک جدول، **نوشتن بررسی از یک جمله** یک قاعده را به یک بررسی SQL سفارشی به زبان SQL موتور شما تبدیل می‌کند. [بررسی‌ها و تطبیق‌ها](/docs/data-observability/checks) را ببینید.

- **رانش آهسته.** وقتی سطرهای یک جدول، یا مقدار یک بررسی، در یک هفته یک پنجم یا بیشتر جابه‌جا شود، آن‌قدر آهسته که هیچ هشداری را فعال نکند، به‌عنوان یک «اینجا را ببینید» به AI Insights می‌رود. کسی را فرا نمی‌خواند.
- **داده کهنه پشت برنامه‌های هوش مصنوعی.** سرویسی که هم یک مدل را صدا می‌زند و هم یک جدول را می‌خواند، مصرف‌کننده هوش مصنوعی آن جدول است. وقتی چنین جدولی دیر می‌شود، صفحهٔ **گفتگوها** در محصول هوش مصنوعی این را می‌گوید: برنامه‌ای که از داده قدیمی پاسخ می‌دهد در ترِیس‌های خودش هیچ ایرادی نشان نمی‌دهد.

هر یک از این‌ها نیاز دارد که OneUptime AI برای پروژه روشن باشد، و با مجوزهای کسی که می‌پرسد عمل می‌کند.

## عامل‌های هوش مصنوعی و سرور MCP

عامل‌های هوش مصنوعی باید پیش از استفاده از داده بررسی کنند که تازه است، و پیش از تغییر یک جدول ببینند چه چیزی از آن ساخته می‌شود. [سرور MCP](/docs/ai/mcp-server) برای هر دو کار ابزارهای فقط‌خواندنی دارد:

| ابزار | به چه چیزی پاسخ می‌دهد |
| --- | --- |
| `get_data_table_freshness` | اینکه آیا یک جدول زیر نظر تازه است، آخرین بار کی تغییر کرده، هشدارهای باز آن، آخرین اجراهای نویسندگانش و محصولات داده‌اش. `table` را به‌صورت `schema.table`، فقط نام جدول، یا ID آن بدهید |
| `get_data_table_lineage` | این‌که یک جدول زیر نظر از چه ساخته می‌شود و چه چیزی از آن ساخته می‌شود، سه گام در هر سو یا تا پنج گام: نخست جدول‌هایی که مشکلی دارند، نزدیک‌ترین‌ها نخست، سپس بقیه، پایپ‌لاین‌هایی که منابع آن را از بیرون بارگذاری می‌کنند و داشبوردهای BI که بر پایهٔ آن ساخته شده‌اند. `table` را همان‌طور که برای تازگی‌اش می‌دهید بدهید، و `depth` را از ۱ تا ۵ |

هر دو با یک ورود فقط‌خواندنی کار می‌کنند، و به نام شخص یا کلید APIای که وارد شده است پاسخ می‌دهند.

## نقاط پایانی

| نقطه پایانی | برای چیست | امضاشده با |
| --- | --- | --- |
| `POST /telemetry/openlineage/api/v1/lineage` | رویدادهای OpenLineage از Airflow، Dagster، Spark، dbt یا Flink | یک کلید دریافت دادهٔ تله‌متری |
| `POST /telemetry/dbt/v1/artifacts` | `manifest` و `run_results` یک build در dbt | یک کلید دریافت دادهٔ تله‌متری |
| `POST /telemetry/fivetran/v1/webhook/<ingestion key ID>` | وب‌هوک‌های همگام‌سازی Fivetran | کلید دریافت داده، به‌عنوان راز امضای Fivetran |
| `POST /telemetry/airbyte/v1/webhook/<ingestion key>` | وب‌هوک‌های همگام‌سازی Airbyte | کلید دریافت داده در URL |
| `POST /api/data-observability/tables/freshness` | تازگی یک جدول، همان‌طور که ابزار MCP پاسخ می‌دهد، با `{ "table": "public.orders" }` | یک کلید API |
| `POST /api/data-observability/tables/lineage` | تبار یک جدول تا چند گام در هر سو، همراه با وضع کنونی هر جدول، همان‌طور که زبانهٔ **تبار** آن را رسم می‌کند، با `{ "dataAssetId": "<table ID>", "depth": 3 }`، و با `"withColumns": true` ستون‌هایی که هر پیکان می‌برد | یک کلید API |
| `POST /api/data-observability/tables/lineage/answer` | تبار یک جدول که با واژه‌ها گفته می‌شود، جدول‌هایی که مشکلی دارند نخست، همان‌طور که ابزار MCP پاسخ می‌دهد، با `{ "table": "public.orders", "depth": 3 }` | یک کلید API |
| `POST /api/data-observability/pipelines/lineage` | جدول‌هایی که یک پایپ‌لاین می‌خواند و می‌نویسد، همراه با وضع کنونی هر جدول، همان‌طور که صفحهٔ آن رسمشان می‌کند، با `{ "dataPipelineId": "<pipeline ID>", "depth": 1 }` | یک کلید API |
| `POST /api/data-observability/alerts/<alert ID>/lineage` | تبار یک هشدار داده، همان‌طور که صفحهٔ آن رسمش می‌کند، همراه با مسیر تا هشداری که باعث آن شده و تا هشدارهایی که آن باعث شده، و برای هشداری که از یک بررسی روی یک ستون آمده است، `column` آن و ستون‌هایی که هر پیکان می‌برد | یک کلید API |
| `POST /api/data-observability/lineage/expand` | جدول‌های بعدی‌ای که یک کارت از نمودار تبار رسم نمی‌کند، همان‌طور که انتخاب عددش آن‌ها را رسم می‌کند: کارت به‌صورت `nodeId` با `side` آن، و آنچه رسم شده به‌صورت `focusNodeId`، `tables` و `dataDashboardIds` | یک کلید API |
| `POST /api/data-observability/checks/apply` | بررسی‌های پروژه را با یک فایل یکی کنید، همان‌طور که `oneuptime data-checks apply` انجام می‌دهد، با `{ "manifest": "...", "isDryRun": true, "shouldPrune": false }` | یک کلید API |
| `GET /api/data-observability/data-products/<data product ID>/badge?token=<badge token>` | نشان «data as of» یک محصول داده | توکن خود نشان |

جدول‌ها، بررسی‌ها، تطبیق‌ها، پایپ‌لاین‌ها، محصولات داده، اتصال‌های BI و کارهای انبار داده همچنین منابع معمولی [API](/docs/api-reference/api-reference) هستند که با یک کلید API دارای مجوزهای متناظر خوانده و تغییر داده می‌شوند، و منابعی در سرور MCP و گردش‌کارها.

## متریک‌ها

هر عددی که مشاهده‌پذیری داده نگه می‌دارد، متریکی است که می‌توانید نمودارش را بکشید، روی داشبورد بگذارید یا بر اساس آن هشدار بگیرید: `oneuptime.data.table.*` برای هر جدول، `oneuptime.data.check.value` برای هر بررسی، `oneuptime.data.reconciliation.*` برای هر تطبیق، `oneuptime.data.pipeline.*` برای هر پایپ‌لاین و `oneuptime.data.product.*` برای هر محصول داده. این‌ها دادهٔ عملیاتی خود OneUptime هستند و به‌عنوان تله‌متری صورت‌حساب نمی‌شوند.
