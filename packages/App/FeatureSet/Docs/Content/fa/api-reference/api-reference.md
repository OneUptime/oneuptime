# مرجع API

OneUptime یک REST API جامع ارائه می‌دهد که با آن می‌توانید پایش، مدیریت حادثه و قابلیت‌های صفحه وضعیت را در برنامه‌ها و گردش‌های کاری خود یکپارچه کنید. **هر کاری که در داشبورد OneUptime می‌توانید انجام دهید از طریق API هم شدنی است، و همین خودکارسازی و یکپارچه‌سازی‌های سفارشی را ممکن می‌کند.**

### شروع به کار

API ما بر پایه اصول REST سازمان‌دهی شده است و از کدهای وضعیت، احراز هویت و افعال استاندارد HTTP استفاده می‌کند. همه نقاط پایانی API پاسخ‌های JSON برمی‌گردانند.

### احراز هویت

همه درخواست‌های API به احراز هویت با کلید API نیاز دارند. می‌توانید کلیدهای API را از داشبورد OneUptime خود در مسیر Settings > API Keys بسازید.

### رکوردهایی که یک درخواست نام می‌برد

بسیاری از منابع رکوردهای دیگری را نام می‌برند: یک مانیتور برچسب‌ها و پراب‌هایش را، یک مشترک صفحه وضعیت صفحه وضعیتش را، یک دستگاه شبکه سایتش را، و عضو یک حادثه، حادثه و نقش را. هر شناسه‌ای که برای یکی از این‌ها می‌فرستید باید رکوردی از پروژه شما باشد — انتخابگرهای داشبورد چیز دیگری پیشنهاد نمی‌کنند — و درخواست‌های ‏Terraform و گردش‌های کار نیز همین‌گونه سنجیده می‌شوند. شناسه رکوردی از پروژه‌ای دیگر و شناسه‌ای که وجود ندارد یکسان رد می‌شوند، با پاسخ `400`ای که نام فیلد و شناسه را می‌آورد:

```text
This network device references records that are not in this project: Network Site "…". Please pick values from this project and try again.
```

افراد با عضویتشان سنجیده می‌شوند: کسی که عضو پروژه نیست به همین شکل رد می‌شود. پراب سراسری، که هر پروژه‌ای می‌تواند به کارش ببرد، از آنِ پروژه شما به شمار می‌آید. تغییر یک منبع فقط شناسه‌هایی را می‌سنجد که آن تغییر می‌افزاید، پس منبعی که از چیزی نام می‌برد که بعداً حذف شده هنوز ذخیره می‌شود.

یک رکورد را می‌توان به دو شکل نام برد: با فیلد شناسه‌اش (`monitorId`)، یا با رابطه (`"monitor": { "_id": "…" }`)، که فرم‌های داشبورد همان را می‌فرستند. یکی از این دو را بفرستید. اگر درخواستی هر دو را بفرستد، هر دو باید یک رکورد را نام ببرند: درخواستی که این دو در آن یکی نیستند — دو شناسه متفاوت، یا یک شناسه و یک مقدار خالی — با پاسخ `400`ای رد می‌شود که نام هر دو فیلد را می‌آورد:

```text
Conflicting Monitor references were provided. monitorId and monitor are names for the same field and must hold the same value: send only one of them, or the same id in each.
```

هر دو نام به یک شکل سنجیده می‌شوند. قاعده‌های مربوط به رکوردی که نام می‌برید، به هر کدام از این دو نام که آن را بفرستید، برقرار می‌مانند: گروه والدِ یک گروه صفحه وضعیت باید در همان صفحه وضعیت باشد، یک صفحه وضعیت حداکثر سه پیوند سرصفحه می‌پذیرد، و نام یک گروه در صفحه وضعیتش باید یکتا باشد.

### وضعیتی که رکورد تازه در آن آغاز می‌شود

یک حادثه، یک هشدار، یک اپیزود حادثه و یک اپیزود هشدار را می‌توان در هر یک از وضعیت‌های پروژه‌تان ساخت، همان کاری که فیلد **Initial State** در فرم‌های ساختنشان می‌کند: `currentIncidentStateId` (برای حادثه‌ها و اپیزودهای حادثه) یا `currentAlertStateId` (برای هشدارها و اپیزودهای هشدار) را بفرستید، یا رابطه را. رکورد در همان وضعیت آغاز می‌شود و خط زمانی وضعیتش با همان وضعیت شروع می‌شود. اگر آن را نفرستید، رکورد در وضعیت created پروژه‌تان آغاز می‌شود، همان که پرچم `isCreatedState` را دارد — یا، برای حادثه‌ای که از روی قالبی با وضعیت آغازین اعلام می‌شود، در وضعیت آن قالب. وضعیتی از پروژه‌ای دیگر مانند هر رکورد دیگری رد می‌شود. `current_incident_state_id` و `current_alert_state_id` در Terraform هم به همین شکل کار می‌کنند.

### مرجع API

برای دیدن مرجع API OneUptime اینجا کلیک کنید ➡️ [مرجع API OneUptime](/reference). مرجع API به چند زبان در دسترس است — زبان مورد نظر شما به‌صورت خودکار از مرورگرتان تشخیص داده می‌شود و هر زمان می‌توانید با انتخابگر بالای صفحه زبان را عوض کنید.
