# رصدپذیری هوش مصنوعی / LLM با OneUptime

برنامه‌های LLM و عامل هوش مصنوعی خود را در OneUptime بپایید: ردیابی به ازای هر فراخوان، مصرف توکن، هزینه، تأخیر، خطاها، و خودِ اعلان‌ها و تکمیل‌ها — همه از راه OpenTelemetry استاندارد. هیچ SDK اختصاصی‌ای در کار نیست. اگر برنامه‌تان اسپن‌ها را با **قراردادهای معنایی GenAI** در OpenTelemetry (`gen_ai.*`) منتشر کند، OneUptime آن‌ها را به تجربه‌ای درجه‌یک از رصدپذیری هوش مصنوعی بدل می‌کند.

## چگونه کار می‌کند

‏OneUptime ردیابی‌های OpenTelemetry را در نقطه پایانی OTLP دریافت می‌کند. وقتی اسپنی ویژگی‌های GenAI را حمل کند، OneUptime خودکار:

- آن را به‌عنوان **فراخوان LLM** برچسب می‌زند و مدل، عملیات، ارائه‌دهنده، شمار توکن‌ها و هزینه را برای پرس‌وجوی سریع در ستون‌های اختصاصی استخراج می‌کند.
- در بخش اختصاصی **AI / LLM** نمایانش می‌کند (فهرستی از فراخوان‌های LLM به‌علاوه نمایی کلی از توکن / هزینه / تأخیر).
- روی اسپن یک **پنل AI / LLM** درجه‌یک ترسیم می‌کند که ارائه‌دهنده، مدل، توکن‌ها، هزینه، پارامترهای درخواست و محتوای اعلان و تکمیل را نشان می‌دهد.

چون همه‌چیز OpenTelemetry است، همان داده به داشبوردها و هشدارهای سنجه هم نیرو می‌دهد.

## گام ۱ — ساخت توکن دریافت تله‌متری

در OneUptime، مسیر **Project Settings → Telemetry & APM → Ingestion Keys** را باز کنید و روی **Create Ingestion Key** بزنید. کلید را کپی کنید — آن را به‌صورت هدر OTLP به برنامه‌تان می‌دهید. (برای تصویرها [راهنمای OpenTelemetry](/docs/telemetry/open-telemetry) را ببینید.)

## گام ۲ — ابزارگذاری برنامه‌تان

هر ابزارگذاری GenAI در OpenTelemetry را می‌توانید به کار ببرید. گزینه‌های محبوب:

- **OpenLLMetry** (Traceloop) — به‌طور خودکار OpenAI، Anthropic، Cohere، Bedrock، LangChain، LlamaIndex، CrewAI و بیشتر را ابزارگذاری می‌کند.
- **OpenInference** (Arize) — ابزارگذارهایی برای OpenAI، LangChain، LlamaIndex، DSPy و مانند آن.
- ابزارگذاری‌های GenAI **بومی OpenTelemetry**.

ترافیک LLM خود را از دروازه‌ای مانند **LiteLLM** یا **Portkey** عبور می‌دهید؟ به‌جای ابزارگذاری تک‌تک برنامه‌ها می‌توانید ردیابی‌ها را از خود دروازه صادر کنید — [پاییدن دروازه‌های هوش مصنوعی](/docs/telemetry/ai-gateways) را ببینید.

دنبال دستیارهای کدنویسی‌ای هستید که مهندسانتان اجرا می‌کنند — Claude Code، Cursor، Codex، Gemini CLI، Copilot — و نه برنامه‌های خودتان؟ آن‌ها OpenTelemetry خودشان را صادر می‌کنند و به هیچ ابزارگذاری‌ای از سوی شما نیاز ندارند. برای ماتریس پشتیبانی و راهنماهای هر ابزار [رصدپذیری دستیارهای کدنویسی هوش مصنوعی](/docs/telemetry/ai-coding-assistants) را ببینید.

### Python (OpenLLMetry)

```bash
pip install traceloop-sdk opentelemetry-exporter-otlp
```

```python
from traceloop.sdk import Traceloop

Traceloop.init(
    app_name="my-ai-agent",
    api_endpoint="https://oneuptime.com/otlp",   # or your self-hosted host + /otlp
    headers={"x-oneuptime-token": "YOUR_INGESTION_TOKEN"},
)

# Your normal OpenAI / Anthropic / LangChain calls are now traced automatically.
```

### Node.js / TypeScript (OpenLLMetry)

```bash
npm install @traceloop/node-server-sdk
```

```ts
import * as traceloop from "@traceloop/node-server-sdk";

traceloop.initialize({
  appName: "my-ai-agent",
  baseUrl: "https://oneuptime.com/otlp", // or your self-hosted host + /otlp
  headers: { "x-oneuptime-token": "YOUR_INGESTION_TOKEN" },
});
```

### متغیرهای محیطی ساده OpenTelemetry

اگر با SDK بومی OpenTelemetry ابزارگذاری می‌کنید، صادرکننده OTLP را به OneUptime نشانه بگیرید:

```bash
export OTEL_EXPORTER_OTLP_ENDPOINT="https://oneuptime.com/otlp"
export OTEL_EXPORTER_OTLP_HEADERS="x-oneuptime-token=YOUR_INGESTION_TOKEN"
export OTEL_SERVICE_NAME="my-ai-agent"
```

‏OneUptime را خودمیزبان می‌کنید؟ `https://oneuptime.com/otlp` را با `https://YOUR-ONEUPTIME-HOST/otlp` جایگزین کنید.

## ویژگی‌هایی که OneUptime می‌شناسد

‏OneUptime نخست قراردادهای GenAI در OpenTelemetry را می‌خواند، و به گونه‌های OpenLLMetry و OpenInference بازمی‌گردد تا کتابخانه‌های محبوب بی‌دردسر کار کنند.

| چه چیزی | ویژگی اصلی | همچنین پذیرفته می‌شود |
| --------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ارائه‌دهنده / سامانه | `gen_ai.provider.name` | `gen_ai.system` (در قراردادها منسوخ شده، اما هنوز گسترده منتشر می‌شود)، `llm.system`، `llm.provider` |
| عملیات | `gen_ai.operation.name` | `llm.request.type`، `openinference.span.kind` |
| مدل درخواست‌شده | `gen_ai.request.model` | `llm.model_name`، `llm.request.model` |
| مدل پاسخ | `gen_ai.response.model` | `llm.response.model` |
| توکن‌های ورودی | `gen_ai.usage.input_tokens` | `gen_ai.usage.prompt_tokens`، `llm.token_count.prompt`، `llm.usage.prompt_tokens` |
| توکن‌های خروجی | `gen_ai.usage.output_tokens` | `gen_ai.usage.completion_tokens`، `llm.token_count.completion`، `llm.usage.completion_tokens` |
| کل توکن‌ها | `gen_ai.usage.total_tokens` | `llm.token_count.total`، `llm.usage.total_tokens`؛ وقتی هیچ‌کدام گزارش نشود از ورودی + خروجی مشتق می‌شود |
| هزینه (دلار) | `gen_ai.usage.cost` | `gen_ai.usage.cost_usd`، `gen_ai.usage.total_cost`، `llm.usage.total_cost`، `gen_ai.cost.total_cost` (‏LiteLLM)، `litellm.cost.total` |
| نام عامل | `gen_ai.agent.name` | `agent.name` |
| نام ابزار | `gen_ai.tool.name` | `tool.name` |
| شناسه گفتگو / نشست | `gen_ai.conversation.id` | `session.id`، `langfuse.session.id`، `traceloop.association.properties.session_id` |
| کارمند (کسی که فراخوان را اجرا کرده) | `user.id` | `enduser.id`، `litellm.metadata.user_api_key_user_id` و `metadata.user_api_key_user_id` (املاهای LiteLLM OTel v2 و v1 — هر دو خوانده می‌شوند)، `traceloop.association.properties.user_id`، `langfuse.user.id`، `user.account_uuid`، `user.account_id`، `cursor.user.id` |
| ایمیل کارمند | `user.email` | `traceloop.association.properties.user_email`، `enduser.email` |

زیرکلیدهای `traceloop.association.properties.*` ویژگی‌های وابستگی‌اند که **فراخوان‌کننده فراهمشان می‌کند**، نه نام‌هایی که OpenLLMetry خودش منتشر کند — Traceloop پیشوند `traceloop.association.properties` را تعریف می‌کند و کد شما آنچه را زیرش می‌آید فراهم می‌کند. OneUptime آن‌ها را می‌خواند، اما فقط اگر برنامه‌هایتان از آن قرارداد پیروی کنند.
| تیم / مرکز هزینه | `team.id` | `team`، `cost_center`، `department`، `litellm.metadata.user_api_key_team_id` و `litellm.team.id` (‏LiteLLM OTel v2)، `metadata.user_api_key_team_id` (‏LiteLLM OTel v1)، `cursor.team.id` |

کلیدهای `gen_ai.usage.total_tokens` و `gen_ai.usage.cost` کلیدهایی **عملاً رایج**اند، نه قراردادهای معنایی GenAI — قراردادها هیچ ویژگی‌ای برای کل توکن و اصلاً هیچ ویژگی هزینه‌ای تعریف نمی‌کنند. OneUptime آن‌ها را می‌خواند چون ابزارگذاری‌های رایج منتشرشان می‌کنند. `gen_ai.system` پیشینِ منسوخ‌شده خودِ قراردادها برای `gen_ai.provider.name` است؛ هر دو خوانده می‌شوند.

**سه سطر هویت با پیشوند `resource.` هم تطبیق داده می‌شوند.** دریافت OTLP هر ویژگی _منبع_ را با پیشوند `resource.` در نگاشت ویژگی‌های اسپن مسطح می‌کند، پس `OTEL_RESOURCE_ATTRIBUTES=team.id=platform` به‌صورت `resource.team.id` می‌رسد، نه `team.id`. OneUptime روی سطرهای شناسه کارمند، ایمیل کارمند و تیم دنبال هر دو املا می‌گردد — نخست کل فهرست برهنه، سپس کل فهرست پیشونددار با `resource.` — پس ویژگی اسپن (که یک فراخوان را توصیف می‌کند) بر ویژگی منبع (که کل فرایند را توصیف می‌کند) می‌چربد. باقی سطرهای جدول فقط بر کلید برهنه تطبیق می‌شوند: آن‌ها مقادیری به ازای هر فراخوان‌اند، و `gen_ai.request.model` در دامنه منبع، به‌جای آنکه قراردادی شایسته پشتیبانی باشد، پیکربندی نادرست است.

**محتوای اعلان و تکمیل** از رخداد کنونی `gen_ai.client.inference.operation.details` و ویژگی‌های اسپن `gen_ai.input.messages` / `gen_ai.output.messages` / `gen_ai.system_instructions` خوانده می‌شود، از رخدادهای اکنون **منسوخ‌شده** به ازای هر نقش که ابزارگذاری‌های قدیمی‌تر هنوز منتشرشان می‌کنند (`gen_ai.system.message`، `gen_ai.user.message`، `gen_ai.tool.message`، `gen_ai.assistant.message`، `gen_ai.choice`)، از ویژگی‌های نمایه‌دار (`gen_ai.prompt.N.content` / `gen_ai.completion.N.content`، و `llm.input_messages.N.message.content` / `llm.output_messages.N.message.content` در OpenInference)، یا از آرایه‌های پیام JSON (`gen_ai.input.messages`، `gen_ai.output.messages`، `gen_ai.prompt`، `gen_ai.completion`، `input.value`، `output.value`) — و در پنل AI / LLM ترسیم می‌شود.

**گروه‌بندی گفتگو:** ‏OneUptime شناسه گفتگو/نشست را از `gen_ai.conversation.id` (قراردادهای معنایی OTel)، `session.id` (‏OpenInference / SDKهای سازگار با Langfuse)، `langfuse.session.id` یا `traceloop.association.properties.session_id` (‏OpenLLMetry) بیرون می‌کشد و آن را به‌عنوان ستونی درجه‌یک و قابل پرس‌وجو (`llmConversationId`) روی اسپن ذخیره می‌کند. این به شما امکان می‌دهد همه فراخوان‌های LLM متعلق به یک تعامل کاربر را بپالایید، حتی وقتی در چند ردیابی پخش شده باشند.

### هزینه چگونه محاسبه می‌شود

اگر ابزارگذاری شما هزینه‌ای گزارش کند (`gen_ai.usage.cost`)، OneUptime همان را عیناً به کار می‌برد — مقدار گزارش‌شده همیشه برنده است. وقتی هزینه‌ای گزارش نشود، OneUptime **هزینه‌ای برآوردی هنگام دریافت** را از روی شمار توکن‌های اسپن و فهرست‌بهای توکاری از مدل‌های رایج OpenAI، Anthropic، Google Gemini، Mistral، DeepSeek، xAI، Cohere، Amazon Nova و Meta Llama محاسبه می‌کند. مدل‌ها بر پایه پیشوند نام تطبیق داده می‌شوند، پس عکس‌های لحظه‌ای تاریخ‌دار مانند `gpt-4o-2024-08-06` و شناسه‌های آراسته با نام فروشنده مانند `us.anthropic.claude-3-5-sonnet-20241022-v2:0` درست تفکیک می‌شوند. مدل‌های ناشناخته یا سفارشی هرگز حدس زده نمی‌شوند — هزینه‌شان `0` می‌ماند. برآوردها از قیمت‌های فهرست استفاده می‌کنند و تخفیف‌های حافظه نهان یا دسته‌ای را به حساب نمی‌آورند.

‏OneUptime را خودمیزبان می‌کنید؟ اگر می‌خواهید فهرست را گسترش دهید، در `Common/Types/Telemetry/LlmCostCatalog.ts` جای دارد.

## انتساب کارمند و تیم

«کدام‌یک از مهندسان ما ماه گذشته ۴ هزار دلار روی Opus سوزاند» پرسشی درباره یک شخص است، و هیچ اسپن LLMای پاسخش نمی‌دهد مگر چیزی روی اسپن شخصی را نام ببرد. OneUptime کنشگر انسانی را هنگام دریافت در ستون‌های قابل پرس‌وجو استخراج می‌کند، پس به‌جای نوشتن دستی جست‌وجوی ویژگی‌ها، روی یک ستون گروه‌بندی و پالایش می‌کنید.

سه سطر هویت در جدول بالا کل سازوکارند. نخستین کلید موجود برنده است، به همان ترتیبی که فهرست شده. `user.id` پیشتاز است چون کلید متعارف OpenTelemetry برای کنشگر انسانی است و همانی است که اگر خودتان هویت را می‌زنید باید بر آن استاندارد شوید. **یک استثنا: Claude Code** مقدار `user.id` را به‌صورت شناسه‌ای ناشناس و تصادفی منتشر می‌کند که در `~/.claude.json` ماندگار می‌شود، نه یک شخص. روی نقطه‌داده‌های سنجه‌اش بی‌ضرر است، چون فهرست سنجه ایمیل‌اول است — اما اگر بتای ردیابی‌های Claude Code را روشن کنید، آن `user.id` ناشناس روی اسپن‌ها بر `user.email` می‌چربد. برای آن ناوگان، `user.id` را در پردازشگر جمع‌کننده بیندازید یا بازنگاشتش کنید. `enduser.id` هنوز ویژگی‌ای فعال در قراردادهای معنایی است — منسوخ‌سازی نسخه 1.25 مقادیر `enduser.role` و `enduser.scope` را برداشت، نه `enduser.id` را — پس به‌عنوان نام مستعاری هم‌ارز پذیرفته می‌شود. `cursor.user.id` آخر مرتب می‌شود چون عددی صحیح، مبهم و در دامنه تیم است که برای رسیدن به یک شخص به API مدیریتی Cursor نیاز دارد.

هویت روی اسپن فقط وقتی خوانده می‌شود که اسپن از پیش به‌عنوان فراخوان LLM شناخته شده باشد. `user.id`، `user.email` و `team.id` کلیدهای عمومی OpenTelemetry هستند که اسپن‌های مرورگر و اسپن‌های معمولی پشتی هم حملشان می‌کنند؛ زدن ستون‌های هویت روی آن‌ها مقدار را در پرحجم‌ترین رده‌های اسپنِ موجود کپی می‌کرد تا به پرسشی خدمت کند که فقط اسپن‌های LLM پاسخش می‌دهند.

**نقطه‌داده‌های سنجه** فهرستی کوتاه‌تر و ایمیل‌اول حمل می‌کنند: `user.email`، `user.id`، `user.account_uuid`، `user.account_id`، `cursor.user.id`، با تیم‌ها از `team.id`، `team`، `cost_center`، `department` و `cursor.team.id` — هرکدام به همان دلیلی که روی اسپن‌ها گفته شد، با پیشوند `resource.` هم تطبیق می‌شوند. ایمیل آنجا پیشتاز است چون CLIهای عامل کدنویسی که سنجه بدون اسپن منتشر می‌کنند، `user.email` را بومی منتشر می‌کنند.

امروز هیچ‌چیزی هویت را از **رکوردهای گزارش** نمی‌خواند.

### تنظیم تیم و مرکز هزینه

هیچ‌یک از `team.id`، `team`، `cost_center` یا `department` را هیچ ابزارگذاری‌ای منتشر نمی‌کند — این‌ها چیزی‌اند که سازمان شما تنظیم می‌کند، به‌طور مرسوم از راه `OTEL_RESOURCE_ATTRIBUTES` روی فرایند:

```bash
export OTEL_RESOURCE_ATTRIBUTES="team.id=platform,team=Platform_Engineering,cost_center=eng-123,department=engineering"
```

آن متغیر ویژگی‌های _منبع_ را تنظیم می‌کند، که به‌صورت `resource.team.id`، `resource.team`، `resource.cost_center` و `resource.department` به OneUptime می‌رسند. هر دو لایه هم روی اسپن‌ها و هم روی نقطه‌داده‌های سنجه شناخته می‌شوند، پس این کار می‌کند چه صادرکننده‌تان کلیدها را در بلوک منبع OTLP رها کند و چه روی هر اسپن و نقطه‌داده کپی‌شان کند (‏Claude Code به‌طور پیش‌فرض دومی را می‌کند). `team.id` برهنه‌ای که مستقیم روی اسپن تنظیم شده باشد هنوز بر نمونه سطح منبع می‌چربد.

املاهای دروازه (`litellm.metadata.user_api_key_team_id`، `litellm.team.id`، `metadata.user_api_key_team_id`، `cursor.team.id`) بدون هیچ پیکربندی‌ای از سوی شما می‌رسند. LiteLLM بسته به اینکه در کدام حالت OpenTelemetry اجرا شود این ویژگی‌ها را جور دیگری نام می‌دهد: فراخوان‌برگشتی پیش‌فرض `otel` نسخه v1 آن‌ها را با پیشوند برهنه `metadata.` منتشر می‌کند (`metadata.user_api_key_user_id`، `metadata.user_api_key_user_email`، `metadata.user_api_key_team_id`)، در حالی که حالت انتخابی v2 (`LITELLM_OTEL_V2=true`) از فضای‌نام `litellm.` استفاده می‌کند. **OneUptime هر دو را می‌خواند**، پس پراکسی LiteLLM دست‌نخورده برای کار کردن انتساب به پیکربندی اضافه‌ای نیاز ندارد.

### کلیدهای مشتری عمداً کنار گذاشته شده‌اند

اسپن LLM می‌تواند **دو** انسان متفاوت را حمل کند: کارمندی که فراخوان را زده، و **مشتری** پایین‌دستی‌ای که فراخوان به نمایندگی از او زده شده است. این سه کلید دومی را حمل می‌کنند، و OneUptime عمداً هیچ‌کدامشان را در ستون هویت **نمی‌خواند**:

- `gen_ai.user` و `llm.user` — همان‌گونه که ابزارگذاری‌ها پارامتر درخواست `user` در OpenAI را بازتاب می‌دهند؛ این پارامتر اکنون به سود `safety_identifier` و `prompt_cache_key` منسوخ شده و OpenAI مستندش کرده است به‌عنوان «شناسه‌ای پایدار برای کاربران نهایی شما»، که فرستاده می‌شود تا OpenAI بتواند سوءاستفاده از سوی کاربرانِ _شما_ را تشخیص دهد.
- `litellm.metadata.user_api_key_end_user_id`، `metadata.user_api_key_end_user_id` و `litellm.end_user.id` — شناسه صریح کاربر نهایی در LiteLLM در هر سه املایش، متمایز از شناسه صاحب کلید که **همان** کارمند است و **شناخته می‌شود**. هر سه کنار گذاشته شده‌اند، پس هیچ‌کدام از دو حالت OTel نمی‌تواند شناسه مشتری را به ستون کارمند نشت دهد.

دلیلش درستی بازپرداخت هزینه است. شناسه مشتری پایین‌دستی را در ستون کارمند بخوانید و رباتی پشتیبان که به ۴۰٬۰۰۰ مشتری خدمت می‌دهد، ۴۰٬۰۰۰ «کارمند» خیالی می‌سازد، در حالی که مهندسی که واقعاً صاحب آن خرج است چنین می‌نماید که هیچ خرج نکرده. انتساب نادرست از انتساب غایب بدتر است، چون شکل یک پاسخ را دارد.

این ویژگی‌ها همچنان در نگاشت ویژگی‌های خام هستند و می‌توانید مستقیم پرس‌وجویشان کنید. اگر تحلیل مشتری پایین‌دستی می‌خواهید، جایش ستون خودش است، هرگز با تا زدن کلید مشتری در فهرست کارمند.

### ستون‌های هویت پاک‌سازی می‌شوند

ستون ایمیل کارمند اطلاعات هویتی واقعی نگه می‌دارد. این ستون دقیقاً مانند ویژگی‌ای که از آن مشتق شده، زیر دامنه **Attributes** مشمول **قواعد پاک‌سازی** تله‌متری شماست، پس قاعده‌ای برای زدودن ایمیل روی ستون استخراج‌شده هم اعمال می‌شود، نه اینکه خاموش از کنار همان یک ستونی بگذرد که محتمل‌ترین جا برای نگه داشتن ایمیل است. قواعد پاک‌سازی و پالایه‌های حذف را زیر **Traces → Settings** پیکربندی کنید.

## دیدن فراخوان‌های LLM

بخش **AI / LLM** را در نوار ناوبری باز کنید (زیر Observability):

- **Overview** — کل فراخوان‌ها، توکن‌های ورودی/خروجی، هزینه و نرخ خطا برای ۷ روز گذشته، به‌علاوه تازه‌ترین فراخوان‌ها.
- **LLM Calls** — فهرستی قابل پالایش از هر فراخوان LLM، جاسازی، عامل و ابزار. بر پایه ارائه‌دهنده، مدل، عملیات یا سرویس بپالاییدش. روی فراخوانی بزنید تا در نمایشگر ردیابی باز شود.
- **Usage** — کارمندان، تیم‌ها، مدل‌ها، ارائه‌دهندگان و سرویس‌ها رتبه‌بندی‌شده بر پایه خرج، ساخته‌شده بر ستون‌های هویت بالا. برای اینکه ببینید منبعی فقط-سنجه مانند CLI عامل کدنویسی اینجا چگونه پدیدار می‌شود، [اسپن‌ها و سنجه‌ها بازگشت‌اند، نه جمع](#اسپنها-و-سنجهها-بازگشتاند-نه-جمع) را ببینید.
- **Budgets** — بودجه‌های هزینه روزانه که به‌صورت سنجه منتشر می‌شوند تا مانیتورها بر آن‌ها هشدار دهند (پایین‌تر [بودجه‌های هزینه روزانه](#بودجههای-هزینه-روزانه) را ببینید).
- هر اسپنی زبانه/پنل **AI / LLM** دارد با مدل، شمار توکن‌ها، هزینه، پارامترهای درخواست، و اعلان و تکمیل ترسیم‌شده.

### اسپن‌ها و سنجه‌ها بازگشت‌اند، نه جمع

این قاعده‌ای است که تعیین می‌کند ناوگانی درهم‌آمیخته چه می‌بیند، پس ارزش دارد به‌جای پانوشت، صریح گفته شود.

**اسپن‌های GenAI مرجع‌اند. جریان سنجه فقط وقتی به مشورت گرفته می‌شود که جریان اسپن هیچ گزارش نکرده باشد، و آن دو هرگز با هم جمع نمی‌شوند.** اسپن مدل، توکن‌ها و هزینه را روی یک سطر حمل می‌کند، پس هرجا اسپن باشد به هر پرسشی پاسخ می‌دهد. هرجا نباشد — CLIهای عامل کدنویسی _سنجه‌های_ توکن و هزینه منتشر می‌کنند و هیچ اسپن GenAI — جریان سنجه جایش را می‌گیرد.

جمع نمی‌شوند چون کم نیستند ابزارگذاری‌هایی که برای همان یک فراخوان هر دو سیگنال را منتشر می‌کنند (‏OpenLLMetry حالت رایج است). افزودنشان به هم، هر یک از آن دلارها را دو بار می‌شمرد، و رقمی بادکرده که هشدار بودجه‌ای را کنترل می‌کند از رقمی غایب بدتر است: بر خرجی شلیک می‌کند که هرگز رخ نداده.

پیامدی که باید برایش برنامه بریزید: **همین که اسپن‌های GenAI شما رقمی ناصفر گزارش کنند، سهم منبعی فقط-سنجه در آن رقم پدیدار نمی‌شود.** اگر سرویسی Python ابزارگذاری‌شده دارید که اسپن‌های `gen_ai.*` منتشر می‌کند _و_ ناوگانی از Claude Code که سنجه‌های `claude_code.*` را به همان پروژه می‌ریزد، کاشی‌های Overview و جدول Usage اسپن‌ها را می‌خوانند و همان‌جا می‌ایستند — خرج Claude Code رویش افزوده نمی‌شود. بازگشت به ازای هر رقم و هر تفکیک است، نه به ازای هر منتشرکننده، پس دقیقاً وقتی روشن می‌شود که رقمی وگرنه صفر می‌بود:

| کجا | چه چیزی به سنجه بازمی‌گردد | چه وقت |
| --------------------------------------- | ------------------------------------------------ | ------------------------------------ |
| ‏Overview → Input / Output tokens | مجموع توکن‌های ورودی و خروجی | هر دو مجموع توکن اسپن ۰ باشند |
| ‏Overview → Cost (USD) | هزینه، بر حسب دلار و میکرودلار، مقیاس‌شده و افزوده | مجموع هزینه اسپن ۰ باشد |
| ‏Overview → LLM calls, Errored calls | هیچ‌چیز — فقط اسپن | — |
| ‏Usage → Employee, Team, Model | فقط هزینه. ستون‌های فراخوان و توکن به‌صورت `—` ترسیم می‌شوند | آن تفکیک هیچ سطر اسپنی برنگرداند |
| ‏Usage → Provider, Application / Service | هیچ‌چیز — فقط اسپن | — |

‏Provider و Application/Service بازگشت سنجه‌ای ندارند چون سیگنالش وجود ندارد: شمارنده‌های عامل کدنویسی هیچ ویژگی ارائه‌دهنده GenAI حمل نمی‌کنند (`gen_ai.provider.name`، یا پیشین منسوخ‌شده‌اش `gen_ai.system`)، و به هیچ سرویس تله‌متری OneUptime پیوست نیستند. زبانه Usage به‌جای گذاشتن جدولی خالی و واگذاشتن شما به حدس، همین را می‌گوید.

هرجا رقمی از سنجه‌ها آمده باشد، صفحه برچسبش می‌زند **from GenAI metrics**، چون هزینه‌ای که از سنجه آمده هیچ سطر متناظری در فهرست LLM Calls ندارد و عددی بی‌برچسب به‌صورت یک تناقض خوانده می‌شد.

**اگر لازم دارید خرج ابزاری فقط-سنجه روی پای خودش بایستد، پروژه‌ای جداگانه بهش بدهید** (یا کلید دریافت و پروژه خودش)، تا جریان اسپنش واقعاً خالی باشد و بازگشت درگیر شود. همین درباره بودجه‌ها هم صدق می‌کند: بودجه‌ای که دامنه‌اش سرویس‌های منتشرکننده اسپن و سرویس‌های فقط-سنجه را درهم می‌آمیزد به اسپن‌ها فرو می‌کاهد و فقط-سنجه‌ها را کم می‌شمارد — به‌جایش به ازای هر سرویس یک بودجه دامنه‌بندی کنید.

## داشبوردها و هشدارها

چون سنجه‌های GenAI به‌صورت سنجه‌های معمولی OpenTelemetry می‌رسند، می‌توانید:

- **داشبورد** بسازید که `gen_ai.client.token.usage`، `gen_ai.client.operation.duration` و مانند آن را نمودار کند (‏Dashboards → افزودن نموداری روی سنجه).
- **مانیتور سنجه** بسازید تا بر خرج توکن، تأخیر یا نرخ خطا هشدار دهد — برای نمونه وقتی p95 مقدار `gen_ai.client.operation.duration` از آستانه‌ای می‌گذرد، گروه‌بندی‌شده بر پایه مدل، هشدار دهد. [مانیتور سنجه](/docs/monitor/metrics-monitor) را ببینید.

## بودجه‌های هزینه روزانه

بخش **AI / LLM** زبانه‌ای به نام **Budgets** دارد. هر بودجه‌ای سقفی روزانه بر حسب دلار می‌گذارد که روی روز UTC سنجیده می‌شود. هر ۱۵ دقیقه کارگری پس‌زمینه‌ای هزینه اسپن LLM آن روز را جمع می‌زند (گزارش‌شده توسط SDK یا محاسبه‌شده)، خرج جاری را روی بودجه ثبت می‌کند، و دو سنجه گیج منتشر می‌کند:

| سنجه | معنا |
| ----------------------------------- | ------------------------------------- |
| `oneuptime.llm.budget.spend.usd` | خرج تا این لحظه آن روز، بر حسب دلار |
| `oneuptime.llm.budget.percent.used` | خرج به‌صورت درصدی از سقف روزانه |

هر دو ویژگی‌های `oneuptime.llm.budget.id` و `oneuptime.llm.budget.name` را حمل می‌کنند (به‌علاوه دامنه سرویس/ارائه‌دهنده/مدل بودجه هرگاه تنظیم شده باشد)، پس یک سری سنجه تمیز به یک خط به ازای هر بودجه تفکیک می‌شود. مانیتورها را با **`oneuptime.llm.budget.id`** بپالایید — پایدار است؛ ویژگی نام برای برچسب نمودار راحت است اما اگر بودجه را بازنام‌گذاری کنید تغییر می‌کند، که مانیتوری پالوده‌شده بر پایه نام را خاموش جدا می‌کرد.

**هشداردهی یعنی یک [مانیتور سنجه](/docs/monitor/metrics-monitor) روی آن سنجه‌ها.** برای الگوی کلاسیک ۸۰٪/۱۰۰٪، مانیتوری روی `oneuptime.llm.budget.percent.used` بسازید، بر پایه `oneuptime.llm.budget.id` بپالاییدش، و دو معیار بیفزایید — مقدار `>= 80` که هشداری با شدت اخطار می‌سازد، و مقدار `>= 100` که هشداری بحرانی می‌سازد و به سیاست کشیک شما پیوست است. **زمان غلتان مانیتور را روی ۳۰ دقیقه بگذارید**: هر بودجه‌ای هر ۱۵ دقیقه یک نقطه منتشر می‌کند، پس پنجره پیش‌فرض ۱ دقیقه‌ای میان جاروها سری خالی می‌یافت و هشدار را می‌لرزاند. چون سنجه‌ای معمولی است، هر کاری مانیتورها می‌توانند بکنند اینجا هم صدق می‌کند: فرمول‌ها، تشخیص ناهنجاری در برابر خط پایه‌های آموخته‌شده، داشبوردهایی که خرج را در سراسر بودجه‌ها نمودار می‌کنند.

بودجه‌ها را می‌توان به سرویس تله‌متری، ارائه‌دهنده LLM (نام ارائه‌دهنده در `gen_ai`) یا مدلی دقیق دامنه‌بندی کرد — یا در سطح کل پروژه رها کرد. چند بودجه می‌توانند کنار هم باشند، برای نمونه بودجه‌ای در سطح پروژه به‌علاوه بودجه‌ای سخت‌گیرانه‌تر برای مدلی گران.

مانیتورهای بودجه بیش از آگاه‌سازی می‌توانند بکنند: یکی را به گردش کاری‌ای زنجیر کنید که در زیرساخت شما وب‌هوکی را فرا می‌خواند تا عاملی لگام‌گسیخته را متوقف کند — [قطع مدار عامل‌های لگام‌گسیخته هوش مصنوعی](/docs/telemetry/ai-agent-circuit-breaker) را ببینید.

## حریم خصوصی و پاک‌سازی

محتوای اعلان و تکمیل می‌تواند داده حساس داشته باشد. OneUptime **قواعد پاک‌سازی** و **پالایه‌های حذف** تله‌متری موجود شما را درست مانند هر ردیابی دیگری بر اسپن‌های LLM اعمال می‌کند، پس می‌توانید ویژگی‌ها را پیش از ذخیره شدن بزدایید یا بیندازید. این‌ها را زیر **Traces → Settings** پیکربندی کنید. ستون استخراج‌شده ایمیل کارمند مشمول همان قواعد است — [ستون‌های هویت پاک‌سازی می‌شوند](#ستونهای-هویت-پاکسازی-میشوند) را ببینید.
