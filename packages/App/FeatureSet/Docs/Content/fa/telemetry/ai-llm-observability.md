# رصدپذیری هوش مصنوعی / LLM با OneUptime

هر گفتگویی را که هوش مصنوعی‌تان داشته بخوانید، آن را همان‌طور که رخ داده بازپخش کنید، و وقتی بد پاسخ می‌دهد باخبر شوید. همه‌چیز بر OpenTelemetry استاندارد اجرا می‌شود و هیچ SDK اختصاصی‌ای در کار نیست: اگر برنامه‌تان اسپن‌ها را با **قراردادهای معنایی GenAI** در OpenTelemetry (`gen_ai.*`) منتشر کند، OneUptime آن‌ها را به گفتگو، هشدار، مصرف و هزینه بدل می‌کند.

## آنچه به دست می‌آورید

بخش **AI / LLM** را در نوار ناوبری، زیر Observability، باز کنید:

- **Conversations** — هر گفتگویی که هوش مصنوعی‌تان داشته: افراد چه پرسیدند، هوش مصنوعی چه پاسخی داد، از چه ابزارهایی استفاده کرد و چه چیزی اشتباه پیش رفت. پنج عدد بالای فهرست می‌نشیند: گفتگوها، پاسخ‌های هوش مصنوعی، شمار گفتگوهایی که نیاز به توجه دارند، هزینه، و مدت معمول یک پاسخ. گفتگویی را باز کنید تا آن را بخوانید یا بازپخش کنید.
- **Calls** — هر فراخوان LLM، تعبیه، عامل و ابزار، قابل پالایش بر پایه سرویس، ارائه‌دهنده، مدل، عملیات، شخص و تیم. روی فراخوانی بزنید تا در نمایشگر ردیابی باز شود.
- **Usage** — فراخوان‌ها، توکن‌ها و هزینه یک بازه زمانی، و اینکه چه کسی چه خرج می‌کند: کارمندان، تیم‌ها، مدل‌ها، ارائه‌دهندگان و برنامه‌ها رتبه‌بندی‌شده بر پایه خرج.
- **Alerts** — هشدارهای آماده برای وقتی که هوش مصنوعی بد پاسخ می‌دهد، و مانیتورهای AI / LLM شما.
- **Budgets** — سقف‌های هزینه روزانه که به‌صورت سنجه منتشر می‌شوند تا بر آن‌ها هشدار دهید.
- **Pricing** — قیمت‌های خودتان به ازای هر مدل، برای مدل‌هایی که فهرست توکار نمی‌شناسد.
- **Setup** — پنج گام زیر، همراه با نقطه پایانی پروژه‌تان.

در نمایشگر ردیابی، اسپن هر فراخوان هوش مصنوعی یک پنل **AI / LLM** هم دارد با مدل، شمار توکن‌ها، هزینه، پارامترهای درخواست، و اعلان و تکمیل.

## گام ۱ — فراخوان‌های هوش مصنوعی‌تان را بفرستید

یک کلید دریافت تله‌متری بسازید: مسیر **Project Settings → Telemetry & APM → Ingestion Keys** را باز کنید و روی **Create Ingestion Key** بزنید. برنامه‌تان کلید را به‌صورت هدر OTLP می‌فرستد. (برای تصویرها [راهنمای OpenTelemetry](/docs/telemetry/open-telemetry) را ببینید.)

سپس برنامه‌تان را با هر کتابخانه GenAI در OpenTelemetry ابزارگذاری کنید:

- **OpenLLMetry** (Traceloop) — ‏OpenAI، Anthropic، Cohere، Bedrock، LangChain، LlamaIndex، CrewAI و بیشتر.
- **OpenInference** (Arize) — ‏OpenAI، LangChain، LlamaIndex، DSPy و بیشتر.
- **Vercel AI SDK**، یا **ابزارگذاری‌های OpenTelemetry** برای OpenAI، Anthropic و Gemini.

ترافیک LLM خود را از دروازه‌ای مانند **LiteLLM** یا **Portkey** عبور می‌دهید؟ به‌جای ابزارگذاری تک‌تک برنامه‌ها، ردیابی‌ها را از خود دروازه صادر کنید — [پاییدن دروازه‌های هوش مصنوعی](/docs/telemetry/ai-gateways) را ببینید. دنبال دستیارهای کدنویسی‌ای هستید که مهندسانتان اجرا می‌کنند — Claude Code، Cursor، Codex، Gemini CLI، Copilot؟ آن‌ها OpenTelemetry خودشان را صادر می‌کنند و چیزی از شما نمی‌خواهند: [رصدپذیری دستیارهای کدنویسی هوش مصنوعی](/docs/telemetry/ai-coding-assistants) را ببینید.

### Python (OpenLLMetry)

```bash
pip install traceloop-sdk opentelemetry-exporter-otlp
```

```python
from traceloop.sdk import Traceloop

Traceloop.init(
    app_name="my-ai-agent",
    api_endpoint="https://oneuptime.com/otlp",   # or your self-hosted host + /otlp
    headers={"x-oneuptime-token": "YOUR_INGESTION_TOKEN"},
)

# Your normal OpenAI / Anthropic / LangChain calls are now traced automatically.
```

### Node.js / TypeScript (OpenLLMetry)

```bash
npm install @traceloop/node-server-sdk
```

```ts
import * as traceloop from "@traceloop/node-server-sdk";

traceloop.initialize({
  appName: "my-ai-agent",
  baseUrl: "https://oneuptime.com/otlp", // or your self-hosted host + /otlp
  headers: { "x-oneuptime-token": "YOUR_INGESTION_TOKEN" },
});
```

### متغیرهای محیطی ساده OpenTelemetry

اگر با یک SDK بومی OpenTelemetry ابزارگذاری می‌کنید، صادرکننده OTLP را به سوی OneUptime بگیرید:

```bash
export OTEL_EXPORTER_OTLP_ENDPOINT="https://oneuptime.com/otlp"
export OTEL_EXPORTER_OTLP_HEADERS="x-oneuptime-token=YOUR_INGESTION_TOKEN"
export OTEL_SERVICE_NAME="my-ai-agent"
```

‏OneUptime را خودمیزبان می‌کنید؟ `https://oneuptime.com/otlp` را با `https://YOUR-ONEUPTIME-HOST/otlp` جایگزین کنید.

## گام ۲ — آنچه گفته شد را ثبت کنید

گفتگو وقتی نشان می‌دهد افراد چه پرسیدند و هوش مصنوعی چه پاسخ داد که ابزارگذاری‌تان آن‌ها را ثبت کند. ‏OpenLLMetry اعلان‌ها و تکمیل‌ها را ثبت می‌کند مگر اینکه خاموشش کنید (`TRACELOOP_TRACE_CONTENT=false`). ابزارگذاری‌های OpenTelemetry فقط وقتی ثبتشان می‌کنند که بخواهید:

```bash
export OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=true
```

بدون آن‌ها، گفتگو همچنان زمان‌بندی، هزینه و مشکلاتش را نشان می‌دهد و می‌گوید محتوایش ثبت نشده است. اعلان‌ها ممکن است داده حساس داشته باشند: برای پوشاندن آن پیش از ذخیره شدن، [حریم خصوصی و پاک‌سازی](#حریم-خصوصی-و-پاکسازی) را ببینید.

## گام ۳ — فراخوان‌ها را در گفتگوها گروه‌بندی کنید

برنامه گفتگومحور در هر نوبت یک فراخوان مدل انجام می‌دهد. `gen_ai.conversation.id` — یا `session.id` — را در هر فراخوان هوش مصنوعی برابر شناسه گفتگوی خود قرار دهید تا هر گفتگو، هر چند فراخوان و ردیابی که گرفته باشد، یک گفتگوی واحد دیده شود. با OpenLLMetry، آن را یک بار در هر درخواست به‌صورت ویژگی وابسته تنظیم کنید:

```python
from traceloop.sdk import Traceloop

Traceloop.set_association_properties({
    "session_id": chat.id,
    "user_email": user.email,
})
```

فراخوان‌های بدون شناسه گفتگو همچنان دیده می‌شوند، هر بار یک درخواست (یک ردیابی).

## گام ۴ — بگویید چه کسی پرسید

`user.id` یا `user.email` را تنظیم کنید — ویژگی وابسته بالا ایمیل را تنظیم می‌کند — تا ببینید هر گفتگو با چه کسی بوده، فهرست را بر پایه شخص جستجو کنید، و در زبانه Usage خرج را بر پایه کارمند رتبه‌بندی کنید. [انتساب کارمند و تیم](#انتساب-کارمند-و-تیم) همه کلیدهایی را که OneUptime می‌خواند فهرست می‌کند.

## گام ۵ — پاسخ‌های بد را علامت بزنید

‏OneUptime هر پاسخ را به محض رسیدن بررسی می‌کند و آنچه را در آن اشتباه پیش رفته علامت می‌زند:

| مشکل    | معنای آن                                                  | از کجا پیدا می‌شود                                                                                                                                            |
| ------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Failed  | فراخوان با خطا پایان یافت و پاسخی نرسید                   | وضعیت Error اسپن، `error.type`، یا دلیل پایان `error`                                                                                                         |
| Refused | هوش مصنوعی خودداری کرد، یا فیلتر ایمنی پاسخ را مسدود کرد | دلیل پایان امتناع یا ایمنی (`content_filter`، `refusal`، `SAFETY` و مانند آن)، امتناع درون پاسخ، یا پاسخی که با جمله امتناع رایج انگلیسی آغاز شود |
| Cut off | پاسخ در سقف توکن متوقف شد                                 | دلیل پایان `length`، `max_tokens` یا `MAX_TOKENS`                                                                                                             |
| Empty   | هوش مصنوعی بدون متن و بدون فراخوانی ابزار پاسخ داد        | محتوای ثبت‌شده‌ای که چیزی در خود ندارد، یا ۰ توکن خروجی                                                                                                       |
| Flagged | ارزیابی‌ای که برنامه‌تان فرستاد پاسخ را بد دانست          | رخداد `gen_ai.evaluation.result`                                                                                                                              |

چهار مورد نخست چیزی از شما نمی‌خواهند. برای علامت زدن بقیه — پاسخی که گاردریل، eval یا داور LLM خودتان آن را رد می‌کند — رخداد `gen_ai.evaluation.result` را با مقدار `fail` برای `gen_ai.evaluation.score.label` به اسپن آن پاسخ بیفزایید:

```python
from opentelemetry import trace

trace.get_current_span().add_event(
    "gen_ai.evaluation.result",
    {
        "gen_ai.evaluation.name": "relevance",
        "gen_ai.evaluation.score.label": "fail",
        "gen_ai.evaluation.explanation": "The answer is about another product.",
    },
)
```

برچسب‌هایی مانند `incorrect`، `wrong`، `unhelpful`، `toxic`، `unsafe` و `hallucination` هم ناموفق به شمار می‌آیند. رخداد باید روی اسپن همان پاسخی باشد که داوری می‌کند، تا وقتی آن اسپن باز است.

‏OneUptime هرگز گفتگوهای شما را برای داوری به هوش مصنوعی دیگری نمی‌فرستد: هر بررسی فقط آنچه را خود فراخوان حمل می‌کند می‌خواند.

## خواندن و بازپخش یک گفتگو

گفتگو کامل باز می‌شود، همان‌گونه که برنامه گفتگو تاریخچه‌اش را نشان می‌دهد: آنچه شخص گفت در یک سو، پاسخ‌های هوش مصنوعی در سوی دیگر همراه با مدل، زمان، توکن‌ها و هزینه‌شان، فراخوانی‌های ابزار میان آن‌ها، و آنچه اشتباه پیش رفت در همان جایی که رخ داد علامت‌خورده. **Details** زیر هر پاسخ دلیل پایان و ارزیابی‌هایش را نشان می‌دهد، همراه با پیوندی به آن فراخوان در Traces.

نوار پایین صفحه گفتگو را همان‌گونه که شخص آن را زیست، بازپخش می‌کند:

- **Replay** آن را از نخستین پیام با همان آهنگی که رخ داد پخش می‌کند، و تا وقتی پاسخی در راه است «AI is answering…» شمارش می‌کند. روی زمان هر پیام بزنید تا از همان‌جا بازپخش شود.
- **Skip waiting** که به‌طور پیش‌فرض روشن است، سکوت‌های بیش از ۳ ثانیه را کوتاه می‌کند. دکمه سرعت با 1×، 2×، 4× یا 8× پخش می‌کند.
- **K** پخش یا مکث می‌کند، **J** یا **←** یک پیام عقب می‌رود، و **L** یا **→** یک پیام جلو می‌رود.
- نشانی صفحه پیامی را که بازپخش در آن ایستاد نگه می‌دارد (`?step=`)، پس پیوند در همان لحظه باز می‌شود.

## وقتی هوش مصنوعی بد پاسخ می‌دهد باخبر شوید

زبانه **Alerts** هشدارهایی را پیشنهاد می‌کند که بیشتر برنامه‌های هوش مصنوعی می‌خواهند. انتخاب یکی، Create Monitor را پرشده باز می‌کند، و پیش از ذخیره می‌توانید هر چیزی را تغییر دهید:

| هشدار                    | چه وقت خبرتان می‌کند                                                                     |
| ------------------------ | ---------------------------------------------------------------------------------------- |
| Answers go wrong         | بیش از ۵٪ پاسخ‌ها در ۱۵ دقیقه ناموفق، رد شده، نیمه‌کاره، خالی یا علامت‌خورده باشند       |
| AI calls fail            | بیش از ۱۰٪ فراخوانی‌های مدل در ۵ دقیقه با خطا پایان یابند                               |
| The AI refuses to answer | بیش از ۵٪ پاسخ‌ها در ۳۰ دقیقه امتناع باشند                                              |
| Answers are cut off      | ۳ پاسخ یا بیشتر در ۳۰ دقیقه در سقف توکن متوقف شوند                                      |
| Answers are flagged      | ارزیابی‌ای پاسخی را بد علامت بزند                                                        |
| Answers are slow         | بیش از ۱۰٪ پاسخ‌ها در ۱۵ دقیقه بیش از ۳۰ ثانیه طول بکشند                                |
| The AI stops answering   | هوش مصنوعی ۳۰ دقیقه هیچ پاسخی ندهد                                                      |

هشدارهای مبتنی بر سهم، دست‌کم ۳ پاسخ بد را هم منتظر می‌مانند، تا یک پاسخ بد از دو پاسخ کسی را بیدار نکند.

هر هشدار یک **مانیتور AI / LLM** است. تنظیماتش می‌گوید چه چیزی پاسخ بد به شمار می‌آید — مشکلات بالا، پاسخی کندتر از سقفی که تعیین می‌کنید، یا هر دو — کدام برنامه‌ها و کدام مدل را می‌پاید، و هر بررسی تا کجا به عقب نگاه می‌کند. زیر آن‌ها، پیش‌نمایشی نشان می‌دهد مانیتور همین حالا چه چیزی را می‌شمارد. معیارهایش سه عدد را مقایسه می‌کنند: **سهم پاسخ‌های بد** (به درصد)، **شمار پاسخ‌های بد** و **شمار پاسخ‌ها**. هشدار آماده، هشداری می‌سازد که خودش برطرف می‌شود و تا وقتی پاسخ‌ها بدند مانیتور را Degraded نشان می‌دهد؛ برای بیدار کردن کسی، رخداد آن را روشن کنید.

خرج را [بودجه‌های هزینه روزانه](#بودجههای-هزینه-روزانه) می‌پایند.

## ویژگی‌هایی که OneUptime می‌شناسد

‏OneUptime نخست قراردادهای GenAI در OpenTelemetry را می‌خواند، و برای اینکه کتابخانه‌های محبوب بی‌دردسر کار کنند به گونه‌های OpenLLMetry و OpenInference بازمی‌گردد.

| چه چیزی                      | ویژگی اصلی                   | نیز پذیرفته می‌شود                                                                                                                                                                                                                                                 |
| ---------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ارائه‌دهنده / سامانه          | `gen_ai.provider.name`       | `gen_ai.system` (در قراردادها منسوخ شده، هنوز به‌فراوانی منتشر می‌شود)، `llm.system`، `llm.provider`                                                                                                                                                              |
| عملیات                       | `gen_ai.operation.name`      | `llm.request.type`، `openinference.span.kind`                                                                                                                                                                                                                      |
| مدل درخواستی                 | `gen_ai.request.model`       | `llm.model_name`، `llm.request.model`                                                                                                                                                                                                                              |
| مدل پاسخ                     | `gen_ai.response.model`      | `llm.response.model`                                                                                                                                                                                                                                               |
| توکن‌های ورودی                | `gen_ai.usage.input_tokens`  | `gen_ai.usage.prompt_tokens`، `llm.token_count.prompt`، `llm.usage.prompt_tokens`                                                                                                                                                                                  |
| توکن‌های خروجی                | `gen_ai.usage.output_tokens` | `gen_ai.usage.completion_tokens`، `llm.token_count.completion`، `llm.usage.completion_tokens`                                                                                                                                                                      |
| کل توکن‌ها                    | `gen_ai.usage.total_tokens`  | `llm.token_count.total`، `llm.usage.total_tokens`؛ وقتی هیچ‌کدام گزارش نشود از ورودی + خروجی به دست می‌آید                                                                                                                                                       |
| هزینه (USD)                  | `gen_ai.usage.cost`          | `gen_ai.usage.cost_usd`، `gen_ai.usage.total_cost`، `llm.usage.total_cost`، `gen_ai.cost.total_cost` (LiteLLM)، `litellm.cost.total`                                                                                                                               |
| نام عامل                     | `gen_ai.agent.name`          | `agent.name`                                                                                                                                                                                                                                                       |
| نام ابزار                    | `gen_ai.tool.name`           | `tool.name`                                                                                                                                                                                                                                                        |
| شناسه گفتگو / نشست           | `gen_ai.conversation.id`     | `session.id`، `langfuse.session.id`، `traceloop.association.properties.session_id`                                                                                                                                                                                 |
| کارمند (اجراکننده فراخوان)    | `user.id`                    | `enduser.id`، `litellm.metadata.user_api_key_user_id` و `metadata.user_api_key_user_id` (املاهای v2 و v1 در OTel لیت‌ال‌ال‌ام — هر دو خوانده می‌شوند)، `traceloop.association.properties.user_id`، `langfuse.user.id`، `user.account_uuid`، `user.account_id`، `cursor.user.id` |
| ایمیل کارمند                 | `user.email`                 | `traceloop.association.properties.user_email`، `enduser.email`                                                                                                                                                                                                     |
| تیم / مرکز هزینه             | `team.id`                    | `team`، `cost_center`، `department`، `litellm.metadata.user_api_key_team_id` و `litellm.team.id` (LiteLLM OTel v2)، `metadata.user_api_key_team_id` (LiteLLM OTel v1)، `cursor.team.id`                                                                             |

زیرکلیدهای `traceloop.association.properties.*` را **فراخواننده فراهم می‌کند**: Traceloop پیشوند را تعریف می‌کند و کد شما آنچه زیرش می‌رود را فراهم می‌کند. `gen_ai.usage.total_tokens` و `gen_ai.usage.cost` کلیدهایی **عملاً رایج**اند، نه قراردادهای معنایی GenAI — قراردادها هیچ ویژگی‌ای برای کل توکن و هیچ ویژگی هزینه‌ای تعریف نمی‌کنند — و OneUptime آن‌ها را می‌خواند چون ابزارگذاری‌های رایج منتشرشان می‌کنند. `gen_ai.system` پیشینِ منسوخ‌شده خودِ قراردادها برای `gen_ai.provider.name` است؛ هر دو خوانده می‌شوند.

**سه سطر هویت با پیشوند `resource.` هم تطبیق داده می‌شوند.** دریافت OTLP هر ویژگی _منبع_ را با پیشوند `resource.` در نگاشت ویژگی‌های اسپن مسطح می‌کند، پس `OTEL_RESOURCE_ATTRIBUTES=team.id=platform` به‌صورت `resource.team.id` می‌رسد. ‏OneUptime نخست کل فهرست برهنه و سپس کل فهرست `resource.` را می‌جوید، پس ویژگی اسپن (که یک فراخوان را توصیف می‌کند) بر ویژگی منبع (که کل فرایند را توصیف می‌کند) می‌چربد. باقی سطرها فقط بر کلید برهنه تطبیق می‌شوند: آن‌ها مقادیری به ازای هر فراخوان‌اند.

**محتوای اعلان و تکمیل** از رخداد `gen_ai.client.inference.operation.details` خوانده می‌شود؛ از ویژگی‌های اسپن `gen_ai.input.messages`، `gen_ai.output.messages` و `gen_ai.system_instructions`؛ از رخدادهای **منسوخ‌شده** به ازای هر نقش که ابزارگذاری‌های قدیمی‌تر هنوز منتشرشان می‌کنند (`gen_ai.system.message`، `gen_ai.user.message`، `gen_ai.tool.message`، `gen_ai.assistant.message`، `gen_ai.choice`)؛ از ویژگی‌های نمایه‌دار (`gen_ai.prompt.N.content` و `gen_ai.completion.N.content`، و `llm.input_messages.N.message.content` و `llm.output_messages.N.message.content` در OpenInference)؛ و از آرایه‌های پیام JSON (`gen_ai.prompt`، `gen_ai.completion`، `input.value`، `output.value`).

### هزینه چگونه محاسبه می‌شود

اگر ابزارگذاری شما هزینه‌ای گزارش کند (`gen_ai.usage.cost`)، OneUptime همان را عیناً به کار می‌برد: مقدار گزارش‌شده همیشه برنده است. وقتی هزینه‌ای گزارش نشود، OneUptime **هزینه‌ای برآوردی هنگام دریافت** را از روی شمار توکن‌های اسپن و فهرست‌بهای توکاری از مدل‌های رایج OpenAI، Anthropic، Google Gemini، Mistral، DeepSeek، xAI، Cohere، Amazon Nova و Meta Llama محاسبه می‌کند. مدل‌ها بر پایه پیشوند نام تطبیق داده می‌شوند، پس عکس‌های لحظه‌ای تاریخ‌دار مانند `gpt-4o-2024-08-06` و شناسه‌های آراسته با نام فروشنده مانند `us.anthropic.claude-3-5-sonnet-20241022-v2:0` درست تفکیک می‌شوند. مدل‌های ناشناخته یا سفارشی هرگز حدس زده نمی‌شوند — هزینه‌شان `0` می‌ماند تا وقتی در زبانه **Pricing** برایشان قیمتی تعیین کنید. برآوردها از قیمت‌های فهرست استفاده می‌کنند و تخفیف‌های حافظه نهان یا دسته‌ای را به حساب نمی‌آورند.

‏OneUptime را خودمیزبان می‌کنید؟ فهرست در `packages/Common/Types/Telemetry/LlmCostCatalog.ts` جای دارد.

## انتساب کارمند و تیم

«کدام‌یک از مهندسان ما ماه گذشته ۴ هزار دلار روی Opus خرج کرد» پرسشی درباره یک شخص است، و هیچ اسپن LLMای پاسخش نمی‌دهد مگر چیزی روی اسپن شخصی را نام ببرد. ‏OneUptime کنشگر انسانی را هنگام دریافت در ستون‌های قابل پرس‌وجو کپی می‌کند، پس به‌جای نوشتن جست‌وجوی ویژگی‌ها، روی یک ستون گروه‌بندی و پالایش می‌کنید.

سه سطر هویت در جدول بالا کل سازوکارند؛ نخستین کلید موجود، به ترتیب فهرست، برنده است. `user.id` پیشتاز است چون کلید متعارف OpenTelemetry برای کنشگر انسانی است و همانی است که اگر خودتان هویت را تنظیم می‌کنید باید بر آن استاندارد شوید. **یک استثنا: Claude Code** مقدار `user.id` را به‌صورت شناسه‌ای ناشناس و تصادفی منتشر می‌کند که در `~/.claude.json` نگه داشته می‌شود، نه یک شخص. روی نقطه‌داده‌های سنجه‌اش، که فهرستشان ایمیل‌اول است، بی‌ضرر است، اما اگر بتای ردیابی‌های Claude Code را روشن کنید، آن `user.id` ناشناس روی اسپن‌ها بر `user.email` می‌چربد: برای آن ناوگان، `user.id` را در پردازشگر جمع‌کننده بیندازید یا بازنگاشتش کنید. `enduser.id` هنوز ویژگی‌ای فعال در قراردادهای معنایی است و به‌عنوان نام مستعاری هم‌ارز پذیرفته می‌شود. `cursor.user.id` آخر می‌آید چون عددی صحیح، مبهم و در دامنه تیم است که برای رسیدن به یک شخص به API مدیریتی Cursor نیاز دارد.

هویت فقط روی اسپن‌هایی خوانده می‌شود که از پیش به‌عنوان فراخوان LLM شناخته شده‌اند: `user.id`، `user.email` و `team.id` کلیدهای عمومی‌ای هستند که اسپن‌های مرورگر و پشتی معمولی هم حملشان می‌کنند. **نقطه‌داده‌های سنجه** فهرستی کوتاه‌تر و ایمیل‌اول حمل می‌کنند — `user.email`، `user.id`، `user.account_uuid`، `user.account_id`، `cursor.user.id`، با تیم‌ها از `team.id`، `team`، `cost_center`، `department` و `cursor.team.id`، هرکدام با پیشوند `resource.` هم تطبیق می‌شوند — چون CLIهای عامل کدنویسی که سنجه بدون اسپن منتشر می‌کنند، `user.email` را بومی منتشر می‌کنند. امروز هیچ‌چیزی هویت را از **رکوردهای گزارش** نمی‌خواند.

### تنظیم تیم و مرکز هزینه

هیچ ابزارگذاری‌ای `team.id`، `team`، `cost_center` یا `department` را منتشر نمی‌کند: سازمان شما آن‌ها را تنظیم می‌کند، به‌طور مرسوم از راه `OTEL_RESOURCE_ATTRIBUTES` روی فرایند:

```bash
export OTEL_RESOURCE_ATTRIBUTES="team.id=platform,team=Platform_Engineering,cost_center=eng-123,department=engineering"
```

آن‌ها به‌صورت `resource.team.id`، `resource.team`، `resource.cost_center` و `resource.department` به OneUptime می‌رسند، و هر دو لایه هم روی اسپن‌ها و هم روی نقطه‌داده‌های سنجه شناخته می‌شوند، چه صادرکننده‌تان کلیدها را در بلوک منبع OTLP رها کند و چه روی هر اسپن کپی‌شان کند (‏Claude Code دومی را می‌کند). `team.id` برهنه‌ای که مستقیم روی اسپن تنظیم شده باشد همچنان برنده است.

املاهای دروازه بدون هیچ پیکربندی‌ای از سوی شما می‌رسند. ‏LiteLLM ویژگی‌هایش را در دو حالت OpenTelemetry خود جور دیگری نام می‌دهد — فراخوان‌برگشتی پیش‌فرض `otel` نسخه v1 از پیشوند برهنه `metadata.` استفاده می‌کند (`metadata.user_api_key_user_id`، `metadata.user_api_key_user_email`، `metadata.user_api_key_team_id`) و حالت انتخابی v2 (`LITELLM_OTEL_V2=true`) از فضای‌نام `litellm.` — و **OneUptime هر دو را می‌خواند**.

### کلیدهای مشتری عمداً کنار گذاشته شده‌اند

اسپن LLM می‌تواند **دو** شخص متفاوت را حمل کند: کارمندی که فراخوان را زده، و **مشتری** پایین‌دستی‌ای که فراخوان برای او زده شده است. این کلیدها مشتری را حمل می‌کنند، و OneUptime عمداً **هیچ‌کدامشان** را در ستون هویت نمی‌خواند:

- `gen_ai.user` و `llm.user` — همان‌گونه که ابزارگذاری‌ها پارامتر درخواست `user` در OpenAI را بازتاب می‌دهند، که OpenAI آن را «شناسه‌ای پایدار برای کاربران نهایی شما» مستند کرده است (اکنون به سود `safety_identifier` و `prompt_cache_key` منسوخ شده).
- `litellm.metadata.user_api_key_end_user_id`، `metadata.user_api_key_end_user_id` و `litellm.end_user.id` — شناسه صریح کاربر نهایی در LiteLLM در هر سه املایش، متمایز از شناسه صاحب کلید که **همان** کارمند است و **خوانده می‌شود**.

دلیلش درستی بازپرداخت هزینه است: شناسه مشتری را در ستون کارمند بخوانید و رباتی پشتیبان که به ۴۰٬۰۰۰ مشتری خدمت می‌دهد، ۴۰٬۰۰۰ «کارمند» خیالی می‌سازد، در حالی که مهندسی که صاحب آن خرج است چنین می‌نماید که هیچ خرج نکرده. این ویژگی‌ها در نگاشت ویژگی‌های خام می‌مانند و می‌توانید مستقیم پرس‌وجویشان کنید.

### ستون‌های هویت پاک‌سازی می‌شوند

ستون ایمیل کارمند داده شخصی واقعی نگه می‌دارد. **قواعد پاک‌سازی** تله‌متری شما زیر دامنه **Attributes** آن را دقیقاً مانند ویژگی‌ای که از آن خوانده شده پوشش می‌دهند، پس قاعده‌ای برای زدودن ایمیل روی ستون هم اعمال می‌شود. قواعد پاک‌سازی و پالایه‌های حذف را زیر **Traces → Settings** پیکربندی کنید.

## اسپن‌ها و سنجه‌ها جایگزین‌اند، نه جمع

**اسپن‌های GenAI مرجع‌اند. جریان سنجه فقط وقتی خوانده می‌شود که جریان اسپن چیزی گزارش نکرده باشد، و این دو هرگز با هم جمع نمی‌شوند.** اسپن مدل، توکن‌ها و هزینه را در یک سطر حمل می‌کند، پس هرجا اسپن باشد به هر پرسشی پاسخ می‌دهد. هرجا نباشد — CLIهای عامل کدنویسی _سنجه_‌های توکن و هزینه منتشر می‌کنند و هیچ اسپن GenAIای ندارند — جریان سنجه جایش را می‌گیرد. جمعشان نمی‌کنیم چون بسیاری از ابزارگذاری‌ها هر دو سیگنال را برای یک فراخوان منتشر می‌کنند (‏OpenLLMetry نمونه رایج است)، و جمع کردنشان هر دلار را دو بار می‌شمرد.

پیامدی که باید برایش برنامه بریزید: **وقتی اسپن‌های GenAI شما رقمی غیرصفر گزارش کنند، سهم یک منبع فقط-سنجه در آن رقم پدیدار نمی‌شود.** جایگزینی به ازای هر رقم و هر تفکیک است، نه به ازای هر منتشرکننده:

| کجا                                     | چه چیزی به سنجه‌ها بازمی‌گردد                       | چه وقت                                  |
| --------------------------------------- | --------------------------------------------------- | --------------------------------------- |
| Usage → Input / Output tokens           | مجموع توکن‌های ورودی و خروجی                         | هر دو مجموع توکن اسپن ۰ باشند           |
| Usage → Cost (USD)                      | هزینه، به دلار و میکرودلار، مقیاس‌شده و جمع‌شده      | مجموع هزینه اسپن ۰ باشد                 |
| Usage → LLM calls                       | هیچ — فقط اسپن                                      | —                                       |
| Usage → Employee, Team, Model           | فقط هزینه. ستون‌های فراخوان و توکن `—` نمایش می‌دهند | آن تفکیک هیچ سطر اسپنی برنگرداند       |
| Usage → Provider, Application / Service | هیچ — فقط اسپن                                      | —                                       |
| Conversations                           | هیچ — گفتگوها از اسپن‌ها ساخته می‌شوند              | —                                       |

‏Provider و Application / Service جایگزین سنجه ندارند چون شمارنده‌های عامل کدنویسی هیچ ویژگی ارائه‌دهنده GenAI ندارند و به هیچ سرویس تله‌متری OneUptime پیوسته نیستند. هرجا رقمی از سنجه‌ها آمده باشد، صفحه آن را **from GenAI metrics** برچسب می‌زند، چون رقمی که از سنجه آمده هیچ سطر متناظری در فهرست Calls ندارد.

**اگر می‌خواهید خرج ابزاری فقط-سنجه جداگانه دیده شود، پروژه خودش را به آن بدهید**، تا جریان اسپنش واقعاً خالی باشد و جایگزینی به کار بیفتد. همین درباره بودجه‌ها هم صدق می‌کند: به‌جای آمیختن سرویس‌های اسپن‌دار و فقط-سنجه، برای هر سرویس یک بودجه تعیین کنید.

## داشبوردها و هشدارهای سنجه

سنجه‌های GenAI به‌صورت سنجه‌های معمولی OpenTelemetry می‌رسند، پس می‌توانید **داشبوردهایی** بسازید که `gen_ai.client.token.usage`، `gen_ai.client.operation.duration` و بقیه را نمودار کنند، و **مانیتورهای سنجه** بر آن‌ها بسازید — برای نمونه وقتی صدک ۹۵ `gen_ai.client.operation.duration` از آستانه‌ای بگذرد، گروه‌بندی‌شده بر پایه مدل. [مانیتور سنجه‌ها](/docs/monitor/metrics-monitor) را ببینید.

## بودجه‌های هزینه روزانه

زبانه **Budgets** سقف‌های روزانه به دلار تعیین می‌کند که بر پایه روز UTC ارزیابی می‌شوند. هر ۱۵ دقیقه یک کارگر پس‌زمینه هزینه اسپن‌های LLM آن روز را (گزارش‌شده یا محاسبه‌شده) جمع می‌زند، آن را روی بودجه ثبت می‌کند، و دو سنجه gauge منتشر می‌کند:

| سنجه                                | معنا                                  |
| ----------------------------------- | ------------------------------------- |
| `oneuptime.llm.budget.spend.usd`    | خرج امروز تا این لحظه، به دلار        |
| `oneuptime.llm.budget.percent.used` | خرج به‌صورت درصدی از سقف روزانه       |

هر دو ویژگی‌های `oneuptime.llm.budget.id` و `oneuptime.llm.budget.name` را حمل می‌کنند، به‌علاوه دامنه سرویس، ارائه‌دهنده و مدل بودجه وقتی تنظیم شده باشد. مانیتورها را بر پایه **`oneuptime.llm.budget.id`** بپالایید که پایدار است؛ نام با تغییر نام بودجه عوض می‌شود.

**هشدار دادن یک [مانیتور سنجه‌ها](/docs/monitor/metrics-monitor) روی آن سنجه‌هاست.** برای الگوی رایج ۸۰٪ / ۱۰۰٪، مانیتوری روی `oneuptime.llm.budget.percent.used` بسازید، آن را بر پایه `oneuptime.llm.budget.id` بپالایید، و دو معیار بیفزایید: `>= 80` که هشداری در سطح هشدار می‌سازد و `>= 100` که هشداری بحرانی می‌سازد. **زمان غلتان مانیتور را ۳۰ دقیقه بگذارید**: بودجه هر ۱۵ دقیقه یک نقطه منتشر می‌کند، پس پنجره پیش‌فرض ۱ دقیقه‌ای میان دو جاروب سری خالی‌ای می‌یافت.

بودجه‌ها را می‌توان به یک سرویس تله‌متری، یک ارائه‌دهنده LLM یا یک مدل دقیق محدود کرد، یا در کل پروژه گذاشت، و چندین بودجه می‌توانند کنار هم باشند. مانیتور بودجه همچنین می‌تواند جریان‌کاری‌ای را فراخواند که عاملی سرکش را متوقف کند — [قطع مدار عامل‌های هوش مصنوعی سرکش](/docs/telemetry/ai-agent-circuit-breaker) را ببینید.

## حریم خصوصی و پاک‌سازی

اعلان‌ها و تکمیل‌ها ممکن است داده حساس داشته باشند. ‏OneUptime **قواعد پاک‌سازی** و **پالایه‌های حذف** تله‌متری شما را مانند هر ردیابی دیگری بر اسپن‌های LLM اعمال می‌کند، پس می‌توانید ویژگی‌ها را بپوشانید یا اسپن‌ها را پیش از ذخیره شدن بیندازید؛ آن‌ها را زیر **Traces → Settings** پیکربندی کنید. ستون ایمیل کارمند مشمول همان قواعد است — [ستون‌های هویت پاک‌سازی می‌شوند](#ستونهای-هویت-پاکسازی-میشوند) را ببینید.

گفتگوها با همان مجوز ردیابی‌ها خوانده می‌شوند: هر کس بتواند ردیابی‌های پروژه را بخواند می‌تواند گفتگوهایش را بخواند، و هیچ کس دیگری نه.
