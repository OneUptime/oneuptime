# وارد کردن منابع

اگر از پیش OneUptime را اجرا می‌کنید — مانیتورهایی ساخته‌شده در داشبورد، صفحه‌های وضعیتی که دستی پیکربندی شده‌اند — برای پذیرفتن Terraform لازم نیست چیزی را از نو بسازید. وارد کردن، منابع موجود را بدون دست زدن به آن‌ها زیر مدیریت Terraform می‌آورد.

وارد کردن برای **هر نوع منبع OneUptime که نقطه پایانی خواندن دارد** کار می‌کند، که همه نوع‌های پرکاربرد را دربر می‌گیرد (`oneuptime_monitor`، `oneuptime_status_page`، `oneuptime_label`، `oneuptime_team`، `oneuptime_on_call_policy`، ...). منبعی بدون نقطه پایانی خواندن، وارد کردن را با خطایی صریح که همین را می‌گوید شکست می‌دهد.

## یافتن شناسه یک منبع

شناسه وارد کردن، ObjectID منبع است — رشته‌ای هگز با ۲۴ نویسه. دو جا برای یافتنش:

- **نشانی داشبورد.** منبع را باز کنید؛ شناسه آخرین بخش مسیر است، برای نمونه `https://oneuptime.com/dashboard/<project-id>/monitors/68a1b2c3d4e5f6a7b8c9d0e1` → شناسه مانیتور `68a1b2c3d4e5f6a7b8c9d0e1` است.
- **API.** منابع را با کلید API پروژه‌تان فهرست کنید؛ هر آیتمی `_id` حمل می‌کند.

## وارد کردن با بلوک import ‏(Terraform 1.5 به بالا، توصیه‌شده)

بلوک‌های import اعلانی، در یک plan قابل بازبینی، و تکرارپذیرند. نخست بلوک `resource` را بنویسید (می‌تواند کمینه آغاز شود)، سپس بلوک `import` را:

```hcl
resource "oneuptime_monitor" "homepage" {
  name         = "Homepage"
  description  = "Checks that the homepage responds"
  monitor_type = "Website"
}

import {
  to = oneuptime_monitor.homepage
  id = "68a1b2c3d4e5f6a7b8c9d0e1"
}
```

سپس:

```bash
terraform plan
```

طرح `oneuptime_monitor.homepage will be imported` را به‌علاوه هر تغییر ویژگی‌ای که پیکربندی شما روی منبع واقعی می‌کرد نشان می‌دهد. **تا وقتی طرح، وارد کردن بدون تغییر را نشان دهد تطبیق دهید** — مقادیر واقعی (نام، توضیحات، نوع، برچسب‌ها) را در پیکربندی‌تان کپی کنید به‌جای اینکه بگذارید Terraform منبع زنده را «تصحیح» کند. سپس:

```bash
terraform apply
```

پس از apply موفق می‌توانید بلوک `import` را حذف کنید؛ دیگر اثری ندارد.

### تولید خودکار پیکربندی

‏Terraform می‌تواند بلوک منبع را برایتان پیش‌نویس کند:

```bash
terraform plan -generate-config-out=generated.tf
```

فقط بلوک `import` را بنویسید (بدون بلوک `resource`)، فرمان را اجرا کنید، سپس `generated.tf` را مرور کنید، ویژگی‌های محاسبه‌شده پرنویز را هرس کنید، و بلوک تمیزشده را به فایل‌های واقعی خود ببرید.

## وارد کردن با فرمان CLI

تک‌خطی کلاسیک، در همه نسخه‌های Terraform در دسترس. بلوک `resource` باید از پیش در پیکربندی وجود داشته باشد:

```bash
terraform import oneuptime_monitor.homepage 68a1b2c3d4e5f6a7b8c9d0e1
```

همین الگو برای هر نوع منبعی کار می‌کند:

```bash
terraform import oneuptime_status_page.public 68a1b2c3d4e5f6a7b8c9d0e2
terraform import oneuptime_label.critical 68a1b2c3d4e5f6a7b8c9d0e3
terraform import oneuptime_team.sre 68a1b2c3d4e5f6a7b8c9d0e4
```

پس از هر وارد کردن، `terraform plan` را اجرا کنید و پیکربندی را تا تمیز شدن طرح تطبیق دهید.

## وارد کردن یک پروژه کامل

برای پذیرفتن همه‌چیز در پروژه‌ای موجود:

1. **موجودی‌برداری.** هر نوع منبع را از راه داشبورد یا API فهرست کنید و نام‌ها و شناسه‌ها را ثبت کنید. با بلوک‌های سازنده آغاز کنید (برچسب‌ها، تیم‌ها، وضعیت‌های مانیتور، شدت‌ها/وضعیت‌های حادثه)، سپس منابعی که به آن‌ها ارجاع می‌دهند (مانیتورها، صفحه‌های وضعیت، سیاست‌های کشیک)، سپس منابع پیونددهنده (دامنه‌های صفحه وضعیت، قواعد تشدید، اعضای تیم).
2. **بلوک‌های import را انبوه بنویسید.** به ازای هر منبع یک `import {}`. Terraform هر تعداد از آن‌ها را در یک plan پردازش می‌کند:

```hcl
import {
  to = oneuptime_label.critical
  id = "68a1b2c3d4e5f6a7b8c9d0e3"
}

import {
  to = oneuptime_monitor.homepage
  id = "68a1b2c3d4e5f6a7b8c9d0e1"
}

import {
  to = oneuptime_monitor.checkout_api
  id = "68a1b2c3d4e5f6a7b8c9d0e5"
}
```

3. **تولید + تطبیق.** برای نخستین پیش‌نویس از `-generate-config-out` استفاده کنید، ارجاع‌های متقابل سخت‌کدشده را با ارجاع منبع جایگزین کنید (`labels = [oneuptime_label.critical.id]` به‌جای شناسه خام) تا گراف وابستگی واقعی باشد.
4. **تأیید.** پیش از آنکه پروژه را واردشده بدانید، `terraform plan` باید به `No changes.` ختم شود.

## هشدارها

- **وارد کردن پیکربندی نمی‌نویسد** (مگر از `-generate-config-out` استفاده کنید). فقط وضعیت می‌سازد. پیکربندی وظیفه شماست، و تا وقتی با واقعیت نخواند، `plan` تغییر پیشنهاد می‌دهد.
- **منبعی بدون نقطه پایانی خواندن قابل وارد کردن نیست** — ارائه‌دهنده خطایی صریح با نام نوع منبع برمی‌گرداند. چنین منابعی را فقط به‌عنوان ساخت تازه مدیریت کنید.
- **مقادیر حساس تولیدشده توسط کارساز** (برای نمونه کلید یک پروب یا راز مانیتور درخواست ورودی) هنگام وارد کردن به وضعیت خوانده می‌شوند. متناسب از وضعیتتان محافظت کنید.
- **منبعی را به دو ریشه Terraform وارد نکنید.** دو وضعیت که هر دو باور دارند مالک یک مانیتورند در هر apply با هم می‌جنگند.
- **دامنه کلید API اعمال می‌شود.** وارد کردن از راه همان کلید API پروژه می‌خواند — کلید به دسترسی خواندن روی نوع منبعی که وارد می‌شود نیاز دارد (و Update/Delete برای مدیریت بعدی).
- **`terraform destroy` منابع واردشده را واقعاً حذف می‌کند.** پس از وارد کردن، مانند هر چیزی که Terraform ساخته مدیریت می‌شوند.
