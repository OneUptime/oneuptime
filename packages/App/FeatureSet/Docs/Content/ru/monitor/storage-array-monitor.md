# Мониторинг систем хранения данных

Монитор системы хранения следит за одним массивом хранения и сообщает, когда массив сам поднимает оповещение, у него заканчивается место, он замедляется, теряет оборудование или путь к хосту либо отстаёт с репликацией. Он работает с Pure Storage FlashArray, Pure Storage FlashBlade и NetApp ONTAP (включая Amazon FSx for NetApp ONTAP) и читает метрики, которые собирает OneUptime Storage Array Agent: серии Pure `purefa_*` и `purefb_*`, а также серии `netapp_*`, которые NetApp Harvest читает из кластера ONTAP.

Он также работает с Dell PowerStore (`dell.powerstore`), по сериям Dell `powerstore_*`.

:::cards
- [Создайте монитор](#создание-монитора-системы-хранения): Шесть шагов в панели управления.
- [Шаблоны](#готовые-шаблоны-оповещений): Готовые оповещения, по инциденту на том, хост, специализированное устройство или компонент.
- [Как устроены серии Pure](#как-устроены-серии-pure): Одно имя метрики, много показателей. У серий ONTAP [есть собственный раздел](#как-устроены-серии-ontap).
- [Метрики](#собираемые-метрики): Все серии, по которым монитор может создавать оповещения.
:::

## Как это работает

OneUptime Storage Array Agent работает на машине, которая может достучаться до интерфейса управления массива. Он читает метрики массива с помощью API-токена только для чтения, помечает их именем массива, `storage.array.name`, и его платформой, `storage.system`, и отправляет их в OneUptime по OTLP. Первые данные регистрируют массив.

Для Dell PowerMax агент не нужен: зонд OneUptime каждые 5 минут входит в Unisphere for PowerMax с учётной записью только для чтения и так же отправляет каждый массив, которым тот управляет, под именем его Symmetrix ID, пока вы его не переименуете ([Dell PowerMax](/docs/telemetry/storage-arrays#dell-powermax)).

Монитор системы хранения привязан к одному массиву. Каждую минуту он выполняет свой запрос по метрикам этого массива и сравнивает результат со своими критериями.

```mermaid title="От системы хранения к инциденту"

    subgraph site["Ваша сеть"]
        direction LR
        array["FlashArray или FlashBlade"] --> agent["OneUptime Storage<br/>Array Agent"]
    end
    agent -->|"метрики purefa и purefb<br/>по OTLP"| oneuptime["OneUptime"]
    oneuptime -->|"первые данные"| registered["Массив<br/>зарегистрирован"]
    oneuptime --> monitor["Монитор системы<br/>хранения"]
    monitor -->|"каждую минуту"| criteria{"Критерии<br/>выполнены?"}
    criteria -->|"да"| incident["Инцидент или<br/>оповещение"]
    criteria -->|"нет"| online["Монитор в сети"]
```

## Перед началом работы

- **Установите Storage Array Agent** там, откуда он может достучаться до массива по HTTPS, с API-токеном пользователя, у которого есть роль массива **readonly**. [Руководство по Storage Array Agent](/docs/telemetry/storage-arrays) описывает пользователя, токен и установку через `ONEUPTIME_URL`, `ONEUPTIME_TELEMETRY_INGESTION_KEY`, `STORAGE_ARRAY_NAME` и адрес и токен массива (`PURE_FA_ENDPOINT` и `PURE_FA_API_TOKEN` или `PURE_FB_ENDPOINT` и `PURE_FB_API_TOKEN`), а для ONTAP — адрес кластера и REST-пользователя только для чтения (`NETAPP_ONTAP_ENDPOINT`, `NETAPP_ONTAP_USERNAME` и `NETAPP_ONTAP_PASSWORD`).
- **Убедитесь, что массив зарегистрирован.** Он появляется в разделе **Продукты → Инфраструктура → Системы хранения → Все системы хранения** под именем из `STORAGE_ARRAY_NAME` агента примерно через минуту после первого считывания.
- **Для Dell PowerMax** вместо этого подключите Unisphere for PowerMax, который им управляет, в разделе **Продукты → Инфраструктура → Системы хранения → Подключения**, как объясняется в [Dell PowerMax](/docs/telemetry/storage-arrays#dell-powermax).

## Создание монитора системы хранения

:::steps
### Создайте новый монитор

Перейдите в **Мониторы** и нажмите **Создать монитор**.

### Выберите «Система хранения»

В разделе **Тип монитора** нажмите **Другие типы мониторов** и выберите **Система хранения** в группе **Инфраструктура** или введите `storage` в поле поиска. Введите **Имя** — оно используется в заголовках инцидентов и оповещений — и нажмите **Далее**.

### Выберите массив

В разделе **Storage Array Monitor Configuration** выберите массив в поле **Система хранения**. В списке есть каждый массив, который отправлял данные. От его платформы зависит, какие метрики и шаблоны предлагает форма. После выбора строка под полем показывает, поступают ли данные. **Добавить систему хранения** открывает шаги настройки с уже подставленными ключами, которые ждут первых данных.

### Выберите, что отслеживать

Новый монитор начинается с **Array Stopped Reporting** в разделе **О чём оповещать**. Чтобы следить за другим:

- **Изменить** — выберите другой [шаблон](#готовые-шаблоны-оповещений). Он задаёт метрику, фильтры по меткам, агрегацию, диапазон времени и пороги и заменяет критерии ниже своими. **Диапазон времени** по-прежнему можно изменить.
- **Custom Metric** (в разделе **Дополнительные поля**) — выберите одну метрику в **Storage Array Metric**, затем задайте **Агрегация** и **Диапазон времени**. [Фильтры](#настройки-монитора) сужают её до одного тома, хоста, пода, компонента, файловой системы или бакета.
- **Расширенный** (в разделе **Дополнительные поля**) — стройте запросы и формулы сами в разделе **Выберите метрики**, например занятую ёмкость как `purefa_array_space_bytes` с фильтром `space=capacity` минус ту же метрику с фильтром `space=empty`. Используйте **Группировать по** по метке объекта, чтобы оценивать каждый объект отдельно.

### Проверьте критерии

Откройте каждый критерий в разделе **Критерии** и проверьте поля **Метрика**, **Агрегация**, **Условие** и **Порог**. Шаблон заполняет их сам. С **Custom Metric** или **Расширенный** монитор начинает с [критериев по умолчанию](#критерии-по-умолчанию), которые замечают только отсутствие данных от метрики, поэтому задайте свой порог.

### Создайте монитор

Нажмите **Создать монитор**. OneUptime открывает страницу монитора и оценивает его каждую минуту. Инциденты и оповещения, которые он поднимает, также видны на страницах массива **Инциденты** и **Оповещения**.
:::

> [!TIP]
> Чтобы настроить сразу несколько шаблонов, откройте массив из **Продукты → Инфраструктура → Системы хранения** и перейдите в **Рекомендации**. Выберите нужные шаблоны, укажите, кого вызывать, и OneUptime создаст по монитору на каждый шаблон.

## Настройки монитора

| Поле | Вкладка | Что делает |
| --- | --- | --- |
| **Система хранения** | Все | Обязательно. Ограничивает каждый запрос атрибутом `resource.storage.array.name`, поэтому два массива, у которых есть том с именем `vol-01`, никогда не смешиваются. |
| **Том** | Custom Metric, Расширенный | Один том: на FlashArray — по метке `name`, например `vol-db-01` (том в поде или группе томов называется `pod::volume` или `group/volume`); на ONTAP — по метке `volume`, которая может совпадать у двух SVM. |
| **Хост** | Custom Metric, Расширенный | Только FlashArray. Один хост, как его знает массив, по метке `host`, например `esxi-01`. |
| **Под** | Custom Metric, Расширенный | Только FlashArray. Один под ActiveCluster или ActiveDR по метке `name` или по `local_pod` в сериях связей реплик. |
| **Компонент оборудования** | Custom Metric, Расширенный | Один аппаратный компонент, например `CH0.BAY1` или `CT0`: метка `component_name` на FlashArray, `name` на FlashBlade, а на ONTAP — метка, которой его называет его серия (`node`, `disk`, `shelf` или `port`). |
| **Файловая система** | Custom Metric, Расширенный | Только FlashBlade. Одна файловая система по метке `name`. |
| **Бакет** | Custom Metric, Расширенный | Только FlashBlade. Один бакет объектного хранилища по метке `name`. |
| **Storage Array Metric** | Custom Metric | Одна метрика из [каталога](#собираемые-метрики). Форма добавляет фильтр по метке, который придаёт ей смысл, и группирует её по объекту, который она описывает, поэтому каждый том, хост или компонент оценивается отдельно. |
| **Агрегация** | Custom Metric | Как объединяются выборки: **Среднее**, **Максимум**, **Минимум**, **Сумма** или **Количество**. Начинается с обычной агрегации метрики. |
| **Диапазон времени** | Все | Скользящее окно, которое читает запрос, от **Past 1 Minute** до **Past 365 Days**. Новый монитор начинается с **Последние 5 минут**; пользовательская метрика файловой системы или бакета — с **Последние 15 минут**; шаблоны задают своё. |
| **Выберите метрики** | Расширенный | Конструктор запросов: **Метрика**, **Агрегировать по**, **Фильтровать по атрибутам**, **Группировать по**, а также **Добавить метрику** и **Добавить формулу** для объединения запросов. |

Агент читает конечную точку массива каждые 60 секунд, а тома, хосты и поды — каждые 2 минуты, поэтому в 5-минутном окне всегда есть выборка. Файловые системы и бакеты FlashBlade он читает каждые 5 минут, отсюда 15, а каталоги FlashArray — каждые 30 минут: дайте монитору каталогов окно в 60 минут. На ONTAP Harvest читает производительность кластера каждую минуту, а его конфигурацию, состояние и события EMS — каждые 3 минуты, поэтому в 5-минутном окне всегда есть выборка.

Он читает PowerStore каждые 5 минут, а состояние её кластера — каждые 60 секунд: дайте монитору PowerStore окно в 15 минут.

## Как устроены серии Pure

Pure помещает несколько показателей в **одно** имя метрики и различает их меткой:

- **`dimension`** в сериях производительности. `purefa_array_performance_latency_usec` несёт задержку чтения (`usec_per_read_op`), задержку записи (`usec_per_write_op`), задержку зеркалированной записи, а также время SAN, очереди, QoS и обслуживания для каждой из них. Всегда фильтруйте по одному `dimension`: среднее по ним смешивает задержку чтения 200 мкс с показателем очереди.
- **`space`** в сериях ёмкости: `capacity`, `empty`, `snapshots`, `total_provisioned`, `total_physical`, `available_ratio` и другие.

Некоторые серии несут своё состояние в **метке**, со значением, которое всегда равно 1:

| Серия | Метка состояния | Одна серия на |
| --- | --- | --- |
| `purefa_alerts_open` | `severity`, с `summary`, `code` и `component_type` | Открытое оповещение |
| `purefa_hw_component_status` | `component_status` | Аппаратный компонент |
| `purefa_host_connectivity_info` | `status`, с `details` | Хост |
| `purefa_drive_capacity_bytes` | `component_status` (значение — ёмкость диска) | Диск |

Серия, отфильтрованная до плохого состояния, существует, только пока что-то находится в этом состоянии, поэтому отсутствие серии означает, что всё в порядке. Поэтому **Max выше 0 срабатывает, а 0 восстанавливает** — правильная форма для таких серий, и так построены шаблоны: их критерии восстановления считают отсутствующую серию нулём. Когда серий совсем не остаётся, такой шаблон восстанавливается, только если `purefa_info`, `purefb_info` или `powermax_array_info` пришёл в том же окне, поэтому массив, переставший отправлять данные, ничего не закрывает.

Серии PowerMax содержат по одному значению и названы по нему: `powermax_array_response_time_usec` отличает чтения от записей с помощью `operation`. Его серии состояния так же существуют, только пока что-то не так: `powermax_alert_open` — пока в Unisphere открыто оповещение, `powermax_director_offline` — пока директор не в сети, `powermax_port_offline` — пока не работает порт, на который кто-то полагается, и `powermax_srdf_group_not_healthy` — пока группа SRDF приостановлена или не в сети.

В фильтрах монитора и ключах группировки атрибуты агента начинаются с `resource.` (`resource.storage.array.name`, `resource.storage.system`), а собственные метки Pure — нет (`name`, `host`, `component_name`, `dimension`, `space`, `severity`), как и метки PowerMax (`storage_group`, `volume`, `director`, `port_id`, `srdf_group`).

## Как устроены серии PowerStore

Экспортёр Dell пишет одно значение на имя метрики, поэтому серии PowerStore не нужен фильтр по меткам. Её метки называют объект: `appliance_id` — специализированное устройство, `name` — часть, том или файловую систему, а `volume_id`, `fc_port_id`, `eth_port_id`, `nas_id` или `volume_group_id` — объект серии производительности. Её серии состояния равны 1, пока всё исправно, и 0 в остальных случаях, поэтому шаблоны срабатывают ниже 1. Её собственные оповещения приходят по syslog, а их шаблоны, мониторы журналов, перечислены после её таблицы ниже.

## Как устроены серии ONTAP

NetApp Harvest называет каждую серию `netapp_<object>_<counter>`, а объект — его метками: том — `volume` в пределах своей `svm`, агрегат — `aggr`, LUN — `lun` в пределах своих `volume` и `svm`, узел — `node`, диск — `disk`, полку — `shelf`, связь SnapMirror — `destination_location`. Задержки — в микросекундах на операцию, `_ops` — операции в секунду, `_data` — байты в секунду.

Состояния ONTAP приходят тремя способами:

| Серия | Состояние | Одна серия на |
| --- | --- | --- |
| `netapp_*_new_status` | 1 — исправно, в сети, работает или запущено, иначе 0 | Объект, при каждом опросе |
| `netapp_health_*_alerts` | Значение 1, с `severity` (`error` или `warning`) и причиной в метках | Открытая проблема: вышедший из строя диск, неисправность полки, узел, который не может взять на себя работу партнёра, недоступный порт, оповещение о состоянии системы |
| `netapp_ems_events` | Значение 1, с `message`, `severity` и параметрами события | Событие EMS, для того единственного опроса, который его собрал; снятие парного события экспортируется ещё раз как 0 |

Состояние в виде числа срабатывает, когда каждое показание окна ниже 1, и восстанавливается, как только показание снова равно 1. Открытая проблема срабатывает, пока её серия есть, и восстанавливается, когда серия исчезает, — при условии, что `netapp_cluster_new_status` всё ещё поступает, поэтому остановленный агент ничего не закрывает. Событие EMS срабатывает по своему единственному показанию и остаётся открытым, пока оно в пределах часа шаблона; оно восстанавливается, когда проходит час без нового события.

## Готовые шаблоны оповещений

OneUptime поставляет 80 шаблонов — 12 для FlashArray, 8 для FlashBlade, 16 для PowerStore, 31 для ONTAP и 13 для PowerMax, — и список **О чём оповещать** предлагает те, что подходят для платформы массива. Каждый строит полный монитор: запрос метрики, её фильтры по меткам, группировку по собственной метке объекта, критерий, который срабатывает, и критерий, который восстанавливает. Пороги — это отправные точки, которые можно изменить.

Критерий срабатывает, только когда условие выполняется для **каждого** значения в его окне, кроме критериев шаблонов EMS для ONTAP: Harvest экспортирует событие для одного опроса, поэтому достаточно одного показания. Монитор, сработавший на пороге ёмкости, задержки, отставания или коэффициента, восстанавливается только на 10 % дальше этого порога, поэтому значение, колеблющееся у порога, не переключает состояние туда и обратно. Шаблоны оповещений, оборудования и подключений срабатывают, когда состояние видно на протяжении всего их 5-минутного окна, и восстанавливаются примерно через 5 минут после того, как оно исчезло.

**Серьёзность** — это метка, которую показывает список выбора. Инцидент и оповещение, которые создаёт шаблон, начинаются с самой высокой серьёзности инцидентов и оповещений вашего проекта; измените их в критерии.

- **Array Stopped Reporting** считает серию идентификации платформы (`purefa_info` или `purefb_info`, которую каждая конечная точка, опрашиваемая агентом, экспортирует при каждом считывании, или `powermax_array_info`, которую записывает каждый сбор PowerMax). Когда данные перестают поступать, остальным шаблонам не с чем сравнивать, и они сохраняют свой последний статус, поэтому сообщает об этом именно этот шаблон.
- **Открытые оповещения и состояния оборудования используют Max** серии, которая существует, только пока оповещение открыто или компонент находится в этом состоянии, поэтому состояние пересекает порог, когда видно на протяжении всего 5-минутного окна.
- **Каждый шаблон для объектов группирует по собственной метке объекта** (`summary`, `component_name`, `host`, `local_pod`, `name`, а на PowerMax — `description`, `component`, `srp`, `srdf_group` и `storage_group`), поэтому срабатывает по одному инциденту на затронутый объект, и инцидент называет этот объект.
- **Шаблоны задержки используют Avg** собственного среднего массива на операцию, а шаблоны ёмкости — **Макс.** его собственного процента использования. Задержки зафиксированы в микросекундах, а ёмкость — в процентах.
- **Hardware Component Unhealthy использует Min** по компоненту: его состояние равно 1, когда он исправен, и падает до 0, когда нет.

Шаблона FlashArray для задержки каждого тома нет, потому что правильный порог зависит от нагрузки: постройте его из каталога с группировкой по `name`. Прогнозу ёмкости нужен тренд роста, а не порог, а для износа дисков нет серии, по которой можно было бы создавать оповещения.

## Собираемые метрики

Агент отправляет всё, что экспортирует массив, а зонд — всё, что он читает с PowerMax, в одних и тех же единицах (миллисекунды Unisphere — как микросекунды, его MB в секунду — как байты в секунду); серии ниже — это каталог, который предлагает форма монитора. Каждое значение — это gauge, который вычисляет сам массив, — задержки в микросекундах на операцию, пропускная способность в секунду, — поэтому вычислять скорость не нужно. **Фильтр** — это фильтр по метке, который придаёт серии смысл, указанный в её строке; форма применяет его за вас.

## Критерии мониторинга

Критерий сравнивает один из запросов или формул монитора с порогом. У критериев монитора системы хранения нет поля **Тип фильтра**: каждое правило проверяет значение метрики с помощью этих полей.

| Поле | Что делает |
| --- | --- |
| **Метрика** | Запрос или формула для проверки, по имени переменной. |
| **Агрегация** | Как значения в окне превращаются в один ответ: **Среднее**, **Сумма**, **Максимальное значение**, **Минимальное значение**, **Все значения** (каждое значение должно совпасть, на протяжении всего окна) или **Любое значение** (достаточно одного). |
| **Условие** | **Больше**, **Меньше**, **Больше или равно**, **Меньше или равно**, **Равно** или **Не равно** — или условие аномалии: **Аномально высоко**, **Аномально низко** или **Аномально**. **Нет данных** срабатывает, когда запрос ничего не вернул за окно, **Есть данные** — когда вернул хоть что-то. **Прогноз: выше** и **Прогноз: ниже** срабатывают, когда тренд метрики в окне окажется за порогом к концу срока из поля **Горизонт прогноза**. |
| **Порог** | Значение, с которым идёт сравнение. Рядом есть список единиц, если у метрики есть единица. Не показывается для условий аномалии. |
| **Чувствительность** | Только условия аномалии. **Низкий** (4σ), **Средний** (3σ, по умолчанию) или **Высокий** (2σ). |
| **Окно базовой линии** | Только условия аномалии. 14 дней (по умолчанию), 28, 60 или 90 дней истории. |
| **Если нет данных** | В разделе **Дополнительные поля**. Что происходит, когда в окне нет выборок: **Ignore** (по умолчанию), **Treat As Zero** или **Триггер**. |

Условия аномалии сравнивают каждое значение с тем же часом недели в базовой линии. Они остаются в состоянии "Learning" и ничего не поднимают, пока в окне базовой линии не накопится достаточно истории. Этот монитор фильтрует запросы по атрибутам, поэтому каждый запрос и каждая серия сгруппированного запроса сравниваются с собственной историей настолько далеко, насколько хранятся ваши метрики. Если это меньше двух недель, сумма, количество или запрос к гистограмме остаются в этом состоянии навсегда, а всё остальное сравнивается со всеми сериями метрики. Перцентиль гистограммы всегда остаётся в этом состоянии.

Несколько критериев для начала:

- **Том работает медленно:** `purefa_volume_performance_latency_usec` с фильтром `dimension=usec_per_read_op`, Среднее, с группировкой по `name`, **Больше** `2000`, за последние 10 минут.
- **Массив заполняется:** `purefa_array_space_utilization`, Максимум, **Больше** `85`, за последние 15 минут.
- **Хост работает через один контроллер:** `purefa_host_connectivity_info` с фильтром `status=critical`, Максимум, с группировкой по `host`, **Больше** `0`.
- **Файловая система FlashBlade почти заполнена:** `purefb_file_systems_space_bytes` с фильтром `space=available_ratio`, Минимум, с группировкой по `name`, **Меньше** `0.05`.

### Критерии по умолчанию

Монитор, который вы строите не из шаблона, начинает с двух критериев:

| Порядок | Критерий | Совпадает, когда | Затем |
| --- | --- | --- | --- |
| 1 | Проверить, что _имя монитора_ не в сети | У первого запроса нет данных за всё окно | Помечает монитор как **Не в сети** и объявляет инцидент "_имя монитора_ не в сети", который разрешается сам, когда монитор восстанавливается. |
| 2 | Проверить, в сети ли _имя монитора_ | У первого запроса есть данные | Помечает монитор как **Работает**. |

> [!IMPORTANT]
> Значение `0` — это данные, поэтому метрика, которая часто равна нулю, например перезапуски или ошибки, не переводит монитор в офлайн. Чтобы получать оповещения по значению, начните с шаблона или добавьте критерий с порогом. Пока данные не приходят совсем и ни один критерий не совпадает, монитор сохраняет свой статус, а открытые инциденты остаются открытыми: тишина — это не восстановление. Время, когда сам OneUptime не получал данные, никогда не считается отсутствием данных: проверка, чьё окно его включает, ждёт, как объясняет [Когда OneUptime не получает данные](/docs/monitor/when-oneuptime-is-not-receiving).

## Terraform

[Terraform-провайдер OneUptime](/docs/terraform/monitor-steps) передаёт конфигурацию шага монитора системы хранения в атрибуте `storage_array_monitor`: сырой JSON конфигурации `storageArrayMonitor` (`arrayIdentifier`, `storageSystem`, `resourceFilters`, `metricViewConfig`, `rollingTime`), записанный с помощью `jsonencode()`:

```hcl title="main.tf"
monitor_steps = [{
  storage_array_monitor = jsonencode({
    arrayIdentifier = "my-storage-array"
    storageSystem   = "purestorage.flasharray"
    resourceFilters = {}
    rollingTime     = "Past 15 Minutes"
    metricViewConfig = {
      queryConfigs = [{
        metricAliasData = { metricVariable = "capacity_used_percent", title = "Capacity Used", description = "", legend = "" }
        metricQueryData = {
          filterData = {
            metricName     = "purefa_array_space_utilization"
            attributes     = {}
            aggegationType = "Max"
            aggregateBy    = {}
          }
        }
      }]
      formulaConfigs = []
    }
  })
  criteria = [ /* ... */ ]
}]
```

`arrayIdentifier` — это `storage.array.name` массива, то есть `STORAGE_ARRAY_NAME`, с которым был запущен агент, а не его ID в OneUptime. `storageSystem` — это `purestorage.flasharray`, `purestorage.flashblade` или `netapp.ontap`. От него зависит, какой каталог и какие шаблоны показывает форма и какую метку читает фильтр тома или оборудования.

## Устранение неполадок

:::details Массива нет в списке «Система хранения»
Массивы регистрируются сами по данным агента. Проверьте, что агент работает и отправляет данные (см. [руководство по Storage Array Agent](/docs/telemetry/storage-arrays)) и что задан `STORAGE_ARRAY_NAME`.
:::

:::details Шаблон оповещений или оборудования никогда не срабатывает
Это нормальный, здоровый случай. `purefa_alerts_open`, `purefa_hw_component_status`, `purefa_drive_capacity_bytes` и `purefa_host_connectivity_info` несут своё состояние в метке, а серия, отфильтрованная до плохого состояния (`severity=critical`, `component_status=failed`), существует, только пока что-то находится в этом состоянии. Чтобы увидеть серию, стоящую за шаблоном, выполните его запрос без фильтра на странице **Метрики**.
:::

:::details Монитор задержки показывает неверные значения
Pure помещает значения чтения, записи, зеркалированной записи, SAN, очереди и QoS в одно имя метрики, различая их только меткой `dimension`, а запрос без фильтра по `dimension` усредняет их все. Фильтруйте по одному измерению, как это делают шаблоны и каталог формы. Серии по томам и по хостам сохраняют только `usec_per_read_op`, `usec_per_write_op` и `usec_per_mirrored_write_op`: агент отбрасывает остальные, чтобы сэкономить серии, и только общая для массива `purefa_array_performance_latency_usec` сохраняет все.
:::

:::details Шаблон ONTAP для события EMS никогда не срабатывает
Шаблон EMS срабатывает, только пока событие его вида находится в его окне: Harvest экспортирует событие один раз — для опроса, который его собрал. Проверьте, что Harvest агента запускает коллектор `Ems` (в поставке так и есть) и что событие входит в список Harvest по умолчанию: в него входят `sk.panic`, `disk.outOfService`, а также события уровней alert и emergency. За неисправностью ONTAP, которая сохраняется (вышедший из строя диск, ошибка полки, узел, который не может взять на себя работу партнёра), следит также её шаблон открытых проблем, который остаётся открытым, пока ONTAP её не снимет.
:::

:::details Окно в 1 минуту не показывает данных
Агент читает тома, хосты и поды каждые 2 минуты, файловые системы и бакеты FlashBlade — каждые 5, а каталоги FlashArray — каждые 30, поэтому в окне в 1 минуту может не оказаться ни одной выборки. Используйте 5 минут или больше: 15 для файловых систем и бакетов, 60 для каталогов.
:::

:::details Монитор PowerMax не показывает данных
Зонд читает PowerMax каждые 5 минут, поэтому используйте окно в 10 минут или больше. Для времени отклика, IOPS и пропускной способности нужен сбор производительности в Unisphere, за которым следит шаблон **Performance Collection Off**, а для значений тома его группа хранения должна быть зарегистрирована в Unisphere для реального времени. Страница подключения в разделе **Продукты → Инфраструктура → Системы хранения → Подключения** сообщает, что не удалось прочитать при последнем сборе.
:::

:::details Инциденты срабатывают один раз для всего массива, а не по одному на том
Группируйте запрос по метке объекта: `name` для томов, подов, каталогов, файловых систем и бакетов, `host` для хостов и `component_name` для оборудования FlashArray; на PowerMax — `storage_group`, `volume`, `component` или `srdf_group`. У меток Pure и PowerMax нет префикса, поэтому `resource.name` ни с чем не совпадает.
:::
