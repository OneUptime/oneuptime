# Мониторинг состояния баз данных

Монитор Database Health по расписанию подключается к PostgreSQL, MySQL или Microsoft SQL Server и сообщает собственные сигналы состояния сервера — запас соединений, заблокированные сеансы, задержку репликации, долю попаданий в кэш, размер базы данных, приближение к переполнению идентификаторов транзакций и ещё около тридцати показателей, — чтобы вы могли получать по ним оповещения так же, как оповещения о недоступности сайта.

Вам не нужно писать SQL. Зонд выполняет фиксированный набор запросов к каталогу только на чтение, выбранный по СУБД, и сообщает небольшой набор именованных чисел.

:::cards
- [Создать пользователя для мониторинга](#создать-пользователя-для-мониторинга): Права, которые нужны каждой СУБД. Этот шаг важнее всего.
- [Создать монитор](#создать-монитор-database-health): Направить зонд на базу данных и выбрать, что собирать.
- [Собираемые метрики](#собираемые-метрики): Каждый ряд и СУБД, которые его сообщают.
- [Настроить критерии](#настроить-критерии): Оповещения о соединениях, блокировках, задержке и переполнении идентификаторов.
:::

## Database Health или SQL Query?

Два типа мониторов баз данных отвечают на разные вопросы и рассчитаны на совместное использование.

| | Database Health | [SQL Query](/docs/monitor/sql-monitor) |
|---|---|---|
| На какой вопрос отвечает | «Здорова ли сама база данных?» | «Такие ли у меня данные, как я ожидаю?» |
| Запрос | Встроенный, свой для каждой СУБД, только на чтение | Ваш собственный |
| Что сообщает | Именованные числовые метрики (см. [Собираемые метрики](#собираемые-метрики)) | Число строк, скалярное значение, первую строку, время выполнения |
| Типичное оповещение | Использовано больше 90 % соединений | Больше 50 отменённых заказов за последние пять минут |
| Нужные права | Чтение статистики/DMV — см. [Создать пользователя для мониторинга](#создать-пользователя-для-мониторинга) | `SELECT` на таблицы, которые затрагивает ваш запрос |

Если нужно оповещение о бизнес-условии, используйте монитор SQL Query. Если нужно узнать, что у сервера заканчиваются соединения, ещё до того, как бизнес-условие вообще сможет нарушиться, используйте этот.

## Поддерживаемые базы данных

| База данных | Порт по умолчанию |
|---|---|
| **PostgreSQL** | `5432` |
| **MySQL** | `3306` |
| **Microsoft SQL Server** | `1433` |

Azure SQL Database и Azure SQL Managed Instance подключаются как **Microsoft SQL Server**. Им нужны другие права — см. [Создать пользователя для мониторинга](#создать-пользователя-для-мониторинга).

СУБД, совместимые с PostgreSQL и MySQL и использующие тот же сетевой протокол, обычно работают, но могут предоставлять меньше представлений статистики; в этом случае затронутые метрики помечаются как недоступные, а не собираются. Официально протестированы только три СУБД выше.

У каждой базы данных, которую используют ваши приложения, кластеры и хосты, — этих трёх СУБД и многих других — есть и собственная страница с метриками СУБД, логами и сервисами, которые к ней обращаются: см. [Базы данных](/docs/telemetry/databases). Если хост и порт, к которым подключается монитор Database Health, совпадают с одной из конечных точек базы данных, оповещения и инциденты монитора также появляются на странице этой базы данных (см. [Оповещения по базе данных](/docs/telemetry/databases#alerts-on-a-database)).

## Как это работает

При каждой проверке зонд:

1. Подключается к базе данных с учётными данными, которые вы указали.
2. Выполняет один лёгкий проверочный запрос. **Это единственная инструкция, сбой которой может перевести монитор в состояние «не в сети».**
3. Выполняет запросы к каталогу для каждой включённой [группы метрик](#группы-метрик), по одной, каждую с тайм-аутом инструкции.
4. Сообщает собранные числа, а также заметку о каждой группе, которую не удалось собрать, с причиной.

```mermaid title="Одна проверка и единственный шаг, который может перевести монитор в состояние «не в сети»"
flowchart TB
    connect["Подключение к базе данных"] --> probe{"Проверочный запрос OK?"}
    probe -->|"Нет"| offline["Монитор не в сети"]
    probe -->|"Да"| groups["Выполнить каждую группу метрик"]
    groups --> group{"Группа собрана?"}
    group -->|"Да"| metrics["Метрики отправлены"]
    group -->|"Нет"| issue["Метрик нет, проблема записана"]
    metrics --> criteria["Критерии проверены"]
    issue --> criteria
```

В OneUptime отправляются только именованные числовые агрегаты. Ни текст запросов, ни строки ваших таблиц, ни имена схем не покидают вашу сеть — запросы читают собственные представления статистики СУБД (`pg_stat_activity`, `performance_schema.global_status`, `sys.dm_exec_sessions` и подобные), но никогда не ваши данные.

Поскольку проверка выполняется с зонда, база данных должна быть доступна только с зонда. Разместите [пользовательский зонд](/docs/probe/custom-probe) внутри своей сети, и OneUptime вообще не понадобится маршрут до базы данных.

## Перед началом

- **Зонд** с сетевым доступом к хосту и порту базы данных. Используйте зонд, размещённый OneUptime, если база данных доступна из интернета, иначе — [пользовательский зонд](/docs/probe/custom-probe) внутри своей сети.
- **Пользователь для мониторинга**, созданный так, как описано в следующем разделе, и его данные для подключения.

## Создать пользователя для мониторинга

**Это самый важный шаг.** Монитор читает представления статистики, которые обычным учётным записям видеть нельзя, и учётная запись с недостаточными правами не всегда завершается ошибкой — в PostgreSQL она даёт неверный ответ. Создайте отдельную учётную запись ровно с этими правами и ничем больше.

### PostgreSQL

```sql
CREATE USER oneuptime_health WITH PASSWORD 'a-strong-password';
GRANT CONNECT ON DATABASE mydb TO oneuptime_health;
-- The one grant that matters. Without it, see the note below.
GRANT pg_monitor TO oneuptime_health;
```

`pg_monitor` — встроенная роль (PostgreSQL 10 и новее), которая даёт доступ на чтение к представлениям статистики и мониторинга. К вашим таблицам она доступа не даёт.

> [!IMPORTANT]
> **Почему `pg_monitor` в PostgreSQL обязательна.** Без неё `pg_stat_activity` не завершается ошибкой — запрос выполняется успешно и возвращает только строку самого сеанса мониторинга. Число соединений всегда показывало бы `1`, заблокированные сеансы — `0`, а задержка репликации — `0`, на сервере, который на самом деле горит. Поэтому зонд **до** выполнения этих запросов проверяет, что учётная запись входит в `pg_monitor` (или `pg_read_all_stats`) либо является суперпользователем. Если ничего из этого не выполняется, зонд сообщает группы Connections, Activity и Locks как недоступные вместе с нужным вам `GRANT`. Не сообщать ничего — честный ответ; сообщать `1` — нет.

В управляемом сервисе, где `pg_monitor` недоступна, те же представления покрывает `pg_read_all_stats`. В Amazon RDS `GRANT rds_superuser` не нужен — `GRANT pg_monitor TO oneuptime_health;` работает от имени участника `rds_superuser`.

### MySQL

```sql
CREATE USER 'oneuptime_health'@'%' IDENTIFIED BY 'a-strong-password';
-- INNODB_TRX (open transactions, longest query) and replication status.
GRANT PROCESS, REPLICATION CLIENT ON *.* TO 'oneuptime_health'@'%';
-- Status counters, server variables, and lock waits.
GRANT SELECT ON performance_schema.* TO 'oneuptime_health'@'%';
-- Database size: information_schema.TABLES only shows tables the login can see.
GRANT SELECT ON mydb.* TO 'oneuptime_health'@'%';
FLUSH PRIVILEGES;
```

В MySQL должна быть включена `performance_schema` (`performance_schema = ON`, по умолчанию начиная с 5.6). Если она выключена, группы Connections, Throughput и Locks помечаются как недоступные, и исправляется это перезапуском сервера, а не правами.

### Microsoft SQL Server и Azure SQL Managed Instance

```sql
-- A server-level grant only runs while the current database is master.
USE master;
CREATE LOGIN oneuptime_health WITH PASSWORD = 'a-strong-password';
-- Every DMV the monitor reads. On SQL Server 2022 and later,
-- VIEW SERVER PERFORMANCE STATE alone is also enough.
GRANT VIEW SERVER STATE TO oneuptime_health;

USE mydb;
CREATE USER oneuptime_health FOR LOGIN oneuptime_health;
```

При запуске из любой другой базы данных `GRANT VIEW SERVER STATE` завершается ошибкой Msg 4621: «Permissions at the server scope can only be granted when the current database is master».

> [!WARNING]
> **Доступа на чтение к вашим таблицам недостаточно.** Учётная запись, которая может только читать данные, — `db_datareader` или любая другая роль «доступа на чтение» — может подключиться и получает размер базы данных, но больше ничего. SQL Server отказывает в доступе к представлениям, которые читает монитор, с сообщением `The user does not have permission to perform this action.` (Msg 297). Сообщение перед ним называет, в чём отказано: Msg 300 `VIEW SERVER STATE` (`VIEW SERVER PERFORMANCE STATE` в 2022) для серверных представлений, включая место в журнале транзакций и свободное место в tempdb, или Msg 262 `VIEW DATABASE STATE` (`VIEW DATABASE PERFORMANCE STATE` в 2022) для представления репликации. Монитор остаётся в сети, сообщает, что группам Connections, Activity, Throughput, Locks, Storage и Replication не хватает прав, и показывает рядом с ними `GRANT` выше. `VIEW SERVER STATE` покрывает их все.
>
> Два представления не отказывают: без этого права `sys.dm_exec_sessions` и `sys.dm_exec_requests` молча показывают только собственный сеанс монитора. Монитор никогда не читает их отдельно — только вместе с представлением, которое отказывает, — поэтому отсутствующее право никогда не может быть записано как «1 соединение».

### Azure SQL Database

В Azure SQL Database нет прав уровня сервера — `GRANT VIEW SERVER STATE` там не работает, — поэтому те же представления открывает право уровня базы данных. Создайте учётную запись в `master`, дайте ей пользователя в базе данных, которую вы отслеживаете, и выдайте право там, а не в `master`:

```sql
-- Connected to master, as the server admin:
CREATE LOGIN oneuptime_health WITH PASSWORD = 'a-strong-password';

-- Connected to the monitored database:
CREATE USER oneuptime_health FOR LOGIN oneuptime_health;
GRANT VIEW DATABASE STATE TO oneuptime_health;
```

Этого достаточно для баз данных vCore и для баз данных DTU уровня S2 и выше. На **Basic, S0 и S1**, а также для любой базы данных в **эластичном пуле** Azure разрешает читать эти представления только администратору сервера, администратору Microsoft Entra или участникам серверной роли `##MS_ServerStateReader##`, что бы ни говорили права базы данных. В этом случае администратор сервера также добавляет учётную запись в эту роль:

```sql
-- Connected to master, as the server admin:
ALTER SERVER ROLE ##MS_ServerStateReader## ADD MEMBER oneuptime_health;
```

`##MS_ServerStateReader##` работает на всех уровнях, поэтому это и запасной вариант, если `VIEW DATABASE STATE` всё же не хватит. Новое членство в роли может вступать в силу несколько минут и действует только для новых соединений; зонд открывает новое соединение при каждой проверке.

Автономный пользователь базы данных (`CREATE USER oneuptime_health WITH PASSWORD = '...'` в отслеживаемой базе данных, без учётной записи сервера) работает с `VIEW DATABASE STATE` на S2 и выше, но не может войти в `##MS_ServerStateReader##`: серверные роли принимают только учётные записи сервера. Чтобы перевести автономного пользователя в роль, удалите его (`DROP USER oneuptime_health;`) и выполните инструкции выше.

Зонд распознаёт Azure SQL Database по `SERVERPROPERTY('EngineEdition')`, а не по версии — Azure SQL Database сообщает `12.0.2000.8`, что бы она ни выполняла на самом деле, а это читается как SQL Server 2014. Поэтому **Engine** монитора показывает `Azure SQL Database 12.0.2000.8`, а отсутствующее право показывается как инструкция для Azure выше и никогда как `VIEW SERVER STATE`.

- **Репликация не собирается в Azure SQL Database.** В Azure SQL Database нет `sys.dm_hadr_database_replica_states`, поэтому группа Replication там пропускается, а не помечается как сбойная при каждой проверке. Собственные представления реплик Azure (`sys.dm_database_replica_states`, `sys.dm_geo_replication_link_status`) пока не читаются.
- **Соединения считаются по базе данных.** С `VIEW DATABASE STATE` Azure SQL Database показывает только сеансы отслеживаемой базы данных, поэтому Connections считает эту базу, а не логический сервер. Отслеживайте каждую базу данных, которая для вас важна.
- **В эластичном пуле TempDB Free Space относится к пулу.** Базы данных в пуле используют одну общую tempdb.

## Создать монитор Database Health

:::steps
### Начните новый монитор

Перейдите в **Мониторы** и нажмите **Создать монитор**. В разделе **Тип монитора** нажмите **Другие типы мониторов** и выберите **Database Health** в группе **Database Monitoring** или введите `health` в поле поиска. Введите **Имя**, затем нажмите **Далее**.

### Введите данные для подключения

Выберите **Database Type**, затем заполните хост, порт, имя базы данных и учётные данные пользователя для мониторинга. Указывайте пароль как ссылку на [секрет монитора](#секрет-монитора-для-пароля), а не вводите его. Каждое поле описано в разделе [Настройка](#настройка).

### Выберите, что собирать

Оставьте все группы в **Metric Groups** включёнными, если у вас нет причины отключить какую-либо из них, — см. [Группы метрик](#группы-метрик).

### Проверьте подключение

Нажмите **Протестировать монитор**, чтобы выполнить одну проверку до сохранения, и посмотрите, что она собрала.

### Задайте критерии

Просмотрите критерии, с которыми начинает монитор, и добавьте свои — см. [Настроить критерии](#настроить-критерии). Затем нажмите **Далее**.

### Выберите зонды и создайте монитор

Выберите **Зонды**, которые могут достучаться до базы данных, и **Интервал мониторинга**, затем нажмите **Создать монитор**.
:::

## Настройка

| Поле | Что ввести |
|---|---|
| **Database Type** | PostgreSQL, MySQL или Microsoft SQL Server. Выбор типа задаёт порт по умолчанию и определяет, какие запросы выполняются. |
| **Хост** | Хост базы данных, доступный с зонда (например, `db.internal`). |
| **Порт** | Порт базы данных. |
| **Имя базы данных** | База данных, к которой нужно подключиться. Метрики уровня базы данных (размер, доля попаданий в кэш, сброс во временные файлы) сообщаются для этой базы; метрики уровня сервера (соединения, время работы, репликация) — для всего сервера, кроме Azure SQL Database, где соединения считаются только для отслеживаемой базы. |
| **Use Windows Integrated Authentication** | Только Microsoft SQL Server. Проверка подлинности от имени процесса зонда вместо имени пользователя и пароля. См. [Встроенная проверка подлинности Windows](/docs/monitor/sql-monitor) на странице монитора SQL Query — настройка та же. |
| **Имя пользователя** | Пользователь для мониторинга. Обязательно, если вы не используете встроенную проверку подлинности Windows. |
| **Пароль** | Пароль. Указывайте ссылку на [секрет монитора](/docs/monitor/monitor-secrets) в виде `{{monitorSecrets.name}}`, а не вводите пароль открытым текстом (см. [Секрет монитора для пароля](#секрет-монитора-для-пароля)). |
| **Use SSL/TLS** | Подключение по TLS. Когда это включено, для самоподписанного сертификата можно отключить **Verify server certificate**. |
| **Metric Groups** | Какие группы выполнять: Connections, Активность, Throughput, Locks and Blocking, Хранилище, Replication и Обслуживание. По умолчанию все включены; см. [Группы метрик](#группы-метрик). В сведениях о мониторе они перечислены как **Collected Metric Groups**. |

### Дополнительные поля

| Поле | По умолчанию | Максимум | Что ограничивает |
|---|---|---|---|
| **Connection Timeout (ms)** | `10000` | `30000` | Сколько ждать установки соединения. |
| **Statement Timeout (ms)** | `10000` | `60000` | Предел для каждого отдельного запроса к каталогу. |

Тайм-аут инструкции по умолчанию намеренно короче, чем у монитора SQL Query: на здоровом сервере эти запросы отвечают за миллисекунды, поэтому если `pg_stat_activity` выполняется десять секунд, полезный сигнал — «у этого сервера проблемы», а не более долгое ожидание. Значение больше максимума уменьшается до максимума.

## Секрет монитора для пароля

Чтобы пароль никогда не хранился в мониторе открытым текстом:

:::steps
1. Перейдите в **Мониторы → Настройки → Секреты** и создайте [секрет монитора](/docs/monitor/monitor-secrets).
2. Задайте ему имя (например, `dbPassword`) и дайте этому монитору доступ к нему.
3. В поле **Пароль** монитора введите `{{monitorSecrets.dbPassword}}`.
:::

Секрет подставляется на сервере до того, как конфигурация передаётся зонду. Поля Хост, Имя пользователя и Имя базы данных принимают такую же ссылку. Учётные данные никогда не записываются в логи, ленты монитора или шаблоны оповещений.

## Группы метрик

Группа — это единица, которую вы включаете или выключаете, и единица, по которой сообщается об отсутствующем праве. Группы нужны, чтобы отсутствие одного права стоило вам одной группы, а не всего монитора. Инструкции группы выполняются по одной, поэтому группа может быть собрана частично: тогда она есть и в `collectedGroups`, и в `unavailableGroups`. Типичный случай — группа Storage в SQL Server для учётной записи без `VIEW SERVER STATE`: размер базы данных собирается, а место в журнале и свободное место в tempdb — нет.

| Группа | Что собирает | Что нужно |
|---|---|---|
| Connections | Число соединений, настроенный предел, прерванные подключения, время работы сервера | PostgreSQL: `pg_monitor`. MySQL: `performance_schema`. SQL Server: `VIEW SERVER STATE` |
| Activity | Самый долгий выполняющийся запрос, самая долгая открытая транзакция, открытые транзакции | PostgreSQL: `pg_monitor`. MySQL: `PROCESS`. SQL Server: `VIEW SERVER STATE` |
| Throughput | Транзакции, запросы, доля попаданий в кэш, чтения и записи на диск, время ввода-вывода | PostgreSQL: ничего, кроме `CONNECT`. MySQL: `performance_schema`. SQL Server: `VIEW SERVER STATE` |
| Locks | Заблокированные сеансы, ожидания блокировок, взаимоблокировки, ожидания табличных блокировок | PostgreSQL: `pg_monitor`. MySQL: `performance_schema`. SQL Server: `VIEW SERVER STATE` |
| Storage | Размер базы данных, сброс во временные файлы, место в журнале, свободное место в tempdb | PostgreSQL: ничего, кроме `CONNECT`. MySQL: `SELECT` на базу данных. SQL Server: ничего для размера базы данных; `VIEW SERVER STATE` для места в журнале и свободного места в tempdb |
| Replication | Подключённые реплики, задержка репликации в секундах и байтах, неактивные слоты, состояние восстановления | PostgreSQL: `pg_monitor`. MySQL: `REPLICATION CLIENT`. SQL Server: `VIEW SERVER STATE`; в Azure SQL Database не собирается |
| Maintenance | Запас до переполнения идентификаторов транзакций, мёртвые кортежи, таблицы, которые autovacuum ни разу не обрабатывал, контрольные точки | PostgreSQL: `pg_monitor` |

В Azure SQL Database читайте `VIEW DATABASE STATE` везде, где в этой таблице написано `VIEW SERVER STATE`, — или `##MS_ServerStateReader##` на Basic, S0, S1 и в эластичных пулах. См. [Azure SQL Database](#azure-sql-database).

Отключение группы происходит молча: нет метрик, нет проблемы сбора, нет оповещения. Это правильное решение в двух случаях:

- **Вы не можете получить право.** Если отключить группу, проблема сбора перестанет повторяться при каждой проверке.
- **Запросы слишком дорогие.** В MySQL обычный кандидат — **Хранилище**: размер базы данных получается суммированием `information_schema.TABLES`, что на схеме с десятками тысяч таблиц не бесплатно и выполняется при каждой проверке. Отключите группу или переведите этот монитор на пятиминутный интервал.

Снять отметки со всех групп — не способ ничего не собирать: пустой список снова превращается во все группы, поэтому монитор нельзя сохранить в состоянии, в котором он молча ничего не собирает.

## Что происходит, если метрику нельзя собрать

**Отсутствующее право никогда не переводит монитор в состояние «не в сети».** Это самое важное поведение этого типа мониторов, и его стоит описать точно.

| Что не удалось | Статус монитора | Что вы видите |
|---|---|---|
| **Подключение** или проверочный запрос — неверные учётные данные, отказ в соединении, сбой TLS, тайм-аут подключения | **Не в сети** | `Database Is Online` равно false, и срабатывают инцидент и политика дежурств, которые вы к нему привязали. |
| **Группа** — отсутствующее право, выключенная `performance_schema`, тайм-аут инструкции | **Остаётся в сети** | Метрики, которые эта группа не смогла прочитать, **отсутствуют**, а не равны нулю. Линия на графике не рисуется, ни один порог по этим рядам не может сработать, и из них не может возникнуть инцидент. Проверка записывает одну проблему сбора с названием группы, причиной и — если он есть — точным `GRANT`, который нужно выполнить; она видна в сводке монитора и учитывается в **Metric Groups Failed**. |
| **СУБД вообще не может выдать метрику** — в стандартной MySQL нет счётчика взаимоблокировок; SQL Server по умолчанию не ограничивает число соединений, поэтому «процент использования» не имел бы смысла | **Остаётся в сети** | Метрики просто нет. Это **не** проблема сбора, она не учитывается в Metric Groups Failed, и исправлять тут нечего. См. столбец Engines в разделе [Собираемые метрики](#собираемые-метрики). |

Отсутствует — значит отсутствует. Значение, которое не было измерено, никогда не сообщается как `0`, потому что график из выдуманных нулей хуже пробела — пробел вы видите.

> [!TIP]
> Чтобы получать оповещения о потере видимости, используйте `Database Collection Error` или порог по **Metric Groups Failed**. Делайте их оповещениями, а не инцидентами: отозванное право — это заявка, а не вызов дежурного.

### "The user does not have permission to perform this action"

Это сообщение SQL Server (Msg 297) для учётной записи, которая может подключиться, но не может читать представления состояния сервера. Оно всегда означает отсутствующее право и никогда — неисправность базы данных. SQL Server отправляет его вторым, после сообщения, в котором названо отклонённое разрешение, и монитор показывает оба: например, `VIEW SERVER STATE permission was denied on object 'server', database 'master'. The user does not have permission to perform this action.` Рядом показана инструкция, которая исправляет это для платформы, к которой подключился зонд:

- **SQL Server или Azure SQL Managed Instance** — `GRANT VIEW SERVER STATE TO oneuptime_health;`, выполненная в `master` (монитор показывает её как `GRANT VIEW SERVER STATE TO [<monitoring_login>]; -- run in master`).
- **Azure SQL Database** — `GRANT VIEW DATABASE STATE TO oneuptime_health;`, выполненная в отслеживаемой базе данных; на Basic, S0, S1 и в эластичных пулах вместо неё — членство в `##MS_ServerStateReader##`. См. [Azure SQL Database](#azure-sql-database).

Размер базы данных тем временем продолжает собираться, потому что это единственная метрика группы Storage, которую может прочитать любая учётная запись.

> [!IMPORTANT]
> **Transaction ID Used** заслуживает критерия на каждом мониторе PostgreSQL, который вы создаёте. ## Настроить критерии

| Тип фильтра | Что проверяет |
|---|---|
| **Database Is Online** | Была ли база данных доступна и выполнился ли проверочный запрос. Это критерий «не в сети», с которым создаётся монитор, и единственная проверка, отражающая доступность. |
| **Database Metric** | Выберите метрику и сравните её: Greater Than, Less Than, Greater Than Or Equal To, Less Than Or Equal To, Equal To или Not Equal To. Список метрик предлагает только те, которые может выдать выбранная СУБД, поэтому нельзя построить критерий, который навсегда останется невыполненным (одно исключение: метрики Replication, предлагаемые для Microsoft SQL Server, никогда не собираются в Azure SQL Database). Если метрика не была собрана при проверке — группа завершилась сбоем или СУБД её не сообщает, — фильтр не совпадает, причём не совпадает и как «false»: он пропускается. Проблема прав не может никого вызвать. |
| **Database Collection Error** | Сводка проблем сбора за проверку, по одной строке «группа: сообщение» на каждую недоступную группу. Настройте оповещение, когда она не пуста, чтобы замечать потерю видимости, или используйте Contains, чтобы следить за конкретной группой. |
| **JavaScript Expression** | Полный контроль. См. [Выражения JavaScript](/docs/monitor/javascript-expression). |

Пороги — целые числа. Пишите `90`, а не `90.5`: проценты и секунды сравниваются как целые.

**Database Is Online** и **Database Metric** можно проверять за период: включите **Оценивать этот критерий в течение определённого периода времени**, затем выберите в **Оценить**, как оценивать значения (например, **All Values**), и заполните **За последние (в минутах)**. За период настройка фильтра **Если нет данных** определяет, что означает отсутствующее значение; оставьте **Ignore**, чтобы отсутствующее право по-прежнему не могло никого вызвать.

### Переменные выражений JavaScript

Для монитора Database Health выражению доступны:

| Переменная | Тип | Описание |
|---|---|---|
| `isOnline` | boolean | Удались ли и подключение, и проверочный запрос |
| `engineVersion` | string | Строка версии, которую сообщил сервер (в SQL Server — просто `ProductVersion`; сводка монитора называет рядом платформу) |
| `connectionError` | string | Очищенная ошибка подключения, пустая, если ошибки не было |
| `collectedGroups` | array | Группы, которые выдали значения при этой проверке |
| `unavailableGroups` | array | Группы с инструкцией, которую не удалось собрать, каждая с причиной и способом исправления. Частично собранная группа есть в обоих списках |
| `metrics` | object | Собранные значения с ключом по имени ряда; ряда, который не был собран, нет |

```javascript
{{isOnline}} === true && {{collectedGroups}}.length >= 5
```

Чтобы прочитать одну метрику в выражении, обращайтесь по индексу ко всему объекту `metrics` — имена рядов содержат точки, поэтому их нельзя поместить в фигурные скобки:

```javascript
{{metrics}}['oneuptime.monitor.database.connections.used.percent'] > 90
```

Для порога по одной метрике лучше подходит **Database Metric**, а не выражение: он сам находит ряд, предлагает только то, что может выдать ваша СУБД, и пропускает проверку, если значение не было собрано, вместо сравнения с пустотой.

### Пример: основной сервер PostgreSQL

| Порядок | Критерий | Фильтр |
|---|---|---|
| 1 | **Не в сети** | `Database Is Online` равно `false`. |
| 2 | **Деградация** | `Database Metric` → Connections Used больше `90`, оценивается за 5 минут с All Values, чтобы одиночный всплеск никого не вызвал. |
| 3 | **Деградация** | `Database Metric` → Transaction ID Used больше `80`. |
| 4 | **Деградация** | `Database Metric` → Blocked Sessions больше `0`, за 5 минут. |
| 5 | **Online** | `Database Is Online` равно `true`. |

Критерии проверяются сверху вниз, и побеждает первое совпадение, поэтому ставьте критерии оповещений первыми, а критерий здорового состояния — последним.

Привяжите политику дежурств к критерию «не в сети», а всё, что основано на **Metric Groups Failed** или `Database Collection Error`, оставьте оповещением без политики дежурств.

## Что учесть

- **Запросы выполняются при каждой проверке.** Они дешёвые по замыслу, но «дешёвые» — понятие относительное и зависит от интервала. Интервал в одну минуту для сервера с тысячами сеансов означает больше сканирований `pg_stat_activity`, чем вам может хотеться; для метрик ёмкости вполне хватает пяти минут.
- **Направляйте монитор на ту базу данных, которая вам важна.** Размер, доля попаданий в кэш и сброс во временные файлы считаются для каждой базы. Соединения, время работы и репликация относятся ко всему серверу и одинаковы из любой базы этого экземпляра.
- **Один монитор на экземпляр, а не на базу данных**, если только вам специально не нужны метрики размера и кэша по каждой базе — иначе вы умножаете серверные запросы без новой информации. Исключение — Azure SQL Database: там соединения считаются по базе данных, поэтому отслеживайте каждую базу.
- **Настраивайте оповещения по скоростям, а не по счётчикам.** Всё, что оканчивается на `total`, только растёт, поэтому порог «больше чем» по такому значению сработает один раз и никогда не восстановится. Стройте по нему график или сравнивайте за окно.
- **Предпочитайте секрет монитора паролю открытым текстом.** Тогда учётные данные хранятся в зашифрованном виде и никогда не отображаются в мониторе.
- **Монитор никогда не пишет.** Каждый запрос — это чтение представления статистики: в PostgreSQL внутри транзакции только на чтение, в MySQL в сеансе только на чтение. Всё, что он не может прочитать, сообщается как отсутствующая метрика, но никогда как сбой.

## Устранение неполадок

:::details Монитор не в сети, но база данных работает
«Не в сети» означает, что зонд не смог подключиться или проверочный запрос завершился сбоем: хост или порт недоступны с зонда, в доступе для учётной записи отказано, TLS завершился сбоем или истёк тайм-аут подключения. Сводка монитора показывает ошибку. Проверьте, что зонд достаёт до базы данных (зонду, размещённому OneUptime, нужен публичный адрес; иначе используйте [пользовательский зонд](/docs/probe/custom-probe)), проверьте имя пользователя и пароль или его секрет монитора и отключите **Verify server certificate** для самоподписанного сертификата. Затем нажмите **Протестировать монитор**, чтобы проверить снова.
:::

:::details В PostgreSQL нет Connections, Activity и Locks
Учётная запись не входит ни в `pg_monitor`, ни в `pg_read_all_stats` и не является суперпользователем, поэтому зонд пропускает эти группы вместо записи неверных чисел. Выполните `GRANT pg_monitor TO oneuptime_health;`, как описано в разделе [PostgreSQL](#postgresql).
:::

:::details В MySQL нет Connections, Throughput и Locks
Либо у учётной записи нет `SELECT` на `performance_schema`, либо `performance_schema` на сервере выключена; сводка монитора показывает сообщение MySQL. Если не хватает права, выполните инструкции из раздела [MySQL](#mysql). Для выключенной `performance_schema` нужны `performance_schema = ON` в конфигурации сервера и перезапуск.
:::

:::details I/O Read Time и I/O Write Time в PostgreSQL всегда равны 0
PostgreSQL измеряет их, только когда включён `track_io_timing`, а по умолчанию он выключен. Включите его в конфигурации сервера или в группе параметров вашего управляемого сервиса, чтобы видеть реальные значения. Дело не в отсутствующем праве.
:::

:::details Metric Groups Failed больше 0 при каждой проверке
Какую-то группу не удаётся собрать ни при одной проверке, поэтому повторяется одна и та же проблема сбора. Сводка монитора называет группу, причину и `GRANT`, который это исправляет. Выдайте это право, а если получить его нельзя, отключите эту группу в **Metric Groups**, чтобы проблема перестала повторяться.
:::
