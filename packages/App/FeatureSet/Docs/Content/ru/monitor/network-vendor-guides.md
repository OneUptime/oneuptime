# Руководства по сетевым вендорам (Sophos, Extreme, Cambium)

Как с помощью OneUptime от начала до конца отслеживать три распространённых парка: Sophos Firewall (XGS, SFOS) с его туннелями IPsec, WAN-каналами и SD-WAN; коммутаторы Extreme Networks (EXOS / Switch Engine и Fabric Engine / VOSS) с их фабрикой; а также коммутаторы cnMatrix и корпоративные точки доступа Wi-Fi Cambium Networks — вплоть до канала и мощности передачи каждого радиомодуля. Они охватывают и коммутаторы SAN — Brocade Fabric OS и Cisco MDS 9000 — вплоть до ошибок каждого порта Fibre Channel.

:::cards
- [Sophos Firewall](#sophos-firewall-xgs-sfos): Туннели, WAN-каналы, шлюзы и SD-WAN.
- [Extreme Networks](#extreme-networks-exos-switch-engine-и-fabric-engine-voss): Коммутаторы, фабрика и её оборудование.
- [Cambium Networks](#cambium-networks-корпоративный-wi-fi-и-cnmatrix): Точки доступа вплоть до каждого радиомодуля и коммутаторы cnMatrix.
- [Brocade Fabric OS](#brocade-fabric-os): Порты Fibre Channel, оптика, датчики и события фабрики.
- [Cisco MDS 9000](#cisco-mds-9000): Интерфейсы Fibre Channel, VSAN, slow drain и тревоги port-monitor.
:::

## Как это работает

Каждое руководство использует одни и те же элементы:

```mermaid title="Элементы, которые использует каждое руководство"
flowchart TB
    Device["Межсетевой экран, коммутатор<br/>или точка доступа"]
    Probe["Зонд"]
    Snmp["Шаблон производителя:<br/>OID состояния и SNMP-таблицы"]
    Syslog["Syslog: конвейер логов,<br/>мониторы журналов, правила записи"]
    Monitor["Монитор сетевого устройства<br/>с рекомендуемыми оповещениями"]
    Incident["Инциденты и оповещения"]
    Device -->|"SNMP"| Probe
    Device -->|"Syslog и трапы"| Probe
    Probe --> Snmp
    Probe --> Syslog
    Snmp --> Monitor
    Monitor --> Incident
    Syslog --> Incident
```

- По одному [сетевому устройству](/docs/monitor/network-device-monitor) на каждый аппарат, опрашиваемому зондом, который может до него достучаться, с шаблоном производителя, приносящим нужные OID состояния и [SNMP-таблицы](/docs/monitor/network-device-monitor#snmp-таблицы).
- По одному монитору сетевого устройства на устройство для оповещений. Создавайте его со страницы устройства, чтобы [рекомендуемые оповещения](/docs/monitor/network-device-monitor#рекомендуемый-набор-оповещений), включая по одному оповещению на строку для каждой таблицы, которая знает, как выглядит норма, заполнились за вас. Для парка [политика оповещений](/docs/monitor/network-device-monitor#политики-оповещений) поддерживает такой монитор на каждом устройстве.
- Для того, о чём производитель сообщает только в журналах: syslog на зонд, который OneUptime сам читает как [сетевые события](/docs/monitor/network-events), [мониторы журналов с Group By](/docs/monitor/logs-monitor#оповещения-по-группам-group-by), чтобы оповещать один раз на туннель или шлюз, и [правила записи журналов](/docs/telemetry/log-recording-rules), чтобы строить графики по числам из этих журналов.

## Sophos Firewall (XGS / SFOS)

| Что вы хотите видеть | Откуда это берётся |
| --- | --- |
| Состояние межсетевого экрана: память, диск, swap, состояние HA, служба IPsec, CPU по ядрам | SNMP с шаблоном производителя **Sophos Firewall (SFOS / XGS)** |
| Статус каждого туннеля IPsec по имени | SNMP-таблица `ipsec_tunnels` (SFOS v20 и новее) |
| Статус, пропускная способность, загрузка и ошибки каждого WAN-канала | Обход интерфейсов WAN-портов |
| Задержка, потеря пакетов и джиттер каждого WAN-канала | Ping-мониторы и опросы устройства с зондов OneUptime |
| Шлюзы в сети и недоступные, SLA SD-WAN выполнен или нет, изменения маршрутов SD-WAN | Syslog межсетевого экрана |
| Задержка, джиттер и потеря пакетов SD-WAN по шлюзам в виде графиков | Правила записи журналов по журналам SLA SD-WAN |

Sophos не сообщает состояние шлюзов и SD-WAN по SNMP ни в одной версии SFOS: оно есть только в журналах межсетевого экрана и в оповещениях Sophos Central, поэтому последние три строки идут через syslog.

### Регистрация межсетевого экрана

:::steps
1. На межсетевом экране включите SNMP в **Administration → SNMP**: добавьте пользователя SNMPv3 или community v2c и разрешите адресу зонда опрашивать его.
2. В OneUptime перейдите в **Сеть → Устройства** и нажмите **Добавить устройство**. Введите адрес управления межсетевого экрана, выберите зонд, который может до него достучаться, и добавьте учётные данные SNMP в разделе **SNMP**.
3. На странице **Настройки** устройства в разделе **Polling & Data Collection** примените шаблон **Sophos Firewall (SFOS / XGS)** из **Vendor Health Template** и добавьте его таблицы через **Add a Vendor's Tables**. Или включите **Auto-Apply Vendor Health Template**, и первый опрос сделает и то, и другое.
:::

После следующего опроса страница **Таблицы SNMP** устройства перечисляет каждое подключение IPsec с его статусом (active, inactive, partially active) и ядра CPU. SFOS нумерует свои ядра начиная с 196608, поэтому CPU берётся из таблицы, а не из одного `hrProcessorLoad.1`.

### Оповещения по каждому туннелю IPsec

На странице устройства нажмите **Создать монитор**. Рекомендуемые оповещения включают **IPsec Tunnels: row unhealthy** — критерий **Строка таблицы SNMP неисправна** по таблице `ipsec_tunnels` с Row `*`: он открывает по инциденту на каждый неактивный туннель, называя его по туннелю, и закрывает каждый, когда его туннель возвращается.

У туннеля, который Sophos считает активным, подняты лишь ассоциации безопасности. Чтобы доказать, что трафик через него проходит, добавьте [Ping-монитор](/docs/monitor/ping-monitor) с зонда на одной площадке до узла на другой стороне каждого туннеля и нарисуйте туннель как связь между площадками в **Сеть → Топология → Связи площадки** между двумя [площадками](/docs/monitor/network-sites), привязав её к этому монитору: связь на карте тогда принимает цвет монитора.

### WAN-каналы

- **Состояние портов.** Обход интерфейсов уже измеряет статус, входящие и исходящие биты, загрузку и ошибки каждого WAN-порта. В мониторе межсетевого экрана критерий **Интерфейс SNMP недоступен** или **Использование интерфейса SNMP (в %)** с **Интерфейс**, равным имени WAN-порта, или `*` для каждого порта оповещает по каждому каналу.
- **Качество пути.** Задержка, потеря пакетов и джиттер каждого канала измеряются снаружи межсетевого экрана: Ping-монитор с облачных зондов OneUptime на публичный адрес каждого WAN-канала и Ping-монитор с зонда на площадке на шлюз каждого провайдера. Критерии потери пакетов и джиттера на этих мониторах оповещают по каждому каналу, а **Сеть → Топология → Матрица задержек** с одного взгляда показывает каждый зонд относительно каждого монитора.
- **Трафик.** SFOS экспортирует NetFlow v5. Отправляйте его на зонд по UDP 2055, где по умолчанию слушает сборщик потоков зонда, и страница **Трафик** устройства покажет, кто с кем общается по каждому WAN-каналу; подробности — в разделе [Сетевой трафик](/docs/monitor/network-traffic).

### Шлюзы и SD-WAN из syslog

:::steps
1. Приёмник syslog зонда включён по умолчанию. Он слушает порт 5140, по UDP и TCP (`PROBE_SYSLOG_RECEIVER_PORT` меняет порт); если зонд работает в Docker, опубликуйте порт. Сообщения сопоставляются с сетевым устройством, у которого имя хоста или один из **Другие адреса** совпадает с адресом отправителя, и появляются на страницах **События** и **Журналы** устройства.
2. На межсетевом экране в **System services → Log settings** добавьте сервер syslog, указывающий на зонд и этот порт, и отметьте типы журналов **Event** для IPsec и шлюзов и тип журнала **SD-WAN**: журналы SLA остаются выключенными, пока он не отмечен.
3. Разбирать ничего не нужно. OneUptime читает поля `key=value` межсетевого экрана как атрибуты `sophos.*` и извлекает из них туннели, шлюзы, изменения SLA SD-WAN, переключения на резерв и входы в виде [сетевых событий](/docs/monitor/network-events). Откройте журнал на странице **Журналы** устройства, чтобы увидеть точные имена атрибутов, которые выдаёт ваша версия SFOS.
4. На странице **События** устройства нажмите **Создать оповещение** и выберите оповещение. Оно открывает заполненный [монитор журналов](/docs/monitor/logs-monitor) с **Группировать по атрибутам**, чтобы каждый туннель или шлюз оповещал отдельно, и с **Устраняется по атрибутам**, чтобы каждое оповещение закрывалось, когда межсетевой экран сообщает о восстановлении. Строки ниже — три, с которых стоит начать.
5. Постройте графики качества SD-WAN: при включённом журналировании SD-WAN межсетевой экран пишет сводку SLA по каждому профилю и шлюзу (`latency`, `jitter`, `packet_loss`). В **Журналы → Настройки → Правила записи** создайте по правилу на каждое число, например среднее `sophos.latency` с группировкой по `sophos.gw_name` и `sophos.profile_name`, затем постройте графики результатов или оповещайте по ним [монитором метрик](/docs/monitor/metrics-monitor) с группировкой по шлюзу. [Правила записи журналов](/docs/telemetry/log-recording-rules) разбирают этот пример.
:::

| Оповещение | Какое событие считает | Одно оповещение на | Чем закрывается |
| --- | --- | --- | --- |
| VPN-туннель падает | `vpn.tunnel_down` | `vpn.tunnel.name` | `vpn.tunnel_up` |
| WAN-канал падает | `gateway.down` | `network.gateway.name` | `gateway.up` |
| Канал SD-WAN ниже своего SLA | `sdwan.sla_not_met` | `network.gateway.name` | `sdwan.sla_met` |

Первые два есть в списке **Создать оповещение**; для третьего откройте одно из его событий и нажмите **Создать оповещение для этого события**. События syslog дополняют SNMP-таблицу: они приходят в момент падения туннеля, а таблица ловит ещё и туннель, который так и не поднялся.

### Трапы

Каждое уведомление Sophos — это один и тот же трап `sfosNotification` (`1.3.6.1.4.1.2604.5.1.8.1.1`) с событием в виде текста в `sfosTrapMessage` (`1.3.6.1.4.1.2604.5.1.8.1.2`). Чтобы оповещать об одном виде событий, объедините **Получен SNMP-трап (OID трапа)** Равно `1.3.6.1.4.1.2604.5.1.8.1.1` с **Значение varbind SNMP-трапа** по этой varbind, например Содержит `IPSec`. Задайте получателя трапов межсетевого экрана с SNMP v2c: приёмник трапов зонда принимает трапы v1 и v2c.

## Extreme Networks (EXOS / Switch Engine и Fabric Engine / VOSS)

| Что вы хотите видеть | Откуда это берётся |
| --- | --- |
| EXOS: CPU, температура и её авария, состояние питания, блоки питания, вентиляторы, память по слотам, члены стека | Шаблон **Extreme Networks EXOS / Switch Engine** |
| Fabric Engine: CPU и память по слотам, датчики температуры, вентиляторы, блоки питания, сессия vIST, число I-SID | Шаблон **Extreme Networks Fabric Engine / VOSS** |
| Каждая смежность Fabric Connect (IS-IS) с именем соседа | Таблица `isis_adjacencies` шаблона Fabric Engine |
| Порты, соседи LLDP, карта сети | Обход интерфейсов, у обоих |

### Какой шаблон

Fabric Engine на универсальном оборудовании Extreme (серии 5000 и 7000) сообщает тот же enterprise-номер, что и EXOS: только его системное описание (`7520-48Y-8C-FabricEngine (9.0.4.0)`) говорит, какая операционная система запущена. OneUptime читает оба, поэтому автоприменение и подсказка на странице устройства выбирают правильный шаблон, а старые коммутаторы VSP сообщают ветку Avaya/Nortel и сразу распознаются как Fabric Engine.

### Оповещения по фабрике и оборудованию

Рекомендуемые оповещения на коммутаторе Fabric Engine включают **Fabric Adjacencies (IS-IS): row unhealthy** — инцидент на каждого соседа, чья смежность не поднята. Fabric Engine также отправляет трап при изменении смежности — `rcnIsisPlsbAdjStateTrap` (`1.3.6.1.4.1.2272.1.21.0.281`), — и критерий **Получен SNMP-трап (OID трапа)** по нему оповещает за секунды, до следующего опроса.

Блоки питания, вентиляторы, датчики температуры и члены стека — это таблицы, объявляющие свои нормальные значения, поэтому каждая получает оповещение на строку в рекомендуемых оповещениях.

### Потоки и Wi-Fi

EXOS и Fabric Engine экспортируют потоки как sFlow и IPFIX. Отправляйте sFlow на зонд по UDP 6343 или IPFIX по UDP 4739, и страница **Трафик** устройства покажет его трафик; см. [Сетевой трафик](/docs/monitor/network-traffic).

У точек доступа IQ Engine (HiveOS) и ExtremeCloud IQ Controller есть собственные шаблоны производителя, заполняющие страницу **Wi-Fi** устройства. О них рассказывает раздел [Поддерживаемые производители Wi-Fi](/docs/monitor/network-device-monitor#поддерживаемые-производители-wi-fi) — вместе с Ubiquiti UniFi, HPE Aruba, TP-Link Omada и Juniper Mist.

## Cambium Networks (корпоративный Wi-Fi и cnMatrix)

### Точки доступа

:::steps
1. Включите SNMP на точках доступа. В cnMaestro SNMP задаётся для группы AP: **Configuration → Wi-Fi Profiles → AP Groups → Management → SNMP**. Включите его с community v2c на чтение или пользователем SNMPv3.
2. Добавьте каждую точку доступа с её адресом управления и этими учётными данными и примените шаблон **Cambium Networks Enterprise Wi-Fi (cnPilot, XV, XE, XH)** или включите автоприменение.
3. Откройте страницу **Wi-Fi** устройства. Она показывает, сколько радиомодулей включено, клиентов и SSID, затем для каждого радиомодуля диапазон, канал, частоту, ширину канала, мощность передачи, клиентов, уровень шума и эфирное время, а также каждый SSID с его клиентами. Частота вычисляется по диапазону и каналу; точка доступа её не сообщает.
:::

Полезные оповещения, все по таблице `wifi_radios` с Row `*`, чтобы каждый радиомодуль оповещал отдельно:

| Оповещение | Критерий |
| --- | --- |
| Радиомодуль выключен | **Строка таблицы SNMP неисправна**, входит в рекомендуемые оповещения |
| Изменилась мощность передачи | **Значение таблицы SNMP**, столбец TX Power, Не равно запланированной вами мощности |
| Перегруженный радиомодуль | **Значение таблицы SNMP**, столбец Clients, Больше вашего лимита |
| Зашумлённый канал | **Значение таблицы SNMP**, столбец Noise Floor, Больше `-80` |

Каждое числовое значение радиомодуля — это ещё и метрика (`oneuptime.monitor.snmp.table.value`, по серии на радиомодуль и столбец), поэтому канал, мощность и клиентов можно выводить на панель во времени; канал, который постоянно меняется, — это работа DFS.

Cambium сообщает общее число клиентов только начиная с прошивки 6.5.3; более ранние прошивки возвращают 0.

### Коммутаторы cnMatrix

Шаблон **Cambium Networks cnMatrix** собирает CPU, RAM, флеш-память, температуру и напряжение питания, а в виде таблиц — вентиляторы, резервный блок питания и потребление PoE каждого порта. Порты и соседи LLDP берутся из обхода интерфейсов, как на любом коммутаторе.

### Аварии cnMaestro

cnMaestro может отправлять свои аварии, например уход точки доступа из сети, на HTTPS-вебхук. Направьте его на [монитор входящих запросов](/docs/monitor/incoming-request-monitor), чтобы превращать эти аварии в инциденты OneUptime рядом с данными SNMP.

## Brocade Fabric OS

| Что вы хотите видеть | Откуда это берётся |
| --- | --- |
| Состояние коммутатора, прошивка, CPU и память | SNMP, с шаблоном производителя **Brocade Fabric OS (SAN switches)** |
| Статус коммутатора, его датчики и сменные блоки (FRU), строка за строкой | Таблицы шаблона `switch_status`, `sensors` и `frus` |
| Тип каждого порта Fibre Channel, причина, по которой отключённый порт отключён, и его ошибки, отброшенные кадры и ожидания кредита в секунду | SW-MIB и FCMGMT-MIB, на странице **Интерфейсы** устройства |
| Принимаемая и передаваемая мощность, температура, напряжение и ток смещения каждого оптического модуля | FA-EXT-MIB, на карточке **Трансиверы** |
| Отказ межкоммутаторного канала, разделённая или перенастроенная фабрика, изменение зонирования, предупреждение MAPS, заменённый FRU | Трапы SNMPv3 |

Каждый коммутатор и директор с Fabric OS сообщает идентификатор системного объекта в ветви `1.3.6.1.4.1.1588.2.1.1`, поэтому шаблон применяется ко всем ним и ни к чему другому от Brocade: коммутаторы VDX и SLX сохраняют свой шаблон.

### Настройка SNMP в Fabric OS

:::steps
1. Добавьте пользователя SNMPv3 с аутентификацией и шифрованием, SHA и AES: `snmpconfig --set snmpv3` спросит пользователя, его протоколы и парольные фразы.
2. Включите FA-MIB командой `snmpconfig --set mibCapability`. В ней 64-битные счётчики ошибок каждого порта и его оптика; без неё порт сообщает только ошибки CRC, ошибки кодирования, отброшенные кадры класса 3 и ожидания кредита, в виде 32-битных счётчиков.
3. В OneUptime добавьте коммутатор с его адресом управления и этим пользователем. Если **Auto-Apply Vendor Health Template** включено, первый опрос применит шаблон **Brocade Fabric OS (SAN switches)**; иначе примените его в **Vendor Health Template** на странице **Настройки** устройства.
:::

После этого страница **Интерфейсы** устройства помечает каждый порт Fibre Channel его типом, например E-Port или F-Port, и показывает, почему отключённый порт отключён, так же как `switchshow`: No light, No module, Disabled. Её карточка **Порты Fibre Channel** строит графики ошибок, отброшенных кадров и счётчиков кредита каждого порта в секунду.

Ошибки CRC, недопустимые слова передачи, сбои линии и потери синхронизации и сигнала порта — это его ошибки: **Ошибки интерфейса SNMP (в секунду)** оповещает о них, а рекомендуемые оповещения включают **Fibre Channel port errors** при более чем одной ошибке за десять секунд. Отброшенные кадры и ожидания кредита — не ошибки; оповещайте об одном из них через **Счётчик Fibre Channel SNMP (в секунду)**.

### Virtual Fabrics

Шасси с Virtual Fabrics отвечает за каждый логический коммутатор в отдельном контексте SNMPv3: `VF:` и идентификатор фабрики логического коммутатора. Добавьте по устройству на каждый логический коммутатор, все с адресом управления шасси, и задайте для каждого **Контекст SNMP v3** (`VF:128`, `VF:20`); устройство без контекста читает логический коммутатор по умолчанию.

### Трапы Brocade

Fabric OS отправляет трапы по SNMPv3. С помощью `snmpconfig --set snmpv3` добавьте зонд получателем трапов для пользователя, которым опрашивает OneUptime, на UDP-порт 162: зонд принимает трапы SNMPv3 от пользователей устройств, которые он опрашивает (см. [Трапы и informs SNMPv3](/docs/monitor/network-device-monitor#трапы-и-informs-snmpv3)), а трапы каждого логического коммутатора называют его контекст, поэтому срабатывают только на его устройстве. Обновление Fabric OS может снова отключить отдельные трапы: после обновления проверьте их командой `snmpconfig --show mibCapability`, а включите трап обратно командой `snmpconfig --enable mibCapability -mib_name SW-MIB -trap_name swFCPortScn`.

Рекомендуемые оповещения для коммутатора Brocade включают по одному на каждое важное событие фабрики: **Inter-switch link down** (E-Port уходит в офлайн), **Fabric segmented**, **Fabric reconfigured**, **Zone configuration changed**, **MAPS alert** и **Field-replaceable unit changed**.

## Cisco MDS 9000

| Что вы хотите видеть | Откуда это берётся |
| --- | --- |
| CPU и память | SNMP, с шаблоном производителя **Cisco MDS 9000 (SAN switches)** |
| Блоки питания, модули и вентиляторные лотки, строка за строкой | Таблицы шаблона `power_supplies`, `modules` и `fan_trays` |
| Каждый VSAN и его состояние | Таблица шаблона `vsans` |
| Тип каждого интерфейса fc, причина, по которой отключённый интерфейс отключён, и его ошибки, отброшенные кадры, потери кредита и ожидания кредита в секунду | CISCO-FC-FE-MIB, на странице **Интерфейсы** устройства |
| Показания и пороги тревоги каждого оптического модуля | CISCO-ENTITY-SENSOR-MIB, на карточке **Трансиверы** |
| Тревоги port-monitor, отказы каналов, изменения зон, VSAN, фабрики и FRU | Трапы |

MDS делит номер предприятия Cisco со всеми остальными устройствами Cisco, поэтому OneUptime распознаёт его по модели или по системному описанию, которое начинается с `Cisco NX-OS(tm) m9`: коммутаторы IOS, IOS-XE и Nexus сохраняют свой шаблон Cisco.

### Настройка SNMP в NX-OS

:::steps
1. Добавьте пользователя SNMPv3 только для чтения: `snmp-server user oneuptime network-operator auth sha <auth-passphrase> priv aes-128 <priv-passphrase>`. Роль `network-operator` читает и ничего не может изменить.
2. Отправляйте трапы на зонд от имени этого пользователя: `snmp-server host <probe-address> traps version 3 priv oneuptime`.
3. Включите трапы, которые по умолчанию выключены: `snmp-server enable traps zone`, `snmp-server enable traps vsan`, `snmp-server enable traps fcdomain`, `snmp-server enable traps fspf` и, для оптики, `snmp-server enable traps link cisco-xcvr-mon-status-chg`.
4. В OneUptime добавьте коммутатор с его адресом управления и этим пользователем: шаблон **Cisco MDS 9000 (SAN switches)** применяется так же.
:::

Рекомендуемые оповещения для MDS включают **Credit loss (slow drain)** и **Timeout discards (slow drain)**, по одному на интерфейс: хост или массив, который перестаёт возвращать буферный кредит, замедляет каждый поток за собой, и эти счётчики показывают это первыми.

### Тревоги port-monitor

Политика port-monitor на MDS поднимает тревогу RMON, когда счётчик порта пересекает порог. Рекомендуемые оповещения включают **Port monitor alarm**, оповещение которого называет счётчик и интерфейс, например "Port monitor: Credit loss rising on fc1/5". Политика, которая следит за slow drain:

```text
port-monitor name slow-drain
  logical-type edge
  counter credit-loss-reco poll-interval 1 delta rising-threshold 1 event 4 falling-threshold 0 event 4
  counter timeout-discards poll-interval 60 delta rising-threshold 200 event 4 falling-threshold 10 event 4
port-monitor activate slow-drain
```

## Устранение неполадок

:::details У таблицы IPsec Tunnels нет статуса
Для статуса туннелей нужна SFOS v20 или новее. Проверьте также, что представление SNMP для ваших учётных данных включает enterprise-дерево Sophos (`1.3.6.1.4.1.2604`): ограниченный пользователь v3 часто видит только системную группу и IF-MIB.
:::

:::details Syslog от межсетевого экрана не приходит
Зонд слушает syslog на порту 5140, по UDP и TCP, если только он не запущен с `PROBE_SYSLOG_RECEIVER_ENABLED=false`: опубликуйте этот порт или ваш `PROBE_SYSLOG_RECEIVER_PORT`, если зонд работает в Docker. Сообщения сопоставляются с устройством по адресу отправителя, поэтому имя хоста межсетевого экрана в OneUptime или один из его **Другие адреса** должны совпадать с адресом, с которого он отправляет syslog; до тех пор они перечислены на странице **События** сети как **Ещё не устройство**.
:::

:::details Коммутатор Fabric Engine получил шаблон EXOS
Шаблон выбирается по системному описанию коммутатора. Проверьте, что обзор устройства показывает описание, в котором упоминается Fabric Engine (например, `7520-48Y-8C-FabricEngine (9.0.4.0)`); если да, удалите OID и таблицы EXOS и примените **Extreme Networks Fabric Engine / VOSS** из **Vendor Health Template**.
:::

:::details Точки доступа Cambium сообщают 0 клиентов
Для общего числа клиентов нужна прошивка 6.5.3 или новее. На более старой прошивке радиомодули по-прежнему сообщают свой канал, мощность и уровень шума.
:::
