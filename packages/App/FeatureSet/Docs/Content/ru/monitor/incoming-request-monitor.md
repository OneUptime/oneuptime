# Монитор входящих запросов

Монитор входящих запросов даёт вам URL, на который другие системы отправляют HTTP-запросы. OneUptime оценивает каждый запрос по вашим критериям и может менять статус монитора, объявлять инциденты и вызывать вашу дежурную смену.

Он закрывает две разные задачи:

- **Мониторинг по heartbeat** — cron-задача, воркер или устройство обращается к URL по расписанию, и OneUptime открывает инцидент, когда сигналы перестают приходить.
- **Приём оповещений от другой системы** — Prometheus Alertmanager, Grafana или что угодно, что умеет отправлять JSON методом POST, шлёт оповещения, а OneUptime превращает каждое из них в инцидент с эскалацией на дежурных и автоматическим закрытием при восстановлении.

Обе задачи используют один и тот же тип монитора. Различают их критерии, которые вы настраиваете.

## Обзор

Мониторы входящих запросов предоставляют уникальный URL, к которому обращаются ваши сервисы. Это позволяет вам:

- Отслеживать cron-задачи и запланированные задания
- Проверять, что фоновые воркеры работают
- Отслеживать сервисы за файрволом, недоступные снаружи
- Принимать оповещения от Prometheus Alertmanager, Grafana и других систем оповещения
- Отслеживать heartbeat-сигналы от любой системы, умеющей HTTP

## Создание монитора входящих запросов

1. Перейдите в раздел **Мониторы** в панели OneUptime
2. Нажмите **Создать монитор**
3. Выберите **Входящий запрос** в качестве типа монитора
4. Для этого монитора будут созданы **Секретный ключ** и URL
5. Откройте монитор и нажмите **Documentation** в левом меню, чтобы скопировать URL
6. Настройте свой сервис на отправку запросов по этому URL
7. Настройте критерии мониторинга, как описано ниже

## URL запроса

У вашего монитора есть уникальный URL в формате:

```
https://oneuptime.com/heartbeat/YOUR_SECRET_KEY
```

Замените `https://oneuptime.com` на URL вашего экземпляра OneUptime, если вы разворачиваете его самостоятельно.

Отправляйте на этот URL запросы **GET** или **POST**. HEAD принимается и обрабатывается как GET. Остальные методы возвращают 404. Секретный ключ в пути — единственные учётные данные, никакие заголовки или токены не нужны.

> **Warning:** Любой, кто знает этот URL, может пометить монитор как здоровый, поэтому относитесь к нему как к секрету. Каждый отправленный заголовок сохраняется на мониторе и виден всем, кто может его прочитать, — не отправляйте на эту конечную точку API-ключи или токены в заголовках.

OneUptime сразу отвечает пустым `200` и обрабатывает запрос в очереди. Этот ответ пишется до какой-либо проверки, поэтому `200` **не** является подтверждением того, что запрос принят: неверный секретный ключ, удалённый монитор и отключённый монитор тоже возвращают `200`. Чтобы убедиться, что запросы доходят, смотрите таймлайн самого монитора.

### Отправка тела запроса

Если вы хотите обращаться к полям внутри тела — `{{requestBody.status}}` в заголовке инцидента, JSON-путь в группировке инцидентов или критерий JavaScript Expression — отправляйте `Content-Type: application/json`; именно этот формат предполагается по всей документации. Тело `application/x-www-form-urlencoded` тоже разбирается, но только в плоские поля верхнего уровня. Любой другой content type (или его отсутствие) не разбирается, и все ссылки на `requestBody` не разрешаются ни во что.

Принимаются тела размером до 50 МБ. Не сжимайте тело с `Content-Encoding: gzip`; оно сохраняется без разбора, и пути внутрь него не будут разрешены.

### Отправка heartbeat

#### С помощью curl

```bash
# Simple GET request
curl https://oneuptime.com/heartbeat/YOUR_SECRET_KEY

# POST request with custom body
curl -X POST https://oneuptime.com/heartbeat/YOUR_SECRET_KEY \
  -H "Content-Type: application/json" \
  -d '{"status": "healthy", "version": "1.2.3"}'
```

#### Из cron-задачи

```bash
# Add to crontab to send heartbeat every 5 minutes
*/5 * * * * curl -s https://oneuptime.com/heartbeat/YOUR_SECRET_KEY > /dev/null
```

#### Из кода приложения

```javascript
// Node.js example
const https = require("https");
https.get("https://oneuptime.com/heartbeat/YOUR_SECRET_KEY");
```

```python
# Python example
import requests
requests.get('https://oneuptime.com/heartbeat/YOUR_SECRET_KEY')
```

## Критерии мониторинга

Вы можете настроить критерии, определяющие, когда сервис считается доступным, деградировавшим или недоступным. У каждого фильтра критерия есть **Filter Type** (на что смотреть), **Filter Condition** (как сравнивать) и **Value**.

### Доступные Filter Type

| Filter Type           | Что проверяет                                        | Примечания                                                                             |
| --------------------- | ---------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Incoming Request      | Был ли получен запрос в течение временного окна      | Единственная проверка, которая может сработать, когда ничего не приходит               |
| Request Body          | Тело запроса                                         | Совпадение по подстроке. Тела-объекты сравниваются как компактный JSON                 |
| Request Header        | Имена заголовков запроса                             | Точное совпадение с именем заголовка в нижнем регистре                                 |
| Request Header Value  | Значения заголовков запроса                          | Точное совпадение со значением заголовка в нижнем регистре                             |
| JavaScript Expression | Любое выражение над `requestBody` и `requestHeaders` | Самый гибкий вариант — см. [Выражения JavaScript](/docs/monitor/javascript-expression) |

### Filter Condition

У каждого Filter Type свой набор условий.

Для **Incoming Request** (приведены с орфографией панели управления):

- **Recieved In Minutes** — запрос был получен в течение указанного числа минут
- **Not Recieved In Minutes** — запрос не был получен в течение указанного числа минут

Для **Request Body**, **Request Header** и **Request Header Value**: **Contains** и **Not Contains**.

Для **JavaScript Expression**: **Evaluates To True**.

> **Note:** Имена и значения заголовков перед сравнением приводятся к нижнему регистру, и сравнение идёт с именем или значением целиком, а не с подстрокой. Пишите `content-type`, а не `Content-Type`, и `application/json`, а не `application/JSON`. Настоящее сравнение по подстроке делает только **Request Body**.

Тела-объекты сравниваются как компактный JSON без пробелов, поэтому фильтр **Request Body** / **Contains** нужно писать как `"status":"firing"` — скопированное из отформатированной нагрузки `"status": "firing"` не совпадёт никогда.

### Примеры критериев

#### Пометить как недоступный, если heartbeat не приходил 10 минут

- **Filter Type**: Incoming Request
- **Filter Condition**: Not Recieved In Minutes
- **Value**: 10

#### Пометить как деградировавший по содержимому тела запроса

- **Filter Type**: Request Body
- **Filter Condition**: Contains
- **Value**: `"status":"degraded"`

> **Warning:** Монитор переоценивается в фоне, только если хотя бы один из его критериев проверяет **Incoming Request**. Монитор, критерии которого проверяют лишь Request Body, Request Header или JavaScript Expression, оценивается при поступлении запроса и больше никогда — значит, сам по себе он никогда не станет недоступным. Если вам нужна тревога по пропавшему heartbeat, нужен критерий **Incoming Request**.

Учтите также: монитор, который ни разу не получал запросов, рассматривается так, будто его момент создания был последним запросом. Критерий «Not Recieved In Minutes: 10» на только что созданном мониторе сработает через 10 минут после создания, даже если отправитель так и не был подключён.

## Приём оповещений от другой системы

Alertmanager, Grafana и подобные инструменты отправляют методом POST JSON-документ, описывающий одно или несколько оповещений. По умолчанию критерий открывает **один** инцидент, поэтому нагрузка с пятью оповещениями дала бы один инцидент. Группировка инцидентов меняет это: она извлекает значение из нагрузки и открывает **отдельный инцидент для каждого уникального значения**, причём все они могут быть открыты одновременно.

### Включение группировки инцидентов

Откройте критерий, разверните **Settings** и включите **Group incidents and alerts by a payload field**. Появятся четыре поля:

| Поле                               | Пример                                   | Что делает                                                                                   |
| ---------------------------------- | ---------------------------------------- | -------------------------------------------------------------------------------------------- |
| Open a separate incident for each… | `requestBody.alerts[*].labels.alertname` | Путь, чьи уникальные значения разделяют инциденты                                            |
| Field that signals recovery        | `requestBody.alerts[*].status`           | Путь, по которому определяется, что оповещение восстановилось                                |
| Value that means recovered         | `resolved`                               | Точное значение, означающее восстановление                                                   |
| Max incidents per request          | `100` (по умолчанию)                     | Предохранитель, чтобы поле высокой кардинальности не открыло неограниченное число инцидентов |

### Синтаксис путей

Пути должны начинаться с буквального префикса `requestBody.`. Путь без него — `alerts[*].labels.alertname` — не совпадает ни с чем, и делает это молча. Обёртка `{{ }}` необязательна: `requestBody.status` и `{{requestBody.status}}` ведут себя одинаково.

- `[*]` разворачивается по массиву — по одному инциденту на каждое **уникальное** значение. Два элемента с одинаковым значением схлопываются в один инцидент, а его состояние firing/resolved берётся из **первого** совпавшего элемента. **Подстановочным знаком является только первый `[*]` в пути**; `requestBody.groups[*].alerts[*].name` не совпадает ни с чем.
- `[0]` и `[last]` выбирают один элемент и могут идти после `[*]`.
- Значения-объекты и массивы, пустые строки и null пропускаются. `0` и `false` — допустимые ключи.

### Закрытие управляется событиями

Вебхук описывает только то, что содержится в этой нагрузке, поэтому OneUptime никогда не закрывает инцидент из-за того, что его ключ перестал появляться. Инцидент закрывается только тогда, когда нагрузка явно сообщает, что этот ключ восстановился. Должны выполняться два условия сразу:

1. **Field that signals recovery** и **Value that means recovered** заданы и совпадают с нагрузкой. Сравнение точное и учитывает регистр — `Resolved` не совпадает с `resolved`.
2. У инцидента критерия включено **Auto Resolve Incident** в разделе **Advanced Options** формы инцидента. Без этого подходящие события восстановления игнорируются, и инциденты остаются открытыми. (То же относится к оповещениям и **Auto Resolve Alert**.)

**Max incidents per request** ограничивает извлечение, а не только создание. Ключи за пределами лимита невидимы и для восстановления, поэтому в нагрузке с большим числом уникальных ключей, чем лимит, оповещение со статусом `resolved` за пределами лимита не закроет свой инцидент.

> **Warning:** Если **Field that signals recovery** содержит `[*]`, а **Open a separate incident for each…** — нет, не закроется ничего и никогда. Используйте `[*]` либо в обоих полях, либо ни в одном. Путь восстановления без `[*]` вычисляется по всей нагрузке, поэтому `status: resolved` на уровне нагрузки закрывает каждый её ключ — включая оповещения, чей собственный статус всё ещё firing.

### Именование инцидентов

Ключ группировки доступен шаблонам инцидентов и оповещений как переменная, названная по **последнему сегменту пути**:

| Путь                                     | Переменная        |
| ---------------------------------------- | ----------------- |
| `requestBody.alerts[*].labels.alertname` | `{{alertname}}`   |
| `requestBody.alerts[*].fingerprint`      | `{{fingerprint}}` |
| `requestBody.commonLabels.severity`      | `{{severity}}`    |

Полная нагрузка доступна рядом с ней, поэтому работают и заголовок инцидента `{{alertname}}`, и описание со ссылкой на `{{requestBody.commonAnnotations.summary}}`. См. [Динамические шаблоны инцидентов и оповещений](/docs/monitor/incident-alert-templating).

> **Warning:** Имя переменной входит в идентичность, по которой OneUptime сопоставляет событие восстановления с открытым инцидентом. Если сменить путь группировки на путь с другим последним сегментом, все инциденты, открытые по старому пути, осиротеют — их больше нельзя закрыть автоматически, придётся закрывать вручную.

Обратите внимание: `[*]` работает **только** в двух полях пути группировки. В остальных местах он не разрешается, а неразрешённый плейсхолдер выводится **дословно**, а не очищается: заголовок `{{requestBody.alerts[*].labels.alertname}}` отобразится вместе с фигурными скобками. Заголовок `{{requestBody.alerts[0].annotations.summary}}` разрешается, но всегда читает первое оповещение в нагрузке, а не то, ради которого был открыт этот инцидент. Предпочитайте переменную группировки вместе с общими полями нагрузки `commonAnnotations`.

## Лучшие практики

1. **Подбирайте временное окно разумно** — если cron-задача выполняется каждые 5 минут, поставьте порог «Not Recieved In Minutes» в 10–15 минут, чтобы допускать редкие задержки
2. **Передавайте осмысленные данные** — отправляйте информацию о состоянии в теле запроса, чтобы можно было настроить детальные критерии
3. **Используйте POST с `Content-Type: application/json`** — всё, что читает внутри тела, зависит от этого
4. **Не смешивайте две задачи на одном мониторе** — у монитора, принимающего событийные оповещения, нет регулярного ритма, поэтому критерий «Not Recieved In Minutes» на нём будет «дребезжать». Для «выключателя мёртвой руки» используйте отдельный монитор
5. **Следите за самим монитором** — убедитесь, что сервис, отправляющий запросы, корректно обрабатывает ошибки, чтобы неудачные запросы не остались незамеченными
