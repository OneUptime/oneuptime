# Агенты runbook-ов

**Агент runbook-ов**, который в панели называется **Runner**, — это небольшой самостоятельно размещаемый процесс, выполняющий шаги JavaScript, Bash, SSH и kubectl ваших runbook-ов **в вашей собственной инфраструктуре**. OneUptime Worker никогда не выполняет ваши скрипты: он ставит их в очередь, а Runner, выбранный автором шага, забирает каждое задание, выполняет его и отправляет результат обратно. Эта страница для тех, кто устанавливает и эксплуатирует Runner-ы. Шаг, который не выбирает Runner, выполняется на [Runner-е проекта по умолчанию](#runner-проекта-по-умолчанию), если вы его задали; иначе шаг JavaScript выполняется на [глобальном Runner-е](#глобальные-runner-ы) — одном из тех, что OneUptime запускает для всех проектов.

- [Установка Runner-а](#установка-runner-а): От панели до подключённого контейнера за пять шагов.
- [Привязка шага к Runner-у](#привязка-шага-к-runner-у): Привяжите шаг к Runner-у, который должен его выполнять.
- [Runner проекта по умолчанию](#runner-проекта-по-умолчанию): Runner, на котором выполняется шаг, не выбравший ни одного.

## Как это работает

```mermaid title="Что передаётся по сети между Runner-ом и OneUptime"
flowchart TB
    subgraph cloud["OneUptime"]
        direction LR
        worker["Worker ставит шаг в очередь"]
        ingest["API Runner-а"]
    end
    subgraph yours["Ваша инфраструктура"]
        direction LR
        runner["Контейнер Runner"]
        targets["Хосты, кластеры, внутренние сервисы"]
    end
    worker --> ingest
    runner -->|"Исходящий HTTPS, ID и ключ Runner-а"| ingest
    ingest -->|"Забранное задание с его секретами"| runner
    runner -->|"Скрипт, SSH или API Kubernetes"| targets
```

1. Вы создаёте Runner в OneUptime. OneUptime генерирует для него ID и секретный ключ.
2. Вы запускаете контейнер Runner на хосте в своей инфраструктуре с этим ID, этим ключом и URL вашего OneUptime.
3. Runner запрашивает у OneUptime работу каждые 5 секунд и каждые 60 секунд сообщает, что он жив.
4. Когда вы пишете шаг JavaScript, Bash, SSH или kubectl, вы выбираете Runner из выпадающего списка в **Дополнительные поля** шага. Шаг привязывается к этому Runner-у. Шаг, который не выбирает ни одного, выполняется на Runner-е проекта по умолчанию, если вы его задали, а иначе шаг JavaScript выполняется на **Глобальный Runner**.
5. Когда шаг выполняется, Worker ставит в очередь задание с `targetAgentId`, равным этому Runner-у. Забрать его может только этот Runner.
6. Runner выполняет задание локально — `bash -c <script>` для Bash и kubectl, песочница `isolated-vm` для JavaScript, SSH-соединение, которое выполняет скрипт через bash на машине, — сохраняет результат, скрывает в нём секреты шага и отправляет его обратно. Worker продолжает runbook с этим результатом.

Runner-у нужен только **исходящий HTTPS** к вашему экземпляру OneUptime. Он не принимает входящих подключений.

Runner хранит только свой ID и ключ. Всё остальное он получает вместе с заданием, которое забирает: скрипт с подставленными [переменными runbook-а](/docs/runbooks/variables), которые в нём названы, а также ключ или пароль шага SSH или kubeconfig шага kubectl. Секрет он получает, только если этот секрет ему разрешён. Поэтому любой, у кого есть ключ Runner-а, может действовать как этот Runner: обращайтесь с ключом так же, как с секретами, которые ему доступны.

## Почему скрипты выполняются на Runner-е

У выполнения скриптов на OneUptime Worker было две проблемы:

- **Граница доверия.** Любой, кто мог написать runbook, мог выполнить код на Worker с доступом ко всему, до чего Worker мог дотянуться.
- **Досягаемость.** Большинство полезных шагов действуют на _вашу_ инфраструктуру («перезапусти этот сервис», «найди запись в нашей внутренней базе данных»), а не на инфраструктуру OneUptime.

С Runner-ами эти шаги выполняются на хосте, которым вы управляете, и вы решаете, что этому хосту разрешено. Шаги HTTP-запросов и AI по-прежнему выполняются на Worker, потому что им ничего не нужно из вашей сети.

## Глобальные Runner-ы

Глобальные Runner-ы — это Runner-ы, которые OneUptime запускает для всех проектов. Шаг JavaScript, который не выбирает собственный Runner, выполняется на одном из них, если у проекта нет [Runner-а по умолчанию](#runner-проекта-по-умолчанию), поэтому его можно написать до того, как вы что-либо установите. **Сборники инструкций → Агенты runbook-ов** показывает их в разделе **Глобальные Runner-ы**, над вашими собственными Runner-ами, а выпадающий список **Runner** шага JavaScript предлагает **Глобальный Runner** первым или сразу после Runner-а проекта по умолчанию. Выпадающий список шага Bash, SSH или kubectl показывает его последним, серым, с надписью **Выполняет только шаги JavaScript.** Такие шаги выполняются на вашем собственном Runner-е, внутри вашей сети, и никогда на Runner-е, общем для всех проектов.

| | Глобальный Runner | Ваш собственный Runner |
| --- | --- | --- |
| Шаги, которые он выполняет | JavaScript | JavaScript, Bash, SSH и kubectl |
| Куда может обращаться шаг | Публичные адреса в интернете | Туда, куда может обращаться его хост |
| Самое долгое выполнение шага | 5 минут | 1 час |
| Секретные переменные | Те, которые вы разрешили глобальным Runner-ам | Те, в которых он указан |

Глобальный Runner выполняет шаги многих проектов, поэтому каждый шаг отделён от всех остальных:

- Каждый шаг выполняется в собственной песочнице `isolated-vm`, созданной для этого шага и уничтожаемой после него: ни файлов, ни процессов, ни переменных окружения, и ничего не сохраняется от одного шага к следующему.
- Его HTTP-запросы обращаются только к публичным адресам в интернете, никогда к частному, loopback- или link-local-адресу либо к конечной точке облачных метаданных, поэтому глобальный Runner никогда не достаёт до вашей сети.
- Он получает секретную переменную, только когда у неё включён переключатель **Глобальные Runner-ы могут его использовать**, и только для шага из собственного проекта переменной.
- Проект одновременно выполняет на глобальных Runner-ах не более трёх шагов, поэтому ни один проект не занимает их целиком.

Выберите один из собственных Runner-ов для шага, которому нужно обращаться к вашей сети, или чтобы шаг оставался на хостах под вашим контролем. Чтобы каждый шаг выполнялся на ваших собственных Runner-ах, выключите **Использовать глобальные Runner-ы** внизу страницы **Сборники инструкций → Агенты runbook-ов**. Шаг JavaScript, который не выбирает Runner, тогда выполняется на Runner-е проекта по умолчанию или, если он не задан, завершается сбоем с объяснением, пока не выберет один из ваших; шаг, выбравший один из ваших Runner-ов, сохраняет его в любом случае. Репозиторий кода, который не выбрал Runner в своих настройках в разделе «Код», тоже работает на глобальном Runner, а пока переключатель выключен, ему нужен один из ваших; см. [Код](/docs/ai/ai-agent#выбор-runner-для-репозитория).

### Откуда берутся глобальные Runner-ы

В OneUptime Cloud их запускает OneUptime. Самостоятельно размещённая установка по умолчанию запускает собственный, так же как запускает собственные глобальные зонды: сервис `global-runner` в Docker Compose и развёртывание `globalRunner` в Helm-чарте. У него собственный ключ, `GLOBAL_RUNNER_KEY`, и больше ничего от сервера.

Главный администратор может добавить ещё, чтобы выполнять шаги с других хостов: в панели администратора откройте **Настройки**, затем **Глобальные Runner-ы**, создайте Runner и выполните команду, которую даёт его **Показать ID и ключ**, на хосте с доступом в интернет.

Чтобы выключить встроенный, задайте `GLOBAL_RUNNER_REPLICAS=0` в `config.env` Docker Compose или `globalRunner.enabled` равным `false` в Helm-чарте. Совсем без глобального Runner-а **Сборники инструкций → Агенты runbook-ов** показывает только ваши собственные Runner-ы, и каждый шаг JavaScript выбирает один из них.

## Прежде чем начать

- **Хост с Docker** в вашей инфраструктуре, который может обращаться к URL вашего OneUptime по HTTPS и к системам, с которыми работают ваши шаги.
- **Роль, которая создаёт Runner-ы.** Создать его могут Project Owner, Project Admin, Project Member и Runbook Admin. Видеть ключ Runner-а, который содержится в команде установки, могут только Project Owner, Project Admin или Runbook Admin.

## Установка Runner-а

### 1. Создайте запись агента

Перейдите в **Сборники инструкций → Агенты runbook-ов** и создайте нового агента. Нажмите **Создать: Runner** и заполните его поля — все на одной странице:

| Поле | Где | Примечания |
| --- | --- | --- |
| **Имя** | На странице | Понятное имя, обычно где он работает и до чего может достучаться, например `prod-eu-west-1`. Именно его вы выбираете при написании шага. |
| **Описание** | На странице | Необязательно. Предложение о том, к чему этот хост имеет доступ. |
| **Выполняет сценарии** | В **Дополнительные поля** | Включено по умолчанию. Позволяет этому Runner-у забирать шаги runbook-ов. |
| **Метки** | В **Дополнительные поля** | Необязательно. |

Runner подхватывает изменение своих возможностей при следующем heartbeat; перезапускать его не нужно. ИИ — не возможность Runner. Репозиторий кода выбирает в своих настройках в разделе «Код» Runner, на котором в нём работает ИИ, а на странице Runner перечислены репозитории, которые его выбрали. Правило ИИ выбирает Runner, на котором OneUptime AI выполняет свои команды: именно выбор Runner там позволяет командам OneUptime AI выполняться на нём.

### 2. Скопируйте команду установки

Нажмите **Показать инструкции по настройке** в строке Runner-а. Диалог **Настройка агента сценария** показывает команду `docker run`, которая уже содержит ID и ключ этого Runner-а. Та же команда есть на собственной странице Runner-а в разделе **Инструкции по настройке**.

Прочитать ключ могут только Project Owner, Project Admin или Runbook Admin. Все остальные вместо команды видят «У вас нет прав на просмотр ключа этого агента сценария».

### 3. Запустите её на хосте в своей инфраструктуре

Запустите команду на хосте в своей среде, который может:

- обращаться к вашему экземпляру OneUptime по HTTPS и
- делать то, что нужно вашим шагам, например подключаться к другим хостам по SSH, вызывать API-сервер кластера или работать с базой данных.

```bash
docker run --name oneuptime-runner --restart unless-stopped \
  -e ONEUPTIME_RUNNER_ID=<runner-id> \
  -e ONEUPTIME_RUNNER_KEY=<runner-key> \
  -e ONEUPTIME_URL=https://oneuptime.yourdomain.com \
  -d oneuptime/runner:release
```

### 4. Убедитесь, что агент подключён

Вернитесь в **Сборники инструкций → Агенты runbook-ов**. В течение минуты после запуска контейнера **Статус** Runner-а должен показать **Подключено** со свежей **Последняя активность**. На собственной странице Runner-а карточка **Статус агента сценария** показывает его **Версия агента сценария** и **Хост**. Если он продолжает показывать **Никогда не подключался** или **Отключено**, см. [Устранение неполадок](#устранение-неполадок).

### 5. Обновляйте агента

Когда агент работает на более старой версии, чем ваш OneUptime, рядом с его **Версия агента сценария** на его странице появляется предупреждающий значок. Выберите его, чтобы узнать, как обновиться: скачайте новый образ, удалите контейнер и снова выполните команду установки из шага 2. Агент, установленный чартом агента Kubernetes, вместо этого обновляется вместе с чартом.

```bash
docker pull oneuptime/runner:release
docker rm -f oneuptime-runner
```

## Привязка шага к Runner-у

:::steps
### Добавьте шаг, который выполняется на Runner-е

Добавьте шаг JavaScript, Bash, SSH или kubectl в **Шаги** вашего runbook-а.

### Выберите Runner

Откройте **Дополнительные поля** шага: его выпадающий список **Runner** показывает все Runner-ы проекта и то, подключены ли они, а свёрнутая строка называет Runner, на котором выполняется шаг. Если в проекте их ещё нет, шаг сообщает об этом и указывает на **Runbooks › Runners**. Первый вариант — то, на чём выполняется шаг, не выбравший Runner: [Runner проекта по умолчанию](#runner-проекта-по-умолчанию) с пометкой **По умолчанию для проекта** или иначе, для шага JavaScript, **Глобальный Runner**.

### Сохраните шаги

Нажмите **Save Steps**. Когда выполнение доходит до шага, Worker ставит задание в очередь для ID этого Runner-а, и забрать его может только этот Runner. Шаг на **Глобальный Runner** ждёт глобальный Runner, который освободится.
:::

Bash выполняется через `bash -c`. JavaScript выполняется в песочнице `isolated-vm` на Runner-е без доступа к файловой системе и процессам; он может вызывать публичные HTTP API через `axios`, но не адреса в частной сети. Шаг SSH или kubectl входит с секретной [переменной runbook-а](/docs/runbooks/variables), в которой Runner шага должен быть указан в **Ваши Runner-ы, которые могут его использовать**.

Нужно больше одного Runner-а? Создайте их и привяжите каждый шаг к нужному. Для отказоустойчивости запустите дополнительный Runner и распределите шаги между ними или держите резервный runbook, шаги которого указывают на другой Runner.

## Runner проекта по умолчанию

Проект может сделать один из своих Runner-ов Runner-ом по умолчанию — так же, как делает одну конфигурацию Twilio конфигурацией по умолчанию. Тогда на нём выполняется каждый шаг runbook-а, который не выбирает Runner: шаги Bash, SSH и kubectl, а также шаги JavaScript, которые иначе выполнялись бы на глобальном Runner-е.

Чтобы сделать Runner Runner-ом по умолчанию, откройте **Сборники инструкций → Агенты runbook-ов**, откройте меню **⋯** в строке Runner-а, нажмите **Установить по умолчанию для проекта** и подтвердите кнопкой **Сделать по умолчанию для проекта**. Или откройте Runner и на его карточке **По умолчанию для проекта** включите **Использовать по умолчанию для проекта**. Список помечает Runner по умолчанию пометкой **По умолчанию для проекта** рядом с именем, как и выпадающий список **Runner** шага — у первого варианта. У проекта один Runner по умолчанию: если сделать Runner-ом по умолчанию другой, он его заменит. **Больше не использовать по умолчанию для проекта** в том же меню или переключатель на странице Runner-а прекращает его использование.

Где выполняется шаг, который не выбирает Runner:

| Проект | Шаг JavaScript | Шаг Bash, SSH или kubectl |
| --- | --- | --- |
| Имеет Runner по умолчанию | Runner по умолчанию | Runner по умолчанию |
| Не имеет его и использует глобальные Runner-ы | Глобальный Runner | Нигде: шаг завершается сбоем, сообщая, что у него нет Runner-а |
| Не имеет его и не использует глобальные Runner-ы | Нигде: шаг завершается сбоем с объяснением | Нигде: шаг завершается сбоем, сообщая, что у него нет Runner-а |

Шаг, выбравший Runner, сохраняет его, каким бы ни был Runner по умолчанию, а шаг JavaScript по-прежнему может сам выбрать **Глобальный Runner**. Задание Runner-а по умолчанию не меняет ни одного сохранённого шага.

Runner по умолчанию — это один из собственных Runner-ов проекта, выполняющий шаги runbook-ов: не глобальный Runner, не Runner внутри кластера, установленный агентом Kubernetes, и не Runner с выключенным **Выполняет сценарии**. Пока Runner является Runner-ом по умолчанию, его **Выполняет сценарии** остаётся включённым. Когда Runner по умолчанию не подключён, выпадающий список шага сообщает об этом, а шаг на нём ждёт его, как любой Runner, пока не пройдёт его claim timeout.

Runner по умолчанию используют только шаги runbook-ов. Репозиторий кода выбирает свой Runner в своих настройках в разделе «Код», а правило ИИ выбирает свой.

## Заметки по эксплуатации

### Тайм-ауты

К каждому шагу, выполняемому на Runner-е, применяются два тайм-аута:

| Тайм-аут | По умолчанию | Что контролирует |
| --- | --- | --- |
| **Тайм-аут получения** | 2 минуты | Сколько Worker ждёт, пока выбранный Runner заберёт задание. Если Runner не заберёт его вовремя, шаг завершается сбоем по тайм-ауту, а runbook продолжается (или останавливается, в зависимости от **Продолжить при сбое**). |
| **Тайм-аут выполнения** | 30 секунд | Сколько Runner даёт шагу выполняться, прежде чем остановить его. Bash получает `SIGKILL`; песочница JavaScript уничтожается. |

Оба настраиваются для каждого шага. Откройте **Runbooks › ваш runbook › Шаги**, разверните шаг и задайте **Тайм-аут выполнения** и **Тайм-аут получения** (в секундах) в его **Дополнительные поля**. Оставьте поле пустым, чтобы использовать значение по умолчанию. Каждый принимает от 1 секунды до 1 часа; значения вне этого диапазона ограничиваются при выполнении шага.

Общее окно ожидания Worker — `claim timeout + execution timeout + a few seconds`. Выбирайте значения, подходящие для шага.

Две вещи, о которых стоит помнить, снижая claim timeout:

- Runner запрашивает работу циклами опроса (`ONEUPTIME_RUNNER_POLL_INTERVAL_MS`, по умолчанию 5 секунд). Claim timeout короче одного цикла может истечь раньше, чем совершенно исправный Runner вообще увидит задание, и тогда шаг завершается сбоем с тем же сообщением, что и при Runner-е не в сети.
- Runner по умолчанию выполняет одно задание за раз (`ONEUPTIME_RUNNER_CONCURRENCY`). Пока его занимает долгий шаг, другие шаги, указывающие на тот же Runner, ждут до истечения своих claim timeout. Если вы увеличиваете execution timeout до минут, соответственно увеличьте claim timeout у шагов, использующих этот Runner, или дайте им другой Runner.

### Lease и heartbeat

```mermaid title="Задание между OneUptime и его Runner-ом"
sequenceDiagram
    participant O as OneUptime
    participant R as Runner
    O->>O: Поставить задание в очередь для этого Runner-а
    R->>O: Забрать следующее задание
    O-->>R: Задание с lease на 30 секунд
    loop Каждые 10 секунд, пока оно выполняется
        R->>O: Продлить lease
    end
    R->>O: Отправить результат
    O->>O: Записать вывод и продолжить выполнение
```

Забирая задание, Runner получает короткий lease (по умолчанию 30 секунд). Пока шаг выполняется, Runner продлевает lease каждые 10 секунд. Если Runner падает или теряет сеть посреди скрипта, lease истекает, и Worker помечает задание как `TimedOut`, а не ждёт вечно.

Подпроцессы Bash **не** отменяются автоматически, когда истекает lease (песочнице JavaScript тоже дают закончить, если она вообще заканчивает), но Worker перестаёт их ждать, а Runner не может отправить результат после того, как задание забрал кто-то другой. Пишите скрипты так, чтобы их можно было безопасно запустить повторно, если для вас важно ровно одно выполнение.

### Если OneUptime Worker перезапускается посреди шага

Выполнение runbook-а идёт на одном Worker от начала до конца, поэтому развёртывание или сбой могут прервать его, пока шаг выполняется. Что будет дальше, зависит от того, подхватят ли выполнение снова:

- **Оно возобновляется.** Worker, который его подхватывает, находит задание, уже созданное вашим шагом, и **снова подключается к нему**. Он ждёт это задание, а не отправляет вашему Runner-у ещё одну копию скрипта. Если Runner уже закончил, записанный результат используется как есть. Шаг отправляется на Runner не более одного раза за выполнение.
- **Оно не возобновляется.** Если выполнение так и не подхватят, очистка помечает его как `Failed`, когда оно выходит за окно claim и выполнения своего текущего шага, с сообщением, в котором назван шаг. Выполнение никогда не зависает в `Running`.

Единственное, чего это не может сказать, — как далеко зашёл скрипт до того, как Worker пропал. Шаг, который был в процессе выполнения, отмечается как неудавшийся с пометкой, что он мог выполниться частично: проверьте целевую систему, прежде чем запускать runbook снова.

### Нет агентов в сети

Если выбранный Runner не в сети, когда выполняется шаг, задание ждёт в `Pending`, пока не пройдёт claim timeout, а затем шаг завершается сбоем с «No runbook agent picked up this step before the wait window expired.» Страница **Агенты runbook-ов** — место, где проверяют покрытие перед тем, как запускать runbook по-настоящему. Шаг на глобальном Runner-е вместо этого завершается сбоем с «No global Runner picked up this step before the wait window expired.»

### Ограничение вывода

stdout и stderr вместе ограничены **50 КБ** на шаг. Более длинный вывод обрезается с пометкой. Если нужен полный лог, запишите его из скрипта в хранилище логов или объектное хранилище и выведите URL через `echo`.

### Отмена

Отмена выполнения runbook-а со страницы выполнения или через API сразу помечает все его задания в `Pending`, `Claimed` и `Running` как `Cancelled`. Runner, который уже выполняет скрипт, доводит работу до конца, но сервер не принимает результат, и ни один последующий шаг runbook-а не отправляется.

### Параллельность

Каждый Runner по умолчанию выполняет одно задание за раз. Чтобы разрешить больше, задайте `ONEUPTIME_RUNNER_CONCURRENCY` в контейнере, но помните, что Runner делит хост со всем остальным, что на нём работает.

## Переменные окружения

Runner читает их при запуске:

| Переменная | Обязательна | По умолчанию | Примечания |
| --- | --- | --- | --- |
| `ONEUPTIME_URL` | да | — | Базовый URL вашего экземпляра OneUptime, например `https://oneuptime.yourdomain.com`. |
| `ONEUPTIME_RUNNER_ID` | да | — | ID Runner-а из его команды установки. |
| `ONEUPTIME_RUNNER_KEY` | да | — | Секретный ключ Runner-а из его команды установки. |
| `ONEUPTIME_RUNNER_POLL_INTERVAL_MS` | нет | `5000` | Как часто Runner запрашивает новые задания. Значение меньше `1000` заменяется значением по умолчанию. |
| `ONEUPTIME_RUNNER_HEARTBEAT_INTERVAL_MS` | нет | `60000` | Как часто Runner сообщает, что он жив. Значение меньше `5000` заменяется значением по умолчанию. |
| `ONEUPTIME_RUNNER_JOB_HEARTBEAT_INTERVAL_MS` | нет | `10000` | Как часто Runner продлевает lease выполняющегося задания. Значение меньше `1000` заменяется значением по умолчанию. |
| `ONEUPTIME_RUNNER_CONCURRENCY` | нет | `1` | Максимум одновременных заданий на этом Runner-е. |
| `ONEUPTIME_RUNNER_ENABLE_RUNBOOKS` | нет | — | Задайте `false`, чтобы этот Runner перестал забирать шаги runbook-ов, что бы ни говорила панель. Эта переменная может только выключить возможность. |
| `ONEUPTIME_RUNNER_ENABLE_CODE_FIXES` | нет | — | Задайте `false`, чтобы этот Runner перестал забирать исправления кода от ИИ, даже для репозитория кода, который его выбрал. |
| `ONEUPTIME_RUNNER_ENABLE_AI_COMMANDS` | нет | — | Задайте `false`, чтобы этот Runner перестал выполнять команды устранения от ИИ, что бы ни говорила панель. |

## Смена ключа агента

Если ключ утёк, сбросьте его. Старый ключ сразу перестаёт работать.

:::steps
### Сбросьте ключ

Откройте Runner из **Сборники инструкций → Агенты runbook-ов**, нажмите **Сбросить ключ агента сценария** и подтвердите. Runner перестаёт подключаться, пока у него нет нового ключа.

### Запустите контейнер с новым ключом

Скопируйте новую команду из **Инструкции по настройке** Runner-а, удалите старый контейнер и выполните новую команду на том же хосте:

```bash
docker rm -f oneuptime-runner
```

### Убедитесь, что он снова подключился

В **Сборники инструкций → Агенты runbook-ов** **Статус** Runner-а в течение минуты вернётся к **Подключено**.
:::

## Разрешения

Управление агентами находится в существующей группе разрешений Runbooks:

- `CreateRunner`, `EditRunner`, `DeleteRunner`, `ReadRunner` — управление записями агентов.
- `RunbookAdmin`, `RunbookMember`, `RunbookViewer` (роли) — `RunbookAdmin` создаёт runbook-и, их правила и Runner-ы, на которых они выполняются, и запускает их. `RunbookMember` открывает runbook-и и их выполнения и запускает их — начинает выполнение, завершает или пропускает его шаги и отменяет его, — но не создаёт, не изменяет и не удаляет ни runbook-и, ни Runner-ы. `RunbookViewer` читает runbook-и и их выполнения и ничего не запускает. `RunbookAdmin` объединяет все перечисленные выше детальные разрешения.
- Глобальные Runner-ы не принадлежат ни одному проекту: добавляет, изменяет или удаляет их только главный администратор, в панели администратора. Их видит каждый, кто может читать Runner-ы проекта, а чтобы выключить **Использовать глобальные Runner-ы**, нужно разрешение на редактирование проекта.

Чтобы запустить runbook (и тем самым отправить его шаги Runner-ам), нужна роль, которая запускает runbook-и, — `ProjectOwner`, `ProjectAdmin`, `ProjectMember`, `RunbookAdmin` или `RunbookMember`, — либо `CreateRunbookExecution`; для завершения, пропуска или отмены выполнения подходит также `EditRunbookExecution`. Роль запускает только те runbook-и, до которых дотягивается её область.

Ключ Runner-а могут прочитать только Project Owner, Project Admin и Runbook Admin.

## API для агентов

Для любопытных: Runner использует эти конечные точки, смонтированные под `/runner-ingest`. Путь до объединения, `/runbook-agent-ingest`, по-прежнему обслуживается для агентов, которые ещё не развёрнуты заново, чтобы обновление сервера их не сломало. Аутентификация — по ID и ключу Runner-а в теле JSON (`agentId` и `agentKey`) или в заголовках `x-agent-id` и `x-agent-key`.

| Конечная точка | Назначение |
| --- | --- |
| `POST /heartbeat` | Сигнал жизни. Обновляет время последней активности Runner-а, версию и сведения о хосте и возвращает возможности, которые ему предоставил проект. |
| `POST /claim-next-job` | Атомарно забрать самое старое задание в `Pending`, адресованное ID этого Runner-а. Возвращает `{ job: null }`, когда делать нечего. Глобальный Runner вместо этого забирает самый старый шаг, ожидающий любой глобальный Runner. |
| `POST /job/:jobId/heartbeat` | Продлить lease задания. Возвращает 404, если lease истёк или задание завершено. |
| `POST /job/:jobId/result` | Отправить итоговый результат. Игнорируется, если lease уже перешёл дальше. |
| `POST /disconnect` | Отключиться при штатной остановке. |

Вызывать их вручную не придётся: это делает поставляемый Runner. Они описаны здесь, чтобы вы могли написать своего агента, если у вас есть ограничение, которому наш не подходит.

## Устранение неполадок

:::details Runner продолжает показывать Никогда не подключался или Отключено
- Проверьте логи контейнера командой `docker logs oneuptime-runner` на ошибки аутентификации или сети.
- Проверьте, что хост может достучаться до URL вашего OneUptime, например через `curl`.
- Проверьте, что ID и ключ скопированы без пробелов и что `ONEUPTIME_URL` — тот адрес, по которому вы открываете OneUptime.

**Никогда не подключался** означает, что Runner ни разу не выходил на связь. **Отключено** означает, что выходил, но не за последние 5 минут.
:::

:::details Шаги завершаются сбоем с «No runbook agent picked up this step before the wait window expired.»
Runner шага не забрал задание в пределах своего claim timeout. Проверьте, что Runner в состоянии **Подключено**, что для него включено **Выполняет сценарии** и что он не занят долгим шагом: он выполняет одно задание за раз, если вы не увеличили `ONEUPTIME_RUNNER_CONCURRENCY`. Claim timeout короче интервала опроса даёт сбой так же.
:::

:::details Шаги завершаются сбоем с «The runbook agent stopped responding while this step was running.»
Runner забрал задание, а затем перестал продлевать lease: он упал, перезапустился или потерял сеть. Убедитесь, что он в сети, а затем проверьте целевую систему, прежде чем запускать runbook снова.
:::

:::details Runner пишет в лог «No capability is enabled»
Для этого Runner-а выключены все возможности. Включите **Выполняет сценарии** на странице Runner-а в OneUptime. Он подхватит изменение при следующем heartbeat.
:::

:::details Шаг завершается ошибкой, потому что его Runner не может использовать секретную переменную
Шаг называет секретную переменную, которая не разрешает её использование его Runner-у, поэтому Runner её не получил, а шаг не был выполнен. Ошибка называет секрет и то, что нужно изменить. В **Сборники инструкций → Настройки → Глобальные переменные** или в **Настройки → Переменные** runbook-а добавьте Runner в **Ваши Runner-ы, которые могут его использовать** или включите **Глобальные Runner-ы могут его использовать** для шага на глобальном Runner-е. Или выберите Runner, которому секрет разрешён.
:::

:::details Шаг kubectl завершается ошибкой, потому что его Runner слишком старый
Шаг завершился с ошибкой "This kubectl step runs a script, and this Runner is too old to run one, so it was not run." Runner старше, чем скрипты kubectl, не может их выполнять. Шаг Kubernetes, перенесённый в скрипт kubectl при обновлении, по-прежнему выполняется на нём как действие, с которым он был записан, пока не изменятся его скрипт или kubeconfig. Обновите Runner, как показано в [Обновление агента](#5-обновляйте-агента), и запустите runbook снова.
:::
