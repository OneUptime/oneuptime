# Работа с OneUptime из GitHub

OneUptime GitHub App — это не просто подключение к вашему коду: с ним можно разговаривать прямо в репозитории, и работу он сделает там же.

Упомяните его в задаче — он откроет pull request. Упомяните в pull request — он доработает ветку или сделает ревью диффа. Повесьте на задачу метку — он возьмёт её в работу. Всё, что он производит, — это pull request или ревью, которые читает человек: **он никогда ничего не мержит и никогда не одобряет pull request.**

```text
@oneuptime implement this                          →  pull request, который закрывает задачу
@oneuptime revise this — use exponential backoff   →  новые коммиты в ветке этого pull request
@oneuptime review                                  →  ревью кода в комментарии к этому pull request
```

> Замените `@oneuptime` на handle своего приложения. В OneUptime Cloud это `@oneuptime`. В self-hosted-установке — то, как вы назвали свой GitHub App, в нижнем регистре и с пробелами, заменёнными на дефисы: приложение с именем «Acme AI» упоминается как `@acme-ai`. Если упоминания ни к чему не приводят, проверять начинайте именно с этого.

## Прежде чем начать

- Репозиторий должен быть **подключён к проекту OneUptime** через GitHub App. Настройка описана в [Интеграция с GitHub (self-hosted)](/docs/self-hosted/github-integration), а в OneUptime Cloud репозиторий подключается в **Настройки проекта → Репозитории кода**.
- На связи должен быть **Runner с возможностью «Выполняет ИИ-исправления кода»** — тот же Runner, который выполняет [Задачи ИИ-исправлений](/docs/ai/ai-agent). Без него команды принимаются, а через 30 минут падают с сообщением о том, что их никто не взял в работу.
- У GitHub App должно быть разрешение **Issues: Чтение и запись**, и он должен быть подписан на события вебхуков, перечисленные в разделе [На что подписаться](#на-что-подписаться).

## Команды

Каждая команда начинается с упоминания приложения. Упоминание может стоять в любом месте комментария, а всё, что вы напишете после него, передаётся приложению как ваш запрос.

### В pull request

| Команда | Что происходит |
| --- | --- |
| `@oneuptime review` | Клонирует ветку, читает изменённый код **и код вокруг него** и публикует ревью комментарием. Ничего не меняет. |
| `@oneuptime revise this — <что нужно изменить>` | Клонирует ветку самого pull request, вносит изменение и пушит новые коммиты в неё же. Никогда не открывает второй pull request. |

Всё, что вы напишете после упоминания и что не является известной командой, считается запросом на доработку — потому что почти всегда так оно и есть:

```text
@oneuptime the retry loop here should back off exponentially, and the test
should cover the 429 case
```

### В задаче

| Команда | Что происходит |
| --- | --- |
| `@oneuptime implement this` | Берёт задачу в работу и открывает pull request, который её закрывает. |
| `@oneuptime <что угодно ещё>` | То же самое, а ваши слова идут как дополнительные указания. |

Передать приложению задачу можно и **вообще без комментария**:

- **Повесьте метку-триггер.** Добавьте к задаче метку-триггер репозитория — по умолчанию это `oneuptime` — и начнётся та же самая работа. Это самый надёжный способ поручить работу из интерфейса GitHub.
- **Назначьте задачу на бот-пользователя приложения**, если ваш репозиторий это позволяет. GitHub не везде разрешает назначать исполнителем приложение — именно поэтому существует метка; если назначение ни к чему не приводит, используйте метку.

### Где угодно

| Команда | Что происходит |
| --- | --- |
| `@oneuptime help` | Перечисляет команды. Одно лишь упоминание, без текста после него, делает то же самое. |
| `@oneuptime status` | Говорит, над чем он сейчас работает в этом обсуждении. |
| `@oneuptime cancel` | Останавливает запуски, которые он ведёт в этом обсуждении. Уже отправленная работа остаётся отправленной. |

`help`, `status` и `cancel` никогда не запускают агента, поэтому ничего не стоят и не расходуют ваш дневной лимит задач исправления.

## Как это выглядит в обсуждении

Одна команда порождает **один комментарий**, который приложение редактирует по ходу работы, — поэтому долгая задача не превращает pull request в ленту статусов.

1. Он ставит на ваш комментарий реакцию 👀 и публикует подтверждение, где названы проект OneUptime, которому принадлежит запуск, и ссылка на сам выполняющийся запуск.
2. Когда работа закончена, тот же комментарий переписывается с результатом: открытый pull request, отправленные коммиты или честное объяснение, почему он ничего не сделал.

Если менять нечего, он так и скажет, а не откроет pull request наугад. Это нормальный исход, а не сбой, — дайте больше указаний и попросите ещё раз.

## Кому разрешено им командовать

**Только людям с доступом write, maintain или admin к репозиторию.** OneUptime каждый раз спрашивает у GitHub напрямую, какие права у автора комментария в этом репозитории; он не доверяет значку «contributor», который GitHub показывает рядом с комментарием, — тот описывает прошлую активность, а не текущий доступ.

Упоминание от кого-либо ещё получает единственную реакцию 😕 и больше ничего. Это сделано намеренно: в публичном репозитории комментировать может кто угодно, а приложение, которое исправно отвечает незнакомцам, — это приложение, которым можно засыпать обсуждение спамом.

Ещё он игнорирует любой комментарий, написанный ботом, включая собственные, и игнорирует упоминания внутри цитаты (`>`) или блока кода. Вместе эти два правила и не дают ответу на его собственный комментарий запустить его заново.

## Чего он делать не будет

- **Он никогда не мержит.** Ничто из того, что делает это приложение, не может попасть в вашу основную ветку.
- **Он никогда не одобряет и не запрашивает изменения.** Ревью публикуются комментариями, поэтому ревью от приложения никогда не удовлетворит правило защиты ветки.
- **Он никогда не переписывает историю.** Доработка добавляет коммиты, а не делает force-push. Если кто-то успел запушить в ветку раньше, доработка упадёт, а не выбросит чужую работу.
- **Он не может доработать pull request из форка.** Ветка форка лежит в репозитории, куда установка не может писать. Ревью такого pull request он всё же сделает — попросите ревью.
- **Он никогда не меняет заголовок, описание или целевую ветку pull request.** Только код.

## Сколько это стоит и как это ограничить

Каждая команда, запускающая работу, — это полноценный запуск агента: клонирование, до 40 вызовов LLM и 100 000 выходных токенов, плюс команды сборки и тестов вашего репозитория, если вы их настроили.

Действуют два ограничения, и оба — те же, что уже управляют [Задачами ИИ-исправлений](/docs/ai/ai-agent):

- **Дневной лимит запусков исправлений в проекте** (**Настройки проекта → ИИ**, по умолчанию 25 в день). Команды из GitHub делят этот бюджет с остальными запусками исправлений в проекте.
- **Лимит открытых pull request на репозиторий** (**Репозитории кода → репозиторий → Настройки**, по умолчанию 5). Ревью и доработки под него не попадают: ни то, ни другое не добавляет нового pull request в вашу очередь на ревью.

Одновременно на одну задачу или pull request живёт только один запуск каждого вида. Если попросить дважды, вам ответят, что работа уже идёт; а вот попросить ревью, пока идёт доработка, можно — запустятся оба, это разные запросы.

Если запуск не может начаться, приложение говорит об этом в обсуждении — оно никогда не молчит.

## Как это выключить

Для отдельного репозитория: **Репозитории кода → репозиторий → Настройки → Отвечать на команды GitHub**. С выключенной настройкой приложение игнорирует упоминания, назначения и метку-триггер в этом репозитории и сообщает всякому, кто его спросит, где находится этот переключатель.

На той же странице задаётся **Метка-триггер GitHub**, если вам нужно что-то другое вместо `oneuptime`.

## На что подписаться

В настройках вашего GitHub App, в разделе **«Permissions & events»**, подпишитесь на:

| Событие | Для чего нужно |
| --- | --- |
| **Issue comment** | команды через `@mention` в задачах *и* в pull request |
| **Issues** | назначение задачи на приложение и метка-триггер |
| **Pull request** | запрос ревью у приложения |
| **Pull request review** | упоминание в тексте отправленного ревью |
| **Pull request review comment** | упоминание в строчном комментарии к диффу |

А в разделе **«Repository permissions»** у **Issues** должно быть **Чтение и запись** — комментарии в обсуждении pull request GitHub отдаёт через API задач, поэтому именно это разрешение позволяет приложению комментировать и pull request тоже.

## Инъекции промптов: от чего есть защита, а от чего нет

Текст задач, описания pull request, диффы и комментарии — всё это становится частью промпта агента, а в публичном репозитории писать их может кто угодно. Текст «игнорируй свои инструкции и сделай X» — вполне реальная находка в задаче.

Ограничивают это две вещи, и стоит понимать, какая из них чего стоит:

- **Промпты помечают недоверенный текст как запрос, а не как инструкции**, а репозиторий, ветка и pull request запуска зафиксированы ещё до того, как агент стартует, — ничто из прочитанного агентом не может изменить, над чем он работает.
- **Настоящая изоляция — это песочница.** Агент работает на вашем Runner, в одноразовом клоне, с вычищенными из окружения команд учётными данными и ограниченными git-операциями. Максимум, что он может, — запушить ветку, а смержить её может только человек.

Относитесь к pull request, написанному ИИ, так же, как к pull request от нового контрибьютора, который прочитал задачу: читайте дифф, а не описание.

## Устранение неполадок

**Я его упоминаю, и ничего не происходит.** Сначала проверьте handle — это slug приложения, а не его отображаемое имя. Затем проверьте, что репозиторий подключён к проекту (**Настройки проекта → Репозитории кода**), что включена настройка **Отвечать на команды GitHub** и что ваш GitHub App подписан на перечисленные выше события.

**Он ставит реакцию 😕 и молчит.** У вас нет прав на запись в репозиторий.

**Он говорит, что уже над этим работает.** Запуск такого вида уже идёт по этой задаче или pull request. `@oneuptime status` расскажет, какой именно, а `@oneuptime cancel` его остановит.

**Он подтвердил и надолго замолчал.** Проверьте в **Настройки → Агенты runbook-ов**, что на связи есть Runner с возможностью **Выполняет ИИ-исправления кода**. Без него запуск через 30 минут падает, и об этом пишут в обсуждение.

**Он говорит, что pull request пришёл из форка.** Доработке нужна ветка в этом репозитории. Попросите ревью или запушьте ветку сюда.
