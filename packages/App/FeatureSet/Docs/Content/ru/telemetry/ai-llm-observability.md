# Наблюдаемость ИИ / LLM в OneUptime

Читайте каждый разговор, который вёл ваш ИИ, воспроизводите его так, как он проходил, и узнавайте, когда ИИ отвечает плохо. Всё работает на стандартном OpenTelemetry, без проприетарного SDK: если ваше приложение отправляет спаны по **семантическим конвенциям GenAI** OpenTelemetry (`gen_ai.*`), OneUptime превращает их в разговоры, оповещения, использование и стоимость.

## Что вы получаете

Откройте **ИИ / LLM** на панели навигации, в разделе Наблюдаемость:

- **Разговоры** — каждый разговор вашего ИИ: что спрашивали люди, что отвечал ИИ, какими инструментами он пользовался и что пошло не так. Над списком стоят пять чисел: разговоры, ответы ИИ, сколько из них требуют внимания, стоимость и сколько обычно длится ответ. Откройте разговор, чтобы прочитать его или воспроизвести заново.
- **Вызовы** — каждый вызов LLM, эмбеддинга, агента и инструмента с фильтрами по сервису, провайдеру, модели, операции, человеку и команде. Нажмите на вызов, чтобы открыть его в просмотрщике трассировок.
- **Использование** — вызовы, токены и стоимость за период и кто сколько тратит: сотрудники, команды, модели, провайдеры и приложения, упорядоченные по расходам.
- **Оповещения** — готовые оповещения на случай, когда ИИ отвечает плохо, и ваши мониторы ИИ / LLM.
- **Бюджеты** — дневные лимиты стоимости, публикуемые как метрики, по которым можно настроить оповещения.
- **Цены** — ваши собственные цены для каждой модели, для моделей, которых нет во встроенном каталоге.
- **Настройка** — пять шагов ниже с конечной точкой вашего проекта.

В просмотрщике трассировок у спана каждого вызова ИИ есть также панель **ИИ / LLM** с моделью, числом токенов, стоимостью, параметрами запроса, а также промптом и ответом модели.

## Шаг 1 — Отправляйте вызовы ИИ

Создайте ключ приёма телеметрии: откройте **Настройки проекта → Телеметрия и APM → Ключи приема** и нажмите **Создать ключ приёма**. Приложение передаёт ключ в заголовке OTLP. (Снимки экрана — в [руководстве по OpenTelemetry](/docs/telemetry/open-telemetry).)

Затем инструментируйте приложение любой библиотекой GenAI для OpenTelemetry:

- **OpenLLMetry** (Traceloop) — OpenAI, Anthropic, Cohere, Bedrock, LangChain, LlamaIndex, CrewAI и другие.
- **OpenInference** (Arize) — OpenAI, LangChain, LlamaIndex, DSPy и другие.
- **Vercel AI SDK** или **инструментирования OpenTelemetry** для OpenAI, Anthropic и Gemini.

Направляете трафик LLM через шлюз вроде **LiteLLM** или **Portkey**? Экспортируйте трассировки из шлюза, а не инструментируйте каждое приложение, — см. [Наблюдение за шлюзами ИИ](/docs/telemetry/ai-gateways). Ищете ассистентов программирования, которыми пользуются ваши инженеры, — Claude Code, Cursor, Codex, Gemini CLI, Copilot? Они экспортируют собственный OpenTelemetry, и от вас ничего не требуется: см. [Наблюдаемость ИИ-ассистентов для программирования](/docs/telemetry/ai-coding-assistants).

### Python (OpenLLMetry)

```bash
pip install traceloop-sdk opentelemetry-exporter-otlp
```

```python
from traceloop.sdk import Traceloop

Traceloop.init(
    app_name="my-ai-agent",
    api_endpoint="https://oneuptime.com/otlp",   # or your self-hosted host + /otlp
    headers={"x-oneuptime-token": "YOUR_INGESTION_TOKEN"},
)

# Your normal OpenAI / Anthropic / LangChain calls are now traced automatically.
```

### Node.js / TypeScript (OpenLLMetry)

```bash
npm install @traceloop/node-server-sdk
```

```ts
import * as traceloop from "@traceloop/node-server-sdk";

traceloop.initialize({
  appName: "my-ai-agent",
  baseUrl: "https://oneuptime.com/otlp", // or your self-hosted host + /otlp
  headers: { "x-oneuptime-token": "YOUR_INGESTION_TOKEN" },
});
```

### Обычные переменные окружения OpenTelemetry

Если вы инструментируете приложение нативным SDK OpenTelemetry, направьте экспортёр OTLP в OneUptime:

```bash
export OTEL_EXPORTER_OTLP_ENDPOINT="https://oneuptime.com/otlp"
export OTEL_EXPORTER_OTLP_HEADERS="x-oneuptime-token=YOUR_INGESTION_TOKEN"
export OTEL_SERVICE_NAME="my-ai-agent"
```

Размещаете OneUptime у себя? Замените `https://oneuptime.com/otlp` на `https://YOUR-ONEUPTIME-HOST/otlp`.

## Шаг 2 — Записывайте, что было сказано

Разговор показывает, что спрашивали люди и что отвечал ИИ, когда ваше инструментирование это записывает. OpenLLMetry записывает промпты и ответы, пока вы это не отключите (`TRACELOOP_TRACE_CONTENT=false`). Инструментирования OpenTelemetry записывают их, только если вы об этом попросите:

```bash
export OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=true
```

Без этого разговор всё равно показывает время, стоимость и проблемы и сообщает, что его содержимое не записано. Промпты могут содержать конфиденциальные данные: о том, как скрыть их до сохранения, см. [Конфиденциальность и скрытие данных](#конфиденциальность-и-скрытие-данных).

## Шаг 3 — Группируйте вызовы в разговоры

Чат-приложение делает один вызов модели на каждый ход. Задайте `gen_ai.conversation.id` — или `session.id` — равным идентификатору вашего чата в каждом вызове ИИ, и каждый чат будет показан одним разговором, сколько бы вызовов и трассировок он ни занял. В OpenLLMetry задайте его один раз на запрос как свойство ассоциации:

```python
from traceloop.sdk import Traceloop

Traceloop.set_association_properties({
    "session_id": chat.id,
    "user_email": user.email,
})
```

Вызовы без идентификатора разговора тоже показываются — по одному запросу (одной трассировке) за раз.

## Шаг 4 — Укажите, кто спрашивал

Задайте `user.id` или `user.email` — свойство ассоциации выше задаёт адрес почты, — чтобы видеть, с кем шёл каждый разговор, искать в списке по человеку и упорядочивать расходы по сотрудникам на вкладке Использование. В разделе [Привязка к сотрудникам и командам](#привязка-к-сотрудникам-и-командам) перечислены все ключи, которые читает OneUptime.

## Шаг 5 — Помечайте плохие ответы

OneUptime проверяет каждый ответ сразу по поступлении и отмечает, что с ним пошло не так:

| Проблема    | Что это значит                                                      | По чему определяется                                                                                                                                                           |
| ----------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Не удалось  | Вызов завершился ошибкой, поэтому ответ не пришёл                   | Статус спана Error, `error.type` или причина завершения `error`                                                                                                                |
| Отказ       | ИИ отказался отвечать, или его заблокировал фильтр безопасности     | Причина завершения из-за отказа или безопасности (`content_filter`, `refusal`, `SAFETY` и подобные), отказ в ответе или ответ, начинающийся с типовой английской фразы отказа |
| Оборван     | Ответ остановился на лимите токенов                                 | Причина завершения `length`, `max_tokens` или `MAX_TOKENS`                                                                                                                     |
| Пусто       | ИИ ответил без текста и без вызова инструмента                      | Записанное содержимое, в котором ничего нет, или 0 выходных токенов                                                                                                            |
| Помечен     | Оценка, отправленная вашим приложением, признала ответ плохим       | Событие `gen_ai.evaluation.result`                                                                                                                                             |

Первые четыре ничего от вас не требуют. Чтобы помечать остальное — ответ, который отклоняет ваш guardrail, ваш eval или ваш собственный LLM-судья, — добавьте событие `gen_ai.evaluation.result` к спану ответа, задав `gen_ai.evaluation.score.label` равным `fail`:

```python
from opentelemetry import trace

trace.get_current_span().add_event(
    "gen_ai.evaluation.result",
    {
        "gen_ai.evaluation.name": "relevance",
        "gen_ai.evaluation.score.label": "fail",
        "gen_ai.evaluation.explanation": "The answer is about another product.",
    },
)
```

Метки вроде `incorrect`, `wrong`, `unhelpful`, `toxic`, `unsafe` и `hallucination` тоже считаются неудачными. Событие должно находиться на спане того ответа, который оно оценивает, пока этот спан открыт.

OneUptime никогда не отправляет ваши разговоры другому ИИ для оценки: каждая проверка читает только то, что несёт сам вызов.

## Чтение и повторное воспроизведение разговора

Разговор открывается целиком, как чат-приложение показывает свою историю: что сказал человек — справа, ответы ИИ — слева с моделью, временем, токенами и стоимостью, вызовы инструментов — между ними, а то, что пошло не так, отмечено там, где это случилось. **Подробности** под ответом показывают причину завершения и оценки, а также ссылку на вызов в разделе Трассировки.

Панель внизу воспроизводит разговор так, как его прожил человек:

- **Воспроизвести заново** проигрывает его с первого сообщения в том темпе, в каком он шёл, а «ИИ отвечает…» отсчитывает время, пока ответ в пути. Нажмите на время любого сообщения, чтобы воспроизвести с этого места.
- **Пропускать ожидание**, включённое по умолчанию, сокращает паузы длиннее 3 секунд. Кнопка скорости воспроизводит с 1×, 2×, 4× или 8×.
- **K** запускает или ставит на паузу, **J** или **←** возвращает на одно сообщение назад, а **L** или **→** переходит на одно вперёд.
- Адрес запоминает сообщение, на котором остановилось воспроизведение (`?step=`), поэтому ссылка открывается именно на этом моменте.

## Узнавайте, когда ИИ отвечает плохо

Вкладка **Оповещения** предлагает оповещения, которые нужны большинству приложений с ИИ. Если выбрать одно из них, откроется уже заполненная форма Создать монитор, где перед сохранением можно изменить что угодно:

| Оповещение                         | Когда сообщает                                                                                         |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------ |
| С ответами что-то не так           | Более 5% ответов за 15 минут завершаются ошибкой, отказом, обрываются, пусты или помечены              |
| Вызовы ИИ завершаются ошибкой      | Более 10% вызовов модели за 5 минут заканчиваются ошибкой                                              |
| ИИ отказывается отвечать           | Более 5% ответов за 30 минут — отказы                                                                  |
| Ответы обрываются                  | 3 или более ответов за 30 минут останавливаются на лимите токенов                                      |
| Ответы помечаются                  | Оценка помечает ответ как плохой                                                                       |
| Ответы медленные                   | Более 10% ответов за 15 минут занимают больше 30 секунд                                                |
| ИИ перестаёт отвечать              | ИИ не даёт ни одного ответа в течение 30 минут                                                         |

Оповещения по доле также ждут как минимум 3 плохих ответов, чтобы один плохой ответ из двух никого не будил.

Каждое оповещение — это монитор **ИИ / LLM**. Его настройки определяют, что считается плохим ответом (проблемы выше, ответ медленнее заданного вами лимита или и то и другое), какие приложения и какую модель он отслеживает и насколько далеко назад смотрит каждая проверка. Под ними предпросмотр показывает, что монитор насчитал бы прямо сейчас. Его критерии сравнивают три числа: **долю плохих ответов** (в %), **число плохих ответов** и **число ответов**. Готовое оповещение создаёт оповещение, которое разрешается само, и показывает монитор в состоянии Деградация, пока ответы плохие; чтобы вызвать дежурного, включите вместо этого его инцидент.

За расходами следят [дневные бюджеты стоимости](#дневные-бюджеты-стоимости).

## Атрибуты, которые распознаёт OneUptime

OneUptime сначала читает конвенции GenAI OpenTelemetry, а затем обращается к вариантам OpenLLMetry и OpenInference, чтобы популярные библиотеки работали сразу.

| Что                                  | Основной атрибут             | Также принимаются                                                                                                                                                                                                                                                         |
| ------------------------------------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Провайдер / система                  | `gen_ai.provider.name`       | `gen_ai.system` (устарел в конвенциях, но всё ещё широко отправляется), `llm.system`, `llm.provider`                                                                                                                                                                     |
| Операция                             | `gen_ai.operation.name`      | `llm.request.type`, `openinference.span.kind`                                                                                                                                                                                                                             |
| Запрошенная модель                   | `gen_ai.request.model`       | `llm.model_name`, `llm.request.model`                                                                                                                                                                                                                                     |
| Модель ответа                        | `gen_ai.response.model`      | `llm.response.model`                                                                                                                                                                                                                                                      |
| Входные токены                       | `gen_ai.usage.input_tokens`  | `gen_ai.usage.prompt_tokens`, `llm.token_count.prompt`, `llm.usage.prompt_tokens`                                                                                                                                                                                         |
| Выходные токены                      | `gen_ai.usage.output_tokens` | `gen_ai.usage.completion_tokens`, `llm.token_count.completion`, `llm.usage.completion_tokens`                                                                                                                                                                             |
| Всего токенов                        | `gen_ai.usage.total_tokens`  | `llm.token_count.total`, `llm.usage.total_tokens`; вычисляется как вход + выход, если ни один не передан                                                                                                                                                                  |
| Стоимость (USD)                      | `gen_ai.usage.cost`          | `gen_ai.usage.cost_usd`, `gen_ai.usage.total_cost`, `llm.usage.total_cost`, `gen_ai.cost.total_cost` (LiteLLM), `litellm.cost.total`                                                                                                                                      |
| Имя агента                           | `gen_ai.agent.name`          | `agent.name`                                                                                                                                                                                                                                                              |
| Имя инструмента                      | `gen_ai.tool.name`           | `tool.name`                                                                                                                                                                                                                                                               |
| Идентификатор разговора / сессии     | `gen_ai.conversation.id`     | `session.id`, `langfuse.session.id`, `traceloop.association.properties.session_id`                                                                                                                                                                                        |
| Сотрудник (кто сделал вызов)         | `user.id`                    | `enduser.id`, `litellm.metadata.user_api_key_user_id` и `metadata.user_api_key_user_id` (написания LiteLLM OTel v2 и v1 — читаются оба), `traceloop.association.properties.user_id`, `langfuse.user.id`, `user.account_uuid`, `user.account_id`, `cursor.user.id` |
| Почта сотрудника                     | `user.email`                 | `traceloop.association.properties.user_email`, `enduser.email`                                                                                                                                                                                                            |
| Команда / центр затрат               | `team.id`                    | `team`, `cost_center`, `department`, `litellm.metadata.user_api_key_team_id` и `litellm.team.id` (LiteLLM OTel v2), `metadata.user_api_key_team_id` (LiteLLM OTel v1), `cursor.team.id`                                                                                   |

Подключи `traceloop.association.properties.*` **задаёт вызывающая сторона**: Traceloop определяет префикс, а ваш код задаёт то, что под ним. `gen_ai.usage.total_tokens` и `gen_ai.usage.cost` — ключи **де-факто**, а не семантические конвенции GenAI: в конвенциях нет ни атрибута общего числа токенов, ни атрибута стоимости. OneUptime читает их, потому что их отправляют распространённые инструментирования. `gen_ai.system` — устаревший предшественник `gen_ai.provider.name` в самих конвенциях; читаются оба.

**Три строки идентичности сопоставляются также с префиксом `resource.`.** Приём OTLP разворачивает каждый атрибут _ресурса_ в карту атрибутов спана под префиксом `resource.`, поэтому `OTEL_RESOURCE_ATTRIBUTES=team.id=platform` приходит как `resource.team.id`. OneUptime сначала просматривает весь список без префикса, затем весь список `resource.`, так что атрибут спана (описывающий один вызов) побеждает атрибут ресурса (описывающий весь процесс). Остальные строки сопоставляются только по ключу без префикса: это значения отдельного вызова.

**Содержимое промптов и ответов** читается из события `gen_ai.client.inference.operation.details`; из атрибутов спана `gen_ai.input.messages`, `gen_ai.output.messages` и `gen_ai.system_instructions`; из **устаревших** событий по ролям, которые всё ещё отправляют старые инструментирования (`gen_ai.system.message`, `gen_ai.user.message`, `gen_ai.tool.message`, `gen_ai.assistant.message`, `gen_ai.choice`); из индексированных атрибутов (`gen_ai.prompt.N.content` и `gen_ai.completion.N.content`, а в OpenInference — `llm.input_messages.N.message.content` и `llm.output_messages.N.message.content`); и из JSON-массивов сообщений (`gen_ai.prompt`, `gen_ai.completion`, `input.value`, `output.value`).

### Как рассчитывается стоимость

Если ваше инструментирование передаёт стоимость (`gen_ai.usage.cost`), OneUptime использует её как есть: переданное значение всегда побеждает. Если стоимость не передана, OneUptime вычисляет **оценочную стоимость при приёме** по числу токенов спана и встроенному каталогу прейскурантных цен распространённых моделей OpenAI, Anthropic, Google Gemini, Mistral, DeepSeek, xAI, Cohere, Amazon Nova и Meta Llama. Модели сопоставляются по префиксу имени, поэтому датированные снимки вроде `gpt-4o-2024-08-06` и идентификаторы с префиксами поставщика вроде `us.anthropic.claude-3-5-sonnet-20241022-v2:0` распознаются правильно. Неизвестные и собственные модели никогда не угадываются — их стоимость остаётся `0`, пока вы не зададите для них цену на вкладке **Цены**. Оценки используют прейскурантные цены и не учитывают скидки за кэш и пакетную обработку.

Размещаете OneUptime у себя? Каталог находится в `packages/Common/Types/Telemetry/LlmCostCatalog.ts`.

## Привязка к сотрудникам и командам

«Кто из наших инженеров потратил 4000 $ на Opus в прошлом месяце?» — вопрос о человеке, и ни один спан LLM на него не ответит, если на спане ничто не называет человека. OneUptime при приёме копирует человека, сделавшего вызов, в столбцы, по которым можно делать запросы, поэтому вы группируете и фильтруете по столбцу, а не пишете поиск по атрибутам.

Три строки идентичности в таблице выше — это весь механизм; побеждает первый найденный ключ в указанном порядке. `user.id` идёт первым, потому что это канонический ключ OpenTelemetry для человека и тот, на котором стоит стандартизироваться, если вы задаёте идентичность сами. **Одно исключение: Claude Code** отправляет `user.id` как случайный анонимный идентификатор, хранящийся в `~/.claude.json`, а не как человека. На его точках данных метрик, список которых начинается с почты, это безвредно, но если вы включите бета-версию трассировок Claude Code, анонимный `user.id` на спанах окажется выше `user.email`: удалите или переназначьте `user.id` в процессоре коллектора для этого парка. `enduser.id` по-прежнему действующий атрибут семантических конвенций и принимается как равноправный псевдоним. `cursor.user.id` стоит последним, потому что это непрозрачное целое число в рамках команды, которое можно сопоставить с человеком только через административный API Cursor.

Идентичность читается только на спанах, уже распознанных как вызовы LLM: `user.id`, `user.email` и `team.id` — общие ключи, которые несут и спаны браузера, и обычные спаны бэкенда. **Точки данных метрик** несут более короткий список, начинающийся с почты, — `user.email`, `user.id`, `user.account_uuid`, `user.account_id`, `cursor.user.id`, а команды из `team.id`, `team`, `cost_center`, `department` и `cursor.team.id`, каждый также с префиксом `resource.`, — потому что CLI агентов программирования, которые отправляют метрики без спанов, сами отправляют `user.email`. Сегодня ничто не читает идентичность из **записей логов**.

### Как задать команду и центр затрат

Ни одно инструментирование не отправляет `team.id`, `team`, `cost_center` или `department`: их задаёт ваша организация, обычно через `OTEL_RESOURCE_ATTRIBUTES` процесса:

```bash
export OTEL_RESOURCE_ATTRIBUTES="team.id=platform,team=Platform_Engineering,cost_center=eng-123,department=engineering"
```

Они приходят в OneUptime как `resource.team.id`, `resource.team`, `resource.cost_center` и `resource.department`, и оба уровня распознаются на спанах и на точках данных метрик — оставляет ли ваш экспортёр ключи в блоке ресурса OTLP или копирует их на каждый спан (Claude Code делает второе). `team.id` без префикса, заданный прямо на спане, по-прежнему побеждает.

Написания шлюзов приходят без какой-либо настройки с вашей стороны. LiteLLM называет атрибуты по-разному в двух своих режимах OpenTelemetry: стандартный callback `otel` v1 использует простой префикс `metadata.` (`metadata.user_api_key_user_id`, `metadata.user_api_key_user_email`, `metadata.user_api_key_team_id`), а включаемый режим v2 (`LITELLM_OTEL_V2=true`) — пространство имён `litellm.`. **OneUptime читает оба**.

### Ключи клиентов исключены намеренно

Спан LLM может нести **двух** разных людей: сотрудника, который сделал вызов, и **клиента** дальше по цепочке, для которого он был сделан. Эти ключи несут клиента, и OneUptime намеренно не читает **ни один** из них в столбец идентичности:

- `gen_ai.user` и `llm.user` — так инструментирования передают параметр запроса `user` из OpenAI, который OpenAI описывает как «a stable identifier for your end-users» (теперь устарел в пользу `safety_identifier` и `prompt_cache_key`).
- `litellm.metadata.user_api_key_end_user_id`, `metadata.user_api_key_end_user_id` и `litellm.end_user.id` — явный идентификатор конечного пользователя LiteLLM во всех трёх написаниях, отличный от идентификатора владельца ключа, который **и есть** сотрудник и **читается**.

Причина — корректное распределение затрат: если прочитать идентификатор клиента в столбец сотрудника, бот поддержки, обслуживающий 40 000 клиентов, создаст 40 000 фантомных «сотрудников», а инженер, которому принадлежат расходы, будет выглядеть так, будто ничего не потратил. Эти атрибуты остаются в исходной карте атрибутов, где их можно запрашивать напрямую.

### Столбцы идентичности очищаются

Столбец с почтой сотрудника содержит настоящие персональные данные. Ваши **Правила очистки** телеметрии в области **Атрибуты** покрывают его точно так же, как атрибут, из которого он прочитан, поэтому правило скрытия адресов почты действует и на столбец. Правила очистки и фильтры отбрасывания настраиваются в разделе **Трассировки → Настройки**.

## Спаны и метрики — запасной вариант, а не сумма

**Спаны GenAI — основной источник. К потоку метрик обращаются, только если поток спанов ничего не сообщил, и эти два потока никогда не складываются.** Спан несёт модель, токены и стоимость в одной строке, поэтому там, где есть спаны, они отвечают на любой вопрос. Там, где их нет — CLI агентов программирования публикуют _метрики_ токенов и стоимости и не отправляют спанов GenAI, — их место занимает поток метрик. Они не суммируются, потому что многие инструментирования отправляют оба сигнала для одного и того же вызова (OpenLLMetry — типичный пример), и сложение посчитало бы каждый доллар дважды.

Следствие, которое нужно учитывать: **как только ваши спаны GenAI сообщают ненулевое значение, вклад источника, отправляющего только метрики, в это значение не отображается.** Запасной вариант работает для каждого значения и каждой разбивки, а не для каждого отправителя:

| Где                                              | Что берётся из метрик                                              | Когда                                       |
| ------------------------------------------------ | ------------------------------------------------------------------ | ------------------------------------------- |
| Использование → Входные токены / Выходные токены | Суммы входных и выходных токенов                                   | Обе суммы токенов по спанам равны 0         |
| Использование → Стоимость (USD)                  | Стоимость в USD и микро-USD, приведённая к масштабу и сложенная    | Сумма стоимости по спанам равна 0           |
| Использование → Вызовы LLM                       | Ничего — только спаны                                              | —                                           |
| Использование → Сотрудник, Команда, Модель       | Только стоимость. Столбцы вызовов и токенов показывают `—`         | Эта разбивка не вернула ни одной строки спанов |
| Использование → Провайдер, Приложение / Сервис   | Ничего — только спаны                                              | —                                           |
| Разговоры                                        | Ничего — разговоры строятся из спанов                              | —                                           |

У разбивок Провайдер и Приложение / Сервис нет запасного варианта из метрик, потому что счётчики агентов программирования не несут атрибута провайдера GenAI и не привязаны ни к одному сервису телеметрии OneUptime. Везде, где значение получено из метрик, страница помечает его **из метрик GenAI**, потому что у значения из метрик нет соответствующих строк в списке Вызовы.

**Если расходы инструмента, отправляющего только метрики, нужно видеть отдельно, выделите ему собственный проект**, чтобы его поток спанов был действительно пуст и включился запасной вариант. То же относится к бюджетам: задавайте по одному бюджету на сервис, а не смешивайте сервисы со спанами и сервисы, отправляющие только метрики.

## Дашборды и оповещения по метрикам

Метрики GenAI приходят как обычные метрики OpenTelemetry, поэтому можно строить **дашборды** с графиками `gen_ai.client.token.usage`, `gen_ai.client.operation.duration` и остальных и создавать по ним **мониторы метрик** — например, когда p95 от `gen_ai.client.operation.duration` превышает порог, с группировкой по модели. См. [Мониторинг метрик](/docs/monitor/metrics-monitor).

## Дневные бюджеты стоимости

Вкладка **Бюджеты** задаёт дневные лимиты в USD, которые оцениваются по суткам UTC. Каждые 15 минут фоновый воркер суммирует стоимость спанов LLM за день (переданную или рассчитанную), записывает её в бюджет и публикует две метрики типа gauge:

| Метрика                             | Значение                                         |
| ----------------------------------- | ------------------------------------------------ |
| `oneuptime.llm.budget.spend.usd`    | Расходы за текущий день на данный момент, в USD  |
| `oneuptime.llm.budget.percent.used` | Расходы в процентах от дневного лимита           |

Обе несут атрибуты `oneuptime.llm.budget.id` и `oneuptime.llm.budget.name`, а также область бюджета (сервис, провайдер и модель), если она задана. Фильтруйте мониторы по **`oneuptime.llm.budget.id`**: он стабилен, а имя меняется при переименовании бюджета.

**Оповещения настраиваются через [Мониторинг метрик](/docs/monitor/metrics-monitor) по этим метрикам.** Для классической схемы 80% / 100% создайте монитор по `oneuptime.llm.budget.percent.used`, отфильтруйте его по `oneuptime.llm.budget.id` и добавьте два критерия: `>= 80`, создающий предупреждение, и `>= 100`, создающий критическое оповещение. **Задайте скользящее окно монитора в 30 минут**: бюджет публикует одну точку каждые 15 минут, поэтому окно по умолчанию в 1 минуту между двумя проходами находило бы пустой ряд.

Бюджеты можно ограничить сервисом телеметрии, провайдером LLM или конкретной моделью либо оставить на весь проект, и несколько бюджетов могут существовать одновременно. Монитор бюджета может также вызвать Workflow, который остановит вышедшего из-под контроля агента, — см. [Предохранители для вышедших из-под контроля ИИ-агентов](/docs/telemetry/ai-agent-circuit-breaker).

## Конфиденциальность и скрытие данных

Промпты и ответы могут содержать конфиденциальные данные. OneUptime применяет ваши **Правила очистки** и **Фильтры отбрасывания** телеметрии к спанам LLM так же, как к любой другой трассировке, поэтому вы можете скрывать атрибуты или отбрасывать спаны до их сохранения; настраиваются они в разделе **Трассировки → Настройки**. Столбец с почтой сотрудника подпадает под те же правила — см. [Столбцы идентичности очищаются](#столбцы-идентичности-очищаются).

Разговоры читаются с тем же разрешением, что и трассировки: тот, кто может читать трассировки проекта, может читать и его разговоры, и больше никто.
