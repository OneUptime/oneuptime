# ИИ-ассистенты для программирования

Ваши инженеры пользуются Claude Code, Cursor, Codex, Gemini CLI и Copilot, а счета продолжают расти. Эта страница отвечает на вопросы руководителя: **кто каким инструментом пользуется, на каких моделях и сколько тратит каждый человек и каждая команда**.

Большинство ассистентов для программирования сами экспортируют OpenTelemetry, поэтому на машины разработчиков ничего ставить не нужно: направьте экспорт в OneUptime, и токены, стоимость и использование инструментов окажутся рядом с ИИ-вызовами ваших собственных приложений. Всё здесь приходит через OpenTelemetry; OneUptime не опрашивает административные и биллинговые API поставщиков.

:::cards
- [Матрица поддержки](#матрица-поддержки): Что отправляет каждый инструмент и называет ли он человека.
- [Привязка к сотрудникам и командам](#привязка-к-сотрудникам-и-командам): Ключи, которые связывают расходы с именем и командой.
- [Вкладка Использование](#вкладка-использование): Что таблицы расходов могут и не могут показать для ассистента.
- [С чего начать](#с-чего-начать): Порядок внедрения, который даёт результат с первого дня.
:::

## Как это работает

Каждый инструмент отправляет телеметрию на OTLP-адрес OneUptime с вашим ключом приёма: с каждой машины разработчика, с серверов поставщика (Cursor) или со шлюза, через который проходит трафик к моделям.

```mermaid title="Как ассистенты для программирования попадают в OneUptime"
flowchart TB
    subgraph sources["Отправляется по OTLP из"]
        direction TB
        machines["Claude Code, Codex, Gemini CLI<br/>и Copilot на каждой машине"]
        cursor["Серверы Cursor"]
        gateway["ИИ-шлюз"]
        machines ~~~ cursor ~~~ gateway
    end
    sources --> ingest["OneUptime"]
    ingest --> usage["Вкладка Использование:<br/>сотрудник, команда, модель"]
```

## Перед началом

1. Создайте ключ приёма телеметрии в разделе **Настройки проекта → Телеметрия и APM → Ключи приема**.
2. Ваш OTLP-адрес — `https://oneuptime.com/otlp` или `https://YOUR-ONEUPTIME-HOST/otlp`, если вы размещаете OneUptime у себя.
3. Каждый экспорт передаёт ключ в заголовке `x-oneuptime-token`.

Одного ключа приёма на весь парк достаточно. Он окажется на каждой машине разработчика, поэтому относитесь к нему как к общему секрету, который может только отправлять данные, и меняйте его, как любой другой.

## Матрица поддержки

Три вещи определяют, что вы получите от инструмента: отправляет ли он OpenTelemetry вообще, как его телеметрия попадает в OneUptime и называет ли что-нибудь в ней человека.

| Инструмент | Что отправляет | Как попадает в OneUptime | Кого называет | Руководство |
| --- | --- | --- | --- | --- |
| Claude Code | Метрики и логи; трассировки в бета-версии | С каждой машины; переменные окружения или файл управляемых настроек | `user.email`, если вход выполнен с аккаунтом Claude | [Claude Code](/docs/telemetry/claude-code) |
| Cursor | Метрики и логи | С серверов Cursor, настраивается один раз в панели Cursor; только на тарифе Enterprise | `cursor.user.id`, целое число | [Cursor](/docs/telemetry/cursor) |
| OpenAI Codex | Трассировки, метрики и логи, каждое включается в `~/.codex/config.toml` | С каждой машины, полный URL на каждый сигнал | Никого в спанах и метриках: вы сами задаёте `user.id` и `user.email` в `[otel.span_attributes]` | [OpenAI Codex](/docs/telemetry/openai-codex) |
| Gemini CLI | Трассировки, метрики и логи | С каждой машины, обычно через локальный коллектор | `user.email`, если вход выполнен | [Gemini CLI и GitHub Copilot](/docs/telemetry/gemini-cli-and-copilot) |
| GitHub Copilot | Трассировки, метрики и логи, только из агентных режимов | Из редактора или хоста агента | Никого: вы сами задаёте `enduser.id` и `user.email` на каждой машине | [Gemini CLI и GitHub Copilot](/docs/telemetry/gemini-cli-and-copilot) |
| Cline | Метрики и логи | Настраивается централизованно, в панели организации Cline | Анонимизированный `user_id` | — |
| LiteLLM и Portkey | Трассировки каждого вызова через шлюз | Из процесса шлюза | В LiteLLM — владельца виртуального ключа | [Шлюзы ИИ](/docs/telemetry/ai-gateways) |
| Ваши собственные приложения | То, что отправляет ваше GenAI-инструментирование | Из вашего приложения | Того, кого вы задали в `user.id` | [Наблюдаемость ИИ / LLM](/docs/telemetry/ai-llm-observability) |
| Windsurf, JetBrains AI, Amazon Bedrock, Azure OpenAI | Собственного OpenTelemetry нет | Только через шлюз, поставленный перед ними | Того, кого называет шлюз | [Шлюзы ИИ](/docs/telemetry/ai-gateways) |

Прочерк означает, что у OneUptime пока нет руководства для этого инструмента. Его телеметрия всё равно принимается, как любой другой OpenTelemetry.

:::details Что именно экспортирует GitHub Copilot
Copilot экспортирует OpenTelemetry только из агентных режимов: чат и режим агента в VS Code, хост агента за Copilot CLI, Copilot SDK и агентные сценарии в IDE JetBrains через плагин Copilot. GitHub не документирует экспорт для встроенных подсказок, Copilot на github.com и ревью кода Copilot. Copilot не отправляет никаких атрибутов пользователя, поэтому задайте `enduser.id` и `user.email` для каждой машины через `resourceAttributes` или `OTEL_RESOURCE_ATTRIBUTES`.
:::

:::details Amazon Bedrock, Azure OpenAI, Windsurf и JetBrains AI
- **Amazon Bedrock**: API `InvokeModel` и `Converse` не отправляют OpenTelemetry. С Bedrock AgentCore иначе: AWS документирует для него метрики, спаны и логи, которые по умолчанию уходят в CloudWatch. Значение `DISABLE_ADOT_OBSERVABILITY=true` отключает конфигурацию ADOT среды выполнения по умолчанию, чтобы вы могли направить ADOT SDK в OneUptime.
- **Azure OpenAI**: сервис ничего не отправляет, а у его метрик Azure Monitor нет измерения по пользователю. Инструментируйте клиент или поставьте перед ним API Management или другой шлюз.
- **Windsurf**: экспорт телеметрии не документирован. Данные по пользователям есть в Enterprise API Windsurf, который OneUptime не опрашивает.
- **JetBrains AI Assistant и Junie**: не экспортируют использование. Плагин OpenTelemetry от JetBrains принимает телеметрию вашего приложения внутри IDE; наружу он ничего не отправляет.
:::

## Привязка к сотрудникам и командам

При поступлении телеметрии OneUptime копирует в колонки человека, сделавшего вызов, и его команду, чтобы вкладка **Использование** могла ранжировать людей и команды без фильтров по атрибутам.

### Атрибуты, читаемые как сотрудник

В спане побеждает первый присутствующий ключ в таком порядке:

| Колонка | Ключи, от предпочтительного |
| --- | --- |
| Идентификатор сотрудника | `user.id`, `enduser.id`, `litellm.metadata.user_api_key_user_id`, `metadata.user_api_key_user_id`, `traceloop.association.properties.user_id`, `langfuse.user.id`, `user.account_uuid`, `user.account_id`, `cursor.user.id` |
| Email сотрудника | `user.email`, `litellm.metadata.user_api_key_user_email`, `metadata.user_api_key_user_email`, `traceloop.association.properties.user_email`, `enduser.email` |
| Команда / центр затрат | `team.id`, `team`, `cost_center`, `department`, `litellm.metadata.user_api_key_team_id`, `litellm.team.id`, `metadata.user_api_key_team_id`, `cursor.team.id` |

В точке данных метрики список короче и начинается с email, потому что ассистенты, отправляющие метрики, сами отправляют `user.email`:

| Колонка | Ключи, от предпочтительного |
| --- | --- |
| Сотрудник | `user.email`, `user.id`, `user.account_uuid`, `user.account_id`, `cursor.user.id` |
| Команда / центр затрат | `team.id`, `team`, `cost_center`, `department`, `cursor.team.id` |
| Модель | `gen_ai.request.model`, `model`, `cursor.model.name` |

Как читаются эти ключи:

- **Каждый ключ читается также с префиксом `resource.`.** Приём OTLP хранит атрибуты ресурса под этим префиксом, поэтому `OTEL_RESOURCE_ATTRIBUTES=team.id=platform` приходит как `resource.team.id`. Ключи без префикса проверяются первыми, так что значение в спане побеждает значение на весь процесс.
- **Вкладка Использование показывает email человека, если он есть у вызова, а иначе — идентификатор.** Строки с одинаковым email складываются, поэтому один инженер на двух машинах — это одна строка.
- **Идентичность читается только из ИИ-вызовов.** `user.id`, `user.email` и `team.id` — общие ключи, которые несут и спаны браузера и бэкенда; колонки получают только спаны, уже распознанные как ИИ-вызовы.
- **Записи логов для идентичности не читаются.** Это важно для Codex, который ставит `user.email` только в своих логах.
- LiteLLM пишет эти ключи двумя способами: его callback `otel` по умолчанию использует префикс `metadata.`, а необязательный режим OpenTelemetry v2 (`LITELLM_OTEL_V2=true`) — пространство имён `litellm.`. OneUptime читает оба, поэтому стандартный прокси работает без дополнительной настройки.

### Команды и центры затрат

Ни одно инструментирование не отправляет `team.id`, `team`, `cost_center` или `department`: их задаёт ваша организация, обычно через `OTEL_RESOURCE_ATTRIBUTES` в процессе инструмента.

```bash
export OTEL_RESOURCE_ATTRIBUTES="team.id=platform,team=Platform_Engineering,cost_center=eng-123,department=engineering"
```

Задавайте её там, где вы уже готовите машины разработчиков: в профиле MDM, файле управляемых настроек или профиле оболочки из ваших dotfiles. Значения не могут содержать пробелов: используйте подчёркивания или процентное кодирование, например `%20`. У Codex нет атрибутов ресурса, поэтому задайте те же ключи в его `[otel.span_attributes]`.

Чтобы разделить расходы по приложениям, используйте имя сервиса (`OTEL_SERVICE_NAME` или собственную настройку инструмента). Разбивка **Приложение / Сервис** охватывает только инструменты, отправляющие спаны GenAI.

### Что намеренно не считается сотрудником

Вызов может нести двух разных людей: сотрудника, который его сделал, и клиента, для которого он сделан. Эти ключи несут клиента, и OneUptime никогда не читает их в колонку идентичности:

- `gen_ai.user` и `llm.user`: так инструментирования передают параметр запроса `user` OpenAI, который OpenAI описывает как идентификатор ваших конечных пользователей.
- `litellm.metadata.user_api_key_end_user_id`, `metadata.user_api_key_end_user_id` и `litellm.end_user.id`: конечный пользователь LiteLLM, в отличие от владельца ключа, который и есть сотрудник.

Если читать идентификатор клиента как сотрудника, бот поддержки, обслуживающий 40 000 клиентов, превратился бы в 40 000 призрачных сотрудников, а инженер, которому принадлежат расходы, выглядел бы так, будто ничего не тратит. Ключи остаются в атрибутах спана, а вкладка **LLM** в просмотрщике трассировок показывает их как конечного пользователя.

### Конфиденциальность

Колонка email сотрудника содержит персональные данные. **Правила очистки** трассировок покрывают её точно так же, как атрибут, из которого она прочитана, поэтому правило, маскирующее email, маскирует и колонку. Они находятся в разделе **Трассировка → Настройки**.

## Метрики ассистентов, которые читает OneUptime

Ассистенты для программирования называют свои метрики с собственным префиксом вместо `gen_ai.*`, поэтому OneUptime знает каждую по имени:

| Метрика | Инструмент | Единица |
| --- | --- | --- |
| `claude_code.token.usage` | Claude Code | Токены |
| `claude_code.cost.usage` | Claude Code | USD |
| `cursor.token.usage` | Cursor | Токены |
| `cursor.cost.usage` | Cursor | USD, оценка по данным самого Cursor |
| `codex.turn.token_usage` | OpenAI Codex | Токены |
| `codex.turn.cost_microusd` | OpenAI Codex | Миллионные доли USD: OneUptime их пересчитывает, так что не делайте этого сами |

OneUptime также читает токены из `gen_ai.client.token.usage`, `gen_ai.client.token.count`, `llm.token.usage` и `llm.usage.tokens`, а стоимость — из `gen_ai.client.cost`, `gen_ai.client.cost.usd`, `gen_ai.usage.cost`, `litellm_spend_metric` и `litellm.cost.total`.

Две вещи, которые нужно знать, прежде чем читать цифры:

- **`gemini_cli.token.usage` пропускается намеренно.** Gemini CLI отправляет свои токены дважды, как собственную метрику и как `gen_ai.client.token.usage`, и чтение обеих удвоило бы их. Его токены считаются один раз, через `gen_ai.client.token.usage`. Gemini CLI не отправляет метрику стоимости: включите его трассировки, чтобы у каждого вызова была цена.
- **Считаются только входные и выходные токены.** Тип токена читается из `gen_ai.token.type`, `llm.token.type`, `type`, `cursor.token.type` или `token_type`, и учитываются только `input` и `output` (или старые `prompt` и `completion`). Чтение и запись кэша, `total` у Codex (повторяющий остальные) и `reasoning_output` (часть `output`) пропускаются, поэтому итог из метрик меньше суммы всего, что отправляет инструмент.

## Вкладка Использование

Откройте **Продукты → AI / LLM** и перейдите на вкладку **Использование**. Она ранжирует **Сотрудник**, **Команда**, **Модель**, **Провайдер** и **Приложение / Сервис** по расходам за последние 7 дней, если не выбрать другой период. Вызовы, в которых никто не назван, учитываются в строке **Без привязки**: большая строка **Без привязки** показывает, какому инструменту ещё нужно задать идентичность.

### Метрики ассистентов — запасной источник, а не добавка

Спаны GenAI идут первыми: метрики читаются только для значения, о котором спаны ничего не сообщили, и одно с другим никогда не складывается ([почему](/docs/telemetry/ai-llm-observability#сначала-спаны-метрики-дополняют)). Для ассистентов из этого следует одно жёсткое следствие: **если тот же проект получает спаны GenAI со стоимостью, расходы ассистентов не отображаются.** Выделите ассистентам отдельный проект с собственным ключом приёма.

Когда запасной источник всё же используется, вот что может показать каждая разбивка для инструмента, отправляющего только метрики:

| Разбивка | Из метрик |
| --- | --- |
| **Сотрудник** | Да, из каждого ключа идентичности выше, с префиксом `resource.` и без него |
| **Команда** | Да, из ключей команды |
| **Модель** | Да: Claude Code и Codex отправляют `model` без префикса, Cursor — `cursor.model.name` |
| **Провайдер** | Нет: метрики ассистентов не называют провайдера |
| **Приложение / Сервис** | Нет: их метрики не принадлежат ни одному сервису OneUptime |

Строка из метрик несёт только стоимость: её ячейки вызовов и токенов показывают `—`, потому что у счётчика расходов нет деталей по вызовам, а 0 там утверждал бы, что человек не сделал ни одного вызова. Таблица помечена как **из метрик GenAI**.

## Нет OpenTelemetry? Поставьте шлюз

Для Windsurf, JetBrains AI, API моделей Bedrock, Azure OpenAI и всего остального без собственного экспорта поставьте перед ними ИИ-шлюз. Тогда каждый вызов проходит через один процесс, который отправляет OpenTelemetry, и экспорт настраивается один раз.

**Используйте LiteLLM с отдельным виртуальным ключом на каждого сотрудника.** LiteLLM ставит в каждый спан идентификатор и email владельца ключа, которые OneUptime читает как сотрудника, а команду ключа — как команду. Он также сам оценивает стоимость каждого вызова с учётом собственных ставок, заданных в прокси, и сообщённая им стоимость побеждает оценку OneUptime. Не используйте для этого его идентификатор конечного пользователя: это клиент. Настройка описана в разделе [Шлюзы ИИ](/docs/telemetry/ai-gateways).

Два ограничения, прежде чем строить планы вокруг шлюза:

- **Шлюз видит только трафик, отправленный через него.** Собственная подмена базового URL в Cursor — это настройка на уровне пользователя, которая охватывает только чат-модели (автодополнение по Tab продолжает использовать модели Cursor), поэтому предпочитайте встроенный экспорт Cursor.
- **Шлюз видит вызов модели, а не агента.** Он записывает промпты и ответы, но не вызовы инструментов, правки файлов и решения о принятии или отклонении, о которых сообщает собственная телеметрия инструмента.

## Содержимое промптов: значения по умолчанию у инструментов разные

Промпты и ответы — самые рискованные данные в этом конвейере: в них регулярно попадают исходный код, данные клиентов и вставленные учётные данные. Проверьте значение по умолчанию у каждого инструмента:

| Инструмент | Содержимое промптов по умолчанию |
| --- | --- |
| Claude Code | Выключено: у каждого вида содержимого своя переменная для включения |
| Cursor | Выключено: текст сообщений отправляет только необязательное семейство `conversation_content` |
| OpenAI Codex | Выключено: `log_user_prompt` по умолчанию `false` |
| Gemini CLI | **Включено**: `logPrompts` по умолчанию `true`, поэтому задайте `false`, когда включаете телеметрию |
| GitHub Copilot | Выключено: `captureContent`, которое управляемые настройки могут зафиксировать через `lockCaptureContent` |
| LiteLLM | Включено с callback `otel` по умолчанию (отключается через `turn_off_message_logging`); выключено в режиме OpenTelemetry v2 |

Codex также по умолчанию отправляет свои метрики в OpenAI: см. [OpenAI Codex](/docs/telemetry/openai-codex). Там, где вы собираете содержимое намеренно, к нему применяются **Правила очистки** и **Фильтры отбрасывания** трассировок, как к любой другой телеметрии.

## Чего OneUptime пока не делает

- **Нет коннекторов к административным и биллинговым API поставщиков.** OneUptime не опрашивает Admin API Anthropic, Admin API Cursor, адреса использования и затрат OpenAI, биллинг Copilot в GitHub, а также API Windsurf и JetBrains. За цифрами уровня счёта обращайтесь к поставщику.
- **Стоимость — это оценка, если инструмент её не сообщает.** Сообщённая стоимость используется как есть; иначе OneUptime оценивает токены по прейскурантным ценам. `cursor.cost.usage` у Cursor сам по себе оценка.
- **Идентичность в записях логов не читается.** `user.email` у Codex, который он отправляет только в логах, не связывается с расходами.
- **`cursor.user.email` у Cursor пока не читается**, поэтому пользователи Cursor отображаются своим целым числом `cursor.user.id`.
- **Спаны Codex не называют модель**, поэтому OneUptime не может оценить их стоимость: Codex показывает токены по людям, а свою стоимость — только в итогах.
- **Инструменты быстро меняются.** Если на этой странице сказано, что у инструмента нет экспорта, проверьте его актуальную документацию, прежде чем строить решение вокруг шлюза.

## С чего начать

Внедряйте в таком порядке; каждый шаг полезен сам по себе. Используйте проект, который ещё не получает спаны GenAI от ваших собственных приложений, иначе [правило запасного источника](#метрики-ассистентов-запасной-источник-а-не-добавка) не даст расходам ассистентов появиться на странице.

1. **Gemini CLI**, если им кто-то пользуется. Он отправляет `user.email` без настройки, поэтому показывает работу привязки от начала до конца. Включите и его трассировки: метрику стоимости он не отправляет.
2. **Claude Code**: один файл управляемых настроек для всего парка, `user.email` без усилий, настоящая метрика стоимости, а также доля принятых правок, коммиты, pull request'ы и строки кода по разработчикам.
3. **Cursor** на тарифе Enterprise: один экран в панели Cursor, ни одна машина разработчика не затронута, хотя люди приходят как целые числа.
4. **Copilot и Codex**, которым обоим нужна идентичность, заданная на каждой машине. Делайте это при подготовке машин: вызовы, пришедшие без неё, потом не привязать.
5. **Шлюз LiteLLM** для всего остального, с отдельным виртуальным ключом на каждого сотрудника.
