# Переменные

Рабочие процессы — это про перемещение данных: от триггера к первому блоку, от блока к блоку и из общих значений туда, где они вам понадобились. Переменные — то, чем данные перемещаются.

Областей видимости у переменных две, плюс выводы компонентов, которые появляются по ходу запуска.

## Глобальные переменные

Значения уровня проекта: сохранили один раз — используете где угодно. Ключи API, адреса, имена каналов — всё, что не хочется копировать в десяток разных рабочих процессов.

Искать их в разделе **Рабочие процессы → Глобальные переменные**. У каждой есть:

- **Имя** — то, по чему вы на неё сошлётесь. Минимум два символа, без пробелов, только буквы, цифры, дефисы и подчёркивания. `UPPER_SNAKE_CASE` — хорошая привычка: так переменная заметна в блоках.
- **Описание** — необязательный произвольный текст, чтобы вы не забыли, для чего она.
- **Секрет** — если включить, значение вычищается из журналов запусков и трассировок шагов.
- **Содержимое** — само значение. Поле длинное, так что многострочные значения тоже работают.

Использовать глобальную переменную в любом рабочем процессе можно так:

```
{{global.variables.NAME}}
```

Скажем, вы сохранили ключ PagerDuty как `PAGERDUTY_KEY` — тогда любой блок обращается к нему как `{{global.variables.PAGERDUTY_KEY}}`: редактор хранит ссылку, а логирование рабочего процесса вычищает подставленное секретное значение.

Переменные создают и удаляют, но не редактируют. Кнопки редактирования в таблице нет, так что поменять значение через интерфейс можно только удалив переменную и создав её заново — либо обновив её через API, о чём рассказано в конце этой страницы. Глобальные переменные и переменные рабочего процесса доступны на плане Growth.

## Локальные переменные рабочего процесса

Переменные, живущие в пределах одного рабочего процесса; ими управляют в разделе **Переменные рабочих процессов** в левом меню этого рабочего процесса. Ссылаться на них так:

```
{{local.variables.NAME}}
```

## Выводы компонентов (данные от предыдущих блоков)

Любой триггер и любой компонент может выдать во время выполнения какой-то вывод. Ссылку на него лучше не набирать руками, а собирать выбором значения компонента в редакторе — он подставит ровно те идентификаторы, которых ждёт исполнитель.

Ссылка на вывод предыдущего блока выглядит так:

```
{{local.components.COMPONENT_ID.returnValues.FIELD_ID}}
```

`COMPONENT_ID` — это **Identifier** блока, короткий идентификатор, написанный на блоке, а не отображаемое на нём имя. Новые блоки получают что-нибудь вроде `api-get-1`, и переименовать это можно в разделе **ID** блока. Переименование ломает все уже существующие ссылки на него — ровно так же, как переименование переменной. `FIELD_ID` — идентификатор выбранного возвращаемого значения.

Примеры:

- После компонента **API** с идентификатором `lookup-user` его код ответа — это `{{local.components.lookup-user.returnValues.response-status}}`, а тело — `{{local.components.lookup-user.returnValues.response-body}}`.
- После компонента **Run Custom JavaScript** с идентификатором `transform` возвращённое им значение — `{{local.components.transform.returnValues.returnValue}}`.
- Триггеры на тип записи — **On Create Incident** и его собратья — возвращают ровно одно значение, `model`, и внутрь него вы проваливаетесь сами. Для триггера с идентификатором `incident-on-create-1` заголовок инцидента — `{{local.components.incident-on-create-1.returnValues.model.title}}`.

Локальные переменные существуют только в рамках текущего запуска. Каждый новый запуск начинается с чистого листа.

## Где работают переменные

Переменные принимает почти любое текстовое поле:

- URL в блоке API.
- Текст сообщения в Slack, Teams, Discord, Telegram, Email.
- Тема и тело письма.
- Заголовки и поля тела запроса (внутри строковых значений).
- Обе части блока **If / Else** (он лежит в категории Conditions).

В JSON-полях переменную можно поставить внутрь строкового значения, но не в ключ. Ссылка, занимающая целое значение целиком, подставляется как есть, так что этим способом в JSON-поле можно уронить и объект целиком. Если структуру нужно собирать динамически, соберите её блоком **Run Custom JavaScript** и передайте его вывод следующему блоку.

Блок **Run Custom JavaScript** переменные сам по себе не получает — в песочницу ничего не внедряется. Положите `{{global.variables.NAME}}` (или любую ссылку на компонент) в JSON-поле **Arguments** этого блока: эти значения подставляются до запуска скрипта и приходят в него как `args`.

## Перебор массивов

Внутри текстового поля массив можно перебрать конструкцией `{{#each path}}…{{/each}}`. Внутри неё `{{property}}` читает поле текущего элемента, `{{@index}}` — его позиция начиная с нуля, а `{{this}}` — сам элемент, если это массив простых значений. Имена внутри блока `{{#each}}` обрезаются по краям, так что лишние пробелы там безвредны — в отличие от всех остальных мест.

## Примеры

### Собрать полезную нагрузку из вебхука

Приходит вебхук с телом вида `{ "service": "checkout", "status": "failed" }`. Чтобы превратить это в инцидент OneUptime:

1. Триггер **Webhook** с идентификатором `ci-webhook`.
2. Блок **If / Else**: выберите вывод Request Body вебхука и его свойство `status`, оператор `==`, справа `failed`.
3. Из ветки **Yes** — блок **Create One Incident** со значениями:
   - Заголовок: `CI build failed: {{local.components.ci-webhook.returnValues.request-body.service}}`
   - Описание: `See {{local.components.ci-webhook.returnValues.request-body.url}} for the logs.`

### Использовать секрет в вызове API

Рабочий процесс, обращающийся к PagerDuty:

1. Сохраните `PAGERDUTY_KEY` как секретную глобальную переменную.
2. В блоке **API** задайте заголовку `Authorization` значение `Token token={{global.variables.PAGERDUTY_KEY}}`.

Ключ не попадает ни в сам рабочий процесс, ни в журналы.

### Связать два вызова API

Первый вызов даёт идентификатор, который нужен второму:

1. Компонент **API** `lookup-order`: через выбор значений вставьте поле email из JSON ручного триггера в `GET /orders?email=...`.
2. Компонент **API** `cancel-order`: `POST /orders/{{local.components.lookup-order.returnValues.response-body.id}}/cancel`.

Если `lookup-order` не отработает, сработает его выход **Error** вместо **Success**. Подключите к нему блок Email или Slack, чтобы сбои не остались незамеченными.

## Обновление переменной из рабочего процесса

Частый сценарий — ротация учётных данных по расписанию: получить у стороннего сервиса свежий токен и положить его обратно в переменную, чтобы следующий запуск взял уже новый. Делается это блоком **API**, обращающимся к API OneUptime.

`PUT /api/workflow-variable/<variable-id>` с заголовком `ApiKey` и — вот на чём чаще всего спотыкаются — с полями, которые вы хотите изменить, **завёрнутыми в объект `data`**:

```json
{
  "data": {
    "content": "{{local.components.get-token.returnValues.response-body.access_token}}"
  }
}
```

Плоское тело без обёртки `data` отклоняется с ошибкой 400. Отправляйте только те поля, которые действительно меняете; `name` и `description` можно вообще не включать.

Ключу API нужно разрешение **Edit Workflow Variables**. Разрешение на чтение не требуется — обновление не перечитывает строку обратно.

За двумя вещами стоит следить:

- **Не переименовывайте переменную, на которую ссылаетесь.** `name` — часть выражения `{{local.variables.NAME}}`. Изменив его, вы оставите все существующие ссылки неразрешёнными, а неразрешённая ссылка проходит дальше буквальным текстом — см. подвох ниже.
- **Записать переменную так можно, а прочитать обратно — нет.** Поле `content` доступно через API только на запись, для любой переменной, секретной или нет. Именно поэтому переменная — безопасное место, чтобы держать ротируемый токен. А отметка «секрет» вдобавок держит значение подальше от журналов запусков и трассировок шагов.

## Подвохи

- **Пользуйтесь выбором значений.** Он подставляет ровно те идентификаторы компонента, возвращаемого значения и переменной, которых ждёт исполнитель, и делает ссылки независимыми от отображаемых подписей.
- **Имена переменных чувствительны к регистру.** `{{global.variables.MyKey}}` и `{{global.variables.mykey}}` — разные вещи.
- **Неразрешившаяся ссылка не обнуляется, а остаётся как есть.** Обращение к несуществующему — не ошибка, и пустой строки вы тоже не получите: фигурные скобки проходят насквозь, поэтому `{{local.components.api-get-1.returnValues.body}}` с опечаткой в идентификаторе шага дословно окажется в вашем сообщении в Slack, в URL или в теле запроса, а запуск всё равно отчитается статусом **Executed**. В журнале запуска будет строка предупреждения с именем каждой такой ссылки.
- **Конструктор не может проверить имена переменных.** Ссылки на компоненты, которые он не может сопоставить, — неизвестный идентификатор шага, неизвестное возвращаемое значение, кривой корень — он помечает ещё до сохранения. А вот существует ли переменная, ему не выяснить, так что переименованную переменную поймает только журнал запуска.
- **Пробелы внутри скобок не обрезаются.** `{{ local.variables.NAME }}` — это другой поиск, чем `{{local.variables.NAME}}`, и он не разрешается никогда. Единственное исключение — внутри блока `{{#each}}`, где имена обрезаются.
