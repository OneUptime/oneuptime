# Интеграция с Grafana

Превращайте оповещения [Grafana](https://grafana.com) в инциденты OneUptime. Grafana вычисляет правила оповещений на ваших дашбордах; OneUptime фиксирует, эскалирует и отслеживает их.

Эта интеграция — **входящая**: **контактная точка Webhook** в Grafana отправляет POST в OneUptime. Принять его можно двумя способами.

| Подход                                                                                  | Когда использовать                                                                                                                                    |
| --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **[Монитор входящих запросов](/docs/monitor/incoming-request-monitor)** (рекомендуется) | Вы хотите, чтобы оповещения становились инцидентами с эскалацией на дежурных, по одному инциденту на оповещение и с автозакрытием при восстановлении. |
| **[Рабочий процесс](/docs/workflows/index) с триггером Webhook**                        | Нужна логика маршрутизации, которой у OneUptime нет из коробки — вызвать другие системы, преобразовать нагрузку, ветвиться по условию.                |

```text
Grafana alert rule fires  ──►  Webhook contact point  ──►  OneUptime  ──►  Incident + on-call
```

Нагрузка webhook Grafana следует формату Alertmanager — `status`, массив `alerts`, `commonLabels` и `commonAnnotations`, а также удобные поля `title` и `message` верхнего уровня.

## Предварительные требования

- Grafana 9+ с включённым [unified alerting](https://grafana.com/docs/grafana/latest/alerting/) (по умолчанию в современных версиях Grafana).
- Grafana должна иметь доступ к вашему экземпляру OneUptime по HTTPS.
- Проект OneUptime, где вы можете создавать мониторы (или рабочие процессы).

## Вариант 1 — Монитор входящих запросов

1. Перейдите в **Мониторы → Создать монитор** и выберите **Входящий запрос**. Откройте его и нажмите **Documentation** в левом меню, чтобы скопировать URL.
2. Откройте **Criteria** монитора и задайте **Filter Type** = `JavaScript Expression`, а **Value** = `"{{requestBody.status}}" === "firing"`.
3. Объявляйте инцидент при совпадении, выберите **On-Call Policies** для вызова и включите **Auto Resolve Incident** в разделе **Advanced Options**.
4. В разделе **Settings** включите **Group incidents and alerts by a payload field** и задайте:

   | Поле                               | Значение                            |
   | ---------------------------------- | ----------------------------------- |
   | Open a separate incident for each… | `requestBody.alerts[*].fingerprint` |
   | Field that signals recovery        | `requestBody.alerts[*].status`      |
   | Value that means recovered         | `resolved`                          |

5. Дайте инциденту заголовок `{{requestBody.commonLabels.alertname}}` и опишите его через `{{requestBody.message}}` или `{{requestBody.commonAnnotations.summary}}`. (`{{fingerprint}}` содержит сам ключ группировки, но это хеш — не то, что стоит показывать дежурному.)
6. Направьте контактную точку Grafana на URL монитора (см. шаги по контактной точке ниже).

Каждое **уникальное** значение группировки становится отдельным инцидентом, и каждый из них закрывается, когда Grafana сообщает о восстановлении. `fingerprint` каждого оповещения в Grafana уникален для набора меток оповещения — поэтому выше он и выбран путём группировки. На странице [Prometheus Alertmanager](/docs/integrations/prometheus-alertmanager) та же настройка разобрана подробнее — форма нагрузки та же, так что каждый шаг оттуда применим и здесь.

> **Warning:** Не группируйте по метке, которая постоянна в пределах уведомления. Политика уведомлений Grafana по умолчанию группирует по `grafana_folder` и `alertname`, поэтому все оповещения в одном вебхуке имеют один и тот же alertname — группировка по `requestBody.alerts[*].labels.alertname` схлопнула бы всю нагрузку в один инцидент. Кроме того, пути группировки должны начинаться с буквального `requestBody.`, и подстановочным знаком является только первый `[*]` в пути. Все эти ошибки происходят молча.

## Вариант 2 — Рабочий процесс

Используйте его, когда нужна логика сложнее, чем «оповещение становится инцидентом».

### Шаг 1 — Создайте рабочий процесс в OneUptime

1. Откройте **Рабочие процессы → Создать рабочий процесс**, назовите его `Grafana → Incidents` и откройте **Конструктор**.
2. Добавьте триггер **Webhook** и **скопируйте его URL**. Переименуйте блок в `Grafana`.
3. Добавьте блок **Условия**, соединённый с триггером:
   - **Left**: `{{Grafana.Request Body.status}}`
   - **Operator**: `==`
   - **Right**: `firing`
4. Из выхода **Да** добавьте блок **Создать инцидент**:
   - **Заголовок**: `{{Grafana.Request Body.title}}`
   - **Описание**: `{{Grafana.Request Body.message}}`
   - **Серьёзность**: выберите один (или ветвитесь по `{{Grafana.Request Body.commonLabels.severity}}`).
5. **Сохраните** (оставьте отключённым до тестирования).

## Настройте контактную точку Grafana

1. В Grafana перейдите в **Alerting → Contact points → Add contact point**.
2. **Name**: `OneUptime`. **Integration**: **Webhook**.
3. **URL**: вставьте URL монитора из Варианта 1 или URL вебхука рабочего процесса из Варианта 2. **HTTP Method**: `POST`.
4. Сохраните контактную точку.
5. Перейдите в **Alerting → Notification policies** и направьте нужные оповещения (или политику по умолчанию) на контактную точку **OneUptime**.

## Проверьте

1. Включите рабочий процесс, если вы его создавали.
2. На экране контактной точки нажмите **Test**, чтобы отправить пробное уведомление, или дождитесь срабатывания реального правила.
3. Проверьте список **Инциденты** — и вкладку **Журналы** рабочего процесса, если вы использовали Вариант 2.

## Закрытие при восстановлении

Когда оповещение снимается, Grafana отправляет ещё одно уведомление со `status: resolved`.

В **Варианте 1** настроенные выше поле и значение восстановления закрывают соответствующий инцидент автоматически — при условии, что включён **Auto Resolve Incident**.

В **Варианте 2** добавьте вторую ветку **Условия** (`status == resolved`), найдите соответствующий инцидент и переведите его в ваш статус «решено» через **Update Incident**.

## Примечания

- **Устаревшая система оповещений (Grafana 8 и раньше)** отправляет другую нагрузку (`ruleName`, `state`, `evalMatches`). Если вы её используете, ссылайтесь на `{{Grafana.Request Body.ruleName}}` и `{{Grafana.Request Body.state}}` и ветвитесь по `state == alerting`.
- Можно вообще обойтись без оповещений Grafana и поручить OneUptime отслеживать те же метрики напрямую — см. [Мониторинг метрик](/docs/monitor/metrics-monitor).

## Устранение неполадок

- **Ничего не приходит** — убедитесь, что Grafana может достучаться до URL (проверьте журналы сервера Grafana), а для Варианта 2 — что рабочий процесс **включён**. OneUptime отвечает на каждый входящий запрос пустым `200` до проверки, поэтому `200` в журналах Grafana не подтверждает, что нагрузка принята.
- **Инциденты открываются, но не закрываются** — проверьте поле и значение восстановления в критерии и то, что **Auto Resolve Incident** включён в **Advanced Options** инцидента. Сравнение чувствительно к регистру.
- **Один инцидент на нагрузку, полную оповещений** — вы сгруппировали по метке, которая не меняется внутри уведомления. Группируйте вместо этого по `requestBody.alerts[*].fingerprint`.
- **В тексте инцидента видны сырые плейсхолдеры `{{...}}`** — путь не разрешился, а неразрешённые плейсхолдеры остаются на месте, а не очищаются. Ссылайтесь на поля, которые есть в вашей версии системы оповещений; изучите вывод триггера на вкладке **Журналы**, если вы использовали Вариант 2.
