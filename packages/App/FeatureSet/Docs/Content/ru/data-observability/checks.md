# Проверки и сверки

Состояние таблиц говорит о том, меняется ли таблица. **Проверка** говорит, верно ли то, что в ней лежит, **сверка** — совпадают ли две копии данных, а **тесты dbt** сообщают о таблицах, которые строит dbt. Каждая из них выполняется там же, где сбор этой базы данных, — в OneUptime или на её зонде, и базу данных покидает только число, если только проект не решит хранить замаскированную выборку проваленных строк.

## Проверки

Добавьте проверку на вкладке **Проверки** таблицы:

| Проверка | Что она читает |
| --- | --- |
| **Доля NULL** | Процент строк, в которых столбец пуст |
| **Доля дубликатов** | Процент значений, повторяющих значение другой строки |
| **Число уникальных значений** | Сколько разных значений содержит столбец |
| **Минимум**, **Максимум**, **Среднее**, **Сумма** | По числовому столбцу (Сумма по пустому набору строк равна 0) |
| **Доля недопустимых значений** | Процент значений вне заданного вами списка |
| **Доля несоответствий формату** | Процент значений, которые не соответствуют выбранному вами формату, например Email, UUID или Country Code, или не соответствуют вашему регулярному выражению (во всех СУБД, кроме SQL Server и Dataverse) |
| **Число осиротевших строк** | Строки, значению которых нет соответствия в столбце другой таблицы |
| **Число строк** | Строки в таблице; полезнее всего вместе с **Разбить по** |
| **Свой SQL** | Число, которое возвращает ваш SELECT только для чтения, под именем `value` (в MongoDB — число конвейера агрегации) |
| **Строки с ошибками** | Сколько строк возвращает ваш SELECT только для чтения: строки, которых быть не должно. 0 — это норма (в MongoDB — документы, которыми заканчивается конвейер) |

Каждая проверка выполняется каждые 15 минут, час, 6 часов или день как одна агрегирующая команда в транзакции только для чтения с тайм-аутом команды. Её значение записывается как `oneuptime.data.check.value` вместе с `oneuptime.data.check.id`, `oneuptime.data.check.name` и `oneuptime.data.check.segment`.

## Предлагаемые проверки

**Предлагаемые проверки** на той же вкладке предлагают проверки, которых требуют столбцы таблицы, только по их именам и типам: id уникален, у `customer_id` есть соответствующая строка в `customers`, email похож на email, сумма не отрицательна, статус сохраняет свои обычные значения, а таблица, разделённая по тенантам, подсчитывается по каждому тенанту. Столбец, о котором Безопасность данных знает, что в нём адрес email, номер телефона или IP-адрес, проверяется на соответствие этому формату, как бы он ни назывался. Добавьте одну проверку, добавьте все или навсегда скройте одну из них.

## Проверка по фразе

**Написать проверку по фразе** превращает правило вроде «у заказов никогда не бывает отрицательной суммы» в проверку «Свой SQL», которая на SQL вашей СУБД считает строки, нарушающие правило, и оповещает, когда такие строки есть. Вы читаете запрос до того, как **Добавить проверку** добавит его, и к нему применяются все те же ограничения, что и к любой проверке «Свой SQL». Для этого в проекте должен быть включён OneUptime AI. Для MongoDB результатом будет конвейер агрегации.

## Сегменты

**Разбить по** выполняет проверку отдельно для каждого значения столбца, например тенанта или региона: по одному ряду и одному оповещению на каждое значение, для 100 крупнейших сегментов. Сегментированная проверка «Число строк» оповещает, когда один тенант перестаёт присылать данные, а остальные продолжают.

## Оповещения по проверке

Задайте **Оповещать, когда**, чтобы получать оповещения по проверке:

- **Необычно высоко** или **Необычно низко** сравнивает каждое значение с его собственным изученным базовым уровнем для этого часа недели.
- **Выше** или **Ниже** сравнивает его с порогом.

При сохранении проверки для неё создаётся монитор метрик — от вашего имени и с вашими разрешениями. Если убрать условие, монитор удаляется.

**Статус** проверки в разделе **Проверки** и на вкладке **Проверки** её таблицы показывает, в каком она состоянии: **Сбой**, пока её оповещение открыто, **Проходит**, пока оно закрыто, и **Не удалось выполнить**, если её запрос завершился ошибкой. У проверки без оповещения статус только **Выполнено**: её запрос сработал. Проверка со сбоем и проверка, которую не удалось выполнить, видны и на странице **Обзор**.

## Во что обходится проверка

Проверка конкурирует с вашим приложением за базу данных, а в хранилище, которое тарифицирует по объёму прочитанного запросом, ещё и стоит денег. Это держат в руках три вещи:

- **Процент выборки** читает долю строк вместо всех, для проверки, которая читает долю: «Доля NULL», «Среднее», «Доля недопустимых значений» и «Доля несоответствий формату». Большинство СУБД пропускают целые страницы таблицы; MySQL, Redshift, ClickHouse и MongoDB всё равно читают каждую строку, и им экономится только остальная работа. Dataverse выборку не делает: проверка там читает каждую строку. Представление может отказаться от этого, и проверка сообщит об этом.
- **Максимум для чтения проверкой (ГБ)** в разделе **Настройки** останавливает проверку в BigQuery или Athena, прежде чем она прочитает больше этого числа гигабайт. По умолчанию это 10, пока вы его не измените.
- **Ждать, когда база данных занята** в разделе **Настройки** откладывает назревшие проверки до следующего сбора, когда база данных PostgreSQL, MySQL или SQL Server выглядит занятой. Включено, пока вы не выключите, и база данных сообщает, когда проверки ждали.

## Проваленные строки

Число говорит, что что-то не так; несколько строк говорят, что именно. **Сохранять проваленные строки** в разделе **Настройки** хранит до 20 строк, которые нашла проверка «Строки с ошибками», «Доля недопустимых значений», «Доля несоответствий формату» или «Число осиротевших строк», а **Строки с ошибками** на проверке их показывает. Этот параметр выключен, пока вы его не включите. Конфиденциальные столбцы маскируются там, где читается строка, по тому, что в них нашла Безопасность данных, или по их именам, поэтому то, что покидает базу данных или зонд, уже замаскировано. Конфиденциальный столбец, который не нашло ни одно сканирование и имя которого его не выдаёт, хранится как есть.

Строки хранятся в OneUptime: на серверах OneUptime в OneUptime Cloud и на ваших собственных при самостоятельном размещении. Их может видеть каждый, кто может читать проверки проекта. Проверка хранит только строки своего последнего запуска, а выключение **Сохранять проваленные строки** удаляет всё, что сохранила каждая проверка.

## Проверки в файле

Проверки, написанные вручную, расходятся с кодом, который меняет таблицы. Храните их в репозитории и проверяйте в том же pull request:

```yaml
checks:
  - name: Orders have a total
    table: public.orders
    type: Null Percent
    column: total
    every: 60
    alert: { when: Above, threshold: 1 }
  - name: Emails look right
    table: public.customers
    database: Orders database
    type: Format Mismatch Percent
    column: email
    format: Email
    sample_percent: 10
  - name: Orders have a customer
    table: public.orders
    type: Orphan Count
    column: customer_id
    references: public.customers.id
  - name: No negative totals
    table: public.orders
    type: Failing Rows
    query: SELECT id FROM orders WHERE total < 0
    alert: { when: Above, threshold: 0 }
```

Применяйте файл из CI с помощью [CLI OneUptime](/docs/cli/index) и API-ключа:

```bash
oneuptime data-checks apply checks.yaml --dry-run
oneuptime data-checks apply checks.yaml --prune
```

Проверка считается той же самой, если у неё то же имя в той же таблице, поэтому повторное применение файла ничего не меняет. Ошибка в любом месте файла ничего не применяет и завершается с ошибкой, поэтому запускайте `--dry-run` в pull request, а применяйте при слиянии. С `--prune` проверка, которую создало предыдущее применение и которой больше нет в файле, удаляется. Проверка, добавленная вручную, не удаляется никогда. Проверка из файла помечена об этом в своей строке, и её следующее применение перезапишет то, что было изменено вручную.

Ключи: `name`, `table`, `database`, `type`, `column`, `segment`, `accepted_values`, `format`, `pattern`, `references`, `query`, `sample_percent`, `every`, `alert`, `description` и `enabled`.

## Сверки

Копии расходятся: в аналитическом хранилище меньше заказов, чем в базе данных приложения, или миграция потеряла строки. Сверка сравнивает один показатель двух таблиц — в одной базе данных или в двух — в разделе **Сверки**:

- **Число строк**
- **Сумма** по столбцу
- **Число уникальных значений** по столбцу
- **Свой SQL**: запрос только для чтения, который возвращает одно число под именем `value`

У неё есть допуск: **Абсолютный**, то есть фиксированная величина, или **Процент** от значения источника. Каждую сторону читает своя проверка, которую сверка создаёт и поддерживает, вместе со сбором своей базы данных, поэтому сверка может сравнить таблицу PostgreSQL в вашей сети с её копией в Snowflake. Два значения сравниваются, когда оба прочитаны с разницей не более 15 минут. Сверка пишет:

- `oneuptime.data.reconciliation.drifted`: 1, когда значения разошлись сильнее допуска, 0, когда они совпадают. Её читает монитор сверки.
- `oneuptime.data.reconciliation.difference`: значение цели минус значение источника.
- `oneuptime.data.reconciliation.difference_percent`: разница в процентах от значения источника.

Копия, загружаемая по расписанию, отстаёт от источника: сравнивайте с помощью своего SQL показатель, который у обеих уже устоялся, например строки старше часа, или заложите отставание в допуск.

## Тесты dbt

После сборки dbt команда `oneuptime dbt upload` отправляет артефакты проекта (см. [Происхождение данных и пайплайны](/docs/data-observability/lineage-and-pipelines)). После этого каждый тест отслеживаемой таблицы отображается на её вкладке **Проверки** с последним результатом и строками, на которых он не прошёл. Выберите **Оповещать о сбоях**, чтобы непрошедший тест открывал оповещение.
