# Происхождение данных и пайплайны

Происхождение данных показывает, из каких таблиц строится каждая таблица и какие пайплайны в неё пишут. Наблюдаемость данных собирает его сразу из шести мест — событий OpenLineage, dbt, синхронизаций Fivetran и Airbyte, заданий в ваших трассировках, представлений и собственной истории запросов каждой базы данных — и использует, чтобы связать каждую опаздывающую или сломанную таблицу с запуском, который за этим стоит, так что одна неполадка открывает одну проблему.

## Откуда берётся происхождение данных

| Источник | Что он даёт |
| --- | --- |
| **OpenLineage** | Каждый запуск задания Airflow, Dagster, Spark, dbt или Flink и таблицы, которые оно прочитало и записало |
| **dbt** | Из чего строится каждая модель, каждая сборка как запуск и результат каждого теста |
| **Fivetran и Airbyte** | Каждая синхронизация как запуск её коннектора и сырые таблицы, которые она загружает |
| **Задания в ваших трассировках** | Kubernetes CronJob или запланированная функция, их запуски и таблицы, которые читали и записывали их обращения к базе данных |
| **Представления** | Представление строится из таблиц, на которых оно определено (PostgreSQL, Redshift, MySQL 8, SQL Server, Oracle, Snowflake, материализованные представления ClickHouse, Databricks, MongoDB) |
| **История запросов** | Запрос, который прочитал одну таблицу и записал другую (история доступа Snowflake, задания BigQuery, журнал запросов Redshift, журнал запросов ClickHouse, таблица происхождения Databricks) |

Вкладка **Происхождение** таблицы показывает таблицы, из которых она строится, пайплайны, которые в неё пишут, с их последним запуском, и таблицы, построенные из неё. У каждой связи указано, где она замечена.

Вверху вкладки диаграмма рисует это происхождение на несколько шагов в каждую сторону (три или выберите 1, 2 или 5): слева то, из чего строится таблица, справа таблицы и дашборды, построенные из неё, а пайплайны, загружающие данные извне, — там, где эти данные входят. Каждая карточка показывает, как обстоят дела сейчас: опоздание, открытое оповещение, неудачный запуск, — а стрелка становится красной, когда последний запуск её пайплайна завершился ошибкой, так что от опоздавшей таблицы можно дойти до запуска, который её остановил. Откройте любую таблицу, чтобы поставить её в центр диаграммы.

Карточка показывает не больше десяти таблиц в каждую сторону и считает остальные, например **+14**. Выберите это число, чтобы дорисовать ещё до десяти из них на своих местах, сначала проблемные, со всеми стрелками между ними и тем, что уже нарисовано. **Сбросить диаграмму** возвращает диаграмму к тому виду, в каком она была нарисована сначала. Когда на одной стороне столько таблиц, сколько вмещает диаграмма, откройте таблицу, чтобы поставить её в центр диаграммы.

Там, где источник называет столбцы, вкладка **Столбцы** таблицы показывает, откуда берётся каждый столбец и что он питает: история доступа Snowflake (редакция Enterprise, для которой нужен `IMPORTED PRIVILEGES` на базе `SNOWFLAKE`) и фасет `columnLineage` в OpenLineage.

На вкладке **Происхождение** выберите один из столбцов таблицы в поле **Проследить столбец**, чтобы выделить, откуда он берётся и куда идёт: вверх по диаграмме к столбцам, из которых он строится, и вниз к столбцам, которые строятся из него, причём на каждой таблице назван её столбец, даже если по пути его переименовали. Стрелка, источники которой не называют столбцов, может нести его дальше, чем выделено, и диаграмма об этом говорит.

## OpenLineage

Отправляйте события OpenLineage в OneUptime без изменений, с [ключом приёма](/docs/telemetry/ingestion-keys) телеметрии:

- **URL:** `https://oneuptime.com/telemetry/openlineage` (в самостоятельно размещённом OneUptime — ваш собственный адрес)
- **Эндпоинт:** `api/v1/lineage`, значение OpenLineage по умолчанию
- **API-ключ:** ключ приёма, отправляемый как `Authorization: Bearer`, или задайте `x-oneuptime-token`

Для провайдера OpenLineage в Airflow:

```bash
AIRFLOW__OPENLINEAGE__TRANSPORT='{"type": "http", "url": "https://oneuptime.com/telemetry/openlineage", "endpoint": "api/v1/lineage", "auth": {"type": "api_key", "apiKey": "YOUR_INGESTION_KEY"}}'
```

Для любого другого клиента OpenLineage задайте `OPENLINEAGE_URL` и `OPENLINEAGE_API_KEY`. Наборы данных сопоставляются с таблицами по спецификации именования OpenLineage, например `postgres://host:5432` с `database.schema.table`, `snowflake://account` с `database.schema.table`, `clickhouse://host:8443` с `database.table` и `databricks://workspace-host` с `catalog.schema.table`.

## dbt

После `dbt build` (или run, test, seed либо snapshot) отправьте артефакты проекта с помощью [OneUptime CLI](/docs/cli/index):

```bash
npm install -g @oneuptime/cli
export ONEUPTIME_URL=https://oneuptime.com
export ONEUPTIME_TELEMETRY_INGESTION_KEY=<ingestion key>
dbt build
oneuptime dbt upload
```

В CI запускайте `oneuptime dbt upload` шагом после сборки, даже если сборка завершилась ошибкой, чтобы непрошедшие тесты были записаны. Каждая таблица, которую строит dbt, получает карточку **dbt** на своей вкладке «Обзор», происхождение данных своих моделей и свои тесты на вкладке **Проверки**; каждая сборка — это запуск пайплайна проекта.

## Fivetran и Airbyte

Их вебхуки сообщают, когда каждая синхронизация начинается и заканчивается. **Пайплайны > Подключить Fivetran или Airbyte** заполняет URL одним из ваших ключей приёма:

- **Fivetran:** вебхук, созданный через REST API Fivetran, для событий `sync_start` и `sync_end`, на `https://oneuptime.com/telemetry/fivetran/v1/webhook/<ingestion key ID>`, с ключом приёма в качестве секрета. Fivetran подписывает им каждую доставку, поэтому ключ никогда не передаётся в URL.
- **Airbyte:** вебхук рабочей области, указывающий на `https://oneuptime.com/telemetry/airbyte/v1/webhook/<ingestion key>` и включённый для неудачных и успешных синхронизаций. Выдайте Airbyte отдельный ключ.

Синхронизация Fivetran, перенесённая из-за ограничения частоты запросов к API, завершается со статусом **Перенесена**: это не сбой, поэтому она никого не вызывает.

## Задания в ваших трассировках

Многие пайплайны — это Kubernetes CronJob или функция по таймеру, без планировщика, который отправлял бы данные о происхождении. Их трассировки всё равно рассказывают всё, и ничего устанавливать не нужно. Каждые пятнадцать минут спаны с атрибутом ресурса `k8s.cronjob.name` или `k8s.job.name`, либо `faas.name` с `faas.trigger`, равным `timer` или `datasource`, становятся пайплайном в разделе **Пайплайны**:

- Запуск CronJob — это его Kubernetes Job, а запуск функции — её `faas.invocation_id`.
- Запуск считается неудачным, если неудачным оказался спан на вершине его трассировки. Вызов, который завершился ошибкой и был повторён внутри запуска, его неудачным не делает.
- Таблицы, которые он записал и прочитал, берутся из его спанов базы данных.

Каждый запуск ссылается на свою трассировку вместе с её журналами. Действуют те же три монитора, поэтому CronJob, который перестал запускаться, считается опаздывающим.

## Дашборды в BI-инструментах

Настоящие последствия плохих данных — это дашборд, который кто-то открывает. В разделе **BI-дашборды** добавьте свои BI-инструменты с учётными данными, которым разрешено читать их дашборды. Каждый час Наблюдаемость данных читает каждый дашборд и таблицы за ним, сопоставляет каждую таблицу с отслеживаемой и показывает дашборды, построенные на таблице и на таблицах, построенных из неё, на её вкладке **Происхождение**, в её оповещениях и в Production Review.

| Инструмент | Учётные данные |
| --- | --- |
| **Metabase** | `{ "apiKey": "mb_..." }` |
| **Superset** | `{ "username": "...", "password": "..." }` |
| **Tableau** | `{ "tokenName": "...", "tokenSecret": "...", "site": "acme" }` |
| **Looker** | `{ "clientId": "...", "clientSecret": "..." }` |
| **Power BI** | `{ "tenantId": "...", "clientId": "...", "clientSecret": "..." }`, субъект-служба (service principal) с правом использовать административные API Power BI только для чтения. Читаются и отчёты, и дашборды, с их просмотрами и обновлениями (ниже) |
| **Hightouch** | `{ "apiKey": "..." }` |
| **Census** | `{ "apiKey": "...", "region": "us" }` (или `eu`) |

Hightouch и Census — это инструменты обратного ETL: синхронизация, копирующая таблицу в CRM, зависит от этой таблицы так же, как дашборд, поэтому она читается так же и называется в оповещениях таблицы.

Читаются только названия и ссылки дашбордов, таблицы, к которым они обращаются, а для Power BI — кто их открывает и как прошли их обновления, но никогда их данные.

### Просмотры и обновления в Power BI

Для каждого отчёта и дашборда Power BI раздел **BI-дашборды** сначала показывает, сколько раз его открывали за последние 28 дней, когда его открывали в последний раз и как прошло последнее обновление его данных, а для неудачного обновления — его ошибку. Сколько человек его открывали, кто открывал его чаще всех и его последние обновления — это столбцы, которые можно включить. Вкладка **Происхождение** таблицы говорит то же самое о каждом дашборде, построенном на ней, а его владелец и зрители — под **Ещё**.

- **Просмотры** берутся из журнала действий Power BI через его административный API событий действий. Power BI хранит его 28 дней, отвечает на 200 запросов в час и делит каждый запрос на часы, поэтому OneUptime читает его по часу: каждое ежечасное чтение добавляет часы с прошлого чтения, а затем идёт назад по 28 дням, начиная с новых, не более чем 100 запросами. Новый инструмент Power BI сразу показывает последние дни, а все 28 дней — в течение суток; до тех пор просмотры указывают, с какого момента они считаются. Событие может попасть в журнал с задержкой до часа, поэтому просмотры отстают до двух часов. Зрители называются так, как их называет Power BI, — по адресу электронной почты.
- **Обновления** наборов данных в ёмкости (Premium, Premium на пользователя или Fabric) берутся из административного списка обновляемых элементов Power BI: последнее обновление каждого набора данных с его ошибкой, а также сколько обновлений выполнилось и завершилось неудачей за семь дней, которые хранит Power BI.
- **Обновлений наборов данных в общей ёмкости** в этом списке нет. Power BI показывает журнал обновлений набора данных только тем, кто может его изменять, поэтому добавьте субъект-службу в его рабочую область как **Соавтор**, **Участник** или **Администратор** и включите для неё **Service principals can call Fabric public APIs** в параметрах разработчика портала администрирования Fabric. Тогда OneUptime читает каждое обновление с его ошибкой. До тех пор BI-инструмент сообщает, для скольких наборов данных он не смог прочитать обновления.
- Дашборд Power BI, плитки которого берутся из нескольких наборов данных, показывает последнее неудачное обновление, а если неудачных не было — самое старое: его данные свежи лишь настолько.

Просмотрам и обновлениям в ёмкостях не нужно ничего сверх административного доступа к API выше: субъект-служба в группе безопасности, разрешённой параметром **Service principals can access read-only admin APIs**, без разрешений Power BI в приложении, требующих согласия администратора. Если просмотры или обновления не удаётся прочитать, дашборды всё равно читаются и сохраняются, BI-инструмент сообщает, что было пропущено и почему, а следующее чтение пробует снова.

### Оповещения о неудачных обновлениях

Включите **Alert on Failed Refreshes**, когда добавляете или изменяете инструмент Power BI (у нового он уже включён), и OneUptime будет вести для инструмента один монитор в разделе **Мониторы**, названный по инструменту. Монитор открывает оповещение для каждого набора данных, последнее обновление которого завершилось ошибкой или было отменено, с набором данных и его рабочей областью в заголовке оповещения, и закрывает его, как только более позднее обновление завершится успешно. Набор данных, опубликованный позже, отслеживается, как только его прочитают. Если выключить переключатель или удалить инструмент, монитор удаляется; до тех пор это обычный монитор со своими владельцами, политиками дежурств и окнами обслуживания.

Неудачные обновления не используют мониторы пайплайнов. Набор данных, обновление которого не удалось, продолжает показывать данные своего последнего успешного обновления, пока не завершится более позднее, поэтому его оповещение остаётся открытым до тех пор, тогда как оповещение о неудачном запуске закрывается через час после запуска. К тому же обновления читаются раз в час: обновление, прочитанное с опозданием до часа, часто выпадало бы из часа, на который смотрит **Pipeline Run Failed**, набор данных, обновляемый каждые полчаса, то и дело становился бы **Pipeline Is Late**, а закончившееся, но ещё не прочитанное обновление выглядело бы как **Pipeline Run Unusually Long**.

- Каждое ежечасное чтение сохраняет наборы данных, последнее завершённое обновление которых закончилось ошибкой или было отменено. Каждые пять минут каждый из них записывает `oneuptime.data.bi.refresh_failed`: 1, пока сбой продолжается, и 0 в течение часа после того, как более позднее обновление завершится успешно, а монитор читает это значение, поэтому один сбой открывает одно оповещение, сколько бы ежечасных чтений его ни увидело.
- Сбой замечается при следующем ежечасном чтении: оповещение открывается не позже чем через час после неудачного обновления и закрывается не позже чем через час после того, как более позднее обновление завершится успешно.
- Обновление, которое ещё идёт, ничего не меняет: оповещение набора данных, обновление которого не удалось, остаётся открытым, пока выполняется его следующее обновление, и закрывается только после успешного обновления.
- В ёмкости список обновляемых элементов Power BI даёт только последнее обновление каждого набора данных, поэтому обновление, которое не удалось и за которым в течение того же часа последовало успешное, никогда не будет замечено: к тому времени данные снова свежие.
- Наборы данных в общей ёмкости дают оповещения только там, где их обновления можно прочитать (см. выше), а набор данных, обновления которого прочитать не удалось, сохраняет своё оповещение как было, пока их не удастся прочитать.

## Пайплайны

Каждое задание, проект dbt и синхронизация отображаются в разделе **Пайплайны** со своими запусками: когда каждый начался и закончился, сколько он длился, какой это была попытка там, где это сообщает планировщик (номер попытки в Airflow), и с какой ошибкой завершился неудачный запуск. После пяти запусков каждый пайплайн по своим же запускам знает, сколько обычно длится запуск и сколько времени проходит между запусками по его расписанию. Страница пайплайна рекомендует три монитора:

- **Pipeline Run Failed**: запуск завершился ошибкой или был прерван.
- **Pipeline Run Unusually Long**: запуск длится вдвое дольше обычного или больше; это проверяется каждые пять минут, пока он идёт, поэтому зависший запуск заметен ещё до его окончания.
- **Pipeline Is Late**: ни один запуск не начинался дольше, чем позволяет его расписание.

На странице пайплайна есть карточка **Происхождение** — первое, куда стоит смотреть, когда запуск завершился ошибкой или опаздывает: слева таблицы, которые он читает, справа таблицы, в которые он пишет, между ними сам пайплайн, и каждая карточка показывает, как обстоят дела сейчас. Выберите больше шагов, чтобы увидеть, из чего строятся эти таблицы и что строится из них, и откройте любую таблицу, чтобы увидеть её собственную вкладку **Происхождение**. Число ненарисованных таблиц на карточке пайплайна или таблицы и здесь дорисовывает их на месте.

## Одна проблема на одну причину

Когда таблица устаревает, устаревает и каждая таблица, построенная из неё. Прежде чем открыть оповещение о данных, OneUptime ищет по происхождению данных уже открытое оповещение на том, из чего строится его таблица или пайплайн: на вышестоящих таблицах, на пайплайнах, которые в них пишут, и на базах данных, где они находятся, — до пяти шагов вверх. Если такое оповещение найдено, новое оповещение становится его следствием:

- Оно сразу **подтверждено**, поэтому никого не вызывают дважды из-за одной неполадки, и восстанавливается само, когда восстанавливаются его данные.
- Его лента и карточка **Данные** показывают, какое оповещение его вызвало, и оно присоединяется к эпизоду причины.

Карточка **Данные** у причины перечисляет её **Влияние на downstream**: все оповещения, которые она вызвала. Карточка оповещения по таблице также показывает сервисы, которые пишут в таблицу, с их неудачными записями, а также их развёртывания и другие изменения за сутки до оповещения.

Под карточкой **Данные** на странице оповещения есть карточка **Происхождение**: происхождение вокруг его таблицы, как его рисует вкладка **Происхождение** этой таблицы, или вокруг его пайплайна. Путь вверх к оповещению, которое его вызвало, и вниз к каждому оповещению, которое вызвало оно, выделен: таблица или пайплайн причины помечены как **Причина**, таблица каждого вызванного оповещения — как **Следствие**, а остальное приглушено, так что тот, кто его открывает, видит, где в цепочке началась проблема. Если причина — пайплайн, нарисованный на стрелке, на этой стрелке под именем пайплайна написано **Причина**. Если причина относится ко всей базе данных или находится выше, чем достаёт диаграмма, карточка говорит об этом словами. Оповещение от проверки одного столбца, например проверки «Доля NULL» для `customer_id`, открывается с этим столбцом, прослеженным рядом с этими путями, как на вкладке **Происхождение** таблицы: откуда он берётся и куда идёт, с его именем на каждой таблице. Там можно выбрать другой столбец таблицы или очистить выбор, чтобы видеть только пути. **Изучить происхождение** открывает вкладку **Происхождение** таблицы или страницу пайплайна.

Тот, кому нельзя видеть оповещение, которое его вызвало, не получает ни карточки **Данные**, ни происхождения, а вызванное оповещение, которое ему нельзя видеть, не выделяется и не учитывается.

## До слияния изменения

Когда pull request меняет отслеживаемую таблицу, [Production Review](/docs/ai/ai-agent) пишет в этом pull request, что от неё зависит: сервисы, которые её читают, таблицы, построенные из неё, дашборды на ней и её продукты данных. Если у таблицы есть копия в базе данных, помеченной как Staging, там же сказано, чем копия отличается: строками, столбцами и тем, что читают там проверки таблицы, выполненные на месте. В базе данных, до которой может добраться только зонд, проверки пропускаются, и об этом сказано.
