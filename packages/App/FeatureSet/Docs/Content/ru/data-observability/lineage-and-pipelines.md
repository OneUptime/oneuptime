# Происхождение данных и пайплайны

Происхождение данных показывает, из каких таблиц строится каждая таблица и какие пайплайны в неё пишут. Наблюдаемость данных собирает его сразу из пяти мест — событий OpenLineage, dbt, синхронизаций Fivetran и Airbyte, представлений и собственной истории запросов каждой базы данных — и использует, чтобы связать каждую опаздывающую или сломанную таблицу с запуском, который за этим стоит, так что одна неполадка открывает одну проблему.

## Откуда берётся происхождение данных

| Источник | Что он даёт |
| --- | --- |
| **OpenLineage** | Каждый запуск задания Airflow, Dagster, Spark, dbt или Flink и таблицы, которые оно прочитало и записало |
| **dbt** | Из чего строится каждая модель, каждая сборка как запуск и результат каждого теста |
| **Fivetran и Airbyte** | Каждая синхронизация как запуск её коннектора и сырые таблицы, которые она загружает |
| **Представления** | Представление строится из таблиц, на которых оно определено (PostgreSQL, Redshift, MySQL 8, SQL Server, Oracle, материализованные представления ClickHouse, Databricks, MongoDB) |
| **История запросов** | Запрос, который прочитал одну таблицу и записал другую (задания BigQuery, журнал запросов Redshift, журнал запросов ClickHouse, таблица происхождения Databricks) |

Вкладка **Происхождение** таблицы показывает таблицы, из которых она строится, пайплайны, которые в неё пишут, с их последним запуском, и таблицы, построенные из неё. У каждой связи указано, где она замечена.

## OpenLineage

Отправляйте события OpenLineage в OneUptime без изменений, с [ключом приёма](/docs/telemetry/ingestion-keys) телеметрии:

- **URL:** `https://oneuptime.com/telemetry/openlineage` (в самостоятельно размещённом OneUptime — ваш собственный адрес)
- **Эндпоинт:** `api/v1/lineage`, значение OpenLineage по умолчанию
- **API-ключ:** ключ приёма, отправляемый как `Authorization: Bearer`, или задайте `x-oneuptime-token`

Для провайдера OpenLineage в Airflow:

```bash
AIRFLOW__OPENLINEAGE__TRANSPORT='{"type": "http", "url": "https://oneuptime.com/telemetry/openlineage", "endpoint": "api/v1/lineage", "auth": {"type": "api_key", "apiKey": "YOUR_INGESTION_KEY"}}'
```

Для любого другого клиента OpenLineage задайте `OPENLINEAGE_URL` и `OPENLINEAGE_API_KEY`. Наборы данных сопоставляются с таблицами по спецификации именования OpenLineage, например `postgres://host:5432` с `database.schema.table`, `snowflake://account` с `database.schema.table`, `clickhouse://host:8443` с `database.table` и `databricks://workspace-host` с `catalog.schema.table`.

## dbt

После `dbt build` (или run, test, seed либо snapshot) отправьте артефакты проекта с помощью [OneUptime CLI](/docs/cli/index):

```bash
npm install -g @oneuptime/cli
export ONEUPTIME_URL=https://oneuptime.com
export ONEUPTIME_TELEMETRY_INGESTION_KEY=<ingestion key>
dbt build
oneuptime dbt upload
```

В CI запускайте `oneuptime dbt upload` шагом после сборки, даже если сборка завершилась ошибкой, чтобы непрошедшие тесты были записаны. Каждая таблица, которую строит dbt, получает карточку **dbt** на своей вкладке «Обзор», происхождение данных своих моделей и свои тесты на вкладке **Проверки**; каждая сборка — это запуск пайплайна проекта.

## Fivetran и Airbyte

Их вебхуки сообщают, когда каждая синхронизация начинается и заканчивается. **Пайплайны > Подключить Fivetran или Airbyte** заполняет URL одним из ваших ключей приёма:

- **Fivetran:** вебхук, созданный через REST API Fivetran, для событий `sync_start` и `sync_end`, на `https://oneuptime.com/telemetry/fivetran/v1/webhook/<ingestion key ID>`, с ключом приёма в качестве секрета. Fivetran подписывает им каждую доставку, поэтому ключ никогда не передаётся в URL.
- **Airbyte:** вебхук рабочей области, указывающий на `https://oneuptime.com/telemetry/airbyte/v1/webhook/<ingestion key>` и включённый для неудачных и успешных синхронизаций. Выдайте Airbyte отдельный ключ.

Синхронизация Fivetran, перенесённая из-за ограничения частоты запросов к API, завершается со статусом **Перенесена**: это не сбой, поэтому она никого не вызывает.

## Дашборды в BI-инструментах

Настоящие последствия плохих данных — это дашборд, который кто-то открывает. В разделе **BI-дашборды** добавьте свои BI-инструменты с учётными данными, которым разрешено читать их дашборды. Каждый час Наблюдаемость данных читает каждый дашборд и таблицы за ним, сопоставляет каждую таблицу с отслеживаемой и показывает дашборды, построенные на таблице и на таблицах, построенных из неё, на её вкладке **Происхождение**, в её оповещениях и в Production Review.

| Инструмент | Учётные данные |
| --- | --- |
| **Metabase** | `{ "apiKey": "mb_..." }` |
| **Superset** | `{ "username": "...", "password": "..." }` |
| **Tableau** | `{ "tokenName": "...", "tokenSecret": "...", "site": "acme" }` |
| **Looker** | `{ "clientId": "...", "clientSecret": "..." }` |
| **Power BI** | `{ "tenantId": "...", "clientId": "...", "clientSecret": "..." }`, субъект-служба (service principal) с правом использовать административные API Power BI |

Читаются только названия и ссылки дашбордов и таблицы, к которым они обращаются, но никогда их данные.

## Пайплайны

Каждое задание, проект dbt и синхронизация отображаются в разделе **Пайплайны** со своими запусками: когда каждый начался и закончился, сколько он длился и с какой ошибкой завершился неудачный запуск. После пяти запусков каждый пайплайн по своим же запускам знает, сколько обычно длится запуск и сколько времени проходит между запусками по его расписанию. Страница пайплайна рекомендует три монитора:

- **Pipeline Run Failed**: запуск завершился ошибкой или был прерван.
- **Pipeline Run Unusually Long**: запуск длится вдвое дольше обычного или больше; это проверяется каждые пять минут, пока он идёт, поэтому зависший запуск заметен ещё до его окончания.
- **Pipeline Is Late**: ни один запуск не начинался дольше, чем позволяет его расписание.

## Одна проблема на одну причину

Когда таблица устаревает, устаревает и каждая таблица, построенная из неё. Прежде чем открыть оповещение о данных, OneUptime ищет по происхождению данных уже открытое оповещение на том, из чего строится его таблица или пайплайн: на вышестоящих таблицах, на пайплайнах, которые в них пишут, и на базах данных, где они находятся, — до пяти шагов вверх. Если такое оповещение найдено, новое оповещение становится его следствием:

- Оно сразу **подтверждено**, поэтому никого не вызывают дважды из-за одной неполадки, и восстанавливается само, когда восстанавливаются его данные.
- Его лента и карточка **Данные** показывают, какое оповещение его вызвало, и оно присоединяется к эпизоду причины.

Карточка **Данные** у причины перечисляет её **Downstream Impact**: все оповещения, которые она вызвала. Карточка оповещения по таблице также показывает сервисы, которые пишут в таблицу, с их неудачными записями, а также их развёртывания и другие изменения за сутки до оповещения.
