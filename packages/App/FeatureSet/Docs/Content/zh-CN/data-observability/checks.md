# 检查与对账

表健康说明表是否在更改。**检查** 说明表中保存的内容是否正确，**对账** 说明数据的两个副本是否一致，**dbt 的测试** 则报告 dbt 构建的表的情况。它们都在数据库的采集运行的地方运行（由 OneUptime 或其探测器执行），离开数据库的只有一个数字。

## 检查

在表的 **检查** 标签页上添加检查：

| 检查 | 读取的内容 |
| --- | --- |
| **Null Percent** | 该列为空的行所占的百分比 |
| **Duplicate Percent** | 与其他行的值重复的值所占的百分比 |
| **Distinct Count** | 该列包含多少个不同的值 |
| **最小值**、**最大值**、**平均值**、**总和** | 数值列的相应值（没有行时总和为 0） |
| **Invalid Percent** | 不在你给出的列表中的值所占的百分比 |
| **Format Mismatch Percent** | 不匹配正则表达式的值所占的百分比（SQL Server 以外的所有引擎） |
| **Orphan Count** | 其值在另一个表的列中没有匹配项的行 |
| **Row Count** | 表中的行数，与 **Segment By** 搭配使用最有用 |
| **自定义 SQL** | 你的一条只读 SELECT 返回的、名为 `value` 的数字 |

每个检查每 15 分钟、每小时、每 6 小时或每天运行一次，作为一条聚合语句，在带有语句超时的只读事务中执行。它的值写入为 `oneuptime.data.check.value`，并带有 `oneuptime.data.check.id`、`oneuptime.data.check.name` 和 `oneuptime.data.check.segment`。

## 建议的检查

同一标签页上的 **Suggested Checks** 会仅根据列的名称和类型，提供表的列所需要的检查：id 是唯一的、`customer_id` 在 `customers` 中有匹配的行、电子邮件看起来像电子邮件、金额不是负数、状态保持其通常的值，以及按租户拆分的表按租户计数。你可以添加一个、全部添加，或者永久隐藏某一个。

## 用一句话编写检查

**用一句话编写检查** 会把“订单的总额从不为负”这样的规则，用你的引擎自己的 SQL 转换成统计违反该规则的行的自定义 SQL 检查，并在有任何违反时发出警报。在用 **添加检查** 添加之前，你可以先阅读查询，它也受到与任何自定义 SQL 检查相同的所有限制。这需要为项目开启 OneUptime AI。

## 分段

**Segment By** 会针对某一列的每个值（例如租户或区域）各运行一次检查：最大的 100 个分段各有一个序列和一个警报。分段的 Row Count 检查会在某个租户停止发送数据、而其他租户仍在继续发送时发出警报。

## 检查的警报

设置 **Alert When** 以针对检查发出警报：

- **Unusually High** 或 **Unusually Low** 会把每个值与它自己在每周该时段学习到的基线进行比较。
- **高于** 或 **低于** 会把它与阈值进行比较。

保存检查时，会以你的身份、按你的权限为它创建一个指标监视器。清除该条件会删除该监视器。

## 对账

副本会出现偏差：数据仓库中的订单比应用程序的数据库少，或者一次迁移丢失了行。对账会在 **对账** 下比较两个表（位于同一个数据库或两个数据库中）的一个度量：

- **Row Count**
- 某一列的 **总和**
- 某一列的 **Distinct Count**
- **自定义 SQL**：一个返回名为 `value` 的数字的只读查询

它有一个容差：一个 **绝对值** 数量，或来源值的一个 **百分比**。每一端都由对账创建并维护的一个专属检查读取，并随其数据库的采集一起进行，因此对账可以把你网络中的 PostgreSQL 表与它在 Snowflake 中的副本进行比较。两个值都在彼此相隔 15 分钟以内被读取后，才会进行比较。对账会写入：

- `oneuptime.data.reconciliation.drifted`：两者的偏差超出容差时为 1，一致时为 0。它的监视器读取的就是这个值。
- `oneuptime.data.reconciliation.difference`：目标的值减去来源的值。
- `oneuptime.data.reconciliation.difference_percent`：该差值占来源值的百分比。

按计划加载的副本会落后于其来源：可以用自定义 SQL 比较两者都已稳定的度量，例如一小时以前的行，或者在容差中为延迟留出余量。

## dbt 测试

dbt 构建完成后，`oneuptime dbt upload` 会发送项目的构建产物（请参阅 [血缘与管道](/docs/data-observability/lineage-and-pipelines)）。之后，受监视的表的每个测试都会显示在该表的 **检查** 标签页上，并附上它的最新结果和它发现的失败行。选择 **Alert on Failures**，即可让失败的测试打开一个警报。
