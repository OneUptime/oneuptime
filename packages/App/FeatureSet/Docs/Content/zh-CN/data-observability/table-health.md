# 表健康

每五分钟，每个已连接数据库的目录都会说明每个表的状况：它最后一次更改的时间、包含多少行、有多大，以及它有哪些列。数据可观测性据此学习每个表的节奏，并在表延迟、缩小或结构改变时告诉你，无需设置任何阈值。

## 读取的内容

对每个表和视图：

- **行数和大小**，来自引擎自身的统计信息。
- **最后一次更改的时间**：如果引擎自己记录了时间，就用该时间；否则就是两次采集之间其写入计数器、行数或字节数发生变化的时刻。
- **它的列**，包括列的类型以及是否可以为空。
- **最后一次被读取的时间**，前提是引擎会统计读取。

只读取目录，在 MongoDB 上还会读取集合最新文档的字段名称。没有任何值离开数据库。

## 新鲜度

表的 **节奏** 是指它通常多久更改一次，从它各次更改之间的时间间隔中学习得出。远远超出节奏的表会在它的页面和 **表** 中显示为 **延迟**，并写入超出了多久。表更改两次后，就能知道它的新鲜度：每小时加载的表在几小时内就能学会，每晚加载的表在几天内就能学会。

视图本身不包含行，因此它的新鲜度就是其来源的新鲜度：请参阅 [血缘与管道](/docs/data-observability/lineage-and-pipelines)。

目录可能会在只是内部维护发生变化时就说表更改了，也可能什么都不说。在表的 **设置** 上，指定一个 **新鲜度列**，例如 `updated_at`，它的最后更改时间就变成该列的最新值。该登录需要能够读取此列，并且每次采集都会读取它，因此应为它建立索引；在按查询读取量计费的 BigQuery 和 Athena 上，它每小时读取一次。不带时区的时间按 UTC 处理。

## 数据量和架构变更

- **行** 会在两次采集之间进行比较：丢失一半行的表，或者行数远少于每周该时段通常水平的表，都会如实报告。
- **列** 也会进行比较。新增、删除、重命名、更改类型或改为可为空的列，会记录在该表的 **时间线** 和 **架构变更** 上，后者按从新到旧列出每个数据库的每次变更。被删除、重命名或更改类型的列会破坏读取它的内容，并且可以发出警报。新增的列不会破坏任何内容，只会留在时间线上。
- **被删除的表** 会保留在 **已删除的表** 下，并显示它们最后一次出现的时间；如果该表重新出现，它会连同历史记录一起恢复。

## 推荐的警报

在 **数据库** 上，为某个数据库选择 **推荐的警报**。每项推荐都是覆盖整个数据库的一个指标监视器，每个表警报一次，因此以后创建的表也会受到监视：

| 警报 | 触发条件 |
| --- | --- |
| **Table Is Late** | 表超出其通常的更改时间已持续十五分钟 |
| **Row Count Fell Sharply** | 表在两次采集之间丢失一半或更多的行 |
| **Row Count Unusually Low** | 表的行数远少于每周该时段的通常水平（基于两周的数据学习） |
| **Schema Changed** | 表的列被删除、重命名或更改类型 |
| **Table Health Stopped Reporting** | 该数据库的任何表都已十五分钟没有被读取 |

在创建时选择严重程度、值班策略、所有者和标签。此后它们就是普通的监视器：可以像其他监视器一样编辑、静音，或放到状态页上。

回填或迁移不应该呼叫任何人。在 [维护事件](/docs/scheduled-maintenance/index) 上指定 **Data Observability 数据库** 下的数据库，或者把它的数据库服务器放进去，在该事件进行期间，它的数据警报就会保持安静。

## 每个表写入的指标

每次采集都会为每个表写入这些指标，因此你可以像对待任何其他指标一样，为它们绘制图表、放到仪表板上并据此发出警报：

| 指标 | 含义 |
| --- | --- |
| `oneuptime.data.table.row_count` | 表中的行数 |
| `oneuptime.data.table.size` | 表及其索引占用的字节数 |
| `oneuptime.data.table.seconds_since_change` | 自表最后一次更改以来的秒数 |
| `oneuptime.data.table.overdue_seconds` | 表超出其通常更改时间的秒数；按时时为 0 |
| `oneuptime.data.table.row_count_change_percent` | 与上一次采集相比行数变化的幅度，以百分比表示 |
| `oneuptime.data.table.schema_changes` | 自上一次采集以来发生变化的列数 |
| `oneuptime.data.table.breaking_schema_changes` | 自上一次采集以来被删除、重命名或更改类型的列数 |

每条指标记录都带有 `oneuptime.data.store.id`、`oneuptime.data.store.name`、`oneuptime.data.table.id`、`oneuptime.data.table.schema`、`oneuptime.data.table.name` 和 `oneuptime.data.table.key`（`schema.table`）。按 `oneuptime.data.table.key` 分组的 [指标监视器](/docs/monitor/metrics-monitor) 会对每个表警报一次，它的 **异常偏高** 和 **异常偏低** 筛选条件会把每个表与它自己在每周该时段的通常值进行比较。这些指标是 OneUptime 自身的运维数据，不按遥测计费。

## 未使用的表

每个统计读取的引擎都会说明每个表最后一次被读取的时间：PostgreSQL 的扫描、MySQL 的 performance_schema、SQL Server 的查找、扫描和键查找，以及 Redshift、ClickHouse 和 Databricks 的查询历史。在你的服务的数据库 Span 中看到的读取也会计入。

**未使用的表** 列出 90 天内无人读取的表，最大的排在前面，并显示每个表最后一次被写入的时间：仍在写入却从未被读取的表，白白耗费写入和存储成本。表在首次采集时计数器为 0，意味着自引擎的统计信息开始以来它从未被读取，因此未使用的表从一开始就会显示为未使用。

## 仓库支出

数据可观测性每小时读取每个 Snowflake 和 BigQuery 仓库在过去一天里逐个作业的支出：Snowflake 的计算积分来自 `QUERY_ATTRIBUTION_HISTORY`，BigQuery 的计费字节来自其作业视图，后者需要 **BigQuery Resource Viewer**。作业是反复运行的同一个查询，按其查询标签或 label，或按它做什么和写入的表来命名：绝不使用查询的文本。

**仓库支出** 显示按团队的合计（作业查询标签或 label 中的 `team`，否则为运行者）、写入成本最高的表、失败的作业，以及花在只写入 90 天内无人读取的表的作业上的支出。

## 使用每个表的服务

表的 **服务** 标签页列出观察到正在写入和读取它的服务，并附上每个服务运行的语句、过去一小时的调用和失败次数，以及最后一次出现的时间。这些信息来自你的服务已经通过 OpenTelemetry 发送的数据库 Span：带有 `db.system.name`、`db.namespace` 和 `db.collection.name` 的客户端 Span。无需额外安装任何东西。

只有当 Span 的数据库是某次采集读取过的数据库时，它才会关联到某个表；当两个数据库同名时，还要求它的 `server.address` 是其中之一的地址。

每个服务还会显示发出这些调用的端点（来自同一追踪中的服务器 Span），并且当服务同时调用模型时，会标记为 **AI 应用**。**提到此表的错误** 会列出写入该表的服务中，按名称提到该表的未解决异常和最近一天的错误日志。

## 所有者和标签

表的 **所有者** 标签页写明它属于哪些人和团队，表的警报会发给他们；如果没有所有者，则发给其数据库的所有者。在表的 **设置** 上，可以为它添加你自己的 **标签**。

你不应该需要把这件事做上数百次。**所有者规则** 和 **标签规则** 会在每个表首次出现时应用于它，按它的标签匹配，或者按它的名称、架构或数据库上的正则表达式匹配：`finance` 中的所有内容都归财务团队，所有名为 `*_pii` 的内容都会获得一个标签。

范围限定为 `Owned` 的权限只能触及其持有者或其团队拥有的表，以及这些表的检查、活动和上报的问题。拥有数据库并不等于拥有其中的表：要把整个数据库交给一个团队，请使用所有者规则。

## 警报打开时

表的警报有一张 **数据** 卡片，按排序说明它最可能为什么发生：上游的警报、失败的运行、写入它的服务的部署、它失败的写入、发生变化的列、数据库本身或它所运行的服务器。下面是依赖于它的内容：它血缘下游的表、仪表板、服务以及拥有它们的人。

说说你的判断：

- **Useful**：它是对的。
- **Expected**：计划内的事件。不会有任何变化，下一次也会照常发出警报。
- **不是问题**：给表更多余地，因此下次同样的情况会保持安静。延迟表的通常间隔会变长，行数的容差会放宽。

如果有人先发现了问题，表上的 **报告问题** 会把它记录下来。**概览** 随后会显示 Data Observability 对你的项目表现如何：每周有用的问题数、有多少不是噪音、读取了多少个表、在有人报告之前它提出问题的频率、速度有多快，以及它的可能原因有多少次就是真实原因。
