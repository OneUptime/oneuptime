# 用户、团队与权限

OneUptime 中的一切都存在于**项目**之内。谁能在项目里做什么，取决于三件事：项目中的**用户**、这些用户所属的**团队**，以及授予这些团队的**权限**。

有一条规则可以解释绝大多数行为：**用户从不直接持有权限。** 一个用户的访问权限，是他在该项目中所属的全部团队权限的并集。想改变某人能做什么，就改变他的团队归属，或者改变那个团队的权限。

**所有者**是另一回事。所有者是对某个具体资源负责的人——一个监视器、一个事件、一个仪表板。所有者会收到关于自己资源的通知，权限也可以选择性地收窄为"只针对我拥有的东西"。

## 模型一览

```text
项目
  └── 团队                   ← 权限挂在这里
       ├── 允许权限          ← 每条都有范围：全部 / 拥有 / 标签
       ├── 阻止权限          ← 始终压过允许权限
       └── 团队成员          ← 已接受邀请的用户
```

| 概念 | 含义 |
| --- | --- |
| 用户 | 一个 OneUptime 账号。一次登录，可参与任意多个项目。 |
| 项目 | 租户边界。监视器、事件、团队和数据都恰好属于一个项目。 |
| 团队 | 项目内的具名分组，承载权限。 |
| 团队成员 | 被邀请加入团队并已接受的用户。 |
| 权限 | 一项单独能力，例如 `CreateProjectMonitor`；或打包多项能力的角色，例如 `MonitorAdmin`。 |
| 范围 | 一条允许权限能覆盖多远：全部资源、仅拥有的资源，或仅带标签的资源。 |
| 所有者 | 被标记为某个具体资源负责人的用户或团队。 |
| 标签 | 打在资源上的标记，用于限制权限和整理资源。 |

## 用户

用户账号在整个 OneUptime 实例范围内通用——同一个登录在该用户受邀的每个项目中都有效。

当用户是项目内**至少一个团队**的成员时，他就"在"这个项目里。没有单独的"把用户加入项目"这一步：邀请某人加入项目，就是邀请他加入一个团队。

- 邀请会创建一条待处理的团队成员记录。用户只有在**接受邀请之后**，才算作项目成员，也才获得任何权限。
- 把用户从项目内所有团队中移除，就撤销了他对该项目的访问权限。
- 离开项目的人不会再收到该项目的通知。此人在该项目中的通知方式、通知规则和通知设置会随最后一个团队一起删除（电子邮件、短信、电话、WhatsApp、Telegram、推送、Webhook、Slack 和 Microsoft Teams、电子邮件汇总及尚未发送的邮件、来电号码以及值班提醒），因此重新加入时会从默认设置开始。之后仍然指向此人的内容（例如来电规则拨打的用户，或已解决事件中保留的负责人）不会再通知此人：不会代表项目向非项目成员发送任何内容，待接受的邀请也还不算成员身份。这些位置会在姓名旁显示 **已不再是成员**，方便您换成其他人。已受邀但尚未接受的人则显示 **尚未接受邀请**。如果某个覆盖把某人的呼叫转给了已离开项目的人，则改为呼叫该覆盖所替代的人。离开项目还会断开此人连接到该项目的 MCP 客户端，此人的个人值班日历链接此后显示空日历。在 OneUptime Cloud 上，通过项目的单点登录回来的人需要再次从邮箱确认。
- 如果项目强制使用 SSO，而用户尚未通过身份提供方认证，他会被视为未授权的 SSO 用户，在完成认证之前什么也看不到。参见 [SSO](/docs/identity/sso)。
- 配置 SCIM 后，身份提供方可以自动创建、更新和移除用户及其团队归属。参见 [SCIM](/docs/identity/scim)。

位置：**设置 → 用户**列出项目中的所有人及其邀请状态。

## 团队

团队是权限抵达人的通道。每个新项目都以三个团队开始：

| 团队 | 持有的权限 | 可编辑 |
| --- | --- | --- |
| Owners | `ProjectOwner` | 否。始终至少有一名成员。 |
| Admin | `ProjectAdmin` | 否 |
| Members | `ProjectMember` | 是——它是一个起点，可以随意修改 |

**Owners** 和 **Admin** 团队被刻意锁定：权限无法编辑，团队也不能删除或改名。正是这一点防止项目意外把自己锁在门外。Owners 团队必须始终保留至少一名成员。

`ProjectOwner` 是最高访问级别：账单、删除项目，以及管理员能做的一切。`ProjectAdmin` 涵盖除账单和删除项目之外的全部内容。

为项目开启或关闭短信、语音电话、WhatsApp 或 Telegram 属于账单事务，因为每条消息都要花钱。只有 `ProjectOwner`、`BillingAdmin` 角色（**Billing Admin**）和 `ManageProjectBilling` 权限（**Manage Billing**）可以在 **项目设置 > 通知 > 通知设置** 中更改这些开关，`ProjectAdmin` 不行。

为项目的预付余额充值同样属于账单事务。在 OneUptime Cloud 上，短信、语音电话、WhatsApp 和 Telegram 从 **项目设置 > 通知 > 通知设置** 中的余额支付，AI 从 **项目设置 > 人工智能 > AI 积分** 中的 AI 积分支付。只有项目所有者或拥有 **Manage Billing** 权限的用户才能为它们充值或更改它们的 **自动充值**，项目管理员不行。关于余额不足的消息会说明谁可以充值，只有这些人才会看到可用的 **充值余额** 按钮或页面链接。

你可以创建任意多个额外团队——"前端待命"、"支持"、"只读审计"——并给每个团队它需要的权限。

位置：**设置 → 团队**。打开团队即可进入 **Members** 和 **Permissions**；**Block Permissions** 位于 Permissions 页面底部的 **More settings** 中。

## 权限

权限是一项单独能力。分发方式有两种，都在团队的 **Permissions** 选项卡中。

### 角色

角色把整个产品领域打包为三个层级之一：

- **Admin** — Member 能做的事，外加该领域自己的配置，例如事件与告警的严重级别和状态、监控器状态以及维护状态。
- **Member** — 日常工作：创建、修改和删除该领域的资源，连同它们的备注、所有者和模板。对于状态页和值班，Member 能做 Admin 能做的一切。
- **Viewer** — 只读。

例如 `MonitorAdmin`、`IncidentMember`、`StatusPageViewer` 等。绝大多数情况下你想要的都是角色——随着 OneUptime 新增功能，角色依然正确，因为与监视器相关的新表会并入已有的监视器角色，而不需要你重新授予。

工作流和 Runbook 是例外。两者都会在你的项目中运行代码——工作流运行它的步骤，Runbook 在你的 Runner 上运行它的脚本——所以 `WorkflowMember` 打开工作流及其运行并手动运行它们，`RunbookMember` 打开 Runbook 及其运行并运行它们：开始一次运行、完成或跳过其步骤、取消运行。两者都不能创建、修改或删除它们运行的东西；由 `WorkflowAdmin` 和 `RunbookAdmin` 构建。角色只运行其范围所及的 Runbook：限于部分标签的 `RunbookMember` 只运行带有这些标签的 Runbook。参见 [工作流配置](/docs/workflows/configuration) 和 [Runbook 配置](/docs/runbooks/configuration)。

领域的规则（标签、所有者、值班、分组和提醒规则）、自定义字段、SLA 和密钥属于项目配置：无论某人拥有哪个领域角色，都需要 `ProjectAdmin`。API 密钥、团队及其权限、标签、SSO 和域名也是如此——Settings 角色负责项目的服务、探针、基础设施和集成，而不是谁能做什么。

账单有三个专属角色。`BillingViewer` 读取项目的账单——套餐和订阅、发票、用量、余额、AI 额度、付款方式以及账单联系信息——但不修改任何内容。`BillingMember` 还能下载发票并修改账单联系信息。`BillingAdmin` 能做 `BillingMember` 能做的事，并能开启和关闭短信、电话、WhatsApp 和 Telegram。更改套餐、付款方式或余额以及支付发票需要 `ProjectOwner` 或 **Manage Billing**；在账单页面上，这些按钮对其他所有人都是锁定的，并注明谁可以使用。

全部 {{PERMISSION_ROLE_COUNT}} 个角色列在[权限参考](/docs/permissions/reference)中。

### 细粒度权限

每一项单独能力也可以单独授予——`CreateProjectMonitor`、`ReadProjectIncident`、`DeleteProjectStatusPage`，以及另外 {{PERMISSION_TOTAL_COUNT}} 项。当角色过于宽泛、你只想给出恰好一件事时使用它们。

修改或删除某样东西的权限只作用于你同时能读取的内容，所以请一并授予对应的读取权限：没有 `ReadProjectIncident`，`EditProjectIncident` 不会修改任何事件。通过另一条记录读取的记录（例如事件的备注）还需要读取那条记录的权限：没有读取事件的权限，`ReadIncidentInternalNote` 不会触及任何备注。角色已经同时包含两者。

它们也是创建 API 密钥时使用的键，以及 API 和 Terraform 提供程序期望的值。

完整清单见[权限参考](/docs/permissions/reference)。

### 允许与阻止

每个团队都有两个列表：

- **Permissions**（允许）——这个团队可以做什么。
- **Block Permissions**——无论允许列表怎么写，这个团队永远不能做什么。

**阻止总是获胜。** 不带标签的阻止条目会彻底取消团队的这项能力。带标签的阻止条目只针对带有这些标签的资源取消它——适合"这个团队可以编辑监视器，但带 Production 标签的除外"。

同一项权限不能同时在两个列表中携带限制标签；OneUptime 会拒绝第二条并给出说明。

用户的允许条目会在其所有团队之间累加，但阻止适用于该用户所做的一切：某个团队上不带标签的阻止，即使另一个团队允许，也会取消这项能力；阻止条目本身永远不授予任何权限。如果某人的权限少于预期，请在他所属的每个团队里查找阻止；如果多于预期，请在每个团队里查找允许。

## 范围：一条允许权限能覆盖多远

每条允许权限在添加时都会选定一个范围：

| 范围 | 含义 |
| --- | --- |
| 项目中的全部资源 | 默认值。权限适用于每一个匹配的资源。 |
| 由该团队或其成员拥有 | 权限只适用于该团队或执行操作的用户被列为所有者的资源。 |
| 按标签限制（高级） | 权限只适用于带有所选标签之一的资源。 |

**拥有**是搭建"各自照看自己服务"模型最简单的方式：给团队授予范围为"拥有"的 `MonitorAdmin`，再把该团队设为它负责的那些监视器的所有者。它只会收窄真正能有所有者的资源——监视器、事件、仪表板、服务之类。项目配置（事件状态、标签、团队本身）没有所有者，因此"拥有"范围的角色在那里表现如常。

**标签**是同一思路更手动的版本：给资源打标记，再授予受这些标记限制的权限。

有些角色按定义就是项目级的，完全不提供范围，因为收窄它们毫无意义——"Billing Admin，但只针对我拥有的账单"什么也没描述：

## 所有者

所有者是关联到某个具体资源的用户或团队。大多数代表你所运维之物的资源——监视器、事件、告警、计划维护、待命策略、仪表板、服务、状态页、工作流、运行手册和 SLO——都有 **Owners** 选项卡。

所有者承担两项职责：

1. **通知。** 当资源发生状况时——监视器宕机、创建了事件、SLO 开始消耗错误预算——OneUptime 通知的就是所有者。
2. **访问权限，如果你这样配置。** "拥有"范围正是依据归属关系来解析的。用户本人是所有者，或他所属的任一团队是所有者，即算匹配。

仅有归属关系并不授予任何权限。身为某个监视器的所有者，如果你所属的团队没有同时持有监视器权限，你仍然无法编辑它。归属关系收窄访问权限，永远不会扩大它。

## 标签

标签是项目级的标记，你把它附加到资源上。它有两个用途：在仪表板中筛选和分组，以及如上所述限制权限。

只要资源带有该权限标签中的**至少一个**，标签限制即告满足。完全没有标签的资源，不满足任何带标签限制的权限。

自身没有标签的记录，例如事件的备注、状态页的公告或关于某个服务的 AI 洞察，带有它所属或所涉及记录的标签。当这些记录中的任意一条带有权限的某个标签时，限于标签的权限可以触及它；当其中某条记录带有被阻止的标签时，带标签的阻止会将其移除，读取、修改和删除都是如此。不涉及其中任何记录的记录（例如不涉及任何服务的 AI 洞察）属于项目本身：标签限制不会收窄它，带标签的阻止也不会将其移除。

位置：**设置 → 标签**。

## 遥测

日志、链路追踪、指标、异常、性能剖析和会话回放都属于发送它们的资源：服务、主机、Kubernetes 集群、监控器、RUM 应用等。遥测权限能读取多远，取决于它的范围：

- **全部资源**读取项目中每个资源的遥测。
- **拥有**读取你或你的某个团队所拥有资源的遥测，以及不指向任何资源的遥测。
- **标签**读取带有该权限某个标签的资源的遥测。

遥测权限上带标签的阻止会排除带有这些标签的资源的遥测，无论你还持有什么权限。凡是读取遥测的地方都是如此：各个探索器及其图表、筛选器和属性列表、导出、会话回放，以及 AI 助手为你读取的内容。指标名称列表显示你可读取的服务上报的指标，以及没有任何服务上报的指标，例如主机和集群指标。如果你还可以读取其他类型资源（例如主机或集群）的遥测，则会显示所有指标名称。

删除遥测数据也限于同样的资源：删除只触及你读取该信号的权限和删除它的权限都能触及的资源的行，并去掉任一权限上的带标签阻止所排除的资源；删除每次只在一个项目中进行。

监控日志、SLO 历史、网络流量和 Kubernetes 成本分摊也以同样的方式读取，通过它们所属的监控、SLO、网络设备或集群："拥有"和"标签"可以触及你可读取记录的数据行，带标签的阻止会排除带有这些标签的记录的数据行。审计日志和威胁情报指标由有权读取的人在整个项目范围内读取。

## API 密钥

API 密钥的权限直接授予在密钥本身上——它们不属于任何团队，也不受团队归属影响。

- 像给团队一样，分配同样的细粒度权限和角色。
- 密钥支持**阻止权限**和**标签限制**，方式与团队相同。
- 密钥**不**支持"拥有"范围。归属关系是相对用户解析的，而密钥不是用户，因此请明确地把所需访问权限授予密钥。

给每个集成配一把自己的密钥，权限集尽可能窄，这样吊销其中一把不会影响其他。

位置：**设置 → API 密钥**。另见 [API 参考](/docs/api-reference/api-reference)。

## OneUptime 如何判定一个请求是否被允许

对于已登录用户，依次执行：

1. 找出用户在本项目中所属的团队，只统计已接受的邀请。请求只会触及本项目的记录：另一个项目的记录，无论是通过 ID 还是在筛选条件中指定，都会被当作不存在。
2. 收集这些团队的每一条权限记录——允许与阻止，各自带有标签和范围。
3. 先检查阻止列表。目标表在该操作上接受的任意一项权限上只要有不带标签的阻止，无论它设在哪个团队，都会直接拒绝该请求。
4. 检查允许列表。请求需要至少一项目标表在该操作上接受的权限。对于运营资源——监视器、事件、仪表板之类——对应的 **All Operational Resources** 权限（Create、Read、Edit 或 Delete）也算数，除非它本身被阻止。
5. 应用范围。范围为"拥有"的授予会把查询收窄到所拥有的资源；标签范围收窄到匹配的标签。如果同一操作还有更宽的授予，以更宽的为准。自身没有标签的记录（例如事件的备注），当它所属的记录中任意一条带有该授予的某个标签时，即符合标签范围的授予。限定到标签的 **All Operational Resources** 权限也以同样方式收窄：它触及带有其中某个标签的运营资源，与限定到这些标签的资源自身权限相同。
6. 应用标签阻止。带标签的阻止在目标资源带有其中之一时拒绝请求。当一条记录自身没有标签时，例如事件的备注或状态页的公告，如果它所属的记录带有其中某个标签，带标签的阻止会在读取、修改和删除时将其排除。一次显示你所有项目记录的列表（例如首页上的事件）会按你在每个项目中的阻止和授予分别收窄该项目的记录。对 **All Operational Resources** 权限的带标签阻止，会从该权限授予的范围中排除带有这些标签的资源。
7. 修改和删除只限于你能读取的内容。修改或删除既受修改权限约束，也受你的读取权限约束：你不能读取的记录——在你的标签或所有者范围之外，或带有被读取阻止排除的标签——你也不能修改或删除；对某类记录读取的不带标签的阻止，也会同时拿走对它的修改和删除。通过另一条记录读取的记录（例如事件的备注或状态页的公告），只能通过你能读取的记录触及：没有读取事件的权限时，对备注的权限不会触及任何备注；对读取事件的带标签阻止，会排除带有这些标签的事件的备注。按 ID 指定的单条记录的修改或删除如果没有触及任何记录：当你不能读取它时，会像该记录不存在一样回答（`404`）；当你能读取但不能修改它时，会被拒绝。当你读取事件的权限范围为"拥有"时，对备注的权限只触及你或你的某个团队所拥有的事件的备注。按 ID 读取单条记录时，如果记录不存在或你不能读取它，也同样回答 `404`。

记录的每个字段都用该记录自己的读取权限来读取：其他类型记录的权限永远打不开它。有些字段刻意收窄了范围。机密只有能编辑或管理其所属记录的人才能读取，例如监控器的传入请求密钥、传入邮件密钥和服务器代理密钥，或工作流的 Webhook 密钥和传入邮件密钥。观看会话回放的录像需要 **Watch Session Replays**，仅有 **List Session Replays** 不够。遥测按信号分别读取：**Read Telemetry Service Log** 读取日志，**Read Telemetry Service Traces** 读取链路追踪，**Read Telemetry Service Metrics** 读取指标，包括指标图表。

字段遵循同样的规则。字段的权限上有不带标签的阻止，该字段就被取消；对于运营资源，对应的 **All Operational Resources** 权限可以打开每一个可读取或修改该记录的人都能打开的字段——但打不开刻意收窄的字段，例如密钥。

其他所有询问你是否持有某项权限的地方，也都由同一规则决定：并非单纯读写的操作，例如充值短信、通话或 AI 额度、支付发票、测试通知规则，以及 OneUptime 显示的按钮。你不能使用的按钮会显示为锁定并说明原因；如果原因是你所在某个团队的阻止，它会指出被阻止的权限。

实时更新也遵循同一规则。当一条记录被创建、修改或删除时，OneUptime 只通知可以读取该记录的人打开的页面，不通知其他任何人。凡是限制你读取的，也同样限制你的实时更新：标签、所有者、带标签的阻止、私有事件，或其他人的 AI 对话。当某项更改使你无法再读取某条记录（例如将其设为私有）时，你打开的页面也会收到通知，从而不再显示它。你的权限变化、账户被封禁或不再是主管理员，都会立即反映到你打开的页面上。

实时更新也会随着开启它们的登录一起结束。退出登录、修改密码或账户被封禁，都会立即停止你打开的页面上的实时更新。打开的页面每 15 分钟续期一次登录，并恢复其实时更新；如果登录无法续期，页面会带你前往登录页。要求 SSO 的项目，与其他一切相同，只向通过 SSO 登录的页面发送实时更新。

每位已登录用户还额外持有一小组自动权限，覆盖诸如读取自己的资料和自己的通知规则等。它们不是管理员权限，也不会开放他人的数据。

解析出的权限按用户和项目缓存，并在团队归属或团队权限变化时刷新。如果你修改了权限而用户没有立即看到变化，让他重新加载页面。

## 配方

**只旁观的团队。** 创建团队并添加 `Viewer` 角色，或者只为它该看的领域添加对应的 `*Viewer` 角色。

**自己管自己服务的待命工程师。** 给团队授予范围为**拥有**的 `MonitorAdmin`、`IncidentMember` 和 `OnCallMember`，再把该团队添加为它所运维监视器的所有者。

**让外包远离生产环境。** 以**全部**范围给团队所需的角色，然后为敏感能力添加一条限定在 `Production` 标签上的**阻止权限**。

**只汇报部署的 CI 流水线。** 创建一把只带所需细粒度权限的 API 密钥——不要给角色。

**不该修改账单或查看发票的人。** 给他 `ProjectMember`，而不是 `ProjectAdmin`：项目管理员不能更改套餐、付款方式或余额，但可以查看和下载发票。若要让某人只读账单页面而不做任何修改，请给他 `BillingViewer`。
