# 运行与日志

工作流每跑一次，OneUptime 都会存下一份记录：什么时候跑的、跑通了没有、每个方块干了什么。这份记录就叫一次 **运行**。你靠运行来确认工作流真的生效了，来排查没生效的那次，也用它回看过去的活动。

## 去哪儿找它们

| 页面                        | 你会看到什么                                                                                       |
| --------------------------- | ---------------------------------------------------------------------------------------------------- |
| **工作流 → 运行和日志** | 项目里所有工作流的每一次运行。可以按工作流名称、状态和时间筛选。           |
| **工作流 → 运行和日志**  | 只有这一个工作流的运行。这里没有工作流筛选，换成了一个 **运行 ID** 筛选。  |
| **某一次运行**            | 用运行那一行上的 **查看日志** 按钮打开——行本身是点不开的。           |

## 运行状态

| 状态                               | 它的意思                                                                                                                                             |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **已计划**                      | 触发器开火了，这次运行正排队等一个执行器。通常不到一秒。一次运行如果 5 分钟后还停在这儿，就判为失败——没人接手它。 |
| **正在运行**                        | 工作流正在进行中。跑得久的方块会让运行一直停在这个状态。                                                                                |
| **正在等待**                        | 运行停在一个 **Sleep** 方块上，之后会自己恢复。等待期间它不占用任何工作进程。                                                      |
| **Executed**                       | 运行一路走到了最后，没有失败。（这就是成功状态——标签上写的是 **Executed**，不是 "Success"。）                                        |
| **错误**                          | 运行因为某个方块抛出错误而停下。另外这几种情况也算错误：排队的运行始终没被接手、休眠中的运行恢复信号丢了、计划表达式解析不出来，或者工作流在运行途中被禁用。 |
| **Timeout**                        | 运行的时间超过了允许的上限。见[工作流配置与安全](/docs/workflows/configuration)。                                                              |
| **Execution Exceeded Current Plan** | 项目在最近 30 天里已经用完了工作流运行次数，或者订阅欠着费。这次运行会被记录下来，但不会执行。仅限 OneUptime Cloud。 |

一个方块交给它的 **错误** 输出——比如 API 方块碰上 4xx——并不会让整次运行失败。错误分支照常跑，运行最后仍然是 **Executed**。那个步骤本身还是画成红色，方便你找到它。

## 读一次运行

在某次运行上点 **查看日志** 打开它。**Workflow Run** 视图有两个标签页。

**步骤**——跑过的每个方块占一行，按顺序排。每行显示方块的标题、它的组件 id、耗时，以及它是从哪个输出离开的（`→ success`、`→ error`、`→ yes`）。展开一行能看到两块详情：

- **Received**——这个方块拿到的设置，变量已经全部解析完毕。
- **Returned**——它产出了什么。

失败的步骤是红色的，而且默认就展开着，错误信息印在 **Received** 上方。

**Full Log**——执行器打印出来的逐行原始日志，方块自己记的内容也在里面。当 **步骤** 视图解释不了这次失败时，就看它。

有两个细节值得知道。每个步骤标题下面印的那个组件 id，正是你要粘进 `{{local.components.<id>.returnValues.…}}` 引用里的那串字符，所以这是把引用写对的最快办法。还有，一次运行只保留最后 100 个步骤——跑得长或者反复恢复的运行，会在早期步骤被丢掉的地方显示一条琥珀色提示。

这里显示的值，是方块在变量填充之后看到的值，只有两个例外：密钥和被方块标为敏感的字段会被打码，特别长的值会被截断并加上 "… (truncated)"。

从 **生成器** 启动的运行会直接打开这个视图并跟着跑，你可以边跑边看，不用事后再去找。

## 常见排查

### "我的工作流没跑。"

1. 确认工作流在它的 **概览** 页面上是 **已启用** 的。新建的工作流一开始是关着的，而被禁用的工作流会拒掉每一次运行，手动的也不例外。
2. 如果是 OneUptime 事件触发器：确认那件事真的发生了。打开那条记录，看它的历史。
3. 如果是 Webhook 触发器：确认对方系统发到的是正确的 URL。大多数工具在发出 Webhook 时都会记一笔——去那儿看。
4. 如果是计划触发器：确认 cron 表达式对应的就是你以为的那个时间。

如果这次运行*确实*出现了，状态是 **Execution Exceeded Current Plan**，那说明项目在最近 30 天里用完了工作流运行次数，或者订阅欠着费。这次运行的日志里会写明用了多少次、你的套餐上限是多少。这一条只适用于 OneUptime Cloud。

### "后面某个方块从来没跑过。"

方块不跑，通常是接线的问题。打开 **生成器** 检查：

- 前一个方块的输出接到这个方块的输入了吗？
- 前一个方块走的输出是不是跟你以为的不一样——走了 **错误** 而不是 **成功**，或者走了 **否** 而不是 **是**？**步骤** 标签页会告诉你它走的是哪个。

### "有个变量传过来是空的。"

打开这次运行，看出问题那一步的 **Received**。

- 如果你看到的是 `{{local.components.…}}` 这样的字面文本，说明引用没解析成功。多半是组件 id 或者返回值 id 打错了——记住那是方块的 **Identifier**，不是它上面显示的名字。`local.components` 本身的拼写也顺手查一下：`{{local.componets.api-get-1.returnValues.response-body}}` 会被当成纯文本原样发出去，而这次运行照样报 **Executed**。
- 如果你看到的是一个空字符串，说明前一个方块跑了，但没产出那个字段。

**Full Log** 标签页里有一行警告，会点名任何没解析成功的引用，这通常是最快的定位办法。

### "手动跑没问题，一从触发器跑就不行。"

打开 **生成器**，点 **运行工作流**，用接近真实触发器会送来的值把触发器的字段填上。然后把这次运行的 **Received** 和真实那次的并排比一比。差别通常就在某一个字段名或者类型上。

## 重新跑一个工作流

这里没有"重试这次运行"的按钮。我们不会自动重跑旧的执行，因为它的副作用——Slack 消息、API 调用、工单——未必能安全地再来一遍。要把这份活儿重做一遍，就把工作流修好，等下一次真实触发带它跑；或者打开 **生成器**，用同样的值点 **运行工作流**。

## 运行会保留多久？

在 OneUptime Cloud 上，运行保留 **30 天**，之后删除——这也是为什么两个运行列表都说自己覆盖的是最近 30 天。自托管的安装会一直保留运行，直到你自己删掉；如果某个工作流跑得特别频繁、把历史刷得很乱，就禁用或者删掉它，别再往里加噪音了。

在步骤追踪上线之前记录下来的运行没有 **步骤** 内容，只显示它们的 **Full Log**。
