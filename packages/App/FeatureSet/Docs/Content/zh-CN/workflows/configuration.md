# 工作流配置与安全

在让工作流处理真实流量之前需要了解的内容：如何安全地开启它、谁能做什么、密钥和 URL 如何保持私密、工作流的步骤可以更改什么，以及每次运行都要遵守的限制。

:::cards
- [上线](#打开或关闭一个工作流): 用运行工作流测试，然后让工作流保持开启。
- [权限](#权限): 工作流角色，以及它们背后的单项权限。
- [步骤可以做什么](#工作流步骤可以做什么): 步骤以工作流所在项目的 Project Admin 身份执行。
- [限制](#套餐限制): 每个套餐的运行次数、运行时间以及工作流之间的调用。
:::

## 打开或关闭一个工作流

每个工作流在它的 **生成器** 顶部和 **概览** 页面上都有一个 **已启用** 开关。关闭时，工作流不会运行——Webhook 调用、收到的邮件、计划时间和 OneUptime 事件都会被忽略，**运行工作流** 和 **Run just this step** 也一样。新工作流一开始是禁用的。

把这个开关当作“准备就绪”的关口：

:::steps
1. 搭建工作流。
2. 用接近真实的值在 **生成器** 中点击 **运行工作流**。已禁用的工作流即使手动也无法运行，所以生成器会先请你开启它：点击 **开启并运行**。
3. 打开这次运行，检查每个块是否都走到了你预期的地方。参见 [运行记录](/docs/workflows/runs-and-logs)。
4. 如果准备好了，就让 **已启用** 保持开启。如果还没有，就先关掉，直到准备好为止：开启期间，它的触发器会在真实事件发生时触发。
:::

关闭工作流会阻止新的运行开始。已经在进行的运行会完成，但停在 **Sleep** 块上等待的运行会在醒来时被取消。

## 归档工作流

把不再需要但想保留的工作流归档。已归档的工作流：

- **永远不会运行**，无论哪种触发器。手动运行和 **Run just this step**、Webhook 调用、计划、OneUptime 事件、收到的邮件，以及其他工作流的 **Execute Workflow** 步骤都会被拒绝。对已归档工作流的 Webhook 调用会收到一个说明工作流已归档的错误。
- **停止正在等待的运行。** 在 **Sleep** 步骤中休眠的运行会在醒来时被取消，已经排队但尚未开始的运行会以 "Workflow was archived before this run started, so it did not run." 结束。
- **离开工作流列表。** 可以在 **工作流 → 高级 → 已归档** 下找到它。
- **保留一切。** 它的步骤、变量、所有者、标签和运行历史都保持原样。

要归档一个工作流，打开它，进入 **设置**，点击 **归档**。要归档多个，在 **工作流** 列表中选中它们，然后选择 **归档**。

要恢复工作流，打开 **工作流 → 高级 → 已归档**，选中它并选择 **取消归档**，或者打开它，点击页面顶部横幅上的 **取消归档**。

归档和 **已启用** 开关是两回事。归档不会动开关，所以原本开启的工作流一取消归档就会再次运行，原本关闭的则保持关闭。**已归档** 页面的 **When Unarchived** 列会显示哪个是哪个。

导出的工作流从不携带归档状态，所以导入的副本永远不会是已归档的。

## 密钥

如果某个变量保存的是敏感内容，就把它标记为 **密钥**：它的值会从运行日志和步骤跟踪中清除。任何变量的值保存后都无法读回，无论是否为密钥，在仪表板中或通过 API 都不行；而且变量一旦设为密钥，就会一直是密钥。

把密钥变量用于：

- 外部服务的 API 密钥。
- 身份验证令牌。
- Webhook 签名密钥。
- 任何你不希望只有只读权限的人看到的内容。

不要把密钥直接粘贴到块中——像 `Authorization: Bearer eyJh...` 这样的值会在工作流和日志中可见。请改用 `{{global.variables.MY_SECRET}}`。

如果密钥是会过期的 OAuth 访问令牌，就把这个变量设为 [OAuth 2.0 变量](/docs/workflows/variables#oauth-20-变量会自动刷新的令牌)。这样 OneUptime 会从你的身份提供商获取令牌，并在工作流即将使用过期令牌时刷新它。OAuth 2.0 变量总是密钥，它们的凭据在数据库中加密。

## 导出与导入工作流

你可以把工作流作为 JSON 文件在项目之间，或在自托管安装与 OneUptime Cloud 之间移动。

:::tabs
@tab 导出
打开工作流，进入 **设置**，点击 **导出工作流**。要把多个工作流放进一个文件，在 **工作流** 列表中选中它们，然后选择 **导出JSON**。
@tab 导入
在 **工作流** 列表中点击 **Import JSON**，选择从任意 OneUptime 项目导出的文件。如果项目中已有同名工作流，导入的工作流会在名称后加上 "(Imported)"。
:::

文件包含工作流的名称、描述、启用状态和它的图。它有意不包含：

- **Webhook 密钥。** 创建工作流时会生成一个新的，所以导入的工作流有不同的 Webhook URL——请从新工作流的 Webhook 触发器复制它。所有调用原工作流的东西都要改指向新的。
- **收到的邮件的地址。** 带 Incoming Email 触发器的导入工作流会得到自己的地址——请从新工作流的触发器复制它。所有给原工作流发邮件的东西都要告知新地址。
- **全局变量。** 读取 `{{global.variables.MY_SECRET}}` 的块会保留这个引用，但值不在文件中。运行导入的工作流之前，请在目标项目中创建这些变量。
- **所有者和标签。** 你的项目自己的标签和所有者规则会作用于导入的工作流，就像你手动创建它一样。

导入的工作流总是以 **已禁用** 状态创建，即使它在导出处是启用的——它的图可能指向目标项目中不存在的监视器、值班策略或其他工作流。检查它，启用它，用 **运行工作流** 测试它，然后让它保持开启。复制工作流也是同样的行为，所以副本永远不会在你编辑之前就与原工作流同时触发。

由于图是原样带过去的，直接输入到块中的任何内容也会一并带过去。这正是把凭据保存在密钥变量中的实际原因：导出一个硬编码了令牌的工作流，就等于把那个令牌交给了拿到文件的任何人。

## Webhook 安全

Webhook 触发器会给你一个唯一的 URL。任何知道这个 URL 的人都能调用它。要防止意外或不受欢迎的调用方：

- 把 URL 当作密码对待。不要公开分享，也不要提交到公开仓库。Webhook 触发器会在你点击 **显示** 之前隐藏 URL 中的密钥，**复制 URL** 会在不显示的情况下复制 URL。
- 如果 URL 泄露，在 **生成器** 中点击 Webhook 触发器，然后点击 **重置 URL**。工作流会得到一个新 URL，旧的会立即失效。
- 如果触发器说它的 URL 以工作流的 ID 结尾，请重置它。在 Webhook URL 拥有自己的密钥之前创建的工作流，用的是工作流的 ID，而任何能打开该工作流的人都能看到它。
- 对于敏感的工作流，请调用方系统在标头中发送一个共享令牌（例如 `X-Webhook-Token`），并在做任何重要的事之前用 **If / Else** 块检查它。把预期的令牌保存为密钥变量。
- 对于非常敏感的工作流，优先使用 OneUptime 事件触发器加手动导入步骤，而不是公开的 Webhook。

只有能编辑工作流的人——**Project Owner**、**Project Admin**、**Workflow Admin** 或 **Edit Workflow**——才能查看或重置它的 Webhook URL。任何拿到 URL 的人都可以不登录、从任何地方启动工作流，所以其他人会看到一条说明应该找谁的提示。这也包括在 **生成器** 中手动运行工作流的 **Workflow Member**。

## 收到的邮件的安全

Incoming Email 触发器会给工作流一个专属地址，任何知道这个地址的人都能给它发邮件。`@` 之前的部分是工作流的密钥，所以请把这个地址当作密码对待：

- 不要公开它，也不要放进公开仓库。触发器会在你点击 **显示** 之前隐藏密钥，**复制地址** 会在不显示的情况下复制地址。
- 如果地址泄露，在 **生成器** 中点击 Incoming Email 触发器，然后点击 **重置地址**。工作流会得到一个新地址，从此发到旧地址的邮件会被忽略。
- 任何人都可以在邮件上填写任意发件人，所以 **From** 不能证明是谁发的。在工作流做任何重要的事之前，用 **If / Else** 块检查只有真正的发件人才知道的东西——主题或标头中的令牌。把预期的令牌保存为密钥变量。
- 运行收到的所有内容中——**To**、**CC**、标头和正文——密钥都会被隐藏，因为运行的日志对任何能读取该工作流运行的人可见。

只有能编辑工作流的人——**Project Owner**、**Project Admin**、**Workflow Admin** 或 **Edit Workflow**——才能查看或重置它的地址。其他人会看到一条说明应该找谁的提示。

## 出站网络访问

API 块和其他 HTTP 块从 OneUptime 发出请求，IRC 块从 OneUptime 连接到 IRC 服务器的端口。如果你是自托管，请确保你的安装能访问你调用的服务。如果你使用 OneUptime Cloud，我们的出站 IP 范围列在 [IP 地址](/docs/configuration/ip-addresses) 中，你可以在对端放行它们。

块可以访问哪些地址取决于块：

| 块                                                             | 回环、链路本地、云元数据                                                     | 私有网络地址                                                                                                                                      |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **API** 块和 **Run Custom JavaScript** 的请求                  | 拒绝，除非确切的主机列在 `PRIVATE_NETWORK_WEBHOOK_ALLOWLIST` 中              | 拒绝，除非自托管管理员通过 `ALLOW_PRIVATE_NETWORK_WEBHOOKS` 或 `PRIVATE_NETWORK_WEBHOOK_ALLOWLIST` 允许                                          |
| **Send Email**、**IRC** 和 OAuth 2.0 令牌 URL                  | 拒绝                                                                         | 在 OneUptime Cloud 上拒绝。在自托管安装上允许，除非 `DATA_SOURCE_BLOCK_PRIVATE_ADDRESSES` 为 `true`                                              |
| Slack、Microsoft Teams、Discord 和 Telegram                    | 拒绝                                                                         | 拒绝：每个都只发送到它自己服务的地址                                                                                                              |

自托管管理员如何放开这些限制，参见 [私有网络访问](/docs/self-hosted/private-network-access)。

## AI 组件

**Generate Text with AI** 向一个 LLM 发送一个请求：项目的默认 LLM 提供商，或者在项目没有时使用安装的全局提供商。在 **项目设置 → 人工智能 → LLM 提供商** 下设置提供商，永远不要把提供商的 API 密钥或你自己的端点放进工作流。

提供商会收到什么，以及模型能用它做什么：

- **只有你放进块里的内容。** OneUptime 会先发送一条固定的安全指令，然后是块的 **System Instructions**、**Prompt** 和 **Context**，其中的引用已填好。**Context** 放在最后，位于一个标记之后，安全指令会告诉模型，标记之后的一切都是不可信的数据，即使是看起来像指令的文本。
- **没有其他任何东西。** 触发器的数据、工作流的历史、其他块的输出、项目记录、遥测和密钥都永远不会被附带。只有当你在这三个设置之一中引用它们时，它们才会离开 OneUptime。
- **只有文本，没有工具。** 模型无法查询 OneUptime、发出 HTTP 请求或更改数据。提供商的附加参数只放行一份只调节生成的字段允许列表：它们不能替换消息，不能添加工具、网页搜索或其他数据源，不能要求文本以外的内容或多个回答，不能流式传输，不能让提供商保留请求，也不能提高块的输出上限。OneUptime 不认识的字段会被丢弃。
- **模型由你的管理员选择。** 如果生成必须保持离线，请选择一个不会在提供商一侧自行检索任何内容的模型。

会记录什么：

- 运行的日志会隐藏块的 **System Instructions**、**Prompt**、**Context** 和 **Response**。后续块在运行期间仍然可以使用它们；你把其中之一插入到某个块中，那个块会按自己的规则记录它，所以插入就意味着选择让它显示。
- 提供商、模型、令牌数、**LLM Log ID** 和一条安全的错误消息仍然可见，用于运维和计费。提供商的原始错误不会进入任何日志，因为提供商可能会在其中复述请求。
- 每次调用都会列在 **项目设置 → 人工智能 → AI 日志** 下，带有提供商、模型、状态、令牌、费用和计费信息，但不包含提示词、回复或原始错误。

它需要什么，以及费用：

- 必须在 **项目设置 → 人工智能 → AI Features** 下开启 **启用 AI**。在 OneUptime Cloud 上，项目还需要 Growth 套餐或更高，以及已付款的订阅。没有计费的自托管安装没有套餐要求。
- 通过收费的全局提供商进行的调用会使用项目的 AI 额度。
- 如果项目所有者设置了 [项目自己的每日 AI 限额](/docs/ai/ai-sre#the-projects-own-daily-limits)，每次调用都会计入其中。一旦达到限额，块会走 **Error**，不联系模型，直到 UTC 午夜。

| 限制                                                          | 值                                                                       |
| ------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **System Instructions**、**Prompt** 和 **Context** 合计       | 50,000 个字符                                                            |
| **Temperature**                                               | 从 `0` 到 `1`                                                            |
| **Maximum Output Tokens**                                     | 从 `1` 到 `4096`，默认 `1024`                                            |
| 一个请求                                                      | 只尝试一次，最长 60 秒                                                   |
| 同时进行的调用                                                | 每个项目 3 个。更多的会走 **Error**，之后的运行可以重试。                |

验证、配置、访问、限额、额度、并发、提供商和超时失败都会走 **Error** 路径，原因放在 **Error** 中。在工作流上线之前把这条路径连好。

> [!WARNING]
> 你引用的每个值都是你发送给提供商的数据。除非提供商被批准接收，否则不要把密钥变量放进提示词或上下文。像 Ollama 这样的自托管本地提供商会把请求留在你自己的基础设施内；托管的提供商则按它自己的数据处理条款接收请求。

## 权限

工作流遵循你项目的基于角色的访问控制。三个工作流角色：

- **Workflow Admin** —— 构建工作流：创建、更改、运行和删除它们，并管理它们使用的变量。
- **Workflow Member** —— 使用工作流：打开工作流及其运行，用 **运行工作流** 手动运行工作流。成员不能创建、更改或删除工作流，也不能单独运行它的某个步骤。
- **Workflow Viewer** —— 读取工作流及其运行。

**Project Owner** 和 **Project Admin** 能做 Workflow Admin 能做的一切。**Project Member** 可以创建和删除工作流，但不能更改或运行它们。

单项权限，用于只需要一项权限的团队或 API 密钥：

- **Create / Read / Edit / Delete Workflow** —— 对工作流本身的基本权限。更改工作流，包括开启或关闭它以及归档它，需要 **Edit Workflow**；**Delete Workflow** 只能删除。
- **Edit Workflow** —— 也是用 **Run just this step** 单独运行一个步骤，以及查看或重置工作流的 Webhook URL 和收到的邮件的地址所需要的权限。手动运行整个工作流需要 **Edit Workflow**、**Workflow Admin** 或 **Workflow Member**。
- **Read Workflow Log** —— 查看运行所需。
- **Create / Read / Edit / Delete Workflow Variables** —— 管理全局变量和工作流变量。

手动运行只能到达你能打开的工作流：限定于某些标签，或限定于你团队拥有的工作流的角色，只能运行这些工作流。不能运行某个工作流的人会看到灰色的 **运行工作流**，原因写在它的提示中。

把 **Workflow Admin** 给构建自动化的人，把 **Workflow Member** 给只负责启动它的人。把变量的编辑权限留给管理项目密钥的人。角色如何授予，参见 [用户、团队与权限](/docs/permissions/index)。

## 工作流步骤可以做什么

读取和更改 OneUptime 记录的步骤——Find、Create、Update 和 Delete 组件，以及 On Create、On Update 和 On Delete 触发器——以工作流所在项目的 **Project Admin** 身份执行。无论工作流是谁搭建的，步骤都要通过与 Project Admin 在仪表板和 API 中相同的检查：

- **只限工作流自己的项目。** 步骤只读写工作流所属项目的记录，不涉及其他项目，Update 也绝不会把记录移到另一个项目。
- **只限 Project Admin 可以做的事。** 步骤只能授予 Project Admin 自己拥有的团队和 API 密钥权限，所以它不能分发 **Project Owner**、计费或删除项目的权限，也不能把人加入权限超出 Project Admin 的团队，例如所有者团队。步骤无法读取是谁创建了探针或 AI 代理，那只有项目所有者能看到。
- **不能读取 Runbook 凭据。** Project Admin 可以读取 Runbook 凭据，但这项权限不会借给步骤。当某个更改需要这项读取权限时——让 OneUptime AI 不经询问就运行它的命令、为某个 Runner 开启 **执行 AI 补救命令**、给运行 OneUptime AI 命令的 Runner 分配 SSH 凭据，或者指定一个 Runbook 凭据（例如在 Runbook 的步骤中）——会改为检查最后保存该工作流步骤的人，除非此人可以读取 Runbook 凭据（**Read Runbook Credential**，或者是 Project Owner 或 Project Admin），否则步骤会被拒绝。OneUptime 会在有人创建工作流时以及每次有人保存它的步骤时记录此人；重命名工作流、更改它的标签或开启关闭它，都不会改变最后保存步骤的人。用 API 密钥保存步骤不会记录任何人，因此在有人保存这些步骤之前，工作流的步骤无法做出这些更改。
- **只限你的套餐包含的内容。** 在 OneUptime Cloud 上，创建或更改你的套餐不包含的内容的步骤会被拒绝，并说明所需的套餐，与仪表板一样。没有计费的自托管安装没有套餐限制。
- **不涉及 OneUptime 自己保留的东西。** 以下操作对所有人都会被拒绝，包括工作流：
  - 编辑或删除动态条目（事件、警报、片段、监视器、值班策略和计划维护的动态）；
  - 写入通知日志（短信、电话、邮件、WhatsApp、Telegram、推送、Webhook 和工作区消息日志）；
  - OneUptime 随着事情发生而设置的值：自定义域名的 CNAME 是否已验证、团队的保护开关（**Is Team Editable**、**Is Team Deleteable**、**Is Permissions Editable**、**Should Have At Least One Member**）、哪个事件角色是主要角色以及它能否被删除、所有者或成员是否已收到通知、提醒的时间和次数、排班中当前和下一位值班人员、值班运行的进度、SLO 当前的消耗速率和错误预算、被事件或维护暂停的监视器、状态页面私有用户的密码重置令牌和最近登录，以及服务报告的关于自身的事实（版本、运行时、云），还有检测规则或威胁源的最近一次运行；
  - 通过向 **Create One Incident** 发送 `createdIncidentTemplateId` 来根据模板宣布事件——请改为在步骤的 **Incident Template** 设置中选择模板：这样步骤会以 Project Admin 身份根据该模板宣布事件，并记录模板；
  - 在记录创建之后更改它属于哪条记录，例如所有者行对应的监视器，或者备注所在的事件。
- **不以任何人的身份。** 工作流创建的记录没有创建者，审计日志会把工作流（以它当时的名称）记为做出更改的一方。

当检查拒绝某个步骤时，步骤会走它的 **Error** 输出，不做被拒绝的更改，运行的日志会用通俗的语言写明步骤和原因，例如 *"Create One Team Permission" was refused. Workflow steps can do only what a Project Admin of this project can do: …*。可以在工作流的 [运行记录](/docs/workflows/runs-and-logs) 中查看。Create Many 步骤会一条一条地创建记录，并在第一条被拒绝时停止：在它之前创建的记录会保留。

与其他系统通信的步骤——API、Email、Slack、Microsoft Teams、Discord、Telegram、IRC、Custom Code 和 Generate Text with AI——不读取也不更改 OneUptime 记录，所以以上这些对它们都没有影响。

## 套餐限制

在 OneUptime Cloud 上，工作流需要 Growth 套餐或更高，每个套餐允许在任意 30 天内运行一定次数：

| 套餐       | 最近 30 天的运行次数     |
| ---------- | ------------------------ |
| Growth     | 500                      |
| Scale      | 2,000                    |
| Enterprise | 实际上没有限制           |

这个窗口是滚动的：项目记录的每次运行，无论是手动还是来自触发器，都会计入 30 天。在 Growth 和 Scale 套餐上，**工作流** 页面会显示一张 **工作流运行** 卡片，说明项目已经用了多少次。一旦达到限制，新的运行会以 **Execution Exceeded Current Plan** 状态记录且不会执行；订阅未付款期间也是如此。没有计费的自托管安装没有限制。

## 一次运行能跑多久

| 限制                                                              | 默认值         | 自托管设置                      |
| ----------------------------------------------------------------- | -------------- | ------------------------------- |
| 一次运行，从开始或从 **Sleep** 之后醒来算起                       | 2 分钟         | `WORKFLOW_TIMEOUT_IN_MS`        |
| 一个 **Run Custom JavaScript** 块                                 | 5 秒           | `WORKFLOW_SCRIPT_TIMEOUT_IN_MS` |
| 一个 **Sleep** 块                                                 | 最长 30 天     | —                               |

运行器会在每个块之前和之后检查截止时间，一旦控制权返回，就把超时的运行标记为 **Timeout**。它无法在块执行到一半时打断它，所以等待网络的块有自己的时间限制：Generate Text with AI 请求最多 60 秒后放弃，OAuth 2.0 令牌请求 20 秒后放弃。在 **Sleep** 块上的等待不计入运行时间：运行会被放到一边，醒来时重新获得 2 分钟。

## 调用其他工作流的限制

**Execute Workflow** 组件让一个工作流启动另一个工作流。为了防止工作流 A 启动 B、B 又启动 A 这样的循环，相互启动的工作流链如果会绕回链中已有的工作流，或深度超过 10 个工作流，就会被拒绝。这时 **Execute Workflow** 块会走它的 **Error** 输出，错误会显示这条链。

如果你确实需要一条很长的链（例如每次运行处理一个条目的任务），通常更简单的做法是用 **Run Custom JavaScript** 在单个工作流内部循环。

## 什么时候工作流不是合适的工具

有几种情况你应该改用别的东西：

- **繁重的计算或大型数据集** —— 工作流是为轻量的衔接工作设计的，不是为大量计算设计的。请在你自己的基础设施中运行繁重的工作，再让工作流去启动它。
- **长时间运行的主动计算** —— 一次运行默认有 2 分钟。对于像“做 A，等两小时，再做 B”这样的被动延迟，请使用 **Sleep** 组件；它会把运行放到一边，稍后再恢复，期间不占用 worker。
- **有人参与的逐步事件响应** —— 这正是 [Runbook](/docs/runbooks/index) 的用途。工作流用于无人值守的自动化。
