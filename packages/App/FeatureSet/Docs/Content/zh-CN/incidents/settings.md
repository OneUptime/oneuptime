# 设置与自动化

事件的配置不在项目设置里，而是在事件这个产品区域内部，位于 **事件 → 设置** 和 **事件 → 规则** 下，路由以 `/dashboard/{projectId}/incidents/settings/` 开头。如果你一直在 **项目设置** 里翻找事件模板或自定义字段，这就是找不到的原因。

事件侧边菜单里的 **规则** 和 **设置** 两个区块默认都是折叠的，得先展开才能看到下面这些条目。这里的一切都以项目为范围：模板、角色、自定义字段和规则都归属于某一个项目，并对该项目中声明的每一个事件生效。

本页就是这套配置的参考——每个页面装了什么，以及其中哪些会在事件创建的那一刻自动跑起来。

## 事件设置都在哪里

在左侧导航中打开 **事件**，然后展开侧边菜单底部的 **设置**。

| 页面                     | 你在那里做什么                                                                                |
| ------------------------ | -------------------------------------------------------------------------------------------- |
| **事件状态**             | 新增、改名、改颜色，以及重新排列事件所经历的各个状态。                                        |
| **事件严重性**           | 新增、改名、改颜色，以及重新排列严重级别。                                                    |
| **事件模板**             | 预填一整个事件——标题、描述、资源、值班策略、所有者、标签。                                    |
| **备注模板**             | 可复用的公开备注和私密备注文本。                                                              |
| **事后分析模板**         | 可复用的事后分析结构。                                                                        |
| **自定义字段**           | 定义出现在每个事件上的额外字段。                                                              |
| **事件角色**             | 定义你指派响应人员担任的角色，比如事件指挥官。                                                |
| **更多设置**             | 事件编号和事件片段编号的前缀。                                                                |

**事件状态** 和 **事件严重性** 在[事件状态与严重级别](/docs/incidents/states-and-severities)里有详细展开——本页从 **事件模板** 开始接着讲。

展开 **规则**，你会再得到八个页面：**分组规则**、**值班规则**、**所有者规则**、**Runbook 规则**、**隐私规则**、**标签规则**、**SLA 规则** 和 **Reminder Rules**。这些在下文中介绍。

## 事件模板

事件模板就是一份保存下来的事件骨架。与其在支付集群每次抖动时都重打一遍同样的标题、同样的监视器清单和同样的值班策略，不如存一次，然后从它声明。

前往 **事件 → 设置 → 事件模板**（`/dashboard/{projectId}/incidents/settings/templates`）。卡片标题是 **事件模板**。创建一个模板要走完一个六步向导：

- **模板信息**——**模板名称** 和 **模板描述**。它们命名的是模板本身，永远不会出现在事件上。
- **事件详情**——**标题**、**描述**（Markdown）、**事件严重性** 和 **初始事件状态**。**初始事件状态** 是可选的，初始为空；它的选项按状态顺序排列。留空的话，用这个模板创建的事件会落到项目的创建状态。
- **受影响的资源**——事件应当关联的监视器、主机、集群和服务，外加 **Change Monitor Status to**。
- **值班**——**值班策略**，也就是用这个模板声明事件时要执行的策略。
- **所有者**——**所有者 - 团队** 和 **所有者 - 用户**。
- **标签**——**标签**。

几条速记规则：

- 模板列表只显示 **名称** 和 **描述**。列表里的行不能直接编辑或删除——打开模板（`/dashboard/{projectId}/incidents/settings/templates/{modelId}`）才能改。
- 模板支持 JSON 导入导出，所以你可以把它从一个项目搬到另一个项目。
- 空状态显示的是 "No incident templates found."。

### 模板是怎么被套用的

有两条路径，行为完全一致。

- **从仪表板**——事件列表上的 **从模板创建** 按钮会打开一个 **选择事件模板** 选择器，声明页面从 `incidentTemplateId` 查询参数中读取模板，然后用模板连同它的所有者团队和所有者用户预填表单。
- **通过 API**——在 `POST /api/incident` 上传入 `createdIncidentTemplateId`，服务端会用模板填充事件。

关键在合并规则：**模板只会填你没有定义的字段**。标题、描述、事件严重性、初始事件状态、**Change Monitor Status to** 背后的监视器状态、监视器、主机、Kubernetes 集群、Docker 主机、Podman 主机、服务、值班策略和标签，只有在调用方或表单什么都没给的时候才会从模板复制过来。凡是你明确设定的，永远优先。

**空状态对话框指错了地方。** 如果你还没有任何模板，**从模板创建** 按钮会弹出一个 **No Incident Templates** 对话框。它的文案指向项目设置，但按钮实际跳转到 **事件 → 设置 → 事件模板**——那才是真正的位置。

## 备注模板

备注模板给响应人员提供现成的事件更新文案，这样凌晨三点的状态页更新就不用由一个半睡半醒的人从零写起。

前往 **事件 → 设置 → 备注模板**（`/dashboard/{projectId}/incidents/settings/note-templates`）。卡片标题是 **事件的公开或私密备注模板**——一个库同时服务两种备注类型。创建表单有两步：

- **模板信息**——**模板名称** 和 **模板描述**，都是必填。
- **备注详情**——备注正文本身，Markdown 格式，必填。

和事件模板一样，列表里的行只能创建和查看，不能就地编辑；要改就打开模板。

备注模板会出现在你真正需要它们的地方：**Acknowledge Incident** 和 **Resolve Incident** 两个确认对话框都在 **公开备注** 字段旁边提供 **选择备注模板**。公开备注和私密备注有何不同，参见[事件备注、负责人与动态](/docs/incidents/notes-owners-and-feed)。

## 事后分析模板

事后分析模板是事件之后那份复盘文档的骨架——你的小标题、你的引导问题、你每次都会问的那几件事——好让项目里的每一次复盘都长成同一个样子。

前往 **事件 → 设置 → 事后分析模板**（`/dashboard/{projectId}/incidents/settings/postmortem-templates`）。卡片标题是 **事后分析模板**。创建表单有两步：

- **模板信息**——**模板名称** 和 **模板描述**，都是必填。
- **事后分析详情**——**事后分析模板**，也就是正文本身，Markdown 格式，必填。

套用模板是在事件里做的，不是在设置里。打开一个事件，在它的侧边菜单中选择 **事后分析**（`/dashboard/{projectId}/incidents/{incidentId}/postmortem`），然后使用 **应用模板**。这会打开一个带 **选择模板** 下拉框的 **应用事后分析模板** 对话框；选中一个，模板正文就会载入 **事后分析备注** 编辑器，你在保存前可以继续修改。事件片段也有同样的 **事后分析** 页面，并共用同一个模板库。

## 自定义字段

自定义字段让你把自己的元数据带在每个事件上——内部服务名、变更工单编号、客户等级。

前往 **事件 → 设置 → 自定义字段**（`/dashboard/{projectId}/incidents/settings/custom-fields`）。页面标题是 **事件自定义字段**。每条定义包含：

- **字段名称**——必填，至少两个字符。占位提示建议使用类似 `internal-service` 这样的短横线命名。
- **字段描述**——可选。
- **字段类型**——必填。它决定数据以什么方式录入。下拉类型还需要列出各个选项。
- **下拉选项**——出现在下拉框里的取值，每个可以配一个可选的颜色。

定义存放在它自己的模型里；取值则存在事件本身的 `customFields` 列上。在单个事件上，你通过事件侧边菜单里的 **自定义字段**（`/dashboard/{projectId}/incidents/{incidentId}/custom-fields`）来填写它们。

**有一处空白值得记住。** 事件自定义字段定义是事件家族里唯一没有工作流触发器的部分——见下面的工作流一节。

## 事件角色

事件角色就是响应过程中你分派给人的那些有名字的职责。在 **事件 → 设置 → 事件角色**（`/dashboard/{projectId}/incidents/settings/roles`）里定义它们；卡片描述举的例子是事件指挥官和响应人员。

角色只是定义。分派是按事件来做的——声明向导里有一个 **事件角色** 步骤，包含 **分配事件角色** 字段，而每个事件的侧边菜单里也有一个 **角色** 页面。

## 编号前缀

每个事件都有一个编号，默认渲染成 `#42`。如果你的团队开口说的是 "INC-42"，那就让产品也这么说。

前往 **事件 → 设置 → 更多设置**（`/dashboard/{projectId}/incidents/settings/more`）。卡片是 **号码前缀**，包含项目上的两个字段：

- **事件编号前缀**——最多 20 个字符，占位符 `INC-`。设置之后，事件 `#42` 会显示为 `INC-42`。
- **事件片段编号前缀**——事件片段编号的同款设置，占位符 `IE-`。

任意一个留空就保持默认的 `#` 前缀；未设置的字段显示为 `# (default)`。用 **更新** 保存。带前缀的值以 `incidentNumberWithPrefix` 存在事件上，事件列表和事件头部渲染的就是它。

## 事件创建时运行的规则

**事件 → 规则** 里有八个规则引擎。它们干的活是一样的——在事件创建的那一刻审视它，命中就动手——但各自做的事不同，多条规则同时命中时的处理方式也不同。

- **分组规则**——把相关事件归并成片段。规则按优先级顺序求值；优先级数字小的先来。
- **值班规则**——为命中的事件执行值班策略。详见下文。
- **所有者规则**——自动指派所有者。
- **Runbook 规则**——事件命中时启动一份 [runbook](/docs/runbooks/index)。
- **隐私规则**——决定命中的事件是否为私密。
- **标签规则**——自动打标签。
- **SLA 规则**——跟踪响应时间和解决时间。规则按 order 顺序求值；order 数字小的先来。
- **Reminder Rules**——在事件仍未关闭期间定期提醒事件所有者。规则按顺序求值，第一条命中的规则胜出。

**顺序语义并不统一。** 分组规则、SLA 规则和 Reminder Rules 是按顺序求值的。值班规则不是——每一条命中的规则都会触发。别以为一套模型适用于全部八种。

**值班规则**、**所有者规则**、**标签规则** 和 **隐私规则** 这四个页面带标签页——一个 **Incident Rules** 标签和一个 **Episode Rules** 标签，各有各的表格。除非你确实指的是片段，否则配置 **Incident Rules** 标签。**分组规则**、**Runbook 规则**、**SLA 规则** 和 **Reminder Rules** 则是单张表格。

## 事件值班规则

**事件 → 规则 → 值班规则**（`/dashboard/{projectId}/incidents/settings/on-call-rules`）是你把呼叫自动化的地方。卡片 **事件值班规则** 描述的是这样一类规则：在命中的事件被创建时自动执行值班策略。页面有两个标签：**Incident Rules** 和 **Episode Rules**。

创建表单有三步：

- **基本信息**——**名称**（占位提示给的例子大意是"任何数据库事件都呼叫数据库团队"）、**描述**，以及一个 **已启用** 开关。列表会为每条规则渲染一个绿色的 **已启用** 或红色的 **已禁用** 标记。
- **匹配条件**——**监视器**、**事件严重性**、**事件标签**、**监视器标签**，外加针对事件标题、事件描述、监视器名称和监视器描述的大小写不敏感正则表达式字段。
- **值班策略**——这条规则要执行的策略。

### 匹配是怎么裁决的

页面自带的那几条规则值得记牢：

- 只有当你填过的**全部**条件都通过时，规则才算命中。你留空的条件会被跳过，而不是判为不通过。
- 在单个列表型条件内部——**监视器**、**事件严重性**、**事件标签**、**监视器标签**——采用任一命中即可。
- 那些模式字段是大小写不敏感的正则表达式。
- **所有命中的规则都会触发。** 没有优先级，也没有短路。
- 真正执行的策略集合，是每条命中规则的策略，加上手动或由模板附加到事件上的策略的并集，并去重，使每个策略最多只运行一次。

严重性在这里是匹配条件，而在别处不是。事件严重性上没有任何值班字段——选中 "Critical Incident" 本身并不会呼叫任何人。如果你想让严重性驱动呼叫，就写一条按它匹配的值班规则。

## 直接附加值班策略

规则不是唯一的途径。每个事件都自带一份值班策略列表，呈现为声明向导 **值班** 步骤上的 **值班策略** 字段，以及事件模板 **值班** 步骤上的同一字段。字段描述说得很直白：这些是本事件创建时要执行的值班策略。

事件创建时，OneUptime 先跑标签规则，再跑值班规则（把命中的策略合并进事件的列表），然后跑 Runbook 规则——如果最终列表非空，其中每个策略都会被执行。这些执行并行进行、各自独立结算，所以一个策略失败不会拖住其他策略。每次执行都会打上触发它的事件，以及"事件已创建"这个通知事件类型的标记。

想看发生了什么，打开事件并在它的侧边菜单中选择 **值班执行**（`/dashboard/{projectId}/incidents/{incidentId}/on-call-policy-execution-logs`）。

## 通过工作流驱动事件

事件的工作流触发器不是手写的——OneUptime 从数据模型生成它们，所以事件家族的每个模型都会得到 **On Create X**、**On Update X** 和 **On Delete X** 组件，名字取自模型的单数名称。最核心的三个是 **On Create Incident**、**On Update Incident** 和 **On Delete Incident**，你可以在 `/dashboard/{projectId}/workflows` 的 **添加组件** 面板中的 **事件** 分类下找到它们。

同一套生成机制也给配置本身提供了触发器：**On Create Incident State**、**On Update Incident Severity**、**On Create Incident Template**、**On Create Incident Note Template**、**On Create Incident State Timeline**、**On Create Incident Public Note**、**On Create Incident Internal Note**、**On Create Incident On-Call Rule**、**On Create Incident Role**、**On Create Incident Member** 等等。每个模型还会得到配套的动作组件——**Find One Incident**、**Create One Incident**、**Update One Incident**、**Delete One Incident** 以及它们的多行版本——于是名字相近的触发器和动作会并排出现在同一个分类里。**On Create Incident** 启动一个工作流；**Create One Incident** 开出一个事件。

接线时有几个细节很重要：

- **On Update X** 有一个可选的 **Listen on** 参数，把触发范围收窄到改动了特定字段的更新。留空则任何变更都会触发。如果某次更新没有附带"哪些字段变了"的记录，这个过滤会被跳过，工作流照跑不误。
- **On Create X** 和 **On Update X** 都有一个必填的 **Select Fields** 参数；**On Delete X** 不接受任何参数。
- 三者都只暴露一个 **成功** 出端口，并且都接受一个 ID 参数，让你可以针对单条记录手动运行工作流。
- 名字来自模型的单数名称，而不是表名——这就是为什么你看到的是 **On Create Incident Team Owner** 和 **On Create Incident User Owner**，而不是按表名命名的形式。
- 事件自定义字段定义没有触发器。在事件家族里，只有这一个模型禁用了工作流。

至于工作流其余部分怎么搭，参见[创建工作流](/docs/workflows/authoring)和[工作流变量](/docs/workflows/variables)。
