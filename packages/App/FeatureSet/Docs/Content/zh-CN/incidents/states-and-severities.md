# 状态与严重级别

每个事件都带着两种分类：一个**状态**，说明它在你的响应流程走到哪一步；一个**严重性**，说明它有多疼。在仪表板里它们长得很像——都以带颜色的标记呈现在事件列表上，都是项目范围的列表，都能改名和改颜色。但它们干的活非常不同。

状态驱动行为。状态记录上的三个布尔标志连同状态的顺序，决定了哪些事件算作活动事件、事件头部会出现哪些按钮、SLA 计时什么时候停止，以及事件什么时候从状态页上撤下来。严重性本身什么都不驱动——它们是描述影响程度的标签，也是其他规则可以匹配的对象。

两个列表都在项目创建时预置，也都在 **事件 → 设置** 下编辑。事件侧边菜单的这个区块默认是折叠的，所以在四处翻找之前，先展开 **设置**。

## 状态承载行为，严重性承载含义

`IncidentState` 模型有 `name`、`description`、`color` 和 `order`，外加三个布尔值：`isCreatedState`、`isAcknowledgedState` 和 `isResolvedState`。产品对状态做的每一件事，依据的都是这些布尔值和 `order`——而绝不是状态的名字。这也是为什么你可以把 **已解决** 改名为"已关闭"而一切照常：标志跟着记录走，不跟着名字走。

`IncidentSeverity` 模型有 `name`、`description`、`color` 和 `order`，再无其他。它没有任何标志。OneUptime 里没有任何地方会主动把 **Critical Incident** 和 **Minor Incident** 区别对待——严重性只有在你把某个东西指向它时才起作用，比如值班规则上的 **事件严重性** 匹配条件。

几条简单规则：

- **用严重性来传达影响** —— 它会显示在事件列表上、事件的 **概览** 上，并且在你声明事件时是必填项。
- **用状态来刻画你的流程** —— 你实际走过的那些响应步骤，按你实际走过的顺序排列。
- **别把紧急程度编码进状态里** —— 一个叫"Critical"的状态不会呼叫任何人。做这件事的是严重性加上一条值班规则。

## 预置的状态

项目创建时会按以下顺序创建三个状态。这个预置过程是幂等的——只有当同名状态尚不存在时才会新增。

| 状态              | `order` | 标志                   | 颜色       | 含义                                |
| ---------------- | ------- | --------------------- | --------- | -------------------------------------------------- |
| **Identified**   | `1`     | `isCreatedState`      | `#fd625e` | 新事件落入的状态。                   |
| **已确认**        | `2`     | `isAcknowledgedState` | `#ffbf53` | 已经有人接手了这个事件。              |
| **已解决**        | `3`     | `isResolvedState`     | `#2ab57d` | 事件结束，不再计入活动事件。           |

留意名称：第一个状态叫 **Identified**，尽管产品内部的一些描述文字仍然把它称为"创建"状态。当文档或提示里提到"创建状态"时，指的是那个带 `isCreatedState` 标志的状态——在全新项目里，就是 **Identified**。

## 每个状态标志到底做什么

| 标志                   | 用途                                                                                                                                                              |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `isCreatedState`      | 没人选状态时事件默认落入的状态。如果项目里没有任何状态带这个标志，创建事件会失败，并提示你去设置里添加一个创建事件状态。                                             |
| `isAcknowledgedState` | 标记项目的已确认状态：**Acknowledge** 会把事件移入的状态，也是已确认统计卡片所用的名称。处于该状态、其后任一状态或已解决的事件都算已确认——不再为它提供 **Acknowledge**，值班不再为它发起呼叫，它的 SLA 会被标记为已响应。 |
| `isResolvedState`     | 标记项目的已解决状态：**解决** 按钮把事件移入的状态，也是已解决统计卡片显示的状态。处于该状态或其后任一状态的事件都算已解决——它会离开 **活动事件** 和状态页的活动区块，其 SLA 也会被标记为已解决。 |

每个项目中，每个标志预期只由一个状态持有——查询取的是单条记录。这三个带标志的状态可以改名、改颜色和重新排序，但设置页面拒绝删除它们，并会报错点名创建状态、已确认状态和已解决状态。

由于界面是动态读取状态名称的，改名会改变你在各处看到的文字——统计卡片、确认对话框标题，以及事件列表上的标记，全都跟随你给这条记录起的名字。

## 添加你自己的状态

前往 **事件 → 设置 → 事件状态**。这个页面是一个按 `order` 升序排列的有序列表，新状态会加在已解决状态的正上方。拖动某一行就能改变它的位置。

**状态上的字段：**

- **名称** —— 必填，至少两个字符。占位提示会建议类似"Investigating"的写法。
- **描述** —— 可选的自由文本，解释事件处于这个状态时意味着什么。
- **颜色** —— 必填。从取色器中选择；以 `#fd625e` 这样的十六进制值存储。

你无法在这个表单上设置那三个标志——它们属于预置的记录。因此你添加的状态是不带标志的状态，这带来两个值得提前规划的后果：

- **在已解决状态之上，它让事件保持活动。** **活动事件** 收录当前状态位于已解决状态之上的事件，所以你加在那里的状态会让事件留在活动列表和侧边栏计数里。拖到已解决状态之下的状态在任何地方都算已解决——活动列表、状态页、提醒和 SLA 都如此——把事件从 **已解决** 移到这样的状态也不算第二次解决。
- **它的转换按钮是通用的。** 确认对话框不会是 **Acknowledge** 或 **解决**，而是标题为 **将事件标记为 `<state name>`**、提交按钮为 **标记为 `<state name>`**。

一种常见做法，是在已确认状态和已解决状态之间插入一个分诊或缓解步骤——比如拖一个新的"Mitigated"状态，让它排在 **已确认** 之后、**已解决** 之前。

## 顺序是真正的约束，不是显示偏好

`order` 列在写入状态变更时就会被强制执行，而不只是用来画列表：

- **向后转换会被拒绝。** 把事件移动到顺序早于当前状态的状态上会失败，错误信息会点名这两个状态。
- **重选当前状态会被拒绝。** 把事件设置成它已经处于的状态会失败，提示 "Incident state cannot be same as previous state."
- **补录的记录不能与相邻记录重复。** 插入一条时间线记录，如果它的状态与紧随其后的那条相同，同样会被拒绝。
- **头部按钮跟随带标志状态在顺序中的位置。** **Acknowledge** 和 **解决** 是否出现，取决于当前状态在按顺序排列的列表中处于什么位置。排在已解决状态*之后*的自定义状态永远不会显示 **解决** 按钮，因为前面已经没有可以推进的目标了。

所以当你添加状态时，把它放在事件真的会经过的位置上。顺序排错不只是看着别扭——它会让转换根本无法进行。

## 预置的严重性

项目创建时会按以下顺序创建三个严重性：

- **Critical Incident**（`order` 1，`#b70400`）—— 对客户影响极大、需要立即响应的问题。比如全面宕机或数据泄露。
- **Major Incident**（`order` 2，`#fd625e`）—— 影响显著，通常需要立即响应，有时存在能限制损害的临时办法。比如某个重要子系统故障。
- **Minor Incident**（`order` 3，`#ffbf53`）—— 影响较低，通常在工作时间内处理，多数客户不太会察觉。比如应用性能略有下降。

声明事件时严重性是必填的，监视器条件里的每一份事件规格也必须带严重性，所以每一个事件——无论手动还是自动——诞生时都带着一个严重性。声明流程见 [声明事件](/docs/incidents/declaring-incidents)，监视器驱动的路径见 [事件与告警模板](/docs/monitor/incident-alert-templating)。

## 编辑严重性

前往 **事件 → 设置 → 事件严重性**。形态与状态页面相同——按 `order` 排序的有序列表、拖动重排、新严重性追加到末尾，表单上有 **名称**、**描述** 和 **颜色**。

与状态有两点不同：

- **没有删除保护。** 任何严重性都可以删除，包括那三个预置的。
- **没有标志可继承。** 新建的严重性和预置的表现完全一样——一个带颜色和位置的标签。

**关于占位提示的一点说明。** 严重性表单一字不差地复用了状态表单的示例文案，所以那些提示讲的是事件状态而不是严重性。忽略它们，写你自己的严重性名称和描述就好。

严重性真正超出"描述"作用的地方在这里：在 **事件 → 规则 → 值班规则** 上，规则的 **事件严重性** 字段是一个匹配条件。想表达"任何严重问题都呼叫数据库团队"，做法就是把 **Critical Incident** 列在那里——值班策略挂在规则上，而不是挂在严重性上。

## 让事件在状态之间流转

事件改变状态有四种方式：

- **头部按钮。** 打开一个事件。如果它的当前状态排在已确认状态之前，你会看到 **确认** 和 **解决**；如果它介于两者之间，你只会看到 **解决**。每个按钮都会打开一个简短的确认对话框——**确认事件** 或 **解决事件**——其中有 **通知状态页订阅者**，以及折叠在 **添加公开备注** 下的可选 **公开备注** 和 **选择备注模板**（项目有备注模板时）。确认还会停止该事件的所有值班升级。
- **状态时间线。** 在事件的 **状态时间线** 页面上手动添加一行，填写 **事件状态**、**开始** 和 **通知状态页订阅者**。
- **批量更改。** 事件列表提供 **更改状态** 批量操作，可以一次移动多个事件。
- **自动。** 启用了 **自动解决事件** 的监视器条件，会在条件不再满足时解决对应的事件；API 也可以通过 `/api/incident-state-timeline` 更新状态。

以上每一种方式都会写入一条时间线记录。状态变更还会附带做几件你不必特意要求的事：向事件信息流写入一条记录、在事件还没有事件指挥官时指派一位，以及更新 SLA 计时。重新打开一个已解决的事件，会从重开时刻起启动一份全新的 SLA 记录。

## 确认会做什么

事件从移入你的已确认状态、其后的任一状态（例如你放在 **已确认** 之下的 **Investigating** 状态）或已解决状态的那一刻起就算已确认——不论是用上面四种方式中的哪一种移动的。状态设置页面会显示是哪些状态。确认之后：

- **不再提供 Acknowledge。** 事件页头、移动应用（按钮和滑动操作）、Slack 或 Microsoft Teams，以及 OneUptime MCP 服务器的 `acknowledge_incident` 都不再提供。仍然去确认它——从值班呼叫、Slack 或 Teams——会以 "Incident is already acknowledged."（或 "Incident is already resolved."）被拒绝，而不是把它在列表中往回移。
- **值班不再为它发起呼叫。** 同事已确认事件或已把它往后推进之后，再确认自己呼叫的值班人员，只会让自己的呼叫被确认，事件保持原状。
- **SLA 被标记为已响应**，时间为第一次这样的移动；之后继续移入更靠后的状态会保留该时间。
- **确认耗时计到第一次这样的移动** ——事件 **概览** 上的统计卡片、**Time to Acknowledge** 指标、在事件被确认时结束的测量，以及 Slack 和 Microsoft Teams 摘要中的 MTTA。从 **Identified** 直接移入 **Investigating** 的事件在那时就已确认；立即解决的事件在解决时算作已确认。
- **已确认筛选** ——例如仪表板上的事件列表小部件——会显示处于你的已确认状态及其后任一状态、尚未解决的事件。

告警和片段按你的告警状态遵循同一规则。

## 解决会做什么

事件从位于你的已解决状态之上的状态，移入已解决状态或其后的任一状态时，就算被解决——不论是用上面四种方式中的哪一种移动的。每次解决：

- **交还事件占用的监视器。** 以未解决状态声明的事件会占用它的监视器：它把监视器置于自己的 **Change Monitor Status to** 状态（如果设置了的话），手动声明时还会暂停它们的监控。事件未解决期间的编辑——添加监视器或更改那个状态——也会让它占用这些监视器。解决时，除非还有别的未解决事件压在这些监视器上，它们的监控会恢复、状态回到正常运行，此后该事件不再占用任何东西。所以一开始就以已解决状态声明的事件不会交还任何东西，重新打开后的第二次解决也一样：监视器在此期间得到的状态——来自探针、维护或手动设置——会保持不变。
- **把 SLA 标记为已解决**，并在 OneUptime AI 的事后分析草稿开启时起草一份事后分析。

从 **已解决** 继续移到其后的状态——比如 **已关闭**——不算第二次解决：以上都不会再执行，也不会开始新的 SLA。在 OneUptime 开始记录这一点之前声明的事件，会像以前一样在下一次解决时交还监视器。

## 状态时间线

事件侧边菜单里的 **状态时间线** 页面，是事件经历过的每一个状态的审计轨迹。该页面上的卡片标题为 **状态时间线**，按时间倒序排列。

**列：**

- **事件状态** —— 一个带状态名称和颜色的彩色标记。
- **开始** —— 事件进入该状态的时间。
- **结束** —— 事件离开该状态的时间。当前状态显示为 `Currently Active`。
- **持续时间** —— 在该状态中停留的时长，当前状态则计算到此刻。
- **订阅者通知状态** —— 本次变更的状态页通知是已发送、已跳过还是仍在等待，带一个 **更多详情** 链接，发送失败时还带一个 **Retry** 操作。

**行操作：**

- **查看原因** —— 打开一个 **根本原因** 对话框，呈现该次状态变更所记录的 Markdown。
- **查看日志** —— 打开一个对话框解释状态为何变化，内含 **事件状态日志** 查看器。

时间线记录可以创建和删除，但不能编辑。删错一行就等于改写事件的历史，所以请把它当成纠错工具，而不是日常清理的习惯。

## 活动事件列表

**事件 → 活动事件** 是你值班时盯着看的那个列表。它的定义只有一个条件：事件的当前状态位于你的已解决状态之上——已解决状态就是顺序中第一个带 `isResolvedState` 标志的状态。别的一概不看——不看严重性，不看时长，也不看有没有人确认过。

侧边菜单项上的红色计数徽章用的是同一个查询，所以徽章和列表永远一致。当没有内容可看时，页面会明确告诉你。

实际后果是：你加在已解决状态之上的自定义状态会让事件留在这个列表里——"Mitigated"不等于"done"——而放在它之后的状态会像已解决状态一样把事件移出列表。告警和片段按各自的状态遵循同一规则，侧边菜单计数、提醒、状态页和移动应用也都读取这一规则。

## 把状态变更告知状态页订阅者

一次状态变更可以给你的状态页订阅者发邮件，但它要过好几道关卡。搞清楚这些关卡，能省下大量"为什么没人收到通知"的排查时间。

通知是按时间线记录逐条请求的，开关就是 **通知状态页订阅者**（`shouldStatusPageSubscribersBeNotified`）——状态变更对话框和手动时间线表单上的那个复选框。关闭时，记录会以"已跳过"的状态连同原因一起保存。开启时，记录会进入队列，由后台任务取走——该任务每分钟运行一次，所以投递很快，但并非瞬时。

**排队的记录在满足以下任一情况时会被跳过：**

- **新状态就是创建状态。** 事件被声明时订阅者已经被告知过了，所以第一条时间线记录刻意不再发第二条消息。
- **事件没有附加任何监视器。** 没有资源，就没有状态页可以把事件映射过去。
- **事件在状态页上不可见**（`isVisibleOnStatusPage` 关闭）。
- **状态页关闭了事件展示**（`showIncidentsOnStatusPage` 关闭）。这一条是按状态页判断的——展示同一监视器的其他页面仍然会收到通知。

**还有一件事会改变结果。** 如果你在状态变更对话框里写了 **公开备注**，那条时间线记录会被标记为"已通知"而不是进入队列。真正送达订阅者的是这条备注本身，所以他们收到的是一条消息而不是两条。这条消息会在每个渠道上写明新的状态，就像状态变更消息那样：例如邮件主题里的 `[Resolved Incident] <title>`，以及 Slack 和 Microsoft Teams 里的 `**Status:** Resolved`。发布这条备注需要创建公开备注的权限：没有该权限时，对话框不会提供备注，而带备注提交的状态变更会被拒绝，状态保持不变。纯状态变更消息背后的事件类型是 `Subscriber Incident State Changed`。

告警、告警片段和事件片段则在状态变更时提供私密备注（**添加私密备注**），规则相同：发布它需要备注自己的权限（自定义角色中的 **Create Alert Internal Note**、**Create Alert Episode Internal Note** 或 **Create Incident Episode Internal Note**；内置的告警、事件和项目角色都有这些权限），没有该权限的人带私密备注提交的状态变更会被整体拒绝，状态保持不变。

关于谁会收到这些消息以及模板如何选择，见 [订阅者与公告](/docs/status-pages/subscribers)。

## 让事件不出现在状态页上

有三件互相独立的事决定了事件是否会出现在公开页面上，而且三者必须同时成立：

- 状态页自身的 **显示事件**（`showIncidentsOnStatusPage`）。
- 事件上的 **在状态页面上可见**（`isVisibleOnStatusPage`）—— 事件 **设置** 页面上的一个开关。它默认为 true，且不在声明向导里；监视器条件可以通过 **在状态页上显示事件** 来设置它。
- **当前状态位于已解决状态之上。** 这正是把事件从活动区块移除的机制：状态页查询取的是当前状态位于你的已解决状态之上的事件，所以已解决状态及其后的任何状态都会把事件撤下。你不需要归档或关闭任何东西——你只要解决它，它就会进入历史。

**私密事件从不出现。** 打开 **私密事件** 会让该事件对所有状态页隐藏，无论上面那些开关如何，并把可见范围限制在它的所有者以及项目管理员和项目所有者。

页面保留多少已解决的历史，是状态页的设置而不是事件的设置。关于页面上的监视器如何决定哪些事件会出现，见 [状态页资源与分组](/docs/status-pages/resources-and-groups)。
