# 备注、所有者与信息流

处理事件的过程中，每个事件都会积累一份书面记录。其中一部分是给客户的——凌晨 02:14 发到状态页上的那条更新，告诉大家你找到了那次糟糕的发布。剩下的是给团队的——某人贴上来的堆栈跟踪、那张终于看懂了的曲线图、决定切换主备的那一刻。

OneUptime 把这两类读者分开。**公开备注** 会发布到状态页，并且可以通知订阅者。**私人备注**（`IncidentInternalNote` 模型）只留在仪表板内部。在两者之下是 **事件信息流**——一条只增不改的时间线，记录事件身上发生的一切；以及 **所有者** 列表，它决定谁会被告知。

这些内容都挂在事件的左侧菜单上：**备注 → 公开备注**、**备注 → 私人备注**，以及 **团队 → 所有者**。信息流则位于事件 **概览** 页面。

## 公开备注与私密备注的区别

这两种备注在仪表板里看着相似，行为却大不相同。

- **公开备注** —— `IncidentPublicNote` 模型，作为事件时间线的一部分提供给状态页。它带有一个你可以自己设定的 **发布于** 日期，以及一个 **通知状态页订阅者** 复选框。
- **私密备注** —— `IncidentInternalNote` 模型。状态页应用中没有任何地方会读取它们。它们没有发布时间字段（列表按 `createdAt` 打戳并排序），也完全没有订阅者相关字段，所以私密备注永远不可能触发订阅者通知。

**"私密"到底意味着什么。** 它的意思是"不发布到状态页"，而不是"限制在更小的人群内"。两种备注共享同一套读取权限，所以任何能读这个事件的人都能读它的私密备注。如果你需要限制谁能看到这个事件本身，请使用事件上的 **私密事件** 标志（`isPrivate`），它会让事件对所有状态页隐藏，并把可见范围限制在该事件的所有者用户、其所有者团队的成员，以及项目管理员和项目所有者。

**所有者两种都能看到。** 所有者通知任务会同时查询公开备注和私密备注。私密备注是对订阅者私密，而不是对正在响应的人私密。

| 如果你想……                                        | 就选             |
| ------------------------------------------------------ | ---------------- |
| 告诉客户你已知的情况以及何时会有进一步消息               | **公开备注**      |
| 补录一条你已经通过别的渠道发出去的更新                   | **公开备注**      |
| 记下一个假设、一条你跑过的命令，或一条走不通的路          | **私密备注**      |
| 附上一份堆内存转储或一张内部仪表板截图                   | **私密备注**      |

## 发布一条公开备注

在事件侧边菜单中打开 **备注 → 公开备注** 并创建一条备注。卡片会说明你在这里写的内容会出现在状态页上；空状态则显示该事件目前还没有创建过公开备注。

| 字段                                | 用途                                                                                       |
| ---------------------------------- | --------------------------------------------------------------------------------------------------- |
| **公开事件备注**                    | 正文，Markdown 格式。必填。表单会提醒你这条备注在状态页上可见，并附上一份速查表链接。          |
| **附件**                           | 在状态页上与订阅者共享的文件。可选。                                                          |
| **通知状态页订阅者**                | 复选框，默认开启。关掉它就能悄悄发布。                                                        |
| **发布于**                         | 必填的日期和时间，默认为当前时间，按你当前所在时区显示。                                       |

**发布于才是备注真正的时间戳。** 状态页按 `postedAt` 而不是按你敲字的时间来排序和展示公开备注——所以如果你是在给状态页补上 40 分钟前发出的那条更新，请把 **发布于** 设成它实际发生的时间。如果一条备注从 API 传来却没带这个字段，OneUptime 会打上当前时间。

列表会显示每条备注的作者、它的 **发布于**、渲染后的 Markdown 及其附件，还有一列 **订阅者通知状态**。你可以按 **创建者**、**备注** 和 **创建于** 筛选。

## 发布一条私密备注

**备注 → 私人备注** 刻意做得更朴素。这里只有两个字段：

- **私密事件备注** —— Markdown 正文，必填。表单直接写明这条备注只对你的团队私有，不会显示在状态页上。
- **附件** —— 提供给事件响应团队的文件。

没有 **发布于**，没有订阅者复选框——备注在创建时打戳。

## 备注上的附件

两种备注都可以通过 **附件** 字段接受文件附件，也都会在备注正文下方渲染出一个附件列表，每个文件带一个 **Download attachment** 链接。

它们的分歧在于谁能取到这个文件：

- **公开备注的附件** 可以由状态页访客通过状态页路由下载，和备注本身一起。
- **私密备注的附件** 只能通过需要认证的仪表板 API 获取。状态页上没有对应的路由。

所以附件的公开/私密选择，和备注文字是同一个选择。面向客户的时间线配图放公开备注；配置转储放私密备注。

## 用 AI 生成备注

两个备注页面都带有 **Generate with AI** 按钮。它会把事件发给你项目配置的 AI 提供方，并把生成的 Markdown 放进备注编辑器，你在保存前可以修改——不会有任何内容被自动发布。

- **Generate Public Note with AI** —— 描述为分析事件数据，产出一条面向客户的备注。模板包括 **Status Update** 和 **Resolution Notice**。
- **Generate Private Note with AI** —— 产出的是一条内部技术备注。模板包括 **Investigation Update** 和 **Technical Analysis**。

按钮背后，仪表板会向 `/incident/generate-note-from-ai/{incidentId}` 发起请求，带上所选模板以及 `public` 或 `internal` 的备注类型。

## 备注模板

如果你的团队每次故障都写同样的三条更新，那就把它们保存一次。两个备注页面都有 **从模板创建** 按钮，点开会出现一个 **从模板创建备注** 选择器，里面有 **选择备注模板** 下拉框。

模板在公开备注和私密备注之间共享：同一份模板列表服务于两者，同一个模板可以插入任意一种备注。

你在 **事件 → 设置 → 备注模板** 管理它们——卡片标题为 **事件的公开或私密备注模板**，表单包含一个 **模板信息** 步骤（**模板名称** 和 **模板描述**，都是必填）和一个用于正文的 **备注详情** 步骤。如果你还没创建任何模板就点了 **从模板创建**，OneUptime 会告诉你一个都还没有；注意提示文字指向的是 Project Settings，但页面实际位于 **事件 → 设置 → 备注模板**。

## 从 Slack 或 Microsoft Teams 发布备注

如果你已经连接了工作区，响应者根本不用离开频道。Slack 和 Microsoft Teams 都提供一个添加备注的操作，它会打开一个对话框，里面有一个可选 **公开备注** 或 **私密备注** 的下拉框加一个文本框，结果会直接写到事件上。

有两个细节值得知道：

- **防重复** —— 每条备注都会记录它来自哪条 Slack 消息（`postedFromSlackMessageId`，格式为 `channel_id:message_ts`），所以好几个人对同一条消息做出反应，最终只会产生一条备注，而不是五条。
- **备注会回传** —— 发布任意一种备注，同时也会向已连接的事件频道推送一条消息，因为该备注的信息流条目在创建时启用了工作区通知。

## 公开备注究竟何时才会真正送达订阅者

创建公开备注时开着 **通知状态页订阅者**，本身并不保证邮件一定会发出去。这条备注必须通过一连串检查，而每一次失败都会记录一个具体原因，而不是直接报错：

1. **通知状态页订阅者** 必须处于开启状态。如果没开，备注在创建的那一刻就会被标记为已跳过。
2. 备注必须属于一个仍然存在的事件。
3. 事件必须至少附加一个监视器——没有监视器，就没有状态页资源可以把备注路由过去。
4. 事件的 **在状态页面上可见** 标志（`isVisibleOnStatusPage`）必须为 true。
5. 该事件所触达的每个状态页都必须开启 **显示事件**（`showIncidentsOnStatusPage`）。
6. 每位订阅者都必须通过自己的偏好检查——未退订，并且在页面允许订阅者选择时，订阅了这个资源和 `Incident` 事件类型。

**通知不是即时的。** 发送任务每分钟运行一次，所以从保存备注到邮件发出，请预期最多约一分钟。这就是 **Sending Soon** 这个标签的含义。

**订阅者通知状态** 这一列跟踪了整个过程：

| 状态                          | 含义                                                     |
| ---------------------------- | ------------------------------------------------------ |
| **Notifications skipped.**   | 上面某道关卡没过。原因会被记录下来。                      |
| **Sending Soon**             | 已排队，等待发送任务的下一次运行。                        |
| **Notifications Being Sent** | 任务正在逐个处理订阅者列表。                              |
| **已发送的通知**              | 所有订阅者通知都已发出。                                  |
| **失败**                     | 任务抛出了异常；错误信息会连同备注一起保存。               |

点击状态上的 **更多详情** 可以打开 **通知状态详情**。在适合重发的情况下，该对话框的按钮是 **Retry**，它会把备注放回待处理状态，让下一次运行重新取走。

订阅者收到的实际消息，是按状态页和按渠道分别套模板的——电子邮件、短信、Slack 和 Microsoft Teams 各自都有针对 **Subscriber Incident Note Created** 事件的模板，其中的变量包括状态页名称和 URL、详情链接、受影响的资源、事件严重性和标题、备注正文，以及每位订阅者专属的退订链接。这些模板和渠道如何配置，见 [订阅者与公告](/docs/status-pages/subscribers)。

## 事件信息流

**事件信息流** 卡片位于事件 **概览** 页面左栏的底部。它是这个事件按顺序讲述的故事：每一条都由一个图标、引发它的人的头像和姓名、一个相对时间戳（悬停可看精确的本地时间）以及一段 Markdown 正文组成。条目按从旧到新排序。

有些条目带有额外细节——比如一条所有者通知会列出所有被发邮件的人。这类条目会显示一个 **More Information** 按钮，点击后打开 **More Information** 面板。

卡片头部还有一个 **操作** 菜单，让你不必离开时间线就能动手：

- **Execute Runbook** —— 针对这个事件启动一份 [runbook](/docs/runbooks/index)。
- **执行值班策略** —— 按需呼叫某个策略。
- **Add Public Note** —— 与公开备注页面相同的四个字段，只是放在对话框里。
- **添加私密注释** —— 只有备注正文和附件。

它旁边的 **刷新** 会重新拉取信息流。

**信息流只增不改，但它不是你的审计日志。** API 允许创建和读取信息流条目，但不允许更新或删除，所以没人能悄悄改写一个事件的历史。它也不是永久的：在计费的部署上，超过三年的信息流记录会被清除。若需要一份持久的"谁改了什么"的记录，请使用事件侧边菜单里的 **审计 → 审计日志**。

## 信息流记录了什么

信息流条目由事件服务本身、两个备注服务、状态时间线、所有者与成员变动、各个规则引擎、值班执行、AI 调查与事后分析运行器，以及通知定时任务共同写入。事件类型涵盖：

- **事件本身** —— `IncidentCreated`、`IncidentUpdated`、`IncidentStateChanged`。
- **备注与复盘文档** —— `PublicNote`、`PrivateNote`、`RootCause`、`RemediationNotes`、`PostmortemNote`。
- **人员** —— `OwnerUserAdded`、`OwnerTeamAdded`、`OwnerUserRemoved`、`OwnerTeamRemoved`、`IncidentMemberAdded`、`IncidentMemberRemoved`。
- **通知** —— `OwnerNotificationSent`、`SubscriberNotificationSent`、`OnCallPolicy`、`OnCallNotification`。
- **自动化** —— `LabelRuleExecuted`、`OwnerRuleExecuted`、`PrivacyRuleExecuted`、`OnCallRuleExecuted`、`AutoRemediation`。

每种类型都有自己的图标，所以你可以扫一遍很长的信息流，把状态变更从闲聊里挑出来。AI 生成的根本原因分析会被明确标记，并以受限的 Markdown 模式渲染。

信息流遵守事件的隐私设置：对于私密事件，信息流的读取会按事件本身相同的方式过滤。

## 所有者

所有者是对一个事件负责的人和团队。事件身上发生的一切都以他们为通知对象——也正是他们，让事件不至于在"我以为别人在处理"的默契中无人问津。

在事件侧边菜单中打开 **团队 → 所有者**。**所有者** 卡片显示一个计数徽章，并把所有者描述为对本事件负责、会收到变更通知的人和团队，还带一个类似"2 人 · 1 个团队"的实时计数。所有者以互相叠压的头像呈现；悬停在某个头像上会显示这个人的电子邮件，或把该条目标记为 **团队**。

- 点击 **添加所有者** 会打开一个选择器，带有搜索人或团队的搜索框。
- 点击头像上的移除控件会打开 **移除所有者** 确认框，然后点 **移除**。
- 还没有任何所有者时，卡片会明确说明，并邀请你添加一位队友或一个团队，好让他们收到变更通知。

所有者用户和所有者团队是分开的记录——添加一个团队，就等于在通知层面让该团队的每位成员都成为所有者，而不必逐个列出他们。

## 所有者是怎么被指派的

有四条路径能进入所有者列表：

- **来自事件模板** —— 模板带有 **所有者 - 团队** 和 **所有者 - 用户** 字段，描述为拥有该事件、并会在事件创建或更新时收到通知的团队和用户。从模板创建事件时会预填它们。参见 [声明事件](/docs/incidents/declaring-incidents)。
- **来自事件所有者规则** —— 匹配的规则会在创建时自动添加所有者。
- **创建时通过 API 传入** —— 随创建调用一起传入的所有者用户和团队会被立即添加，并带一个标志控制他们是否会收到"你被添加了"的邮件。
- **手动** —— 事件进行中的任何时刻，都可以用 **所有者** 页面上的 **添加所有者** 控件添加。

重复添加同一个人是安全的；已经指派过的所有者不会被重复添加。

## 事件所有者规则

**事件所有者规则** 会在匹配的事件创建时自动指派所有者用户和团队——正是这一层路由，让数据库相关的事件不用任何人操心就落到数据库团队手里。你可以在 [事件设置与自动化](/docs/incidents/settings) 里连同其余事件自动化一起找到它们。

规则表单有三个步骤——**基本信息**、**匹配条件** 和 **Owners**——所有者这一步包含两个区块：

- **要分配的所有者** —— 选择 **所有者团队** 和 **所有者用户**。规则匹配时，所选的每个用户和团队都会被添加为所有者，已经指派过的不会重复添加。
- **继承所有者** —— 从相关实体继承所有者，而不是逐一点名。**从监视器继承所有者** 会让该事件所有监视器的每一位所有者都成为该事件的所有者，而 **从主机继承所有者**、**… From Kubernetes Clusters**、**… From Docker Hosts**、**… From Podman Hosts** 和 **… From Services** 则对这些资源做同样的事。

一个 **通知所有者** 开关控制这些人是否会知情。做真正的路由时保持开启；想悄悄添加所有者就关掉它——当某条规则只是记账上的便利而不是为了呼叫人时，这很有用。

每一次规则执行都会写入事件信息流，所以你随时能分辨某个人是被规则加进来的，还是被人加进来的。

## 所有者会收到哪些通知

有五个任务通知所有者，每个都每分钟运行一次：

- **事件已创建** —— 主题 `[New Incident {number}] - {title}`。
- **有人发布了备注** —— 公开备注*和*私密备注都算，主题 `[Update Incident {number}] - {title}`。
- **事件状态发生变化** —— 参见 [事件状态与严重级别](/docs/incidents/states-and-severities)。
- **你被添加为所有者** —— 主题 `You have been added as the owner of Incident {number} - {title}`。
- **仍未解决** —— 由事件的下次提醒时间驱动的提醒，主题 `[Reminder] Incident {number} is still {state} - {title}`。

每条通知都会构建电子邮件、短信、语音电话、推送和 WhatsApp 版本，然后交给用户的通知设置来决定实际发送哪些。每位接收者都可以逐项关闭它们——按用户的设置措辞为：向你发送事件创建、备注发布、状态变更、所有者添加、成员分配和仍未解决提醒的通知。只想在状态变更时接到电话的人，可以精确地做到这一点。

**没有所有者的事件不会悄无声息。** 如果一个事件完全没有所有者，通知任务会回退到项目的所有者，所以不会有消息掉在地上。每一位被通知的人也会被追加到对应的信息流条目里，所以事后你能准确看到谁被告知了、发到了哪个地址。
