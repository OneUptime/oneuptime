# 核心概念

OneUptime 有很多产品，但它们都建立在几个概念之上：项目、监视器、事件和告警、值班、状态页面以及遥测。围绕这些概念的，还有你监视的对象、你安装的组件，以及替你采取行动的规则。本页用几句话解释每个概念，展示它们之间的联系，并链接到详细介绍它们的页面。读过一遍之后，文档中的其他页面都会更容易理解。如需逐个查词，请参阅 [术语表](/docs/introduction/glossary)；如需在两个看起来相似的东西之间做选择，请参阅 [该用哪一个？](/docs/introduction/which-one)。

:::cards
- [项目和人员](#项目和人员): 一切存放在哪里，以及谁能做什么。
- [监视器和探测器](#监视器和探测器): OneUptime 如何发现问题。
- [事件和告警](#事件和告警): 团队开展工作所依据的记录。
- [值班](#值班): 呼叫谁、如何呼叫，以及下一个是谁。
:::

## 各部分如何联系

问题在 OneUptime 中沿着一个方向流动。探测器和你自己的遥测数据为监视器提供输入。监视器的条件决定何时出了问题，以及要打开什么：事件、告警，或两者兼有。值班策略就此呼叫相关人员，状态页面则把事件告知你的客户。

```mermaid title="问题如何在 OneUptime 中流转"
flowchart TB
    probes["探测器运行检查"] --> monitors["监视器"]
    telemetry["应用和代理<br/>发送遥测数据"] --> monitors
    monitors -->|"声明"| incident["事件"]
    monitors -->|"创建"| alert["告警"]
    incident --> policy["值班策略"]
    alert --> policy
    incident --> statuspage["状态页面"]
    policy --> person["值班人员"]
    statuspage --> subscribers["订阅者"]
```

## 项目和人员

**项目** 包含一切：监视器、事件、值班策略、状态页面、遥测数据和设置。大多数公司只需要一个，也有一些公司为每个环境或业务部门各建一个。你在一个项目中创建的内容，在另一个项目中不可见。

你的 **账户** 独立于项目。一个账户使用一个邮箱和密码，可以属于任意数量的项目；使用左上角的项目选择器在它们之间切换。请参阅 [您的账户](/docs/introduction/your-account)。

人员通过 **团队** 加入项目，团队的权限决定其成员可以做什么。每个新项目一开始都有三个团队：包含你在内的 Owners，以及 Admin 和 Members。在 OneUptime Cloud 上，每个项目都有自己的套餐。

:::cards
- [用户、团队与权限](/docs/permissions/index): 邀请成员并决定他们可以做什么。
:::

## 监视器和探测器

**监视器** 检查你运行的某一样东西，并判断它是否正常工作。大多数监视器由 **探测器** 来检查：探测器是按计划运行检查的机器，例如请求页面、调用 API、ping 主机或查询数据库。OneUptime Cloud 在多个区域运行探测器，自托管安装运行自己的探测器，你也可以在自己的网络内添加自定义探测器。其他监视器则读取你发送的内容：来自应用的遥测数据，或者服务器、Kubernetes 集群和其他基础设施上的代理所报告的数据。

监视器的 **条件** 决定每个结果意味着什么。条件按顺序检查，第一个匹配的条件可以改变监视器的状态、声明事件、创建告警，或三者都做。每个新项目都有三种监视器状态：**运行正常**、**性能下降** 和 **离线**。

:::cards
- [创建监视器](/docs/monitor/create-monitor): 选择类型，说明要检查什么以及多久检查一次。
- [自定义探针](/docs/probe/custom-probe): 检查只有你自己的网络才能访问的内容。
:::

## 你监视的对象

一个监视器只检查一样东西。在监视器之外，OneUptime 还会记录你运行的东西，你会在菜单中遇到这些记录：

- **监视器组** 把多个监视器汇总为一个状态，这样状态页面就可以把由许多部分组成的东西（例如 Checkout）显示为一行。
- **服务** 是你运行的应用或微服务。它的遥测第一次到达时，OneUptime 会添加它，并把它的日志、追踪、指标、异常和事件汇集到一个页面上。
- **主机**、**Kubernetes** 集群以及 **基础设施** 中的其他部分，是你运行的机器和平台，由你安装的代理填充。
- **清单** 是这一切的完整列表：服务、主机、集群、设备、云资源，以及根本不发送遥测的东西。

它们在问题出现的地方交汇。一个服务的监视器可以汇总成一个监视器组，SLO 会衡量这些监视器，当其中一个失败时，它会声明一个事件。该事件会把这个服务列入它影响的资源，状态页面则显示该组和该事件。

```mermaid title="一个服务、监视它的东西，以及它显示在哪里"
flowchart TB
    service["服务：Checkout"] -->|"被监视"| monitors["它的监视器"]
    monitors --> group["监视器组"]
    monitors --> slo["SLO"]
    monitors -->|"声明"| incident["事件"]
    group --> statuspage["状态页面"]
    incident --> statuspage
```

:::cards
- [监视器组](/docs/monitor/monitor-groups): 把多个监视器汇总为一个状态。
- [服务](/docs/telemetry/services): 你运行的每个应用，各占一个页面。
- [资产清单概览](/docs/inventory/overview): OneUptime 对你的环境所知道的一切。
:::

## 可靠性目标

**SLO**（服务等级目标）是为你所监控的对象设定的可靠性目标，例如在 30 天内 99.9% 的时间可用。OneUptime 每 5 分钟根据它的监视器测量一次。目标所允许的停机时间就是它的错误预算：余量充足时你可以承担风险，余量不多时就要放慢节奏，投入稳定性建设。

:::cards
- [SLO 概览](/docs/slo/introduction): 设定目标，并查看预算还剩多少。
:::

## 事件和告警

两者都记录一个问题，也都可以呼叫值班人员。区别在于问题影响的是谁。

| | 事件 | 告警 |
| --- | --- | --- |
| **是什么** | 影响用户的问题，例如服务中断或变慢 | 需要团队在用户受影响之前调查的问题 |
| **在状态页面上** | 可以显示，并通知订阅者 | 从不显示 |
| **初始状态** | **已识别**、**已确认**、**已解决** | **已识别**、**已确认**、**已解决** |
| **初始严重性** | Critical Incident、Major Incident、Minor Incident | **高**、**低** |

确认表示已经有人在处理，并阻止值班策略呼叫下一级。解决则将其关闭。你可以添加自己的状态和严重性，并把告警关联到它们最终被证明所属的事件。

**片段** 将相关的事件或相关的告警归为一组，让团队把它们作为一个整体处理。分组规则决定哪些属于同一组。

:::cards
- [事件概览](/docs/incidents/index): 事件如何被声明、处理和解决。
- [警报概览](/docs/alerts/index): 警报从何而来，以及片段如何对它们分组。
- [关联的告警](/docs/incidents/linked-alerts): 把一次故障引发的告警关联到它的事件。
:::

## 值班

**值班策略** 决定针对事件或告警呼叫谁，以及没人响应时下一个呼叫谁。它的 **升级规则** 就是它的级别：每一级先呼叫其人员，然后等待有人确认，再呼叫下一级。一个级别可以呼叫人员、团队或 **值班计划**，值班计划是一种轮换，随时都知道谁在值班。

如何联系每个人由他们自己决定。在 **用户设置** 中，每个人都保存了 OneUptime 可以联系他们的方式，例如邮件、短信、电话、推送通知、Slack 或 Microsoft Teams，以及被呼叫时使用其中哪些方式。

:::cards
- [值班概览](/docs/on-call/index): 呼叫如何送达某人，以及各部分位于何处。
- [升级规则](/docs/on-call/escalation-rules): 逐级呼叫人员，直到有人响应。
- [值班计划](/docs/on-call/schedules): 轮换、层级和交接。
- [OneUptime 如何联系你](/docs/notifications/index): 决定如何联系每个人的通知方式、规则和设置。
:::

## 状态页面和维护

**状态页面** 向客户展示你的服务是否正常工作。你选择它显示哪些监视器，并使用客户能理解的名称。当其中某个监视器上有活动事件时，页面会显示它，其 **订阅者** 会通过邮件、短信、Slack、Microsoft Teams 或 Webhook 收到通知。状态页面可以是公开的，也可以只对你允许的人开放。

**计划维护** 提前公布计划中的工作。一个维护事件会依次经历 **已计划**、**进行中**、**已结束** 和 **已完成**，显示它的状态页面会告知访问者和订阅者。

:::cards
- [状态页概览](/docs/status-pages/index): 创建状态页面并决定它显示什么。
- [订阅者与公告](/docs/status-pages/subscribers): 通知谁，以及何时通知。
- [计划维护概览](/docs/scheduled-maintenance/index): 事件如何进行，以及它会暂停什么。
:::

## 遥测

**遥测** 是你的系统发送给 OneUptime 的内容：日志、指标、追踪、异常和性能剖析。应用通过 OpenTelemetry 发送，OneUptime 的代理则从主机、Kubernetes 集群、Docker 主机和其他基础设施发送。每个发送方都使用一个 **摄取密钥**，它在 **项目设置 → 遥测与 APM → 摄取密钥** 下创建。你可以搜索遥测数据、在仪表板上绘制图表，并用遥测监视器监控它；遥测监视器会像其他监视器一样产生事件和告警。在菜单中，**日志**、**指标**、**追踪**、**性能剖析** 和 **异常** 各自打开一类数据；**AI / LLM** 跟踪你的 AI 的对话，**数据可观测性** 监视你数据库中的表，**拓扑** 则描绘这一切如何相互连接。

:::cards
- [OpenTelemetry](/docs/telemetry/open-telemetry): 从你的应用发送日志、指标和追踪。
- [日志监控](/docs/monitor/logs-monitor): 当日志中出现某种模式时收到通知。
:::

## 安全

**安全事件** 保存来自你的日志、安全工具以及你发送的其他任何内容的安全事件。它的检测规则会把发现的内容变成安全案例，由你的团队在队列中处理，并由剧本作出响应。**数据安全** 找出你的存储桶、数据库和遥测中的敏感数据，并指出它们的保存方式有什么问题。

:::cards
- [安全入门](/docs/telemetry/security-getting-started): 在你已有的数据中发现威胁。
- [数据安全概览](/docs/data-security/index): 找出你的敏感数据，并改进它的保存方式。
:::

## 你安装的组件和密钥

OneUptime 的大部分功能都无需安装任何东西。只有在需要访问 OneUptime 从外部看不到的内容时，你才需要安装某样东西，而每个组件都使用一个密钥向外连接到 OneUptime：

- 自定义探测器在你的网络内部运行监视器的检查，使用它自己的探测器 ID 和密钥。
- **OpenTelemetry Collector**、Kubernetes 代理和 Docker 代理使用 **摄取密钥** 发送遥测。Server / VM 监视器背后的基础设施代理则使用该监视器的密钥发送数据。
- **Runner** 在你的基础设施内部运行运行手册步骤，使用它自己的 Runner ID 和密钥。

摄取密钥只能把遥测发送进来。**API 密钥** 是另一种密钥：它让脚本、CLI、Terraform 或 AI 助手读取和更改你的项目，权限由你授予。两者都不能代替对方。

:::cards
- [该用哪一个？](/docs/introduction/which-one#探测器代理收集器还是-runner): 要安装什么，以及每一个使用哪种密钥。
- [摄取密钥](/docs/telemetry/ingestion-keys): 创建、限定范围和轮换用于发送遥测的密钥。
:::

## 自动化与 AI

- **工作流** 在发生某些事情时运行操作，例如在声明事件时向 Slack 发帖。
- **运行手册** 把响应流程变成团队可以手动或自动执行的步骤。
- **OneUptime AI** 调查新的事件和告警，并把发现发布到它们的时间线上；**询问 AI** 回答关于你项目的问题。新项目默认开启 AI；**项目设置 → 人工智能 → AI 功能** 下的 **启用 AI** 开关可以把它全部关闭。

:::cards
- [工作流概览](/docs/workflows/index): 通过触发器和组件自动执行操作。
- [AI SRE](/docs/ai/ai-sre): OneUptime AI 如何调查事件和告警。
:::

## 标签和所有者

**标签** 是你添加到监视器、事件、状态页面和大多数其他资源上的标记，用于筛选和分组。团队的权限可以限定在带有某些标签的资源上。**所有者** 是对某个资源负责的人员和团队：当该资源发生情况时，他们会收到通知。标签规则和所有者规则会自动为新资源添加标签和所有者。

:::cards
- [标签与所有者规则](/docs/configuration/label-and-owner-rules): 自动为新资源添加标签并分配所有者。
:::

## 规则的类型

OneUptime 中有许多东西都叫作规则。每一种都会在新内容到来时替你做一个决定，它们可以分成几个类别。其中大部分位于 **事件** 和 **警报** 侧边菜单的 **规则** 下。

| 决定什么 | 规则 |
| --- | --- |
| 呼叫谁 | **值班规则** 挑选新事件或警报要运行的值班策略，策略的 **升级规则** 则逐级呼叫 |
| 谁拥有它，以及如何给它加标签 | **所有者规则**、**标签规则** 和 **隐私规则** |
| 哪些属于同一组 | **分组规则** 创建片段并向其中添加内容 |
| 在它上面运行什么 | **Runbook 规则** 启动运行手册，**AI 规则** 决定 OneUptime AI 调查和修复什么 |
| 何时跟进 | **SLA 规则** 跟踪响应和解决时间，**提醒规则** 在它尚未关闭时提醒所有者 |

监视器自身的规则就是它的条件。**用户设置** 下的值班规则则是另一回事：它们属于每个人自己，决定呼叫如何送达这个人。

:::cards
- [事件设置与自动化](/docs/incidents/settings#事件创建时运行的规则): 创建事件时运行的规则，按顺序排列。
- [如何联系我](/docs/notifications/on-call-rules): 呼叫如何送达你。
:::
