## 事件、警报还是其他类型的问题？

大多数问题要么是事件，要么是警报：根据问题影响的是谁来选择。其他几种是 OneUptime 为你保存的记录，它们每一种都可能引出事件或警报。

| 记录 | 是什么 | 何时使用 |
| --- | --- | --- |
| [事件](/docs/incidents/index) | 影响用户的问题。它可以呼叫值班人员，并显示在你的状态页面上。 | 客户已经注意到或很快就会注意到：服务中断、变慢、结账失败。 |
| [警报](/docs/alerts/index) | 需要团队处理的问题。它可以呼叫值班人员，但从不显示在状态页面上。 | 团队应在用户注意到之前采取行动：磁盘快要写满、证书即将过期。 |
| [片段](/docs/incidents/episodes) | 一组相关的事件或相关的警报，作为一个整体处理。 | 一个原因引发了许多事件或警报。分组规则会为你创建片段。 |
| [异常](/docs/telemetry/exceptions) | 你的代码抛出的某个错误的每次出现，归为一组，并附有堆栈跟踪。 | 你想修复一个 bug。错误激增时，异常监视器可以创建警报或事件。 |
| [AI 洞察](/docs/ai/ai-sre#洞察主动检测) | OneUptime 在任何呼叫发生之前就在你的遥测中发现的问题，例如错误日志激增。 | 你想要提前预警。洞察从不呼叫任何人，也从不创建事件：它在收件箱中等待。 |
| [安全案例](/docs/telemetry/security-cases) | 一个值得调查的威胁，关于同一用户、主机或地址的每次检测都归入其中。 | 你的安全团队进行调查。用户受到影响时，在案例上点击 **声明事件** 即可创建一个事件。 |

警报可以关联到它最终被证明所属的事件，因此从警报开始不会丢失任何信息。

## 工作流、运行手册、剧本还是 AI 规则？

这四种都可以自动运行。根据它们作用于什么、步骤由谁编写来选择。

| 工具 | 做什么 | 何时使用 |
| --- | --- | --- |
| [工作流](/docs/workflows/index) | 画布上的块，在其触发器触发时运行：事件被创建、计划时间到达、其他工具调用一个 URL。 | 你想把 OneUptime 连接到其他工具，或对它的记录执行操作，而无需编写代码。 |
| [运行手册](/docs/runbooks/index) | 把你的响应流程写成步骤，从手动检查清单到脚本、HTTP 请求和 kubectl，在事件、警报或维护事件上运行。 | 响应人员每次都应遵循相同的步骤。运行手册规则会在匹配的事件上启动运行手册。 |
| [剧本](/docs/telemetry/security-cases#剧本) | 响应安全案例的步骤：保全证据、呼叫值班人员、停用用户。 | 你的安全团队每次都以相同的方式响应同一类威胁。 |
| [AI 规则](/docs/ai/ai-sre#哪些事件会被调查和修复) | 决定 OneUptime AI 调查和修复哪些新的事件和警报，以及是否先征求同意。 | OneUptime AI 只应处理部分事件，或无需征求同意就进行修复。没有规则时，它会调查每一个。 |

## 监视器组、服务还是标签？

这三种都能把东西归到一起，但面向不同的读者。它们也可以配合使用：一个服务的监视器可以组成一个监视器组，而它们都可以带有同一个标签。

| 选项 | 是什么 | 何时使用 |
| --- | --- | --- |
| [监视器组](/docs/monitor/monitor-groups) | 把多个监视器汇总为一个状态（取其中最差的），并拥有自己的正常运行时间。 | 对于由多个监视器组成的东西（例如 Checkout），客户应在状态页面上只看到一行。 |
| [服务](/docs/telemetry/services) | OneUptime 在你的遥测中发现的应用，它的日志、追踪、指标、事件和所有者都在一个页面上。 | 你想把关于一个应用的一切放在一个地方。它会根据自己的 `service.name` 自动出现。 |
| [标签](/docs/configuration/label-and-owner-rules) | 你加到监视器和大多数其他记录上的标记。一条记录可以带有多个标签。 | 你想筛选列表、限制团队的权限，或在规则中挑选记录。 |

监视器组默认是关闭的：在 **项目设置 → 高级 → 功能标志** 下开启它们。

## 探测器、代理、收集器还是 Runner？

OneUptime 的大部分功能都无需安装任何东西：只有在需要访问 OneUptime 从外部看不到的内容时，才需要安装。每一种都向外建立连接，并使用自己那一类密钥。

| 安装内容 | 做什么 | 何时安装 | 使用的密钥 |
| --- | --- | --- | --- |
| [自定义探测器](/docs/probe/custom-probe) | 在你的网络内部运行监视器的检查。 | 你要检查的内容位于防火墙之后。OneUptime 自己的探测器检查公开的内容。 | 它自己的探测器 ID 和密钥 |
| [基础设施代理](/docs/monitor/server-monitor) | 向 Server / VM 监视器报告一台机器的 CPU、内存、磁盘和进程。 | 你想为一台服务器设置一个监视器，并对它的数值设置条件。 | 该监视器的密钥 |
| [OpenTelemetry Collector](/docs/telemetry/hosts) | 发送机器的指标、日志和进程。**添加主机** 用一条命令安装它。 | 你想让一台机器连同它的遥测出现在 **主机** 下。 | 摄取密钥 |
| [Kubernetes 代理](/docs/telemetry/kubernetes-agent) | 收集集群的指标、事件、日志和追踪。你用 Helm 安装它。 | 你在运行 Kubernetes。 | 摄取密钥 |
| [Runner](/docs/runbooks/agents) | 在你的基础设施内部运行运行手册步骤，例如 Bash、SSH 和 kubectl。 | 你的运行手册需要访问你自己的主机和集群。 | 它自己的 Runner ID 和密钥 |

### 摄取密钥还是 API 密钥？

| 密钥 | 它让你做什么 | 在哪里创建 |
| --- | --- | --- |
| [摄取密钥](/docs/telemetry/ingestion-keys) | 向项目发送遥测，仅此而已。 | **项目设置 → 遥测与 APM → 摄取密钥** |
| [API 密钥](/docs/permissions/index#api-密钥) | 通过 API、CLI、Terraform 或 AI 助手读取和更改项目，权限由你授予。 | **项目设置 → 高级 → API 密钥** |

两者都不能代替对方。

## 仪表板、公开仪表板还是状态页？

根据谁应该看到它来选择。

| 共享方式 | 谁能看到 | 何时使用 |
| --- | --- | --- |
| [仪表板](/docs/dashboards/index) | 登录到你项目的人。 | 你的团队查看图表和列表：值班屏幕、团队自己的视图。 |
| [公开仪表板](/docs/dashboards/sharing) | 任何拥有链接的人，除非你添加密码、限制只有某些 IP 地址可以访问，或在你自己的域名上托管它。 | 项目之外的人应该看到你的图表，例如合作伙伴或墙上的屏幕。 |
| [状态页](/docs/status-pages/index) | 你的客户，可以公开，也可以只对你允许的私有用户开放。 | 客户想知道你的服务是否正常工作，并希望收到有关事件和维护的通知。 |

状态页面用事件和你为监视器起的名称来说话；仪表板则显示它们背后的数字。
