# 機密データタイプ

データセキュリティは 143 種類の機密データを知っています: カード番号、銀行口座、43 か国の国民 ID、医療関連の識別子、API キーとトークン、そして特別なカテゴリの個人データです。それぞれにカテゴリと機密度があり、1 つの国に属するものには、その国も設定されています。このページでは、値がどのように見つかるかを説明し、すべてのデータタイプを一覧するので、何かが見つかった理由を理解し、どう対処するかを決められます。

## 値の見つけ方

```mermaid title="候補から検出結果まで"
flowchart TB
    shape["形: パターンが<br/>候補を見つける"] --> valid{"バリデーターに<br/>合格するか？"}
    valid -->|"いいえ"| none["検出結果なし"]
    valid -->|"はい"| context["コンテキスト: 近くの語、<br/>またはフィールド名"]
    context --> test{"既知の<br/>テスト値か？"}
    test -->|"はい"| apart["別に数えられ、<br/>検出結果にはならない"]
    test -->|"いいえ"| finding["信頼度付きの<br/>検出結果"]
```

ログ行、CSV のセル、データベースの行、オブジェクトの先頭のバイトなど、どのスキャンも同じ手順を実行します。

1. **形。** 各データタイプには候補を見つけるパターンがあります: 16 桁の数字、 `AKIA` と 16 文字、語と `@` とドメインなどです。パターンはより長いトークンの内部では一致しないので、より長い数字の並びの中からカード番号が見つかることはありません。
2. **バリデーター。** 候補は、そのタイプ独自のルールに合格する必要があります: チェックサム (カードには Luhn、IBAN には mod 97、Aadhaar 番号には Verhoeff、ほとんどの国民 ID にはチェックディジット)、実在する日付、既知のプレフィックス、シークレットであれば十分なランダム性です。合格しなかった候補は、検出結果にはまったくなりません。 `000000000` や `123456789` のようなプレースホルダーは、どの数値タイプにも合格しません。
3. **コンテキスト。** 候補の近く (デフォルトでは前 64 文字、後ろ 32 文字まで) に、それが何であるかを示す語があると信頼度が 1 段階上がり、名前がそのタイプを示すフィールドにある場合も同様です。注文番号や追跡番号など、別のものであることを示す語があると、信頼度は 1 段階下がります。パスポート番号や銀行口座のように、チェックサムがなくありふれた形の番号は、それを名指しする語の隣にある場合にだけ数えられます。
4. **既知のテスト値。** 公開されているテスト用のカード番号 (Stripe の `4242 4242 4242 4242` など)、例示用の IBAN、 `example.com` などの予約済みドメインのアドレス、ドキュメント用の IP アドレス、政府の資料に印刷されているサンプルの ID、 `sk_test_` のようなテストモードのキー、プレースホルダーのキーは別に数えられます。これらが検出結果になることはないので、これらだらけのデータストアは漏えいではなく、テスト環境として扱われます。
5. **信頼度。** 残ったものが検出結果になり、その確かさは証拠が許す範囲までです。

| 信頼度 | 意味 |
| --- | --- |
| **高** | 値がバリデーターに合格し、周囲の語や値があるフィールドが、それが何であるかを示している。または、フィールドの場合は、値の大半がそのタイプである。 |
| **中** | 値はバリデーターに合格したが、周囲にそれを裏付けるものがない。または、フィールド名が保持しているものを示し、一部の値がそれと一致する。 |
| **低** | 形は一致するが、それを裏付けるものがない。 |

数えられるのは高と中の検出結果だけです: これらはデータストアを機密にし、問題を開くことがあります。低の検出結果はデータストアに折りたたまれて一覧され、人が判断します。正しいものに **確認** を使うと高になり、以後のスキャンでも高のままです。

2 つのデータタイプが同じ文字列を主張したときは、より確かな検出結果が優先されます: 信頼度が高いもの、次に独自のルールがより多くを証明する検出器、次により長い一致です。

値は、人が書くとおりにも読み取られます。URL のパーセントエスケープが文字の UTF-8 バイトも含めて読み取られるため、クエリ文字列内の IP アドレス、メールアドレス（`jane%40example.com` や `jos%C3%A9%40example.com` など）、トークンやキーが見つかります。番号の数字はどの文字体系でも読み取られ、全角数字（`４１１１ １１１１ １１１１ １１１１`）やアラビア・インド数字などは、まず文字体系ごとに、次にまとめて読み取られます。対象は、カード番号、電話番号、米国社会保障番号、IBAN、ルーティング番号、国民 ID 番号、そして NHS 番号のような医療関連の ID 番号です。メールアドレスは `张伟@example.com` や `почта@пример.рф` のようにどの文字体系でも見つかり、キーのコロンの直後にある IPv6 アドレス（`ip:2001:db8::1` など）も見つかります。各検出結果は書かれたとおりの値なので、スクラブルールはその場所でそれを隠します。

長い値は 4 KB ずつ重なる 64 KB のウィンドウで読み取られるので、値はどこにあっても丸ごと見つかります。1 つの値から読み取るのは最大 4 MB です。

## フィールドと列

列、JSON のフィールド、ログの属性は、全体として判定されます。その名前はデータタイプを示唆し、サンプリングした値がそれを証明します。値のうちそのタイプを含むものの割合で、検出結果の確かさが決まります。

| そのタイプを含む値 | 信頼度 |
| --- | --- |
| 60% 以上 | 高 |
| 25% 以上 | フィールド名がそのタイプを示していれば高、そうでなければ中 |
| それ未満 | フィールド名がそのタイプを示していれば中、そうでなければ低: ほかのものの列に少しだけ含まれるメールアドレスなど |

値の平均が 80 文字を超えるフィールドは自由テキスト (メモ、メッセージ、説明) であり、1 つのタイプを保持するとは想定されていません。その検出結果は、それぞれの一致が単独で得た信頼度を保持し、自由テキストで見つかったことが示されます。分類されるのは 1 つのフィールドにつき最大 1,000 個の値で、それぞれ最大 16 KB です。

フィールド名は語に分割され ( `customerEmail` 、 `customer_email` 、 `customer-email` はすべて「customer email」になります)、タイプの名前のヒントは、その語が同じ順序で隣り合って現れたときに一致します: 「date of birth」は `customer_date_of_birth` に一致しますが、 `birth_city` には一致しません。ドット区切りのパスでは最後の部分だけがフィールド自身の名前で、最後の部分が `number` 、 `id` 、 `value` のような一般的な語の場合はその前の部分も含みます: `customer.address.city` は住所ではなく、 `card.number` はカード番号のままです。

値からは判別できないデータタイプもあります: 人名と通りの名前、宗教とほかの語を区別できるパターンはありません。これらは、フィールドに値がある場合に、フィールド名だけから見つかります: 人名、ユーザー名、性別、国籍、健康情報、人種または民族的出身、宗教的信条、性的指向、政治的意見、労働組合への加入、生体データ、遺伝データ、犯罪歴です。名前、ユーザー名、性別、国籍は、値の 60% 以上がそれらしく見える場合は高、そうでなければ中になります。自由テキストでは、人名と住所は小さなモデルでも見つかります: [自由テキスト中の名前と住所](#自由テキスト中の名前と住所) を参照してください。人名は URL のクエリ文字列でも、そのようなフィールドと同じように名付けられたパラメーターの下で見つかります。たとえば `full_name` は `/contacts?full_name=Jos%C3%A9%20Garc%C3%ADa` のように書かれます。その値は URL の書き方に従って読まれ、名前に見える場合は高になり、エスケープも含めて書かれた場所で見つかります。`name` とだけ名付けられたパラメーターはモデルに任されます。

名前がパスワードを保持していることを示すフィールド ( `password` 、 `passwordHash` 、 `pwd` 。 `password_changed_at` は除く) は、ハッシュを保持しているはずです: bcrypt、argon2、scrypt、PBKDF2、またはデータストアが使いそうなほかの方式です。空の値、 `********` のようなプレースホルダー、暗号化された値は除外されます。残りのうちハッシュでないものがハッシュより多い場合、そのフィールドはパスワードそのものを保持しています。これはどのパターンにも見えないもので、データストアは [パスワードが平文で保存されている](/docs/data-security/checks-and-issues#データの衛生管理) チェックに不合格になります。

### どの検出器も分類できなかったフィールド

名前がどのデータタイプも示さず、値がどの検出器にも一致しない列やフィールドは、安全とわかっているわけではありません: 自社の顧客番号や、別の言語で名付けられた列かもしれません。プロジェクトの **AI を有効化** がオンなら、コンテンツスキャンはそのようなフィールドを 1 回のスキャンで最大 200 個保持し、それぞれがプロジェクトのどのデータタイプを含むかを OneUptime AI に尋ねます。1 つのデータストアについて一度に尋ねるのは最大 40 フィールドです。伝えるのはフィールド名、隣のフィールドの名前、値の形だけで、各文字を `a` または `A`、各数字を `9` と書くので `AB-1234` は `AA-9999` になります。値そのものは決して伝えません。自由記述のテキスト、値が 5 個未満のフィールド、小さな整数、ID・時刻・ステータスとして名付けられたフィールドは尋ねません。

テレメトリのスキャンも、どの検出器も分類できなかった属性を同じように保持します。サービスのログ、スパン、メトリクス、その他のテレメトリから、1 回のスキャンでサービスごとに最大 50 個です。OneUptime 自身の属性、OpenTelemetry の規約がレコードの出どころを示すために全レコードに書く属性 (サービス、ホスト、Pod など)、ログ本文のような自由記述のテキストは決して保持しません。

OneUptime AI が挙げた各タイプは低の検出結果になり、理由とともに **OneUptime AI の提案** と表示されます。理由はプロジェクトの言語で書かれ、検出結果の行全体にわたって表示されます。ほかの低の検出結果と同じく、人がデータストアの **内容** ページで **確認** を選ぶまでは何にも数えられません。 **機密ではないとマーク** を選ぶと却下されます。回答を得たフィールドは 30 日間は再び尋ねられず、人が判断したフィールドは二度と尋ねられません。

## 自由テキスト中の名前と住所

人の名前をほかの語と区別できるパターンはありません。そのため、自由テキスト (サポートのメモ、ログの行、例外メッセージ、プロンプト) は、人名と住所を見つける小さな言語モデルでも読み取られます。モデルはスキャナーの中、OneUptime のワーカーとお使いのプローブ上で動きます: テキストがスキャナーの外に出ることはなく、実行中に何もダウンロードされず、プロンプトも作られません。これは OneUptime AI ではなく、OneUptime AI のスイッチではオンにもオフにもなりません: それを決めるのは **名前と住所を検出** です。

- **読み取るもの。** 値の平均が 80 文字を超えるフィールド、値がどれほど短くても人が自由テキストを書き込むと名前が示すフィールド (たとえば `delivery_note`、`comentario`、`Lieferhinweis`、`opmerking`。[短い値](#短い値) を参照)、そしてテレメトリでは、どれほど短くてもすべてのログ本文、例外メッセージ、スタックトレース、AI の会話です。1 つのフィールドから異なる値を最大 100 個、合計 32 KB のテキストまで、1 つの値からは最大 16 KB まで読み取ります。読み取るものの中の URL は URL として読まれます: パーセントエスケープが読み取られ、2 つの文字の間の `+` は空白として読まれるため、`/profile?name=Jos%C3%A9%20Garc%C3%ADa` の中の名前が見つかり、書かれたとおりに隠されます。
- **見つけるもの。** **個人名** (`person-name`) と **住所** (`postal-address`) です。住所は、モデルが番地と並べて読み取る場所で、たとえば `14 Calle Mayor` と、その後に続く郵便番号と都市を含みます。都市や国だけでは住所になりません。
- **確信度。** モデルが見つけた名前や住所は、それだけでは中です。フィールド名がそのフィールドに名前や住所があると示すとき、または "customer"、"Kunde"、"dirección" のような近くの語がそう示すときは高です。モデルが確信を持てないとき、つまりスコアが 0.6 未満のときは低です。それぞれが自力で得た確信度を保つので、1,000 行のログの中の 1 つの名前も中のままです。
- **テスト値。** `Jane Doe`、`John Smith`、`Max Mustermann`、`123 Main Street` のようなプレースホルダーは、どのタイプのテスト値とも同じく、別に数えられます。
- **保持するもの。** サンプルは、フィールド名から見つかった名前と同じようにマスクされます: 先頭の 1 文字と 4 つの星で `M****` になります。フィンガープリントは作られません。データストアの **内容** ページでは、このような検出結果に **スキャナーのモデルが自由テキストで検出** と表示されます。
- **レコードとルール。** モデルが見つけた検出は、それが見つかったレコードを一覧にします。各行は名前や住所の周りで切り取られ、その中のすべての名前と住所はマスクされます。また、ほかの検出と同じように、 **スクラブ** はそれらのレコードでルールを証明します。レコードはそのたびに最大 20 秒のモデルの時間を使って、モデルで読み直されます。モデルの時間が足りなかったレコードは一覧に載らず、一覧には時間が足りなかった値の数が示されます。モデルを実行できない場所では一覧がそのことを伝え、その検出のルールは証明されません。

| [openmasq/ner-multilingual](https://huggingface.co/openmasq/ner-multilingual): 多言語 BERT の 6 層、int8 ONNX | Apache 2.0 | 98 MB | `8cf7273` | 英語、スペイン語、ドイツ語、フランス語、イタリア語、ポルトガル語、オランダ語 |

### 短い値

短いフィールドは、人が自由テキストを書き込むと名前が示す場合にだけ読み取られます。このルールは、選ぶ前に 7 言語のデータベースの 49 列、合計 588 個の値で測定しました。商品名、タイトル、ラベル、役職名、店舗名 (ブランド、登場人物、通りの名前は検出になりません) と、91 個の名前と 28 個の住所を含む短い配送メモ、サポートのコメント、顧客の備考です。最初に検討したルール、つまり 4 語以上のすべてのフィールドを読むルールは、カタログの値を 108 個読み取り、そのうち 53 個を誤って名前としました。たとえばポロシャツの名前の `Ralph Lauren` や、本のタイトルの `Tom Sawyer` です:

### どこで動き、どれだけかかるか

- **すべてのイメージに。** ワーカーを動かす App イメージと Probe イメージには、モデル、その語彙、ランタイムが含まれます。エアギャップ環境のイメージと Iron Bank のイメージも同じで、ディスク上で約 114 MB です。これらはイメージのビルド時に固定されたリビジョンから取得され、それぞれの SHA-256 と照合されます。スキャンの実行中には何もダウンロードされません。
- **メモリ。** スキャンが初めて必要としたときに、プロセスごとに 1 回読み込まれます: 約 550 MB で、スキャンのない状態が 10 分続くと解放されます。
- **時間。** 1 コアで、ログの行ほどの長さの値 1,000 件あたり 30 秒から 1 分、1,200 文字の値 1,000 件あたり約 9 分です。データストアのコンテンツスキャンは最大 2 分を割り当てます。1 時間ごとのテレメトリスキャンは合計で最大 1 分、データストアごとに 6 秒を、1 時間ごとに異なるデータストアの組に割り当てます。
- **順番。** 各コンテンツスキャンのモデルは、前回のモデルが止まったところから始めます。自由テキストを読み取らなかった最初のテーブルやコンテナーから始め、時間が足りなかったバケットのオブジェクトは、ほかのどれよりも先に読み直します。始めたものの終えられなかったものは再び最初には回されないため、どれかがスキャンのたびにモデルの時間を占めることはなく、データストアに自由テキストがどれほどあっても、すべてのテーブルとオブジェクトに順番が回ってきます。
- **時間を使い切ると**、スキャンはモデルが読み取った分で完了し、その警告は自由テキストの値をいくつ読み取ったかを伝えますが、何を読んだかは決して伝えません。モデルを持たないワーカーやプローブはこれまでどおりスキャンし、その理由を伝えます:

```text
Names and street addresses were looked for in 120 of 500 free-text values: this store's 6 seconds of model time ran out.
Names and street addresses in free text were not looked for: the model's model_quantized.onnx is not installed on this probe.
```

スキャンの詳細には、これらの警告も、コンテンツやテレメトリのスキャンのほかのすべての警告も、読む人の言語で表示されます。

**名前と住所を検出** はすべてのプロジェクトでオンです: バケット、データベース、BigQuery データセットのコンテンツスキャンは、ワーカーでもプローブでも、モデルで自由テキストを読み取ります。その下の **テレメトリで名前と住所を検出** はオフです: 200 のサービスを持つ忙しいプロジェクトのログ本文、例外、会話をすべて 1 回読むには 1 コアで約 48 分かかり、スキャンの 1 時間あたり 1 分ではその約 4% しか読めません。毎時のスキャンでその一部を読ませるには、オンにしてください。どちらも **データセキュリティ → 設定 → スキャン設定** の **データセキュリティが読み取る内容** にあります。 **テスト** はモデルなしでお使いのブラウザーで動くため、モデルが見つけるものはそこには表示されません。モデルを加えると、ダウンロードが約 113 MB (圧縮時 67 MB)、タブのメモリが約 440 MB 増えるため、モデルはスキャナーの中でだけ動きます。

## 機密度

| 機密度 | 意味 |
| --- | --- |
| **制限** | 漏えいすると害が生じるもの: シークレット、カード番号、診療記録、政府発行の ID。 |
| **機密** | 個人データと、機密と記された文書。 |
| **内部** | 部外者向けではない、企業自身のデータ。 |
| **公開** | 機密のものは何も見つからなかった。 |

データストアの機密度は、少なくとも中の信頼度で見つかったデータタイプのうち、最も機密度の高いものと同じになります。テスト値と、機密ではないとマークされた検出結果は数えられず、何も見つからなかったデータストアは公開です。検出結果が示すよりも機密度を高く、または低く扱うには、データストアの **設定** で機密度を自分で設定します: その後はチェックがその値を使います。

## 独自のデータタイプ

社員 ID、保険証券番号、プロジェクトコードなど、自社にしかないもののためにデータタイプを追加できます。 **データセキュリティ → 設定 → データタイプ** を開き、 **独自のデータタイプ** の下に追加します。次のスキャン以降、組み込みのものとまったく同じように、バケット、データベース、テレメトリでスキャンされます。

:::steps
### それが何かを指定する

**名前** (社員 ID など)、 **カテゴリ** 、そして **感度** (それを保持するデータストアがどれだけ機密になるか) を指定します。 **説明** には、その検出結果を読む人のために、それが何であるかを書きます。

### 見つけ方を指定する

**パターン** を入力します: `EMP-\d{6}` のような、1 つの値を表す JavaScript の正規表現です。 `employee id` のような、それを保持する **フィールド名** と、値の近くにあればこのタイプであることを裏付ける **キーワード** を追加します。フィールド名だけからタイプを見つけるには、パターンを空のままにします。

### テストする

**テスト** にサンプルのテキストを貼り付けると、データタイプがその中で何を見つけるかを確認できます。ブラウザー内で、スキャナー自身のコードがテキストに対して実行されます: テキストが OneUptime に送られることはなく、テストされるのは最初の 64 KB だけです。
:::

**その他の項目** では、 **大文字と小文字を区別しない** を使うと文字の大小に関係なくパターンが一致し、 **キーワードが必要** を使うとキーワードが近くにあるかフィールド名がこのタイプを示している場合にだけ値が数えられ、 **チェックサム** では値が合格すべきチェックを指定します: **なし** 、 **Luhn** (カード番号が持つチェックディジット)、 **Mod97** (IBAN のチェックディジット)、 **Verhoeff** (Aadhaar 番号のチェックディジット) のいずれかです。

パターンは保存時にチェックされます: コンパイルでき、空のテキストに一致せず、テキストの長さに比例した時間で実行できる必要があります。パターンはバックトラックしないマッチャーで実行されるので、どう書かれていても、パターンがスキャンを止めることはありません。1 つのタイプに指定できるのは、最大 50 個のキーワードと 50 個のフィールド名です。

独自のタイプの値は、チェックサムに合格する場合、単独では中、近くにキーワードがあれば高になり、チェックサムがない場合、単独では低、キーワードがあれば中になります。列では、ほかのすべてのタイプと同じく、一致する値の割合で決まります。

### 説明する

新しいデータタイプのフォームの上部で、 **説明する** がフォームに入力します。「社員 ID は EMP-123456 のような形で、ダッシュがないこともあります」のようにデータの形を書き、必要なら例を 1 行に 1 つずつ追加して、 **フォームに入力** を選びます。OneUptime AI に送られるのは文と例の形だけで、例そのものは決して送られません。例はブラウザーの中に留まり、 **テスト** がそのパターンで例をいくつ見つけたかを示します。入力内容を読み、必要なら変更してから保存してください。保存するまで何も保存されず、パターンは自分で書いたものと同じようにチェックされます。説明するには、プロジェクトの **AI を有効化** がオンである必要があります。

## OneUptime AI が見つけるデータタイプ

どの検出器も分類できなかったフィールドには、同じ意味の名前で多くの場所に保存された自社独自のデータタイプがよく含まれています。たとえば保険会社の保険証券番号が、すべてのデータベースで `policy_no`、`policyNumber`、`police_nr` という名前の列に入っている場合です。プロジェクトの **AI を有効化** がオンなら、OneUptime AI はスキャンが保持したフィールドからそのようなデータタイプを見つけ、自社のスキャンで裏付けが取れてから初めて確認を求めます。

:::steps
### フィールドのグループを見つける

2 つ以上のデータストアにある 3 つ以上のフィールドは、値の大半が同じ形 (部分の間の区切り文字の有無は問いません) で、名前が保持内容を表す単語を共有しているとき、1 つのグループになります。数字を含まない形、日付、時刻、小数は決してグループになりません。また `id`、`no`、`number` のような単語は、それだけでは何も表しません。

### データタイプを下書きする

OneUptime AI は新しいグループごとにデータタイプを下書きします。一度に最大 3 つで、フィールドの名前と値の形から作り、値そのものは使いません。下書きは保存済みのタイプと同じチェックに合格し、下書きの元になった形を見つける必要があります。そうでない下書きは、理由を添えてもう一度依頼されます。

### 次回のスキャンで裏付ける

下書きは、グループの各データストアの次回のスキャンで、最大 48 時間またはスキャン間隔 1 回分のうち長い方の間、実行されます。検出結果は作りません。各スキャンは、グループのフィールドと同じデータストアのほかのすべてのフィールドで、それが見つける値の数を数えます。自分のフィールドの値の 80% 以上を見つけ、ほかの値の 1% 以下しか見つけないときに提案されます。ほかの場所でほぼすべての値を見つけるフィールドは、同じデータを別の名前で保持しているものとして示され、不利には数えられません。
:::

各下書きは同時に、絞り込んだ形でも数えられます。絞り込んだ下書きは、グループのフィールドの外では、キーワードのいずれかが隣にあるか、それを示すフィールド名の下にある値だけを見つけます。ほかの場所で見つけすぎる下書きは、それで十分なら絞り込んだ形で提案されます。どちらの形でも十分でない下書きは破棄され、そのグループは 30 日間再び下書きされません。

提案された各データタイプは、 **データセキュリティ → 設定 → データタイプ** の上部と **データセキュリティ → AI** の **確認待ちのデータタイプ** に、スキャンで数えた結果とともに表示されます。たとえば「これら 11 個のフィールドの値の 98% に一致し、同じデータストアの他の場所の値の 0.1% に一致します。」です。 **データタイプを追加** は、その内容で入力済みのデータタイプのフォームを開き、変更とテストができます。保存するとタイプが追加され、次回の実行からスキャンで見つかります。 **データタイプではない** を選ぶと却下され、それらのフィールドについて二度と提案されません。追加するには、データタイプを作成できるロールが必要です。

## 機密ではない値と、機密扱いしない値

スキャンでは、見た目どおりではないものが見つかることがあります: Luhn チェックに合格する注文番号の列や、すべてのログ行にある自社のサポート用アドレスなどです。そのことを OneUptime に伝えると、数えるのをやめます。

- **検出結果を機密ではないとマークする。** データストアの **内容** ページで、検出結果の **機密ではないとマーク** を選び、理由を書きます。その検出結果はデータストアの機密度にもチェックにも数えられなくなり、データストアはすぐに再チェックされます。検出結果はマークと理由が付いたままデータストアに残るので、次の人も何が決まったかがわかります。
- **値を「機密扱いしない」に追加する。** データセキュリティの設定で、 `support@yourcompany.com` のように、どこでも決して検出結果にならない値に使います。値は、スキャナーが正規化した後に、大文字と小文字を区別せずに比較されます。
- **組み込みデータタイプをオフにする。** **データセキュリティ → 設定 → データタイプ** の **組み込みデータタイプ** の下で、すべてのデータタイプにスイッチがあり、切り替えた瞬間に保存されます。オフにしたタイプは、プロジェクトのどのスキャンでも探されません。

## OneUptime AI の判定

プロジェクトの **AI を有効化** がオンで、 **データセキュリティ → AI** の **新しい問題に対応する** もオンなら、OneUptime AI はデータストアをスキャンするたびに、人の判断を待つすべての検出結果に判定を下します。検出結果が判断を待つのは、スキャンがその検出結果に確信を持てなかったとき (低の検出結果、または OneUptime AI の提案) か、中または高の検出結果に誤一致の兆候があるときです:

- 一致したものの大半が既知のテスト値だった
- フィールドの名前が、このデータタイプではなく別のデータタイプを示している
- `order_number` 、 `invoice_no` 、 `ref_id` のような ID フィールドに、Luhn アルゴリズムでチェックされるタイプ (任意の数字の並びの 10 個に 1 個が合格します) が含まれ、その名前がそのタイプを示していない

判定は **確認を推奨** 、 **機密ではない** 、 **判断不能** のいずれかで、プロジェクトの言語で書かれた理由が付きます。判定はデータストアの **内容** ページと **テレメトリ内** で検出結果の行全体にわたって表示され、「チームが 4 件のデータストアで `order_number` を機密ではないとマークしました」のように、その根拠となったチームの判断も示されます。 **判断を表示** を押すと、その判断が 1 つずつ一覧表示されます: データストア、フィールド、チームが示した理由です。

### 前例としてのチームの判断

OneUptime AI には、同じデータタイプの検出結果に対するチームの過去の判断が最大 10 件伝えられます。最初に来るのは、どのデータストアかを問わず、同じ名前のフィールドにあるものです: `order_number` 、 `orderNumber` 、 `public.orders.order_number` はすべて「order number」になります。その中では同じ場所のものが先で、次に新しい判断から順に並びます。その次に、名前や、示された理由が同じことを言っているフィールドが来ます。たとえば、理由が「Shopify の注文番号」の `order_ref` です。伝えられるのは、各検出結果があった場所、判断の内容、示された理由で、理由に含まれる値は除かれます。値、マスクされたサンプル、レコードが伝えられることは決してありません。

ログ本文やメッセージなど、自由テキストにある検出結果には、照合に使うフィールド名がありません。その前例は、ほかのデータストアの同じ場所 (たとえば、別のサービスのログ本文) です。

### OneUptime AI が自分で決めること

- **検出結果を機密ではないとマークすることは決してありません。** どのルールの下でも同じです。マークするのは人で、その人自身の理由を添えます。判定が **機密ではない** の場合、 **機密ではないとマーク** には OneUptime AI が下書きした理由があらかじめ入っていて、変更できます。
- **検出結果を自動で確認するのは、AI ルールで定められている場合だけです。** そのデータストアとデータタイプについて、 **判定** が **自動** になっているデータセキュリティの AI ルールが必要です。さらに、類似の検出結果をチーム自身が確認していること、または名前がそのタイプを示すフィールドであることも必要です。この確認はデータストアの **タイムライン** と、 **データセキュリティ → AI** の **AI が実行済み** に記録され、 **元に戻す** で取り消せます。

それ以外の場合、判定は検出結果の行で人を待ちます。プロジェクトに AI ルールがある場合、検出結果に判定が下されるのは、そのデータストアとデータタイプに対するルールで **判定** がオンのときだけです。一部のチェックや重大度に限定されたルールは問題を対象とするもので、検出結果は判定しません。OneUptime AI がスキャン後に判定するのは 1 つのデータストアにつき最大 40 件の検出結果で、まだ一度も判定していないものが先になり、残りは次のスキャンの後に判定します。以降のスキャンでは、類似の検出結果に新しい判断があったときなど、判定の根拠が変わったときにだけ、その検出結果について再び尋ねます。

## 類似の検出結果

検出結果を確認するか機密ではないとマークすると、 **類似の検出結果に適用** に、まだ誰も判断していない類似の検出結果が一覧表示されます: このデータストアと、あなたが読み取れるほかのすべてのデータストアで、同じ名前のフィールドにある同じデータタイプの検出結果です。どれも選択された状態で表示されます。個別に判断したいものの選択を解除すると、残りにはあなた自身の変更として、あなたの理由とともに同じ判断が適用されます。あなたに変更する権限がない検出結果はそのままです。 **あとで** を選ぶと、すべてそのままになります。自由テキストにある検出結果に、類似の検出結果はありません: あるテキストの内容は、別のテキストについて何も示さないからです。

## チームの判断がスキャンについて示すこと

チームが検出結果を機密ではないとマークすると、OneUptime AI は **データセキュリティ → AI** の **あなたの対応待ち** で、スキャンの変更を提案します:

- **組み込みデータタイプをオフにする**: そのタイプの検出結果がすべて機密ではないとマークされたときです。少なくとも 2 つのデータストアで、少なくとも 3 件の検出結果が必要です。OneUptime AI が提案しただけの検出結果は数えません。
- **データストアのスキャンから場所を除外する**: その場所の検出結果がすべて機密ではないとマークされたときで、少なくとも 2 件が必要です。提案されるのは、スキャンが個別に除外できるデータベースの列またはテレメトリの属性です。

どちらの提案も、常に人の承認を待ちます: 探すのをやめたスキャンは、後から来る本物のデータを見逃すからです。 **機密扱いしない** が提案されることはありません。値を保持するものであり、OneUptime AI が値を見ることは決してないからです。
