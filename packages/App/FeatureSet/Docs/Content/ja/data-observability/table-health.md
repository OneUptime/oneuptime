# テーブルのヘルス

5 分ごとに、接続された各データベースのカタログが、すべてのテーブルの状態を伝えます: 最後に変更された日時、行数、サイズ、そして列の構成です。データオブザーバビリティはそこから各テーブルのリズムを学習し、テーブルが遅れたとき、縮んだとき、形が変わったときに知らせます。しきい値を設定する必要はありません。

## 読み取る内容

すべてのテーブルとビューについて、次のものを読み取ります。

- **行数とサイズ**。エンジン自身の統計情報から読み取ります。
- **最後に変更された日時**: エンジンが時刻を記録していればその時刻、そうでなければ 2 回の収集の間に書き込みカウンター、行数、バイト数が動いた時点です。
- **列**。その型と、空でもよいかどうかも読み取ります。
- **最後に読み取られた日時**。エンジンが読み取りを数えている場合に読み取ります。

読み取るのはカタログと、MongoDB ではコレクションの最新のドキュメントのフィールド名だけです。値がデータベースの外に出ることはありません。

## 鮮度

テーブルの **リズム** とは、そのテーブルがふだんどのくらいの頻度で変更されるかのことで、変更と変更の間隔から学習されます。リズムを大きく過ぎたテーブルは、そのページと **テーブル** で **遅延** と表示され、どれだけ過ぎているかが書き込まれます。鮮度は、テーブルが 2 回変更されるとわかります: 1 時間ごとにロードされるテーブルなら数時間以内に、毎晩ロードされるテーブルなら数日以内に学習されます。

ビューは自身の行を持たないため、ビューの鮮度はそのソースの鮮度です: [リネージとパイプライン](/docs/data-observability/lineage-and-pipelines) を参照してください。

カタログは、テーブルの内部管理だけが動いたのに変更があったと伝えることがあり、何も伝えないこともあります。テーブルの **設定** で、`updated_at` などの **鮮度列** を指定すると、最終変更はその列の最新の値になります。ログインにはその列を読み取る権限が必要です。列は収集のたびに読み取られるため、インデックスを付けてください。読み取った量で課金される BigQuery と Athena では、1 時間に 1 回読み取ります。タイムゾーンのない時刻は UTC として扱われます。

## データ量とスキーマの変更

- **行** は収集ごとに比較されます: 行の半分を失ったテーブルや、週のその時間帯としてはふだんよりはるかに少ない行しかないテーブルは、そのことを知らせます。
- **列** も比較されます。追加、削除、名前の変更、型の変更、または NULL 許容への変更があった列は、テーブルの **タイムライン** と、すべてのデータベースのすべての変更を新しい順に一覧する **スキーマの変更** に記録されます。削除、名前の変更、型の変更をされた列は、それを読み取るものを壊すため、アラートの対象になることがあります。追加された列は何も壊さず、タイムラインに残るだけです。
- **ドロップされたテーブル** は、最後に確認された日時とともに **削除されたテーブル** に残り、テーブルが戻ってくれば履歴ごと復帰します。

## 推奨アラート

**データベース** で、データベースの **推奨アラート** を選びます。各推奨は、データベース全体を対象とする 1 つのメトリクスモニターで、テーブルごとに 1 回アラートを出します。そのため、後から作成されたテーブルも監視されます:

| アラート | 発生条件 |
| --- | --- |
| **Table Is Late** | テーブルが、ふだん変更されるまでの時間を過ぎた状態が 15 分続いた |
| **Row Count Fell Sharply** | 2 回の収集の間に、テーブルが行の半分以上を失った |
| **Row Count Unusually Low** | テーブルの行数が、週のその時間帯のふだんの値よりはるかに少ない (2 週間かけて学習) |
| **Schema Changed** | テーブルの列が削除、名前の変更、または型の変更をされた |
| **Table Health Stopped Reporting** | データベースのどのテーブルも 15 分間読み取られていない |

作成するときに、重大度、オンコールポリシー、所有者、ラベルを選びます。それ以降は通常のモニターです: ほかのモニターと同じように、編集したり、ミュートしたり、ステータスページに載せたりできます。

バックフィルや移行で誰も呼び出されないようにしたい場合は、[メンテナンスイベント](/docs/scheduled-maintenance/index) で **Data Observability のデータベース** にそのデータベースを指定するか、そのデータベースサーバーをイベントに含めてください。イベントの間、そのデータアラートは通知されません。

## すべてのテーブルが書き込むメトリクス

各収集は、すべてのテーブルについて次のメトリクスを書き込みます。そのため、ほかのメトリクスと同じように、グラフにしたり、ダッシュボードに置いたり、アラートを設定したりできます:

| メトリクス | 内容 |
| --- | --- |
| `oneuptime.data.table.row_count` | テーブルの行数 |
| `oneuptime.data.table.size` | テーブルとそのインデックスが占めるバイト数 |
| `oneuptime.data.table.seconds_since_change` | テーブルが最後に変更されてからの秒数 |
| `oneuptime.data.table.overdue_seconds` | テーブルが、ふだん変更されるまでの時間を過ぎている秒数。時間どおりなら 0 |
| `oneuptime.data.table.row_count_change_percent` | 前回の収集から行数がどれだけ変動したか (パーセント) |
| `oneuptime.data.table.schema_changes` | 前回の収集から変更された列の数 |
| `oneuptime.data.table.breaking_schema_changes` | 前回の収集から削除、名前の変更、型の変更をされた列の数 |

どのメトリクスにも `oneuptime.data.store.id`、`oneuptime.data.store.name`、`oneuptime.data.table.id`、`oneuptime.data.table.schema`、`oneuptime.data.table.name`、`oneuptime.data.table.key` ( `schema.table` ) が付きます。 `oneuptime.data.table.key` でグループ化した [メトリクスモニター](/docs/monitor/metrics-monitor) はテーブルごとに 1 回アラートを出し、その **異常に高い** と **異常に低い** のフィルターは、各テーブルを、週のその時間帯におけるそのテーブル自身のふだんの値と比較します。これらのメトリクスは OneUptime 自身の運用データであり、テレメトリとして課金されません。

## 未使用のテーブル

読み取りを数えるエンジンはどれも、各テーブルが最後に読み取られた日時を伝えます: PostgreSQL のスキャン、MySQL の performance_schema、SQL Server のシーク、スキャン、ルックアップ、そして Redshift、ClickHouse、Databricks のクエリ履歴です。サービスのデータベーススパンで確認された読み取りも数えられます。

**未使用のテーブル** には、90 日間誰も読み取っていないテーブルが、大きい順に、それぞれ最後に書き込まれた日時とともに一覧されます: 書き込まれ続けているのに読み取られないテーブルは、書き込みとストレージのコストだけがかかっています。テーブルの最初の収集でカウンターが 0 なら、エンジンの統計情報が始まってから一度も読み取られていないということなので、未使用のテーブルは最初から未使用として表示されます。

## ウェアハウスの支出

データオブザーバビリティは毎時、Snowflake と BigQuery の各ウェアハウスが過去一日に使った額をジョブごとに読み取ります。Snowflake のコンピュートクレジットは `QUERY_ATTRIBUTION_HISTORY` から、BigQuery の課金バイト数はジョブビューから読み取り、後者には **BigQuery Resource Viewer** が必要です。ジョブとは繰り返し実行される 1 つのクエリで、クエリタグやラベル、または処理内容と書き込むテーブルで名前が付けられ、クエリのテキストが使われることはありません。

**ウェアハウスの支出** には、チーム別の合計 (ジョブのクエリタグやラベルの `team`、なければ実行者)、書き込みに最もコストがかかるテーブル、失敗したジョブ、そして 90 日間誰も読んでいないテーブルだけを書き込むジョブへの支出が表示されます。

## 各テーブルを使うサービス

テーブルの **サービス** タブには、そのテーブルへの書き込みと読み取りが確認されたサービスが、それぞれが実行したステートメント、直近 1 時間の呼び出しと失敗、そして最後に確認された日時とともに一覧されます。これは、サービスがすでに OpenTelemetry で送っているデータベーススパンから得られます: `db.system.name`、`db.namespace`、`db.collection.name` を持つクライアントスパンです。追加でインストールするものはありません。

スパンがテーブルに結び付けられるのは、そのデータベースがいずれかの収集で読み取ったデータベースである場合だけです。2 つのデータベースが同じ名前を持つ場合は、スパンの `server.address` がそのどちらかのものである場合に限ります。

各サービスには、同じトレースのサーバースパンから得られる、その呼び出しを行うエンドポイントも表示され、モデルも呼び出す場合は **AI アプリ** と表示されます。**このテーブルに言及するエラー** には、そのテーブルに書き込むサービスの、未解決の例外と直近 1 日のエラーログが、テーブルを名前で挙げているときに一覧されます。

## 所有者とラベル

テーブルの **所有者** タブには、そのテーブルが属する人とチームが示され、テーブルのアラートはその人たちに送られます。所有者がいない場合は、そのデータベースの所有者に送られます。テーブルの **設定** で、独自の **ラベル** を付けられます。

これを何百回も行う必要はありません。**所有者ルール** と **ラベルルール** は、テーブルが最初に現れたときにすべてのテーブルに適用され、ラベル、または名前、スキーマ、データベースに対する正規表現で一致させます: `finance` にあるものはすべて財務チームに割り当てられ、`*_pii` という名前のものにはラベルが付きます。

`Owned` にスコープされた権限が届くのは、その保有者または所属チームがオーナーであるテーブルと、そのチェック、アクティビティ、報告された問題だけです。データベースのオーナーであっても、そのテーブルのオーナーにはなりません。データベース全体をチームに任せるには、オーナールールを使います。

## アラートが開いたとき

テーブルのアラートには **データ** カードがあり、最も可能性の高い順に、なぜ起きたかが示されます: 上流のアラート、失敗した実行、そのテーブルに書き込むサービスのデプロイ、失敗した書き込み、変更された列、データベース自体、またはそれが動いているサーバーです。その下には、何がそれに依存しているかが示されます: リネージの下流のテーブル、ダッシュボード、サービス、そしてそれらを所有する人です。

あなたの判断を伝えてください:

- **Useful**: 正しかった。
- **Expected**: 計画されたイベント。何も変わらず、次のものも通知されます。
- **問題ではない**: テーブルにより多くの余裕が与えられ、次回は同じことが通知されません。遅れたテーブルのふだんの間隔は広がり、行数の許容範囲も広がります。

人が先に問題を見つけた場合は、テーブルの **問題を報告** がそれを記録します。すると **概要** に、Data Observability がプロジェクトでどう機能しているかが表示されます: 週あたりの有用な問題数、ノイズではなかった数、読み取られているテーブルの数、人が報告する前に問題を検知した頻度、その速さ、そして推定された原因が実際の原因だった頻度です。
