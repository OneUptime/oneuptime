# リネージとパイプライン

リネージは、各テーブルがどのテーブルから作られ、どのパイプラインがそのテーブルに書き込んでいるかを示します。データオブザーバビリティは、OpenLineage のイベント、dbt、Fivetran と Airbyte の同期、トレース内のジョブ、ビュー、そして各データベース自身のクエリ履歴という 6 つの場所から同時にリネージを集め、それを使って、遅れたテーブルや壊れたテーブルをその背後にある実行に結び付けます。そのため、1 つの問題で開くアラートは 1 件だけです。

## リネージの取得元

| ソース | 得られるもの |
| --- | --- |
| **OpenLineage** | Airflow、Dagster、Spark、dbt、Flink のジョブのすべての実行と、その実行が読み書きしたテーブル |
| **dbt** | 各モデルが何から作られているか、1 回の実行としての各ビルド、そして各テストの結果 |
| **Fivetran と Airbyte** | コネクターの 1 回の実行としての各同期と、その同期がロードする生のテーブル |
| **トレース内のジョブ** | Kubernetes の CronJob やスケジュールされた関数、その実行、そしてそのデータベース呼び出しが読み書きしたテーブル |
| **ビュー** | ビューは、その定義に使われているテーブルから作られます (PostgreSQL、Redshift、MySQL 8、SQL Server、Oracle、Snowflake、ClickHouse のマテリアライズドビュー、Databricks、MongoDB) |
| **クエリ履歴** | あるテーブルを読み取り、別のテーブルに書き込んだクエリ (Snowflake のアクセス履歴、BigQuery のジョブ、Redshift のクエリログ、ClickHouse のクエリログ、Databricks のリネージテーブル) |

テーブルの **リネージ** タブには、そのテーブルの作成元のテーブル、そのテーブルに書き込むパイプラインとその最新の実行、そしてそのテーブルから作られるテーブルが表示されます。各エッジには、それがどこで確認されたかが示されます。

タブの上部には、そのリネージを各方向に数ステップ分 (3 ステップ、または 1、2、5 を選択) 描いた図が表示されます。左にはテーブルの作成元、右にはそのテーブルから作られるテーブルとダッシュボードが描かれ、外部からデータを読み込むパイプラインは、データが入ってくる位置に描かれます。各カードには現在の状態 (遅延、開いているアラート、失敗した実行) が示され、パイプラインの最新の実行が失敗した矢印は赤くなるので、遅延したテーブルをその原因となった実行までたどれます。任意のテーブルを開くと、図の中心がそのテーブルになります。

各カードは各方向に最大 10 個のテーブルを描き、残りを **+14** のように数で示します。その数を選ぶと、残りのうち最大 10 個を問題のあるものから順にその場に描き足し、それらとすでに描かれたものとの間の矢印もすべて描きます。**図をリセット** を選ぶと、最初に描かれた図に戻ります。片側に図が保持できるだけのテーブルがある場合は、テーブルを開くと図の中心がそのテーブルになります。

ソースが列の名前を示す場合、テーブルの **列** タブには、各列がどこから来て何に使われるかが表示されます。対応するのは Snowflake のアクセス履歴 (Enterprise エディション。`SNOWFLAKE` データベースに対する `IMPORTED PRIVILEGES` が必要です) と、OpenLineage の `columnLineage` ファセットです。

**リネージ** タブでは、**列をたどる** でテーブルの列を 1 つ選ぶと、その列がどこから来てどこへ行くかをハイライト表示します。図を上流へ、その列の作成元の列までたどり、下流へ、その列から作られる列までたどります。途中で名前が変わっていても、各テーブル上の列名が示されます。ソースが列を示していない矢印は、ハイライト表示より先までその列を運んでいる可能性があり、図にはそのことが示されます。

リネージを表示するどの画面も - テーブルの **リネージ** タブ、パイプラインのもの、アラートのもの、**リネージマップ**、そして OneUptime AI と API が伝える内容も - あなたのロールが読めるテーブルとパイプラインだけを表示します。メンバーが所有するもの、または一部のラベルに限定されたロールには、それ以外のテーブルやパイプラインは表示されません。描画されず、矢印にも名前が出ず、その先にあるテーブルの数にも含まれません。

## リネージマップ

**データオブザーバビリティ > リネージマップ** は、プロジェクトで確認されたデータのフローをすべて 1 つのページに描画します。テーブルを先に選ばなくても、誰がどのデータを使い、データがどこへ行くかがわかります。表示されるのは次のとおりです。

- テーブルに書き込み、テーブルを読み取る **サービス**。トレースのデータベーススパンから得られます。テーブル名 (`db.collection.name`、または古い `db.sql.table`) と文 (`db.operation.name`。`INSERT` や `SELECT` など) を示すスパンが対象です。
- 上記のすべてのソースから得られる、ほかのテーブルから作られる **テーブル**。
- OneUptime が監視していないデータ (Fivetran の同期など) からテーブルを読み込む **パイプライン**。監視対象の 2 つのテーブルの間でデータを移すパイプラインは、その間の矢印上に名前が示されます。
- BI ツールの **ダッシュボード** とリバース ETL の同期。元になっているテーブルを、そのテーブルにほかに何も触れていなくても読み取ります。OneUptime が監視するテーブルのどれにも基づいていない Power BI レポートは、そのレポートが表示するデータセットと、データセットの読み込み元のデータソースとともに描かれます。BI ツールのダッシュボードがどれも監視対象のテーブルに基づいていない場合は、その理由をマップが示します ([Power BI のリネージ](#power-bi-のリネージ))。

すべての矢印は OneUptime が記録したものであり、推測ではありません。カードは、データが流れる向きに沿って左から右に並び、テーブルの図と同じように状態を示します。遅延したテーブル、開いているアラート、失敗した実行は赤で示されます。サービスのトレースで確認された矢印は青緑になります。

テーブル、サービス、パイプライン、ダッシュボードを検索すると、一致するものと、その上流および下流のすべてが残ります。カードを選ぶとそのリネージ全体がハイライトされ、取得元と送信先が表示され、そのページを開けます。**このリネージのみ表示** を選ぶと、マップにはそのリネージだけが残ります。検索の横のスイッチで、サービス、パイプライン、ダッシュボードを非表示にできます。**リスト** はすべての矢印を 1 行ずつ表示し、スマートフォンではこちらが開きます。

1 つのマップには最大 400 枚のカードが描画され、最近確認されたフローが優先されます。プロジェクトにそれより多くある場合は、マップにその旨が表示されます。同じマップは `POST /api/data-observability/lineage/map` でも提供され、データアセットを読み取る権限のあるユーザーと、その API キーで利用できます。 それより多い場合、マップは描画しなかったテーブルの数を（それぞれ 1 回ずつ数えて）示し、別の起点から始めることもできます。データベースを選ぶと、そのテーブルのフローとそれらがつなぐカードをマップにします。名前を入力して **プロジェクト全体を検索** を選ぶと、名前にそれを含むすべてのテーブル、パイプライン、サービス、ダッシュボードのフローを、どれほど古くてもマップにします。**マップ全体を表示** で元に戻ります。API のマップを別の起点から始めるには、`{ "dataStoreId": "<database ID>" }` または `{ "search": "orders" }` を送信します。

## OpenLineage

テレメトリの [取り込みキー](/docs/telemetry/ingestion-keys) を使って、OpenLineage のイベントを変更せずにそのまま OneUptime に送信します:

- **URL:** `https://oneuptime.com/telemetry/openlineage` (セルフホストの OneUptime では、自分のアドレス)
- **エンドポイント:** `api/v1/lineage` (OpenLineage のデフォルト)
- **API キー:** 取り込みキー。 `Authorization: Bearer` として送るか、 `x-oneuptime-token` を設定します

Airflow の OpenLineage プロバイダーの場合:

```bash
AIRFLOW__OPENLINEAGE__TRANSPORT='{"type": "http", "url": "https://oneuptime.com/telemetry/openlineage", "endpoint": "api/v1/lineage", "auth": {"type": "api_key", "apiKey": "YOUR_INGESTION_KEY"}}'
```

ほかの OpenLineage クライアントでは、 `OPENLINEAGE_URL` と `OPENLINEAGE_API_KEY` を設定します。データセットは、OpenLineage の命名仕様に従ってテーブルに対応付けられます。たとえば `postgres://host:5432` と `database.schema.table`、 `snowflake://account` と `database.schema.table`、 `clickhouse://host:8443` と `database.table`、 `databricks://workspace-host` と `catalog.schema.table` です。

## dbt

`dbt build` (または run、test、seed、snapshot) の後、 [OneUptime CLI](/docs/cli/index) でプロジェクトのアーティファクトを送信します:

```bash
npm install -g @oneuptime/cli
export ONEUPTIME_URL=https://oneuptime.com
export ONEUPTIME_TELEMETRY_INGESTION_KEY=<ingestion key>
dbt build
oneuptime dbt upload
```

CI では、ビルドの次のステップとして、ビルドが失敗した場合でも `oneuptime dbt upload` を実行してください。そうすれば、失敗したテストが記録されます。dbt が作成する各テーブルには、概要に **dbt** カードが、そのモデルのリネージが、そして **チェック** タブにそのテストが表示されます。各ビルドは、プロジェクトのパイプラインの 1 回の実行です。

## Fivetran と Airbyte

それらの Webhook は、各同期がいつ始まり、いつ終わったかを伝えます。 **パイプライン > Fivetran または Airbyte を接続** では、取り込みキーの 1 つを使って URL が入力されます:

- **Fivetran:** Fivetran の REST API で作成する Webhook です。イベント `sync_start` と `sync_end` を対象とし、宛先は `https://oneuptime.com/telemetry/fivetran/v1/webhook/<ingestion key ID>`、シークレットは取り込みキーです。Fivetran はすべての配信にこのキーで署名するため、キーが URL に含まれて送られることはありません。
- **Airbyte:** ワークスペースの Webhook を `https://oneuptime.com/telemetry/airbyte/v1/webhook/<ingestion key>` に設定し、失敗した同期と成功した同期についてオンにします。Airbyte には専用のキーを渡してください。

API のレート制限によって再スケジュールされた Fivetran の同期は、 **再スケジュール** として終わります: 失敗ではないので、誰も呼び出されません。

## トレース内のジョブ

多くのパイプラインは、Kubernetes の CronJob や、タイマーで動く関数であり、リネージを送るスケジューラーがありません。それでもトレースがすべてを語るので、インストールするものはありません。15 分ごとに、リソース属性 `k8s.cronjob.name` または `k8s.job.name` を持つスパン、または `faas.name` を持ち `faas.trigger` が `timer` または `datasource` のスパンが、**パイプライン** の下のパイプラインになります:

- CronJob の実行は、その Kubernetes Job であり、関数の実行は、その `faas.invocation_id` です。
- 実行が失敗したとみなされるのは、そのトレースの最上位のスパンが失敗したときです。その内部で失敗して再試行された呼び出しは、実行を失敗にしません。
- 書き込んだテーブルと読み取ったテーブルは、そのデータベーススパンから得られます。

各実行は、ログとともに、そのトレースにリンクされます。同じ 3 つのモニターが適用されるので、実行されなくなった CronJob は遅延として検知されます。

## BI ツールのダッシュボード

不正なデータの本当の影響は、誰かが開くダッシュボードです。**BI ダッシュボード** で、ダッシュボードを読み取れる認証情報とともに BI ツールを追加します。データオブザーバビリティは毎時、各ダッシュボードとその背後のテーブルを読み取り、各テーブルを監視対象のテーブルと照合し、テーブルとそれから構築されるテーブルを基にしたダッシュボードを、その **リネージ** タブ、アラート、Production Review に表示します。

| ツール | 認証情報 |
| --- | --- |
| **Metabase** | `{ "apiKey": "mb_..." }` |
| **Superset** | `{ "username": "...", "password": "..." }` |
| **Tableau** | `{ "tokenName": "...", "tokenSecret": "...", "site": "acme" }` |
| **Looker** | `{ "clientId": "...", "clientSecret": "..." }` |
| **Power BI** | `{ "tenantId": "...", "clientId": "...", "clientSecret": "..." }`, Power BI の読み取り専用の管理 API の使用を許可されたサービス プリンシパル。各レポートの背後のテーブルを読み取るには、[Power BI のリネージ](#power-bi-のリネージ) の 2 つのメタデータのテナント設定をオンにします。レポートとダッシュボードの両方を、その閲覧と更新とともに読み取ります (下記) |
| **Hightouch** | `{ "apiKey": "..." }` |
| **Census** | `{ "apiKey": "...", "region": "us" }` (または `eu`) |

Hightouch と Census はリバース ETL ツールです: テーブルを CRM にコピーする同期は、ダッシュボードと同じようにそのテーブルに依存するので、同じように読み取られ、テーブルのアラートに名前が表示されます。

読み取るのはダッシュボードの名前とリンク、クエリ対象のテーブル、そして Power BI では誰が開いたかと更新の結果だけで、データは決して読み取りません。

### Power BI の閲覧と更新

Power BI の各レポートとダッシュボードについて、**BI ダッシュボード** は最初に、過去 28 日間に開かれた回数、最後に開かれた日時、データの最後の更新の結果 (失敗した更新はそのエラー) を表示します。開いた人の数、最もよく開いた人、最新の更新は、表示を切り替えられる列です。テーブルの **リネージ** タブは、そのテーブルの上に作られた各ダッシュボードについて同じことを示し、所有者と閲覧者は **その他** の下にあります。

- **閲覧** は Power BI のアクティビティ ログから、その管理用アクティビティ イベント API で読み取ります。Power BI はログを 28 日間保持し、1 時間に 200 件の要求に応え、すべての要求を 1 時間単位に分けるため、OneUptime は 1 時間ずつ読み取ります。毎時の読み取りで前回以降の時間を追加し、その後 28 日間を新しい順にさかのぼります。1 回の読み取りの要求は最大 100 件です。新しい Power BI ツールでは直近の数日がすぐに表示され、28 日間すべてが 1 日以内にそろいます。それまでは、閲覧数がいつから数えられているかが表示されます。イベントがログに届くまで最大 1 時間かかるため、閲覧数は最大 2 時間遅れます。閲覧者は Power BI が示すとおり、メール アドレスで示されます。
- 容量 (Premium、Premium Per User、Fabric) 上のデータセットの **更新** は、Power BI の管理用の更新可能アイテムの一覧から読み取ります。各データセットの最後の更新とそのエラー、そして Power BI が保持する 7 日間に実行された更新と失敗した更新の数です。
- **共有容量上のデータセットの更新** は、その一覧にありません。Power BI はデータセットの更新履歴を、そのデータセットを変更できる人にしか表示しないため、サービス プリンシパルをそのワークスペースに **共同作成者**、**メンバー**、または **管理者** として追加し、Fabric 管理ポータルの開発者設定でそのサービス プリンシパルに対して **Service principals can call Fabric public APIs** をオンにしてください。そうすると OneUptime は各更新をエラーとともに読み取ります。それまでは、更新を読み取れなかったデータセットの数を BI ツールが示します。
- タイルが複数のデータセットから来ている Power BI ダッシュボードは、失敗した最新の更新を、失敗がなければ最も古い更新を表示します。そのデータの新しさはその更新までです。

閲覧と、容量上の更新には、上記の管理 API へのアクセス以外は何も必要ありません。サービス プリンシパルが **Service principals can access read-only admin APIs** で許可されたセキュリティ グループに入っていて、アプリに管理者の同意が必要な Power BI のアクセス許可がないことです。閲覧や更新を読み取れない場合でも、ダッシュボードは読み取られて保持され、何がなぜスキップされたかを BI ツールが示し、次の読み取りで再試行します。

### 失敗した更新のアラート

Power BI ツールを追加または編集するときに **Alert on Failed Refreshes** をオンにすると (新しいツールでは最初からオンです)、OneUptime はそのツールのモニターを 1 つ、ツール名を付けて **モニター** の下に保持します。このモニターは、最後の更新が失敗またはキャンセルされたデータセットごとにアラートを 1 件開き、アラートのタイトルにデータセットとそのワークスペースを示し、後の更新が完了した時点でそのアラートを解決します。後から公開されたデータセットも、読み取られた時点で監視されます。スイッチをオフにするか、ツールを削除すると、モニターも削除されます。それまでは、所有者、オンコール ポリシー、メンテナンス ウィンドウを持つ通常のモニターです。

失敗した更新には、パイプラインのモニターを使いません。更新が失敗したデータセットは、後の更新が完了するまで、最後に完了した更新のデータを表示し続けます。そのためアラートはそれまで開いたままです。一方、失敗した実行のアラートは実行の 1 時間後に解消されます。また、更新は 1 時間に 1 回読み取られます。終了から最大 1 時間後に読み取られる更新は、**Pipeline Run Failed** が見る 1 時間から外れることが多く、30 分ごとに更新されるデータセットは何度も **Pipeline Is Late** になり、終了したがまだ読み取られていない更新は **Pipeline Run Unusually Long** に見えてしまいます。

- 1 時間ごとの読み取りでは、最後に終了した更新が失敗またはキャンセルされたデータセットを保持します。5 分ごとに、それぞれが `oneuptime.data.bi.refresh_failed` を書き込みます。失敗している間は 1、後の更新が完了してから 1 時間は 0 で、モニターがこれを読み取るので、1 時間ごとの読み取りが何回その失敗を見ても、1 つの失敗で開くアラートは 1 件です。
- 失敗は次の 1 時間ごとの読み取りで検知されます。アラートは更新の失敗から最大 1 時間後に開き、後の更新の完了から最大 1 時間後に解決されます。
- 実行中の更新は何も変えません。更新が失敗したデータセットのアラートは、次の更新が実行されている間も開いたままで、更新が完了したときにだけ解決されます。
- 容量上では、Power BI の更新可能アイテムの一覧は各データセットの最後の更新しか返さないため、失敗した後に同じ 1 時間のうちに完了した更新が続いた場合、その失敗は検知されません。そのときにはデータはすでに最新に戻っています。
- 共有容量上のデータセットは、更新を読み取れる場合にだけアラートを出します (上記を参照)。更新を読み取れなかったデータセットは、読み取れるようになるまでアラートをそのままの状態で保ちます。

## パイプライン

各ジョブ、dbt プロジェクト、同期は、その実行とともに **パイプライン** の下に表示されます: 各実行がいつ始まりいつ終わったか、どれだけかかったか、スケジューラーが示す場合は何回目の試行か (Airflow の try number)、そして失敗した実行のエラーです。各パイプラインは、5 回の実行の後、自身の実行から、1 回の実行に通常どれだけかかるか、そしてスケジュール上で実行と実行の間がどれだけ空くかを学習します。パイプラインのページは、4 つのモニターを推奨します:

- **Pipeline Run Failed**: 実行が失敗した、または中止された。
- **Pipeline Run Unusually Long**: 実行に通常の 2 倍以上の時間がかかっている。実行中は 5 分ごとにチェックされるので、ハングした実行は終わる前に検知されます。
- **Pipeline Is Late**: スケジュールで許される時間を超えても、実行が始まっていない。
- **Pipeline Stopped by Circuit Breaker**: サーキットブレーカーが stop と答えた。停止は、go と答えるか実行が始まるまで続きます。

パイプラインの **所有者** タブには、それを担当する人やチームが表示され、パイプラインのアラートはその人たちに届きます。 **概要** と **問題** には、失敗したか遅れているパイプラインの所有者が表示されるか、 **所有者なし** と表示され、所有者を追加する方法が示されます。

**所有者ルール** で、パイプラインの所有者を自動で指定できます。**パイプラインルール** タブでは、ルールがパイプラインの名前 (`orders_daily.load_orders` など) や、実行場所を表す Namespace (`airflow://prod` など) に正規表現で一致させ、OneUptime がそのパイプラインを初めて検出したときに、ルールのユーザーとチームをパイプラインの所有者として追加します。既存のパイプラインに追加するには、ルールを開いて **今すぐ実行** を選択します。

パイプラインのページには **リネージ** カードがあり、実行が失敗したときや遅れているときにまず見る場所です: 左にはパイプラインが読み取るテーブル、右には書き込むテーブル、その間にパイプラインが描かれ、各カードには現在の状態が示されます。ステップ数を増やすと、それらのテーブルの作成元と、それらから作られるものが表示されます。任意のテーブルを開くと、そのテーブル自身の **リネージ** タブが表示されます。パイプラインのカードやテーブルのカードにある、描画されていないテーブルの数を選ぶと、ここでもその場に描き足せます。 書き込む列を 1 つ選ぶと、パイプラインをまたいでその列をたどれます。上流では読み取る各テーブルの構築元の列まで、下流では書き込む各テーブルまでたどります。

## サーキットブレーカー

チェックの失敗やテーブルの遅延は所有者に通知されますが、そのテーブルを読むパイプラインはそのまま実行され、不正なデータを下流にコピーしてしまいます。サーキットブレーカーは、その前にパイプラインを止めます。パイプラインの最初のステップが、読み取るテーブルが正常かどうかを OneUptime に問い合わせ、答えが go のときだけ残りが実行されます。

- パイプラインが読み取るテーブルのチェックが失敗中なら、必ず停止します。アラートが開いているチェックや、失敗した dbt テストです。
- パイプラインの **サーキットブレーカー** ページで **読み取るテーブルが遅延したら停止する** をオンにすると、遅延テーブルでも停止します。テーブルの遅延は単に静かな一日を意味することもあるため、どのパイプラインでもオフになっています。
- 実行できなかったチェックやまだ実行されていないチェック、チェックのないテーブルでは、何も停止しません。

ステップは、データオブザーバビリティを読み取れるプロジェクトの API キーで問い合わせ、パイプラインを `namespace/name`、名前のみ、または ID で指定します。サーキットブレーカーは、パイプラインが読み取るテーブルをリネージから取得します。リクエストでは `tables` も指定でき、それだけを指定することもできます。それぞれ `schema.table`、名前のみ、または ID で指定します。どのテーブルにも一致しない名前は `notFound` で返され、合格したテーブルとして数えられることはありません。判定されるのは、API キーが読み取れるテーブルだけです。

```bash
curl -sSf https://oneuptime.com/api/data-observability/circuit-breaker \
  -H "ApiKey: $ONEUPTIME_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"pipeline": "airflow://prod/orders_daily.load_orders", "failWithStatusCode": true}'
```

回答の `verdict` は `go` または `stop` です。`reasons` には失敗中の各チェックとそのテーブル、遅延中の各テーブルとその遅延時間が並び、`tables` には判定したすべてのテーブルが並びます。`answer` は同じ内容を、ステップのログ向けにいくつかの文で伝えます。`failWithStatusCode` を指定すると、停止時に HTTP 412 が返るため、`curl -f` でステップが失敗します。1 つのリクエストだけで決めるには `stopsOnLateTables` に `true` または `false` を、回答を保存せずに問い合わせるには `dryRun` に `true` を送ります。

Airflow では、テーブルを読むタスクの前に `ShortCircuitOperator` を置きます。その関数が false を返すと、後続のタスクはすべてスキップされます。

```python title="orders_daily.py"
import os

import requests
from airflow.operators.python import ShortCircuitOperator


def inputs_are_healthy() -> bool:
    response = requests.post(
        "https://oneuptime.com/api/data-observability/circuit-breaker",
        headers={"ApiKey": os.environ["ONEUPTIME_API_KEY"]},
        json={"pipeline": "airflow://prod/orders_daily.load_orders"},
        timeout=30,
    )
    response.raise_for_status()
    answer = response.json()
    print(answer["answer"])
    return answer["verdict"] == "go"


check_inputs = ShortCircuitOperator(
    task_id="check_inputs",
    python_callable=inputs_are_healthy,
)

check_inputs >> load_orders
```

dbt の `on-run-start` フックはウェブリクエストではなくウェアハウスで SQL を実行するため、dbt を開始するステップで問い合わせます。CI のジョブ、cron の行、または dbt を実行するタスクです。dbt プロジェクトのパイプライン名は、`dbt/` の後にプロジェクト名が続きます。

```bash
curl -sSf https://oneuptime.com/api/data-observability/circuit-breaker \
  -H "ApiKey: $ONEUPTIME_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"pipeline": "dbt/analytics", "failWithStatusCode": true}' \
  && dbt build
```

パイプラインを指定したリクエストは、試行でない限りそのパイプラインに保存されます。サーキットブレーカーがパイプラインを停止している間、その **サーキットブレーカー** ページにはいつからなぜ停止しているかが表示され、**概要** は停止の表示から始まり、**要対応** と **問題** には失敗や遅延した実行の代わりに、停止として表示されます。停止は、サーキットブレーカーが次に go と答えたとき、または停止の後に実行が始まったときに終わります。同じページには、回答を保存せずにサーキットブレーカーに問い合わせる **今すぐテスト** と、パイプライン名を入力済みの curl、Airflow、dbt 向けのステップがあります。

停止を知るには、パイプラインの **推奨事項** から **Pipeline Stopped by Circuit Breaker** を追加します。そのアラートは、サーキットブレーカーが stop と答えたときに開き、パイプラインの所有者に届き、停止が保存されている間は開いたままで、停止が終わると解決します。このモニターはパイプラインの `oneuptime.data.pipeline.circuit_breaker_stopped` メトリクスを読みます: サーキットブレーカーが停止している間は 1、停止していなければ 0 で、サーキットブレーカーが答えるときと、その後 5 分ごとに書き込まれます。

サーバーでデータオブザーバビリティがオフの間、サーキットブレーカーは go と答え、何も保存しません。製品をオフにしても、パイプラインが止まることはありません。

## 原因ごとに 1 件のアラート

テーブルが古くなると、そのテーブルから作られるすべてのテーブルも古くなります。データアラートが開く前に、OneUptime はリネージをたどり、そのテーブルやパイプラインの作成元ですでに開いているアラートを探します: 上流のテーブル、それらに書き込むパイプライン、そしてそれらがあるデータベースを、最大 5 段階さかのぼります。見つかった場合、新しいアラートはそのアラートの結果になります:

- 最初から **確認済み** の状態で始まるので、1 つの問題で誰かが 2 回呼び出されることはありません。データが回復すると、アラートも自動で回復します。
- そのフィードと **データ** カードに、どのアラートが原因かが示され、アラートは原因のエピソードに加わります。

原因の **データ** カードには、その **下流への影響** が一覧されます: それが引き起こしたすべてのアラートです。テーブルアラートのカードには、そのテーブルに書き込むサービスも、その失敗した書き込み、そしてアラートまでの 1 日間のデプロイやその他の変更とともに表示されます。

アラートのページには、**データ** カードの下に **リネージ** カードがあります: アラートのテーブルの周りのリネージ (テーブルの **リネージ** タブと同じ描き方) か、アラートのパイプラインの周りのリネージです。このアラートを引き起こしたアラートまでさかのぼる経路と、このアラートが引き起こした各アラートまで下る経路が強調され、原因のテーブルまたはパイプラインには **原因**、引き起こされた各アラートのテーブルには **影響先** の印が付き、それ以外は薄く表示されます。開いた人は、問題がチェーンのどこで始まったかを確認できます。原因が矢印上に描かれたパイプラインにある場合、その矢印のパイプライン名の下に **原因** と表示されます。原因がデータベース全体についてのものであるか、図が届くよりも上流にある場合は、カードがそのことを文章で伝えます。1 つの列に対するチェック (たとえば `customer_id` の「NULL の割合」チェック) から上がったアラートは、テーブルの **リネージ** タブと同じように、これらの経路と並べてその列をたどった状態で開きます: その列がどこから来てどこへ行くかが、各テーブル上の列名とともに示されます。そこでテーブルの別の列を選ぶことも、選択を解除して経路だけを表示することもできます。**リネージを探索** は、テーブルの **リネージ** タブ、またはパイプラインのページを開きます。 矢印上に描かれたパイプラインで引き起こされたアラートも、同じように **影響先** と表示されます。列の選択肢には、まずチェックの列が、続いてテーブルのほかの列がテーブル自身の順序で並びます。

このアラートを引き起こしたアラートを見ることができない人には、**データ** カードもリネージも表示されません。また、引き起こされたアラートのうち、その人が見ることのできないものは、強調も集計もされません。

## Power BI のリネージ

各 BI ツールの **一致したテーブル** は、そのダッシュボードがいくつの監視対象のテーブルに基づいているかを示し、その下に、残りのテーブルが一致しない最初の理由を示します。**See Why** は、前回の読み取りで見つかったものと、すべきことを一覧にします。ダッシュボードが読み取っているのに OneUptime に接続されていないデータベース (それぞれ種類とアドレスが入力済みで、**Connect Database** ですぐに接続できます)、接続済みのデータベースが監視していないテーブル (スキャンから除外されているか、まだ収集されていない可能性があります)、そしてファイルや Web ページなど、データベースではないソースです。Power BI では、オフになっているテナント設定、データフローから読み取るデータセット、Power BI が説明できないデータセットも示します。各ダッシュボードの **構築元** は、そのダッシュボードが表示するデータセットと、そのデータの取得元を Power BI のとおりに示します。

OneUptime は各 Power BI データセットを、Power BI のメタデータ スキャンから、各テーブルの背後にある Power Query とともに読み取ります。

- **コネクタが指定するデータベース**: SQL Server と Azure SQL (`Sql.Database`)、PostgreSQL、MySQL、Oracle、Amazon Redshift、Snowflake、Google BigQuery、Databricks、Amazon Athena、Microsoft Dataverse、そしてナビゲーションが選ぶスキーマとテーブル。
- **クエリが実行する SQL**: コネクタの **SQL statement** オプション、`Value.NativeQuery`、`Odbc.Query`、そして各 `FROM` と `JOIN` の後のテーブル。
- **パラメーターと共有クエリ**: パラメーターは名前が使われているすべての場所で置き換えられ、ステージング クエリを読み取るテーブルは、そのクエリが読み取るものを読み取ります。
- **複合モデル** は、元になっているデータセットのテーブルを表示します。

レポートはそのデータセットのテーブルを、ダッシュボードはそのタイルのデータセットのテーブルを表示します。データの取得元 (データベースのサーバーと名前、ファイルのパス、Web アドレス) はスキャンのデータソースから得られ、上記の管理 API へのアクセス以外は何も必要ありません。

Power BI がデータセットのテーブルを返すのは、Fabric 管理者が管理ポータルの **Tenant settings > Admin API settings** で、サービス プリンシパルが含まれるセキュリティ グループに対して 2 つのテナント設定をオンにした後だけです。

- **Enhance admin APIs responses with detailed metadata**: 各データセットのテーブル。
- **Enhance admin APIs responses with DAX and mashup expressions**: テーブルを読み込むクエリ。どのデータベース テーブルを読み取るかがわかります。

その後 Power BI は、データセットが更新または再発行されると、そのデータセットを説明します。DirectQuery だけを使うデータセットは、誰かがそのデータセットのレポートを開いた後です。リアルタイム データセット、Analysis Services へのライブ接続のデータセット、Excel ブック、共有容量上の 1 GB を超えるデータセットは決して説明されません。

各テーブルは名前、スキーマ、データベースで監視対象のテーブルと照合され、サーバーは短い名前か完全な名前で照合されます。別のエンジンのテーブルや、別のデータベースのテーブルは照合されません。`Archive` だけを監視している場合、`Sales.dbo.Orders` のレポートは `Archive.dbo.Orders` とは結び付けられません。

[更新](#power-bi-の閲覧と更新) はテーブルとは別に読み取られます。一部のデータセットの更新を読み取れなかったという警告は、それらのテーブルについては何も示しません。

## 変更がマージされる前に

プルリクエストが監視対象のテーブルを変更すると、[Production Review](/docs/ai/ai-agent) は、何がそれに依存しているかをプルリクエストに示します: そのテーブルを読み取るサービス、そのテーブルから作られるテーブル、そのテーブルを基にしたダッシュボード、そしてそのデータプロダクトです。ステージングとしてマークされたデータベースにコピーを持つテーブルは、そのコピーがどう違うかも示します: その行、その列、そしてテーブルのチェックがそこで読み取る内容であり、その場で実行されます。プローブからしか到達できないデータベースでは、チェックは省かれ、その旨が表示されます。
