# ワークフロー 設定と安全性

ワークフローを本番のトラフィックに向ける前に知っておくべきこと: 安全にオンにする方法、誰が何をできるか、シークレットと URL を非公開に保つ方法、ワークフローのステップが変更できるもの、そしてすべての実行に適用される上限です。

:::cards
- [本番運用を始める](#ワークフローのオンオフ切り替え): ワークフローを実行 でテストしてから、ワークフローをオンのままにします。
- [権限](#権限): ワークフローのロールと、その背後にある個別の権限。
- [ステップにできること](#ワークフローのステップができること): ステップはワークフローのプロジェクトの Project Admin として動作します。
- [上限](#プランの上限): プランごとの実行回数、実行時間、ワークフロー間の呼び出し。
:::

## ワークフローのオン/オフ切り替え

どのワークフローにも、**ビルダー** の上部と **概要** ページに **有効** スイッチがあります。オフのときはワークフローは実行されません。Webhook の呼び出し、受信メール、スケジュールの時刻、OneUptime のイベントはすべて無視され、**ワークフローを実行** と **このステップだけを実行** も同様です。新しいワークフローは無効の状態で始まります。

このスイッチを「準備完了」の関門として使ってください。

:::steps
1. ワークフローを作成します。
2. 現実的な値で、**ビルダー** の **ワークフローを実行** をクリックします。無効なワークフローは手動でも実行できないため、ビルダーはまずオンにするよう求めます。**オンにして実行** をクリックしてください。
3. 実行を開き、各ブロックが期待どおりに進んだかを確認します。[実行履歴](/docs/workflows/runs-and-logs) を参照してください。
4. 準備ができていれば **有効** をオンのままにします。そうでなければ、準備ができるまでオフにしてください。オンのあいだは、本物のイベントでトリガーが発火します。
:::

ワークフローをオフにすると、新しい実行は始まらなくなります。すでに進行中の実行は最後まで進みますが、**Sleep** ブロックで待っている実行は、目覚めたときにキャンセルされます。

## ワークフローのアーカイブ

もう必要ないが残しておきたいワークフローはアーカイブします。アーカイブされたワークフローは次のようになります。

- **決して実行されません**。どのトリガーからもです。手動実行と **このステップだけを実行**、Webhook の呼び出し、スケジュール、OneUptime のイベント、受信メール、他のワークフローの **Execute Workflow** ステップはすべて拒否されます。アーカイブされたワークフローへの Webhook の呼び出しには、ワークフローがアーカイブ済みであることを示すエラーが返ります。
- **待機中の実行を止めます。** **Sleep** ステップでスリープ中の実行は目覚めたときにキャンセルされ、キューに入っていてまだ始まっていなかった実行は "Workflow was archived before this run started, so it did not run." で終わります。
- **ワークフローの一覧から外れます。** **ワークフロー → 詳細 → アーカイブ済み** にあります。
- **すべてを保持します。** ステップ、変数、所有者、ラベル、実行履歴はそのまま残ります。

1 つのワークフローをアーカイブするには、それを開いて **設定** に移動し、**アーカイブ** をクリックします。複数をアーカイブするには、**ワークフロー** の一覧で選択して **アーカイブ** を選びます。

ワークフローを元に戻すには、**ワークフロー → 詳細 → アーカイブ済み** を開いて選択し、**アーカイブ解除** を選ぶか、ワークフローを開いてページ上部のバナーにある **アーカイブ解除** をクリックします。

アーカイブと **有効** スイッチは別物です。アーカイブはスイッチに触れないので、オンだったワークフローはアーカイブ解除されるとすぐにまた実行され、オフだったものはオフのままです。**アーカイブ済み** ページの **アーカイブ解除時** 列に、どちらなのかが表示されます。

エクスポートしたワークフローはアーカイブの状態を持ち出さないため、インポートしたコピーがアーカイブ済みになることはありません。

## 所有者とラベル

| 対象             | 場所                                              | 役割                                                                                                                                                      |
| ---------------- | ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **所有者**       | ワークフローの **所有者** ページ                  | ワークフローに責任を持つユーザーとチーム。チームが所有するものに限定されたロールは、そのチームが所有するワークフローに届きます。                            |
| **ラベル**       | ワークフローの **概要** ページ                    | チーム、インテグレーション、環境などでワークフローをまとめるタグ。**ワークフロー** の一覧をラベルで絞り込んだり、ロールを一部のラベルに限定したりできます。 |
| **ラベルルール** | **ワークフロー → 設定 → ラベルルール**            | 名前や説明のパターンから、新しいワークフローに自動でラベルを付けます。                                                                                    |
| **所有者ルール** | **ワークフロー → 設定 → 所有者ルール**            | 新しいワークフローに所有者を自動で割り当てます。                                                                                                          |

ルールの照合方法については、[ラベルと所有者のルール](/docs/configuration/label-and-owner-rules) を参照してください。

## シークレット

機密情報を含む変数は **シークレット** としてマークしてください。その値は実行のログとステップのトレースから取り除かれます。シークレットかどうかに関係なく、変数の値は保存後にダッシュボードでも API でも読み戻せません。また、一度シークレットにした変数はシークレットのままです。

シークレットの変数は次のものに使います。

- 外部サービスの API キー。
- 認証トークン。
- Webhook の署名キー。
- 読み取り専用のアクセス権を持つ人に見せたくないもの全般。

シークレットをブロックに直接貼り付けないでください。`Authorization: Bearer eyJh...` のような値は、ワークフローとログに見えてしまいます。代わりに `{{global.variables.MY_SECRET}}` を使ってください。

シークレットが期限切れになる OAuth のアクセストークンなら、変数を [OAuth 2.0 変数](/docs/workflows/variables#oauth-20-変数自動で更新されるトークン) にしてください。OneUptime が ID プロバイダーからトークンを取得し、ワークフローが期限切れのトークンを使おうとするたびに更新します。OAuth 2.0 変数は常にシークレットで、その認証情報はデータベースで暗号化されます。

## ワークフローのエクスポートとインポート

ワークフローは JSON ファイルとして、プロジェクト間や、セルフホスト環境と OneUptime Cloud のあいだで移動できます。

:::tabs
@tab エクスポート
ワークフローを開き、**設定** に移動して **ワークフローをエクスポート** をクリックします。複数のワークフローを 1 つのファイルにまとめるには、**ワークフロー** の一覧で選択して **JSON をエクスポート** を選びます。
@tab インポート
**ワークフロー** の一覧で **JSON をインポート** をクリックし、任意の OneUptime プロジェクトからエクスポートしたファイルを選びます。プロジェクトにすでにある名前のワークフローは、名前の後に "(Imported)" を付けてインポートされます。
:::

ファイルには、ワークフローの名前、説明、有効状態、グラフが含まれます。次のものは意図的に含まれません。

- **Webhook のシークレットキー。** ワークフローの作成時に新しいものが生成されるため、インポートしたワークフローの Webhook URL は別物になります。新しいワークフローの Webhook トリガーからコピーしてください。元のものを呼び出していたものはすべて、向け直す必要があります。
- **受信メールのアドレス。** Incoming Email トリガーを持つインポートしたワークフローには、専用のアドレスが付きます。新しいワークフローのトリガーからコピーしてください。元のものにメールを送っていたものすべてに、新しいアドレスを伝える必要があります。
- **グローバル変数。** `{{global.variables.MY_SECRET}}` を読むブロックはその参照を保持しますが、値はファイルに含まれません。インポートしたワークフローを実行する前に、移行先のプロジェクトで変数を作成してください。
- **所有者とラベル。** 手動で作成した場合と同じように、プロジェクト自身のラベルと所有者のルールがインポートしたワークフローに適用されます。

インポートしたワークフローは、エクスポート元で有効だったとしても、常に **無効** の状態で作成されます。そのグラフは、移行先のプロジェクトに存在しないモニター、オンコールポリシー、他のワークフローを指している可能性があるからです。内容を確認し、有効にし、**ワークフローを実行** でテストしてから、オンのままにしてください。ワークフローの複製も同じ動作なので、編集する前にコピーが元のものと並んで発火し始めることはありません。

グラフはそのまま運ばれるため、ブロックに直接入力したものも一緒に運ばれます。これが、認証情報をシークレットの変数に置いておく実際的な理由です。トークンをハードコードしたワークフローをエクスポートすると、そのトークンをファイルの受け取り手に渡すことになります。

## Webhook のセキュリティ

Webhook トリガーは固有の URL を発行します。URL を知っている人は誰でも呼び出せます。意図しない呼び出しや望まない呼び出しから守るには、次のようにします。

- URL をパスワードと同じように扱ってください。公開したり、公開リポジトリにコミットしたりしないでください。Webhook トリガーは、**表示** をクリックするまで URL のシークレットキーを隠し、**URL をコピー** は URL を表示せずにコピーします。
- URL が漏れた場合は、**ビルダー** で Webhook トリガーをクリックし、**URL をリセット** をクリックします。ワークフローに新しい URL が発行され、古い URL はすぐに使えなくなります。
- URL がワークフローの ID で終わるとトリガーに表示されている場合は、リセットしてください。Webhook URL が専用のシークレットキーを持つようになる前に作成されたワークフローは、代わりにワークフローの ID を使っていて、それはワークフローを開ける人なら誰でも見られます。
- 機密性の高いワークフローでは、呼び出し元のシステムに共有トークンをヘッダー（`X-Webhook-Token` など）で送ってもらい、重要な処理の前に **If / Else** ブロックで確認してください。期待するトークンはシークレットの変数として保存します。
- 特に機密性の高いワークフローでは、公開の Webhook よりも、OneUptime のイベントトリガーと手動のインポートステップを選んでください。

Webhook URL を表示またはリセットできるのは、ワークフローを編集できる人 — **Project Owner**、**Project Admin**、**Workflow Admin**、**Edit Workflow** — だけです。URL を持っている人は誰でもサインインせずにどこからでもワークフローを開始できるため、それ以外の人には誰に頼めばよいかを示す注記が表示されます。これは、**ビルダー** からワークフローを手動で実行する **Workflow Member** にも当てはまります。

## 受信メールのセキュリティ

Incoming Email トリガーはワークフローに専用のアドレスを発行し、アドレスを知っている人は誰でもそこにメールを送れます。`@` より前の部分はワークフローのシークレットキーなので、アドレスはパスワードと同じように扱ってください。

- 公開したり、公開リポジトリに置いたりしないでください。トリガーは **表示** をクリックするまでキーを隠し、**アドレスをコピー** はアドレスを表示せずにコピーします。
- アドレスが漏れた場合は、**ビルダー** で Incoming Email トリガーをクリックし、**アドレスをリセット** をクリックします。ワークフローに新しいアドレスが発行され、それ以降、古いアドレスへのメールは無視されます。
- メールの送信者は誰でも好きなように設定できるため、**From** は送信者の証明になりません。ワークフローが重要な処理をする前に、本物の送信者だけが知っていること（件名やヘッダーにあるトークンなど）を **If / Else** ブロックで確認してください。期待するトークンはシークレットの変数として保存します。
- 実行が受け取るものすべて — **To**、**CC**、ヘッダー、本文 — でキーは伏せられます。実行のログは、ワークフローの実行を読めるすべての人に見えるからです。

アドレスを表示またはリセットできるのは、ワークフローを編集できる人 — **Project Owner**、**Project Admin**、**Workflow Admin**、**Edit Workflow** — だけです。それ以外の人には、誰に頼めばよいかを示す注記が表示されます。

## 送信ネットワークアクセス

API ブロックやその他の HTTP ブロックは OneUptime からリクエストを送り、IRC ブロックは OneUptime から IRC サーバーのポートに接続します。セルフホストの場合は、呼び出すサービスにインストール環境から到達できることを確認してください。OneUptime Cloud を使っている場合、送信元の IP 範囲は [IP アドレス](/docs/configuration/ip-addresses) に記載されているので、相手側で許可できます。

ブロックが到達できるアドレスは、ブロックによって異なります。

| ブロック                                                       | ループバック、リンクローカル、クラウドメタデータ                             | プライベートネットワークのアドレス                                                                                                                |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **API** ブロックと **Run Custom JavaScript** のリクエスト      | 拒否。ただし、正確なホストが `PRIVATE_NETWORK_WEBHOOK_ALLOWLIST` にある場合を除く | 拒否。ただし、セルフホスト環境の管理者が `ALLOW_PRIVATE_NETWORK_WEBHOOKS` または `PRIVATE_NETWORK_WEBHOOK_ALLOWLIST` で許可した場合を除く      |
| **Send Email**、**IRC**、OAuth 2.0 のトークン URL              | 拒否                                                                         | OneUptime Cloud では拒否。セルフホスト環境では、`DATA_SOURCE_BLOCK_PRIVATE_ADDRESSES` が `true` でない限り許可                                   |
| Slack、Microsoft Teams、Discord、Telegram                      | 拒否                                                                         | 拒否。それぞれ自分のサービスのアドレスにしか送りません                                                                                            |

セルフホスト環境の管理者がこれらを開放する方法は、[プライベートネットワークアクセス](/docs/self-hosted/private-network-access) を参照してください。

## AI コンポーネント

**Generate Text with AI** は LLM に 1 つのリクエストを送ります。プロジェクトの既定の LLM プロバイダー、またはプロジェクトにない場合はインストール全体のグローバルプロバイダーです。プロバイダーは **プロジェクト設定 → AI → LLM プロバイダー** で設定し、プロバイダーの API キーや独自のエンドポイントをワークフローに入れないでください。

プロバイダーが受け取るもの、そしてモデルがそれでできること:

- **ブロックに入れたものだけ。** OneUptime は固定の安全指示を送り、その後にブロックの **System Instructions**、**Prompt**、**Context** を、参照を埋めた状態で送ります。**Context** は区切りの後の最後に置かれ、安全指示はモデルに、区切りより後のものはすべて、指示のように見えるテキストであっても信頼できないデータだと伝えます。
- **それ以外は何も送りません。** トリガーのデータ、ワークフローの履歴、他のブロックの出力、プロジェクトのレコード、テレメトリー、シークレットが添付されることはありません。これらが OneUptime の外に出るのは、3 つの設定のいずれかで参照したときだけです。
- **テキストのみで、ツールはありません。** モデルは OneUptime に問い合わせたり、HTTP リクエストを送ったり、データを変更したりできません。プロバイダーの追加パラメーターが通すのは、生成の調整だけを行う許可リストのフィールドだけです。メッセージを置き換える、ツール、Web 検索、その他のデータソースを加える、テキスト以外や複数の回答を求める、ストリーミングする、プロバイダーにリクエストを保持させる、ブロックの出力上限を引き上げる、といったことはできません。OneUptime が知らないフィールドは捨てられます。
- **モデルは管理者が選びます。** 生成をオフラインに保つ必要がある場合は、プロバイダー側で自分から何も取得しないモデルを選んでください。

ログに残るもの:

- 実行のログは、ブロックの **System Instructions**、**Prompt**、**Context**、**Response** を伏せます。後続のブロックは実行中にそれらを使えます。それらのどれかを挿入したブロックは、自分のルールでそれを記録するため、挿入することはそれを表示する選択になります。
- プロバイダー、モデル、トークン数、**LLM Log ID**、安全なエラーメッセージは、運用と課金のために表示されたままです。プロバイダーの生のエラーは、リクエストの内容を繰り返している可能性があるため、どのログにも残しません。
- 各呼び出しは **プロジェクト設定 → AI → AI ログ** に、プロバイダー、モデル、ステータス、トークン、費用、課金とともに一覧表示されます。プロンプト、応答、生のエラーは含まれません。

必要なものと費用:

- **プロジェクト設定 → AI → AI 機能** で **AI を有効化** がオンになっている必要があります。OneUptime Cloud では、プロジェクトに Growth プラン以上と支払い済みのサブスクリプションも必要です。課金のないセルフホスト環境にはプランの条件はありません。
- 費用のかかるグローバルプロバイダー経由の呼び出しは、プロジェクトの AI クレジットを使います。
- プロジェクトの所有者が設定している場合、各呼び出しは [プロジェクト独自の 1 日あたりの AI 上限](/docs/ai/ai-sre#the-projects-own-daily-limits) に数えられます。上限に達すると、ブロックは UTC の午前 0 時まで、モデルに接続せずに **Error** をたどります。

| 上限                                                          | 値                                                                       |
| ------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **System Instructions**、**Prompt**、**Context** の合計       | 50,000 文字                                                              |
| **Temperature**                                               | `0` から `1` まで                                                        |
| **Maximum Output Tokens**                                     | `1` から `4096` まで。既定値は `1024`                                    |
| 1 回のリクエスト                                              | 試行は 1 回、最大 60 秒                                                  |
| 同時の呼び出し                                                | プロジェクトごとに 3。それを超えるものは **Error** をたどり、後の実行で再試行できます。 |

検証、設定、アクセス、上限、クレジット、同時実行、プロバイダー、タイムアウトの失敗は、すべて **Error** の経路をたどり、理由は **Error** に入ります。ワークフローを本番運用する前に、その経路を接続してください。

> [!WARNING]
> 参照する値はすべて、プロバイダーに送るデータです。プロバイダーがそれを受け取ることを承認されていない限り、シークレットの変数をプロンプトやコンテキストに入れないでください。Ollama のようなセルフホストのローカルプロバイダーはリクエストを自社のインフラ内に留めます。ホスト型のプロバイダーは、そのプロバイダー自身のデータ処理条件のもとでリクエストを受け取ります。

## 権限

ワークフローは、プロジェクトのロールベースのアクセス制御に従います。ワークフローのロールは 3 つです。

- **Workflow Admin** — ワークフローを構築します。作成、変更、実行、削除を行い、ワークフローが使う変数を管理します。
- **Workflow Member** — ワークフローを使います。ワークフローとその実行を開き、**ワークフローを実行** でワークフローを手動で実行します。メンバーは、ワークフローの作成、変更、削除や、そのステップの単独実行はできません。
- **Workflow Viewer** — ワークフローとその実行を閲覧します。

**Project Owner** と **Project Admin** は、Workflow Admin ができることをすべてできます。**Project Member** はワークフローを作成、削除できますが、変更や実行はできません。

1 つのことだけが必要なチームや API キーのための、個別の権限:

- **Create / Read / Edit / Delete Workflow** — ワークフロー自体に対する基本的な権限。ワークフローの変更（オン/オフの切り替えやアーカイブを含む）には **Edit Workflow** が必要です。**Delete Workflow** は削除するだけです。
- **Edit Workflow** — **このステップだけを実行** で 1 つのステップを単独で実行するときや、ワークフローの Webhook URL と受信メールのアドレスを表示またはリセットするときにも必要です。ワークフロー全体を手動で実行するには、**Edit Workflow**、**Workflow Admin**、**Workflow Member** のいずれかが必要です。
- **Read Workflow Log** — 実行を表示するのに必要です。
- **Create / Read / Edit / Delete Workflow Variables** — グローバル変数とワークフロー変数の管理。

手動実行が届くのは、自分が開けるワークフローだけです。一部のラベルや、自分のチームが所有するワークフローに限定されたロールは、それらだけを実行します。ワークフローを実行できない人には、**ワークフローを実行** が淡色表示され、ツールチップに理由が示されます。

自動化を構築する人には **Workflow Admin** を、開始するだけの人には **Workflow Member** を付与してください。変数の編集権限は、プロジェクトのシークレットを管理する人に限ってください。ロールの付与方法については [ユーザー、チーム、権限](/docs/permissions/index) を参照してください。

## ワークフローのステップができること

OneUptime のレコードを読み書きするステップ — Find、Create、Update、Delete のコンポーネントと、On Create、On Update、On Delete のトリガー — は、ワークフローのプロジェクトの **Project Admin** として動作します。誰がワークフローを作ったかにかかわらず、ステップは Project Admin がダッシュボードと API で受けるのと同じチェックを受けます。

- **ワークフロー自身のプロジェクトだけ。** ステップが読み書きするのはワークフローが属するプロジェクトのレコードだけで、それ以外のプロジェクトには触れません。Update がレコードを別のプロジェクトに移すこともありません。
- **Project Admin に許されることだけ。** ステップが付与できるのは、Project Admin 自身が持つチームと API キーの権限だけです。そのため、**Project Owner**、課金、プロジェクト削除の権限を配ることはできず、オーナーのチームのように Project Admin を超える権限を持つチームに誰かを追加することもできません。プローブや AI エージェントを誰が作成したかも、ステップは読めません。それを見られるのはプロジェクトの所有者だけです。
- **Runbook の認証情報の読み取りは除外。** Project Admin は Runbook の認証情報を読めますが、それはステップには貸し出されません。変更にその読み取りが必要な場合 — OneUptime AI に確認なしでコマンドを実行させる、Runner で **AI 修復コマンドを実行** をオンにする、OneUptime AI のコマンドを実行する Runner に SSH の認証情報を割り当てる、Runbook のステップなどで Runbook の認証情報を指定する — は、代わりにワークフローのステップを最後に保存した人がチェックされ、その人が Runbook の認証情報を読めない限り（**Read Runbook Credential**、または Project Owner か Project Admin）、ステップは拒否されます。OneUptime は、誰かがワークフローを作成したときと、誰かがステップを保存するたびにその人を記録します。ワークフローの名前の変更、ラベルの変更、オン/オフの切り替えでは、最後にステップを保存した人は変わりません。API キーでステップを保存しても誰も記録されないため、人がステップを保存するまで、ワークフローのステップはこれらの変更を行えません。
- **プランに含まれるものだけ。** OneUptime Cloud では、プランに含まれないものを作成または変更するステップは、ダッシュボードと同じく、必要なプランとともに拒否されます。課金のないセルフホスト環境にはプランの上限はありません。
- **OneUptime が自分のために確保しているものは対象外。** 次のことは、ワークフローを含め、誰に対しても拒否されます。
  - フィードのエントリーの編集や削除（インシデント、アラート、エピソード、モニター、オンコールポリシー、計画メンテナンスのフィード）
  - 通知ログの書き込み（SMS、通話、メール、WhatsApp、Telegram、プッシュ、Webhook、ワークスペースメッセージのログ）
  - OneUptime が出来事に応じて設定する値: カスタムドメインの CNAME が検証済みかどうか、チームの保護スイッチ（**Is Team Editable**、**Is Team Deleteable**、**Is Permissions Editable**、**Should Have At Least One Member**）、どのインシデントロールが主要なものでそれを削除できるかどうか、所有者やメンバーに通知済みかどうか、リマインダーの時刻と回数、スケジュールで現在と次にオンコールの人、オンコールの実行の進行状況、SLO の現在のバーンレートとエラーバジェット、インシデントやメンテナンスによって一時停止されたモニター、ステータスページのプライベートユーザーのパスワードリセットトークンと最終サインイン、サービスが自分について報告する事実（バージョン、ランタイム、クラウド）、検出ルールや脅威フィードの最終実行
  - `createdIncidentTemplateId` を **Create One Incident** に送ってテンプレートからインシデントを宣言すること — 代わりにステップの **Incident Template** 設定でテンプレートを選んでください。そうすればステップは Project Admin としてそのテンプレートからインシデントを宣言し、テンプレートを記録します
  - 作成後に、レコードがどのレコードに属するかを変更すること。たとえば、所有者の行が対象とするモニターや、メモが付いているインシデントです
- **誰でもない者として。** ワークフローが作成したレコードには作成者が記録されず、監査ログには、変更を行った者として、その時点の名前でワークフローが記録されます。

チェックがステップを拒否すると、ステップは拒否された変更を行わずに **Error** の出力をたどり、実行のログにはステップと理由が分かりやすい言葉で記録されます。例: *"Create One Team Permission" was refused. Workflow steps can do only what a Project Admin of this project can do: …*。ワークフローの [実行履歴](/docs/workflows/runs-and-logs) で確認してください。Create Many ステップはレコードを 1 件ずつ作成し、最初に拒否されたところで止まります。それより前に作成したレコードは残ります。

他のシステムとやり取りするステップ — API、Email、Slack、Microsoft Teams、Discord、Telegram、IRC、Custom Code、Generate Text with AI — は OneUptime のレコードを読み書きしないため、これらには何も変わりません。

## プランの上限

OneUptime Cloud では、ワークフローには Growth プラン以上が必要で、各プランで任意の 30 日間に実行できる回数が決まっています。

| プラン     | 直近 30 日間の実行回数   |
| ---------- | ------------------------ |
| Growth     | 500                      |
| Scale      | 2,000                    |
| Enterprise | 実質的に無制限           |

期間はずれていきます。手動でもトリガーからでも、プロジェクトが記録した実行は 30 日間数えられます。Growth と Scale のプランでは、**ワークフロー** ページに、プロジェクトが使った回数を示す **ワークフローの実行** カードが表示されます。上限に達すると、新しい実行は **Execution Exceeded Current Plan** のステータスで記録されて処理されず、サブスクリプションが未払いのあいだも同様です。課金のないセルフホスト環境には上限はありません。

## 1 回の実行にかけられる時間

| 上限                                                              | 既定値         | セルフホストでの設定            |
| ----------------------------------------------------------------- | -------------- | ------------------------------- |
| 実行（開始時から、または **Sleep** の後に目覚めたときから）       | 2 分           | `WORKFLOW_TIMEOUT_IN_MS`        |
| **Run Custom JavaScript** ブロック                                | 5 秒           | `WORKFLOW_SCRIPT_TIMEOUT_IN_MS` |
| **Sleep** ブロック                                                | 最大 30 日     | —                               |

ランナーは各ブロックの前後で期限を確認し、期限を過ぎた実行は、制御が戻った時点で **Timeout** としてマークします。ブロックを途中で中断することはできないため、ネットワークを待つブロックにはそれぞれ独自の時間制限があります。Generate Text with AI のリクエストは最大 60 秒で、OAuth 2.0 のトークンリクエストは 20 秒であきらめます。**Sleep** ブロックでの待ち時間は実行時間に数えられません。実行は脇に置かれ、目覚めたときに新しく 2 分が与えられます。

## 他のワークフローを呼び出す際の上限

**Execute Workflow** コンポーネントを使うと、あるワークフローから別のワークフローを開始できます。ワークフロー A が B を開始し、B がまた A を開始するようなループを防ぐため、互いを開始するワークフローの連鎖は、すでに連鎖に含まれるワークフローに戻る場合や、10 ワークフローより深くなる場合に拒否されます。その場合、**Execute Workflow** ブロックは **Error** の出力をたどり、エラーに連鎖が示されます。

本当に長い連鎖が必要な場合（1 回の実行で 1 項目を処理するジョブなど）は、たいてい **Run Custom JavaScript** を使って 1 つのワークフローの中でループするほうが簡単です。

## ワークフローが適さない場面

別のものを使うべきケースがいくつかあります。

- **重い計算や大きなデータセット** — ワークフローは軽いつなぎの作業のためのもので、大量の計算向けではありません。重い処理は自社のインフラで実行し、ワークフローからそれを起動してください。
- **長時間の能動的な計算** — 実行の既定の持ち時間は 2 分です。「A をして、2 時間待って、B をする」のような受け身の待ちには **Sleep** コンポーネントを使ってください。実行を脇に置き、ワーカーを占有せずに後で再開します。
- **人が関わる段階的なインシデント対応** — それは [Runbook](/docs/runbooks/index) の役割です。ワークフローは無人の自動化のためのものです。
