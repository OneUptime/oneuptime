# 設定と安全性

このページでは、ワークフローを本物のトラフィックに向ける前に知っておく価値のある設定と、安全のための上限を扱います。

## ワークフローのオン/オフ切り替え

どのワークフローにも **設定** の中に **有効** の切り替えがあります。オフのあいだ、そのワークフローは動きません — Webhook の呼び出しも、スケジュールの時刻も、OneUptime のイベントも、すべて無視されます。新しいワークフローは無効の状態で始まります。

このスイッチを「準備完了」のゲートとして使ってください。

1. ワークフローを組み立てる。
2. **ビルダー** で現実的な値を入れて **ワークフローを実行** をクリックする。
3. **ログ** を確認する — どのブロックも想定どおりの経路を通ったか確かめます。
4. **有効** をオンにする。

ワークフローをオフにしても、すでに進行中の実行は止まりません。新しい実行が始まらなくなるだけです。

## 所有者とラベル

- **所有者** — 所有者として登録されたユーザーとチームは、そのワークフローにアクセスでき、失敗したときの通知を受け取るよう設定できます。**設定 → 所有者** で指定します。
- **ラベル** — ワークフローをまとめるためのタグです。ワークフローの一覧はラベルで絞り込めるので、忙しいプロジェクトがずっと見通しよくなります。チーム別、連携先別、環境別に整理したいときに便利です。
- **ラベルルール** — **ワークフロー → 設定 → ラベルルール** で、名前や説明のパターンに応じて新しいワークフローにラベルを自動で付けられます。
- **所有者ルール** — **ワークフロー → 設定 → 所有者ルール** で、新しいワークフローに所有者を自動で割り当てられます。

## シークレット

機微なものを含むグローバル変数には **シークレット** の印を付けてください。保存したあとは通常の API や UI からの読み取りで値が隠され、ワークフローのログ出力も、実行ログを保存する前に解決済みの値を伏せます。

シークレット変数を使うべきもの:

- 外部サービスの API キー。
- 認証トークン。
- Webhook の署名鍵。
- 読み取り専用の権限しかない人には見られたくないもの全般。

シークレットをブロックに直接貼り付けないでください — `Authorization: Bearer eyJh...` のような値は、ワークフローにもログにも見えるかたちで残ってしまいます。代わりに `{{global.variables.MY_SECRET}}` を使ってください。

## ワークフローのエクスポートとインポート

ワークフローは JSON ファイルとして、プロジェクト間や、セルフホストと OneUptime Cloud のあいだで移せます。

- **エクスポート** — ワークフローを開き、**設定** の **Export Workflow** を使います。ワークフローの一覧から複数を選んで、1 つのファイルにまとめて書き出すこともできます。
- **インポート** — **ワークフロー** の一覧で **Import JSON** をクリックし、どの OneUptime プロジェクトから書き出したファイルでも選べます。

ファイルにはワークフローの名前、説明、有効かどうかの状態、そしてグラフが入ります。意図的に入れていないものもあります。

- **Webhook のシークレットキー。** ワークフローが作成された時点で新しいものが生成されるので、インポートしたワークフローの Webhook URL は元とは別になります。元の URL を呼んでいたものは向け直しが必要です。
- **グローバル変数。** `{{global.variables.MY_SECRET}}` を読むブロックはその参照を保ったままですが、値はファイルに入っていません。インポートしたワークフローを実行する前に、移し先のプロジェクトで変数を作ってください。
- **所有者とラベル。** 移し先のプロジェクト自身のラベルルールと所有者ルールが、手で作った場合とまったく同じように、インポートされたワークフローに対して走ります。

インポートされたワークフローは、書き出し元で有効だったとしても、必ず **無効** の状態で作成されます — そのグラフは、移し先のプロジェクトに存在しないモニターやオンコールポリシー、他のワークフローを指しているかもしれないからです。中身を見直し、有効にし、**ワークフローを実行** で試してから、オンのままにしてください。ワークフローの複製も同じ挙動なので、あなたが手を入れる前にコピーが元と並んで動き出すことはありません。

グラフはそのまま丸ごと移動するので、ブロックに直接打ち込んだものも一緒についてきます。認証情報をシークレット変数に置いておくべき現実的な理由がこれです。トークンを直書きしたワークフローをエクスポートすると、そのファイルを受け取った人にトークンごと渡すことになります。

## 1 回の実行にかけられる時間

実行の試行ごとに、実時間での期限があります。ランナーは各コンポーネントの前後でこれを確認し、期限を過ぎた実行は制御が戻った時点で **Timeout** とマークします。ネットワークやスクリプトの処理を行うコンポーネントは、自分でもタイムアウトを持つ必要があります。ランナーは任意のコンポーネントのコードを強制的に中断できないからです。

AI コンポーネントは、プロバイダーへのリクエストのタイムアウトをワークフローの残り時間から導き、最大 60 秒で頭打ちにします。ログ出力と後始末のための余裕を少し残すためです。

## 他のワークフローを呼び出す際の上限

**Execute Workflow** コンポーネントを使うと、あるワークフローから別のワークフローを呼べます。ワークフロー A が B を呼び、B がまた A を呼ぶといった事故的なループを防ぐため、連鎖の深さには上限があります。上限を超えた実行は、はっきりしたエラーで終わります。

（1 回の実行で 1 件ずつ処理するジョブのように）長い連鎖が本当に必要な場面もありますが、たいていは **Custom Code** を使って 1 つのワークフローの中でループするほうが簡単です。

## Webhook のセキュリティ

Webhook トリガーには専用の URL が付きます。その URL を知っている人は誰でも叩けます。事故や望まない呼び出しから守るには:

- URL はパスワードだと思って扱ってください。公開の場で共有したり、公開リポジトリにコミットしたりしないこと。
- 機微なワークフローでは、呼び出し側に共有トークンをヘッダー（`X-Webhook-Token` など）で送ってもらい、重要なことをする前に **条件** ブロックで確認してください。期待するトークンはシークレット変数として保存します。
- 非常に機微なワークフローでは、公開の Webhook ではなく、OneUptime のイベントトリガーと手作業の取り込みステップを選んでください。

## 送信ネットワークアクセス

API や他の HTTP のブロックは、OneUptime からリクエストを送ります。セルフホストなら、あなたのインストールが呼び出し先のサービスに到達できることを確かめてください。OneUptime Cloud を使っているなら、送信元の IP レンジを [IP アドレス](/docs/configuration/ip-addresses) に載せてあるので、相手側で許可できます。

## AI コンポーネント

**Generate Text with AI** は、OneUptime に設定された LLM ゲートウェイを通してリクエストを 1 回送ります。使われるのはプロジェクトの既定の LLM プロバイダー、プロジェクトに設定がなければインストール全体のプロバイダーです。プロバイダーは **プロジェクト設定 → AI → LLM プロバイダ** で設定してください。プロバイダーの API キーや任意のモデルのエンドポイントをワークフローそのものに書いてはいけません。

AI コンポーネントには、はっきりした外向きの境界があります。

- OneUptime が設定済みのプロバイダーに送るのは、固定のコンポーネント安全指示に加えて、解決済みの **System Instructions**、**Prompt**、シリアライズされた **Context** です。Context はユーザーメッセージの末尾で明示的なマーカーの後ろに付けられ、固定の指示は、そのマーカーより後ろはタグや指示が含まれていても信頼できないデータのままである、と述べています。
- トリガーのペイロード、ワークフローの履歴、他のコンポーネントの出力、プロジェクトのレコード、テレメトリ、シークレットが自動で付くことはありません。データが出ていくのは、その 3 つの入力のどれかであなたが参照したときだけです。
- ツール定義やプロバイダー固有の機能フィールドは送りません。モデルはこのコンポーネントを通して OneUptime に問い合わせたり、HTTP リクエストを出したり、プロジェクトのデータを書き換えたりはできません。設定されたプロバイダーとモデルは管理者が引く信頼境界のままなので、厳密にオフラインでの生成が必要なインストールでは、プロバイダー側で管理される検索機能を内蔵しないモデルを選んでください。
- プロバイダーレベルの追加パラメータは、生成の調整に関わるフィールドだけの許可リストに制限されています。ワークフローのメッセージを差し替えたり、ツールやプロバイダー固有の Web 検索・データソースを足したり、テキスト以外のモダリティを有効にしたり、複数の候補を要求したり、ストリーミングを有効にしたり、プロバイダーの保存フラグでリクエストを残したり、このコンポーネントの出力トークン上限を引き上げたりはできません。将来の未知の機能フィールドは、既定で捨てられます。
- System Instructions、Prompt、Context、そして生成された Response の値は、自動のワークフロー実行ログにおける、この AI コンポーネント自身の引数と戻り値のエントリからは伏せられます。実行中は、後続のコンポーネントから引き続き利用できます。それを別のコンポーネントに差し込んだ場合は、そのコンポーネントのログ方針が適用され、解決済みの値が記録されることがあります — 再利用は明示的な開示だと考えてください。プロバイダーとモデルの名前、トークン数、LLM Log ID、安全なエラーメッセージは、運用と請求のために引き続き見えます。プロバイダーからの生のエラー本文は、ワークフローのログ、LLM ログ、アプリケーションログ、トレースのいずれからも除外されます。プロバイダーがリクエストの内容をそのまま返してくることがあるためです。

参照する変数はすべて、あなたが意図的にプロバイダーへ送るデータだと考えてください。とりわけ、その開示がどうしても必要で、かつそのプロバイダーが受け取ってよいと承認されているのでない限り、シークレットのグローバル変数をプロンプトやコンテキストに差し込まないでください。Ollama のようなセルフホストのローカルプロバイダーなら、リクエストを自社のインフラ内にとどめられます。ホスト型のプロバイダーは、そのプロバイダーのデータ処理条件のもとでリクエストを受け取ります。

呼び出しは 1 件ずつ **プロジェクト設定 → AI → AI ログ** に記録され、プロバイダー、モデル、ステータス、トークン、コスト、請求情報が含まれます。プロンプトとレスポンスのプレビュー、プロバイダーからの生のエラー詳細は AI ログには保存されません。課金対象のグローバルプロバイダー経由の呼び出しは、プロジェクトの AI クレジット残高を消費します。ワークフローの AI は、プロジェクトの 1 日あたりの自律 AI トークン予算にも算入されます。予算を使い切ると、コンポーネントはモデルに接続せずに **エラー** の経路を通ります。プロジェクトの AI が有効になっている必要があります。OneUptime Cloud では、サブスクリプションが支払い済みであることと、Growth プラン（または Growth の機能を含むプラン）が必要です。請求を無効にしたセルフホストのインストールに、このプランの制限はありません。

組み込みの上限が、無人の呼び出しを有限に保ちます。System Instructions、Prompt、シリアライズされた Context は合計 50,000 文字まで。Temperature は `0` から `1` まで、Maximum Output Tokens は `1` から `4096` まで（既定は `1024`）でなければなりません。プロバイダーへのリクエストは 1 回だけ試み、最長 60 秒でタイムアウトします。ワークフローの AI 呼び出しは 1 プロジェクトあたり同時に 3 件までで、それを超えた呼び出しは **エラー** の経路を通り、あとのワークフロー実行で再試行できます。検証、設定、アクセス、予算、残高、同時実行数、プロバイダー、タイムアウトのいずれの失敗も **エラー** の経路を通り、**エラー** の出力に値が入ります。本番のワークフローを有効にする前に、この経路をつないでおいてください。

## 権限

ワークフローはプロジェクトのロールベースアクセス制御に従います。関係する権限は次のとおりです。

- **Create / Read / Edit / Delete Workflow** — ワークフロー自体に対する基本の権限。
- **ワークフローを実行** — 手動で実行したり、API 経由でトリガーしたりするのに必要です。
- **Read Workflow Log** — 実行を閲覧するのに必要です。
- **Read / Create / Edit / Delete Workflow Variable** — グローバル変数の一覧を扱う権限。

たいていのエンジニアには、ワークフローの作成・編集・閲覧は与えつつ、変数の権限は与えないのがよいでしょう。変数を編集できる権限は、プロジェクトのシークレットを管理する人のために取っておいてください。

## プランの上限

OneUptime Cloud では、小さめのプランで月あたりの実行回数に上限があります。現在の上限は **プロジェクト設定 → 請求** で確認できます。上限に達すると、次の請求サイクルまで新しいトリガーは拒否されます。セルフホストのインストールにこの上限はありません。

## ワークフローが適さない場面

別のものに手を伸ばしたほうがよい場面もいくつかあります。

- **重い計算や大きなデータセット** — ワークフローは軽い接着作業のためのもので、数値計算のためのものではありません。重い処理は自分のインフラで走らせ、ワークフローにはその起動だけを任せてください。
- **長く動き続ける計算** — 1 回の実行の試行は、短時間で終わることを想定しています。「A をやって 2 時間待って B をやる」のような受け身の待ちには **Sleep** コンポーネントを使ってください。実行を保存しておき、ワーカーを占有せずに後で再開します。
- **人が間に入る段階的なインシデント対応** — それは [Runbook](/docs/runbooks/index) の役目です。ワークフローは人の手を介さない自動化のためのものです。
