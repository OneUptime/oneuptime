# 実行とログ

ワークフローが動くたびに、OneUptime は何が起きたかの記録を残します — いつ動いたか、うまくいったか、どのブロックが何をしたか。この記録を **実行** と呼びます。ワークフローがうまくいったことを確かめるのも、うまくいかなかったものを調べるのも、過去の動きを振り返るのも、実行を通して行います。

## どこで見られるか

| ページ                                              | 見えるもの                                                                                          |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **ワークフロー → 実行とログ**（プロジェクト全体）   | プロジェクト内のすべてのワークフローの、すべての実行。ワークフロー名、ステータス、時刻で絞り込めます。 |
| **ワークフロー → 実行とログ**（個別のワークフロー） | このワークフローの実行だけ。こちらには、ワークフローの絞り込みの代わりに **実行 ID** の絞り込みがあります。 |
| **1 件の実行**                                      | 実行の行にある **ログを表示** ボタンで開きます — 行そのものはクリックできません。                    |

## 実行のステータス

| ステータス                          | 意味                                                                                                                                                      |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **予定**                            | トリガーが発火し、実行がランナー待ちのキューに入っています。ふつうは 1 秒に満たない時間です。5 分たってもまだ予定のままの実行は失敗扱いです — どのランナーも拾わなかったということです。 |
| **実行中**                          | ワークフローが進行中です。時間のかかるブロックがあると、この状態のままになります。                                                                        |
| **待機中**                          | 実行が **Sleep** ブロックで止まっていて、時間が来れば自分で再開します。待っているあいだ、ワーカーは占有しません。                                          |
| **Executed**                        | 実行が失敗せずに最後まで到達しました。（これが成功の状態です — ピルに出るのは「Success」ではなく **Executed** です。）                                     |
| **エラー**                          | ブロックがエラーを出したため、実行が止まりました。キューに入った実行が結局拾われなかったとき、待機中の実行の再開が失われたとき、スケジュールの式が解決できなかったとき、実行の途中でワークフローが無効にされたときにも使われます。 |
| **Timeout**                         | 実行が、許された時間より長くかかりました。[ワークフロー 設定と安全性](/docs/workflows/configuration) を参照してください。                                  |
| **Execution Exceeded Current Plan** | プロジェクトが直近 30 日分のワークフロー実行数を使い切っているか、サブスクリプションが未払いです。実行は記録されますが、実行されません。OneUptime Cloud のみ。 |

**エラー** の出力に処理を渡すブロック — たとえば 4xx を受け取った API ブロック — があっても、実行そのものは失敗しません。エラー側の分岐が動き、実行は **Executed** で終わります。見つけやすいように、そのステップだけは赤で描かれます。

## 実行を読む

実行の **ログを表示** をクリックすると開きます。**Workflow Run** の画面には、タブが 2 つあります。

**ステップ** — 動いたブロック 1 つにつき 1 行が、順番に並びます。各行には、ブロックのタイトル、コンポーネントの id、かかった時間、そしてどの出力から抜けたか（`→ success`、`→ error`、`→ yes`）が出ます。行を開くと、詳細が 2 つのかたまりで見られます。

- **Received** — 変数がすべて解決されたあとに、そのブロックへ渡された設定です。
- **Returned** — そのブロックが返したものです。

失敗したステップは赤く、最初から開いた状態で表示され、**Received** の上にエラーメッセージが出ます。

**Full Log** — ランナーが出力した生のログを 1 行ずつそのまま並べたもので、ブロック自身が書いたログも含まれます。ステップの画面で失敗の理由が分からないときに使ってください。

知っておく価値のある点が 2 つあります。各ステップのタイトルの下に出ているコンポーネント id は、`{{local.components.<id>.returnValues.…}}` の参照にそのまま貼り付けられる文字列です。参照を正しく書くには、これがいちばん早い方法です。もう 1 つ、実行が保持するのは最後の 100 ステップだけです。長い実行や、何度も再開した実行では、古いステップが捨てられた場所に橙色の注記が出ます。

表示される値は、変数が埋まったあとにブロックが実際に見た値です。ただし例外が 2 つあります。シークレットと、ブロックが機微だと印を付けた項目は伏せられます。そして、とても長い値は「… (truncated)」で切り詰められます。

**ビルダー** から実行を始めると、この同じ画面が実行を追いかける状態で開くので、あとから探しに行かずに、その場で様子を見られます。

## よくある調べ方

### 「ワークフローが動かない」

1. そのワークフローの **概要** ページで **有効** になっているか確かめます。新しいワークフローは無効の状態で始まり、無効のワークフローはすべての実行を拒否します — 手動の実行も含めてです。
2. OneUptime のイベントトリガーなら、そのイベントが本当に起きたか確かめます。該当のレコードを開いて、履歴を見てください。
3. Webhook トリガーなら、相手のシステムが正しい URL に送っているか確かめます。たいていのツールは Webhook を送ったことを記録しているので、そちらを見てください。
4. スケジュールトリガーなら、cron 式が思っている時刻と合っているか確かめます。

実行そのものは **Execution Exceeded Current Plan** というステータスで *現れている* 場合、プロジェクトが直近 30 日分のワークフロー実行数を使い切っているか、サブスクリプションが未払いです。その実行のログに、使った回数とプランの上限が書かれています。これは OneUptime Cloud だけの話です。

### 「後ろのブロックが動かなかった」

動かないブロックは、たいてい配線の問題です。**ビルダー** を開いて確かめてください。

- 前のブロックの出力は、このブロックの入力につながっていますか。
- 前のブロックは、思っていたのとは違う出力を通ったのではありませんか — **成功** ではなく **エラー**、**はい** ではなく **いいえ**、というように。どちらを通ったかは、**ステップ** タブで分かります。

### 「変数が空のまま渡ってきた」

実行を開いて、失敗したステップの **Received** を見てください。

- `{{local.components.…}}` という文字がそのまま見えているなら、参照が解決されていません。たいていはコンポーネント id か戻り値 id の打ち間違いです — ブロックに表示されている名前ではなく **Identifier** のほうだ、ということを思い出してください。`local.components` 自体の綴りも確かめましょう。`{{local.componets.api-get-1.returnValues.response-body}}` はただの文字列として送られ、それでも実行は **Executed** と報告されます。
- 空の文字列が見えているなら、前のブロックは動いたけれど、その項目を返さなかったということです。

**Full Log** タブには、解決できなかった参照を名指しする警告行が出ます。たいていは、これがいちばん早い見つけ方です。

### 「手で実行すると動くのに、トリガーからだと動かない」

**ビルダー** を開いて **ワークフローを実行** をクリックし、本物のトリガーが送ってきそうな値でトリガーの入力欄を埋めます。そのうえで、その実行の **Received** の値と、本物の実行の **Received** の値を並べて見比べてください。違いはたいてい、項目名か型のどちらか 1 つです。

## ワークフローを実行し直す

「この実行をやり直す」ボタンはありません。過去の実行を自動で再実行しないのは、副作用 — Slack のメッセージ、API 呼び出し、チケット — を繰り返すのが安全とは限らないからです。やり直したいときは、ワークフローを直して次の本物のトリガーに任せるか、**ビルダー** を開いて同じ値で **ワークフローを実行** をクリックしてください。

## 実行はどのくらい残るか

OneUptime Cloud では、実行は **30 日間** 保持されてから削除されます — どちらの実行の一覧も、直近 30 日分を対象としていると書いてあるのはそのためです。セルフホストの環境では、削除するまで実行が残ります。とても頻繁に動くワークフローが履歴を埋めてしまうなら、そのワークフローを無効にするか削除して、これ以上ノイズを増やさないようにしてください。

ステップのトレースが追加される前に記録された実行には **ステップ** の内容がなく、**Full Log** だけが表示されます。
