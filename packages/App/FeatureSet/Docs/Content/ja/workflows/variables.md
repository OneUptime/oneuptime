# 変数

ワークフローの本質は、データを動かすことです — トリガーから最初のブロックへ、ブロックから次のブロックへ、そして共有の値を必要な場所へ。そのデータを動かす手段が変数です。

変数のスコープは 2 つあり、それに加えて、実行のあいだに生まれるコンポーネントの出力があります。

## グローバル変数

一度保存すればどこからでも使い回せる、プロジェクト全体の値です。API キー、URL、チャンネル名など — 10 個のワークフローにコピーして回りたくないものを入れておきます。

**ワークフロー → グローバル変数** にあります。それぞれ次の項目を持ちます。

- **名前** — 参照するときの名前です。2 文字以上、空白なし、使えるのは英数字とハイフンとアンダースコアだけです。`UPPER_SNAKE_CASE` にしておくとブロックの中で目立つので、習慣にしておくとよいでしょう。
- **説明** — 任意。何のための値かを思い出すための自由記述です。
- **シークレット** — オンにすると、実行ログとステップのトレースから値が消されます。
- **コンテンツ** — 実際の値です。長文のテキスト欄なので、複数行の値も入ります。

グローバル変数は、どのワークフローでも次のように書いて使えます。

```
{{global.variables.NAME}}
```

たとえば PagerDuty の鍵を `PAGERDUTY_KEY` として保存しておけば、どのブロックからでも `{{global.variables.PAGERDUTY_KEY}}` として使えます — エディターが保存するのは参照だけで、ワークフローのログ出力は解決後のシークレットの値を伏せます。

変数にできるのは作成と削除だけで、編集はできません。一覧に編集ボタンはないので、UI で値を変えるには、変数を削除して作り直します — あるいは API で更新します。その方法はこのページの最後で扱います。グローバル変数とワークフロー変数は Growth プランの機能です。

## ワークフロー内のローカル変数

1 つのワークフローの中だけで有効な変数で、そのワークフローの左メニューの **ワークフロー変数** で管理します。参照はこう書きます。

```
{{local.variables.NAME}}
```

## コンポーネントの出力（前のブロックのデータ）

どのトリガーもコンポーネントも、実行のあいだに出力を生み出せます。参照は手で打つのではなく、エディターのコンポーネント値ピッカーで作ってください — ランナーが期待するとおりの id を挿入してくれます。

前のブロックの出力は、次のように参照します。

```
{{local.components.COMPONENT_ID.returnValues.FIELD_ID}}
```

`COMPONENT_ID` はブロックの **Identifier** — ブロック上に表示されている短い id であって、表示名ではありません。新しいブロックには `api-get-1` のような id が付き、ブロックの **ID** のところで変えられます。変えると、そこを指していた参照はすべて壊れます。変数の名前を変えたときと同じです。`FIELD_ID` は、選んだ戻り値の id です。

例を挙げます。

- ID が `lookup-user` の **API** コンポーネントが動いたあと、そのステータスコードは `{{local.components.lookup-user.returnValues.response-status}}`、ボディは `{{local.components.lookup-user.returnValues.response-body}}` です。
- ID が `transform` の **Run Custom JavaScript** コンポーネントなら、返ってくる値は `{{local.components.transform.returnValues.returnValue}}` です。
- レコード種別のトリガー — **On Create Incident** とその仲間 — が返す値はちょうど 1 つ、`model` だけで、そこから下に辿ります。ID が `incident-on-create-1` のトリガーなら、インシデントのタイトルは `{{local.components.incident-on-create-1.returnValues.model.title}}` です。

ローカルの値が存在するのは、いまの実行のあいだだけです。実行が変われば、まっさらな状態から始まります。

## 変数が使える場所

ほとんどすべてのテキスト欄が変数を受け付けます。

- API ブロックの URL。
- Slack、Teams、Discord、Telegram、メールのメッセージ本文。
- メールの件名と本文。
- ヘッダーとボディの項目（文字列の値の中で）。
- **If / Else** ブロックの左右どちらの値も（Conditions カテゴリにあります）。

JSON の欄では、文字列の値の中に変数を書けますが、キーには使えません。参照が値まるごとを占めている場合は裸のまま置き換わるので、その書き方なら JSON の欄にオブジェクトごと流し込めます。構造を動的に組み立てたいときは、**Run Custom JavaScript** ブロックで作ってから、その出力を次のブロックに渡してください。

**Run Custom JavaScript** ブロックには、変数が自動では渡りません — サンドボックスには何も注入されないからです。`{{global.variables.NAME}}`（やコンポーネントの参照）は、ブロックの **Arguments** の JSON 欄に書いてください。そこに書いた値はスクリプトが動く前に置き換えられ、`args` として届きます。

## 配列を繰り返す

テキスト欄の中では `{{#each path}}…{{/each}}` で配列を回せます。ブロックの中では、`{{property}}` が現在の要素から読み、`{{@index}}` が 0 起点の位置、`{{this}}` は要素そのもの（値が並ぶだけの配列で使います）です。`{{#each}}` ブロックの中の名前は前後の空白が取り除かれるので、他の場所とは違って、ここだけは余計な空白があっても害はありません。

## 例

### Webhook からペイロードを組み立てる

`{ "service": "checkout", "status": "failed" }` のようなボディで Webhook が届きます。これを OneUptime のインシデントにするには、こうします。

1. id が `ci-webhook` の **Webhook** トリガー。
2. **If / Else** ブロック。Webhook の **リクエストボディ** の出力を選んでその `status` プロパティを使い、演算子は `==`、右の値は `failed` にします。
3. **はい** の分岐から、**Create One Incident** ブロックへ。設定はこうです。
   - タイトル: `CI build failed: {{local.components.ci-webhook.returnValues.request-body.service}}`
   - 説明: `See {{local.components.ci-webhook.returnValues.request-body.url}} for the logs.`

### API 呼び出しでシークレットを使う

PagerDuty を呼ぶワークフローの場合。

1. `PAGERDUTY_KEY` を、シークレットのグローバル変数として保存します。
2. **API** ブロックで、`Authorization` ヘッダーを `Token token={{global.variables.PAGERDUTY_KEY}}` にします。

これで鍵は、ワークフローにもログにも残りません。

### API 呼び出しを 2 つつなぐ

1 つめの呼び出しが、2 つめに必要な ID を返してくれます。

1. **API** コンポーネント `lookup-order`: ピッカーを使って、手動トリガーの JSON の email の項目を `GET /orders?email=...` に挿入します。
2. **API** コンポーネント `cancel-order`: `POST /orders/{{local.components.lookup-order.returnValues.response-body.id}}/cancel`。

`lookup-order` が失敗すると、**成功** ではなく **エラー** の出力が発火します。そこをメールや Slack のブロックにつないでおけば、失敗を見逃さずに済みます。

## ワークフローから変数を更新する

よくあるのは、資格情報をスケジュールでローテーションするパターンです。外部から新しいトークンを取ってきて、それを変数に書き戻し、次の実行がそれを拾えるようにします。これは、OneUptime の API を呼ぶ **API** ブロックで行います。

`ApiKey` ヘッダーを付けて `PUT /api/workflow-variable/<variable-id>` を呼びます。そして — ここでつまずく人が多いのですが — 変えたい項目は **`data` オブジェクトで包みます**。

```json
{
  "data": {
    "content": "{{local.components.get-token.returnValues.response-body.access_token}}"
  }
}
```

`data` で包まずに平らなボディを送ると、400 で拒否されます。本当に変えたい項目だけを送ってください。`name` と `description` はペイロードに入れなくて構いません。

API キーには **Edit Workflow Variables** の権限が必要です。読み取りの権限は要りません — この更新は、行を読み返さないからです。

気をつけたいことが 2 つあります。

- **参照している変数の名前を変えないこと。** `name` は `{{local.variables.NAME}}` の一部です。名前を変えると、既存の参照はどれも解決できなくなります。そして解決されなかった参照は、そのままの文字列として通り抜けます — 下の落とし穴を参照してください。
- **この方法で変数に書き込めますが、読み返すことはできません。** `content` は API では書き込み専用で、シークレットかどうかにかかわらず、すべての変数でそうです。だからこそ、ローテーションするトークンを置いておく場所として変数が安全なのです。シークレットの印を付ければ、さらに実行ログとステップのトレースからも値が消えます。

## 落とし穴

- **ピッカーを使うこと。** ランナーが期待するとおりのコンポーネント id、戻り値 id、変数 id を挿入してくれますし、参照が表示ラベルに左右されなくなります。
- **変数名は大文字と小文字を区別します。** `{{global.variables.MyKey}}` と `{{global.variables.mykey}}` は別物です。
- **解決できなかった参照は、空にされずそのまま残ります。** 存在しないものを参照してもエラーにはならず、空の文字列にもなりません。波かっこごとそのまま通り抜けるので、ステップ id を打ち間違えた `{{local.components.api-get-1.returnValues.body}}` は、Slack のメッセージにも URL にもリクエストボディにも、字面のまま入ってしまいます。しかも実行は **Executed** と報告されます。実行ログには、すり抜けた参照を名指しする警告行が出ます。
- **ビルダーは変数名を検査できません。** 一致しないコンポーネント参照 — 知らないステップ id、知らない戻り値、形の壊れたルート — は、保存の前に指摘してくれます。けれど変数が実在するかどうかは判断できないので、名前を変えた変数に気づけるのは実行ログだけです。
- **波かっこの中の空白は取り除かれません。** `{{ local.variables.NAME }}` は `{{local.variables.NAME}}` とは別の参照で、決して解決されません。唯一の例外は `{{#each}}` ブロックの中で、そこでは名前の空白が取り除かれます。
