# 用語集

OneUptime で使われるすべての言葉を 1〜2 文で説明し、ほかの呼び名と、詳しく扱うページを添えています。言葉は出会う順にグループにまとめてあります。最初のグループはどのプロジェクトでも回るループで、最後のグループは複数の意味を持つ言葉です。

:::cards
- [ここから始める](#ここから始める): モニターから呼び出し、ステータスページまで、どのプロジェクトでも回るループ。
- [監視する対象](#監視する対象): サービス、ホスト、クラスター、クラウドと、それらに課す目標。
- [問題への対応](#問題への対応): 状態、重大度、所有者、ラベル、そしてほかの種類の問題。
- [テレメトリとダッシュボード](#テレメトリとダッシュボード): システムが送るものと、それを見る場所。
- [自動化と AI](#自動化と-ai): 自動で動くものと、OneUptime AI が行うこと。
- [インストールするものとキー](#インストールするものとキー): 実行するエージェントと、それぞれが使うキー。
- [複数の意味を持つ言葉](#複数の意味を持つ言葉): ルール、ロール、リソース、設定など、いくつもの役割を持つ言葉。
:::

## ここから始める

### プロジェクト

設定したものすべてが置かれる場所です。モニター、インシデント、オンコール、ステータスページ、テレメトリ、設定がここにあります。あるプロジェクトの中身は別のプロジェクトからは見えず、ほとんどの会社は 1 つで足ります。

[基本概念](/docs/introduction/core-concepts#プロジェクトと人) を参照してください。

### アカウント

あなた自身です。サインインに使うメールアドレスとパスワード、名前、タイムゾーン、言語です。1 つのアカウントで、いくつでもプロジェクトに所属できます。

[アカウント](/docs/introduction/your-account) を参照してください。

### チーム

プロジェクト内の人のグループで、その権限がメンバーにできることを決めます。新しいプロジェクトは、Owners、Admin、Members の 3 つのチームから始まります。人は **ユーザー** で招待し、 **チーム** でグループにまとめます。

[ユーザー、チーム、権限](/docs/permissions/index) を参照してください。

### モニター

運用しているもの 1 つ (Web サイト、API、サーバー、Kubernetes クラスターなど) をチェックし、それが動いているかを判断します。条件に一致すると、ステータスを変え、インシデントを宣言したりアラートを作成したりできます。

[モニターの作成](/docs/monitor/create-monitor) を参照してください。

### 条件

モニターのルールで、各チェック結果が何を意味するかを決めます。条件は順番にチェックされ、最初に一致したものが、モニターのステータスを変えたり、インシデントを宣言したり、アラートを作成したり、その 3 つすべてを行ったりできます。

別名: **監視条件**、 **モニター条件**、 **モニターのステップ**。 [条件とステータス](/docs/monitor/criteria-and-statuses) を参照してください。

### モニターステータス

モニターの現在の状態です。新しいプロジェクトには **稼働中**、 **機能低下**、 **オフライン** の 3 つのモニターステータスがあり、独自のステータスを追加することもできます。

[条件とステータス](/docs/monitor/criteria-and-statuses) を参照してください。

### プローブ

モニターのチェックをスケジュールに沿って実行するマシンです。ページをリクエストしたり、API を呼び出したり、ホストに ping を送ったりします。OneUptime Cloud は複数のリージョンでプローブを動かしており、自社ネットワークの内側で動かすカスタムプローブは、そのネットワークからしか届かないものをチェックします。

別名: **カスタムプローブ**。 [カスタム プローブ](/docs/probe/custom-probe) を参照してください。

### インシデント

障害や速度低下など、ユーザーに影響する問題であり、それが続く間チームが拠り所にする記録です。オンコール担当者を呼び出したり、ステータスページに表示したりできます。

[インシデント 概要](/docs/incidents/index) を参照してください。

### アラート

ディスクの容量不足や期限切れが迫った証明書など、ユーザーが気付く前にチームが調べるべき問題です。オンコール担当者を呼び出せますが、ステータスページに表示されることはありません。

[アラートの概要](/docs/alerts/index) を参照してください。

### エピソード

関連するインシデント、または関連するアラートのまとまりで、チームはこれを 1 組の所有者と 1 つの状態を持つ 1 つのものとして扱います。何をまとめるかはグループ化ルールが決めます。

別名: **インシデントエピソード**、 **アラートエピソード**。 [エピソード](/docs/incidents/episodes) を参照してください。

### オンコールポリシー

インシデント、アラート、エピソードについて誰を呼び出すか、そして誰も確認しなければ次は誰かを決めます。そのレベルがエスカレーションルールです。

別名: **オンコール**、 `OnCallDutyPolicy`。 [オンコールポリシー](/docs/on-call/policies) を参照してください。

### エスカレーションルール

オンコールポリシーの 1 つのレベルです。誰を呼び出すか、そして次のレベルを呼び出す前に、誰かが確認するのをどれだけ待つかを決めます。レベルは、人、チーム、またはオンコールスケジュールを呼び出せます。

[エスカレーションルール](/docs/on-call/escalation-rules) を参照してください。

### オンコールスケジュール

いつ誰がオンコールかを示します。担当者が交代で受け持ち、それぞれが次の人に引き継ぎます。スケジュールを呼び出すエスカレーションルールは、その時点でスケジュール上のオンコール担当者を呼び出します。

別名: **ローテーション**、**オンコールポリシーのスケジュール**。 [オンコールスケジュール](/docs/on-call/schedules) を参照してください。

### レイヤー

オンコールスケジュールの中の1つのローテーションです。誰が交代で担当するか、どのくらいの頻度で引き継ぐか、どの時間帯を受け持つかを決めます。オンコール担当者がいる最上位のレイヤーが呼び出されるため、メインのローテーションを上に、予備の担当を下に置きます。

[オンコールスケジュール](/docs/on-call/schedules#レイヤー) を参照してください。

### 通知方法

プロジェクト内で OneUptime があなたに連絡できる宛先です。メールアドレス、SMS や電話用の電話番号、Slack や Microsoft Teams のアカウント、スマートフォンの OneUptime アプリがあります。各自が **ユーザー設定** で自分の通知方法を追加します。

[通知方法](/docs/notifications/notification-methods) を参照してください。

### 私への連絡方法

呼び出しを受けるためのあなた自身のルールです。呼び出しでどの通知方法を、どれだけ待ってから試すかを決めます。1 つのラダーがすべてのインシデント、アラート、エピソードに適用され、重大度ごとに独自のルールを持たせることもできます。各自が **ユーザー設定** で自分のものを設定します。

別名: **個人のオンコールルール**。 [私への連絡方法](/docs/notifications/on-call-rules) を参照してください。

### ステータスページ

サービスが動いているか、そしてそれに影響するインシデントやメンテナンスを顧客に示すページです。公開にも、招き入れた人だけの非公開にもできます。

[ステータス ページ 概要](/docs/status-pages/index) を参照してください。

### 購読者

メール、SMS、Slack、Microsoft Teams、Webhook でステータスページをフォローし、そこでのインシデントやメンテナンスの開始、変更、終了の知らせを受け取る人です。

[購読者とお知らせ](/docs/status-pages/subscribers) を参照してください。

### 定期メンテナンス

事前に告知する計画作業です。各メンテナンスイベントはメンテナンスの状態 **予定**、 **進行中**、 **終了**、 **完了** と進み、イベントを表示するステータスページが訪問者と購読者にそれを知らせます。

別名: **定期メンテナンスイベント**、 **定期イベント**、 **イベント**。 [定期メンテナンスの概要](/docs/scheduled-maintenance/index) を参照してください。

### テレメトリ

システムが OneUptime に送るものです。ログ、メトリクス、トレース、例外、プロファイルがあります。アプリは OpenTelemetry で送信し、OneUptime のエージェントはホスト、クラスター、その他のインフラストラクチャから送信します。どちらも取り込みキーを使います。

[OpenTelemetry](/docs/telemetry/open-telemetry) を参照してください。

## 監視する対象

### モニターグループ

複数のモニターを 1 つのステータス (その中で最も悪いもの) にまとめたもので、独自の稼働率を持ちます。ステータスページはグループ全体を 1 行で表示できます。モニターグループは **プロジェクト設定 → 詳細 → 機能フラグ** でオンにします。

[モニターグループ](/docs/monitor/monitor-groups) を参照してください。

### サービス

運用しているアプリケーションやマイクロサービスです。OneUptime はテレメトリが初めて届いたときに `service.name` の名前でサービスを追加し、そのログ、トレース、メトリクス、例外、インシデント、所有者を 1 つのページにまとめます。

別名: **サービスカタログ**、 **テレメトリサービス**。 [サービス](/docs/telemetry/services) を参照してください。

### ホスト

メトリクス、プロセス、ログ、サービスの状態を OpenTelemetry Collector 経由で送る Linux、Windows、macOS のマシンです。 **ホストを追加** はコマンド 1 つでコレクターをインストールし、OneUptime がその設定を最新に保ちます。

[ホスト](/docs/telemetry/hosts) を参照してください。

### Kubernetes

Kubernetes クラスターと、そのノード、Pod、ワークロード、イベント、ログです。Helm でインストールする Kubernetes エージェントが送信します。

[Kubernetes エージェント](/docs/telemetry/kubernetes-agent) を参照してください。

### インフラストラクチャ

運用しているマシンとプラットフォームをまとめたメニューのグループです。ホスト、Kubernetes、Docker、Docker Swarm、Podman、Proxmox、OpenStack、VMware、Ceph、ストレージアレイ、ネットワーク、IoT があります。それぞれをエージェントや接続が埋め、その中のマシン、クラスター、デバイスがそれぞれどんな状態かを示します。

[ホスト](/docs/telemetry/hosts) を参照してください。

### ネットワーク

スイッチ、ルーター、ファイアウォール、アクセスポイントなど、ネットワーク上でアドレスを持つあらゆるものです。SNMP に対応しているかどうかは問いません。

[ネットワークデバイス モニター](/docs/monitor/network-device-monitor) を参照してください。

### クラウド

ダッシュボードから接続した AWS アカウント、Azure サブスクリプション、Google Cloud プロジェクトです。OneUptime はその中のすべてのリソースを一覧にし、主要なメトリクスを読み取り、何が変わったかを記録します。

[クラウド アカウントの接続](/docs/telemetry/cloud-accounts) を参照してください。

### アプリプラットフォーム

Amazon ECS や Fargate、Google Cloud Run、Azure App Service などのマネージドプラットフォームで動かすアプリです。アプリが動く場所はそれぞれクラウド環境であり、OneUptime はそのテレメトリが初めて届いたときにクラウド環境を作成します。

別名: **クラウド環境**。 [クラウド環境](/docs/telemetry/cloud-environments) を参照してください。

### サーバーレス

AWS Lambda、Google Cloud Functions、Azure Functions などのサーバーレス関数です。OpenTelemetry のデータが届くとすぐに、トレース、ログ、メトリクスとともに一覧に表示されます。

別名: **サーバーレス関数**。 [サーバーレス関数](/docs/telemetry/serverless-functions) を参照してください。

### データベース

アプリケーションがクエリするすべてのデータベースです。トレース、データベース自身のメトリクス、OneUptime が読み取れるその他のソースから組み立てられ、エンジンの状態も示します。

[データベース](/docs/telemetry/databases) を参照してください。

### キュー

Apache Kafka、RabbitMQ、Amazon SQS など、サービスが使うメッセージキューとトピックです。トレースとブローカーのメトリクスから把握します。

[キュー](/docs/telemetry/queues) を参照してください。

### リアルユーザーモニタリング

Web アプリやモバイルアプリで実際の人が体験していることです。ページの読み込み、リクエスト、エラー、Core Web Vitals を、プローブではなくアプリ自身が報告します。

[RUM 概要](/docs/rum/index) を参照してください。

### インベントリ

OneUptime があなたの環境について知っているすべてを 1 つにまとめた一覧です。サービス、ホスト、Kubernetes オブジェクト、仮想マシン、ネットワークデバイス、クラウドリソース、そしてテレメトリをまったく送らないものまで含まれます。その大半は自動的に埋まります。

[インベントリの概要](/docs/inventory/overview) を参照してください。

### トポロジー

システムがどうつながっているか、どのサービスがどのサービスを呼び出し、何がどこで動いているかを示すマップです。すでに送っているテレメトリから描かれます。

[トポロジー](/docs/telemetry/topology) を参照してください。

### SLO

監視している対象の信頼性の目標です。たとえば「30 日間で 99.9% の時間は稼働」のように表します。OneUptime は 5 分ごとに、各 SLO をそのモニターに照らして測定します。

別名: **サービスレベル目標**。 [SLO 概要](/docs/slo/introduction) を参照してください。

### エラーバジェット

SLO の目標が許容するダウンタイムです。30 日間で 99.9% なら、43 分 12 秒です。十分に残っていればリスクを取れますが、残りが少なければペースを落とし、安定性に投資します。

[エラーバジェット](/docs/slo/error-budget) を参照してください。

## 問題への対応

### 状態

インシデントやアラートが対応のどの段階にあるかです。新しいプロジェクトは **原因特定**、 **確認済み**、 **解決済み** から始まります。確認すると、誰かが対応中であることが伝わり、次のエスカレーションレベルは呼び出されなくなります。解決すると、それは閉じられます。

別名: **インシデントの状態**、 **アラートの状態**。 [インシデントの状態と重大度](/docs/incidents/states-and-severities) を参照してください。

### 重大度

インシデントやアラートがどれほど重要かです。新しいプロジェクトには、インシデント用に Critical Incident、Major Incident、Minor Incident、アラート用に **高** と **低** があります。名前や色を変えたり、独自の重大度を追加したりできます。

別名: **インシデントの重大度**、 **アラートの重大度**。 [インシデントの状態と重大度](/docs/incidents/states-and-severities) を参照してください。

### 所有者

モニター、インシデント、ステータスページなど、1 つのレコードに責任を持つ人またはチームです。所有者は、自分が所有するものに何かが起きると知らせを受けます。

[ラベルルールと所有者ルール](/docs/configuration/label-and-owner-rules) を参照してください。

### ラベル

Production や Checkout のようなタグで、モニター、インシデント、ステータスページ、その他ほとんどのレコードに付けて、絞り込みやグループ化に使います。チームの権限を、特定のラベルが付いたレコードに限定することもできます。

[ラベルルールと所有者ルール](/docs/configuration/label-and-owner-rules) を参照してください。

### 例外

コードがスローするエラーです。OneUptime は同じエラーの発生をすべて 1 つの例外にまとめ、スタックトレース、傾向、発生したリクエストとともに示します。

別名: **例外トラッキング**、 `/telemetry-exception`。 [例外](/docs/telemetry/exceptions) を参照してください。

### AI インサイト

何かが呼び出しを行う前に、OneUptime がテレメトリの中で見つける問題です。新しい例外や急増する例外、エラーログの急増、遅くなったトレース、メトリクスのドリフト、状況を悪化させたデプロイなどです。インサイトは誰も呼び出さず、インシデントも開きません。誰かが見るまで受信トレイで待ちます。製品やレコードの AI セクションにある **インサイト** ページには、OneUptime AI がそこで学んだことが表示されます。

別名: **インサイト**。 [AI SRE](/docs/ai/ai-sre#インサイト-先回りの検出) を参照してください。

### セキュリティイベント

OneUptime の SIEM です。ログ、セキュリティツール、その他送信したあらゆるもののセキュリティイベントを、テレメトリと並べて 1 つの形式で保持し、検出ルールがその中から脅威を見つけます。

別名: **SIEM**。 [セキュリティイベント (SIEM)](/docs/telemetry/security-events) を参照してください。

### セキュリティケース

検出ルール、脅威インテリジェンス、または接続されたセキュリティ製品から上がった、調べる価値のある 1 つの事柄で、同じユーザー、ホスト、アドレスに関するすべての検出がまとめられます。アナリストはキューでケースに対応し、プレイブックがそれに応答します。

別名: **ケース**。 [セキュリティケースとプレイブック (SOAR)](/docs/telemetry/security-cases) を参照してください。

## テレメトリとダッシュボード

### ログ

サービス、ホスト、エージェントが書き出す行です。ログエクスプローラーで検索し、ログモニターで見守ります。

[ログエクスプローラー](/docs/telemetry/logs-explorer) を参照してください。

### メトリクス

サービスやインフラストラクチャが時間とともに報告する数値です。リクエスト数、レイテンシ、CPU、キューの深さなどがあります。

[メトリクスエクスプローラー](/docs/telemetry/metrics-explorer) を参照してください。

### トレース

1 つのリクエストがサービスを通っていく経路を、ステップごとに示したものです。各ステップはスパンであり、所要時間と結果を持ちます。

[トレースエクスプローラー](/docs/telemetry/traces-explorer) を参照してください。

### プロファイル

アプリケーションが CPU 時間とメモリを関数ごとにどう使っているかです。OneUptime の Pyroscope 互換 API に送信するプロファイラーが送ります。

別名: **パフォーマンスプロファイル**、 **継続的プロファイリング**。 [プロファイル](/docs/telemetry/profiles) を参照してください。

### AI / LLM

AI アプリやエージェントが行う会話です。すべてのモデル呼び出しを、トークン、コスト、レイテンシ、プロンプト、回答とともに、アプリが送る OpenTelemetry のスパンから組み立てます。

別名: **AI / LLM オブザーバビリティ**。 [AI / LLM オブザーバビリティ](/docs/telemetry/ai-llm-observability) を参照してください。

### データオブザーバビリティ

データベースやデータウェアハウスのテーブルを見守り、データが遅れている、欠けている、誤っているときに、その原因となった実行、デプロイ、テーブルとともに知らせます。

[データオブザーバビリティの概要](/docs/data-observability/index) を参照してください。

### データセキュリティ

クラウドのバケット、データベース、データウェアハウス、送信しているテレメトリの中から、会社が保持している機密データを見つけ、その保管方法の問題点を知らせます。

[データセキュリティの概要](/docs/data-security/index) を参照してください。

### ダッシュボード

自分で並べるウィジェットのページです。メトリクス、ログ、トレースのチャート、インシデントやモニターの一覧、SLO などを載せられます。ダッシュボードは、共有するまでプロジェクト内だけのものです。

[ダッシュボード 概要](/docs/dashboards/index) を参照してください。

### 公開ダッシュボード

公開リンクで共有したダッシュボードで、プロジェクトにサインインしない人に向けたものです。パスワードで保護したり、特定の IP アドレスに限定したり、独自ドメインでホストしたりできます。

[共有と公開ダッシュボード](/docs/dashboards/sharing) を参照してください。

## 自動化と AI

### ワークフロー

コードを書かない自動化です。キャンバス上のブロックが、トリガーの発火で実行されます。たとえば、インシデントが宣言されたときに Slack に投稿したり、別のツールを呼び出したりします。

[ワークフロー 概要](/docs/workflows/index) を参照してください。

### Runbook

再利用できる対応手順です。インシデント、アラート、メンテナンスイベントに対してチームが実行する手動と自動のステップで、手で実行することも、Runbook ルールが一致したときに実行することもできます。

[Runbook 概要](/docs/runbooks/index) を参照してください。

### プレイブック

セキュリティケースに応答するステップです。証拠の保全、オンコール担当者の呼び出し、ユーザーの停止などを、自動で、またはクリック 1 つで実行します。

別名: **セキュリティプレイブック**。 [セキュリティケースとプレイブック (SOAR)](/docs/telemetry/security-cases#プレイブック) を参照してください。

### AI ルール

OneUptime AI がどの新しいインシデントやアラートを調査・修正するか、そしてその方法を決めます。AI ルールがなければすべてを調査するので、ほとんどのプロジェクトでは不要です。

別名: **自動修復ルール**。 [AI SRE](/docs/ai/ai-sre#調査修正されるインシデント) を参照してください。

### OneUptime AI

OneUptime の AI サイト信頼性エンジニアです。新しいインシデントとアラートをそれぞれテレメトリ全体にわたって調査し、見つけたことをタイムラインに投稿します。 **プロジェクト設定** の **AI を有効化** スイッチで、そのすべてをオフにできます。

別名: **AI SRE**。 [AI SRE](/docs/ai/ai-sre) を参照してください。

### AI に質問

プロジェクトのデータを対象にしたチャットです。ログ、トレース、メトリクス、インシデント、モニターなどを照会し、すべての主張に出典を付けて答えます。

別名: **チャット**。 [AI に質問](/docs/ai/ask-ai) を参照してください。

### コード

コーディングエージェントに頼むのと同じように、リポジトリでの作業を OneUptime AI に依頼する場所です。バグの修正、テストの作成、変更を頼むと、プルリクエストが返ってきます。

別名: **タスク**。 [コード](/docs/ai/ai-agent) を参照してください。

### フォーム

リンクを知っていれば誰でも、アカウントなしで記入できるページです。送信のたびに、問題報告ならインシデントが、変更依頼ならメンテナンスイベントが作成されます。

[フォームの概要](/docs/forms/index) を参照してください。

## インストールするものとキー

### インフラストラクチャエージェント

Server / VM モニターの裏で動く `oneuptime-infrastructure-agent` サービスです。1 台のマシンの CPU、メモリ、ディスク、プロセスを 30 秒ごとに、モニターのシークレットキーで署名して報告します。

[サーバー / VM モニター](/docs/monitor/server-monitor) を参照してください。

### Kubernetes エージェント

クラスターのメトリクス、イベント、Pod のログ、そして eBPF によるトレースを収集し、取り込みキーを使って送信する Helm チャートです。

[Kubernetes エージェント](/docs/telemetry/kubernetes-agent) を参照してください。

### OpenTelemetry Collector

テレメトリを受信、処理、送信するオープンソースのエージェントです。 **ホストを追加** はこれをマシンにインストールし、Docker エージェントもその一種です。自分で運用するコレクターも、取り込みキーを使って OneUptime に送信します。

別名: **コレクター**。 [ホスト](/docs/telemetry/hosts) と [ホスト OpenTelemetry Collector](/docs/telemetry/host-otel-collector) を参照してください。

### Runner

自社のインフラストラクチャ内で動かす小さなプロセスで、Runbook の JavaScript、Bash、SSH、kubectl のステップを実行します。独自の Runner ID とキーで、OneUptime に外向きに接続します。

別名: **Runbook エージェント**。 [Runbook エージェント](/docs/runbooks/agents) を参照してください。

### 取り込みキー

OpenTelemetry を使うアプリ、コレクター、エージェントなどが、プロジェクトにテレメトリを送るためのキーです。 `x-oneuptime-token` ヘッダーに入れます。プロジェクトの API キーは代わりになりません。

別名: **テレメトリ取り込みキー**、 `oneuptime.apiKey`。 [取り込みキー](/docs/telemetry/ingestion-keys) を参照してください。

### API キー

スクリプト、CLI、Terraform、AI アシスタントが、与えた権限の範囲で API を通じてプロジェクトを読み書きするためのキーです。 **プロジェクト設定 → 詳細 → API キー** で作成します。

[ユーザー、チーム、権限](/docs/permissions/index#api-キー) を参照してください。

## 複数の意味を持つ言葉

### ルール

OneUptime では多くのものがルールであり、それぞれがあなたに代わって 1 つの判断を下します。誰を呼び出すか (**オンコールルール**、**エスカレーションルール**)、新しいレコードの所有者とラベル (**所有者ルール**、**ラベルルール**)、何をまとめるか (**グループ化ルール**)、OneUptime AI が何をするか (**AI ルール**) です。モニター自身のルールは、その条件です。

[基本概念](/docs/introduction/core-concepts#ルールの種類) を参照してください。

### ロール

4 つの異なるものを指します。プロジェクト所有者やプロジェクト管理者のような、チームが与える権限。権限を組み合わせて作る **カスタムロール**。1 つのインシデントで誰かが担う役割である **インシデントロール**。そして、ネットワーク上のデバイスが果たす役割である **ネットワークデバイスのロール** です。

[ユーザー、チーム、権限](/docs/permissions/index) を参照してください。

### リソース

多くの場合、OneUptime が記録するインフラストラクチャ (ホスト、クラスター、データベース、クラウドリソースなど) を指します。インシデントの **影響を受けるリソース** はそれが関わるモニターとインフラストラクチャ、ステータスページのリソースはそこに表示するモニターとグループで、OpenTelemetry のリソース属性はテレメトリの送信元を示します。

[インベントリの概要](/docs/inventory/overview) を参照してください。

### 設定

レベルごとに独自の設定があります。プロジェクト全体の **プロジェクト設定**、OneUptime からの連絡方法を決める **ユーザー設定**、そして製品のサイドメニューにあるその製品自身の **設定** (たとえば **インシデント** の下にあるインシデントの状態とテンプレート) です。セルフホストのサーバーの設定は管理ダッシュボードにあります。

[プロジェクト設定](/docs/configuration/project-settings) を参照してください。

### ポリシー

多くの場合は **オンコールポリシー** のことで、誰を呼び出し、次は誰かを決めます。着信ポリシーはオンコール担当者につながる電話番号をチームに提供し、エラーバジェットポリシーは SLO のバジェットが尽きかけたときにチームが何をするかを書き留めます。

[オンコールポリシー](/docs/on-call/policies) を参照してください。

### テンプレート

保存された出発点です。モニターテンプレートはモニターを作成し、インシデントとアラートのテンプレートは新しいレコードに値を入れ、メモとポストモーテムのテンプレートは書き始めの下地になり、ダッシュボードテンプレートはダッシュボードのウィジェットを組み立てます。

[モニターテンプレート](/docs/monitor/monitor-templates) を参照してください。

### ワークスペース

**ワークスペース接続** で OneUptime に接続する Slack または Microsoft Teams のワークスペースで、チャンネルに更新を投稿したり、チャットからインシデントを操作したりするのに使います。ほかのツールでワークスペースと呼ばれるものは、OneUptime ではプロジェクトです。

[Slack](/docs/workspace-connections/slack) を参照してください。

### エージェント

インストールして OneUptime に報告したり、OneUptime の代わりに動作したりするプログラムです。インフラストラクチャ、Kubernetes、Docker の各エージェントは収集したものを送り、Runner は Runbook のステップを実行し、AI エージェントは OneUptime AI がクラスターやホストを調べられるようにします。 **コード** に与えるタスクは AI エージェントのタスクです。

[どれを使うべきか](/docs/introduction/which-one#プローブエージェントコレクターrunner-のどれか) を参照してください。

### オンコールルール

**インシデント** と **アラート** の下では、オンコールルールが、新しいインシデントやアラートで実行するオンコールポリシーを選びます。呼び出しが届く方法を決める各自のルールもオンコールルールと呼ばれていましたが、今は **ユーザー設定** の下の **私への連絡方法** です。

[インシデントの設定と自動化](/docs/incidents/settings#インシデントのオンコールルール) と [私への連絡方法](/docs/notifications/on-call-rules) を参照してください。

### 通知設定

**ユーザー設定** では、所有しているものについてどの更新をどのチャネルで受け取るかを決めます。SMS と電話の切り替え、メッセージング残高、独自の SMTP と Twilio といったプロジェクトの設定も通知設定と呼ばれていましたが、今は **プロジェクト設定** の下の **通知チャネル** です。

[通知設定](/docs/notifications/notification-settings) を参照してください。
