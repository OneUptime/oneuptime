# GitHub から OneUptime を使う

OneUptime GitHub App は、単にコードへつなぐためのものではありません。リポジトリの中で話しかければ、その場で作業をこなします。

Issue でメンションすればプルリクエストを開きます。プルリクエストでメンションすれば、そのブランチに修正を加えるか、差分をレビューします。Issue にラベルを付ければ、その Issue を引き受けます。App が生み出すものはすべて、人間が読むためのプルリクエストかレビューです。**マージすることは決してなく、プルリクエストを承認することもありません。**

```text
@oneuptime implement this                          →  Issue をクローズするプルリクエスト
@oneuptime revise this — use exponential backoff   →  このプルリクエストのブランチへの新しいコミット
@oneuptime review                                  →  このプルリクエストに投稿されるコードレビュー
```

> `@oneuptime` は、ご自身の App のハンドルに置き換えてください。OneUptime Cloud では `@oneuptime` です。セルフホストのインスタンスでは、GitHub App に付けた名前を小文字にし、スペースをハイフンに置き換えたものになります —「Acme AI」という名前の App は `@acme-ai` でメンションします。メンションしても何も起きないときは、まずここを確認してください。

## 始める前に

- リポジトリが GitHub App を通じて **OneUptime プロジェクトに接続されている**こと。セットアップ方法は [GitHub 連携（セルフホスト）](/docs/self-hosted/github-integration) を参照してください。OneUptime Cloud では **プロジェクト設定 → コードリポジトリ** から接続できます。
- **「AI コード修正を実行」機能を持つ Runner** がオンラインであること — [AI 修正タスク](/docs/ai/ai-agent) を実行するのと同じ Runner です。これがないと、コマンドはいったん受け付けられたあと、どのエージェントにも引き受けられないまま 30 分後に失敗します。
- GitHub App が **Issues: Read & write** 権限を持ち、[購読すべきイベント](#購読すべきイベント) に挙げた Webhook イベントを購読していること。

## コマンド

どのコマンドも App へのメンションで始まります。メンションはコメントのどこにあってもよく、その後に書いた内容がそのまま依頼として渡されます。

### プルリクエストでのコマンド

| コマンド | 何が起こるか |
| --- | --- |
| `@oneuptime review` | ブランチをクローンし、変更されたコード**とその周辺のコード**を読み、レビューをコメントとして投稿します。何も変更しません。 |
| `@oneuptime revise this — <変更してほしい内容>` | そのプルリクエスト自身のブランチをクローンし、変更を加え、同じブランチに新しいコミットをプッシュします。2 つ目のプルリクエストを開くことはありません。 |

メンションの後に書いた内容が既知のコマンドでない場合は、修正依頼として扱われます。実際、ほとんどの場合それが意図だからです。

```text
@oneuptime the retry loop here should back off exponentially, and the test
should cover the 429 case
```

### Issue でのコマンド

| コマンド | 何が起こるか |
| --- | --- |
| `@oneuptime implement this` | Issue に取り組み、それをクローズするプルリクエストを開きます。 |
| `@oneuptime <それ以外の内容>` | 同じ動作をしますが、書いた文章が追加の指示として渡されます。 |

**コメントを書かずに** Issue を App に渡すこともできます。

- **トリガーラベルを付ける。** リポジトリのトリガーラベル（既定では `oneuptime`）を Issue に付けると、同じ作業が始まります。GitHub の UI から作業を割り当てる方法としては、これが最も確実です。
- **App のボットユーザーに Issue をアサインする**（リポジトリがそれを許可している場合）。GitHub はどのリポジトリでも App を担当者にできるわけではなく、そのためにラベルが用意されています。アサインしても何も起きない場合はラベルを使ってください。

### どこでも使えるコマンド

| コマンド | 何が起こるか |
| --- | --- |
| `@oneuptime help` | コマンドの一覧を表示します。何も書かずにメンションするだけでも同じです。 |
| `@oneuptime status` | このスレッドで現在取り組んでいる内容を伝えます。 |
| `@oneuptime cancel` | このスレッドで進行中の実行を停止します。すでにプッシュされた作業はそのまま残ります。 |

`help`、`status`、`cancel` はエージェントの実行を開始しないため、コストはかからず、1 日あたりの修正タスクの予算にも影響しません。

## スレッド上での見え方

1 つのコマンドが生むコメントは **1 つだけ**で、作業の進み具合に合わせて App がそのコメントを書き換えます。長時間かかるタスクでも、プルリクエストがステータスログで埋まることはありません。

1. あなたのコメントに 👀 のリアクションを付け、その実行がどの OneUptime プロジェクトのものかを示し、進行中の実行へのリンクを添えた受付コメントを投稿します。
2. 作業が終わると、同じコメントが結果に書き換えられます。開いたプルリクエスト、プッシュしたコミット、あるいは何もしなかった理由の率直な説明です。

変更すべき点が見つからなければ、憶測でプルリクエストを開くのではなく、その旨を伝えます。これは失敗ではなく正常な結果です — もっと具体的に指示して、もう一度依頼してください。

## 誰がコマンドを実行できるか

**リポジトリへの write、maintain、admin いずれかの権限を持つ人だけです。** OneUptime は毎回、そのリポジトリにおけるコメント投稿者の権限を GitHub に直接問い合わせます。GitHub がコメントの横に表示する「contributor」バッジは、現在のアクセス権ではなく過去の活動を表すものなので、信頼しません。

それ以外の人からのメンションには、そのコメントに 😕 のリアクションが 1 つ付くだけで、他には何も起きません。これは意図的な動作です。パブリックリポジトリでは誰でもコメントでき、見知らぬ相手に必ず返信する App は、スレッドを荒らす道具として使われかねないからです。

また、自分自身のものを含めボットが書いたコメントはすべて無視し、引用（`>`）やコードブロックの中に現れたメンションも無視します。この 2 つのルールがあるおかげで、App 自身のコメントへの返信が App を再び起動してしまうことがありません。

## App がしないこと

- **決してマージしません。** この App の動作によって、デフォルトブランチにコードが入ることはありません。
- **承認も変更要求もしません。** レビューはコメントとして投稿されるため、App のレビューがブランチ保護ルールを満たすことはありません。
- **履歴を書き換えません。** 修正はコミットを追加するだけで、強制プッシュはしません。誰かが先にそのブランチへプッシュしていた場合は、その作業を捨てるのではなく修正のほうが失敗します。
- **フォークからのプルリクエストは修正できません。** フォークのブランチは、インストールが書き込めないリポジトリにあります。レビューはできるので、代わりにレビューを依頼してください。
- **プルリクエストのタイトル、説明、ターゲットブランチを変更しません。** 変えるのはコードだけです。

## コストと、その抑え方

作業を開始するコマンドはいずれもエージェントの完全な実行です — クローン、最大 40 回の LLM 呼び出しと 100,000 出力トークン、そしてリポジトリにビルドコマンドとテストコマンドを設定していればその実行も加わります。

適用される上限は 2 つあり、どちらも [AI 修正タスク](/docs/ai/ai-agent) にすでに適用されているものと同じです。

- **プロジェクトの 1 日あたりの修正実行数の上限**（**プロジェクト設定 → AI**、既定では 1 日 25 回）。GitHub からのコマンドは、プロジェクトの他の修正実行とこの予算を共有します。
- **リポジトリごとのオープンなプルリクエスト数の上限**（**コードリポジトリ → 対象リポジトリ → 設定**、既定では 5）。レビューと修正はこの対象外です。どちらもレビュー待ちのプルリクエストを増やさないからです。

同じ種類の実行は、1 つの Issue またはプルリクエストにつき同時に 1 つだけです。2 回依頼すると、すでに作業中である旨が返ります。修正の実行中にレビューを依頼した場合は、別々の依頼なので両方が動きます。

実行を開始できない場合、App はその理由をスレッドに書きます — 黙って失敗することはありません。

## 機能をオフにする

リポジトリごとの設定は **コードリポジトリ → 対象リポジトリ → 設定 → GitHub コマンドに応答する** です。オフにすると、App はそのリポジトリでのメンション、アサイン、トリガーラベルを無視し、話しかけた人にはスイッチの場所を伝えます。

同じページには **GitHub トリガーラベル** もあり、`oneuptime` 以外を使いたい場合はここで変更します。

## 購読すべきイベント

GitHub App の **Permissions & events** 設定で、以下を購読してください。

| イベント | 必要な理由 |
| --- | --- |
| **Issue comment** | Issue *および* プルリクエストでの `@mention` コマンド |
| **Issues** | App へのアサインと、トリガーラベル |
| **Pull request** | App へのレビュー依頼 |
| **Pull request review** | 送信されたレビュー本文に書かれたメンション |
| **Pull request review comment** | 差分へのインラインコメントに書かれたメンション |

さらに **Repository permissions** の **Issues** を **Read & write** にする必要があります。GitHub はプルリクエストの会話コメントを issues API 経由で扱うため、この権限によって App はプルリクエストにもコメントできるようになります。

## プロンプトインジェクション: 守られるものと守られないもの

Issue の本文、プルリクエストの説明、差分、コメントはすべてエージェントのプロンプトの一部になります。そしてパブリックリポジトリでは、誰でもそれらを書けます。「指示を無視して X をしろ」と書かれたテキストが Issue に紛れ込むのは、現実に起こりうることです。

これを制限するものが 2 つあります。どちらがどちらなのかを知っておく価値があります。

- **プロンプトは、信頼できないテキストを指示ではなく依頼として扱います。** また、実行対象のリポジトリ、ブランチ、プルリクエストはエージェントが動き出す前に固定されます — エージェントが読んだ内容によって作業対象が変わることはありません。
- **本当の封じ込めはサンドボックスです。** エージェントはお客様の Runner 上で、使い捨てのクローンの中で動きます。コマンドの実行環境から認証情報は取り除かれ、git 操作も制限されています。できるのはブランチへのプッシュだけで、マージできるのは人間だけです。

AI が書いたプルリクエストは、Issue を読んだ新しいコントリビューターからのプルリクエストと同じように扱ってください。説明ではなく差分をレビューするということです。

## トラブルシューティング

**メンションしても何も起きない。** まずハンドルを確認してください — 表示名ではなく App のスラッグです。次に、リポジトリがプロジェクトに接続されているか（**プロジェクト設定 → コードリポジトリ**）、**GitHub コマンドに応答する** がオンになっているか、GitHub App が上記のイベントを購読しているかを確認します。

**😕 のリアクションが付くだけで何も言わない。** そのリポジトリへの write 権限がありません。

**すでにこの件に取り組んでいる、と言われる。** その種類の実行が、この Issue またはプルリクエストで進行中です。`@oneuptime status` で内容がわかり、`@oneuptime cancel` で停止できます。

**受け付けたきり、長い間何も起きない。** **設定 → Runbook エージェント** で **AI コード修正を実行** が有効な Runner がオンラインかどうか確認してください。オンラインの Runner がないと、実行は 30 分後に失敗し、その旨がスレッドに書き込まれます。

**プルリクエストがフォークからのものだと言われる。** 修正にはこのリポジトリ内のブランチが必要です。代わりにレビューを依頼するか、ブランチをこのリポジトリにプッシュしてください。
