# インシデント 概要

OneUptime のインシデントは、何かが壊れたときにチームが集まる拠点となる記録です。番号、タイトル、重大度、現在の状態、影響を受けるリソース、そして対応中にチームが書き残したものすべて — ノート、根本原因、修復手順、そして誰が何をしたかを追記のみで記録するフィードを持ちます。

モニターが赤くなっただけの出来事を、組織立った対応に変えるのがインシデントです。宣言すれば適切なオンコールローテーションが呼び出され、あらゆる変更の通知を受け取る所有者が追加され、Runbook が動き出します。そして — そうしたければ — 障害を公開ステータスページに掲載し、「もう把握していますか」と尋ねるチケットが顧客から届くのを止められます。

午前 3 時に手で宣言することもできますし、モニターの条件が一致した瞬間にモニターに宣言させることもできます。どちらの場合も、できあがるインシデントは同じオブジェクトで、ライフサイクルも同じ、最後に残る記録も同じです。

## ひと目でわかる要点

- **トップレベルの機能** — ダッシュボードの左ナビゲーションにある **インシデント**、URL は `/dashboard/{projectId}/incidents`。
- **初期状態は 3 つ** — **確認済み**、**承認済み**、**解決済み** が新規プロジェクトごとに作成されます。独自の状態を追加できますが、この 3 つは名前と色を変更できても削除はできません。
- **初期重大度は 3 つ** — **重大インシデント**、**主要インシデント**、**軽微なインシデント**。重大度は色と並び順を持つラベルであり、それ自体に振る舞いはありません。
- **入口は 4 つ** — **インシデントを宣言** ウィザード、**テンプレートから作成**、モニターの条件ルール、そして `POST /api/incident`。
- **番号はプロジェクト単位** — すべてのインシデントにインシデント番号が付き、既定では `#42`、独自のプレフィックスを設定すれば `INC-42` のように表示されます。
- **ノートは 2 種類** — チーム向けのプライベートノート(内部ノート)と、ステータスページ購読者向けのパブリックノート。
- **設定は プロジェクト設定 ではなく インシデント の下** — 状態、重大度、テンプレート、カスタムフィールド、各ルールエンジンはすべて **インシデント → 設定** と **インシデント → ルール** にあります。

## 主要な用語

このセクションのどのページにも出てくる言葉がいくつかあります。まずここを押さえてください。

| 用語                       | 意味                                                                                                                                 |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| **インシデント**           | 記録そのもの — タイトル、説明、重大度、現在の状態、影響を受けるリソース、そして対応中に書き込まれたすべて。                                    |
| **インシデントの状態**     | ライフサイクル上の位置。名前、色、`order`、そして意味を与えるフラグを持つプロジェクトスコープの行です。                                       |
| **インシデントの重大度**   | どれだけ深刻か。名前、色、`order` を持つプロジェクトスコープの行です。純粋な分類であり、特定の重大度を特別扱いする処理はありません。            |
| **インシデント番号**       | プロジェクトごとのカウンター。`#42`、あるいは設定したプレフィックスを付けて `INC-42` と表示されます。                                        |
| **影響を受けるリソース**   | インシデントに紐付けるモニター、ホスト、Kubernetes クラスター、Docker ホスト、サービスなどのインフラです。                                    |
| **パブリックノート**       | ステータスページの読者と購読者に向けて書く更新。ステータスページのタイムラインに表示されます。                                                |
| **プライベートノート**     | 対応チーム向けの内部ノート(`IncidentInternalNote` モデル)。ステータスページに届くことはありません。                                        |
| **所有者**                 | インシデントに責任を持つユーザーまたはチーム。作成時、ノート投稿時、状態変更時に通知を受け取ります。                                          |
| **インシデント フィード**  | インシデントの **概要** にある追記のみの活動タイムライン。状態変更、ノート、所有者の変更、ルール実行、通知を記録します。                       |
| **状態タイムライン**       | インシデントがどの状態に、いつ、どれだけの時間いたかの記録 — 各遷移の購読者通知ステータス付きです。                                          |

## すべてのプロジェクトに用意される 3 つの状態

プロジェクトを作成すると、OneUptime はちょうど 3 つのインシデント状態をこの順序で用意します。

| 状態             | 順序  | 色                 | 意味                                                                    |
| ---------------- | ----- | ------------------ | ------------------------------------------------------------------------- |
| **確認済み**     | 1     | 赤(`#fd625e`)    | 新しいインシデントが最初に置かれる状態。これが作成状態です。            |
| **承認済み**     | 2     | 黄(`#ffbf53`)    | 誰かがインシデントを引き受け、対応を始めています。                      |
| **解決済み**     | 3     | 緑(`#2ab57d`)    | インシデントは終わりました。解決するとステータスページから外れます。    |

名前はあくまでラベルです。実際に振る舞いを決めているのは、状態の行にある 3 つのブール値 — `isCreatedState`、`isAcknowledgedState`、`isResolvedState` です。各フラグを持つ状態は、プロジェクトごとに 1 つだけであることが前提になっています。

この区別は、聞こえる以上に重要です。

- `isCreatedState` は新しいインシデントがどこから始まるかを決めます。作成時に状態が明示的に選ばれていなければ、OneUptime はプロジェクトの作成状態を探してそれを使います。
- `isAcknowledgedState` と `isResolvedState` は、インシデントヘッダーの **Acknowledge** ボタンと **解決** ボタン、インシデントの **概要** にある 2 つの統計タイル、そしてサイドメニューの **アクティブなインシデント** 件数バッジを動かします。
- **アクティブなインシデント** の定義は「現在の状態が解決状態ではないこと」だけです。したがって、追加したカスタム状態は解決状態でない限りすべてアクティブ扱いになります。

**名前に注意してください。** 最初の初期状態の名前は **確認済み** ですが、製品内のいくつかの説明では今でもこれを作成状態と呼んでいます。プロジェクトの状態一覧で「Created」を探しているなら、それは **確認済み** という名前の行です。

独自の状態は **インシデント → 設定 → インシデントの状態** で追加できます。新しい状態は順序付きリストの末尾に追加され、ドラッグして並べ替えられます。フラグを持つ 3 つの状態は削除できません — OneUptime が拒否します — が、名前と色は変更できます。UI が状態名を動的に読み取っているのはそのためです。

順序は見た目の都合ではなく強制されます。インシデントは、現在の状態より順序が前にある状態へは移動できません。

詳細は [インシデントの状態と重大度](/docs/incidents/states-and-severities) にあります。

## すべてのプロジェクトに用意される 3 つの重大度

新しいプロジェクトには重大度も 3 つ用意されます。

| 重大度                 | 順序  | 色                   | 意味                                                        |
| --------------------- | ----- | ------------------ | ---------------------------------------------------------- |
| **重大インシデント**   | 1     | えんじ(`#b70400`) | 顧客への影響が非常に大きく、即時対応が必要。               |
| **主要インシデント**   | 2     | 赤(`#fd625e`)     | 影響が大きく、通常は即時対応が必要。                       |
| **軽微なインシデント** | 3     | 黄(`#ffbf53`)     | 影響が小さく、通常は業務時間内に対応。                     |

初期設定の説明文の全文は [インシデントの状態と重大度](/docs/incidents/states-and-severities) にあります。

重大度が持つのは `name`、`description`、`color`、`order` だけです。フラグはなく、「重大インシデント」を他の行と違う扱いにするコードパスもありません。重大度は人間がトリアージするための手段であり、オンコールルールを書くときのマッチ条件としても使えます — ただし重大度を選ぶこと自体は誰の呼び出しも起こしません。

重大度の編集と追加は **インシデント → 設定 → インシデントの重大度** で行います。

## インシデントの一生

### 1. 宣言される

4 つの経路が、同じオブジェクトにたどり着きます。

- **手動で** — インシデント一覧から **インシデントを宣言** をクリックします。**新しいインシデントを宣言** ウィザードが開き、**インシデントの詳細**、**影響を受けるリソース**、**インシデントの役割**、**オンコール**、**もっと** の 5 ステップに分かれています。
- **テンプレートから** — **テンプレートから作成** をクリックし、保存済みの **インシデントテンプレート** を選びます。テンプレートはタイトル、説明、重大度、初期状態、リソース、オンコールポリシー、所有者、ラベルを事前入力します。
- **モニターから** — 「インシデントを宣言する」トグルを有効にしたモニターの条件ルールが、フィルターに一致した瞬間に自動でインシデントを作成します。ここでのタイトルと説明は `{{variable}}` によるテンプレート化に対応しています。
- **API 経由で** — API キーを付けた `POST /api/incident`。`declaredAt`、作成状態、インシデント番号はサーバーが埋めてくれます。

フィールドごとの解説は [インシデントの宣言](/docs/incidents/declaring-incidents) を参照してください。

### 2. 適切な人に伝わる

作成時、OneUptime は設定済みの自動化を実行します — ラベルルール、オンコールルール、所有者ルール、Runbook ルールです。インシデントに紐付いたオンコール勤務ポリシーは、手動で付けたもの、テンプレート由来のもの、一致したオンコールルールが合流させたもののいずれであっても、並行して実行されます。

所有者にはメール、SMS、電話、プッシュ、WhatsApp で通知が届きます — ただし各ユーザー自身の通知設定に従います。所有者が 1 人もいないインシデントでは、通知は破棄されずプロジェクトの所有者にフォールバックします。

インシデントがステータスページに表示されていて購読者通知が有効なら、購読者にも伝わります。通知は cron 駆動で毎分実行されるため、即時送信ではなく最大 1 分程度の遅れがあると考えてください。

### 3. チームが対応する

対応者はインシデントを承認し、影響を受けるリソースを紐付け、Runbook を実行し、インシデントの役割を割り当て、わかったことを書き留めていきます — チーム向けのプライベートノート、顧客向けのパブリックノート、そして状況が見えてきたら **根本原因** と **修復** のページです。彼らの行動はすべて **概要** ページの **インシデント フィード** に残ります。

### 4. 解決される

**解決** をクリックすると、インシデントは解決状態に移り、状態タイムラインに記録され、経過時間の計測が止まり、掲載されていたステータスページのアクティブ欄から外れます。そのために他の何かを変える必要はありません — ステータスページのクエリが見ているのは解決状態のフラグだけです。

そのあとでポストモーテムを書き、必要ならステータスページに公開できます。

## ダッシュボードのどこにインシデントがあるか

左ナビゲーションで **インシデント** を開きます。サイドメニューはセクションに分かれています。

| セクション    | そこで行うこと                                                                                                                                                     |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **概要**      | **すべてのインシデント** と **アクティブなインシデント** — 後者には解決状態にないインシデント数を示す赤いバッジが付きます。                                     |
| **エピソード**| インシデントエピソード。独自のページを持つ別のグループ化機能です。                                                                                              |
| **AI**        | **調査** と **修復** — 自動調査と自動修復の設定です。                                                                                                          |
| **ワークスペース** | インシデント向けの **Slack** と **Microsoft Teams** の接続です。                                                                                            |
| **ルール**    | 各ルールエンジン — **グループ化ルール**、**オンコールルール**、**所有者ルール**、**Runbook ルール**、**プライバシールール**、**ラベルルール**、**SLA ルール**、**Reminder Rules**。 |
| **設定**      | **インシデントの状態**、**インシデントの重大度**、**インシデントテンプレート**、**ノートテンプレート**、**ポストモーテムテンプレート**、**カスタムフィールド**、**インシデントの役割**、**その他の設定**。 |

**ルール** と **設定** は既定で折りたたまれています — このドキュメントの残りが参照するページを見つけるには展開してください。インシデントの設定は プロジェクト設定 の下にはなく、すべてここにあります。

インシデント一覧そのものには **インシデント番号**、**タイトル**、**状態**、**重大度**、**影響を受けるリソース**、**宣言済み**、**期間**、**ラベル**、**所有者** が表示され、複数をまとめて閉じるための **状態を変更** 一括アクションがあります。

## インシデントの各ページに何があるか

インシデントを開くと、左サイドメニューがこのように分かれています。

- **概要** — **インシデントの詳細** カード(タイトル、重大度、ラベル、インシデント番号、宣言日時、宣言者、オンコールポリシー)、**影響を受けるリソース** カード、そして **インシデント フィード**。その上には承認までの時間、解決までの時間、合計 **期間** の統計タイルが並びます。
- **状態タイムライン** — インシデントが経てきたすべての状態と、各遷移の **開始**、**終了**、**期間**、購読者通知ステータス。**原因を表示** と **ログを表示** が、その変更が起きた理由を説明します。
- **SLA** — このインシデントの SLA トラッキング。
- **説明**、**根本原因**、**修復** — 3 つの Markdown ページ。ステータスページに表示されるのは説明です。
- **Runbook** — このインシデントに紐付いた Runbook の実行。
- **ポストモーテム** — 事後の書き起こし。必要ならステータスページに公開できます。
- **役割**、**オンコール実行**、**所有者** — 誰が対応しているか、どのポリシーが動いたか、誰に通知が行くか。
- **通知ログ**、**AI ログ**、**監査ログ** — 何が送られ、何が変わったか。
- **公開ノート** と **プライベートノート** — サイドメニューの **ノート** セクションの下にあります。
- **カスタムフィールド**、**設定**、**インシデントを削除** — **詳細** の下です。**設定** ページには **ステータスページに表示**、**プライベートインシデント**、**Reminders** カードがあります。

コラボレーション用のページは [インシデントのメモ、オーナー、フィード](/docs/incidents/notes-owners-and-feed) で詳しく扱います。

## インシデントと OneUptime の他の機能との関係

- **モニターが問題を見つけ、インシデントが記録する。** モニターの条件ルールはインシデントを自動宣言でき、タイトル、重大度、オンコールポリシー、所有者、ラベル、修復ノートを事前入力します。そこで使える変数は [インシデント & アラート テンプレート](/docs/monitor/incident-alert-templating) を参照してください。
- **呼び出しはオンコールポリシーが行う。** ポリシーは宣言ウィザードの **オンコール** ステップ、テンプレート、あるいは **インシデント → ルール → オンコールルール** で紐付けます。一致したルールはすべて発火し、実行される集合は全一致分と直接紐付けたものの和集合から重複を除いたものになります。
- **やるべきことは Runbook が示す。** Runbook ルールは一致するインシデントの作成時に手順を自動で紐付け、対応者はインシデントから手動で開始することもできます。[Runbook 概要](/docs/runbooks/index) を参照してください。
- **顧客にはステータスページが伝える。** インシデントがステータスページのアクティブ一覧に載るのは、ページでインシデント表示が有効で、そのインシデントがステータスページに表示する設定になっていて、現在の状態が解決状態ではないときです。プライベートインシデントは、常に、どのステータスページからも隠されます。[ステータス ページ 概要](/docs/status-pages/index) を参照してください。
- **その周りをワークフローが自動化する。** **On Create Incident**、**On Update Incident**、**On Delete Incident** の各トリガーを使えば、インシデントのライフサイクルの上にノーコードの自動化を組めます。[ワークフロー 概要](/docs/workflows/index) を参照してください。
