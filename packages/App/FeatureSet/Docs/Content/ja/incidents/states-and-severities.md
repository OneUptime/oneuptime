# 状態と重大度

すべてのインシデントは 2 つの分類を持ちます。対応のどこにいるかを示す **状態** と、どれだけ痛いかを示す **重大度** です。ダッシュボード上では似て見えます — どちらもインシデント一覧に色付きのピルとして表示され、どちらも名前と色を変更できるプロジェクトスコープのリストです。しかし、果たしている役割はまったく違います。

状態は振る舞いを動かします。状態の行にある 3 つのブールフラグが、どのインシデントをアクティブと数えるか、インシデントヘッダーにどのボタンを出すか、SLA の計測をいつ止めるか、そしていつインシデントがステータスページから外れるかを決めます。重大度はそれ自体では何も動かしません — 影響を言い表すラベルであり、他のルールがマッチ条件として使えるものです。

どちらのリストもプロジェクト作成時に用意され、どちらも **インシデント → 設定** で編集します。インシデントのサイドメニューのこのセクションは既定で折りたたまれているので、探しに行く前に **設定** を展開してください。

## 状態は振る舞いを、重大度は意味を担う

`IncidentState` モデルは `name`、`description`、`color`、`order` に加えて、`isCreatedState`、`isAcknowledgedState`、`isResolvedState` の 3 つのブール値を持ちます。製品が状態に対して行うことはすべて、このブール値と `order` を見て決まります — 状態の名前を見ることはありません。**解決済み** を「クローズ」に改名しても何も壊れないのはこのためです。フラグは行と一緒に移動します。

`IncidentSeverity` モデルが持つのは `name`、`description`、`color`、`order` だけです。フラグはありません。OneUptime のどこにも、**重大インシデント** を **軽微なインシデント** と違う扱いにする処理はありません — 重大度が意味を持つのは、オンコールルールの **インシデント 重大度** マッチ条件のように、あなたが何かをそこに向けたときだけです。

押さえておきたい決まりがいくつかあります。

- **重大度は影響を伝えるために選ぶ** — インシデント一覧とインシデントの **概要** に表示され、インシデントを宣言するときの必須フィールドです。
- **状態は自分たちのプロセスを表すために選ぶ** — 実際にたどる対応の段階を、実際にたどる順序で並べます。
- **緊急度を状態に埋め込まない** — 「Critical」という名前の状態は誰も呼び出しません。それをするのは重大度とオンコールルールです。

## 初期設定の状態

プロジェクトと一緒に 3 つの状態がこの順序で作られます。この初期化は冪等です — 同じ名前の状態がまだ存在しないときにだけ追加されます。

| 状態             | `order` | フラグ                | 色        | 意味                                               |
| ---------------- | ------- | --------------------- | --------- | -------------------------------------------------- |
| **確認済み**     | `1`     | `isCreatedState`      | `#fd625e` | 新しいインシデントが置かれる状態。                |
| **承認済み**     | `2`     | `isAcknowledgedState` | `#ffbf53` | 誰かがインシデントを引き受けた状態。              |
| **解決済み**     | `3`     | `isResolvedState`     | `#2ab57d` | インシデントが終わり、アクティブに数えなくなる。  |

名前に注意してください。最初の状態は **確認済み** ですが、製品内のいくつかの説明では今でもこれを「作成」状態と呼んでいます。ドキュメントやツールチップが「作成状態」と言うとき、それは `isCreatedState` を持つ状態のことであり、新規プロジェクトでは **確認済み** です。

## 各状態フラグが実際にすること

| フラグ                | 役割                                                                                                                                                                                                 |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `isCreatedState`      | 誰も状態を選ばなかったときにインシデントが取る状態。プロジェクト内にこのフラグを持つ状態がなければ、インシデントの作成は失敗し、設定から作成用のインシデント状態を追加するよう促すエラーが出ます。 |
| `isAcknowledgedState` | **Acknowledge** ボタンと、インシデントの **概要** にある「<状態名> in」統計タイルを動かします。この状態への遷移時に、インシデントの SLA は応答済みとして記録されます。                              |
| `isResolvedState`     | **解決** ボタンと解決の統計タイルを動かし、**アクティブなインシデント** の一覧を定義し、ステータスページのアクティブ欄からインシデントを外します。SLA を解決済みにします。                          |

各フラグを持つ状態は、プロジェクトごとに 1 つだけであることが前提です — 参照処理は 1 行だけを取得します。フラグを持つ 3 つの状態は名前変更、色変更、並べ替えができますが、設定ページは削除を拒否し、作成・承認・解決の各状態を名指ししたエラーを表示します。

UI は状態名を動的に読み取るため、状態の名前を変えると表示も全体で変わります — 統計タイル、確認モーダルのタイトル、インシデント一覧のピルは、どれもその行に付けた名前に従います。

## 独自の状態を追加する

**インシデント → 設定 → インシデントの状態** へ行きます。このページは `order` の昇順に並んだ順序付きリストで、新しい状態は末尾に追加されます。行をドラッグすれば位置を変えられます。

**状態のフィールド:**

- **名前** — 必須、2 文字以上。プレースホルダーは「Investigating」のような例を示します。
- **説明** — 任意の自由記述。インシデントがこの状態にあるのはどんなときかを説明します。
- **色** — 必須。カラーピッカーから選び、`#fd625e` のような 16 進数の値として保存されます。

このフォームから 3 つのフラグを設定することはできません — フラグは初期設定の行に属します。したがって追加した状態はフラグなしの状態になり、計画に織り込んでおくべき影響が 2 つあります。

- **アクティブとして数えられます。** **アクティブなインシデント** は「現在の状態が解決状態ではない」と定義されているため、解決状態以外に追加したものはすべて、インシデントをアクティブ一覧とサイドバーの件数に残します。
- **遷移ボタンが汎用になります。** **Acknowledge** や **解決** ではなく、確認モーダルのタイトルは **Mark Incident as `<状態名>`** となり、送信ボタンは **Mark as `<状態名>`** になります。

よくある形は、承認状態と解決状態の間にトリアージや暫定対応の段階を挟むことです — 例えば「Mitigated」という新しい状態をドラッグして、**承認済み** の後、**解決済み** の前に置きます。

## 順序は表示の好みではなく、実際の制約

`order` カラムは、リストを描くときだけでなく、状態変更が書き込まれるときにも強制されます。

- **後戻りの遷移は拒否されます。** 現在の状態より順序が前にある状態へインシデントを移そうとすると、両方の状態を名指ししたエラーで失敗します。
- **現在の状態の再選択も拒否されます。** すでにその状態にあるインシデントを同じ状態に設定すると、「Incident state cannot be same as previous state.」で失敗します。
- **遡って追加した行が隣の行と重複することもできません。** その次に続く行と同じ状態のタイムライン行を挿入することも拒否されます。
- **ヘッダーのボタンは、フラグ付き状態の順序上の位置に従います。** **Acknowledge** と **解決** が提示されるかどうかは、順序で並べたリスト上で現在の状態がどこにあるかで決まります。解決状態より *後* に置いたカスタム状態では **解決** ボタンが決して表示されません。前に進む先が残っていないからです。

ですから状態を追加するときは、インシデントが本当に通過する位置に置いてください。順序を間違えると見た目が妙になるだけでなく、遷移そのものが不可能になります。

## 初期設定の重大度

プロジェクトと一緒に 3 つの重大度がこの順序で作られます。

- **重大インシデント**(`order` 1、`#b70400`)— 顧客への影響が非常に大きく、即時対応が必要な問題。全面的な障害やデータ漏洩など。
- **主要インシデント**(`order` 2、`#fd625e`)— 影響が大きく通常は即時対応が必要で、被害を抑える回避策があることもあります。重要なサブシステムの障害など。
- **軽微なインシデント**(`order` 3、`#ffbf53`)— 影響が小さく、通常は業務時間内に対応し、ほとんどの顧客は気付かないでしょう。アプリケーション性能のわずかな低下など。

重大度はインシデントを宣言するときに必須であり、モニターの条件内のインシデント定義それぞれにも必須です。したがって手動でも自動でも、すべてのインシデントは重大度を持って生まれます。宣言のフローは [インシデントの宣言](/docs/incidents/declaring-incidents)、モニター経由の経路は [インシデント & アラート テンプレート](/docs/monitor/incident-alert-templating) を参照してください。

## 重大度を編集する

**インシデント → 設定 → インシデントの重大度** へ行きます。状態のページと同じ形です — `order` で並んだ順序付きリスト、ドラッグで並べ替え、新しい重大度は末尾に追加され、フォームには **名前**、**説明**、**色** があります。

状態との違いは 2 つです。

- **削除のガードがありません。** 初期設定の 3 つを含め、どの重大度も削除できます。
- **引き継ぐフラグがありません。** 新しい重大度は初期設定のものとまったく同じに振る舞います — 色と位置を持つラベルです。

**プレースホルダーについての注意。** 重大度のフォームは状態のフォームの例文をそのまま流用しているため、ヒントは重大度ではなくインシデントの状態の話をしています。無視して、自分の重大度の名前と説明を書いてください。

重大度が説明以上の働きをする場所もあります。**インシデント → ルール → オンコールルール** では、ルールの **インシデント 重大度** フィールドがマッチ条件になります。「重大なものはすべてデータベースチームを呼び出す」を表現する方法が、そこに **重大インシデント** を並べることです — オンコールポリシーは重大度ではなくルールの側にあります。

## インシデントを状態間で動かす

インシデントの状態が変わる方法は 4 つあります。

- **ヘッダーのボタン。** インシデントを開きます。現在の状態が承認状態より前なら **Acknowledge** と **解決** が、その 2 つの間なら **解決** が表示されます。どちらも確認モーダル — **Acknowledge Incident** または **Resolve Incident** — を開き、そこでは **ノートテンプレートを選択**、**パブリックノート**、**ステータスページの購読者に通知** も選べます。
- **状態タイムライン。** インシデントの **状態タイムライン** ページから、**インシデントステータス**、**開始**、**ステータスページの購読者に通知** を指定して手動で行を追加します。
- **一括変更。** インシデント一覧には、複数のインシデントをまとめて動かす **状態を変更** 一括アクションがあります。
- **自動的に。** **インシデントを自動解決** を有効にしたモニター条件は、条件を満たさなくなった時点でそのインシデントを解決します。また API は `/api/incident-state-timeline` から状態を更新できます。

このいずれもタイムラインの行を書き込みます。状態変更は、頼まなくてもいくつかのことをします。インシデントフィードにエントリーを投稿し、Incident Commander がまだいなければ割り当て、SLA の計測を更新します。解決済みのインシデントを再オープンすると、その時点から新しい SLA レコードが始まります。

## 状態タイムライン

インシデントのサイドメニューにある **状態タイムライン** ページは、インシデントが経てきたすべての状態の監査証跡です。そのページのカードのタイトルは **ステータスタイムライン** で、新しい順に並びます。

**列:**

- **インシデントステータス** — 状態の名前と色を持つ色付きのピル。
- **開始** — インシデントがこの状態に入った時刻。
- **終了** — 抜けた時刻。現在の状態には `Currently Active` と表示されます。
- **期間** — その状態で過ごした時間。現在の状態については今この瞬間までを数えます。
- **購読者通知ステータス** — この変更に対するステータスページ通知が送信されたか、スキップされたか、まだ保留かを示します。**詳細** リンクが付き、送信に失敗した場合は **Retry** アクションも表示されます。

**行のアクション:**

- **原因を表示** — その状態変更と一緒に記録された Markdown を表示する **根本原因** モーダルを開きます。
- **ログを表示** — ステータスが変わった理由を説明するモーダルを開き、**インシデント状態ログ** ビューアーを表示します。

タイムラインの行は作成と削除ができますが、編集はできません。間違った行を削除するとインシデントの履歴を書き換えることになるので、日常的な片付けの手段ではなく、訂正のための道具として扱ってください。

## アクティブなインシデント一覧

**インシデント → アクティブなインシデント** は、シフト中に見ておく一覧です。その定義はたった 1 つの条件 — インシデントの現在の状態が `isResolvedState` が false の状態であること。それ以外は一切考慮されません。重大度も、経過時間も、誰かが承認したかどうかも関係ありません。

サイドメニューの項目には同じクエリを使った赤い件数バッジが付くので、バッジと一覧は必ず一致します。見るものがないときは、ページがそう伝えます。

実務上の帰結として、追加したカスタム状態はインシデントをこの一覧に残します。たいていはそれが望みどおりです — 「Mitigated」は「完了」ではありません — が、バッジが消えるのはインシデントが実際に解決状態に到達したときだけだ、ということでもあります。

## 状態変更をステータスページ購読者に伝える

状態変更はステータスページの購読者にメールを送れますが、いくつもの関門を通ります。ここを理解しておくと、「なぜ誰にも通知が行かなかったのか」の調査を大幅に減らせます。

通知はタイムラインの行ごとに **ステータスページの購読者に通知**(`shouldStatusPageSubscribersBeNotified`)で要求されます。これは状態変更モーダルと手動のタイムラインフォームにあるチェックボックスです。オフの場合、行はスキップ扱いのステータスと理由付きで保存されます。オンの場合、行はキューに入り、バックグラウンドジョブが拾います — ジョブは毎分実行されるため、配信は速いものの瞬時ではありません。

**キューに入った行は、次のいずれかに当てはまるとスキップされます。**

- **新しい状態が作成状態である。** 購読者にはインシデント宣言時にすでに伝えているので、最初のタイムライン行は 2 通目を意図的に送りません。
- **インシデントにモニターが紐付いていない。** リソースがなければ、インシデントを対応付けるステータスページもありません。
- **インシデントがステータスページに表示されない**(`isVisibleOnStatusPage` がオフ)。
- **ステータスページ側でインシデント表示がオフ**(`showIncidentsOnStatusPage` がオフ)。これはステータスページごとの設定です — 同じモニターを載せている他のページには通知が届きます。

**もう 1 つ結果を変えるもの。** 状態変更モーダルに **パブリックノート** を書き込むと、そのタイムライン行はキューではなく通知済みとして記録されます。購読者に届くのはノートそのものなので、2 通ではなく 1 通になります。素の状態変更メッセージの裏にあるイベントタイプは `Subscriber Incident State Changed` です。

誰が受け取るのか、テンプレートがどう選ばれるのかは [購読者とお知らせ](/docs/status-pages/subscribers) を参照してください。

## インシデントをステータスページに出さない

インシデントが公開ページに載るかどうかは 3 つの別々の要素が決め、その 3 つすべてが真である必要があります。

- ステータスページ自体の **インシデントを表示**(`showIncidentsOnStatusPage`)。
- インシデント側の **ステータスページに表示**(`isVisibleOnStatusPage`)— インシデントの **設定** ページにあるトグルです。既定は true で、宣言ウィザードにはありません。モニターの条件からは **ステータスページにインシデントを表示** で設定できます。
- **現在の状態が解決状態でないこと。** これがインシデントをアクティブ欄から外すものです。ステータスページのクエリは、現在の状態が未解決のいずれかであるインシデントを取得します。何かをアーカイブしたりクローズしたりするのではありません — 解決すれば、履歴へ移ります。

**プライベートインシデントは決して表示されません。** **プライベートインシデント** をオンにすると、上記のトグルにかかわらずすべてのステータスページから隠され、所有者に加えてプロジェクト管理者と所有者だけに限定されます。

解決済みの履歴をページがどれだけ保持するかは、インシデントではなくステータスページの設定です。ページ上のモニターがどのインシデントを表示対象にするかは [ステータス ページのリソースとグループ](/docs/status-pages/resources-and-groups) を参照してください。
