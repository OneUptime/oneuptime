# インシデントの設定と自動化

インシデントの設定は **プロジェクト設定** の中にはありません。Incidents の製品エリアそのものの中、**インシデント → 設定** と **インシデント → ルール** にあり、URL は `/dashboard/{projectId}/incidents/settings/` で始まります。インシデントテンプレートやカスタムフィールドを求めて **プロジェクト設定** を探し回っていたなら、見つからなかった理由はこれです。

インシデントのサイドメニューにある **ルール** と **設定** はどちらも既定で折りたたまれているため、以下の項目を表示するにはまず展開してください。ここにあるものはすべてプロジェクト単位です — テンプレート、ロール、カスタムフィールド、ルールは 1 つのプロジェクトに属し、そこで宣言されるすべてのインシデントに適用されます。

このページはその設定のリファレンスです — 各ページに何があるのか、そしてそのうちどれがインシデント作成の瞬間に自動で動くのかをまとめます。

## インシデント設定がある場所

左ナビゲーションで **インシデント** を開き、サイドメニュー下部の **設定** を展開します。

| ページ                       | そこでできること                                                                                     |
| ---------------------------- | ---------------------------------------------------------------------------------------------------- |
| **インシデントの状態**       | インシデントがたどる状態の追加、名前変更、色変更、並べ替え。                                        |
| **インシデントの重大度**     | 重大度レベルの追加、名前変更、色変更、並べ替え。                                                    |
| **インシデントテンプレート** | インシデント一式を事前入力 — タイトル、説明、リソース、オンコールポリシー、所有者、ラベル。         |
| **ノートテンプレート**       | パブリックノートとプライベートノートで使い回せる定型文。                                            |
| **ポストモーテムテンプレート** | 使い回せるポストモーテムの構成。                                                                   |
| **カスタムフィールド**       | すべてのインシデントに表示される追加フィールドを定義します。                                        |
| **インシデントの役割**       | インシデントコマンダーなど、対応者に割り当てる役割を定義します。                                    |
| **その他の設定**             | インシデントとインシデントエピソードの番号プレフィックス。                                          |

**インシデントの状態** と **インシデントの重大度** は [インシデントの状態と重大度](/docs/incidents/states-and-severities) で詳しく扱っています — このページはその続き、**インシデントテンプレート** から始めます。

**ルール** を展開すると、さらに 8 つのページが現れます。**グループ化ルール**、**オンコールルール**、**所有者ルール**、**Runbook ルール**、**プライバシールール**、**ラベルルール**、**SLA ルール**、**Reminder Rules** です。これらはこのページの後半で扱います。

## インシデントテンプレート

インシデントテンプレートは、保存しておくインシデントの骨組みです。決済クラスタが揺らぐたびに同じタイトル、同じモニターの並び、同じオンコールポリシーを打ち直す代わりに、一度保存しておいてそこから宣言します。

**インシデント → 設定 → インシデントテンプレート**（`/dashboard/{projectId}/incidents/settings/templates`）を開きます。カードのタイトルは **インシデントテンプレート** です。作成すると 6 ステップのウィザードが案内します。

- **テンプレート情報** — **テンプレート名** と **テンプレートの説明**。これはテンプレート自体の名前であり、インシデントには表示されません。
- **インシデントの詳細** — **タイトル**、**説明**（Markdown）、**インシデントの重大度**、**初期インシデント状態**。**初期インシデント状態** は任意で、初期値は空です。選択肢は状態の順序で並びます。空のままにすると、このテンプレートから作られたインシデントはプロジェクトの作成用の状態に入ります。
- **影響を受けるリソース** — インシデントに紐付けるモニター、ホスト、クラスタ、サービスと、**Change Monitor Status to**。
- **オンコール** — **オンコールポリシー**。このテンプレートから作られたインシデントが宣言されたときに実行するポリシーです。
- **所有者** — **所有者 - チーム** と **所有者 - ユーザー**。
- **ラベル** — **ラベル**。

押さえておきたい点をいくつか。

- テンプレート一覧に出るのは **名前** と **説明** だけです。行はその場では編集も削除もできません — 変更するにはテンプレート（`/dashboard/{projectId}/incidents/settings/templates/{modelId}`）を開きます。
- テンプレートは JSON のインポートとエクスポートに対応しているので、プロジェクト間で移せます。
- 空の状態では "No incident templates found." と表示されます。

### テンプレートが適用される仕組み

適用の経路は 2 つあり、どちらも同じ振る舞いをします。

- **ダッシュボードから** — インシデント一覧の **テンプレートから作成** ボタンが **インシデントテンプレートを選択** のピッカーを開きます。宣言ページはクエリ文字列パラメータ `incidentTemplateId` からテンプレートを読み取り、テンプレートの内容と所有者チーム・所有者ユーザーでフォームを事前入力します。
- **API から** — `POST /api/incident` に `createdIncidentTemplateId` を渡すと、サーバーがテンプレートからインシデントを埋めます。

肝心なのはマージのルールです。**テンプレートが埋めるのは、あなたが未指定にしたフィールドだけです**。タイトル、説明、インシデントの重大度、初期インシデント状態、**Change Monitor Status to** の裏にあるモニターステータス、モニター、ホスト、Kubernetes クラスタ、Docker ホスト、Podman ホスト、サービス、オンコールポリシー、ラベルがテンプレートからコピーされるのは、呼び出し側やフォームが何も指定しなかったときだけです。明示的に設定した値は必ず優先されます。

**空の状態のダイアログは間違った場所を指しています。** テンプレートがまだ 1 つもない状態で **テンプレートから作成** を押すと、**No Incident Templates** というダイアログが出ます。その文面は Project Settings を指していますが、ボタンの遷移先は **インシデント → 設定 → インシデントテンプレート** です — こちらが本当の場所です。

## ノートテンプレート

ノートテンプレートは、インシデント更新のための定型文を対応者に渡すものです。おかげで午前 3 時のステータスページ更新を、半分寝ている人がゼロから書かずに済みます。

**インシデント → 設定 → ノートテンプレート**（`/dashboard/{projectId}/incidents/settings/note-templates`）を開きます。カードのタイトルは **インシデント用のパブリックまたはプライベートノートテンプレート** — 1 つのライブラリが両方のノート種別を賄います。作成フォームは 2 ステップです。

- **テンプレート情報** — **テンプレート名** と **テンプレートの説明**。どちらも必須です。
- **メモの詳細** — ノート本文そのもの。Markdown で、必須です。

インシデントテンプレートと同じく、行は作成と表示のためのもので、その場では編集できません。変更するにはテンプレートを開きます。

ノートテンプレートは実際に必要になる場所に現れます。**Acknowledge Incident** と **Resolve Incident** の確認ダイアログには、どちらも **パブリックノート** フィールドの隣に **ノートテンプレートを選択** があります。パブリックノートとプライベートノートの違いは [インシデントのメモ、オーナー、フィード](/docs/incidents/notes-owners-and-feed) を参照してください。

## ポストモーテムテンプレート

ポストモーテムテンプレートは、インシデント後に書くレポートの骨組みです — 自分たちの見出し、問いかけ、いつも確認する質問をまとめておけば、プロジェクト内のどのレビューも同じ形になります。

**インシデント → 設定 → ポストモーテムテンプレート**（`/dashboard/{projectId}/incidents/settings/postmortem-templates`）を開きます。カードのタイトルは **ポストモーテムテンプレート** です。作成フォームは 2 ステップです。

- **テンプレート情報** — **テンプレート名** と **テンプレートの説明**。どちらも必須です。
- **事後分析の詳細** — **事後分析テンプレート**、つまり本文そのもの。Markdown で、必須です。

適用するのは設定画面からではなく、インシデントからです。インシデントを開き、サイドメニューで **ポストモーテム**（`/dashboard/{projectId}/incidents/{incidentId}/postmortem`）を選び、**テンプレートを適用** を使います。**事後分析テンプレートを適用** ダイアログが開き、**テンプレートを選択** のドロップダウンからひとつ選ぶと、その本文が **事後分析ノート** のエディタに読み込まれます。保存する前にそこで編集します。インシデントエピソードにも同じ **ポストモーテム** ページがあり、同じテンプレートライブラリを使います。

## カスタムフィールド

カスタムフィールドを使うと、独自のメタデータをすべてのインシデントに持たせられます — 社内サービス名、変更チケットの参照、顧客ティアなど。

**インシデント → 設定 → カスタムフィールド**（`/dashboard/{projectId}/incidents/settings/custom-fields`）を開きます。ページのタイトルは **インシデントのカスタムフィールド** です。定義ごとに次の項目があります。

- **フィールド名** — 必須で、2 文字以上。プレースホルダーは `internal-service` のようなスラッグ風の名前を勧めています。
- **フィールドの説明** — 任意。
- **フィールドタイプ** — 必須。データの入力方法を決めます。ドロップダウン系のタイプでは選択肢の指定も必要です。
- **ドロップダウンのオプション** — ドロップダウンに並ぶ値。それぞれに色を付けることもできます。

定義は専用のモデルに、値はインシデント自身の `customFields` カラムに保存されます。個々のインシデントでは、サイドメニューの **カスタムフィールド**（`/dashboard/{projectId}/incidents/{incidentId}/custom-fields`）から値を入力します。

**知っておく価値のある穴がひとつ。** インシデントのカスタムフィールド定義は、インシデント系のモデルの中で唯一ワークフロートリガーを持ちません — 後述のワークフローの節を参照してください。

## インシデントの役割

インシデントの役割は、対応中に人に割り当てる名前付きの持ち場です。**インシデント → 設定 → インシデントの役割**（`/dashboard/{projectId}/incidents/settings/roles`）で定義します。カードの説明では、例としてインシデントコマンダーとレスポンダーが挙げられています。

役割はあくまで定義です。人を割り当てるのはインシデントごと — 宣言ウィザードには **インシデントのロールを割り当てる** フィールドを持つ **インシデントの役割** ステップがあり、各インシデントのサイドメニューにも **役割** ページがあります。

## 番号プレフィックス

インシデントにはそれぞれ番号が付きます。既定では `#42` のように表示されます。チームが口頭で「INC-42」と呼んでいるなら、製品にもそう表示させましょう。

**インシデント → 設定 → その他の設定**（`/dashboard/{projectId}/incidents/settings/more`）を開きます。カードは **番号プレフィックス** で、プロジェクト上の 2 つのフィールドを持ちます。

- **インシデント番号のプレフィックス** — 最大 20 文字、プレースホルダーは `INC-`。設定するとインシデント `#42` は `INC-42` と表示されます。
- **インシデントエピソード番号のプレフィックス** — インシデントエピソード番号に対する同じ仕組み。プレースホルダーは `IE-`。

どちらも空のままにすれば既定の `#` プレフィックスが使われ、未設定のフィールドは `# (default)` と表示されます。**更新** で保存します。プレフィックス付きの値はインシデントの `incidentNumberWithPrefix` に保存され、インシデント一覧とインシデントのヘッダーはこれを表示します。

## インシデント作成時に実行されるルール

**インシデント → ルール** には 8 つのルールエンジンがあります。どれも仕事は同じ — インシデントが作られた瞬間にそれを見て、条件に合えば動く — のですが、何をするか、そして複数のルールが一致したときにどう解決するかが異なります。

- **グループ化ルール** — 関連するインシデントをエピソードにまとめます。ルールは優先度順に評価され、優先度の数値が小さいものが先です。
- **オンコールルール** — 一致したインシデントに対してオンコール当番ポリシーを実行します。詳しくは後述します。
- **所有者ルール** — 所有者を自動で割り当てます。
- **Runbook ルール** — インシデントが一致したときに [Runbook](/docs/runbooks/index) を開始します。
- **プライバシールール** — 一致したインシデントをプライベートにするかどうかを決めます。
- **ラベルルール** — ラベルを自動で付けます。
- **SLA ルール** — 応答時間と解決時間を追跡します。ルールは順序どおりに評価され、順序の数値が小さいものが先です。
- **Reminder Rules** — インシデントが未解決のあいだ、インシデントの所有者に定期的にリマインドします。ルールは順序どおりに評価され、最初に一致したルールが採用されます。

**順序の扱いは一様ではありません。** グループ化ルール、SLA ルール、Reminder Rules は順序で評価されます。オンコールルールはそうではなく、一致したルールがすべて発火します。1 つのモデルが 8 つすべてに当てはまると考えないでください。

**オンコールルール**、**所有者ルール**、**ラベルルール**、**プライバシールール** の各ページはタブ構成です — **Incident Rules** タブと **Episode Rules** タブがあり、それぞれ独自のテーブルを持ちます。エピソードを狙っているのでない限り、**Incident Rules** タブを設定してください。**グループ化ルール**、**Runbook ルール**、**SLA ルール**、**Reminder Rules** は単一のテーブルです。

## インシデントのオンコールルール

**インシデント → ルール → オンコールルール**（`/dashboard/{projectId}/incidents/settings/on-call-rules`）は、ページングを自動化する場所です。カード **インシデントオンコールルール** の説明にあるとおり、一致するインシデントが作られたときにオンコール当番ポリシーを自動実行するルールを扱います。ページには **Incident Rules** と **Episode Rules** の 2 つのタブがあります。

作成フォームは 3 ステップです。

- **基本情報** — **名前**（プレースホルダーは、DB のインシデントならデータベースチームを呼び出す、といった例を示しています）、**説明**、**有効** トグル。一覧にはルールごとに緑の **有効** か赤の **無効** のピルが表示されます。
- **一致条件** — **モニター**、**インシデント 重大度**、**インシデントのラベル**、**モニターラベル**、そしてインシデントのタイトル、インシデントの説明、モニター名、モニターの説明に対する大文字小文字を区別しない正規表現フィールド。
- **オンコールポリシー** — このルールが実行するポリシー。

### 一致の解決の仕方

このページ自体に書かれているルールは、頭に入れておく価値があります。

- ルールが一致するのは、入力した条件が **すべて** 通ったときだけです。空のままの条件はスキップされ、不一致にはなりません。
- 1 つのリスト条件の中 — **モニター**、**インシデント 重大度**、**インシデントのラベル**、**モニターラベル** — では、いずれかに一致すれば一致とみなされます。
- パターンのフィールドは大文字小文字を区別しない正規表現です。
- **一致したルールはすべて発火します。** 優先度もショートサーキットもありません。
- 実際に実行されるポリシーの集合は、一致したすべてのルールのポリシーに、手動またはテンプレートでインシデントに紐付けられたポリシーを加えた和集合です。重複は除かれるので、各ポリシーの実行は多くても 1 回です。

重大度が一致条件として使えるのはここだけです。インシデントの重大度にオンコールのフィールドはありません — 「重大インシデント」を選んだだけでは誰も呼び出されません。重大度でページングを動かしたいなら、それに一致するオンコールルールを書いてください。

## オンコールポリシーを直接紐付ける

ルールだけが手段ではありません。どのインシデントも自分専用のオンコールポリシーの一覧を持っており、宣言ウィザードの **オンコール** ステップと、インシデントテンプレートの **オンコール** ステップにある **オンコールポリシー** フィールドがそれです。フィールドの説明にはっきり書かれているとおり、これはこのインシデントが作られたときに実行するオンコール当番ポリシーです。

インシデントが作られると、OneUptime はラベルルール、次にオンコールルール（一致したポリシーをインシデントの一覧にマージします）、次に Runbook ルールを実行します。そして出来上がった一覧が空でなければ、その中のポリシーがすべて実行されます。実行は並行に走り、それぞれ独立に決着するので、1 つのポリシーが失敗しても他は止まりません。各実行には、きっかけとなったインシデントと、インシデント作成の通知イベントタイプがタグ付けされます。

何が起きたかを確認するには、インシデントを開いてサイドメニューの **オンコール実行**（`/dashboard/{projectId}/incidents/{incidentId}/on-call-policy-execution-logs`）を選びます。

## ワークフローからインシデントを動かす

インシデント向けのワークフロートリガーは手書きではありません — OneUptime がデータモデルから生成するので、インシデント系のモデルはどれも **On Create X**、**On Update X**、**On Delete X** のコンポーネントを持ち、名前はモデルの単数形から付けられます。代表格の 3 つは **On Create Incident**、**On Update Incident**、**On Delete Incident** で、`/dashboard/{projectId}/workflows` の **コンポーネントを追加** パネルの **インシデント** カテゴリにあります。

同じ生成の仕組みで、設定そのもののトリガーも手に入ります。**On Create Incident State**、**On Update Incident Severity**、**On Create Incident Template**、**On Create Incident Note Template**、**On Create Incident State Timeline**、**On Create Incident Public Note**、**On Create Incident Internal Note**、**On Create Incident On-Call Rule**、**On Create Incident Role**、**On Create Incident Member** などです。各モデルには対応するアクションコンポーネント — **Find One Incident**、**Create One Incident**、**Update One Incident**、**Delete One Incident** とその複数行版 — も付くので、似た名前のトリガーとアクションが同じカテゴリに並びます。**On Create Incident** はワークフローを始動させ、**Create One Incident** はインシデントを起票します。

これらを組むときに効いてくる細かい点をいくつか。

- **On Update X** は任意の **Listen on** 引数を取り、特定のフィールドに触れた更新だけにトリガーを絞れます。空のままなら、どんな変更でも発火します。どのフィールドが変わったかの記録がない更新が届いた場合、フィルターはスキップされ、ワークフローはそのまま実行されます。
- **On Create X** と **On Update X** はどちらも必須の **Select Fields** 引数を取ります。**On Delete X** は引数を取りません。
- 3 つとも出力ポートは **成功** の 1 つだけで、いずれも ID 引数を受け取れるので、1 件のレコードに対して手動でワークフローを実行できます。
- 名前はテーブル名ではなくモデルの単数形から付きます。テーブル名風ではなく **On Create Incident Team Owner** や **On Create Incident User Owner** という名前になっているのはこのためです。
- インシデントのカスタムフィールド定義にはトリガーがありません。このモデルだけが、インシデント系でワークフローを無効化されています。

ワークフローの残りの部分を組み立てるには、[ワークフローを作成する](/docs/workflows/authoring) と [ワークフロー 変数](/docs/workflows/variables) を参照してください。
