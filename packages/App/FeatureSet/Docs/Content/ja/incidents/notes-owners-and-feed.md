# ノート、所有者、フィード

インシデントは、対応している間ずっと書き物を溜めていきます。その一部は顧客のためのもの — 02:14 にステータスページへ出す、まずいデプロイを見つけたという更新です。残りはチームのためのもの — 誰かが貼り付けたスタックトレース、ようやく意味が通ったグラフ、フェイルオーバーするという判断です。

OneUptime はこの 2 つの読み手を分けて扱います。**公開ノート** はステータスページに公開され、購読者に通知できます。**プライベートノート**(`IncidentInternalNote` モデル)はダッシュボードの中に留まります。その両方の下に、インシデントに起きたことをすべて記録する追記のみのタイムライン **インシデント フィード** と、誰に知らせるかを決める **所有者** の一覧があります。

これらはすべてインシデントの左サイドメニューにあります — **ノート → 公開ノート**、**ノート → プライベートノート**、そして **チーム → 所有者** です。フィードはインシデントの **概要** ページにあります。

## パブリックノートとプライベートノートの違い

2 つのノートはダッシュボード上では似て見えますが、振る舞いはまったく違います。

- **パブリックノート** — `IncidentPublicNote` モデルで、インシデントのタイムラインの一部としてステータスページに提供されます。自分で設定できる **投稿日時** と、**ステータスページの購読者に通知** チェックボックスを持ちます。
- **プライベートノート** — `IncidentInternalNote` モデルです。ステータスページアプリはこれを一切読みません。投稿日時のフィールドもなく(一覧は `createdAt` で記録・並べ替えされます)、購読者関連のフィールドもないため、プライベートノートが購読者通知を引き起こすことはありえません。

**「プライベート」の実際の意味。** これは「ステータスページに公開しない」という意味であって、「見られる人を絞る」という意味ではありません。両方のノートは同じ読み取り権限を共有するので、インシデントを読める人は誰でもそのプライベートノートを読めます。インシデントそのものを見られる人を制限したい場合は、インシデント側の **プライベートインシデント** フラグ(`isPrivate`)を使ってください。これはインシデントをすべてのステータスページから隠し、所有者ユーザー、所有者チームのメンバー、プロジェクト管理者と所有者だけに限定します。

**所有者は両方を見ます。** 所有者通知のジョブはパブリックノートとプライベートノートをまとめて取得します。プライベートノートは購読者に対してプライベートなのであって、対応している人たちに対してではありません。

| やりたいこと                                                | 選ぶもの             |
| ------------------------------------------------------ | ---------------- |
| 分かっていることと次に分かる時期を顧客に伝える            | **パブリックノート**   |
| すでに別の場所で出した更新を遡って記録する                | **パブリックノート**   |
| 仮説、実行したコマンド、行き止まりを書き留める            | **プライベートノート** |
| ヒープダンプや社内ダッシュボードのスクリーンショットを添える | **プライベートノート** |

## パブリックノートを投稿する

インシデントのサイドメニューで **ノート → 公開ノート** を開き、ノートを作成します。カードには、ここに書いた内容がステータスページに表示されることが説明されており、空の状態では、このインシデントにはまだパブリックノートが作成されていないと表示されます。

| フィールド                          | 用途                                                                                                                  |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| **パブリックインシデントノート**    | 本文、Markdown で書きます。必須。フォームは、このノートがステータスページに表示されることを伝え、チートシートを案内します。 |
| **添付ファイル**                    | ステータスページで購読者に共有されるファイル。任意。                                                                  |
| **ステータスページの購読者に通知**  | チェックボックスで、既定はオン。静かに公開したいときはオフにします。                                                  |
| **投稿日時**                        | 必須の日時。既定は現在時刻で、あなたの現在のタイムゾーンで表示されます。                                              |

**投稿日時こそがノートの本当のタイムスタンプです。** ステータスページはパブリックノートを、入力した時刻ではなく `postedAt` で並べて表示します — ですから 40 分前に送った更新を後からステータスページに反映するなら、**投稿日時** を実際に起きた時刻に設定してください。API 経由で投稿日時なしのノートが届いた場合は、OneUptime が現在時刻を記録します。

一覧には各ノートの書き手、**投稿日時**、レンダリングされた Markdown と添付ファイル、そして **購読者通知ステータス** 列が表示されます。**作成者**、**ノート**、**作成日** で絞り込めます。

## プライベートノートを投稿する

**ノート → プライベートノート** は意図的にもっと素っ気ない作りです。フィールドは 2 つだけです。

- **プライベートインシデントノート** — Markdown の本文、必須。フォームには、これがチーム内限定でステータスページには表示されないとはっきり書かれています。
- **添付ファイル** — インシデント対応チーム向けのファイル。

**投稿日時** も購読者向けチェックボックスもありません — ノートは作成された時刻で記録されます。

## ノートの添付ファイル

どちらのノートも **添付ファイル** フィールドからファイルを添付でき、どちらもノート本文の下に添付ファイル一覧を表示して、ファイルごとに **Download attachment** リンクを出します。

分かれるのは、誰がそのファイルを取得できるかです。

- **パブリックノートの添付ファイル** は、ノート本体と並んでステータスページのルート経由で訪問者がダウンロードできます。
- **プライベートノートの添付ファイル** は、認証されたダッシュボード API からしか到達できません。ステータスページ側のルートは存在しません。

つまり添付ファイルも、ノート本文と同じ公開・非公開の判断になります。顧客に見せるタイムラインの画像はパブリックノートへ、設定ダンプはプライベートノートへ。

## AI でノートを生成する

どちらのノートページにも **Generate with AI** ボタンがあります。押すとインシデントの内容がプロジェクトの AI プロバイダーに送られ、生成された Markdown がノートエディターに入ります。保存前に編集する前提で、自動で公開されるものは何もありません。

- **Generate Public Note with AI** — インシデントのデータを分析して顧客向けのノートを作る、と説明されています。テンプレートには **Status Update** と **Resolution Notice** があります。
- **Generate Private Note with AI** — 代わりに社内向けの技術的なノートを作ります。テンプレートには **Investigation Update** と **Technical Analysis** があります。

ボタンの裏側では、ダッシュボードが選択したテンプレートと `public` または `internal` のノート種別を付けて `/incident/generate-note-from-ai/{incidentId}` に POST しています。

## ノートテンプレート

障害のたびにチームが同じ 3 つの更新を書いているなら、一度保存してしまいましょう。どちらのノートページにも **テンプレートから作成** ボタンがあり、**ノートテンプレートを選択** ドロップダウンを備えた **テンプレートからノートを作成** ピッカーが開きます。

テンプレートはパブリックノートとプライベートノートで共有されます。テンプレートの一覧は 1 つで両方に使われ、同じテンプレートをどちらの種類のノートにも挿入できます。

管理は **インシデント → 設定 → ノートテンプレート** で行います — カードのタイトルは **Public or Private Note Templates for Incidents** で、フォームには **テンプレート情報** ステップ(**テンプレート名** と **テンプレートの説明**、どちらも必須)と、本文を書く **メモの詳細** ステップがあります。1 つも作らないうちに **テンプレートから作成** をクリックすると、まだ存在しないと表示されます。なおそのメッセージは プロジェクト設定 を指していますが、実際のページは **インシデント → 設定 → ノートテンプレート** にあります。

## Slack や Microsoft Teams からノートを投稿する

ワークスペースを接続していれば、対応者はチャンネルを離れる必要がありません。Slack と Microsoft Teams のどちらにもノート追加のアクションがあり、**パブリックノート** か **プライベートノート** を選ぶドロップダウンとテキストボックスを備えたモーダルが開いて、結果がそのままインシデントに書き込まれます。

知っておくとよい点が 2 つあります。

- **重複の防止** — 各ノートは、元になった Slack メッセージを記録します(`postedFromSlackMessageId`、形式は `channel_id:message_ts`)。そのため同じメッセージに複数人が反応しても、ノートは 5 つではなく 1 つになります。
- **ノートは反響します** — どちらの種類のノートを投稿しても、接続済みのインシデントチャンネルにメッセージが送られます。ノートのフィード項目がワークスペース通知を有効にして作成されるためです。

## パブリックノートが実際に購読者に届くとき

**ステータスページの購読者に通知** をオンにしてパブリックノートを作っても、それだけでメールが出ていくとは限りません。ノートは一連のチェックを通過する必要があり、どこで止まってもエラーにはならず、それぞれ具体的な理由が記録されます。

1. **ステータスページの購読者に通知** がオンであること。オフなら、ノートは作成された瞬間にスキップとして記録されます。
2. ノートの属するインシデントがまだ存在すること。
3. インシデントに少なくとも 1 つモニターが紐付いていること — モニターがなければ、ノートを届けるステータスページのリソースがありません。
4. インシデントの **ステータスページに表示** フラグ(`isVisibleOnStatusPage`)が true であること。
5. インシデントが届く各ステータスページで **インシデントを表示**(`showIncidentsOnStatusPage`)がオンであること。
6. 各購読者が自分の設定を満たすこと — 購読解除しておらず、このリソースを購読しており、ページが購読者に選択を許している場合は `Incident` イベントタイプも購読していること。

**通知は即時ではありません。** 送信ジョブは 1 分に 1 回動くので、ノートを保存してからメールが出るまで最大 1 分程度かかると考えてください。**Sending Soon** のラベルはその状態を意味します。

**購読者通知ステータス** 列が、その道のり全体を追跡します。

| ステータス                    | 意味                                                   |
| ---------------------------- | ------------------------------------------------------ |
| **Notifications skipped.**   | 上記の関門のどれかが閉じました。理由が記録されます。 |
| **Sending Soon**             | キュー待ち。送信ジョブの次の実行を待っています。     |
| **Notifications Being Sent** | ジョブが購読者リストを処理中です。                   |
| **送信済み通知**             | すべての購読者への通知が送信されました。             |
| **失敗**                     | ジョブが例外を出しました。エラーはノートに保存されます。 |

ステータスの **詳細** をクリックすると **通知ステータスの詳細** が開きます。再送に意味がある場合、そのモーダルのボタンは **Retry** で、押すとノートは保留状態に戻り、次の実行で再び拾われます。

購読者が実際に受け取るメッセージは、ステータスページごと・チャネルごとにテンプレート化されています。メール、SMS、Slack、Microsoft Teams のそれぞれが **Subscriber Incident Note Created** イベント用の独自テンプレートを持ち、ステータスページの名前と URL、詳細へのリンク、影響を受けるリソース、インシデントの重大度とタイトル、ノート本文、購読者ごとの購読解除リンクといった変数を使えます。テンプレートとチャネルの設定方法は [購読者とお知らせ](/docs/status-pages/subscribers) を参照してください。

## インシデントフィード

**インシデント フィード** カードは、インシデントの **概要** ページの左カラムの一番下にあります。インシデントの物語を順に並べたものです。各項目にはアイコン、その原因となった人のアバターと名前、ホバーで正確なローカル時刻が出る相対タイムスタンプ、そして Markdown の本文があります。並び順は古いものが先です。

項目によっては追加の詳細を持ちます — 例えば所有者通知には、メールが送られた全員が並びます。そうした項目には **More Information** パネルを開く **More Information** ボタンが付きます。

カードのヘッダーには **アクション** メニューもあり、タイムラインを離れずに操作できます。

- **Execute Runbook** — このインシデントに対して [Runbook](/docs/runbooks/index) を開始します。
- **オンコールポリシーを実行** — ポリシーを任意のタイミングで呼び出します。
- **Add Public Note** — 公開ノートのページと同じ 4 つのフィールドを、モーダルで表示します。
- **プライベートメモを追加** — ノート本文と添付ファイルだけです。

その隣の **更新** はフィードを取得し直します。

**フィードは追記のみであり、監査ログではありません。** API はフィード項目の作成と読み取りは許しますが、更新と削除は許さないので、誰かがこっそりインシデントの履歴を書き換えることはできません。ただし恒久的でもありません。課金対象のインストールでは、3 年より古いフィードの行は削除されます。誰が何を変えたかの永続的な記録には、インシデントのサイドメニューの **監査 → 監査ログ** を使ってください。

## フィードが記録するもの

フィード項目を書き込むのは、インシデントサービス自身、両方のノートサービス、状態タイムライン、所有者とメンバーの変更、各ルールエンジン、オンコール実行、AI の調査とポストモーテムの実行、そして通知の cron ジョブです。イベントタイプは次の範囲をカバーします。

- **インシデント本体** — `IncidentCreated`、`IncidentUpdated`、`IncidentStateChanged`。
- **ノートと書き起こし** — `PublicNote`、`PrivateNote`、`RootCause`、`RemediationNotes`、`PostmortemNote`。
- **人** — `OwnerUserAdded`、`OwnerTeamAdded`、`OwnerUserRemoved`、`OwnerTeamRemoved`、`IncidentMemberAdded`、`IncidentMemberRemoved`。
- **通知** — `OwnerNotificationSent`、`SubscriberNotificationSent`、`OnCallPolicy`、`OnCallNotification`。
- **自動化** — `LabelRuleExecuted`、`OwnerRuleExecuted`、`PrivacyRuleExecuted`、`OnCallRuleExecuted`、`AutoRemediation`。

種類ごとに専用のアイコンが付くので、長いフィードでも雑多な記録の中から状態変更を拾い出せます。AI が生成した根本原因分析は区別できるように印が付き、制限付きの Markdown モードで表示されます。

フィードはインシデントのプライバシーを尊重します。プライベートインシデントでは、フィードの読み取りもインシデント本体と同じようにフィルタされます。

## 所有者

所有者は、インシデントに責任を持つ人とチームです。インシデントに起きるすべての通知先であり — 全員が「誰か他の人が見ているだろう」と思っている間にインシデントが放置される、という事態を防ぐ仕組みでもあります。

インシデントのサイドメニューで **チーム → 所有者** を開きます。**所有者** カードには件数バッジが付き、所有者はこのインシデントに責任を持ち変更について通知を受ける人とチームである、という説明と、「2 people · 1 team」のような集計が表示されます。所有者は重なり合ったアバターとして表示され、ホバーするとその人のメールアドレスが出るか、**チーム** であることが示されます。

- **所有者を追加** をクリックすると、人やチームを検索できるピッカーが開きます。
- アバターの削除コントロールをクリックすると **所有者を削除** の確認が開き、**削除** で確定します。
- まだ所有者がいない場合、カードはそのことを伝え、変更の通知が届くようにチームメイトかチームを追加するよう促します。

所有者ユーザーと所有者チームは別々のレコードです。チームを追加すれば、そのメンバー全員を個別に並べなくても、通知の観点で全員が所有者になります。

## 所有者はどうやって割り当てられるか

所有者一覧に載る経路は 4 つあります。

- **インシデントテンプレートから** — テンプレートは **所有者 - チーム** と **所有者 - ユーザー** のフィールドを持ち、インシデントを所有し作成時・更新時に通知を受けるチームとユーザーとして説明されています。テンプレートからインシデントを作成すると事前入力されます。[インシデントの宣言](/docs/incidents/declaring-incidents) を参照してください。
- **インシデントの所有者ルールから** — 一致したルールが、作成時に自動で所有者を追加します。
- **API での作成時に** — 作成の呼び出しと一緒に渡した所有者ユーザーとチームは即座に追加されます。「所有者に追加されました」のメールを送るかどうかを制御するフラグも付いています。
- **手動で** — **所有者** ページの **所有者を追加** から、インシデント対応中いつでも追加できます。

同じ人を 2 回追加しても問題ありません。すでに割り当てられている所有者が重複することはありません。

## インシデントの所有者ルール

**インシデントの所有者ルール** は、一致するインシデントが作成されたときに所有者ユーザーとチームを自動で割り当てます — データベースのインシデントが、誰も考えなくてもデータベースチームに届くようにするルーティング層です。他のインシデント自動化と一緒に [インシデントの設定と自動化](/docs/incidents/settings) で扱っています。

ルールのフォームは **基本情報**、**一致条件**、**所有者** の 3 ステップで、所有者のステップには 2 つのセクションがあります。

- **割り当てる所有者** — **所有者チーム** と **所有者ユーザー** を選びます。ルールが一致すると、選んだユーザーとチームがすべて所有者として追加され、すでに割り当てられている所有者は重複しません。
- **所有者を継承** — 名指しする代わりに、関連するエンティティから所有者を割り当てます。**モニターから所有者を継承** は、インシデントのモニターの所有者全員をインシデントの所有者にします。**ホストから所有者を継承**、**… Kubernetesクラスターから所有者を継承**、**… Dockerホストから所有者を継承**、**… Inherit Owners From Podman Hosts**、**… サービスから所有者を継承** も、それぞれのリソースについて同じことをします。

**所有者に通知** トグルが、実際に人に知らせるかどうかを制御します。本当のルーティングにはオンのままにし、静かに所有者を追加したいときはオフにしてください — ルールが呼び出しではなく記録上の便宜であるときに便利です。

ルールの実行はすべてインシデントフィードに書き込まれるので、ある人がルールで追加されたのか人間が追加したのかは、いつでも判別できます。

## 所有者が通知を受ける内容

所有者に通知するジョブは 5 つあり、それぞれ 1 分に 1 回動きます。

- **インシデントが作成された** — 件名は `[New Incident {number}] - {title}`。
- **ノートが投稿された** — パブリックノート *と* プライベートノートの両方について、件名は `[Update Incident {number}] - {title}`。
- **インシデントの状態が変わった** — [インシデントの状態と重大度](/docs/incidents/states-and-severities) を参照してください。
- **所有者として追加された** — 件名は `You have been added as the owner of Incident {number} - {title}`。
- **まだ未解決** — インシデントの次回リマインド時刻に基づくリマインダーで、件名は `[Reminder] Incident {number} is still {state} - {title}`。

各通知はメール、SMS、音声通話、プッシュ、WhatsApp 向けに組み立てられ、ユーザーの通知設定に渡されます。実際に何が送られるかを決めるのはその設定です。受信者は 1 つずつ個別にオフにできます — ユーザーごとの設定は、インシデント作成、ノート投稿、状態変更、所有者追加、メンバー割り当て、未解決リマインダーの各通知を送る、という表現になっています。状態変更のときだけ電話がほしい人は、まさにそれだけを設定できます。

**所有者がいないインシデントも無音にはなりません。** 所有者が 1 人もいないインシデントでは、通知ジョブはプロジェクトの所有者にフォールバックするので、取りこぼしはありません。通知した全員は対応するフィード項目にも追記されるので、あとから誰にどのアドレスで伝えたかを正確に確認できます。
