# インシデントの宣言

インシデントを宣言した瞬間から、OneUptime は記録を取り始めます。レコードが作られ、番号が刻まれ、オンコールポリシーが動き出し — そうしないよう指定しない限り — ステータスページの購読者にも知らせが届きます。インシデントのライフサイクルの残りは、すべてこの最初の書き込みにぶら下がっています。

インシデントが OneUptime に入ってくる経路は 4 つあり、行き着く先はどれも同じです。重大度、現在の状態、影響を受けるリソースの一覧を持つ `Incident` テーブルの 1 行です。違うのは誰がフィールドを埋めるかだけ — 午前 3 時のあなた、保存済みのテンプレート、モニターの条件、あるいは API を呼ぶあなたのコードです。

このページでは 4 つすべてをフィールド単位でたどり、そのあとサーバーが代わりに埋めるもの、そしてインシデントが存在した瞬間に何が動き出すかを扱います。

## インシデントが宣言される 4 つの方法

| やりたいこと                                                  | 選ぶもの                                                                    |
| ------------------------------------------------------------ | --------------------------------------------------------------------------- |
| すべて自分で入力して手動でインシデントを開く                | **インシデントを宣言** ウィザード                                           |
| よくある型のインシデントを事前入力済みで開く                | **テンプレートから作成**                                                    |
| モニターのチェックが失敗したら自動で開く                    | **When filters match, declare an incident.** を有効にしたモニターの条件フィルター |
| 自分のコード、スクリプト、別のツールから開く                | `POST /api/incident`                                                        |

4 つとも同じモデルに書き込むため、プローブが開いたインシデントは対応者が手で開いたものとまったく同じに見えます — 自動作成分にサーバーが付ける数個の管理用カラムを除けば、です。

## 手動で宣言する

**インシデント → すべてのインシデント** を開き、**インシデント** 一覧の右上にある **インシデントを宣言** をクリックします。**新しいインシデントを宣言** というタイトルのカードが開き、フォームは **インシデントの詳細**、**影響を受けるリソース**、**オンコールとロール** の 3 ステップに分かれ、その後に確認用の概要が続きます。プロジェクトが作成時にインシデントのカスタムフィールドの一部を尋ねる場合は、**影響を受けるリソース** の直後に 4 つ目のステップ **詳細** が入ります。

必須フィールドがあるのは最初のステップだけで、加えて管理者が **作成時に必須** に設定したカスタムフィールドも必須です。リソースの添付、オンコールポリシーの追加、ロールの割り当ては、後からインシデント自身のページで行うこともできます。 概要より前の各ステップには通常の **次へ** があり、**インシデントを宣言** は最後のステップである概要にあります。

**その他の項目**。ほとんどのインシデントで使わないオプションは、各ステップの末尾にある **その他の項目** 見出しの下に折りたたまれています。クリックすると開きます。折りたたまれている間、見出しには中にある項目の名前が並び、設定されている項目(たとえばテンプレートによって)はその値とともに表示されます。修正が必要な項目があると自動的に開きます。概要には、折りたたまれたオプションは設定されている場合にのみ表示されますが、**ステータスページの購読者に通知** は例外で、通知先とともに常に表示されます。

### ステップ 1 — インシデントの詳細

- **タイトル** — 必須。一覧、Slack、そして(インシデントが表示対象なら)ステータスページで誰もが目にする 1 行の要約です。
- **インシデントの重大度** — 必須。プロジェクトに設定された重大度のいずれかです。
- **説明** — 任意。Markdown で記述します。ステータスページに表示される内容なので、チームではなく顧客に向けて書いてください。

**その他の項目** の下:

- **宣言日時** — ページを開いた時刻から始まります。インシデントのあらゆる所要時間はここから測られるため、以前に始まったインシデントを記録するときはさかのぼって設定してください。
- **初期状態** — 任意で、最初は空です。空のままにすると、インシデントは `isCreatedState` フラグの付いた状態、またはテンプレートの初期状態で始まります。すでに確認済みまたは解決済みのインシデントを記録する場合にのみ、後の状態を選んでください。
- **ラベル** — 任意。ラベルは関連するインシデントをまとめます。ラベルで制限されたチームは、自分のラベルのいずれかが付いたインシデントだけを見られます。
- **プライベートインシデント** — 既定ではオフ(`isPrivate`)。プライベートインシデントは、その所有者、プロジェクト管理者、プロジェクト所有者だけが閲覧でき、すべてのステータスページで非表示になります。

**状態のドロップダウンでつまずいたら。** プロジェクトに `isCreatedState` フラグを持つ状態が 1 つもない場合、作成の呼び出しは失敗し、設定から作成用のインシデント状態を追加するよう促されます。これが起きるのは通常、状態を大きく編集したプロジェクトだけです — [インシデントの状態と重大度](/docs/incidents/states-and-severities) を参照してください。

### ステップ 2 — 影響を受けるリソース

モニターは最初に、単独で尋ねられます。ステータスページはモニターを通してインシデントを認識し、モニターの変更後のステータスはそのすぐ下にあります。

- **モニター** — インシデントの影響を受けるモニターを添付する検索ボックスです(`monitors`)。これらのモニターのいずれかを掲載しているステータスページに、インシデントが表示され、購読者に通知されます。
- **変更後のモニターステータス** — 任意。モニターが 1 つ以上選ばれたときにだけ表示されます。インシデントのすべてのモニターにモニターステータスを適用するので、インシデントの宣言とモニターの劣化表示を 1 回の操作で行えます。テンプレートのステータスはモニターを選んだ時点で表示され、モニターが 1 つも選ばれていなければステータスは保存されません。
- **その他の影響を受けるリソース** — インシデントが影響するその他すべてのための 2 つ目の検索ボックスです。ホスト、Kubernetes クラスター、Docker と Podman のホスト、Proxmox・Ceph・Docker Swarm のクラスター、vCenter、ストレージアレイ、IoT フリート、データベース、サービスが対象です。これらはインシデントの別々のリレーションです(`hosts`、`kubernetesClusters`、`services` など)。

インシデントの **影響を受けるリソース** カードも、後で編集するときに同じ形で尋ねます。

**その他の項目** の下:

- **次のステータスページに限定** — 任意。空のままにすると、インシデントはそのモニターを掲載しているすべてのステータスページに表示され、購読者に通知されます。ページを選ぶと、その中の選んだページだけになります。[対象者ごとのステータス ページ](/docs/status-pages/one-status-page-per-audience) を参照してください。
- **ステータスページの購読者に通知** — チェックボックス。既定でオンです(`shouldStatusPageSubscribersBeNotifiedOnIncidentCreated`)。その下と概要で、どのステータスページに通知され、それぞれに何人の購読者がいるかがフォームに表示されます。概要では **通知をプレビュー** で購読者が受け取るメールを確認できます。記録だけ残したい内部向けのノイズではオフにしてください。

**冗長に思えてもモニターは紐付けてください。** インシデントとステータスページのつながりは、インシデントのモニターを経由します。ステータスページがインシデントを表示するのは、そのページのリソースの 1 つがインシデントのモニターであるときです。また、モニターが 1 つも紐付いていないインシデントでは、購読者への状態変更通知はそもそもスキップされます。[ステータス ページのリソースとグループ](/docs/status-pages/resources-and-groups) を参照してください。

### ステップ 3 — オンコールとロール

- **オンコールポリシー** — このインシデントの作成時に実行するオンコールポリシーの複数選択です(`onCallDutyPolicies`)。
- **インシデントのロールを割り当てる** — プロジェクトで定義された各ロールを誰が担うか。**プライマリ** のタグが付いたロールを空のままにすると、インシデントの宣言時にあなたがそのロールを担います。

オンコールポリシーをインシデントに直接紐付けられるのは、ここだけです。重大度はオンコールポリシーを持ちません — 重大度はラベルであり、呼び出しに影響するのはオンコールルール内の *マッチ条件* としてだけです。**インシデント → ルール → オンコールルール** で設定したルールは、ここで選んだものに自分のポリシーを上乗せします。最終的に実行される集合は、両者の和集合から重複を除いたものです。

ロール自体は **インシデント → 設定 → インシデントの役割** で設定します。新しいプロジェクトには Incident Commander が 1 つあります。プロセスに必要なものはそこで追加してください。

**Should be visible on status page?** フラグ(`isVisibleOnStatusPage`)はウィザードにはなく、既定は true です。変更はあとからインシデントのサイドメニューの **設定** で行い、そこでは **ステータスページに表示** というラベルになっています。

## テンプレートから宣言する

同じ形のインシデント — 同じタイトルのパターン、同じ重大度、同じオンコールポリシー — を何度も宣言しているなら、一度テンプレートとして保存してください。

**テンプレートから作成**(**インシデントを宣言** の隣にあるアウトラインボタン)をクリックすると、**Select Incident Template** ドロップダウンを備えた **テンプレートからインシデントを作成** モーダルが開きます。テンプレートを選ぶと作成フォームが事前入力された状態で開き、送信前ならどこでも変更できます。プロジェクトにまだテンプレートがなければ代わりに **No Incident Templates** モーダルが表示され、**Create Template** ボタンから **インシデント → 設定 → インシデントテンプレート** へ移動できます。

テンプレートは専用のウィザードで作成します — **テンプレート情報**、**インシデントの詳細**、**影響を受けるリソース**、**オンコール**。プロジェクトにインシデントのカスタムフィールドがある場合は、そのステップも加わります。所有者とラベルは **インシデントの詳細** の末尾の **その他の項目** にあります。**影響を受けるリソース** は宣言フォームと同じように尋ねます — **モニター**、次に **変更後のモニターステータス**、次に **その他の影響を受けるリソース**、そして **その他の項目** の下に **次のステータスページに限定**。ただしテンプレートは常にモニターステータスを尋ねます。テンプレートからインシデントを宣言するときに選ばれるモニターにも適用されるためです。フィールドは次のとおりです:

| フィールド                    | 用途                                                   |
| ---------------------------- | ------------------------------------------------------ |
| **テンプレート名**            | ピッカー上でテンプレートを識別する名前。             |
| **テンプレートの説明**        | どんなときに使うのかを未来の自分に残すメモ。         |
| **タイトル**                  | インシデントに事前入力されるタイトル。               |
| **説明**                      | インシデントに事前入力される Markdown の説明。       |
| **インシデントの重大度**      | インシデントに事前入力される重大度。                 |
| **初期インシデント状態**      | このテンプレートから作られるインシデントの開始状態。 |
| **モニター** | 添付するモニター。 |
| **変更後のモニターステータス** | インシデントのモニター(宣言時に選んだものを含む)に適用するモニターステータス。 |
| **その他の影響を受けるリソース** | 添付するホスト、クラスター、サービス。 |
| **次のステータスページに限定** | インシデントの表示先を限定するステータスページ。 |
| **オンコールポリシー**        | インシデント作成時に実行するポリシー。               |
| **所有者** | このテンプレートから作成されたインシデントを所有するユーザーとチーム。1 つの一覧から選びます。 |
| **ラベル**                    | インシデントに付けるラベル。                         |

押さえておきたい決まりがいくつかあります。

- テンプレートは一覧からは編集できません — 作成したら、開いて変更してください。
- テンプレートが埋めるのは、空のままにしたフィールドだけです。作成ページではテンプレートは上書き可能な事前入力として適用され、API ではリクエストがそのフィールドを `undefined` のままにした場合にだけサーバーがテンプレートから埋めます。呼び出し側が渡した値が常に勝ちます。

## モニターの条件から自動で宣言する

ほとんどのインシデントは、人が打ち込む必要などないはずです。モニターの条件エディターで **When filters match, declare an incident.** トグルをオンにすると、**インシデントを追加** ボタンを備えた **インシデントを作成** セクションが現れます — 1 つの条件フィルターから複数のインシデントを宣言できます。

各エントリーには次の項目があります。

- **インシデントタイトル** — テンプレート化に対応しており、プレースホルダーは `{{monitorName}} is down` のような形を示します。
- **重大度** — 必須。
- **インシデントの説明** — こちらもテンプレート化できます。
- **オンコール → オンコールポリシー** — このインシデントの作成時に実行するポリシー。
- **インシデントの役割** — チームメンバーを役割にあらかじめ割り当てます。
- **所有権とラベル → 所有者チーム**、**所有者ユーザー**、**ラベル**。
- **その他の項目 → インシデントを自動解決**(条件に一致しなくなったらインシデントを自動で解決)、**ステータスページにインシデントを表示**、**プライベートインシデント**、**修復ノート**。

タイトル、説明、修復ノートで使える `{{variable}}` プレースホルダーの全一覧は [インシデント & アラート テンプレート](/docs/monitor/incident-alert-templating) を参照してください。

この経路で作られたインシデントには、サーバーが印を付けます。`isCreatedAutomatically` が設定され、`createdCriteriaId` にどの条件フィルターが発火したか、`createdByProbe` にどのプローブが検知したかが記録されます。それ以外の振る舞いは、手で宣言したインシデントとまったく同じです。

## API から宣言する

インシデントモデルは標準的な CRUD エンドポイントを公開しているため、`POST /api/incident` で作成できます。認証には **プロジェクト設定 → API キー** で発行した API キーを `apikey` ヘッダーで送ります — キーがプロジェクトを特定するので、プロジェクト ID を別に渡す必要はありません。

```bash
curl -X POST https://oneuptime.com/api/incident \
  -H "apikey: $ONEUPTIME_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "data": {
      "title": "Checkout latency above SLO",
      "description": "Investigating elevated p99 latency on the checkout service.",
      "incidentSeverityId": "<incident-severity-id>"
    }
  }'
```

リクエストボディで役に立つフィールドは次のとおりです。

- `title` — 本当に必ず指定しなければならない唯一のフィールド。
- `declaredAt` — フォームでは必須ですが、ここでは任意です。省略するとサーバーが現在時刻を使います。
- `incidentSeverityId` と `currentIncidentStateId` — サーバーは両方が API キーと同じプロジェクトに属するかを確認し、そうでなければリクエストを拒否します。同じ確認が **Change Monitor Status to** の裏にあるモニターステータスにも適用されます。
- `createdIncidentTemplateId` — 保存済みのテンプレートを適用します。省略したフィールドはテンプレートから埋められ、送ったフィールドはそのまま保持されます。

関連するエンドポイントは `/api/incident-state`、`/api/incident-severity`、`/api/incident-state-timeline` です。自動生成された [API リファレンス](/reference) に、モニターなどのリレーションフィールドの表現方法も含め、それぞれの正確なリクエストとレスポンスの形が載っています。

## インシデント番号とプレフィックス

すべてのインシデントには、プロジェクトごとのカウンターから連番が振られます。割り当てるのは作成時のサーバーです。番号は 2 つのカラムに保持されます。`incidentNumber`(生の整数)と `incidentNumberWithPrefix`(実際に目にする値)です。プレフィックスを設定していなければ、表示値は `#42` になります。

これを変えるには **インシデント → 設定 → 番号プレフィックス** を開き、**更新** を押します。**インシデント番号のプレフィックス** フィールドには入力中の番号がプレビューされます（`INC-` なら `INC-42`）。空のままにすれば既定の `#` が使われます。新しいプレフィックスは保存後に宣言されたインシデントに適用され、既存のインシデントは番号がそのまま残ります。同じダイアログに、エピソード番号用の **インシデントエピソード番号のプレフィックス** もあります。

番号はインシデント一覧の最初の列に表示されてインシデントへのリンクになり、インシデントの **概要** では **インシデント番号** として表示されます。

## インシデントが宣言された瞬間に起きること

作成の呼び出しは、1 行書き込む以上のことをします。順番に見ていきます。

1. **サーバーが空欄を埋めます。** `declaredAt` は現在時刻が既定になり、現在の状態はプロジェクトの `isCreatedState` の状態が既定になり、インシデント番号とプレフィックス付き番号がプロジェクトのカウンターから割り当てられます。
2. **テンプレートが適用されます。** `createdIncidentTemplateId` が指定されていた場合で、呼び出し側が未定義のままにしたフィールドだけを埋めます。
3. **プライバシールールが実行されます。** 一致するルールがそう指示すれば、インシデントをプライベートにします。これは最初に走るルールエンジンなので、以降のすべてが正しいプライバシー設定を前提に動けます。
4. **所有者ルールが実行され**、一致したルールが指定する所有者ユーザーとチームを追加します。
5. **ラベルルールが実行され**、インシデントに一致するラベルを追加します。
6. **オンコールルールが実行されます。** **インシデント → ルール → オンコールルール** にある有効なルールのうち、条件が一致したものはすべて自分のポリシーをインシデントに追加します。優先順位もショートサーキットもありません — 一致したルールはすべて発火し、ポリシーは重複が除かれます。
7. **Runbook ルールが実行され**、一致した Runbook を紐付けて開始します。[Runbook 概要](/docs/runbooks/index) を参照してください。
8. **オンコールポリシーが実行されます。** インシデント上のすべてのポリシー — ウィザードで選んだもの、テンプレートから引き継いだもの、ルールが追加したもの — が、イベントタイプ `IncidentCreated` で並行して実行されます。1 つのポリシーが失敗しても、他は止まりません。 すでに確認済みまたは解決済みとして宣言されたインシデントは、どのポリシーも実行しません。誰も呼び出されず、そのフィードにポリシー名とともにその旨が記録されます。
9. **購読者がキューに入ります。** **ステータスページの購読者に通知** をオンのままにしていて、インシデントがステータスページに表示される場合です。配信はリクエストと同期ではなく、バックグラウンドジョブが担当します。
10. **ワークフローが発火します。** **On Create Incident** トリガーが、それを土台に作られたワークフローを開始します。[ワークフロー 概要](/docs/workflows/index) を参照してください。

ここからインシデントは稼働状態になります。インシデントのサイドメニューの **アクティブなインシデント** バッジにカウントされ(解決状態より上の状態はすべてアクティブ扱いです)、そのモニターを載せているステータスページに現れ、**状態タイムライン** が記録を始めます。
