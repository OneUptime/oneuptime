# 条件とステータス

モニターの条件は、各チェックが何を意味するかを決めます。モニターが稼働しているかダウンしているか、そして OneUptime がインシデントを宣言するかアラートを作成するかです。ステータスは、モニターがなりうる状態を並べたプロジェクトの一覧で、**稼働中** から **オフライン** まであります。このページでは、すべてのモニターの種類についてその両方を説明します。各種類のページには、その種類が提供するフィルターが載っています。

:::cards
- [条件の決め方](#条件の決め方): 上から順に見て、最初に一致したものが勝ちます。
- [条件の中身](#条件の中身): フィルター、一致条件、アクション、設定。
- [チェックの期間を判定する](#チェックの期間を判定する): 失敗したチェックを数え、不安定さを見つけ、パーセンタイルを読みます。
- [モニターの条件を変更する](#モニターの条件を変更する): 条件の編集、追加、並べ替え、テスト。
- [モニターのステータス](#モニターのステータス): 組み込みのステータスと独自のステータス。
:::

## 条件の決め方

モニターがチェックされるたびに、その条件がリストの上から順に結果を判定します。フィルターが一致した最初の条件が何が起きるかを決め、そのチェックではそれより下の条件は見られません。どれにも一致しない場合、モニターは **デフォルトのモニターステータス** になります。ただし、モニターを戻す条件がまだ一致していない間は、代わりに今のステータスを維持します。[条件が回復するとき](#条件が回復するとき) を参照してください。

```mermaid title="各チェックの判定方法"
flowchart TB
    R["チェックの結果"] --> C1{"最初の条件:<br/>フィルターは<br/>一致？"}
    C1 -->|"はい"| A["その条件が動く"]
    C1 -->|"いいえ"| C2{"次の条件:<br/>フィルターは<br/>一致？"}
    C2 -->|"はい"| A
    C2 -->|"どれも不一致"| D["モニターは<br/>デフォルトの<br/>ステータスへ"]
    A --> S["ステータスを変更"]
    A --> I["インシデ<br/>ントを宣言"]
    A --> L["アラートを作成"]
```

順序もルールの一部です。新しいモニターは条件を悪いものから順に並べます。オフライン、次にその種類にあれば警告（期限切れが近い証明書やドメイン）、最後にオンラインです。**オンライン状態** が **真** のような広い正常系の条件はほぼすべてのチェックに一致するため、最後に置きます。ほかの条件より上にあると毎回最初に一致してしまい、ほかの条件が動くことはありません。

一致してもステータスを変えない条件も、そのチェックの結果を決めます。モニターは今のステータスを保ち、その下の条件は次のチェックを待ちます。**デフォルトのモニターステータス** が適用されるのは、どの条件にも一致しないときだけです。新しいモニターのデフォルトは **稼働中** で、条件の下にある **その他の項目** で変更できます。

> [!NOTE]
> ホスト、コンテナ、ディスク、インターフェースごとにインシデントやアラートを開くモニターは、各チェックですべての条件を判定するため、2 つのホストが同時に別々の条件に一致することがあります。これは、クエリに **グループ化** があるモニター（メトリクスモニターやログモニターなど）や、すべてのディスクやインターフェースに `*` を指定した条件のことです。PromQL の式を監視するメトリクスモニターも同じで、式が返す系列はそれぞれ個別に判定されます。ペイロードのフィールドでインシデントをグループ化する受信リクエストモニターは、それでも最初の一致で止まります。
>
> このようなモニターでもステータスは 1 つで、最初に一致した条件が決めます。モニターを **デフォルトのモニターステータス** に戻すだけで、インシデントもアラートも開かない条件は、別のステータスを設定する条件を満たしたホストを待ち、ほかのホストの状態に関係なく、それらがすべて満たしたときに一致します。それまでは、どの条件も一致しないときでもモニターはステータスを維持します。一方、各ホストのインシデントとアラートは、引き続きそれぞれ個別に解決します。

## 条件の中身

条件を開くと、名前と 3 つのセクションがあり、それぞれ 1 行の要約に折りたためます。

| 部分 | 内容 |
| --- | --- |
| **条件名** | 条件リストに表示される名前で、その条件が開くすべてのインシデントとアラートの根本原因にも使われます。**条件を追加** は新しい条件にフィルターに沿った名前を付け、自分で名前を入力するまで、名前はフィルターに合わせて変わります。 |
| **フィルター** | チェックが示すべき内容で、ひとつ以上のフィルターで表します。Kubernetes モニターとメトリクスモニターでは **アラートルール** と呼びます。 |
| **アクション** | フィルターが一致したときに起きること。ステータスの変更、アラートの作成、インシデントの宣言、またはその組み合わせです。 |
| **設定** | **この条件を有効化**、任意の **説明**、回復するタイミングと判定するタイミング、そして Incoming Request モニターでは **ペイロードのフィールドでインシデントとアラートをグループ化**。 |

### フィルター

フィルターはチェックから値をひとつ読み取り、比較します。**フィルタータイプ**（何を読むか。例: **レスポンスステータスコード**）、**フィルター条件**（どう比較するか。例: **より大きい**）、**値** です。Kubernetes モニターやメトリクスモニターのようにメトリクスを比較するモニターでは、代わりに **条件** と **しきい値** を指定します。モニターの種類ごとに独自のフィルタータイプがあり、[監視条件](/docs/monitor/website-monitor#監視条件) のように各種類のページに載っています。

フィルターが 2 つ以上あると、その下に **一致条件** が表示されます。**すべて** はすべてのフィルターが一致する必要があることを、**いずれか** はひとつで十分であることを意味します。新しい条件は **すべて** から始まります。

**オンライン状態**、**レスポンスステータスコード**、**レスポンスタイム（ms）** のように各チェックを測るフィルターには、**この条件を一定期間にわたって評価する** があります。最新のチェックだけでなく最近のチェックの期間を判定し、最初は直近 5 分間と **すべての値** に設定されています。この場合、期間内のすべてのチェックが一致したときにだけ一致します。期間は最長 24 時間まで設定でき、チェックを数えることもできます。[チェックの期間を判定する](#チェックの期間を判定する) を参照してください。[一定期間にわたる評価](/docs/monitor/website-monitor#一定期間にわたる評価) を参照してください。

### アクション

各アクションは **アクション** の下にあるスイッチです。

| スイッチ | 何をするか |
| --- | --- |
| **フィルターが一致したとき、モニターのステータスを変更します。** | **モニターのステータスを次に変更** で選んだステータスにモニターを移します。 |
| **フィルターが一致したとき、アラートを作成します。** | **アラートを作成** で設定したアラートを作成します。アラートはチームに知らせるもので、ステータスページには表示されません。 |
| **フィルターが一致したとき、インシデントを宣言します。** | **インシデントを作成** で設定したインシデントを宣言します。ステータスページに表示できます。 |

インシデントやアラートでは、タイトル、**重大度**、そして折りたたまれた部分で説明、所有者、ラベル、オンコールポリシーを指定します。タイトルと説明には `{{monitorName}}` のようにチェックの値を入れられます。[インシデント & アラート テンプレート](/docs/monitor/incident-alert-templating) を参照してください。条件が一致したときに誰かを呼び出すには、**オンコール** でポリシーを選びます。[オンコールポリシー](/docs/on-call/policies) を参照してください。

### 設定

**この条件を有効化** は、新しい条件ではすべてオンです。オフにすると、条件を使わずに残しておけます。その条件はすべてのチェックで飛ばされ、ステータスを変えず、何も開かず、見出しに **無効** と表示されます。

**ペイロードのフィールドでインシデントとアラートをグループ化** は、受信リクエストで見つかった値ごとにインシデントをひとつ開くため、ひとつの Webhook アドレスで複数のインシデントを開いたままにできます。[インシデントのグループ化を有効にする](/docs/monitor/incoming-request-monitor#インシデントのグループ化を有効にする) を参照してください。

**独自の条件を満たしたときにのみ回復** と **特定の曜日と時間帯にのみこの条件を評価** は、新しい条件ではオフです。[条件が回復するとき](#条件が回復するとき) と [特定の曜日と時間帯だけ](#特定の曜日と時間帯だけ) を参照してください。

## チェックの期間を判定する

**この条件を一定期間にわたって評価する** をオンにすると、**評価** で期間内のチェックの判定方法を、**過去** で期間の長さを 2 分から 24 時間までの範囲で指定します。各チェックが示すべき内容は、**オンライン状態** を **偽** にするなど、フィルター自身の条件が決めます。

| 評価 | 一致するとき |
| --- | --- |
| **すべての値** | 期間内のすべてのチェックが条件を満たした。 |
| **いずれかの値** | 期間内の少なくとも一つのチェックが条件を満たした。 |
| **平均**、**合計**、**最大値**、**最小値** | 期間内の値のその集計値が条件を満たす。たとえば平均応答時間が 300 ms を超える。 |
| **パーセンタイル** | **パーセンタイル** で選んだ p50 から p99 までのパーセンタイルが条件を満たす。p95 が 300 ms を超えるとは、最も遅い 5% のチェックが 300 ms を超えることです。 |
| **カウント** | 条件を満たしたチェックの数を、**一致するチェック** の設定どおりに比較する。たとえば **より大きい** 30。 |
| **割合** | 期間内のチェックに占めるその割合を、**一致するチェックの割合** の設定どおりに比較する。たとえば **より大きい** 10%。 |
| **ステータスの変化** | チェックが条件を満たす状態と満たさない状態の間で変化した回数を、**変化した回数** の設定どおりに比較する。ダウンしてから復帰するデバイスは二度変化します。 |

期間の設定の下にある一文が、設定どおりにフィルターを読み返します: 「確認: 過去 8 時間の 30 件を超えるチェックで "オンライン状態" が偽」。

- **プローブごとに数える。** **カウント**、**割合**、**ステータスの変化** は、そのチェックを行ったプローブのチェックを数えます。そのため、3 つのプローブからチェックされるモニターが 3 倍の速さで数えることはなく、その後はどの条件とも同じようにプローブ同士が一致する必要があります。
- **まだ埋まっていない期間。** チェックが期間の始まりまでさかのぼるまでは、始まったばかりのモニターのチェック数は、いずれ持つ数より少なくなります。**カウント** と **ステータスの変化** は、すでに **より大きい** または **以上** を超えていれば早めに一致します。チェックが増えても数が増えるだけだからです。それ以外は期間が埋まるのを待ちます。
- **チェックのない期間。** 期間にチェックがない間、またはまだ埋まっていない間は、**データがない場合** が決めます。**Ignore** は待ち、**トリガー** は一致し、**Treat As Zero** は足りないチェックが条件を満たさなかったものとして判定します。

平均とパーセンタイルは、**平均** がこれまでそうしてきたように、すべてのプローブのチェックの値を読みます。**カウント**、**割合**、**ステータスの変化** は、期間を指定できるすべてのフィルターで使えます。Website、API、Ping、IP、Port モニター、サーバーの CPU、メモリ、ディスク、負荷、ネットワーク機器の **SNMP デバイスのオンライン状態** と応答時間、そして DNS、NTP、データベース、外部ステータスページ、プローブステータスの各モニターです。Server モニターの **オンライン状態** は数えません。サーバーが最後に報告してからの時間で判定するためです。メトリクスなどのテレメトリーモニターは、代わりにクエリの時間範囲を、クエリ自身の集計で判定します。その集計でパーセンタイルも読めます。

### 例: ダウンしているアクセスポイントと、不安定なアクセスポイント

Ping モニターがオフィスのアクセスポイントを 1 分ごとにチェックします。期間でチェックを数えられるようになる前は、何度も切れるアクセスポイントは、ダウンしているものと同じに見えるか、何も起きていないように見えました。次の 3 つの条件をこの順に並べると、両者を見分けられます:

| 条件 | フィルター | 評価 | ステータスの変更先 |
| --- | --- | --- | --- |
| アクセスポイントがダウン | **オンライン状態** が **偽** | **すべての値**、**過去** 5 分 | **オフライン**、障害インシデントを宣言 |
| アクセスポイントが不安定 | **オンライン状態** が **偽** | **ステータスの変化**、**より大きい** 5、**過去** 1 時間 | **機能低下**、不安定インシデントを宣言 |
| アクセスポイントがオンライン | **オンライン状態** が **真** | 期間で評価しない | **稼働中** |

2 つ目では、**独自の条件を満たしたときにのみ回復** をオンにし、**ステータスの変化**、**以下** 1、**過去** 1 時間を設定します。こうすると、不安定インシデントは、復帰した最初の 1 分で閉じるのではなく、アクセスポイントが 1 時間安定するまで開いたままです。8 時間で 30 回を超える ping の失敗でアラートを出すには、代わりに 2 つ目の条件を **カウント**、**より大きい** 30、**過去** 8 時間にします。

## 条件が回復するとき

条件は、フィルターが一致しなくなるとすぐに動作を止めます。そのチェックで、**インシデントを自動解決** と **アラートを自動解決** がオンならインシデントとアラートが解決され、モニターは次に一致する条件に移ります。

**独自の条件を満たしたときにのみ回復** は、フィルターが一致しなくなった後も、**回復条件** のフィルターが一致するまで条件を有効なままにします。このフィルターは条件のフィルターの逆を直近 10 分間で見るところから始まり、チェックを数える期間など、フィルターにできることは何でも使えます。条件は、モニターがその条件の設定するステータスにある間、またはその条件が宣言したインシデントやアラートが開いている間、有効です。有効な間は、一覧の中の自分の位置で一致として扱われます。それより上の条件が一致すれば、そちらが優先されます。

どの条件も一致しないとき、条件によって **デフォルトのモニターステータス** から外れたモニターは、そのステータスに戻すだけで何も開かない条件も持っている限り、今のステータスを維持します。これが回復マージンです。テンプレートは 90% を超えると発火し、81% 以下で戻るので、89% ではモニターはそのままです。インシデントとアラートは、それぞれの条件が一致しなくなれば解決されます。そのような条件のないモニターは、これまでどおり **デフォルトのモニターステータス** に移ります。

## 特定の曜日と時間帯だけ

**特定の曜日と時間帯にのみこの条件を評価** では、曜日、**開始時刻** と **終了時刻**、そして **タイムゾーン** を設定します。タイムゾーンは最初はあなたのものです。この時間帯以外では、条件は無効にした条件と同じようにスキップされます。何にも一致しないので、その条件が開いたものは解決され、評価ログには時間帯外だったことが記録されます。時間はそのタイムゾーンの時計で読むので、時計の切り替え後も 08:00 は 08:00 のままです。また、開始より早く終わる時間帯は翌朝まで続きます。

## インシデントとアラートが開くときと閉じるとき

インシデントを宣言する条件は、一致したときにインシデントを開きます。モニターが回復すると、条件でそう設定されていれば、インシデントは自動で閉じます。

```mermaid title="条件が宣言したインシデントの一生"
flowchart TB
    M["チェックが条件に一致"] --> Q{"宣言したインシデントは<br/>まだ開いている？"}
    Q -->|"はい"| N["新しいものは開かない"]
    Q -->|"いいえ"| O["新しいインシデントが開く"]
    O --> K["後のチェックが<br/>別の条件に一致、<br/>またはどれにも不一致"]
    N --> K
    K --> R{"自動解決は<br/>オン？"}
    R -->|"はい"| X["インシデントが解決する"]
    R -->|"いいえ"| H["誰かが解決するまで<br/>開いたまま"]
```

- **ひとつずつ。** 条件が宣言したインシデントがまだ開いている間は、同じ条件がまた一致しても、別のインシデントは宣言されません。アラートも同じです。ホストやペイロードのフィールドでグループ化するモニターは、ホストや値ごとにひとつずつ開いたままにし、**メールごとに新しいインシデントを開く** がオンの受信メールの条件は、メールごとにひとつ開きます。
- **閉じるとき。** 別の条件が一致するか、どれも一致しない後のチェックで、条件の **インシデントを自動解決** がオンのインシデントは解決され、**アラートを自動解決** がオンのアラートも同様です。どちらもインシデントまたはアラートの **その他の項目** の中にあり、新しいモニターが最初に持つ条件ではオンになっています。
- **複数のプローブ。** 複数のプローブでチェックされるモニターは、プローブの結果がそろったときにだけ変わります。[条件の評価方法](/docs/monitor/create-monitor#条件の評価方法) を参照してください。
- **親モニターがダウンしているとき。** モニターの **構成 → 依存関係** ページでは、**依存するモニター** にそのモニターが依存するモニターを指定します。そのどれかが **親のステータスがこの場合に抑制** に挙げたステータス（空のままならオフラインのステータスのいずれか）にある間、モニターはインシデントもアラートも開きません。ステータスは引き続き変わり、開いているものは引き続き解決されます。
- **定期メンテナンス。** 進行中のメンテナンスイベントに含まれるモニターはチェックされないため、その条件も実行されません。[定期メンテナンスの概要](/docs/scheduled-maintenance/index) を参照してください。

チェックがどう判定されたかを見るには、モニターの **概要** を開きます。**モニターの概要** カードに、どの条件が一致し、それぞれが何をしたかが表示されます。すでにひとつ開いていたためにスキップしたインシデントも含まれます。

## ダウンしたときに誰に通知されるか

**ダウンしたとき** は、モニターが失敗したときに何が起き、誰に通知されるかを、いくつかの文で示します。設定されるステータス、作成されるインシデントまたはアラート、メールの送信先、呼び出される人を名前で示します。誰かに通知が届かなくなる原因はそれぞれ 1 行で示され、修正するページへのリンクが付きます。モニターの **概要**、**条件** ページの条件の下、設定中のモニターについては **モニターを作成** の条件ステップ、そして Web サイトのガイド付きセットアップに表示されます。

通知の流れは、実際のインシデントやアラートと同じように求められます。プロジェクトの所有者ルール、プライバシールール、ラベルルール、オンコールルール、アラートをインシデントに変えるアラートのインシデントルール、そして各オンコールポリシーの最初のエスカレーションルールが今誰に届くかを使います。アラートの所有者を条件にするオンコールルール（**アラートの所有者**）は、アラートが持つことになる所有者と照合されます。条件で指定されたユーザーとチーム、モニターが監視するネットワークデバイスの所有者、所有者ルールが追加する所有者です。チェックでしか埋まらないタイトルのプレースホルダーは、書かれたとおりに表示されます。**通知の流れを表示** を押すと、行ごとに開きます。

| 行 | 内容 |
| --- | --- |
| **ステータス** | 条件が設定するステータス。 |
| **開く** | インシデントまたはアラート、括弧内の重大度、タイトル。 |
| **メール** | 作成通知メールの送信先: 所有者、所有者ルールが追加する所有者、所有者がいない場合はプロジェクト所有者。オンコールの呼び出しが先に届く人には、所有者としてのメールは送られません。 |
| **所有者ルール** | 所有者を追加する所有者ルール。 |
| **非公開** | 非公開である理由: プライバシールールまたは条件。非公開のインシデントはどのステータスページにも表示されず、購読者にも通知されません。閲覧できるのは所有者、プロジェクト所有者、プロジェクト管理者のみです。 |
| **ラベルルール** | ラベルによって、呼び出すオンコールルールを変えるラベルルール。 |
| **オンコールルール** | 一致するオンコールルール。アラートの所有者を条件にするルールでは、どの所有者によって一致したかも示されます。 |
| **オンコールポリシー** | それらのルールが実行する各ポリシー: 最初のエスカレーションルールが今誰にどの手段で届くか、届かない人とその理由。 |
| **ステータスページ** | それを表示するステータスページと、各ページがモニターを表示するときに経由するモニターグループ。 |
| **インシデントルール** | アラートの場合: アラートからインシデントを宣言するアラートのインシデントルール (すぐに、またはアラートが開いたままのとき) と、そのインシデント。ほかのインシデントと同じように示されます。 |

### 通知を妨げるもの

| 妨げるもの | リンク |
| --- | --- |
| ステータスを変える条件も、インシデントやアラートを作成する条件もありません。 | **条件を開く** |
| 誰も呼び出されません: 一致するオンコールルールがないか、プロジェクトにまだオンコールポリシーがありません。 | **呼び出しを設定** |
| モニターはアラートを作成しますが、オンコールルールがあるのはインシデントだけです。 | **呼び出しを設定** |
| オンコールポリシーにエスカレーションルールがありません。 | **オンコールポリシーを開く** |
| オンコールポリシーが今誰にも届きません。 | **オンコールポリシーを開く** |
| ポリシーが呼び出す人に連絡できません: 呼び出しを拒否している、認証済みの方法がない、またはフォールバックのないプロジェクトでその重大度のルールがありません。 | **準備状況を開く** |
| プロジェクトで SMS、通話、WhatsApp、Telegram のいずれかがオフになっています。 | **通知チャネルを開く** |
| プロジェクトに SMS と通話の残高がありません (OneUptime Cloud)。 | **請求を開く** |
| サーバーはまだメール、SMS、通話を送信できません。 | **管理者ダッシュボードを開く** (サーバーの管理者向け) |

アラートのインシデントルールによって、誰かを呼び出すインシデントに変わるアラートは、通知の妨げにはなりません。代わりにインシデント自体のポリシーが確認されます。

メールが届かない所有者は、妨げの後に、理由と指定されている場所とともに一覧表示されます。プロジェクトのメンバーではない人、プロジェクトのメンバーが一人もいないチーム (**チームを開く**)、別のプロジェクトのチームで、条件 (**条件を開く**)、モニターが監視するネットワークデバイス (**ネットワークデバイスを開く**)、または所有者ルール (**所有者ルールを開く**) で指定されているものです。メールは届く所有者またはプロジェクト所有者に送られるため、これらは妨げにはなりません。セットアップのヘルスにも、修正をおすすめする項目として一覧表示されます。

### 再確認と表示される内容

回答は最大 1 分前のもので、**再確認** で改めて求められます。再確認に失敗しても、カードは最後の回答を残し、その下に理由を表示します。

カードには閲覧できるものだけが名前付きで表示されます。閲覧できないオンコールポリシー、ルール、ステータスページ、モニターグループは名前なしで表示され、閲覧できなくなる非公開のインシデントやアラートは、作成されることと非公開であることだけが示されます。

## インシデントやアラートがチェックから保持する内容

モニターが開いたインシデントやアラートは、それを開いたチェックを保持するため、モニター自体のログが消えたずっと後でも理由を確認できます。根本原因の下にある **評価の詳細** には、一致した条件と、一致した各フィルターについてチェックが見つけたものが表示されます。**詳細を表示** を押すと、残りの根拠、一致しなかったフィルター、そしてチェックそのもの（リクエスト、実行日時、プローブ、返ってきた内容）が追加されます。フィルターが見つけたものには次があります。

- **フィールド。** JSON の本文で **レスポンスボディ** フィルターが一致した場所（例: `checks[1].status`）、または **レスポンスヘッダーの値** フィルターが一致したヘッダー。
- **値。** **JavaScript 式** が読む各値が評価時に持っていた内容（例: `responseBody.status = "down"`）。
- **抜粋。** 一致箇所の前後にあるレスポンスの短い一部で、一致箇所が強調表示されます。本文全体は保持しません。

シークレットと個人データは、保持される前にマスクされます。対象は `Authorization`、`Cookie`、`Set-Cookie` などのヘッダー、名前が `password`、`token`、`key`、`session`、`email` を示すフィールド、そして bearer トークン、JWT、カード番号、メールアドレスのように見えるテキストです。リクエストの URL はモニターに設定したもので、`{{monitorSecrets.NAME}}` は名前のまま残り、シークレットのクエリ値はマスクされます。モニターの **モニタリングログ** と、根本原因が引用する値も、同じようにマスクされます。手動で開いたインシデントやアラート、または評価の詳細が保持されるようになる前に開いたものには、評価の詳細はありません。

> [!TIP]
> ウェブサイトモニターや API モニターのレスポンス自体が機密である場合は、その **詳細 → 設定** ページの **レスポンスの内容** カードで **レスポンスの内容を保持** をオフにします。そのモニタリングログ、インシデント、アラートには、一致したフィルター、ステータスコード、応答時間だけが保持され、レスポンスの内容は保持されません。受信リクエストモニターには、受け取るリクエストについて同じスイッチがあります。**リクエストの内容** カードの **リクエストの内容を保持** です。このスイッチは、変更した後に実行されるチェックと、その後に開かれるインシデントとアラートに適用されます。受信リクエストモニターの概要に表示される最新のリクエストは、スイッチにすぐに従います。

## モニターの条件を変更する

:::steps
### 条件のページを開く

**モニター** に移動してモニターを開きます。サイドメニューの **構成** を展開し、**条件** をクリックします。**条件** カードに、各条件、何をチェックするか、何をするかが表示されます。

### 「監視条件を編集」をクリックする

エディターではすべての条件が開いた状態で表示されます。条件の見出しをクリックすると 1 行に折りたたまれ、名前、フィルターの数、何をするかが表示されます。

### 条件を追加、変更、並べ替える

**条件を追加** は、開いた状態でフィルターに沿った名前の条件を末尾に追加します。条件を移動するには、左側のハンドルをドラッグします。最初の一致が勝つので、最悪のケースを先頭に置きます。**条件を削除** は条件をひとつ削除します。モニターには少なくともひとつの条件が残ります。

### 条件を保存する

**変更を保存** をクリックします。次のチェックからは新しい条件で判定されます。

### モニターをテストする

プローブがチェックするモニターでは、カードの **モニターをテスト** をクリックします。テストは、モニターをチェックするプローブで始まります。必要なら **プローブを選択** で別のプローブを選び、**テストを実行** をクリックします。**モニターテスト結果** にチェックの結果が表示されます。あわせて、回答がどの条件に一致し、その後に何が起こるか (ステータス、インシデントまたはアラート、誰に通知されるか) も示されます。
:::

手動モニターには条件がありません。ステータスは自分で設定します。[ステータスを更新する](/docs/monitor/manual-monitor#ステータスを更新する) を参照してください。

## モニターのステータス

モニターは常にプロジェクトのステータスのどれかにあります。新しいプロジェクトには、最も健全なものから最悪のものまで、次の 3 つがあります。

| ステータス | 位置 | 色 | OneUptime がどう扱うか |
| --- | --- | --- | --- |
| **稼働中** | 1 | 緑 | 新しいモニターはこのステータスから始まり、新しいモニターの **デフォルトのモニターステータス** でもあります。組み込み。 |
| **機能低下** | 2 | 黄 | それ自体では何もしません。あなたの条件がモニターをここに移します。 |
| **オフライン** | 3 | 赤 | 新しいモニターのオフラインの条件がモニターをここに移し、OneUptime はこのステータスのモニターをダウンとして扱います。組み込み。 |

この一覧は順序でもあります。モニターがまとめて表示される場所では、一覧で最も下にあるステータスが優先されます。モニターグループ、ステータスページのグループ、ステータスページ全体のステータスは、それぞれのモニターの中で最悪のステータスを表示します。

### ステータスが効く場所

| 場所 | ステータスが決めること |
| --- | --- |
| **モニター** の一覧 | 各モニターの現在のステータス。**非稼働** には稼働中以外のステータスにあるモニターが並び、横に赤い件数が表示されます。監視がオフのモニターは含まれません。何もチェックしないためで、それらは **無効** に並びます。**無効** はサイドメニューの **すべてのモニター** の下にあり、件数はグレーで表示されます。監視をオフにするのは選択であって、障害ではないためです。**非稼働** と並んで **注意が必要** の下には、有効なプローブがすべて切断されたモニターが並ぶ **プローブが切断されました** と、有効なプローブがひとつもチェックしていないモニターが並ぶ **有効なプローブなし** があります。後者はプローブがすべて無効か、プローブがひとつもないモニターです。 |
| ステータスページ | 各行の色と稼働率。ページの **ダウンタイムとしてカウント** にあるステータスだけが稼働率に響きます。新しいステータスページは、稼働中以外のすべてのステータスから始まります。[ページに表示する内容を選ぶ](/docs/status-pages/index#ページに表示する内容を選ぶ) を参照してください。 |
| モニターグループ | グループのステータス。そのモニターの中で最悪のものです。[モニターグループ](/docs/monitor/monitor-groups) を参照してください。 |
| SLO | SLO が数えるダウンタイム。SLO 自身のステータスの一覧に基づきます。[ダウンタイムとして数えるステータス](/docs/slo/introduction#ダウンタイムとして数えるステータス) を参照してください。 |
| 依存関係 | 親モニターが子のインシデントとアラートを抑えるかどうか。デフォルトでは、親がオフラインのステータスにある間です。 |

あとから追加したステータスは、既存のステータスページの **ダウンタイムとしてカウント** の一覧には追加されません。自分で追加してください。

### 独自のステータスを追加する

:::steps
### 「モニターステータス」を開く

**モニター → 設定 → モニターステータス** に移動します。サイドメニューの **設定** は折りたたまれているので、先に展開します。**モニターステータス** カードに、最も健全なものから最悪のものまでステータスが並びます。

### ステータスを作成する

**モニターステータスを作成** をクリックし、**名前**、**説明**、**色** を入力します。新しいステータスはオフラインのステータスのすぐ上に入るため、障害は引き続き最悪として扱われます。

### 位置を決める

ハンドルでステータスをドラッグします。一覧で下にあるステータスほど、その上のどのステータスよりも悪いものとして扱われます。

### 条件で使う

ステータスは、条件がモニターをそこに移すまで何もしません。そのステータスを設定すべき条件の **モニターのステータスを次に変更** で選びます。
:::

稼働中とオフラインのステータスには **組み込み** の印が付いています。名前と色は変更できますが、削除はできません。OneUptime Cloud では、ステータスの作成や変更に Growth プランが必要です。ステータスの管理には、プロジェクト所有者、プロジェクト管理者、モニター管理者のいずれかのロール、または対応するモニターステータスの権限を持つカスタムロールが必要です。

### ステータスのタイムライン

ステータスの変更はすべて、モニターの **ステータスタイムライン** に残ります。開始時刻、継続時間、そしてそのステータスを設定した条件を示す **原因を表示** です。**モニターのステータスイベントを作成** は手動でステータスを追加します。プローブがチェックするモニターでは、ステータスを持つ条件に一致した次のチェックで、そのステータスが再び設定されます。

モニターのステータスの変更が所有者に通知されるのは、所有者が通知設定で **モニターのステータスが変更されました** をオンにしている場合だけで、最初はオフです。どの条件にも一致せず **デフォルトのモニターステータス** に戻ったモニターは、誰にも通知しません。[新しいメンバーでオンになっているもの](/docs/notifications/notification-settings#新しいメンバーでオンになっているもの) を参照してください。

## モニターステータスのアーカイブ

チームで使わなくなったステータスは、削除する代わりにアーカイブします。アーカイブしてもモニターは何も変わりません。そのステータスのモニターはステータスが変わるまでそのままで、ステータスタイムラインにも表示されます。

- **アーカイブ** は行の **⋯** メニューにあります。最初に確認を求め、そのステータスを使うように設定されているモニター条件、テンプレート、ステータスページを一覧表示します。これらは変更するまでそのステータスを使い続けます。
- **誰も再び選択できません。** 条件、モニターのステータスメニュー、インシデントやメンテナンスイベントのモニターステータス、ステータスページのダウンタイムステータスはそのステータスを表示しません。API、Terraform、MCP は拒否します。
- **アーカイブされたステータスは別に表示されます。** 表の下の折りたたまれたセクション **アーカイブ済みのモニターステータス** に表示されます。**アーカイブ解除** で元の状態に戻せます。
- **組み込みのステータスはアーカイブできません。** 新しいモニターは稼働中のステータスから始まり、OneUptime はオフラインのステータスのモニターをダウンとして扱います。これらの **アーカイブ** は理由とともにロックされています。

## トラブルシューティング

:::details サイトはダウンしているのに、モニターが稼働中のまま
リストの上のほうにある条件が先に一致しています。**構成 → 条件** を開いて順序を確認してください。正常系の条件は最後に置きます。また、オフラインの条件で **この条件を有効化** がオンになっていること、そのアクション **フィルターが一致したとき、モニターのステータスを変更します。** がオンでステータスが選ばれていることも確認してください。
:::

:::details モニターがダウンしたのにインシデントが開かなかった
一致した条件を確認してください。**フィルターが一致したとき、インシデントを宣言します。** がオンである必要があります。同じ条件のインシデントがまだ開いている間、**依存するモニター** の親モニターがダウンしている間、モニターが定期メンテナンス中の間は、インシデントは宣言されません。モニターの **概要** にある **モニターの概要** カードに、どれだったかが表示されます。
:::

:::details モニターが回復してもインシデントが開いたまま
インシデントの条件を開き、そのインシデントの **その他の項目** を展開してください。**インシデントを自動解決** がオンである必要があります。その後削除した条件のインシデントは、モニターでは解決されません。手動で解決してください。
:::

:::details オフラインの削除ボタンがロックされている
**稼働中** と **オフライン** は組み込みです。OneUptime がモニターをこれらに移すため、名前は変更できますが削除はできません。代わりに独自のステータスを削除するか、組み込みのステータスの名前を変更してください。
:::
