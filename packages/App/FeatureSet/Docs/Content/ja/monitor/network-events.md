# ネットワークイベント（syslog と SNMP トラップ）

ルーター、ファイアウォール、スイッチ、アクセスポイントは、自分に起きたことを syslog に書き出します。リンクがダウンした、トンネルが切れた、ファイアウォールがフェイルオーバーした、誰かがサインインした、といったことです。ベンダーごとに書き方は違います。その syslog を OneUptime のプローブに向けると、**イベント** ページが、デバイスのメーカーを問わず同じ言葉で何が起きたかを表示し、同じことがまた起きたときにアラートで知らせます。

イベントページは 2 か所にあります。

- **ネットワーク** -> **イベント**：ネットワーク全体です。すべてのデバイスのイベントと、まだデバイスになっていないのに syslog を送っているすべてのアドレスを 1 ページで表示します。
- デバイスの **イベント** タブ：そのデバイスが報告した内容です。

## イベントページに表示される内容

- 期間内のイベントを新しい順に表示します。各行には、何が起きたか、どのデバイスで、何に対して（インターフェース、トンネル、ゲートウェイ）起きたか、そしてデバイス自身の言葉が表示されます。
- **問題**、**復旧**、**情報** と、それぞれの期間内の件数です。クリックすると、その種類だけが表示されます。
- **すべてのイベント** の選択と、ネットワークのページでは **すべてのデバイス** の選択で、一覧をさらに絞り込めます。期間とフィルターはページのアドレスに保存されるため、リンクを開くとまったく同じ表示になります。
- イベントをクリックすると開きます。いつ起きたか、何についてのものか、デバイスが送ったままのメッセージ、OneUptime がそこから読み取ったすべての属性が表示されます。
- **アラートを作成** では、ほとんどのネットワークで必要になるアラートを選べます。**このイベントのアラートを作成** では、開いているイベントのアラートを作成できます。[アラート](#アラート) を参照してください。

イベントはログです。イベントページにあるものはすべて、**ログ** からも検索、グラフ化、アラート設定ができます。イベントとは、属性 `event.domain` が `network` で、何が起きたかが `event.name` に入っているログです。

## OneUptime が読み取るもの

RFC 3164 形式と RFC 5424 形式の syslog、および Common Event Format（CEF）は、どの製品のものでも読み取ります。加えて、OneUptime は次の製品が書き出す内容を理解します。

| ベンダー | 製品 | 読み取るイベント | 属性 |
| --- | --- | --- | --- |
| Cisco | IOS, IOS XE, NX-OS, ASA | インターフェース、デバイス、高可用性、VPN、ルーティング、ハードウェア、スイッチング、サインイン | `cisco.*` |
| Sophos | Sophos Firewall (SFOS, XG, XGS) | インターフェース、デバイス、高可用性、VPN、WAN、サインイン | `sophos.*` |
| Fortinet | FortiGate (FortiOS) | インターフェース、デバイス、高可用性、VPN、WAN、ハードウェア、サインイン | `fortigate.*` |
| Extreme Networks | ExtremeXOS, Switch Engine | インターフェース、デバイス、高可用性、ルーティング、ハードウェア、スイッチング、サインイン | `extreme.*` |
| Extreme Networks | Fabric Engine, VOSS | インターフェース、ルーティング | `extreme.*` |
| HPE Aruba Networking | AOS-CX | インターフェース、ハードウェア | `aruba.*` |
| HPE Aruba Networking | AOS-Switch (ArubaOS-Switch, ProCurve) | インターフェース | `aruba.*` |
| MikroTik | RouterOS | インターフェース、デバイス、サインイン | `mikrotik.*` |
| Cambium Networks | Enterprise Wi-Fi (cnPilot, XV, XE, XH) | デバイス、VPN、Wi-Fi | `cambium.*` |
| Ubiquiti | UniFi Network | デバイス、WAN、スイッチング、サインイン、Wi-Fi | `cef.*` |
| すべて | Linux ベースのデバイス（kernel、hostapd、OpenSSH、Dropbear） | インターフェース、サインイン、Wi-Fi | - |

これらの形式のメッセージでは、メッセージ自身のフィールドが、最後の列のプレフィックスを付けた属性として保存されます。たとえば Sophos ファイアウォールの `con_name="HQ-Branch1"` は属性 `sophos.con_name` になります。それ以外の製品の CEF メッセージでは、ヘッダーと拡張フィールドが `cef.*` の下に保存されます。OneUptime が分類できないメッセージも、syslog ヘッダーを読み取ったうえでログとして保存されます。そのイベントには自分で名前を付けられます。[独自のイベント](#独自のイベント) を参照してください。

標準の SNMP トラップも同じイベントとして読み取ります。`linkDown` と `linkUp` は **インターフェースがダウン** と **インターフェースがアップ** に、`coldStart` と `warmStart` は **デバイスが再起動** になります。

## イベント

OneUptime が認識したメッセージはすべて、デバイスのメーカーを問わず、次のいずれかの名前を `event.name` に入れて保存されます。

| イベント | `event.name` | 種類 | 対象 |
| --- | --- | --- | --- |
| インターフェースがダウン | `interface.down` | 問題 | `network.interface.name` |
| インターフェースがアップ | `interface.up` | 復旧 | `network.interface.name` |
| スイッチがポートを停止 | `interface.error_disabled` | 問題 | `network.interface.name` |
| デバイスが再起動 | `device.reboot` | 問題 | - |
| 設定変更 | `device.config_change` | 情報 | `user.name` |
| デバイスがオフライン | `device.offline` | 問題 | - |
| デバイスがオンライン | `device.online` | 復旧 | - |
| フェイルオーバー | `ha.failover` | 問題 | `ha.role` |
| 高可用性の状態が変化 | `ha.state_change` | 情報 | `ha.role` |
| 高可用性ピアがダウン | `ha.peer_down` | 問題 | `ha.peer` |
| 高可用性ピアが復旧 | `ha.peer_up` | 復旧 | `ha.peer` |
| VPN トンネルがダウン | `vpn.tunnel_down` | 問題 | `vpn.tunnel.name` |
| VPN トンネルがアップ | `vpn.tunnel_up` | 復旧 | `vpn.tunnel.name` |
| ルーティングネイバーがダウン | `routing.neighbor_down` | 問題 | `network.peer.address` |
| ルーティングネイバーが復旧 | `routing.neighbor_up` | 復旧 | `network.peer.address` |
| ゲートウェイがダウン | `gateway.down` | 問題 | `network.gateway.name` |
| ゲートウェイが復旧 | `gateway.up` | 復旧 | `network.gateway.name` |
| WAN フェイルオーバー | `wan.failover` | 問題 | `network.gateway.name` |
| SD-WAN リンクが SLA を下回る | `sdwan.sla_not_met` | 問題 | `network.gateway.name` |
| SD-WAN リンクが SLA 内に復帰 | `sdwan.sla_met` | 復旧 | `network.gateway.name` |
| ファン故障 | `hardware.fan_failed` | 問題 | `hw.name` |
| ファン復旧 | `hardware.fan_ok` | 復旧 | `hw.name` |
| 電源装置の故障 | `hardware.power_supply_failed` | 問題 | `hw.name` |
| 電源装置の復旧 | `hardware.power_supply_ok` | 復旧 | `hw.name` |
| 温度が高すぎる | `hardware.temperature_high` | 問題 | - |
| ループを検出 | `loop.detected` | 問題 | `network.interface.name` |
| スパニングツリーのトポロジ変更 | `stp.topology_change` | 情報 | - |
| PoE 障害 | `poe.fault` | 問題 | `network.interface.name` |
| サインイン失敗 | `auth.login_failed` | 問題 | `user.name` |
| サインイン成功 | `auth.login_success` | 情報 | `user.name` |
| Wi-Fi クライアントが接続 | `wireless.client_connected` | 情報 | `client.mac` |
| Wi-Fi クライアントが切断 | `wireless.client_disconnected` | 情報 | `client.mac` |

最後の列は、イベントが何についてのものかを示す属性です。すべての製品がすべてのイベントを報告するわけではありません。スイッチには VPN トンネルがなく、製品の syslog が伝える内容にも限りがあります。

すべてのイベントには次の属性も付きます。

| 属性 | 内容 |
| --- | --- |
| `event.domain` | `network`。すべてのネットワークイベントに付きます |
| `event.kind` | `problem`、`recovery`、`info` のいずれか |
| `event.category` | `interface`、`device`、`ha`、`vpn`、`routing`、`wan`、`hardware`、`switching`、`security`、`wireless` のいずれか（上の表のイベント） |
| `event.device` | どのデバイスか。OneUptime での名前、なければデバイスが名乗る名前、それもなければアドレス |
| `event.message` | デバイスが伝えた内容（デバイス自身の言葉） |
| `syslog.vendor`、`syslog.parser` | メッセージをどの形式として読み取ったか |

## イベントが届くまで

すべてのプローブは、ポート 5140 で UDP と TCP の両方の syslog を待ち受けます。TCP では、メッセージは 1 行であるか、RFC 6587 のとおり先頭に長さが付きます。プローブは受け取ったものを数秒ごとに OneUptime に転送し、OneUptime は送信元のアドレスで各メッセージをデバイスに対応付けます。

1. プローブがポーリングするデバイスのうち、ホスト名がそのアドレスである（またはそのアドレスに解決される）もの、または **設定** ページの **その他のアドレス** にそのアドレスがあるもの。
2. 自分の（カスタム）プローブでは、そのアドレスを持つプロジェクト内の任意のデバイス、またはメッセージに含まれるホスト名を持つデバイス（その名前のデバイスがちょうど 1 台の場合）。
3. それ以外の場合、自分のプローブでは、どのデバイスのものかを指定するまで、メッセージはネットワークのイベントページの **syslog を送信中、まだデバイスではない** に保持されます。グローバルプローブはそれを破棄します。

不明なアドレスからの行で、syslog の優先度がなく、イベントでもないものは、ノイズとみなして破棄されます。

コントローラーは、管理しているデバイスの代わりに報告します。UniFi コンソールは、配下のアクセスポイントとスイッチについて報告します。あるデバイスからのメッセージが、別のデバイスを MAC アドレス、シリアル番号、アドレス、またはコントローラーが付けた名前で指している場合、イベントはそのデバイスのものになり、ログには中継したコントローラーの名前が `syslog.relay.name` に残ります。

ログは、プローブが受信した時刻で保存されます。保留されていたメッセージ、つまりタイムスタンプがタイムゾーンを含む RFC 5424 形式で、5 分より古いものは、7 日前までならデバイスの時刻のまま保存されます。それ以外で、プローブの時計から 5 分を超えてずれているタイムスタンプは信用されません。ログは受信した時刻で保存され、デバイスの時刻は `syslog.deviceTime` に残ります。

HTTPS で [syslog エンドポイント](/docs/telemetry/syslog) に送信した syslog も、同じパーサーで読み取ります。その場合、メッセージがネットワークイベントになるのは、ネットワークベンダー独自の形式であるとき、またはネットワークデバイスのいずれかを MAC アドレス、シリアル番号、アドレス、ホスト名で指しているときです。サーバーの `sshd` の行は通常のログのままです。

## 設定方法

1. **デバイスのネットワーク上にあるプローブを使います。** syslog はデバイスが送信するため、デバイスから到達できる [カスタムプローブ](/docs/probe/custom-probe) が必要です。公開インターネット上のグローバルプローブでは受信できません。
2. **syslog がプローブに届くようにします。** デバイスからプローブへのポート 5140（UDP または TCP）を許可します。カスタムプローブのページのとおりホストネットワーク（`--network host`）で起動した Docker のプローブはそのまま受信できます。ホストネットワークを使わない場合は `-p 5140:5140/udp -p 5140:5140/tcp` でポートを公開します。ポート 514 にしか送信できないデバイスには `-p 514:5140/udp` で公開するか、ホストネットワークのプローブで `PROBE_SYSLOG_RECEIVER_PORT=514` を設定します。
3. **プローブをデバイスの syslog サーバーに設定します。** 主なデバイスのコマンドは下にあります。最初のメッセージが届くまでは **イベント** ページにも同じ手順が表示され、届くと自動的に一覧に切り替わります。
4. **デバイスのアドレスを確認します。** メッセージはデバイスが送信元にしたアドレスで対応付けられます。ホスト名ではないループバックや管理インターフェースから送信している場合は、そのアドレスをデバイスの **その他のアドレス** に追加してください。

syslog レシーバーはデフォルトで有効です。設定はプローブの環境変数で行います。

| 変数 | 説明 | デフォルト |
| --- | --- | --- |
| `PROBE_SYSLOG_RECEIVER_ENABLED` | `false` にすると syslog レシーバーを無効にします | `true` |
| `PROBE_SYSLOG_RECEIVER_PORT` | UDP と TCP のポート | `5140` |
| `PROBE_SYSLOG_RATE_LIMIT_PER_MINUTE` | すべてのデバイスを合わせた、1 分あたりの転送メッセージ数 | `600` |

上限を超えても、プローブはネットワークイベントとして読み取れたメッセージを、さらに同じ数まで転送します。日常的な行が大量に届いても、リンクダウンを知らせる 1 行が埋もれないようにするためです。この機能より古いプローブは、`PROBE_SYSLOG_RECEIVER_ENABLED=true` を付けて起動したときだけ、UDP でのみ待ち受けます。プローブを更新してください。

### Cisco IOS、IOS XE、NX-OS

```text
logging host <probe-address> transport udp port 5140
logging trap informational
service timestamps log datetime msec
```

2 行目は、情報レベル以上のメッセージを送信します。リンクの変化、再起動、サインインはここに含まれます。NX-OS では `logging server <probe-address> 6 port 5140 use-vrf management` と指定します。

### Sophos Firewall

1. ファイアウォールの Web 管理画面で **System services** > **Log settings** を開き、**Syslog servers** で **Add** を選びます。
2. プローブの IP アドレスとポート `5140` を入力し、重大度レベルを **Information** に設定します。ファイアウォールが提供するどちらのログ形式でも読み取れます。
3. **Log settings** に戻り、送信するログについて新しいサーバーにチェックを入れます。少なくともシステムイベントと、SLA の変化を知るための **SD-WAN** です。ファイアウォールのトラフィックログは量が多いので、必要でなければ外してください。

### Fortinet FortiGate

```text
config log syslogd setting
    set status enable
    set server "<probe-address>"
    set port 5140
    set mode udp
    set format default
end
```

FortiGate は、ログ設定で選択したものを送信します。イベントログにはトンネル、リンク、フェイルオーバーが含まれます。トラフィックログは量が多いので、必要でなければ外してください。

### Extreme Networks

```text
configure syslog add <probe-address>:5140 vr VR-Default local7
enable log target syslog <probe-address>:5140 vr VR-Default local7
enable syslog
```

`VR-Default` は、プローブに到達できる仮想ルーターに変更してください。

### HPE Aruba

```text
logging <probe-address> udp 5140 severity info
```

AOS-CX では、管理ポート経由でプローブに到達する場合、行に `vrf mgmt` を追加します。AOS-Switch では `logging <probe-address> udp 5140` と指定します。

### MikroTik RouterOS

```text
/system logging action set remote remote=<probe-address> remote-port=5140
/system logging add topics=info action=remote
/system logging add topics=warning action=remote
/system logging add topics=error action=remote
/system logging add topics=critical action=remote
```

1 行目は、ルーターに組み込まれているリモートアクションの宛先をプローブにします。残りの行は、送信する内容を選びます。リモートログの形式はそのままにしてください。

### Ubiquiti UniFi

1. UniFi Network で **Integration** > **System Logging / SIEM** を開き、送信先として **SIEM Server** を選びます。
2. プローブの IP アドレスとポート `5140` を入力し、エクスポートするログのカテゴリを選びます。

コンソールは、管理しているアクセスポイントとスイッチについて報告します。デバイスが MAC アドレス付きで OneUptime に登録されていれば、イベントはそのデバイスのページに表示され、そうでなければコンソールのページに表示されます。

### Cambium Networks

1. cnMaestro またはアクセスポイントの Web インターフェースでシステム設定を開き、syslog サーバーの設定を探します。
2. プローブの IP アドレスを syslog サーバーとして入力し、ポートの入力欄があれば `5140` を指定して、syslog の重大度を **Info** に設定します。

ポートを設定できない場合、アクセスポイントはポート 514 に送信します。[設定方法](#設定方法) の手順 2 のとおり、プローブのポートをそこに公開してください。

### その他のデバイス

デバイスにリモート syslog サーバーを追加します。プローブの IP アドレス、ポート 5140、UDP または TCP で、情報レベル以上のメッセージを送信するようにします。OneUptime が形式を知らないデバイスのメッセージも保存され、そのイベントには自分で名前を付けられます。

## アラート

イベントページの **アラートを作成** には、ほとんどのネットワークで必要になるアラートが並びます。どれを選んでも、入力済みの **モニターを作成** が開き、保存する前に自由に変更できます。

| アラート | 通知の条件 | アラートの単位 | 閉じる条件 |
| --- | --- | --- | --- |
| VPN トンネルがダウンしたとき | `vpn.tunnel_down` | デバイスとトンネルごと | そのトンネルの `vpn.tunnel_up` |
| ファイアウォールまたはスイッチがフェイルオーバーしたとき | `ha.failover` | デバイスごと | 次の発生がないまま 5 分経過 |
| WAN リンクがダウンしたとき | `gateway.down` | デバイスとゲートウェイごと | そのゲートウェイの `gateway.up` |
| ルーティングネイバーがダウンしたとき | `routing.neighbor_down` | デバイスとネイバーごと | そのネイバーの `routing.neighbor_up` |
| デバイスが再起動したとき | `device.reboot` | デバイスごと | 次の発生がないまま 5 分経過 |
| ハードウェアが故障したとき | ファン、電源、または温度 | デバイスとコンポーネントごと | 同じコンポーネントが正常に戻ったと報告される |
| インターフェースがダウンしたとき | `interface.down` | デバイスとインターフェースごと | そのインターフェースの `interface.up` |
| 誰かがサインインに失敗し続けたとき | 10 件を超える `auth.login_failed` が 5 分間に発生 | デバイスごと | 10 件以下のまま 5 分経過 |

いずれも、直近 5 分間のイベントを数える [ログモニター](/docs/monitor/logs-monitor) です。**Group by Attributes** が設定されているので、トンネル、ゲートウェイ、インターフェースごとに別々のアラートになり、**解決する属性** には問題の解消を知らせるイベントが設定されています。このようなアラートは、同じデバイスの同じトンネルについてそのイベントが届くまで、どれだけ時間がかかっても開いたままです。[ログによる解決](/docs/monitor/logs-monitor#ログによる解決) を参照してください。温度が正常に戻ったことを知らせるイベントを OneUptime は読み取らないため、温度のアラートは自分で解決するまで開いたままです。

デバイスの **イベント** タブから作成したモニターは、そのデバイスだけを監視します。それ以外のイベントについては、イベントページでイベントを開き、**このイベントのアラートを作成** をクリックします。アラートをどこかに送信したり、担当者を呼び出したりするには、ほかのモニターと同じように、モニターにオンコールポリシーやワークフローを追加します。

## まだデバイスになっていないアドレス

syslog は、送信元のデバイスが OneUptime に追加される前に届くことがあります。自分のプローブでは、その syslog は保持され、イベントはデバイスが名乗る名前でネットワークのイベントページに表示され、アドレスは **syslog を送信中、まだデバイスではない** に **まだデバイスではありません** と付いて表示されます。

- **デバイスとして追加** を選ぶと、アドレスとプローブが入力済みの **デバイスを追加** が開きます。すでに届いたメッセージはネットワークのページに残り、新しいメッセージはデバイスのものになります。
- **自分のデバイスの 1 つです** を選ぶと、そのアドレスがデバイスの **その他のアドレス** に追加されます。追加済みのデバイスがループバックなど別のアドレスから送信しているときに使います。メッセージは次の 1 分以降、そのデバイスのものになります。

1 つの NAT アドレスの背後に複数のデバイスがある場合、そのアドレスは共有されるため、メッセージが自分のデバイスを指していない限り、メッセージはそのアドレスを持つ 1 台のデバイスのものになります。

## 独自のイベント

OneUptime が形式を知らないデバイスや、読み取らないイベントには、[ログパイプライン](/docs/telemetry/log-pipelines) を使います。

1. `attributes.networkDevice.name = 'rack-ups'` のように、フィルターがそのデバイスのログに一致するパイプラインを作成します。
2. **Grok パーサー** または **Key=Value Parser** を追加して、必要なフィールドをメッセージから取り出します。
3. **ターゲット属性** を `event.name` にした **カテゴリプロセッサ** を追加し、イベントごとにルールを 1 つ作ります。ルールの名前は、上のイベントと同じように、小文字とドットまたはアンダースコアで付けます（例：`ups.on_battery`）。

そのような名前の付いたネットワークデバイスのログは、ネットワークイベントになります。イベントページに表示され、**このイベントのアラートを作成** も使えます。何についてのイベントかを示すには、自分のフィールドをイベントの表にある属性のいずれか（`hw.name` など）にコピーする **属性リマッパー** を追加します。パイプラインで `event.kind` を `problem` または `recovery` に設定しない限り、イベントは **情報** に表示されます。`interface.down` のように組み込みイベントと同じ名前を付けたルールは、種類もアラートもそのままの組み込みイベントになります。

パイプラインはプロジェクトに属します。別のプロジェクトで使うには、同じプロセッサーでそのプロジェクトに作成してください。

## 含まれないもの

- **TLS 経由の syslog**（RFC 5425）。プローブが受け付けるのは平文の UDP と TCP です。デバイスとプローブの間の経路は、信頼できるネットワーク内に置いてください。
- **プロジェクト間でのパーサーの共有。** パイプラインのエクスポートとインポートにはまだ対応していません。
- **標準の 4 種類以外の SNMP トラップからのイベント。** ベンダー独自のトラップはログとして保存され、**SNMP Trap Received (Trap OID)** 条件を使って [ネットワークデバイスモニター](/docs/monitor/network-device-monitor) でアラートを設定できます。
- **Cambium cnMatrix スイッチ、Aruba モビリティコントローラー、CEF モードの FortiGate。** メッセージは保存され、検索できますが、イベントはまだ読み取られません。
- **ライブテール。** イベントページには、開いた時点までに届いたものが表示されます。更新ボタンを使うか、**ログ** のライブテールを使ってください。

## トラブルシューティング

イベントページに設定手順が表示されたままの場合：

- **プローブは何か受信していますか？** ネットワークのイベントページの **syslog を送信中、まだデバイスではない** に、期間内に syslog を送ったすべてのアドレスが表示されます。デバイスがそこにある場合、ホスト名ではないアドレスから送信しています。そのアドレスをデバイスの **その他のアドレス** に追加してください。
- **ファイアウォールと Docker。** デバイスからプローブへのポート 5140 を許可し、プローブが Docker で動いている場合はポートを公開してください。多くのデバイスは、指定しなければポート 514 に送信します。
- **プローブのログ。** プローブは起動時に、待ち受けているポート、またはポートを開けなかったことをログに記録します。`PROBE_SYSLOG_RATE_LIMIT_PER_MINUTE` を超えてメッセージを破棄したときは、その件数を 1 分に 1 回記録します。
- **グローバルプローブ。** グローバルプローブでポーリングされているデバイスは、プライベートネットワークからそのプローブに syslog を送れません。デバイスのネットワーク内でカスタムプローブを動かし、デバイスの設定で選択してください。
- **メッセージは届くのに、イベントがない。** ページにそのように表示され、すべてのメッセージはデバイスの **ログ** タブにあります。デバイスがエラーだけでなく情報レベルのメッセージも送信していること、製品が [OneUptime が読み取るもの](#oneuptime-が読み取るもの) のいずれかであることを確認してください。そうでなければ、ログパイプラインでイベントに名前を付けます。
