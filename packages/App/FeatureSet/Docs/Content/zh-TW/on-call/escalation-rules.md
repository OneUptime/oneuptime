# 上報規則

待命策略會依級別呼叫人員。每條上報規則就是一個級別：呼叫誰，以及在呼叫下一級之前等待有人確認多久。策略的規則會依序列在其 **上報規則** 頁面上。

```mermaid title="待命策略逐級呼叫，直到有人確認"
flowchart TB
    trigger["事件或警示"] --> level1["Level 1 呼叫"]
    level1 --> ack1{"及時<br/>確認了嗎？"}
    ack1 -->|"是"| stop["停止呼叫"]
    ack1 -->|"否"| level2["Level 2 呼叫"]
    level2 --> ack2{"及時<br/>確認了嗎？"}
    ack2 -->|"是"| stop
    ack2 -->|"否，最後一級"| repeat{"重複策略？"}
    repeat -->|"是"| level1
    repeat -->|"否"| done["策略停止"]
```

:::cards
- [首先呼叫誰](#首先呼叫誰): 建立含第一個級別的策略。
- [新增上報規則](#新增上報規則): 逐步新增下一個級別。
- [各級別如何呼叫人員](#各級別如何呼叫人員): 時間、重複，以及如何聯絡到每個人。
- [輪換中的下一個人](#上報給輪換中的下一個人): 從同一輪換中呼叫待命人員的後援人員。
- [升級呼叫](#升級呼叫): 無法處理呼叫？立即呼叫下一級。
- [API 與 Terraform](#使用-api-或-terraform-建立規則): 以程式碼建立策略與規則。
:::

## 首先呼叫誰

在 **待命策略** 頁面建立待命策略時，表單會詢問它的 **名稱** 與 **首先通知誰？** 。這個問題使用與 **通知** 相同的選擇器：待命排程、團隊和人員，需要多少就選多少。所選對象會成為策略的第一條上報規則 **Level 1** ，在呼叫下一級之前等待確認 **30 分鐘** 。

:::steps
1. 前往 **待命** > **待命策略** ，然後點選 **建立待命策略** 。
2. 輸入 **名稱** 。
3. 在 **首先通知誰？** 下點選 **新增回應者** ，選擇首先要呼叫的待命排程、團隊和人員。
4. 點選 **建立待命策略** 。新策略隨後會在其 **上報規則** 頁面開啟，你可以在那裡新增更多級別。
:::

**首先通知誰？** 是選填的。留空時，策略會在沒有上報規則的情況下開始：在你新增規則之前，它不會呼叫任何人，其概覽也會提示這一點。描述和標籤位於 **更多欄位** 下。只有可以新增上報規則的人才會看到這個問題。

## 新增上報規則

:::steps
### 開啟策略的上報規則

開啟待命策略，在側邊選單中選擇 **上報規則** ，然後點選 **新增上報規則** 。對話方塊只有簡短的一頁。

### 選擇通知對象

在 **通知** 下點選 **新增回應者** ，搜尋並選擇此級別要呼叫的待命排程、團隊和人員，需要多少就選多少。至少新增一個。

| 回應者 | 此級別執行時呼叫誰 |
| --- | --- |
| **待命排程** | 此級別執行時在其中待命的人，而不是固定的某個人。 |
| 待命排程的 **輪換中的下一個人** | 該排程中排在目前待命人員之後的人，來自同一輪換。請參閱 [上報給輪換中的下一個人](#上報給輪換中的下一個人) 。 |
| **團隊** | 團隊的每位成員。 |
| **人員** | 直接呼叫此人。 |

### 設定等待時間

**升級延遲（分鐘）** 是在呼叫下一級之前等待確認的時間。初始值為 **30 分鐘** ，可依該級別的需要修改。

### 如有需要，為規則命名

其他所有內容都在 **更多欄位** 下，開啟之前處於收合狀態：

- **名稱**：選填。未命名的規則以其級別命名：策略的第一條規則是 **Level 1** ，第二條是 **Level 2** ，依此類推。名稱欄位會顯示規則將取得的名稱。
- **描述**：選填的備註，例如此級別呼叫誰以及原因。

收合時， **更多欄位** 的標題會列出這兩項，並顯示規則已設定的內容：描述或你自己取的名稱。

### 建立規則

點選 **建立規則** 。規則會新增在其他規則下方，成為策略的下一個級別。
:::

## 各級別如何呼叫人員

當事件或警示到達策略時， **Level 1** 會立即呼叫其回應者。如果在等待時間內無人確認，就會呼叫 **Level 2** ，依此沿清單往下。當最後一級的等待時間過去仍無人確認時，若策略的 **重複策略** （位於規則下方）要求重複，策略會在允許的次數內從 **Level 1** 重新開始，否則停止。確認或解決事件或警示，會在任何級別停止呼叫。被呼叫但無法處理的人可以升級呼叫，下一級會立即被呼叫，無需等待：參見 [升級呼叫](#升級呼叫) 。

以已確認或已解決狀態建立的事件、警示或片段（即事後補登的）不會執行任何策略：不會呼叫任何人，其 Feed 會記下這一點並列出這些策略。請參閱 [宣告時即已確認或已解決](/docs/incidents/declaring-incidents#宣告時即已確認或已解決) 。

若要重複策略，請在 **重複策略** 卡片上點選 **編輯** ，選擇 **從 Level 1 重新開始** ，並設定 **再重複幾次？** 。

### 上報概要

**上報規則** 頁面頂端的概要會顯示整個階梯：每個級別何時被呼叫、呼叫誰，以及最後一級之後會發生什麼事。若某個級別的回應者無法全部被呼叫，其卡片上會註明；點選標籤即可查看是誰以及原因。

### 如何聯絡到每個人

級別所呼叫的每個人，都依其本人的待命規則聯絡： **使用者設定** > **待命規則** ，其中為事件、事件片段、警示和警示片段各設一個分頁，每個嚴重程度一張卡片，列出嘗試哪種通知方式以及間隔多久。專案管理員可以在 **使用者** > 成員 > **待命規則** 中查看和變更成員的規則。請參閱 [個人待命規則](/docs/notifications/on-call-rules)。

```mermaid title="級別呼叫誰，以及如何聯絡到每個人"
flowchart TB
    subgraph notify["通知"]
        direction LR
        schedule["待命排程"]
        team["團隊"]
        user["人員"]
    end
    schedule -->|"當時待命的人"| person["被呼叫的人"]
    team -->|"每位成員"| person
    user -->|"直接"| person
    person --> rules["其待命規則"]
    rules --> methods["其通知方式"]
```

對某人生效的使用者覆寫，會把其呼叫改送給代班的人。未指定代班人的覆寫會略過此人：不會呼叫此人，策略的執行紀錄會註明此人不在崗及截止時間，在待命排程中，此人的每一輪值班都會交給輪換中的下一個人。請參閱 [使用者覆寫](/docs/on-call/user-overrides)。

每則訊息都是服務供應商會接受的訊息，因此呼叫一定能送出。各管道能承載的內容如下：

| 管道 | 能承載的最長訊息 |
| --- | --- |
| SMS | 1,600 個字元 |
| 電話 | Twilio 4,000 個字元的通話腳本能容納的內容 |
| 推播通知 | 4 KB，其中標題、內文和資料最多占 3 KB |
| WhatsApp | 1,024 個字元 |
| Telegram | 4,096 個字元 |

更長的訊息（標題很長，或範本放入了很長的描述）會被截斷，並以一則說明全文在 OneUptime 中的提示結尾："… (truncated — see OneUptime for the full text)"。WhatsApp 訊息的措辭是固定範本，因此在那裡截斷的是最長的那些值，每個都以 "…" 結尾。訊息中的連結永遠不會被截斷。

### 呼叫簡訊的內容

簡訊按每段 160 個字元傳送並計費。以簡訊傳送的呼叫會盡可能寫成一段，只說明在鎖定的手機上需要知道的內容：誰傳送的、發生了什麼，以及用來確認或升級該呼叫的唯一連結。在手機上顯示如下：

```text
OneUptime: Critical Incident INC-42 in Acme Prod: Checkout API is down.
Ack or escalate: https://oneuptime.com/l/XJlaZRsd
```

簡訊依序寫明嚴重程度和發生的情況（事件、警示，或其中之一的片段）、編號、專案和標題。當這些內容無法全部放進一段時：

1. 首先省略專案。
2. 接著截斷標題，並以 `...` 結尾。

嚴重程度、編號和連結永遠不會被截斷。標題至少保留 20 個字元：如果連這些也放不下，例如位址或產品名稱很長，簡訊就會占用第二段，把內容全部寫出。

當策略因已確認的事件或警示仍未解決而再次通知時，簡訊會在編號和專案之後寫明這一點，這幾個字也永遠不會被截斷：

```text
OneUptime: Critical Incident INC-42 in Acme Prod is still not resolved:
Checkout API is down. Ack or escalate: https://oneuptime.com/l/XJlaZRsd
```

只要有一個字元不在簡訊的基本字元集中，整則訊息就會按每段 70 個字元傳送。因此，彎引號和破折號會寫成 `"` 、 `'` 和 `-` ， `…` 寫成 `...` ，像 `ç` 和 `ł` 這樣的字母會去掉重音符號；表情符號會被省略。以其他文字（例如日文或俄文）撰寫的標題會照原樣傳送，占用兩段或更多。

OneUptime 傳給你的其他簡訊，例如你作為擁有者的事件有所變更，或你的待命班次開始時的簡訊，也以 `OneUptime:` 開頭，以 `Turn off in User Settings > Notification Settings.` 結尾；如果去掉這句話才能放進一段，這句話就會被省略。

### 呼叫未送出時

未送出的呼叫會在此人的 **待命日誌** （使用者設定）中說明原因：該列顯示 **錯誤** ，狀態訊息會說明原因。它不會再停留在 **傳送中** 。訊息會說明以下之一：

- 專案餘額不足以支付，以及誰可以加值；
- 專案中該管道已關閉，以及誰可以開啟它。

專案擁有者會就此收到一封電子郵件，直到餘額加值或管道重新開啟。

在 OneUptime Cloud 上，每則簡訊、每通電話、每則 WhatsApp 和 Telegram 訊息都從 **專案設定 > 通知 > 通知設定** 上的專案餘額支付：服務供應商接受訊息時，確切費用就會從餘額扣除，不論同時送出多少則訊息。

- 若那裡開啟了 **自動儲值** ，發現餘額低於門檻的那則訊息會先儲值自動儲值所設定的金額，並向專案的卡片扣款；在同一時刻發現餘額不足的多則訊息只會扣款一次。
- 若扣款失敗（沒有付款方式或卡片遭拒），自動儲值會在一小時後再次嘗試扣款，在此之前 **通知設定** 頂端會提示這一點。手動加值或再次儲存自動儲值會立即重試。
- 在自動儲值無法扣款期間，呼叫會繼續使用剩餘餘額送出。

> [!IMPORTANT]
> 新專案中的簡訊、電話、WhatsApp 和 Telegram 預設為關閉：在 OneUptime Cloud 上，每則訊息都從專案餘額支付；自行託管的安裝則需要先設定 Twilio 帳戶或 Telegram 機器人。管道關閉期間，專案中的任何人都無法在該管道上新增通知方式。只有專案擁有者、 **帳單管理員** 或擁有 **Manage Billing** 權限的人才能開啟管道，位置在 **專案設定 > 通知 > 通知設定** 上的 **通知管道** 卡片中——專案管理員不能。在管道關閉的每個地方，其他所有人都會被確切告知誰可以開啟：在他們自己該管道的通知方式清單上方、在他們的設定檢查清單中，以及在需要該管道時他們收到的訊息中。

## 上報給輪換中的下一個人

一個級別可以呼叫待命排程輪換中的下一個人，也就是該排程中排在目前待命人員之後的人。這樣，策略只需一個待命排程，就能先呼叫待命人員，再呼叫同一輪換中的後援人員，然後呼叫團隊或經理。

| 級別 | 通知 | 呼叫誰 |
| --- | --- | --- |
| **Level 1** | Payments primary 待命排程 | 在其中待命的人，例如 Alex |
| **Level 2** | 同一排程的 **輪換中的下一個人** | 輪換中排在 Alex 之後的人，例如 Sam |
| **Level 3** | Platform 團隊 | 團隊的每位成員 |

:::steps
1. 確認策略的第一級 **Level 1** 會通知該待命排程。
2. 點選 **新增上報規則** ，再點選 **新增回應者** ，在 **輪換中的下一個人** 下選擇同一個待命排程。設定 **升級延遲（分鐘）** ，然後點選 **建立規則** 。
3. 再新增一個級別，給接下來應收到通知的團隊或經理。
:::

下一個人在該級別執行時決定，依據的是當時的待命排程：

- 是排在目前待命人員之後的人，依輪換成員輪流待命的順序。最後一人之後又回到第一人。
- 不在崗的人會被略過，無論是否有人代班；代替他人待命的人也會被略過。
- 一定是同一輪換中的人：有多個層時，是目前待命人員所在的層。輪換中沒有其他人，或其他人都不在崗時，就沒有下一個人，該級別不會在那裡呼叫任何人，並會註明這一點。
- 待命排程中完全沒有人待命時，也就沒有下一個人，該級別會在幾分鐘內重試，與待命排程本身相同。

策略執行在 Slack 和 Microsoft Teams 中的訊息、事件的 Feed 以及 **執行時間軸** 都會註明誰以輪換中的下一個人身分被呼叫，以及來自哪個待命排程："Sam Lee (next in the Payments primary rotation)"。

> [!TIP]
> 一個待命排程就夠了：不必再維護一個與第一個保持同步的後援排程，其成員登記的不在崗時間對兩個級別都有效。

## 升級呼叫

被呼叫的人如果因為正在睡覺、在飛機上或已經在處理另一個事件而無法處理，可以升級呼叫，而不是任其一直響下去。策略會立即呼叫下一級，無需等待該級別的 **升級延遲（分鐘）** 結束，此人也不會再因此被呼叫。

```mermaid title="升級呼叫會讓策略立即進入下一級"
flowchart TB
    page["Level 1 呼叫 Alex"] --> take{"Alex 能<br/>處理嗎？"}
    take -->|"能"| ack["Alex 確認：<br/>呼叫停止"]
    take -->|"不能"| pass["Alex 升級呼叫"]
    pass --> others{"Level 1 上還有<br/>其他人被呼叫嗎？"}
    others -->|"有"| wait["策略照舊<br/>等待他們"]
    others -->|"沒有"| next["立即呼叫<br/>Level 2"]
```

每次呼叫都可以從它到達你的地方升級：

| 位置 | 如何升級 |
| --- | --- |
| 郵件 | 點選 **Escalate** 按鈕，然後在開啟的頁面上點選 **Escalate** |
| 簡訊和 WhatsApp | 訊息中的連結會開啟確認頁面，那裡也有 **Escalate** |
| Telegram、Slack 和 Microsoft Teams | 開啟 "Can't take it? Escalate" 連結，然後在開啟的頁面上點選 **Escalate** |
| 電話 | 按 2。電話隨後會說明發生了什麼 |
| 推播通知 | 點選它：事件、警示或片段會在 OneUptime On-Call 應用程式中開啟，下方有 **Escalate** |
| OneUptime | 事件、警示或片段頂部、狀態按鈕之後的 **升級** |

除電話外，每種方式都會在執行任何操作前先詢問，並說明將會發生什麼，例如 "This will immediately page Platform leads (Level 2 of 3), without waiting."；在電話中，按 2 就是回答。只有被呼叫的人才能升級自己的呼叫：OneUptime 中的按鈕只對本人顯示，訊息中的連結只能升級該訊息所涉及的呼叫，只對收件人本人有效，有效期為 7 天。

接下來會發生什麼，取決於還有誰正在被呼叫：

- 同一級別上還有其他人正在被呼叫：策略照舊等待他們。當該級別的等待時間結束，或其中最後一人也升級了呼叫時，策略才會繼續。
- 該級別上沒有其他人了：立即呼叫下一級。
- 這是最後一級：如果 **重複策略** 要求重複，策略會立即從 **Level 1** 重新開始；否則呼叫停止，需要有人來處理。

升級呼叫並不等於確認：事件或警示仍在等待有人確認，升級的人自己也仍然可以確認。本次執行不會再因此呼叫此人：之後的級別或重複中如果包含此人，會略過此人。當策略呼叫的所有人都已升級、再無人可呼叫時，呼叫停止，事件的 Feed 會註明這一點。

工作流程直接傳給相關人員的呼叫沒有級別：升級後你不會再被呼叫，當它呼叫的所有人都已升級時，呼叫停止。

每次升級都會被記錄。執行的 **執行時間軸** 會把此人的那一列標為 **已升級** ，事件的 Feed 會寫 "Alex Kim escalated the page from on-call policy Payments at Level 1 of 3."，策略執行在 Slack 和 Microsoft Teams 中的訊息會註明此人已升級，此人的 **待命日誌** 也會把這次呼叫顯示為 **已升級** 。

## 編輯、重新排序和刪除規則

每條規則的卡片上都有 **編輯規則** ，以及包含其他操作的 **⋯** 選單：

- **編輯規則** 會開啟同樣的單頁對話方塊，並依規則目前的內容填好：回應者、等待時間，以及 **更多欄位** 下的名稱和描述。新增或移除回應者，然後點選 **儲存變更** 。清空名稱會讓規則重新取得其級別的名稱。
- 規則 **⋯** 選單中的 **上移** 和 **下移** 會改變它的級別。以級別命名的規則會保持與其位置相符的名稱：當 **Level 3** 上移到 **Level 2** 之上時，兩者互換名稱。你自己選擇的名稱，例如 **經理** ，無論規則移到哪裡都保持不變。
- **刪除規則** 會先詢問確認，並說明該級別呼叫誰。刪除一個級別後，其下方的級別會上移，以級別命名的規則會相應重新命名。

## 使用 API 或 Terraform 建立規則

上報規則是 `/api/on-call-duty-policy-escalation-rule` 資源；規則所呼叫的人員、團隊和排程是 `/api/on-call-duty-policy-escalation-rule-user` 、 `-team` 和 `-schedule` 資源。

- 不帶 `name` 建立的規則會像在儀表板中一樣以其級別命名：成為策略第三級的規則命名為 **Level 3** 。Terraform 的上報規則資源仍然需要名稱。
- `escalateAfterInMinutes` 在儀表板之外沒有預設值。不帶它建立的規則不會等待：此級別執行後會立即呼叫下一級。請明確設定它——儀表板建議的值是 30。
- 在 `miscDataProps` 中帶 `onCallSchedules` 、 `teams` 或 `users` （ID 清單）建立的規則會取得這些回應者，儀表板的 **通知** 選擇器就是這樣傳送它們的。不帶它們建立的規則，在你透過上述資源新增回應者之前不會呼叫任何人。
- 在 `miscDataProps` 中帶 `nextInRotationSchedules` （待命排程 ID 清單）建立的規則，會呼叫其中每個待命排程輪換中的下一個人。在 `-schedule` 資源上， `pageNextInRotation` 設為 `true` 的列作用相同；此值在建立該列時設定。
- 以級別命名的規則只會在你於儀表板中移動或刪除規則時重新命名。透過 API 或 Terraform 變更 `order` 只會改變順序。
- 在 `/api/on-call-duty-policy` 建立待命策略時，在 `miscDataProps` 中帶上 `onCallSchedules` 、 `teams` 或 `users` （ID 清單），會像儀表板一樣為它建立第一條上報規則：呼叫這些對象的 **Level 1** ， `escalateAfterInMinutes` 為 30。每個 ID 都必須屬於該專案，呼叫端必須有權建立上報規則，否則不會建立策略。不帶它們建立的策略和以前一樣沒有規則；Terraform 的策略資源不會傳送它們。

```bash
curl -X POST https://oneuptime.com/api/on-call-duty-policy \
  -H "apikey: $ONEUPTIME_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "data": {
      "projectId": "<project-id>",
      "name": "Production on-call"
    },
    "miscDataProps": {
      "onCallSchedules": ["<schedule-id>"],
      "users": ["<user-id>"]
    }
  }'
```
