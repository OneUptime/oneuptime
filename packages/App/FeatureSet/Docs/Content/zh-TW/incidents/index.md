# 事件概觀

OneUptime 裡的事件，就是出狀況時整個團隊集結圍繞的那筆紀錄。它帶著一個編號、一個標題、一個嚴重程度、一個當前狀態、它所影響的資源，以及團隊在應變過程中寫下的所有東西——備註、根本原因、補救步驟，還有一條只能追加、記錄誰做了什麼的動態時間軸。

事件是把「監測器變紅」轉成一次有默契的應變的關鍵。宣告一個事件，會呼叫到對的待命輪值、加入會收到每一項變更通知的擁有者、啟動 runbook，而且——只要你要——把這次中斷發佈到公開狀態頁面，讓客戶不用再開工單問你知不知道。

你可以在凌晨三點親手宣告一個事件，也可以讓監測器在條件相符的當下替你宣告。走哪一條路都一樣：同一個物件、同一套生命週期，最後留下同一份紀錄。

## 一覽

- **頂層功能** —— 儀表板左側導覽中的 **事件**，路徑為 `/dashboard/{projectId}/incidents`。
- **三個預設狀態** —— 每個新專案都會建立 **已識別**、**已確認** 與 **已解決**。你可以自行新增狀態；這三個預設狀態可以改名、換顏色，但永遠不能刪除。
- **三個預設嚴重程度** —— **嚴重事件**、**重大事件** 與 **輕微事件**。嚴重程度只是一個有顏色和排序的標籤，它本身不帶任何行為。
- **四種建立方式** —— **宣告事件** 精靈、**從範本建立**、監測器條件規則，或 `POST /api/incident`。
- **依專案編號** —— 每個事件都會拿到一個事件編號，預設顯示成 `#42`，也可以加上你自己的前綴，例如 `INC-42`。
- **兩種備註** —— 給團隊看的私人備註（內部備註），以及給狀態頁面訂閱者看的公開備註。
- **設定在「事件」底下，不在專案設定裡** —— 狀態、嚴重程度、範本、自訂欄位和各種規則引擎，全都在 **事件 → 設定** 與 **事件 → 規則** 之下。

## 關鍵術語

本節後面每一頁都會反覆出現這幾個詞。先把它們弄清楚。

| 術語                   | 意義                                                                                                                       |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **事件**               | 紀錄本身——標題、描述、嚴重程度、當前狀態、受影響的資源，以及應變期間寫在上面的一切。                    |
| **事件狀態**           | 事件在生命週期中的位置。一筆專案範圍的資料列，帶有名稱、顏色和 `order`，再加上賦予它意義的旗標。         |
| **事件嚴重程度**       | 事情有多嚴重。一筆專案範圍的資料列，帶有名稱、顏色和 `order`。純粹是分類——產品裡沒有任何地方會特別對待某個嚴重程度。 |
| **事件編號**           | 每個專案各自的計數器，顯示成 `#42`，或是加上你設定的前綴後顯示成 `INC-42`。                            |
| **受影響的資源**       | 你掛到事件上的監測器、主機、Kubernetes 叢集、Docker 主機、服務和其他基礎架構。                        |
| **公開備註**           | 寫給狀態頁面讀者與訂閱者看的更新。它會呈現在狀態頁面的時間軸上。                                   |
| **私人備註**           | 給應變團隊看的內部備註（`IncidentInternalNote` 模型）。它永遠不會出現在狀態頁面上。                 |
| **擁有者**             | 對事件負責的使用者或團隊。事件建立時、有人張貼備註時、狀態變更時，擁有者都會收到通知。         |
| **事件 動態消息**      | 事件 **概覽** 上只能追加的活動時間軸，記錄狀態變更、備註、擁有者異動、規則執行與通知。            |
| **狀態時間軸**         | 記錄事件在什麼時候處於什麼狀態、待了多久——以及每次轉換的訂閱者通知狀態。                          |

## OneUptime 為每個專案預先建立的三個狀態

專案建立時，OneUptime 會依這個順序建立正好三個事件狀態：

| 狀態         | 順序  | 顏色              | 意義                                                       |
| ------------ | ----- | ----------------- | ---------------------------------------------------------- |
| **已識別**   | 1     | 紅色（`#fd625e`） | 全新事件會落到的狀態，也就是所謂的建立狀態。               |
| **已確認**   | 2     | 黃色（`#ffbf53`） | 有人接手了這個事件，正在處理中。                           |
| **已解決**   | 3     | 綠色（`#2ab57d`） | 事件結束了。把事件解決，才會讓它從狀態頁面上撤下來。       |

名稱只是標籤——真正驅動行為的是狀態資料列上的三個布林值：`isCreatedState`、`isAcknowledgedState` 和 `isResolvedState`。每個專案的每個旗標，預期都只由一個狀態持有。

這個區別比聽起來更要緊：

- `isCreatedState` 決定新事件從哪裡開始。建立時如果沒有明確選狀態，OneUptime 會去找專案的建立狀態並套用它。
- `isAcknowledgedState` 和 `isResolvedState` 驅動事件標頭上的 **Acknowledge** 與 **解決** 按鈕、事件 **概覽** 上的兩塊統計方塊，以及側邊選單裡的 **進行中事件** 計數徽章。
- **進行中事件** 的定義單純就是「當前狀態不是已解決狀態」。因此你新增的任何自訂狀態，只要不是已解決狀態，都算進行中。

**留意命名。** 第一個預設狀態叫 **已識別**，儘管產品裡有幾處說明仍稱它為建立狀態。如果你在專案的狀態清單裡找「Created」，那就是名為 **已識別** 的那一列。

你可以在 **事件 → 設定 → 事件狀態** 新增自己的狀態。新狀態會被加到排序清單的最後，你可以拖曳來重新排列。三個帶旗標的狀態無法刪除——OneUptime 會擋下來——但可以改名和換顏色，這也是為什麼介面上的狀態名稱是動態讀取的。

順序是會被強制執行的，不只是好看：事件不能移動到順序比當前狀態更前面的狀態。

完整細節請見 [事件狀態與嚴重程度](/docs/incidents/states-and-severities)。

## OneUptime 為每個專案預先建立的三個嚴重程度

每個新專案也會拿到三個嚴重程度：

| 嚴重程度       | 順序  | 顏色                | 意義                                       |
| -------------- | ----- | ------------------- | ------------------------------------------ |
| **嚴重事件**   | 1     | 暗紅色（`#b70400`） | 客戶受到非常高的影響，需要立刻應變。       |
| **重大事件**   | 2     | 紅色（`#fd625e`）   | 影響顯著，通常需要立刻應變。               |
| **輕微事件**   | 3     | 黃色（`#ffbf53`）   | 影響輕微，通常在上班時間處理即可。         |

預設的完整描述在 [事件狀態與嚴重程度](/docs/incidents/states-and-severities) 裡。

嚴重程度只有 `name`、`description`、`color` 和 `order`，就這些。沒有旗標，也沒有任何程式碼路徑會把「嚴重事件」跟其他資料列區別對待。嚴重程度是給人分類用的，而且在你撰寫待命規則時可以拿來當比對條件——但選一個嚴重程度，本身不會呼叫任何人。

要編輯或新增嚴重程度，請到 **事件 → 設定 → 事件嚴重性**。

## 事件的一生

### 1. 事件被宣告

四條路通往同一個物件：

- **手動建立** —— 在事件清單中點 **宣告事件**。這會開啟 **宣告新事件** 精靈，共五個步驟：**事件詳細資訊**、**受影響的資源**、**事件角色**、**待命**、**更多**。
- **從範本建立** —— 點 **從範本建立**，挑一個已存的 **事件範本**。範本會預先填好標題、描述、嚴重程度、初始狀態、資源、待命策略、擁有者和標籤。
- **由監測器建立** —— 開啟了「宣告事件」開關的監測器條件規則，會在篩選器相符的當下自動建立事件。那裡的標題和描述支援 `{{variable}}` 樣板語法。
- **透過 API** —— 帶著 API 金鑰呼叫 `POST /api/incident`。伺服器會替你填上 `declaredAt`、建立狀態和事件編號。

逐欄位的操作說明請見 [宣告事件](/docs/incidents/declaring-incidents)。

### 2. 對的人收到消息

事件建立時，OneUptime 會執行你設定好的自動化：標籤規則、待命規則、擁有者規則和 runbook 規則。掛在事件上的所有待命職責策略——不論是手動加的、從範本來的，還是由相符的待命規則併進來的——都會平行執行。

擁有者會收到電子郵件、簡訊、電話、推播和 WhatsApp 通知，實際送出什麼取決於每位使用者自己的通知偏好。如果一個事件完全沒有擁有者，通知會退回給專案擁有者，而不是直接丟掉。

如果事件在某個狀態頁面上可見，而且訂閱者通知是開啟的，訂閱者也會收到消息。通知由 cron 驅動、每分鐘執行一次，所以請預期最多約一分鐘的延遲，而不是即時送達。

### 3. 團隊開始處理

應變人員會確認事件、掛上受影響的資源、執行 runbook、指派事件角色，並隨著理解加深把東西寫下來——給團隊的私人備註、給客戶的公開備註，以及在輪廓逐漸清楚後填寫的 **根本原因** 與 **補救** 頁面。他們做的每一件事，都會落到 **概覽** 頁面的 **事件 動態消息** 裡。

### 4. 事件被解決

點 **解決** 會把事件移到已解決狀態、在狀態時間軸上蓋章、停止持續時間的計時，並把事件從它所出現的任何狀態頁面的進行中區塊移除。要達成這些，其他東西都不必改——狀態頁面查詢看的就是已解決狀態旗標。

之後你可以撰寫事後分析，並且視需要把它發佈到狀態頁面。

## 事件在儀表板中的位置

在左側導覽開啟 **事件**。它的側邊選單分成幾個區段：

| 區段         | 你在這裡做什麼                                                                                                                   |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| **概覽**     | **所有事件** 與 **進行中事件**——後者會帶一個紅色徽章，顯示不在已解決狀態的事件數量。                                          |
| **片段**     | 事件片段，一個有自己頁面的獨立分組功能。                                                                                         |
| **人工智慧** | **調查** 與 **補救**——自動調查與自動補救的設定。                                                                                 |
| **工作區**   | 事件用的 **Slack** 與 **Microsoft Teams** 連線。                                                                                 |
| **規則**     | 各種規則引擎：**分組規則**、**待命規則**、**擁有者規則**、**Runbook 規則**、**隱私規則**、**標籤規則**、**SLA 規則**、**Reminder Rules**。 |
| **設定**     | **事件狀態**、**事件嚴重性**、**事件範本**、**備註範本**、**事後分析範本**、**自訂欄位**、**事件角色**、**更多設定**。            |

**規則** 與 **設定** 預設是收合的——展開它們才會看到本文件其餘部分提到的頁面。事件的設定不在專案設定裡，全都在這裡。

事件清單本身會顯示 **事件編號**、**標題**、**狀態**、**嚴重程度**、**受影響的資源**、**已宣告**、**持續時間**、**標籤** 與 **擁有者**，並提供 **變更狀態** 批次操作，一次收掉好幾個事件。

## 事件的每一頁顯示什麼

打開一個事件，左側會出現一個側邊選單，分組如下：

- **概覽** —— **事件詳細資訊** 卡片（標題、嚴重程度、標籤、事件編號、宣告時間、宣告者、待命策略）、**受影響的資源** 卡片，以及 **事件 動態消息**。上方還有確認耗時、解決耗時和總 **持續時間** 的統計方塊。
- **狀態時間軸** —— 事件待過的每一個狀態，附上 **開始**、**結束**、**持續時間**，以及每次轉換的訂閱者通知狀態。**檢視原因** 與 **檢視日誌** 會說明每次變更為什麼發生。
- **SLA** —— 這個事件的 SLA 追蹤。
- **描述**、**根本原因**、**補救** —— 三個 Markdown 頁面。會顯示在狀態頁面上的是描述。
- **運行手冊** —— 掛在這個事件上的 runbook 執行紀錄。
- **事後分析** —— 事後的完整撰寫，你可以選擇發佈到狀態頁面。
- **角色**、**待命執行**、**擁有者** —— 誰在處理、哪些策略被觸發、誰會收到通知。
- **通知日誌**、**AI 日誌**、**稽核日誌** —— 送出了什麼、改動了什麼。
- **私人備註** 與 **公開備註** —— 在側邊選單的 **備註** 區段下。
- **自訂欄位**、**設定**、**刪除事件** —— 在 **進階** 之下。**設定** 頁面收錄了 **於狀態頁面可見**、**私人事件** 和 **Reminders** 卡片。

[事件備註、負責人與動態](/docs/incidents/notes-owners-and-feed) 深入說明這些協作頁面。

## 事件如何與 OneUptime 的其他部分搭配

- **監測器發現問題，事件記錄問題。** 監測器條件規則可以自動宣告事件，並預先填好標題、嚴重程度、待命策略、擁有者、標籤和補救備註。那裡可用的變數請見 [事件與警示範本](/docs/monitor/incident-alert-templating)。
- **待命策略負責呼叫人。** 你可以在宣告精靈的 **待命** 步驟、在範本上，或透過 **事件 → 規則 → 待命規則** 掛上策略。所有相符的規則都會觸發——實際執行的集合，是所有相符結果加上直接掛上去的策略，去重之後的聯集。
- **Runbook 告訴大家該做什麼。** Runbook 規則會在相符的事件建立時自動掛上並啟動程序，應變人員也可以從事件裡手動啟動。請見 [Runbook 概觀](/docs/runbooks/index)。
- **狀態頁面負責告訴客戶。** 當狀態頁面啟用了事件顯示、事件被標為在狀態頁面上可見，而且當前狀態不是已解決狀態時，事件就會出現在該頁面的進行中清單裡。私人事件則永遠不會出現在任何狀態頁面上。請見 [狀態頁概觀](/docs/status-pages/index)。
- **工作流程在周邊自動化。** **On Create Incident**、**On Update Incident** 與 **On Delete Incident** 觸發器，讓你在事件生命週期之上建立免寫程式的自動化。請見 [工作流程概觀](/docs/workflows/index)。
