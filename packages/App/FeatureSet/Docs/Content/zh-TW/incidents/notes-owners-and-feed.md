# 備註、擁有者與動態

每個事件在你處理的過程中都會累積一份書面紀錄。其中一部分是給客戶看的——凌晨 02:14 發到狀態頁面上、說你找到了那次糟糕部署的那則更新。其餘是給團隊看的——某人貼上的堆疊追蹤、那張終於說得通的圖表、決定要做容錯移轉的那個決定。

OneUptime 把這兩種讀者分開。**公開備註** 會發佈到你的狀態頁面，並可以通知訂閱者。**私人備註**（`IncidentInternalNote` 模型）則留在儀表板裡。在兩者之下是 **事件 動態消息**，一條只能追加、記錄事件所有經歷的時間軸；以及 **擁有者** 清單，它決定誰會被告知。

這些全都掛在事件的左側選單上：**備註 → 公開備註**、**備註 → 私人備註**，以及 **團隊 → 擁有者**。動態則在事件的 **概覽** 頁面上。

## 公開備註 vs 私人備註

這兩種備註在儀表板裡看起來很像，行為卻大不相同。

- **公開備註** —— `IncidentPublicNote` 模型，會作為事件時間軸的一部分提供給狀態頁面。它有一個你可以自己設定的 **張貼時間**，以及一個 **通知狀態頁面訂閱者** 核取方塊。
- **私人備註** —— `IncidentInternalNote` 模型。狀態頁面應用程式完全不會讀它。它沒有張貼時間欄位（清單以 `createdAt` 蓋章並排序），也完全沒有訂閱者相關欄位，所以私人備註永遠不可能觸發訂閱者通知。

**「私人」實際上是什麼意思。** 它的意思是「不發佈到狀態頁面」，而不是「只限少數人看」。兩種備註的讀取權限完全相同，所以能讀這個事件的人，就能讀它的私人備註。如果你需要限制誰能看到事件本身，請用事件上的 **私人事件** 旗標（`isPrivate`），它會把事件從所有狀態頁面隱藏，並限制在事件的擁有者使用者、擁有者團隊的成員，以及專案管理員與擁有者。

**擁有者兩種都看得到。** 擁有者通知工作會一起查詢公開和私人備註。私人備註是對訂閱者私密，不是對應變的人私密。

| 如果你想…                                      | 就選             |
| ---------------------------------------------- | ---------------- |
| 告訴客戶你知道什麼、什麼時候會知道更多         | **公開備註**     |
| 補記一則你已經從別的管道發出去的更新           | **公開備註**     |
| 記下一個假設、一條你跑過的指令，或一條死路     | **私人備註**     |
| 附上一份堆積傾印或內部儀表板截圖               | **私人備註**     |

## 張貼公開備註

在事件側邊選單開啟 **備註 → 公開備註**，然後建立一則備註。卡片會說明你在這裡寫的內容會出現在狀態頁面上；空白狀態則會告訴你這個事件目前還沒有任何公開備註。

| 欄位                       | 用途                                                                                     |
| -------------------------- | ---------------------------------------------------------------------------------------- |
| **公開事件備註**           | 備註內文，Markdown 格式。必填。表單會提醒你這則備註會顯示在狀態頁面上，並附上速查表連結。 |
| **附件**                   | 在狀態頁面上與訂閱者共享的檔案。選填。                                                   |
| **通知狀態頁面訂閱者**     | 核取方塊，預設開啟。關掉它就能安靜地發佈。                                               |
| **張貼時間**               | 必填的日期與時間，預設為現在，以你目前的時區顯示。                                       |

**張貼時間才是備註真正的時間戳。** 狀態頁面是依 `postedAt` 排序和顯示公開備註的，不是依你打字的時間——所以如果你是在替狀態頁面補上 40 分鐘前送出的更新，請把 **張貼時間** 設成它實際發生的時間。如果備註透過 API 進來而沒帶這個欄位，OneUptime 會蓋上當下的時間。

清單會顯示每則備註的作者、它的 **張貼時間**、算繪後的 Markdown 及其附件，以及一個 **訂閱者通知狀態** 欄位。你可以用 **建立者**、**備註** 和 **建立於** 篩選。

## 張貼私人備註

**備註 → 私人備註** 刻意做得更樸素。只有兩個欄位：

- **私人事件備註** —— Markdown 內文，必填。表單直白地寫著這是團隊私有的，不會顯示在狀態頁面上。
- **附件** —— 給事件應變團隊看的檔案。

沒有 **張貼時間**，也沒有訂閱者核取方塊——備註在建立時就蓋上時間。

## 備註上的附件

兩種備註都可以透過 **附件** 欄位加上檔案，也都會在備註內文底下呈現一份附件清單，每個檔案附一個 **Download attachment** 連結。

兩者的差別在於誰能取得檔案：

- **公開備註的附件** 可以由狀態頁面訪客透過狀態頁面路由下載，就在備註旁邊。
- **私人備註的附件** 只能透過需要驗證的儀表板 API 取得。狀態頁面沒有對應的路由。

所以附件的公開／私人抉擇，跟備註文字是同一個決定。面向客戶的時間軸圖片放公開備註；設定檔傾印放私人備註。

## 用 AI 產生備註

兩個備註頁面都有一顆 **Generate with AI** 按鈕。它會把事件送到你專案的 AI 提供者，並把產生的 Markdown 放進備註編輯器，你在儲存前可以修改——什麼都不會自動發佈。

- **Generate Public Note with AI** —— 說明中寫的是分析事件資料，產出一則面向客戶的備註。範本包含 **Status Update** 與 **Resolution Notice**。
- **Generate Private Note with AI** —— 產出的則是內部技術備註。範本包含 **Investigation Update** 與 **Technical Analysis**。

按鈕背後，儀表板會帶著選定的範本以及 `public` 或 `internal` 的備註類型，向 `/incident/generate-note-from-ai/{incidentId}` 發出請求。

## 備註範本

如果你的團隊每次中斷都寫同樣那三則更新，那就存一次就好。兩個備註頁面都有一顆 **從範本建立** 按鈕，會開啟 **從範本建立備註** 選擇器，裡面有一個 **選擇備註範本** 下拉選單。

範本是公開與私人備註共用的：同一份範本清單同時服務兩者，而同一個範本可以插入任一種備註。

你在 **事件 → 設定 → 備註範本** 管理它們——卡片標題為 **事件的公開或私人備註範本**，表單有一個 **範本資訊** 步驟（**範本名稱** 與 **範本描述**，兩者皆必填）和一個放內文的 **備註詳細資料** 步驟。如果你在還沒建立任何範本前就點 **從範本建立**，OneUptime 會告訴你目前沒有範本；請注意訊息指向的是專案設定，但這個頁面實際上位於 **事件 → 設定 → 備註範本**。

## 從 Slack 或 Microsoft Teams 張貼備註

如果你連接了工作區，應變人員完全不必離開頻道。Slack 和 Microsoft Teams 都提供一個新增備註的動作，它會開啟一個對話框，裡面有一個提供 **公開備註** 或 **私人備註** 的下拉選單和一個文字框，結果會直接寫到事件上。

有兩個細節值得知道：

- **重複保護** —— 每則備註都會記下它來自哪一則 Slack 訊息（`postedFromSlackMessageId`，格式為 `channel_id:message_ts`），所以好幾個人對同一則訊息按反應，只會產生一則備註，而不是五則。
- **備註會回傳** —— 張貼任一種備註時，也會把一則訊息推到已連接的事件頻道，因為備註的動態項目建立時就啟用了工作區通知。

## 公開備註什麼時候才真的送到訂閱者手上

開著 **通知狀態頁面訂閱者** 建立公開備註，本身並不保證信一定會寄出去。備註得通過一連串檢查，而每一次失敗都會記下具體原因，而不是拋出錯誤：

1. **通知狀態頁面訂閱者** 必須開啟。沒開的話，備註在建立的當下就會被標記為已略過。
2. 備註必須屬於一個仍然存在的事件。
3. 事件必須至少掛了一個監測器——沒有監測器，就沒有狀態頁面資源可以把備註路由過去。
4. 事件的 **於狀態頁面可見** 旗標（`isVisibleOnStatusPage`）必須為 true。
5. 事件所觸及的每個狀態頁面，都必須開啟 **顯示事件**（`showIncidentsOnStatusPage`）。
6. 每位訂閱者都必須通過自己的偏好設定——沒有取消訂閱、有訂閱這個資源，而且在頁面允許訂閱者選擇時，有訂閱 `Incident` 事件類型。

**通知不是即時的。** 發送的工作每分鐘執行一次，所以從你儲存備註到信件寄出，請預期最多約一分鐘。這就是 **Sending Soon** 標籤的意思。

**訂閱者通知狀態** 欄位會追蹤整段旅程：

| 狀態                         | 意義                                   |
| ---------------------------- | -------------------------------------- |
| **Notifications skipped.**   | 上面某一道關卡關上了，原因會被記錄。   |
| **Sending Soon**             | 已排入佇列，等待發送工作的下一次執行。 |
| **Notifications Being Sent** | 工作正在逐一處理訂閱者清單。           |
| **已傳送的通知**             | 所有訂閱者通知都已送出。               |
| **失敗**                     | 工作拋出例外；錯誤會與備註一起存下。   |

點狀態上的 **更多詳細資料**，會開啟 **通知狀態詳細資料**。在重送有意義的情況下，該對話框的按鈕是 **Retry**，它會把備註放回等待狀態，讓下一次執行重新處理它。

訂閱者實際收到的訊息，是依狀態頁面和管道各自套用範本的——電子郵件、簡訊、Slack 和 Microsoft Teams 各有自己針對 **Subscriber Incident Note Created** 事件的範本，變數包含狀態頁面名稱與網址、詳細資料連結、受影響的資源、事件嚴重程度與標題、備註內文，以及每位訂閱者專屬的取消訂閱連結。這些範本和管道怎麼設定，請見 [訂閱者與公告](/docs/status-pages/subscribers)。

## 事件動態

**事件 動態消息** 卡片位於事件 **概覽** 頁面左欄的底部。它是這個事件按順序講出來的故事：每一則項目都有一個圖示、造成它的人的頭像與名字、一個相對時間戳（滑鼠移上去可看到精確的本地時間），以及一段 Markdown 內文。項目依最舊在前排序。

有些項目帶著額外細節——例如一則擁有者通知會列出所有被寄信的人。這類項目會顯示一顆 **More Information** 按鈕，開啟一個 **More Information** 面板。

卡片標頭還有一個 **操作** 選單，讓你不用離開時間軸就能動手：

- **Execute Runbook** —— 對這個事件啟動一份 [runbook](/docs/runbooks/index)。
- **執行待命策略** —— 隨時呼叫一條策略。
- **Add Public Note** —— 跟公開備註頁面同樣的四個欄位，做成對話框。
- **新增私人註記** —— 只有備註內文和附件。

旁邊的 **重新整理** 會重新抓取動態。

**動態只能追加，而且它不是你的稽核日誌。** API 允許建立和讀取動態項目，但不允許更新或刪除，所以沒有人能悄悄改寫事件的歷史。它也不是永久的：在計費的安裝上，超過三年的動態資料列會被移除。若需要誰改了什麼的長期紀錄，請用事件側邊選單裡的 **稽核 → 稽核日誌**。

## 動態記錄些什麼

動態項目由事件服務本身、兩個備註服務、狀態時間軸、擁有者與成員異動、各種規則引擎、待命執行、AI 調查與事後分析執行器，以及通知的 cron 工作寫入。事件類型涵蓋：

- **事件本身** —— `IncidentCreated`、`IncidentUpdated`、`IncidentStateChanged`。
- **備註與書面紀錄** —— `PublicNote`、`PrivateNote`、`RootCause`、`RemediationNotes`、`PostmortemNote`。
- **人員** —— `OwnerUserAdded`、`OwnerTeamAdded`、`OwnerUserRemoved`、`OwnerTeamRemoved`、`IncidentMemberAdded`、`IncidentMemberRemoved`。
- **通知** —— `OwnerNotificationSent`、`SubscriberNotificationSent`、`OnCallPolicy`、`OnCallNotification`。
- **自動化** —— `LabelRuleExecuted`、`OwnerRuleExecuted`、`PrivacyRuleExecuted`、`OnCallRuleExecuted`、`AutoRemediation`。

每一種類型都有自己的圖示，所以你可以掃過一長串動態，從雜訊中挑出狀態變更。AI 產生的根本原因分析會被特別標示，並以受限的 Markdown 模式呈現。

動態會遵守事件的隱私設定：對私人事件而言，動態的讀取會以跟事件相同的方式被過濾。

## 擁有者

擁有者是對一個事件負責的人與團隊。事件上發生的一切都會通知他們——而且他們就是「事件不會在大家都以為別人在處理時被晾在一邊」的原因。

在事件側邊選單開啟 **團隊 → 擁有者**。**擁有者** 卡片會顯示一個計數徽章，說明擁有者是對這個事件負責、且會收到變更通知的人與團隊，並附上類似「2 人 · 1 個團隊」的即時計數。擁有者以重疊的頭像呈現；滑鼠移到某個頭像上會顯示該人的電子郵件，或標示該項目是一個 **團隊**。

- 點 **新增擁有者** 會開啟一個選擇器，裡面有搜尋人員或團隊的搜尋框。
- 點頭像上的移除控制項會開啟 **移除擁有者** 確認，然後點 **移除**。
- 還沒有擁有者時，卡片會這麼告訴你，並邀請你加入一位同事或一個團隊，好讓他們收到變更通知。

擁有者使用者和擁有者團隊是分開的紀錄——加入一個團隊，就等於讓該團隊的每位成員在通知上都成為擁有者，不必逐一列出。

## 擁有者是怎麼被指派的

有四條路可以進到擁有者清單：

- **從事件範本** —— 範本帶有 **擁有者 - 團隊** 與 **擁有者 - 使用者** 欄位，說明中寫的是擁有此事件、並會在事件建立或更新時收到通知的團隊與使用者。從範本建立事件時會預先填好。請見 [宣告事件](/docs/incidents/declaring-incidents)。
- **從事件擁有者規則** —— 相符的規則會在建立時自動加入擁有者。
- **在建立時透過 API** —— 隨建立呼叫傳入的擁有者使用者與團隊會立刻加入，並帶有一個旗標控制他們是否收到「你被加入了」的信。
- **手動** —— **擁有者** 頁面上的 **新增擁有者** 控制項，事件進行中的任何時候都能用。

同一個人加兩次是安全的；已經指派過的擁有者不會被重複加入。

## 事件擁有者規則

**事件擁有者規則** 會在相符的事件建立時自動指派擁有者使用者與團隊——這一層路由，讓資料庫的事件不必任何人動腦就落到資料庫團隊身上。你會在 [事件設定與自動化](/docs/incidents/settings) 中，跟其他事件自動化一起找到它們。

規則表單有三個步驟——**基本資訊**、**比對條件** 與 **擁有者**——而擁有者步驟裡有兩個區段：

- **要指派的擁有者** —— 挑選 **擁有者團隊** 與 **擁有者使用者**。規則相符時，所有選定的使用者和團隊都會被加為擁有者，已指派過的不會重複。
- **繼承擁有者** —— 不用指名，而是從相關實體指派擁有者。**從監測器繼承擁有者** 會讓事件所有監測器的每一位擁有者也成為事件的擁有者，而 **從主機繼承擁有者**、**從 Kubernetes 叢集繼承擁有者**、**從 Docker 主機繼承擁有者**、**Inherit Owners From Podman Hosts** 與 **從服務繼承擁有者** 則對那些資源做同樣的事。

一個 **通知擁有者** 開關控制人們會不會知道。真正要做路由時就開著它；想安靜地加入擁有者就關掉——當某條規則只是記帳方便、而不是要呼叫人時很好用。

每一次規則執行都會寫進事件動態，所以你隨時都能分辨某個人是被規則加入的，還是被人加入的。

## 擁有者會收到哪些通知

有五個工作會通知擁有者，每個都是每分鐘執行一次：

- **事件已建立** —— 主旨為 `[New Incident {number}] - {title}`。
- **有人張貼了備註** —— 公開*和*私人備註都算，主旨為 `[Update Incident {number}] - {title}`。
- **事件狀態變更了** —— 請見 [事件狀態與嚴重程度](/docs/incidents/states-and-severities)。
- **你被加為擁有者** —— 主旨為 `You have been added as the owner of Incident {number} - {title}`。
- **仍未解決** —— 由事件的下次提醒時間驅動的提醒，主旨為 `[Reminder] Incident {number} is still {state} - {title}`。

每一則通知都會準備電子郵件、簡訊、語音來電、推播和 WhatsApp 版本，然後交給使用者的通知設定，由它決定實際送出什麼。每位收件者都可以個別關閉這些通知——每位使用者的設定分別對應事件建立、備註張貼、狀態變更、擁有者加入、成員指派，以及仍未關閉的提醒通知。只想在狀態變更時接到電話的人，就能只設定成那樣。

**沒有擁有者的事件不會靜悄悄的。** 如果事件完全沒有擁有者，通知工作會退回給專案的擁有者，所以不會有東西掉在地上。每一位被通知的人也會被附加到對應的動態項目上，所以事後你能確切看到誰被告知了、寄到哪個位址。
