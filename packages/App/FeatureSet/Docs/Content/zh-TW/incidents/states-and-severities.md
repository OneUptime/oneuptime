# 狀態與嚴重程度

每個事件都帶著兩種分類：一個**狀態**，說明它走到應變流程的哪裡；一個**嚴重程度**，說明它有多痛。在儀表板裡兩者長得很像——都在事件清單上呈現為彩色標籤，都是專案範圍、可改名可換色的清單。但它們做的事天差地遠。

狀態驅動行為。狀態資料列上的三個布林旗標，決定哪些事件算進行中、事件標頭上出現哪些按鈕、SLA 計時什麼時候停、事件什麼時候從狀態頁面上撤下。嚴重程度本身什麼都不驅動——它們是描述影響的標籤，其他規則可以拿來比對。

兩份清單都在專案建立時預先產生，也都在 **事件 → 設定** 底下編輯。事件側邊選單的那個區段預設是收合的，所以去找之前請先展開 **設定**。

## 狀態帶行為，嚴重程度帶意義

`IncidentState` 模型有 `name`、`description`、`color` 和 `order`，再加上三個布林值：`isCreatedState`、`isAcknowledgedState` 和 `isResolvedState`。產品對狀態做的所有事，都是看這些布林值和 `order`——絕不看狀態的名稱。所以你可以把 **已解決** 改名成「已關閉」而什麼都不會壞：旗標是跟著資料列走的。

`IncidentSeverity` 模型有 `name`、`description`、`color` 和 `order`，就這些。沒有旗標。OneUptime 裡沒有任何東西會自動把 **嚴重事件** 和 **輕微事件** 區別對待——嚴重程度只有在你主動指向它時才有作用，例如待命規則上的 **事件 嚴重性** 比對條件。

幾條簡單的規則：

- **用嚴重程度傳達影響** —— 它會顯示在事件清單、事件的 **概覽** 上，而且宣告事件時是必填欄位。
- **用狀態刻畫你的流程** —— 你實際走過的應變步驟，依你實際走的順序排列。
- **不要把急迫性編碼進狀態** —— 一個叫「Critical」的狀態不會呼叫任何人。做這件事的是嚴重程度加上待命規則。

## 預設的狀態

專案建立時會依這個順序產生三個狀態。這個產生程序具有冪等性——只有在還沒有同名狀態時才會新增。

| 狀態         | `order` | 旗標                  | 顏色      | 意義                                 |
| ------------ | ------- | --------------------- | --------- | ------------------------------------ |
| **已識別**   | `1`     | `isCreatedState`      | `#fd625e` | 新事件會落到的狀態。                 |
| **已確認**   | `2`     | `isAcknowledgedState` | `#ffbf53` | 有人接手了這個事件。                 |
| **已解決**   | `3`     | `isResolvedState`     | `#2ab57d` | 事件結束了，不再計為進行中。         |

留意名稱：第一個狀態叫 **已識別**，儘管產品裡有幾處說明仍稱它為「建立」狀態。當文件或提示文字說「建立狀態」時，指的是帶有 `isCreatedState` 的那個狀態——在全新專案裡就是 **已識別**。

## 每個狀態旗標實際上做什麼

| 旗標                  | 用途                                                                                                                                   |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `isCreatedState`      | 沒有人挑狀態時，事件會拿到的狀態。如果專案裡沒有任何狀態帶這個旗標，建立事件就會失敗，並提示你從設定新增一個建立事件狀態。          |
| `isAcknowledgedState` | 驅動 **Acknowledge** 按鈕，以及事件 **概覽** 上的「<狀態名稱> in」統計方塊。狀態變更為此狀態時，事件的 SLA 會被標記為已回應。       |
| `isResolvedState`     | 驅動 **解決** 按鈕與已解決統計方塊、定義 **進行中事件** 清單，也是把事件從狀態頁面進行中區塊移除的關鍵。同時把 SLA 標記為已解決。   |

每個專案的每個旗標，預期都只由一個狀態持有——查詢時只會取回單一列。這三個帶旗標的狀態可以改名、換色和重新排序，但設定頁面拒絕刪除它們，並會顯示錯誤，指出建立、已確認與已解決狀態。

由於介面是動態讀取狀態名稱的，改一個狀態的名字會改變你到處看到的字：統計方塊、確認對話框的標題，以及事件清單上的標籤，全都跟著你給那一列的名稱走。

## 新增你自己的狀態

前往 **事件 → 設定 → 事件狀態**。這個頁面是一份依 `order` 遞增排序的清單，新狀態會被加到最後。拖曳某一列就能改變它的位置。

**狀態上的欄位：**

- **名稱** —— 必填，至少兩個字元。提示文字會建議類似「Investigating」的寫法。
- **描述** —— 選填的自由文字，說明事件在什麼情況下會停在這個狀態。
- **顏色** —— 必填。從色彩選擇器挑選，儲存為 `#fd625e` 這樣的十六進位值。

你無法從這張表單設定那三個旗標——它們屬於預設的資料列。因此你新增的狀態都是不帶旗標的狀態，這會帶來兩個值得事先規劃的後果：

- **它會算進行中。** **進行中事件** 的定義是「當前狀態不是已解決狀態」，所以除了已解決狀態以外，你新增的任何狀態都會讓事件留在進行中清單和側邊欄計數裡。
- **它的轉換按鈕是通用的。** 確認對話框不會寫 **Acknowledge** 或 **解決**，而是標題為 **將事件標示為 `<狀態名稱>`**，送出按鈕為 **Mark as `<狀態名稱>`**。

常見的做法是在已確認與已解決之間插入一個分流或緩解步驟——例如拖一個新的「已緩解」狀態，讓它排在 **已確認** 之後、**已解決** 之前。

## 順序是真的限制，不是顯示偏好

`order` 欄位在寫入狀態變更時就會被強制執行，不只是畫清單時才用：

- **往回的轉換會被拒絕。** 把事件移到順序比當前狀態更前面的狀態會失敗，錯誤訊息會指出這兩個狀態。
- **重選當前狀態會被拒絕。** 把事件設成它已經在的狀態會失敗，訊息是「Incident state cannot be same as previous state.」。
- **補記的資料列不能跟鄰居重複。** 插入一列時間軸紀錄，如果它的狀態跟緊接在後的那一列相同，同樣會被拒絕。
- **標頭按鈕跟著帶旗標狀態在順序中的位置走。** **Acknowledge** 與 **解決** 是依當前狀態在排序清單中的位置決定是否顯示。排在已解決狀態*之後*的自訂狀態，永遠不會出現 **解決** 按鈕，因為前面已經沒有可以往前推進的東西了。

所以新增狀態時，請把它放在事件真的會經過的位置。順序排錯不只是看起來怪——它會讓轉換根本走不下去。

## 預設的嚴重程度

專案建立時會依這個順序產生三個嚴重程度：

- **嚴重事件**（`order` 1，`#b70400`）—— 對客戶造成非常高影響、需要立刻應變的問題。像是全面中斷或資料外洩。
- **重大事件**（`order` 2，`#fd625e`）—— 影響顯著，通常需要立刻應變，有時會有能限制損害的替代方案。像是某個重要子系統故障。
- **輕微事件**（`order` 3，`#ffbf53`）—— 影響輕微，通常在上班時間處理，大多數客戶不太可能察覺。像是應用程式效能略微下滑。

宣告事件時嚴重程度是必填的，監測器條件裡每一筆事件規格也必須有嚴重程度，所以每個事件——不論手動或自動——都一定帶著一個。宣告流程請見 [宣告事件](/docs/incidents/declaring-incidents)，監測器驅動的路徑請見 [事件與警示範本](/docs/monitor/incident-alert-templating)。

## 編輯嚴重程度

前往 **事件 → 設定 → 事件嚴重性**。形式跟狀態頁面一樣——依 `order` 排序的清單、拖曳重新排列、新嚴重程度加到最後，表單上有 **名稱**、**描述** 和 **顏色**。

跟狀態有兩點不同：

- **沒有刪除保護。** 任何嚴重程度都可以刪除，包括三個預設的。
- **沒有旗標可以繼承。** 新的嚴重程度行為跟預設的完全一樣——一個有顏色和位置的標籤。

**關於提示文字的一點說明。** 嚴重程度表單一字不改地沿用了狀態表單的範例文字，所以提示講的是事件狀態而不是嚴重程度。忽略它們，寫你自己的嚴重程度名稱和描述就好。

嚴重程度真正不只是描述的地方在這裡：在 **事件 → 規則 → 待命規則** 上，規則的 **事件 嚴重性** 欄位是一個比對條件。把 **嚴重事件** 列在那裡，就是「任何嚴重問題都呼叫資料庫團隊」的表達方式——待命策略是掛在規則上，不是掛在嚴重程度上。

## 讓事件在狀態之間移動

事件變更狀態有四種方式：

- **標頭按鈕。** 打開一個事件。如果當前狀態排在已確認狀態之前，你會看到 **Acknowledge** 和 **解決**；如果落在兩者之間，你會看到 **解決**。每一顆都會開啟一個確認對話框——**Acknowledge Incident** 或 **Resolve Incident**——對話框裡還提供 **選擇備註範本**、**公開備註** 與 **通知狀態頁面訂閱者**。
- **狀態時間軸。** 從事件的 **狀態時間軸** 頁面手動新增一列，欄位有 **事件狀態**、**開始** 與 **通知狀態頁面訂閱者**。
- **批次變更。** 事件清單有 **變更狀態** 批次操作，可以一次移動好幾個事件。
- **自動變更。** 啟用了 **自動解決事件** 的監測器條件，會在條件不再成立時解決它的事件；API 也可以透過 `/api/incident-state-timeline` 更新狀態。

這四種方式每一種都會寫入一列時間軸紀錄。狀態變更還會順手做幾件你不必開口要的事：在事件動態中張貼一則項目、在事件還沒有事件指揮官時指派一位，以及更新 SLA 計時。重新開啟已解決的事件，會從重新開啟的時間起算一筆全新的 SLA 紀錄。

## 狀態時間軸

事件側邊選單裡的 **狀態時間軸** 頁面，是事件待過的每一個狀態的稽核軌跡。該頁面上的卡片標題為 **狀態時間軸**，並依最新在前排序。

**欄位：**

- **事件狀態** —— 一個彩色標籤，帶著狀態的名稱和顏色。
- **開始** —— 事件進入這個狀態的時間。
- **結束** —— 事件離開的時間。當前狀態會顯示 `Currently Active`。
- **持續時間** —— 停留在該狀態的時間；當前狀態會算到現在。
- **訂閱者通知狀態** —— 這次變更的狀態頁面通知是已送出、已略過還是等待中，附一個 **更多詳細資料** 連結，若發送失敗還會有 **Retry** 操作。

**列操作：**

- **檢視原因** —— 開啟一個 **根本原因** 對話框，呈現隨該次狀態變更記錄的 Markdown。
- **檢視日誌** —— 開啟一個說明狀態為何變更的對話框，內含 **事件狀態日誌** 檢視器。

時間軸的資料列可以建立和刪除，但不能編輯。刪錯一列等於改寫了事件的歷史，所以請把它當成更正工具，而不是清理習慣。

## 進行中事件清單

**事件 → 進行中事件** 是你值班時盯著看的那份清單。它的定義只有一個條件：事件的當前狀態是 `isResolvedState` 為 false 的狀態。其他一概不看——不看嚴重程度、不看時間長短、也不看有沒有人確認過。

側邊選單項目用同一個查詢帶著一個紅色計數徽章，所以徽章和清單永遠一致。沒有東西可看時，頁面會直接告訴你。

實務上的後果是：你新增的任何自訂狀態都會讓事件留在這份清單裡。這通常正是你要的——「已緩解」不等於「處理完了」——但這也表示只有事件真正走到已解決狀態，徽章才會歸零。

## 把狀態變更告訴狀態頁面訂閱者

狀態變更可以寄信給你的狀態頁面訂閱者，但它要通過好幾道關卡。搞懂這些關卡，可以省下大量「為什麼都沒人收到通知」的除錯時間。

通知是逐列時間軸請求的，由 **通知狀態頁面訂閱者**（`shouldStatusPageSubscribersBeNotified`）控制——它就是狀態變更對話框和手動時間軸表單上的那個核取方塊。關閉時，該列會以已略過的狀態和一段說明被存下來。開啟時，該列會進入佇列，由背景工作接手——這個工作每分鐘執行一次，所以送達很快，但不是瞬間。

**已排入佇列的資料列，在下列任一情況成立時仍會被略過：**

- **新狀態就是建立狀態。** 事件宣告時就已經通知過訂閱者了，所以第一列時間軸刻意不會再發第二則訊息。
- **事件沒有掛任何監測器。** 沒有資源，就沒有狀態頁面能對應到這個事件。
- **事件在狀態頁面上不可見**（`isVisibleOnStatusPage` 關閉）。
- **狀態頁面關閉了事件顯示**（`showIncidentsOnStatusPage` 關閉）。這一項是逐個狀態頁面判斷的——顯示同一個監測器的其他頁面仍然會發出通知。

**還有一件事會改變結果。** 如果你在狀態變更對話框裡打了 **公開備註**，這列時間軸會被標記為已通知，而不是排入佇列。真正送到訂閱者手上的是那則備註，所以他們收到一則訊息而不是兩則。純狀態變更訊息背後的事件類型是 `Subscriber Incident State Changed`。

誰會收到這些訊息、範本怎麼挑選，請見 [訂閱者與公告](/docs/status-pages/subscribers)。

## 讓事件不出現在狀態頁面上

有三件互相獨立的事決定事件是否會出現在公開頁面上，而且三者都必須成立：

- 狀態頁面本身的 **顯示事件**（`showIncidentsOnStatusPage`）。
- 事件上的 **於狀態頁面可見**（`isVisibleOnStatusPage`）——事件 **設定** 頁面上的一個開關。它預設為開，且不在宣告精靈裡；監測器條件可以用 **在狀態頁面上顯示事件** 來設定它。
- **當前狀態不是已解決狀態。** 這就是把事件從進行中區塊移除的關鍵：狀態頁面查詢抓的是當前狀態為任一未解決狀態的事件。你不需要封存或關閉任何東西——你解決它，它就會移進歷史紀錄。

**私人事件永遠不會出現。** 開啟 **私人事件** 會把事件從所有狀態頁面隱藏，不論上面那些開關如何，並把它限制在擁有者加上專案管理員與擁有者的範圍內。

頁面保留多少已解決的歷史紀錄，是狀態頁面的設定，不是事件的設定。頁面上的監測器如何決定哪些事件會出現，請見 [狀態頁資源與群組](/docs/status-pages/resources-and-groups)。
