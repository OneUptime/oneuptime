# 設定與自動化

事件的設定不放在專案設定裡。它就住在事件這個產品區域本身，位於 **事件 → 設定** 與 **事件 → 規則** 底下，路由都以 `/dashboard/{projectId}/incidents/settings/` 開頭。如果你一直在 **專案設定** 裡翻找事件範本或自訂欄位，這就是找不到的原因。

事件側邊選單裡的 **規則** 和 **設定** 兩個區段預設都收合著，所以得先展開，下面這些項目才會出現。這裡的每一項都是專案範圍：範本、角色、自訂欄位和規則都屬於某一個專案，並套用到在該專案裡宣告的每一個事件。

本頁是這些設定的參考——每個頁面裝了什麼，以及其中哪些會在事件建立的當下自動跑起來。

## 事件設定放在哪裡

在左側導覽點開 **事件**，然後展開側邊選單最下方的 **設定**。

| 頁面             | 你在那裡做什麼                                               |
| ---------------- | ------------------------------------------------------------ |
| **事件狀態**     | 新增、改名、換色，以及重新排序事件會經歷的狀態。             |
| **事件嚴重性**   | 新增、改名、換色，以及重新排序嚴重程度層級。                 |
| **事件範本**     | 預先填好整個事件——標題、描述、資源、待命策略、擁有者、標籤。 |
| **備註範本**     | 公開與私人備註都能重複使用的文字。                           |
| **事後分析範本** | 可重複使用的事後分析結構。                                   |
| **自訂欄位**     | 定義每個事件上都會出現的額外欄位。                           |
| **事件角色**     | 定義你要指派應變人員擔任的角色，例如事件指揮官。             |
| **更多設定**     | 事件與事件片段的編號前綴。                                   |

**事件狀態** 與 **事件嚴重性** 在 [事件狀態與嚴重程度](/docs/incidents/states-and-severities) 有完整說明——本頁其餘部分從 **事件範本** 接著講。

展開 **規則**，還會多出八個頁面：**分組規則**、**待命規則**、**擁有者規則**、**Runbook 規則**、**隱私規則**、**標籤規則**、**SLA 規則** 和 **Reminder Rules**。這些留到後面說明。

## 事件範本

事件範本就是存起來的一副事件骨架。與其在付款叢集每次出狀況時都重打同樣的標題、同一份監測器清單和同一條待命策略，不如存一次，之後直接從它宣告。

前往 **事件 → 設定 → 事件範本**（`/dashboard/{projectId}/incidents/settings/templates`）。卡片標題是 **事件範本**。建立一份範本會帶你走過六個步驟的精靈：

- **範本資訊** —— **範本名稱** 與 **範本描述**。這兩者命名的是範本本身，永遠不會出現在事件上。
- **事件詳細資訊** —— **標題**、**描述**（Markdown）、**事件嚴重性** 與 **初始事件狀態**。**初始事件狀態** 是選填的，一開始留空，選項依狀態順序排列。留空的話，從這份範本建立的事件會落在專案的建立狀態。
- **受影響的資源** —— 事件該掛在哪些監測器、主機、叢集與服務上，再加上 **將監測器狀態變更為**。
- **待命** —— **待命策略**，也就是從這份範本建立的事件被宣告時要執行的策略。
- **擁有者** —— **擁有者 - 團隊** 與 **擁有者 - 使用者**。
- **標籤** —— **標籤**。

幾條要記住的規則：

- 範本清單只顯示 **名稱** 與 **描述**。清單上的資料列不能直接編輯或刪除——要改就開啟範本（`/dashboard/{projectId}/incidents/settings/templates/{modelId}`）。
- 範本支援 JSON 匯入與匯出，所以你可以把一份範本搬到另一個專案。
- 空白狀態顯示的是「No incident templates found.」

### 範本是怎麼套用的

有兩條路徑，行為完全一樣。

- **從儀表板** —— 事件清單上的 **從範本建立** 按鈕會打開 **選擇事件範本** 選擇器，宣告頁面則從 `incidentTemplateId` 查詢字串參數讀取範本，然後用範本連同它的擁有者團隊與擁有者使用者預先填好表單。
- **從 API** —— 在 `POST /api/incident` 帶上 `createdIncidentTemplateId`，伺服器就會用範本填好事件。

真正的重點是合併規則：**範本只會填你沒有給值的欄位**。標題、描述、事件嚴重性、初始事件狀態、**將監測器狀態變更為** 背後的監測器狀態、監測器、主機、Kubernetes 叢集、Docker 主機、Podman 主機、服務、待命策略與標籤，都只有在呼叫端或表單什麼都沒給時，才會從範本複製過來。你明確設定的東西一律優先。

**空白狀態的對話框指錯地方了。** 如果你手上還沒有任何範本，**從範本建立** 按鈕會跳出一個 **No Incident Templates** 對話框。它的文字指向專案設定，但按鈕實際上會導向 **事件 → 設定 → 事件範本**——那才是真正的位置。

## 備註範本

備註範本給應變人員現成的事件更新文字，這樣凌晨三點的狀態頁面更新，就不必由一個半睡半醒的人從零寫起。

前往 **事件 → 設定 → 備註範本**（`/dashboard/{projectId}/incidents/settings/note-templates`）。卡片標題是 **事件的公開或私人備註範本**——同一個庫同時服務兩種備註類型。建立表單有兩個步驟：

- **範本資訊** —— **範本名稱** 與 **範本描述**，兩者皆為必填。
- **備註詳細資料** —— 備註本文，Markdown 格式，必填。

和事件範本一樣，資料列是拿來建立與檢視的，不能在清單上直接編輯；要改就開啟範本。

備註範本會出現在你真正需要它的地方：**Acknowledge Incident** 與 **Resolve Incident** 兩個確認對話框，都在 **公開備註** 欄位旁邊提供 **選擇備註範本**。公開與私人備註的差別請見 [事件備註、負責人與動態](/docs/incidents/notes-owners-and-feed)。

## 事後分析範本

事後分析範本是事件結束後那份檢討報告的骨架——你的標題、你的提示語、你每次都要問的問題——好讓專案裡的每一次檢討都長成同一個樣子。

前往 **事件 → 設定 → 事後分析範本**（`/dashboard/{projectId}/incidents/settings/postmortem-templates`）。卡片標題是 **事後分析範本**。建立表單有兩個步驟：

- **範本資訊** —— **範本名稱** 與 **範本描述**，兩者皆為必填。
- **事後檢討詳細資訊** —— **事後檢討範本**，也就是本文，Markdown 格式，必填。

套用範本是在事件裡做，不是在設定裡。開啟一個事件，在它的側邊選單選 **事後分析**（`/dashboard/{projectId}/incidents/{incidentId}/postmortem`），然後使用 **套用範本**。這會打開 **套用事後檢討範本** 對話框，裡面有一個 **選擇範本** 下拉選單；選定之後，範本本文會載入 **事後檢討備註** 編輯器，你在儲存前可以先修改。事件片段也有同樣的 **事後分析** 頁面，並共用同一份範本庫。

## 自訂欄位

自訂欄位讓每個事件都能帶著你自己的中繼資料——內部服務名稱、變更工單編號、客戶層級。

前往 **事件 → 設定 → 自訂欄位**（`/dashboard/{projectId}/incidents/settings/custom-fields`）。頁面標題是 **事件自訂欄位**。每個定義包含：

- **欄位名稱** —— 必填，至少兩個字元。佔位文字建議使用類似 slug 的名稱，例如 `internal-service`。
- **欄位描述** —— 選填。
- **欄位類型** —— 必填。這決定資料要怎麼輸入。下拉選單類型還得列出它的選項。
- **下拉選單選項** —— 會出現在下拉選單裡的值，每個都可以選配一個顏色。

定義存在自己的模型裡；值則放在事件本身的 `customFields` 欄。在單一事件上，你從事件側邊選單的 **自訂欄位** 填寫它們（`/dashboard/{projectId}/incidents/{incidentId}/custom-fields`）。

**有一個缺口值得知道。** 事件自訂欄位定義是事件家族中唯一沒有工作流程觸發器的部分——請見下面的工作流程段落。

## 事件角色

事件角色是應變過程中你指派給人的具名職務。在 **事件 → 設定 → 事件角色**（`/dashboard/{projectId}/incidents/settings/roles`）定義它們；卡片描述舉的例子是事件指揮官與應變人員。

角色本身只是定義。實際指派是逐一事件進行的——宣告精靈有一個 **事件角色** 步驟，裡面是 **指派事件角色** 欄位，而每個事件的側邊選單也都有一個 **角色** 頁面。

## 編號前綴

每個事件都會拿到一個編號，預設呈現成 `#42`。如果你的團隊口頭上都說「INC-42」，那就讓產品也這麼說。

前往 **事件 → 設定 → 更多設定**（`/dashboard/{projectId}/incidents/settings/more`）。卡片是 **號碼前置碼**，上面有兩個專案層級的欄位：

- **事件編號前綴** —— 最多 20 個字元，佔位文字為 `INC-`。設定之後，事件 `#42` 就會顯示成 `INC-42`。
- **事件片段編號前綴** —— 事件片段編號的同一套做法，佔位文字為 `IE-`。

任一欄留空就維持預設的 `#` 前綴，未設定的欄位會顯示 `# (default)`。用 **更新** 儲存。加上前綴的值會以 `incidentNumberWithPrefix` 存在事件上，而那正是事件清單與事件標頭所呈現的內容。

## 事件建立時會跑的規則

**事件 → 規則** 底下有八套規則引擎。它們做的是同一件事——在事件建立的當下看它一眼，符合就動作——差別在於做什麼，以及多條規則同時符合時要怎麼裁決。

- **分組規則** —— 把相關的事件歸進同一個片段。規則依優先順序評估，數字小的先跑。
- **待命規則** —— 為符合條件的事件執行待命值班策略。下面有詳細說明。
- **擁有者規則** —— 自動指派擁有者。
- **Runbook 規則** —— 事件符合條件時啟動一份 [Runbook](/docs/runbooks/index)。
- **隱私規則** —— 決定符合條件的事件是不是私人的。
- **標籤規則** —— 自動套用標籤。
- **SLA 規則** —— 追蹤回應與解決時間。規則依順序評估，順序數字小的先跑。
- **Reminder Rules** —— 事件還沒關閉時，定期提醒事件擁有者。規則依順序評估，第一條符合的規則勝出。

**順序的語意並不一致。** 分組規則、SLA 規則和 Reminder Rules 是依順序評估的。待命規則不是——每一條符合的規則都會觸發。別以為同一套模型適用於全部八種。

**待命規則**、**擁有者規則**、**標籤規則** 與 **隱私規則** 這幾個頁面是分頁式的——一個 **Incident Rules** 分頁和一個 **Episode Rules** 分頁，各有自己的表格。除非你確實是要處理片段，否則請設定 **Incident Rules** 分頁。**分組規則**、**Runbook 規則**、**SLA 規則** 和 **Reminder Rules** 則是單一表格。

## 事件待命規則

**事件 → 規則 → 待命規則**（`/dashboard/{projectId}/incidents/settings/on-call-rules`）是你讓呼叫自動化的地方。卡片 **事件待命規則** 描述的是：符合條件的事件被建立時，自動執行待命值班策略的規則。這個頁面有兩個分頁：**Incident Rules** 與 **Episode Rules**。

建立表單有三個步驟：

- **基本資訊** —— **名稱**（佔位文字給的例子大致是：任何資料庫事件都呼叫資料庫團隊）、**描述**，以及一個 **已啟用** 切換開關。清單會為每條規則呈現綠色的 **已啟用** 或紅色的 **已停用** 標籤。
- **比對條件** —— **監測器**、**事件 嚴重性**、**事件標籤**、**監測器標籤**，再加上針對事件標題、事件描述、監測器名稱與監測器描述的不分大小寫正規表示式欄位。
- **待命策略** —— 這條規則要執行的策略。

### 比對是怎麼裁決的

這個頁面本身附帶的規則值得記進腦子裡：

- 只有當你填寫的**所有**條件都通過，規則才算符合。你留空的條件會被略過，不算失敗。
- 在單一清單型條件內部——**監測器**、**事件 嚴重性**、**事件標籤**、**監測器標籤**——任一符合即可。
- 樣式欄位是不分大小寫的正規表示式。
- **所有符合的規則都會觸發。** 沒有優先順序，也不會短路。
- 實際執行的策略集合，是每一條符合規則的策略的聯集，再加上手動或由範本掛在事件上的任何策略，並去除重複，讓每條策略最多只跑一次。

嚴重程度只有在這裡才是比對條件，別的地方都沒有。事件嚴重性上沒有待命欄位——光是選了「嚴重事件」，本身並不會呼叫任何人。如果你想讓嚴重程度驅動呼叫，就寫一條比對它的待命規則。

## 直接掛上待命策略

規則不是唯一的途徑。每個事件都帶著自己的一份待命策略清單，呈現為宣告精靈 **待命** 步驟上的 **待命策略** 欄位，以及事件範本 **待命** 步驟上的同一個欄位。欄位描述講得很白：這些是這個事件建立時要執行的待命值班策略。

事件建立時，OneUptime 會先跑標籤規則，接著跑待命規則（把符合的策略併進事件的清單），然後跑 Runbook 規則——如果最後得到的清單不是空的，裡面每一條策略都會被執行。這些執行是平行進行、各自結算的，所以一條策略失敗不會拖住其他策略。每次執行都會標記觸發它的事件，以及「事件已建立」這個通知事件類型。

想知道發生了什麼，開啟該事件，在側邊選單選 **待命執行**（`/dashboard/{projectId}/incidents/{incidentId}/on-call-policy-execution-logs`）。

## 用工作流程驅動事件

事件的工作流程觸發器不是手寫的——OneUptime 從資料模型產生它們，所以事件家族的每個模型都會拿到 **On Create X**、**On Update X** 與 **On Delete X** 元件，名稱取自模型的單數名。最主要的三個是 **On Create Incident**、**On Update Incident** 與 **On Delete Incident**，你可以在 `/dashboard/{projectId}/workflows` 的 **新增元件** 面板中，**事件** 分類底下找到它們。

同一套產生機制也給了你設定本身的觸發器：**On Create Incident State**、**On Update Incident Severity**、**On Create Incident Template**、**On Create Incident Note Template**、**On Create Incident State Timeline**、**On Create Incident Public Note**、**On Create Incident Internal Note**、**On Create Incident On-Call Rule**、**On Create Incident Role**、**On Create Incident Member** 等等。每個模型還會拿到對應的動作元件——**Find One Incident**、**Create One Incident**、**Update One Incident**、**Delete One Incident** 以及它們的多列版本——所以名稱相近的觸發器和動作，會並排在同一個分類裡。**On Create Incident** 啟動一個工作流程；**Create One Incident** 開啟一個事件。

實際串接時，有幾個細節很重要：

- **On Update X** 接受一個選填的 **Listen on** 引數，把觸發器縮限到只針對特定欄位的更新。留空就是任何變更都觸發。如果某次更新沒有附上哪些欄位變動過的紀錄，這個篩選會被略過，工作流程照跑。
- **On Create X** 與 **On Update X** 都需要一個必填的 **Select Fields** 引數；**On Delete X** 不接受任何引數。
- 三者都只暴露一個 **成功** 出口，而且都接受一個 ID 引數，讓你可以手動針對單筆記錄執行工作流程。
- 名稱來自模型的單數名，不是資料表名稱——這就是為什麼你看到的是 **On Create Incident Team Owner** 和 **On Create Incident User Owner**，而不是資料表形狀的名字。
- 事件自訂欄位定義沒有觸發器。那個模型是事件家族中唯一停用工作流程的成員。

工作流程其餘部分怎麼組，請見 [建立工作流程](/docs/workflows/authoring) 與 [工作流程變數](/docs/workflows/variables)。
