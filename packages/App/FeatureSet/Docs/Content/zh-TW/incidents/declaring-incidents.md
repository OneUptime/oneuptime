# 宣告事件

宣告事件，就是 OneUptime 開始計分的那一刻。一筆紀錄被建立、一個編號被蓋上去、待命策略被觸發，而且——除非你另有交代——你的狀態頁面訂閱者會收到消息。事件生命週期中的其他一切，都掛在這第一次寫入之上。

事件進到 OneUptime 有四種方式，而它們最後都通往同一個地方：`Incident` 資料表中的一列，帶著嚴重程度、當前狀態和一份受影響資源清單。差別只在於是誰把欄位填起來——凌晨三點的你、一份存好的範本、監測器的條件，或是你自己呼叫 API 的程式碼。

本頁會逐欄位走過這四條路，接著說明伺服器會替你補上什麼，以及事件一存在就會觸發什麼。

## 宣告事件的四種方式

| 如果你想…                                    | 就選                                             |
| -------------------------------------------- | ------------------------------------------------ |
| 手動開一個事件，所有欄位自己填               | **宣告事件** 精靈                                |
| 開一個常見類型的事件，欄位先幫你填好         | **從範本建立**                                   |
| 在監測器檢查失敗時自動開一個                 | 加上 **當篩選器相符時，宣告事件。** 的監測器條件篩選器 |
| 從你自己的程式碼、腳本或其他工具開一個       | `POST /api/incident`                             |

四種方式寫入的是同一個模型，所以由探針開出來的事件，看起來跟應變人員手動開的完全一樣——除了伺服器會在自動建立的事件上多設幾個記帳用的欄位。

## 手動宣告

開啟 **事件 → 所有事件**，點選 **事件** 清單右上角的 **宣告事件**。隨即會開啟標題為 **宣告新事件** 的卡片，表單分為三個步驟：**事件詳細資訊**、**受影響的資源** 和 **待命與角色**，之後是供檢查的摘要。當你的專案在建立時詢問部分事件自訂欄位時，**受影響的資源** 之後會緊接第四個步驟 **詳細資料**。

只有第一個步驟有必填欄位，另外還有管理員標記為 **建立時必填** 的自訂欄位。附加資源、新增待命策略與指派角色，也可以之後在事件自己的頁面上完成。 摘要之前的每個步驟都有一般的 **下一步**，而 **宣告事件** 位於最後一個步驟——摘要中。

**進階。** 大多數事件永遠用不到的選項，會收合在各步驟末尾的 **進階** 標題下；點選即可展開。收合時，若其中有內容已設定（例如由範本設定），標題會顯示 **已設定**；若其中有內容需要修正，它會自動展開。摘要只在收合的選項已設定時才列出它，但 **通知狀態頁面訂閱者** 例外：摘要一律會列出它，並說明將通知誰。

### 步驟 1 —— 事件詳細資訊

- **標題** —— 必填。所有人都會在清單、Slack 以及（事件可見時）狀態頁面上看到的一行摘要。
- **事件嚴重性** —— 必填。專案中設定的嚴重性之一。
- **描述** —— 選填，以 Markdown 撰寫。狀態頁面顯示的就是它，所以請寫給客戶而不是團隊。

在 **進階** 下：

- **宣告時間** —— 從你開啟頁面的時刻開始。事件的所有時長都從這裡起算；要記錄更早開始的事件，請把它往前調。
- **初始狀態** —— 選填，一開始為空。留空時，事件會從帶有 `isCreatedState` 旗標的狀態或範本的初始狀態開始。只有在記錄已確認或已解決的事件時，才選擇後面的狀態。
- **標籤** —— 選填。標籤把相關事件歸在一起；受標籤限制的團隊只會看到帶有其某個標籤的事件。
- **私人事件** —— 預設關閉（`isPrivate`）。私人事件只對其擁有者、專案管理員與專案擁有者可見，並在所有狀態頁面上隱藏。

**如果狀態下拉選單出問題。** 如果你的專案沒有任何狀態帶有 `isCreatedState` 旗標，建立呼叫會失敗，並告訴你要從設定裡新增一個建立事件狀態。這通常只會發生在狀態被大幅改過的專案上——請見 [事件狀態與嚴重程度](/docs/incidents/states-and-severities)。

### 步驟 2 —— 受影響的資源

監測器單獨排在最前面：狀態頁面透過事件的監測器看到事件，而監測器要變更成的狀態就在它們正下方。

- **監測器** —— 用來附加受事件影響之監測器的搜尋框（`monitors`）。狀態頁面列出其中任一監測器時，就會顯示該事件並通知其訂閱者。
- **將監測器狀態變更為** —— 選填，只有在至少選擇一個監測器後才會顯示。它會把事件的每個監測器設為某個監測器狀態，因此宣告事件與把監測器標記為降級只需一個動作。範本的狀態會在你選擇監測器後立即顯示；若沒有選擇任何監測器，則不會儲存任何狀態。
- **其他受影響的資源** —— 第二個搜尋框，用於事件影響的其他一切：主機、Kubernetes 叢集、Docker 與 Podman 主機、Proxmox、Ceph 與 Docker Swarm 叢集、vCenter、IoT 機群、資料庫與服務。它們是事件上各自獨立的關聯（`hosts`、`kubernetesClusters`、`services` 等）。

之後編輯時，事件的 **受影響的資源** 卡片也以相同方式詢問。

在 **進階** 下：

- **僅限這些狀態頁面** —— 選填。留空時，事件會顯示在列出其監測器的每個狀態頁面上，並通知這些頁面的訂閱者；選擇頁面後，只會在其中選中的頁面上顯示。請參閱 [每個受眾一個狀態頁](/docs/status-pages/one-status-page-per-audience)。
- **通知狀態頁面訂閱者** —— 核取方塊，預設勾選（`shouldStatusPageSubscribersBeNotifiedOnIncidentCreated`）。在它下方以及摘要中，表單會顯示哪些狀態頁面會收到通知、每個頁面有多少訂閱者；在摘要中，**預覽通知** 會顯示他們將收到的電子郵件。對於只想記錄下來的內部雜訊，請取消勾選。

**就算感覺多餘，也要把監測器掛上去。** 事件與狀態頁面之間的連結，是透過事件的監測器建立的：當狀態頁面的某個資源是事件的監測器之一時，該頁面才會顯示這個事件。如果事件沒有掛任何監測器，狀態變更給訂閱者的通知會直接被略過。請見 [狀態頁資源與群組](/docs/status-pages/resources-and-groups)。

### 步驟 3 —— 待命與角色

- **待命策略** —— 多選，選擇建立此事件時要執行的待命策略（`onCallDutyPolicies`）。
- **指派事件角色** —— 由誰擔任專案定義的每個角色。標記為 **主要** 的角色若留空，就歸你：事件宣告時由你擔任。

這是唯一能把待命策略直接掛到事件上的地方。嚴重程度本身不帶待命策略——嚴重程度只是標籤，它只有在待命規則裡作為*比對條件*時才會影響呼叫。在 **事件 → 規則 → 待命規則** 設定的規則，會把它們的策略疊加在你這裡選的策略之上；最終執行的集合是兩者去重後的聯集。

角色本身在 **事件 → 設定 → 事件角色** 中設定。新專案有一個角色 Incident Commander；流程還需要什麼，就在那裡新增。

**Should be visible on status page?** 這個旗標（`isVisibleOnStatusPage`）不在精靈裡，預設為 true。要改的話，事後從事件側邊選單的 **設定** 修改，它在那裡的標籤是 **於狀態頁面可見**。

## 從範本宣告

如果你一直在宣告同一種形狀的事件——同樣的標題模式、同樣的嚴重程度、同樣的待命策略——那就把它存成範本，一次搞定。

點 **從範本建立**（**宣告事件** 旁邊那顆外框按鈕），會開啟 **從範本建立事件** 對話框，裡面有一個 **選擇事件範本** 下拉選單。挑一個範本，建立表單就會帶著預填內容開啟；送出前你仍然可以改任何欄位。如果專案還沒有任何範本，你看到的會是 **No Incident Templates** 對話框，上面有一顆 **Create Template** 按鈕，會把你帶到 **事件 → 設定 → 事件範本**。

範本透過它們自己的精靈建立——**範本資訊**、**事件詳細資訊**、**受影響的資源**、**待命**——當專案有事件自訂欄位時，還會加上自訂欄位的步驟。範本的擁有者與標籤位於 **事件詳細資訊** 末尾的 **進階** 下。**受影響的資源** 的詢問方式與宣告表單相同——**監測器**，然後是 **將監測器狀態變更為**，然後是 **其他受影響的資源**，**僅限這些狀態頁面** 位於 **進階** 下——只是範本一律會詢問監測器狀態：它也適用於從範本宣告事件時選擇的監測器。欄位如下：

| 欄位                       | 用途                                       |
| -------------------------- | ------------------------------------------ |
| **範本名稱**               | 範本在選擇器中的識別方式。                 |
| **範本描述**               | 提醒未來的自己什麼時候該拿出這個範本。     |
| **標題**                   | 預先填到事件上的標題。                     |
| **描述**                   | 預先填到事件上的 Markdown 描述。           |
| **事件嚴重性**             | 預先填到事件上的嚴重程度。                 |
| **初始事件狀態**           | 由此範本建立的事件會從哪個狀態開始。       |
| **監測器** | 要附加的監測器。 |
| **將監測器狀態變更為** | 套用到事件監測器（包括宣告時選擇的監測器）的監測器狀態。 |
| **其他受影響的資源** | 要附加的主機、叢集與服務。 |
| **僅限這些狀態頁面** | 事件所限定的狀態頁面。 |
| **待命策略**               | 事件建立時要執行的策略。                   |
| **擁有者** | 擁有從此範本建立之事件的人員與團隊，從同一份清單中選擇。 |
| **標籤**                   | 套用到事件上的標籤。                       |

幾條簡單的規則：

- 範本無法從範本清單直接編輯——你先建立一個，再打開它來修改。
- 範本只會填補你留空的欄位。在建立頁面上，範本是以可覆寫的預填形式套用；在 API 上，只有當請求把某個欄位留成 `undefined` 時，伺服器才會用範本填它。呼叫端送出的值永遠勝出。

## 由監測器條件自動宣告

大部分事件都不該需要人工輸入。在監測器的條件編輯器中，開啟 **當篩選器相符時，宣告事件。** 這個開關，就會出現一個 **建立事件** 區段和一顆 **新增事件** 按鈕——一個條件篩選器可以宣告不只一個事件。

每一筆項目包含：

- **事件標題** —— 支援樣板語法；提示文字會建議類似 `{{monitorName}} is down` 的寫法。
- **嚴重程度** —— 必填。
- **事件描述** —— 同樣支援樣板語法。
- **待命 → 待命策略** —— 這個事件建立時要執行的策略。
- **事件角色** —— 預先把團隊成員指派到角色上。
- **擁有權與標籤 → 擁有者團隊**、**擁有者使用者**、**標籤**。
- **進階選項 → 自動解決事件**（條件不再相符時自動解決事件）、**在狀態頁面上顯示事件**、**私人事件** 與 **補救備註**。

標題、描述和補救備註可用的 `{{variable}}` 佔位符完整清單，請見 [事件與警示範本](/docs/monitor/incident-alert-templating)。

這樣建立的事件會被伺服器打上標記：`isCreatedAutomatically` 會被設定、`createdCriteriaId` 記錄是哪個條件篩選器觸發的、`createdByProbe` 記錄是哪個探針發現的。其他一切行為都跟手動宣告的事件完全一樣。

## 透過 API 宣告

事件模型提供標準的 CRUD 端點，所以 `POST /api/incident` 就能建立一個事件。請用在 **專案設定 → API 金鑰** 產生的 API 金鑰驗證，放在 `apikey` 標頭中——金鑰本身就標識了專案，所以你不需要另外傳專案 ID。

```bash
curl -X POST https://oneuptime.com/api/incident \
  -H "apikey: $ONEUPTIME_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "data": {
      "title": "Checkout latency above SLO",
      "description": "Investigating elevated p99 latency on the checkout service.",
      "incidentSeverityId": "<incident-severity-id>"
    }
  }'
```

請求主體中好用的欄位：

- `title` —— 唯一真正非給不可的欄位。
- `declaredAt` —— 這裡是選填的，即使表單上是必填。省略它，伺服器就會用當下時間。
- `incidentSeverityId` 與 `currentIncidentStateId` —— 伺服器會檢查兩者是否屬於 API 金鑰所在的同一個專案，不符就拒絕請求。**將監測器狀態變更為** 背後的監測器狀態也適用同樣的檢查。
- `createdIncidentTemplateId` —— 套用一個已存的範本。你沒給的欄位會由範本填補；你有給的欄位則原封不動保留。

相關的端點還有 `/api/incident-state`、`/api/incident-severity` 和 `/api/incident-state-timeline`。自動產生的 [API 參考](/reference) 有每一個端點確切的請求與回應結構，包括監測器這類關聯欄位如何表達。

## 事件編號與前綴

每個事件都會從專案各自的計數器拿到一個連續編號，由伺服器在建立時指派。有兩個欄位存放它：`incidentNumber`（原始整數）和 `incidentNumberWithPrefix`（你實際看到的值）。沒有設定前綴時，顯示值是 `#42`。

要改的話，請到 **事件 → 設定 → 編號前綴**，點選 **更新**。**事件編號前綴** 欄位會在你輸入時預覽編號：`INC-` 會變成 `INC-42`。留空則維持預設的 `#`。新前綴會用在儲存之後宣告的事件；現有事件會保留原本的編號。同一個對話框也有給片段編號用的 **事件片段編號前綴**。

編號會出現在事件清單的第一欄、連往該事件，也會在事件的 **概覽** 上以 **事件編號** 呈現。

## 事件宣告當下會發生什麼

建立呼叫做的事不只是寫入一列。依序如下：

1. **伺服器補上空缺。** `declaredAt` 預設為現在，當前狀態預設為專案的 `isCreatedState` 狀態，事件編號與帶前綴的編號則從專案計數器指派。
2. **套用範本**（如果有給 `createdIncidentTemplateId`）——只填補呼叫端留成 undefined 的欄位。
3. **執行隱私規則**，在相符規則這麼說時把事件標為私人。這是第一個執行的規則引擎，所以後面的一切看到的都是正確的隱私設定。
4. **執行擁有者規則**，加入相符規則指名的擁有者使用者與團隊。
5. **執行標籤規則**，加入與事件相符的標籤。
6. **執行待命規則。** **事件 → 規則 → 待命規則** 中每一條啟用且條件相符的規則，都會把它的策略加到事件上。沒有優先順序，也不會短路——所有相符的規則都會觸發，策略則會去重。
7. **執行 runbook 規則**，掛上並啟動相符的 runbook。請見 [Runbook 概觀](/docs/runbooks/index)。
8. **執行待命策略。** 事件上的每一條策略——不論是在精靈裡選的、從範本繼承的，還是由規則加上的——都會以 `IncidentCreated` 事件類型平行執行。其中一條失敗不會擋住其他的。
9. **把訂閱者排入佇列**，前提是 **通知狀態頁面訂閱者** 保持開啟，而且事件在狀態頁面上可見。實際發送由背景工作處理，不會跟你的請求同步進行。
10. **觸發工作流程。** **On Create Incident** 觸發器會啟動任何建立在它之上的工作流程。請見 [工作流程概觀](/docs/workflows/index)。

到這裡，事件就正式上線了：它會計入事件側邊選單的 **進行中事件** 徽章（任何未標記 `isResolvedState` 的狀態都算進行中）、出現在帶有其監測器之一的狀態頁面上，而它的 **狀態時間軸** 也開始記錄。
