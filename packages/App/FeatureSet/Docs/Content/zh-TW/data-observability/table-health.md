# 資料表健康

每五分鐘，每個已連接資料庫的目錄都會說明每個資料表的狀況：它最後一次變更的時間、包含多少列、有多大，以及它有哪些欄。資料可觀測性據此學習每個資料表的節奏，並在資料表延遲、縮小或結構改變時告訴你，不需設定任何閾值。

## 讀取的內容

針對每個資料表和檢視：

- **列數和大小**，來自引擎本身的統計資料。
- **最後一次變更的時間**：如果引擎本身有記錄時間，就使用該時間；否則就是兩次收集之間，其寫入計數器、列數或位元組數有所變動的時刻。
- **它的欄**，包括欄的類型以及是否可以為空。
- **最後一次被讀取的時間**，前提是引擎會計算讀取次數。

只讀取目錄，在 MongoDB 上還會讀取集合最新文件的欄位名稱。沒有任何值離開資料庫。

## 新鮮度

資料表的 **節奏** 是指它通常多久變更一次，從它各次變更之間的間隔學習而來。遠遠超出節奏的資料表會在它的頁面和 **資料表** 中顯示為 **延遲**，並寫入超出了多久。資料表變更兩次後，就能得知它的新鮮度：每小時載入的資料表在幾小時內就能學會，每晚載入的資料表在幾天內就能學會。

檢視本身不包含列，因此它的新鮮度就是其來源的新鮮度：請參閱 [血緣與管線](/docs/data-observability/lineage-and-pipelines)。

目錄可能在資料表只是進行例行維護時就說它變更了，或是什麼都沒說。在資料表的 **設定** 上指定 **Freshness 欄位**，例如 `updated_at`，它的最後變更時間就會改為該欄位的最新值。登入需要能讀取該欄位，而且每次收集都會讀取，因此應該為它建立索引；在依查詢讀取量計費的 BigQuery 和 Athena 上，則每小時讀取一次。未標示時區的時間會視為 UTC。

## 資料量和結構描述變更

- **資料列** 會在兩次收集之間進行比較：失去一半列的資料表，或列數遠少於每週該時段通常水準的資料表，都會如實回報。
- **欄位** 也會進行比較。新增、移除、重新命名、變更類型或改為可為空的欄，會記錄在該資料表的 **時間軸** 和 **結構描述變更** 上，後者會由新到舊列出每個資料庫的每次變更。被移除、重新命名或變更類型的欄會破壞讀取它的東西，並可能發出警示。新增的欄不會破壞任何東西，只會留在時間軸上。
- **被刪除的資料表** 會保留在 **已刪除的資料表** 下，並顯示它們最後一次出現的時間；如果該資料表重新出現，它會連同歷程一起恢復。

## 建議的警示

在 **資料庫** 上，為某個資料庫選擇 **建議的警示**。每項建議都是涵蓋整個資料庫的一個指標監測器，每個資料表各警示一次，因此日後建立的資料表也會受到監看：

| 警示 | 觸發條件 |
| --- | --- |
| **Table Is Late** | 資料表超出其通常的變更時間已持續十五分鐘 |
| **Row Count Fell Sharply** | 資料表在兩次收集之間失去一半或更多的列 |
| **Row Count Unusually Low** | 資料表的列數遠少於每週該時段的通常水準（以兩週的資料學習） |
| **Schema Changed** | 資料表的欄遭到移除、重新命名或變更類型 |
| **Table Health Stopped Reporting** | 該資料庫的任何資料表都已十五分鐘沒有被讀取 |

在建立時選擇嚴重程度、待命原則、擁有者和標籤。此後它們就是一般的監測器：可以像其他監測器一樣編輯、靜音，或放到狀態頁面上。

回填或移轉不該呼叫任何人。在 [維護事件](/docs/scheduled-maintenance/index) 的 **Data Observability 資料庫** 下指定該資料庫，或把它的資料庫伺服器放進去，事件進行期間它的資料警示就會保持安靜。

## 每個資料表寫入的指標

每次收集都會為每個資料表寫入這些指標，因此你可以像對待任何其他指標一樣，為它們繪製圖表、放到儀表板上並據此發出警示：

| 指標 | 意義 |
| --- | --- |
| `oneuptime.data.table.row_count` | 資料表中的列數 |
| `oneuptime.data.table.size` | 資料表及其索引所占的位元組數 |
| `oneuptime.data.table.seconds_since_change` | 自資料表最後一次變更以來的秒數 |
| `oneuptime.data.table.overdue_seconds` | 資料表超出其通常變更時間的秒數；準時時為 0 |
| `oneuptime.data.table.row_count_change_percent` | 與上一次收集相比，列數變動的幅度，以百分比表示 |
| `oneuptime.data.table.schema_changes` | 自上一次收集以來有所變更的欄數 |
| `oneuptime.data.table.breaking_schema_changes` | 自上一次收集以來被移除、重新命名或變更類型的欄數 |

每筆指標資料都帶有 `oneuptime.data.store.id`、`oneuptime.data.store.name`、`oneuptime.data.table.id`、`oneuptime.data.table.schema`、`oneuptime.data.table.name` 和 `oneuptime.data.table.key`（`schema.table`）。依 `oneuptime.data.table.key` 分組的 [指標監測器](/docs/monitor/metrics-monitor) 會為每個資料表各警示一次，它的 **異常偏高** 和 **異常偏低** 篩選條件會把每個資料表與它自己在每週該時段的通常值進行比較。這些指標是 OneUptime 本身的營運資料，不以遙測計費。

## 未使用的資料表

每個會計算讀取次數的引擎，都會說明每個資料表最後一次被讀取的時間：PostgreSQL 的掃描、MySQL 的 performance_schema、SQL Server 的搜尋、掃描和查閱，以及 Redshift、ClickHouse 和 Databricks 的查詢歷史。在你的服務的資料庫 Span 中看到的讀取也會計入。

**未使用的資料表** 會列出 90 天內無人讀取的資料表，最大的排在前面，並顯示每個資料表最後一次被寫入的時間：仍在寫入卻從未被讀取的資料表，只是白白耗費寫入和儲存成本。資料表在首次收集時計數器為 0，表示自引擎的統計資料開始以來它從未被讀取，因此未使用的資料表從一開始就會顯示為未使用。

## 倉儲支出

資料可觀測性每小時讀取每個 Snowflake 和 BigQuery 倉儲在過去一天裡逐個作業的支出：Snowflake 的運算點數來自 `QUERY_ATTRIBUTION_HISTORY`，BigQuery 的計費位元組來自其作業檢視，後者需要 **BigQuery Resource Viewer**。作業是反覆執行的同一個查詢，依其查詢標籤或 label，或依它做什麼和寫入的資料表來命名：絕不使用查詢的文字。

**倉儲支出** 顯示依團隊的合計（作業查詢標籤或 label 中的 `team`，否則為執行者）、寫入成本最高的資料表、失敗的作業，以及花在只寫入 90 天內無人讀取之資料表的作業上的支出。

## 使用每個資料表的服務

資料表的 **服務** 索引標籤會列出觀察到正在寫入和讀取它的服務，並附上每個服務執行的陳述式、過去一小時的呼叫和失敗次數，以及最後一次出現的時間。這些資訊來自你的服務已經透過 OpenTelemetry 傳送的資料庫 Span：帶有 `db.system.name`、`db.namespace` 和 `db.collection.name` 的用戶端 Span。不需額外安裝任何東西。

只有當 Span 的資料庫是某次收集讀取過的資料庫時，它才會連結到某個資料表；當兩個資料庫同名時，還要求它的 `server.address` 是其中之一的位址。

每個服務還會顯示發出這些呼叫的端點（來自同一條追蹤中的伺服器 Span），當它同時呼叫模型時，會標示為 **AI 應用程式**。**提及此資料表的錯誤** 會列出寫入該資料表的服務所產生的未解決例外狀況和過去一天的錯誤日誌，前提是它們以名稱提到了該資料表。

## 擁有者和標籤

資料表的 **擁有者** 索引標籤會列出它所屬的人員和團隊，資料表的警示會傳給他們；沒有擁有者時，則傳給其資料庫的擁有者。在資料表的 **設定** 上，為它指定你自己的 **標籤**。

你不該把這件事做上數百次。**擁有者規則** 和 **標籤規則** 會在每個資料表首次出現時套用，依它的標籤，或依其名稱、結構描述或資料庫上的規則運算式比對：`finance` 中的所有資料表都交給財務團隊，所有名為 `*_pii` 的資料表都會取得一個標籤。

範圍限定為 `Owned` 的權限只能觸及其持有者或其團隊擁有的資料表，以及這些資料表的檢查、活動和回報的問題。擁有資料庫並不等於擁有其中的資料表：要把整個資料庫交給一個團隊，請使用擁有者規則。

## 警示開啟時

資料表的警示有一張 **資料** 卡片，依排序說明它最可能是如何發生的：上游的警示、失敗的執行、寫入它的服務的部署、它失敗的寫入、變更過的欄、資料庫本身，或它所在的伺服器。其下是依賴它的內容：它血緣下游的資料表、儀表板、服務，以及擁有它們的人。

說明你的判斷：

- **Useful**：它是對的。
- **Expected**：計畫中的事件。不會有任何改變，而且下一次同樣會發出警示。
- **不是問題**：資料表會獲得更多餘裕，因此下一次同樣的情況就會保持安靜。延遲資料表的通常間隔會變長，列數的容許度會放寬。

如果有人先發現了問題，資料表上的 **回報問題** 會記錄下來。**概覽** 隨後會顯示資料可觀測性對你的專案表現如何：每週有用的問題數、有多少不是雜訊、讀取了多少資料表、它在有人回報之前先提出問題的頻率、速度有多快，以及它可能的原因有多常就是真正的原因。
