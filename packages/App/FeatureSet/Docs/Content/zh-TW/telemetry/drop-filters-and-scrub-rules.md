# 捨棄過濾器與清理規則

捨棄過濾器和清理規則在你的日誌和 Span 到達時就對其起作用，早於任何儲存。捨棄過濾器會丟掉你永遠用不到的記錄，或者只保留其中的一部分樣本。清理規則會遮蓋個人資料和機密，例如電子郵件地址、卡號和密碼，讓它們永遠不會進入你的儲存空間。

:::cards
- [它們在哪裡執行](#它們在哪裡執行): 在管道之前，在儲存之前。
- [捨棄或取樣記錄](#捨棄或取樣記錄): 比對記錄，然後捨棄它們或保留一部分。
- [清理敏感資料](#清理敏感資料): 對模式找到的內容進行編修、遮罩或雜湊處理。
- [查看過濾器捨棄了什麼](#查看過濾器捨棄了什麼): 每個過濾器上的計數。
:::

## 它們在哪裡執行

日誌的規則位於 **日誌 → 設定**，Span 的規則位於 **追蹤 → 設定**。記錄到達時，OneUptime 依以下順序執行它們：

```mermaid title="日誌或 Span 到達時會發生什麼"
flowchart TB
    arrive["日誌或 Span<br/>到達"] --> drop{"捨棄過濾器<br/>是否捨棄它？"}
    drop -->|"是"| gone["已捨棄：<br/>從不儲存"]
    drop -->|"否"| scrub["清理規則遮蓋<br/>比對到的內容"]
    scrub --> pipelines["管道修改<br/>記錄"]
    pipelines --> stored["已儲存，<br/>可供搜尋"]
```

- **它們只作用於新記錄。** 你建立或修改的規則適用於大約一分鐘後到達的記錄。已經儲存的記錄不會改變。
- **被捨棄的記錄就沒有了。** 任何搜尋、圖表、監測器或記錄規則都看不到它，也不會從它產生例外。在 OneUptime Cloud 上，它也不會計費。
- **每個清單依順序執行。** 拖曳清單中的列即可變更順序。只有已啟用的過濾器和規則才會執行。

日誌捨棄過濾器和清理規則同樣適用於來自 OpenTelemetry、Syslog、Fluent Bit 和 Fluentd 的日誌。[日誌管道](/docs/telemetry/log-pipelines) 介紹了它們之後的步驟。

## 開始之前

- **正在到達的日誌或 Span。** 請參閱 [OpenTelemetry](/docs/telemetry/open-telemetry)。
- **能夠修改遙測設定的角色。** 專案擁有者或專案管理員，或者擁有你所修改內容之權限（例如 Create Log Drop Filter 或 Create Trace Scrub Rule）的自訂角色。Telemetry 角色可以檢視過濾器和規則，但不能修改它們。

## 捨棄或取樣記錄

:::steps
### 開啟捨棄過濾器

前往 **日誌 → 設定 → 捨棄過濾器**；若是 Span，前往 **追蹤 → 設定 → 捨棄過濾器**。

### 比對記錄

點選 **建立日誌捨棄過濾器**；若是 Span，點選 **建立追蹤捨棄過濾器**。在 **比對** 步驟中為過濾器指定 **名稱**，然後建立它的 **篩選查詢**：為每個條件指定欄位、運算子和值，並選擇必須符合 **所有條件** 還是 **任一條件**。點選 **下一步**。

### 選擇操作

在 **操作** 步驟中，保留 **捨棄** 以丟掉每筆符合的記錄，或者選擇 **範例** 並輸入要保留的 **取樣百分比**，範圍為 1 到 99。然後建立過濾器。
:::

過濾器會在一分鐘內開始捨棄。若要先儲存而暫不捨棄任何內容，請在建立之前關閉 **進階** 下方的 **已啟用**。

> [!WARNING]
> 被捨棄的記錄無法找回。請讓過濾器的查詢盡量精確，並在建立後留意它的 **已捨棄** 計數。

過濾器可以檢查以下欄位，也可以透過 **Custom Attribute...** 檢查任意屬性：

| 記錄 | 欄位 |
| --- | --- |
| 日誌 | **嚴重程度**、**日誌內文**、**服務 ID** |
| Span | **Span 名稱**、**Span 種類**、**狀態**、**狀態訊息**、**服務 ID**、**有例外**、**為根 Span** |

| 運算子 | 符合 |
| --- | --- |
| **等於** | 完全相同的值，區分大小寫：`Debug` 符合，`DEBUG` 不符合。 |
| **不等於** | 除完全相同的值之外的任何值。 |
| **包含** | 欄位中任意位置出現的該值，不區分大小寫。值中的 `%` 是萬用字元。 |
| **是其中之一** | 以逗號分隔的精確值清單中的任意一個。 |

**Preview query** 會顯示這些條件組成的查詢。下面這個查詢會捨棄健康檢查的偵錯日誌行：

```text
severityText = 'Debug' AND body LIKE 'healthcheck'
```

取樣逐筆記錄決定：當 **取樣百分比** 為 10 時，大約每十筆符合的記錄保留一筆。過濾器依清單順序執行，第一個捨棄某筆記錄的過濾器說了算；被樣本保留的記錄會繼續進入下一個過濾器。

## 清理敏感資料

:::steps
### 開啟清理規則

前往 **日誌 → 設定 → 清理規則**；若是 Span，前往 **追蹤 → 設定 → 清理規則**。

### 選擇要尋找的內容

點選 **建立日誌清理規則**；若是 Span，點選 **建立追蹤清理規則**。然後選擇一個 **模式類型**。在你輸入自己的名稱之前，規則會以它命名，例如 **清除電子郵件地址**。若選擇 **自訂 Regex**，還要輸入 **自訂正規表示式模式**。

### 選擇清理方式

在 **進階** 下方選擇 **清除動作** 和 **要清除的欄位**，或者保持原樣：新規則會把每個符合項目替換為 `[REDACTED]`，無論它位於記錄中的什麼位置。然後建立規則。
:::

| 模式類型 | 它尋找的內容 |
| --- | --- |
| **電子郵件地址** | 電子郵件地址，例如 `jane@example.com` |
| **信用卡號碼** | 四位一組的十六位數字，例如 `4111 1111 1111 1111` |
| **SSN（社會安全號碼）** | 美國社會安全號碼，例如 `123-45-6789` |
| **電話號碼** | 北美電話號碼，例如 `555-123-4567` |
| **IP 位址** | 公用 IPv4 與 IPv6 位址，例如 `203.0.113.7` 或 `2001:db8::1`，但不包括私有、回送及連結本機位址 |
| **敏感屬性鍵** | 鍵看起來像機密的任何屬性的完整值，例如 `password`、`token`、`api_key`、`authorization` 或 `cookie` |
| **自訂 Regex** | 你自己的規則運算式，不帶斜線或旗標，並區分大小寫進行比對 |

| 清除動作 | 符合項目會變成什麼 |
| --- | --- |
| **編修** | `[REDACTED]`，即預設值 |
| **遮罩** | 大部分被隱藏：電子郵件地址保留首字母和網域結尾，卡號、電話號碼或社會安全號碼保留最後四位，自訂符合項目或機密值保留第一個和最後一個字元。IP 位址會被完全隱藏。 |
| **雜湊** | 你的專案獨有的權杖，同一個值每次都相同，因此仍然可以統計重複次數，但沒有人能據此還原出原值 |

例如，一條 **電子郵件地址** 規則會把下面這筆日誌內文：

```text
Payment failed for jane@example.com
```

依據它的 **清除動作** 儲存為以下形式之一：

```text
Redact: Payment failed for [REDACTED]
Mask:   Payment failed for j***@***.com
Hash:   Payment failed for [HASHED:5e29db14e508e09a]
```

對於日誌規則，**要清除的欄位** 為 **兩者（本文與屬性）**，除非你選擇 **僅本文** 或 **僅屬性**；對於 Span 規則，它為 **全部（名稱、屬性與事件）**，除非你選擇 **僅 Span 名稱**、**僅屬性** 或 **僅事件屬性**。Span 連結上的屬性會與 Span 本身的屬性一起清理，**全部（名稱、屬性與事件）** 也會清理 Span 的狀態訊息及其事件的名稱。**敏感屬性鍵** 規則讀取的是鍵，因此一律清理鍵下的值：屬性中的，以及日誌 JSON 本文中的。

- **規則可以只針對一個服務。** 在 **進階** 下的 **僅限一個服務** 中選擇服務：規則會清理該服務的記錄，其他服務的記錄維持不變。留空時，它會清理所有服務的記錄。清單的 **範圍** 欄會顯示是哪一種。
- **表單會說明規則會為其他項目帶來什麼變化。** 在你建立規則之前以及啟用規則時，OneUptime 會列出讀取它將隱藏之值的項目：監測器、儀表板、已儲存的檢視、記錄規則和 SLO，每項都是連結，也會說明 [安全性事件](/docs/telemetry/security-events) 將失去什麼。依隱藏值篩選的監測器將不再相符。無論如何規則都會儲存。
- **IP 位址規則會隱藏屬於個人資料的位址。** 也就是公用 IPv4 與 IPv6 位址，無論寫法如何：簡寫形式，如 `2001:db8::1`；帶連接埠的方括號形式，如 `[2001:db8::1]:443`，方括號與連接埠會保留；帶區域的形式，如 `2001:db8::2%eth0`，區域會保留；或寫成 IPv6 的 IPv4 位址，如 `::ffff:203.0.113.7`，會被整個隱藏。它會保留私有、回送及連結本機位址，如 `10.0.0.12`、`127.0.0.1` 與 `fe80::1`，也會保留請求 URL 中的雲端中繼資料位址 `169.254.169.254`，[安全性事件](/docs/telemetry/security-events)正是在這裡尋找伺服器端請求偽造。若也要隱藏內部位址，請為它們新增一條 **自訂 Regex** 規則，例如用 `\b(?:\d{1,3}\.){3}\d{1,3}\b` 比對所有 IPv4 位址。除非規則對其執行雜湊，否則安全性事件不會為它在該規則清理的日誌或追蹤中發現的攻擊指出任何位址：請參閱[已被清除規則隱藏](/docs/telemetry/security-events#已被清除規則隱藏)。
- **雜湊權杖是你的專案獨有的。** 它以你的專案自己的金鑰產生，該金鑰由安裝的 `ENCRYPTION_SECRET` 衍生而來，因此同一個值在另一個專案中會得到另一個權杖，讀到權杖的人也無法據此還原出原值，或透過對猜測的值計算雜湊來比對。一個 IP 位址無論怎麼寫都只有一個權杖：`::ffff:203.0.113.7` 與 `203.0.113.7` 共用同一個。權杖還沒有金鑰時儲存的記錄中是 8 個字元的權杖，如 `[HASHED:8c87b489]`，與現在 16 個字元的權杖不同：在這些記錄到達保留期限之前，請同時搜尋兩者。變更 `ENCRYPTION_SECRET` 會改變所有權杖；在自行託管的安裝中，權杖的保密程度只與它相同。
- **安全性事件仍能指出經過雜湊的 IP 位址。** 當[安全性事件](/docs/telemetry/security-events)讀取你的日誌或追蹤時，執行雜湊的 IP 位址規則還會把它隱藏的每個位址與其權杖一起保存在一個只有安全性事件的掃描才會讀取的儲存區中：任何頁面、搜尋、匯出、API 或 AI 工具都無法讀取它。因此，來自一個在日誌中只顯示為權杖的位址的攻擊，仍會指出該位址，其案件也會說明應封鎖哪個位址。每個位址會保存到最後一次出現後的 30 天。清除或遮蓋位址的規則不會保存任何內容，此時安全性事件會說明是某條清理規則隱藏了該位址；超過 30 天的權杖，或在權杖有金鑰之前產生的權杖，也是如此。
- **清單和巢狀值也會被讀取。** 規則會讀取清單、清單的清單或鍵值清單中的每一段文字（例如 HTTP 標頭的值），並保留值的形狀：數字和布林值保持不變。**敏感屬性鍵** 規則也會讀取值內部的鍵，因此鍵值清單中的 `password` 也會被隱藏。以映射或清單形式傳送的日誌本文會以其 JSON 文字儲存，**敏感屬性鍵** 規則會讀取其中的鍵，就像讀取以 JSON 寫成的本文一樣。模式規則會讓這樣的本文保持為 JSON，以 JSON 寫成的屬性（例如 AI 呼叫的訊息）也一樣：它依照你的應用程式寫下的樣子讀取文字，把 `\n` 這樣的跳脫字元讀作它所代表的換行，並且只在其中的文字和數字內替換它找到的內容。
- **字串中的 JSON 也會被讀取。** 本身就是 JSON 的文字，例如包含 `{"password":"hunter2"}` 的屬性 `http.request.body`，或日誌本文中 Fluentd 記錄的 `log` 行，會當作 JSON 讀取，最多到彼此巢狀的 4 層 JSON，更深的部分當作文字讀取。**敏感屬性鍵** 規則會隱藏其中看起來像機密的鍵下的值，其他內容一概不變：其中的數字、空格和其他文字保持你的應用程式寫下的樣子。只是看起來像 JSON 的文字（例如 `{token}`）保持原樣。
- **太大而無法逐項讀取的值會當作文字讀取。** 巢狀超過 32 層的值，或會使一筆記錄的清單和映射中的值超過 10,000 個的值，會以其 JSON 文字讀取並儲存。模式規則會清理它在該文字中找到的內容；當其中出現 `password` 或 `token` 之類的字詞時，**敏感屬性鍵** 規則會隱藏整個值。 在日誌本文和字串中的 JSON 裡，只有超出這些上限的部分會當作文字讀取，其餘部分仍會逐一按鍵讀取。
- **例外來自清理後的記錄。** 在日誌中發現的例外在清理之後才產生，清理 Span 事件的規則也會清理記錄在這些事件上的例外。 每個例外仍依清理前的內容分組，因此新增規則絕不會把你已有的例外變成新例外，也不會再次為它觸發 **新例外**。當規則隱藏了新例外分組所依據內容的一部分時，它的指紋會像雜湊權杖一樣以你的專案自己的金鑰產生，因此沒有人能據此還原被隱藏的內容。
- **syslog 行的原始副本會隱藏規則在其各部分中隱藏的內容。** syslog 會把 RFC 5424 行的結構化資料依到達時的原樣保存在 `syslog.structured.raw` 中，透過 HTTP 傳送的 syslog 還會把整行保存在 `syslog.raw` 中。每個副本都會用規則對標頭欄位、結構化資料的每個參數與訊息留下的內容重新組成，然後規則會像讀取任何屬性一樣讀取它。因此，**敏感屬性鍵** 規則在 `syslog.structured.auth_1.password` 中隱藏的密碼，或 **僅本文** 規則在訊息中隱藏的地址，在副本中也會被隱藏，並依 RFC 5424 寫入值的方式寫成 `password="[REDACTED\]"`。規則沒有改動任何內容的行會依到達時的原樣保留其副本。
- **記錄的工作階段 ID 會被保留。** **敏感屬性鍵** 規則會隱藏登入工作階段，例如 `session_id`、`sessionid` 或 Cookie，但當 `session.id` 保存的是該日誌或 Span 所屬的工作階段時，會保留它：這是 [Session Replay](/docs/telemetry/session-replay) 用來把記錄歸檔到錄製內容下的隨機 ID，記錄無論如何都會把它保留為自己的工作階段。AI 呼叫的對話 ID 也以同樣的方式保留。不要把登入工作階段的密鑰作為 `session.id` 傳送。
- **Session Replay 也會被清理。** 除了錄製器在瀏覽器中進行的遮罩之外，適用於所有服務的日誌清理規則也會作用於 Session Replay 錄製內容。
- **規則依清單順序執行。** 每條規則看到的是前面的規則處理後的內容。
- **自訂模式所用的時間與記錄長度成正比。** 無論怎麼寫，它都保留 JavaScript 的語法與結果，包括先行斷言和後行斷言。反向參照（例如 `\1`）無法這樣執行：含有反向參照的規則在儲存時會被拒絕，大到無法執行的模式也一樣。如果要找出所有比對需要一遍又一遍地重讀一個很長的值，規則會清理整個值。專案的捨棄過濾器、清理規則和管道也為它傳送的每一批資料共用一份工作額度，與這批資料的大小成正比，足以讓數十個自訂模式讀取每個值。當它們的模式需要更多工作時，自訂清理規則會清理整個值，而無法得出結果的過濾器不會套用於該記錄。

## 查看過濾器捨棄了什麼

**捨棄過濾器** 清單會顯示每個過濾器的 **已捨棄** 計數，以及它最後一次捨棄的時間 **Last Dropped**。**Nothing dropped yet** 表示它從未符合過。過濾器自己的頁面會在 **活動** 下方顯示同樣的資訊，並在捨棄後一分鐘內更新。它的 **篩選條件** 卡片會顯示它比對的內容，你可以在那裡修改條件。

## 疑難排解

:::details 捨棄過濾器什麼都沒有捨棄
**等於**、**不等於** 和 **是其中之一** 比較的是精確文字，包含大小寫。嚴重程度寫作 `Information` 和 `Warning`，而不是 `INFO` 或 `WARN`。請檢查過濾器是否已啟用，並在修改後等待一分鐘。
:::

:::details 我預期的日誌不見了
查看每個捨棄過濾器的 **已捨棄** 計數和 **Last Dropped** 時間。關閉你懷疑的那個過濾器的 **已啟用**，之後的日誌就會重新到達。
:::

:::details 自訂清理規則顯示不會清除任何內容
它的模式為空，或者不是有效的規則運算式，或者無法執行（例如含有 `\1` 這樣的反向參照），因此它不會清理任何內容。編輯該規則，為它指定一個至少符合一個字元的模式。
:::

:::details 舊記錄仍然顯示新規則要清理的資料
清理規則在記錄到達時起作用。在規則之前儲存的記錄會保留原有內容，直到其保留期結束。請參閱 [資料保留](/docs/telemetry/data-retention)。
:::
