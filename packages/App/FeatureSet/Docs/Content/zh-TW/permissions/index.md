# 使用者、團隊與權限

OneUptime 中的一切都存在於**專案**之內。誰能在專案裡做什麼，取決於三件事：專案中的**使用者**、這些使用者所屬的**團隊**，以及授予這些團隊的**權限**。

有一條規則可以解釋絕大多數行為：**使用者從不直接持有權限。** 一位使用者的存取權，是他在該專案中所屬全部團隊權限的聯集。想改變某人能做什麼，就改變他的團隊歸屬，或者改變那個團隊的權限。

**擁有者**是另一回事。擁有者是對某個具體資源負責的人——一個監視器、一起事件、一個儀表板。擁有者會收到關於自己資源的通知，權限也可以選擇性地收窄為「只針對我擁有的東西」。

## 模型一覽

```text
專案
  └── 團隊                   ← 權限掛在這裡
       ├── 允許權限          ← 每一條都有範圍：全部 / 擁有 / 標籤
       ├── 封鎖權限          ← 一律凌駕於允許權限之上
       └── 團隊成員          ← 已接受邀請的使用者
```

| 概念 | 說明 |
| --- | --- |
| 使用者 | 一個 OneUptime 帳號。一次登入，可參與任意多個專案。 |
| 專案 | 租戶邊界。監視器、事件、團隊與資料都恰好屬於一個專案。 |
| 團隊 | 專案內的具名群組，承載權限。 |
| 團隊成員 | 受邀加入團隊並已接受的使用者。 |
| 權限 | 一項單獨能力，例如 `CreateProjectMonitor`；或打包多項能力的角色，例如 `MonitorAdmin`。 |
| 範圍 | 一條允許權限能涵蓋多遠：全部資源、僅擁有的資源，或僅帶標籤的資源。 |
| 擁有者 | 被標記為某個具體資源負責人的使用者或團隊。 |
| 標籤 | 貼在資源上的標記，用於限制權限與整理資源。 |

## 使用者

使用者帳號在整個 OneUptime 執行個體範圍內通用——同一組登入在該使用者受邀的每個專案中都有效。

當使用者是專案內**至少一個團隊**的成員時，他就「在」這個專案裡。沒有獨立的「把使用者加入專案」步驟：邀請某人加入專案，就是邀請他加入一個團隊。

- 邀請會建立一筆待處理的團隊成員記錄。使用者只有在**接受邀請之後**，才算作專案成員，也才取得任何權限。
- 把使用者從專案內所有團隊中移除，就撤銷了他對該專案的存取權。
- 若專案強制使用 SSO，而使用者尚未透過身分提供者驗證，他會被視為未授權的 SSO 使用者，在完成驗證前什麼都看不到。參見 [SSO](/docs/identity/sso)。
- 設定 SCIM 後，身分提供者可以自動建立、更新與移除使用者及其團隊歸屬。參見 [SCIM](/docs/identity/scim)。

位置：**設定 → 使用者**列出專案中的所有人及其邀請狀態。

## 團隊

團隊是權限抵達人的通道。每個新專案都以三個團隊開始：

| 團隊 | 持有的權限 | 可編輯 |
| --- | --- | --- |
| Owners | `ProjectOwner` | 否。一律至少有一名成員。 |
| Admin | `ProjectAdmin` | 否 |
| Members | `ProjectMember` | 是——它是一個起點，可以任意修改 |

**Owners** 與 **Admin** 團隊被刻意鎖定：權限無法編輯，團隊也不能刪除或改名。正是這一點避免專案意外把自己鎖在門外。Owners 團隊必須一直保留至少一名成員。

`ProjectOwner` 是最高存取層級：帳務、刪除專案，以及管理員能做的一切。`ProjectAdmin` 涵蓋除帳務與刪除專案以外的全部內容。

為專案開啟或關閉簡訊、語音電話、WhatsApp 或 Telegram 屬於帳務事項，因為每則訊息都要花錢。只有 `ProjectOwner` 和 `ManageProjectBilling` 權限（**Manage Billing**）可以在 **專案設定 > 通知 > 通知設定** 中變更這些開關，`ProjectAdmin` 不行。

為專案的預付餘額儲值同樣屬於帳務事項。在 OneUptime Cloud 上，簡訊、語音電話、WhatsApp 和 Telegram 從 **專案設定 > 通知 > 通知設定** 中的餘額支付，AI 從 **專案設定 > 人工智慧 > AI 點數** 中的 AI 點數支付。只有專案擁有者或擁有 **Manage Billing** 權限的使用者才能為它們儲值或變更它們的 **自動儲值**，專案管理員不行。關於餘額不足的訊息會說明誰可以儲值，只有這些人才會看到可用的 **儲值餘額** 按鈕或頁面連結。

你可以建立任意多個額外團隊——「前端待命」、「支援」、「唯讀稽核」——並給每個團隊它需要的權限。

位置：**設定 → 團隊**。開啟團隊即可進入 **Members** 與 **Permissions**；**Block Permissions** 位於 Permissions 頁面底部的 **More settings** 中。

## 權限

權限是一項單獨能力。發放方式有兩種，都在團隊的 **Permissions** 分頁中。

### 角色

角色把整個產品領域打包為三個層級之一：

- **Admin** — 對該領域的完全控制，包含其設定（嚴重程度、狀態、範本）。
- **Member** — 日常工作：建立、編輯與刪除資源，但不能重新設定該領域。
- **Viewer** — 唯讀。

例如 `MonitorAdmin`、`IncidentMember`、`StatusPageViewer` 等。絕大多數情況下你想要的都是角色——隨著 OneUptime 新增功能，角色依然正確，因為與監視器相關的新資料表會併入既有的監視器角色，而不需要你重新授予。

全部 {{PERMISSION_ROLE_COUNT}} 個角色列於[權限參考](/docs/permissions/reference)。

### 細部權限

每一項單獨能力也可以單獨授予——`CreateProjectMonitor`、`ReadProjectIncident`、`DeleteProjectStatusPage`，以及另外 {{PERMISSION_TOTAL_COUNT}} 項。當角色過於寬泛、你只想給出恰好一件事時使用它們。

它們也是建立 API 金鑰時使用的鍵，以及 API 與 Terraform 供應器期望的值。

完整清單見[權限參考](/docs/permissions/reference)。

### 允許與封鎖

每個團隊都有兩份清單：

- **Permissions**（允許）——這個團隊可以做什麼。
- **Block Permissions**——無論允許清單怎麼寫，這個團隊永遠不能做什麼。

**封鎖一律獲勝。** 不帶標籤的封鎖項目會徹底取消團隊的這項能力。帶標籤的封鎖項目只針對帶有這些標籤的資源取消它——適合「這個團隊可以編輯監視器，但帶 Production 標籤的除外」。

同一項權限不能同時在兩份清單中攜帶限制標籤；OneUptime 會拒絕第二筆並給出說明。

使用者的允許項目會在其所有團隊之間累加，但封鎖適用於該使用者所做的一切：某個團隊上不帶標籤的封鎖，即使另一個團隊允許，也會取消這項能力；封鎖項目本身永遠不授予任何權限。若某人的權限少於預期，請在他所屬的每個團隊裡尋找封鎖；若多於預期，請在每個團隊裡尋找允許。

## 範圍：一條允許權限能涵蓋多遠

每條允許權限在新增時都會選定一個範圍：

| 範圍 | 意義 |
| --- | --- |
| 專案中的全部資源 | 預設值。權限適用於每一個相符的資源。 |
| 由該團隊或其成員擁有 | 權限只適用於該團隊或執行操作的使用者被列為擁有者的資源。 |
| 依標籤限制（進階） | 權限只適用於帶有所選標籤之一的資源。 |

**擁有**是打造「各自照顧自己服務」模型最簡單的方式：給團隊授予範圍為「擁有」的 `MonitorAdmin`，再把該團隊設為它負責的那些監視器的擁有者。它只會收窄真正能有擁有者的資源——監視器、事件、儀表板、服務之類。專案設定（事件狀態、標籤、團隊本身）沒有擁有者，因此「擁有」範圍的角色在那裡表現如常。

**標籤**是同一思路更手動的版本：為資源貼上標記，再授予受這些標記限制的權限。

有些角色依定義就是專案層級，完全不提供範圍，因為收窄它們毫無意義——「Billing Admin，但只針對我擁有的帳務」什麼也沒描述：

## 擁有者

擁有者是關聯到某個具體資源的使用者或團隊。大多數代表你所維運之物的資源——監視器、事件、警示、排程維護、待命政策、儀表板、服務、狀態頁、工作流程、Runbook 與 SLO——都有 **Owners** 分頁。

擁有者承擔兩項職責：

1. **通知。** 當資源發生狀況時——監視器中斷、建立了事件、SLO 開始消耗錯誤預算——OneUptime 通知的就是擁有者。
2. **存取權，若你如此設定。** 「擁有」範圍正是依據歸屬關係來解析的。使用者本人是擁有者，或他所屬的任一團隊是擁有者，即算相符。

僅有歸屬關係並不授予任何權限。身為某個監視器的擁有者，如果你所屬的團隊沒有同時持有監視器權限，你仍然無法編輯它。歸屬關係收窄存取權，永遠不會擴大它。

## 標籤

標籤是專案層級的標記，你把它附加到資源上。它有兩個用途：在儀表板中篩選與分組，以及如上所述限制權限。

只要資源帶有該權限標籤中的**至少一個**，標籤限制即告滿足。完全沒有標籤的資源，不滿足任何帶標籤限制的權限。

位置：**設定 → 標籤**。

## 遙測

記錄、追蹤、指標、例外、效能剖析和工作階段重播都屬於傳送它們的資源：服務、主機、Kubernetes 叢集、監控器、RUM 應用程式等。遙測權限能讀取多遠，取決於它的範圍：

- **全部資源**讀取專案中每個資源的遙測。
- **擁有**讀取你或你的某個團隊所擁有資源的遙測，以及不指向任何資源的遙測。
- **標籤**讀取帶有該權限某個標籤的資源的遙測。

遙測權限上帶標籤的封鎖會排除帶有這些標籤的資源的遙測，無論你還持有什麼權限。凡是讀取遙測的地方都是如此：各個探索器及其圖表、篩選器和屬性清單、匯出、工作階段重播，以及 AI 助理為你讀取的內容。指標名稱清單顯示你可讀取的服務回報的指標，以及沒有任何服務回報的指標，例如主機和叢集指標。如果你還可以讀取其他類型資源（例如主機或叢集）的遙測，則會顯示所有指標名稱。

## API 金鑰

API 金鑰的權限直接授予在金鑰本身上——它們不屬於任何團隊，也不受團隊歸屬影響。

- 就像給團隊一樣，指派同樣的細部權限與角色。
- 金鑰支援**封鎖權限**與**標籤限制**，方式與團隊相同。
- 金鑰**不**支援「擁有」範圍。歸屬關係是相對使用者解析的，而金鑰不是使用者，因此請明確地把所需存取權授予金鑰。

為每個整合配一把自己的金鑰，權限集盡可能窄，這樣撤銷其中一把不會影響其他。

位置：**設定 → API 金鑰**。另見 [API 參考](/docs/api-reference/api-reference)。

## OneUptime 如何判定一個請求是否獲准

對於已登入的使用者，依序執行：

1. 找出使用者在本專案中所屬的團隊，只計入已接受的邀請。
2. 收集這些團隊的每一筆權限記錄——允許與封鎖，各自帶有標籤與範圍。
3. 先檢查封鎖清單。目標資料表在該操作上接受的任一項權限上只要有不帶標籤的封鎖，無論它設在哪個團隊，都會直接拒絕該請求。
4. 檢查允許清單。請求需要至少一項目標資料表在該操作上接受的權限。對於營運資源——監視器、事件、儀表板之類——對應的 **All Operational Resources** 權限（Create、Read、Edit 或 Delete）也算數，除非它本身被封鎖。
5. 套用範圍。範圍為「擁有」的授予會把查詢收窄到所擁有的資源；標籤範圍收窄到相符的標籤。若同一操作還有更寬的授予，以更寬的為準。
6. 套用標籤封鎖。帶標籤的封鎖在目標資源帶有其中之一時拒絕請求。當一筆記錄本身沒有標籤時，例如事件的備註或狀態頁的公告，針對讀取它的帶標籤封鎖會在它所屬的記錄帶有其中某個標籤時將其排除。

記錄的每個欄位都以該記錄自己的讀取權限來讀取：其他類型記錄的權限永遠打不開它。有些欄位刻意縮小了範圍。機密只有能編輯或管理其所屬記錄的人才能讀取，例如監控器的傳入請求金鑰、傳入郵件金鑰和伺服器代理程式金鑰，或工作流程的 Webhook 金鑰和傳入郵件金鑰。觀看工作階段重播的錄影需要 **Watch Session Replays**，僅有 **List Session Replays** 不夠。遙測依訊號分別讀取：**Read Telemetry Service Log** 讀取記錄，**Read Telemetry Service Traces** 讀取追蹤，**Read Telemetry Service Metrics** 讀取指標，包括指標圖表。

欄位遵循同樣的規則。欄位的權限上有不帶標籤的封鎖，該欄位就被取消；對於營運資源，對應的 **All Operational Resources** 權限可以打開每一個可讀取或修改該記錄的人都能打開的欄位——但打不開刻意縮小範圍的欄位，例如密鑰。

其他所有詢問你是否持有某項權限的地方，也都由同一規則決定：並非單純讀寫的操作，例如加值簡訊、通話或 AI 額度、支付發票、測試通知規則，以及 OneUptime 顯示的按鈕。你不能使用的按鈕會顯示為鎖定並說明原因；若原因是你所屬某個團隊的封鎖，它會指出被封鎖的權限。

每位已登入的使用者還額外持有一小組自動權限，涵蓋讀取自己的個人資料與自己的通知規則等。它們不是管理員權限，也不會開放他人的資料。

解析出的權限依使用者與專案快取，並在團隊歸屬或團隊權限變更時重新整理。若你修改了權限而使用者沒有立即看到變化，請他重新載入頁面。

## 配方

**只旁觀的團隊。** 建立團隊並加入 `Viewer` 角色，或者只為它該看的領域加入對應的 `*Viewer` 角色。

**自己管自己服務的待命工程師。** 給團隊授予範圍為**擁有**的 `MonitorAdmin`、`IncidentMember` 與 `OnCallMember`，再把該團隊加入為它所維運監視器的擁有者。

**讓外包遠離正式環境。** 以**全部**範圍給團隊所需的角色，接著為敏感能力加入一條限定在 `Production` 標籤上的**封鎖權限**。

**只回報部署的 CI 流水線。** 建立一把只帶所需細部權限的 API 金鑰——不要給角色。

**不該看到帳務的人。** 不要把他加入 Owners 團隊。`ProjectAdmin` 本就不含帳務。
