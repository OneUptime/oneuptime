# 執行與日誌

工作流程每跑一次，OneUptime 都會存下一筆紀錄——什麼時候跑的、成不成功，以及每個區塊做了什麼。那筆紀錄就叫做一次**執行**。你要確認工作流程有效、要對出錯的那次除錯、要回頭看過去的活動，靠的都是執行紀錄。

## 去哪裡找

| 頁面 | 你會看到什麼 |
| ---- | ------------ |
| **工作流程 → 執行與日誌** | 專案裡每一個工作流程的每一次執行。可依工作流程名稱、狀態和時間篩選。 |
| **某個工作流程 → 執行與日誌** | 只有這一個工作流程的執行。這裡有的是 **執行 ID** 篩選器，而不是工作流程篩選器。 |
| **單一次執行** | 從執行列上的 **檢視日誌** 按鈕打開——執行列本身不能點。 |

## 執行狀態

| 狀態 | 代表什麼 |
| ---- | -------- |
| **已排定** | 觸發器已經開火，這次執行正在排隊等執行器接手。通常不到一秒。過了 5 分鐘還停在已排定的執行會被判為失敗——沒有人接走它。 |
| **執行中** | 工作流程正在進行。跑很久的區塊會讓執行一直停在這個狀態。 |
| **等待中** | 執行停在 **Sleep** 區塊上，之後會自己恢復。等待期間不佔用任何工作者。 |
| **Executed** | 這次執行一路跑到最後都沒有失敗。（這就是成功狀態——標籤上寫的是 **Executed**，不是「Success」。） |
| **錯誤** | 執行因為某個區塊拋出錯誤而停下。另外這幾種情況也用這個狀態：排隊的執行始終沒被接走、休眠中的執行恢復訊號遺失、排程運算式無法解析，或工作流程在執行途中被停用。 |
| **Timeout** | 執行的時間超過允許的長度。請見[工作流程設定與安全](/docs/workflows/configuration)。 |
| **Execution Exceeded Current Plan** | 專案在過去 30 天裡的工作流程執行次數已經用完，或訂閱費用未付。這次執行會被記錄下來，但不會真的執行。僅限 OneUptime Cloud。 |

把流程交給 **錯誤** 輸出的區塊——例如 API 區塊收到 4xx——不會讓整次執行失敗。錯誤分支照樣執行，而這次執行最後仍然是 **Executed**。那個步驟本身還是會畫成紅色，方便你找到它。

## 讀一次執行

在某次執行上點 **檢視日誌** 就會打開它。**Workflow Run** 檢視有兩個分頁。

**步驟**——每個跑過的區塊一列，依順序排。每一列會顯示區塊的標題、它的元件 id、花了多久，以及它從哪個輸出離開（`→ success`、`→ error`、`→ yes`）。展開一列，可以看到兩塊細節：

- **Received**——區塊實際拿到的設定，也就是所有變數都解析完之後的樣子。
- **Returned**——它產出了什麼。

失敗的步驟是紅色的，而且一開始就是展開的，錯誤訊息印在 **Received** 上方。

**Full Log**——執行器一行一行印出來的原始日誌，包含區塊自己記下的任何東西。當步驟檢視解釋不了失敗原因時就看這裡。

有兩個細節值得記著。每個步驟標題底下印的元件 id，正好就是可以貼進 `{{local.components.<id>.returnValues.…}}` 參照裡的那串字，所以這是把參照寫對的最快方法。另外，一次執行只保留最後 100 個步驟——很長或反覆恢復的執行，會在早期步驟被丟掉的地方顯示一則琥珀色提示。

顯示出來的值，是變數填好之後區塊看到的內容，但有兩個例外：密鑰以及區塊標記為敏感的欄位會被遮蔽，過長的值則會被截斷並加上「… (truncated)」。

從 **建構器** 啟動的執行會直接打開這個檢視並跟著跑，所以你可以當場看著它發生，不必事後再回頭找。

## 常見的除錯情境

### 「我的工作流程沒有跑。」

1. 確認工作流程在它的 **概覽** 頁上是 **已啟用**。新工作流程一開始是停用的，而停用的工作流程會拒絕每一次執行——包括手動的。
2. OneUptime 事件觸發器：確認那個事件真的發生了。打開那筆記錄，看它的歷程。
3. Webhook 觸發器：確認對方系統送到的是正確的網址。多數工具在送出 webhook 時都會留下紀錄——去那裡查。
4. Schedule 觸發器：確認 cron 運算式對應的時間，就是你以為的那個時間。

如果執行紀錄*確實*出現了，狀態卻是 **Execution Exceeded Current Plan**，那就是專案在過去 30 天裡的工作流程執行次數已經用完，或訂閱費用未付。那次執行的日誌會寫出次數和你方案的上限。這只適用於 OneUptime Cloud。

### 「後面的某個區塊一直沒跑。」

區塊沒跑，通常是接線的問題。打開 **建構器** 檢查：

- 前一個區塊的輸出，有沒有連到這個區塊的輸入？
- 前一個區塊走的輸出，是不是跟你以為的不一樣——走了 **錯誤** 而不是 **成功**，或走了 **否** 而不是 **是**？步驟分頁會顯示它走的是哪一個。

### 「有個變數傳過來是空的。」

打開那次執行，看失敗步驟的 **Received** 區塊。

- 如果你看到的是字面上的 `{{local.components.…}}` 文字，代表參照沒有解析。通常是元件 id 或回傳值 id 打錯了——記得那是區塊的 **Identifier**，不是顯示在上面的名稱。也順便檢查 `local.components` 本身的拼字：`{{local.componets.api-get-1.returnValues.response-body}}` 會被當成字面文字送出去，而那次執行仍然報 **Executed**。
- 如果你看到的是空字串，代表前一個區塊有跑，只是沒有產出那個欄位。

**Full Log** 分頁裡有一行警告會指名任何沒解析成功的參照，通常這是最快找到它的辦法。

### 「我手動跑沒問題，從觸發器跑就不行。」

打開 **建構器**，點 **執行工作流程**，用貼近真實觸發器會送出的值把觸發器的欄位填好。然後把這次執行的 **Received** 值和真實執行的並排比較。差別通常就在某一個欄位名稱或型別上。

## 重新執行工作流程

沒有「重試這次執行」的按鈕。我們不會自動重跑舊的執行，因為那些副作用——Slack 訊息、API 呼叫、工單——重複一次未必安全。想把事情重做一遍，就把工作流程修好、等下一次真實的觸發把它跑起來，或是打開 **建構器**、用同樣的值點 **執行工作流程**。

## 執行紀錄會保留多久？

在 OneUptime Cloud 上，執行紀錄保留 **30 天** 之後刪除——這也是為什麼兩份執行清單都說自己涵蓋最近 30 天。自架的安裝會一直保留到你自己刪掉；如果某個工作流程跑得非常頻繁、把歷史弄得很亂，就把它停用或刪掉，別再往裡面加雜訊。

在步驟追蹤加進來之前記錄的執行沒有 **步驟** 內容，只會顯示它們的 **Full Log**。
