# 工作流程設定與安全

在讓工作流程處理真實流量之前需要了解的內容：如何安全地開啟它、誰能做什麼、密鑰和 URL 如何保持私密、工作流程的步驟可以變更什麼，以及每次執行都要遵守的限制。

- [權限](#權限): 工作流程角色，以及它們背後的個別權限。
- [步驟可以做什麼](#工作流程步驟可以做什麼): 步驟以工作流程所在專案的 Project Admin 身分執行。

## 開啟或關閉工作流程

每個工作流程在它的 **建構器** 頂端和 **概覽** 頁面上都有一個 **已啟用** 開關。關閉時，工作流程不會執行——Webhook 呼叫、收到的電子郵件、排程時間和 OneUptime 事件都會被忽略，**執行工作流程** 和 **Run just this step** 也一樣。新的工作流程一開始是停用的。

把這個開關當作「準備就緒」的關卡：

:::steps
1. 建構工作流程。
2. 用接近真實的值在 **建構器** 中點選 **執行工作流程**。已停用的工作流程即使手動也無法執行，所以建構器會先請你開啟它：點選 **開啟並執行**。
3. 開啟這次執行，檢查每個區塊是否都走到了你預期的地方。請參閱 [執行記錄](/docs/workflows/runs-and-logs)。
4. 如果準備好了，就讓 **已啟用** 保持開啟。如果還沒有，就先關掉，直到準備好為止：開啟期間，它的觸發器會在真實事件發生時觸發。
:::

關閉工作流程會阻止新的執行開始。已經在進行的執行會完成，但停在 **Sleep** 區塊上等待的執行會在醒來時被取消。

## 封存工作流程

把不再需要但想保留的工作流程封存起來。已封存的工作流程：

- **永遠不會執行**，無論是哪種觸發器。手動執行和 **Run just this step**、Webhook 呼叫、排程、OneUptime 事件、收到的電子郵件，以及其他工作流程的 **Execute Workflow** 步驟都會被拒絕。對已封存工作流程的 Webhook 呼叫會收到一個說明工作流程已封存的錯誤。
- **停止正在等待的執行。** 在 **Sleep** 步驟中休眠的執行會在醒來時被取消，已經在佇列中但尚未開始的執行會以 "Workflow was archived before this run started, so it did not run." 結束。
- **離開工作流程清單。** 可以在 **工作流程 → 進階 → 已封存** 底下找到它。
- **保留一切。** 它的步驟、變數、擁有者、標籤和執行歷史都保持原樣。

要封存一個工作流程，開啟它，前往 **設定**，點選 **封存**。要封存多個，在 **工作流程** 清單中選取它們，然後選擇 **封存**。

要恢復工作流程，開啟 **工作流程 → 進階 → 已封存**，選取它並選擇 **取消封存**，或開啟它，點選頁面頂端橫幅上的 **取消封存**。

封存和 **已啟用** 開關是兩回事。封存不會動到開關，所以原本開啟的工作流程一取消封存就會再次執行，原本關閉的則保持關閉。**已封存** 頁面的 **When Unarchived** 欄會顯示哪個是哪個。

匯出的工作流程從不攜帶封存狀態，所以匯入的副本永遠不會是已封存的。

## 密鑰

如果某個變數儲存的是敏感內容，就把它標記為 **密鑰**：它的值會從執行日誌和步驟追蹤中清除。任何變數的值儲存後都無法讀回，無論是否為密鑰，在儀表板中或透過 API 都不行；而且變數一旦設為密鑰，就會一直是密鑰。

把密鑰變數用於：

- 外部服務的 API 金鑰。
- 驗證權杖。
- Webhook 簽署金鑰。
- 任何你不希望只有唯讀權限的人看到的內容。

不要把密鑰直接貼到區塊中——像 `Authorization: Bearer eyJh...` 這樣的值會在工作流程和日誌中可見。請改用 `{{global.variables.MY_SECRET}}`。

如果密鑰是會過期的 OAuth 存取權杖，就把這個變數設為 [OAuth 2.0 變數](/docs/workflows/variables#oauth-20-變數會自動重新整理的權杖)。這樣 OneUptime 會從你的身分提供者取得權杖，並在工作流程即將使用過期權杖時重新整理它。OAuth 2.0 變數一律是密鑰，它們的憑證在資料庫中加密。

## 匯出與匯入工作流程

你可以把工作流程作為 JSON 檔案在專案之間，或在自行託管的安裝與 OneUptime Cloud 之間移動。

:::tabs
@tab 匯出
開啟工作流程，前往 **設定**，點選 **匯出工作流程**。要把多個工作流程放進一個檔案，請在 **工作流程** 清單中選取它們，然後選擇 **匯出JSON**。
@tab 匯入
在 **工作流程** 清單中點選 **Import JSON**，選擇從任何 OneUptime 專案匯出的檔案。如果專案中已有同名的工作流程，匯入的工作流程會在名稱後加上 "(Imported)"。
:::

檔案包含工作流程的名稱、描述、啟用狀態和它的圖形。它刻意不包含：

- **Webhook 密鑰。** 建立工作流程時會產生一個新的，所以匯入的工作流程有不同的 Webhook URL——請從新工作流程的 Webhook 觸發器複製它。所有呼叫原工作流程的東西都要改為指向新的。
- **收到的電子郵件的地址。** 帶有 Incoming Email 觸發器的匯入工作流程會得到自己的地址——請從新工作流程的觸發器複製它。所有寄郵件給原工作流程的東西都要告知新地址。
- **全域變數。** 讀取 `{{global.variables.MY_SECRET}}` 的區塊會保留這個參照，但值不在檔案中。執行匯入的工作流程之前，請在目標專案中建立這些變數。
- **擁有者和標籤。** 你的專案自己的標籤和擁有者規則會作用於匯入的工作流程，就像你手動建立它一樣。

匯入的工作流程一律以 **已停用** 狀態建立，即使它在匯出處是啟用的——它的圖形可能指向目標專案中不存在的監測器、待命策略或其他工作流程。檢查它、啟用它、用 **執行工作流程** 測試它，然後讓它保持開啟。複製工作流程也是同樣的行為，所以副本永遠不會在你編輯之前就與原工作流程同時觸發。

由於圖形是原樣帶過去的，直接輸入到區塊中的任何內容也會一併帶過去。這正是把憑證保存在密鑰變數中的實際原因：匯出一個寫死了權杖的工作流程，就等於把那個權杖交給了拿到檔案的任何人。

## Webhook 安全

Webhook 觸發器會給你一個唯一的 URL。任何知道這個 URL 的人都能呼叫它。要防止意外或不受歡迎的呼叫端：

- 把 URL 當作密碼對待。不要公開分享，也不要提交到公開存放庫。Webhook 觸發器會在你點選 **顯示** 之前隱藏 URL 中的密鑰，**複製 URL** 會在不顯示的情況下複製 URL。
- 如果 URL 外洩，請在 **建構器** 中點選 Webhook 觸發器，然後點選 **重設 URL**。工作流程會得到一個新的 URL，舊的會立即失效。
- 如果觸發器說它的 URL 以工作流程的 ID 結尾，請重設它。在 Webhook URL 擁有自己的密鑰之前建立的工作流程，用的是工作流程的 ID，而任何能開啟該工作流程的人都能看到它。
- 對於敏感的工作流程，請呼叫端系統在標頭中傳送一個共用權杖（例如 `X-Webhook-Token`），並在做任何重要的事之前用 **If / Else** 區塊檢查它。把預期的權杖儲存為密鑰變數。
- 對於非常敏感的工作流程，優先使用 OneUptime 事件觸發器加上手動匯入步驟，而不是公開的 Webhook。

只有能編輯工作流程的人——**Project Owner**、**Project Admin**、**Workflow Admin** 或 **Edit Workflow**——才能查看或重設它的 Webhook URL。任何拿到 URL 的人都可以不登入、從任何地方啟動工作流程，所以其他人會看到一則說明應該找誰的提示。這也包括在 **建構器** 中手動執行工作流程的 **Workflow Member**。

## 收到的電子郵件的安全

Incoming Email 觸發器會給工作流程一個專屬地址，任何知道這個地址的人都能寄郵件給它。`@` 之前的部分是工作流程的密鑰，所以請把這個地址當作密碼對待：

- 不要公開它，也不要放進公開存放庫。觸發器會在你點選 **顯示** 之前隱藏密鑰，**複製地址** 會在不顯示的情況下複製地址。
- 如果地址外洩，請在 **建構器** 中點選 Incoming Email 觸發器，然後點選 **重設地址**。工作流程會得到一個新的地址，從此寄到舊地址的郵件會被忽略。
- 任何人都可以在電子郵件上填寫任意寄件者，所以 **From** 不能證明是誰寄的。在工作流程做任何重要的事之前，請用 **If / Else** 區塊檢查只有真正的寄件者才知道的東西——主旨或標頭中的權杖。把預期的權杖儲存為密鑰變數。
- 執行收到的所有內容中——**To**、**CC**、標頭和內文——密鑰都會被隱藏，因為執行的日誌對任何能讀取該工作流程執行的人都可見。

只有能編輯工作流程的人——**Project Owner**、**Project Admin**、**Workflow Admin** 或 **Edit Workflow**——才能查看或重設它的地址。其他人會看到一則說明應該找誰的提示。

## 對外網路存取

API 區塊和其他 HTTP 區塊會從 OneUptime 發出請求，IRC 區塊會從 OneUptime 連線到 IRC 伺服器的連接埠。如果你是自行託管，請確保你的安裝能連線到你呼叫的服務。如果你使用 OneUptime Cloud，我們的對外 IP 範圍列在 [IP 位址](/docs/configuration/ip-addresses) 中，你可以在對方那一端放行它們。

區塊可以連線到哪些位址取決於區塊：

| 區塊                                                           | 回送、link-local、雲端中繼資料                                               | 私人網路位址                                                                                                                                      |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **API** 區塊和 **Run Custom JavaScript** 的請求                | 拒絕，除非確切的主機列在 `PRIVATE_NETWORK_WEBHOOK_ALLOWLIST` 中              | 拒絕，除非自行託管的管理員透過 `ALLOW_PRIVATE_NETWORK_WEBHOOKS` 或 `PRIVATE_NETWORK_WEBHOOK_ALLOWLIST` 允許                                      |
| **Send Email**、**IRC** 和 OAuth 2.0 權杖 URL                  | 拒絕                                                                         | 在 OneUptime Cloud 上拒絕。在自行託管的安裝上允許，除非 `DATA_SOURCE_BLOCK_PRIVATE_ADDRESSES` 為 `true`                                          |
| Slack、Microsoft Teams、Discord 和 Telegram                    | 拒絕                                                                         | 拒絕：每個都只會傳送到它自己服務的位址                                                                                                            |

自行託管的管理員如何開放這些限制，請參閱 [私人網路存取](/docs/self-hosted/private-network-access)。

## AI 元件

**Generate Text with AI** 會向一個 LLM 傳送一個請求：專案的預設 LLM 提供者，或在專案沒有時使用安裝的全域提供者。在 **專案設定 → 人工智慧 → LLM 提供商** 底下設定提供者，並且絕對不要把提供者的 API 金鑰或你自己的端點放進工作流程。

提供者會收到什麼，以及模型能用它做什麼：

- **只有你放進區塊的內容。** OneUptime 會先傳送一則固定的安全指示，然後是區塊的 **System Instructions**、**Prompt** 和 **Context**，其中的參照已經填好。**Context** 放在最後，位於一個標記之後，安全指示會告訴模型，標記之後的一切都是不可信的資料，即使是看起來像指示的文字。
- **沒有其他任何東西。** 觸發器的資料、工作流程的歷史、其他區塊的輸出、專案記錄、遙測和密鑰都永遠不會被附上。只有當你在這三個設定之一中參照它們時，它們才會離開 OneUptime。
- **只有文字，沒有工具。** 模型無法查詢 OneUptime、發出 HTTP 請求或變更資料。提供者的其他參數只會放行一份只調整產生方式的欄位允許清單：它們不能取代訊息，不能加入工具、網頁搜尋或其他資料來源，不能要求文字以外的內容或多個回答，不能串流，不能讓提供者保留請求，也不能提高區塊的輸出上限。OneUptime 不認識的欄位會被捨棄。
- **模型由你的管理員選擇。** 如果產生必須保持離線，請選擇一個不會在提供者那一端自行擷取任何內容的模型。

會記錄什麼：

- 執行的日誌會隱藏區塊的 **System Instructions**、**Prompt**、**Context** 和 **Response**。後續區塊在執行期間仍然可以使用它們；你把其中之一插入到某個區塊中，那個區塊會依自己的規則記錄它，所以插入就等於選擇讓它顯示。
- 提供者、模型、權杖數、**LLM Log ID** 和一則安全的錯誤訊息仍然可見，供營運和計費使用。提供者的原始錯誤不會進入任何日誌，因為提供者可能會在其中重述請求。
- 每次呼叫都會列在 **專案設定 → 人工智慧 → AI 日誌** 底下，附有提供者、模型、狀態、權杖、費用和計費資訊，但不包含提示詞、回覆或原始錯誤。

它需要什麼，以及費用：

- 必須在 **專案設定 → 人工智慧 → AI Features** 底下開啟 **啟用 AI**。在 OneUptime Cloud 上，專案還需要 Growth 方案或更高，以及已付款的訂閱。沒有計費的自行託管安裝沒有方案要求。
- 透過收費的全域提供者進行的呼叫會使用專案的 AI 額度。
- 如果專案擁有者設定了 [專案自己的每日 AI 限額](/docs/ai/ai-sre#the-projects-own-daily-limits)，每次呼叫都會計入其中。一旦達到限額，區塊會走 **Error**，不聯繫模型，直到 UTC 午夜。

| 限制                                                          | 值                                                                       |
| ------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **System Instructions**、**Prompt** 和 **Context** 合計       | 50,000 個字元                                                            |
| **Temperature**                                               | 從 `0` 到 `1`                                                            |
| **Maximum Output Tokens**                                     | 從 `1` 到 `4096`，預設 `1024`                                            |
| 一個請求                                                      | 只嘗試一次，最長 60 秒                                                   |
| 同時進行的呼叫                                                | 每個專案 3 個。更多的會走 **Error**，之後的執行可以重試。                |

驗證、設定、存取、限額、額度、並行、提供者和逾時失敗都會走 **Error** 路徑，原因放在 **Error** 中。在工作流程上線之前把這條路徑連好。

> [!WARNING]
> 你參照的每個值都是你傳送給提供者的資料。除非提供者獲准接收，否則不要把密鑰變數放進提示詞或上下文。像 Ollama 這樣自行託管的本機提供者會把請求留在你自己的基礎架構內；託管的提供者則依它自己的資料處理條款接收請求。

## 權限

工作流程遵循你專案的角色型存取控制。三個工作流程角色：

- **Workflow Admin** —— 建構工作流程：建立、變更、執行和刪除它們，並管理它們使用的變數。
- **Workflow Member** —— 使用工作流程：開啟工作流程及其執行，用 **執行工作流程** 手動執行工作流程。成員不能建立、變更或刪除工作流程，也不能單獨執行它的某個步驟。
- **Workflow Viewer** —— 讀取工作流程及其執行。

**Project Owner** 和 **Project Admin** 能做 Workflow Admin 能做的一切。**Project Member** 可以建立和刪除工作流程，但不能變更或執行它們。

個別權限，用於只需要一項權限的團隊或 API 金鑰：

- **Create / Read / Edit / Delete Workflow** —— 對工作流程本身的基本權限。變更工作流程，包括開啟或關閉它以及封存它，需要 **Edit Workflow**；**Delete Workflow** 只能刪除。
- **Edit Workflow** —— 也是用 **Run just this step** 單獨執行一個步驟，以及查看或重設工作流程的 Webhook URL 和收到的電子郵件的地址所需要的權限。手動執行整個工作流程需要 **Edit Workflow**、**Workflow Admin** 或 **Workflow Member**。
- **Read Workflow Log** —— 查看執行所需。
- **Create / Read / Edit / Delete Workflow Variables** —— 管理全域變數和工作流程變數。

手動執行只能到達你能開啟的工作流程：限定於某些標籤，或限定於你團隊擁有之工作流程的角色，只能執行這些工作流程。無法執行某個工作流程的人會看到灰色的 **執行工作流程**，原因寫在它的工具提示中。

把 **Workflow Admin** 給建構自動化的人，把 **Workflow Member** 給只負責啟動它的人。把變數的編輯權限留給管理專案密鑰的人。角色如何授予，請參閱 [使用者、團隊與權限](/docs/permissions/index)。

## 工作流程步驟可以做什麼

讀取和變更 OneUptime 記錄的步驟——Find、Create、Update 和 Delete 元件，以及 On Create、On Update 和 On Delete 觸發器——以工作流程所在專案的 **Project Admin** 身分執行。無論工作流程是誰建構的，步驟都要通過與 Project Admin 在儀表板和 API 中相同的檢查：

- **只限工作流程自己的專案。** 步驟只會讀寫工作流程所屬專案的記錄，不涉及其他專案，Update 也絕不會把記錄移到另一個專案。
- **只限 Project Admin 可以做的事。** 步驟只能授予 Project Admin 自己擁有的團隊和 API 金鑰權限，所以它不能分派 **Project Owner**、計費或刪除專案的權限，也不能把人加入權限超出 Project Admin 的團隊，例如擁有者團隊。步驟無法讀取是誰建立了探針或 AI 代理程式，那只有專案擁有者才看得到。
- **不能讀取 Runbook 憑證。** Project Admin 可以讀取 Runbook 憑證，但這項權限不會借給步驟。當某個變更需要這項讀取權限時——讓 OneUptime AI 不經詢問就執行它的指令、為某個 Runner 開啟 **執行 AI 修復指令**、把 SSH 憑證指派給執行 OneUptime AI 指令的 Runner，或指定一個 Runbook 憑證（例如在 Runbook 的步驟中）——會改為檢查最後儲存該工作流程步驟的人，除非此人可以讀取 Runbook 憑證（**Read Runbook Credential**，或是 Project Owner 或 Project Admin），否則步驟會被拒絕。OneUptime 會在有人建立工作流程時，以及每次有人儲存它的步驟時記錄此人；重新命名工作流程、變更它的標籤或開啟關閉它，都不會改變最後儲存步驟的人。用 API 金鑰儲存步驟不會記錄任何人，因此在有人儲存這些步驟之前，工作流程的步驟無法做出這些變更。
- **只限你的方案包含的內容。** 在 OneUptime Cloud 上，建立或變更你的方案不包含之內容的步驟會被拒絕，並說明所需的方案，與儀表板一樣。沒有計費的自行託管安裝沒有方案限制。
- **不涉及 OneUptime 自己保留的東西。** 以下操作對所有人都會被拒絕，包括工作流程：
  - 編輯或刪除動態項目（事件、警示、片段、監測器、待命策略和排定維護的動態）；
  - 寫入通知日誌（簡訊、電話、電子郵件、WhatsApp、Telegram、推播、Webhook 和工作區訊息日誌）；
  - OneUptime 隨著事情發生而設定的值：自訂網域的 CNAME 是否已驗證、團隊的保護開關（**Is Team Editable**、**Is Team Deleteable**、**Is Permissions Editable**、**Should Have At Least One Member**）、哪個事件角色是主要角色以及它能否被刪除、擁有者或成員是否已收到通知、提醒的時間和次數、排班中目前和下一位待命人員、待命執行的進度、SLO 目前的消耗率和錯誤預算、被事件或維護暫停的監測器、狀態頁面私人使用者的密碼重設權杖和最近登入、服務回報的關於自身的事實（版本、執行階段、雲端），以及偵測規則或威脅來源的最近一次執行；
  - 透過向 **Create One Incident** 傳送 `createdIncidentTemplateId` 來依據範本宣告事件——請改為在步驟的 **Incident Template** 設定中選擇範本：這樣步驟會以 Project Admin 身分依據該範本宣告事件，並記錄範本；
  - 在記錄建立之後變更它屬於哪一筆記錄，例如擁有者列對應的監測器，或備註所在的事件。
- **不以任何人的身分。** 工作流程建立的記錄沒有建立者，稽核日誌會把工作流程（以它當時的名稱）記為做出變更的一方。

當檢查拒絕某個步驟時，步驟會走它的 **Error** 輸出，不做被拒絕的變更，執行的日誌會用淺白的文字寫明步驟和原因，例如 *"Create One Team Permission" was refused. Workflow steps can do only what a Project Admin of this project can do: …*。可以在工作流程的 [執行記錄](/docs/workflows/runs-and-logs) 中查看。Create Many 步驟會一筆一筆地建立記錄，並在第一筆被拒絕時停止：在它之前建立的記錄會保留。

與其他系統溝通的步驟——API、Email、Slack、Microsoft Teams、Discord、Telegram、IRC、Custom Code 和 Generate Text with AI——不會讀取或變更 OneUptime 記錄，所以以上這些對它們都沒有影響。

## 方案限制

在 OneUptime Cloud 上，工作流程需要 Growth 方案或更高，每個方案允許在任意 30 天內執行一定次數：

| 方案       | 最近 30 天的執行次數     |
| ---------- | ------------------------ |
| Growth     | 500                      |
| Scale      | 2,000                    |
| Enterprise | 實際上沒有限制           |

這個時間範圍是滾動的：專案記錄的每次執行，無論是手動還是來自觸發器，都會計入 30 天。在 Growth 和 Scale 方案上，**工作流程** 頁面會顯示一張 **工作流程執行** 卡片，說明專案已經用了多少次。一旦達到限制，新的執行會以 **Execution Exceeded Current Plan** 狀態記錄且不會執行；訂閱未付款期間也是如此。沒有計費的自行託管安裝沒有限制。

## 一次執行能跑多久

| 限制                                                              | 預設值         | 自行託管設定                    |
| ----------------------------------------------------------------- | -------------- | ------------------------------- |
| 一次執行，從開始或從 **Sleep** 之後醒來算起                       | 2 分鐘         | `WORKFLOW_TIMEOUT_IN_MS`        |
| 一個 **Run Custom JavaScript** 區塊                               | 5 秒           | `WORKFLOW_SCRIPT_TIMEOUT_IN_MS` |
| 一個 **Sleep** 區塊                                               | 最長 30 天     | —                               |

執行器會在每個區塊之前和之後檢查截止時間，一旦控制權返回，就把逾時的執行標記為 **Timeout**。它無法在區塊執行到一半時中斷它，所以等待網路的區塊有自己的時間限制：Generate Text with AI 請求最多 60 秒後放棄，OAuth 2.0 權杖請求 20 秒後放棄。在 **Sleep** 區塊上的等待不計入執行時間：執行會被擱置一旁，醒來時重新取得 2 分鐘。

## 呼叫其他工作流程的限制

**Execute Workflow** 元件讓一個工作流程啟動另一個工作流程。為了防止工作流程 A 啟動 B、B 又啟動 A 這樣的迴圈，相互啟動的工作流程鏈如果會繞回鏈中已有的工作流程，或深度超過 10 個工作流程，就會被拒絕。這時 **Execute Workflow** 區塊會走它的 **Error** 輸出，錯誤會顯示這條鏈。

如果你確實需要一條很長的鏈（例如每次執行處理一個項目的工作），通常更簡單的做法是用 **Run Custom JavaScript** 在單一工作流程內部迴圈。

## 什麼時候工作流程不是合適的工具

有幾種情況你應該改用別的東西：

- **繁重的運算或大型資料集** —— 工作流程是為輕量的銜接工作設計的，不是為大量運算設計的。請在你自己的基礎架構中執行繁重的工作，再讓工作流程去啟動它。
- **長時間執行的主動運算** —— 一次執行預設有 2 分鐘。對於像「做 A，等兩小時，再做 B」這樣的被動延遲，請使用 **Sleep** 元件；它會把執行擱置一旁，稍後再恢復，期間不佔用 worker。
- **有人參與的逐步事件應變** —— 這正是 [Runbook](/docs/runbooks/index) 的用途。工作流程用於無人看管的自動化。
