# 민감한 데이터 유형

데이터 보안은 143가지 민감한 데이터를 알고 있습니다. 카드 번호, 은행 계좌, 43개국의 국가 신분증 번호, 건강 식별자, API 키와 토큰, 그리고 특수 범주의 개인 데이터입니다. 각 데이터 유형에는 범주와 민감도가 있고, 한 국가에 속하는 경우에는 그 국가도 있습니다. 이 페이지에서는 값을 찾는 방식을 설명하고 모든 데이터 유형을 나열하므로, 무언가가 발견된 이유를 이해하고 어떻게 대응할지 결정할 수 있습니다.

:::cards
- [값을 찾는 방식](#값을-찾는-방식): 형태, 검증기, 문맥, 테스트 값, 신뢰도.
- [필드와 열](#필드와-열): 열이나 속성 전체를 판단하는 방식.
- [자유 텍스트 속 이름과 거리 주소](#자유-텍스트-속-이름과-거리-주소): 스캐너 안에서 실행되는 작은 모델과 그 점수.
- [모든 데이터 유형](#기본-제공-데이터-유형): 143가지 전부를 범주별로.

## 값을 찾는 방식

```mermaid title="후보에서 발견 사항까지"
flowchart TB
    shape["형태: 패턴이<br/>후보를 찾음"] --> valid{"검증기를<br/>통과하는가?"}
    valid -->|"아니요"| none["발견 사항 없음"]
    valid -->|"예"| context["문맥: 주변 단어<br/>또는 필드 이름"]
    context --> test{"알려진<br/>테스트 값인가?"}
    test -->|"예"| apart["따로 집계되며<br/>발견 사항이 되지 않음"]
    test -->|"아니요"| finding["신뢰도와 함께<br/>발견 사항이 됨"]
```

로그 줄, CSV 셀, 데이터베이스 행, 객체의 처음 몇 바이트 등 무엇을 스캔하든 모든 스캔은 같은 단계를 거칩니다.

1. **형태.** 각 데이터 유형에는 후보를 찾는 패턴이 있습니다. 열여섯 자리 숫자, `AKIA` 와 열여섯 글자, 단어와 `@` 와 도메인 같은 것입니다. 패턴은 더 긴 토큰 안에서는 절대 일치하지 않으므로, 더 긴 숫자열 안에서는 카드 번호를 찾지 않습니다.
2. **검증기.** 후보는 유형 자체의 규칙을 통과해야 합니다. 체크섬(카드는 Luhn, IBAN은 mod 97, Aadhaar 번호는 Verhoeff, 대부분의 국가 신분증 번호는 검사 숫자), 실제 날짜, 알려진 접두사, 시크릿이라면 충분한 무작위성입니다. 통과하지 못한 후보는 전혀 발견 사항이 되지 않습니다. `000000000` 과 `123456789` 같은 자리 표시 값은 모든 숫자 유형에서 실패합니다.
3. **문맥.** 후보 주변의 단어(기본적으로 앞쪽 최대 64자, 뒤쪽 최대 32자)가 그것이 무엇인지 말해 주면 신뢰도가 한 단계 올라가며, 이름이 그 유형을 가리키는 필드도 마찬가지입니다. 주문 번호나 운송장 번호처럼 다른 것이라고 말해 주는 단어는 신뢰도를 한 단계 낮춥니다. 여권 번호나 은행 계좌처럼 체크섬이 없고 흔한 형태의 번호는 그것을 가리키는 단어 옆에 있을 때만 집계됩니다.
4. **알려진 테스트 값.** 공개된 테스트 카드 번호(예: Stripe의 `4242 4242 4242 4242`), 예시 IBAN, `example.com` 과 기타 예약된 도메인의 주소, 문서용 IP 주소, 정부 문서에 실린 샘플 ID, `sk_test_` 같은 테스트 모드 키, 자리 표시 키는 따로 집계됩니다. 이 값들은 절대 발견 사항이 되지 않으므로, 이런 값으로 가득한 저장소는 유출이 아니라 테스트 환경으로 읽힙니다.
5. **신뢰도.** 남은 것은 발견 사항이 되며, 신뢰도는 증거가 허용하는 만큼입니다.

| 신뢰도 | 의미 |
| --- | --- |
| **높음** | 값이 검증기를 통과했고, 주변의 단어나 값이 들어 있는 필드가 그것이 무엇인지 말해 줍니다. 필드의 경우에는 값 대부분이 그 유형입니다. |
| **보통** | 값이 검증기를 통과했지만 주변에 이를 확인해 주는 것이 없거나, 필드의 이름이 담긴 내용을 말해 주고 일부 값이 이와 일치합니다. |
| **낮음** | 형태는 일치하지만 이를 확인해 주는 것이 없습니다. |

신뢰도가 높음과 보통인 발견 사항만 집계됩니다. 이들은 저장소를 민감하게 만들고 이슈를 열 수 있습니다. 신뢰도가 낮음인 발견 사항은 사람이 판단하도록 저장소에 접힌 채로 나열되며, 맞는 발견 사항에서 **확인** 을 누르면 높음이 되고 이후 스캔에서도 높음으로 유지됩니다.

두 데이터 유형이 같은 문자를 차지하려 하면 더 확실한 발견 사항이 이깁니다. 신뢰도가 더 높은 쪽, 그다음은 자체 규칙이 더 많은 것을 증명하는 탐지기, 그다음은 더 긴 일치입니다.

값은 사람이 쓰는 방식으로도 읽습니다. URL의 퍼센트 이스케이프를 문자의 UTF-8 바이트까지 읽으므로, 쿼리 문자열 안의 IP 주소, 이메일 주소(`jane%40example.com`이나 `jos%C3%A9%40example.com` 등), 토큰이나 키를 찾습니다. URL의 쿼리 문자열은 폼이 공백마다 더하기 기호를 넣어 쓰는 방식으로도 읽으므로, 묶음으로 쓴 번호는 묶음 사이에 퍼센트 인코딩된 공백이나 더하기 기호가 있어도 찾습니다(`4111+1111+1111+1111`이나 `DE44%205001%200517%205407%203249%2031` 등). 우편번호, 도로명 주소, 생년월일도 마찬가지입니다(`SW1A+2AA`, `10+Downing+Street`, `dob=12%2F03%2F1985` 등). 번호의 숫자는 전각 숫자(`４１１１ １１１１ １１１１ １１１１`)나 아랍-인도 숫자처럼 어떤 문자 체계로 쓰였든 읽으며, 먼저 문자 체계마다 따로 읽고 그다음 함께 읽습니다. 카드 번호, 카드 보안 코드나 유효 기간, 전화번호, 미국 사회 보장 번호, IBAN, 라우팅 번호, 은행 계좌 번호, sort code, BSB, BIC, IFSC, 국가 신분증 번호, NHS 번호 같은 건강 식별 번호, 우편번호, 그리고 생년월일이 그 대상입니다. 이메일 주소는 `张伟@example.com`이나 `почта@пример.рф`처럼 어떤 문자 체계로 쓰였든 찾고, 키의 콜론 바로 뒤에 있는 IPv6 주소(`ip:2001:db8::1` 등)도 찾습니다. 각 발견 사항은 쓰인 그대로의 값이므로, 스크럽 규칙이 그 자리에서 숨깁니다.

긴 값은 4 KB씩 겹치는 64 KB 크기의 창 단위로 읽으므로, 값이 어디에 있든 온전히 찾아내며, 값 하나에서 최대 4 MB까지 읽습니다.

## 필드와 열

열, JSON 필드, 로그 속성은 전체로 판단합니다. 이름은 데이터 유형을 암시하고, 샘플링한 값은 데이터 유형을 증명합니다. 그 유형을 담은 값의 비율이 발견 사항의 신뢰도를 정합니다.

| 그 유형을 담은 값 | 신뢰도 |
| --- | --- |
| 60% 이상 | 높음 |
| 25% 이상 | 필드의 이름이 그 유형을 가리키면 높음, 그렇지 않으면 보통 |
| 그보다 적음 | 필드의 이름이 그 유형을 가리키면 보통, 그렇지 않으면 낮음: 다른 것을 담은 열에 이메일이 몇 개 있는 경우 |

값의 평균 길이가 80자를 넘는 필드는 메모, 메시지, 설명 같은 자유 텍스트로 보며, 한 가지 유형만 담을 것으로 기대하지 않습니다. 이런 필드의 발견 사항은 각 일치가 스스로 얻은 신뢰도를 유지하며, 자유 텍스트에서 발견되었다고 표시됩니다. 필드 하나에서 값을 최대 1,000개까지, 각 값은 최대 16 KB까지 분류합니다.

필드의 이름은 단어로 나뉩니다. `customerEmail`, `customer_email`, `customer-email` 은 모두 "customer email"입니다. 유형의 이름 힌트는 그 단어들이 그 순서대로 나란히 나타날 때 일치합니다. "date of birth"는 `customer_date_of_birth` 와 일치하지만 `birth_city` 와는 일치하지 않습니다. 점으로 구분된 경로에서는 마지막 부분만 필드 자체의 이름이며, 마지막 부분이 `number`, `id`, `value` 같은 일반적인 단어라면 그 앞부분도 함께 봅니다. `customer.address.city` 는 도로명 주소가 아니고, `card.number` 는 여전히 카드 번호입니다.

어떤 데이터 유형은 값만으로는 알아볼 수 없습니다. 어떤 패턴도 사람 이름과 거리 이름을, 종교와 다른 단어를 구분하지 못합니다. 이런 유형은 필드에 값이 있을 때 필드의 이름만으로 찾습니다. 사람 이름, 사용자 이름, 성별, 국적, 건강 정보, 인종 또는 민족 출신, 종교적 신념, 성적 지향, 정치적 견해, 노동조합 가입 여부, 생체 인식 데이터, 유전 데이터, 범죄 기록입니다. 이때 이름, 사용자 이름, 성별, 국적은 값의 60% 이상이 그렇게 보이면 높음이고, 그렇지 않으면 보통입니다. 자유 텍스트에서는 사람 이름과 거리 주소를 작은 모델도 찾습니다: [자유 텍스트 속 이름과 거리 주소](#자유-텍스트-속-이름과-거리-주소)를 참고하세요. 사람 이름은 URL의 쿼리 문자열에서도, 그런 필드와 같은 이름이 붙은 매개변수 아래에서 찾습니다. 예를 들어 `full_name` 매개변수는 `/contacts?full_name=Jos%C3%A9%20Garc%C3%ADa`처럼 쓰입니다. 그 값은 URL이 쓰는 방식대로 읽고, 이름처럼 보이면 높음이며, 이스케이프까지 포함해 쓰인 자리에서 찾습니다. 이름이 `name`뿐인 매개변수는 모델에 맡깁니다.

이름이 비밀번호를 담고 있다고 말하는 필드(`password`, `passwordHash`, `pwd` 이며 `password_changed_at` 은 아님)에는 해시가 들어 있어야 합니다. bcrypt, argon2, scrypt, PBKDF2 또는 저장소가 사용할 만한 다른 방식입니다. 빈 값, `********` 같은 자리 표시 값, 암호화된 값은 제외합니다. 나머지 중 해시가 아닌 값이 해시인 값보다 많으면, 그 필드는 어떤 패턴으로도 볼 수 없는 비밀번호 자체를 담고 있는 것이며, 저장소는 [비밀번호가 평문으로 저장되어 있음](/docs/data-security/checks-and-issues#데이터-위생) 검사에 실패합니다.

### 어떤 탐지기도 분류하지 못한 필드

이름이 어떤 데이터 유형도 가리키지 않고 값이 어떤 탐지기와도 맞지 않는 열이나 필드는 안전하다고 알려진 것이 아닙니다. 회사 고유의 고객 번호일 수도 있고, 다른 언어로 이름 붙인 열일 수도 있습니다. 프로젝트의 **AI 활성화** 가 켜져 있으면, 콘텐츠 스캔은 이런 필드를 스캔당 최대 200개 보관하고, 각 필드가 프로젝트의 어떤 데이터 유형을 담고 있는지 OneUptime AI에 묻습니다. 한 저장소에 대해 한 번에 묻는 필드는 최대 40개입니다. AI에는 필드 이름, 옆 필드들의 이름, 값의 모양만 전달합니다. 모든 글자는 `a` 또는 `A` 로, 모든 숫자는 `9` 로 쓰므로 `AB-1234` 는 `AA-9999` 가 되며, 값 자체는 절대 전달하지 않습니다. 자유 텍스트, 값이 5개 미만인 필드, 작은 정수, ID·시간·상태로 이름 붙은 필드는 묻지 않습니다.

텔레메트리 스캔도 어떤 탐지기도 분류하지 못한 속성을 같은 방식으로 보관합니다. 서비스의 로그, 스팬, 메트릭과 나머지 텔레메트리에서 스캔마다 서비스당 최대 50개입니다. OneUptime 자체의 속성, OpenTelemetry 규약이 레코드의 출처를 알리려고 모든 레코드에 쓰는 속성(서비스, 호스트, 파드 등), 로그 본문 같은 자유 텍스트는 절대 보관하지 않습니다.

OneUptime AI가 지목한 각 유형은 신뢰도가 낮음인 발견 사항이 되며, 이유와 함께 **OneUptime AI의 제안** 으로 표시됩니다. 이유는 프로젝트의 언어로 작성되며, 발견 사항의 행 전체에 걸쳐 표시됩니다. 다른 낮음 발견 사항처럼 사람이 저장소의 **내용** 페이지에서 **확인** 을 고르기 전까지는 아무것도 집계되지 않으며, **민감하지 않음으로 표시** 를 고르면 거절됩니다. 답을 받은 필드는 30일 동안 다시 묻지 않고, 사람이 판단한 필드는 다시는 묻지 않습니다.

## 자유 텍스트 속 이름과 거리 주소

어떤 패턴도 사람의 이름을 다른 단어와 구별하지 못합니다. 그래서 자유 텍스트(지원 메모, 로그 한 줄, 예외 메시지, 프롬프트)는 사람 이름과 거리 주소를 찾는 작은 언어 모델도 읽습니다. 모델은 스캐너 안에서, OneUptime의 워커와 여러분의 프로브에서 실행됩니다: 텍스트는 스캐너 밖으로 나가지 않고, 실행 중에는 아무것도 내려받지 않으며, 프롬프트도 만들지 않습니다. 이것은 OneUptime AI가 아니며, OneUptime AI의 스위치로 켜거나 끄지 않습니다: 그것은 **이름과 거리 주소 찾기** 가 합니다.

- **읽는 것.** 값의 평균 길이가 80자를 넘는 필드, 값이 아무리 짧아도 사람이 자유 텍스트를 적는다고 이름이 말해 주는 필드(예: `delivery_note`, `comentario`, `Lieferhinweis`, `opmerking`, [짧은 값](#짧은-값) 참고), 그리고 텔레메트리에서는 아무리 짧아도 모든 로그 본문, 예외 메시지, 스택 트레이스, AI 대화입니다. 한 필드에서 서로 다른 값을 최대 100개, 모두 합쳐 32 KB의 텍스트까지 읽고, 값 하나는 최대 16 KB까지 읽습니다. 읽는 것 안의 URL은 URL로 읽습니다: 퍼센트 이스케이프를 읽고 두 글자 사이의 `+`는 공백으로 읽으므로, `/profile?name=Jos%C3%A9%20Garc%C3%ADa` 안의 이름을 찾고 쓰인 그대로 숨깁니다.
- **찾는 것.** **사람 이름** (`person-name`)과 **거리 주소** (`postal-address`)입니다. 거리 주소는 모델이 번지와 함께 읽는 장소로, 예를 들어 `14 Calle Mayor`와 그 뒤에 오는 우편번호와 도시를 포함합니다. 도시나 국가만으로는 거리 주소가 아닙니다.
- **얼마나 확실한가.** 모델이 찾은 이름이나 주소는 그 자체로 보통입니다. 필드 이름이 그 필드에 이름이나 주소가 있다고 말하거나, "customer", "Kunde", "dirección" 같은 가까운 단어가 그렇게 말하면 높음입니다. 모델이 확신하지 못하면, 즉 점수가 0.6 미만이면 낮음입니다. 각각 스스로 얻은 신뢰도를 유지하므로, 로그 1,000줄 사이의 이름 하나도 보통으로 남습니다.
- **테스트 값.** `Jane Doe`, `John Smith`, `Max Mustermann`, `123 Main Street` 같은 자리표시자는 모든 유형의 테스트 값처럼 따로 셉니다.
- **보관하는 것.** 샘플은 필드 이름으로 찾은 이름처럼 마스킹됩니다: 첫 글자와 별 네 개, `M****`입니다. 지문은 만들지 않습니다. 저장소의 **내용** 페이지에서 이런 발견 사항에는 **스캐너의 모델이 자유 텍스트에서 찾음** 이라고 표시됩니다.
- **레코드와 규칙.** 모델이 만든 발견 사항은 그것이 발견된 레코드를 나열하며, 각 줄은 이름이나 주소를 중심으로 잘리고 그 안의 모든 이름과 주소는 마스킹됩니다. 그리고 다른 발견 사항과 마찬가지로 **정리** 가 그 레코드로 규칙을 증명합니다. 레코드는 매번 모델 시간을 최대 20초까지 써서 모델로 다시 읽습니다. 모델이 시간이 없어 읽지 못한 레코드는 나열되지 않으며, 목록은 시간이 없어 읽지 못한 값이 몇 개인지 알려 줍니다. 모델을 실행할 수 없는 곳에서는 목록이 그렇다고 알려 주고, 그 발견 사항의 규칙은 증명되지 않습니다.

| 모델 | 라이선스 | 크기 | 리비전 | 측정한 언어 |
| --- | --- | --- | --- | --- |
| [openmasq/ner-multilingual](https://huggingface.co/openmasq/ner-multilingual): 다국어 BERT 6개 층, int8 ONNX | Apache 2.0 | 98 MB | `8cf7273` | 영어, 스페인어, 독일어, 프랑스어, 이탈리아어, 포르투갈어, 네덜란드어 |

### 얼마나 잘 찾는가

스캐너 자체의 코드로, 이를 위해 작성한 테스트 세트에서 측정했습니다: 7개 언어로 지어낸 문장 392개(로그 줄, 지원 메모, 이메일, 프롬프트)이며, 그중 168개에는 이름도 주소도 없습니다. 발견 사항이 같은 유형의 이름이나 주소와 겹치면 정답입니다. 기준은 어떤 모델도 측정하기 전에 작성했습니다: 모든 언어에서 유형별 정밀도 0.90 이상, 언어별 0.85 이상, 재현율 0.70 이상, 둘 다 없는 값 1,000개당 잘못된 발견 사항 20개 이하입니다. 측정한 모델 4개 중 2개가 기준을 넘었고, 그중 더 작은 모델을 골랐습니다. 이 점수는 테스트가 지킵니다: 모델이나 스캐너를 바꿔 점수 하나라도 떨어지면 테스트가 실패합니다.

### 짧은 값

짧은 필드는 사람이 자유 텍스트를 적는다고 이름이 말해 줄 때만 읽습니다. 이 규칙은 고르기 전에 7개 언어로 된 데이터베이스의 49개 열, 모두 588개의 값으로 측정했습니다. 상품 이름, 제목, 라벨, 직함, 매장 이름(여기서 브랜드, 등장인물, 거리의 이름은 발견 사항이 아닙니다)과, 이름 91개와 거리 주소 28개가 담긴 짧은 배송 메모, 지원 댓글, 고객 비고입니다. 처음 검토한 규칙인 네 단어 이상의 모든 필드를 읽는 규칙은 카탈로그 값 108개를 읽고 그중 53개를 잘못된 이름으로 만들었습니다. 예를 들어 폴로 셔츠 이름의 `Ralph Lauren`과 책 제목의 `Tom Sawyer`입니다:

### 어디서 실행되고, 비용은 얼마인가

- **모든 이미지에.** 워커를 실행하는 App 이미지와 프로브 이미지에는 모델, 그 어휘, 런타임이 들어 있으며, 에어갭 이미지와 Iron Bank 이미지도 마찬가지입니다: 디스크에서 약 114 MB입니다. 이 파일들은 이미지를 빌드할 때 고정된 리비전에서 가져와 각각의 SHA-256으로 확인합니다. 스캔이 실행되는 동안에는 아무것도 내려받지 않습니다.
- **메모리.** 스캔에 처음 필요할 때 프로세스마다 한 번 불러옵니다: 약 550 MB이며, 스캔 없이 10분이 지나면 반환합니다.
- **시간.** 코어 1개에서 로그 한 줄 길이의 값 1,000개당 30초에서 1분, 1,200자 값 1,000개당 약 9분입니다. 저장소의 콘텐츠 스캔은 최대 2분을 줍니다. 매시간 텔레메트리 스캔은 모두 합쳐 최대 1분, 저장소마다 6초를 주며, 매시간 다른 저장소 묶음에 줍니다.
- **차례.** 각 콘텐츠 스캔의 모델은 지난 스캔의 모델이 멈춘 곳에서 시작합니다. 자유 텍스트를 읽지 않은 첫 테이블이나 컨테이너에서 시작하고, 시간이 없어 읽지 못한 버킷의 객체는 다른 어떤 것보다 먼저 다시 읽습니다. 시작했지만 끝내지 못한 것은 다시 첫 번째가 되지 않으므로, 어느 것도 스캔마다 모델의 시간을 붙잡고 있지 않고, 데이터 저장소에 자유 텍스트가 아무리 많아도 모든 테이블과 객체에 차례가 돌아옵니다.
- **시간이 다 되면** 스캔은 모델이 읽은 만큼으로 끝나고, 경고는 자유 텍스트 값을 몇 개 읽었는지만 알려 줄 뿐 무엇을 읽었는지는 절대 알려 주지 않습니다. 모델이 없는 워커나 프로브는 전처럼 스캔하고 그 이유를 알려 줍니다:

```text
Names and street addresses were looked for in 120 of 500 free-text values: this store's 6 seconds of model time ran out.
Names and street addresses in free text were not looked for: the model's model_quantized.onnx is not installed on this probe.
```

스캔 세부 정보는 이 경고와 콘텐츠 또는 텔레메트리 스캔의 다른 모든 경고를 읽는 사람의 언어로 보여 줍니다.

**이름과 거리 주소 찾기** 는 모든 프로젝트에서 켜져 있습니다: 버킷, 데이터베이스, BigQuery 데이터 세트의 콘텐츠 스캔은 워커와 프로브에서 모델로 자유 텍스트를 읽습니다. 그 아래의 **텔레메트리에서 이름과 거리 주소 찾기** 는 꺼져 있습니다: 서비스 200개가 있는 바쁜 프로젝트의 모든 로그 본문, 예외, 대화를 한 번 읽는 데 코어 1개로 약 48분이 걸리고, 스캔의 시간당 1분으로는 그중 약 4%를 읽습니다. 매시간 스캔이 그중 일부를 읽게 하려면 켜세요. 둘 다 **데이터 보안 → 설정 → 스캔 설정** 의 **데이터 보안이 읽는 항목** 아래에 있습니다. **테스트** 는 모델 없이 브라우저에서 실행되므로, 모델이 찾을 것은 거기에 표시되지 않습니다. 모델을 더하면 다운로드가 약 113 MB(압축 시 67 MB), 탭의 메모리가 약 440 MB 늘어나므로, 모델은 스캐너 안에서만 실행됩니다.

## 민감도

| 민감도 | 의미 |
| --- | --- |
| **제한** | 유출되면 피해가 따릅니다. 시크릿, 카드 번호, 건강 기록, 정부 발급 ID. |
| **기밀** | 개인 데이터, 그리고 기밀로 표시된 문서. |
| **내부** | 외부인을 위한 것이 아닌 비즈니스 자체의 데이터. |
| **공개** | 민감한 것이 발견되지 않았습니다. |

저장소의 민감도는 그 안에서 보통 이상의 신뢰도로 발견된 가장 민감한 데이터 유형의 민감도와 같습니다. 테스트 값과 민감하지 않음으로 표시된 발견 사항은 전혀 집계되지 않으며, 아무것도 발견되지 않은 저장소는 공개입니다. 저장소를 발견 사항이 말하는 것보다 더 민감하게 또는 덜 민감하게 다루려면 저장소의 **설정** 에서 민감도를 직접 설정하세요. 그러면 검사는 그 값을 사용합니다.

개인 데이터는 GDPR, CCPA, LGPD, DPDP가 정의하는 의미의, 사람에 관한 데이터입니다. 시크릿과 비즈니스 문서만 담은 저장소는 개인정보 보호 프레임워크의 범위 밖에 있지만, 보안 프레임워크의 범위 밖에 있는 일은 절대 없습니다([데이터 보안 규정 준수](/docs/data-security/compliance) 참고).

## 기본 제공 데이터 유형

한 국가에 속하는 데이터 유형은 그 국가를 ISO 3166-1 코드로 나타냅니다. 데이터 상주 규칙과 특정 국가에 묶인 프레임워크가 이 값을 읽습니다([데이터 상주](/docs/data-security/flows-access-residency#데이터-상주-규칙) 참고). ID는 API와 발견 사항이 그 유형을 부르는 이름입니다.

## 직접 만드는 데이터 유형

회사에만 있는 것을 위한 데이터 유형을 추가하세요. 직원 ID, 보험 증권 번호, 프로젝트 코드 같은 것입니다. **데이터 보안 → 설정 → 데이터 유형** 으로 이동해 **내 데이터 유형** 아래에 추가합니다. 다음 스캔부터 기본 제공 데이터 유형과 똑같이 버킷, 데이터베이스, 텔레메트리에서 스캔됩니다.

:::steps
### 무엇인지 정하기

**이름**(예: 직원 ID), **카테고리**, **민감도** 를 지정합니다. 민감도는 이 유형을 담은 저장소가 얼마나 민감한지입니다. **설명** 은 이 유형의 발견 사항을 읽는 사람에게 이것이 무엇인지 알려 줍니다.

### 찾는 방법 정하기

**패턴** 을 입력합니다. `EMP-\d{6}` 처럼 값 하나에 대한 JavaScript 정규식입니다. 이 유형을 담는 **필드 이름**(예: `employee id`)과, 값 근처에 있으면 이 유형임을 확인해 주는 **키워드** 를 추가합니다. 필드 이름만으로 유형을 찾으려면 패턴을 비워 두세요.

### 테스트하기

데이터 유형이 무엇을 찾는지 보려면 **테스트** 에 샘플 텍스트를 붙여 넣으세요. 브라우저에서 스캐너 자체의 코드로 텍스트를 검사하므로 텍스트는 OneUptime으로 절대 전송되지 않으며, 처음 64 KB만 테스트합니다.
:::

**추가 필드** 에서 **대소문자 무시** 는 글자의 대소문자와 관계없이 패턴을 일치시키고, **키워드 필요** 는 값 근처에 키워드가 있거나 필드의 이름이 이 유형이라고 말할 때만 값을 집계하며, **체크섬** 은 값이 검사를 통과하도록 요구합니다. **없음**, **Luhn**(카드 번호에 붙는 검사 숫자), **Mod97**(IBAN의 검사 숫자), **Verhoeff**(Aadhaar 번호의 검사 숫자) 중에서 고릅니다.

패턴은 저장할 때 검사합니다. 컴파일되어야 하고, 빈 텍스트와 일치하지 않아야 하며, 텍스트 길이에 비례하는 시간 안에 실행되어야 합니다. 패턴은 절대 역추적하지 않는 매처로 실행되므로, 어떻게 작성하든 스캔을 붙잡아 둘 수 없습니다. 유형 하나에는 키워드를 최대 50개, 필드 이름을 최대 50개까지 둘 수 있습니다.

직접 만든 유형의 값은 체크섬을 통과하면 그 자체로는 보통, 근처에 키워드가 있으면 높음이고, 체크섬이 없으면 그 자체로는 낮음, 키워드가 있으면 보통입니다. 열에서는 모든 유형과 마찬가지로 일치하는 값의 비율이 결정합니다.

### 설명하기

새 데이터 유형 양식의 맨 위에서 **설명하기** 가 양식을 대신 채워 줍니다. "우리 직원 ID는 EMP-123456처럼 생겼고, 대시가 없을 때도 있습니다"처럼 데이터가 어떻게 생겼는지 적고, 원하면 예시를 한 줄에 하나씩 추가한 뒤 **양식 채우기** 를 선택하세요. OneUptime AI에는 문장과 예시의 형태만 전송되고 예시 자체는 절대 전송되지 않습니다. 예시는 브라우저에 남으며, **테스트** 가 패턴이 그중 몇 개를 찾는지 보여 줍니다. 채워진 내용을 읽고 원하는 대로 바꾼 뒤 저장하세요. 저장하기 전에는 아무것도 저장되지 않으며, 패턴은 직접 작성한 것과 똑같이 검사됩니다. 설명하기를 쓰려면 프로젝트의 **AI 활성화** 가 켜져 있어야 합니다.

## OneUptime AI가 찾는 데이터 유형

어떤 탐지기도 분류하지 못한 필드에는 같은 뜻의 이름으로 여러 곳에 보관된 회사 고유의 데이터 유형이 들어 있는 경우가 많습니다. 예를 들어 보험사의 보험 증권 번호가 모든 데이터베이스에서 `policy_no`, `policyNumber`, `police_nr` 라는 열에 들어 있는 경우입니다. 프로젝트의 **AI 활성화** 가 켜져 있으면 OneUptime AI가 스캔이 보관한 필드에서 이런 데이터 유형을 찾고, 자체 스캔으로 입증된 뒤에야 묻습니다.

:::steps
### 필드 그룹을 찾습니다

두 개 이상의 저장소에 있는 세 개 이상의 필드는 값 대부분이 하나의 형태를 가지고(부분 사이의 구분자는 있어도 없어도 됩니다) 이름이 담긴 내용을 말해 주는 단어를 공유하면 하나의 그룹이 됩니다. 숫자가 없는 형태, 날짜, 시간, 소수는 절대 그룹이 되지 않으며, `id`, `no`, `number` 같은 단어는 그것만으로는 아무것도 말해 주지 않습니다.

### 데이터 유형 초안을 작성합니다

OneUptime AI는 새 그룹마다 데이터 유형 초안을 작성합니다. 한 번에 최대 3개이며, 필드 이름과 값의 형태로 작성하고 값 자체는 쓰지 않습니다. 초안은 저장된 유형과 같은 검사를 통과하고 초안의 바탕이 된 형태를 찾아야 합니다. 그렇지 않은 초안은 이유와 함께 한 번 더 요청됩니다.

### 다음 스캔이 입증합니다

초안은 그룹의 각 저장소의 다음 스캔에서 최대 48시간 또는 스캔 간격 한 번 중 더 긴 기간 동안 실행됩니다. 결과는 만들지 않습니다. 각 스캔은 그룹의 필드와 같은 저장소의 다른 모든 필드에서 초안이 찾을 값의 수를 셉니다. 자기 필드 값의 80% 이상을 찾고 다른 값은 1% 이하만 찾을 때 제안됩니다. 다른 곳에서 거의 모든 값을 찾는 필드는 같은 데이터를 다른 이름으로 담고 있는 것으로 표시되며, 불리하게 세지 않습니다.
:::

각 초안은 동시에 좁힌 형태로도 셉니다. 좁힌 초안은 그룹의 필드 밖에서는 키워드 중 하나가 옆에 있거나 그것을 가리키는 필드 이름 아래에 있는 값만 찾습니다. 다른 곳에서 너무 많이 찾는 초안은 그것으로 충분하면 좁힌 형태로 제안됩니다. 어느 형태로도 충분하지 않은 초안은 버려지며, 그 그룹은 30일 동안 다시 초안이 작성되지 않습니다.

제안된 각 데이터 유형은 **데이터 보안 → 설정 → 데이터 유형** 맨 위와 **데이터 보안 → AI** 의 **검토할 데이터 유형** 에서 스캔이 센 결과와 함께 기다립니다. 예를 들면 "이 필드 11개의 값 중 98%, 같은 저장소의 다른 곳에 있는 값 중 0.1%와 일치합니다."입니다. **데이터 유형 추가** 는 그 내용으로 채워진 데이터 유형 양식을 열어 바꾸고 테스트할 수 있게 합니다. 저장하면 유형이 추가되고, 스캔은 다음 실행부터 그것을 찾습니다. **데이터 유형 아님** 은 거절하며, 그 필드에 대해서는 다시 제안되지 않습니다. 추가하려면 데이터 유형을 만들 수 있는 역할이 필요합니다.

## 민감하지 않음과 항상 민감하지 않음

스캔은 보이는 것과 다른 무언가를 찾을 수 있습니다. Luhn 검사를 통과하는 주문 번호 열이나, 모든 로그 줄에 있는 회사의 지원 주소 같은 것입니다. OneUptime에 그렇다고 알려 주면 집계를 멈춥니다.

- **발견 사항을 민감하지 않음으로 표시합니다.** 저장소의 **내용** 페이지에서 발견 사항의 **민감하지 않음으로 표시** 를 선택하고 이유를 적습니다. 그 발견 사항은 더 이상 저장소의 민감도나 검사에 반영되지 않으며, 저장소는 즉시 다시 검사됩니다. 발견 사항은 표시와 이유와 함께 저장소에 남으므로, 다음 사람이 무엇이 결정되었는지 볼 수 있습니다.
- **값을 항상 민감하지 않음에 추가합니다.** 데이터 보안의 설정에서 하며, `support@yourcompany.com` 처럼 어디에서도 발견 사항이 되지 않는 값에 사용합니다. 값은 스캐너가 정규화한 뒤 대소문자를 무시하고 비교합니다.
- **기본 제공 데이터 유형을 끕니다.** **데이터 보안 → 설정 → 데이터 유형** 의 **기본 제공 데이터 유형** 아래에서 모든 데이터 유형에 스위치가 있으며, 스위치를 바꾸는 즉시 저장됩니다. 프로젝트의 어떤 스캔도 꺼진 유형은 찾지 않습니다.

## OneUptime AI의 판정

프로젝트의 **AI 활성화** 가 켜져 있고 **데이터 보안 → AI** 에서 **새 이슈 처리** 도 켜져 있으면, OneUptime AI는 저장소를 스캔할 때마다 사람의 결정을 기다리는 모든 발견 사항에 판정을 내립니다. 발견 사항이 결정을 기다리는 것은 스캔이 그 발견 사항을 확신하지 못했을 때(신뢰도가 낮음인 발견 사항 또는 OneUptime AI의 제안), 또는 신뢰도가 보통이나 높음인 발견 사항에 잘못된 일치의 징후가 있을 때입니다:

- 일치한 값의 대부분이 알려진 테스트 값입니다
- 필드의 이름이 이 데이터 유형이 아니라 다른 데이터 유형을 가리킵니다
- `order_number`, `invoice_no`, `ref_id` 같은 ID 필드가 Luhn 알고리즘으로 검사하는 유형을 담고 있지만, 필드 이름은 그 유형을 가리키지 않습니다. 아무 숫자열이나 열 개 중 하나는 Luhn 검사를 통과합니다

판정은 **확인 권장**, **민감하지 않음**, **판단 불가** 중 하나이며, 프로젝트의 언어로 쓴 이유가 함께 붙습니다. 판정은 저장소의 **내용** 페이지와 **텔레메트리 내** 에서 발견 사항의 행 전체에 걸쳐 표시되며, "팀이 저장소 4개에서 `order_number` 필드를 민감하지 않음으로 표시했습니다"처럼 판정의 근거가 된 팀의 결정도 함께 표시됩니다. **결정 보기** 는 각 결정을 나열합니다. 그 저장소, 그 필드, 팀이 제시한 이유입니다.

### 선례가 되는 팀의 결정

OneUptime AI에는 같은 데이터 유형의 발견 사항에 대한 팀의 이전 결정이 최대 열 개까지 전달됩니다. 먼저 어느 저장소에 있든 같은 이름의 필드에 대한 결정이 옵니다. `order_number`, `orderNumber`, `public.orders.order_number` 는 모두 "order number"입니다. 그중에서는 같은 위치가 먼저 오고, 그다음은 가장 최근의 결정 순입니다. 그다음에는 이름이나 그 필드에 대해 제시된 이유가 같은 것을 말하는 필드가 옵니다. 예를 들어 이유가 "Shopify 주문 번호"인 `order_ref` 입니다. 각 발견 사항이 있던 위치, 결정 내용, 제시된 이유가 전달되며, 이유에 포함된 값은 빠집니다. 값, 마스킹된 샘플, 레코드는 절대 전달되지 않습니다.

로그 본문이나 메시지 같은 자유 텍스트에 있는 발견 사항에는 맞춰 볼 필드 이름이 없습니다. 그 선례는 다른 저장소의 같은 위치, 예를 들어 다른 서비스의 로그 본문입니다.

### OneUptime AI가 스스로 결정하는 것

- **발견 사항을 민감하지 않음으로 표시하는 일은 절대 없습니다.** 어떤 규칙에서도 마찬가지입니다. 표시는 사람이 자신의 이유와 함께 합니다. 판정이 **민감하지 않음** 이면 **민감하지 않음으로 표시** 는 OneUptime AI가 작성한 이유 초안으로 시작하며, 이 이유는 바꿀 수 있습니다.
- **AI 규칙이 정한 경우에만 발견 사항을 스스로 확인합니다.** 그 저장소와 데이터 유형에 대해 **판정** 이 **자동** 인 데이터 보안 AI 규칙이 있어야 합니다. 또한 팀이 비슷한 발견 사항을 직접 확인했거나, 필드 이름이 그 유형을 가리켜야 합니다. 이 확인은 저장소의 **타임라인** 과 **데이터 보안 → AI** 의 **AI가 처리함** 에 기록되며, **실행 취소** 로 되돌릴 수 있습니다.

그렇지 않으면 판정은 발견 사항의 행에서 기다립니다. 프로젝트에 AI 규칙이 있으면, 발견 사항은 그 저장소와 데이터 유형에 대한 규칙에서 **판정** 이 켜져 있을 때만 판정을 받습니다. 일부 검사나 심각도로 제한된 규칙은 이슈에 관한 것이므로 발견 사항을 판정하지 않습니다. OneUptime AI는 스캔 후 저장소 하나당 최대 40개의 발견 사항을 판정하며, 한 번도 판정하지 않은 것을 먼저 판정하고 나머지는 다음 스캔 후에 판정합니다. 이후의 스캔에서는 비슷한 발견 사항에 대한 새 결정처럼 판정의 근거가 바뀐 경우에만 그 발견 사항에 대해 다시 묻습니다.

## 비슷한 발견 사항

발견 사항을 확인하거나 민감하지 않음으로 표시하면, **비슷한 발견 사항에 적용** 에 아직 아무도 결정하지 않은 비슷한 발견 사항이 나열됩니다. 같은 이름의 필드에 있는 같은 데이터 유형으로, 이 저장소와 사용자가 읽을 수 있는 다른 모든 저장소에 있는 발견 사항입니다. 처음에는 모두 선택되어 있습니다. 따로 판단하려는 항목의 선택을 해제하면, 나머지에는 같은 결정이 사용자의 이유와 함께 사용자 본인의 변경으로 적용됩니다. 변경할 권한이 없는 발견 사항은 그대로 남습니다. **나중에** 를 누르면 모두 그대로 둡니다. 자유 텍스트에 있는 발견 사항에는 비슷한 발견 사항이 없습니다. 한 텍스트에 담긴 내용은 다른 텍스트에 대해 아무것도 말해 주지 않기 때문입니다.

## 팀의 결정이 스캔에 대해 말해 주는 것

팀이 발견 사항을 민감하지 않음으로 표시하면, OneUptime AI는 **데이터 보안 → AI** 의 **귀하를 기다리는 중** 에서 스캔 변경을 제안합니다:

- **기본 제공 데이터 유형 끄기**: 그 유형의 발견 사항이 모두 민감하지 않음으로 표시되었을 때입니다. 최소 저장소 2개에서 발견 사항이 최소 3개 있어야 합니다. OneUptime AI가 제안하기만 한 발견 사항은 세지 않습니다.
- **저장소의 스캔에서 위치 제외하기**: 그 위치의 발견 사항이 모두 민감하지 않음으로 표시되었을 때이며, 최소 2개가 있어야 합니다. 스캔이 개별적으로 제외할 수 있는 데이터베이스 열이나 텔레메트리 속성에 대해 제안됩니다.

각 제안은 항상 사람의 승인을 기다립니다. 찾기를 멈춘 스캔은 나중에 들어오는 실제 데이터를 놓치기 때문입니다. **항상 민감하지 않음** 은 절대 제안되지 않습니다. 값을 담고 있는데, OneUptime AI는 값을 절대 보지 않기 때문입니다.
