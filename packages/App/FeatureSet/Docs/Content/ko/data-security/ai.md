# 데이터 보안의 OneUptime AI

OneUptime AI는 데이터를 보지 않고 데이터 보안이 찾은 것을 다룹니다. OneUptime AI에 보내는 것은 이름, 형태, 개수, 구성뿐이며, 데이터의 값, 마스킹된 샘플, 레코드, 연결 문자열은 절대 보내지 않습니다. 모든 기능은 프로젝트 자체 모델(자체 호스팅 모델 포함)에서 실행되며, 데이터 보안의 모든 페이지, 검사, 스캔, 통합은 AI를 꺼도 작동합니다.

:::cards
- [스스로 처리](#스스로-처리): 새 이슈마다 하는 일, 사용자를 기다리는 것, 그리고 AI 규칙.
- [OneUptime AI가 보는 정보](#oneuptime-ai가-보는-정보): 각 기능이 보내는 내용과 절대 보내지 않는 내용.
- [직접 확인하기](#직접-확인하기): 이슈 하나가 보낼 정확한 입력.
- [자체 모델](#자체-모델): 모든 기능을 프로젝트의 공급자, Ollama, vLLM 또는 OpenAI 호환 엔드포인트에서 실행.
- [측정 방법](#측정-방법): 모든 기능을 릴리스마다 고정된 사례로 측정.
:::

## 스스로 처리

**데이터 보안 → AI** 에서 **새 이슈 처리** 를 켜면(새 프로젝트에서는 켜져 있음) OneUptime AI가 심각도가 심각 또는 높음인 새 이슈를 하나하나 스스로 처리합니다. **AI로 설명** 과 같은 방식으로, 그 동작이 보내는 내용을 바탕으로 이슈의 분석을 작성해 이슈의 **타임라인** 에 올립니다. 텔레메트리 이슈의 경우 새 텔레메트리에서 그 데이터를 숨기는 정리 규칙을 제안합니다. 제안은 그 페이지의 **귀하를 기다리는 중** 에서 위험이 큰 순서로, 무엇이 바뀌는지, 이유, 검증 방법, 실행 취소 방법과 함께 대기합니다. **승인** 은 사용자 본인의 권한으로 변경을 적용합니다. 정리 규칙에는 로그 정리 규칙, 트레이스 정리 규칙 또는 메트릭 파이프라인 규칙을 만들 수 있는 권한이 필요합니다. **제안 무시** 는 사유와 함께 제안을 거절하며, 사유는 이슈의 타임라인에 기록됩니다. 변경이 효과가 있었는지는 이슈 자체의 검사가 판단합니다. 저장소를 다시 검사하고, 그 데이터가 하나도 남지 않으면 이슈가 해결됩니다.

OneUptime AI는 소유자가 없는 저장소에 대해, 이미 소유자를 가리키는 정보에서 소유자도 제안합니다. 저장소의 클라우드 태그, 저장소를 사용하는 서비스와 그 소유자, 저장소를 선언한 파일의 코드 소유자, 클라우드 변경 로그에 따르면 저장소를 변경한 사람, 그리고 저장소를 OneUptime에 추가한 사람입니다. 프로젝트 자체의 팀과 사람만 제안하며, 얼마나 확실한지와 증거가 서로 다른 부분도 알려 줍니다. 민감한 저장소에 대한 제안은 해당 **이 민감한 저장소의 소유자가 없음** 이슈와 함께 오고, 다른 새 저장소에 대한 제안은 하루에 한 번, 그리고 클라우드 연결을 처음 읽을 때 옵니다. 저장소 3개 이상의 소유자가 같은 태그나 같은 이름 시작 부분에 근거하면, 다음 비슷한 저장소에도 소유자가 유지되도록 하는 소유자 규칙도 제안하고, 그 규칙이 일치할 저장소 수를 알려 줍니다. 이 제안들은 이 페이지와 **데이터 저장소** 의 **검토할 소유자** 에서 기다립니다. **승인** 은 사용자 본인의 권한으로 소유자를 추가하며, 추가된 소유자는 다른 소유자와 마찬가지로 알림을 받습니다. **변경 후 승인** 은 먼저 다른 소유자를 고릅니다. **실행 취소** 는 추가한 소유자만 정확히, 규칙과 함께 되돌립니다. 소유자 추가는 알림 대상을 바꾸므로, AI 규칙이 어떻게 설정되어 있든 항상 사용자의 확인을 기다립니다.

기본적으로 OneUptime AI는 데이터를 숨기기만 하고, 되돌릴 수 있으며, 안전이 검증된 변경을 제외한 모든 변경 전에 확인을 요청하며, 확인 없이 데이터를 삭제하거나 누군가를 호출하는 일은 절대 없습니다. 확인 없이 적용한 변경은 **AI가 처리함** 에 **실행 취소** 와 함께 나열됩니다. **AI가 조치하지 않은 이유** 에는 살펴보았지만 그대로 둔 이슈와 그 이유가 나열됩니다. 모든 제안, 승인, 무시, 실행 취소는 이슈와 저장소의 **타임라인** 에 기록됩니다. 스위치가 꺼져 있거나 프로젝트에서 AI가 꺼져 있어도 데이터 보안은 평소처럼 작동하며, **AI로 설명** 과 **AI로 수정** 은 누르면 여전히 작동합니다.

이슈 페이지에서는 **수정 방법** 위의 **OneUptime AI** 카드가 그 이슈의 분석과 제안 내용을 같은 버튼과 함께 보여 줍니다. 데이터 보안 **개요**는 이번 주에 OneUptime AI가 봉쇄한 유출 수와 사용자를 기다리는 제안 수를 알려 줍니다. 변경의 결과는 **AI 성과**에서 주 단위로 집계됩니다. [OneUptime AI가 얼마나 잘하고 있는지](/docs/ai/ai-sre#oneuptime-ai가-얼마나-잘하고-있는지)를 참조하세요.

### AI 규칙

**데이터 보안 → AI**의 **AI 규칙**에서 규칙은 OneUptime AI가 처리할 이슈(검사 또는 검사 그룹, 심각도, 저장소의 민감도, 종류, 공급자, 환경, 레이블, 데이터 범주, 서비스 기준)와 작업 종류 **분석**, **봉쇄**, **수정**, **판정**마다 **꺼짐**, **제안**(제안하고 사용자를 기다림), **묻지 않고** 중 무엇인지를 정합니다. 여러 규칙이 한 이슈에 일치하면 그중 하나라도 켠 작업은 실행되며, **제안**이 **묻지 않고**보다 우선합니다. 각 제안에는 이를 결정한 규칙이 표시됩니다. 규칙이 없으면 프로젝트 기본값이 적용됩니다. 심각 및 높음 이슈를 분석하고 나머지는 모두 제안합니다.

AI 규칙은 인시던트와 경고의 AI 규칙처럼 프로젝트 전체의 것입니다. 프로젝트 소유자와 관리자, 그리고 AI 규칙 권한을 받은 사람이 변경합니다. 보안 역할은 OneUptime AI가 제안하고 수행한 것은 보지만 규칙은 보지 못합니다.

## OneUptime AI가 보는 정보

어떤 기능도 모델에 다음을 보내지 않습니다:

- 데이터의 값
- `j***@e******.com` 같은 마스킹된 샘플: 마스킹된 이메일에도 도메인이 남고, 마스킹된 카드에도 마지막 네 자리가 남습니다
- 텔레메트리의 레코드: 로그 줄, 스팬 또는 세션
- 연결 문자열, 키 또는 기타 시크릿

데이터 보안은 스캔 안에서 데이터를 직접 읽고 아무것도 보관하지 않습니다. OneUptime AI에 보내는 내용은 보내도 되는 항목의 목록에서 한곳에서만 만들어지며, 어떤 기능이든 다른 것을 모델에 보내면 테스트가 실패합니다.

| 기능 | 전송 내용 | 자동 실행 |
| --- | --- | --- |
| **AI로 설명** | 이슈의 제목, 심각도, 증거, 해당 검사가 중요한 이유, 저장소 클라우드에 맞는 수정 방법. 저장소의 이름, 종류, 지역, 클라우드 ID, 민감도, 데이터 유형 이름. 텔레메트리 이슈의 경우 각 데이터 종류가 발견된 위치, 즉 해당 데이터가 있는 속성, 로그 본문 또는 프롬프트 | 아니요: 사용자가 이슈 페이지에서 요청합니다 |
| **새 이슈 분석** | 이슈의 제목, 심각도, 증거, 해당 검사가 중요한 이유, 저장소 클라우드에 맞는 수정 방법. 저장소의 이름, 종류, 지역, 클라우드 ID, 민감도, 데이터 유형 이름. 텔레메트리 이슈의 경우 각 데이터 종류가 발견된 위치, 즉 해당 데이터가 있는 속성, 로그 본문 또는 프롬프트 | 예: **새 이슈 처리**가 켜져 있는 동안 새 심각 또는 높음 이슈가 시작합니다 |
| **AI로 수정** | AI로 설명이 보내는 내용을 코딩 에이전트에 대한 요청으로 보내며, 코딩 에이전트는 변경을 위해 리포지토리 자체의 코드를 읽습니다 | 아니요: 사용자가 **코드** 에서 변경할 수 있는 리포지토리에서 요청합니다 |
| **어떤 감지기도 판별하지 못한 필드에 대한 제안** | 저장소 종류와 AI가 지정할 수 있는 데이터 유형. 각 필드의 이름, 옆에 있는 필드의 이름, 값의 형태(모든 문자는 `a` 또는 `A`로, 모든 숫자는 `9`로 표시). 읽은 값의 개수와 길이 | 예: 저장소의 콘텐츠 스캔이 시작합니다 |
| **AI에게 질문** | 사용자가 데이터 보안에서 읽을 수 있는 저장소, 이슈, 접근 권한. 무엇이 어디서 발견되었는지(위치별 각 데이터 유형, 개수, 신뢰도) | 아니요: 사용자가 질문합니다 |
| **데이터 저장소 소유자** | 저장소의 이름, 종류, 공급자, 환경, 민감도, 데이터 유형 이름. 소유자를 가리키는 정보: 클라우드 태그, 이를 사용하는 서비스, 이를 선언한 파일의 코드 소유자, 이에 대한 변경 내역. 증거가 가리키는 팀은 이름으로, 사람은 번호가 매겨진 후보로만 보내며 이름이나 이메일 주소는 보내지 않음 | 예: 소유자가 없는 저장소가 시작합니다. 새 저장소는 하루에 한 번, 그리고 클라우드 연결을 처음 읽을 때이며, **새 이슈 처리** 가 켜져 있는 동안입니다 |

**AI로 설명** 과 **AI에게 질문** 은 팀에 [AI 컨텍스트](/docs/ai/ai-context)가 있으면 그것도 먼저 읽습니다. 팀이 시스템에 대해 OneUptime AI를 위해 작성한 메모입니다. **새 이슈 분석**도 이를 읽습니다.

### 시스템이 쓴 텍스트는 데이터입니다

저장소의 이름, 클라우드 ID, 태그, 클라우드가 응답한 증거, 속성의 키는 클라우드와 코드에서 오기 때문에, 버킷 이름을 짓거나 리소스에 태그를 달 수 있는 사람은 누구나 OneUptime AI가 읽는 내용을 쓰게 됩니다. OneUptime AI는 모든 지시를 별도의 메시지로 받고, 그 텍스트는 두 번째 메시지로, 데이터로서 받습니다:

- 각 텍스트는 길이가 제한되고 한 줄로 바뀌며, 시크릿, 이메일 주소, IP 주소처럼 보이는 것은 빠집니다
- "ignore previous instructions"처럼 AI에 대한 지시로 읽히는 텍스트는 표시되며, OneUptime AI는 그것을 절대 따르지 말라는 지시를 받습니다
- 필드 제안과 같은 구조화된 답변은 엄격하게 읽습니다: 요청한 객체이거나, 답변이 없거나입니다

### 보관되는 내용

**프로젝트 설정 → AI → AI 로그** 의 각 호출 행에는 어떤 기능이 어떤 모델을 호출했는지, 그 토큰과 비용이 기록됩니다. 보낸 내용이나 응답은 절대 보관하지 않습니다. AI 로그는 프로젝트 구성원과 뷰어가 읽을 수 있지만, 데이터 보안의 레코드는 그 소유자와 보안 역할을 위한 것이기 때문입니다. 서버 운영자가 다른 AI 호출이 보내는 내용을 기록하는 경우에도, OneUptime 자체 텔레메트리는 AI로 설명이나 필드 제안이 보낸 내용을 절대 기록하지 않습니다.

호출이 실패하면 AI로 설명과 필드 제안은 보낸 내용을 인용할 수 있는 공급자의 오류를 한 마디도 보관하지 않습니다. AI로 수정 뒤에 있는 코딩 에이전트와 AI에게 질문의 채팅은 실패한 호출의 공급자 오류를 여전히 해당 행에 보관합니다.

소유자 제안은 AI로 설명 과 같은 것을 보관합니다. 호출 행에는 기능, 모델, 토큰, 비용이 남지만 보낸 내용이나 응답은 남지 않으며, 실패한 호출의 오류도 한 마디도 남지 않습니다.

## 직접 확인하기

**데이터 보안 → 설정 → OneUptime AI** 에서 프로젝트에 대한 이 모든 내용을 볼 수 있습니다:

- **OneUptime AI가 보는 정보**: 각 기능, 보내는 내용과 절대 보내지 않는 내용, 시작 조건, 실행되는 모델, 보관되는 내용. 모델은 프로젝트의 LLM 공급자를 읽을 수 있는 사람에게만 표시됩니다.
- **예시 보기**: 위험도가 가장 높은 열린 이슈에 대해 **AI로 설명** 이 보낼 정확한 입력을 보내는 그대로, **AI로 수정** 이 요청할 내용과 함께 보여 줍니다. 맨 앞에 들어가는 프로젝트의 AI 컨텍스트는 길이로 표시됩니다. 읽을 수 있는 이슈만 보여 줍니다.

**프로젝트 설정 → AI → LLM 공급자** 에서 이 페이지로 연결되므로, 모델을 고르는 사람이 찾을 수 있습니다.

## 자체 모델

데이터 보안의 모든 AI 기능은 프로젝트가 고른 모델에서 실행됩니다:

- **AI로 설명** 과 필드 제안은 AI 규칙이 그 작업에 고른 공급자, 없으면 프로젝트의 기본 LLM 공급자, 그것도 없으면 서버 자체의 공급자에서 실행됩니다.
- **AI로 수정** 의 코딩 에이전트는 AI 규칙이 고른 공급자, 없으면 프로젝트 자체 공급자 중 하나, 그것도 없으면 서버 자체의 공급자에서 실행됩니다.
- **AI에게 질문** 은 채팅에서 고른 공급자, 없으면 프로젝트의 기본 공급자에서 실행됩니다.

자체 호스팅 모델로 이 모두를 실행할 수 있습니다: Ollama, vLLM 또는 **프로젝트 설정 → AI → LLM 공급자** 에서 추가하는 OpenAI 호환 엔드포인트입니다. 네트워크와 분리된 서버에서는 Helm 차트에 포함된 vLLM이 서버 자체의 공급자이므로, 아무것도 서버 밖으로 나가지 않습니다.

### AI를 끈 경우

**프로젝트 설정 → AI → AI 기능** 에서 **AI 활성화** 가 꺼져 있으면 OneUptime AI는 아무것도 보내지 않으며, 데이터 보안은 이전처럼 계속 작동합니다: 모든 페이지, 검사, 스캔, 통합이 그렇습니다. 이슈에 AI 버튼이 나타나지 않고, 스캔 후에 어떤 필드에 대해서도 묻지 않습니다.

## 측정 방법

데이터 보안의 모든 AI 기능은 지어낸 사례로 이루어진 고정된 세트에서 측정됩니다. 사례는 기능이 입력을 만드는 방식 그대로 만들어지고, 올바른 답변이 말하는 내용으로 채점됩니다: 수정 방법을 말하고 저장소 이름이 말하라고 한 것을 아무것도 되풀이하지 않는 설명, 각 필드에 맞는 데이터 유형, 검사에 필요한 것만 바꾸고 다른 것은 바꾸지 않는 수정, 그리고 AI에게 질문이 읽은 내용에 근거한 답변입니다. 사례는 매일 밤, 데이터 보안의 AI 프롬프트가 바뀔 때마다, 그리고 모든 릴리스 전에 고정된 모델에 대해 실행되며, 릴리스하려면 각 기능이 기준치를 넘어야 합니다.

소유자 제안은 증거가 가리키는 소유자를 제안하는지, 증거가 아무도 가리키지 않을 때 아무도 고르지 않는지, 증거가 서로 다를 때 확실하지 않다고 하는지로 평가합니다.

같은 사례로 자체 모델을 측정하려면, 모델에 키가 필요한 경우 그 키를 `AI_EVAL_LLM_API_KEY`에 넣고 OneUptime 체크아웃에서 평가를 실행하세요:

```bash
npm run ai-data-security-eval -- --llm-type=Ollama --model=llama3.1:70b --base-url=http://localhost:11434
```
