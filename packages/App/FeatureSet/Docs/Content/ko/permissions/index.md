# 사용자, 팀 및 권한

OneUptime의 모든 것은 **프로젝트** 안에 있습니다. 그 프로젝트에서 누가 무엇을 할 수 있는지는 세 가지로 결정됩니다. 프로젝트에 속한 **사용자**, 그 사용자가 속한 **팀**, 그리고 그 팀에 부여된 **권한**입니다.

대부분의 동작을 설명하는 한 가지 규칙이 있습니다. **사용자는 권한을 직접 갖지 않습니다.** 사용자의 접근 권한은 해당 프로젝트에서 속해 있는 모든 팀의 권한을 합친 것입니다. 어떤 사람이 할 수 있는 일을 바꾸려면 팀 소속을 바꾸거나 그 팀의 권한을 바꿉니다.

**소유자**는 별개의 개념입니다. 소유자란 특정 리소스(모니터, 인시던트, 대시보드 등)를 책임지는 사람입니다. 소유자는 자신의 리소스에 대한 알림을 받고, 권한은 필요하다면 "내가 소유한 것만"으로 좁힐 수 있습니다.

## 한눈에 보는 모델

```text
프로젝트
  └── 팀                     ← 권한은 여기에 붙습니다
       ├── 허용 권한          ← 각각 범위를 가짐: 전체 / 소유 / 라벨
       ├── 차단 권한          ← 언제나 허용보다 우선함
       └── 팀 멤버            ← 초대를 수락한 사용자
```

| 개념 | 설명 |
| --- | --- |
| 사용자 | 하나의 OneUptime 계정. 한 번의 로그인으로 여러 프로젝트에 참여합니다. |
| 프로젝트 | 테넌트 경계. 모니터, 인시던트, 팀, 데이터는 모두 정확히 하나의 프로젝트에 속합니다. |
| 팀 | 프로젝트 안의 이름 있는 그룹으로, 권한을 담습니다. |
| 팀 멤버 | 팀에 초대되어 수락한 사용자. |
| 권한 | 하나의 기능(예: `CreateProjectMonitor`) 또는 여러 기능을 묶은 역할(예: `MonitorAdmin`). |
| 범위 | 허용 권한이 미치는 넓이. 모든 리소스, 소유한 것만, 또는 라벨이 붙은 것만. |
| 소유자 | 특정 리소스의 책임자로 지정된 사용자 또는 팀. |
| 라벨 | 리소스에 붙이는 태그. 권한을 제한하고 정리하는 데 사용합니다. |

## 사용자

사용자 계정은 OneUptime 인스턴스 전체에서 공통입니다. 같은 로그인이 초대받은 모든 프로젝트에서 동작합니다.

사용자가 프로젝트에 "속해 있다"는 것은 그 안의 **팀 하나 이상**에 소속되어 있다는 뜻입니다. "사용자를 프로젝트에 추가"하는 별도의 단계는 없습니다. 누군가를 프로젝트에 초대하는 것은 곧 팀에 초대하는 것입니다.

- 초대는 대기 중인 팀 멤버를 만듭니다. 사용자가 프로젝트 멤버로 집계되고 어떤 권한이든 얻는 것은 **초대를 수락한 뒤**입니다.
- 프로젝트의 모든 팀에서 사용자를 제거하면 그 프로젝트에 대한 접근 권한이 사라집니다.
- 프로젝트가 SSO를 강제하고 사용자가 아직 ID 공급자로 인증하지 않았다면, 미승인 SSO 사용자로 취급되어 인증할 때까지 아무것도 볼 수 없습니다. [SSO](/docs/identity/sso)를 참고하세요.
- SCIM을 구성하면 ID 공급자가 사용자와 팀 소속을 자동으로 생성, 갱신, 제거할 수 있습니다. [SCIM](/docs/identity/scim)을 참고하세요.

위치: **설정 → 사용자**에서 프로젝트의 모든 인원과 초대 상태를 확인할 수 있습니다.

## 팀

팀은 권한이 사람에게 전달되는 통로입니다. 새 프로젝트는 세 개의 팀으로 시작합니다.

| 팀 | 보유 권한 | 편집 가능 |
| --- | --- | --- |
| Owners | `ProjectOwner` | 불가. 항상 최소 한 명의 멤버가 있습니다. |
| Admin | `ProjectAdmin` | 불가 |
| Members | `ProjectMember` | 가능 — 출발점으로 제공되니 자유롭게 바꾸세요 |

**Owners**와 **Admin** 팀은 의도적으로 잠겨 있습니다. 권한을 편집할 수 없고 팀을 삭제하거나 이름을 바꿀 수도 없습니다. 프로젝트가 실수로 스스로를 잠가 버리는 일을 막는 장치입니다. Owners 팀에는 항상 최소 한 명의 멤버가 남아 있어야 합니다.

`ProjectOwner`는 가장 높은 접근 수준으로, 결제와 프로젝트 삭제를 포함해 관리자가 할 수 있는 모든 것을 포함합니다. `ProjectAdmin`은 결제와 프로젝트 삭제를 제외한 전부를 다룹니다.

추가 팀은 원하는 만큼 만들 수 있습니다. "프런트엔드 온콜", "지원", "읽기 전용 감사"처럼 만들고 각각 필요한 권한을 주세요.

위치: **설정 → 팀**. 팀을 열면 **Members**, **Permissions**, **Block Permissions**로 갈 수 있습니다.

## 권한

권한은 하나의 기능입니다. 나눠 주는 방법은 두 가지이고, 둘 다 팀의 **Permissions** 탭에 있습니다.

### 역할

역할은 제품 영역 전체를 세 가지 수준 중 하나로 묶습니다.

- **Admin** — 해당 영역의 완전한 제어. 구성(심각도, 상태, 템플릿)까지 포함합니다.
- **Member** — 일상 업무. 리소스를 만들고 편집하고 삭제할 수 있지만 영역을 재구성하지는 못합니다.
- **Viewer** — 읽기 전용.

`MonitorAdmin`, `IncidentMember`, `StatusPageViewer` 등이 있습니다. 거의 모든 경우에 역할이 정답입니다. OneUptime에 기능이 추가되어도 모니터 관련 새 테이블은 기존 모니터 역할에 편입되므로, 여러분이 새로 부여할 필요가 없습니다.

{{PERMISSION_ROLE_COUNT}}개 역할 전체는 [권한 레퍼런스](/docs/permissions/reference)에 있습니다.

### 세분화된 권한

개별 기능도 하나씩 할당할 수 있습니다. `CreateProjectMonitor`, `ReadProjectIncident`, `DeleteProjectStatusPage` 외에 {{PERMISSION_TOTAL_COUNT}}개가 더 있습니다. 역할이 너무 넓어서 딱 하나만 주고 싶을 때 사용하세요.

API 키를 만들 때 사용하는 키이기도 하고, API와 Terraform 프로바이더가 기대하는 값이기도 합니다.

전체 목록은 [권한 레퍼런스](/docs/permissions/reference)에 있습니다.

### 허용과 차단

각 팀에는 두 개의 목록이 있습니다.

- **Permissions**(허용) — 이 팀이 할 수 있는 일.
- **Block Permissions** — 허용 항목과 무관하게 이 팀이 결코 할 수 없는 일.

**차단이 언제나 이깁니다.** 라벨이 없는 차단 항목은 그 기능을 팀에서 완전히 제거합니다. 라벨이 있는 차단 항목은 그 라벨이 붙은 리소스에 대해서만 제거합니다. "이 팀은 모니터를 편집할 수 있지만 Production 라벨이 붙은 것은 제외" 같은 설정에 유용합니다.

하나의 권한이 두 목록에서 동시에 제한 라벨을 가질 수는 없습니다. OneUptime이 두 번째 항목을 설명과 함께 거부합니다.

사용자의 접근 권한은 속한 모든 팀의 합집합이므로, 한 팀의 차단이 다른 팀의 허용을 취소하지는 **않습니다**. 차단은 그것이 설정된 팀만 제한합니다. 누군가가 예상보다 많은 권한을 갖고 있다면 그 사람이 속한 모든 팀을 확인하세요.

## 범위: 허용 권한이 미치는 넓이

모든 허용 권한에는 추가할 때 선택하는 범위가 붙습니다.

| 범위 | 의미 |
| --- | --- |
| 프로젝트의 모든 리소스 | 기본값. 권한이 해당하는 모든 리소스에 적용됩니다. |
| 이 팀 또는 그 멤버가 소유 | 이 팀이나 작업하는 사용자가 소유자로 등록된 리소스에만 권한이 적용됩니다. |
| 라벨로 제한(고급) | 선택한 라벨 중 하나 이상이 붙은 리소스에만 권한이 적용됩니다. |

**소유**는 "자기 서비스는 자기가 챙긴다"는 모델을 만드는 가장 간단한 방법입니다. 팀에 `MonitorAdmin`을 소유 범위로 주고, 그 팀을 담당 모니터의 소유자로 지정하세요. 실제로 소유자를 가질 수 있는 리소스(모니터, 인시던트, 대시보드, 서비스 등)만 좁혀집니다. 프로젝트 구성(인시던트 상태, 라벨, 팀 자체)에는 소유자가 없으므로, 그곳에서는 소유 범위 역할도 평소처럼 동작합니다.

**라벨**은 같은 발상을 좀 더 수동으로 구현한 것입니다. 리소스에 태그를 붙이고, 그 태그로 제한된 권한을 부여합니다.

일부 역할은 정의상 프로젝트 전체에 적용되며 범위를 아예 제공하지 않습니다. 좁히는 것이 의미가 없기 때문입니다. "Billing Admin, 단 내가 소유한 결제에 한해서"라는 말은 아무것도 설명하지 못합니다.

## 소유자

소유자는 특정 리소스 하나에 연결된 사용자 또는 팀입니다. 운영 대상을 나타내는 대부분의 리소스(모니터, 인시던트, 알림, 예정된 유지 보수, 온콜 정책, 대시보드, 서비스, 상태 페이지, 워크플로, 런북, SLO)에는 **Owners** 탭이 있습니다.

소유자는 두 가지 일을 합니다.

1. **알림.** 리소스에 무슨 일이 생겼을 때(모니터 다운, 인시던트 생성, SLO의 오류 예산 소진 시작) OneUptime이 알려 주는 대상이 소유자입니다.
2. **접근 권한(원할 때).** 소유 범위가 대조하는 대상이 소유 관계입니다. 본인이 직접 소유자이거나, 속한 팀 중 하나가 소유자이면 일치합니다.

소유 관계만으로는 아무것도 부여되지 않습니다. 모니터의 소유자라도 속한 팀 중 하나가 모니터 권한을 함께 갖고 있지 않으면 편집할 수 없습니다. 소유 관계는 접근을 좁힐 뿐, 넓히지 않습니다.

## 라벨

라벨은 리소스에 붙이는 프로젝트 전역 태그입니다. 용도는 두 가지, 대시보드에서의 필터링과 그룹화, 그리고 위에서 설명한 권한 제한입니다.

라벨 제한은 리소스가 권한의 라벨 중 **하나 이상**을 가지고 있으면 충족됩니다. 라벨이 전혀 없는 리소스는 라벨 제한이 걸린 권한을 하나도 충족하지 못합니다.

위치: **설정 → 라벨**.

## API 키

API 키는 키 자체에 권한을 직접 부여받습니다. 팀에 속하지 않으며 팀 소속의 영향을 받지 않습니다.

- 팀에 줄 법한 세분화된 권한과 역할을 그대로 할당하세요.
- 키는 팀과 마찬가지로 **차단 권한**과 **라벨 제한**을 지원합니다.
- 키는 소유 범위를 지원하지 **않습니다**. 소유 관계는 사용자를 기준으로 확인되는데 키는 사용자가 아니므로, 필요한 접근 권한을 명시적으로 부여하세요.

각 통합에는 동작하는 선에서 가장 좁은 권한 집합을 가진 전용 키를 발급하세요. 하나를 폐기해도 다른 것에 영향이 없습니다.

위치: **설정 → API 키**. [API 레퍼런스](/docs/api-reference/api-reference)도 참고하세요.

## OneUptime이 요청 허용 여부를 결정하는 방식

로그인한 사용자의 경우 순서는 다음과 같습니다.

1. 이 프로젝트에서 사용자가 속한 팀을 찾습니다. 수락된 초대만 셉니다.
2. 그 팀들의 모든 권한 행을 모읍니다. 허용과 차단 각각에 라벨과 범위가 붙어 있습니다.
3. 차단 목록을 먼저 확인합니다. 라벨이 없는 일치 차단이 있으면 즉시 요청을 거부합니다.
4. 허용 목록을 확인합니다. 대상 테이블이 해당 작업에 대해 받아들이는 권한이 최소 하나 필요합니다.
5. 범위를 적용합니다. 소유 범위 부여는 질의를 소유 리소스로 좁히고, 라벨 범위는 일치하는 라벨로 좁힙니다. 같은 작업에 대한 다른 부여가 더 넓다면 넓은 쪽이 이깁니다.
6. 라벨 차단을 적용합니다. 라벨이 붙은 차단은 대상 리소스가 그 라벨을 갖고 있으면 요청을 거부합니다.

로그인한 사용자는 이 밖에도 자기 프로필과 자기 알림 규칙 읽기 같은 소수의 자동 권한을 갖습니다. 관리자 권한이 아니며 다른 사람의 데이터를 열지 못합니다.

확인된 권한은 사용자와 프로젝트 단위로 캐시되고, 팀 소속이나 팀 권한이 바뀌면 갱신됩니다. 권한을 바꿨는데 사용자가 즉시 변화를 보지 못한다면 새로고침하도록 안내하세요.

## 설정 예시

**보기만 하는 팀.** 팀을 만들고 `Viewer` 역할을 추가하거나, 보여 줄 영역에 대해서만 영역별 `*Viewer` 역할을 추가합니다.

**자기 서비스를 직접 관리하는 온콜 엔지니어.** 팀에 `MonitorAdmin`, `IncidentMember`, `OnCallMember`를 **소유** 범위로 주고, 그 팀을 운영 중인 모니터의 소유자로 추가합니다.

**프로덕션에서 떼어 놓을 외부 인력.** 팀에 필요한 역할을 **전체** 범위로 준 다음, 민감한 기능에 대한 **차단 권한**을 `Production` 라벨로 한정해 추가합니다.

**배포만 보고하는 CI 파이프라인.** 필요한 세분화된 권한만 담은 API 키를 만듭니다. 역할은 주지 않습니다.

**결제를 보면 안 되는 사람.** Owners 팀에 넣지 마세요. `ProjectAdmin`은 이미 결제를 제외합니다.
