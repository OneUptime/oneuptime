# 에스컬레이션 규칙

온콜 정책은 단계별로 사람을 호출합니다. 각 에스컬레이션 규칙은 하나의 단계로, 누구를 호출할지, 그리고 다음 단계를 호출하기 전에 누군가 확인하기를 얼마나 기다릴지를 정합니다. 정책의 규칙은 정책의 **에스컬레이션 규칙** 페이지에 순서대로 표시됩니다.

```mermaid title="온콜 정책은 누군가 확인할 때까지 단계별로 호출합니다"
flowchart TB
    trigger["인시던트 또는 알림"] --> level1["Level 1 호출"]
    level1 --> ack1{"제시간에<br/>확인했나요?"}
    ack1 -->|"예"| stop["호출 중지"]
    ack1 -->|"아니요"| level2["Level 2 호출"]
    level2 --> ack2{"제시간에<br/>확인했나요?"}
    ack2 -->|"예"| stop
    ack2 -->|"아니요, 마지막 단계"| repeat{"정책을 반복할까요?"}
    repeat -->|"예"| level1
    repeat -->|"아니요"| done["정책 중지"]
```

- [에스컬레이션 규칙 추가](#에스컬레이션-규칙-추가): 다음 단계를 차례대로 추가합니다.
- [단계가 사람을 호출하는 방식](#단계가-사람을-호출하는-방식): 타이밍, 반복, 각 사람에게 연락하는 방법.
- [로테이션의 다음 사람](#로테이션의-다음-사람에게-에스컬레이션): 온콜 담당자의 백업을 같은 로테이션에서 호출합니다.
- [호출 에스컬레이션](#호출-에스컬레이션): 호출을 받을 수 없나요? 바로 다음 단계를 호출합니다.
- [API와 Terraform](#api-또는-terraform으로-규칙-만들기): 정책과 규칙을 코드로 만듭니다.
:::

## 먼저 호출되는 사람

**온콜 정책** 페이지에서 온콜 정책을 만들면 양식에서 **이름** 과 **누구에게 먼저 알릴까요?** 를 묻습니다. 이 질문은 **알림** 과 같은 선택기를 사용하므로 온콜 스케줄, 팀, 사람을 필요한 만큼 고를 수 있습니다. 선택한 대상은 정책의 첫 번째 에스컬레이션 규칙인 **Level 1** 이 되며, 다음 단계를 호출하기 전에 확인을 **30분** 기다립니다.

:::steps
1. **온콜 듀티** > **온콜 정책** 으로 이동하여 **온콜 정책 만들기** 를 클릭합니다.
2. **이름** 을 입력합니다.
3. **누구에게 먼저 알릴까요?** 에서 **응답자 추가** 를 클릭하고 먼저 호출할 온콜 스케줄, 팀, 사람을 선택합니다.
4. **온콜 정책 만들기** 를 클릭합니다. 새 정책은 해당 **에스컬레이션 규칙** 페이지에서 열리며, 여기서 단계를 더 추가할 수 있습니다.
:::

**누구에게 먼저 알릴까요?** 는 선택 사항입니다. 비워 두면 정책은 에스컬레이션 규칙 없이 시작합니다. 규칙을 추가할 때까지 아무도 호출하지 않으며, 개요에도 그렇게 표시됩니다. 설명과 레이블은 **추가 필드** 아래에 있습니다. 이 질문은 에스컬레이션 규칙을 추가할 수 있는 사람에게만 표시됩니다.

## 에스컬레이션 규칙 추가

:::steps
### 정책의 에스컬레이션 규칙 열기

온콜 정책을 열고 사이드 메뉴에서 **에스컬레이션 규칙** 을 선택한 다음 **에스컬레이션 규칙 추가** 를 클릭합니다. 대화 상자는 짧은 한 페이지입니다.

### 알릴 대상 선택

**알림** 에서 **응답자 추가** 를 클릭하고, 검색하여 이 단계에서 호출할 온콜 스케줄, 팀, 사람을 필요한 만큼 선택합니다. 하나 이상 추가하세요.

| 응답자 | 단계가 실행될 때 호출되는 사람 |
| --- | --- |
| **온콜 스케줄** | 단계가 실행될 때 해당 스케줄의 온콜 담당자입니다. 고정된 사람이 아닙니다. |
| 스케줄의 **로테이션의 다음 사람** | 해당 스케줄에서 온콜 담당자 다음 사람이며, 같은 로테이션에서 정해집니다. [로테이션의 다음 사람에게 에스컬레이션](#로테이션의-다음-사람에게-에스컬레이션) 을 참조하세요. |
| **팀** | 팀의 모든 구성원. |
| **사람** | 그 사람에게 직접. |

### 대기 시간 설정

**에스컬레이션 대기 시간(분)** 은 다음 단계를 호출하기 전에 확인을 기다리는 시간입니다. 처음 값은 **30분** 이며, 단계에 맞게 바꾸면 됩니다.

### 원하면 규칙에 이름 지정

나머지 항목은 모두 **추가 필드** 아래에 있으며, 열기 전까지 접혀 있습니다.

- **이름**: 선택 사항입니다. 이름을 지정하지 않은 규칙은 단계에 따라 이름이 붙습니다. 정책의 첫 번째 규칙은 **Level 1**, 두 번째는 **Level 2** 등입니다. 이름 필드에는 규칙이 받게 될 이름이 표시됩니다.
- **설명**: 선택 사항인 메모입니다. 예를 들어 이 단계가 누구를 왜 호출하는지 적습니다.

접혀 있을 때 **추가 필드** 의 머리글에는 두 항목의 이름과 규칙에 설정된 항목(설명 또는 직접 지정한 이름)이 표시됩니다.

### 규칙 만들기

**규칙 만들기** 를 클릭합니다. 규칙은 다른 규칙 아래에 정책의 다음 단계로 추가됩니다.
:::

## 단계가 사람을 호출하는 방식

인시던트나 알림이 정책에 도달하면 **Level 1** 이 즉시 응답자를 호출합니다. 대기 시간 안에 아무도 확인하지 않으면 **Level 2** 가 호출되고, 목록 아래로 계속 이어집니다. 마지막 단계의 대기 시간이 확인 없이 지나면, 정책의 **반복 정책** (규칙 아래에 있음)이 반복하도록 되어 있을 경우 허용된 횟수만큼 **Level 1** 부터 다시 시작하고, 그렇지 않으면 중지합니다. 인시던트나 알림을 확인하거나 해결하면 어느 단계에서든 호출이 중지됩니다. 호출을 받았지만 대응할 수 없는 사람은 호출을 에스컬레이션할 수 있으며, 그러면 기다리지 않고 다음 단계가 호출됩니다. [호출 에스컬레이션](#호출-에스컬레이션)을 참고하세요.

이미 인지됨 또는 해결됨 상태로 생성된 인시던트, 알림, 에피소드(사후에 기록한 것)는 어떤 정책도 실행하지 않습니다. 아무도 호출되지 않으며, 피드에 정책 이름과 함께 그 사실이 남습니다. [이미 인지되었거나 해결된 상태로 선언된 인시던트](/docs/incidents/declaring-incidents#이미-인지되었거나-해결된-상태로-선언된-인시던트) 를 참조하세요.

도달했을 때 호출할 사람이 없는 단계는 즉시 건너뜁니다. 기다리지 않고 다음 단계가 바로 호출됩니다. 응답자가 없는 단계와, 그 시점에 응답자 중 호출할 수 있는 사람이 아무도 없는 단계가 여기에 해당합니다. 구성원이 없는 팀, 아무도 온콜이 아닌 스케줄, 또는 대신할 사람 없이 부재 중이거나 프로젝트를 떠났거나 전혀 연락할 수 없는 사람입니다. 어느 단계에도 호출할 사람이 없으면 정책은 즉시 중지되며 반복하지 않습니다.

정책을 반복하려면 **반복 정책** 카드에서 **편집** 을 클릭하고, **Level 1부터 다시 시작** 을 고른 다음 **몇 번 더 할까요?** 를 설정합니다.

### 에스컬레이션 요약

**에스컬레이션 규칙** 페이지 맨 위의 요약에는 전체 단계가 표시됩니다. 각 단계가 언제 호출되는지, 누구를 호출하는지, 마지막 단계 이후에 무슨 일이 일어나는지입니다. 응답자를 모두 호출할 수 없는 단계는 카드에 그렇게 표시되며, 레이블을 클릭하면 누구이고 왜 그런지 볼 수 있습니다. 응답자가 없는 단계에는 **바로 건너뜀** 이 표시되며, 그 대기 시간은 다음 단계가 호출되는 시점에 포함되지 않습니다.

### 각 사람에게 연락하는 방법

단계가 호출하는 각 사람에게는 그 사람의 온콜 규칙에 따라 연락합니다. **사용자 설정** > **온콜 규칙** 에는 인시던트, 인시던트 에피소드, 알림, 알림 에피소드별 탭이 있고, 심각도별 카드에 어떤 알림 방법을 얼마 후에 시도하는지가 나옵니다. 프로젝트 관리자는 **사용자** > 구성원 > **온콜 규칙** 에서 구성원의 규칙을 보고 바꿀 수 있습니다. [개인 온콜 규칙](/docs/notifications/on-call-rules) 을 참조하세요.

```mermaid title="단계가 호출하는 대상과 각 사람에게 연락하는 방법"
flowchart TB
    subgraph notify["알림"]
        direction LR
        schedule["온콜 스케줄"]
        team["팀"]
        user["사람"]
    end
    schedule -->|"그때의 온콜 담당자"| person["호출된 사람"]
    team -->|"모든 구성원"| person
    user -->|"직접"| person
    person --> rules["그 사람의 온콜 규칙"]
    rules --> methods["그 사람의 알림 방법"]
```

어떤 사람에게 적용 중인 사용자 재정의가 있으면, 그 사람에게 가는 호출은 대신 맡은 사람에게 전송됩니다. 대신할 사람을 지정하지 않은 재정의는 그 사람을 건너뜁니다. 그 사람은 호출되지 않고, 정책 실행에는 부재 중이라는 것과 언제까지인지가 표시되며, 온콜 스케줄에서는 그 사람의 각 순번이 로테이션의 다음 사람에게 넘어갑니다. [사용자 재정의](/docs/on-call/user-overrides) 를 참조하세요.

모든 메시지는 제공자가 받아들이는 형태로 보내지므로 호출은 항상 발송됩니다. 채널마다 담을 수 있는 양은 다음과 같습니다.

| 채널 | 담을 수 있는 가장 긴 메시지 |
| --- | --- |
| SMS | 1,600자 |
| 전화 | Twilio의 4,000자 통화 스크립트에 들어가는 만큼 |
| 푸시 알림 | 4KB, 그중 제목, 본문, 데이터가 최대 3KB |
| WhatsApp | 1,024자 |
| Telegram | 4,096자 |

이보다 긴 메시지(긴 제목이나 템플릿이 넣은 긴 설명이 있는 메시지)는 잘리며, 전체 내용은 OneUptime에 있다는 안내로 끝납니다: "… (truncated — see OneUptime for the full text)". WhatsApp 메시지의 문구는 고정된 템플릿이므로, 그곳에서는 대신 가장 긴 값이 잘리고 각각 "…"로 끝납니다. 메시지의 링크는 절대 잘리지 않습니다.

### 호출 SMS의 내용

SMS는 160자 단위의 부분으로 나뉘어 발송되고, 부분마다 요금이 매겨집니다. SMS로 보내는 호출은 가능하면 한 부분에 들어가도록 쓰이며, 잠긴 휴대폰에서 필요한 것만 알려 줍니다. 누가 보냈는지, 무슨 일이 일어났는지, 그리고 호출을 확인하거나 에스컬레이션하는 하나의 링크입니다. 휴대폰에서는 다음과 같이 보입니다.

```text
OneUptime: Critical Incident INC-42 in Acme Prod: Checkout API is down.
Ack or escalate: https://oneuptime.com/l/XJlaZRsd
```

심각도와 일어난 일(인시던트, 알림 또는 둘 중 하나의 에피소드), 그 번호, 프로젝트, 제목을 이 순서로 알려 줍니다. 모두 한 부분에 들어가지 않으면 다음과 같이 합니다.

1. 먼저 프로젝트가 빠집니다.
2. 다음으로 제목이 잘리고 `...` 로 끝납니다.

심각도, 번호, 링크는 절대 잘리지 않습니다. 제목은 최소 20자가 남습니다. 그것조차 들어가지 않으면(아주 긴 주소나 제품 이름 등) SMS가 두 번째 부분을 써서 모두 알려 줍니다.

인지된 인시던트나 알림이 아직 해결되지 않아 정책이 다시 알릴 때는 SMS가 번호와 프로젝트 다음에 그렇다고 알려 줍니다. 이 말도 절대 잘리지 않으며, 다음과 같이 보입니다.

```text
OneUptime: Critical Incident INC-42 in Acme Prod is still not resolved:
Checkout API is down. Ack or escalate: https://oneuptime.com/l/XJlaZRsd
```

SMS의 기본 문자 집합에 없는 문자가 하나라도 있으면 메시지 전체가 70자 단위의 부분으로 발송됩니다. 그래서 둥근 따옴표와 대시는 `"` , `'` , `-` 로, `…` 는 `...` 로 쓰이고, `ç` , `ł` 같은 글자는 악센트가 빠지며, 이모지는 생략됩니다. 일본어나 러시아어처럼 다른 문자로 된 제목은 쓰인 그대로 발송되며 두 부분 이상을 차지합니다.

OneUptime이 보내는 다른 SMS(내가 소유한 인시던트의 변경이나 온콜 근무 시작 등)도 `OneUptime:` 로 시작해 `Turn off in User Settings > Notification Settings.` 로 끝납니다. 이 문장을 빼야 한 부분에 들어가는 경우에는 이 문장이 빠집니다.

### 호출이 전송되지 않는 경우

전송되지 않은 호출은 그 사람의 **온콜 로그** (사용자 설정)에 이유가 표시됩니다. 행에는 **오류** 가 표시되고, 상태 메시지에 이유가 나옵니다. 더 이상 **전송 중** 상태로 남지 않습니다. 메시지는 다음 중 하나를 알려 줍니다.

- 프로젝트 잔액으로 비용을 낼 수 없었으며, 누가 잔액을 추가할 수 있는지;
- 프로젝트에서 채널이 꺼져 있으며, 누가 켤 수 있는지.

프로젝트 소유자는 잔액이 충전되거나 채널이 다시 켜질 때까지 이에 관한 이메일을 한 번 받습니다.

OneUptime Cloud에서는 SMS, 통화, WhatsApp, Telegram 메시지마다 **프로젝트 설정 > 알림 > 알림 설정** 에 있는 프로젝트 잔액에서 비용이 지불됩니다. 제공자가 메시지를 받으면 정확한 비용이 잔액에서 차감되며, 한꺼번에 나가는 메시지 수와는 관계가 없습니다.

- 그곳에서 **자동 충전** 이 켜져 있으면, 잔액이 기준치 아래인 것을 발견한 메시지가 먼저 자동 충전에 설정된 금액을 추가하고 프로젝트의 카드에 청구합니다. 같은 순간에 잔액 부족을 발견한 메시지들은 카드에 한 번만 청구합니다.
- 그 청구가 실패하면(결제 수단이 없거나 카드가 거절된 경우) 자동 충전은 1시간 후 카드로 다시 시도하며, 그때까지 **알림 설정** 맨 위에 그렇게 표시됩니다. 잔액을 직접 추가하거나 자동 충전을 다시 저장하면 즉시 시도합니다.
- 자동 충전이 카드에 청구하지 못하는 동안에도 호출은 남은 잔액으로 계속 발송됩니다.

> [!IMPORTANT]
> 새 프로젝트에서는 SMS, 전화, WhatsApp, Telegram이 꺼져 있습니다. OneUptime Cloud에서는 모든 메시지가 프로젝트 잔액에서 지불되고, 자체 호스팅 설치에서는 먼저 Twilio 계정이나 Telegram 봇을 설정해야 하기 때문입니다. 채널이 꺼져 있는 동안에는 프로젝트의 누구도 그 채널에 알림 방법을 추가할 수 없습니다. 채널은 프로젝트 소유자, **결제 관리자**, 또는 **Manage Billing** 권한이 있는 사람만 **프로젝트 설정 > 알림 > 알림 설정** 의 **알림 채널** 카드에서 켤 수 있으며, 프로젝트 관리자는 켤 수 없습니다. 다른 모든 사람에게는 채널이 꺼져 있는 모든 곳에서 누가 켤 수 있는지 정확히 알려 줍니다. 그 채널에 대한 자신의 방법 목록 위, 설정 체크리스트, 그리고 무언가에 그 채널이 필요할 때 받는 메시지입니다.

## 로테이션의 다음 사람에게 에스컬레이션

단계는 온콜 스케줄 로테이션의 다음 사람, 즉 해당 스케줄의 온콜 담당자 다음 사람을 호출할 수 있습니다. 그래서 정책은 스케줄 하나만으로 먼저 온콜 담당자를, 다음으로 같은 로테이션의 백업을, 그다음 팀이나 관리자를 호출할 수 있습니다.

| 단계 | 알림 | 호출되는 사람 |
| --- | --- | --- |
| **Level 1** | Payments primary 스케줄 | 해당 스케줄의 온콜 담당자(예: Alex) |
| **Level 2** | 같은 스케줄의 **로테이션의 다음 사람** | 로테이션에서 Alex 다음 사람(예: Sam) |
| **Level 3** | Platform 팀 | 팀의 모든 구성원 |

:::steps
1. 정책의 첫 번째 단계인 **Level 1** 이 온콜 스케줄에 알리는지 확인합니다.
2. **에스컬레이션 규칙 추가** 를 클릭한 다음 **응답자 추가** 를 클릭하고, **로테이션의 다음 사람** 아래에서 같은 스케줄을 선택합니다. **에스컬레이션 대기 시간(분)** 을 설정하고 **규칙 만들기** 를 클릭합니다.
3. 그다음에 알아야 할 팀이나 관리자를 위해 단계를 하나 더 추가합니다.
:::

다음 사람은 단계가 실행될 때 그 시점의 스케줄을 기준으로 정해집니다.

- 온콜 담당자 다음 사람이며, 순서는 로테이션 구성원이 교대하는 순서입니다. 마지막 사람 다음에는 다시 첫 번째 사람이 옵니다.
- 부재 중인 사람은 대신 맡은 사람이 있든 없든 건너뛰며, 다른 사람 대신 온콜을 맡고 있는 사람도 마찬가지입니다.
- 항상 같은 로테이션의 사람입니다. 레이어가 여러 개라면 온콜 담당자가 속한 레이어에서 정해집니다. 다른 사람이 없거나 다른 모두가 부재 중인 로테이션에는 다음 사람이 없으며, 그 단계는 그곳에서 아무도 호출하지 않고 그 사실을 남깁니다.
- 스케줄에 온콜 담당자가 아예 없으면 다음 사람도 없으며, 그 단계는 거기서 아무도 호출하지 않습니다.

Slack과 Microsoft Teams의 실행 메시지, 인시던트의 피드, **실행 타임라인** 에는 누가 로테이션의 다음 사람으로 호출되었는지와 어느 스케줄에서였는지가 표시됩니다: "Sam Lee (next in the Payments primary rotation)".

> [!TIP]
> 스케줄 하나면 충분합니다. 첫 번째 스케줄과 맞춰 관리해야 하는 두 번째 백업 스케줄이 필요 없고, 구성원이 등록한 부재는 두 단계 모두에 적용됩니다.

## 호출 에스컬레이션

호출을 받았지만 자고 있거나, 비행기 안에 있거나, 이미 다른 인시던트를 처리하고 있어서 대응할 수 없는 사람은 호출이 계속 울리게 두는 대신 에스컬레이션할 수 있습니다. 그러면 정책은 그 단계의 **에스컬레이션 대기 시간(분)** 을 기다리지 않고 바로 다음 단계를 호출하며, 그 사람은 이 건으로 다시 호출되지 않습니다.

```mermaid title="호출을 에스컬레이션하면 정책이 바로 다음 단계로 넘어감"
flowchart TB
    page["Level 1 이 Alex 를 호출"] --> take{"Alex 가<br/>대응할 수 있나?"}
    take -->|"예"| ack["Alex 가 확인:<br/>호출이 중지됨"]
    take -->|"아니요"| pass["Alex 가<br/>에스컬레이션함"]
    pass --> others{"Level 1 에서 아직<br/>호출 중인 사람?"}
    others -->|"있음"| wait["정책은 전처럼<br/>그들을 기다림"]
    others -->|"없음"| next["Level 2 를<br/>지금 호출"]
```

모든 호출은 받은 곳에서 에스컬레이션할 수 있습니다.

| 위치 | 에스컬레이션하는 방법 |
| --- | --- |
| 이메일 | **Escalate** 버튼을 누른 다음, 열린 페이지에서 **Escalate** 을 누릅니다 |
| SMS 및 WhatsApp | 메시지의 링크가 확인 페이지를 열며, 그 페이지에도 **Escalate** 이 있습니다 |
| Telegram, Slack, Microsoft Teams | "Can't take it? Escalate" 링크를 연 다음, 열린 페이지에서 **Escalate** 을 누릅니다 |
| 전화 | 2번을 누릅니다. 그러면 전화가 무슨 일이 일어났는지 알려 줍니다 |
| 푸시 알림 | 탭하면 인시던트, 알림 또는 에피소드가 OneUptime On-Call 앱에서 열리고, 그 아래에 **Escalate** 이 있습니다 |
| OneUptime | 인시던트, 알림 또는 에피소드 상단의 상태 버튼 다음에 있는 **에스컬레이션** |

전화를 제외한 모든 방법은 무엇이든 하기 전에 먼저 묻고, 무슨 일이 일어날지 알려 줍니다. 예: "This will immediately page Platform leads (Level 2 of 3), without waiting." 전화에서는 2번을 누르는 것이 그 답입니다. 호출을 에스컬레이션할 수 있는 사람은 호출받는 본인뿐입니다. OneUptime의 버튼은 본인에게만 보이고, 메시지의 링크는 그 메시지로 보낸 호출만, 받은 사람 본인을 위해서만, 7일 동안 에스컬레이션할 수 있습니다.

그다음에 일어나는 일은 다른 누가 호출되고 있는지에 따라 다릅니다.

- 같은 단계의 다른 사람이 아직 호출되고 있는 경우: 정책은 전처럼 그들을 기다립니다. 단계의 대기 시간이 끝나거나, 그중 마지막 사람도 에스컬레이션하는 즉시 다음으로 넘어갑니다.
- 그 단계에 다른 사람이 남아 있지 않은 경우: 다음 단계가 바로 호출됩니다.
- 마지막 단계였던 경우: **반복 정책** 이 반복하도록 되어 있으면 정책은 바로 **Level 1** 부터 다시 시작합니다. 그렇지 않으면 호출이 중지되고, 누군가 처리해야 합니다.

호출을 에스컬레이션해도 확인한 것은 아닙니다. 인시던트나 알림은 여전히 누군가 확인하기를 기다리고, 에스컬레이션한 사람도 직접 확인할 수 있습니다. 이번 실행은 그 사람을 이 건으로 다시 호출하지 않으며, 그 사람이 포함된 이후 단계나 반복은 그 사람을 건너뜁니다. 호출한 모든 사람이 에스컬레이션해서 더 호출할 사람이 남지 않으면 호출이 중지되고, 인시던트의 피드에 그렇게 표시됩니다.

워크플로우가 사람들에게 직접 보내는 호출에는 단계가 없습니다. 에스컬레이션하면 더 이상 호출되지 않으며, 호출받은 모든 사람이 에스컬레이션하면 호출이 중지됩니다.

에스컬레이션한 내역은 모두 기록됩니다. 실행의 **실행 타임라인** 은 그 사람의 줄을 **에스컬레이션됨** 으로 표시하고, 인시던트의 피드에는 "Alex Kim escalated the page from on-call policy Payments at Level 1 of 3." 라고 표시되며, Slack과 Microsoft Teams의 실행 메시지는 그 사람이 에스컬레이션했다고 알리고, 그 사람의 **온콜 로그** 는 그 호출을 **에스컬레이션됨** 으로 보여 줍니다.

## 규칙 편집, 순서 변경, 삭제

각 규칙의 카드에는 **규칙 편집** 과 나머지 작업이 있는 **⋯** 메뉴가 있습니다.

- **규칙 편집** 은 같은 한 페이지짜리 대화 상자를 규칙의 현재 내용(응답자, 대기 시간, **추가 필드** 아래의 이름과 설명)이 채워진 상태로 엽니다. 응답자를 추가하거나 제거하고 **변경 사항 저장** 을 클릭합니다. 이름을 지우면 규칙은 다시 단계의 이름을 받습니다.
- 규칙의 **⋯** 메뉴에 있는 **위로 이동** 과 **아래로 이동** 은 규칙의 단계를 바꿉니다. 단계에 따라 이름이 붙은 규칙은 위치에 맞는 이름을 유지합니다. **Level 3** 이 **Level 2** 위로 올라가면 두 규칙의 이름이 서로 바뀝니다. **관리자** 처럼 직접 고른 이름은 규칙이 어디로 이동해도 그대로입니다.
- **규칙 삭제** 는 먼저 확인을 요청하고 그 단계가 누구를 호출하는지 알려 줍니다. 단계를 삭제하면 그 아래 단계들이 위로 올라가고, 단계에 따라 이름이 붙은 규칙은 그에 맞게 이름이 바뀝니다.

## API 또는 Terraform으로 규칙 만들기

에스컬레이션 규칙은 `/api/on-call-duty-policy-escalation-rule` 리소스이고, 규칙이 호출하는 사람, 팀, 스케줄은 `/api/on-call-duty-policy-escalation-rule-user`, `-team`, `-schedule` 리소스입니다.

- `name` 없이 만든 규칙은 대시보드에서와 같이 단계에 따라 이름이 붙습니다. 정책의 세 번째 단계가 되는 규칙이라면 **Level 3** 입니다. Terraform의 에스컬레이션 규칙 리소스에는 여전히 이름이 필요합니다.
- `escalateAfterInMinutes` 에는 대시보드 밖에서는 기본값이 없습니다. 이 값 없이 만든 규칙은 기다리지 않으며, 이 단계가 실행되자마자 다음 단계가 호출됩니다. 명시적으로 설정하세요. 대시보드가 제안하는 값은 30입니다.
- `miscDataProps` 에 `onCallSchedules`, `teams`, `users` (ID 목록)를 넣어 만든 규칙은 그 응답자를 받습니다. 대시보드의 **알림** 선택기가 응답자를 보내는 방식입니다. 이것들 없이 만든 규칙은 위의 리소스로 응답자를 추가할 때까지 아무도 호출하지 않습니다.
- `miscDataProps` 에 `nextInRotationSchedules` (스케줄 ID 목록)를 넣어 만든 규칙은 각 스케줄 로테이션의 다음 사람을 호출합니다. `-schedule` 리소스에서는 `pageNextInRotation` 이 `true` 인 행이 같은 일을 하며, 이 값은 행을 만들 때 정해집니다.
- 단계에 따라 이름이 붙은 규칙의 이름이 바뀌는 것은 대시보드에서 규칙을 이동하거나 삭제할 때입니다. API나 Terraform으로 `order` 를 바꾸면 순서만 바뀝니다.
- `/api/on-call-duty-policy` 에서 `miscDataProps` 에 `onCallSchedules`, `teams`, `users` (ID 목록)를 넣어 온콜 정책을 만들면, 대시보드와 같이 첫 번째 에스컬레이션 규칙이 생깁니다. 이들을 호출하는 **Level 1** 이며, `escalateAfterInMinutes` 는 30입니다. 모든 ID가 프로젝트에 속해야 하고 호출자가 에스컬레이션 규칙을 만들 수 있어야 하며, 그렇지 않으면 정책이 만들어지지 않습니다. 이것들 없이 만든 정책에는 이전처럼 규칙이 없으며, Terraform의 정책 리소스는 이것들을 보내지 않습니다.

```bash
curl -X POST https://oneuptime.com/api/on-call-duty-policy \
  -H "apikey: $ONEUPTIME_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "data": {
      "projectId": "<project-id>",
      "name": "Production on-call"
    },
    "miscDataProps": {
      "onCallSchedules": ["<schedule-id>"],
      "users": ["<user-id>"]
    }
  }'
```
