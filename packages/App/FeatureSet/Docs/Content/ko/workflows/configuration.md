# 워크플로우 설정 및 보안

워크플로를 실제 트래픽에 연결하기 전에 알아 둘 것들입니다. 안전하게 켜는 방법, 누가 무엇을 할 수 있는지, 시크릿과 URL을 비공개로 유지하는 방법, 워크플로의 단계가 바꿀 수 있는 것, 그리고 모든 실행이 따르는 한도입니다.

:::cards
- [운영 시작하기](#워크플로-켜고-끄기): 워크플로 실행으로 테스트한 다음 워크플로를 켜 둡니다.
- [권한](#권한): 워크플로 역할과 그 뒤에 있는 개별 권한.
- [단계가 할 수 있는 일](#워크플로-단계가-할-수-있는-일): 단계는 워크플로 프로젝트의 Project Admin으로 동작합니다.
- [한도](#플랜-한도): 플랜별 실행 횟수, 실행 시간, 워크플로 간 호출.
:::

## 워크플로 켜고 끄기

모든 워크플로에는 **빌더** 맨 위와 **개요** 페이지에 **활성화됨** 스위치가 있습니다. 꺼져 있으면 워크플로가 실행되지 않습니다. 웹훅 호출, 수신 이메일, 예약된 시각, OneUptime 이벤트가 모두 무시되며, **워크플로 실행**과 **Run just this step**도 마찬가지입니다. 새 워크플로는 비활성화된 상태로 시작합니다.

이 스위치를 "준비 완료" 관문으로 쓰세요.

:::steps
1. 워크플로를 만듭니다.
2. 현실적인 값으로 **빌더**에서 **워크플로 실행**을 클릭합니다. 비활성화된 워크플로는 수동으로도 실행할 수 없으므로, 빌더가 먼저 켜라고 요청합니다. **켜고 실행**을 클릭하세요.
3. 실행을 열고 각 블록이 예상한 곳으로 갔는지 확인합니다. [실행 기록](/docs/workflows/runs-and-logs)을 참조하세요.
4. 준비되었다면 **활성화됨**을 켜 둡니다. 아니라면 준비될 때까지 끄세요. 켜져 있는 동안에는 실제 이벤트에 트리거가 발생합니다.
:::

워크플로를 끄면 새 실행이 시작되지 않습니다. 이미 진행 중인 실행은 끝까지 진행되지만, **Sleep** 블록에서 기다리는 실행은 깨어날 때 취소됩니다.

## 워크플로 보관하기

더는 필요 없지만 남겨 두고 싶은 워크플로는 보관하세요. 보관된 워크플로는 다음과 같습니다.

- **절대 실행되지 않습니다**. 어떤 트리거에서도요. 수동 실행과 **Run just this step**, 웹훅 호출, 일정, OneUptime 이벤트, 수신 이메일, 다른 워크플로의 **Execute Workflow** 단계가 모두 거부됩니다. 보관된 워크플로로의 웹훅 호출에는 워크플로가 보관되었다는 오류가 돌아갑니다.
- **기다리는 실행을 멈춥니다.** **Sleep** 단계에서 잠든 실행은 깨어날 때 취소되고, 대기열에 있었지만 아직 시작하지 않은 실행은 "Workflow was archived before this run started, so it did not run."으로 끝납니다.
- **워크플로 목록에서 빠집니다.** **워크플로 → 고급 → 보관됨**에서 찾을 수 있습니다.
- **모든 것을 유지합니다.** 단계, 변수, 소유자, 레이블, 실행 기록이 그대로 남습니다.

워크플로 하나를 보관하려면 그것을 열고 **설정**으로 가서 **보관**을 클릭하세요. 여러 개를 보관하려면 **워크플로** 목록에서 선택하고 **보관**을 고르세요.

워크플로를 되돌리려면 **워크플로 → 고급 → 보관됨**을 열고 선택한 다음 **보관 취소**를 고르거나, 워크플로를 열고 페이지 맨 위 배너의 **보관 취소**를 클릭하세요.

보관과 **활성화됨** 스위치는 별개입니다. 보관은 스위치를 건드리지 않으므로, 켜져 있던 워크플로는 보관이 취소되자마자 다시 실행되고, 꺼져 있던 것은 꺼진 채로 남습니다. **보관됨** 페이지의 **When Unarchived** 열에 어느 쪽인지 표시됩니다.

내보낸 워크플로는 보관 상태를 가져가지 않으므로, 가져온 사본은 절대 보관된 상태가 아닙니다.

## 소유자와 레이블

| 무엇              | 어디                                              | 하는 일                                                                                                                                                   |
| ----------------- | ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **소유자**        | 워크플로의 **소유자** 페이지                      | 워크플로를 책임지는 사용자와 팀. 팀이 소유한 것으로 제한된 역할은 그 팀이 소유한 워크플로에 접근합니다.                                                   |
| **레이블**        | 워크플로의 **개요** 페이지                        | 팀, 통합, 환경별로 워크플로를 묶는 태그. **워크플로** 목록을 레이블로 필터링하고, 역할을 일부 레이블로 제한할 수 있습니다.                                |
| **레이블 규칙**   | **워크플로 → 설정 → 레이블 규칙**                 | 이름이나 설명의 패턴에 따라 새 워크플로에 레이블을 자동으로 붙입니다.                                                                                     |
| **소유자 규칙**   | **워크플로 → 설정 → 소유자 규칙**                 | 새 워크플로에 소유자를 자동으로 지정합니다.                                                                                                               |

규칙이 일치하는 방식은 [레이블 및 소유자 규칙](/docs/configuration/label-and-owner-rules)을 참조하세요.

## 시크릿

민감한 것을 담은 변수는 **시크릿**으로 표시하세요. 그러면 값이 실행 로그와 단계 추적에서 지워집니다. 시크릿이든 아니든 어떤 변수의 값도 저장한 뒤에는 대시보드에서도 API로도 다시 읽을 수 없으며, 한 번 시크릿이 된 변수는 계속 시크릿으로 남습니다.

시크릿 변수는 다음에 쓰세요.

- 외부 서비스의 API 키.
- 인증 토큰.
- 웹훅 서명 키.
- 읽기 전용 접근 권한이 있는 사람이 보지 않았으면 하는 모든 것.

시크릿을 블록에 직접 붙여 넣지 마세요. `Authorization: Bearer eyJh...` 같은 값이 워크플로와 로그에 그대로 보이게 됩니다. 대신 `{{global.variables.MY_SECRET}}` 를 쓰세요.

시크릿이 만료되는 OAuth 접근 토큰이라면 변수를 [OAuth 2.0 변수](/docs/workflows/variables#oauth-20-변수스스로-갱신되는-토큰)로 만드세요. 그러면 OneUptime이 ID 공급자에게서 토큰을 가져오고, 워크플로가 만료된 토큰을 쓰려 할 때마다 갱신합니다. OAuth 2.0 변수는 항상 시크릿이며, 그 자격 증명은 데이터베이스에 암호화되어 저장됩니다.

## 워크플로 내보내기와 가져오기

워크플로를 JSON 파일로 프로젝트 사이, 또는 셀프 호스팅 설치와 OneUptime Cloud 사이에서 옮길 수 있습니다.

:::tabs
@tab 내보내기
워크플로를 열고 **설정**으로 가서 **워크플로 내보내기**를 클릭하세요. 여러 워크플로를 한 파일에 담으려면 **워크플로** 목록에서 선택하고 **JSON 내보내기**를 고르세요.
@tab 가져오기
**워크플로** 목록에서 **Import JSON**을 클릭하고, 아무 OneUptime 프로젝트에서나 내보낸 파일을 고르세요. 프로젝트에 이미 있는 이름의 워크플로는 이름 뒤에 "(Imported)"가 붙어서 가져와집니다.
:::

파일에는 워크플로의 이름, 설명, 활성화 상태, 그래프가 들어 있습니다. 다음은 일부러 넣지 않습니다.

- **웹훅 비밀 키.** 워크플로를 만들 때 새로 생성되므로, 가져온 워크플로의 웹훅 URL은 다릅니다. 새 워크플로의 웹훅 트리거에서 복사하세요. 원래 것을 호출하던 모든 것을 새로 가리키게 해야 합니다.
- **수신 이메일 주소.** Incoming Email 트리거가 있는 가져온 워크플로는 자체 주소를 받습니다. 새 워크플로의 트리거에서 복사하세요. 원래 것으로 메일을 보내던 모든 것에 새 주소를 알려야 합니다.
- **전역 변수.** `{{global.variables.MY_SECRET}}` 를 읽는 블록은 그 참조를 유지하지만, 값은 파일에 없습니다. 가져온 워크플로를 실행하기 전에 대상 프로젝트에 변수를 만드세요.
- **소유자와 레이블.** 직접 만든 것과 똑같이, 프로젝트 자체의 레이블 및 소유자 규칙이 가져온 워크플로에 적용됩니다.

가져온 워크플로는 내보낸 곳에서 활성화되어 있었더라도 항상 **비활성화**된 상태로 만들어집니다. 그래프가 대상 프로젝트에 없는 모니터, 온콜 정책, 다른 워크플로를 가리킬 수 있기 때문입니다. 검토하고, 활성화하고, **워크플로 실행**으로 테스트한 다음 켜 두세요. 워크플로 복제도 같은 방식으로 동작하므로, 편집하기 전에 사본이 원본과 나란히 발생하기 시작하는 일은 없습니다.

그래프는 그대로 옮겨지므로 블록에 직접 입력한 것도 함께 옮겨집니다. 이것이 자격 증명을 시크릿 변수에 두어야 하는 실질적인 이유입니다. 토큰을 하드코딩한 워크플로를 내보내면, 파일을 받는 사람에게 그 토큰을 넘기는 셈입니다.

## 웹훅 보안

웹훅 트리거는 고유한 URL을 줍니다. URL을 아는 사람은 누구나 호출할 수 있습니다. 실수로 또는 원치 않게 호출되는 것을 막으려면:

- URL을 비밀번호처럼 다루세요. 공개적으로 공유하거나 공개 저장소에 커밋하지 마세요. 웹훅 트리거는 **표시**를 클릭하기 전까지 URL의 비밀 키를 가리고, **URL 복사**는 URL을 보여 주지 않고 복사합니다.
- URL이 유출되면 **빌더**에서 웹훅 트리거를 클릭하고 **URL 재설정**을 클릭하세요. 워크플로에 새 URL이 생기고 이전 URL은 즉시 작동을 멈춥니다.
- 트리거가 URL이 워크플로의 ID로 끝난다고 표시하면 재설정하세요. 웹훅 URL에 자체 비밀 키가 생기기 전에 만든 워크플로는 대신 워크플로의 ID를 쓰며, 워크플로를 열 수 있는 사람은 누구나 그것을 볼 수 있습니다.
- 민감한 워크플로라면 호출하는 시스템이 공유 토큰을 헤더(`X-Webhook-Token` 등)로 보내게 하고, 중요한 일을 하기 전에 **If / Else** 블록으로 확인하세요. 기대하는 토큰은 시크릿 변수로 저장합니다.
- 매우 민감한 워크플로라면 공개 웹훅보다 OneUptime 이벤트 트리거와 수동 가져오기 단계를 선택하세요.

워크플로를 편집할 수 있는 사람 — **Project Owner**, **Project Admin**, **Workflow Admin** 또는 **Edit Workflow** — 만 웹훅 URL을 보거나 재설정할 수 있습니다. URL을 가진 사람은 로그인하지 않고 어디서든 워크플로를 시작할 수 있으므로, 그 밖의 사람에게는 누구에게 요청하면 되는지 알려 주는 메모가 표시됩니다. **빌더**에서 워크플로를 수동으로 실행하는 **Workflow Member**도 마찬가지입니다.

## 수신 이메일 보안

Incoming Email 트리거는 워크플로에 자체 주소를 주며, 주소를 아는 사람은 누구나 그곳으로 이메일을 보낼 수 있습니다. `@` 앞부분은 워크플로의 비밀 키이므로 주소를 비밀번호처럼 다루세요.

- 공개하거나 공개 저장소에 두지 마세요. 트리거는 **표시**를 클릭하기 전까지 키를 가리고, **주소 복사**는 주소를 보여 주지 않고 복사합니다.
- 주소가 유출되면 **빌더**에서 Incoming Email 트리거를 클릭하고 **주소 재설정**을 클릭하세요. 워크플로에 새 주소가 생기고, 그 뒤로 이전 주소로 온 이메일은 무시됩니다.
- 누구나 이메일에 아무 보낸 사람이나 넣을 수 있으므로, **From**은 누가 보냈는지 증명하지 않습니다. 워크플로가 중요한 일을 하기 전에 진짜 보낸 사람만 아는 것 — 제목이나 헤더에 있는 토큰 — 을 **If / Else** 블록으로 확인하세요. 기대하는 토큰은 시크릿 변수로 저장합니다.
- 실행이 받는 모든 것 — **To**, **CC**, 헤더, 본문 — 에서 키가 가려집니다. 실행의 로그는 워크플로의 실행을 읽을 수 있는 모든 사람에게 보이기 때문입니다.

워크플로를 편집할 수 있는 사람 — **Project Owner**, **Project Admin**, **Workflow Admin** 또는 **Edit Workflow** — 만 주소를 보거나 재설정할 수 있습니다. 그 밖의 사람에게는 누구에게 요청하면 되는지 알려 주는 메모가 표시됩니다.

## 아웃바운드 네트워크 접근

API 블록과 그 밖의 HTTP 블록은 OneUptime에서 요청을 보내고, IRC 블록은 OneUptime에서 IRC 서버의 포트로 연결합니다. 셀프 호스팅한다면 설치가 호출하는 서비스에 연결할 수 있는지 확인하세요. OneUptime Cloud를 쓴다면 아웃바운드 IP 범위가 [IP 주소](/docs/configuration/ip-addresses)에 나와 있으므로 상대편에서 허용할 수 있습니다.

블록이 연결할 수 있는 주소는 블록에 따라 다릅니다.

| 블록                                                           | 루프백, 링크 로컬, 클라우드 메타데이터                                       | 사설 네트워크 주소                                                                                                                                |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **API** 블록과 **Run Custom JavaScript** 요청                  | 거부. 단, 정확한 호스트가 `PRIVATE_NETWORK_WEBHOOK_ALLOWLIST` 에 있으면 허용 | 거부. 단, 셀프 호스팅 관리자가 `ALLOW_PRIVATE_NETWORK_WEBHOOKS` 또는 `PRIVATE_NETWORK_WEBHOOK_ALLOWLIST` 로 허용하면 허용                       |
| **Send Email**, **IRC**, OAuth 2.0 토큰 URL                    | 거부                                                                         | OneUptime Cloud에서는 거부. 셀프 호스팅 설치에서는 `DATA_SOURCE_BLOCK_PRIVATE_ADDRESSES` 가 `true` 가 아니면 허용                                |
| Slack, Microsoft Teams, Discord, Telegram                      | 거부                                                                         | 거부. 각각 자기 서비스의 주소로만 보냅니다                                                                                                        |

셀프 호스팅 관리자가 이를 여는 방법은 [사설 네트워크 접근](/docs/self-hosted/private-network-access)을 참조하세요.

## AI 구성 요소

**Generate Text with AI**는 LLM에 요청 하나를 보냅니다. 프로젝트의 기본 LLM 공급자, 또는 프로젝트에 없으면 설치의 전역 공급자입니다. 공급자는 **프로젝트 설정 → AI → LLM 공급자**에서 설정하고, 공급자의 API 키나 자체 엔드포인트를 워크플로에 넣지 마세요.

공급자가 받는 것, 그리고 모델이 그것으로 할 수 있는 일:

- **블록에 넣은 것만.** OneUptime은 고정된 안전 지침을 보낸 다음, 참조가 채워진 블록의 **System Instructions**, **Prompt**, **Context**를 보냅니다. **Context**는 표시 뒤에 마지막으로 오며, 안전 지침은 모델에게 표시 뒤의 모든 것이 지침처럼 보이는 텍스트라도 신뢰할 수 없는 데이터라고 알려 줍니다.
- **그 밖에는 아무것도.** 트리거의 데이터, 워크플로의 기록, 다른 블록의 출력, 프로젝트 레코드, 원격 측정, 시크릿은 절대 첨부되지 않습니다. 세 설정 중 하나에서 참조할 때만 OneUptime 밖으로 나갑니다.
- **텍스트만, 도구는 없음.** 모델은 OneUptime을 조회하거나, HTTP 요청을 하거나, 데이터를 바꿀 수 없습니다. 공급자의 추가 매개변수는 생성만 조정하는 허용 목록의 필드만 통과시킵니다. 메시지를 바꾸거나, 도구, 웹 검색 또는 다른 데이터 원본을 추가하거나, 텍스트가 아닌 것이나 여러 답을 요청하거나, 스트리밍하거나, 공급자가 요청을 보관하게 하거나, 블록의 출력 한도를 높일 수 없습니다. OneUptime이 모르는 필드는 버려집니다.
- **모델은 관리자가 고릅니다.** 생성이 오프라인으로 유지되어야 한다면, 공급자 쪽에서 스스로 아무것도 가져오지 않는 모델을 고르세요.

로그에 남는 것:

- 실행의 로그는 블록의 **System Instructions**, **Prompt**, **Context**, **Response**를 가립니다. 이후 블록은 실행 중에 이것들을 계속 쓸 수 있으며, 그중 하나를 넣은 블록은 자기 규칙대로 기록하므로, 넣는 것은 그것을 보이기로 선택하는 것입니다.
- 공급자, 모델, 토큰 수, **LLM Log ID**, 안전한 오류 메시지는 운영과 청구를 위해 계속 보입니다. 공급자의 원본 오류는 요청 내용을 되풀이할 수 있으므로 어떤 로그에도 남기지 않습니다.
- 각 호출은 **프로젝트 설정 → AI → AI 로그**에 공급자, 모델, 상태, 토큰, 비용, 청구와 함께 나열되며, 프롬프트, 응답, 원본 오류는 들어 있지 않습니다.

필요한 것과 비용:

- **프로젝트 설정 → AI → AI Features**에서 **AI 활성화**가 켜져 있어야 합니다. OneUptime Cloud에서는 프로젝트에 Growth 플랜 이상과 결제된 구독도 필요합니다. 청구가 없는 셀프 호스팅 설치에는 플랜 조건이 없습니다.
- 비용이 드는 전역 공급자를 통한 호출은 프로젝트의 AI 크레딧을 씁니다.
- 프로젝트 소유자가 설정한 경우, 모든 호출은 [프로젝트 자체의 일일 AI 한도](/docs/ai/ai-sre#the-projects-own-daily-limits)에 포함됩니다. 한도에 도달하면 블록은 UTC 자정까지 모델에 연결하지 않고 **Error**를 따릅니다.

| 한도                                                          | 값                                                                       |
| ------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **System Instructions**, **Prompt**, **Context** 합계          | 50,000자                                                                 |
| **Temperature**                                               | `0` 부터 `1` 까지                                                        |
| **Maximum Output Tokens**                                     | `1` 부터 `4096` 까지, 기본값 `1024`                                      |
| 요청 하나                                                     | 한 번 시도, 최대 60초                                                    |
| 동시 호출                                                     | 프로젝트당 3개. 그 이상은 **Error**를 따르며, 이후 실행에서 다시 시도할 수 있습니다. |

검증, 설정, 접근, 한도, 크레딧, 동시성, 공급자, 시간 초과 실패는 모두 **Error** 경로를 따르며, 이유는 **Error**에 담깁니다. 워크플로를 운영에 넣기 전에 그 경로를 연결하세요.

> [!WARNING]
> 참조하는 모든 값은 공급자에게 보내는 데이터입니다. 공급자가 받도록 승인되지 않았다면 시크릿 변수를 프롬프트나 컨텍스트에 넣지 마세요. Ollama 같은 셀프 호스팅 로컬 공급자는 요청을 자체 인프라 안에 둡니다. 호스팅되는 공급자는 자체 데이터 처리 약관에 따라 요청을 받습니다.

## 권한

워크플로는 프로젝트의 역할 기반 접근 제어를 따릅니다. 워크플로 역할은 세 가지입니다.

- **Workflow Admin** — 워크플로를 만듭니다. 워크플로를 생성, 변경, 실행, 삭제하고, 워크플로가 쓰는 변수를 관리합니다.
- **Workflow Member** — 워크플로를 사용합니다. 워크플로와 그 실행을 열고, **워크플로 실행**으로 워크플로를 수동으로 실행합니다. 멤버는 워크플로를 생성, 변경, 삭제하거나 단계 하나만 따로 실행할 수 없습니다.
- **Workflow Viewer** — 워크플로와 그 실행을 읽습니다.

**Project Owner**와 **Project Admin**은 Workflow Admin이 할 수 있는 모든 일을 할 수 있습니다. **Project Member**는 워크플로를 생성하고 삭제할 수 있지만, 변경하거나 실행할 수는 없습니다.

정확히 한 가지만 필요한 팀이나 API 키를 위한 개별 권한:

- **Create / Read / Edit / Delete Workflow** — 워크플로 자체에 대한 기본 권한입니다. 워크플로를 바꾸는 것은, 켜고 끄거나 보관하는 것을 포함해 **Edit Workflow**가 필요합니다. **Delete Workflow**는 삭제만 합니다.
- **Edit Workflow** — **Run just this step**으로 단계 하나를 따로 실행하거나, 워크플로의 웹훅 URL과 수신 이메일 주소를 보거나 재설정할 때도 필요합니다. 워크플로 전체를 수동으로 실행하려면 **Edit Workflow**, **Workflow Admin** 또는 **Workflow Member**가 필요합니다.
- **Read Workflow Log** — 실행을 보는 데 필요합니다.
- **Create / Read / Edit / Delete Workflow Variables** — 전역 변수와 워크플로 변수 관리.

수동 실행은 열 수 있는 워크플로에만 닿습니다. 일부 레이블이나 팀이 소유한 워크플로로 제한된 역할은 그것들만 실행합니다. 워크플로를 실행할 수 없는 사람에게는 **워크플로 실행**이 흐리게 표시되고, 도구 설명에 이유가 나옵니다.

자동화를 만드는 사람에게는 **Workflow Admin**을, 시작만 하는 사람에게는 **Workflow Member**를 주세요. 변수 편집 권한은 프로젝트의 시크릿을 관리하는 사람에게만 주세요. 역할을 부여하는 방법은 [사용자, 팀 및 권한](/docs/permissions/index)을 참조하세요.

## 워크플로 단계가 할 수 있는 일

OneUptime 레코드를 읽고 바꾸는 단계 — Find, Create, Update, Delete 구성 요소와 On Create, On Update, On Delete 트리거 — 는 워크플로 프로젝트의 **Project Admin**으로 동작합니다. 누가 워크플로를 만들었든, 단계는 Project Admin이 대시보드와 API에서 받는 것과 같은 검사를 받습니다.

- **워크플로 자체의 프로젝트만.** 단계는 워크플로가 속한 프로젝트의 레코드만 읽고 쓰며 다른 프로젝트는 건드리지 않고, Update는 레코드를 다른 프로젝트로 옮기지 않습니다.
- **Project Admin에게 허용된 것만.** 단계는 Project Admin 자신이 가진 팀 및 API 키 권한만 부여할 수 있으므로, **Project Owner**, 청구, 프로젝트 삭제 권한을 나눠 주거나, 소유자 팀처럼 Project Admin을 넘어서는 권한을 가진 팀에 누군가를 추가할 수 없습니다. 단계는 프로브나 AI 에이전트를 누가 만들었는지 읽을 수 없으며, 그것은 프로젝트 소유자만 봅니다.
- **Runbook 자격 증명 읽기는 제외.** Project Admin은 Runbook 자격 증명을 읽을 수 있지만, 그 권한이 단계에 빌려지지는 않습니다. 변경에 그 읽기가 필요한 경우 — OneUptime AI가 묻지 않고 명령을 실행하게 하기, Runner에서 **AI 해결 명령 실행**을 켜기, OneUptime AI의 명령을 실행하는 Runner에 SSH 자격 증명을 지정하기, Runbook의 단계처럼 Runbook 자격 증명을 지정하기 — 에는 대신 워크플로의 단계를 마지막으로 저장한 사람을 확인하며, 그 사람이 Runbook 자격 증명을 읽을 수 없다면(**Read Runbook Credential**, 또는 Project Owner나 Project Admin) 단계가 거부됩니다. OneUptime은 누군가 워크플로를 만들 때와 누군가 단계를 저장할 때마다 그 사람을 기록합니다. 워크플로 이름을 바꾸거나, 레이블을 바꾸거나, 켜고 끄는 것은 마지막으로 단계를 저장한 사람을 바꾸지 않습니다. API 키로 단계를 저장하면 아무도 기록되지 않으므로, 사람이 단계를 저장할 때까지 워크플로의 단계는 이런 변경을 할 수 없습니다.
- **플랜에 포함된 것만.** OneUptime Cloud에서는 플랜에 포함되지 않은 것을 만들거나 바꾸는 단계가 대시보드와 마찬가지로 필요한 플랜과 함께 거부됩니다. 청구가 없는 셀프 호스팅 설치에는 플랜 한도가 없습니다.
- **OneUptime이 직접 관리하는 것은 제외.** 다음은 워크플로를 포함해 모두에게 거부됩니다.
  - 피드 항목 편집 또는 삭제(인시던트, 경고, 에피소드, 모니터, 온콜 정책, 예정된 유지보수 피드)
  - 알림 로그 쓰기(SMS, 통화, 이메일, WhatsApp, Telegram, 푸시, 웹훅, 워크스페이스 메시지 로그)
  - 일이 일어나면서 OneUptime이 설정하는 값: 사용자 지정 도메인의 CNAME 검증 여부, 팀의 보호 스위치(**Is Team Editable**, **Is Team Deleteable**, **Is Permissions Editable**, **Should Have At Least One Member**), 어떤 인시던트 역할이 기본 역할인지와 삭제할 수 있는지, 소유자나 멤버에게 알림이 갔는지, 알림 시각과 횟수, 일정에서 지금과 다음 온콜인 사람, 온콜 실행의 진행 상황, SLO의 현재 소진율과 오류 예산, 인시던트나 유지보수로 일시 중지된 모니터, 상태 페이지 비공개 사용자의 비밀번호 재설정 토큰과 마지막 로그인, 서비스가 자신에 대해 보고하는 사실(버전, 런타임, 클라우드), 탐지 규칙이나 위협 피드의 마지막 실행
  - `createdIncidentTemplateId` 를 **Create One Incident**에 보내 템플릿으로 인시던트를 선언하기 — 대신 단계의 **Incident Template** 설정에서 템플릿을 고르세요. 그러면 단계가 Project Admin으로서 그 템플릿으로 인시던트를 선언하고 템플릿을 기록합니다
  - 레코드를 만든 뒤 그 레코드가 어느 레코드에 속하는지 바꾸기. 예를 들어 소유자 행이 대상으로 하는 모니터나 메모가 달린 인시던트입니다
- **누구도 아닌 이로서.** 워크플로가 만든 레코드에는 생성자가 없으며, 감사 로그는 변경한 주체로 당시 이름의 워크플로를 기록합니다.

검사가 단계를 거부하면, 단계는 거부된 변경을 하지 않고 **Error** 출력을 따르며, 실행의 로그에는 단계와 이유가 알기 쉬운 말로 나옵니다. 예: *"Create One Team Permission" was refused. Workflow steps can do only what a Project Admin of this project can do: …*. 워크플로의 [실행 기록](/docs/workflows/runs-and-logs)에서 읽으세요. Create Many 단계는 레코드를 하나씩 만들며 처음 거부된 것에서 멈춥니다. 그 전에 만든 레코드는 남습니다.

다른 시스템과 대화하는 단계 — API, Email, Slack, Microsoft Teams, Discord, Telegram, IRC, Custom Code, Generate Text with AI — 는 OneUptime 레코드를 읽거나 바꾸지 않으므로, 이 중 어느 것도 이들에게는 바뀌는 것이 없습니다.

## 플랜 한도

OneUptime Cloud에서 워크플로를 쓰려면 Growth 플랜 이상이 필요하며, 각 플랜은 임의의 30일 동안 실행할 수 있는 횟수를 허용합니다.

| 플랜       | 지난 30일 동안의 실행 횟수 |
| ---------- | -------------------------- |
| Growth     | 500                        |
| Scale      | 2,000                      |
| Enterprise | 사실상 제한 없음           |

기간은 이동합니다. 수동이든 트리거든 프로젝트가 기록한 모든 실행이 30일 동안 집계됩니다. Growth와 Scale 플랜에서는 **워크플로** 페이지에 프로젝트가 사용한 횟수를 보여 주는 **워크플로 실행** 카드가 표시됩니다. 한도에 도달하면 새 실행은 **Execution Exceeded Current Plan** 상태로 기록되고 수행되지 않으며, 구독 요금이 미납된 동안에도 마찬가지입니다. 청구가 없는 셀프 호스팅 설치에는 한도가 없습니다.

## 실행이 걸릴 수 있는 최대 시간

| 한도                                                              | 기본값         | 셀프 호스팅 설정                |
| ----------------------------------------------------------------- | -------------- | ------------------------------- |
| 실행(시작 시점부터, 또는 **Sleep** 뒤에 깨어난 시점부터)          | 2분            | `WORKFLOW_TIMEOUT_IN_MS`        |
| **Run Custom JavaScript** 블록                                    | 5초            | `WORKFLOW_SCRIPT_TIMEOUT_IN_MS` |
| **Sleep** 블록                                                    | 최대 30일      | —                               |

실행기는 각 블록 전후로 마감 시간을 확인하고, 마감을 넘긴 실행은 제어가 돌아오는 즉시 **Timeout**으로 표시합니다. 블록을 중간에 끊을 수는 없으므로, 네트워크를 기다리는 블록에는 자체 시간 한도가 있습니다. Generate Text with AI 요청은 최대 60초, OAuth 2.0 토큰 요청은 20초 후에 포기합니다. **Sleep** 블록에서 기다리는 시간은 실행 시간에 포함되지 않습니다. 실행은 옆으로 치워졌다가 깨어날 때 새로 2분을 받습니다.

## 다른 워크플로 호출 제한

**Execute Workflow** 구성 요소로 한 워크플로가 다른 워크플로를 시작할 수 있습니다. 워크플로 A가 B를 시작하고 B가 다시 A를 시작하는 루프를 막기 위해, 서로를 시작하는 워크플로의 사슬은 이미 사슬에 있는 워크플로로 되돌아가거나 10개 워크플로보다 깊어지면 거부됩니다. 그러면 **Execute Workflow** 블록은 **Error** 출력을 따르고, 오류에 사슬이 표시됩니다.

정말로 긴 사슬이 필요하다면(실행마다 항목 하나를 처리하는 작업 등), 보통은 **Run Custom JavaScript**로 단일 워크플로 안에서 반복하는 편이 더 간단합니다.

## 워크플로가 적합하지 않은 경우

다른 것을 써야 하는 몇 가지 경우:

- **무거운 연산이나 큰 데이터 세트** — 워크플로는 가벼운 연결 작업을 위한 것이지, 대량 계산용이 아닙니다. 무거운 작업은 자체 인프라에서 실행하고 워크플로가 그것을 시작하게 하세요.
- **오래 걸리는 능동적 연산** — 실행에는 기본적으로 2분이 주어집니다. "A를 하고, 두 시간 기다렸다가, B를 한다" 같은 수동적인 대기에는 **Sleep** 구성 요소를 쓰세요. 실행을 옆으로 치워 두었다가 작업자를 차지하지 않고 나중에 재개합니다.
- **사람이 참여하는 단계별 인시던트 대응** — 그것이 [Runbook](/docs/runbooks/index)의 역할입니다. 워크플로는 사람의 개입 없는 자동화를 위한 것입니다.
