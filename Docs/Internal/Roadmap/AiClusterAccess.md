# AI cluster access — OneUptime AI with a terminal on the cluster

**Status:** shipped for Kubernetes (investigation + remediation). Hosts, Docker, Podman and the other resource kinds are the next epic and reuse every layer below except the executor.

## The problem this solves

An AI investigation could only read the telemetry the agents ship. For a Kubernetes signal that is frequently not enough: "pods stuck in Pending" is diagnosed by describing the pod and reading its events, which no metric carries. The investigation on the alert that started this work finished "without a report" for exactly that reason.

Remediation existed (the `AutoRemediationRule` + `RemediationExecution` lane: policy-checked Bash/SSH commands on opted-in Runners) but reaching a cluster took five steps: create a Runner, install it, create a Kubernetes credential, assign it, write a rule that composes commands. Customers got lost.

## What shipped

One helm flag gives OneUptime AI kubectl on a cluster; the cluster's **AI** page is the single place that says what AI may do and what is missing.

```
helm repo update
helm upgrade kubernetes-agent oneuptime/kubernetes-agent -n oneuptime-agent --reuse-values \
  --set aiAccess.enabled=true \
  [--set aiAccess.remediation.enabled=true [--set "aiAccess.remediation.namespaces={web,api}"]]
```

`helm repo update` is part of the command, not a nicety: an old local index resolves the chart the release was installed from, whose schema rejects `aiAccess.*`. Published chart versions follow the OneUptime version (`release.yml` packages the chart with `--version`/`--app-version` set to it), so customer-facing copy never names `Chart.yaml`'s own version. `kubernetes-agent` in `oneuptime-agent` is what the dashboard's install instructions use.

## Trust model, in one paragraph

Three independent checks keep an investigation read-only: the toolkit refuses non-Read tiers, the enqueue chokepoint refuses non-Read for the investigation origin, and the Runner refuses non-Read for that origin before spawning. Remediation is bounded by three layers that do different jobs. RBAC bounds **where** the in-cluster Runner may write: patch/update on Deployments, StatefulSets, DaemonSets, ReplicaSets and their scale subresource, Jobs, CronJobs, Pods and HPAs, create on Jobs and HPAs, and delete on Pods and Jobs only, in the namespaces `aiAccess.remediation.namespaces` lists (cluster-wide when it is empty), plus node operations cluster-wide; never Secrets, exec/attach/port-forward, ServiceAccount tokens, impersonation, CRDs or RBAC writes. RBAC does **not** bound what a write may do: patch/update on workloads, pods and CronJobs (and create on Jobs) in a namespace is equivalent to running any image as any ServiceAccount there and reading its Secrets, and `apply`/`edit`/`replace`, `--all-namespaces` writes and `delete --all` are ordinary patch/update/delete calls to it. The policy bounds that (tiers, the deny list — pod-template security patches, `set serviceaccount`, `create … --image`, non-JSON patch bodies, RBAC/CRD/APIService/admission writes included — the token-wise allowlist, and never an unattended write in kube-system / kube-public / kube-node-lease, drain or taint), though it still allows `set image` as a riskier change, and the Runner re-checks it, refuses writes when `ONEUPTIME_KUBECTL_ALLOW_WRITES=false`, outside `ONEUPTIME_KUBECTL_WRITE_NAMESPACES`, and in its own namespace. RBAC cannot exclude namespaces from a ClusterRoleBinding, so on the cluster-wide default the protected and own-namespace lines are held by the policy and the Runner alone; the docs say so. The model never sees a credential: an in-cluster Runner uses its ServiceAccount (and is never handed a credential or used as a Bash/SSH host), an external Runner gets the credential resolved at claim time and written to a private temp file for the life of one command.

## Next epics

- **Hosts / Docker / Podman / other resources.** The same shape: a per-resource AI page, a readiness status with gaps, a Runner binding, and a resource-specific executor with a tiered policy (`systemctl`/`journalctl`/`docker`/`podman` reads; restarts as SafeWrite). The infrastructure agents are push-only today; the Runner (or a Runner mode inside the agent image) is the control channel.
- **Plan preview in the investigation panel.** Today the remediation card sits below the investigation. A single timeline (investigating → commands → root cause → fix → approval → verification) is the next UI step.
- **Per-namespace scoping beyond the chart.** The chart already binds write RBAC per namespace (`aiAccess.remediation.namespaces`) and tells the Runner the list, and whether node operations are allowed (`ONEUPTIME_KUBECTL_ALLOW_NODE_OPERATIONS`). Next: show that scope on the cluster's AI page from the Runner's posture (`writeNamespaces`, `podNamespace`, `allowNodeOperations`, which registration should carry as well as the heartbeat), have the remediation toolkit refuse an out-of-scope namespace or a node operation the Runner would refuse before a plan is composed, and let teams that own part of a cluster scope investigations (read access) the same way.
